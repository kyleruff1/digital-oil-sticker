## Summary

The MVP is now a **browser application**, not a native iOS/Android app. The product's core value is unchanged and is the part of the plan that survives intact: **vendoring** automobile and oil/filter data — acquiring it, clearing redistribution rights, normalizing it into an auditable catalog with provenance, and serving it. What changed is the delivery vehicle underneath that catalog. Phoenix LiveView now runs **hosted on Fly.io** behind `digitaloilsticker.com`; Netlify (already paid, team `cDiscourse`) keeps only static marketing, support, privacy, and attribution content. All personal data — garage, service history, odometer readings, usage samples, reminder intent — lives in **anonymous browser storage** (IndexedDB, with `localStorage` only for small preferences); there are no accounts and no server-side personal records, and versioned export/import is the sole portability escape hatch. Native mobile (Mob `0.7.20`) is **deferred, not deleted**: Mob is pre-1.0, five distinct Windows-host defects surfaced in a single session, upstream has no Windows CI, and the iOS half is unreachable without a Mac/Xcode, so `DOS-M00-003`'s go/no-go cannot complete as written; the physical-device evidence captured on a Motorola Razr Ultra 2025 is retained for the eventual native re-entry.

Of the 77 issues, **18 survive unchanged, 54 must be re-scoped, 5 are deferred to the native re-entry, and 0 are obsolete**. Nothing is deleted. The re-scope count is high because the pivot changes *where code runs* almost everywhere — server vs. device, browser storage vs. SQLite, deploy vs. store release — while leaving *what the product claims* largely intact. Almost every M03 issue survives untouched, which is the point: the data work was never platform-bound. The gap analysis at the end identifies the work the browser MVP needs that **no existing issue covers at all**, and proposes one new milestone (**M09 — Hosted browser platform and anonymous client storage**) with ten concrete issues.

## Architectural consequences that must be stated honestly

These are the places where the pivot creates a genuinely new problem rather than a relabeling. They are the source of most of the gap issues below.

### 1. LiveView holds state on the server; the owner chose client-side storage. This requires an explicit hydration protocol.

Phoenix LiveView keeps UI state in server-side socket assigns. The owner's decision puts the authoritative personal record in the browser. These are not compatible by default and the seam must be specified, not hand-waved:

- **Mount is unhydrated.** The LiveView `mount/3` has *no* user data. It renders a determinate pre-hydration state — never a fake garage, never a "you have no vehicles" empty state that could be wrong.
- **Hydration.** A JS hook (`phx-hook`) opens IndexedDB, reads a versioned snapshot, and `pushEvent`s it to the server. The server **validates** the payload (it is untrusted client input, even though the client is the user), coerces it into domain structs, and places it in `assigns` **for the socket lifetime only**. It is never written to a server table, never logged, and dies with the socket.
- **Mutation is a round trip.** Every write is `pushEvent` → server computes the new domain state → server pushes a write instruction to the hook → hook commits the IndexedDB transaction → hook acknowledges. **The UI must not present a mutation as committed until the hook acknowledges the write.** Optimistic rendering is permitted only if a failed commit visibly reverts.
- **Reconnect re-hydrates.** A LiveView reconnect (network blip, server redeploy, laptop sleep) discards assigns. The hook must re-hydrate on every `reconnected` event, and the server must never assume assigns survived.
- **Multi-tab.** Two tabs are two sockets over one shared IndexedDB. The MVP adopts a single logical writer with a version check on commit (`BroadcastChannel` notification + monotonic record version; a stale-version commit is rejected and the losing tab re-hydrates). "Last write wins silently" is not acceptable for service history.
- **Storage eviction, quota, and private browsing are first-class states, not error toasts.** iOS Safari's ITP evicts unused site data after roughly seven days of no visits. Firefox and Safari private windows expose a storage API that then throws or discards. Chrome evicts under pressure unless `navigator.storage.persist()` is granted. The app requests persistent storage, reports the quota estimate in Settings, and, when storage is blocked or unavailable, says so plainly and offers read-only browsing of the catalog rather than pretending to save.
- **When the browser clears storage, the data is gone.** There is no backup. The existing no-implied-backup invariant (`DOS-M00-001` FR-10 / INV-5) still binds: no interface may imply a local profile is backed up or recoverable. Under the pivot this rule gets *harder*, not easier, because a hosted URL naturally reads to users as "my data is on their server." First-run copy, Settings, and export must actively contradict that assumption.

### 2. Reminders: OS local notifications are unavailable. The MVP ships in-app due state only.

`mob_notify` does not exist in a browser. **The MVP delivers due/overdue state in the app only** — the dashboard shows it, the vehicle card shows it, and that is the whole promise. Nothing is scheduled, nothing arrives when the app is closed, and the UI must not imply otherwise.

**Web Push is an explicitly deferred post-MVP decision, not a plan.** It requires a service worker, a VAPID key pair, and a browser-vendor push service (FCM/APNs/Mozilla autopush) as an intermediary. That means (a) a persistent server-held subscription endpoint per browser — which is a remote record tied to a person's device, in direct tension with the "no server-side personal record" stance — and (b) a third-party push service in the delivery path. It is tracked as a go/no-go spike (`DOS-M09-010`), and the tension is the decision, not a footnote to it.

### 3. Offline: the bundled-catalog-at-first-launch promise cannot hold and is withdrawn.

The old invariant — "the app bundle includes a usable baseline catalog, so first launch works in airplane mode with no provisioning download" — is a property of a signed native package. A plain browser app has no bundle. **It is replaced by: the catalog is queried from the server; the app requires connectivity to search vehicles and resolve requirements; the user's own records remain in the browser and remain readable, but the catalog does not.** This must be stated in the constitution rewrite (`DOS-M00-001`) as a withdrawn promise with a dated supersession, not quietly edited out.

Optional service-worker/PWA offline — caching the app shell and a slice of the catalog — is a **separate future decision** (`DOS-M09-010`) and is **not promised by the MVP**. No marketing copy, no store-style listing, and no in-app text may describe the MVP as "offline-first" or "works without a connection."

## Gaps: work the browser MVP needs that no existing issue covers

The 77 issues were written for a signed native app with a bundled database and no server. The following work has **no owner anywhere in the current roadmap** — it is not a re-scope of anything, because nothing analogous existed:

1. **Client-side storage as a designed subsystem.** There is no issue for an IndexedDB schema, its version line, or its migration path. `DOS-M04-003`/`DOS-M04-007` re-scope toward it but presuppose SQL and Ecto; the browser story needs its own schema and upgrade contract because IndexedDB has no rollback, no constraints, and no cross-store foreign keys.
2. **The hydration protocol.** Nothing in the roadmap describes moving state between a JS hook and socket assigns. This is the single highest-risk new component and currently has zero coverage.
3. **Pre-hydration, storage-denied, quota, and eviction UX.** `DOS-M02-003` covers first-run for a device that always has storage; it has no concept of a browser that refuses to store, evicts after seven days, or is in a private window.
4. **A server-side catalog query layer.** Every search and resolve issue assumes an in-process local read. A hosted app needs a read-only query surface with a latency budget, caching, and rate limiting — and one that takes no personal parameters, so queries cannot become a de facto activity log.
5. **Fly.io deployment.** No issue covers a Dockerfile, `fly.toml`, regions, scaling, health checks, secrets, release IDs, or rollback. `DOS-M05-006` and `DOS-M07-007` re-scope toward it but were written about app stores.
6. **Custom domain and TLS.** The owner owns `digitaloilsticker.com` and `.net`; nothing assigns DNS, certificates, HSTS, canonical redirects, or the Fly-versus-Netlify content boundary.
7. **Internet-facing security hardening.** `DOS-M07-001` was written for an app that binds to `127.0.0.1`. A public host needs CSP, security headers, origin/CSRF checks on the socket, rate limiting, and a *tested* guarantee that no personal data is persisted or logged server-side.
8. **A browser support matrix and storage-behavior conformance suite.** The device matrix has no browser equivalent, and the storage behaviors that will actually break users (ITP eviction, private mode, quota) are untested by anything today.
9. **The PWA/Web Push decision.** Both were previously out of scope by fiat. Under the pivot they are open questions that need a written, dated go/no-go rather than drift.

### Proposed new milestone

**M09 — Hosted browser platform and anonymous client storage**
*Establish the hosted Phoenix/Fly runtime and the anonymous client-storage subsystem that the browser MVP depends on, including the hydration protocol between them.*

**Where it sits in the dependency order.** M09 executes **after M01 (engineering foundation) and before M02, M04, and M05** — the UX contract cannot be frozen without knowing the hydration and empty-state model, and the persistence and MVP milestones build directly on the storage adapter and query layer. Concretely: M09 is `blocked_by` M00-000 and M01-000, and becomes a blocker of M02-000, M04-000, and M05-000; `DOS-M03-*` remains independent and can run in parallel throughout.

**On the identifier.** `roadmap.yml` orders by the `sequence` field, not by milestone number, and `ROADMAP_LEDGER.md` treats roadmap IDs as stable and never renumbered. M09 therefore takes **sequence band 250–299** (between M01's 200s and M02's 300s) so it executes third while keeping every existing ID untouched. Renumbering the existing 77 to make ID order match execution order would break the ledger contract and is not proposed.

**Note on non-duplication.** The browser-MVP architecture ADR is *not* a new issue — it is the re-scoped `DOS-M00-002` (#3), which remains the ratification gate. M09 issues implement what that ADR ratifies.
