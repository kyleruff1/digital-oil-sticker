# Release ledger

One row per production release of the Fly.io app `digital-oil-sticker`. The ledger exists to answer three questions that nothing else in this repository can answer:

1. **What do I roll back to?** Not "the previous commit" — the previous *release*, by the number and image reference the platform will actually accept.
2. **Which data did that release serve?** The catalog is a build artifact produced by a data pipeline, not a file in the source tree. The commit does not tell you which automotive facts a user saw.
3. **What was checked before we called it good?** A deploy that reported success is not a deploy that was verified.

**What this file is not.** It is not a record of anything belonging to a user. Under [ADR-0004](../architecture/ADR-0004-browser-first-client-and-hosting.md) §3–§4 and INV-23, the garage, service history, odometer readings, and reminder intent live in the user's browser (IndexedDB), and the server persists no personal row of any kind. A rollback recorded here restores **code and catalog**. It restores nothing belonging to a user, because the server never held anything belonging to a user, and there is no server-side backup of user records — by design, not by omission (INV-5, INV-25). Do not add a field to this schema that would require the server to know something about a person.

Every fact in this document was measured against the live app or the repository on the date given. Where a value was not measured, the document says `unmeasured` or `unrecoverable` and says what would establish it. Vendor documentation is not measurement.

## 1. Entry schema

Every release record carries all thirteen fields. A field with no known value is written `unrecoverable` (the value cannot be established after the fact) or `unmeasured` (it could be measured, but was not) — never left blank and never guessed.

| # | Field | Where it comes from | Why it is in the schema |
| --- | --- | --- | --- |
| 1 | **Date (UTC)** | `flyctl releases --json` → `CreatedAt` | Orders the ledger and anchors an incident to a log window. Local timestamps are useless across a platform that reports UTC; the ledger is UTC throughout. |
| 2 | **Reason** | Human. `workflow_dispatch` input `reason` in [`deploy.yml`](../../.github/workflows/deploy.yml), which makes it `required: true` | The one field no tool can derive. Six months later the question is never "what changed" — `git log` answers that — it is "why did we ship on a Saturday night", and only the person who decided can answer it. |
| 3 | **Commit** | `GET /version` → `git_sha`, baked into the image by the `GIT_SHA` build arg | Identifies the source tree. This is **not** recoverable from an image after the fact: a container carries no record of the tree it was built from unless the build put one there. That is precisely why `DigitalOilSticker.Release` reads a build arg rather than shelling out to `git`, and why `deploy.yml` passes `--build-arg GIT_SHA="${{ github.sha }}"`. |
| 4 | **App version** | `GET /version` → `app_version` | Coarse, but it is what the health endpoint and user-visible surfaces report, so it is the string a user or a log line will quote back at you. |
| 5 | **Catalog `data_version`** | `GET /version` → `catalog_data_version`, read at runtime from the catalog database's own metadata | Says which vintage of automotive data the release served. This is a *product* fact, not a build fact — it changes on a different schedule from the code, and it is the field that matters when someone asks "was the 2019 Silverado interval right in July". Note that this is read from the catalog artifact itself, not from `catalog-manifest.json`, so it cannot disagree with the data actually being queried. |
| 6 | **Catalog payload sha256** | `GET /version` → `catalog_payload_sha256`, computed by streaming the artifact on disk at request time | **The field that proves which data a release served, and the reason the commit alone is insufficient.** The catalog is generated by a pipeline against upstream sources (vPIC, fueleconomy.gov) that move independently of this repository. Two builds of the *same commit* can therefore carry *different* catalogs, and the *same* catalog can ship under many commits. When a user reports a wrong interval, the hash identifies the exact bytes that produced it — nothing else does. It is also load-bearing at runtime: `/ready` re-hashes the artifact on every probe and compares it against the value recorded at boot, so the hash in this ledger is what the machine kept asserting for its whole life, not a claim made once at build time. |
| 7 | **LocalStore schema version** | `GET /version` → `local_store_schema_version` (`DigitalOilSticker.LocalStore.Envelope.current_schema_version/0`) | The envelope contract the deployed server expects the browser to speak. A user who has been away for months arrives holding records written by an older server; a user with two tabs may hold two. When hydration (INV-24) breaks, you need to know which server versions were live when that browser last wrote. This is the only field in the ledger that is about the client side of the boundary, and it is here because the client is where the data is. |
| 8 | **Fly release number** | `flyctl releases --json` → `Version` | The platform's own monotonic counter. It is what a human says out loud ("we're on v12") and what a rollback is reasoned about in. |
| 9 | **Image reference (tag + digest)** | Tag from `flyctl releases --json` → `ImageRef`; digest from `flyctl machines list --json` → `image_ref.digest` | Record **both**. The tag is a name and a name can be re-pushed; the digest is the identity and cannot be. Rollback is performed by image reference, so this field is the operational payload of the whole row. The releases API returns only the tag — the digest must be taken from a machine running that release, which means it has to be captured at deploy time or it is gone. |
| 10 | **Rollback target** | Captured *before* the deploy by `deploy.yml` step `before`, which reads the currently live release number | Recorded at deploy time and never inferred later. "The previous row in the table" is the wrong answer the moment a rollback itself becomes a row: after rolling v12 → v11, the release that follows is v13, whose safe target is v11, not v12. |
| 11 | **Who deployed** | Mechanism, not just identity: a workflow run URL for a CI deploy, or a named person plus "workstation" for a manual one | Fly attributes every release to a Fly *account*, which does not distinguish a laptop from a CI token — both can be the same person. The mechanism is what tells you whether the gates in `deploy.yml` ran at all. |
| 12 | **Verification evidence** | Links: the readiness poll result, the `git_sha` assertion, the smoke walk, and the post-deploy conformance run | Fly reporting a successful deploy means Fly accepted the image. It does not mean the machine can serve — the catalog could be absent, writable, or unqueryable. `/ready` is what answers that, and this field is where the answer is filed. See [`docs/quality/RELEASE_GATES.md`](../quality/RELEASE_GATES.md): a green check with no artifact behind it is a failed gate. |
| 13 | **Base image pins** | `BUILDER_IMAGE` and `RUNNER_IMAGE` digests from `app/Dockerfile` at the recorded commit | The Dockerfile pins by digest rather than tag so that two builds of one commit are the same image, and its own comment commits to recording both here. The operational use is CVE triage: when an advisory lands against a Debian trixie digest, this column is how you find which releases carry it without rebuilding anything. |

### Fields deliberately absent

No user identifier, session identifier, storage key, request, or IP appears in any row. `/version` is built to expose build metadata only (INV-4, INV-26), and the ledger inherits that boundary. If a future field would require the server to learn something about a person in order to be filled in, the field is wrong, not the constitution.

## 2. How entries are produced

**From the first deploy that runs through [`.github/workflows/deploy.yml`](../../.github/workflows/deploy.yml) onward, entries are generated, not typed.** The workflow's `Write the release ledger entry` step curls `/version` on the machine that is actually live, renders a Markdown table to `artifacts/ledger-entry.md`, and uploads it as the `release-evidence` artifact with 365-day retention. Paste that table into §4 under a new heading and add the fields the generator does not know.

The generation is not decoration. A hand-typed entry records what someone *believed* they deployed; the generated one records what the serving machine *says it is*, after the same run has already asserted that its `git_sha` matches the commit that was built. That assertion is the point — a deploy that silently reused a cached image would otherwise be undetectable.

**What the generator supplies:** reason, commit, app version, catalog `data_version`, catalog payload sha256, LocalStore schema version, Fly release number, Fly image reference, rollback target.

**What must be added by hand when pasting** (verified by reading the workflow, not assumed):

| Missing | Why |
| --- | --- |
| Exact UTC timestamp | The step reads `DEPLOY_AT` from the environment, but the `env:` block sets only `REASON` and `PREVIOUS`. The field will therefore print the literal fallback `see workflow run`. Take the timestamp from `flyctl releases --json` or the run's own metadata. |
| Image digest | The generator uses `FLY_IMAGE_REF` from the machine environment. Whether that variable carries a digest or only a tag is **unmeasured** — it has never been read from a live machine, because no release currently serves `/version`. The digest is definitely available from `flyctl machines list --json`; take it from there. |
| Base image pins | Not exposed by `/version`. Read from `app/Dockerfile` at the recorded commit. |
| Catalog `schema_version` | `/version` returns it, but the generator's row list omits it. |
| Who deployed | Add the workflow run URL. |
| Verification evidence | Add links to the readiness poll, `git_sha` assertion, smoke walk, and conformance run for that run. |

### The pipeline is not armed yet

Two independent facts, both measured on 2026-08-01, mean no release has ever been produced this way:

- **No deploy credential exists.** `flyctl tokens list --app digital-oil-sticker` returns an empty table, and `gh secret list` returns nothing. The workflow's `preflight` job would set `armed=false`, emit its warning, and skip the deploy job entirely — which is the intended behavior, because a deploy workflow that silently no-ops looks identical to one that worked.
- **The workflow is not on the remote default branch.** `origin/main` (`5074745`) contains exactly one file under `.github/workflows/`: `conformance.yml`. GitHub reports exactly one registered workflow, `Browser conformance`. `ci.yml` and `deploy.yml` exist only in local commits that have not been pushed.

Arming it requires the owner to run `fly tokens create deploy` and add the result as the `FLY_API_TOKEN` repository secret, and to push the branch carrying the workflows. Both are owner actions: the first mints a credential, and the second makes a deploy path live.

### 4.3 The non-inference rule

**Do not reconstruct a commit by matching a release timestamp against a commit timestamp, and do not add a "probable commit" column.**

Nine of the twelve releases fall inside a four-hour window on a single day, during which the working tree was being edited continuously and multiple commits were made — the repository moved twice during the writing of this document alone. Timestamp adjacency would produce a confident-looking answer with no evidence behind it. A wrong commit in a ledger is strictly worse than an absent one, because the absent one prompts a question and the wrong one gets trusted, and the moment it is trusted it will be used to decide what to roll back to during an incident.

Every unknowable cell is marked `unrecoverable` and stays that way. The gap is closed going forward, not backwards.

### 4.4 What closes the gap

The first release built through `deploy.yml` carries `GIT_SHA` and `BUILD_TIMESTAMP` as build args, serves `/version`, and has its identity asserted against `github.sha` before the run is allowed to pass. From that release onward every field in §1 is populated from the running machine. The backfill above is the permanent record of the period before that was true.

## 5. Rollback

The rollback target field exists so this procedure needs no investigation while something is broken.

`flyctl` v0.4.77 (the version that produced every release above, per machine metadata) has **no `releases rollback` subcommand** — verified by reading `flyctl releases --help`, which offers only `--image` and `--json`. Rollback is therefore a redeploy of a known image:

```
flyctl releases --app digital-oil-sticker --image     # find the target's image reference
flyctl deploy --app digital-oil-sticker --image <reference from the ledger row>
```

Three things must be understood before this is used in anger:

- **This has never been exercised.** No rollback has been performed on this app. Its duration, its behavior with two machines, and whether the target image is still pullable from `registry.fly.io` are all **unmeasured**. What would measure it: performing one deliberate rollback to v11 during a quiet period and recording the result here as a ledger row.
- **Rolling back does not roll back user data, and does not need to.** The user's records are in their browser (INV-23). A machine replacement or a release rollback cannot lose them, because the server was never the system of record (INV-24.1). What a rollback *does* change is the LocalStore schema version the server expects — which is why field 7 exists.
- **Every deploy, including a rollback, drops every live LiveView socket.** That is a decision about interrupting people mid-task, which is why `deploy.yml` is `workflow_dispatch`-only rather than deploy-on-merge, and why that trigger choice is recorded as an open product decision rather than settled by an agent.

## 6. Open posture questions for the owner

These are decisions, not defects. Each names what is actually true today, what the options cost, and what "settled" would look like.

### Q1 — One always-on machine, or two?

**Measured.** Two machines are running in `ord`: `2862e40c6e0758` and `48ee567fd20ee8`, both `started`, both on release 12, both on image digest `sha256:59405c0d…`. `app/fly.toml` declares `min_machines_running = 1`.

**What that discrepancy is and is not.** `min_machines_running` is a *floor* for autostop, not a cap, and `auto_stop_machines = "off"` means nothing stops either machine. So two machines running is not a violated setting. It is an **undeclared posture**: anyone reading `fly.toml` would conclude the intent is one machine, and the platform is running two. The file does not currently say what the intended count is, and that is the thing that must not persist — an operator reading the config would make a wrong decision about capacity, and a future `flyctl scale count` would silently resolve the ambiguity in whichever direction it happened to point.

| Option | What it buys | What it costs |
| --- | --- | --- |
| **Two machines** (today's actual state) | A host failure or a rolling deploy leaves a serving machine up. Deploys can replace one at a time, so the app is never fully dark. | Roughly double the compute line. The exact figure is **unmeasured** — see Q2. |
| **One machine** (what the file implies) | One VM's cost instead of two. | Every deploy and every host event is a full outage of **unmeasured** duration. Every live LiveView socket drops with no second machine to land on. Under ADR-0004 that loses in-flight *UI* state, not user records — the records are in IndexedDB — but a user mid-way through recording an oil change sees the app go away. |

**Settled looks like:** `min_machines_running` set to the intended number, the machine count scaled to match, and the reason recorded in a one-line comment in `fly.toml` next to the always-on rationale already there. The owner picks; the ambiguity is what has to end.

### Q2 — What does this cost per month?

**Unmeasured. No number appears in this document because none was measured, and none will be added by an agent.**

What is known about the billed footprint, from the platform:

- Two `shared-cpu-1x` machines, 512 MB each, running continuously in `ord` with autostop off.
- One 1 GB volume in `iad`, encrypted, `auto_backup_enabled: true`, `snapshot_retention: 5` — attached to nothing (see §7).
- Bandwidth, plus registry storage for twelve deployment images.

**Why an agent must not fill this in.** A figure read off a vendor pricing page is a list price, not a bill. It cannot account for the org's plan, trial or promotional credits, free allowances, per-region variation, snapshot storage, egress, or a resource that is quietly billing because nobody remembers creating it — which is exactly the situation in §7. Reading a pricing page and writing the product down is arithmetic dressed as evidence, and this ledger does not carry that.

**How to measure it.** The owner opens the Fly.io billing view for the `personal` org and records here: the last full invoice total, its line items, and the date of the invoice.

**One existing estimate needs reconciling with that bill.** `app/fly.toml` justifies the always-on posture against "the ~$3-5/mo it saves" by scaling to zero. That figure is an unsourced estimate written in a comment, not a measurement. Once the invoice is in hand, either correct the comment or cite the invoice next to it — because the always-on decision in ADR-0004 rests on that number being roughly right.

## 7. Recorded divergences

Not decisions in the sense of Q1 and Q2 — these are known gaps between what the repository says and what the platform is doing. They are recorded so they cannot quietly become permanent.

### 7.1 The readiness check is declared but not deployed

`app/fly.toml` declares two service checks: `/ready` every 15s (readiness — rotates a machine out if the catalog is absent, altered, writable, unsupported, or unqueryable) and `/health` every 30s (liveness — checks nothing, on purpose, so one bad artifact cannot cause a restart storm). **Production now runs both**: as of release v14 each `ord` machine reports `2 total, 2 passing`.

Readiness gating is therefore in effect. It has been exercised once, by accident and successfully: v13's machine failed `release_identified` and was rotated out. What remains unrehearsed is a fault injected against an already-running machine — v13 failed at rollout, not mid-life.

### 7.2 Orphan volume `vol_4y8d01doz7gmz21r`

**Measured.** Name `digital_oil_sticker_data`, 1 GB, region `iad`, zone `31d1`, encrypted, state `created`, `attached_machine_id: null`, `attached_alloc_id: null`, created 2026-08-01T16:48:52Z, `snapshot_retention: 5`, `auto_backup_enabled: true`. It is attached to nothing, and it predates the first release (v1, 16:50:26Z). No claim is made here about what created it.

**Why it matters.** ADR-0004 §4 puts no personal rows on the server, and `fly.toml` carries no `[[mounts]]` precisely because there is no server state to persist — the catalog is a read-only build artifact inside the image, not state. A persistent volume is the one thing that posture forbids. It is also in `iad`, not the primary region `ord`, so it could not serve these machines even if something tried to mount it. Its continued existence is a standing invitation for a future deploy to attach it, and a billed resource with backups enabled.

**This is an owner action, not an agent action.** Deleting a volume is destructive and irreversible, and deletion also ends its snapshot retention. Before deleting, confirm nothing is wanted from it — it is unattached, so nothing is currently writing to it. When it is deleted, record the date and the volume ID here.
