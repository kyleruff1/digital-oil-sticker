## Outcome

A version-pinned compatibility report proves the minimum Mob path needed by the product on at least one physical iPhone and one physical Android phone. The report converts Mob's pre-1.0 status into explicit upgrade and containment rules.

## Why this matters and what it unblocks

Simulator success does not establish WebView persistence, lifecycle behavior, native permissions, safe-area rendering, release signing, or background behavior. Mob `0.7.20` is pre-1.0 and may change APIs incompatibly. This issue unblocks platform support claims, native project setup, CI expectations, storage, and notifications. Within M00 it is a hard blocker for DOS-M00-004 and DOS-M00-005, and its runtime verdict must be reflected in the final DOS-M00-002 ADR.

## Included

- Pin Mob to exactly `0.7.20` (including the resolved source/checksum) for the proof; record all required Elixir/Erlang, Node, Xcode, CocoaPods/Swift, JDK/Gradle/Kotlin, Android SDK, and OS versions.
- Produce the `mix mob.new digital_oil_sticker --liveview` disposable shell that installs, starts embedded BEAM/Phoenix, opens the loopback LiveView in the native WebView, renders safe-area-aware content, accepts input, backgrounds/resumes, is force-quit/reopened, and produces useful redacted logs.
- Run debug and release-like builds on physical iOS and Android hardware. Capture build/signing prerequisites without committing certificates, provisioning profiles, keystores, or secrets.
- Identify API surfaces the product expects from Mob: embedded BEAM lifecycle, WebView/loopback navigation, native packaging/deep links, application-support paths for SQLite, lifecycle, and `mob_notify`. Mark each supported, unsupported, experimental, or requiring a thin adapter.
- Define a Mob isolation boundary and upgrade policy: all Mob calls live behind platform ports; upgrades occur in dedicated tickets with release-note review, physical regression runs, and a rollback point.

## Excluded

- App Store/Play Store publication, polished UI, production identifiers, notification completion, storage selection, and broad device-matrix certification.

- FR-5: "Supported" is only claimed when an API was executed successfully on both physical platforms or is explicitly platform-specific with an approved fallback.

- FR-8: Production constraints hold in the proof: production Phoenix binds only to `127.0.0.1`, and production WebView debugging is disabled.

## Technical implementation contract

### Hypothesis

Mob exactly `0.7.20`, with a fully pinned native toolchain, can deliver the product's minimum required path on physical hardware: install, embedded BEAM/Phoenix startup, loopback WebView/LiveView rendering with safe-area awareness and keyboard input, background/resume and force-quit/reopen survival, release-like builds with capturable signing prerequisites, and identifiable support status for every API surface the product needs (BEAM lifecycle, WebView/loopback navigation, packaging/deep links, application-support paths for SQLite, lifecycle, `mob_notify`) — such that pre-1.0 risk can be contained behind platform ports and a disciplined upgrade policy.

### Timebox

Duration is assigned at refinement (estimates stay blank at bootstrap). If the timebox expires before the compatibility matrix is complete, the report ships with every unproven surface marked unsupported-or-blocking rather than assumed; a go/no-go verdict is still produced, and any blocking gap becomes a named decision before foundation work.

### Alternatives considered

- Simulator-only validation: rejected — the catalog states simulator success does not establish WebView persistence, lifecycle behavior, native permissions, safe-area rendering, release signing, or background behavior.
- Floating (unpinned) Mob or toolchain versions: rejected — pre-1.0 API drift makes unpinned proofs non-reproducible; the pin includes the resolved source/checksum.
- Letting Mob types flow into domain modules or persisted schema: rejected — the isolation boundary requires all Mob calls behind platform ports so a breaking Mob upgrade is contained in dedicated tickets.
- Abandoning Mob for an alternative shell if the proof fails: that is a replacement-architecture decision owned by the DOS-M00-002 ADR/stop gate, not a silent substitution inside this spike.

### Success and failure criteria

Success: acceptance criteria AC-1 through AC-7 pass — a clean setup guide, complete compatibility matrix, locked versions, release-like installs and relaunches on both physical devices, recorded lifecycle/safe-area/keyboard/log/bridge results, verified BEAM readiness and strict loopback binding and WebView reconnection, named fallbacks or blocking decisions for every unsupported/unstable capability, and an approved adapter boundary plus upgrade checklist. Failure: any product-required API surface is unsupported without a viable fallback, or release-like physical builds cannot be produced; the verdict then feeds the DOS-M00-002 stop gate and M01 remains blocked.

### Mandatory ADR and follow-ups

- Deliverable: the version-pinned compatibility report (setup guide + matrix + upgrade/containment rules). Its runtime verdict must be reflected in the final DOS-M00-002 ADR — that ADR is not ratifiable without it.
- The Mob isolation boundary and upgrade policy (platform ports, dedicated upgrade tickets, release-note review, physical regression runs, rollback point) must be approved before foundation work begins in M01.
- Follow-ups on success: release the DOS-M00-004 and DOS-M00-005 blockers; hand CI expectations (pinned toolchain, unavoidable manual signing prerequisites) to the M01 foundation issues.
- Follow-ups on failure or partial support: file a blocking decision per gap (named fallback or replacement architecture) and record it in the DOS-M00-000 limitation/gate register.

## Rollout and rollback

Rollout: the approved compatibility report, adapter boundary, and upgrade checklist become binding inputs to M01 foundation work and CI design; the verdict is written into the DOS-M00-002 ADR. The disposable shell is archived, not promoted. Rollback: the upgrade policy itself is the rollback mechanism for future Mob changes — any Mob version change happens in a dedicated ticket with release-note review, physical regression runs, and a rollback point to the last proven pin. If the report's verdict is invalidated later, the DOS-M00-002 replacement trigger governs.

## Risks, decisions, and open questions

- Risk: Mob `0.7.20` breaks or under-delivers on a required surface (for example application-support paths or WebView reconnection). Mitigation: per-surface status with named fallbacks or blocking decisions (AC-6); the go/no-go verdict feeds the DOS-M00-002 stop gate.
- Risk: signing prerequisites make the release-like build non-reproducible across environments. Mitigation: FR-7's second-environment repeat and explicit documentation of unavoidable manual steps.
- Risk: pre-1.0 API drift after the proof. Mitigation: the pinned checksum, platform-port isolation boundary, and dedicated-ticket upgrade policy with physical regression runs and a rollback point.
- Decision produced here: the approved adapter boundary and upgrade checklist (a prerequisite for foundation work).
- Open question (resolved by the spike): which capabilities are experimental or need thin adapters on exactly one platform, and what their approved fallbacks are.
