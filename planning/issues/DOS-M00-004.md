## Outcome

A persistence ADR and physical-device benchmark prove two distinct `ecto_sqlite3` repositories running inside the on-device BEAM: a replaceable, read-mostly `CatalogRepo` and a writable, private `UserRepo`. The artifact fixes paths, startup order, migrations, corruption recovery, and catalog replacement behavior.

## Why this matters and what it unblocks

The reference catalog and personal oil-change history have different update and retention lifecycles. Putting both in one database risks erasing user records during a catalog refresh; relying on WebView storage would bypass the chosen Elixir/Ecto architecture. This issue unblocks schema design, data packaging, offline search, migrations, and honest local-data messaging. It is the M00 proof behind the entire M04 local domain and persistence milestone and the M03 catalog artifact pipeline.

## Included

- Add and pin Ecto, `ecto_sql`, and `ecto_sqlite3` versions compatible with the selected Elixir/OTP/Mob stack. Start `CatalogRepo` and `UserRepo` under supervision only after Mob supplies valid application-support paths; never write databases into a read-only application bundle or a temporary/cache directory.
- Define `CatalogRepo` as a separate versioned SQLite file. A baseline file is bundled with the native application and is available on first launch without network access; if it must be copied out of the app bundle, the copy is checksummed and atomically activated before queries begin.
- Define `UserRepo` as a separate writable SQLite file containing local profile/settings, saved vehicle, oil-change history, driving samples, forecast inputs, and reminder intent. Catalog install, repair, replacement, or downgrade MUST NOT delete or overwrite it.
- Define distinct migration histories: catalog schema is built and validated by the data pipeline; user-schema Ecto migrations run transactionally on app upgrade. Record supervision/startup ordering, `PRAGMA` choices, journal/WAL sidecar handling, busy timeout, foreign keys, integrity checks, and graceful close/reopen across native lifecycle events.
- Create representative fixtures large enough to model 30 model years, major makes/models/variants/engines, provenance, and a small licensed/synthetic oil/filter cross-section. Benchmark indexed selection/search, first database readiness, UserRepo writes, migrations, catalog copy/swap, and disk use on physical iOS and Android devices.
- Define atomic catalog replacement with staged filename, checksum/schema/app compatibility validation, close/reopen coordination, and rollback to the last known-good catalog. User records retain stable source keys and display snapshots when a catalog row changes or disappears.
- Specify corruption detection/recovery, storage-pressure messaging, OS backup inclusion/exclusion policy, uninstall behavior, and optional future user-initiated export. Do not call the data backed up or encrypted unless that exact behavior is implemented and verified.

## Excluded

- Full production schema, full catalog population, cloud synchronization, device-to-device sync, server backup, Web Storage, IndexedDB, OPFS, SQLite-WASM, a browser persistence adapter, or claiming at-rest encryption beyond what `ecto_sqlite3` and the selected OS actually provide.

## Technical implementation contract

### Hypothesis

Two supervised `ecto_sqlite3` repositories inside the on-device BEAM — a bundled, checksummed, atomically activated `CatalogRepo` and a durable, transactionally migrated `UserRepo` — can start in the Mob-provided application-support paths on physical iOS and Android hardware, meet (or force explicit revision of) the provisional M00-001 readiness/latency/size budgets against 30-model-year-scale fixtures, and survive interrupted migrations, interrupted catalog copy/swap, corruption, and incompatible-schema injections with the prior working version and all local user records intact.

### Timebox

Duration is assigned at refinement (estimates stay blank at bootstrap). If the timebox expires with budgets unmet or failure injections unproven, the verdict is documented rather than assumed: either revised budgets are proposed for explicit approval, or the gap becomes a blocking decision at the DOS-M00-000 gate. The timebox is not extended silently.

### Alternatives considered

- One combined database for catalog and user data: rejected — a catalog refresh could erase user records; the two lifecycles (replaceable reference vs. durable personal history) require separate files (§4.2).
- WebView storage (Web Storage, IndexedDB, OPFS, SQLite-WASM, a browser persistence adapter): rejected and explicitly excluded — it would bypass the chosen Elixir/Ecto architecture.
- Cross-database foreign keys: rejected by §4.2 — user rows store a stable catalog key plus a readable snapshot so old history remains understandable when a catalog changes.
- Patching `CatalogRepo` via user migrations: rejected by §8 — the catalog is replaced as a versioned artifact, never migrated in place by the app.
- FTS5-based search as a baseline dependency: deferred — optional FTS tables are added only after the Mob/exqlite build proves FTS5 support; cascading indexed selectors must work without FTS.

### Success and failure criteria

Success: acceptance criteria AC-1 through AC-6 pass — the ADR fixes the two-repository design with durable paths, supervision order, and lifecycle behavior; measured p50/p95 timings meet the provisional M00-001 budgets or trigger revised, approved budgets; lifecycles are separate and diagrammed; interrupted migration/catalog update preserves the prior working version and all user records; quota/corruption/uninstall/eviction have user-visible recovery contracts; the baseline catalog is queryable on first launch in airplane mode on both physical platforms. Failure: any failure injection loses user records or the prior working catalog, or budgets are unmeetable without an approved revision — either outcome blocks the M00 gate until an explicit decision resolves it.

### Mandatory ADR and follow-ups

- Deliverable: the persistence ADR fixing the two-repository Ecto/`ecto_sqlite3` design, durable paths, supervision order, `PRAGMA`/journal/busy-timeout/foreign-key/integrity-check policy, migration split, atomic catalog replacement protocol, and corruption/storage-pressure/backup/uninstall contracts.
- Follow-ups on success: the ADR baselines M03 (catalog artifact build and packaging), M04 (production schema per master prompt §8 tables), and the honest local-data messaging required by M02 copy work; benchmark results feed back into the DOS-M00-001 target table (with explicit re-ratification if budgets changed).
- Follow-ups on failure: file the blocking decision (for example revised budgets, alternative pragma/journal policy, or catalog sizing changes) at the DOS-M00-000 gate before M01/M04-dependent planning proceeds.
- FTS5 follow-up: record whether the Mob/exqlite build proves FTS5 support; if unproven, the no-FTS indexed-selector requirement carries forward as a constraint on M03/M04 search design.

## UX and content states

The proof fixes honest local-data messaging contracts rather than screens: storage-pressure and corruption states must have user-visible recovery contracts (what the user is told, what is recoverable, what is not); uninstall behavior is documented truthfully; the app never claims data is backed up or encrypted unless that exact behavior is implemented and verified; first-launch catalog availability means airplane-mode first launch shows a queryable catalog, not a download prompt. These contracts flow into M02 content states and the DOS-M00-001 constitution's no-implied-backup rule.

## Test plan

### Automated

- A benchmark harness (committed with the proof) measuring indexed selection/search, first database readiness, UserRepo writes, migration duration, catalog copy/swap, and disk use against the representative fixtures, emitting raw results by device/OS with p50/p95 summaries.
- Failure-injection scripts: an interrupted catalog copy/swap, a `UserRepo` migration failure mid-transaction, a corrupt catalog file, and an incompatible schema version — each asserting rollback/recovery and intact user records.
- Integrity verification: checksum validation of the staged catalog before atomic activation; SQLite integrity checks wired into the startup order.
- Query-plan capture proving indexed access (no full scans) for the cascading selection paths.

### Manual/device matrix

- Physical iOS and physical Android devices (models and OS versions recorded): run the benchmark suite and record raw results, file sizes, and disk use per device.
- Demonstrate airplane-mode `CatalogRepo` search and `UserRepo` writes after force-quit/relaunch on both physical devices.
- Exercise graceful close/reopen across native lifecycle events (background/resume, force-quit/relaunch) and verify journal/WAL sidecar handling leaves no corruption.
- Verify first-launch behavior on a clean install in airplane mode: bundled catalog is checksummed, activated, and queryable before any network is available.

## Rollout and rollback

Rollout: the ratified persistence ADR becomes binding for M03 catalog artifact design and M04 schema/migration work; benchmark-driven budget revisions are re-ratified into the DOS-M00-001 target table. The proof code and fixtures are archived as reference, not promoted to production. Rollback: within the proven design, rollback is a first-class behavior — staged catalog replacement retains the last known-good catalog, and risky user migrations are preceded by a local atomic backup with documented recovery (per §8); if the ADR itself is later invalidated, it is superseded by a new ADR through the DOS-M00-002/DOS-M00-000 decision path.

## Risks, decisions, and open questions

- Risk: benchmarks miss the provisional budgets at 30-model-year fixture scale. Mitigation: AC-2's explicit revised-budget path with approval, never silent acceptance.
- Risk: platform filesystem semantics (paths, sidecar files, lifecycle kills) differ between iOS and Android. Mitigation: per-device evidence, journal/WAL handling in the ADR, and lifecycle close/reopen tests.
- Risk: FTS5 is unavailable in the Mob/exqlite build. Mitigation: cascading indexed selectors are required to work without FTS; FTS remains optional by design.
- Risk: overstating durability ("backed up", "encrypted"). Mitigation: FR-7 forbids such claims unless implemented and verified; OS-sandbox-only protection is stated honestly.
- Decision produced here: the persistence ADR (paths, supervision, PRAGMAs, migration split, replacement protocol, recovery contracts).
- Open question (resolved by the proof): OS backup inclusion/exclusion policy per platform and its user-facing wording.
