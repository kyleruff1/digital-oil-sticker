This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The dual-store idea survives but splits across a boundary: prove a read-only server-side catalog SQLite plus a client IndexedDB user store with its own forward-only versioning, not two on-device Ecto repos._

## Outcome

A ratified boundary-split persistence architecture and its proof establish that the dual-store idea survives the pivot in two physically distinct places rather than one: (a) a read-only server-side SQLite catalog opened by `DigitalOilSticker.CatalogRepo` in the deployed Phoenix LiveView application on Fly.io, produced deterministically by the M03 catalog build pipeline and swapped only by a full release image; and (b) an anonymous browser IndexedDB user store `dos_local` in the client, with its own monotonic integer `schema_version`, ordered pure forward-only migration functions, no downgrade path, no cross-store foreign keys, quarantined-record read-time validation, and a versioned envelope that participates in the ADR-0004 hydration/mutation round trip so the server never writes a personal row. The proof exercises both halves against real browser engines, drives the ADR-0004 §Enforcement gates end-to-end, and produces a new persistence ADR that supersedes the pre-pivot two-repo client-runtime design for the MVP; the pre-pivot design is preserved below as historical record for the deferred alternative-client re-entry.

## Why this matters and what it unblocks

The reference catalog and the personal record still have different update and retention lifecycles — that fact is not what changed. What changed is that they no longer share an OS process, a filesystem, or a language runtime: the catalog lives on Fly and the record lives in the user's browser. Putting personal data anywhere on the server would create a durable record keyed by *something* (a cookie, an IP, a session ID), and a durable server-keyed personal record is an account without a password (ADR-0004 §Alternatives considered 5). Conversely, shipping the catalog to the client as static JSON would be bulk redistribution of licensed data over the public web (ADR-0004 §Alternatives considered 4) and would double the resolver in JavaScript. The boundary split is therefore not a compromise but the architecture; this issue proves it holds.

It also proves the harder half honestly. IndexedDB has no rollback, no `CHECK` or `UNIQUE` constraints outside indexes, no foreign keys, and no cross-store referential integrity — every guarantee the pre-pivot `UserRepo` leaned on is gone (DOS-M09-001 makes this argument in full). The compensating machinery — server-side validation on hydration, read-time integrity checks, quarantine, compare-and-set on `meta.seq`, honest failure paths — must be exercised here or it does not exist.

This issue unblocks the re-scoped `DOS-M04-001` (dual-repository persistence ADR — this issue is its input), `DOS-M04-003` (IndexedDB object-store layout with server re-validation), `DOS-M04-005` (browser storage adapter with transactional semantics), `DOS-M04-007` (IndexedDB `onupgradeneeded` forward-only upgrades), `DOS-M04-009` (export/import as the *sole* recovery path), and `DOS-M04-010` (browser-matrix conformance replacing the physical-device matrix). It also unblocks `DOS-M09-002` (hydration protocol), `DOS-M09-003` (pre-hydration/storage-denied/quota/eviction UX), `DOS-M09-004` (impersonal server-side catalog query layer), and `DOS-M09-008` (browser support matrix and conformance suite). And it directly gates the enforcement tests specified in ADR-0004 §Enforcement.

- Prove the impersonal catalog-query surface (built in DOS-M09-004) is exercised only through catalog-scoped keys — no personal identifier, no stable client identifier — in every benchmark path (INV-26).

## Functional requirements

- **FR-1** (exactly-one-repo, read-only enforcement). The deployed OTP release supervises exactly one Ecto repo, `DigitalOilSticker.CatalogRepo`, opened with a read-only SQLite connection (`?mode=ro` or the adapter's equivalent). A runtime assertion enumerates every `Ecto.Repo`-implementing module and fails the release-health check if that list is not exactly `[DigitalOilSticker.CatalogRepo]`. No `DigitalOilSticker.UserRepo` module is compiled into the release. Enforces ADR-0004 §4 and §Enforcement bullet 1. **Replaces pre-pivot FR-3** (writable client-resident `UserRepo` under the pre-pivot supervised paths), which is retired.
- **FR-2** (catalog is a build artifact, not runtime state). The catalog SQLite file is baked into the deploy image at build time, its SHA-256 matches the manifest emitted by the deterministic catalog build pipeline, and no runtime code path opens the file `read_write`. Catalog replacement is a Fly release; rollback is a redeploy of the prior image. Enforces ADR-0004 §"Catalog database on Fly". **Replaces pre-pivot FR-2** (bundled inside a signed client-side application package) and **pre-pivot FR-6** (client-resident atomic staged copy/swap with rollback to last-known-good catalog).
- **FR-3** (no server-side personal record). Personal data on the server exists only in `socket.assigns` for the lifetime of a single LiveView connection. No module under `DigitalOilSticker.Catalog`, `.Garage`, `.Forecast`, or any other domain namespace writes a personal value to any Ecto repo, ETS table, DETS file, persistent term, external store, cache, or log line. A static check protects this at compile time; the runtime log-scan test (FR-9) protects it at runtime. Enforces INV-3, INV-23. **Retires** the pre-pivot writable-`UserRepo` design; addresses the sweep finding 1 clause a.
- **FR-4** (IndexedDB `dos_local` schema). The client-side IndexedDB database `dos_local` is opened with the object stores in ADR-0004 §"Storage layout": `meta` (singleton, holding `schema_version`, `seq`, `created_at`, `last_write_at`, `persist_granted`), `vehicles` (keyed by client-generated UUIDv4), `events`, `readings`, `reminders` (each UUIDv4-keyed), and `prefs` (singleton). A monotonic integer `meta.schema_version` — **distinct from** IndexedDB's own database version — governs migration. `localStorage` holds only the non-personal `dos_boot_state` boot hint (`"never"` | `"has_data"`) and never a personal value. **Replaces pre-pivot FR-4** (dual Ecto migration histories under the pre-pivot client-runtime lifecycle, with `PRAGMA`/journal/WAL/busy-timeout/foreign-keys/graceful-close-and-reopen), which is retired for the MVP; the successor mechanism is IndexedDB `onupgradeneeded` (see DOS-M09-001) plus pure server-side migration functions (FR-5). Addresses finding 1 clause b.
- **FR-5** (forward-only migration; refuse-newer). Migration is forward-only. Ordered pure functions `LocalStore.Migrations.migrate/3` transform an older-`schema_version` payload into the current schema in a single round trip and immediately push a `local_store:put` write-back with the migrated payload (ADR-0004 §Schema versioning step 5). A newer-`schema_version` payload is refused: the server enters read-only mode, renders the "this browser holds data from a newer version of the app" banner, disables mutations, and offers export. Silent downgrading and silent-unknown-key-dropping are prohibited. Each historical `schema_version` has a recorded fixture; every migration function is unit-tested against every prior version.
- **FR-6** (hydration is idempotent). Hydrating the same envelope twice produces byte-identical `socket.assigns` and emits no `local_store:put`. Enforces ADR-0004 §Enforcement bullet 4.
- **FR-7** (mutation round trip with honest failure). Every mutation is a `pushEvent` → server-assigns → `local_store:put` → hook `readwrite` transaction with compare-and-set on `meta.seq` → `local_store:ack` round trip. No ack within 2 000 ms, or an error ack, renders a persistent "Not saved to this browser" state on the affected record, keeps the optimistic value visibly marked as unsaved, offers export, and does **not** silently retry or silently roll back. Enforces ADR-0004 §"Mutation round trip". **New in the rescoped spec** — the pre-pivot client-resident Ecto transactions carried this contract implicitly and did not require it to be explicit.
- **FR-8** (multi-tab consistency; no lost updates). Multi-tab consistency is enforced by (a) `BroadcastChannel("dos_local_store")` notifications carrying `{seq, mutation_id, tab_id}` after every commit and (b) a compare-and-set on `meta.seq` inside the write transaction. A stale-seq transaction aborts and the hook pushes `local_store:conflict`, driving re-hydration. Conflict resolution is last-write-wins at record granularity with the loss made visible; the `BroadcastChannel`-unavailable path degrades to per-mount re-hydration and the compare-and-set still prevents lost-update corruption.
- **FR-9** (server-side redaction; scripted-session log-scan). A scripted-session log-scan test drives hydrate → several mutations → export → clear → import, captures every application log line, and asserts that no VIN, odometer value, service date, note text, custom vehicle name, `tab_id`, or hydration/mutation/import/export payload fragment appears. Enforces ADR-0004 §Enforcement bullet 3 and §Logging. **Replaces pre-pivot FR-8's** WebView/SQLite/static-endpoint prohibitions with the hosted-app equivalents.
- **FR-10** (honest failure states — quota, private mode, blocked storage, corruption). Failure injections have defined, distinguishable behaviors and passing tests: (a) `QuotaExceededError` follows the failed-ack path with a quota-specific message and no silent drop; (b) private browsing / refused-storage enters session-only mode with a persistent banner and prominent repeated export offer; (c) blocked or unavailable IndexedDB never silently falls back to `localStorage` for records or to server storage; (d) a payload with a corrupt or unparseable record hydrates the valid subset and quarantines the invalid records with an exportable raw payload; (e) `dos_boot_state == "has_data"` with zero hydrated records renders the `:data_missing` warning (never an empty state) and offers import. Enforces ADR-0004 §"First-paint and empty-state rules", §"Quota and eviction", §"Private browsing and blocked storage". **Replaces pre-pivot FR-7** (OS-sandbox-based storage-pressure/backup-inclusion/uninstall contract), whose OS-container semantics no longer apply to a browser origin.
- **FR-11** (export/import is the sole recovery). Export is produced entirely in the hook: read all stores, wrap in the envelope, append a SHA-256 content hash, serialize to a `Blob` download named `digital-oil-sticker-export-YYYYMMDD.json`. Import is a hook file-input round-tripped through `local_store:hydrate` so it inherits all validation and migration; import is explicitly replace-or-merge with counts previewed before commit. Export/import is the *only* recovery mechanism; the UI says so unprompted and the words "backup", "synced", "safe", "we'll remember", "your account" are prohibited (INV-5, INV-25; ADR-0004 §"Export and import"). This FR strengthens the pre-pivot spec's optional export into a mandatory, sole recovery path.
- **FR-12** (impersonal catalog-query surface). The read-only server-side catalog query layer built in DOS-M09-004 accepts no personal identifier and no stable client identifier as a query parameter (INV-26). This issue's benchmarks exercise catalog lookups only through catalog-scoped keys and record that boundary in the benchmark harness.
- **FR-13** (browser-matrix benchmarks; provisional-budget contract). Benchmarks are recorded on the browser matrix named by DOS-M09-008 (Chrome/Chromium, Firefox, Safari/WebKit, Edge; latest and one back on each; desktop and mobile viewports where distinct engines apply). p50/p95 hydration latency, p50/p95 mutation round-trip latency, storage footprint per 1 000 text-only records, and quota estimate at cold hydration are captured; measurements either meet the CONSTITUTION §9 provisional budgets or trigger a revised-and-approved entry in the target table. **Replaces pre-pivot FR-5** (physical-device benchmarks on the pre-pivot phone matrix at 30-model-year fixture scale).
- **FR-14** (referential integrity without foreign keys). There are no cross-store foreign keys inside IndexedDB (the engine does not support them). Referential integrity is enforced by (a) the server-side validation changeset on hydration (event `vehicle_id` must exist in the payload's vehicles, odometer values non-negative and within sane bounds, dates parseable, per ADR-0004 §Validation), (b) client-side changeset logic in the storage adapter (DOS-M09-002), and (c) hard caps rejected explicitly at the server (≤ 1 MiB decoded, ≤ 200 vehicles, ≤ 5 000 events, ≤ 20 000 readings). Unknown top-level keys are rejected; unknown *within-record* keys are preserved verbatim for forward compatibility. **Successor to pre-pivot §4.2's** "no cross-database foreign keys" rule, now enforced across a network boundary rather than across two client-resident SQLite files.
- **FR-15** (auditable retirement of pre-pivot FRs). The pre-pivot FRs that this rewrite retires are enumerated so the diff is auditable: pre-pivot FR-1 (Ecto/`ecto_sqlite3` pins + client-runtime application-support paths), FR-2 (baseline catalog bundled inside a signed client-side application package), FR-3 (writable client-resident `UserRepo` file), FR-4 (dual Ecto migration histories with `PRAGMA`/journal/WAL/busy-timeout/foreign-keys/graceful-close-and-reopen across the pre-pivot client-runtime lifecycle), FR-5 (pre-pivot phone-hardware benchmarks), FR-6 (client-resident atomic staged catalog copy/swap with rollback), FR-7 (OS-sandbox storage-pressure/backup/uninstall/optional-export contract), FR-8 (WebView-cannot-open-SQLite + database-not-reachable-through-Phoenix-static-endpoint rules). Each is now inapplicable at MVP; the named successor is called out in the FR that replaces it. The full pre-pivot text is preserved below under "Superseded pre-pivot spec (historical record)". Addresses finding 1 clause a in the aggregate.

## Technical implementation contract

### Hypothesis

A read-only server-side `CatalogRepo` baked into the Fly image, combined with an IndexedDB `dos_local` client store owning `schema_version` and driven through the ADR-0004 hydration/mutation protocol, can (a) prove exactly-one-repo + read-only enforcement at deploy time, (b) survive interrupted mutations, stale/newer client payloads, quota exhaustion, private browsing, blocked storage, and corrupt records without losing valid data and without emitting any personal value to logs, and (c) meet or force explicit revision of the CONSTITUTION §9 provisional hydration and mutation-latency budgets across the DOS-M09-008 browser matrix.

### Components and ownership boundaries

- `DigitalOilSticker.CatalogRepo` (server; `ecto_sqlite3`, read-only): the *only* Ecto repo in the deployed release; owned by the persistence workstream. The file lives in the deploy image and is treated as a build artifact.
- `DigitalOilSticker.LocalStore.Envelope`, `LocalStore.Migrations`, `LocalStore.Validator` (server; pure Elixir): envelope changeset, ordered forward-only migrations, and validation with quarantine; owned jointly by persistence and the LiveView workstream.
- `DigitalOilSticker.LocalStoreLive.Hook` (client; `phx-hook="LocalStore"`, TypeScript/JS): opens `dos_local`, runs IDB upgrade, executes read/write transactions, drives `local_store:hydrate` / `local_store:put` / `local_store:ack` / `local_store:conflict`; owned by the LiveView workstream. Implementation is the responsibility of DOS-M09-002 — this issue exercises it end-to-end.
- Benchmark harness (`spikes/m00-004-boundary-persistence/bench/`): browser-driven; owned by this issue. Emits raw results by engine, viewport, and cold vs. warm mount.
- The new persistence ADR (proposed `docs/architecture/ADR-0006-boundary-split-persistence.md`; number confirmed at refinement): owned by the architect role; drafted here and linked from the M00-000 gate.

### Data and persistence

- **Server side.** One SQLite file (the catalog) opened read-only, versioned by the catalog build's `data_version`, replaced only by a full deploy. Zero personal-data tables, zero personal-data migrations, zero personal-data backup jobs.
- **Client side.** IndexedDB `dos_local` with the object stores in ADR-0004 §"Storage layout". `meta.schema_version` is the migration authority; IndexedDB's own database version bumps only when store/index shape changes. Personal payload never leaves the origin.
- **In transit.** WSS only (INV-22); payload envelope hashed for export (SHA-256 in the hook, not on the server); no third-party origin ever receives a payload fragment.

### Interfaces and events

- `phx_hook:LocalStore` events: `local_store:hydrate`, `local_store:put`, `local_store:ack`, `local_store:conflict`, `local_store:export`, `local_store:import` — payload shapes fixed by the ADR-0004 envelope; validated by the server-side changeset on every hydrate/import.
- `BroadcastChannel("dos_local_store")` post-commit message shape `{seq, mutation_id, tab_id}` — used for multi-tab notification only; never used to move data between tabs and never a transport for personal payloads.

### Alternatives considered

- Two client-resident Ecto repos (the pre-pivot design): rejected for MVP by ADR-0004 §Decision; retained for the deferred alternative-client re-entry through ADR-0004's revival-triggers section.
- Server-side personal-data tables keyed by an anonymous cookie or session ID: rejected by ADR-0004 §"Alternatives considered" item 5 — a durable server-side record keyed by a stable identifier is an account without a password.
- SQLite on a Fly persistent volume, LiteFS, or a managed Postgres for the MVP catalog: rejected by ADR-0004 §"Catalog database on Fly" — none is justified for a read-only, deploy-versioned dataset.
- Static SPA on Netlify with the catalog shipped as static JSON: rejected by ADR-0004 §"Alternatives considered" item 4 — bulk redistribution of licensed data and a doubled resolver in JavaScript.
- IndexedDB → `localStorage` silent fallback for records: prohibited by ADR-0004 §"Private browsing and blocked storage".
- FTS5 as a gating dependency: deferred — indexed selectors first per DOS-M09-004.

### Success and failure criteria

Success: FR-1 through FR-15 pass with attached evidence; the exactly-one-read-only-repo test asserts `[CatalogRepo]` and read-only; hydration is idempotent; the migration matrix (older-with-write-back / current / newer-refused) behaves exactly as specified for every recorded fixture; mutation round-trip meets its 2 000 ms ack budget or the failure path renders honestly; the log-scan test comes back clean; browser-matrix p50/p95 measurements meet the CONSTITUTION §9 provisional budgets or explicitly propose revised, approved entries. ## Risks, decisions, and open questions

- Risk: browser eviction of infrequently-used site storage (ADR-0004 R1). A quarterly usage cadence is exactly the profile most at risk. Mitigation: `navigator.storage.persist()` requested once after the first meaningful write; honest storage-status UI; export nudges after meaningful writes; the `:data_missing` state so loss is never disguised as an empty garage. - Risk: hydration latency dominates first meaningful paint on every mount and every reconnect (ADR-0004 R2). Mitigation: FR-13 measures it against the CONSTITUTION §9 provisional budget; sub-second is a design target on a cold connection, not an aspiration.
- Risk: last-write-wins conflict resolution at record granularity (ADR-0004 R4) may be materially wrong for two-tab flows (one logs a service while the other edits it). Mitigation: losses are made visible; re-examine on evidence.
- Risk: CONSTITUTION §9 hydration and mutation-latency budgets are provisional and cover coast-to-coast public-internet paths (ADR-0004 R9). Mitigation: FR-13 revises them explicitly if unmet; a missed provisional budget triggers ratification of the revised entry, not silent acceptance.

### Outcome

A persistence ADR and physical-device benchmark prove two distinct `ecto_sqlite3` repositories running inside the on-device BEAM: a replaceable, read-mostly `CatalogRepo` and a writable, private `UserRepo`. The artifact fixes paths, startup order, migrations, corruption recovery, and catalog replacement behavior.

### Why this matters and what it unblocks

The reference catalog and personal oil-change history have different update and retention lifecycles. Putting both in one database risks erasing user records during a catalog refresh; relying on WebView storage would bypass the chosen Elixir/Ecto architecture. This issue unblocks schema design, data packaging, offline search, migrations, and honest local-data messaging. It is the M00 proof behind the entire M04 local domain and persistence milestone and the M03 catalog artifact pipeline.

### Context and source of truth

- Master prompt §4.2 (SQLite is the runtime database: Mob documents on-device Ecto plus `ecto_sqlite3` including explicit startup migrations; replace the Phoenix generator's PostgreSQL default before the first application build; two local SQLite databases — `CatalogRepo` replaceable read-mostly reference data, `UserRepo` durable local data never replaced by a catalog update; `pool_size: 1` per SQLite Repo; no cross-database foreign keys; user rows store a stable catalog key plus a readable snapshot).
- Master prompt §8 (database and data-contract baseline: `CatalogRepo` and `UserRepo` table baselines, integer base units for persisted mileage, migration and catalog rules — forward Ecto migrations run explicitly before the UI becomes writable, atomic backup before risky migration, staged/integrity-checked/atomically renamed catalog with previous catalog retained for rollback; FTS tables only after the Mob/exqlite build proves FTS5 support).
- Master prompt §7 (production shell security: SQLite is protected by the OS app sandbox but is not automatically encrypted; avoid full VIN storage by default; redaction rules) and §3 rules 2 and 9 (offline from first launch; multi-vehicle-safe internals).

#### Hypothesis

Two supervised `ecto_sqlite3` repositories inside the on-device BEAM — a bundled, checksummed, atomically activated `CatalogRepo` and a durable, transactionally migrated `UserRepo` — can start in the Mob-provided application-support paths on physical iOS and Android hardware, meet (or force explicit revision of) the provisional M00-001 readiness/latency/size budgets against 30-model-year-scale fixtures, and survive interrupted migrations, interrupted catalog copy/swap, corruption, and incompatible-schema injections with the prior working version and all local user records intact.

#### Alternatives considered

- One combined database for catalog and user data: rejected — a catalog refresh could erase user records; the two lifecycles (replaceable reference vs. durable personal history) require separate files (§4.2).
