> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _"Offline-safe" becomes "reproducible and deployable" — the platform target is a container on Fly, not a signed device package._

## Outcome

Implement the engineering platform the browser-first MVP actually runs on: a version-pinned hosted Phoenix/LiveView application deployable as a reproducible container to Fly.io behind `digitaloilsticker.com`, a single server-side read-only `DigitalOilSticker.CatalogRepo` (Ecto/SQLite) seeded from a tiny bundled fixture, the module boundaries and adapter ports that keep the domain client-agnostic per [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §6, the static Netlify support site as the second (static-only) origin, and the automated quality gates that keep the browser-first invariants (INV-3, INV-4, INV-5, INV-22, INV-23, INV-26, INV-27) hard to violate accidentally.

When this epic closes, a clean checkout can build and test the generated Phoenix/LiveView application, create the single server-side `CatalogRepo` opened read-only and seeded with the tiny bundled fixture catalog, produce a reproducible container image ready for Fly deploy, and emit the separate deployable static Netlify support site. The hosted endpoint terminates HTTPS/WSS through Fly's proxy, enforces the hardened origin/CSP boundary that replaced INV-2, and reaches a documented readiness state (HTTP 200 on `/health/ready` plus a successful `/live` socket handshake into the pre-hydration skeleton) on both the local dev environment and a staging Fly release. Personal data is never provisioned server-side — the browser IndexedDB `local_store` layout is delivered by DOS-M09-001 / DOS-M09-002 and hydrated on connect per DOS-M09-003. No feature milestone is considered implemented by this epic.

## Why this matters and what it unblocks

Every later milestone assumes a reproducible, honestly deployable engineering platform on the surface [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) ratified: hosted Phoenix on Fly, a read-only server catalog, and an anonymous browser store owned by the client. Without pinned toolchains, enforced module boundaries, an approved catalog schema, a deterministic catalog-artifact seam, a hardened public transport boundary (INV-22), and CI gates that block regressions, the browser-first invariants ratified in Constitution 2.0.0 — no server-side personal record (INV-3, INV-23), no third-party trackers (INV-4), no implied backup (INV-5, INV-25), impersonal catalog queries (INV-26), and a clean two-origin boundary (INV-27) — would exist only as prose and would erode under implementation pressure.

This epic unblocks:

- M09 (Hosted browser platform and anonymous client storage), whose issues implement what [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) ratifies and which cite the module boundaries (DOS-M01-002), the read-only `CatalogRepo` (DOS-M01-003), and the CI/deploy-evidence contract (DOS-M01-006) established here.
- The rescoped M04 (Local domain and persistence), which builds on the boundaries here and mounts the browser storage adapter M09 delivers.
- M03 production catalog ingestion, which consumes the catalog-artifact contract scaffolded by DOS-M01-004 and later bakes into the Fly deploy image (DOS-M09-006).
- M05 single-vehicle MVP screens, which require the hosted Phoenix/Fly deploy contract and the LiveView hydration protocol delivered by the rescoped DOS-M01-005 and by M09 (DOS-M09-003, DOS-M09-005, DOS-M09-006) per [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) and [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md).
- Every implementation ticket in the rescoped M04-M08, which cites the CI suites and evidence standards from DOS-M01-006 (browser/engine matrix, deploy evidence) instead of inventing per-ticket QA strategy.

## Included

Child issues (all six must close before this epic closes):

- DOS-M01-003 — Define the read-only server-side `DigitalOilSticker.CatalogRepo` (Ecto/SQLite) schema and its build-time migrations: approved catalog logical model, executable initial migrations, a migration contract, and the connection-opened-read-only assertion required by [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §4. - DOS-M01-004 — Scaffold the catalog-build contract with a tiny offline fixture: pipeline stage contracts plus a deterministic fixture-to-SQLite build that proves the artifact boundary without live acquisition. The artifact produced here is what DOS-M09-006 later bakes into the Fly image.
- DOS-M01-005 — Implement the hosted Phoenix/LiveView shell and the separate static Netlify support site: a Phoenix endpoint bound to `0.0.0.0` behind Fly's proxy with TLS termination at the edge, `check_origin` restricted to the deploy hostnames, `Plug.SSL` with `rewrite_on: [:x_forwarded_proto, :x_forwarded_host, :x_forwarded_port]`, CSRF/origin-checked LiveView socket, the CSP from ADR-0004, read-only `CatalogRepo` boot, `/health` (and `/health/ready`) endpoints suitable for Fly checks, and the separately deployable static Netlify support site. The former loopback/WebView handshake is deleted.
- DOS-M01-006 — Establish CI, test pyramids, quality budgets, and release evidence: automated gates (format, static analysis, dependency/license audit, secret scan, boundary enforcement, unit/contract/migration/pipeline/LiveView/endpoint suites, fixture catalog build, support-site build, container-image build), the wiring for the browser/engine conformance matrix (delivered fully in DOS-M09-009), and deploy evidence (container image digest, catalog `data_version`, Fly release ID) as the replacement for signed store artifacts.

## Technical implementation contract

### Components and ownership boundaries

N/A — epic-level tracking issue. Component ownership is defined in DOS-M01-002 and in [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Decision" (specifically §6 client-agnostic domain). Each child owns its slice as stated in its own body. The Fly-runtime vs. Netlify-static split is owned jointly by DOS-M01-005 (server shell + static site) and DOS-M09-007 (custom domain + certificates); at the M01 layer only the code and build-time separation is fixed.

### Data and persistence

Epic-level constraint per [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §4: the deployed application starts exactly one Ecto repo — `DigitalOilSticker.CatalogRepo` — and opens it read-only. **No `UserRepo` may be added to the application's supervision tree**, and no server-side personal row exists in any form (INV-3, INV-23). Schema and lifecycle contracts for the catalog are owned by DOS-M01-003 (schema/migrations) and DOS-M01-004 (build-time artifact). The browser IndexedDB `local_store` is not owned by this epic — DOS-M09-001 defines the object-store layout and version line, and DOS-M09-002 implements the adapter. This card cross-links to those but does not duplicate their contract.

### Interfaces and events

N/A — epic-level tracking issue. The browser-storage port, the LiveView hook contract (server-side interface), the domain-namespace static checks, and the error taxonomy are owned by DOS-M01-002. The hydration/mutation protocol itself (envelope, `local_store:hydrate`, `local_store:put`, `local_store:ack`, `local_store:conflict`, deadlines, validation) is normative in [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"The client-storage + LiveView hydration protocol" and is implemented by DOS-M09-003; M01 defines only the seams it plugs into.

### Failure and recovery behavior

N/A — epic-level tracking issue. Startup / readiness failure states for the hosted endpoint are owned by DOS-M01-005 (including WSS handshake failure, origin-check rejection, and CSP violation reporting if enabled). Catalog migration failure behavior is owned by DOS-M01-003. Gate-failure behavior in CI is owned by DOS-M01-006. Client-side storage failure states (denied storage, quota, eviction, private browsing) are owned by DOS-M09-002 / DOS-M09-004 and are explicitly out of scope here.

### Security and privacy

Epic-level constraint: every child preserves the hosted-transport boundary that replaced INV-2 — HTTPS + WSS only, `force_ssl` with redirect, `check_origin` restricted to the exact deploy hostnames, the CSP from ADR-0004 (`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' wss://digitaloilsticker.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and a `Permissions-Policy` denying geolocation, camera, microphone, and payment (INV-22). No third-party analytics, tag manager, session recording, A/B service, or error-reporting integration may be introduced (INV-4). No credentials in the repository. No personal or restricted source data in fixtures or CI artifacts. `debug_errors: false` in production so no assigns reach an error page. LiveDashboard is disabled in production. The session cookie is signed, `secure`, `http_only`, `same_site: "Lax"`, and contains no personal data and no stable user identifier (INV-3, INV-23).

### Accessibility and performance

Epic-level constraint: budgets for first-paint payload, time-to-hydrated, LiveView round-trip latency, server memory-per-socket, and container-image size come from the rescoped M00 (per Constitution 2.0.0's replacement of the now-void §9 device budgets) and are enforced as gates by DOS-M01-006; the pre-hydration skeleton, storage-status affordances, and readiness states in DOS-M01-005 (and later DOS-M09-004) must be screen-reader reachable and satisfy WCAG 2.2 AA verified against a named browser + assistive-technology matrix (delivered in DOS-M09-009).

## Risks, decisions, and open questions

- Risk: the pre-pivot children (DOS-M01-001 through DOS-M01-006) that referenced Xcode / Android SDK / Gradle / Mob, the on-device shell, or the two-Ecto-repo design must all be rewritten before implementation, per the pivot. Mitigation: FR-1 gates work on any child until it has been rewritten to the browser-first target.
- Risk: hosted-transport hardening is discipline-heavy and easy to erode after the first green build. Mitigation: FR-10 / FR-11 and AC-4 / AC-5 make CSP presence, origin restriction, the repo-list assertion, and the domain-namespace static check release-gating rather than review-gating.
- Risk: the domain-agnosticism static check from ADR-0004 §6 is what preserves the native re-entry option. If it is weakened or opt-in, the domain contexts silently couple to LiveView and the native track becomes theoretical. Mitigation: the check runs as a release gate (FR-11, AC-4) with a controlled-failure demonstration in CI.
- Risk: the hosted app depends entirely on Fly.io availability (ADR-0004 §"Consequences"). M01 cannot eliminate this; DOS-M09-006 records the rollback contract and the rescoped M07 records the launch monitoring.
- Risk: web-serving rights for licensed catalog sources are unreviewed (ADR-0004 R6 / ADR-0003 addendum). Mitigation: this epic ships only the tiny bundled fixture (DOS-M01-004), which contains no licensed source data; production catalog ingestion (M03) honors the addendum and cannot be attempted here.
- Risk: an unresolved M00-era gate is disavowed rather than closed — the pre-pivot M00 go/no-go card is DEFERRED per the pivot (Context and source of truth) and cannot resolve on the current toolchain.
