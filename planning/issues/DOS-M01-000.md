## Outcome

Implement only the platform skeleton selected by M00: the Mob `0.7.20` on-device LiveView runtime, strict loopback hardening, two Ecto/SQLite repositories, a tiny bundled fixture catalog, the `mob_notify` adapter boundary, a separate static Netlify support site, and automated quality gates. The foundation must make privacy, offline, and runtime-boundary constraints hard to violate accidentally.

When this epic closes, a clean checkout can build and test the generated Mob/LiveView application, create both SQLite repositories with a tiny bundled fixture catalog, produce iOS/Android development packages, and emit a separate deployable static Netlify support site. The native shell starts on-device BEAM/Phoenix, connects the WebView only to `127.0.0.1`, and exposes a local diagnostic/readiness screen in airplane mode. No feature milestone is considered implemented by this epic.

## Why this matters and what it unblocks

Every later milestone assumes a reproducible, offline-safe engineering platform. Without pinned toolchains, enforced module boundaries, approved schemas, a deterministic catalog-artifact seam, a hardened loopback shell, and CI gates, the roadmap's non-negotiable rules (no accounts, offline from first launch, no fabricated automotive facts, local notifications only) would exist only as prose and would erode under implementation pressure.

This epic unblocks:

- M04 (Local domain and persistence), which builds on the module boundaries (DOS-M01-002) and schemas (DOS-M01-003) established here.
- M03 production catalog ingestion, which consumes the pipeline stage contracts and artifact boundary scaffolded in DOS-M01-004.
- M05 single-vehicle MVP screens, which require the working on-device shell from DOS-M01-005.
- Every implementation ticket in M04-M08, which cites the CI suites and evidence standards from DOS-M01-006 instead of inventing per-ticket QA strategy.

## Risks, decisions, and open questions

- Risk: Mob is pre-1.0; `0.7.20` APIs may change under the project. Mitigation: exact version pinning (DOS-M01-001), adapter isolation (DOS-M01-002), and the M00 fallback ADR path.
- Risk: platform toolchain churn (Xcode, Gradle, OS versions) breaks reproducibility. Mitigation: pinned versions and documented update policy.
- Risk: scope creep from "foundation" into feature work. Mitigation: change control (non-negotiable rule 10) — anything not in a child's Included scope becomes a new issue or ADR.
- Decision inherited: one Mob/Phoenix application, not an umbrella, unless the M00 spike proved a concrete need.
- Open question: none may remain at epic close; unresolved child-level questions must be tracked as follow-up issues before the exit gate is declared.
