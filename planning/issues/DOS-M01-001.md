> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Drop Xcode/Android SDK/Gradle/Mob pins; keep Elixir/OTP/Phoenix/esbuild/Tailwind/SQLite pins and add Docker base image and `flyctl` version pinning._

## Outcome

The repository builds, tests, and *deploys* predictably from a clean environment with exact runtime, container-image, and dependency versions pinned; with no credentials or machine-specific state committed; and with the tool-version, secret-hygiene, and image-provenance gates that make the browser MVP reproducible. The application code under `app/` is the plain Phoenix 1.8 + LiveView 1.2 scaffold selected by [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md), configured for `ecto_sqlite3` on the read-only `DigitalOilSticker.CatalogRepo` and for a Fly.io-hosted deploy. None of the deferred pins catalogued in [ADR-0004 §"Trigger conditions that revive the native track"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#trigger-conditions-that-revive-the-native-track) ship in the deployment lockfile, gate a fresh checkout, or survive as a security claim in the runtime configuration.

## Why this matters and what it unblocks

Every implementation and CI card depends on a reproducible skeleton, and after the 2026-08-01 pivot "reproducible" now means two things at once: the local development toolchain (Erlang/OTP, Elixir, Node/esbuild, Tailwind, SQLite, Hex/Rebar) and the release toolchain (the base container image plus `flyctl`) both produce byte-identical outputs from the same commit. Pinning the container base image and `flyctl` alongside the Elixir toolchain is what turns a "works on my machine" LiveView build into a Fly.io release ledger entry that can be rolled back to. Removing the deferred pin set from the MVP checkout also matters — because pretending those tools are still required on a fresh checkout would make setup fail on things nobody in the MVP path actually needs.

This card unblocks the browser-first children of M01 — module scaffolding ([DOS-M01-002](DOS-M01-002.md)) whose "platform adapter" port is now the browser-storage port; the read-only catalog schema ([DOS-M01-003](DOS-M01-003.md)) served over `CatalogRepo`; the deterministic catalog build ([DOS-M01-004](DOS-M01-004.md)) that produces the artefact baked into the deploy image; the hosted Phoenix + separate static Netlify site ([DOS-M01-005](DOS-M01-005.md)) that replaces the loopback WebView; and the browser/engine + deploy-evidence CI ([DOS-M01-006](DOS-M01-006.md)) that replaces the device matrix. Downstream of M01, the hosted-runtime cards in M09 — Fly deploy pipeline ([DOS-M09-006](DOS-M09-006.md)), custom domain and TLS ([DOS-M09-007](DOS-M09-007.md)), and the internet-facing hardening gate ([DOS-M09-008](DOS-M09-008.md)) — all consume the pinned base image, the pinned `flyctl`, and the secret-hygiene scanner defined here.

## Functional requirements

- **FR-1: The application scaffold is Phoenix 1.8 + LiveView 1.2, configured for a hosted Fly.io deployment.** The repository under `app/` contains a plain Phoenix LiveView scaffold (as generated by the Phoenix 1.8-line generator with `--live` and SQLite selected), with `ecto_sqlite3` configured for the read-only server-side `DigitalOilSticker.CatalogRepo`, and none of the `:mob`, `:mob_notify`, `:mob_dev`, or `:mob_new` dependencies from the deferred pin set in `app/mix.exs` or `app/mix.lock`. The pre-pivot generator invocation that this card previously mandated is not part of the MVP deliverable; it is preserved only in the historical section below, as required by ADR-0004 §"ADR-0001 → Deferred". _(Addresses staleness-sweep finding 1.)_
- **FR-2: The browser-MVP toolchain is pinned exactly or under a documented update policy, and lockfiles are committed.** Pinned: Erlang/OTP, Elixir, Hex/Rebar; Phoenix, `phoenix_ecto`, `ecto_sql`, `ecto_sqlite3`, `phoenix_live_view`, `phoenix_html`, `bandit`, `jason`, `telemetry_metrics`, `telemetry_poller`, `dns_cluster`; `esbuild` and `tailwind` Elixir wrappers and the underlying binaries they install; the GitHub-sourced `heroicons` (tag `v2.2.0`) and `daisyui` (tag `v5.5.20`); and Node when it is invoked directly by asset tooling. `app/mix.lock` is committed. _(Replaces the pre-pivot FR-2, which additionally required the deferred pin set catalogued in ADR-0004; those pins were retired from this card per staleness-sweep finding 3.)_
- **FR-3: The container base image and `flyctl` version are pinned by content digest and by version, respectively.** `app/Dockerfile` pins the builder image (`hexpm/elixir`) and the runner image (`debian`) by `@sha256:` digest, with the corresponding human-readable tag retained as a comment on the same line for provenance. `flyctl` is pinned to a specific documented version consumed by CI and by the deploy runbook. Advancing either pin is a single reviewed commit that updates the digest, the tag comment, and the release-ledger record together.
- **FR-4: A committed example environment file documents every required runtime variable and contains no secret values.** At minimum: `PHX_HOST`, `PORT`, and a documented `SECRET_KEY_BASE` placeholder. The file states plainly that `fly secrets set` is the production-set mechanism and that `.env` files are never committed and never used in production, per ADR-0004 §"Secrets".
- **FR-5: The documented directory layout matches the shipped repository.** Domain code (`app/lib/digital_oil_sticker/`), LiveView surface (`app/lib/digital_oil_sticker_web/`), assets (`app/assets/`), tests (`app/test/`), release configuration (`app/rel/`, `app/config/`, `app/Dockerfile`, `app/fly.toml`), data-import tooling (`tools/catalog/`), architecture and governance records (`docs/`), planning cards (`planning/issues/`), and conformance harnesses (`conformance/`) are the canonical locations; generated build output (`app/_build/`, `app/deps/`, `app/priv/static/assets/`) is git-ignored except explicitly committed fixtures.
- **FR-6: One canonical command exists for each concern, and every canonical command fails loudly on unsupported tool versions.** The Mix-alias interface covers setup (`mix setup`), quality gates (`mix precommit` — compile with warnings-as-errors, `deps.unlock --unused`, `format`, `test`), tests (`mix test`), asset build (`mix assets.build`), and asset deploy (`mix assets.deploy`). The container release is a documented `flyctl deploy` invocation using the pinned `flyctl`. Every command fails with an actionable message on an unsupported Elixir/OTP or `flyctl` version rather than silently proceeding.
- **FR-7: Runtime configuration binds to the Fly proxy over HTTPS/WSS, per INV-22 hosted-transport rules.** In production, `Endpoint` is served over HTTPS via the Fly proxy on the interfaces Fly requires (as configured in `app/fly.toml` and `app/config/runtime.exs`); `Plug.SSL` is enabled with `rewrite_on: [:x_forwarded_proto, :x_forwarded_host, :x_forwarded_port]`; `check_origin` is set to an explicit host list restricted to production hostnames (never `true`, never `false`); `PHX_HOST` is set explicitly; and the LiveView socket uses WSS. There is no loopback-only binding rule — that rule was a property of the deferred native on-device shell and is retired per Constitution INV-2 → INV-22 (see [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Security and privacy boundary for a hosted application"). The default application performs no telemetry and speaks to no third-party origin; the CSP served in production forbids third-party `script-src` and `connect-src`. _(Replaces the pre-pivot FR-7's `127.0.0.1`-only binding language per staleness-sweep finding 2.)_
- **FR-8: The deployed application ships exactly one Ecto repo, `DigitalOilSticker.CatalogRepo`, opened read-only.** There is no `UserRepo` in the deployed application, no personal-data table, and no personal-data migration. The scaffold's `mix.exs` `aliases/0` therefore omits `ecto.setup` and `ecto.migrate`. This is the enforcement seam that ADR-0004 §"Enforcement" and INV-23 rely on and that later hardening ([DOS-M09-008](DOS-M09-008.md)) asserts on with an automated test. _(Replaces the pre-pivot FR-8's native pin requirement per staleness-sweep finding 3; the retired notifier and platform bridges are catalogued in the deferred pin set in ADR-0004.)_
- **FR-9: Setup documentation covers only the browser-MVP toolchain.** The documented prerequisites are Erlang/OTP, Elixir, Node (only where the asset toolchain invokes it directly), Docker (for the release build), and `flyctl` (for deploy). Documentation states which commands are safe to run without a Fly-scoped deploy token, and which are gated by it. The deferred pin set catalogued in ADR-0004 §"Trigger conditions that revive the native track" is explicitly *out of scope for a fresh MVP checkout*.
- **FR-10: Secret-hygiene ignore rules and an automated scanner gate prevent committing Fly API tokens, `SECRET_KEY_BASE` values, `.env` files, raw restricted catalog datasets, and personal test exports.** The gate is proven with representative forbidden filenames and with a deliberate secret-like fixture value that the scanner rejects — without any real secret ever being committed.

## Technical implementation contract

### Components and ownership boundaries

This card owns the repository skeleton, the pinned toolchain and container base image, the Mix-alias task interface, the setup documentation, and the secret-hygiene gate. It does **not** own: module content (that is [DOS-M01-002](DOS-M01-002.md)); the read-only catalog schema (that is [DOS-M01-003](DOS-M01-003.md)); the deterministic catalog build pipeline (that is [DOS-M01-004](DOS-M01-004.md)); the hosted Phoenix runtime configuration and the separate static Netlify support site (that is [DOS-M01-005](DOS-M01-005.md)); CI orchestration and the browser/engine matrix (that is [DOS-M01-006](DOS-M01-006.md)); the Fly.io deploy pipeline (that is [DOS-M09-006](DOS-M09-006.md)); custom-domain cutover (that is [DOS-M09-007](DOS-M09-007.md)); or the internet-facing hardening gate (that is [DOS-M09-008](DOS-M09-008.md)). The shipped Phoenix scaffold is preserved; project-specific structure is added around it.

### Data and persistence

No runtime data is created by this card. `ecto_sqlite3` is configured for the read-only `DigitalOilSticker.CatalogRepo`; the catalog artefact itself is a build output owned by [DOS-M01-004](DOS-M01-004.md) and is baked into the deploy image at release time per ADR-0004 §"Catalog database on Fly". No `UserRepo` is added and no personal-data table exists — INV-23 is enforced structurally by the absence of any server-side personal-data schema. Reference-fixture and generated-artefact directories are established with ignore rules.

### Interfaces and events

The task interface is the only public contract: one canonical Mix alias per concern, plus `flyctl deploy` for release. Command names are stable; internals may evolve. `runtime.exs` is the single source of production configuration; secrets flow only through `fly secrets set`.

### Failure and recovery behavior

Commands fail loudly with actionable messages on unsupported tool versions, missing prerequisites, or absent optional credentials (clearly distinguishing "cannot deploy without a Fly-scoped token" from "broken checkout"). Setup documentation includes common failure-recovery steps. No command mutates state outside the repository, its build directories, and — for `flyctl deploy` only — the operator's deploy-scoped Fly app.

### Security and privacy

Governance for this scaffold is the ADR-0004 §"Security and privacy boundary for a hosted application" list, which supersedes the loopback stance of the retired INV-2: HTTPS + HSTS (enabled after certificate verification, per [DOS-M09-007](DOS-M09-007.md)); WSS for LiveView; CSRF on the LiveView session and on every non-idempotent HTTP endpoint; a Content-Security-Policy forbidding third-party `script-src` and `connect-src`; cookies `Secure`, `HttpOnly` where applicable, `SameSite`-restricted, with no personal data and no stable user identifier in the session cookie; `check_origin` set to an explicit host list; no third-party analytics, tag managers, session recorders, or externally-hosted fonts or scripts; and structured logging with no personal data reaching any log sink. Secret material (Fly API tokens, `SECRET_KEY_BASE`, licensed dataset raw inputs, personal test exports) is kept out of the repository by ignore rules and by the scanner gate; the sample environment file contains placeholders only.

### Accessibility and performance

N/A — no user-facing UI is produced by this card. The WCAG 2.2 AA browser-AT contract lives in [DOS-M02-002](DOS-M02-002.md) and the browser/engine matrix and conformance suite live in [DOS-M09-009](DOS-M09-009.md). Tooling performance is informational only; latency and payload budgets are enforced later by [DOS-M07-003](DOS-M07-003.md) against the re-ratified ADR-0004 §"Consequences" targets.

## Test plan

### Automated

- Run every canonical Mix alias from a clean checkout of `app/`: `mix setup`, `mix precommit`, `mix test`, `mix assets.build`, `mix assets.deploy`. All pass in CI.
- Tool-version guard test: invoke `mix precommit` under an unsupported Elixir/OTP version and assert a loud, actionable failure.
- `flyctl --version` guard test: invoke a documented deploy command under an unpinned/older `flyctl` and assert an actionable failure with the exact required version.
- Container-pin assertion test: parse `app/Dockerfile` and assert both `BUILDER_IMAGE` and `RUNNER_IMAGE` are pinned by `@sha256:` digest and that a corresponding tag comment is present on the same line.
- Dependency-hygiene assertion test: parse `app/mix.exs` and `app/mix.lock` and assert none of `:mob`, `:mob_notify`, `:mob_dev`, or `:mob_new` appears in either file (finding-3 regression test).
- Runtime-configuration assertion test: assert `runtime.exs` sets `check_origin` to an explicit host list, uses `Plug.SSL` with the `rewrite_on` shape above, and does not configure the endpoint to bind to `127.0.0.1` in production (finding-2 regression test).
- Repo-list assertion test: assert the application's configured Ecto repos are exactly `[DigitalOilSticker.CatalogRepo]` and that its connection is opened read-only.
- Secret-hygiene test: stage representative forbidden filenames (Fly API token, `SECRET_KEY_BASE` value, `.env`, raw restricted dataset, personal test export) and a secret-like fixture value; assert the ignore rules and the scanner gate reject them.

### Manual

- Second-developer environment: an engineer other than the author performs the documented setup on a clean machine, runs `mix setup && mix precommit`, and reaches green using only the browser-MVP toolchain listed in FR-9 — verifying that no Xcode, Android SDK, Gradle, or Mob install is required. Discrepancies are fixed in the docs before close.
- Container build rehearsal on a clean machine: `docker build` succeeds against the pinned digests without touching the network for a moving-tag lookup.

## Risks, decisions, and open questions

- **Risk:** a container base-image tag republishes and a rebuild silently produces a different image. **Mitigation:** pin by `@sha256:` digest per FR-3 and record the tag as documentation only.
- **Risk:** `flyctl` releases a breaking change between deploys. **Mitigation:** pin `flyctl` version in CI and in the operator runbook; treat an advance as a reviewed commit.
- **Risk:** temptation to reintroduce the deferred pin set incrementally "just in case." **Mitigation:** AC-4 and AC-7 are release gates; the deferred pin set is catalogued in ADR-0004 and re-entry requires a new ADR (the next available number in the ADR sequence, not ADR-0005 which is already accepted on a different subject) per ADR-0004 §"Trigger conditions that revive the native track".
- **Risk:** documentation drifts to imply the deployed app stores personal data on the server. **Mitigation:** AC-9 asserts the single-repo `[CatalogRepo]` shape and it is re-asserted downstream by [DOS-M09-008](DOS-M09-008.md).
- **Decision recorded here:** the deployed application uses Phoenix 1.8 + LiveView 1.2 with `ecto_sqlite3` for the read-only catalog. The pre-pivot generator invocation is not the MVP deliverable and is preserved only in the historical section below.
- **Open question:** the exact pinned Elixir 1.18 / OTP 28.4 point releases move as security releases land upstream; the update policy that governs when the pin advances is documented, but the *cadence* is unspecified. First advancement will set the pattern.
