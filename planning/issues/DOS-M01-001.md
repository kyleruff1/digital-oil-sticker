## Outcome

The repository builds predictably from a clean environment with exact runtime/dependency versions, documented native prerequisites, and no credentials or machine-specific state. The scaffold is the Mob `0.7.20` LiveView project generated by exactly `mix mob.new digital_oil_sticker --liveview`, wrapped in a small documented task interface, pinned dependency manifests, directory conventions, setup documentation, and secret-hygiene gates.

## Why this matters and what it unblocks

Every implementation and CI issue depends on a reproducible skeleton. Pinning is especially important for Mob `0.7.20` and its pre-1.0 APIs: an unpinned transitive upgrade could silently change bridge, build, or runtime behavior on device. This issue unblocks module scaffolding (DOS-M01-002), storage (DOS-M01-003), data tooling (DOS-M01-004), native builds (DOS-M01-005), and tests/CI (DOS-M01-006). It also makes the project's privacy stance structural from the first commit: no credentials, no telemetry, no machine-specific state.

## Included

- Scaffold the application with exactly `mix mob.new digital_oil_sticker --liveview`, preserving the generated embedded Phoenix/LiveView and native-project structure unless an M00-approved compatibility fix is required and documented. Any deviation from generator output is recorded with its motivating M00 decision.
- Pin Erlang/OTP, Elixir, Hex/Rebar, Mob `0.7.20`, Ecto/`ecto_sql`/`ecto_sqlite3`, `mob_notify`, and required Node/package-manager, Xcode/iOS, and Gradle/Android dependencies. Version pins are exact or constrained under an approved, documented update policy. Browser tooling may support local LiveView development/tests only — it is never a production target. Commit dependency lockfiles (`mix.lock` and any Node/Gradle lockfiles) and an example environment file containing no secrets.
- Establish directories for domain code, UI/client, platform adapters, native wrappers, data-import tooling, reference fixtures, migrations, tests, architecture records, and generated artifacts. Generated catalogs/build output are ignored by version control unless a deliberate small fixture is needed for tests, in which case the fixture is explicitly committed and documented.
- Add standard format, compile-with-warnings-as-errors where practical, static analysis/lint, unit-test, dependency audit, native-build, support-site-build, and fixture-catalog commands behind a small documented task interface (for example Mix aliases or an equivalent single entry point). Each concern has one canonical command.
- Document local setup, physical-device prerequisites, common failure recovery, and which commands are safe without signing credentials, covering both macOS/Xcode (iOS) and Gradle/Android toolchains.
- Add secret scanning rules and ensure iOS signing materials, Android keystores, `.env` files, raw restricted datasets, and personal test exports cannot be committed accidentally — via ignore rules plus an automated scanner gate exercised with representative filenames.

## Technical implementation contract

### Components and ownership boundaries

This issue owns the repository skeleton, task interface, version manifests, documentation, and secret-hygiene gates. It does not own module content: domain/adapter boundaries belong to DOS-M01-002, schemas to DOS-M01-003, pipeline behavior to DOS-M01-004, shell behavior to DOS-M01-005, and CI orchestration to DOS-M01-006. The generated Mob/Phoenix structure is preserved; project-specific structure is added around it, not by rewriting it.

### Data and persistence

No runtime data is created. The PostgreSQL default from the Phoenix generator is replaced with `ecto_sqlite3` configuration before the first application build (per master prompt section 4.2); actual Repo modules and migrations are DOS-M01-003 scope. Reference-fixture and generated-artifact directories are established with ignore rules.

### Interfaces and events

The task interface is the only public contract: one canonical, documented command per concern (setup, quality, tests, audit, fixture catalog, iOS build, Android build, support-site build). Commands are stable names that later issues and CI cite; their internals may evolve.

### Failure and recovery behavior

Commands fail loudly with actionable messages on unsupported tool versions, missing prerequisites, or absent optional credentials (clearly distinguishing "cannot build for device without signing" from "broken checkout"). Setup documentation includes common failure recovery steps. No command mutates state outside the repository and its build directories.

### Security and privacy

No credentials, tokens, keystores, or signing materials in the repository; the example environment file contains placeholders only. Secret scanning and ignore rules gate iOS signing materials, Android keystores, `.env` files, raw restricted datasets, and personal test exports. Production endpoint configuration binds only to `127.0.0.1`. The default app performs no telemetry or network calls.

### Accessibility and performance

N/A — no user-facing UI is produced by this issue. Tooling performance is informational only; budgets are enforced later by DOS-M01-006 against the M00 targets.

## UX and content states

N/A — repository and toolchain work with no product UI. The only human-facing surfaces are documentation (setup, prerequisites, recovery) and command output, which must be plain, actionable American English.

## Test plan

### Automated

- Run every canonical task command in CI from a clean checkout: setup, format check, compile with warnings-as-errors where practical, lint/static analysis, unit tests, dependency audit, fixture-catalog placeholder build, and support-site build; iOS/Android builds where runner capability allows.
- Tool-version guard test: invoke a command under an unsupported version and assert a loud, actionable failure.
- Secret-hygiene test: stage representative forbidden filenames (iOS signing material, Android keystore, `.env`, raw restricted dataset, personal test export) and a secret-like fixture value; assert ignore rules and the scanner gate reject them without a real secret ever being committed.
- Configuration assertion test: production endpoint config binds `127.0.0.1` only.

### Manual/device matrix

- Second developer environment: an engineer other than the author performs the documented setup on a clean machine and reaches green on all safe-without-credentials commands; discrepancies are fixed in the docs before close.
- macOS + Xcode host: verify documented iOS prerequisites produce a development build entry point.
- Android/Gradle host: verify documented Android prerequisites produce a development build entry point.

## Risks, decisions, and open questions

- Risk: Mob `0.7.20` is pre-1.0; generator output or dependency constraints may shift. Mitigation: exact pins, committed lockfiles, and documenting any compatibility fix against its M00 decision.
- Risk: "works on my machine" drift between macOS/iOS and Android toolchains. Mitigation: second-developer verification and loud version guards.
- Risk: over-abstracting the task interface. Mitigation: one canonical command per concern, nothing speculative.
- Decision to record here: the exact pinned versions of Erlang/OTP, Elixir, and platform toolchains (must satisfy Mob `0.7.20` requirements, including Elixir 1.19+ per Mob's getting-started documentation).
- Open question: whether any generator file requires an M00-approved compatibility fix; if so, it must be documented, not silently patched.
