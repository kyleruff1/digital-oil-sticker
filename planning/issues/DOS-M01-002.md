## Outcome

A compileable module skeleton and architecture contract isolate deterministic oil-change logic from Mob, the native WebView, concrete Ecto repositories, `mob_notify`, data sources, and LiveView rendering concerns. Bounded contexts, ports, the `DeviceCommandBroker` protocol, no-op/in-memory adapters, an error taxonomy, documented data ownership, and automated dependency enforcement exist and are proven by contract tests.

## Why this matters and what it unblocks

The product must survive Mob changes and platform differences without rewriting calculation or data rules. Explicit boundaries also let QA test offline behavior without physical devices for every case. This issue unblocks all feature epics and prevents ad hoc framework coupling. It is the structural embodiment of master prompt section 4.1's warning: the native WebView bridge and the `MobHook` LiveView bridge are mutually exclusive, `Phoenix.LiveView.Socket` is not `Mob.Socket`, and no implementation ticket may simply pass a Phoenix socket to `MobNotify`.

## Included

- Define bounded contexts/modules for reference catalog, garage/local profile, maintenance records, recommendation/provenance, driving samples/forecast, reminder intent, local persistence, catalog updates, and UI presentation — aligned with the master prompt section 7 context names (`DigitalOilSticker.Catalog`, `Garage`, `Maintenance`, `Forecasting`, `Reminders`, `DataPacks`, `Boot`, `Clock`, plus UI modules).
- Define ports (behaviours) for catalog queries, user-record transactions, clock/timezone, ID generation, notification scheduling, app lifecycle, connectivity/readiness, and optional file export/import. Each port has a documented contract and at least one test double.
- Define the `DeviceCommandBroker` protocol separately from page-level LiveView messaging: command envelope/version, correlation ID, target capability, allowlisted arguments, reply/error envelope, deadline, idempotency, and root-screen generation. The production broker dispatches to the registered root `Mob.Screen`; fake adapters answer without Mob.
- Implement no-op/in-memory adapters and contract-test fixtures; production platform adapters remain thin and contain Mob/WebView/`Mob.Socket`/`mob_notify` types only in the root-screen adapter, while persistence adapters own Ecto schemas/queries. `Phoenix.LiveView.Socket` is never accepted by a native-plugin adapter contract.
- Define command/query boundaries and an error taxonomy: validation error, missing data, unsupported platform capability, unavailable/permission denied, quota/corruption, migration required, and unexpected failure. Every error that can reach the UI maps to one taxonomy entry.
- Record data flow and ownership. Derived due dates are recomputable projections; oil-change history and user settings are source records; OS notifications are disposable projections of reminder intent.
- Add architecture checks or dependency rules so domain modules cannot import UI, Mob, WebView/native, network, `mob_notify`, or concrete Ecto persistence modules — enforced automatically, not by convention.

## Technical implementation contract

### Components and ownership boundaries

Domain contexts own rules and calculations and depend only on ports. Persistence adapters own Ecto schemas/queries for the two repositories defined in DOS-M01-003. The root-screen adapter (`DigitalOilSticker.MobScreen` plus the production `DeviceCommandBroker`) is the only module set containing Mob/WebView/`Mob.Socket`/`mob_notify` types. LiveView modules own presentation only and speak to domain contexts through their public APIs. Plugin-specific values never leak into domain modules.

### Data and persistence

This issue defines interfaces, not schemas: user-record transaction and catalog-query ports are specified against the DOS-M01-003 schema contract. In-memory adapters simulate persistence for contract tests. External source records retain provenance. The ownership rule from master prompt section 8 is encoded: catalog data is replaceable/versioned, user data is durable and never overwritten by catalog refresh.

### Interfaces and events

- Ports: catalog queries, user-record transactions, clock/timezone, ID generation, notification scheduling, app lifecycle, connectivity/readiness, optional file export/import.
- `DeviceCommandBroker` envelope: versioned command, correlation ID, target capability, allowlisted arguments, deadline, idempotency, reply/error envelope, root-screen generation.
- Local event contract (direct context return plus Phoenix PubSub where more than one active process needs it) reserved for at least `vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, and `catalog_activated`. Events carry local stable IDs and reason codes, not display strings.

### Failure and recovery behavior

Broker behavior is specified and contract-tested for: root-screen registration and restart (generation change), duplicate reply, timeout/deadline expiry, unsupported command, and malformed payload. Errors reaching the UI are typed taxonomy values that map to actionable states, not raw exceptions. Adapters reporting reduced capability degrade features without corrupting domain state; in-app due status never depends on native capability.

### Security and privacy

Acknowledgements crossing the broker are redacted; plugin-specific and device-specific values never enter domain modules or logs. No port may introduce network access; the connectivity/readiness port reports state, it does not fetch. Personal records are created/read/updated/deleted entirely through the local repository interface. Fixtures contain no personal or restricted data.

### Accessibility and performance

N/A — no user-facing UI in this issue beyond contracts. Determinism and boundary rules are the performance-relevant deliverables: domain tests must run fast, offline, and without device dependencies, which is what enables broad QA coverage later.

## UX and content states

N/A — architecture skeleton only. The error taxonomy is the UX-relevant deliverable: it guarantees every UI state in later milestones (denied notifications, absent recommendations, unavailable storage, migration required) has a typed, mappable origin instead of ad hoc strings.

## Test plan

### Automated

- Contract-test suite executed against every in-memory/no-op adapter and the selected local-store adapter skeleton, shared so production adapters run the same suite later.
- Broker protocol tests: registration/restart with generation change, duplicate reply, timeout, unsupported command, malformed payload; plus a compile/type-level failure proving a `Phoenix.LiveView.Socket` cannot satisfy a `Mob.Socket` capability contract.
- Determinism tests: fixed `Clock` and timezone injection produce identical outputs for identical fixtures.
- Error-mapping tests for denied notifications, absent recommendations, and unavailable storage.
- Architecture-enforcement test: introduce a deliberate forbidden import (domain → UI, Mob, WebView/native, network, `mob_notify`, or concrete Ecto persistence) and assert the gate fails.

### Manual/device matrix

- Design review: architecture document walkthrough with domain, UI, data, and QA owners; sign-off recorded on the issue.
- Where harnesses are available, run the same deterministic fixture through web (local development), iOS, and Android test targets and compare outputs; physical-device execution beyond available harnesses defers to DOS-M01-005/DOS-M01-006 evidence paths.

## Rollout and rollback

## Risks, decisions, and open questions

- Risk: over-abstraction — ports that serve no roadmap use case. Mitigation: the Excluded list bans speculative generic abstractions; every port maps to a named consumer in M01, M04, M05, or M06.
- Risk: the broker protocol under-specifies real Mob behavior discovered later on device. Mitigation: DOS-M01-005 exercises the production path; protocol changes go through an ADR amendment, not silent edits.
- Risk: architecture enforcement tooling gaps in the Elixir ecosystem. Mitigation: the acceptance criterion is behavioral (a deliberate violation fails); the mechanism may be any reliable check.
- Decision to record: the concrete enforcement mechanism for dependency rules.
- Open question: the exact set of allowlisted broker capabilities for M01 (at minimum, what DOS-M01-005's diagnostics need); additions later require contract versioning.
