> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The "platform adapter" port is no longer a native bridge but a browser-storage port whose only implementation is the JS hook plus IndexedDB adapter, with a test double for server-side tests._

## Outcome

A compilable module skeleton and architecture contract isolate deterministic domain code (Catalog, Garage, Maintenance, Forecasting, Reminders) from `Phoenix.LiveView`, from the browser-storage transport (IndexedDB via a `LocalStore` `phx-hook`), from the sole server-side Ecto adapter (`DigitalOilSticker.CatalogRepo`, opened read-only), from the HTTP/WSS transport, and from rendering. Bounded contexts, ports (behaviours), the `LocalStore` behaviour and its `pushEvent`/`push_event` message contract, an in-memory test-double adapter, an error taxonomy, documented data ownership under [INV-23](../../docs/product/CONSTITUTION.md) and [INV-24](../../docs/product/CONSTITUTION.md), and automated dependency enforcement exist and are proven by contract tests. The design mechanically enforces ADR-0004 §"Enforcement": no domain module references `Phoenix.LiveView`, `Plug`, or `LocalStore.*` protocol modules; the deployed application's Ecto repo list is exactly `[CatalogRepo]` and its connection is opened read-only; a scripted-session log-scan finds no personal value in any log line.

## Why this matters and what it unblocks

Under ADR-0004 the product's core value (the vendored catalog) is served from the server while every personal record lives client-side in IndexedDB. The seam between them — the [INV-24](../../docs/product/CONSTITUTION.md) hydration protocol — is the highest-risk new component of the entire browser MVP and had **zero** coverage in the pre-pivot roadmap. This card is where the seam becomes a specified contract instead of implementation taste: the `LocalStore` behaviour and its hook message set become one of a small set of released ports, and the "no personal rows on the server" claim ([INV-3](../../docs/product/CONSTITUTION.md), [INV-23](../../docs/product/CONSTITUTION.md)) becomes structurally enforceable rather than aspirational.

Every M02 UX card, every M04 persistence card, every M05 single-vehicle flow, and every M07 hardening test descends from these contracts. Downstream, `DOS-M09-002` implements the IndexedDB adapter behind the `LocalStore` behaviour; `DOS-M09-003` exercises the full hydration/mutation protocol end-to-end and adds multi-tab consistency; `DOS-M09-005` builds the impersonal catalog-query layer on top of the `CatalogRepo` boundary this card fixes; `DOS-M09-008` turns the "no personal rows" rule and the log-scrub rules into release gates that plug into the enforcement mechanism scaffolded here.

## Included

- **Bounded-context module map** for the browser MVP: `DigitalOilSticker.Catalog` (server-side read-only), `.Garage`, `.Maintenance`, `.Forecasting`, `.Reminders` (in-app due-state computation only, per INV-17), `.LocalStore` (the browser-storage port), `.Clock`, `.Boot`. LiveView modules are presentation only and speak to domain contexts through their public APIs. **No pre-pivot on-device-bridge module survives** (see the historical section for the specific module names) — see FR-1 addressing sweep finding 1.
- **Ports (behaviours)** for: catalog queries (over `CatalogRepo`), `LocalStore` (browser storage), `Clock`/timezone, ID generation (client-generated UUIDv4 per ADR-0004 §"Storage layout"), in-app due-state computation, the export/import file pipeline, and a **LiveView socket-lifecycle port** (mount, hydrate, reconnect, terminate) that composes with the INV-24 hydration protocol — see FR-2 addressing sweep finding 2. Each port has a documented contract and at least one test double.
- **The `LocalStore` behaviour and its `pushEvent`/`push_event` message contract:** `local_store:hydrate`, `local_store:put`, `local_store:ack`, `local_store:conflict`, using the envelope shape from ADR-0004 §"Payload envelope" (`envelope`, `schema_version`, `seq`, `tab_id`, `generated_at`, `data`). Server-side, the behaviour is satisfied by an **in-memory Elixir test double**; the **sole production implementation** is the JS phx-hook plus IndexedDB adapter, owned by `DOS-M09-002`.
- **Server-side rules made mechanically enforceable** per ADR-0004 §"Enforcement": (a) a test asserting the deployed application's Ecto repo list is exactly `[CatalogRepo]` and that its connection is opened read-only; (b) a static check that no module under the domain namespaces references `Phoenix.LiveView`, `Plug`, or `LocalStore.*` protocol modules; (c) the assigns-only rule that personal state never touches disk, database, cache, ETS, external store, or log; (d) a scripted-session log-scan scaffold (fully exercised by `DOS-M09-008`).
- **Hosted-endpoint hardening port surface** (production implementations belong to `DOS-M09-008`, but the ports are defined here so the domain never touches them directly): (a) an origin allowlist consumed by Phoenix `check_origin`; (b) a CSP header composer whose default forbids `'unsafe-inline'` and every third-party origin (INV-22); (c) session-cookie invariants (contents allowlist = `_csrf_token` + `live_socket_id`; `Secure` + `HttpOnly` + `SameSite=Lax` + short `max_age`); (d) a `Logger` filter that drops `handle_event` params by default with an explicit non-personal allowlist; (e) rate-limit hook points on socket connects, catalog search events, and hydrate/import events.
- **Error taxonomy**: validation error, missing catalog data, storage unavailable, quota exceeded, hydration deadline exceeded, migration required (client-older-than-server), read-only mode (client-newer-than-server), conflict/stale-`seq`, unexpected failure. Every error that reaches the LiveView renders through this taxonomy — raw exceptions do not cross the presentation boundary.

- **FR-7** (retained from pre-pivot FR-7, restated under INV-23/INV-24): Data ownership is documented. - **FR-10** (replaces pre-pivot FR-10; addresses INV-24.3–24.8): The `LocalStore` port and its LiveView consumers surface **four distinct assigns states** — `:hydrating`, `:empty`, `:storage_unavailable`, and `:data_missing` — as defined by ADR-0004 §"First-paint and empty-state rules". - **FR-11** (NEW, addresses the pivot line's "hosted-endpoint hardening ports"): The hardening port surface is defined so that the domain never composes CSP headers, cookies, or rate-limit tokens directly. - **FR-12** (NEW, addresses INV-26 and INV-27): The catalog-query port's callback signatures accept **only impersonal selectors** (year/make/model/trim/engine) and never a VIN, odometer, note, record identifier, or any client identifier. ## Technical implementation contract

### Components and ownership boundaries

Domain contexts (`DigitalOilSticker.Catalog`, `.Garage`, `.Maintenance`, `.Forecasting`, `.Reminders`, `.Clock`) own rules and calculations and depend only on ports. The `CatalogRepo` Ecto adapter is the **sole** server-side database attachment and is opened read-only. The `LocalStore` port is the **only** path between the LiveView server and browser-held personal data; its production adapter is the JS phx-hook plus IndexedDB module owned by `DOS-M09-002`, and its test double is an in-memory Elixir module. LiveView modules are the presentation layer and speak to domain contexts through their public APIs; personal state exists in `socket.assigns` for one connection's lifetime. No module contains pre-pivot on-device-bridge types (see the historical section for the specific namespaces) — those namespaces are absent from the tree.

### Data and persistence

Per ADR-0004: `CatalogRepo` is a SQLite database baked into the deploy image, opened read-only (SQLite read-only open mode). Personal state has **no** server-side persistence path — no schema, no migration, no table, no cache, no ETS, no external store. The `LocalStore` behaviour is contract-tested against an in-memory adapter that mirrors the envelope shape (`schema_version`, monotonic `seq`, per-store CRUD) and the compare-and-set on `meta.seq`. The IndexedDB schema layout, its schema-version line, and forward-migration functions are `DOS-M09-001`'s deliverable; this card only depends on the envelope contract that `DOS-M09-001` will honor.

### Interfaces and events

- **Ports:** catalog queries, `LocalStore`, `Clock`/timezone, ID generation, in-app due-state computation, export/import file pipeline, LiveView socket-lifecycle.
- **`LocalStore` message set** (server ⇄ hook):
  - `local_store:hydrate` — hook → server; carries the full envelope on mount and reconnect.
  - `local_store:put` — server → hook; carries `{mutation_id, seq, upserts, deletes}`.
  - `local_store:ack` — hook → server; carries `{mutation_id, seq, status}`.
  - `local_store:conflict` — hook → server; stale-`seq` compare-and-set failure requesting re-hydrate.
- **Local event contract** (direct context return plus Phoenix PubSub where more than one process needs it): `vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled` (in-app only), `catalog_activated`. Events carry local stable IDs and reason codes, not display strings. There is **no** cross-user PubSub topic for personal events because there is no server-side personal state to publish.

### Failure and recovery behavior

The `LocalStore` port contract-tests cover: successful hydrate; hydrate with invalid envelope (validation error → `:storage_unavailable` distinct from `:empty`); hydrate deadline expiry; older-`schema_version` payload triggering server migration plus write-back; newer-`schema_version` payload entering read-only mode with an explicit banner (no writes); mutation ack success; mutation ack error (persistent "Not saved to this browser" state with pending value visible); mutation ack timeout (same); `local_store:conflict` on stale-`seq` compare-and-set (server discards optimistic assign, triggers re-hydration, shows visible notice); and **idempotence** — hydrating the same payload twice produces identical assigns and emits no write-back (ADR-0004 §"Enforcement" bullet 4).

### Security and privacy

Per ADR-0004 §"Security and privacy boundary for a hosted application" and INV-22:
- HTTPS everywhere; WSS for the LiveView socket; `force_ssl` on; HSTS enabled after certificate verification.
- `check_origin` restricted to production hostnames — never `true`, never `false`.
- `protect_from_forgery` on all HTTP routes; LiveView `_csrf_token` on the socket connect.
- Session cookies carry only `_csrf_token` and `live_socket_id`; `Secure`, `HttpOnly`, `SameSite=Lax`, short `max_age`; **no** personal values.
- CSP as specified in ADR-0004 §"Content Security Policy" — first-party only, no third-party script/style/font/connect origins, no `'unsafe-inline'`.
- `debug_errors: false` in production; no assigns reach an error page.
- Request-param logging disabled; `filter_parameters` configured; `Logger` filter drops `handle_event` params by default with an explicit non-personal allowlist.
- LiveDashboard disabled in production (process state includes users' vehicles and mileage).

### Accessibility and performance

N/A directly — no user-facing UI in this card. The performance-relevant deliverable is that the port design does not obstruct the [Constitution 2.0.0 §9](../../docs/product/CONSTITUTION.md) sub-second hydration budget (hydration p95 ≤ 300 ms after socket join). The accessibility-relevant deliverable is that the four distinct assigns states in FR-10 (INV-24.3–24.8) are available to every downstream UX card so that live-region announcements and skeleton-vs-empty rendering are possible without ad-hoc string dispatch.

## UX and content states

N/A directly — architecture skeleton only. The port design **makes possible** the four states every downstream UX card must render (INV-24.3–24.8):

- `:hydrating` — skeleton; never an empty-garage claim.
- `:empty` — genuine first visit; distinguishable in copy from `:data_missing`.
- `:storage_unavailable` — private-browsing or blocked storage; explicit banner **before** any data entry (INV-24.6).
- `:data_missing` — `dos_boot_state == "has_data"` but hydration returned zero records; offer import; never a fresh empty garage (INV-25).

The error taxonomy (FR-6) is the UX-relevant deliverable: it guarantees every INV-25 storage-loss surface has a typed, mappable origin instead of ad-hoc strings.

## Test plan

- **Risk:** over-abstraction — ports that serve no roadmap use case. **Mitigation:** the Excluded list bans speculative abstractions; every port maps to a named consumer in M09-* or `DOS-M04-005`.
- **Risk:** the `LocalStore` behaviour under-specifies real IndexedDB behavior discovered later (browser eviction quirks, private-mode edge cases, quota reporting variance). **Mitigation:** `DOS-M09-002` exercises the production path; behaviour changes go through an ADR-0004 amendment, not silent edits.
- **Risk:** the static architecture check misses a violation buried in a metaprogramming path. **Mitigation:** the acceptance criterion is behavioral (a deliberate violation fails); the mechanism may be any reliable check (a `mix xref` graph filter plus a compiler tracer are both acceptable).
- **Risk:** the Ecto-repo-list assertion is trivially bypassed by opening a second repo outside the application supervisor. **Mitigation:** the test also asserts against `Ecto.Repo.all_running/0` at runtime, not only against `Application.get_env/2`, and against the read-only connection mode.
- **Decision to record:** whether the `LocalStore` behaviour's typed errors are Elixir structs or tagged tuples. Both compose with the taxonomy; the tie-breaker is which pattern the LiveView layer will pattern-match on cleanly.
- **Open question:** whether the LiveView socket-lifecycle port needs an explicit `terminate/2` callback for cleanup, or whether relying on Phoenix's built-in `terminate/2` on the LiveView is enough. Resolved in `DOS-M09-003` once the full lifecycle is exercised.
- **Open question:** the exact allowlist for the non-personal `handle_event` names that the `Logger` filter permits. Additions later require the log-scrub scripted-session test to be re-run.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

Domain contexts own rules and calculations and depend only on ports. Persistence adapters own Ecto schemas/queries for the two repositories defined in DOS-M01-003. The root-screen adapter (`DigitalOilSticker.MobScreen` plus the production `DeviceCommandBroker`) is the only module set containing Mob/WebView/`Mob.Socket`/`mob_notify` types. LiveView modules own presentation only and speak to domain contexts through their public APIs. Plugin-specific values never leak into domain modules.

#### Data and persistence

This issue defines interfaces, not schemas: user-record transaction and catalog-query ports are specified against the DOS-M01-003 schema contract. In-memory adapters simulate persistence for contract tests. External source records retain provenance. The ownership rule from master prompt section 8 is encoded: catalog data is replaceable/versioned, user data is durable and never overwritten by catalog refresh.

#### Interfaces and events

- Ports: catalog queries, user-record transactions, clock/timezone, ID generation, notification scheduling, app lifecycle, connectivity/readiness, optional file export/import.
- `DeviceCommandBroker` envelope: versioned command, correlation ID, target capability, allowlisted arguments, deadline, idempotency, reply/error envelope, root-screen generation.
- Local event contract (direct context return plus Phoenix PubSub where more than one active process needs it) reserved for at least `vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, and `catalog_activated`. Events carry local stable IDs and reason codes, not display strings.

#### Failure and recovery behavior

Broker behavior is specified and contract-tested for: root-screen registration and restart (generation change), duplicate reply, timeout/deadline expiry, unsupported command, and malformed payload. Errors reaching the UI are typed taxonomy values that map to actionable states, not raw exceptions. Adapters reporting reduced capability degrade features without corrupting domain state; in-app due status never depends on native capability.

#### Security and privacy

Acknowledgements crossing the broker are redacted; plugin-specific and device-specific values never enter domain modules or logs. No port may introduce network access; the connectivity/readiness port reports state, it does not fetch. Personal records are created/read/updated/deleted entirely through the local repository interface. Fixtures contain no personal or restricted data.

#### Accessibility and performance

N/A — no user-facing UI in this issue beyond contracts. Determinism and boundary rules are the performance-relevant deliverables: domain tests must run fast, offline, and without device dependencies, which is what enables broad QA coverage later.

### UX and content states (pre-pivot)

N/A — architecture skeleton only. The error taxonomy is the UX-relevant deliverable: it guarantees every UI state in later milestones (denied notifications, absent recommendations, unavailable storage, migration required) has a typed, mappable origin instead of ad hoc strings.
