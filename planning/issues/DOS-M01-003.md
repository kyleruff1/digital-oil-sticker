## Outcome

An approved logical data model, two explicitly configured `ecto_sqlite3` repositories, executable initial migrations, and a migration contract support a compact searchable reference catalog plus durable local-only user records without coupling either lifecycle to the other. `CatalogRepo` is the replaceable, versioned reference layer; `UserRepo` is the durable local layer that a catalog refresh never overwrites.

## Why this matters and what it unblocks

Vehicle selection, product compatibility, history, calculations, and reminders all depend on stable identifiers and provenance. Adding columns ad hoc would make bundled-catalog updates and device migrations unsafe. This issue unblocks ingestion (DOS-M01-004 and all of M03) and every persistent feature (M04 onward). It also freezes the two-lifecycle boundary early enough that no feature code can ever assume a single database or cross-database foreign keys.

## Included

- Model `CatalogRepo` as the versioned reference layer sufficient for: catalog metadata/version; market; model year; make; model; vehicle variant/series; engine/powertrain attributes when sourced; aliases/search terms; maintenance recommendations; oil specification/product claims; filter fitments; sources/licenses/revisions; and confidence/applicability links — consistent with the master prompt section 8 table baseline.
- Model `UserRepo` as the separate local-user layer sufficient for: installation/local-profile settings; the MVP active vehicle with schema room for post-MVP additional vehicles; nickname and selected catalog reference or custom snapshot; odometer unit; oil-change events; oil/filter selections or free-text snapshots; driving samples/profile; forecast policy/version; reminder intent; and migration/audit timestamps.
- Use stable surrogate IDs within a catalog version plus durable external/source keys where provided. User records referencing catalog rows must retain a minimal immutable display snapshot so catalog retirement does not make history unreadable.
- Define nullability versus "unknown," unit representation, ISO dates/local timezone identifiers, integer odometer storage, decimal conversion rules, soft/archive behavior, uniqueness, foreign keys, indexes, and cascades. A missing interval is never encoded as zero. Persisted mileage uses integer base units with conversion at the boundary so switching miles/kilometers never loses precision; UTC instants are stored with the IANA time zone used to derive local times, and service dates are stored as dates when time-of-day is not meaningful.
- Create separate forward-only migration paths/schema-version records for `CatalogRepo` and `UserRepo`. User migrations are transactional; catalog construction/replacement is build-then-validate/copy-and-swap. Define when a destructive user transformation requires an on-device safety copy.
- Provide a data dictionary and example rows for exact, ambiguous, missing, custom, retired, and conflicting-source cases.

## Excluded

- Full production catalog population, unapproved source fields, cloud/user/auth tables, arbitrary JSON as a substitute for modeled query fields, or physical optimization unsupported by benchmark data.
- Live data acquisition or fixture-build implementation (DOS-M01-004 / M03) and feature CRUD behavior (M04).
- FTS tables before the Mob/exqlite build proves FTS5 support; cascading indexed selectors must work without FTS.

- FR-1: Two explicitly configured `ecto_sqlite3` repositories exist (`CatalogRepo`, `UserRepo`), each with `pool_size: 1`, separate storage files, separate migration paths, and separate schema-version records; no cross-database foreign keys exist.
- FR-2: `CatalogRepo` migrations create the versioned reference layer covering catalog metadata/version, market, model year, make, model, vehicle variant/series, engine/powertrain attributes when sourced, aliases/search terms, maintenance recommendations, oil specification/product claims, filter fitments, sources/licenses/revisions, and confidence/applicability links, preserving the master prompt section 8 field/constraint baseline (including stable IDs, nullable provider IDs, normalized-name indexes, and `vehicle_configurations` completeness codes where unknown is nullable, not false).
- FR-3: `UserRepo` migrations create the local-user layer covering installation/local-profile settings, the MVP active vehicle with schema room for post-MVP additional vehicles, nickname and selected catalog reference or custom snapshot, odometer unit, oil-change events, oil/filter selections or free-text snapshots, driving samples/profile, forecast policy/version, reminder intent, and migration/audit timestamps — multi-vehicle-safe from the first migration.
- FR-4: Stable surrogate IDs are unique within a catalog version; durable external/source keys are stored where provided; user rows referencing catalog rows retain a minimal immutable display snapshot.
- FR-5: The model documents nullability versus "unknown," unit representation, ISO dates and IANA local timezone identifiers, integer odometer storage in a documented fixed base unit, decimal conversion rules, soft/archive behavior, uniqueness, foreign keys, indexes, and cascades; a missing interval is never encoded as zero.
- FR-6: Migrations are forward-only, monotonic, idempotence-checked, and cannot silently downgrade; user migrations are transactional; catalog construction/replacement is build-then-validate/copy-and-swap; the conditions requiring an on-device safety copy before a destructive user transformation are defined.
- FR-7: A field-level data dictionary with example rows covers exact, ambiguous, missing, custom, retired, and conflicting-source cases.
- FR-8: Every recommendation and compatibility claim representable in the schema points to provenance and applicability; historical oil-change events snapshot what the user saw/entered at the time.
- FR-9: Schema names avoid source-specific assumptions so a future source change does not force renames.
- FR-10: Expected full-catalog size and representative query plans stay within the DOS-M00-004 budgets.

## Technical implementation contract

### Components and ownership boundaries

Persistence adapters (per DOS-M01-002) own the Ecto schemas, changesets, and queries for both repositories. Domain contexts consume them only through ports. The WebView does not access either database file directly. Migration modules live in the separate per-repository migration paths established by DOS-M01-001's directory layout.

### Data and persistence

- `CatalogRepo`: replaceable/versioned; records are immutable within one `data_version`; opened read-mostly; replaced only by build-then-validate/copy-and-swap (mechanics in DOS-M01-004/DOS-M01-005; protocol defined here).
- `UserRepo`: durable; migrated in place transactionally or copy-and-swapped; never overwritten by a catalog refresh.
- Integer base units for persisted mileage with boundary conversion; UTC instants plus stored IANA time zone; dates without time-of-day where meaningful; explicit `pool_size: 1`; uniqueness, foreign keys (within each database only), indexes, and cascades as specified in the dictionary.

### Interfaces and events

The schemas define the persistence contract behind DOS-M01-002's catalog-query and user-record-transaction ports. Schema-version records in each repository are the interface DOS-M01-005's boot sequence and future migrations consult. No runtime events are emitted by this issue.

### Failure and recovery behavior

A failed user migration leaves data intact via transaction rollback or copy-and-swap recovery; a mid-migration crash never yields a half-migrated readable state. Migration attempts and outcomes are recordable in `schema_events` with version and non-sensitive result. Catalog validation failure means the candidate artifact is rejected before activation, never a partially replaced catalog.

### Security and privacy

No cloud, user-account, or auth tables exist. Optional local-only VIN storage requires explicit consent per the section 8 `vehicles` baseline and is avoided by default. Fixtures and example rows contain no personal data and no real VINs. Log/fixture redaction rules from master prompt section 7 apply to anything derived from these tables.

### Accessibility and performance

N/A for accessibility — no UI. Performance: indexes support the cascading year → make → model → configuration selectors without FTS; representative query plans and expected full-catalog size are measured against DOS-M00-004 budgets; physical optimization beyond that evidence is excluded.

## Test plan

### Automated

- Migration matrix: run migrations from empty to current, from each prior fixture version to current, twice against current (idempotence check), and with an injected mid-migration failure asserting rollback/recovery.
- Constraint/index tests: uniqueness, foreign keys, cascades, nullability, and the "missing interval is never zero" rule.
- Representative query-plan checks for the cascading selector and lookup paths; row-count/hash checks on fixture data.
- Catalog-swap preservation test: replace a fixture catalog version and assert garage links survive via stable mapping or retained snapshots.
- Unit-representation tests: integer base-unit mileage round-trips through miles and kilometers without precision loss; UTC instant plus IANA zone round-trips.

### Manual/device matrix

- Joint dictionary review with data, domain, UX, and QA owners; approval recorded on the issue.
- Verification on at least one physical or emulated device build that both SQLite files are created in the approved app-support locations (full device coverage lands in DOS-M01-005).

## Rollout and rollback

Initial migrations land through reviewed pull requests. No installed user base exists yet, so rollback is source-control revert plus regenerating local development databases. From this issue forward, schema changes require new forward-only migrations under the migration contract — never edits to shipped migrations — and destructive user transformations require the defined on-device safety copy.

## Risks, decisions, and open questions

- Risk: schema decisions made before production data (M03) reveal missing fields. Mitigation: M03/M04 may refine names and add fields via forward migrations; the boundaries and semantics frozen here are deliberately minimal and baseline-conformant.
- Risk: SQLite/`ecto_sqlite3` behavior differences from development assumptions (transactional DDL limits, FTS5 availability). Mitigation: migration matrix tests run on the real driver; FTS stays excluded until proven on the Mob/exqlite build.
- Decision to record: the documented fixed base unit for integer mileage storage and its conversion rules.
- Decision to record: the exact conditions that classify a user transformation as destructive and require a safety copy.
- Open question: which prior fixture versions constitute the upgrade-path test set at this stage (before any shipped release, the set may be empty plus the current baseline; the matrix must grow with each shipped schema version).
