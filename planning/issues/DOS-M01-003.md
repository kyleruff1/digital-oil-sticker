> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): "`CatalogRepo` stays server-side Ecto/SQLite unchanged; `UserRepo` stops being an Ecto schema and becomes an IndexedDB object-store layout with an independent version line."

## Outcome

The deployed Phoenix application opens **exactly one** Ecto repository — `DigitalOilSticker.CatalogRepo`, an `ecto_sqlite3` connection to the read-only catalog artifact baked into the Fly image — and there is **no `UserRepo` in the deployment**. `CatalogRepo` has an explicit configuration (read-only mode at the SQLite level, `pool_size: 1`, its own migration path, its own schema-version record), a forward-only migration contract, no cross-schema references of any kind, and an executable initial migration set that stands up the versioned reference layer described in [INV-8](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-9](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-10](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-11](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-15](../../docs/product/CONSTITUTION.md#5-core-user-promise), and [INV-16](../../docs/product/CONSTITUTION.md#5-core-user-promise). The "no personal row on the server" guarantee of [INV-3](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage) and [INV-23](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage) is enforced structurally by this configuration — a test asserts the deployed application's Ecto repo list is exactly `[CatalogRepo]`, the connection is opened read-only, and no personal-data table, migration, or schema exists in the server codebase. The IndexedDB object-store layout that replaces the pre-pivot `UserRepo` is out of scope here and is owned by [DOS-M09-001](DOS-M09-001.md) under its own forward-only version line.

## Why this matters and what it unblocks

Vehicle identity, intervals, oil requirements, filter fitments, confidence tiers, and support statuses are the vendored data that is the product's core value ([ADR-0003](../../docs/architecture/ADR-0003-data-boundaries.md), [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §Context). All of them are served from `CatalogRepo`. Freezing its schema, its migration contract, and its "one repo only, read-only, pool_size: 1" boot posture at M01 is what lets every downstream server-side milestone — catalog ingest (M03), the read-only server-side catalog query layer ([DOS-M09-005](DOS-M09-005.md)), and the atomic catalog activation flow inside a Fly release ([DOS-M04-008](DOS-M04-008.md) as re-scoped) — implement against a decided contract instead of re-litigating it.

It also freezes the boundary that [INV-3](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), [INV-4](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), and [INV-23](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage) exist to protect: there is no server-side `UserRepo`, no personal-data table, no personal-data migration, and no personal-data schema module anywhere in the deployed application, and this issue is where that becomes a mechanically enforced release gate rather than a convention. The browser-side counterpart of the retired server `UserRepo` — an IndexedDB object-store layout with its own monotonic version line and its own forward-only upgrade contract — belongs to [DOS-M09-001](DOS-M09-001.md); this issue does not restate it and does not depend on it having landed.

- Add the mechanical "no server `UserRepo`" enforcement: a test that walks the application supervision tree and Ecto repo list and asserts both exactly `[CatalogRepo]`, a static check that no module under `DigitalOilSticker.*` defines a personal-data Ecto schema, and a redirect note in the data dictionary pointing browser storage schema questions at [DOS-M09-001](DOS-M09-001.md).

## Functional requirements

- FR-1 *(rewritten from pre-pivot FR-1; addresses sweep finding 1)*: Exactly one `ecto_sqlite3` repository, `DigitalOilSticker.CatalogRepo`, is opened by the deployed application. Its configuration MUST include: SQLite read-only mode at the connection level, `pool_size: 1`, a dedicated migration path, and a dedicated schema-version record. It MUST have no cross-schema references to any personal-data schema (none exist in the deployment). The deployed Ecto repo list MUST be exactly `[DigitalOilSticker.CatalogRepo]`, verified by an application-boot assertion **and** by a release-gating test that reads the running application's repo list ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Enforcement", first bullet). Starting any other repo — a `UserRepo`, an analytics repo, a session repo — is a build failure, not a runtime warning.
- FR-2: `CatalogRepo` migrations create the versioned reference layer covering catalog metadata/version, market, model year, make, model, vehicle variant/series, engine/powertrain attributes when sourced, aliases/search terms, maintenance recommendations, oil specification/product claims, filter fitments, sources/licenses/revisions, and confidence/applicability links, preserving the master prompt section 8 field/constraint baseline (including stable IDs, nullable provider IDs, normalized-name indexes, and `vehicle_configurations` completeness codes where unknown is nullable, not false; [INV-11](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-15](../../docs/product/CONSTITUTION.md#5-core-user-promise)).
- FR-3 *(retires pre-pivot FR-3; addresses sweep finding 1)*: **No server-side `UserRepo` exists.** This card MUST NOT define, migrate, seed, or reference any personal-data table, personal-data Ecto schema, or personal-data migration in the server codebase. The browser-side counterpart — an IndexedDB object-store layout for the garage, service events, odometer readings, usage samples, reminder intent, and preferences, with its own monotonic schema version and forward-only upgrade path — is owned by [DOS-M09-001](DOS-M09-001.md) and specified there. A test asserts the server codebase contains no personal-data Ecto schema module and that `DATA_DICTIONARY.md` redirects browser storage schema questions at [DOS-M09-001](DOS-M09-001.md).
- FR-4: Stable surrogate IDs are unique within a catalog `data_version`; durable external/source keys are stored where provided. Because there is no server-side `UserRepo`, the "user rows referencing catalog rows retain a minimal immutable display snapshot" rule of the pre-pivot spec is no longer a `CatalogRepo` obligation and moves to the browser storage schema at [DOS-M09-001](DOS-M09-001.md) (which requires every historical browser record to carry a stable catalog reference **and** an immutable human-readable snapshot). `CatalogRepo` MUST expose the stable catalog reference fields the browser records need to snapshot from, and MUST NOT retire a stable ID silently — support-status transitions ([INV-11](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default)) are the only way a catalog reference changes meaning across releases.
- FR-5: The model documents nullability versus "unknown," unit representation, ISO dates and IANA local timezone identifiers where they appear in catalog rows, integer base-unit storage where mileage-like values appear (e.g. threshold intervals), decimal conversion rules, soft/archive behavior, uniqueness, foreign keys **within `CatalogRepo` only**, indexes, and cascades; a missing interval is never encoded as zero ([INV-11](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-15](../../docs/product/CONSTITUTION.md#5-core-user-promise)).
- FR-6 *(splits pre-pivot FR-6; addresses sweep finding 2)*: `CatalogRepo` migrations are forward-only, monotonic, idempotence-checked, and cannot silently downgrade. Catalog construction and replacement follow the "build-then-validate/copy-and-swap" rule, specialized here to the Fly image and to a `data_version` release: the candidate catalog artifact is built and validated in CI, then activated by rolling a new Fly image forward; a partially replaced catalog is never observable at runtime; catalog validation failure means the candidate artifact is rejected before activation ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Catalog database on Fly"; atomic activation mechanics belong to [DOS-M04-008](DOS-M04-008.md) as re-scoped). The pre-pivot sentences that required user-side Ecto transactions and a pre-transformation safety copy of the local user database are **deleted** — they assume a server-owned or client-owned `UserRepo` with Ecto transaction semantics, which no longer exists. IndexedDB has no cross-store transactions of that shape, no rollback beyond a single request, and no server participation; forward-only IndexedDB migration semantics are respecified in [DOS-M09-001](DOS-M09-001.md) FR-7 through FR-10 (ordered idempotent upgrade steps under `onupgradeneeded`, all-or-nothing version-change transaction, no rollback path, newer-than-deployment read-only mode with export offered).
- FR-7: A field-level data dictionary with example rows covers exact, ambiguous, missing, custom, retired, and conflicting-source cases **for `CatalogRepo` fields only**. Example rows contain no personal data and no real VINs ([INV-4](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)). The dictionary carries a redirect note pointing browser storage schema questions at [DOS-M09-001](DOS-M09-001.md).
- FR-8: Every recommendation and compatibility claim representable in the schema points to provenance and applicability ([INV-15](../../docs/product/CONSTITUTION.md#5-core-user-promise)). The "historical oil-change events snapshot what the user saw/entered at the time" clause is a browser-storage obligation and moves to [DOS-M09-001](DOS-M09-001.md) FR-4; `CatalogRepo` merely guarantees that the fields the browser snapshots from — stable catalog IDs, human-readable strings, support status, provenance labels — are present and stable enough to be snapshot-worthy.
- FR-9: Schema names in `CatalogRepo` avoid source-specific assumptions so a future source change does not force renames.
- FR-10: Expected full-catalog size and representative query plans stay within the [DOS-M00-004](DOS-M00-004.md) budgets and are shaped to let [DOS-M09-005](DOS-M09-005.md) meet the §9 catalog query p95 targets. The index set supports the cascading year → make → model → configuration selectors without FTS.
- FR-11 *(new; addresses sweep finding 1)*: `CatalogRepo` MUST carry no field, index, or table that would make a request-time query correlate a person across visits ([INV-26](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)). No table records the VIN, the odometer, the note text, the free-text field, the record identifier, or the stable client identifier of any user. The impersonal query surface is defined at [DOS-M09-005](DOS-M09-005.md); this issue merely guarantees the schema does not offer a field for such a query to land in.
- FR-12 *(new; addresses sweep finding 1)*: The `CatalogRepo` connection MUST be opened read-only at the SQLite level (SQLite's read-only open mode), not only enforced by code discipline. A test drives the running application and asserts the `CatalogRepo` connection rejects a write attempt at the driver level. This is the mechanical enforcement of [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) Decision §4 ("its connection is opened read-only") and closes the "we promise not to write" loophole for the catalog side.

## Technical implementation contract

### Components and ownership boundaries

Persistence adapters (per [DOS-M01-002](DOS-M01-002.md) as re-scoped) own the Ecto schemas, changesets, and read-only queries for `CatalogRepo`. Domain contexts (`DigitalOilSticker.Catalog`, `.Garage`, `.Forecast`) consume them only through ports and never depend on `Phoenix.LiveView`, on the browser-storage protocol, or on any transport ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) Decision §6). Migration modules live in the per-repository migration path established by [DOS-M01-001](DOS-M01-001.md). There is no server-side personal-data adapter, no server-side personal-data schema module, and no server-side personal-data query — because there is no server-side `UserRepo`. The browser-storage adapter is a separate concern owned by [DOS-M09-002](DOS-M09-002.md).

### Data and persistence

- `CatalogRepo`: replaceable/versioned; records are immutable within one `data_version`; opened **read-only at the SQLite level**; `pool_size: 1`; replaced only by build-then-validate/copy-and-swap, specialized to the Fly image (build the artifact in CI, validate it, ship a new deploy image, activate a new `data_version` by rolling forward). Mechanics of atomic activation inside a Fly release live in [DOS-M04-008](DOS-M04-008.md) as re-scoped and [DOS-M09-006](DOS-M09-006.md); this issue defines the rule they must obey.
- **No server-side `UserRepo`.** Personal data exists on the server only as transient values in `socket.assigns` for the lifetime of one LiveView connection, and is never written to disk, database, cache, ETS table, external store, or log ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) Decision §4). The IndexedDB layout that holds the durable copy is [DOS-M09-001](DOS-M09-001.md).
- Integer base units for any mileage-like catalog value (e.g. threshold intervals) with boundary conversion; ISO dates and IANA time zones where dates and instants appear; explicit `pool_size: 1`; uniqueness, foreign keys **within `CatalogRepo` only**, indexes, and cascades as specified in the dictionary.

### Interfaces and events

The `CatalogRepo` schemas define the persistence contract behind [DOS-M01-002](DOS-M01-002.md)'s catalog-query port and behind the read-only server-side catalog query layer at [DOS-M09-005](DOS-M09-005.md). The schema-version record in `CatalogRepo` is the interface [DOS-M09-006](DOS-M09-006.md)'s deploy pipeline and future migrations consult. No runtime events are emitted by this issue. Because no server-side `UserRepo` exists, no user-record transaction port exists on the server side; the corresponding contract on the browser side is owned by [DOS-M09-002](DOS-M09-002.md) and [DOS-M09-003](DOS-M09-003.md).

### Failure and recovery behavior

- Catalog validation failure means the candidate artifact is rejected before activation, never a partially replaced catalog. A failed deploy is rolled back by redeploying the previous image ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Catalog database on Fly"), which restores the old catalog exactly.
- A read-only-mode violation attempted by any code path fails at the SQLite driver level, not by convention.
- User-side failure and recovery — a failed IndexedDB upgrade, an evicted store, a quarantine, a repair — is out of scope here and is respecified in [DOS-M09-001](DOS-M09-001.md) FR-8 through FR-13.

### Security and privacy

- No cloud, user-account, or auth tables exist. No push-subscription, session-durable, or anonymous-ID table exists.
- No personal data ever appears in `CatalogRepo` fixtures or in `CatalogRepo` example rows. No real VINs. `filter_parameters` and log-scrubbing rules from ADR-0004 §"Logging" apply to anything derived from these tables.
- The "no server personal record" claim of [INV-3](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage) and [INV-23](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage) is enforced by three release gates: (a) the "repo list is exactly `[CatalogRepo]`" test, (b) the "no personal-data Ecto schema module exists" static check, and (c) the "CatalogRepo connection is read-only at the driver level" test.

### Accessibility and performance

N/A for accessibility — no UI. Performance: indexes support the cascading year → make → model → configuration selectors without FTS; representative query plans and expected full-catalog size are measured against [DOS-M00-004](DOS-M00-004.md) budgets and shaped to let [DOS-M09-005](DOS-M09-005.md) meet the §9 catalog query p95 targets; physical optimization beyond that evidence is excluded.

## UX and content states

N/A — schema work with no direct UI. The uncertainty vocabulary defined here (unknown versus null versus not-applicable, retired references, conflicting sources) is what later UI states render; the data dictionary's example rows for exact, ambiguous, missing, custom, retired, and conflicting-source cases are the canonical fixtures for those future states ([INV-11](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-15](../../docs/product/CONSTITUTION.md#5-core-user-promise), [INV-20](../../docs/product/CONSTITUTION.md#8-safety-adjacent-copy-ratifies-6-terminology), [INV-21](../../docs/product/CONSTITUTION.md#8-safety-adjacent-copy-ratifies-6-terminology)).

## Rollout and rollback

Initial migrations land through reviewed pull requests. No installed user base exists yet, so rollback of the initial `CatalogRepo` schema is source-control revert plus regenerating local development databases and rebuilding the deploy image. From this issue forward, `CatalogRepo` schema changes require new forward-only migrations under the migration contract — never edits to shipped migrations — and a catalog replacement is a Fly deploy: a new image with a new `data_version` rolls forward and the old one rolls back on demand ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Catalog database on Fly"). There is no client-owned Ecto migration to reconcile and no client-owned Ecto safety copy to define, because there is no client-owned `UserRepo`; the equivalent rule for browser storage — forward-only IndexedDB upgrades with no rollback, and a newer-than-deployment read-only mode — is defined in [DOS-M09-001](DOS-M09-001.md) FR-7 through FR-10.

## Risks, decisions, and open questions

- Risk: schema decisions made before production data (M03) reveal missing fields. Mitigation: M03/M04 may refine names and add fields via forward-only migrations; the boundaries and semantics frozen here are deliberately minimal and baseline-conformant.
- Risk: `ecto_sqlite3` behavior differences from development assumptions (transactional DDL limits, FTS5 availability). Mitigation: the migration matrix runs on the real driver; FTS stays excluded until proven on the exqlite build.
- Risk: a future contributor adds a "convenience" server-side personal-data table (session store, anonymous-ID table, push subscription) without noticing the invariant. Mitigation: the repo-list assertion, the "no personal-data Ecto schema" static check, and the read-only-driver assertion together turn this into a build failure rather than a review escape.
- Risk: catalog replacement via Fly image rollout is coarser-grained than a live catalog copy-and-swap on a single machine; a bad `data_version` reaches every user before a canary catches it. Mitigation: the "build-then-validate" half of the rule runs in CI, and the canary belongs to [DOS-M04-008](DOS-M04-008.md) and [DOS-M09-006](DOS-M09-006.md).
- Decision to record: `CatalogRepo` is opened read-only at the SQLite driver level, not only enforced by code discipline. This closes the "we promise not to write" loophole.
- Decision to record: no server-side `UserRepo` exists in the deployment, and the mechanical enforcement is the repo-list assertion plus the "no personal-data Ecto schema" static check ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Enforcement", first two bullets).
- Decision to record: the "build-then-validate/copy-and-swap" rule now applies to the Fly image and to a `data_version` release; the atomic activation mechanics belong to [DOS-M04-008](DOS-M04-008.md) as re-scoped, not to this card.
- Open question: which prior fixture `data_version`s constitute the upgrade-path test set at this stage (before any shipped release, the set may be empty plus the current baseline; the matrix must grow with each shipped schema version).

### Outcome (pre-pivot)

An approved logical data model, two explicitly configured `ecto_sqlite3` repositories, executable initial migrations, and a migration contract support a compact searchable reference catalog plus durable local-only user records without coupling either lifecycle to the other. `CatalogRepo` is the replaceable, versioned reference layer; `UserRepo` is the durable local layer that a catalog refresh never overwrites.

### Why this matters and what it unblocks (pre-pivot)

Vehicle selection, product compatibility, history, calculations, and reminders all depend on stable identifiers and provenance. Adding columns ad hoc would make bundled-catalog updates and device migrations unsafe. This issue unblocks ingestion (DOS-M01-004 and all of M03) and every persistent feature (M04 onward). It also freezes the two-lifecycle boundary early enough that no feature code can ever assume a single database or cross-database foreign keys.

### Technical implementation contract (pre-pivot)

**Components and ownership boundaries.** Persistence adapters (per DOS-M01-002) own the Ecto schemas, changesets, and queries for both repositories. Domain contexts consume them only through ports. The WebView does not access either database file directly. Migration modules live in the separate per-repository migration paths established by DOS-M01-001's directory layout.

**Data and persistence.** `CatalogRepo`: replaceable/versioned; records are immutable within one `data_version`; opened read-mostly; replaced only by build-then-validate/copy-and-swap (mechanics in DOS-M01-004/DOS-M01-005; protocol defined here). `UserRepo`: durable; migrated in place transactionally or copy-and-swapped; never overwritten by a catalog refresh. Integer base units for persisted mileage with boundary conversion; UTC instants plus stored IANA time zone; dates without time-of-day where meaningful; explicit `pool_size: 1`; uniqueness, foreign keys (within each database only), indexes, and cascades as specified in the dictionary.

**Interfaces and events.** The schemas define the persistence contract behind DOS-M01-002's catalog-query and user-record-transaction ports. Schema-version records in each repository are the interface DOS-M01-005's boot sequence and future migrations consult. No runtime events are emitted by this issue.

**Failure and recovery behavior.** A failed user migration leaves data intact via transaction rollback or copy-and-swap recovery; a mid-migration crash never yields a half-migrated readable state. Migration attempts and outcomes are recordable in `schema_events` with version and non-sensitive result. Catalog validation failure means the candidate artifact is rejected before activation, never a partially replaced catalog.

**Security and privacy.** No cloud, user-account, or auth tables exist. Optional local-only VIN storage requires explicit consent per the section 8 `vehicles` baseline and is avoided by default. Fixtures and example rows contain no personal data and no real VINs. Log/fixture redaction rules from master prompt section 7 apply to anything derived from these tables.

**Accessibility and performance.** N/A for accessibility — no UI. Performance: indexes support the cascading year → make → model → configuration selectors without FTS; representative query plans and expected full-catalog size are measured against DOS-M00-004 budgets; physical optimization beyond that evidence is excluded.
