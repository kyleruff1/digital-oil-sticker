## Outcome

An Elixir-based pipeline skeleton defines stage contracts and converts a small committed/cached vPIC fixture into the bundled `CatalogRepo` SQLite artifact plus provenance manifest. This foundation deliberately stops short of live acquisition or full ETL; M03 owns production-source ingestion, normalization, coverage, and catalog publishing.

## Why this matters and what it unblocks

The foundation needs a real artifact boundary and test database without prematurely implementing the most source-sensitive portion of the product. A tiny deterministic fixture proves schema/build/package integration now and gives M03 a stable contract later. It also ensures the bundled catalog — not runtime vPIC access — supports first launch, making the offline-from-first-launch rule structural. Downstream, DOS-M01-005 packages this artifact into both native apps and DOS-M01-006 gates its determinism and integrity.

## Functional requirements

- FR-1: Stage behaviours/data contracts exist for acquisition, raw immutable inputs, normalization, validation, indexing, packaging, manifesting, and publishing; only the fixture path (raw fixture → normalize → validate → index → package → manifest) is implemented.
- FR-2: The cached vPIC fixture set is committed, small, redistribution-safe, and immutable; fixture inputs are never mutated by a build.
- FR-3: One canonical Mix task performs the full fixture build: read fixture, normalize only proof-required fields, run `CatalogRepo` migrations/build, create indexes, validate integrity/provenance, and emit a deterministic SQLite file to the native bundle staging directory.
- FR-4: The build emits a manifest containing catalog schema/content version, fixture source URLs/revisions/retrieval metadata, attribution/license note, row counts, rejected fixture rows/reasons, file checksum/size, and build-tool version.
- FR-5: The same cached fixtures, mapping version, and schema version produce byte-identical or logically identical output, with documented treatment of timestamps and SQLite page ordering.
- FR-6: Unknown values remain unknown (nullable), never defaulted; normalization performs no inference beyond the proof-required field mapping.
- FR-7: The artifact is checksummed and schema/app compatibility is validated before packaging; validation failures reject the artifact with actionable errors.
- FR-8: Ordinary setup, CI, and app startup never call vPIC or another source endpoint; no code in this issue implies production coverage or contacts vPIC at app runtime.
- FR-9: M03 handoff interfaces are defined (not implemented) for rate-limited/resumable live acquisition, raw caching, source-specific transformations, cross-source reconciliation, coverage reports, signing/publishing, and separately licensed maintenance/oil/filter inputs, preserving distinct provenance per source domain.
- FR-10: Native packaging asserts a compatible baseline catalog is present; a missing or incompatible fixture catalog fails packaging rather than causing a first-launch download.

## Technical implementation contract

### Components and ownership boundaries

The pipeline lives in the data-import tooling area established by DOS-M01-001, behind the DOS-M01-002 boundaries: source-specific fixture parsing stays outside domain/query modules; domain code consumes only the built `CatalogRepo`. Stage behaviours are the ownership seams M03 implements later. The packaging assertion is owned jointly with DOS-M01-005's build integration.

### Data and persistence

The build populates the DOS-M01-003 `CatalogRepo` schema (makes, models, vehicle_configurations, aliases, `catalog_metadata`, `data_sources` as needed by the proof) and creates the required indexes. Output is a single deterministic SQLite file in the native bundle staging directory. Raw fixture inputs are immutable committed artifacts. `UserRepo` is untouched.

### Interfaces and events

- One canonical Mix task (single documented name, wired into the DOS-M01-001 task interface and DOS-M01-006 CI).
- Stage behaviour contracts with typed inputs/outputs per stage: acquisition (future), raw input, normalization, validation, indexing, packaging, manifesting, publishing (future).
- Manifest file format as the machine-readable artifact contract consumed by packaging (DOS-M01-005) and CI (DOS-M01-006).

### Failure and recovery behavior

Invalid references, duplicate keys, out-of-range years, incompatible schema, and fixture source-shape changes fail the build with actionable errors identifying the offending rows/fields. A failed build emits no artifact to the staging directory (or clearly invalidates it); partial artifacts are never packaged. Recovery is rerunning the deterministic build from committed fixtures.

### Security and privacy

Fixtures contain no personal data and no restricted/licensed content: only the redistribution-safe cached vPIC responses approved by DOS-M00-006. No network access occurs during setup, CI, or app startup. No credentials are involved. Attribution and license notes travel with the artifact via the manifest and `data_sources` rows.

### Accessibility and performance

N/A for accessibility — build tooling only. Performance: fixture build timing and artifact size are measured and recorded as evidence; blocking budgets for the full catalog belong to DOS-M00-004/DOS-M01-006, but the fixture artifact must stay comfortably small enough for native packaging.

### Data change specifics

- Source/version/license: NHTSA vPIC API cached responses only, as selected in DOS-M00-006; official U.S. government structured data handled under the master prompt section 4.4 green lane (17 U.S.C. §105 treatment), with source URLs, revision/retrieval metadata, agency attribution/disclaimer note, and review status recorded in the manifest and `data_sources`.
- Mapping: fixture JSON fields map only to the proof-required `CatalogRepo` columns (identity spine: makes, models, configurations, aliases); the mapping is versioned, and a mapping-version change is a new build input by definition.
- Stable keys: stable surrogate IDs within the catalog version plus vPIC provider keys (`vpic_make_id`, `vpic_model_id`, provider namespace/key for configurations) per the DOS-M01-003 schema.
- Constraints/indexes: the build runs the DOS-M01-003 migrations and creates all required uniqueness constraints and normalized-name/provider-key indexes; constraint violations are build failures, not warnings.
- Idempotency: same fixtures + mapping version + schema version → byte-identical or logically identical artifact under the documented timestamp/page-ordering treatment; two-run comparison is a standing test.
- Rejected-row policy: rows failing validation are reported with reasons in the rejection report and excluded from the artifact; rejection is never silent and never "fixed" by inference.
- Checksums: SHA-256 (or the project-standard digest) and file size for the artifact recorded in the manifest; `PRAGMA integrity_check` must pass.
- Coverage report: row counts per populated table are emitted; the report explicitly states this is a fixture proof, not production coverage — no coverage claim is implied.
- Fixture strategy: small, committed, redistribution-safe, immutable cached responses; changes to fixtures go through reviewed commits and re-approval against DOS-M00-006's selection criteria.
- Update cadence: none in M01 — the fixture changes only by reviewed commit; production update cadence, refresh purchases, and publishing are M03 decisions.
- Rollback/recovery: the artifact is fully regenerable from committed fixtures at any commit; staging output is replaced atomically per build; packaged apps rely on the packaging assertion (FR-10) so an incompatible artifact can never ship silently.

## Test plan

### Automated

- Unit-test the implemented fixture parser/build/validation seams and golden-test representative normalized rows.
- Contract-test unimplemented acquisition/publishing ports with fakes; do not create live HTTP behavior in M01.
- Two-run determinism test: build twice and compare per the hash/logical contract; assert row counts.
- Negative tests: injected invalid reference, duplicate key, out-of-range year, incompatible schema version, and a mutated fixture shape each fail with an actionable error.
- Integrity gate: `PRAGMA integrity_check`, schema validation, and manifest completeness checks in CI.
- Network guard: assert no source endpoint is contacted during setup, CI, and the build (for example by running with network access disabled or instrumented).
- Packaging assertion test: remove/corrupt the staged artifact and assert native packaging fails.

### Manual/device matrix

- Review the manifest, attribution note, and rejection report for accuracy against the committed fixture set (data owner review, recorded on the issue).
- One local end-to-end walkthrough: clean checkout → canonical build command → artifact in the native bundle staging directory → DOS-M01-005 packaging consumes it. Device execution evidence itself belongs to DOS-M01-005.

## Rollout and rollback

The pipeline skeleton and fixture land through reviewed pull requests; the artifact is a build output, never committed. Rollback is source-control revert plus rebuild. Nothing is published to Netlify or any distribution channel in this issue; signing/publishing remain M03 scope.

## Risks, decisions, and open questions

- Risk: SQLite output is not naturally byte-stable (timestamps, page ordering). Mitigation: the determinism contract explicitly defines byte-identical or logically identical comparison and documents timestamp/page-ordering treatment; the chosen definition is recorded.
- Risk: the fixture path over-fits the contracts to vPIC shapes, making M03 multi-source work awkward. Mitigation: stage contracts are typed per stage, provenance is per-source, and maintenance/oil/filter inputs are explicitly separate in the handoff.
- Risk: scope creep toward live acquisition "just to test." Mitigation: hard Excluded list; acquisition ports are contract-tested with fakes only.
- Decision to record: the deterministic-comparison definition (byte-identical versus logically identical) and digest algorithm.
- Open question: exact staging-directory path/naming within the native bundle layout — coordinate with DOS-M01-005, which owns packaging.
