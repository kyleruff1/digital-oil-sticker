## Outcome

The native iOS/Android shell starts its embedded BEAM/Phoenix runtime, opens only its loopback LiveView in the native WebView, initializes both SQLite repositories, and reaches a diagnostic screen in airplane mode. A separate static Netlify site publishes placeholder marketing/help/privacy/attribution pages without participating in application runtime.

## Why this matters and what it unblocks

Embedded-runtime startup, loopback security, repository readiness, and native lifecycle are architectural properties, not final packaging details. Establishing them now prevents feature UI from assuming remote Phoenix or WebView-owned state. Separating the support site prevents Netlify from being mistaken for the app host. This issue unblocks screen development and offline end-to-end tests: every M05 LiveView will render inside this shell, and every offline guarantee the product makes is only as strong as the boot/readiness behavior proven here.

## Functional requirements

- FR-1: The native shell implements the native-to-BEAM readiness handshake, starts the Phoenix endpoint on `127.0.0.1`, navigates the WebView to the loopback URL, handles LiveView reconnect, and survives native lifecycle transitions (background/resume, force-quit/relaunch) without orphaning multiple BEAM/endpoint instances.
- FR-2: No non-loopback listener exists in any build; the endpoint rejects invalid Host/Origin requests and is unreachable from LAN/public interfaces.
- FR-3: The WebView permits only loopback application routes: no arbitrary navigation, remote scripts, mixed content, or production WebView debugging; on Android, any cleartext exception is limited to device loopback.
- FR-4: External help/privacy links open only through an explicit allowlisted system-browser action and are never necessary for core use.
- FR-5: Boot initializes `CatalogRepo` and `UserRepo` before the diagnostic LiveView becomes interactive: the packaged fixture catalog is verified and copied atomically to its approved location as needed, `UserRepo` migrations run, and no writable UI appears before repositories are healthy.
- FR-6: Explicit, distinguishable states exist for: native shell starting; embedded BEAM starting/failed; local LiveView connecting/reconnecting; databases initializing/migrating; bundled catalog verifying/corrupt/incompatible; ready; and unrecoverable user-store error. Each error state has plain-language copy and an idempotent retry/restart path; local records are never cleared as error recovery.
- FR-7: An app build never opens an incompatible catalog schema; incompatibility yields the explicit error state, not a crash or silent fallback.
- FR-8: The separate support site builds from its own directory to static Netlify output containing only minimal marketing, help, privacy, source attribution, and contact content — no app UI, LiveView, service worker, PWA manifest, Functions, Edge Functions, Blobs, database, personal data, or runtime API.
- FR-9: App startup and core use make no request to the Netlify site, a remote Phoenix server, remote database, analytics endpoint, or push service.
- FR-10: A documented static path/naming contract is reserved for future versioned catalog artifacts, without publishing or in-app update implementation; the bundled catalog remains sufficient for first launch.
- FR-11: Native package size, startup time, and database-readiness timing meet the DOS-M00-004 budgets or carry an approved exception.

## Technical implementation contract

### Components and ownership boundaries

`DigitalOilSticker.Boot` owns the ordered startup sequence (catalog verification, user migration, Repo startup, recovery state, endpoint readiness). The root `Mob.Screen` and `DeviceCommandBroker` from DOS-M01-002 own all native interaction; the diagnostic LiveView is an ordinary Phoenix LiveView reading readiness state through domain APIs. The support site is an isolated directory with its own build; it shares no runtime code with the app. Catalog-update mechanics beyond bundled verification remain M03/M08 scope.

### Data and persistence

On first launch the bundled fixture catalog is verified and copied into application support atomically (stage, integrity-check, atomic rename), per master prompt section 8. `UserRepo` migrations run before the UI is writable. `CatalogRepo` opens read-mostly; `UserRepo` writes must survive background/resume and force-quit/relaunch. Neither database file is accessible to the WebView directly.

### Interfaces and events

- Native-to-BEAM readiness handshake and root-screen registration (broker generation tracking per DOS-M01-002).
- Boot state machine exposed to the diagnostic LiveView as typed readiness states, not ad hoc strings.
- The allowlisted external-link action as the only WebView escape hatch, handing approved URLs to the system browser.
- The reserved static path/naming contract for future versioned catalog artifacts, documented for M03.

### Failure and recovery behavior

Every startup/database error state maps to plain-language copy and an idempotent retry/restart path. BEAM start failure, catalog corruption/incompatibility, migration failure, and unrecoverable user-store error are distinct, recoverable-where-possible states; recovery never silently clears local records. Native lifecycle transitions must not orphan multiple BEAM/endpoint instances; relaunch after force-quit reaches a correct state without data loss.

### Security and privacy

Strict `127.0.0.1` binding; the endpoint rejects invalid Host/Origin requests and is unreachable from another LAN device. Production builds use `MIX_ENV=prod` with code reload, LiveDashboard, development routes, remote inspector, and Erlang distribution disabled; CSRF protections retained; no production WebView debugging. Packaged session keys are local integrity material, not remote secrets. No telemetry or third-party analytics; the support site collects no personal data and app core use never contacts it.

### Accessibility and performance

Readiness and error states are screen-reader reachable (VoiceOver/TalkBack) and non-destructive. Safe-area, software-keyboard, and orientation policy behavior pass on supported phone sizes. Native package size, cold-start, and database-readiness timings are measured against the DOS-M00-004 budgets; the support site passes a simple accessibility/link check.

## UX and content states

Diagnostic/boot surface states (placeholder visual design; final visual language belongs to M02):

- Native shell starting; embedded BEAM starting; embedded BEAM failed (retry/restart path).
- Local LiveView connecting; reconnecting after interruption.
- Databases initializing; `UserRepo` migrating.
- Bundled catalog verifying; catalog corrupt; catalog incompatible (each with plain-language copy, no data loss).
- Ready (diagnostic/readiness screen with environment and repository status).
- Unrecoverable user-store error (honest, non-destructive guidance; never auto-clearing records).

No false-ready state may render a writable form before repositories are healthy. Support-site content states: minimal placeholder marketing, help, privacy, source attribution, and contact pages in American English.

## Test plan

### Automated

- Local-development LiveView component tests for the diagnostic/readiness states and boot state machine.
- Listener/binding tests: assert loopback-only binding, invalid Host/Origin rejection, and absence of non-loopback listeners in release configuration.
- WebView policy checks where automatable: navigation allowlist, no remote scripts/mixed content, production debugging disabled, Android cleartext limited to loopback.
- Boot-sequence tests with injected failures: corrupt catalog artifact, incompatible catalog schema version, and `UserRepo` migration failure each reach their explicit recoverable state without data loss.
- Packaging assertion (with DOS-M01-004): missing/incompatible bundled catalog fails the native package build.
- Support-site build test: static output only, no Functions/Edge Functions/service worker/PWA manifest artifacts; link and basic accessibility check.
- Network guard: instrument or block egress and assert app startup/core use performs no remote request.

### Manual/device matrix

- Physical iOS phone and physical Android phone (supported sizes per the M00 device matrix): cold launch in airplane mode to diagnostic screen; background/resume; force-quit/relaunch; corrupt-catalog and migration-failure scenarios where injectable on device.
- LAN reachability check from a second device on the same network: the endpoint must be unreachable.
- Screen-reader pass (VoiceOver on iOS, TalkBack on Android) over readiness and error states.
- Netlify deploy preview inspection: artifact inventory, config audit, and confirmation the site plays no runtime role.

## Rollout and rollback

The shell lands through reviewed pull requests; development packages are distributed only to the team (no store publication). The support site deploys via Netlify deploy previews and a production static deploy of placeholder content; rollback is redeploying the previous static build. App-side rollback is source-control revert; no end-user installations exist yet. The reserved catalog-artifact path contract is documentation only and publishes nothing.

## Risks, decisions, and open questions

- Risk: Mob `0.7.20` lifecycle behavior differs across OS versions (background BEAM handling, WebView process death). Mitigation: explicit lifecycle tests on physical devices; deviations become ADR amendments or Mob-issue follow-ups, not silent workarounds.
- Risk: budget misses (package size, cold start) caused by BEAM runtime overhead. Mitigation: measure early against DOS-M00-004; an approved exception process exists rather than silent acceptance.
- Risk: the support site quietly grows runtime features. Mitigation: static-only build assertions and the DOS-M01-006 boundary gate.
- Decision to record: the approved application-support location and atomic-copy procedure for the verified catalog.
- Open question: exact allowlist contents for external system-browser links at this stage (help/privacy URLs on the support site are the expected initial set).
