> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The shell becomes a hosted Phoenix app bound to a public interface behind Fly's proxy with TLS and origin checks — replacing the loopback/WebView handshake — while the separate static Netlify support-site half carries over as written._

## Outcome

A hosted Phoenix LiveView application shell runs on Fly.io in region `ord` at `digitaloilsticker.com` behind the Fly proxy with TLS termination, WSS transport, and `check_origin` restricted to the exact production hostnames. On mount, the shell executes the ADR-0004 hydration-from-empty protocol: a `LocalStore` JS hook opens the origin-scoped IndexedDB database `dos_local`, reads the versioned envelope, and pushes it to the server, which validates it into `socket.assigns` for the socket lifetime only — never to any server-side durable store. Distinct, screen-reader-reachable states exist for `:hydrating`, `:empty`, `:storage_unavailable`, and `:data_missing`, and no writable UI appears while `:hydrating`. A separate static Netlify build (team `cDiscourse`) continues to publish placeholder marketing, help, privacy, source-attribution, and contact content at the static subdomains (help./legal./attribution., and `digitaloilsticker.net`) with no application runtime path, per ADR-0002 as amended by ADR-0004.

## Why this matters and what it unblocks

The hosted shell is the physical seam where every future browser feature meets the "no server-side personal record" promise. Getting the hosted-transport hardening (INV-22), the hydration protocol (INV-24), and the honest storage-loss vocabulary (INV-25) right *once*, at shell level, is what lets the M02 UX contract, the M04 storage adapter, and the M05 single-vehicle MVP be written on top of it without each re-litigating the seam. Establishing the Fly/Netlify content boundary (INV-27) at the same time prevents Netlify from being mistaken for the app host and prevents the app from acquiring a hidden dependency on Netlify. Downstream, DOS-M05-005 (dashboard) will render inside this shell, DOS-M09-003 (protocol specification) hardens what this card first implements, and DOS-M09-006 (deploy pipeline) will land the reproducible release image this shell runs from.

## Functional requirements

- FR-1: The shell is a Phoenix LiveView application deployed on Fly.io in region `ord` with `min_machines_running = 1` (scale-to-zero prohibited), serving `digitaloilsticker.com` and `www.digitaloilsticker.com`; a cold GET to the apex returns the pre-hydration skeleton over HTTPS. (Addresses finding #1: replaces the native-shell/embedded-BEAM/loopback-WebView boot with the hosted-Phoenix boot required by [ADR-0004 §"Decision" clause 1](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision).)
- FR-2: The endpoint is served only over HTTPS (with HTTP → HTTPS redirect and HSTS enabled after certificate verification on both hostnames) behind the Fly proxy; the LiveView socket runs on WSS with `check_origin` restricted to the exact production hostname list (never `true`, never `false`); CSRF protection is enabled for the LiveView session and every non-idempotent HTTP endpoint per [ADR-0004 §"Security and privacy boundary"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#security-and-privacy-boundary-for-a-hosted-application); a Content-Security-Policy per ADR-0004 §"Content Security Policy" forbids third-party origins, external scripts, and `'unsafe-inline'`. (Addresses finding #3: restates INV-22 in place of the retired INV-2, which is not cited.)
- FR-3: The deployed application declares exactly one Ecto repo, `DigitalOilSticker.CatalogRepo`, opened read-only; no `UserRepo` is started in the release. Personal data lives on the server only as transient values in `socket.assigns` for one connection and is never written to any table, cache, ETS, external store, or log. A release-gating test enumerates the running repo list and its connection mode.
- FR-4: On mount with `connected?(socket) == false` the server renders `assigns.local_state == :hydrating` as a skeleton — never an empty state or onboarding-from-zero flow. On socket connect the server arms a hydration deadline (default 5000 ms) and awaits the hook's `local_store:hydrate` event; on receipt it validates the envelope through an embedded-schema changeset per `schema_version`, migrates it if needed, places the result in assigns, and sets `local_state` to `:loaded`, `:empty`, `:storage_unavailable`, or `:data_missing`. All four are distinct rendered states with plain-language copy; each is reachable via VoiceOver on iOS Safari, TalkBack on Android Chrome, and NVDA on Windows Firefox/Chrome. (Addresses finding #1: replaces on-device catalog verification with the ADR-0004 hydration-from-empty protocol.)
- FR-5: The `LocalStore` hook opens the origin-scoped IndexedDB database `dos_local` at a monotonic IDB version, with object stores `meta` / `vehicles` / `events` / `readings` / `reminders` / `prefs` keyed and shaped exactly as [ADR-0004 §"Storage layout"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#storage-layout) specifies. `localStorage` holds only the non-personal `dos_boot_state` boot hint. If `indexedDB.open()` throws or the probe write+read+delete fails, the shell enters session-only mode with a persistent banner, exposes export prominently, and MUST NOT silently fall back to `localStorage` for records or to server storage of any kind.
- FR-6: Hydration input is treated as untrusted client input: parsed through the changeset, capped at 1 MiB decoded / 200 vehicles / 5000 events / 20 000 readings (rejected explicitly, never silently truncated), and referentially checked. Invalid records go to a quarantine list with the raw payload offered for export; the valid subset still hydrates. Migrations are pure and forward-only; a client payload newer than the server's `schema_version` puts the session into read-only mode with an explicit banner and disables mutations.
- FR-7: Every mutation is a round trip per [ADR-0004 §"Mutation round trip"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#mutation-round-trip): server assigns `mutation_id` and `seq`, renders optimistically with a "saving" affordance, `push_event`s `local_store:put`, and clears the pending write on ack. Failure to ack within 2000 ms renders a persistent, non-dismissible "Not saved to this browser" affordance on the affected record, keeps the value visible but visibly unsaved, and offers export; the server never retries silently and never rolls back invisibly. Multi-tab writes use compare-and-set on `meta.seq` inside the same IndexedDB transaction with `BroadcastChannel("dos_local_store")` for cross-tab notification.
- FR-8: The session cookie is signed, `secure`, `http_only`, `same_site: "Lax"`, with a short `max_age`, and contains only the CSRF token and `live_socket_id`. It contains no VIN, odometer value, service date, note text, vehicle name, preference, anonymous user ID, or any value that could correlate one visit to another. LiveDashboard is disabled in production; `debug_errors: false`.
- FR-9: Server logs MUST NOT contain VIN, odometer/mileage values, service dates, note text, custom vehicle names, the specific vehicle a session selected, any hydration/mutation/import/export payload or fragment, the `tab_id`, or the full client IP. Enforced by disabled param logging, configured `filter_parameters`, an allowlisted Logger filter on `handle_event` params, and a scripted-session log-scanning release-gate test. No third-party analytics, tag manager, session recorder, or error reporter is loaded on any page (INV-4 preserved without qualification).
- FR-10: The static Netlify support site (team `cDiscourse`) publishes from its own directory as static output only — no app UI, LiveView, service worker, PWA manifest, Functions, Edge Functions, Blobs, database, personal data, or runtime API. It is served from static subdomains (e.g. `help.` / `legal.` / `attribution.` on `digitaloilsticker.com`, and/or from `digitaloilsticker.net`) with the apex reserved for Fly. This carries over the pre-pivot support-site FR as written. The application footer links the privacy and attribution URLs and those URLs remain stable across deploys.
- FR-11: The written Fly/Netlify content-boundary rule (INV-27) is filed with this card and linked from ADR-0002-as-amended; it states in one paragraph which host serves what, and forbids the application from making any request to the Netlify origin at runtime.
- FR-12: First-visit payload meets the *provisional* Constitution §9 budget of ≤ 250 KiB compressed initial HTML+CSS+JS and ≤ 500 KiB total first-visit transfer with zero third-party origins; hydration completes sub-second on a warm connection so the skeleton is not the dominant impression of the product. The old DOS-M00-004 package-size and cold-start budgets do **not** apply and are not cited by this card.
- FR-13 (retired-and-replaced record): The pre-pivot FRs that cited on-device loopback binding (old FR-2, invoking INV-2), the native WebView navigation allowlist (old FR-3), the on-device catalog verify-and-copy (old FR-5), the on-device readiness state list (old FR-6), the incompatible-catalog device-error state (old FR-7), the native package-size/startup budgets (old FR-11), and the reserved static path for future in-app catalog updates (old FR-10) are **retired** for the MVP and their obligations are transferred as follows: old FR-2 → new FR-2 (hosted transport); old FR-3 → new FR-2 (CSP); old FR-5/6/7 → new FR-3/4/5/6 (hydration + read-only catalog); old FR-11 → new FR-12 (page-load budget); old FR-10 → deferred to [DOS-M09-010](DOS-M09-010.md). ## Technical implementation contract

### Components and ownership boundaries

`DigitalOilSticker.Application` starts exactly one Ecto repo (`CatalogRepo`, read-only), the `DigitalOilSticker.Endpoint`, and the `LocalStore` server-side helpers (validators, migrations, quarantine buffer). The `AppShellLive` LiveView owns the pre-hydration render and the `local_state` state machine. The `LocalStore` JS hook owns everything on the client side of the seam: opening `dos_local`, running `onupgradeneeded`, reading the envelope, pushing `local_store:hydrate`, receiving `local_store:put`, committing IndexedDB transactions, sending `local_store:ack`, and driving the `BroadcastChannel` cross-tab protocol. Domain contexts (`Catalog`, `Garage`, `Forecast`, resolver) belong to later cards and MUST NOT depend on `Phoenix.LiveView`, `Plug`, or the `LocalStore` modules — a static-check test enforces this per [ADR-0004 §"Enforcement"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#enforcement). The Netlify support site shares no runtime code with the app and lives in its own directory with its own build.

### Data and persistence

Server: `CatalogRepo` opens a read-only SQLite database baked into the Fly release image (no volume, no writer, no LiteFS); connection is opened in SQLite read-only mode so decision §4 of ADR-0004 is enforced by the connection itself. Client: IndexedDB database `dos_local` at monotonic IDB version, with the object stores/keys of ADR-0004 §"Storage layout"; `onupgradeneeded` never deletes stores holding data and is forward-only. The client requests `navigator.storage.persist()` after the first meaningful write and records the boolean in `meta.persist_granted`; `navigator.storage.estimate()` is read on hydration and if usage exceeds 80% of quota the shell surfaces it. `QuotaExceededError` follows the failed-ack path with a quota-specific message; data is never silently dropped.

### Interfaces and events

- `LocalStore` JS hook events: outbound `local_store:hydrate` (envelope), `local_store:ack {mutation_id, seq, status}`, `local_store:conflict`; inbound `local_store:put {mutation_id, seq, upserts, deletes}`.
- Server: `handle_event("local_store:hydrate", …)` and `handle_event("local_store:ack", …)` on `AppShellLive`; `LocalStore.Envelope.validate/1` and `LocalStore.Migrations.migrate/3` as the only validation and migration path.
- `BroadcastChannel("dos_local_store")` for cross-tab `{seq, mutation_id, tab_id}` notifications.
- The application footer's external-link surface points at the Netlify static site hostnames only; no other outbound origin appears anywhere in the shell.

### Failure and recovery behavior

Hydration deadline expiry → `:storage_unavailable`. Store open failure or probe failure → session-only mode with persistent banner and export offered repeatedly. `dos_boot_state == "has_data"` but hydration returns zero records → `:data_missing` (never `:empty`, per ADR-0004 first-paint rule). Client payload newer than server → read-only mode with banner and mutations disabled. Ack timeout or error → persistent unsaved marker on the affected record; no silent retry; no invisible rollback. Reconnect after network blip or deploy → LiveView retains the client DOM under `phx-disconnected` styling; the hook re-hydrates underneath a stable view; pending writes are re-driven from client storage (the source of truth). A `SECRET_KEY_BASE` rotation invalidates session cookies and socket tokens; the client reconnects and re-hydrates from IndexedDB and no user data is lost.

### Security and privacy

TLS at the Fly proxy for both hostnames; HSTS enabled only after certificates verify (no `preload` at MVP); `Plug.SSL` with `rewrite_on` for `x_forwarded_proto`/`_host`/`_port`; `check_origin` locked to the explicit host list; CSRF on all HTTP routes and on socket connect; the CSP of [ADR-0004 §"Content Security Policy"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#content-security-policy) served on every response; `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and a `Permissions-Policy` denying geolocation/camera/microphone/payment. Per-IP and per-socket token-bucket limits on connects, HTTP requests, and `hydrate`/`import` events. LiveDashboard disabled; `debug_errors: false`. Operator console access is scoped to application incident diagnosis, never to inspecting a live user's assigns; the privacy page says exactly this rather than overclaiming.

### Accessibility and performance

`:hydrating`, `:loaded`, `:empty`, `:storage_unavailable`, and `:data_missing` are each screen-reader reachable, each announce a distinct label, and none is a spinner-only state. The pre-hydration skeleton preserves layout to avoid content jumps on hydration. Keyboard focus is preserved across reconnect and re-hydration. WCAG 2.2 AA is the target for browser assistive technology (VoiceOver on iOS Safari, TalkBack on Android Chrome, NVDA on Windows Firefox/Chrome). Page-load and hydration timings are measured against the provisional §9 budgets (see FR-12); the DOS-M00-004 package-size and cold-start budgets do not apply and are not measured here.

## UX and content states

Pre-pivot device-boot states are removed. Shell states shown to the user (placeholder visual design; final visual language belongs to M02):

- `:hydrating` — skeleton only; controls MUST NOT accept input (INV-24.3); accessible label: "Loading your saved data from this browser."
- `:loaded` — normal shell with the returning user's records rendered from assigns; INV-5-compliant copy in Settings ("This data lives in this browser only. Clearing browser data deletes it permanently. Export is the only recovery.").
- `:empty` — first-time visitor with no prior records; accessible label: "This browser has no saved vehicles yet."; explicitly distinct from `:hydrating`.
- `:storage_unavailable` — IndexedDB refused; persistent banner: "Your browser is not saving anything you enter here — closing this tab will lose it."; export offered repeatedly; catalog browsing still works.
- `:data_missing` — `dos_boot_state == "has_data"` but hydration was empty; explicit warning: "Your browser storage appears to have been cleared."; import offered; MUST NOT show a fresh empty garage.
- `:read_only_newer_client_payload` — the browser holds data from a newer app version than this deployment; banner + mutations disabled + export offered.
- Reconnect and deploy transitions render via `phx-disconnected` styling on the existing DOM — never a teardown to skeleton.

Prohibited vocabulary anywhere in the shell: "backup", "synced", "safe", "we'll remember", "your account", "cloud", "restore". Required copy: an always-reachable statement that data lives in this browser only.

Support-site content states (unchanged from pre-pivot): minimal placeholder marketing, help, privacy, source attribution, and contact pages in American English, published from the separate Netlify build.

## Test plan

### Automated

- LiveView component tests for `AppShellLive` covering each of the six rendered states (`:hydrating`, `:loaded`, `:empty`, `:storage_unavailable`, `:data_missing`, `:read_only_newer_client_payload`) including the hydration-deadline timer.
- Repo-inventory and read-only-connection assertion for `CatalogRepo`; static check that no domain module references `Phoenix.LiveView` / `Plug` / `LocalStore` (ADR-0004 §"Enforcement").
- Envelope validator property tests: unknown top-level keys rejected; unknown record-level keys preserved verbatim; caps rejected explicitly (1 MiB / 200 vehicles / 5 000 events / 20 000 readings) with no silent truncation; hydration idempotence; migration round-trip fixtures for every prior `schema_version`.
- Mutation round-trip tests: ack timeout, ack error, and `QuotaExceededError` each produce the persistent unsaved affordance; compare-and-set aborts on stale `meta.seq`; `BroadcastChannel` re-hydration path.
- Security tests: `check_origin` rejection for non-production origins; CSRF-absent socket rejected; HTTP → HTTPS redirect; HSTS served only after cert verification; CSP present on every response and blocks a probe third-party script; `filter_parameters` and Logger-allowlist tests using the scripted-session log-scanning gate from ADR-0004 §"Enforcement".
- Support-site build test: static output only; no Functions/Edge Functions/service worker/PWA manifest; link and basic accessibility check; footer-link parity between the Fly app and the Netlify site.
- Network guard: instrument the deployed app and assert zero outbound requests to the Netlify origin at runtime; runtime scan for third-party origins in the served pages.
- Payload-budget gate against provisional §9 numbers.

### Manual/browser matrix

- Desktop: Chrome, Firefox, Safari, Edge on macOS and Windows current versions.
- Mobile: iOS Safari (current + one back), Android Chrome (current + one back).
- Screen-reader pass: VoiceOver on iOS Safari, TalkBack on Android Chrome, NVDA on Windows Firefox and Chrome.
- Private-browsing/hardened-privacy pass on Safari (ITP) and Firefox: `:storage_unavailable` and session-only banner surface correctly and are non-dismissible.
- Multi-tab pass: two tabs of the same origin drive a scripted write in tab A, verify tab B receives the `BroadcastChannel` message and re-hydrates.
- Deploy pass: perform a rolling deploy of a no-op image while a scripted session has an unacked mutation; verify reconnect, re-hydration, and no lost work.
- Netlify support-site deploy-preview inspection: artifact inventory, config audit, confirmation the site plays no runtime role, and correctness of the Fly/Netlify content-boundary rule.

## Rollout and rollback

The shell lands through reviewed pull requests. The Fly deploy is initially issued to a staging hostname (e.g. `staging.digitaloilsticker.com`) for the browser-matrix and reconnect passes, then promoted to the apex. Rollback is `flyctl releases rollback` to the previous immutable release identifier — the read-only catalog reverts atomically with the image (no volume, no writer). The Netlify support site rolls back by redeploying the previous static build. DNS/TLS changes are staged: point `www` first, verify certs, then apex; HSTS enabled only after both hostnames serve correctly. No end-user installations exist yet; there is no store publication.

## Risks, decisions, and open questions

- Risk (R1 from ADR-0004): browser eviction of infrequently-used site storage — quarterly usage is exactly the profile most at risk. Mitigation here: `navigator.storage.persist()` request on first meaningful write, honest storage-status UI, `:data_missing` state, and export offered repeatedly. Actual eviction behavior per browser must be **measured** (DOS-M09-009), not assumed.
- Risk (R2): hydration adds latency to every mount including every reconnect. Mitigation: sub-second hydration is a design constraint and is measured against FR-12.
- Risk (R3): the strict CSP is unverified against LiveView's runtime behavior. Mitigation: verify in this shell's deployment; if a nonce is required, add a nonce plug — `'unsafe-inline'` is not an acceptable resolution.
- Risk (R4): multi-tab last-write-wins at record granularity. Accepted for MVP under the single-user assumption; losses are visible.
- Risk (R8): single region, single always-on machine — a Fly zone failure is a full outage; a deploy drops every socket. Accepted at MVP; the reconnect+re-hydration path in AC-10 is the compensating property.
- Decision to record: the exact hostname assignments for the Fly/Netlify content boundary (which of `help.` / `legal.` / `attribution.` / `docs.` are used) and whether the static content is served from `digitaloilsticker.net` or from subdomains of `.com`. This is the INV-27 rule filed with this card.
- Open question: whether `same_site: "Lax"` is sufficient for the session cookie or `"Strict"` should be used; the deployment spike measures the impact on refresh/back-button behavior.
- Open question (from ADR-0004 R11): whether users will accept a product that does nothing offline. That is the core product bet the browser MVP exists to test; this shell is what lets the test run.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

`DigitalOilSticker.Boot` owns the ordered startup sequence (catalog verification, user migration, Repo startup, recovery state, endpoint readiness). The root `Mob.Screen` and `DeviceCommandBroker` from DOS-M01-002 own all native interaction; the diagnostic LiveView is an ordinary Phoenix LiveView reading readiness state through domain APIs. The support site is an isolated directory with its own build; it shares no runtime code with the app. Catalog-update mechanics beyond bundled verification remain M03/M08 scope.

#### Data and persistence

On first launch the bundled fixture catalog is verified and copied into application support atomically (stage, integrity-check, atomic rename), per master prompt section 8. `UserRepo` migrations run before the UI is writable. `CatalogRepo` opens read-mostly; `UserRepo` writes must survive background/resume and force-quit/relaunch. Neither database file is accessible to the WebView directly.

#### Interfaces and events

- Native-to-BEAM readiness handshake and root-screen registration (broker generation tracking per DOS-M01-002).
- Boot state machine exposed to the diagnostic LiveView as typed readiness states, not ad hoc strings.
- The allowlisted external-link action as the only WebView escape hatch, handing approved URLs to the system browser.
- The reserved static path/naming contract for future versioned catalog artifacts, documented for M03.

#### Failure and recovery behavior

Every startup/database error state maps to plain-language copy and an idempotent retry/restart path. BEAM start failure, catalog corruption/incompatibility, migration failure, and unrecoverable user-store error are distinct, recoverable-where-possible states; recovery never silently clears local records. Native lifecycle transitions must not orphan multiple BEAM/endpoint instances; relaunch after force-quit reaches a correct state without data loss.

#### Security and privacy

Strict `127.0.0.1` binding; the endpoint rejects invalid Host/Origin requests and is unreachable from another LAN device. Production builds use `MIX_ENV=prod` with code reload, LiveDashboard, development routes, remote inspector, and Erlang distribution disabled; CSRF protections retained; no production WebView debugging. Packaged session keys are local integrity material, not remote secrets. No telemetry or third-party analytics; the support site collects no personal data and app core use never contacts it.

#### Accessibility and performance

Readiness and error states are screen-reader reachable (VoiceOver/TalkBack) and non-destructive. Safe-area, software-keyboard, and orientation policy behavior pass on supported phone sizes. Native package size, cold-start, and database-readiness timings are measured against the DOS-M00-004 budgets; the support site passes a simple accessibility/link check.

### UX and content states (pre-pivot)

Diagnostic/boot surface states (placeholder visual design; final visual language belongs to M02):
