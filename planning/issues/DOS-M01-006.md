> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The device matrix becomes a browser/engine matrix, and "release evidence" becomes deploy evidence (image digest, catalog version, release ID) rather than store-build artifacts._

## Outcome

Automated gates validate the browser-first MVP's real seams: pure domain behavior, the read-only server-side catalog contract and its migrations, the deterministic catalog pipeline, LiveView components and the hydration protocol, the hosted internet-facing transport boundary (HTTPS/WSS, origin/CSRF, CSP, rate limiting, log scrubbing), the anonymous IndexedDB client-storage adapter across a named browser/engine matrix, and a successful Fly.io deploy of the release image. Release evidence is a deploy manifest — image digest, `data_version`, Fly release ID, catalog SHA, browser/engine matrix result, and CSP/security-header snapshot — not a store-build artifact. Feature teams inherit named test suites, blocking budgets, and a standard evidence format instead of recreating QA strategy per ticket.

## Why this matters and what it unblocks

Under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) the product is a hosted Phoenix LiveView application on Fly.io with anonymous IndexedDB storage in the browser. Its exit gates therefore have to be about the seams that exist — the hosted transport boundary (INV-22), the impersonal catalog query surface (INV-26), anonymous client-side storage as the only home for personal data (INV-23), the LiveView hydration protocol (INV-24), and the Fly/Netlify origin boundary (INV-27) — not about loopback binding, native lifecycles, or store-signed packages that the MVP does not produce. Turning these seams into repeatable gates so feature teams can ship without re-deriving QA strategy is what makes the constitution's guarantees continuously verifiable rather than one-time claims. Every M02, M04, M05, M06, M07, and M09 issue's Definition of done cites these suites; the M01 epic exit gate depends on them; the hosted release gates in the re-scoped M07 build on the deploy-evidence format standardized here; and `DOS-M09-009` (browser support matrix and storage-behavior conformance suite) hands its named browser/engine/OS combinations up into the CI matrix specified below.

## Functional requirements

- FR-1 (INV-22, INV-23, INV-24, INV-26; addresses staleness sweep finding #1): Named suites exist for exactly the browser-first seams that ship in the MVP: **(a)** pure domain unit/property tests; **(b)** `CatalogRepo` read-only contract/integration tests (asserting the deployed repo list is exactly `[CatalogRepo]` and its connection is opened read-only, per ADR-0004 §"Enforcement"); **(c)** `CatalogRepo` migration tests; **(d)** pipeline fixture/golden tests; **(e)** LiveView component tests plus hydration-protocol tests (mount-unhydrated skeleton, `local_store:hydrate` round trip, mutation `pushEvent`→`local_store:put`→`local_store:ack`, reconnect re-hydration, multi-tab `BroadcastChannel` compare-and-set, storage-denied session-only fallback); **(f)** hosted-endpoint security tests (HTTPS/WSS-only, `check_origin` allowlist, `protect_from_forgery`, CSP and other security-header snapshot, per-IP and per-socket rate limits, log-scrubbing / no-personal-data-in-logs, third-party-origin scan); **(g)** IndexedDB client-storage adapter conformance tests **consumed from `DOS-M09-009`** across its named browser/engine/OS matrix; and **(h)** Fly deploy smoke (health check, canonical hostname, WSS handshake, one scripted hydrate against a preview app). The previously-required `UserRepo` contract/integration, `Mob`/`mob_notify` adapter, native lifecycle, and physical-device acceptance smoke suites are **retired for the MVP**; their historical wording is preserved under §"Superseded pre-pivot spec (historical record)" for future native re-entry. Each surviving suite has at least one meaningful passing example and one deliberate failing example demonstrating it can catch its target defect class.
- FR-2 (INV-22, INV-27; addresses staleness sweep finding #1): CI jobs run on change for: format; warnings/static analysis; dependency/license audit; secret scan; boundary enforcement (including the ADR-0004 §"Enforcement" domain-isolation static check); the FR-1 test suites; deterministic fixture-catalog build; static Netlify support-site build; Docker image build with the catalog artifact baked in; and a preview deploy against a non-production Fly app. The previously-required iOS compile and Android build jobs are **retired for the MVP** and preserved under §"Superseded pre-pivot spec" for future native re-entry.
- FR-3 (INV-22): CI images/actions and the Docker base image are pinned by immutable digest under a documented update policy; caches hold only reproducible dependencies (mix, node, deterministic build inputs), never credentials, personal fixture data, or the deploy-scoped Fly token. The deploy-scoped Fly token is a repository secret with least privilege (ADR-0004 §"Secrets"); a workflow that could echo it into logs is treated as a supply-chain defect.
- FR-4: The constitution 2.0.0 §9 budgets are enforced with named owners and stable blocking thresholds separated from informational trends: **first-visit payload** blocking (INV-22), **accessibility WCAG 2.2 AA** blocking on the M01 surfaces (diagnostic/readiness states, hosted shell, static support site), and *provisional* thresholds for hydration time and LiveView round-trip latency pending ADR-0004 R9 re-ratification. Any *provisional* threshold is labelled as such in job output so it cannot be quietly promoted to a permanent number without governance.
- FR-5 (INV-22, INV-27): Every CI run produces a versioned **deploy evidence bundle** containing environment/version manifest, catalog `data_version` and SHA, seed, clock/timezone, Docker image digest, Fly release ID (for preview and production runs), browser/engine matrix result set (browser, engine, OS, conformance-suite pass/fail per row), CSP and security-header snapshot as served, WSS handshake log for the smoke run, artifact checksums, and the redaction-reviewed log capture from the scripted-session test. Physical device/OS metadata is not a required field; the historical bundle format is retained under §"Superseded pre-pivot spec" for future native re-entry.
- FR-6: Tests run offline from committed/generated fixtures after dependencies are installed. Time-, mileage-, locale-, and timezone-dependent tests use injected values. The Fly preview-deploy smoke is the one job that requires outbound network; it is scoped to the non-production Fly app only, and is separable from the offline suites so a temporary Fly outage cannot mask an offline-suite regression.
- FR-7: Flaky-test quarantine rules, severity/triage classification, and release-blocker definitions are documented; a skipped required check requires an explicit exception with owner and expiration. Browser-matrix rows in particular may not be quarantined without an owner and expiration because they are the only proof of behaviour on real engines.
- FR-8 (INV-3, INV-22, INV-23, INV-26; addresses staleness sweep finding #2; retires the pre-pivot loopback gate): The **hosted-transport boundary from ADR-0004 and Constitution 2.0.0 is proven by gates, not assumed**. The retired pre-pivot gate ("non-loopback bind fails the appropriate check") is **removed** — under ADR-0004 the hosted app binds on public interfaces intentionally, and a loopback gate would fail every deploy. In its place, each of the following controlled failures is introduced on a scratch branch and each **must** fail exactly its intended gate and only its intended gate: **(a)** a route added without `protect_from_forgery` **or** with `check_origin` set to `true`/`false` instead of the explicit hostname allowlist; **(b)** a response served without the required CSP header, or with a CSP that adds a third-party `connect-src` / `script-src` origin; **(c)** code that opens a **second** `Repo` in the deployment, or writes a personal row (e.g. attempts an `insert` against a would-be user table), or opens `CatalogRepo` in read-write mode (violating ADR-0004 §"Enforcement" — deployed repo list is exactly `[CatalogRepo]`, opened read-only); **(d)** a `handle_event` that logs its params without the allowlist, so a VIN, odometer, service date, note, custom vehicle name, `tab_id`, or full client IP appears in a captured log line (violating ADR-0004 §"Logging"); **(e)** a `pushEvent` handler that persists client hydration input to disk, database, cache, ETS, external store, or log (violating ADR-0004 §4). Additionally: a forbidden dependency, a bad migration on `CatalogRepo`, and a secret-like value each still fail their respective gate. Every failing example is reproducible so gate regressions are detectable.
- FR-9 (INV-27; supersedes the pre-pivot FR-9 iOS/Android compile/smoke responsibilities): Browser/engine matrix responsibilities are explicit. The named browser/engine/OS matrix from `DOS-M09-009` is the source of truth; this pipeline runs it, records per-row pass/fail in the evidence bundle, and treats a required-row failure as merge-blocking. A row may be marked `unproven` with an owner and expiration when a runner is temporarily unavailable, but `unproven` is not `passing` and never counts as coverage. iOS/Android compile/smoke and the manual physical-device evidence path are **retired for the MVP** and preserved under §"Superseded pre-pivot spec" for future native re-entry.
- FR-10 (INV-3, INV-4, INV-5, INV-25): No CI artifact, cache entry, deploy evidence bundle, or preview-deploy Fly log includes secrets, raw restricted source data, or personal data of any kind. The scripted-session test from ADR-0004 §"Enforcement" (hydrate → several mutations → export → clear → import) runs as part of FR-1(f), and its captured logs are asserted to contain no VIN, odometer value, service date, note text, custom vehicle name, or `tab_id`. A passing build proves the hosted-transport boundary and does not merely verify that code compiles.
- FR-11 (INV-24; addresses staleness sweep finding #1): The hydration-protocol suite covers the states ADR-0004 mandates as **distinct**: `:hydrating`, `:empty`, `:storage_unavailable`, and `:data_missing`. A test asserts hydration is idempotent (hydrating the same payload twice produces identical assigns and emits no write-back). A test asserts the `local_store:conflict` compare-and-set path aborts a stale-`seq` write and triggers re-hydration. A test asserts that a hydration payload above the ADR-0004 §"Validation" hard caps (1 MiB decoded, 200 vehicles, 5 000 events, 20 000 readings) is rejected with an explicit error state rather than silently truncated.

## Technical implementation contract

### Components and ownership boundaries

CI configuration invokes only the canonical DOS-M01-001 task commands so local and CI behavior cannot diverge. Suite definitions live with the code they test; gate policy (budgets, quarantine, exceptions, blockers) lives in `docs/quality/`. Budget owners are named per budget. This issue owns gate orchestration and the deploy-evidence format; the gated behaviors are owned by their source issues — boundaries by DOS-M01-002, `CatalogRepo` schema/migrations by DOS-M01-003, pipeline by DOS-M01-004, hosted Phoenix shell and Netlify boundary by DOS-M01-005, catalog query layer by DOS-M09-005, Fly deploy pipeline and release provenance by DOS-M09-006, custom domain and TLS by DOS-M09-007, hosted-application hardening by DOS-M09-008, and browser support matrix + storage-behavior conformance suite by DOS-M09-009. The deployed application's Ecto repo list is asserted to be exactly `[CatalogRepo]`, opened read-only (ADR-0004 §4, §"Enforcement"), and there is no `UserRepo` to gate.

### Data and persistence

All server-side test data derives from committed or generated `CatalogRepo` fixtures; server-side tests run offline after dependency installation. Fixtures cover missing/conflicting provenance and the INV-11 statuses (`identity_only`, `schedule_supported`, `full_product_supported`, `not_applicable`, `unsupported`). Client-storage tests use IndexedDB in a real browser (the `DOS-M09-009` matrix runs) with per-run scratch origins; no personal exports, raw restricted datasets, or credentials enter fixtures, caches, or evidence bundles. The scripted-session test writes only synthetic garage data, and its captured logs are asserted to be free of personal fields per FR-10.

### Interfaces and events

- The CI pipeline definition (jobs, triggers, required checks) as the merge-blocking interface.
- The versioned **deploy evidence bundle** format as the standard artifact later issues attach to their Definition of done. Fields: environment/version manifest, `data_version` + catalog SHA, seed, clock/timezone, image digest, Fly release ID, browser/engine matrix result set, CSP/security-header snapshot, WSS handshake log, artifact checksums, redaction-reviewed log capture.
- The browser/engine matrix result-set schema (row = browser × engine × OS × suite-pass/fail), consumed from `DOS-M09-009` and rendered into the evidence bundle.
- The controlled-failure catalogue from FR-8 as a versioned set of scratch branches so gate regressions are detectable by re-running them.
- The exception record format: check, reason, owner, expiration.

### Failure and recovery behavior

A failing required gate blocks merge; there is no soft-fail mode for architectural gates (transport boundary, CSP, log scrubbing, repo-list assertion, hydration protocol). Flaky tests enter quarantine under documented rules with owner and expiration instead of being deleted or retried into green; browser-matrix rows may not be quarantined without an owner and expiration because they are the only proof of behaviour on real engines. Controlled-failure demonstrations are reproducible. CI infrastructure failure is distinguishable from product failure in job output. A Fly preview-deploy step that fails because Fly itself is unavailable is reported as infrastructure-degraded rather than as a product regression, but does not gate merge on its own — the offline suites remain the hard block.

### Security and privacy

Secret scanning and dependency/license audit run on every change. Caches never contain credentials, personal fixture data, or the deploy-scoped Fly token. Deploy evidence bundles are reviewed for redaction: no secrets, no raw restricted source data, no personal data, and no session assigns in logs (ADR-0004 §"Logging"). The hosted-transport gates (FR-8) prove that CSP is served, `check_origin` is an explicit allowlist, CSRF is enforced, rate limits fire, and the deployed repo list is exactly `[CatalogRepo]` opened read-only. Pinned immutable CI images/actions and Docker base images reduce supply-chain drift and are updated only under the documented policy. Third-party error reporting is not present and is not permitted (ADR-0004 §"No third-party anything"); the CSP third-party-origin scan is one of the gates that enforces this structurally.

### Accessibility and performance

The WCAG 2.2 AA accessibility baseline is a blocking budget with an owner, applied to the M01 surfaces that exist (diagnostic/readiness states, hosted shell, static Netlify support site) and verified via browser assistive-technology probes on the `DOS-M09-009` matrix. Performance budgets: first-visit payload (constitution 2.0.0 §9 — ≤ 250 KiB compressed initial HTML/CSS/JS, ≤ 500 KiB total first-visit transfer, zero third-party origins) is blocking; hydration time and LiveView round-trip latency are enforced as *provisional* thresholds pending ADR-0004 R9 re-ratification, labelled `provisional` in job output so they cannot be quietly promoted. CI runtime and cache behavior are recorded so the pipeline itself stays maintainable.

## UX and content states

N/A — CI and quality infrastructure with no product UI. No copy on these surfaces may imply the MVP is offline-capable, notifies the user when closed, or backs up user data — the surviving invariants INV-5, INV-6 (amended), INV-7 (amended), INV-17 (amended), and INV-25 apply to internal documentation too.

## Test plan

### Automated

- One full green pipeline run on a clean change, producing the complete versioned deploy evidence bundle enumerated in FR-5.
- Controlled-failure runs, one per architectural gate (addresses staleness sweep finding #2):
  - Injected route without `protect_from_forgery` or with `check_origin: true` — fails the transport-boundary gate.
  - Response served without CSP, or CSP with an added third-party `connect-src` — fails the CSP/third-party-origin gate.
  - A second `Repo` opened in the deployment, or an attempted personal-row write, or `CatalogRepo` opened read-write — fails the repo-list/read-only assertion.
  - A `handle_event` that logs its params so a VIN, odometer value, or `tab_id` appears in captured logs — fails the log-scrubbing gate.
  - A `pushEvent` handler that persists client hydration input to disk, database, cache, ETS, external store, or log — fails the no-server-side-personal-record gate.
  - A forbidden dependency, a bad `CatalogRepo` migration, and a secret-like value each fail their respective gate.
  - **Not run**: any "non-loopback bind" injection. That gate is retired with INV-2 (see §"Superseded pre-pivot spec" for the historical rationale).
- Offline verification: execute the FR-1(a)–(f) suites with network access disabled after dependency installation and confirm green. The Fly preview-deploy step is the one exception and runs after this check.
- Determinism spot-check: rerun the fixture-catalog and domain suites with identical seeds/clock/timezone injection and compare results.
- Budget-gate test: an artifact exceeding the first-visit payload blocking threshold fails; an informational trend metric and a *provisional* threshold do not block, but the *provisional* label is asserted to be present in job output.
- Hydration-protocol tests: idempotent hydration, `local_store:conflict` compare-and-set, hard-cap rejection, and the four distinct state assertions (`:hydrating`, `:empty`, `:storage_unavailable`, `:data_missing`).
- Fly preview-deploy smoke: image build, `flyctl deploy` to the non-production app, health check, canonical hostname, WSS handshake, one scripted `local_store:hydrate` round trip. On success, the deploy evidence bundle records image digest, Fly release ID, and WSS handshake log.

### Browser/engine matrix

- Execute the `DOS-M09-009` IndexedDB client-storage adapter conformance suite across the named browser/engine/OS matrix, recording per-row pass/fail in the deploy evidence bundle.
- Execute the hosted-endpoint security tests (HTTPS/WSS-only, `check_origin` allowlist, CSP/security headers) against the preview deploy from at least one representative row of the matrix.
- QA review session: walk through how a future M02/M04/M05/M06/M07/M09 issue cites these suites and attaches the deploy evidence bundle; record sign-off.
- Review of a sample deploy evidence bundle for redaction compliance (no secrets, restricted data, personal exports, or session assigns in logs).

## Rollout and rollback

CI configuration lands through reviewed pull requests and becomes required on the default branch once green. Rollback is reverting the configuration commit; gate policy changes (thresholds, quarantine, exceptions, blockers) require documented review under the update policy rather than ad hoc edits. No user-facing rollout exists. When a required gate is introduced that would newly break the default branch, it lands behind a short recorded soak window during which it is required-on-preview but advisory-on-main, then promoted to required-on-main in a follow-up commit that references the soak evidence — this is the one supported soft-launch pattern; there is no permanent soft-fail mode.

## Risks, decisions, and open questions

- Risk: browser-matrix runners flake or are temporarily unavailable, tempting a permanent quarantine. Mitigation: FR-7 requires owner and expiration on any `unproven` row; `unproven` is never counted as passing; a repeated quarantine is a defect against `DOS-M09-009`, not this pipeline.
- Risk: budget gates flake on shared runners (timing variance) — especially the *provisional* hydration and round-trip thresholds. Mitigation: *provisional* labels in job output, separate from stable blocking thresholds; measurement methodology documented per budget; ADR-0004 R9 re-ratification is the promotion path, not an off-the-record threshold tweak.
- Risk: deploy evidence bundles bloat CI storage. Mitigation: versioned, size-conscious format; artifacts are checksummed and retained under a documented policy.
- Risk: a well-meaning contributor re-adds a "non-loopback bind" gate from the pre-pivot spec (visible under §"Superseded pre-pivot spec") and every deploy fails. Mitigation: the FR-8 catalogue is the closed set of controlled failures; adding a new one is a governance change, and the pre-pivot section is explicitly historical.
- Decision to record: the CI platform/runner matrix and the immutable digest pinning mechanism for images, actions, and the Docker base image.
- Open question: whether the Fly preview-deploy step becomes required-on-main or stays required-on-preview until ADR-0004 R8 (single region / single machine) has real usage evidence. Track as follow-up rather than pre-decide.
- Open question: which browser/engine matrix rows are `required` versus `informational` — owned by `DOS-M09-009`; this pipeline consumes that answer and does not re-litigate it.

### Superseded technical implementation contract

*(Preserved verbatim from the pre-pivot spec.)*

**Components and ownership boundaries.** CI configuration invokes only the canonical DOS-M01-001 task commands so local and CI behavior cannot diverge. Suite definitions live with the code they test; gate policy (budgets, quarantine, exceptions, blockers) lives in `docs/quality/`. Budget owners are named per budget. This issue owns gate orchestration and evidence format; the gated behaviors are owned by their source issues (boundaries by DOS-M01-002, migrations by DOS-M01-003, pipeline by DOS-M01-004, shell by DOS-M01-005).

**Data and persistence.** All test data derives from committed or generated fixtures; tests run offline after dependency installation. Fixtures cover missing/conflicting provenance and offline/permission-denied states. No personal exports, raw restricted datasets, or credentials enter fixtures, caches, or evidence bundles.

**Interfaces and events.**

- The CI pipeline definition (jobs, triggers, required checks) as the merge-blocking interface.
- The versioned evidence-bundle format as the standard artifact later issues attach to their Definition of done.
- The physical-device smoke checklist template as the manual evidence interface until automation exists. **Superseded**: no physical-device smoke path in the MVP.
- The exception record format: check, reason, owner, expiration.

**Failure and recovery behavior.** A failing required gate blocks merge; there is no soft-fail mode for architectural gates. Flaky tests enter quarantine under documented rules with owner and expiration instead of being deleted or retried into green. Controlled-failure demonstrations are reproducible so gate regressions are detectable. CI infrastructure failure is distinguishable from product failure in job output.

**Security and privacy.** Secret scanning and dependency/license audit run on every change. Caches never contain credentials or personal fixture data. Evidence bundles are reviewed for redaction: no secrets, no raw restricted source data, no personal exports, and no private vehicle data in logs or fixtures. Pinned immutable CI images/actions reduce supply-chain drift and are updated only under the documented policy.

**Accessibility and performance.** The accessibility baseline from DOS-M00-004 is a blocking budget with an owner, applied to the surfaces that exist in M01 (diagnostic/readiness states, support site). Performance budgets (shell/catalog size, startup/readiness, query latency) are enforced with stable blocking thresholds; trend metrics are collected as informational. CI runtime and cache behavior are recorded so the pipeline itself stays maintainable.
