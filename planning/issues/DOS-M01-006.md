## Outcome

Automated gates validate domain behavior, schema/pipeline integrity, static/offline boundaries, accessibility baseline, dependency safety, and build reproducibility. Physical-device checks have a defined manual or device-lab evidence path until they can be automated. Feature teams inherit named test suites, blocking budgets, and a standard evidence format instead of recreating QA strategy per ticket.

## Why this matters and what it unblocks

The roadmap's constraints will erode if they are only prose. This issue turns them into repeatable gates and standard evidence so feature teams can ship without recreating QA strategy per ticket. Every M04-M08 issue's Definition of done cites these suites; the M01 epic exit gate depends on them; and the release gates in M07 build on the evidence bundle format standardized here.

- FR-5: Every CI run produces a versioned evidence bundle containing environment/version manifest, fixture/catalog version, seed, clock/timezone, logs, screenshots for UI failures, artifact checksums, and physical device/OS metadata where applicable.
- FR-6: Tests run offline from committed/generated fixtures after dependencies are installed; time-, mileage-, locale-, and timezone-dependent tests use injected values.

## Technical implementation contract

### Components and ownership boundaries

CI configuration invokes only the canonical DOS-M01-001 task commands so local and CI behavior cannot diverge. Suite definitions live with the code they test; gate policy (budgets, quarantine, exceptions, blockers) lives in `docs/quality/`. Budget owners are named per budget. This issue owns gate orchestration and evidence format; the gated behaviors are owned by their source issues (boundaries by DOS-M01-002, migrations by DOS-M01-003, pipeline by DOS-M01-004, shell by DOS-M01-005).

### Data and persistence

All test data derives from committed or generated fixtures; tests run offline after dependency installation. Fixtures cover missing/conflicting provenance and offline/permission-denied states. No personal exports, raw restricted datasets, or credentials enter fixtures, caches, or evidence bundles.

### Interfaces and events

- The CI pipeline definition (jobs, triggers, required checks) as the merge-blocking interface.
- The versioned evidence-bundle format as the standard artifact later issues attach to their Definition of done.
- The physical-device smoke checklist template as the manual evidence interface until automation exists.
- The exception record format: check, reason, owner, expiration.

### Failure and recovery behavior

A failing required gate blocks merge; there is no soft-fail mode for architectural gates. Flaky tests enter quarantine under documented rules with owner and expiration instead of being deleted or retried into green. Controlled-failure demonstrations are reproducible so gate regressions are detectable. CI infrastructure failure is distinguishable from product failure in job output.

### Security and privacy

Secret scanning and dependency/license audit run on every change. Caches never contain credentials or personal fixture data. Evidence bundles are reviewed for redaction: no secrets, no raw restricted source data, no personal exports, and no private vehicle data in logs or fixtures. Pinned immutable CI images/actions reduce supply-chain drift and are updated only under the documented policy.

### Accessibility and performance

The accessibility baseline from DOS-M00-004 is a blocking budget with an owner, applied to the surfaces that exist in M01 (diagnostic/readiness states, support site). Performance budgets (shell/catalog size, startup/readiness, query latency) are enforced with stable blocking thresholds; trend metrics are collected as informational. CI runtime and cache behavior are recorded so the pipeline itself stays maintainable.

## Test plan

### Automated

- One full green pipeline run on a clean change, producing the complete versioned evidence bundle.
- Controlled-failure runs, one per architectural gate: injected remote server call, non-loopback bind, forbidden dependency import, bad migration, and secret-like value — each demonstrably failing its gate and only its gate.
- Offline verification: execute the test suites with network access disabled after dependency installation and confirm green.
- Determinism spot-check: rerun the fixture-catalog and domain suites with identical seeds/clock/timezone injection and compare results.
- Budget-gate test: an artifact exceeding a blocking threshold fails; an informational trend metric does not block.

### Manual/device matrix

- Execute the physical-device smoke checklist template once on a physical iOS device and once on a physical Android device, recording device/OS metadata in the evidence bundle format.
- QA review session: walk through how a future issue cites suites and attaches evidence; record sign-off.
- Review of a sample evidence bundle for redaction compliance (no secrets, restricted data, or personal exports).

## Rollout and rollback

CI configuration lands through reviewed pull requests and becomes required on the default branch once green. Rollback is reverting the configuration commit; gate policy changes (thresholds, quarantine, exceptions) require documented review under the update policy rather than ad hoc edits. No user-facing rollout exists.

## Risks, decisions, and open questions

- Risk: iOS CI capability (runners/signing) limits automation. Mitigation: "iOS compile where runners/signing allow" plus the explicit manual physical-evidence path with owner and expiration on any skipped required check.
- Risk: budget gates flake on shared runners (timing variance). Mitigation: stable blocking thresholds separated from informational trends; measurement methodology documented per budget.
- Risk: evidence bundles bloat CI storage. Mitigation: versioned, size-conscious format; artifacts are checksummed and retained under a documented policy.
- Decision to record: the CI platform/runner matrix and the immutable pinning mechanism for images/actions.
- Open question: which physical-device checks can move from the manual checklist to a device lab, and on what criteria; each promotion is a follow-up issue, not silent scope growth.
