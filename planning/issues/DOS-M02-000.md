## Outcome

Produce implementation-ready flows, component/state specifications, content rules, accessibility expectations, and testable native-mobile prototypes for local onboarding, one active MVP vehicle, oil-change records, forecasts, and reminders. Preserve a clearly separated post-MVP design direction for multi-vehicle tabs/search without adding it to MVP implementation acceptance. Designs must show offline, missing-data, denied-permission, native-runtime failure, and destructive states—not only the happy path.

The mobile interaction and language model is frozen before feature UI is built: every screen, state, and sentence that M05/M06 implement is specified here, so that no implementation ticket invents product behavior, terminology, or navigation.

## Why this matters and what it unblocks

Feature implementation milestones (M05 single-vehicle MVP, M06 forecasting and reminders) cannot begin honest UI work while navigation models, component states, content rules, and accessibility expectations are undecided. Without this milestone, screen tickets would encode conflicting navigation models, misleading compatibility language, and happy-path-only states, and QA would have no state inventory to test against.

This epic unblocks the M02 → M05 edge of the cross-milestone DAG: M05 ("Single-vehicle MVP") is blocked on both M02 and M04. It also gives M06 its forecast/reminder UX contract and gives QA the content/state matrix used in M07 hardening.

## Excluded

- Any application code, LiveView implementation, or native build work — this milestone produces specifications and prototypes only.
- Implementing multi-vehicle tabs/Garage in MVP; the post-MVP direction is documented but never added to MVP implementation acceptance.
- Any UX that assumes an online account, runtime API lookup, remote Phoenix host, PWA/browser production surface, guaranteed notification delivery, or unverified compatibility data.
- Netlify marketing/support-site design, store screenshots, and all child-issue Excluded items (each child's exclusions apply unchanged).
- Data acquisition, licensing, or catalog-content work (M03) and persistence implementation (M04).

## Dependency rationale

Position in the M00→M08 DAG: M00 → M02 (this epic starts only after the DOS-M00-000 architecture gate), and M02 → M05 (the single-vehicle MVP consumes these frozen specs together with M04's domain/persistence work). M02 may run in parallel with M01 and permitted free-source M03 investigation after its exact M00 blockers close, but individual children carry hard M01 blockers (DOS-M01-002/003/004/005) where screen states must cite approved technical contracts to remain truthful. M02 deliberately precedes feature UI so M05/M06 implementation tickets inherit, rather than invent, interaction and language decisions.

## Risks, decisions, and open questions

- Risk: M01 contract churn invalidates already-specified screen data requirements. Mitigation: children cite contract versions; changed contracts reopen the affected spec through change control.
- Risk: post-MVP multi-vehicle design ambition leaks into MVP acceptance. Mitigation: FR-8/AC-5 require labeled appendices and forbid MVP acceptance references.
- Risk: specs drift toward happy-path fidelity because failure states are harder to draw. Mitigation: AC-4 makes failure/destructive states an explicit exit condition.
- Open question: exact prototype tooling (clickable prototype platform) is a child-level decision; the epic only requires that the result be testable on mobile at both text sizes.
- Decision recorded: no UX may promise behavior the M00 proofs did not demonstrate (notifications, runtime capabilities); disagreements route to ADRs, not design workarounds.

## Definition of done

All eight children are accepted and closed with attached evidence; the milestone exit gate (clickable prototype plus content/state matrix covering every core path at compact and large text sizes; engineering and QA able to implement/test without inventing behavior) is verified in a recorded sign-off; the post-MVP direction is separated; no accepted design violates the entry-gate constraints; and this epic links every deliverable so M05/M06 planning can proceed without re-litigating UX decisions.
