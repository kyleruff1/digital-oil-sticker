> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Routes become real shareable URLs with browser history, refresh, and deep-link semantics, and every flow must define its pre-hydration entry state._

## Outcome

A route map and task-flow specification for the **hosted browser MVP**: every MVP destination is a real, shareable URL on the Fly.io-hosted Phoenix router at `digitaloilsticker.com`, addressable by the browser's location bar, restorable on refresh, navigable with the browser's back and forward buttons, and safe to paste into an email or another tab. Every flow declares its **pre-hydration entry state** — the honest skeleton that the LiveView renders after `mount/3` but before the `LocalStore` hook has returned the user's records from IndexedDB — so that no returning user is ever told, even for one frame, that their garage is empty (INV-24.3).

The deliverable is the navigation spine of the browser product: a sitemap/route table keyed by URL, end-to-end flow diagrams for every listed scenario, per-screen data/ownership declarations that cite the server-side catalog query surface (`DigitalOilSticker.Catalog` per DOS-M09-004) or the IndexedDB object stores (per DOS-M09-001) rather than inventing fields, restoration/deep-link rules that survive browser refresh, tab restore, deploy-induced socket drop, and multi-tab open, and the hydration-state contract every downstream M02 and M05 ticket must observe. Post-MVP multi-vehicle navigation is documented separately as a web navigation pattern with per-vehicle URLs.

## Why this matters and what it unblocks

Under the browser-first architecture the navigation model is no longer a private convention inside a single WebView — it is the URL surface of a public website. Component and screen tickets will otherwise encode conflicting assumptions about what a URL means, when hydration completes, what a refresh preserves, and whether a "notification deep link" exists at all (it does not; INV-17 retires OS notifications for the MVP). This issue freezes those assumptions so that the design system, the LiveView shell, and every downstream flow spec can be built without renegotiating them.

Concretely, it unblocks the re-scoped DOS-M02-002 (design system needs a fixed URL/route model, browser accessibility contract, and the hydration-state taxonomy), DOS-M02-003 through DOS-M02-008 (each flow plugs into these routes and inherits their pre-hydration rules), DOS-M05-001 through DOS-M05-007 (integrate the domain contract, wire vehicle/change flows, ship the sticker dashboard, and export/import — all against these URLs), and gives QA the route/state coverage table that later becomes end-to-end browser cases exercised on the DOS-M09-008 browser support matrix.

## Included

- Define MVP primary destinations as **URL routes** on the Phoenix router: the sticker dashboard (active vehicle status), first-run/onboarding, vehicle add/search or replace, oil-change history and detail, record/edit change, vehicle settings/driving usage, reminders (in-app due/overdue only), app/data settings including storage status and export/import, About / Data Sources, and the honest-degradation destinations (storage unavailable, data missing after clear, session-only mode).
- Specify how each URL behaves under browser refresh, tab restore, back/forward, sharing to another tab or window (same browser), sharing to a different browser or device (which is defined as _no continuity_ per INV-19 and INV-23), and reload after a Fly.io deploy that dropped the socket.
- Specify, for every route, the **pre-hydration entry state** the LiveView renders while `assigns.local_state == :hydrating`: what the skeleton shows, what it does not show, what interactive controls are inert until the hydration state is known, and what live-region announcements fire when hydration resolves. This is the section that operationalizes INV-24.3 for each route.
- Specify how routes carrying a client-scoped identifier (`vehicle_id`, `event_id`) resolve **after** hydration: the identifier is not resolved server-side against a database — the server has no personal database — it is resolved against the hydrated payload held in `socket.assigns` for the socket lifetime, with an honest fallback route and message when the identifier is stale, missing, or held in the quarantine list produced by ADR-0004 §"Validation".
- Map the browser-MVP flows: first-visit (empty store), returning-visit (hydration succeeds), record oil change, forecast-insufficient-data, due/overdue in-app, offline/disconnected (WSS down), catalog-query-failed, hydration-deadline-exceeded (`:storage_unavailable`), storage-cleared (`:data_missing`), quota-exhausted, session-only (private browsing / blocked storage), custom-vehicle (manual entry when catalog cannot resolve), export, import (replace or merge with preview), and local-data-reset. Multi-vehicle add/switching appears **only** in the labeled post-MVP appendix, as a web navigation pattern with per-vehicle URLs.
- Identify all exits/cancel paths, back-button behavior (browser back is a first-class control the flow must not fight), refresh behavior, unsaved-change handling on beforeunload and on cross-route navigation, keyboard/focus behavior including tab order across the skeleton-to-content swap, and destructive confirmations.
- Establish screen-level data requirements and ownership: catalog fields cite `DigitalOilSticker.Catalog` behaviors provided by DOS-M09-004; personal fields cite the IndexedDB object stores defined by DOS-M09-001; nothing is invented.
- Produce the route table (URL, purpose, LiveView owner, catalog dependencies, IndexedDB dependencies, entry/exit URLs, pre-hydration skeleton spec, state inventory) and flow diagrams as reviewable, versioned planning artifacts under `planning/`.

## Functional requirements

- **FR-1 (replaces pre-pivot FR-1; addresses finding 1):** The route map defines every MVP primary destination listed in Included as a real URL on the Fly.io-hosted Phoenix router at `digitaloilsticker.com` (INV-1, INV-22, INV-27), each with a stable URL, a purpose statement, and an owning LiveView. URLs are shareable within the same browser, restorable on refresh, and navigable with browser back and forward. No route requires a second navigation stack, a WebView shell, or any on-device chrome; there is no "single Mob root WebView" — the hosted Phoenix route stack, served over HTTPS and WSS behind Fly's proxy, is the whole navigation surface (ADR-0004 §"Decision").
- **FR-2 (new; addresses the pivot line):** Every flow declares its **pre-hydration entry state** per INV-24.3 and ADR-0004 §"First-paint and empty-state rules". The declaration names the skeleton the LiveView renders while `assigns.local_state == :hydrating`, states what it does not show (no empty-garage claim, no onboarding-from-zero copy, no cheerful welcome that a returning user could see for even one frame), lists which interactive controls are inert until the hydration state is known, and specifies the live-region announcement that fires when the state resolves. The three states `:hydrating`, `:empty` (genuine first visit), and `:storage_unavailable` are visibly distinct and their skeletons/copy differ.
- **FR-3 (replaces pre-pivot FR-3):** Route/state restoration is specified for **browser refresh, tab restore, browser back/forward, Fly.io-deploy socket drop, and multi-tab open**. On any reconnect, LiveView assigns are wiped, the hook re-hydrates, and the prior DOM is retained under `phx-disconnected` styling — the flow may not tear down to a fresh skeleton on reconnect (ADR-0004 §"First-paint and empty-state rules"). A URL that references a client-scoped identifier (`vehicle_id`, `event_id`) resolves against the hydrated payload in `socket.assigns` **after** hydration, never against a server database. If the identifier is stale, missing, or quarantined by ADR-0004 §"Validation", the flow routes to a named fallback (Garage or the sticker dashboard) with an explicit message; the URL bar reflects the fallback via `push_patch`, never a silent redirect that leaves the stale URL visible.
- **FR-4 (new):** URLs carry **no personal data**. Path segments and query parameters may hold only impersonal selectors (route name, vehicle configuration identifiers resolved server-side per INV-26, client-generated `vehicle_id` UUIDv4 values used purely as opaque keys into IndexedDB) — never a VIN, odometer, date, note, custom vehicle name, or any value from `socket.assigns.data` that originated in the user's browser (INV-4, INV-26, ADR-0004 §"Security and privacy boundary"). Client-scoped UUIDs in URLs are opaque and are resolved only via the hydrated assigns; the server has no personal database to resolve them against.
- **FR-5 (replaces pre-pivot FR-5):** Every flow specifies exits/cancel paths, browser back-button behavior (the browser back button is a first-class control the flow must not intercept without warning), refresh behavior, unsaved-change handling on both `beforeunload` and cross-route navigation (no in-progress form is lost without warning, and mutation-in-flight — a `pushEvent` waiting on the hook's ack per INV-24.2 — is either allowed to complete or is visibly reverted, never silently dropped), keyboard/focus behavior across the skeleton-to-content swap, and destructive confirmations.
- **FR-6 (replaces pre-pivot FR-6):** Each screen declares required data and its owner by citing the browser-first data surfaces:
  - Catalog data (vehicles, schedules, oil requirements, filter fitments, provenance, support statuses) cites a typed behavior on `DigitalOilSticker.Catalog` provided by DOS-M09-004, opened read-only via `CatalogRepo`, and carries only impersonal parameters (INV-26).
  - Personal data (garage vehicles, service events, odometer readings, reminder intent, preferences) cites an IndexedDB object store from the layout owned by DOS-M09-001 (`vehicles`, `events`, `readings`, `reminders`, `prefs`, `meta`) and reaches assigns via the hydration protocol owned by DOS-M09-002.
  - No field is invented; no route implies a server-side personal record; and no route reads or writes across the CatalogRepo / IndexedDB boundary in a way that would create one.
- **FR-7 (replaces pre-pivot FR-7):** Core tasks are reachable on a mid-tier mobile browser without a keyboard, and equivalently reachable on a desktop browser using keyboard only, per Constitution §9 accessibility (WCAG 2.2 AA, 200% zoom, 320 CSS px reflow width, full keyboard operability with visible focus). Route transitions must not depend on high network quality: hydration completion is budgeted at p95 ≤ 300 ms after socket join per §9, and the honest degradation states cover longer paths without inventing content.
- **FR-8 (replaces pre-pivot FR-8):** Each route declares its state inventory using the named browser-first taxonomy: `:hydrating` (pre-hydration skeleton), `:empty` (genuine first visit, hydration returned zero records with `dos_boot_state == "never"`), `:loaded` (hydration returned records), `:data_missing` (`dos_boot_state == "has_data"` but hydration returned zero records — the storage-cleared state that must be visibly distinct from `:empty` per INV-24.4/INV-24.8/INV-25), `:storage_unavailable` (IndexedDB blocked, unavailable, or hydration deadline exceeded per ADR-0004; session-only fallback), plus route-specific states such as `:catalog_error` (INV-7) and `:socket_disconnected` (INV-7, ADR-0004 `phx-disconnected` styling). No route may collapse two of these into a shared "something went wrong" fallback.
- **FR-9 (replaces pre-pivot FR-9):** Selected-vehicle context is visible on every vehicle-scoped screen and is not inferred solely from color (Constitution §9 accessibility; INV-11). The one-active-vehicle rule (INV-18) is enforced in the MVP UI; the underlying garage in IndexedDB is multi-vehicle-safe from the first write.
- **FR-10 (replaces pre-pivot FR-2 and FR-10):** Reminders are **in-app due/overdue state only** (INV-17). No route, control, disabled affordance, or copy anywhere in the MVP implies scheduled notifications, background alerts, Web Push, or a service worker (INV-17, INV-19). The pre-pivot FR-10 "notification deep links use stable local IDs" is retired: there are no OS notifications in the browser MVP, and URLs — the only shareable references — carry no personal data (FR-4, INV-26). The post-MVP multi-vehicle appendix respecifies "vehicle tabs" as a web navigation pattern with per-vehicle URLs (per the pivot doc's DOS-M08-002 disposition), not a native bottom-tab bar.
- **FR-11 (new):** Every flow addresses browser lifecycle events that the pre-pivot spec never had to consider: **tab visibility change** (`visibilitychange`, LiveView heartbeat during background tab), **browser back/forward via `popstate`** (routes must be idempotent across back-navigation, and forms must not silently re-submit), **`beforeunload` on unsaved changes**, **multi-tab writes** (per ADR-0004 §"Multi-tab consistency"; a mutation in tab A must be reflected in tab B via `BroadcastChannel` re-hydration, and the losing tab must be told), and **deploy-induced socket drop** (proven-robust reconnect per ADR-0004 §"WebSocket and LiveView considerations"; the flow must not lose an in-flight mutation across a deploy).

## Technical implementation contract

### Components and ownership boundaries

The route map assigns each destination to a LiveView served by the Fly.io-hosted Phoenix application at `digitaloilsticker.com`, over HTTPS/WSS behind Fly's proxy with `check_origin` bound to the exact production hostnames (INV-1, INV-22, INV-27; ADR-0004 §"WebSocket and LiveView considerations"). (Note on vocabulary: the prohibited-vocabulary rule that keeps `on-device`, `native`, `Mob`, and WebView terminology out of the browser-first spec permits explicit retirement statements that name the retired mechanism; a handful of such statements follow across the FR block, the Components section, and FR-10's post-MVP appendix note, each flagged by "retired", "no longer", or "not a".) The historical "single Mob root WebView / Phoenix route stack" framing is retired: there is no on-device WebView, no `Mob.Socket` distinction, no second native navigation stack. Navigation is the browser's URL bar plus history stack, driven by `live_patch`/`push_patch`/`push_navigate` and the browser's back/forward buttons.

Screen data ownership cites the client-agnostic domain contexts named by ADR-0004 §"Decision" clause 6 — `DigitalOilSticker.Catalog`, `.Garage`, `.Forecast`, and the resolver — plus the read-only server-side query surface (`CatalogRepo` via DOS-M09-004) and the client IndexedDB stores (DOS-M09-001) reached via the hydration protocol (DOS-M09-002). No screen owns storage directly. No domain module references `Phoenix.LiveView` or the `LocalStore` protocol (mechanically enforced per ADR-0004 §"Enforcement").

### Data and persistence

This is a specification deliverable — no data is persisted by this issue, and by architectural rule the server persists **no** personal data at any time (INV-3, INV-23, ADR-0004 §"Decision" clause 4). The spec itself must:

- Reference only fields present in `DigitalOilSticker.Catalog` (typed behaviors resolved server-side by DOS-M09-004 over `CatalogRepo`) or in the IndexedDB object stores defined by DOS-M09-001 (`meta`, `vehicles`, `events`, `readings`, `reminders`, `prefs`).
- Declare, per route, which fields come from the server (catalog reads over the LiveView socket, cached by `data_version` per DOS-M09-004) and which come from the client (hydrated from IndexedDB per DOS-M09-002, held in `socket.assigns` for the socket lifetime only).
- Declare, per route, the **minimum hydrated payload** needed for the pre-hydration skeleton to progress to `:loaded` — this is what the hook returns from the initial `readonly` IDB transaction; anything the route needs beyond that is either fetched from the catalog by an impersonal query (INV-26) or waited on with an honest loading state.
- Never declare a "restoration state" that assumes server-side survival across a socket drop: assigns die with the socket, and reconnect re-runs hydration.

### Interfaces and events

Flows annotate where domain events flow between the LiveView and the `LocalStore` hook per the mutation round trip in ADR-0004 §"Mutation round trip": user acts → `handle_event` → server computes new state in assigns → `push_event(local_store:put, ...)` → hook commits the IndexedDB transaction with compare-and-set on `meta.seq` → hook `pushEvent(local_store:ack, ...)` → server clears the pending write. The flow spec identifies, per mutation, the affected stores, the optimistic-render affordance, and the failure path when no ack arrives within 2 000 ms (persistent "Not saved to this browser" state, per ADR-0004; never a silent retry or invisible rollback).

Shareable references are **URLs**, not notification payloads (INV-17). URLs carry only impersonal selectors and opaque client-generated identifiers per FR-4; a stale identifier resolves to a named fallback route with an explicit message via `push_patch`.

### Failure and recovery behavior

Every route declares its browser-first failure states per FR-8: `:catalog_error` when a catalog query fails (INV-7 — distinguishable from missing data, never "no data for this vehicle"), `:socket_disconnected` under `phx-disconnected` styling with the previous DOM retained (ADR-0004), `:storage_unavailable` when the hydration deadline expires or IndexedDB is blocked, `:data_missing` when `dos_boot_state == "has_data"` but hydration returned zero records (the honest storage-loss state per INV-24.8 / INV-25 — never rendered as `:empty`), and session-only mode when the availability probe fails (functional for catalog browsing, explicit persistent banner that nothing is being saved, export offered prominently and repeatedly). Deploy-induced socket drop is a first-class case: the flow proves that reconnect re-runs hydration and that any in-flight mutation is either driven to completion from client storage or surfaced as unsaved, never lost.

### Security and privacy

Routes never embed personal data in URL parameters, path segments, fragments, or connect params (FR-4, INV-4, INV-26, ADR-0004 §"Security and privacy boundary"). All routes serve over HTTPS with HSTS enabled after certificate verification and WSS for the LiveView socket (INV-22). CSRF is verified on socket connect and every non-idempotent HTTP route (INV-22). The strict CSP from ADR-0004 §"Content Security Policy" applies — no third-party origins, no CDN scripts, no external fonts. External About / Data Sources links to non-owned domains are marked `rel="noopener noreferrer"` and open in a new tab; the Netlify static content boundary per INV-27 is honored (static content lives at `help.` / `legal.` subdomains or on `digitaloilsticker.net` per the DOS-M09-006 disposition, never mixed into the application origin).

### Accessibility and performance

Core tasks reachable on a mid-tier mobile browser without a keyboard, and equivalently reachable on a desktop browser keyboard-only (FR-7, Constitution §9 accessibility: WCAG 2.2 AA, text contrast, 200% zoom, 320 CSS px reflow, visible focus indicator, no keyboard traps, target size, screen-reader operability with live-region announcement of hydration and due-state changes). Route transitions must budget within Constitution §9's provisional targets — LCP p75 ≤ 2.5 s, TTI p75 ≤ 3.5 s, LiveView connect p95 ≤ 1.0 s, hydration completion p95 ≤ 300 ms, LiveView event round trip p95 ≤ 150 ms — and every flow's pre-hydration entry state must be honest about the ≤ 300 ms window between assigns being empty and the hook returning. Detailed component accessibility is delegated to the re-scoped DOS-M02-002, which this spec must not contradict.

## UX and content states

- **Per-route state inventory** drawn from the named browser-first taxonomy (FR-8): `:hydrating`, `:empty`, `:loaded`, `:data_missing`, `:storage_unavailable`, session-only, `:socket_disconnected`, `:catalog_error`, plus flow-specific states — each with entry/exit URLs and its own copy.
- **Flow-level states:** first-visit vs. returning-visit; forecast-insufficient-data; due/overdue in-app; storage-cleared / evicted (`:data_missing`); private-browsing / blocked-storage (session-only); catalog-query-failed; hydration-deadline-exceeded; quota-pressure and quota-exhaustion; custom-vehicle manual entry; local-data-reset confirmation and completion.
- **Cross-cutting states:** unsaved-change warning (both `beforeunload` and cross-route navigation), destructive confirmation, mutation-in-flight indicator, `phx-disconnected` styling on reconnect, stale-reference fallback with `push_patch` to the fallback URL, and selected-vehicle context display.
- **Terminology** follows CONSTITUTION.md INV-21 and INV-25: "stored in this browser" is the required framing; "saved to your account", "synced", "backed up", and "restore" MUST NOT appear (a route-level copy-lint gate — owned by DOS-M09-003 — fails the build on prohibited words). Route names are frozen by AC-5.

### Technical implementation contract

#### Components and ownership boundaries

The route map assigns each destination to an expected LiveView from master prompt §7 (`OnboardingLive`, `VehiclePickerLive`, `StickerLive`, `OilChangeLive`, `RecommendationLive`, `MileageLive`, `SettingsLive`, plus `AppShell`) or explicitly proposes a new one for M02-002 to specify. Navigation lives in the single Phoenix route stack inside the one Mob root WebView; no flow may require a second native navigation stack. Screen data ownership cites `DigitalOilSticker.Catalog`, `Garage`, `Maintenance`, `Forecasting`, and `Reminders` context boundaries; no screen owns storage directly.

#### Data and persistence

This is a specification deliverable — no data is persisted by this issue. The spec itself must: (a) reference only fields present in the DOS-M01-003 schemas / master prompt §8 tables (`vehicles`, `service_events`, `odometer_readings`, `maintenance_plans`, `reminder_rules`, `scheduled_notifications`, `catalog_metadata`, `data_sources`, and catalog identity tables); (b) declare which routes read `CatalogRepo` versus `UserRepo`; (c) declare restoration state (what minimal state each route needs to rehydrate after process death).

#### Interfaces and events

Flows annotate where domain events from the §7 local event contract fire or are consumed: `vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, `catalog_activated`. Notification deep links are specified as stable local identifiers (vehicle/cycle/rule IDs per the `scheduled_notifications` table), resolved through a validation step before navigation; the spec defines the fallback route when resolution fails.

#### Failure and recovery behavior

Every route declares its error and stale-data behavior (FR-8). Specific mandatory failure flows: bundled-catalog-invalid (route to the readiness/repair experience defined in DOS-M02-003), missing/archived/deleted vehicle on deep link (resolve to Garage with explanation), interrupted in-progress form (warn before discard), and app-restart mid-flow (declared restoration state per route).

#### Security and privacy

Routes never embed personal data (VIN, odometer, notes) in URL parameters or deep-link payloads; deep links carry only stable local IDs. All routes are loopback application routes per §7 shell security; external links (e.g., About/Data Sources) are flagged for system-browser handoff. No route requires or implies network access or an account.

#### Accessibility and performance

Core tasks reachable with one hand (FR-7); back/cancel/focus behavior specified per flow (FR-5); selected-vehicle context is never color-only (FR-9). Keyboard/focus behavior includes software-keyboard interactions on form routes. Route transitions must not depend on network latency — all navigation is local. Detailed component accessibility is delegated to DOS-M02-002, which this spec must not contradict.

### UX and content states

- Per-route state inventory: loading, empty, ready, offline, error, stale-data (where applicable), each with entry/exit paths.
- Flow-level states: first-use vs. returning-use; forecast-insufficient-data; due/overdue; denied-notification; offline-ready; bundled-catalog-invalid; custom-vehicle; local-data-reset confirmation and completion.
- Cross-cutting states: unsaved-change warning, destructive confirmation, stale deep link ("this vehicle is no longer available" explanation on the Garage resolution), and selected-vehicle context display.
- Terminology follows §6 required terminology and DOS-M00-001 ratified vocabulary; route names are frozen by AC-5.
