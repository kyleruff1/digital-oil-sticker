## Outcome

A route map and task-flow specification establish where users find the one active MVP vehicle's status, history, replace/edit vehicle, record oil change, driving usage, reminders, local-data controls, and source information, with post-MVP multi-vehicle navigation documented separately.

The deliverable is the navigation spine of the product: a sitemap/route table, end-to-end flow diagrams for every listed scenario, per-screen data/ownership declarations, and restoration/deep-link rules that all later M02 specifications and all M05/M06 implementation tickets must follow.

## Why this matters and what it unblocks

Component and screen tickets will otherwise encode conflicting navigation models. This issue unblocks the prototype, component inventory, deep links, state restoration, and test scenarios.

Concretely, it unblocks DOS-M02-002 (design system components need a fixed navigation model), DOS-M02-003 through DOS-M02-008 (each flow spec plugs into these routes), and gives QA the route/state coverage table that later becomes end-to-end test cases.

## Included

- Define MVP primary destinations for mobile: active vehicle status, add/search or replace vehicle, oil-change history/detail, record/edit change, vehicle settings/driving usage, reminders, app/data settings, and About/Data Sources.
- Document—but do not include in MVP implementation acceptance—the post-MVP scalable model: horizontally scrollable/reorderable vehicle tabs or selector for quick switching plus a searchable Garage list for larger collections. Do not create one permanent bottom-navigation item per vehicle.
- Define route/state restoration after app restart, deep link, update, and notification tap. A missing/archived/deleted vehicle route resolves safely to Garage with explanation.
- Map first-use, returning-use, add/replace-active-vehicle, log-change, forecast-insufficient-data, due/overdue, denied-notification, offline-ready, bundled-catalog-invalid, custom-vehicle, and local-data-reset flows. Place add-second-vehicle/switching in the labeled post-MVP appendix.
- Identify all exits/cancel paths, back behavior, unsaved-change handling, keyboard/focus behavior, and destructive confirmations.
- Establish screen-level data requirements and ownership, citing schema/query contracts rather than inventing fields.
- Produce the route table (route identifier, purpose, required data, entry paths, exit paths, state inventory) and flow diagrams as reviewable, versioned planning artifacts.

## Excluded

- Final colors/typography, code, desktop-specific feature parity beyond responsive adaptation, online sharing/sync, advertisements, service-shop discovery, or telematics.
- Implementing any route or screen; visual design tokens/components (DOS-M02-002); per-flow interaction detail owned by DOS-M02-003 through DOS-M02-008.
- Multi-vehicle navigation as MVP scope; it appears only in the labeled post-MVP appendix.

## Functional requirements

- FR-1: The route map defines every MVP primary destination listed in Included, each with a stable route identifier, purpose statement, and owning context per DOS-M01-002 boundaries.
- FR-2: The post-MVP scalable navigation model (horizontally scrollable/reorderable vehicle tabs or selector plus searchable Garage list) is documented in a clearly labeled appendix, is excluded from MVP implementation acceptance, and never proposes one permanent bottom-navigation item per vehicle.
- FR-3: Route/state restoration is specified for app restart, deep link, app update, and notification tap; a route referencing a missing/archived/deleted vehicle resolves safely to Garage with an explanation, never to a crash or wrong vehicle.
- FR-4: End-to-end flow diagrams cover all eleven MVP scenarios: first-use, returning-use, add/replace-active-vehicle, log-change, forecast-insufficient-data, due/overdue, denied-notification, offline-ready, bundled-catalog-invalid, custom-vehicle, and local-data-reset; add-second-vehicle and vehicle switching appear only in the post-MVP appendix.
- FR-5: Every flow identifies exits/cancel paths, back behavior, unsaved-change handling (no in-progress form is lost without warning), keyboard/focus behavior, and destructive confirmations.
- FR-6: Each screen declares required data and its owner by citing schema/query contracts (DOS-M01-003 tables, DOS-M01-002 context boundaries); no field is invented.
- FR-7: Core tasks are reachable with one hand and without network after provisioning.
- FR-8: Each route declares loading, empty, ready, offline, error, and stale-data behavior where applicable.
- FR-9: Selected-vehicle context is visible on every vehicle-scoped screen and never inferred solely from color.
- FR-10: Notification deep links use stable local IDs and cannot expose another deleted/archived vehicle accidentally.

## Technical implementation contract

### Components and ownership boundaries

The route map assigns each destination to an expected LiveView from master prompt §7 (`OnboardingLive`, `VehiclePickerLive`, `StickerLive`, `OilChangeLive`, `RecommendationLive`, `MileageLive`, `SettingsLive`, plus `AppShell`) or explicitly proposes a new one for M02-002 to specify. Navigation lives in the single Phoenix route stack inside the one Mob root WebView; no flow may require a second native navigation stack. Screen data ownership cites `DigitalOilSticker.Catalog`, `Garage`, `Maintenance`, `Forecasting`, and `Reminders` context boundaries; no screen owns storage directly.

### Data and persistence

This is a specification deliverable — no data is persisted by this issue. The spec itself must: (a) reference only fields present in the DOS-M01-003 schemas / master prompt §8 tables (`vehicles`, `service_events`, `odometer_readings`, `maintenance_plans`, `reminder_rules`, `scheduled_notifications`, `catalog_metadata`, `data_sources`, and catalog identity tables); (b) declare which routes read `CatalogRepo` versus `UserRepo`; (c) declare restoration state (what minimal state each route needs to rehydrate after process death).

### Interfaces and events

Flows annotate where domain events from the §7 local event contract fire or are consumed: `vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, `catalog_activated`. Notification deep links are specified as stable local identifiers (vehicle/cycle/rule IDs per the `scheduled_notifications` table), resolved through a validation step before navigation; the spec defines the fallback route when resolution fails.

### Failure and recovery behavior

Every route declares its error and stale-data behavior (FR-8). Specific mandatory failure flows: bundled-catalog-invalid (route to the readiness/repair experience defined in DOS-M02-003), missing/archived/deleted vehicle on deep link (resolve to Garage with explanation), interrupted in-progress form (warn before discard), and app-restart mid-flow (declared restoration state per route).

### Security and privacy

Routes never embed personal data (VIN, odometer, notes) in URL parameters or deep-link payloads; deep links carry only stable local IDs. All routes are loopback application routes per §7 shell security; external links (e.g., About/Data Sources) are flagged for system-browser handoff. No route requires or implies network access or an account.

### Accessibility and performance

Core tasks reachable with one hand (FR-7); back/cancel/focus behavior specified per flow (FR-5); selected-vehicle context is never color-only (FR-9). Keyboard/focus behavior includes software-keyboard interactions on form routes. Route transitions must not depend on network latency — all navigation is local. Detailed component accessibility is delegated to DOS-M02-002, which this spec must not contradict.

## UX and content states

- Per-route state inventory: loading, empty, ready, offline, error, stale-data (where applicable), each with entry/exit paths.
- Flow-level states: first-use vs. returning-use; forecast-insufficient-data; due/overdue; denied-notification; offline-ready; bundled-catalog-invalid; custom-vehicle; local-data-reset confirmation and completion.
- Cross-cutting states: unsaved-change warning, destructive confirmation, stale deep link ("this vehicle is no longer available" explanation on the Garage resolution), and selected-vehicle context display.
- Terminology follows §6 required terminology and DOS-M00-001 ratified vocabulary; route names are frozen by AC-5.

## Rollout and rollback

The route map and flow spec are committed, versioned planning artifacts. Acceptance freezes route terminology for downstream issues. Changes after acceptance go through change control (new issue or ADR per non-negotiable rule 10); rollback is reverting to the prior accepted revision. No runtime rollout applies.

## Dependency rationale

- DOS-M00-001: flows must use ratified invariants and terminology; writing flows before ratification would bake in disallowed language.
- DOS-M00-004 through DOS-M00-006: restoration, catalog-invalid, and data-boundary flows must describe proven two-repo SQLite, `mob_notify`, and data-slice behavior, not aspirations.
- DOS-M01-002: screen ownership declarations require the approved module/adapter boundary map.
- DOS-M01-003: screen-level data requirements must cite real schema contracts; this is the explicit alternative to inventing fields.
- Downstream: DOS-M02-002 through DOS-M02-008 all list this issue (directly or transitively) as a prerequisite; it is the first child of the M02 epic.

## Risks, decisions, and open questions

- Risk: flows drift from the single-WebView/single-route-stack constraint by assuming native navigation. Mitigation: the components contract binds every destination to the Phoenix route stack; deviations require an ADR.
- Risk: the post-MVP appendix quietly becomes MVP scope during review. Mitigation: FR-2/AC-3 keep it labeled and non-blocking.
- Risk: deep-link rules are specified beyond what DOS-M00-005 proved. Mitigation: notification-tap flows cite the M00-005 evidence; unproven behaviors are marked open questions, not requirements.
- Open question: exact step-count targets for the two cognitive-walkthrough tasks are set during the walkthrough and recorded as evidence; they must be justified, not invented.
- Decision to record: final list of route identifiers and their mapping to §7 LiveView names (any proposed new LiveView is flagged for DOS-M02-002).

## Definition of done

All FRs satisfied and all ACs checked with evidence attached; the route table, flow diagrams, and coverage table are committed as versioned artifacts; the four-party terminology approval is recorded; the post-MVP appendix is clearly separated; and DOS-M02-002 through DOS-M02-008 can cite stable route identifiers without rework.
