## Outcome

A compact design-system specification defines tokens, reusable LiveView components, native-WebView behavior, interaction states, and accessibility rules for the production iOS and Android applications.

The deliverable is the single component and accessibility contract that every M02 flow spec references and every M05/M06 UI ticket implements: semantic tokens, a complete component inventory with all interactive states, WCAG 2.2 AA rendered-content rules, and VoiceOver/TalkBack expectations for LiveView content inside the native WebView.

## Why this matters and what it unblocks

Shared states—vehicle selection, provenance badges, status, forms, tabs, permissions, and errors—will drift without a common contract. This issue unblocks all UI implementation and visual/interaction QA.

It also gives DOS-M02-003 through DOS-M02-008 a fixed component vocabulary, gives engineering the component-to-owner mapping needed to avoid duplicate implementations, and gives QA the accessibility state matrix used in prototype reviews and later device testing.

## Included

- Define semantic color, type scale, spacing, elevation/borders, iconography, motion, safe-area, focus, and breakpoint tokens. Status must use text/icon/shape in addition to color.
- Specify components: app shell/header, bottom navigation where selected, vehicle tab/selector, search field, filter control/chips, virtualized result row, vehicle/status card, due-status meter, source/confidence badge, form fields, date/mileage/unit inputs, product selector, banners, inline validation, empty/error/offline panels, permission prompt, modal/sheet, toast, destructive confirmation, and progress/readiness indicators.
- Include all interactive states: rest, hover where applicable, pressed, focus-visible, selected, disabled with reason, loading, invalid, success, stale, offline, and reduced-capability.
- Use WCAG 2.2 AA as the rendered LiveView-content baseline and define native WebView semantics, labels, reading order, rotor/headings, contrast, reduced motion, and switch/keyboard operation for VoiceOver and TalkBack.
- Support at least 44×44 pt iOS and 48×48 dp Android touch targets, safe areas, portrait-first layouts, software keyboard avoidance, text scaling/dynamic type, and long localized strings.
- Define skeleton versus spinner use and prohibit indefinite loading for local queries.
- Map each design component to a single reusable implementation owner (the §7 component/LiveView inventory or an explicitly proposed addition).

## Excluded

- Netlify marketing/support-site design, browser/PWA production design, custom illustration system, animation for decoration, final store screenshots, or platform-specific divergence without a functional reason.
- Implementing any component in code; flow-specific screen layouts (owned by DOS-M02-003 through DOS-M02-008); final content strings beyond the state/terminology rules needed to specify components.

## Functional requirements

- FR-1: Token specification covers semantic color, type scale, spacing, elevation/borders, iconography, motion, safe-area, focus, and breakpoint tokens; every status expression uses text/icon/shape in addition to color.
- FR-2: The component inventory specifies at minimum: app shell/header, bottom navigation where selected, vehicle tab/selector, search field, filter control/chips, virtualized result row, vehicle/status card, due-status meter, source/confidence badge, form fields, date/mileage/unit inputs, product selector, banners, inline validation, empty/error/offline panels, permission prompt, modal/sheet, toast, destructive confirmation, and progress/readiness indicators.
- FR-3: Every interactive component defines all applicable states: rest, hover where applicable, pressed, focus-visible, selected, disabled with reason, loading, invalid, success, stale, offline, and reduced-capability.
- FR-4: WCAG 2.2 AA is the rendered LiveView-content baseline; the spec defines native WebView semantics, labels, reading order, rotor/headings, contrast, reduced motion, and switch/keyboard operation for VoiceOver and TalkBack.
- FR-5: Touch targets are at least 44×44 pt on iOS and 48×48 dp on Android; layouts respect safe areas, are portrait-first, avoid the software keyboard, and survive text scaling/dynamic type and long localized strings.
- FR-6: Skeleton versus spinner use is defined per component class; indefinite loading indicators are prohibited for local queries.
- FR-7: Components consume semantic view models and typed states; they do not query storage or invoke Mob directly.
- FR-8: Every icon-only control has an accessible name; focus is restored after sheets/dialogs and moves to meaningful error summaries after failed submission.
- FR-9: Motion respects reduced-motion settings; dense vehicle data reflows rather than forcing horizontal page scrolling; vehicle tabs may scroll within their clearly labeled control.
- FR-10: Each design component maps to exactly one reusable implementation owner, reconciled against the §7 expected component list.

## Technical implementation contract

### Components and ownership boundaries

Components are presentation-layer LiveView components/function components rendered in the Mob WebView. They consume semantic view models and typed states supplied by LiveViews; they never query `CatalogRepo`/`UserRepo` or invoke Mob plugins directly (that path belongs to the `DeviceCommandBroker` boundary from §7/DOS-M01-002). The spec's ownership table maps every component to a single implementation owner, reusing §7 names (`AppShell`, `VehicleSummary`, `DueStatus`, `SourceBadge`, `ConfidenceBadge`, `CascadeSelect`, `ProductPicker`, `PermissionPrimer`, `OfflineState`) where they fit and explicitly registering any additions.

### Data and persistence

N/A — specification deliverable; components are stateless renderers of typed view models. The spec defines the shape of those view-model states (e.g., due-status meter takes a typed status of not-enough-data/upcoming/due/overdue plus confidence code), not storage. No component stores data.

### Interfaces and events

Each component spec declares its inputs (semantic view model, typed state enum), emitted user-intent events (e.g., pressed, selected, dismissed, confirm-destructive), and accessibility surface (role, name, state announcements). Result-count and state changes in search/filter components must be announced accessibly without excessive live-region noise (coordinated with DOS-M02-004). Permission-prompt component states mirror the proven DOS-M00-005 platform states.

### Failure and recovery behavior

Empty/error/offline panels and banners are first-class components with specified copy patterns and recovery actions. Loading states are bounded: local-query components must specify what happens if data does not arrive (error panel with retry), never an indefinite spinner. Disabled states always carry a reason. Stale and reduced-capability states are defined so screens degrade honestly rather than hiding functionality silently.

### Security and privacy

Component specs must not require rendering sensitive values where the platform could expose them (e.g., no VIN or notes in toasts or system-surface content); redaction guidance follows §7 shell security. No component embeds remote assets — all iconography/typography ships in the app, consistent with offline-from-first-launch (rule 2).

### Accessibility and performance

This issue owns the accessibility contract: WCAG 2.2 AA baseline for rendered content, VoiceOver/TalkBack semantics through the native WebView, contrast, reduced motion, switch/keyboard operation, focus management (restore after sheets/dialogs; move to error summaries after failed submission), 44×44 pt / 48×48 dp targets, dynamic type/200% text, long-string resilience, and safe-area behavior. Performance guidance: virtualized result rows for long lists, skeletons for structured local loads, spinners only for brief indeterminate operations, and no horizontal page scrolling for dense data.

## UX and content states

- Component-level state matrix: every component × every applicable interactive state (rest, hover where applicable, pressed, focus-visible, selected, disabled with reason, loading, invalid, success, stale, offline, reduced-capability), each with visual, textual, and assistive-technology treatment.
- Status semantics: due/overdue/upcoming/not-enough-data and provenance/confidence expressions are readable without color (text/icon/shape), consistent with §6 terminology ("Estimated due date", "Source unavailable", "Exact configuration not verified", "Meets the recorded requirements").
- Platform adaptations: iOS and Android examples for safe areas, dark mode if supported, compact-phone and large-phone breakpoints, and 200% text.
- Loading language: skeleton vs. spinner rules and the prohibition on indefinite loading for local queries.

## Test plan

### Automated

- Run automated contrast checks across the token palette and all component state examples; attach pass/fail output.
- Where the chosen design tooling supports it, run automated target-size lint against component specs (44×44 pt / 48×48 dp minimums).

### Manual/device matrix

- Manual VoiceOver (iOS) and TalkBack (Android) prototype reviews covering reading order, labels, rotor/headings, and state announcements on physical devices.
- Test longest expected labels, 200% text, reduced motion, and small-screen keyboard forms; record defects and revised specs.
- Review annotated component boards against the Storybook/equivalent plan and its accessibility state matrix with engineering and QA.
- Verify due/overdue and provenance/confidence comprehension without color (grayscale review).

## Rollout and rollback

The design-system spec is a committed, versioned planning artifact; acceptance freezes the component vocabulary and accessibility contract for downstream specs and implementation. Post-acceptance changes require change control (new issue/ADR); rollback is reversion to the prior accepted revision. No runtime rollout applies.

## Documentation and evidence

- Token specification and annotated component boards covering every component and state.
- Storybook/equivalent plan with an accessibility state matrix.
- Automated contrast-check output and manual VoiceOver/TalkBack review notes with recorded defects and revised specs.
- Long-label/200%-text/reduced-motion/keyboard test results.

## Dependency rationale

- DOS-M02-001 (hard blocker): components serve a fixed navigation model and route/state vocabulary; specifying a shell, tabs, or navigation components before the IA exists would force rework.
- DOS-M00-003 (hard blocker, platform constraints): WebView rendering/input/accessibility realities on physical devices bound what the spec may promise.
- DOS-M00-005 (hard blocker, platform constraints): the permission-prompt component must reflect proven notification-permission states, not imagined ones.
- Downstream: DOS-M02-003 through DOS-M02-008 consume this component vocabulary; all M05/M06 UI tickets implement against it.

## Risks, decisions, and open questions

- Risk: WebView accessibility bridges (VoiceOver/TalkBack over WebView content) behave differently than native controls. Mitigation: expectations are validated in manual device reviews; gaps become documented constraints or ADRs, not silent spec fiction.
- Risk: component sprawl — flow specs invent one-off variants. Mitigation: AC-5's single-owner mapping plus change control for additions.
- Risk: dark mode scope ambiguity. The catalog conditions it as "dark mode if supported"; the spec must record the explicit decision and its token consequences.
- Open question: which Storybook-equivalent tool hosts the component/state examples for LiveView components; the plan (not the tool implementation) is this issue's deliverable.
- Decision to record: bottom navigation adoption ("where selected") — the spec documents whether MVP uses bottom navigation, per the DOS-M02-001 IA.

## Definition of done

All FRs satisfied; all ACs checked with attached evidence (boards, matrices, automated contrast output, device review notes, owner mapping); the spec is committed and versioned; terminology matches §6 and DOS-M00-001; and downstream M02 specs can reference components by name without inventing states.
