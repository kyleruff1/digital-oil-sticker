> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Replace native platform components and OS accessibility APIs with a responsive web design system and a WCAG 2.2 AA contract verified against browser assistive technology._

## Outcome

A compact design-system specification defines semantic tokens, a reusable Phoenix LiveView component inventory, interaction and hydration states, and a WCAG 2.2 AA accessibility contract for the **hosted browser MVP** served from `digitaloilsticker.com` (ADR-0004, decisions §1–§2).

The deliverable is the single component and accessibility contract that every M02 flow spec references, every M05 UI ticket implements, and every M09 platform ticket surfaces its states through: semantic tokens; a complete component inventory covering the hydration lifecycle (INV-24.3), storage-loss surfaces (INV-25), connection-loss surfaces (INV-7), and impersonal catalog rendering (INV-11/INV-15); all applicable interactive states; and a WCAG 2.2 AA rendered-content contract verified against browser assistive technology on the §9 browser support matrix — not against the deferred client shell's WebView bridge or platform accessibility APIs, which are held for the post-MVP client re-entry (see "Superseded pre-pivot spec" below).

## Why this matters and what it unblocks

The 2026-08-01 pivot moved the client out of a signed platform container and onto a public URL. That change deletes several component categories that revision 1.0.0 of the design system depended on (platform-supplied chrome, OS permission prompts, safe-area primitives coupled to iOS/Android insets, `mob_notify` permission states) and creates several new ones that no prior card owns (a pre-hydration first paint that must never flash "no vehicles yet"; a storage-unavailable state that is not an error and is not an empty garage; a `data_missing` warning distinguishable from a fresh install; a connection-lost affordance for LiveView reconnect; and a persist-granted status the user is entitled to see honestly). Shared states will otherwise drift again — this time on a public host where the visible mistake is worse than a device-only prototype.

This issue unblocks all downstream UI implementation and accessibility QA on the browser MVP. It gives `DOS-M02-003` through `DOS-M02-008` a fixed component vocabulary in the pivoted world; it gives `DOS-M05-*` and `DOS-M06-*` implementers a component-to-owner mapping that keeps the domain contexts client-agnostic (ADR-0004 §6 enforcement); it gives `DOS-M07-002` the WCAG 2.2 AA release bar it now certifies (per its own rescoping row in [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification)); and it gives `DOS-M09-003` (hydration protocol) and `DOS-M09-004` (pre-hydration/storage-denied UX and copy) the presentation-layer contract their protocol and copy hang on.

## Included

- **Semantic tokens** for a responsive web design system: color (light and dark schemes if adopted at MVP; the decision is recorded here), type scale, spacing, elevation/borders, iconography, motion (with a `prefers-reduced-motion` variant), focus, and breakpoint tokens spanning the §9 browser support matrix (approx. 320 CSS px through desktop widths). Status expressions MUST carry text and icon or shape in addition to color, so `identity_only`/`schedule_supported`/`full_product_supported`/`not_applicable`/`unsupported` (INV-11) remain legible without color.
- **A responsive web component inventory** covering: `AppShell` (with the two-origin footer to Netlify legal/help pages per INV-27); primary navigation (URL-first, browser-back-friendly, per the M02-001 route map); a **hydration-lifecycle set** — `Skeleton`, `StorageUnavailable`, `DataMissing`, `Reconnecting` — realizing the ADR-0004 state machine and INV-24.3–24.8; a **storage-status surface** — `StoragePersistenceStatus` — reporting `persist_granted` truthfully (§"Quota and eviction"); a **connection surface** — `ConnectionState` (renamed from `OfflineState` because the browser MVP is not offline-capable and the old name would lie); `VehicleSummary`, `DueStatus`, `SourceBadge`, `ConfidenceBadge`, `CascadeSelect`, `ProductPicker`; result-list primitives (search field, filter chips, virtualized result row, vehicle/status card); form fields, date/mileage/unit inputs, banners, inline validation, empty/error panels, modal/sheet, toast, destructive confirmation, and a bounded `Progress` primitive.
- **All interactive states** for every component: rest, hover, pressed, focus-visible, selected, disabled with reason, loading, invalid, success, stale — plus the **hydration and connection states** the browser architecture introduces: `hydrating`, `storage_unavailable`, `data_missing`, `reconnecting`, `quota_warning`, `persist_denied`.
- **A WCAG 2.2 AA rendered-content contract** validated against browser assistive technology on the §9 support matrix: iOS Safari + VoiceOver, Android Chrome + TalkBack, desktop Chrome/Edge/Firefox with NVDA and JAWS on Windows, and macOS Safari + VoiceOver. Contrast ≥ 4.5:1 for text and ≥ 3:1 for UI components and graphical objects; usable at 200% zoom and at 320 CSS px reflow width; full keyboard operability with a visible focus indicator and no keyboard traps; live-region announcement of due-state and hydration changes without a live-region-noise regression.
- **Touch targets** ≥ 24×24 CSS px, ≥ 44×44 SHOULD where touch is primary, per §9. Layouts reflow instead of forcing horizontal page scroll; dense vehicle data stacks or truncates with an accessible expand affordance.
- **Skeleton versus spinner rules** for local versus server round trips, and an explicit prohibition on indefinite loading and on any empty-garage claim rendered before `local_state` resolves (INV-24.3).
- **Component-to-owner mapping** for the presentation-layer LiveView components, reconciled against ADR-0004 §"Enforcement" (no domain module may reference `Phoenix.LiveView`, `Plug`, or `LocalStore`).

Each new state has a specified visual, textual, and assistive-technology treatment. (This FR expands pre-pivot FR-3, which knew only `offline` and `reduced-capability`.)
- **FR-4 [REWRITE — retires pre-pivot FR-4]:** WCAG 2.2 AA is the rendered-content baseline for the hosted browser application. The accessibility contract is verified against **browser assistive technology combinations** drawn from the §9 support matrix — at minimum iOS Safari + VoiceOver, Android Chrome + TalkBack, macOS Safari + VoiceOver, desktop Chrome + NVDA, and desktop Firefox + NVDA — with desktop Edge and Windows JAWS covered where available. The contract specifies reading order, accessible names for icon-only controls, heading structure and landmark roles, contrast (≥ 4.5:1 text, ≥ 3:1 non-text), reduced-motion behavior, full keyboard operability with a visible focus indicator and no keyboard traps, and live-region policy for due-state and hydration changes. The pre-pivot phrase covering WebView-bridged accessibility semantics is retired — there is no embedded WebView in the MVP; the browser is the runtime, and the accessibility bridge is the browser's own accessibility tree served from Phoenix LiveView markup.
- **FR-5:** Touch targets are ≥ 24×24 CSS px, with ≥ 44×44 CSS px SHOULD where touch is the primary input (§9). Layouts remain usable at 200% zoom and reflow at 320 CSS px width with no loss of content or function. There is no horizontal page scroll for dense data; dense information stacks, truncates with an accessible expand affordance, or scrolls within a clearly labeled control.
- **FR-6:** Skeleton vs. spinner use is defined per component class. Skeletons are used for the pre-hydration first paint (INV-24.3) and for server round trips that have a known bounded shape (e.g., a paged catalog result). Spinners are permitted only for brief indeterminate operations. Indefinite loading is prohibited: a bounded deadline (the hydration deadline for `Skeleton`, a server-response deadline for catalog reads) is required, after which the component MUST transition to a specified error or storage-state surface. The pre-hydration `Skeleton` MUST NOT reveal an empty-garage claim under any condition (INV-24.3, ADR-0004 §"First-paint and empty-state rules").
- **FR-7:** Components consume typed view models supplied by LiveView `socket.assigns` and typed state enums. - **FR-8:** Every icon-only control has an accessible name; focus is restored after modals/sheets/dialogs; focus moves to a meaningful error summary after a failed submission; the visible focus indicator meets §9.
- **FR-9:** Motion respects `prefers-reduced-motion`. Announcements for search result counts, filter changes, due-state changes, and hydration state changes use polite live regions with an explicit deduplication rule so screen readers are not spammed on every `patch`.
- **FR-10 [NEW]:** The design system includes explicit **storage-loss and connection-loss surfaces** as first-class components — `StoragePersistenceStatus` (renders `persist_granted` truthfully — granted, denied, unavailable — never described as a backup, per INV-5/INV-25), `StorageUnavailable` (private-browsing or blocked storage; distinct from `:empty`), `DataMissing` (`dos_boot_state == "has_data"` but hydration returned zero — the ADR-0004 explicit warning; never rendered as a fresh install), `QuotaWarning` (usage over 80% of estimate; offers export/pruning), and `ConnectionState` (WSS reconnecting after a network blip or a deploy — communicates reconnection honestly rather than freezing a stale UI). Copy strings for these states are owned by `DOS-M09-004` and must satisfy INV-21 ("Stored in this browser"; prohibited words include "saved to your account", "synced", "backed up", "restore", and "we'll remember"). This FR retires the pre-pivot `PermissionPrimer` `mob_notify` states, which have no MVP consumer.
- **FR-11 [NEW]:** The design system is responsive across the §9 browser support matrix (evergreen Chrome, Edge, Firefox, Safari desktop; iOS Safari 16+; Android Chrome). It MUST NOT bake in platform-specific assumptions such as iOS/Android safe-area primitives coupled to hardware insets, vendor-specific control chrome, or fixed portrait-only layouts. `env(safe-area-inset-*)` MAY be consulted where a browser exposes it, but no layout is allowed to break in a browser that does not.
- **FR-12:** Each design component maps to exactly one reusable LiveView implementation owner. The mapping preserves the ADR-0004 §6 boundary: no component's owner module is permitted to reference `Phoenix.LiveView` from a domain namespace, nor to invoke the `LocalStore` hook outside the specified hydration/mutation protocol. Additions require a change-control record (a follow-on issue or ADR).

## Technical implementation contract

### Components and ownership boundaries

Components are Phoenix LiveView / function components rendered directly in the browser DOM served from `digitaloilsticker.com` on Fly.io — **not** inside the deferred client's embedded WebView. They consume typed view models and typed state enums placed in `socket.assigns` by LiveViews, and never open IndexedDB, invoke the `LocalStore` hook, or fetch catalog data directly (ADR-0004 §"Enforcement"). The spec's ownership table maps every component to a single implementation owner, keeps the surviving §7 names where their behavior survives the pivot (`AppShell`, `VehicleSummary`, `DueStatus`, `SourceBadge`, `ConfidenceBadge`, `CascadeSelect`, `ProductPicker`), renames `OfflineState` to `ConnectionState` (browser MVP is not offline-capable), replaces the pre-pivot `PermissionPrimer` with `StoragePersistenceStatus`, and registers the four new hydration-lifecycle components (`Skeleton`, `StorageUnavailable`, `DataMissing`, `Reconnecting`) plus `QuotaWarning`. Additions require change control.

### Data and persistence

N/A — specification deliverable; components are stateless renderers of typed view models. This card does not open, migrate, or write to `dos_local` IndexedDB, and does not invoke Phoenix `push_event`/`handle_event` (those live in the LiveView layer and are specified by `DOS-M09-002`/`DOS-M09-003`). The spec defines the *shape* of the view-model states the components render (e.g., `DueStatus` takes a typed `{status, confidence, source_id}` triple where `status` is one of `not_enough_data | upcoming | due | overdue`; `Skeleton` takes a `region_kind` enum so pre-hydration paint matches the eventual layout).

### Interfaces and events

Each component spec declares its inputs (typed view model, typed state enum), emitted user-intent events (e.g., `pressed`, `selected`, `dismissed`, `confirm_destructive`, `export_requested`, `import_requested`), and accessibility surface (role, name, state announcements). Result-count and state changes in search/filter components are announced through polite live regions with a deduplication rule (coordinated with `DOS-M02-004`). No user-intent event carries a personal identifier that could reach a catalog request (INV-26); the LiveView receiving the event is responsible for mapping intent to an impersonal selector before calling `DigitalOilSticker.Catalog`.

### Failure and recovery behavior

The hydration-lifecycle surfaces (`Skeleton`, `StorageUnavailable`, `DataMissing`, `Reconnecting`) are first-class components with specified visual, textual, and assistive-technology treatment. `Skeleton` is bounded by the hydration deadline (default 5 000 ms per ADR-0004 §"Mount and hydration sequence"); expiry transitions to `StorageUnavailable` with an offered export path. `DataMissing` is rendered when `dos_boot_state == "has_data"` and hydration returned zero records — it is **not** an empty state, and its copy contract (owned by `DOS-M09-004`) tells the user their browser storage appears to have been cleared and offers import. `QuotaWarning` surfaces when `navigator.storage.estimate()` reports > 80% usage. `ConnectionState` uses `phx-disconnected` styling to communicate reconnection honestly rather than tearing the shell to a skeleton. Every failed mutation renders a persistent, non-dismissible "Not saved to this browser" affordance on the affected record (ADR-0004 §"Mutation round trip") — no silent retries, no invisible rollback.

### Security and privacy

The design system carries INV-22 at the presentation layer: no component references a remote asset, a CDN font, or a third-party script. Icons and typography ship first-party from the application origin. No component embeds an `iframe`, an analytics beacon, a session recorder, or a third-party error reporter (INV-4). No component surface may render a VIN, an odometer value, a note, or any personal field into a toast, a `document.title`, a URL fragment, a live-region announcement scraped by an assistive-tech transcript service, or any other place where the browser or an operator could observe it beyond the intended surface (ADR-0004 §"Logging" and §"LiveDashboard and operator access"). The `StoragePersistenceStatus` component reports `persist_granted` truthfully and MUST NOT describe a grant as a backup (INV-5, INV-25).

### Accessibility and performance

This issue owns the accessibility contract for the browser MVP: WCAG 2.2 AA rendered-content baseline; the browser assistive-technology matrix listed in FR-4; contrast ≥ 4.5:1 text and ≥ 3:1 non-text; full keyboard operability with a visible focus indicator and no keyboard traps; reduced-motion behavior; focus management (restore after modals/sheets/dialogs; move to error summaries after failed submission); ≥ 24×24 CSS px touch targets (≥ 44×44 SHOULD where touch is primary); usable at 200% zoom and at 320 CSS px reflow width; live-region policy for due-state and hydration announcements; and honest-degradation surfaces for the hydration lifecycle. Performance guidance: virtualized result rows for long catalog lists; skeletons for pre-hydration paint and known-shape server responses; spinners only for brief indeterminate operations; no horizontal page scroll; a first-visit payload budget compatible with §9 (initial HTML + CSS + JS ≤ 250 KiB compressed, total first-visit transfer ≤ 500 KiB) — the design system's own asset weight (fonts, icons, component CSS) MUST fit inside that ceiling.

## UX and content states

- Component-level state matrix: every component × every applicable interactive state (rest, hover, pressed, focus-visible, selected, disabled with reason, loading, invalid, success, stale, plus the browser-runtime states `hydrating`, `storage_unavailable`, `data_missing`, `reconnecting`, `quota_warning`, `persist_denied`) with visual, textual, and assistive-technology treatment specified.
- Status semantics: due/overdue/upcoming/not-enough-data and provenance/confidence expressions readable without color (text/icon/shape), consistent with INV-11 and INV-21 ("Estimated due date" with a confidence label, "Source unavailable", "Exact configuration not verified", "Meets the recorded requirements"). Prohibited phrases in every component's copy contract: "saved to your account", "synced", "backed up", "restore", "we'll remember", "your account".
- Browser adaptations: light and dark schemes if adopted at MVP (the decision is recorded here); compact-mobile, large-mobile, tablet, and desktop breakpoints; 200% zoom and 320 CSS px reflow examples across the §9 support matrix.
- Hydration and storage narrative: `Skeleton` never claims data absence; `StorageUnavailable` distinguishes private-browsing / blocked-storage from an empty garage; `DataMissing` distinguishes a cleared browser from a first visit; `QuotaWarning` is offered before a write fails; `Reconnecting` says "reconnecting" rather than freezing a stale UI. Copy strings are owned by `DOS-M09-004`; component shape and state are owned here.

### Manual/browser-assistive-technology matrix

- Manual screen-reader prototype reviews across the FR-4 browser AT matrix: iOS Safari + VoiceOver, Android Chrome + TalkBack, macOS Safari + VoiceOver, desktop Chrome + NVDA, desktop Firefox + NVDA (Edge + JAWS where available). Cover reading order, accessible names for icon-only controls, heading/landmark structure, live-region announcements for due-state and hydration changes, and keyboard-only operation with a visible focus indicator.
- Test longest expected labels, 200% zoom, 320 CSS px reflow, `prefers-reduced-motion: reduce`, and small-screen keyboard forms; record defects and revised specs.
- Grayscale review to verify due/overdue and provenance/confidence comprehension without color.
- **Hydration-lifecycle review**: exercise every hydration/storage/connection state (`hydrating`, `storage_unavailable`, `data_missing`, `reconnecting`, `quota_warning`, `persist_denied`) through prototype scripts — private-browsing mode, storage-cleared mid-session, quota-exceeded write, deploy-triggered socket drop — and verify each state is distinguishable, non-misleading, and reachable by keyboard and screen reader.
- **Two-tab review**: two tabs open to the same route; a mutation in one is reflected in the other within the multi-tab consistency window (§9 target row for multi-tab consistency); no stale-tab overwrite is silent.

## Rollout and rollback

The design-system spec is a committed, versioned planning artifact; acceptance freezes the component vocabulary, the hydration-lifecycle state names, and the WCAG 2.2 AA browser accessibility contract for downstream specs and implementation. Post-acceptance changes require change control (new issue or ADR); rollback is reversion to the prior accepted revision. There is no runtime rollout for this issue — the runtime rollout of the design system's implementations is owned by `DOS-M05-*` and `DOS-M09-006` (the Fly.io deploy pipeline).

## Dependency rationale

- **Constitution 2.0.0 (environmental fact, ratified 2026-08-01):** the invariants that bind an MVP browser design system live here in ratified form (INV-1, INV-3/INV-4/INV-5, INV-11, INV-15, INV-17 amended, INV-21, INV-22, INV-23, INV-24.3–24.8, INV-25, INV-26, INV-27, §9). Without a ratified constitution 2.0.0 the component contract has no bright line to enforce; it is now the environment this card runs in, not a card gate.
- **`DOS-M00-002` (hard blocker):** the browser-MVP architecture (Fly.io + hydration protocol + client-only personal data) is the architecture this design system exists to serve.
- **`DOS-M02-001` (hard blocker):** components serve a fixed route/state vocabulary; specifying `AppShell`, primary navigation, or per-route landing regions before the IA exists would force rework.
- **`DOS-M09-003` (hard blocker at the state-contract level, not the implementation level):** the typed hydration states this card's components render are defined by the hydration protocol. Formal completion of `DOS-M09-003` is not required to specify the components, but the state names and typed error kinds must be agreed before AC-1 can be checked.
- **`DOS-M09-004` (hard blocker at the copy-contract level):** the plain-language copy strings that populate `StorageUnavailable`, `DataMissing`, `QuotaWarning`, `StoragePersistenceStatus`, and `ConnectionState` are owned by `DOS-M09-004`; this card owns their component shape and state.
- **`DOS-M09-002` (soft blocker):** the browser storage adapter's typed error kinds (`quota_exceeded`, `storage_unavailable`, `private_browsing`) feed the state variants rendered by `StorageUnavailable` and `QuotaWarning`.
- **Retired blockers:** `DOS-M00-003` (physical-device Mob proof) and `DOS-M00-005` (`mob_notify` behavior). Per ADR-0004, DOS-M00-003 is suspended (no Mac/Xcode; Windows-host Android defects; no upstream Windows CI) and DOS-M00-005 is DEFER (no browser equivalent to `mob_notify`). Neither can gate this card without keeping it artificially Blocked.
- **Downstream:** `DOS-M02-003` through `DOS-M02-008` consume this component vocabulary; `DOS-M05-*` and `DOS-M06-*` implementation tickets implement against it; `DOS-M07-002` certifies the WCAG 2.2 AA browser-AT release bar defined here; `DOS-M09-004` uses the component shapes defined here to hang its copy contract on.

## Risks, decisions, and open questions

- **Risk:** browser assistive-technology combinations behave differently across engines (VoiceOver on iOS Safari vs. macOS Safari; TalkBack on Chrome vs. Samsung Internet — Samsung Internet is not in §9 today but is common on Android); NVDA vs. JAWS live-region behavior differs on Windows. **Mitigation:** expectations are validated in the FR-4 manual reviews across the §9 matrix; gaps become documented constraints or ADRs, not silent spec fiction (mirrors the pre-pivot risk framing for WebView bridges; the risk has shifted vendor, not vanished).
- **Risk:** live-region noise on LiveView `patch` operations — a naive polite live region on every filter change will spam a screen reader. **Mitigation:** FR-9's explicit deduplication rule; verified in the manual AT review.
- **Risk:** component sprawl — flow specs invent one-off variants. **Mitigation:** AC-7's single-owner mapping plus change control for additions.
- **Risk:** dark-mode scope ambiguity carried over from the pre-pivot spec. **Decision to record here:** dark-mode adoption for the browser MVP is either "adopted at MVP with token consequences recorded" or "explicitly deferred to a post-MVP revision"; the choice is made and recorded during this issue's review, not left to implementation.
- **Risk:** the design system implies durability. Even a well-designed `AppShell` on a `.com` URL reads to users as "my data is on their server", and INV-5/INV-25 bind harder because of that (ADR-0004 §"Consequences — Lost — honestly"). **Mitigation:** the copy contract (owned by `DOS-M09-004`) is reviewed against the INV-25 prohibited-words list before AC-4 can be checked, and the `StoragePersistenceStatus` component is required to render `persist_granted` truthfully.
- **Open question:** which component/state-catalog tool hosts the LiveView component examples for review (Storybook, `Phoenix.LiveView.Playground`, an internal `/design` route in the application itself). The plan (not the tool implementation) is this issue's deliverable.
- **Decision to record:** whether the primary navigation adopts a bottom-nav pattern on mobile breakpoints — the pre-pivot "bottom navigation where selected" language is retained as a question but recorded as decided in this issue against the M02-001 IA.
- **Decision to record:** the removal of `PermissionPrimer` from the MVP component set and its replacement by `StoragePersistenceStatus` — recorded here with a pointer to INV-17 amended and to ADR-0004 §"Consequences — Lost — honestly" ("no OS local notifications").

## Superseded pre-pivot spec (historical record)

> This section preserves the card as chartered before the 2026-08-01 pivot to browser-first, and is retained for historical readability of the ADR record. The Outcome above is authoritative.

### Outcome (pre-pivot)

A compact design-system specification defines tokens, reusable LiveView components, native-WebView behavior, interaction states, and accessibility rules for the production iOS and Android applications.

The deliverable is the single component and accessibility contract that every M02 flow spec references and every M05/M06 UI ticket implements: semantic tokens, a complete component inventory with all interactive states, WCAG 2.2 AA rendered-content rules, and VoiceOver/TalkBack expectations for LiveView content inside the native WebView.

### Why this matters and what it unblocks (pre-pivot)

Shared states—vehicle selection, provenance badges, status, forms, tabs, permissions, and errors—will drift without a common contract. This issue unblocks all UI implementation and visual/interaction QA.

It also gives DOS-M02-003 through DOS-M02-008 a fixed component vocabulary, gives engineering the component-to-owner mapping needed to avoid duplicate implementations, and gives QA the accessibility state matrix used in prototype reviews and later device testing.

### Included (pre-pivot)

- Define semantic color, type scale, spacing, elevation/borders, iconography, motion, safe-area, focus, and breakpoint tokens. Status must use text/icon/shape in addition to color.
- Specify components: app shell/header, bottom navigation where selected, vehicle tab/selector, search field, filter control/chips, virtualized result row, vehicle/status card, due-status meter, source/confidence badge, form fields, date/mileage/unit inputs, product selector, banners, inline validation, empty/error/offline panels, permission prompt, modal/sheet, toast, destructive confirmation, and progress/readiness indicators.
- Include all interactive states: rest, hover where applicable, pressed, focus-visible, selected, disabled with reason, loading, invalid, success, stale, offline, and reduced-capability.
- Use WCAG 2.2 AA as the rendered LiveView-content baseline and define native WebView semantics, labels, reading order, rotor/headings, contrast, reduced motion, and switch/keyboard operation for VoiceOver and TalkBack.
- Support at least 44×44 pt iOS and 48×48 dp Android touch targets, safe areas, portrait-first layouts, software keyboard avoidance, text scaling/dynamic type, and long localized strings.
- Define skeleton versus spinner use and prohibit indefinite loading for local queries.
- Map each design component to a single reusable implementation owner (the §7 component/LiveView inventory or an explicitly proposed addition).

### Excluded (pre-pivot)

- Netlify marketing/support-site design, browser/PWA production design, custom illustration system, animation for decoration, final store screenshots, or platform-specific divergence without a functional reason.
- Implementing any component in code; flow-specific screen layouts (owned by DOS-M02-003 through DOS-M02-008); final content strings beyond the state/terminology rules needed to specify components.

### Preconditions (pre-pivot)

- DOS-M02-001 accepted: the navigation model, route inventory, and per-route state vocabulary exist, so shell/navigation/tab components serve a fixed information architecture.
- DOS-M00-003 accepted: physical-device proof of Mob 0.7.20 establishes real WebView constraints (rendering, input, safe areas, accessibility bridge behavior) the spec must honor.
- DOS-M00-005 accepted: proven `mob_notify` permission flows constrain the permission-prompt component's states.

### Functional requirements (pre-pivot)

- FR-1: Token specification covers semantic color, type scale, spacing, elevation/borders, iconography, motion, safe-area, focus, and breakpoint tokens; every status expression uses text/icon/shape in addition to color.
- FR-2: The component inventory specifies at minimum: app shell/header, bottom navigation where selected, vehicle tab/selector, search field, filter control/chips, virtualized result row, vehicle/status card, due-status meter, source/confidence badge, form fields, date/mileage/unit inputs, product selector, banners, inline validation, empty/error/offline panels, permission prompt, modal/sheet, toast, destructive confirmation, and progress/readiness indicators.
- FR-3: Every interactive component defines all applicable states: rest, hover where applicable, pressed, focus-visible, selected, disabled with reason, loading, invalid, success, stale, offline, and reduced-capability.
- FR-4: WCAG 2.2 AA is the rendered LiveView-content baseline; the spec defines native WebView semantics, labels, reading order, rotor/headings, contrast, reduced motion, and switch/keyboard operation for VoiceOver and TalkBack.
- FR-5: Touch targets are at least 44×44 pt on iOS and 48×48 dp on Android; layouts respect safe areas, are portrait-first, avoid the software keyboard, and survive text scaling/dynamic type and long localized strings.
- FR-6: Skeleton versus spinner use is defined per component class; indefinite loading indicators are prohibited for local queries.
- FR-7: Components consume semantic view models and typed states; they do not query storage or invoke Mob directly.
- FR-8: Every icon-only control has an accessible name; focus is restored after sheets/dialogs and moves to meaningful error summaries after failed submission.
- FR-9: Motion respects reduced-motion settings; dense vehicle data reflows rather than forcing horizontal page scrolling; vehicle tabs may scroll within their clearly labeled control.
- FR-10: Each design component maps to exactly one reusable implementation owner, reconciled against the §7 expected component list.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

Components are presentation-layer LiveView components/function components rendered in the Mob WebView. They consume semantic view models and typed states supplied by LiveViews; they never query `CatalogRepo`/`UserRepo` or invoke Mob plugins directly (that path belongs to the `DeviceCommandBroker` boundary from §7/DOS-M01-002). The spec's ownership table maps every component to a single implementation owner, reusing §7 names (`AppShell`, `VehicleSummary`, `DueStatus`, `SourceBadge`, `ConfidenceBadge`, `CascadeSelect`, `ProductPicker`, `PermissionPrimer`, `OfflineState`) where they fit and explicitly registering any additions.

#### Data and persistence

N/A — specification deliverable; components are stateless renderers of typed view models. The spec defines the shape of those view-model states (e.g., due-status meter takes a typed status of not-enough-data/upcoming/due/overdue plus confidence code), not storage. No component stores data.

#### Interfaces and events

Each component spec declares its inputs (semantic view model, typed state enum), emitted user-intent events (e.g., pressed, selected, dismissed, confirm-destructive), and accessibility surface (role, name, state announcements). Result-count and state changes in search/filter components must be announced accessibly without excessive live-region noise (coordinated with DOS-M02-004). Permission-prompt component states mirror the proven DOS-M00-005 platform states.

#### Failure and recovery behavior

Empty/error/offline panels and banners are first-class components with specified copy patterns and recovery actions. Loading states are bounded: local-query components must specify what happens if data does not arrive (error panel with retry), never an indefinite spinner. Disabled states always carry a reason. Stale and reduced-capability states are defined so screens degrade honestly rather than hiding functionality silently.

#### Security and privacy

Component specs must not require rendering sensitive values where the platform could expose them (e.g., no VIN or notes in toasts or system-surface content); redaction guidance follows §7 shell security. No component embeds remote assets — all iconography/typography ships in the app, consistent with offline-from-first-launch (rule 2).

#### Accessibility and performance

This issue owns the accessibility contract: WCAG 2.2 AA baseline for rendered content, VoiceOver/TalkBack semantics through the native WebView, contrast, reduced motion, switch/keyboard operation, focus management (restore after sheets/dialogs; move to error summaries after failed submission), 44×44 pt / 48×48 dp targets, dynamic type/200% text, long-string resilience, and safe-area behavior. Performance guidance: virtualized result rows for long lists, skeletons for structured local loads, spinners only for brief indeterminate operations, and no horizontal page scrolling for dense data.
