> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _First run now means hydration-from-empty rather than bundled-catalog verification, and the privacy copy must say "this browser on this device," explicitly warn that clearing site data destroys the record, and cover private-browsing and storage-blocked cases._

## Outcome

The first-visit experience of the hosted browser application says the truth about where the user's data lives, gets a returning visitor from URL to their garage without a flash of "you have no vehicles yet," and never resembles an online account. The deliverable is a written, reviewed content-and-flow specification covering: the pre-hydration first paint, the empty-vs-returning-vs-cleared distinction, the optional-only personalization step, the unit/time-zone capture that persists into `prefs`, the storage-condition states (`:hydrating`, `:empty`, `:loaded`, `:data_missing`, `:storage_unavailable`) that first run must render distinctly per [ADR-0004 §"First-paint and empty-state rules"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md), private-browsing and blocked-storage fallbacks, plain-language privacy copy for a public URL, and the Settings surface that shows storage status, catalog `data_version`, source attribution, export/import as the sole recovery path, and destructive controls that operate only on IndexedDB and `localStorage`.

## Why this matters

The hosted URL reads to a first-time visitor like a service that holds their record on a server. The product's core promise is the opposite: personal data lives in this browser on this device and nowhere else (INV-3, INV-4, INV-23). If first-visit copy, empty-state framing, or Settings language ever implies otherwise, the product breaks its own privacy claim before a vehicle is even saved, and INV-5's "no implied backup" rule fails on the first paint. Every downstream surface — MVP dashboard (DOS-M05-005), export/import (DOS-M05-007, DOS-M04-009), harden-and-release copy audits (DOS-M07-001, DOS-M07-006), and the Netlify privacy page under DOS-M09-007's domain plan — inherits the language this spec fixes.

This card also freezes the state-machine the LiveView shell must present. The hydration protocol (DOS-M09-002) exposes typed storage conditions; the empty-state UX contract (DOS-M09-003) defines their visual rules; this card writes the words, the flow, and the acceptance evidence for onboarding and Settings specifically, so the implementation milestones do not have to invent copy.

## Included

- First-visit flow for a browser with no `dos_local` data: welcome/explanation → optional personalization (skippable) → unit and time-zone confirmation → arrive at "add first vehicle" (the search UX itself is DOS-M02-004).
- Determinate pre-hydration first paint per INV-24.3: while `local_state == :hydrating` the shell renders a skeleton, never an onboarding-from-zero flow. Onboarding is entered only after the hydration deadline resolves to `:empty` **and** `dos_boot_state != "has_data"`.
- Returning-visitor flow: instant-loaded state with `phx-disconnected` reconnect styling; explicit `:data_missing` warning (INV-24.4) when `dos_boot_state == "has_data"` but hydration returns zero records, offering import and stating plainly that the browser cleared site data.
- Storage-condition states — the words, headings, primary actions, and prohibited phrasings for each of `:hydrating`, `:empty`, `:loaded`, `:data_missing`, and `:storage_unavailable` (the last spans private-browsing, blocked storage, and `QuotaExceededError` per ADR-0004 §"Private browsing and blocked storage" and INV-24.5/24.6).
- Plain-language privacy content that says: information stays in **this browser on this device**; there is no sign-in and no server copy; clearing site data, private-browsing sessions, browser eviction, using a different browser or profile, or losing the device will destroy the record; connectivity is required to reach the app and to search the catalog; there is no offline mode.
- Optional-only personalization (display name, avatar/color) — skippable and never re-prompted; unit system (miles/kilometers) and IANA time zone captured or confirmed and written to the IndexedDB `prefs` singleton through `local_store:put`.
- Settings surface content: storage status (`persist_granted` value from `meta`, usage/quota estimate, `schema_version`), catalog `data_version` and source attribution, export (produces the versioned JSON envelope from DOS-M09-001), import (replace or merge with counts preview), erase-all-local-data destructive control, and stable links to the Netlify privacy and attribution pages.
- Multi-tab acknowledgment surface: when `local_store:conflict` triggers a re-hydration ([ADR-0004 §"Multi-tab consistency"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md)), the "reloaded from this browser's newer data" notice is written here.

## Excluded

- Authentication, cloud sync, social onboarding, mandatory personalization, Web Push permission, or any claim of backup/recovery beyond export/import.
- Implementing the hydration protocol, the storage adapter, or the empty-state UX primitives themselves — those are DOS-M09-002, DOS-M09-001, and DOS-M09-003 respectively. This card writes onboarding and Settings copy on top of them.
- The Netlify privacy and attribution page authoring (DOS-M09-007 owns the site; the copy this spec produces is the source of truth the Netlify page must match).
- Vehicle search/selection UX (DOS-M02-004).
- Any "catalog repair" or bundled-catalog-verification affordance — no such artifact exists in the deployed application (ADR-0004 §Decision.2; INV-6 amended). Catalog `data_version` is a deploy-time property surfaced read-only in Settings.
- A PWA install prompt, service-worker install copy, or "add to home screen" nudge — that decision is DOS-M09-010; this card treats the browser as a plain browser.

## Functional requirements

- **FR-1** (replaces the pre-pivot FR-1 that described bundled-catalog verification): First visit is specified as a *hydration-from-empty* flow, not a provisioning flow. The shell enters onboarding only after `local_state` resolves to `:empty` **and** the `localStorage` boot hint `dos_boot_state != "has_data"` (ADR-0004 §"Storage layout" and §"First-paint and empty-state rules"). No copy anywhere in the flow refers to verifying, unpacking, copying, downloading, or repairing a bundled catalog — no such artifact exists in the deployed application. Addresses staleness finding #1.
- **FR-2**: Plain-language privacy content states, and only states, facts that hold under ADR-0004: information stays in this browser on this device; there is no sign-in and no server copy of a personal record; clearing site data, private-browsing sessions, browser eviction, a different browser or profile, or losing the device will destroy the record; connectivity is required to reach the app and to search the catalog. Prohibited words (per ADR-0004 §"Export and import" and INV-5/INV-25): "backup", "backed up", "synced", "safe", "we'll remember", "your account", "cloud", "restore" used in a way that implies remote durability, "encrypted" without a scoped and true referent.
- **FR-3**: Local display name and avatar/color are optional and skippable; the flow never asks for email, phone, password, date of birth, contacts, advertising consent, cross-app tracking, or any stable identifier. Skipping personalization never re-prompts.
- **FR-4**: After the unit/time-zone step, the flow routes directly to "add first vehicle" (the search UX itself is DOS-M02-004). Web Push and any browser-notification permission prompt are prohibited at first visit (INV-17 amended: in-app due state only; Web Push deferred per DOS-M09-010).
- **FR-5**: Returning-visitor states are specified against the hydration protocol, not against boot phases: instant `:loaded` on hydrate; `phx-disconnected` reconnect styling and behavior (ADR-0004 §"First-paint and empty-state rules"); explicit `:data_missing` warning with import offered when `dos_boot_state == "has_data"` but hydration returns zero records (INV-24.4); explicit `:storage_unavailable` state for private-browsing, blocked storage, and `QuotaExceededError` (INV-24.5/24.6, ADR-0004 §"Private browsing and blocked storage"); a stale-deployment "this browser holds data from a newer version" read-only banner (ADR-0004 §"Schema versioning and migration"); a multi-tab "reloaded from this browser's newer data" notice (ADR-0004 §"Multi-tab consistency"). No returning-visitor state references an embedded-BEAM startup sequence, catalog schema migrations run in the browser, unsupported-OS terminal states, or loopback endpoints — none of those artifacts exist in the deployed application.
- **FR-6**: Settings content is specified to read from real stores and real deploy-time values only: storage status from `meta` (`persist_granted`, `schema_version`, `seq`, `last_write_at`) and `navigator.storage.estimate()`; catalog `data_version` and source attribution from the read-only `CatalogRepo` (ADR-0004 §Decision.4); export producing the DOS-M09-001 envelope; import as replace-or-merge with a counts preview (ADR-0004 §"Export and import"); erase-all-local-data as a destructive control specified in FR-9. Prohibited: any Settings row that reads or writes a server-side personal store, requires an account, or implies remote sync.
- **FR-7** (replaces the pre-pivot FR-7 that specified a `UserRepo` transaction): Profile-adjacent creation writes are IndexedDB writes, not `UserRepo` transactions. Display name (if provided), unit system, and IANA time zone are persisted to the `dos_local` `prefs` singleton (and, where profile identity is required, a client-generated UUIDv4 record in the appropriate `dos_local` store) through the `local_store:put` protocol defined in [ADR-0004 §"Mutation round trip"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md). The write is not shown as saved to the user until the hook returns `local_store:ack`. There is no server-side row and no `UserRepo` in the deployment (ADR-0004 §Decision.4 — the sole Ecto repo is `DigitalOilSticker.CatalogRepo`, opened read-only). Addresses staleness finding #2.
- **FR-8** (retired and replaced): The pre-pivot FR-8 ("bundled-catalog verification/copy retry is idempotent and user records are never deleted by 'repair catalog'") is retired — there is no bundled catalog, no verify/copy step, and no in-app "repair catalog" affordance in the deployed application (ADR-0004 §"Consequences", "No bundled offline catalog"). The surviving concern — that no first-visit path may destroy a returning visitor's IndexedDB data — is enforced by INV-24.3 (no false empty-state flash), INV-24.4 (`:data_missing` warning instead of silent empty state), and the DOS-M09-003 empty-state contract this card conforms to. This spec explicitly states that no onboarding action writes to `vehicles`, `events`, `readings`, or `reminders`.
- **FR-9** (rewritten): The "erase all local user data" control is specified to operate only on the browser's `dos_local` IndexedDB stores (`meta`, `vehicles`, `events`, `readings`, `reminders`, `prefs`) and the `dos_boot_state` `localStorage` key. It requires an explicit destructive confirmation whose text names exactly those stores/keys, warns that export is the only recovery path (INV-5, INV-25), states that the action affects only this browser on this device (it does not sign the user out of anything, because there is nothing to be signed out of), and clarifies that the deployed catalog is untouched because it is a read-only server artifact.
- **FR-10**: Privacy copy is honest about the hosted transport boundary. It says HTTPS/WSS in operator-oriented Settings/attribution surfaces (INV-22) but does not use the word "encrypted" to describe storage. It says the server holds no personal record and this is verified by a release-gating test (per ADR-0004 §"Enforcement" and DOS-M09-008). It acknowledges operator access ([ADR-0004 §"LiveDashboard and operator access — stated honestly"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md)) at the accuracy required: "we store no personal data on the server," not overclaimed.
- **FR-11**: Unit system (miles/kilometers) and IANA time zone are captured or confirmed during first visit and written to the `prefs` singleton in `dos_local` via `local_store:put`. Return visits do not re-prompt unless the user changes them in Settings.
- **FR-12** (new): Onboarding covers browsers that refuse storage. When the hook reports `:storage_unavailable`, first visit renders the DOS-M09-003 session-only banner in this card's words: "Nothing you enter here will be saved. Closing this tab loses everything. You can still browse vehicle data. To save a garage, use a normal browser window and allow site data." Export is offered from the same surface (ADR-0004 §"Private browsing and blocked storage" ladder step 2). No silent fallback to `localStorage` for records; no silent fallback to server storage; both are prohibited by ADR-0004.
- **FR-13** (new): First-visit and Settings copy explicitly acknowledge browser eviction as a realistic loss scenario, per ADR-0004 R1 (the single biggest product risk of the pivot). The copy names the concrete conditions — "if you clear site data, use private browsing, don't visit for a long time, switch browsers or profiles, or lose this device, your garage is gone" — and offers export as the answer.

## Technical implementation contract

### Components and ownership boundaries

The spec targets two LiveViews built on the DOS-M02-002 web design system: `OnboardingLive` (first-visit welcome, optional personalization, unit/time-zone capture, hand-off to "add first vehicle") and `SettingsLive` (storage status, catalog attribution, export/import, erase). Both mount over the DOS-M09-002 hydration protocol; both consume the DOS-M09-003 storage-condition state contract; neither reads or writes a server-side personal store. The `LocalStore` `phx-hook` (DOS-M09-002) is the only bridge to `dos_local`; this card never proposes bypassing it.

### Data and persistence

There is no `UserRepo` in the deployment and no `local_profiles` table anywhere in the system — the sole Ecto repo is `DigitalOilSticker.CatalogRepo`, opened read-only ([ADR-0004 §Decision.4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md)). Personal-record persistence for anything this card touches is IndexedDB in `dos_local`, per the storage layout in [ADR-0004 §"Storage layout"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md): the `prefs` singleton holds unit system, time zone, and display preferences; `meta` holds `schema_version`, `seq`, `created_at`, `last_write_at`, and `persist_granted`; identity, if needed, is a client-generated UUIDv4 in the appropriate store. Every write from onboarding or Settings is a `local_store:put` round trip whose UI does not display "saved" until the hook returns `local_store:ack` (ADR-0004 §"Mutation round trip"). Catalog attribution and `data_version` are read from `CatalogRepo` — a build-time, read-only artifact baked into the Fly image (ADR-0004 §"Catalog database on Fly"). Addresses staleness finding #2.

### Interfaces and events

The onboarding and Settings surfaces consume typed `local_state` values (`:hydrating`, `:empty`, `:loaded`, `:data_missing`, `:storage_unavailable`) and the hydration-deadline behavior specified in ADR-0004 §"Mount and hydration sequence" and §"First-paint and empty-state rules". Writes emit `local_store:put`; acknowledgments arrive as `local_store:ack`; multi-tab divergence surfaces as `local_store:conflict` and re-hydrates with a visible notice per ADR-0004 §"Multi-tab consistency". Stale-deployment ("client payload newer than server") triggers read-only mode with an explicit banner (ADR-0004 §"Schema versioning and migration"). No onboarding surface pushes a payload that includes a `vehicles`, `events`, `readings`, or `reminders` mutation.

### Failure and recovery behavior

Mandatory states, each with cause explanation, safe action, and honest persistence outcome: hydration-deadline timeout → `:storage_unavailable` state with the FR-12 session-only banner (ADR-0004 default 5 000 ms); IndexedDB open failure or probe failure → same `:storage_unavailable` state; `QuotaExceededError` on a write → the failed-ack UI (persistent "Not saved to this browser" affordance, optimistic value still visible but marked unsaved, export offered — ADR-0004 §"Mutation round trip" and §"Quota and eviction"); `dos_boot_state == "has_data"` but hydration returns zero records → `:data_missing` warning naming the eviction/clearing scenarios, offering import (INV-24.4/24.8, INV-25); import validation failure → the DOS-M09-001 quarantine surface with counts and export of raw payload; stale-deployment newer-payload → read-only banner, mutations disabled, export offered. No failure path anywhere in this spec deletes a returning visitor's IndexedDB data.

### Security and privacy

This card owns first-visit and Settings *content*; the transport and origin security posture is INV-22 and DOS-M09-008. The privacy copy is bound to what ADR-0004 makes true: server holds no personal record (release-gated test per ADR-0004 §"Enforcement"); no third-party analytics, tag manager, session recorder, error reporter, or embedded widget on any surface (INV-4, CSP-enforced per ADR-0004 §"Content Security Policy"); no cookie carries a personal value or a stable user identifier (ADR-0004 §"CSRF and session"); operator access to a live socket is possible in principle and the copy is scoped to reflect that (ADR-0004 §"LiveDashboard and operator access — stated honestly"). Destructive confirmations name exactly the IndexedDB stores and `localStorage` keys they clear (FR-9). No copy claims encryption of storage, promises recovery beyond export/import, or implies a server-side record exists that could be deleted.

### Accessibility and performance

Every state follows the DOS-M02-002 WCAG 2.2 AA contract for browser assistive technology (NVDA + Firefox, VoiceOver + Safari on macOS and iOS, TalkBack + Chrome on Android, JAWS + Chrome). `:hydrating` renders a skeleton with an accessible-name description; state transitions are announced to screen readers via `aria-live="polite"` and are not color-only; destructive confirmations are fully operable by keyboard, switch control, VoiceOver, and TalkBack; text scales to 200% zoom without loss of content or function; focus order is deterministic on state changes; the multi-tab "reloaded" notice does not steal focus. First-visit reaches "add first vehicle" in as few steps as possible while keeping optional personalization skippable in one action. Hydration budget: onboarding is entered only after `:empty` resolves; the sub-second hydration budget itself is owned by DOS-M09-002 (ADR-0004 R2).

## UX and content states

- **First visit, storage healthy**: skeleton (`:hydrating`) → welcome and privacy explanation (`:empty`) → optional personalization (skippable) → unit/time-zone confirmation → "add first vehicle" (DOS-M02-004).
- **Returning visitor, hydrated**: instant `:loaded` state; `phx-disconnected` styling on reconnect; no onboarding surface.
- **Returning visitor, storage cleared** (`:data_missing`): explicit warning naming eviction/clearing scenarios; import offered; onboarding not re-run silently.
- **Private browsing or blocked storage** (`:storage_unavailable`): FR-12 session-only banner; catalog browsing remains available; export offered from the banner.
- **Stale deployment (client payload newer than server)**: read-only banner; mutations disabled; export offered.
- **Multi-tab re-hydration**: visible non-focus-stealing notice; last-write-wins loss made visible per ADR-0004 §"Multi-tab consistency".
- **Settings**: storage status row, catalog `data_version` and attribution row, export button, import button (replace/merge with counts preview), erase-all-local-data row with FR-9 confirmation, links to Netlify privacy and attribution pages (DOS-M09-007).
- **Content rules**: FR-2 prohibited words apply everywhere; INV-24.3 (no false empty-state flash), INV-24.4/24.8 (honest cleared-data messaging), INV-25 (honest storage-loss messaging) bind every surface this card writes.

## Dependency rationale

## Risks, decisions, and open questions

- **Risk**: privacy copy overpromises against the hosted URL that reads to users as "their server holds my data." Mitigation: FR-2 prohibited-words list, INV-25 honest storage-loss framing, and AC-5 mapping every claim to an ADR-0004/Constitution citation.
- **Risk**: eviction-related data loss reads to the user as a bug rather than an honestly-disclosed browser behavior. Mitigation: FR-13 explicit eviction naming, INV-24.4 `:data_missing` state, and DOS-M09-003 empty-state contract are stacked so the moment loss is visible the copy already told the user it could happen.
- **Risk**: onboarding subtly reintroduces a "profile" concept that reads as an account. Mitigation: FR-3 (optional-only personalization; no email/phone/password/DOB/contacts/consent), FR-7 (writes go to `prefs`, not a `UserRepo`), and the AC-2 prohibited-words check.
- **Open question**: whether an in-app "install this app" (PWA install) prompt should appear on first visit as an R1 mitigation. Explicitly deferred — this card treats the browser as a plain browser; the decision is DOS-M09-010.
- **Open question**: whether the Settings "storage status" row should surface `navigator.storage.estimate()` as absolute bytes, a percentage of quota, or both, given that browsers report quotas differently. Decision to record during copy review with a real-browser sample.
- **Decision to record**: how the multi-tab "reloaded from this browser's newer data" notice presents the losing tab's discarded optimistic edit — a compact diff, a "your last change was replaced" line, or both. ADR-0004 §"Multi-tab consistency" mandates the loss be visible; this card chooses the wording.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries (pre-pivot)

The spec targets `OnboardingLive` and `SettingsLive` (per §7), composed from DOS-M02-002 components (readiness/progress indicators, banners, destructive confirmation, empty/error/offline panels, `PermissionPrimer` explicitly not used at first launch). Readiness states surface `DigitalOilSticker.Boot` phases (catalog verification, user migration, Repo startup, recovery state, endpoint readiness) and `DataPacks` verification results; the UI consumes typed readiness states, never raw storage errors.

#### Data and persistence (pre-pivot)

Profile creation writes one `local_profiles` row (UUID, optional display name, unit system, IANA time zone, onboarding version, timestamps) in a single `UserRepo` transaction — one active profile in MVP, no credentials. Settings reads `catalog_metadata` (`data_version`, `generated_at`, content hash) and `data_sources` attribution for display. Catalog repair operates only on `CatalogRepo` staging/copy per §8 catalog rules (verify, stage, atomic rename, retain previous for rollback); "erase all local user data" operates only on `UserRepo`. The two operations never share a code path or a confirmation dialog.

#### Interfaces and events (pre-pivot)

Readiness UX consumes Boot state transitions; profile save follows the standard context-return pattern. Catalog activation surfaces the `catalog_activated` event where relevant (e.g., after repair/replace). The spec defines what each failure state exposes to the user (non-sensitive result codes per `schema_events` semantics) and the route taken after each terminal state (ready → add first vehicle; unrecoverable → explained failure with support guidance).

#### Failure and recovery behavior (pre-pivot)

Mandatory failure states, each with cause explanation, safe action, and persistence outcome: interrupted catalog copy (idempotent retry, FR-8); corrupt/incompatible bundled catalog (explain, retry/repair; download not the normal path); corrupt user store (recovery guidance per DOS-M00-004 proven strategy; never silent reset per §8 migration rules); embedded-BEAM startup failure; loopback LiveView reconnection (transient, auto-recovering indicator); storage-low (warn before writes fail); unsupported-OS (honest terminal state). Retries are idempotent; no failure path deletes user records.

#### Security and privacy (pre-pivot)

This issue owns privacy UX: copy must be accurate against §7 shell security (loopback-only endpoint, no telemetry or third-party analytics by default, opt-in diagnostic export is local/reviewable/redacted) and §8 storage facts. No collection of email, phone, password, date of birth, contacts, advertising consent, or cross-app tracking. Destructive actions require explicit confirmation naming exactly what is removed. Privacy claims are limited to reviewed facts — no "encrypted" or "backed up" claims the architecture does not support.

#### Accessibility and performance (pre-pivot)

All states follow the DOS-M02-002 contract: readiness progress is announced to screen readers, is not color-only, and uses skeleton/progress patterns with no indefinite spinner for local operations; text scales to 200%; destructive confirmations are fully operable by keyboard/switch/VoiceOver/TalkBack. First-run must reach "add first vehicle" with minimal friction — the spec records the step count and keeps optional steps skippable.

### UX and content states (pre-pivot)

- First-run: welcome/explanation → readiness (verifying/copying catalog) → optional personalization (skippable) → unit/time-zone confirmation → add first vehicle.
- Readiness failures: interrupted copy (retry), corrupt/incompatible bundled data (explained failure), embedded-BEAM startup failure, storage-low, unsupported-OS.
- Returning user: instant-ready, migration/update in progress, corrupt user store, loopback reconnection.
- Settings: data size/version, last catalog update, source/attribution, export/import (only if approved), reset catalog (repair), delete one vehicle, erase all local user data — with distinct destructive confirmations for the last three.
- Content rules: plain-language privacy copy per FR-2; terminology per §6 and DOS-M00-001; nothing that resembles account creation, sign-in, or cloud backup.
