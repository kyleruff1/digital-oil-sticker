## Outcome

An implementation-ready flow lets a user find the closest supported year/make/model/variant from the local catalog, understand match quality, and create a clearly labeled custom vehicle when exact coverage is unavailable.

The deliverable specifies progressive offline filtering, free-text search, disambiguation and confidence display, custom-vehicle creation, identity editing after history exists, and duplicate handling — all against the bundled `CatalogRepo` with zero network dependency.

## Why this matters and what it unblocks

Vehicle identity anchors every later recommendation. A fast but ambiguous selector can attach incorrect oil/filter claims; a perfectly strict selector can strand users when source data is incomplete. This issue unblocks vehicle-query APIs, add/edit screens, and data-quality QA.

It also fixes the honesty contract for search: unknown fields are never defaulted, match quality is always visible, and manual/custom vehicles never inherit curated recommendations — the UX embodiment of non-negotiable rules 4 and 5.

## Included

- Specify progressive filtering in the source-supported order (normally market/model year → make → model → variant/series → engine/powertrain attributes), with free-text search across normalized names/aliases and active-filter visibility.
- Define dependent-filter reset behavior, result counts, sorting, recent selections where privacy permits, no-result recovery, and fast keyboard/screen-reader operation.
- Display enough disambiguation attributes to distinguish variants without showing unsourced values. Expose match/confidence level and the attributes to which a recommendation actually applies.
- Support manual/custom vehicle creation with required nickname plus user-entered year/make/model fields and optional engine/notes. Custom records do not inherit curated compatibility/recommendations unless the user explicitly enters values.
- Specify editing a vehicle identity after history exists: preview impact, retain event snapshots, recalculate projections only after confirmation, and never silently remap to a newer catalog row.
- Define duplicate handling: the same catalog vehicle may be added more than once with distinct nicknames/odometers; warn but do not prohibit legitimate household duplicates.
- Specify the zero-result distinction between "no catalog match" and "catalog not installed/corrupt", and the recovery path from each.

## Excluded

- VIN scanning/decoding unless separately scheduled, live vPIC calls, fuzzy inference of engine/trim, license-plate lookup, dealer inventory, or guaranteeing every build configuration.
- Implementing vehicle-query APIs or screens (M04/M05); catalog content/coverage work (M03); recommendation display detail beyond applicability/confidence exposure (DOS-M02-006).

## Functional requirements

- FR-1: Progressive filtering follows the source-supported order — normally market/model year → make → model → variant/series → engine/powertrain attributes — with free-text search across normalized names/aliases and always-visible active filters.
- FR-2: Dependent-filter reset behavior, result counts, sorting rules, recent selections (only where privacy permits), no-result recovery, and fast keyboard/screen-reader operation are each specified.
- FR-3: Result rows and detail views display enough disambiguation attributes to distinguish variants without showing unsourced values; unknown fields are omitted or labeled unknown, never defaulted.
- FR-4: Match/confidence level and the attributes to which a recommendation actually applies are exposed before the user commits a selection.
- FR-5: Manual/custom vehicle creation requires a nickname plus user-entered year/make/model fields, with optional engine/notes; custom records do not inherit curated compatibility/recommendations unless the user explicitly enters values, and are clearly labeled as custom.
- FR-6: Identity editing after history exists shows an impact preview, retains event snapshots, recalculates projections only after confirmation, and never silently remaps to a newer catalog row.
- FR-7: Duplicate handling permits the same catalog vehicle more than once with distinct nicknames/odometers; the flow warns but does not prohibit legitimate household duplicates.
- FR-8: All queries use the provisioned local catalog and meet the accepted p95 latency budget; no flow requires network.
- FR-9: The zero-result state distinguishes "no catalog match" from "catalog not installed/corrupt", each with its own recovery path (manual/custom fallback vs. catalog repair per DOS-M02-003).
- FR-10: Selection persists stable ID (`configuration_key`), catalog version, and display snapshot; recommendation applicability is revalidated after any identity edit.
- FR-11: Search/filter controls announce result changes accessibly without excessive live-region noise.

## Technical implementation contract

### Components and ownership boundaries

The flow targets `VehiclePickerLive` (per §7) composed from DOS-M02-002 components: search field, filter chips, `CascadeSelect`, virtualized result rows, source/confidence badges, and empty/error/offline panels. Queries are owned by `DigitalOilSticker.Catalog` (read-only, `CatalogRepo`); persistence of a selection is owned by `DigitalOilSticker.Garage` (`UserRepo`). The UI consumes typed query results and support statuses; it never composes SQL or interprets raw completeness codes.

### Data and persistence

Search reads `vehicle_configurations` (indexed `(model_year, make_id, model_id)`), `makes`/`models` (indexed normalized names), and `aliases`; cascading indexed selectors must work without FTS (optional FTS tables exist only if the Mob/exqlite build proves FTS5 support). Selection writes a `vehicles` row persisting the nullable stable `configuration_key`, catalog version, nickname, year/make/model/configuration display snapshots, and support status; custom vehicles persist a null `configuration_key` with user-entered snapshots and `manual` provenance semantics. Old history remains readable via snapshots when a catalog changes (§4.2 stable-key-plus-snapshot rule).

### Interfaces and events

The spec maps each UI state to a `Catalog` query contract (filter cascade, free-text, count, detail) and each commit to a `Garage` operation emitting `vehicle_saved`. Identity edits define a preview interface (impact summary: affected recommendation applicability, projections requiring recalculation) and a confirmation step that triggers `forecast_changed`/`reminders_reconciled` reconciliation downstream. Result-change announcements are specified as polite, debounced live-region updates.

### Failure and recovery behavior

Zero-result honesty per FR-9: "no catalog match" leads to broadened filters, alias search hints, and the custom-vehicle fallback; "catalog not installed/corrupt" leads to the DOS-M02-003 repair path and never to the custom-vehicle path by default. Query failure/timeout states surface a bounded error panel with retry. Interrupted selection (process death mid-flow) restores per the DOS-M02-001 restoration contract without persisting a partial vehicle.

### Security and privacy

All search runs locally; no query, keystroke, or selection leaves the device. Recent selections are stored only where privacy permits and are clearable via the DOS-M02-003 data controls. No VIN capture exists in this flow (VIN scan/decode is excluded). Custom-vehicle notes are user content and are redacted from any logs/fixtures per §7.

### Accessibility and performance

Fast keyboard/screen-reader operation is a stated requirement (FR-2): filter cascades and result lists are fully operable via VoiceOver/TalkBack/keyboard per the DOS-M02-002 contract; result changes are announced without excessive live-region noise (FR-11). All queries meet the accepted p95 latency budget from the ratified non-functional targets (DOS-M00-001); result lists use virtualized rows; the prototype must remain usable at the maximum tested result volume and text size.

## UX and content states

- Search states: initial (cascade start), filtering (active filters visible), results (count + sorted rows), narrowing (dependent-filter reset), no-result ("no catalog match" with recovery), catalog-unavailable ("catalog not installed/corrupt" with repair path), detail/disambiguation (variant comparison with sourced attributes only), confirm-selection (match/confidence and applicability shown).
- Custom-vehicle states: entry form (required nickname, year/make/model; optional engine/notes), clearly labeled custom badge, no inherited recommendations.
- Identity-edit states: edit form, impact preview, confirmation, post-edit revalidation result.
- Duplicate states: duplicate-detected warning with proceed option.
- Terminology: "Exact configuration not verified" and unknown labels per §6; support statuses surfaced per the §5 status vocabulary; match quality language must not overstate confidence.

## Risks, decisions, and open questions

- Risk: over-strict selection strands users on incomplete data. Mitigation: custom-vehicle fallback is a first-class, clearly labeled path with no inherited recommendations.
- Risk: ambiguous selection attaches wrong recommendations. Mitigation: FR-3/FR-4 make disambiguation attributes and applicability visible before commit; unknown never collapses to compatible (§9).
- Risk: p95 latency budget unproven at realistic catalog scale. Mitigation: the spec cites the DOS-M00-001 budget and flags scale validation as an M04/M05 benchmark obligation, not a design assumption.
- Open question: recent-selections retention policy (where privacy permits) — the spec must define retention and clearing, coordinated with DOS-M02-003 data controls.
- Decision to record: sorting defaults and the exact dependent-filter reset semantics per level of the cascade.
