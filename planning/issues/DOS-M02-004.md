> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Search is served by a server-side query layer rather than a local database, so the spec must add network-latency, request-failure, and offline states that the offline design never needed._

## Outcome

An implementation-ready specification for a hosted, browser-based vehicle finder: a user opens `digitaloilsticker.com` in a mainstream browser, searches the server-side catalog over the LiveView WSS transport, understands match quality and confidence, and either commits a supported selection or creates a clearly labeled custom vehicle. Every result row, cascade transition, and detail view is answered by a server round trip against the read-only `CatalogRepo` baked into the Fly.io deploy image ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) Decision 2, "Catalog database on Fly"); the resulting selection is persisted **only** to the user's IndexedDB through the hydration protocol (INV-23, INV-24.2). The spec fixes network-latency, request-failure, socket-drop, reconnect, and hosted-connectivity-required states that had no counterpart in the pre-pivot offline design, and reconciles duplicate handling and identity-editing behavior with the "browser is the system of record" boundary.

## Why this matters and what it unblocks

Vehicle identity anchors every later recommendation, and under the pivot the *client of that anchor* changed twice at once: search now travels the public internet on every keystroke, and the persisted selection lives in the user's browser IndexedDB rather than in a client-bundled SQLite `UserRepo`. Either seam can silently attach the wrong recommendation to the wrong garage entry, and neither seam existed in the pre-pivot spec. Freezing the specification here prevents the M05 single-vehicle MVP work (`DOS-M05-002` re-scoped search-and-select, `DOS-M05-003` re-scoped create/edit round trip) from being invented flow-by-flow against untested assumptions about hosted latency, request failure, and hydration-time selection replay.

It also refits the honesty contract for search to a hosted product: unknown fields still never default, match quality is still always visible, and the previously implicit promise "search works with no network" is retired honestly (ADR-0004 "Consequences": "the user needs connectivity to select a vehicle or read a schedule") rather than left as an unfulfilled AC.

## Included

- Specify progressive filtering in the source-supported order (normally market/model year → make → model → variant/series → engine/powertrain attributes) with free-text search across normalized names/aliases and always-visible active filters, delivered by server round trip against the hosted `CatalogRepo` through LiveView events.
- Specify dependent-filter reset behavior, result counts, sorting, no-result recovery, and fast keyboard/screen-reader operation for a browser AT surface (VoiceOver in Safari, NVDA in Firefox/Edge, JAWS in Chrome, TalkBack in Android Chrome, keyboard-only desktop) as the specification surface for this card.
- Specify what disambiguation attributes are displayed to distinguish variants without showing unsourced values, and how the match/confidence level and applicability of a recommendation are shown before commit.
- Specify manual/custom vehicle creation (nickname + user-entered year/make/model, optional engine/notes), the custom-badge treatment, and the rule that custom records do not inherit curated compatibility/recommendations.
- Specify identity editing after history exists: impact preview, event-snapshot retention, and recalculation only after confirmation. The commit path travels the INV-24.2 round trip and is not shown as saved until the hook acknowledges the IndexedDB write.
- Specify duplicate handling: the same catalog vehicle may be added more than once with distinct nicknames/odometers; warn but do not prohibit legitimate household duplicates.
- Specify the network-facing states that did not exist offline: `:hydrating` (search UI inert until hydration resolves per INV-24.3), `:query_pending`, `:query_slow` (long-tail warning past the §9 provisional budget), `:query_failed` (with retry), `:socket_disconnected` (phx-disconnected styling; a re-render after reconnect does not lose the entered query), `:reconnect_rehydrating` (post-remount replay of the last selection state without a false empty flash).
- Specify the hosted-connectivity precondition and the honest offline state: with no socket the UI cannot search or resolve; the storage-loss/offline copy is drawn from `DOS-M09-004`; there is no airplane-mode selection path.
- Specify the "recent selections" behavior in a browser: recents are held **only** in IndexedDB alongside the user's other records; nothing recent-vehicle is remembered server-side, in a cookie, or in a URL query parameter (INV-3, INV-26).
- Specify the request-payload shape for every search/filter/resolve event: no VIN, odometer, nickname, note, or other personal value is transmitted as a catalog-query parameter (INV-26); catalog queries carry only catalog identifiers and filter values.
- Specify the zero-result distinction: "no catalog match" (recover via broadened filters, aliases, custom-vehicle fallback) vs. "catalog server error / request failed" (retry; not the custom-vehicle path) vs. "hydration in progress" vs. "socket disconnected". Each is a different state with different copy.

## Excluded

- VIN scanning/decoding (a camera-permission decision that would need a new ADR touching the Permissions-Policy header, per ADR-0004 §"Content Security Policy"), live vPIC calls, fuzzy inference of engine/trim, license-plate lookup, dealer inventory, and guaranteeing every retail build configuration.
- Any PWA / service-worker offline mode for search: explicitly deferred at MVP (ADR-0004 "Consequences"; PIVOT gap 9). No copy in this spec may describe search as "offline-capable" or "works without a connection."
- Any server-side "recent selections" or "search history" retention: prohibited by INV-3/INV-26 and would create an account without a password.
- The implementation of the query layer itself (`DOS-M09-005`), the hydration protocol wire format (`DOS-M09-003`), and the IndexedDB adapter (`DOS-M09-002`); this card consumes their contracts and specifies the search UX over them.
- Multi-vehicle garage semantics beyond duplicate handling (post-MVP; `DOS-M08-001` re-scoped).
- Recommendation display detail beyond applicability/confidence exposure (`DOS-M02-006` remains SURVIVES for that content).

## Functional requirements

- FR-1: Progressive filtering follows the source-supported order (normally market/model year → make → model → variant/series → engine/powertrain attributes), with free-text search across normalized names/aliases and always-visible active filters. Every cascade step is a LiveView `handle_event` that reads the server-side `CatalogRepo` through the `DOS-M09-005` query contract; no cascade result is inferred client-side from stale data.
- FR-2: Dependent-filter reset behavior, result counts, sorting, no-result recovery, and full keyboard/screen-reader operation are each specified against the browser AT surface (VoiceOver, NVDA, JAWS, TalkBack, keyboard-only desktop) per `DOS-M02-002` and §9's WCAG 2.2 AA row.
- FR-3: Result rows and detail views display enough disambiguation attributes to distinguish variants without showing unsourced values; unknown fields are omitted or labeled unknown, never defaulted (INV-4 in the pre-pivot form is preserved verbatim in 2.0.0).
- FR-4: Match/confidence level and the attributes to which a recommendation actually applies are exposed before the user commits a selection, using the INV-11 support-status vocabulary.
- FR-5: Manual/custom vehicle creation requires a nickname plus user-entered year/make/model, with optional engine/notes; custom records do not inherit curated compatibility/recommendations unless the user explicitly enters values, and are clearly labeled as custom. The commit writes to the IndexedDB `vehicles` object store through the INV-24.2 round trip; the "Saved to this browser" affordance appears only after the hook acknowledges the write.
- FR-6: Identity editing after history exists shows an impact preview, retains event snapshots, and recalculates projections only after confirmation. The edit commit travels the same INV-24.2 round trip; a missed acknowledgment surfaces the persistent "Not saved to this browser" state defined by `DOS-M09-004`, and never a silent rollback.
- FR-7: Duplicate handling permits the same catalog vehicle more than once with distinct nicknames/odometers; the flow warns but does not prohibit legitimate household duplicates. Duplicate detection reads only the IndexedDB `vehicles` payload already in socket assigns (post-hydration); the server does not compare against any other user's data because there is no other user on the server (INV-3).
- FR-8 **(replaces the retired pre-pivot FR-8)**: Search, filter, disambiguation, selection, and identity-editing flows require a connected WSS session against `digitaloilsticker.com`. The pre-pivot claim "no flow requires network" is retired per ADR-0004 "Consequences" ("the user needs connectivity to select a vehicle or read a schedule"); airplane-mode operation is not a supported mode. When the socket is disconnected the UI enters the `:socket_disconnected` state (INV-7): the search field is disabled with an honest message, entered text is preserved locally, and on reconnect the query is re-run without the user retyping it. There is no silent local-cache fallback.
- FR-9 **(replaces the retired pre-pivot FR-9)**: The zero-result state distinguishes four cases with distinct copy and recovery: (a) "no catalog match" — offer broadened filters, alias hints, and custom-vehicle fallback; (b) "catalog server error / request failed" — offer retry; do **not** offer the custom-vehicle path by default, because a transient server error is not evidence the vehicle is unsupported; (c) "hydration in progress" (INV-24.3) — show the honest hydrating skeleton, never a false "no vehicles" state; (d) "socket disconnected" (INV-7) — as in FR-8. Cases (b), (c), and (d) had no counterpart in the pre-pivot offline design.
- FR-10: Selection persists a stable `configuration_key`, catalog `data_version`, and a display snapshot to the IndexedDB `vehicles` record so that later history remains readable even if a subsequent catalog release retires the configuration. Recommendation applicability is revalidated by the server (against the currently deployed catalog) after any identity edit, and the applicability answer is a render output, not a durable server row.
- FR-11: Search/filter controls announce result changes accessibly through a polite, debounced ARIA live region, coordinated with the hydration and reconnect announcements from `DOS-M09-004` so the user is not flooded with overlapping announcements.
- FR-12 **(new; addresses ADR-0004 §"Consequences" and INV-24.1)**: A LiveView reconnect (network blip, server redeploy, laptop sleep) does not lose the user's in-progress selection state. The specification defines what "in-progress" means (partially cascaded filters, focused row, un-committed identity edit) and how it is restored after remount: cascade filters are restored from the current URL/route parameters where they belong on the URL, and any un-committed edit is restored from IndexedDB rather than from server memory (INV-24.1 — the server was never the system of record). No selection that was previously acknowledged in IndexedDB is ever "lost by a deploy."
- FR-13 **(new; addresses INV-26)**: Every catalog-query event payload carries only catalog identifiers and filter values. VIN, odometer, nickname, note text, and any other personal field are prohibited from catalog-query payloads, from URL query parameters, from cookies, and from server logs (INV-4/INV-26). The spec enumerates the exact payload shape for each catalog event.
- FR-14 **(new; addresses ADR-0004 R9 and Constitution §9 *provisional* targets)**: The flow is specified against the §9 (2.0.0) *provisional* targets: catalog first paged result server-side p95 ≤ 250 ms, subsequent filter server-side p95 ≤ 150 ms, LiveView event round trip p95 ≤ 150 ms measured from the client, hydration completion p95 ≤ 300 ms after socket join, page LCP p75 ≤ 2.5 s, TTI p75 ≤ 3.5 s. The pre-pivot §9 loopback budgets are void per ADR-0004 R9; this card cites only the re-ratified 2.0.0 *provisional* row, and any tighter budget waits on the re-measurement obligation.
- FR-15 **(new; addresses ADR-0004 R1 and INV-24.4/24.5/24.6)**: Search UX degrades honestly under browser storage constraints per `DOS-M09-004`: when IndexedDB is unavailable, restricted, or in a private/incognito context the search flow still runs but the selection cannot be persisted; the UI states this before the user enters data (INV-24.6), offers export as the only recovery, and never silently degrades to a session-only vehicle that looks durable.
- FR-16 **(new; addresses INV-24.7 / multi-tab)**: Two tabs of the same origin may be searching independently; a selection committed in one tab must not be silently overwritten by a stale selection commit in the other. The spec defers the mechanism to `DOS-M09-003`'s compare-and-set on `meta.seq` and specifies the user-visible outcome: on a conflict, the losing tab re-hydrates and shows an honest "reloaded from this browser's newer data" notice rather than a silent rollback.

## Technical implementation contract

### Components and ownership boundaries

The flow targets a `VehiclePickerLive` LiveView composed from `DOS-M02-002` browser components — search field, filter chips, `CascadeSelect`, virtualized result rows, source/confidence badges, and the empty/error/hydrating/disconnected/storage-unavailable panels from `DOS-M09-004`. Catalog queries are owned by `DigitalOilSticker.Catalog` (read-only `CatalogRepo`, opened with the SQLite read-only mode per ADR-0004 §"Catalog database on Fly"). Persistence of a selection is owned by the browser-side `LocalStore` hook and its IndexedDB adapter (`DOS-M09-002`); the server holds the resulting selection **only** in `socket.assigns` for the socket's lifetime (INV-24.1). Domain contexts (`Catalog`, `Garage`, `Forecast`) MUST NOT reference `Phoenix.LiveView` or the `LocalStore` protocol modules, per ADR-0004 §"Enforcement".

### Data and persistence

Server-side reads: `vehicle_configurations` (indexed `(model_year, make_id, model_id)`), `makes`/`models` (indexed normalized names), and `aliases` — from the read-only `CatalogRepo` inside the deploy image. Cascading indexed selectors must work without FTS; optional FTS5 tables are used only if the deployed SQLite build supports FTS5 and the query layer (`DOS-M09-005`) exposes them.

Client-side persistence: selection is written to the IndexedDB `vehicles` object store defined by `DOS-M09-001` — client-generated UUIDv4 key, stable `configuration_key` (nullable for custom vehicles), catalog `data_version`, nickname, year/make/model/configuration display snapshots, and support status. There is no server-side `vehicles` table; the deployed application holds exactly one Ecto repo (`CatalogRepo`), opened read-only, per ADR-0004 Decision 4 and the enforcement test that pins the repo list.

### Interfaces and events

Each UI state maps to one of the catalog query contracts exposed by `DOS-M09-005` (cascade, free-text, count, detail). Each commit is a LiveView `pushEvent` → server round trip → `push_event("local_store:put", ...)` → hook writes IndexedDB → hook `pushEvent("local_store:ack", ...)` sequence per `DOS-M09-003`. Identity edits define a preview interface (impact summary: affected recommendation applicability and projections requiring recalculation) and a confirmation step that only takes effect after the client `local_store:ack` — never before. Result-change announcements are specified as polite, debounced live-region updates coordinated with the hydration/reconnect announcements.

### Failure and recovery behavior

Every state named in FR-9 has a specified panel and copy; none silently collapses into another. `:socket_disconnected` uses `phx-disconnected` styling per ADR-0004 §"WebSocket and LiveView considerations", preserves entered query text locally, and re-issues the query on reconnect. `:query_failed` offers retry only; a retry ceiling produces a bounded error panel with no fallback to the custom-vehicle path (a transient error is not evidence the catalog lacks the vehicle). `:hydrating` never shows an onboarding-from-zero flow (INV-24.3). `:storage_unavailable` follows the `DOS-M09-004` copy — search still works, but the "Save vehicle" affordance is disabled with an honest explanation and export is offered. An in-flight identity edit that fails to acknowledge within the `DOS-M09-003` 2 000 ms window renders as "Not saved to this browser" per INV-24.2 and does not roll back invisibly.

### Security and privacy

Transport: HTTPS + WSS only (INV-22, ADR-0004 §"Transport"); LiveView socket protected by CSRF token passed through connect params and by the `check_origin` host allow-list. Session cookie is signed, `secure`, `http_only`, `same_site: "Lax"` and carries **no** vehicle, VIN, odometer, or selection state (ADR-0004 §"CSRF and session"). Catalog-query payloads carry only catalog identifiers and filter values (FR-13, INV-26); no VIN capture exists in this flow (VIN scan is explicitly excluded and would require a separate ADR touching the Permissions-Policy header). URL query parameters MAY carry cascade filter values (year/make/model IDs) because those identify catalog rows, not the user, and are useful for shareable and refresh-safe URLs (`DOS-M02-001`); URL parameters MUST NOT carry VIN, odometer, nickname, note text, or any other personal field. Server logs MUST NOT include `handle_event` params by default (ADR-0004 §"Logging"); an explicit non-personal event allow-list governs what is logged.

### Accessibility and performance

Accessibility targets the browser AT surface named in the §9 (2.0.0) support matrix row (Chrome/Edge/Firefox/Safari desktop plus iOS Safari 16+ and Android Chrome) as the only supported surface at MVP. WCAG 2.2 AA per the §9 row: text contrast ≥ 4.5:1, usable at 200% zoom and 320 CSS px reflow, full keyboard operability with visible focus indicators and no keyboard traps, target size ≥ 24×24 CSS px (≥ 44×44 SHOULD where touch is primary), full screen-reader operability including live-region announcement of hydration, disconnect, and result-count changes. Performance targets are the §9 (2.0.0) *provisional* rows named in FR-14; the pre-pivot loopback budget is void (ADR-0004 R9) and MUST NOT be cited. Result lists use virtualized rows; the prototype must remain usable at the maximum tested result volume and text size and on the slowest supported browser/engine combination.

## UX and content states

- Search states (network-aware): `:hydrating` (skeleton per INV-24.3, search inert), `:idle_ready` (cascade start), `:filtering` (active filters visible), `:query_pending` (server request in flight, debounced), `:query_slow` (long-tail warning past the §9 provisional budget), `:results` (count + sorted rows), `:narrowing` (dependent-filter reset), `:no_catalog_match` (recovery via broadened filters, alias hints, custom fallback), `:query_failed` (retry; no custom fallback), `:socket_disconnected` (phx-disconnected styling, preserved text, no search), `:reconnect_rehydrating` (post-remount replay), `:storage_unavailable` (search runs but selection cannot be saved; export offered), `:detail_disambiguation` (variant comparison with sourced attributes only), `:confirm_selection` (match/confidence and applicability shown).
- Custom-vehicle states: entry form (required nickname, year/make/model; optional engine/notes), clearly labeled custom badge, no inherited recommendations, `:saving` and `:saved_to_this_browser` reflecting the INV-24.2 round trip.
- Identity-edit states: edit form, impact preview, confirmation, `:saving`, `:saved_to_this_browser`, `:not_saved_to_this_browser` (persistent per INV-24.2/DOS-M09-004), post-edit revalidation result rendered from the server against the currently deployed catalog.
- Duplicate states: duplicate-detected warning with proceed option; the warning reads only from the hydrated in-assigns garage payload.
- Multi-tab states: `:reloaded_from_newer_data` after a compare-and-set conflict (INV-24.7), rather than a silent overwrite.
- Terminology: "Exact configuration not verified" and unknown labels per the terminology row of the constitution; support statuses surfaced per INV-11; match-quality language must not overstate confidence; no state may describe browser storage as "saved" without the "to this browser" qualifier (INV-5, INV-25); no state may describe search as "offline-capable."

## Acceptance criteria

- [ ] AC-1: Flows cover exact-match, multiple-match, ambiguous, missing, custom, duplicate, retired-configuration, identity-edit, disconnected-then-reconnected, query-failed-then-retried, and hydration-in-progress cases.
- [ ] AC-2: Users can see why two variants differ, and match/confidence and applicability are visible before commit.
- [ ] AC-3 **(replaces the retired pre-pivot AC-3)**: The hosted flow works over WSS against `digitaloilsticker.com` on every browser/engine in the §9 (2.0.0) support matrix row. The pre-pivot "first launch in airplane mode" requirement is retired per ADR-0004 "Consequences" ("the user needs connectivity to select a vehicle or read a schedule"); airplane mode produces the honest `:socket_disconnected` state defined by FR-8/INV-7, with entered text preserved locally and re-run on reconnect.
- [ ] AC-4: Identity edits preserve readable history through the `configuration_key`-plus-snapshot rule, require confirmation before forecast changes, and are not shown as saved until the `local_store:ack` returns per INV-24.2.
- [ ] AC-5: Prototype remains usable at the maximum tested result volume and text size, on the slowest supported browser/engine combination in the §9 matrix.
- [ ] AC-6: Unknown fields are omitted or labeled unknown in every specified state; no state defaults an unknown to a value.
- [ ] AC-7: The zero-result state distinguishes the four FR-9 cases with distinct copy and recovery paths; only "no catalog match" leads to the custom-vehicle path by default.
- [ ] AC-8 **(new; addresses FR-12, FR-16, INV-24.1/24.7)**: A LiveView reconnect during any search state does not lose in-progress selection state; a two-tab commit conflict enters the `:reloaded_from_newer_data` state rather than silently overwriting.
- [ ] AC-9 **(new; addresses FR-13, INV-4/26)**: A scripted-session log-scan finds no VIN, odometer, nickname, note text, or custom-vehicle name in any captured log line, and no catalog-query event payload contains a personal field.
- [ ] AC-10 **(new; addresses FR-15, INV-24.4/24.5/24.6, ADR-0004 R1)**: In a private/incognito context and in a storage-blocked context the search flow runs, the "Save vehicle" affordance is disabled with an honest explanation, and export is offered; no state silently degrades to a session-only vehicle presented as saved.
- [ ] AC-11 **(new; addresses FR-11, INV-7, DOS-M09-004)**: Result-change, hydration, and reconnect announcements use polite, debounced ARIA live regions and are coordinated so that a screen-reader user is never read overlapping updates; this is verified against the `DOS-M02-002` browser AT surface (VoiceOver in Safari, NVDA in Firefox/Edge, JAWS in Chrome, TalkBack in Android Chrome, keyboard-only desktop) with the debounce interval, live-region politeness setting, and coordination rule (hydration and reconnect announcements take precedence over result-count announcements for the same tick) fixed in the spec rather than left to implementation.

## Test plan

### Automated

## Risks, decisions, and open questions

- Risk: hosted round-trip latency makes the cascade feel sluggish on a mid-tier mobile device over 4G. Mitigation: the §9 (2.0.0) *provisional* budgets in FR-14 are the design ceiling, virtualized rows and debounced live regions keep the UI responsive under it, and `DOS-M09-005` owns the server-side latency work; final numbers are measured post-provisioning, not asserted here.
- Risk: a user selects a vehicle, closes the tab, and a browser eviction (ADR-0004 R1) later clears IndexedDB; the user opens the app and sees no garage. Mitigation: the `:data_missing` warning from `DOS-M09-004` is the correct state, not a fresh empty garage; INV-25 messaging is mandatory; export is the recovery path and is surfaced after every meaningful write.
- Risk: a user in a private-browsing window commits a "selection" that dies with the tab. Mitigation: FR-15 / AC-10 require the honest "not saved" messaging *before* the user enters data (INV-24.6); the "Save vehicle" affordance is disabled and export is offered.
- Risk: an over-eager retry loop on `:query_failed` amplifies a Fly incident. Mitigation: bounded retries with exponential backoff and a visible error state; no silent retry on top of a queued LiveView event.
- Risk: URL-shareable cascade filters accidentally include a personal identifier. Mitigation: FR-13 pins the payload shape; URL params carry only catalog identifiers; `DOS-M02-001` route contracts are the enforcement point.
- Open question: whether a "recent selections" list stored in IndexedDB is worth the complexity vs. simply relying on the garage list; the pre-pivot recents feature was ambient in a bundled client store, and in the browser the same UX is now indistinguishable from the garage itself.
- Open question: exact sorting defaults and dependent-filter reset semantics per level of the cascade — deferred to the flow specification deliverable, not fabricated here.
- Decision to record: whether a shareable "cascade filter" URL exists at all, or whether only the committed vehicle route is shareable. Recommendation: allow shareable cascade URLs because they are useful and INV-26-compatible, but only for catalog identifiers.

### Outcome (superseded)

An implementation-ready flow lets a user find the closest supported year/make/model/variant from the local catalog, understand match quality, and create a clearly labeled custom vehicle when exact coverage is unavailable.

### Technical implementation contract (superseded)

#### Components and ownership boundaries (superseded)

The flow targets `VehiclePickerLive` (per §7) composed from DOS-M02-002 components: search field, filter chips, `CascadeSelect`, virtualized result rows, source/confidence badges, and empty/error/offline panels. Queries are owned by `DigitalOilSticker.Catalog` (read-only, `CatalogRepo`); persistence of a selection is owned by `DigitalOilSticker.Garage` (`UserRepo`). The UI consumes typed query results and support statuses; it never composes SQL or interprets raw completeness codes.

#### Data and persistence (superseded)

Search reads `vehicle_configurations` (indexed `(model_year, make_id, model_id)`), `makes`/`models` (indexed normalized names), and `aliases`; cascading indexed selectors must work without FTS (optional FTS tables exist only if the Mob/exqlite build proves FTS5 support). Selection writes a `vehicles` row persisting the nullable stable `configuration_key`, catalog version, nickname, year/make/model/configuration display snapshots, and support status; custom vehicles persist a null `configuration_key` with user-entered snapshots and `manual` provenance semantics. Old history remains readable via snapshots when a catalog changes (§4.2 stable-key-plus-snapshot rule).

#### Interfaces and events (superseded)

The spec maps each UI state to a `Catalog` query contract (filter cascade, free-text, count, detail) and each commit to a `Garage` operation emitting `vehicle_saved`. Identity edits define a preview interface (impact summary: affected recommendation applicability, projections requiring recalculation) and a confirmation step that triggers `forecast_changed`/`reminders_reconciled` reconciliation downstream. Result-change announcements are specified as polite, debounced live-region updates.

#### Failure and recovery behavior (superseded)

Zero-result honesty per FR-9: "no catalog match" leads to broadened filters, alias search hints, and the custom-vehicle fallback; "catalog not installed/corrupt" leads to the DOS-M02-003 repair path and never to the custom-vehicle path by default. Query failure/timeout states surface a bounded error panel with retry. Interrupted selection (process death mid-flow) restores per the DOS-M02-001 restoration contract without persisting a partial vehicle.

#### Security and privacy (superseded)

All search runs locally; no query, keystroke, or selection leaves the device. Recent selections are stored only where privacy permits and are clearable via the DOS-M02-003 data controls. No VIN capture exists in this flow (VIN scan/decode is excluded). Custom-vehicle notes are user content and are redacted from any logs/fixtures per §7.

#### Accessibility and performance (superseded)

Fast keyboard/screen-reader operation is a stated requirement (FR-2): filter cascades and result lists are fully operable via VoiceOver/TalkBack/keyboard per the DOS-M02-002 contract; result changes are announced without excessive live-region noise (FR-11). All queries meet the accepted p95 latency budget from the ratified non-functional targets (DOS-M00-001); result lists use virtualized rows; the prototype must remain usable at the maximum tested result volume and text size.

### UX and content states (superseded)

- Search states: initial (cascade start), filtering (active filters visible), results (count + sorted rows), narrowing (dependent-filter reset), no-result ("no catalog match" with recovery), catalog-unavailable ("catalog not installed/corrupt" with repair path), detail/disambiguation (variant comparison with sourced attributes only), confirm-selection (match/confidence and applicability shown).
- Custom-vehicle states: entry form (required nickname, year/make/model; optional engine/notes), clearly labeled custom badge, no inherited recommendations.
- Identity-edit states: edit form, impact preview, confirmation, post-edit revalidation result.
- Duplicate states: duplicate-detected warning with proceed option.
- Terminology: "Exact configuration not verified" and unknown labels per §6; support statuses surfaced per the §5 status vocabulary; match quality language must not overstate confidence.
