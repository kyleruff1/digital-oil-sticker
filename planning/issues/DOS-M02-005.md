## Outcome

The blocking MVP specification supports exactly one active vehicle and its status/lifecycle. A clearly labeled, non-blocking appendix designs how a later milestone can add a searchable Garage and vehicle tabs without requiring MVP implementation.

The deliverable is the home/status experience — the "digital sticker" — for zero or one active vehicle: the vehicle card contract, lifecycle actions (add, view, edit/replace, permanently delete), attention states, and destructive-action semantics, plus the separated post-MVP multi-vehicle design direction.

## Why this matters and what it unblocks

MVP needs a small, testable interaction surface, while the schema/navigation should avoid making later multi-vehicle support impossible. This issue fixes the boundary so tabs and many-vehicle workflows do not leak into MVP acceptance.

It unblocks the M05 home/status screen (`StickerLive`), the vehicle lifecycle implementation in `Garage`, and DOS-M02-006/007/008, which all need an authoritative definition of the active vehicle, its card fields, and its status vocabulary.

## Technical implementation contract

### Components and ownership boundaries

The home/status screen targets `StickerLive` composed from DOS-M02-002 components (`VehicleSummary`, `DueStatus`, `SourceBadge`, `ConfidenceBadge`, destructive confirmation, empty panels). Vehicle lifecycle is owned by `DigitalOilSticker.Garage`; status derivation by `Maintenance`/`Forecasting` per §7 boundaries. The card renders typed status/confidence values; no screen computes its own due arithmetic (§9: no screen may implement its own arithmetic).

### Data and persistence

The active-vehicle constraint is a service/repository contract over the `vehicles` table (stable UUIDs, plural table names, archival-state fields retained) so the one-vehicle limit is a policy, not a schema shape. Card data derives from `vehicles` snapshots, latest `service_events`, `forecast_snapshots`/current forecast policy output, and `reminder_rules`/`scheduled_notifications` state. Permanent deletion enumerates the affected rows across `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, and `scheduled_notifications`; replace preserves history per DOS-M02-004 identity-edit/replace semantics and never silently remaps.

### Interfaces and events

Lifecycle actions map to `Garage`/`Maintenance` operations emitting `vehicle_saved` and driving `forecast_changed`/`reminders_reconciled` where applicable; delete/replace flows must specify the reminder-intent update and OS-notification cancellation handoff (executed via the `Reminders` context and `DeviceCommandBroker`, per DOS-M02-008's reconciliation contract). The card's primary action routes per the DOS-M02-001 route table.

### Failure and recovery behavior

Specified states include unavailable-recommendation (catalog cannot support this vehicle — honest unsupported/identity-only messaging per the §5 status vocabulary), stale-driving-sample and invalid-odometer (attention prompts to update data, coordinated with DOS-M02-006/007 handling), and data-migration (read-only or progress state during `UserRepo` migration per DOS-M02-003). Interrupted delete/replace must not leave partial state: the spec requires transactional semantics and defines what the user sees on retry.

### Security and privacy

Deletion is a permanent, explicitly confirmed destructive action naming exact record categories; it is distinct from catalog repair (DOS-M02-003). No card content leaks to system surfaces beyond what DOS-M02-008 permits for notifications. Nickname and notes are user content, redacted from logs/fixtures per §7.

### Accessibility and performance

Card status must be understandable without color (text/icon/shape per DOS-M02-002); the status vocabulary (not enough data/upcoming/due/overdue) has distinct accessible announcements. The one-vehicle home renders entirely from local data within the accepted latency budgets. The post-MVP appendix must include the tab/selector accessibility treatment and a 100-vehicle performance plan (virtualization, safe switching) as non-blocking roadmap evidence.

## UX and content states

- Empty state (zero vehicles): explains the product and routes to add first vehicle.
- One-vehicle states: ready (sticker view with card fields per FR-2), not enough data, upcoming, due, overdue, unavailable-recommendation, stale-driving-sample, invalid-odometer, data-migration.
- Lifecycle states: add (via DOS-M02-004), view, edit/replace (impact preview + confirmation), permanent-delete (enumerated records + destructive confirmation + completion).
- Vehicle-context display: persistent, non-color-only context on every log/edit/reminder screen.
- Post-MVP appendix states (non-blocking): tabs/selector at 1, 5, 20, 100 vehicles; Garage search/filter/sort; overflow fallback; archive/restore.
- Terminology per §6: "Estimated due date" with confidence label; no invented due dates; reminder state reflects true permission/scheduling status.

## Risks, decisions, and open questions

- Risk: multi-vehicle ambition leaks into MVP acceptance. Mitigation: FR-5/AC-5 keep the appendix labeled and non-blocking; §3 rule 9 is cited on the boundary.
- Risk: status stored as text drifts from source records. Mitigation: FR-8 mandates derived status from records plus versioned forecast policy.
- Risk: deletion under-enumerates affected records, causing surprise data loss. Mitigation: AC-6 plus the destructive-action matrix reviewed against the DOS-M01-003 schema.
- Open question: whether "replace" is modeled as archive-then-add or in-place identity change is recorded as an explicit decision with its history/reminder consequences (coordinated with DOS-M02-004 edit semantics).
- Decision to record: the exact primary action per status (e.g., due → record change; not enough data → add mileage), consistent with DOS-M02-001 task flows.
