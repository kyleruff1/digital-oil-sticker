> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The one-vehicle-now/multi-vehicle-later product shape is unchanged, but the "tabs" navigation direction must be respecified as a web navigation pattern._

## Outcome

A committed browser-MVP specification of the **one active vehicle** home/status experience — the hosted "digital sticker" rendered by Phoenix LiveView from anonymous browser storage — plus a clearly labeled, non-blocking post-MVP appendix that respecifies the multi-vehicle direction as a **web navigation pattern** (real URLs per vehicle, browser history, keyboard-first tab semantics) rather than the bare tab-bar direction originally chartered before the browser-first pivot.

The deliverable is (a) the vehicle card contract and its states as they must render in a hosted LiveView view whose personal data lives only in the user's IndexedDB and only reaches the server as transient socket assigns per [ADR-0004 §"Client-storage + LiveView hydration protocol"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#the-client-storage--liveview-hydration-protocol); (b) the lifecycle actions add, view, edit/replace, and permanently delete, expressed as `pushEvent` → hook → IndexedDB round trips per INV-24; (c) the enumerated MVP states including the browser-specific storage states (`:hydrating`, `:empty`, `:storage_unavailable`, `:data_missing`) that a device MVP never needed; and (d) the post-MVP appendix that names the accessible web-tabbed-garage direction — per-vehicle routes, browser back/forward, focus management, and virtualization for 5/20/100-vehicle states — as non-blocking evidence for a later milestone.

## Why this matters and what it unblocks

The one-vehicle-now/multi-vehicle-later shape survived the pivot intact (Constitution 2.0.0 INV-18) and remains the safest way to ship a first release without foreclosing a garage. What changed is the medium: a hosted LiveView view has to answer questions the pre-pivot tab-bar direction never raised — what the URL is per vehicle, what the browser back button does mid-lifecycle, what happens when a reconnect re-hydrates during a destructive-delete confirmation, and what the shell shows before hydration resolves. Freezing those answers now is what keeps the M05 rescoped home/status implementation from inventing them under pressure.

It unblocks the rescoped M05 hosted sticker view ([DOS-M05-005](DOS-M05-005.md)), the rescoped vehicle lifecycle in `DigitalOilSticker.Garage` ([DOS-M05-003](DOS-M05-003.md)), and the rescoped downstream cards that all read the active-vehicle contract off this one: [DOS-M02-006](DOS-M02-006.md) (logging/history, SURVIVES), [DOS-M02-007](DOS-M02-007.md) (usage sampling and explainable forecasts, SURVIVES), and [DOS-M02-008](DOS-M02-008.md) (RESCOPE — in-app due state only, INV-17 amended). It also fixes the MVP/post-MVP boundary that [DOS-M08-002](DOS-M08-002.md) (RESCOPE — accessible tabbed garage as a web pattern) inherits without having to reopen it.

## Included

- The **browser-MVP home/status experience** for zero or one active vehicle, rendered from hydrated socket assigns per INV-24 and re-rendered idempotently on every reconnect.
- The **vehicle card contract**: nickname, concise identity snapshot (year/make/model/trim as far as identity resolves against the server-queried catalog per INV-26), last recorded change date/mileage, estimated next date/mileage with a confidence/source indicator, in-app **due status** vocabulary (not enough data / upcoming / due / overdue), and the primary action for the current status. Every field is a rendered value over assigns; no card field is a durable server row.
- Lifecycle actions **add, view, edit/replace, permanently delete**, each specified as a `pushEvent` → hook → IndexedDB round trip per INV-24.2, including the not-yet-committed rendering rules and the visible-revert-on-failed-ack rule.
- The enumerated **browser-specific first-paint states** distinct in copy and DOM: `:hydrating` (skeleton, never an empty-garage flash), `:empty` (verified genuine first visit), `:storage_unavailable` (private-browsing / blocked-storage per INV-24.6), `:data_missing` (boot hint said `has_data` but hydration returned zero — likely browser-cleared, per INV-24.8 / INV-25), plus the domain states unavailable-recommendation, stale-driving-sample, and invalid-odometer.
- **Deletion enumeration** expressed over the ADR-0004 IndexedDB object-store layout: on confirm, deletion clears the vehicle's row in `vehicles` and enumerates and clears all `events`, `readings`, `reminders`, and any related singleton entries in `prefs` that reference that vehicle, plus updating `meta.seq`. The confirmation surface names those stores in user-readable terms before the user confirms.
- **Reminder-intent reconciliation on delete/replace** expressed as in-app due-state recomputation only (INV-17 amended) — no OS notification cancellation because none was scheduled.
- **Vehicle-context display** on every log/edit/reminder screen, persistent and non-color-only, to prevent recording against the wrong car.
- **Post-MVP appendix (non-blocking):** the tabbed-garage direction expressed as a **web navigation pattern** — one URL per vehicle (`/vehicles/:vehicle_id`), a horizontal tab strip that maps to LiveView `handle_params`, browser back/forward preserving the active vehicle, keyboard tab semantics per WAI-ARIA Authoring Practices, overflow menu, sort/filter, virtualization for 100-vehicle rendering, and archive/restore.

## Functional requirements

- **FR-1 (browser-MVP home/status):** The MVP home/status experience is specified for exactly zero or one active vehicle, rendered by a hosted LiveView (`StickerLive`) on Fly.io per INV-1 and INV-27. Its lifecycle actions are add, view, edit/replace, and permanently delete, each expressed as a `pushEvent` → hook → IndexedDB round trip per INV-24.2 with an explicit not-yet-committed state that visibly reverts on failed ack.
- **FR-2 (card contract):** The vehicle card defines these fields, each rendered from hydrated socket assigns and never persisted server-side: nickname; concise identity snapshot (year/make/model/trim as resolved against the server-queried catalog per INV-26, with the ADR-0003 support status shown honestly per INV-11); last recorded change date/mileage; estimated next date/mileage with confidence/source indicator per INV-15; in-app due status (`not_enough_data` / `upcoming` / `due` / `overdue`) per INV-21; **in-app reminder state** (see FR-4) — no OS notification state, because none exists (INV-17 amended); and the primary action for the current status.
- **FR-3 (browser-MVP states, superset of the pre-pivot list):** MVP states are specified for empty (verified zero vehicles), one-vehicle (ready), unavailable-recommendation, stale-driving-sample, invalid-odometer, data-migration (client-side IndexedDB `onupgradeneeded` per [DOS-M09-001](DOS-M09-001.md)) **and the four browser-specific states introduced by ADR-0004**: `:hydrating` (skeleton, never a false empty-garage flash per INV-24.3), `:storage_unavailable` (private-browsing or blocked storage per INV-24.6 — copy per [DOS-M09-004](DOS-M09-004.md) and INV-25), `:data_missing` (boot hint indicated prior data but hydration returned zero — likely browser-cleared, per INV-24.8/INV-25), and `:reconnecting` (LiveView disconnect: retain the last hydrated DOM, apply `phx-disconnected` styling, do not tear down to a skeleton, and re-run hydration on reconnect per INV-24.1).
- **FR-4 (replace and permanent-delete over IndexedDB, no OS notifications):** Replace and permanent-delete specify their effects on the user's local records and on in-app due-state recomputation. **Deletion enumerates exactly the ADR-0004 IndexedDB stores it will touch**: the vehicle's row in `vehicles`, every `events` record with that `vehicle_id`, every `readings` record with that `vehicle_id`, every `reminders` record with that `vehicle_id`, any related singleton entry in `prefs`, and the `meta.seq` update that accompanies the transaction. The confirmation surface names those stores in user-readable terms before the user confirms. Replace preserves history per [DOS-M02-004](DOS-M02-004.md) identity-edit/replace semantics and never silently remaps. **The pre-pivot FR-4 language that referenced "OS notifications" and `scheduled_notifications` is retired**: no `scheduled_notifications` store exists in the ADR-0004 layout, no OS notification is ever scheduled by the MVP (INV-17 amended), and delete/replace instead trigger an in-app due-state recomputation over the updated hydrated assigns.
- **FR-5 (post-MVP appendix — respecified as a web navigation pattern):** The non-blocking post-MVP appendix defines the multi-vehicle direction as a **web navigation pattern**, not a bare tab-bar control borrowed from a pre-pivot app shell. It specifies: one URL per vehicle (`/vehicles/:vehicle_id`) with `handle_params` selecting the active vehicle; a horizontal, scrollable, reorderable tab strip that behaves as a WAI-ARIA `tablist` for AT users and preserves reading order for keyboard users; browser back/forward preserving the active vehicle; an overflow menu at counts that overflow the strip; a searchable/filterable garage view at `/garage`; sort/filter that survives page refresh (URL-encoded); virtualization for the 100-vehicle rendering test; archive/restore semantics; and 5/20/100-vehicle states (visual density, performance budgets, and AT verification). This appendix is explicitly non-blocking and MUST NOT be implied by any MVP copy or control.
- **FR-6 (vehicle context display):** Every log/edit/reminder screen displays the vehicle context (nickname plus identity snapshot) in a persistent, non-color-only affordance, so the user cannot record against the wrong car. In MVP with one active vehicle this is always the active vehicle; the affordance is specified now so multi-vehicle presentation is a wiring change, not a redesign.
- **FR-7 (one-active-vehicle policy in the client store):** The one-active-vehicle limit is enforced by the browser-MVP UI over the IndexedDB `vehicles` store from [DOS-M09-001](DOS-M09-001.md): the store is multi-vehicle-safe (stable client-generated UUIDv4 keys per ADR-0004), the MVP UI exposes only one row, and adding a second vehicle in MVP requires the replace flow. The store shape MUST NOT be reshaped to encode "only one row" — INV-18 requires multi-vehicle-safe internals from day one. Server-side, the socket assigns per INV-24 hold at most the one active vehicle plus its lifecycle-related records; no server row of any kind exists (INV-23).
- **FR-8 (status is derived, not stored):** Due status is derived from the user's `events` and `readings` records plus the current server-resolved catalog schedule (queried impersonally per INV-26) and the versioned forecast policy from [DOS-M06-001](DOS-M06-001.md), computed on hydration and after every acknowledged mutation. It MUST NOT be stored as authoritative text in `vehicles`, `events`, `readings`, `reminders`, or `prefs`, and MUST NOT be computed inside the LiveView view function.
- **FR-9 (honest attention status, no invention):** Attention status communicates missing or low-confidence data honestly per INV-11 and INV-15 — the vocabulary term is `not_enough_data`, not a guessed due date, and the copy names what is missing (mileage samples, catalog support, driving profile). This preserves the pre-pivot FR-9 semantics under the amended constitution.
- **FR-10 (browser-specific storage-loss and reconnect behavior, new under ADR-0004):** The card surface honors the ADR-0004 storage contract: (a) on `:data_missing`, the copy explicitly says the browser storage appears to have been cleared and offers import per [DOS-M05-007](DOS-M05-007.md), and MUST NOT render as a fresh empty state (INV-24.8/INV-25); (b) on `:storage_unavailable`, the card surface is read-only for catalog exploration and disables mutation controls with a plain-language reason; (c) a reconnect during a pending mutation does not lose the mutation — the pending write is re-driven from `pending_writes` in assigns after re-hydration per ADR-0004 §"Deploys drop every WebSocket"; (d) a hydration deadline expiry (default 5 000 ms per ADR-0004) renders `:storage_unavailable`, not `:empty`.
- **FR-11 (impersonal catalog query for identity, INV-26):** The card's identity snapshot is resolved by an impersonal query to the server-side catalog layer per [DOS-M09-005](DOS-M09-005.md): the query carries only the impersonal selectors needed to resolve the configuration (year/make/model/engine choice) and MUST NOT carry a VIN, an odometer value, a note, or any stable client identifier, in path, query string, body, headers, or socket payload. The server MUST NOT be able to reconstruct a garage from its request stream (INV-26).
- **FR-12 (INV-5 / INV-25 language enforcement on lifecycle surfaces):** Delete, replace, reset, and every storage-state surface MUST NOT use the prohibited words "backup", "synced", "safe", "we'll remember", or "your account" (ADR-0004 §"Export and import"), and MUST include a reachable statement that records live in this browser only and that clearing browser data deletes them permanently. This binds the copy this card owns; the reusable copy strings live with [DOS-M02-003](DOS-M02-003.md) and [DOS-M09-004](DOS-M09-004.md).

## Technical implementation contract

### Components and ownership boundaries

The home/status view is `StickerLive`, a hosted Phoenix LiveView served on Fly.io per INV-1/INV-27. It composes the [DOS-M02-002](DOS-M02-002.md) responsive web components (`VehicleSummary`, `DueStatus`, `SourceBadge`, `ConfidenceBadge`, destructive confirmation, empty and storage-state panels) rendered from hydrated `socket.assigns`. Vehicle lifecycle is owned by `DigitalOilSticker.Garage` as a client-agnostic Elixir context per ADR-0004 decision §6 — it MUST NOT depend on `Phoenix.LiveView` or on the `LocalStore` protocol modules, and its unit tests use an in-memory storage double. Status derivation is owned by `Maintenance`/`Forecasting` per the same enforcement rule. The LiveView view function does **no** due arithmetic — it renders typed status values produced by domain contexts (INV-15 traceability).

The `phx-hook` `LocalStore` owns all IndexedDB access per ADR-0004 §"Storage layout" and §"Mount and hydration sequence" and is implemented in [DOS-M09-002](DOS-M09-002.md). This card does not re-implement the hook; it consumes it and specifies the surfaces the hook drives.

### Data and persistence

**Personal data is anonymous and client-only (INV-23).** The active-vehicle constraint is a UI-and-Garage-context policy enforced over the ADR-0004 IndexedDB layout — origin-scoped database `dos_local`, object stores `vehicles` (client-generated UUIDv4 keys, catalog reference keys, user overrides), `events` (oil-change and service events), `readings` (odometer check-ins), `reminders` (reminder intent/thresholds), `prefs` (units, time zone, display), and the `meta` singleton (`schema_version`, `seq`, timestamps, `persist_granted`).

Card data is derived at render time from: (a) the hydrated `vehicles` record for the active vehicle in socket assigns; (b) the latest `events` and `readings` records for that vehicle in socket assigns; (c) the server-resolved catalog schedule from the impersonal query layer per INV-26 / [DOS-M09-005](DOS-M09-005.md); (d) the current forecast policy output ([DOS-M06-001](DOS-M06-001.md), [DOS-M06-003](DOS-M06-003.md)); and (e) the `reminders` record's in-app due-state (INV-17 amended).

**Permanent deletion (RESCOPED — this replaces the pre-pivot line 68 enumeration):** on confirm, the hook opens one `readwrite` transaction over `vehicles`, `events`, `readings`, `reminders`, and `meta` (plus `prefs` when a per-vehicle preference exists), performs the compare-and-set on `meta.seq` per ADR-0004 §"Multi-tab consistency", deletes the vehicle row plus every child record whose `vehicle_id` matches, updates `meta.seq`, and commits. The affected stores are named to the user in the confirmation surface. The pre-pivot enumeration over `maintenance_plans`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `service_events`, `odometer_readings`, and `scheduled_notifications` is **retired**: none of those stores exist in the ADR-0004 layout, and `scheduled_notifications` in particular is doubly obsolete under INV-17 amended.

Replace preserves history per [DOS-M02-004](DOS-M02-004.md) identity-edit/replace semantics: the `vehicle_id` is preserved (never silently remapped) and history rows are retained; only the catalog reference and identity snapshot are updated.

### Interfaces and events

- **Lifecycle events**, all routed through the Garage context and emitted as domain-level events for downstream contexts to react to: `vehicle_saved`, `vehicle_replaced`, `vehicle_deleted`. These events are process-local; they never reach a server-side event store because no such store exists (INV-23).
- **Hydration events** (owned by [DOS-M09-003](DOS-M09-003.md), consumed here): `local_store:hydrate`, `local_store:put`, `local_store:ack`, `local_store:conflict`. The card renders `:hydrating` until the first hydrate arrives or the deadline expires; every mutation waits for the ack before rendering as saved.
- **In-app due-state reconciliation:** on `vehicle_saved` / `vehicle_replaced` / `vehicle_deleted` and on every acknowledged `events` / `readings` mutation, the derived due-state on the card is recomputed from assigns. There is no OS-notification handoff and no `DeviceCommandBroker` call from this MVP — the pre-pivot `DeviceCommandBroker` reference is retired for the MVP surface (it remains in the deferred set retained by ADR-0004 for a future client revival, which is out of scope for this card).
- **Primary-action routing** honors the [DOS-M02-001](DOS-M02-001.md) route table, which under the pivot expresses each route as a real shareable URL with browser back/forward semantics.

### Failure and recovery behavior

- **Pre-hydration and storage failures (new under ADR-0004):** `:hydrating` (skeleton for up to the hydration deadline), `:storage_unavailable` (INV-24.6 — mutations disabled with a plain reason, catalog exploration read-only), `:data_missing` (INV-24.8 / INV-25 — explicit browser-cleared copy and import offer, never a false empty state), `:reconnecting` (retain last DOM, `phx-disconnected` styling, re-hydrate on reconnect).
- **Domain failures:** unavailable-recommendation (catalog cannot support this vehicle — honest `unsupported` messaging per ADR-0003 support statuses and INV-11), stale-driving-sample and invalid-odometer (attention prompts to update data, coordinated with [DOS-M02-006](DOS-M02-006.md) and [DOS-M02-007](DOS-M02-007.md)), data-migration (IndexedDB `onupgradeneeded` running per [DOS-M09-001](DOS-M09-001.md) — read-only or progress state, no rollback).
- **Interrupted delete/replace:** the transaction is atomic in one `readwrite` IDB transaction (ADR-0004 §"Mutation round trip"). If the ack fails, the "Not saved to this browser" state renders per ADR-0004 with export offered; the record's assigns still reflect the pre-delete state until the retry commits.
- **Quota exhaustion on write** (INV-24.5): the failed-ack path renders a quota-specific message and offers export; the prior state is preserved. Silent write failure is a release blocker.

### Security and privacy

- **INV-22 hosted-transport:** the view is served over HTTPS/WSS with `check_origin` restricted to the production hostnames per ADR-0004 §"Security and privacy boundary for a hosted application". `Plug.SSL` with `rewrite_on: [:x_forwarded_proto, :x_forwarded_host, :x_forwarded_port]` and `force_ssl` are already set at the endpoint; this card assumes and does not re-specify them.
- **INV-23 no server-side personal record:** the card view function reads only `socket.assigns`; no `Repo.get`, `Repo.insert`, `Repo.update`, or `Repo.delete` call may reach personal data. The static enforcement check named in ADR-0004 §"Enforcement" (deployed Ecto repo list is `[CatalogRepo]`, read-only) is the release gate.
- **INV-26 impersonal catalog query:** every catalog resolution done to render the card carries only impersonal selectors. The socket payload for identity resolution MUST NOT include VIN, odometer, notes, nickname, or any stable client identifier.
- **INV-4 logging:** nickname, notes, VIN, odometer values, service dates, and the specific vehicle a session selected MUST NOT appear in any log line. Deletion confirmation copy MUST NOT be logged with vehicle-identifying values. The scripted-session log-scan test from ADR-0004 §"Enforcement" is the release gate.
- **INV-5 / INV-25 destructive-action honesty:** deletion is a permanent, explicitly confirmed destructive action naming exact IndexedDB stores; the copy MUST NOT use the prohibited words (INV-25 / ADR-0004 §"Export and import") and MUST include the reachable statement about browser-only storage.

### Accessibility and performance

- **INV-24.3 first paint:** the `:hydrating` state is a skeleton, distinct in DOM from `:empty`; the shell never flashes an empty-garage message during hydration. `aria-busy` is set on the shell region during hydration.
- **WCAG 2.2 AA (per [DOS-M02-002](DOS-M02-002.md), verified against browser AT):** status is understandable without color — text plus icon plus shape; the four due-status terms have distinct accessible announcements; the vehicle-context affordance on log/edit/reminder screens is announced by the region label.
- **Post-MVP appendix keyboard/AT (non-blocking):** the tab strip is a WAI-ARIA `tablist` with the arrow-key focus model, `aria-selected`, and roving tabindex; the overflow menu is keyboard-reachable; the 100-vehicle virtualized garage view remains navigable by keyboard.
- **Latency:** the card renders from hydrated assigns without a further round trip; the impersonal catalog resolution for identity is bounded by the [DOS-M09-005](DOS-M09-005.md) p95 budget. ## Risks, decisions, and open questions

- **Risk:** multi-vehicle ambition leaks into MVP acceptance. **Mitigation:** FR-5/AC-5 keep the appendix labeled and non-blocking; INV-18 is cited on the boundary; the post-MVP direction is now a web pattern (URLs and WAI-ARIA), which is closer to the platform and less tempting to bolt on prematurely.

- **Risk:** the destructive-delete surface leaks a vehicle identifier through logging when the confirmation is announced. **Mitigation:** INV-4 filter list plus the scripted-session log-scan test; deletion confirmation copy uses store names ("this vehicle's events, readings, and reminders in your browser") rather than repeating identifying values.
- **Risk:** a reconnect mid-delete leaves an ambiguous state (some records deleted, some not). **Mitigation:** the deletion is one IDB `readwrite` transaction (atomic); if the ack fails, the "Not saved to this browser" state renders per ADR-0004 and the prior assigns remain visible until retry.
- **Risk:** the multi-tab compare-and-set (ADR-0004 §"Multi-tab consistency") rejects a delete in one tab because another tab bumped `meta.seq`. **Mitigation:** FR-10 references the ADR-0004 conflict path (`local_store:conflict` → server re-hydrates and shows a visible "reloaded from this browser's newer data" notice). This is a specified state, not an error.
- **Open question:** whether "replace" is modeled as archive-then-add or in-place identity change is recorded as an explicit decision in [DOS-M02-004](DOS-M02-004.md) with its history/reminder consequences; this card renders whichever is decided.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

The home/status screen targets `StickerLive` composed from DOS-M02-002 components (`VehicleSummary`, `DueStatus`, `SourceBadge`, `ConfidenceBadge`, destructive confirmation, empty panels). Vehicle lifecycle is owned by `DigitalOilSticker.Garage`; status derivation by `Maintenance`/`Forecasting` per §7 boundaries. The card renders typed status/confidence values; no screen computes its own due arithmetic (§9: no screen may implement its own arithmetic).

#### Data and persistence

The active-vehicle constraint is a service/repository contract over the `vehicles` table (stable UUIDs, plural table names, archival-state fields retained) so the one-vehicle limit is a policy, not a schema shape. Card data derives from `vehicles` snapshots, latest `service_events`, `forecast_snapshots`/current forecast policy output, and `reminder_rules`/`scheduled_notifications` state. Permanent deletion enumerates the affected rows across `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, and `scheduled_notifications`; replace preserves history per DOS-M02-004 identity-edit/replace semantics and never silently remaps. *Post-pivot note: this enumeration is retired; ADR-0004 eliminated `UserRepo`, and the rescoped Data-and-persistence section above enumerates deletion over the IndexedDB stores `vehicles`, `events`, `readings`, `reminders`, and any related `prefs` entries.*

#### Interfaces and events

Lifecycle actions map to `Garage`/`Maintenance` operations emitting `vehicle_saved` and driving `forecast_changed`/`reminders_reconciled` where applicable; delete/replace flows must specify the reminder-intent update and OS-notification cancellation handoff (executed via the `Reminders` context and `DeviceCommandBroker`, per DOS-M02-008's reconciliation contract). The card's primary action routes per the DOS-M02-001 route table. *Post-pivot note: `DeviceCommandBroker` and the OS-notification cancellation handoff are retired for the MVP surface per INV-17 amended; they remain valid in the native-revival deferred set. Replace with the in-app due-state recomputation as specified in the rescoped card above.*

#### Failure and recovery behavior

Specified states include unavailable-recommendation (catalog cannot support this vehicle — honest unsupported/identity-only messaging per the §5 status vocabulary), stale-driving-sample and invalid-odometer (attention prompts to update data, coordinated with DOS-M02-006/007 handling), and data-migration (read-only or progress state during `UserRepo` migration per DOS-M02-003). Interrupted delete/replace must not leave partial state: the spec requires transactional semantics and defines what the user sees on retry.

#### Security and privacy

Deletion is a permanent, explicitly confirmed destructive action naming exact record categories; it is distinct from catalog repair (DOS-M02-003). No card content leaks to system surfaces beyond what DOS-M02-008 permits for notifications. Nickname and notes are user content, redacted from logs/fixtures per §7.

Card status must be understandable without color (text/icon/shape per DOS-M02-002); the status vocabulary (not enough data/upcoming/due/overdue) has distinct accessible announcements. The one-vehicle home renders entirely from local data within the accepted latency budgets.
