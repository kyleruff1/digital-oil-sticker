## Outcome

A complete record/edit/history flow captures an oil change with enough evidence for later estimates while clearly separating manufacturer guidance, oil-maker claims, filter fitment claims, and user-entered choices.

The deliverable specifies the oil-change event form (required and optional fields), recommendation/product selection display, validation rules, history list/detail, edit/delete consequences, and the fast repeat-change path — the UX contract for the product's primary local source record.

## Why this matters and what it unblocks

The oil-change event is the primary local source record. Loose fields or misleading "compatible" labels would corrupt forecasts and historical traceability. This issue unblocks maintenance domain rules, forms, history, and recommendation components.

It also operationalizes non-negotiable rules 4 and 5 in the recording UX: provenance is always visible, a brand name or viscosity alone never proves compatibility, and manual history is never relabeled as verified compatibility.

## Included

- Define required event fields: vehicle, service date, odometer value and unit. Define optional fields supported by sourced schema: oil brand/product, viscosity/specification, quantity if authoritative, filter brand/part, service provider/type, notes, and provenance/display snapshots.
- Support selecting from the locally available compatible/applicable cross-section and entering an unlisted product/filter as user-entered. Show why an item is listed and at what vehicle/configuration granularity.
- Display manufacturer interval guidance separately from oil-brand/product claims. Show normal/severe-service distinctions only when sourced; otherwise invite a user-defined interval without presenting it as manufacturer guidance.
- Define validation for future dates, negative/implausible mileage, unit changes, odometer decreases/rollover/replacement, duplicate events, and editing/deleting an event used by forecasts.
- Define history list/detail, chronological order, source snapshots, edit audit timestamp, and recalculation preview after edits/deletes. Preserve what was selected even if a later catalog removes the product.
- Define a fast repeat-change path that pre-fills non-volatile prior product choices but never pre-fills date or odometer as though measured.

## Functional requirements

- FR-1: Required event fields are vehicle, service date, odometer value and unit; optional fields supported by sourced schema are oil brand/product, viscosity/specification, quantity if authoritative, filter brand/part, service provider/type, notes, and provenance/display snapshots.
- FR-2: The user can select from the locally available compatible/applicable cross-section or enter an unlisted product/filter as user-entered; every listed item shows why it is listed and at what vehicle/configuration granularity.

- FR-4: Validation is specified for future dates, negative/implausible mileage, unit changes, odometer decreases/rollover/replacement, duplicate events, and editing/deleting an event used by forecasts.
- FR-5: History list/detail is specified with chronological order, source snapshots, edit audit timestamp, and a recalculation preview after edits/deletes; what was selected is preserved even if a later catalog removes the product.
- FR-6: The fast repeat-change path pre-fills non-volatile prior product choices but never pre-fills date or odometer as though measured.
- FR-7: Odometer is stored in a canonical integer representation with explicit display unit/conversion rules from DOS-M01-003; original user entry is recoverable where rounding matters.
- FR-8: Submission is one local transaction and is idempotent against accidental double taps.
- FR-9: A recommendation row always exposes provenance/confidence on demand, including the §6-required detail view content (provider/document, source version/revision, retrieved/verified date, market/condition, data-error report route).
- FR-10: Editing an old event triggers deterministic forecast/reminder reconciliation and never rewrites later event snapshots silently.
- FR-11: Manufacturer, oil-maker, filter-maker, and user-entered data are visually and verbally distinct in every state, and manual entries are never relabeled as verified compatibility.

## Technical implementation contract

### Components and ownership boundaries

The flow targets `OilChangeLive` (record/edit) and `RecommendationLive`/history views (per §7), composed from DOS-M02-002 components: form fields, date/mileage/unit inputs, `ProductPicker`, inline validation, `SourceBadge`/`ConfidenceBadge`, banners, and destructive confirmation. Event persistence and cycle semantics are owned by `DigitalOilSticker.Maintenance`; compatible/applicable cross-sections come from `Catalog` read queries; the UI consumes typed recommendation results (`verified`/`partial`/`conflict`/`unsupported`/`not_applicable`) and never infers compatibility client-side.

### Data and persistence

Events persist to `service_events` with the FR-1 field set, provenance mode (`catalog` or `manual`), timestamps and correction lineage; the service odometer also yields an `odometer_readings` row with source `service_event`. Odometer values use the canonical integer base unit with boundary conversion (FR-7). Oil/filter selections persist as snapshots (brand/product/viscosity, filter brand/part) so history stays readable after catalog/product retirement (§4.2 stable-key-plus-snapshot rule). Edits create correction lineage rather than destructive overwrites; deletes are specified with their forecast/reminder consequences and confirmation.

### Interfaces and events

Submission emits `service_event_recorded` (and `odometer_recorded` for the embedded reading); per §6 journey step 8, recording a new change closes the previous cycle, starts a new one, recomputes the forecast, and replaces obsolete notification requests atomically — the spec declares these downstream effects and hands their UX to DOS-M02-007/008. Edits/deletes trigger `forecast_changed`/`reminders_reconciled` reconciliation with a user-visible recalculation preview before commit (FR-5, FR-10). The product selector queries the compatible/applicable cross-section with `match_basis` exposure per §9.

### Failure and recovery behavior

Validation failures are inline, specific, and recoverable (per DOS-M02-002 inline-validation states); duplicate detection warns with an explicit proceed/cancel choice; odometer decrease/rollover/replacement paths route to the DOS-M02-007 sample-validity semantics instead of silently accepting or rejecting. Double-tap submission is idempotent (FR-8). Interrupted submission (process death) must not create partial event/reading pairs; the restoration behavior follows DOS-M02-001. Missing-recommendation states (unsupported/partial/conflict) show honest guidance without blocking manual recording.

### Security and privacy

Notes, provider names, products, and odometer values are user content: local-only, never in URLs or notification payloads, redacted from logs/fixtures per §7. No purchase, pricing, or affiliate integration exists (Excluded). The data-error report route on recommendation detail is a local/static-site route per the accepted architecture, not a telemetry channel.

### Accessibility and performance

Minimum required entry (vehicle context + date + odometer + unit) is completable quickly with one hand and offline; form inputs follow DOS-M02-002 keyboard-avoidance, target-size, and dynamic-type rules; validation errors move focus to a meaningful error summary. History lists follow virtualization guidance for long histories. All queries and submissions are local and bounded — no indefinite spinners.

## UX and content states

- Record flow: empty form (vehicle context visible per DOS-M02-005), in-progress, validation-error, duplicate-warning, unlisted-product entry, missing-recommendation (unsupported/partial/conflict per §9 vocabulary), success with forecast/reminder update summary.
- Repeat-change path: pre-filled non-volatile product choices, empty date/odometer with explicit entry required.
- History: chronological list, event detail with source snapshots and edit audit timestamp, retired-product display (snapshot preserved with honest "no longer listed" framing), post-identity-edit readability.
- Edit/delete: recalculation preview, confirmation, and outcome states; correction lineage visible as an audit trail.
- Recommendation display: listed-item rationale ("why is this listed", configuration granularity), provenance/confidence on demand, manufacturer guidance vs. product claims vs. user entries visually and verbally distinct; severe/normal distinction only when sourced; user-defined interval invitation when unsourced.
- Terminology per §6: "Meets the recorded requirements", "Source unavailable", "Exact configuration not verified"; never "manufacturer approved" without documented approval.

## Risks, decisions, and open questions

- Risk: "compatible" language overstates what sources prove. Mitigation: FR-9/FR-11 bind display to §9 resolver results and §6 terminology; conflict states show no automatic product recommendation.
- Risk: validation strictness blocks honest data entry (e.g., real odometer replacement). Mitigation: FR-4 enumerates the exceptional paths with quarantine/confirm semantics instead of hard rejection, coordinated with DOS-M02-007 sample validity.
- Risk: edits silently corrupt forecast history. Mitigation: FR-10 correction lineage plus mandatory recalculation preview.
- Open question: "quantity if authoritative" — the spec must define when quantity is shown/captured based on licensed capacity data availability (`oil_requirements` capacity fields), never as a guess.
- Decision to record: duplicate-event detection window and criteria; the exact user-defined-interval capture flow when guidance is unsourced (coordinated with DOS-M02-007).
