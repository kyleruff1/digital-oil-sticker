## Outcome

A user-understandable driving profile and forecast contract translate manually entered usage samples into an estimated date while preserving the authoritative mileage/time thresholds and exposing uncertainty.

The deliverable specifies the two usage-input modes, the versioned calculation policy's UX contract, sample validity and edge-case handling, confidence states, plain-language explanation content, and the reconciliation triggers that keep status and reminders consistent with the forecast.

## Why this matters and what it unblocks

The app cannot read the car. Forecasting from sparse, self-reported mileage is inherently uncertain, and an opaque average could create false confidence. This issue unblocks forecast algorithms, status cards, sample-entry UI, and QA fixtures.

It is the UX half of the §9 forecast rules: it fixes what users see, how estimates are explained, and how uncertainty is communicated, so the M06 algorithm work implements a frozen contract instead of inventing presentation.

## Included

- Define two input modes: a simple expected distance per week/month supplied by the user, and dated odometer samples that allow the app to derive usage. Define how the user chooses/changes mode.
- Specify a versioned calculation policy: derive distance since the last change; determine remaining distance to the applicable mileage threshold; estimate usage rate from valid intervals; combine mileage-estimated date with a calendar-time threshold by taking the earlier applicable due condition; preserve both next mileage and estimated date.
- Define sample validity, minimum sample count/span, same-day entries, odometer decrease/replacement, long gaps, outliers, zero driving, unit conversion, timezone/date boundaries, and policy upgrades. Choose and document an averaging/robustness method during implementation; UX must not imply precision beyond the data.
- Define confidence states: no recommendation, no baseline oil change, insufficient usage data, user-declared usage, sample-derived low/medium/higher confidence, stale samples, due, and overdue.
- Explain the estimate in plain language with the last-change baseline, interval source, usage basis/sample window, calculation date, and "update mileage" action. Let the user set a conservative manual interval where sourced guidance is absent.
- Define status changes and reminder reconciliation after new samples, event edits, interval/source changes, time-zone changes, and policy-version changes.

## Excluded

- Machine learning, GPS/background mileage tracking, OBD/telematics, prediction from population behavior, driving-style diagnostics, engine-oil-life-system emulation, or guaranteed service dates.
- Choosing the exact averaging/robustness weights and confidence thresholds — the implementation issue (M06) chooses and freezes them; this spec defines the UX contract they must satisfy.
- Implementing forecast code, sample-entry screens, or reminder scheduling (M05/M06); reminder setup/permission UX (DOS-M02-008).

## Functional requirements

- FR-1: Two input modes are specified — user-supplied expected distance per week/month, and dated odometer samples from which usage is derived — including how the user chooses and changes mode and what happens to existing data on a mode change.
- FR-2: The versioned calculation policy's UX contract covers: distance since last change; remaining distance to the applicable mileage threshold; usage rate from valid intervals; combining the mileage-estimated date with the calendar-time threshold by taking the earlier applicable due condition; and preserving both next mileage and estimated date as separately inspectable values.
- FR-3: Sample handling is specified for validity, minimum sample count/span, same-day entries, odometer decrease/replacement, long gaps, outliers, zero driving, unit conversion, timezone/date boundaries, and policy upgrades; the averaging/robustness method is chosen and documented during implementation, and the UX never implies precision beyond the data.
- FR-4: Confidence states are defined: no recommendation, no baseline oil change, insufficient usage data, user-declared usage, sample-derived low/medium/higher confidence, stale samples, due, and overdue — each with distinct, actionable copy.
- FR-5: The estimate explanation shows, in plain language: the last-change baseline, interval source, usage basis/sample window, calculation date, and an "update mileage" action.
- FR-6: Where sourced guidance is absent, the user may set a conservative manual interval that is never presented as manufacturer guidance.
- FR-7: Status changes and reminder reconciliation are specified after new samples, event edits, interval/source changes, time-zone changes, and policy-version changes.
- FR-8: Forecasts are pure deterministic projections of versioned policy plus explicit local records, clock, timezone, and units; raw samples are retained and derived rates/dates can be recomputed.
- FR-9: The UI shows sensible date granularity (for example, a range or "around" language when uncertainty is high) and never claims the car's current mileage.
- FR-10: Calendar threshold and mileage threshold remain separately inspectable; unknown input yields "not enough information," not a fabricated default.
- FR-11: The earlier-threshold-wins rule (§3 rule 6) is visible in the UX: the effective due date is the earliest applicable condition, and no state may present a later date than a known sourced threshold; a sourced oil-life-monitor rule adds the §9-required prominent monitor instruction.

## Technical implementation contract

### Components and ownership boundaries

The flow targets `MileageLive` (sample entry/usage profile) and the status/explanation surfaces on `StickerLive` per DOS-M02-005, composed from DOS-M02-002 components (`DueStatus`, `ConfidenceBadge`, date/mileage/unit inputs, banners). All computation is owned by `DigitalOilSticker.Forecasting` (deterministic pure functions per §7); `Clock` injects date/time-zone so no screen reads wall-clock directly; no screen may implement its own arithmetic (§9).

### Data and persistence

Inputs: `usage_profiles` (baseline distance/week, unit, severe-use answers, selected condition, effective timestamps — answers that selected the condition are preserved), `odometer_readings` (validity/supersession fields; rejected/quarantined readings are never silently deleted per §9), the active cycle's `service_events` baseline, and the plan's sourced thresholds. Outputs: `forecast_snapshots` rows (algorithm version, input hash, computation time, effective rate, due odometer, projected/calendar/effective dates, confidence code, reason code) as explainability/audit records, not the only source of truth. Mileage persists in integer base units; time uses UTC instants plus the persisted IANA time zone.

### Interfaces and events

New samples emit `odometer_recorded`; recomputation emits `forecast_changed` and drives `reminders_reconciled` (UX handoff to DOS-M02-008). The spec enumerates the §9 recompute triggers as UX-visible refresh points: vehicle/plan/service/reading/unit/time-zone/catalog changes and app foreground. The explanation surface reads the persisted snapshot (algorithm version, inputs, reason code) so every displayed result is traceable.

### Failure and recovery behavior

Invalid samples (negative distance, duplicate-time contradictions, implausible values outside the approved threshold, superseded readings) are rejected or quarantined with explanatory UX — never silently deleted, never silently accepted. Zero/unknown rate yields an unknown mileage date, not infinity; past-due odometer yields overdue-now (§9). Policy-version upgrades trigger recompute with a visible policy-version change note. Stale samples degrade confidence and surface an "update mileage" prompt rather than a stale date presented as fresh.

### Security and privacy

Odometer values, usage answers, and derived rates are local user data: never in URLs or notification payloads beyond what DOS-M02-008 permits, redacted from logs/fixtures per §7. No GPS, background tracking, or telemetry exists (Excluded). Forecast explanations expose only the user's own inputs and cited sources.

### Accessibility and performance

Confidence and due states follow the DOS-M02-002 non-color-only rules with distinct accessible announcements; explanation content reads coherently via screen reader; sample entry follows form accessibility rules. Recomputation is synchronous/on a supervised foreground task after mutations and at app foreground (§7 — no perpetual background process); the UX must define what the user sees during recompute (bounded, no indefinite spinner).

## UX and content states

- Input-mode states: no usage data, user-declared baseline mode, sample-derived mode, mode-change confirmation.
- Confidence/status states (FR-4): no recommendation, no baseline oil change, insufficient usage data, user-declared usage, sample-derived low/medium/higher confidence, stale samples, due, overdue — each with distinct, actionable copy and an unambiguous next action.
- Explanation surface: last-change baseline, interval source, usage basis/sample window, calculation date, "update mileage" action; date granularity language ("around", ranges) when uncertainty is high.
- Edge-case states: odometer decrease/replacement resolution, outlier quarantine notice, zero-driving, long-gap staleness, timezone/DST boundary notes, policy-upgrade recompute note, missing-interval manual-interval invitation (clearly user-defined).
- Oil-life-monitor state: prominent instruction to follow the vehicle indicator when a sourced OLM rule applies; estimates labeled as estimates (§3 rule 7).
- Terminology per §6: "Estimated due date" with confidence label; calendar vs. mileage interval always separately inspectable.

## Risks, decisions, and open questions

- Risk: false precision — a single confident date from sparse data. Mitigation: FR-9 granularity/"around" language, FR-4 confidence states, AC-6.
- Risk: UX contradicts the frozen §9 math (e.g., inventing a default rate). Mitigation: FR-10 "not enough information" rule; spec review against §9 line by line.
- Risk: reconciliation gaps leave stale reminders after edits. Mitigation: FR-7 enumerates every trigger; AC-4 verifies them.
- Open question: exact minimum sample count/span values and confidence thresholds are deliberately deferred to M06 (which freezes weights/half-life/thresholds with tests); this spec must state the constraint envelope, not the numbers.
- Decision to record: how a mode change (declared ↔ sample-derived) treats existing samples/baseline (retain and blend per §9 vs. explicit user choice), documented as part of FR-1.
