## Outcome
Every permitted upstream response or vendor delivery used in a catalog can be reproduced and audited without committing licensed payloads to Git.

## Why this matters and what it unblocks
Separating acquisition from transformation makes retries safe, supports source audits, permits deterministic rebuilds, and prevents upstream changes from silently changing a catalog. This landing zone and ledger are the substrate every source adapter writes into: it blocks the vPIC client (DOS-M03-004) and the gated provider adapters (DOS-M03-007, DOS-M03-008, DOS-M03-009). It is also the mechanism by which the project can prove, per the rights matrix, exactly what was acquired, when, under which license version, and with which checksum.

## Context and source of truth
- Master prompt section 4.4: the reproducible human-reviewed extraction queue guidance (capture document URL, revision, market, applicability, locator, extracted value, reviewer, and checksum; store only what the rights matrix permits) and the rule that raw acquisitions respect publisher terms.
- Master prompt section 8: the `data_sources` table baseline (SHA-256, retrieved/effective/verified timestamps, license reference) that ledger data ultimately feeds, and the catalog builder's requirement for deterministic artifacts.
- Section 11.2 "Research-backed source policy (binding on both milestones)": license-respecting acquisition, no scraping without authorization, and per-source terms evidence.
- DOS-M03-001's `config/data_sources.yml` contract: `source_key`, `status`, `retain_raw`, `license_version`, retention/termination duties that this issue's retention/pruning behavior must honor.
- Master prompt section 7 security constraints: secrets never in logs or fixtures; redaction rules for VIN and personal data.
- The required dependency order for GitHub Projects: "After vocabulary approval, implement DOS-M03-003."

## Included
- Define directories/object keys by `source_key/source_version/retrieved_date/content_sha256` with an immutable raw object and a small checked-in sanitized fixture.
- Write an ingest ledger entry before transformation: request/delivery identity, HTTP status, response headers permitted by policy, checksum, byte size, MIME type, retrieval time, tool/git SHA, source license version, and parent object for archives.
- Verify archive integrity and defend against zip-slip, decompression bombs, invalid encodings, duplicate filenames, unexpectedly large records, and schema drift.
- Redact query secrets, authorization headers, cookies, VINs, and personal data. Raw vPIC catalog requests must not contain end-user VINs.
- Define retention/pruning behavior per the rights matrix. A deletion routine produces a tombstone/audit record, never a false claim that the build remains reproducible after a contract-required deletion.

## Excluded
- Final catalog packaging.
- Storing end-user data.
- Using Git LFS as an assumed license-compliant distribution mechanism.

## Preconditions
- DOS-M03-001 approved: `config/data_sources.yml` exists so every landing-zone write can resolve a `source_key`, `license_version`, and `retain_raw`/retention class.
- DOS-M03-002 approved: the `_provenance` contract (including `raw_object_sha256` and `transform_version`) is frozen so receipts link to normalized outputs deterministically.
- Storage location for immutable raw objects (outside Git) selected with access control appropriate to licensed content.

## Functional requirements
- FR-1: Raw objects are stored immutably under keys of the form `source_key/source_version/retrieved_date/content_sha256`; an object, once completed, is never modified in place.
- FR-2: Each source ships a small checked-in sanitized fixture that stands in for the raw object in tests; licensed raw payloads are never committed to Git.
- FR-3: An ingest ledger entry (`ingest_receipt.json`) is written before any transformation, with fields exactly: `receipt_version`, `ingest_run_id`, `source_key`, `source_version`, `requested_at`, `completed_at`, `request_fingerprint`, `http_status`, `retry_count`, `content_type`, `content_length`, `raw_sha256`, `archive_members[]`, `tool_version`, `license_version`, `retention_class`, `redactions[]`.
- FR-4: The request fingerprint hashes canonical method, endpoint path, and non-secret parameters; it must not include credentials.
- FR-5: Archive handling verifies integrity and rejects zip-slip path traversal, decompression bombs, invalid encodings, duplicate filenames, unexpectedly large records, and schema drift, quarantining the offending object with a reason.
- FR-6: Redaction removes query secrets, authorization headers, cookies, VINs, and personal data from stored receipts, headers, and logs; raw vPIC catalog requests must not contain end-user VINs; every applied redaction is listed in `redactions[]`.
- FR-7: Interrupted downloads resume or restart safely; a partial object is never marked complete.
- FR-8: Identical acquisitions deduplicate by checksum while retaining separate receipts (one object, many receipts).
- FR-9: Re-running transform against the same raw SHA and transform version must produce the same normalized SHA.
- FR-10: Retention/pruning follows each source's rights-matrix retention class; a contract-required deletion produces a tombstone/audit record and downgrades reproducibility claims for affected builds instead of falsifying them.
- FR-11: A developer can rebuild normalized fixture output using only the receipt, the approved raw fixture, and a documented command.

## Technical implementation contract
### Components and ownership boundaries
- Landing-zone storage layout and immutability rules: owned by the data-pipeline boundary; adapters get write access only through the acquisition library, never ad-hoc file writes.
- Ingest ledger writer/reader library: single shared implementation producing `ingest_receipt.json`; adapters must not hand-roll receipts.
- Archive verifier/unpacker: shared component enforcing FR-5 defenses before any member is exposed to a transform.
- Retention/tombstone routine: owned by the pipeline; executes rights-matrix retention classes and emits audit records.
### Data and persistence
- Immutable raw object store (filesystem/object storage outside Git) keyed `source_key/source_version/retrieved_date/content_sha256`; access-controlled because contents may be licensed.
- Receipts stored alongside objects and indexed by `ingest_run_id` and `raw_sha256`; receipts are retained even when their raw object is tombstoned.
- Sanitized fixtures live in the repository per source, small and license-clean.
### Interfaces and events
- Write path: adapter → acquisition library → (raw object + receipt); the receipt is the adapter's only proof of acquisition and the transform stage's only entry ticket.
- Read path: transform resolves `raw_sha256` from a receipt; the pair (raw SHA, `transform_version`) is the deterministic input identity for FR-9.
- Ledger summaries feed the DOS-M03-005 run manifest and DOS-M03-010 provenance report.
### Failure and recovery behavior
- Download failure or interruption leaves either no object or an explicitly incomplete staging entry; completion is an atomic rename/commit after checksum verification.
- Verification failures (corrupt archive, oversize, MIME mismatch, encoding, traversal, duplicates, schema drift) quarantine the object with a machine-readable reason; nothing quarantined is transformable.
- Deduplication on retry: an object whose `content_sha256` already exists gains a new receipt, not a duplicate object.
- Contract-required deletion: tombstone + audit record; subsequent rebuild attempts referencing the deleted object fail with an honest "raw object deleted per retention class" error.
### Security and privacy
- Secrets (query secrets, authorization headers, cookies) are stripped before persistence; the request fingerprint excludes credentials by construction (FR-4).
- VINs and personal data are redacted from receipts and logs; raw vPIC catalog requests must not contain end-user VINs at all.
- Licensed raw objects are Git-ignored; production logs contain no secrets or full payloads; the raw store is access-controlled per rights-matrix build/backup retention terms.
### Accessibility and performance
N/A — build-side pipeline with no UI. Performance note: checksum-based dedupe and resumable downloads keep repeated acquisition runs cheap and courteous to upstream publishers.
### Data change specifics
- Source/version/license: every landed object is bound to a `source_key`, `source_version`, and `license_version` resolved from `config/data_sources.yml` at acquisition time; no landing without an approved or evaluation-permitted status per DOS-M03-001.
- Mapping: none at this stage by design — the landing zone stores upstream bytes verbatim; transformation happens downstream against the DOS-M03-002 schemas.
- Stable keys: object identity is `content_sha256`; acquisition identity is `ingest_run_id` + `request_fingerprint`; archives record `archive_members[]` with the parent object.
- Constraints/indexes: uniqueness on `content_sha256` per source path; receipts indexed by `ingest_run_id` and `raw_sha256`; completed objects immutable.
- Idempotency: re-acquisition of identical content deduplicates by checksum (FR-8); re-transform of the same raw SHA + transform version reproduces the same normalized SHA (FR-9); interrupted runs resume without duplicates (FR-7).
- Rejected-row policy: verification failures quarantine whole objects/members with reasons; quarantine is reported, never silently dropped.
- Checksums: SHA-256 for every object (`raw_sha256`) and archive member accounting; checksums appear in receipts and downstream `_provenance.raw_object_sha256`.
- Coverage report: ledger completeness summary per acquisition run (objects landed, deduplicated, quarantined, tombstoned) feeding DOS-M03-005/010 reports.
- Fixture strategy: per-source small sanitized fixtures checked into Git; fixtures are the only raw stand-ins usable in CI.
- Update cadence: event-driven per acquisition run; no scheduled crawling; cadence governed by each source's rights-matrix terms.
- Rollback/recovery: immutability plus receipts make any prior catalog rebuild auditable; tombstones document contract-required deletions and their reproducibility impact.

## Test plan
### Automated
- Integration tests: interrupted-download resume/restart (kill mid-transfer, verify no completed partial object); duplicate-acquisition dedupe with two receipts; atomic completion rename.
- Adversarial fixtures: zip-slip path traversal, decompression bomb/oversized archive, corrupt archive, invalid encoding, duplicate filenames, unexpected MIME type, schema drift — each rejected/quarantined with a reason (AC-3).
- Redaction tests: seeded secrets, auth headers, cookies, VIN-like strings verified absent from stored receipts and logs; `redactions[]` populated.
- Determinism test: transform of the same raw SHA + transform version twice yields identical normalized SHA (FR-9).
- Repo hygiene check: Git ignore rules block licensed raw object paths; secret scanner over receipts and logs.
- Retention dry-run: tombstone creation, audit record content, and honest rebuild failure for a deleted object.
### Manual/device matrix
- Developer walkthrough of AC-5: rebuild normalized fixture output from receipt + approved raw fixture + documented command only, on a machine without access to the live raw store.
- Review of a sample receipt and retention dry-run output by the data owner for policy conformance.
- No device work: N/A — build-side pipeline.

## Rollout and rollback
Rollout is adoption by adapters: once DOS-M03-004 lands, all acquisition flows through this library; direct writes are forbidden by review. Layout or receipt-schema changes bump `receipt_version` with a documented migration for existing receipts. Rollback of the component is reverting to a prior version; stored objects are unaffected because they are immutable. Contract-required deletions are governed by the retention/tombstone routine, never manual deletion.

## Risks, decisions, and open questions
- Risk: a licensed payload accidentally committed to Git; mitigated by ignore rules, secret/paylod scanning, and small sanitized fixtures as the only in-repo artifacts.
- Risk: storage/access control for licensed raw objects mis-scoped; the rights matrix's build/backup retention terms define who may hold raw copies — access is reviewed against it.
- Risk: over-aggressive redaction destroying audit value; `redactions[]` records what was removed so audits know the shape of what is missing.
- Decision: Git LFS is explicitly not assumed to be a license-compliant distribution mechanism (Excluded) — raw objects live outside Git entirely.
- Open question: physical storage backend (local encrypted volume vs. access-controlled object storage) — choose during implementation within the rights-matrix constraints; the key layout and receipt contract are backend-independent.
