## Outcome
An Elixir vPIC client acquires only approved catalog endpoints with validation, caching, bounded retries, and observable traffic behavior.

## Why this matters and what it unblocks
NHTSA applies automated traffic control without publishing a numeric quota. A centralized client prevents accidental request storms and isolates upstream schema changes from the pipeline. It is the single HTTP boundary for the identity-corpus acquisition (DOS-M03-005) and the guardrail that keeps the project a courteous consumer of the official government API, consistent with the green-lane treatment of vPIC in the rights strategy.

## Context and source of truth
- Master prompt section 4.4: vPIC is the vehicle-identity spine; it supplies manufacturer-reported identity, year/make/model endpoints, VIN decoding, and vehicle variables; missing values mean unknown; the standalone downloads are limited to VIN-decoding functionality.
- Section 11.2 "Research-backed source policy" (verified 2026-07-31): NHTSA describes vPIC as manufacturer-reported data from 49 CFR Part 565 submissions; automated traffic rate control is applied with no published numeric request quota; absent decoded values mean NHTSA has no data for that variable and must not be read as a negative assertion; the API supports a maximum of 50 VINs in the batch VIN-decode operation; the standalone databases are VIN-decode-only.
- Research-anchor URLs: [vPIC API](https://vpic.nhtsa.dot.gov/api/), [vPIC downloads](https://vpic.nhtsa.dot.gov/Downloads), [vPIC FAQ](https://vpic.nhtsa.dot.gov/api/home/index/faq), [vPIC release notes](https://vpic.nhtsa.dot.gov/api/Home/Index/ReleaseNotes).
- DOS-M03-002: normalized-record and `_provenance` contract; `not_provided` semantics.
- DOS-M03-003: landing zone/ingest receipts that every client acquisition must write.

## Included
- Implement endpoints required by the plan, initially `GetMakesForVehicleType`, `GetVehicleTypesForMakeId`, and `GetModelsForMakeIdYear`; use numeric make IDs after discovery to avoid partial-name ambiguity.
- Support official JSON responses and keep response decoding isolated so an official CSV endpoint can be evaluated later. The vPIC standalone database is excluded because NHTSA limits it to VIN decoding. Validate `Count`, `Message`, `SearchCriteria`, and `Results` rather than assuming HTTP 200 means usable data.
- One global configurable concurrency limiter with conservative default `1`, configurable minimum request spacing (default 1 request/second until NHTSA guidance or measured approval says otherwise), connect/read timeouts, and a descriptive User-Agent/contact.
- Retry only transient network errors, 408, 429, and 5xx with capped exponential backoff + full jitter; honor `Retry-After`; default maximum 5 attempts and maximum 60-second delay. Do not retry semantic 4xx or schema errors.
- Persistent response cache keyed by request fingerprint, positive and bounded negative caching, and a `--refresh` operation. Resume checkpoints must make a stopped run idempotent.
- Capture metrics: requests, cache hits, latency, retry reasons, status distribution, validation failures, bytes, and last-success time. Do not emit payloads at normal log level.
- Contract fixtures include null/empty fields, renamed display values with stable numeric IDs, non-success `Message`, malformed JSON, HTML error body, 429 with/without `Retry-After`, 5xx, timeout, and duplicate results.

## Excluded
- End-user/live VIN lookup.
- More than the official maximum of 50 VINs in a batch.
- Bypassing traffic controls.
- Assuming a numeric NHTSA quota that the publisher has not stated.

## Preconditions
- DOS-M03-002 approved (normalized-record schemas, `_provenance` contract, `not_provided` semantics).
- DOS-M03-003 available (landing zone and `ingest_receipt.json` writer) so every acquisition produces a receipt.
- vPIC recorded in the rights matrix as a green-lane government source with its terms evidence captured (DOS-M03-001 row exists; vPIC itself is not commercially gated).

## Functional requirements
- FR-1: The client implements `GetMakesForVehicleType`, `GetVehicleTypesForMakeId`, and `GetModelsForMakeIdYear`, addressing makes by numeric make ID after discovery to avoid partial-name ambiguity; adding endpoints requires a plan reference, not ad-hoc calls.
- FR-2: Response decoding is an isolated module supporting official JSON now and structured so an official CSV endpoint can be evaluated later without touching call sites; the vPIC standalone database is excluded as VIN-decode-only.
- FR-3: Envelope validation checks `Count`, `Message`, `SearchCriteria`, and `Results`; HTTP 200 with a non-success `Message` or inconsistent envelope is a typed semantic failure, not usable data.
- FR-4: A single global concurrency limiter (default `1`) and configurable minimum request spacing (default 1 request/second until NHTSA guidance or measured approval says otherwise) govern all traffic, with connect/read timeouts and a descriptive User-Agent including a project contact.
- FR-5: Retries apply only to transient network errors, 408, 429, and 5xx, using capped exponential backoff plus full jitter, honoring `Retry-After`, with default maximum 5 attempts and maximum 60-second delay; semantic 4xx and schema errors are never retried.
- FR-6: A persistent response cache is keyed by request fingerprint with positive and bounded negative caching and an explicit `--refresh` operation; resume checkpoints make a stopped run idempotent.
- FR-7: The client returns `{:ok, %VpicEnvelope{results: [...], receipt: ...}}` or typed errors `:rate_limited`, `:transport`, `:upstream_status`, `:schema`, `:semantic`, `:exhausted`.
- FR-8: The adapter records NHTSA integer IDs as source IDs and preserves original source spelling separately from canonical display spelling.
- FR-9: A result with a missing value is normalized to `not_provided`; it is never interpreted as `false`.
- FR-10: Metrics capture requests, cache hits, latency, retry reasons, status distribution, validation failures, bytes, and last-success time; payloads are not emitted at normal log level.
- FR-11: Every completed acquisition writes an ingest receipt through the DOS-M03-003 ledger; no catalog code calls `Req`/HTTP directly outside the client boundary.

## Technical implementation contract
### Components and ownership boundaries
- `Vpic.Client` (naming per project conventions): the only module allowed to perform vPIC HTTP; owns limiter, spacing, retry, timeout, User-Agent.
- `Vpic.Decoder`: isolated envelope/result decoding (JSON now; CSV evaluable later) and validation.
- `Vpic.Cache`: persistent fingerprint-keyed cache with positive/bounded-negative entries, `--refresh`, and resume checkpoints.
- `Vpic.Telemetry`: metrics emission per FR-10.
- Boundary rule: build-side pipeline only; nothing in the shipped mobile app calls vPIC (offline-from-first-launch rule); no catalog code outside this client touches `Req`/HTTP.
### Data and persistence
- Cache entries and resume checkpoints persist across runs, keyed by the DOS-M03-003 request fingerprint (canonical method, endpoint path, non-secret parameters).
- Raw responses land in the DOS-M03-003 immutable store with receipts; normalized outputs carry `_provenance` with `raw_object_sha256`.
- Source IDs are NHTSA integers; original source spelling is preserved separately from canonical display spelling (feeds `makes`/`models` provider-identity fields in section 8).
### Interfaces and events
- Public API returns `{:ok, %VpicEnvelope{results: [...], receipt: ...}}` or typed errors `:rate_limited`, `:transport`, `:upstream_status`, `:schema`, `:semantic`, `:exhausted`; callers (DOS-M03-005) branch on types, never on raw HTTP details.
- Telemetry events for each request outcome; run summaries aggregate into the DOS-M03-005 run manifest.
- Configuration (concurrency, spacing, timeouts, retry caps, cache location, refresh) is explicit and testable; defaults are the conservative values in FR-4/FR-5.
### Failure and recovery behavior
- Transient failures retry within FR-5 caps; exhaustion returns `:exhausted` with the retry history in the receipt.
- `Retry-After` is honored verbatim when present; 429 without `Retry-After` uses backoff + full jitter.
- Semantic failures (`Message` non-success, malformed JSON, HTML error body, schema mismatch) fail fast with redacted diagnostics and are never retried or cached as positive results.
- A stopped/killed run resumes from checkpoints without duplicate upstream requests or duplicate output (idempotency per FR-6).
### Security and privacy
- No end-user VINs in any request (build-side catalog traversal only; end-user/live VIN lookup is excluded).
- No credentials are required by vPIC; if any configuration secret exists it is referenced by environment-variable name only and excluded from fingerprints, receipts, and logs.
- Payloads are not logged at normal level; diagnostics are redacted.
### Accessibility and performance
N/A for accessibility — build-side client with no UI. Performance/courtesy: the limiter and spacing defaults (concurrency `1`, 1 request/second) are deliberately conservative because NHTSA publishes no numeric quota; the cache and resume checkpoints minimize repeated upstream traffic (warm reruns make zero upstream requests, verified in DOS-M03-005).

## Rollout and rollback
The client is a build-side library versioned with the pipeline; rollout is adoption by DOS-M03-005. Configuration changes to spacing/concurrency require recorded justification (NHTSA guidance or measured approval) — the conservative defaults are the fallback. Rollback is reverting the library version; the cache format carries a version so an incompatible change invalidates cleanly rather than corrupting.

## Dependency rationale
Depends on DOS-M03-002 (normalized output and `_provenance` semantics, including `not_provided`) and DOS-M03-003 (landing zone/receipts that make acquisitions auditable and reproducible). Blocks DOS-M03-005, which drives this client across the full rolling 30-year enumeration and must not start without the courtesy, caching, and typed-error guarantees proven here.

## Risks, decisions, and open questions
- Risk: NHTSA throttles or changes envelope shape without notice; mitigated by typed `:rate_limited`/`:schema` failures, loud contract-fixture breakage, and the isolated decoder.
- Risk: over-eager retry amplifying load during upstream incidents; mitigated by retry whitelist, caps (5 attempts, 60-second max delay), full jitter, and `Retry-After` honoring.
- Decision: conservative defaults (concurrency `1`, 1 request/second) stand until NHTSA guidance or measured approval says otherwise; any relaxation is a recorded configuration change.
- Decision: the standalone database is excluded for enumeration per NHTSA's own scope statement (VIN-decode-only).
- Open question: whether an official CSV endpoint is worth adopting later — decoder isolation keeps this a cheap future evaluation, not a rewrite.
