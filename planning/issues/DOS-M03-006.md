## Outcome
vPIC identity rows, approved FuelEconomy.gov enrichment rows, and licensed-provider vehicle identities resolve to stable catalog configurations without unsafe fuzzy joins.

## Why this matters and what it unblocks
OEM schedules and filter applications frequently use provider/ACES vehicle IDs and configuration detail beyond a vPIC year/make/model row. This issue makes those joins reviewable and prevents a recommendation for one engine/trim being applied to another. It is the safety boundary that lets DOS-M03-007/008/009 records reach publication only through exact or explicitly reviewed crosswalks, and it blocks DOS-M03-010 and DOS-M04-002 finalization.

## Context and source of truth
- Master prompt section 8: `vehicle_configurations` (stable `configuration_key`; year, make/model IDs, trim/series/body/drive/fuel/electrification/engine fields when known; provider namespace/key; completeness code; "Unknown is nullable, not false") and `aliases` (unique alias within entity type, indexed for lookup).
- Master prompt section 4.4 and section 11.2 source policy: absent vPIC values mean unknown, never a negative assertion; EPA/DOE data is enrichment/QA, never authority for oil schedules or fitment; VCdb supplies reference identities, not applications.
- DOS-M03-002: stable-ID rules (UUIDv5/namespaced digest; no IDs from row order, rowid, display spelling, or catalog version), `crosswalk_status` enum (`exact`, `qualified`, `ambiguous`, `rejected`, `manual_review`), and the four missing-value states.
- DOS-M03-005: the normalized vPIC candidate corpus and source-namespaced FuelEconomy.gov staging rows this issue consumes.
- Required dependency order: "Build crosswalks in DOS-M03-006 as provider identities arrive. Do not publish provider rows until it passes."

## Included
- Normalize Unicode (NFKC), whitespace, punctuation, case-folded search keys, and approved make/model aliases while preserving publisher display values.
- Model hierarchy: manufacturer → make → model → model year/configuration. Engine, body, drive, fuel, and trim are optional qualifiers; unknown qualifiers remain null/`not_provided` and never act as wildcards for safety-sensitive compatibility unless the source explicitly defines an all-configurations application.
- Import approved FuelEconomy.gov, EPA certification/test, provider, and ACES vehicle identifiers into `vehicle_external_ids`; one catalog configuration may have many external IDs. EPA/DOE engine/transmission/configuration detail is enrichment and QA evidence, not authority for oil schedules or fitment.
- Deterministic exact matching uses numeric/provider IDs and qualified natural keys. Rule-based alias matching may propose candidates. Fuzzy matches may only enter a review queue; they cannot publish automatically.
- Define split/merge handling so corrections produce aliases/supersession edges rather than reassigning an old stable ID to a different configuration.
- Assign match confidence class and retain rejected/ambiguous candidates. Provide a review artifact with side-by-side source fields and provenance.

## Excluded
- Guessing an engine from model name.
- Treating trim marketing names as globally unique.
- Applying a filter or schedule to broader configurations than its source application.

## Preconditions
- DOS-M03-002 approved: identity tuple, stable-ID algorithm/namespace, `crosswalk_status` contract, missing-value states.
- DOS-M03-005 delivering normalized vPIC candidate rows (and FuelEconomy.gov staging when rights-approved).
- Provider/ACES identities from DOS-M03-007 and DOS-M03-009 arrive incrementally; the engine must operate correctly before and after they exist.

## Functional requirements
- FR-1: Normalization applies NFKC Unicode normalization, whitespace and punctuation handling, and case-folded search keys, while preserving publisher display values unchanged; approved make/model aliases resolve through the alias table, never by ad-hoc string edits.
- FR-2: The configuration hierarchy is manufacturer → make → model → model year/configuration; engine, body, drive, fuel, and trim are optional qualifiers that remain null/`not_provided` when unknown and never act as wildcards for safety-sensitive compatibility unless the source explicitly defines an all-configurations application.
- FR-3: The canonical configuration identity tuple is versioned and includes `model_year`, canonical make/model IDs, vehicle type, and only source-supported disambiguators; the stable ID algorithm and namespace UUID are committed.
- FR-4: `vehicle_external_ids` stores approved FuelEconomy.gov, EPA certification/test, provider, and ACES vehicle identifiers with fields `id`, `vehicle_configuration_id`, `source_id`, `external_entity_type`, `external_key`, `effective_from`, `effective_to`, `match_method`, `match_status`, `reviewed_by`, `reviewed_at`, `evidence_ref`; one catalog configuration may hold many external IDs.
- FR-5: Indexing includes a unique index on `(source_id, external_entity_type, external_key, effective_from)`, an index on `vehicle_configuration_id`, and a partial index for `match_status IN ('ambiguous','manual_review')` in staging QA storage.
- FR-6: Matching is tiered: deterministic exact matching on numeric/provider IDs and qualified natural keys; rule-based alias matching proposes candidates only; fuzzy matches may only enter a review queue and cannot publish automatically.
- FR-7: Split/merge corrections produce aliases/supersession edges; an old stable ID is never reassigned to a different configuration.
- FR-8: Every match carries a confidence class; rejected and ambiguous candidates are retained, and a review artifact presents side-by-side source fields with provenance for human decision.
- FR-9: EPA/DOE engine/transmission/configuration detail is stored as enrichment and QA evidence only, never as authority for oil schedules or fitment.
- FR-10: Crosswalk generation is deterministic: same logical inputs in shuffled order generate byte-identical IDs and crosswalk rows.

## Technical implementation contract
### Components and ownership boundaries
- Normalization library (NFKC, whitespace/punctuation, case-folding, alias resolution): shared, versioned; the only place normalization rules live.
- Crosswalk engine: consumes normalized staging from DOS-M03-005/007/008/009 sources and emits `vehicle_external_ids` candidates with `match_method`/`match_status`.
- Review queue and review artifact generator: renders side-by-side source fields and provenance for `ambiguous`/`manual_review` candidates; records reviewer identity and evidence.
- Supersession/alias manager: owns split/merge edges and guarantees stable-ID permanence.
### Data and persistence
- Staging QA storage holds all candidates (including `rejected`/`ambiguous`) with the FR-5 indexes; publishable catalog output contains only `exact` or reviewed `qualified` rows.
- `vehicle_external_ids` per FR-4; configuration rows per the section 8 `vehicle_configurations` contract with completeness codes and nullable unknowns.
- All rows carry `_provenance` per DOS-M03-002; review decisions carry reviewer/evidence/timestamps.
### Interfaces and events
- Input: normalized, source-namespaced identity rows (vPIC corpus, FuelEconomy.gov staging, provider vehicle lists from DOS-M03-007, supplier/ACES vehicles from DOS-M03-009, EPA certification/test identifiers).
- Output: crosswalk rows keyed by stable configuration IDs; coverage metrics separating YMM coverage, qualified-configuration coverage, and unmatched external applications — consumed by DOS-M03-010 QA.
- Review workflow: queue in, human decision out; decisions are recorded data (`reviewed_by`, `reviewed_at`, `evidence_ref`), not ephemeral approvals.
### Failure and recovery behavior
- An unmatched or ambiguous external identity never blocks the pipeline; it is retained, reported, and excluded from publishable schedule/fitment joins.
- A provider identity arriving before its source issue completes is staged and re-evaluated when data lands (incremental operation per the dependency order).
- Erroneous published matches are corrected by supersession/alias edges plus a new catalog version — never by reassigning stable IDs.
### Security and privacy
- No personal data or VINs in crosswalk inputs; provider identities are catalog-level keys.
- Licensed provider identifiers are handled per their rights-matrix terms; review artifacts expose only fields the license permits engineers/reviewers to see.
- Evidence references point to access-controlled landing-zone objects, not embedded payloads.
### Accessibility and performance
N/A for accessibility — build-side engine. Performance: matching over the 30-year corpus must be batch-tractable and deterministic; indexes per FR-5 keep review-queue queries and QA scans fast; determinism (FR-10) is a hard requirement over speed.
### Data change specifics
- Source/version/license: consumes only sources already gated by DOS-M03-001; each external-ID row binds `source_id` and inherits the source's license terms; EPA/DOE rows are green-lane enrichment.
- Mapping: source identity rows → canonical configuration tuple + `vehicle_external_ids`; qualifiers map only from source-supported disambiguators; no inferred fields.
- Stable keys: committed UUIDv5/namespaced-digest algorithm over the versioned identity tuple; external identity uniqueness per `(source_id, external_entity_type, external_key, effective_from)`.
- Constraints/indexes: FR-5 set; publishable views constrained to `match_status` `exact` or reviewed `qualified`.
- Idempotency: rerunning the engine over identical inputs (any order) yields byte-identical IDs and crosswalk rows; review decisions are stable data and are not re-derived.
- Rejected-row policy: `rejected` and `ambiguous` candidates are retained in staging QA storage with reasons and surfaced in metrics; nothing is silently dropped.
- Checksums: crosswalk output hashes recorded per run for determinism comparison; evidence references carry landing-zone SHAs.
- Coverage report: separates YMM coverage, qualified-configuration coverage, and unmatched external applications; feeds DOS-M03-010.
- Fixture strategy: golden crosswalk set covering badge-engineered makes, renamed models, same model name across makes, multiple engines, and provider splits/merges; property-test generators for normalization idempotence.
- Update cadence: re-run as provider identities arrive (per required dependency order) and per catalog release build.
- Rollback/recovery: versioned run outputs; supersession edges are additive so recovery is re-pinning a prior run plus replaying recorded review decisions.

## Acceptance criteria
- [ ] AC-1: Same logical inputs in shuffled order generate byte-identical IDs and crosswalk rows.
- [ ] AC-2: No ambiguous or rejected crosswalk can appear in publishable schedule/fitment tables.
- [ ] AC-3: Golden cases cover badge-engineered makes, renamed models, same model name across makes, multiple engines, and provider splits/merges.
- [ ] AC-4: Every published non-vPIC application resolves through an exact or explicitly reviewed qualified crosswalk with evidence.
- [ ] AC-5: Coverage report separates YMM coverage, qualified-configuration coverage, and unmatched external applications.
- [ ] AC-6: Every crosswalk row carries auditable provenance (`source_id`, `match_method`, `match_status`, `reviewed_by`, `evidence_ref`), only sources rights-approved by DOS-M03-001 participate in published crosswalks, and the review artifact shows side-by-side source fields with provenance for each qualified match.

## Test plan
### Automated
- Property tests for normalization idempotence (NFKC, whitespace, punctuation, case-folding) and for display-value preservation.
- Determinism test: shuffled-input runs diffed byte-for-byte against baseline crosswalk output (AC-1).
- Publishability constraint tests: `ambiguous`/`rejected`/`manual_review` rows are excluded from publishable schedule/fitment joins; only `exact`/reviewed `qualified` pass (AC-2, AC-4).
- Golden crosswalk suite per AC-3, including split/merge supersession behavior and the prohibition on stable-ID reassignment.
- Index/constraint tests for the FR-5 unique and partial indexes.
- Wildcard-prohibition tests: unknown qualifiers never match qualified applications absent an explicit all-configurations assertion.
### Manual/device matrix
- Reviewer dry-run of the review queue: a batch of seeded ambiguous candidates reviewed via the side-by-side artifact; decisions recorded with `reviewed_by`/`reviewed_at`/`evidence_ref`.
- Data-owner audit of a sample of published qualified crosswalks against source evidence.
- No device work: N/A — build-side engine.

## Rollout and rollback
Crosswalk outputs are versioned per run and consumed by the compiler via pinned run identity; promotion of new crosswalks happens only through a catalog release that passes DOS-M03-010 gates. Rollback is re-pinning the prior run. Corrections ship as supersession/alias edges in a new version; stable IDs are never mutated or reassigned in place.

## Documentation and evidence
Property tests for normalization/idempotence; golden crosswalk set; reviewer report; unmatched/ambiguous metrics. Plus the committed stable-ID algorithm/namespace documentation and the coverage report separating the three coverage classes.

## Dependency rationale
Depends on DOS-M03-002 (identity tuple, stable-ID and crosswalk-status contracts) and DOS-M03-005 (the canonical candidate corpus). It receives provider IDs from DOS-M03-007 and DOS-M03-009 incrementally — coordination, not a start blocker, per the required dependency order ("Build crosswalks in DOS-M03-006 as provider identities arrive"). It blocks DOS-M03-010 (no provider row publishes until its crosswalk passes) and DOS-M04-002 finalization (physical schema needs the finalized identity/external-ID shapes).

## Risks, decisions, and open questions
- Risk: pressure to fuzzy-join provider vehicles to boost coverage numbers; hard-blocked by FR-6 (fuzzy → review queue only) and AC-2.
- Risk: badge engineering and marketing trim names producing false merges; covered by the golden set and the rule that trim names are not globally unique.
- Risk: provider identity churn (splits/merges) corrupting history; handled by supersession edges and stable-ID permanence.
- Decision: EPA/DOE detail is enrichment/QA evidence only — never schedule/fitment authority.
- Open question: review-queue tooling form (spreadsheet-based vs. lightweight web artifact); the contract fixes the recorded fields either way.

## Definition of done
All acceptance criteria checked; normalization library, crosswalk engine, review queue, and supersession manager implemented against the DOS-M03-002 contracts; determinism, publishability, and golden suites green in CI; reviewer workflow exercised with recorded decisions; coverage metrics published; DOS-M03-010 and DOS-M04-002 consumers unblocked with pinned run outputs.
