## Outcome
When API grants suitable access/redistribution rights, the catalog contains time-bounded EOLCS licensee, brand, product, viscosity-grade, and service-category claims without implying vehicle fitment.

## Why this matters and what it unblocks
Users need a searchable oil-product shortlist, but certification status changes and is not equivalent to compatibility. A dedicated adapter preserves that distinction and supports refresh/removal policy. It supplies the `oil_brands`/`oil_products`/`oil_product_claims` domain, enables the M05 product picker to show licensed products with freshness context, and blocks the oil-product sections of DOS-M03-010. It also enforces non-negotiable rule 5: a brand name or viscosity alone never proves compatibility.

## Context and source of truth
- Master prompt section 4.4: the API EOLCS directory can verify licensed oil product claims but does not map a product to a vehicle; free candidate matrix row "Oil product identity and published claims" — verify a specific SKU's published claims and effective status; certification/viscosity alone does not establish vehicle compatibility or an interval.
- Master prompt section 8: `oil_brands`, `oil_products`, `oil_product_claims` (stable brand/product/SKU, market/status/effective dates, viscosity and certification/approval claims, claim source and last verification; a brand row alone is never compatible).
- Section 11.2 "Research-backed source policy" (verified 2026-07-31): API says its EOLCS directory lists active licensees and licensed products; Publication 1520 is online-only and updated as often as several times a week; API's public pages do not document a supported bulk-download or product API for this use; do not scrape or redistribute directory content until written permission or licensed delivery terms cover automated extraction, caching, attribution, update cadence, and offline redistribution.
- Research-anchor URLs: [EOLCS directory](https://www.api.org/products-and-services/engine-oil/eolcs-licensee-directory), [Publication 1520](https://www.api.org/products-and-services/engine-oil/documents/publication-1520), [API certification directories](https://www.api.org/products-and-services/certifications-directories).
- Section 11.2 "Mandatory fallback": EOLCS defaults to user-entered oil product data when rights are not secured; DOS-M03-001 matrix row governs.

## Included
- Start with the publicly accessible API directory as a free-source candidate, but obtain exact terms or written permission before automating it. Obtain a documented delivery mechanism and permission for automation, caching, normalization/derived output, build backups, transformed offline distribution/end-user storage, historical product snapshots, continued distribution of the acquired snapshot after termination, API trademark/mark representation, attribution, optional future updates, and stale/withdrawn product handling. If API offers a one-time authorized snapshot, prefer it to runtime/subscription access; do not assume either exists.
- Import licensee identity, license/reference number if supplied, brand, product name, SAE viscosity grade, API service category/classification, market geography if supplied, active/status dates, and directory observation date.
- Model one product with multiple claims/grades as explicit claim rows rather than concatenated text.
- Canonicalize only controlled viscosity/category codes; preserve exact source text and quarantine unknown codes for review.
- Add a freshness SLA and removal/supersession logic. Historical oil-change events retain product snapshots even if a product later leaves the active catalog.
- Fixture-only fallback remains available for UI/test development; it is branded synthetic and cannot enter production.

## Excluded
- Scraping the online-only directory without authorization.
- Copying API quality marks/logos without permission.
- Treating EOLCS status as an OEM recommendation.
- Deriving vehicle compatibility from viscosity alone.
- Claiming current certification when the catalog is stale.

## Functional requirements
- FR-1: The adapter runs against a documented, authorized delivery mechanism only; automation of the public directory without written permission is prohibited; a one-time authorized snapshot is preferred over runtime/subscription access when API offers it, and neither is assumed to exist.
- FR-2: The rights capture covers automation, caching, normalization/derived output, build backups, transformed offline distribution/end-user storage, historical product snapshots, continued distribution of the acquired snapshot after termination, API trademark/mark representation, attribution, optional future updates, and stale/withdrawn product handling, recorded in the DOS-M03-001 matrix.
- FR-3: Import covers licensee identity, license/reference number if supplied, brand, product name, SAE viscosity grade, API service category/classification, market geography if supplied, active/status dates, and directory observation date.
- FR-4: Normalized entities are licensee, brand, product, and product claim; claim fields include `claim_type` (`api_service_category`, `sae_viscosity_grade`, later approved types), `claim_code`, `status`, `valid_from`, `valid_to`, `observed_at`, and provenance.
- FR-5: One product with multiple claims/grades yields explicit claim rows, never concatenated text.
- FR-6: Only controlled viscosity/category codes are canonicalized; exact source text is preserved; unknown codes are quarantined for review, not guessed.
- FR-7: Product identity uses the provider key when available, otherwise an approved versioned natural key; name changes produce aliases/supersession, not destructive overwrites.
- FR-8: A freshness SLA plus removal/supersession logic exists; the manifest exposes `eolcs_observed_at`, freshness status, and count of active/inactive/quarantined products; UI-facing query data always exposes observation/freshness.
- FR-9: Historical oil-change events retain product snapshots even if a product later leaves the active catalog (browser IndexedDB `events` store snapshot semantics per [DOS-M09-001](DOS-M09-001.md); catalog removal never rewrites history — the server holds no personal row to rewrite).
- FR-10: No catalog surface may call a product `compatible` absent a separate vehicle-requirement match; EOLCS rows carry certification claims only.
- FR-11: The fixture-only fallback is branded synthetic and cannot enter production; with rights unapproved, the production adapter is off and the release artifact contains zero EOLCS rows.
- FR-12: Refresh imports produce a diff report (additions, removals, material claim changes, unusual count deltas) reviewed before publication.

## Technical implementation contract
### Components and ownership boundaries
- EOLCS adapter: parses the authorized delivery into normalized licensee/brand/product/claim staging; owned by the data workstream; enabled per `config/data_sources.yml` only.
- Code canonicalizer: controlled vocabulary for SAE viscosity grades and API service categories; unknown codes → quarantine queue.
- Freshness/supersession manager: computes freshness status against the SLA, applies removal/supersession, and feeds manifest fields.
- Diff reporter: before/after comparison gate for refreshes.
### Data and persistence
- Raw deliveries in the DOS-M03-003 landing zone with receipts; normalized staging validated against DOS-M03-002 schemas with `_provenance` including `observed_at`.
- Downstream mapping to section 8 `oil_brands`/`oil_products`/`oil_product_claims` with market/status/effective dates and last verification; claim rows per FR-4.
- Aliases/supersession edges for renames per FR-7; quarantine storage for unknown codes with source text.
### Interfaces and events
- Input: authorized delivery or snapshot (per rights); no runtime API dependency for the installed app ever.
- Output: publishable product/claim staging, freshness manifest fields (`eolcs_observed_at`, freshness status, active/inactive/quarantined counts), and the refresh diff report — consumed by DOS-M03-010's oil-product sections and the M05 product picker queries.
- The recommendation resolver consumes claims only through requirement-matching logic (M05/M06); this adapter exposes no compatibility signal.
### Failure and recovery behavior
- Parse failures, unknown codes, duplicate ambiguity, and unresolved renames quarantine with reasons; publication proceeds only for clean rows.
- A stale catalog (freshness SLA exceeded) downgrades UI claims (no "currently certified" language) rather than blocking the app; freshness status ships in the manifest.
- Withdrawn products supersede rather than delete; historical user snapshots are untouched.
- Rights termination: production flag off, zero EOLCS rows in subsequent releases; already-acquired snapshot handling follows the contracted continued-distribution terms.
### Security and privacy
- No scraping, no credentials in code or logs; delivery credentials (if any) referenced by environment-variable name only.
- API trademark/quality-mark usage strictly per written approval and attribution requirements; marks never embedded without recorded permission.
- Licensed delivery payloads stay out of Git; synthetic fixtures are visibly branded synthetic.
### Accessibility and performance
N/A for accessibility — build-side adapter. Performance: product/claim tables must stay within DOS-M03-010 size budgets; claim-row explosion (multi-grade products) is measured in the coverage counts; search-key normalization supports the offline product picker without FTS dependence.
### Data change specifics
- Source/version/license: API EOLCS directory under written permission/licensed delivery only; `source_key` status gates production; each import pins delivery version and `observed_at`; license version recorded per receipt.
- Mapping: delivery records → licensee/brand/product/claim staging (FR-3/FR-4) → section 8 oil-product tables; exact source text preserved beside canonical codes.
- Stable keys: provider key when available, else approved versioned natural key (FR-7); claim identity = product + `claim_type` + `claim_code` + validity window; renames via aliases/supersession.
- Constraints/indexes: uniqueness on product identity and on claim identity; status/effective-date validity checks; staging indexes on brand and normalized product name.
- Idempotency: re-import of the same delivery SHA + transform version yields identical staging hashes; refresh imports are new versions diffed against prior, never in-place edits.
- Rejected-row policy: unknown codes, malformed rows, and ambiguous duplicates quarantine with reasons and counts exposed in the manifest.
- Checksums: delivery SHA-256 via receipts; staging output hashes per run; manifest counts reconcile against staging totals.
- Coverage report: active/inactive/quarantined product counts, claim-type distribution, and freshness status; refresh diff report per FR-12.
- Fixture strategy: synthetic branded fixtures covering multi-grade/multi-category products, duplicate brand names, withdrawal, rename, and unknown category; production-excluded by construction.
- Update cadence: governed by the freshness SLA and the negotiated update terms (Publication 1520 changes as often as several times a week upstream; the catalog snapshot cadence is a recorded product decision, and staleness is always displayed rather than hidden).
- Rollback/recovery: versioned imports; rollback is re-pinning the prior import; supersession preserves history; user-event product snapshots are independent of catalog state.

## UX and content states
This adapter fixes the content states the UI must honor: products display certification claims with observation/freshness context ("as of `eolcs_observed_at`"), never "currently certified" from a stale catalog; no product is labeled `compatible` absent a separate vehicle-requirement match ("Meets the recorded requirements" wording comes from requirement matching, not EOLCS presence); withdrawn products remain visible in historical service events as snapshots; when the source is disabled, the picker offers user-entered oil products labeled `User entered`.

## Rollout and rollback
Production enablement is flag-driven by rights status; EOLCS rows ship only in catalog releases passing DOS-M03-010 gates, with `eolcs_observed_at` and freshness in the manifest. Refreshes are versioned imports gated by the diff report. Rollback is re-pinning the prior import or disabling the source (zero rows) with the user-entered fallback; user history snapshots are never rewritten.

## Risks, decisions, and open questions
- Risk: API grants no suitable terms; planned outcome — production adapter off, zero EOLCS rows, user-entered oil products; the app remains shippable.
- Risk: upstream volatility (Publication 1520 updated as often as several times a week) makes any snapshot stale quickly; mitigated by the freshness SLA, `observed_at` display, and prohibition on stale currency claims.
- Risk: brand/product name collisions and renames corrupting identity; mitigated by provider-key preference, versioned natural keys, and supersession-not-overwrite.
- Decision: certification is never compatibility; the resolver alone may say a product meets recorded requirements.
- Open question: whether API offers a one-time authorized snapshot vs. negotiated recurring delivery; both paths are specified, with the snapshot preferred.
