## Outcome
One command/CI job turns pinned, approved normalized inputs into a content-addressed SQLite catalog release plus manifest, reports, and rollback metadata.

## Why this matters and what it unblocks
M04 and the user experience need a small, immutable, validated artifact—not raw provider feeds—and operations need a safe promotion boundary. This is the epic's exit deliverable: the versioned catalog that M04's network-free installer copies and verifies, that M05 queries offline, and that M07's data-quality sign-off audits. Its QA gates are the last line preventing an unauthorized source, ambiguous crosswalk, or corrupt artifact from reaching users.

## Context and source of truth
- Master prompt section 8: `catalog_metadata` (`schema_version`, `data_version`, `generated_at`, `min_app_version`, content hash); the catalog builder emits rejected-row reports, coverage counts, collisions, source diffs, a manifest, and a deterministic SQLite artifact; catalog records are immutable within one `data_version`; `CatalogRepo` bundled-artifact verification/copy and rollback rules ("stage, integrity-check, atomically rename, and retain the previous catalog for rollback").
- Master prompt section 4.2: SQLite is the runtime database (`CatalogRepo` replaceable, read-mostly, bundled); `pool_size: 1`; no cross-database foreign keys.
- Master prompt section 5: coverage contract and support statuses that coverage claims must respect.
- Section 11.2 source policy and DOS-M03-000 exit criteria: `catalog-manifest.json`, compressed catalog payload(s), provenance report, coverage report, license report, checksums, and release notes generated in CI from pinned inputs; the catalog is copied into the iOS/Android application bundle for M04's installer.
- DOS-M03-001 (`config/data_sources.yml` gates), DOS-M03-002 (final-record schemas), DOS-M03-005/006/007/008/009 (normalized inputs, crosswalks, and per-domain reports this compiler consumes).
- Required dependency order step 7: "Compile the full approved catalog—or the explicitly reduced but still maximally useful free-approved baseline—in DOS-M03-010, then implement/validate atomic installer DOS-M04-008."

## Included
- Compile the M04 catalog schema with deterministic row ordering, stable timestamps supplied by `SOURCE_DATE_EPOCH`, fixed SQLite pragmas/page size, normalized indexes, `ANALYZE` statistics, integrity check, and optional deterministic vacuum strategy.
- Generate `catalog-manifest.json`: `manifest_version`, semantic `catalog_version`, `schema_version`, `built_at`, rolling years, region, feature coverage flags, source versions/license versions, record counts, uncompressed/compressed byte sizes, payload SHA-256, compression, minimum app version, supersedes, release notes URL, and signature/key ID when signing is adopted.
- Generate per-source and combined QA: schema validity, referential integrity, duplicate natural keys, orphan external IDs, intervals/capacities ranges, qualifier retention, crosswalk status, year/make coverage, stale source SLA, diff versus previous release, and catalog/query size budgets.
- Define severity: blockers fail build; warnings require named waiver with expiry. Required blockers include unauthorized source, expired rights, failed integrity, checksum mismatch, orphan fitment/schedule, ambiguous published crosswalk, invalid interval/unit, and unexplained record-count delta beyond thresholds.
- Produce a compressed full artifact first; add make/year shards only if measured device install/memory budgets require them. If sharded, all shards belong to one application-bundle release transaction and manifest root hash.
- Stage the catalog as a versioned native application-bundle resource, run M04 install/conformance tests against the exact packaged iOS/Android artifacts, and include it only after those tests pass. The app bundle is immutable; M04 copies/verifies the bundled asset into the app's Application Support/device-files directory. Retain the currently installed catalog for rollback during an app upgrade subject to license terms.

## Excluded
- Mutating a released catalog in place.
- Embedding provider secrets/raw licensed deliveries.
- Making catalog availability dependent on live provider APIs.
- Silently waiving QA failures.

## Functional requirements
- FR-1: Compilation targets the M04 catalog schema with deterministic row ordering, stable timestamps supplied by `SOURCE_DATE_EPOCH`, fixed SQLite pragmas/page size, normalized indexes, `ANALYZE` statistics, an integrity check, and an optional deterministic vacuum strategy.
- FR-2: `catalog-manifest.json` contains exactly the fields listed under Included (`manifest_version` through signature/key ID when signing is adopted); the manifest checksum matches the exact artifact bytes.
- FR-3: Per-source and combined QA covers schema validity, referential integrity, duplicate natural keys, orphan external IDs, intervals/capacities ranges, qualifier retention, crosswalk status, year/make coverage, stale source SLA, diff versus previous release, and catalog/query size budgets.
- FR-4: Severity policy: blockers fail the build; warnings require a named waiver with expiry; the required blocker set is: unauthorized source, expired rights, failed integrity, checksum mismatch, orphan fitment/schedule, ambiguous published crosswalk, invalid interval/unit, and unexplained record-count delta beyond thresholds.
- FR-5: Artifact names are content-addressed, for example `catalog-v{catalog_version}-s{schema_version}-{sha256_prefix}.sqlite.{compression}`.
- FR-6: Compression is selected from `zstd`, `gzip`, or an uncompressed SQLite bundle only after the exact decoder/NIF or native implementation is proven in release-like Mob builds on both platforms; a smaller artifact does not justify an unsupported native dependency.
- FR-7: A bundle-local `catalog-manifest.json` names the exact immutable resource; there is no runtime channel-manifest fetch in M03/M04; signed online catalog delivery is deferred to DOS-M08.
- FR-8: The compressed full artifact is produced first; make/year shards are added only if measured device install/memory budgets require them, and if sharded, all shards belong to one application-bundle release transaction and manifest root hash.
- FR-9: The catalog is staged as a versioned native application-bundle resource and included only after M04 install/conformance tests pass against the exact packaged iOS/Android artifacts; the app bundle is immutable and M04 copies/verifies the bundled asset into the app's Application Support/device-files directory; the currently installed catalog is retained for rollback during an app upgrade subject to license terms.
- FR-10: Release output includes SPDX-style software/source notices plus the product-specific attribution/license report; no open-data license is asserted for mixed licensed content.
- FR-11: Catalog rows include provenance IDs, but raw payloads and contract documents do not ship.
- FR-12: Builds are reproducible: two builds from identical pinned inputs/toolchain produce the same logical dump and payload SHA (or a documented byte-level exception with canonical logical hash), with input order randomized in CI.

## Technical implementation contract
### Components and ownership boundaries
- Catalog compiler (one command/CI job): consumes pinned normalized staging + crosswalk runs + `config/data_sources.yml`; emits artifact, manifest, and reports; owned by the data pipeline.
- QA gate engine: evaluates FR-3 checks with FR-4 severity policy and the waiver registry (named waiver, expiry, reason).
- Packaging/staging step: places the artifact and bundle-local manifest into the native application-bundle resources; hands off to M04 conformance tests.
- Release notes and attribution/license report generator.
### Data and persistence
- Output SQLite database conforming to the M04 catalog schema (section 8 tables) with fixed pragmas/page size, normalized indexes, `ANALYZE` statistics run, and `catalog_metadata` populated (`schema_version`, `data_version`, `generated_at` from `SOURCE_DATE_EPOCH`, `min_app_version`, content hash).
- Content-addressed artifact naming per FR-5; compression per FR-6; manifest per FR-2; catalog records immutable within one `data_version`.
- Inputs are pinned by run manifests/hashes from DOS-M03-005/006/007/008/009; no live provider access during compilation.
### Interfaces and events
- Input interface: pinned normalized inputs + source gates; the compiler refuses unpinned or gate-failing inputs.
- Output interface: artifact + `catalog-manifest.json` + QA/provenance/coverage/license reports + rollback metadata (`supersedes`), consumed by M04's installer (DOS-M04-008) and release operations.
- Promotion event: QA pass + M04 packaged-device conformance pass + product/data owner coverage approval → artifact enters the application bundle; every promotion and rollback is logged.
### Failure and recovery behavior
- Any FR-4 blocker fails the build with a diagnostic naming the failing check, source, and records; there is no silent waiver — warnings proceed only under a named waiver with expiry.
- A failed reproducibility comparison blocks promotion until explained (documented byte-level exception with canonical logical hash) or fixed.
- Packaging failures or M04 conformance failures keep the previous catalog as the shipped resource; the `supersedes` chain and retained on-device previous catalog provide upgrade rollback.
- Partial/corrupt artifacts can never be promoted: checksum mismatch is a required blocker at every hop (build, bundle, device copy).
### Security and privacy
- No provider secrets, credentials, raw licensed deliveries, or contract documents in the artifact, manifest, reports, or bundle; provenance ships as IDs only (FR-11).
- Attribution/license output follows the rights matrix; trademark/mark usage per recorded approvals.
- The artifact contains no user data by construction (catalog is read-only reference data; `UserRepo` is a separate database that a catalog update never overwrites).
### Accessibility and performance
N/A for accessibility — build artifact. Performance: catalog and query size budgets are explicit QA checks (FR-3); device install/memory budgets are measured before any sharding decision (FR-8); deterministic `ANALYZE` statistics keep on-device query plans predictable; compression choice is subordinate to proven decoder support in release-like Mob builds (FR-6).
### Data change specifics
- Source/version/license: the manifest records source versions/license versions for every included source; only `approved`/`approved_with_conditions` sources compile; unauthorized/expired sources are required blockers.
- Mapping: normalized staging → M04 catalog schema (section 8 tables); crosswalk-passing rows only; per-domain feature coverage flags in the manifest reflect what actually shipped.
- Stable keys: catalog rows carry the DOS-M03-002 stable IDs; artifact identity is content-addressed (`sha256_prefix` in the name; payload SHA-256 in the manifest); `supersedes` links versions.
- Constraints/indexes: referential integrity, duplicate-natural-key, and orphan checks enforced as QA blockers; normalized indexes and `ANALYZE` run deterministically; `PRAGMA integrity_check` must return `ok`.
- Idempotency: identical pinned inputs/toolchain reproduce the same logical dump and payload SHA with input order randomized (FR-12); compilation is a pure function of pinned inputs.
- Rejected-row policy: rejected-row reports are release outputs; rejects never silently disappear — counts reconcile in QA and unexplained record-count deltas beyond thresholds are blockers.
- Checksums: SHA-256 for the payload (and per-shard plus manifest root hash if sharded); manifest checksum must match the exact downloadable bytes; device-copy verification is M04's mirror of the same hash.
- Coverage report: year/make coverage, per-domain feature coverage flags, and support-status counts reviewed and explicitly approved by the product/data owner before any advertised coverage claim.
- Fixture strategy: QA-gate fixtures (unauthorized source, ambiguous crosswalk, stale feed, extreme interval, orphan product, large unexplained diff) prove each blocker; a synthetic/golden catalog remains available for M04 host and device contract tests independent of licensed data.
- Update cadence: per release; each catalog is a new `data_version` with diff-versus-previous QA; no in-place mutation of a released catalog.
- Rollback/recovery: `supersedes` metadata plus the retained previously installed catalog enable app-upgrade rollback (subject to license terms); promotion/rollback logs are release evidence.

## Acceptance criteria
- [ ] AC-1: Two builds from identical pinned inputs/toolchain produce the same logical dump and payload SHA (or a documented byte-level exception with canonical logical hash); input order is randomized in CI.
- [ ] AC-2: `PRAGMA integrity_check` returns `ok`, all foreign-key/orphan checks pass, and the manifest checksum matches the exact downloadable bytes.
- [ ] AC-3: An unauthorized-source fixture, ambiguous crosswalk, stale feed, extreme interval, orphan product, and large unexplained diff each block promotion.
- [ ] AC-4: A clean physical iOS and Android device can install the packaged app, copy/verify/query the bundled catalog, survive app kill/reboot offline, and roll back to the retained compatible catalog during a simulated app upgrade via M04 tests.
- [ ] AC-5: Product/data owner reviews the coverage report and explicitly approves any advertised coverage claim.
- [ ] AC-6: The release output includes SPDX-style software/source notices and the product-specific attribution/license report; an unauthorized source or expired rights is a blocking failure; catalog rows carry provenance IDs while raw licensed payloads and contract documents do not ship; no open-data license is asserted for mixed licensed content.

## Test plan
### Automated
- Reproducibility job: two full builds from identical pinned inputs/toolchain with input order randomized; compare logical dump and payload SHA (AC-1).
- Integrity suite: `PRAGMA integrity_check`, foreign-key/orphan scans, duplicate-natural-key checks, manifest-vs-bytes checksum verification (AC-2).
- QA-gate fixture suite: unauthorized source, ambiguous published crosswalk, stale feed, extreme interval, orphan product, large unexplained record-count diff — each must block promotion (AC-3); waiver-path test proving warnings require a named waiver with expiry.
- Manifest schema validation and content-addressed naming checks; SPDX/attribution report generation test; secret/raw-payload absence scan over artifact and bundle.
- Compression/decoder gate: chosen compression proven against release-like Mob build decoding on both platforms before adoption (FR-6).
- Size-budget checks: catalog and representative query budgets enforced in QA.
### Manual/device matrix
- Physical-device smoke via M04 install/conformance tests on one clean iOS device and one clean Android device: install packaged app, copy/verify/query bundled catalog, airplane-mode app kill/reboot survival, simulated app-upgrade rollback to the retained compatible catalog (AC-4).
- Product/data owner review session of the coverage report with explicit recorded approval of any advertised coverage claim (AC-5).
- Release-operations dry run of promotion and rollback using the logs and `supersedes` metadata.

## Rollout and rollback
Promotion path: CI build → QA gates → staging as a versioned native application-bundle resource → M04 packaged-artifact conformance tests → inclusion in the app bundle. The bundle is immutable; devices copy/verify the asset on install/upgrade and retain the previously installed catalog for rollback (subject to license terms). Rollback is shipping a bundle pinned to the prior artifact (or the device-side retained catalog during upgrade). No released catalog is mutated in place; online signed delivery is deferred to DOS-M08.

## Risks, decisions, and open questions
- Risk: byte-level nondeterminism in SQLite output; mitigated by fixed pragmas/page size, deterministic ordering, `SOURCE_DATE_EPOCH`, and the documented logical-hash exception path.
- Risk: compression choice introducing an unproven native dependency in Mob release builds; blocked by FR-6's proof-first rule.
- Risk: QA thresholds tuned too loose (silent data drift) or too tight (constant blocks); the named-waiver-with-expiry mechanism plus diff thresholds make every exception visible and temporary.
- Risk: sharding complexity adopted prematurely; FR-8 requires measured device budgets first.
- Decision: no runtime channel-manifest fetch in M03/M04; bundle-local manifest only; signed online delivery deferred to DOS-M08.
- Open question: signing adoption timing (manifest reserves signature/key ID); resolved with the release-engineering work in M07/M08.
