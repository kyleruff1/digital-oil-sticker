> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The epic splits along the new boundary: read-only catalog persistence on the server, and anonymous personal-record persistence in the browser._

## Outcome

Split the persistence boundary along the ADR-0004 line: a **read-only server-side catalog** on Fly.io (`DigitalOilSticker.CatalogRepo`, `Ecto.Adapters.SQLite3`, `pool_size: 1`, opened read-only, baked into the deploy image) plus an **anonymous browser store** for all personal data (origin-scoped IndexedDB `dos_local`, forward-only schema-versioned, mediated by a `phx-hook` running the ADR-0004 hydration and mutation protocol). The deployed application has exactly one Ecto repo and it holds zero personal rows (Constitution 2.0.0 INV-23); the browser is the sole system of record for garage, service history, odometer readings, reminder intent, and preferences.

At epic close: the Fly image ships a byte-identical catalog SQLite alongside the release binary; the `LocalStore` `phx-hook` hydrates and write-backs correctly across mount, reconnect, and multi-tab commits; export/import round-trips via browser File APIs; browser/engine conformance passes on the ratified support matrix — with an automated release-gate test asserting the deployed app's Ecto repo list is exactly `[CatalogRepo]` opened read-only (ADR-0004 §Enforcement).

## Why this matters and what it unblocks

Every surviving MVP feature — vehicle search and selection, oil-change history, odometer check-ins, forecasting, and in-app due/overdue state — reads through the server catalog boundary this epic delivers and writes through the browser storage boundary this epic delivers. The product's non-negotiable rules — no online accounts, no server-side personal record, no implied backup, no third-party trackers (INV-3, INV-4, INV-5, INV-22, INV-23) — are enforced structurally here, in the repo topology and the hydration protocol, not by UI discipline alone. Closing this epic unblocks the rescoped M05 (Single-vehicle MVP screens, whose flows are wired directly to the LiveView hydration protocol and browser storage adapter this epic implements against) and, through it, the rescoped M06 (in-app due state, which persists through the same IndexedDB object stores rather than through the deleted on-device `usage_profiles`/`forecast_snapshots` tables). Failure to enforce the empty-repo-list gate now would create the exact server-side personal record ADR-0004 exists to prevent.

## Excluded

Post-pivot exclusion list. The pre-pivot list forbade the ratified architecture (browser/IndexedDB and the remote application server); those items are removed here. What remains is the set of things ADR-0004 preserves and strengthens, plus items ADR-0004 explicitly defers to a separate ADR.

- Any `UserRepo`, or any server-side database table, cache, ETS store, disk file, external store, or log line that holds a personal row (INV-3, INV-23). Enforced structurally by the ADR-0004 §Enforcement test asserting the deployed app's Ecto repo list is exactly `[CatalogRepo]`.
- Online accounts, login, remote profile, identity provider, cloud sync, or any cross-device continuity beyond user-initiated export/import (INV-3, INV-19).
- Server-side or cookie-borne stable client identifiers, "anonymous user IDs", or any value that could correlate one visit to another. The session cookie carries only the CSRF token and `live_socket_id`; nothing else (INV-3; ADR-0004 §"CSRF and session").
- Third-party analytics, tag managers, session recorders, advertising pixels, CDN-hosted fonts or scripts, and error reporters that could serialize `socket.assigns` (INV-4, INV-22; ADR-0004 §"No third-party anything").
- Web Push, service workers used for push, and background sync — each is a separately deferred decision (INV-17, INV-19; ADR-0004 §Consequences) requiring its own ADR and a new constitution revision, not a ticket under this epic.
- Service-worker/PWA offline caching and any "offline-first" promise (INV-6 amended, INV-19; ADR-0004 §Consequences). ADR-0004 explicitly excludes PWA from the MVP; if adopted later it requires its own ADR.
- Netlify-hosted Phoenix runtime, and any use of Netlify for the interactive application, personal data storage, or catalog queries. Netlify serves only static marketing, support, privacy, and attribution content on `help.` / `legal.` subdomains and on `digitaloilsticker.net` (INV-27; ADR-0002 as amended by ADR-0004 §"ADR-0002 → Amended").
- OS-scheduled local notifications, `mob_notify`, background scheduling, or any implication of alerting the user when the browser tab is closed (INV-17 amended). In-app due/overdue state only; the OS-notification delivery half moves to the native re-entry.
- Native mobile packaging, app-store distribution, on-device BEAM/Phoenix, Mob 0.7.20 runtime, on-device SQLite `UserRepo`, and every on-device durability drill (crash/kill/reboot/low-space on a packaged app) originally chartered here (INV-1 amended; ADR-0001 deferred).
- End-user network catalog updates outside a Fly deploy. The catalog is a build artifact baked into the deploy image; catalog activation is a deploy (ADR-0004 §"Catalog database on Fly"). Out-of-band catalog updates remain the concern of the rescoped M08 and would require an ADR before being adopted here.
- Multiple SQLite pool connections in any configuration (`pool_size > 1`) — preserved from the pre-pivot spec because it still applies to the surviving `CatalogRepo`.
- Work not stated in a child issue's Included scope (change control: discoveries become a new issue or ADR).

## Functional requirements

Entry-gate conditions:

- **FR-1:** The epic may not move past Backlog until Constitution 2.0.0 is ratified (achieved), ADR-0004 is Accepted (achieved), and the M03 vocabulary/stable-ID contract (`DOS-M03-002`) is approved.
- **FR-2:** The persistence architecture — one server-side read-only `CatalogRepo`, one browser IndexedDB `dos_local` user store, and the ADR-0004 hydration protocol — is fixed and ratified in the rescoped `DOS-M04-001` before any other M04 child starts implementation. `DOS-M04-001` blocks all other numbered M04 issues.

Server catalog exit-gate conditions:

- **FR-3:** `DigitalOilSticker.CatalogRepo` is the **only** Ecto repo in the deployed application, uses `Ecto.Adapters.SQLite3`, is opened read-only, runs with `pool_size: 1`, and is baked into the Fly deploy image (no volume, no Postgres). Verified by the ADR-0004 §Enforcement release-gate test asserting the deployed app's repo list is exactly `[CatalogRepo]` and that its connection is opened read-only.
- **FR-4:** No module under the domain namespaces (`DigitalOilSticker.Catalog`, `.Garage`, `.Forecast`, resolver) references `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules — enforced by the ADR-0004 §Enforcement static check, protecting decision §6 (client-agnostic domain contract) mechanically so a future native client's storage adapter is a drop-in swap.
- **FR-5:** Catalog releases activate atomically within a Fly release: a new deploy either fully replaces the catalog image or does not; there is no half-swapped read; there is no writer at runtime; rollback is redeploy of the prior image (ADR-0004 §"Catalog database on Fly"). `UserRepo` cannot be modified by catalog activation because `UserRepo` does not exist server-side (FR-3).

Browser store exit-gate conditions:

- **FR-6:** The browser storage subsystem opens `dos_local` (IndexedDB) with the ADR-0004 object stores (`meta` singleton, `vehicles`, `events`, `readings`, `reminders`, `prefs` singleton), a monotonic `schema_version` owned by the server, and forward-only migrations (`LocalStore.Migrations.migrate/3`) unit-tested against recorded fixtures of every prior version. Downgrading or dropping unknown fields is prohibited; a client payload newer than the server's version puts the server in read-only mode with an explicit banner and mutations disabled (ADR-0004 §"Schema versioning and migration"). `localStorage` holds only the non-personal `dos_boot_state` hint (ADR-0004 §"Storage layout").
- **FR-7:** LiveView mount renders `assigns.local_state = :hydrating` as a skeleton; the states `:hydrating`, `:empty`, `:data_missing`, and `:storage_unavailable` are distinct and render differently; the UI MUST NOT flash "You have no vehicles yet" while hydrating; a stored `dos_boot_state == "has_data"` returning zero records renders `:data_missing`, not an empty state (INV-24.3, INV-25; ADR-0004 §"First-paint and empty-state rules").
- **FR-8:** Every mutation is a `pushEvent` → server assigns → `local_store:put` → IndexedDB `readwrite` transaction with compare-and-set on `meta.seq` → `local_store:ack` round trip. A mutation is not rendered as committed until the ack arrives; failed or missing acks (default 2 000 ms deadline) render a persistent, non-dismissible "Not saved to this browser" state on the affected record, keep the optimistic value visible but visibly marked unsaved, and offer export (INV-24.2; ADR-0004 §"Mutation round trip").
- **FR-9:** Hydration input is validated as untrusted client input through explicit embedded-schema changesets per `schema_version`; hard caps (≤ 1 MiB decoded payload, ≤ 200 vehicles, ≤ 5 000 events, ≤ 20 000 readings) are rejected explicitly and never silently truncated; validation failure is never fatal to the session (valid subset hydrates, invalid records go to a quarantine list surfaced with export of the raw payload) (ADR-0004 §Validation).
- **FR-10:** Multi-tab consistency: a `BroadcastChannel("dos_local_store")` per tab broadcasts `{seq, mutation_id, tab_id}` on successful commit; receiving tabs re-hydrate when the broadcast `seq` is ahead of their last-known `seq`; every write is a compare-and-set on `meta.seq` inside the same transaction (a stale `seq` aborts the transaction and triggers `local_store:conflict`); conflict resolution is last-write-wins at record granularity with the loss made visible (INV-24.7; ADR-0004 §"Multi-tab consistency"; Constitution §9 two-tab mutation test).
- **FR-11:** IndexedDB availability is probed at runtime (open + write/read/delete round trip). On unavailable or blocked storage the app enters **session-only mode** with a persistent banner and prominent, repeated export offer; there is no silent fallback to `localStorage` for records and no fallback to server storage (INV-24.6; ADR-0004 §"Private browsing and blocked storage").
- **FR-12:** After the user's first meaningful write the hook calls `navigator.storage.persist()` once and records the boolean result in `meta.persist_granted`, which is reflected honestly in the storage-status UI (a grant is **never** described as a backup); `navigator.storage.estimate()` is read on hydration and >80% usage surfaces export/pruning guidance; `QuotaExceededError` follows the failed-ack path with a quota-specific message (INV-24.4, INV-24.5; ADR-0004 §"Quota and eviction").

Portability, privacy, and matrix exit-gate conditions:

- **FR-13:** Export produces a browser-generated `Blob` download named `digital-oil-sticker-export-YYYYMMDD.json` carrying the ADR-0004 envelope and a SHA-256 content hash; import reads via file input, hash-checks, and pushes as a normal `local_store:hydrate` (so it inherits FR-9 validation and FR-6 migration); import is explicitly replace or merge, chosen by the user with counts previewed before commit; the copy contract in ADR-0004 §"Export and import" holds (prohibited: "backup", "synced", "safe", "we'll remember", "your account"; required: an always-reachable statement that data lives in this browser only). Erasure clears both IndexedDB and `localStorage` (INV-5, INV-25).
- **FR-14:** Hosted transport (INV-22): HTTPS with HSTS (enabled only after certs are verified for both hostnames); WSS for the LiveView socket via `/live/websocket`; `check_origin` set to an explicit host list (never `true` and never `false`); Phoenix `protect_from_forgery` on all HTTP routes and LiveView `_csrf_token` verified on connect; session cookie signed, `secure`, `http_only`, `same_site: "Lax"`, short `max_age`, and carrying **no** personal data and no stable user identifier; the ADR-0004 §"Content Security Policy" served on every response with no `'unsafe-inline'`; `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and a `Permissions-Policy` denying geolocation, camera, microphone, and payment.
- **FR-15:** Server logs MAY contain the ADR-0004 §Logging allowlist (timestamp, HTTP method/path/status/duration for non-LiveView routes, LiveView event *name* only, error type and stacktrace, release version, machine ID, coarse counters); MUST NOT contain any VIN, odometer or mileage value, service date, note text, custom vehicle name, the specific vehicle a session selected, any hydration/mutation/import/export payload or fragment, the `tab_id`, or the full client IP. Enforced by the ADR-0004 §Enforcement scripted-session log-scanning release gate, plus `filter_parameters`, a Logger filter with an explicit allowlist for non-personal events, and `debug_errors: false` in production. LiveDashboard is disabled in production.
- **FR-16:** The certified conformance suite passes on the ratified browser support matrix (Constitution §9: current and prior stable release of Chrome, Edge, Firefox, and Safari desktop, plus iOS Safari 16+ and Android Chrome), including hydration, forward-schema migration, quota exhaustion, ITP-style eviction, private-mode refusal, multi-tab writes, and export/import round trips — scoped to `DOS-M04-010` and coordinated with the proposed `DOS-M09-009` browser-support-matrix work. ## Technical implementation contract

### Components and ownership boundaries

Epic-level tracking issue. Component ownership per child:

- **Server side (Fly.io deploy image):** `DigitalOilSticker.CatalogRepo` opened read-only (`DOS-M04-001`, `DOS-M04-004`); catalog SQL schema and build-time migrations (`DOS-M04-002`); server boot and health signal before traffic (`DOS-M04-006` server half); atomic catalog activation via Fly release (`DOS-M04-008`).
- **Browser side (client hook + IndexedDB):** the `LocalStore` `phx-hook` and IndexedDB adapter (`DOS-M04-005`); object-store layout and indexes (`DOS-M04-003`); `onupgradeneeded` forward-only migration executor (`DOS-M04-007`); export/import via browser File APIs plus erasure (`DOS-M04-009`).
- **Seam (LiveView protocol):** hydration mount sequence, mutation round trip, multi-tab compare-and-set, private-browsing/quota/eviction paths — architecturally owned by the proposed `DOS-M09-003` hydration protocol card and consumed by `DOS-M04-005` (client hook) and `DOS-M04-006` (client boot).
- **Certification:** `DOS-M04-010` — browser/engine conformance, quota/eviction/private-browsing/multi-tab drills, privacy log-scan on the deployable Fly image.

### Data and persistence

**Server:** exactly one Ecto repo, `CatalogRepo`, `Ecto.Adapters.SQLite3`, opened read-only, `pool_size: 1`, baked into the deploy image (ADR-0004 §"Catalog database on Fly"). No volume. No Postgres. The catalog is a build artifact, not runtime state; a catalog release is a deploy.

**Client:** origin-scoped IndexedDB database `dos_local` with the ADR-0004 object stores (`meta`, `vehicles`, `events`, `readings`, `reminders`, `prefs`). Record keys are client-generated UUIDv4; `meta` and `prefs` are singleton stores. `localStorage` holds only the non-personal `dos_boot_state` hint (one of `"never"`, `"has_data"`).

Catalog foreign IDs in client records are deliberately not database foreign keys (there is no cross-database FK path anywhere); records retain a display/product/schedule **snapshot** of the referenced catalog row so history remains intelligible after a catalog release changes or withdraws a configuration (INV-11 `unsupported` is rendered honestly rather than as a UI error).

### Interfaces and events

Named events on the LiveView socket, all defined in ADR-0004 §"The client-storage + LiveView hydration protocol":

- `local_store:hydrate` (client → server): the envelope carrying `schema_version`, `seq`, `tab_id`, `generated_at`, and `data`; subject to FR-9 validation.
- `local_store:put` (server → client): server-computed `{mutation_id, seq, upserts: [...], deletes: [...]}` applied within one `readwrite` transaction spanning the affected stores plus `meta`.
- `local_store:ack` (client → server): confirms or reports the write; deadline 2 000 ms.
- `local_store:conflict` (client → server): compare-and-set on `meta.seq` failed; triggers re-hydration.

`BroadcastChannel("dos_local_store")` is a browser-internal channel and carries no server involvement (ADR-0004 §"Multi-tab consistency").

### Failure and recovery behavior

Aggregate expectations: hydration is idempotent (identical payload twice → identical assigns, no write-back — verified by the ADR-0004 §Enforcement test); a deploy is a disconnect + remount + re-hydrate (FR-16); a failed ack does not roll back invisibly (FR-8); a quota-exceeded write does not silently drop data (FR-12); an unavailable IndexedDB does not silently fall back to fake durability (FR-11); export is the sole recovery mechanism and the UI says so unprompted (FR-13; INV-5, INV-25). Server-side, there is no personal state to lose on machine replacement, secret rotation, or scale event — a genuine architectural property, not a hardening test.

### Security and privacy

Hosted transport per INV-22 and ADR-0004 §"Security and privacy boundary for a hosted application" (transport, CSRF/session, CSP, no third-party anything, rate limiting, log redaction). The single most important structural claim — **no personal data on the server** — is enforced by FR-3's empty-repo-list release gate, by FR-4's domain-namespace static check, by FR-15's log-scanning gate, and by FR-17's query-surface check. Overclaiming is avoided: the operator retains the technical capability to inspect a live socket's assigns via `fly ssh console`, and the privacy page states this rather than claiming otherwise (ADR-0004 §"LiveDashboard and operator access — stated honestly").

### Accessibility and performance

The hydration and honest-degradation states defined by FR-7/FR-11/FR-13 must meet WCAG 2.2 AA per Constitution §9 accessibility, with live-region announcement of hydration and due-state changes. Performance budgets in scope for this epic: hydration completion (Constitution §9: p95 ≤ 300 ms after socket join), first-visit payload budget (≤ 250 KiB compressed HTML/CSS/JS with zero third-party origins), client storage footprint (≤ 1 MiB per 1 000 text-only records, ≤ 5 MiB working ceiling), and the two-tab mutation test. Pre-pivot physical-device budgets (cold tap-to-interactive, warm start, on-device Phoenix readiness, packaged app size, bundled catalog size, minimum supported OS, airplane-mode readiness) are **removed** per Constitution 2.0.0 §9.

## UX and content states

Epic-level tracking issue with no direct UI. Children specify the honest states the M05 screens surface: `:hydrating` skeleton, `:empty` (verified after a successful hydrate), `:data_missing` (had-data boot hint but empty store), `:storage_unavailable` (open failed or probe failed), unsaved-mutation state (ack timeout), stale-deployment banner (client payload newer than server `schema_version`), and quota-approaching / quota-exhausted messaging. Prohibited copy: "backup", "synced", "safe", "we'll remember", "your account" (ADR-0004 §"Export and import"; INV-5, INV-21, INV-25). Required copy: an always-reachable statement that data lives in this browser only and that clearing browser data deletes it permanently.

## Risks, decisions, and open questions

- **Risk (ADR-0004 R1):** browser storage eviction (Safari ITP ~7 days on unvisited sites; Chrome eviction under pressure; browser-vendor policies for infrequently-visited sites). The natural cadence of this product — quarterly oil-change checks — is exactly the profile most at risk. Mitigations owned in this epic: `navigator.storage.persist()` request (FR-12), honest storage-status UI (FR-7, FR-11), `:data_missing` state distinct from `:empty` (FR-7), and export nudges after meaningful writes (FR-12, FR-13). Actual per-browser eviction behavior must be **measured** in `DOS-M04-010`, not assumed from documentation.
- **Risk (ADR-0004 R2):** hydration round trip adds latency to first meaningful paint on every mount, including every reconnect. Mitigation: FR-16 measurement against Constitution §9 (hydration p95 ≤ 300 ms after socket join; TTI p75 ≤ 3.5 s).
- **Risk (ADR-0004 R4):** multi-tab conflict resolution is last-write-wins at record granularity. Accepted for MVP under the single-user assumption, with losses made visible (FR-10). Open question: whether any real workflow (two tabs, one logging a service, one editing it) makes this materially wrong; re-examine on evidence.
- **Risk:** commercial data licensing may lag; **and post-pivot, sources cleared under 1.0.0 for offline redistribution must be re-reviewed for hosted-serving rights** per INV-15 amended emphasis and ADR-0004's new §"ADR-0003 → Unchanged" obligation. Impact on this epic is bounded: a source being unavailable reduces catalog surface area but does not block the repo/store/hydration mechanics.
- **Decision (ratify in `DOS-M04-001`):** single read-only server `CatalogRepo` + browser `dos_local` IndexedDB + ADR-0004 hydration protocol.
- **Decision (ratify in `DOS-M04-001`):** no server-side personal storage of any kind — enforced structurally by FR-3, FR-4, FR-15, and FR-17.
- **Open question (owned by `DOS-M04-009` ADR):** import policy — replace-after-backup and/or deterministic merge-by-UUID; must be decided before FR-13 evidence closes.
- **Open question (owned by `DOS-M04-010` ADR):** final ratified page-load, hydration, server-response, catalog-query, payload, and client-storage budgets replacing Constitution §9's *provisional* values.
- **Open question (roadmap governance):** the pivot doc's proposed M09 milestone and its ten issues must be ratified into the roadmap; until then this epic's Preconditions and Dependency rationale cite proposal IDs, not ratified card IDs.
- **Deferred decisions this epic does not re-open:** Web Push, service worker/PWA offline caching, native mobile revival — each requires its own ADR and constitution revision (INV-17, INV-19, INV-1 as amended).
