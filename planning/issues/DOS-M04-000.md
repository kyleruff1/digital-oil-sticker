## Outcome

Implement separate read-only catalog and mutable user-data persistence boundaries that work offline, survive upgrades/crashes, support multiple vehicles from day one, and require no online account or server-side personal-data store.

At epic close, the on-device persistence layer of Digital Oil Sticker is complete and certified: `DigitalOilSticker.CatalogRepo` and `DigitalOilSticker.UserRepo` are separate `Ecto.Repo` processes using `Ecto.Adapters.SQLite3`, distinct files, and `pool_size: 1`; the bundled catalog installs and upgrades atomically with rollback; `UserRepo` boot migrations preserve data; export/import recovery works; and the whole contract passes on packaged builds on the minimum supported physical iOS and Android devices.

## Why this matters and what it unblocks

Every MVP feature — vehicle selection, oil-change history, odometer check-ins, forecasting, and reminders — reads and writes through the boundaries this epic delivers. The product's non-negotiable rules (no online accounts, offline from first launch, one-vehicle MVP with multi-vehicle-safe internals) are enforced structurally here, in the schema and repository contracts, rather than by UI discipline alone. Closing this epic unblocks M05 (Single-vehicle MVP) and, through it, M06 (Forecasting and reminders); it also provides the durable persistence substrate that M07 hardening validates and that M08 catalog updates extend. Failure to separate catalog and user storage now would make catalog updates destructive to user history and would force a rewrite before multi-vehicle support.

## Included

Child issues tracked by this epic:

- `DOS-M04-001` — Approve the Mob/Ecto dual-repository persistence ADR: pin Mob 0.7.20 + Ecto + `ecto_sqlite3` architecture, dual repos with `pool_size: 1`, native paths, boot sequence, and no-server-account rule.
- `DOS-M04-002` — Implement versioned catalog SQL schema and build-time migrations: encode the proposed catalog schema as deterministic, migration-tested SQL the M03 compiler populates and `CatalogRepo` opens read-only.
- `DOS-M04-003` — Implement multi-vehicle-safe user SQL schema and invariants: fresh `UserRepo` supporting one local profile, any number of vehicles, history, usage profiles, forecast snapshots, reminder rules, scheduled notifications, and catalog-install metadata.
- `DOS-M04-004` — Implement deterministic, read-only `CatalogRepo`: typed, deterministic catalog query interface with pagination, ordering, provenance, and no SQL/storage knowledge in domain/UI code.
- `DOS-M04-005` — Implement transactional, vehicle-scoped `UserRepo`: atomic, typed, multi-vehicle-safe mutation boundary for all local user workflows including `record_oil_change`.
- `DOS-M04-006` — Bootstrap dual on-device Ecto SQLite repos and durable native files: native storage paths, supervision/boot coordinator, lifecycle/durability handling, low-space and containment safety.
- `DOS-M04-007` — Run `UserRepo` Ecto migrations safely at device boot: bundled `Ecto.Migrator` migrations with backup, recovery marker, and never-reset guarantees.
- `DOS-M04-008` — Install and atomically upgrade the catalog from the native app bundle: verify, stage, atomically activate, and roll back the bundled catalog without network access or risk to `UserRepo`.
- `DOS-M04-009` — Implement versioned local export/import and user-controlled erasure: portable user-data backup envelope, safe restore on clean install, and account-free delete-all.
- `DOS-M04-010` — Certify Ecto repository conformance, integrity, privacy, and physical-device budgets: the epic's release-gate evidence on packaged physical iOS and Android apps.

Epic-level tracking also includes: keeping the child dependency edges current, collecting each child's attached evidence, and confirming the exit criteria below before closing.

## Excluded

- Any PWA/browser/OPFS/IndexedDB/WASM database, Netlify-hosted Phoenix runtime, cloud accounts/sync, or remote application server (per child exclusions and §4.3).
- End-user network catalog updates, signed online catalog fetch, delta patches, or remote signature/key workflows — these belong exclusively to M08.
- Forecasting algorithm content (M06), OS notification scheduling implementation (M06), and user-facing LiveView feature screens (M05).
- Multiple SQLite pool connections (`pool_size > 1`) in any configuration.
- Placing mutable user rows in the catalog database, or any remotely served user identity/session requirement in the repository interface.
- Work not stated in a child issue's Included scope (change control: discoveries become a new issue or ADR).

## Dependency rationale

Position in the M00→M08 DAG: M04 is blocked by M01 (engineering foundation: repository, CI, and test scaffolding that all child suites run on) and by M03 (the vocabulary/stable-ID contract `DOS-M03-002` that the catalog schema and crosswalks consume, and later the compiled release candidate `DOS-M03-010` that the installer and certification consume). M04 in turn blocks M05 (Single-vehicle MVP screens are built on the `CatalogRepo`/`UserRepo` contracts), which blocks M06 (forecasting/reminders persist through `usage_profiles`, `forecast_snapshots`, `reminder_rules`, and `scheduled_notifications` delivered here). M07 hardening consumes M04's certification evidence, and M08's signed online catalog updates reuse the atomic install/rollback protocol proven in `DOS-M04-008`. Within the epic, `DOS-M04-001` blocks all other numbered issues, and `DOS-M04-010` closes the epic only after every other child closes. Per §12, a downstream issue is not Ready merely because work could be prototyped; native blockers and source rights remain authoritative.

## Risks, decisions, and open questions

- Risk: Mob 0.7.20 is pre-1.0; SQLite feature availability (WAL behavior, FTS5, `STRICT`) on packaged builds may differ from host assumptions. Mitigation: `DOS-M04-002` verifies features against the exact packaged SQLite/Exqlite versions; `DOS-M04-006` proves durability on physical devices; portable shadow columns are the fallback.
- Risk: commercial data licensing may lag. Mitigation locked in the catalog: at every gate, a source being unavailable reduces data-backed features; it does not block development against synthetic fixtures, local user-entered values, repository interfaces, or offline persistence — but it does block any production claim based on that source.
- Decision (made, ratify in `DOS-M04-001`): dual SQLite repos, `pool_size: 1`, no cross-database foreign keys, snapshot-plus-stable-key user rows.
- Open question (owned by `DOS-M04-001`): OS backup inclusion policy per durability class.
- Open question (owned by `DOS-M04-009` ADR): import policy — `replace after backup` and/or deterministic merge by UUID.
- Open question (owned by `DOS-M04-010` ADR): final absolute size/latency/memory budgets replacing the candidate values.
