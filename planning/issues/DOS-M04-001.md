> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The ADR must now cover server CatalogRepo plus browser UserStore plus the hydration/mutation protocol, and state as a MUST that no personal row is ever written server-side._

## Outcome

This card is the ratification gate for the **browser-MVP dual-store persistence architecture** as fixed by [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md). Closing it means all four of the following are true and reviewed together:

1. **ADR-0004 is accepted, merged, and pointed at by this card as the authoritative artifact** — replacing ADR-0001 as the ratified persistence architecture for the MVP. ADR-0001 is moved to `Deferred — superseded for MVP by ADR-0004; retained for a future native client` per ADR-0004 §"What this supersedes"; its analysis is preserved for the native re-entry set (this card's historical section below), not repudiated.
2. **The dual-store shape is written down and cited as a MUST**: the server owns a single read-only Ecto repo, `DigitalOilSticker.CatalogRepo`, opened read-only against a catalog-only SQLite file baked into the deploy image (ADR-0004 §"Catalog database on Fly"; Constitution 2.0.0 INV-23); the browser owns the anonymous personal `UserStore`, an origin-scoped IndexedDB database (`dos_local`) whose object-store layout, key strategy, and forward-only version line are specified in [DOS-M09-001](DOS-M09-001.md) and implemented by [DOS-M09-002](DOS-M09-002.md).
3. **The hydration/mutation protocol between the two stores is ratified** as the specified seam (ADR-0004 §"The client-storage + LiveView hydration protocol"; Constitution 2.0.0 INV-24 and its sub-clauses INV-24.1–INV-24.8): mount-unhydrated → hook reads IndexedDB → validated envelope pushed into `socket.assigns` for the socket lifetime only → every mutation is a `local_store:put` → `local_store:ack` round trip that is not rendered as committed until the hook acknowledges → reconnects re-hydrate → multi-tab consistency is enforced by compare-and-set on `meta.seq`. The protocol is owned by [DOS-M09-003](DOS-M09-003.md); this card ratifies that it is the ADR-blessed seam.
4. **The absence-of-personal-server-rows invariant is stated as a MUST in the ratified document and is release-gated by an executable test.** ADR-0004 §Decision 4 and §Enforcement, and Constitution INV-23, both bind that the deployed application has exactly one Ecto repo (`CatalogRepo`), opened read-only, with no `UserRepo`, no personal-data table, no personal-data migration, and no personal-data backup job. This card is not closed until the release-gating assertion owned by [DOS-M09-007](DOS-M09-007.md) FR-13 / AC-9 is present in the deployed application's CI: the runtime Ecto repo list on the packaged Fly release digest is exactly `[DigitalOilSticker.CatalogRepo]`, its connection is opened read-only, and a schema/migration scan finds no personal-data table.

The deliverable is the ratification plus the ADR-index update; the implementation cards are the M09 children listed under Preconditions and Dependency rationale. The physical-iOS/Android proof from the pre-pivot Outcome is retired and replaced by the browser-MVP evidence set defined in Acceptance criteria.

## Why this matters and what it unblocks

The M04 milestone was chartered to fix a **single** on-device architecture and thereby unblock every other M04 child. Under ADR-0004 the location of the persistence has moved: `CatalogRepo` is server-side and read-only, and the personal store is a browser subsystem specified by the M09 issues. Until a card exists that formally names ADR-0004 as the ratified persistence architecture, three concrete failures follow:

- **Downstream M04 children stay blocked on a dead pointer.** Per [ROADMAP_LEDGER.md](../../docs/governance/ROADMAP_LEDGER.md) and [`planning/roadmap.yml`](../../planning/roadmap.yml), the re-scoped M04 children (`DOS-M04-002` through `DOS-M04-010`) all inherit paths, supervision boundaries, error semantics, and the no-server-personal-row rule from this decision. Leaving the card pointed at ADR-0001 leaves them blocked on a superseded artifact (see finding #1 below).
- **The header of the milestone becomes permanently unpassable.** The pre-pivot AC-2 required a packaged debug build on physical iOS and Android hardware; ADR-0004 records that the iOS half is unreachable ("No Mac and no Xcode") and DOS-M00-003 is "suspended, not passed and not failed", so with this card blocking every other M04 issue the milestone stalls indefinitely (finding #2).
- **FR-2 and the pre-pivot repo shape contradict a release gate that already exists.** ADR-0004 §Enforcement and DOS-M09-007 FR-13 both require a test asserting the deployed application's Ecto repo list is exactly `[CatalogRepo]`, which a ratification that still names `UserRepo` would fail at CI (finding #3).

This card rescopes those three failure modes into gates the milestone can actually pass, and anchors the invariants that every downstream card cites (INV-3, INV-23, INV-24, INV-25, INV-26, INV-27).

## Functional requirements

- **FR-1 (retires pre-pivot FR-1; addresses finding #3):** The ratified architecture pins the runtime dependency set for a **hosted Phoenix LiveView on Fly.io**, not for an on-device Mob 0.7.20 runtime. `mix.lock` pins Elixir/OTP, Phoenix, `phoenix_live_view`, Bandit (or Cowboy), `ecto_sql`, `ecto_sqlite3`, Exqlite, esbuild, and Tailwind at versions compatible with the Fly deploy target; the ADR-index entry records the Docker base image and `flyctl` versions covered by [`DOS-M01-001`](DOS-M01-001.md) and [`DOS-M09-006`](DOS-M09-006.md). Mob 0.7.20, `mob_notify`, `mob_dev`, and `mob_new` are **not** MVP runtime dependencies; the pinned toolchain matrix for the native track is preserved in the historical section for the future ADR-0005 (ADR-0004 §"Trigger conditions that revive the native track").
- **FR-2 (replaces pre-pivot FR-2; addresses findings #1 and #3):** The deployed application defines **exactly one Ecto repo**: `DigitalOilSticker.CatalogRepo`, using `use Ecto.Repo, otp_app: :digital_oil_sticker, adapter: Ecto.Adapters.SQLite3`, `pool_size: 1`, opened **read-only** against the catalog SQLite file baked into the Fly release image (ADR-0004 §"Catalog database on Fly"). There is **no `DigitalOilSticker.UserRepo`** in the deployment, no personal-data table, no personal-data migration, and no personal-data backup job (Constitution INV-23; ADR-0004 §Decision 4). The connection is opened with the read-only open mode where `ecto_sqlite3` supports it and always runs `PRAGMA query_only = ON`.
- **FR-3 (replaces pre-pivot FR-3 and FR-4; addresses finding #3):** The catalog file lives inside the deploy image at a documented image-relative path; there is no runtime writable location for it, no volume, no pointer file, no staging directory, and no OS-specific `Application Support`/files-dir path resolution. Rollback is a redeploy of the previous image (ADR-0004 §"Catalog database on Fly" table row "Rollback"). Logs never contain the raw file path; they log the release digest and the catalog `data_version` instead.
- **FR-4 (new, browser-first counterpart to the pre-pivot FR-3/FR-4):** The **browser `UserStore`** is the sole home for personal data. It is the origin-scoped IndexedDB database `dos_local` with the object stores listed in ADR-0004 §"Storage layout" (`meta`, `vehicles`, `events`, `readings`, `reminders`, `prefs`); `localStorage` holds nothing but the non-personal boot hint `dos_boot_state`. The schema, key strategy, and forward-only version line are owned by [`DOS-M09-001`](DOS-M09-001.md); the adapter is owned by [`DOS-M09-002`](DOS-M09-002.md).
- **FR-5 (replaces pre-pivot FR-5; addresses finding #1):** The application boot sequence has two halves that meet at the hydration protocol, not one on-device sequence. **Server boot:** the Fly release starts, opens `CatalogRepo` read-only against the image-baked catalog file, runs a health check that asserts a known-row-count catalog query, and only then serves traffic (owned by [`DOS-M09-006`](DOS-M09-006.md)). **Client boot:** on LiveView mount the JS hook opens `dos_local`, reads all object stores in one readonly transaction, and `pushEvent`s the versioned envelope; the server places the validated envelope in `socket.assigns` and transitions `assigns.local_state` from `:hydrating` to `:loaded`, `:empty`, `:data_missing`, or `:storage_unavailable` per ADR-0004 §"Mount and hydration sequence" and §"First-paint and empty-state rules" (owned by [`DOS-M09-003`](DOS-M09-003.md)). The pre-pivot `Ecto.Migrator` / `DigitalOilSticker.Boot` on-device stage sequence is retired.
- **FR-6 (new; MUST):** The ratified architecture states as a **MUST** that no personal row is ever written server-side. Personal data lives in the browser `UserStore` and, transiently, in `socket.assigns` for the lifetime of one LiveView connection; it is never written to any database, cache, ETS table, external store, cookie, or log (Constitution INV-3, INV-4, INV-23, INV-24.1; ADR-0004 §Decision 4). Session cookies contain only framework CSRF and socket-identification material; no VIN, no odometer value, no vehicle identifier, no anonymous user ID, and no value that could correlate one visit to another (INV-22; ADR-0004 §"CSRF and session").
- **FR-7 (new):** The **hydration protocol** is ratified as the seam between server catalog reads and browser personal storage, with the payload envelope, mount and hydration sequence, first-paint and empty-state rules (`:hydrating` ≠ `:empty` ≠ `:storage_unavailable` ≠ `:data_missing`), server-side validation as untrusted client input with hard caps (≤ 1 MiB decoded, ≤ 200 vehicles, ≤ 5 000 events, ≤ 20 000 readings), schema versioning and forward-only migrations with write-back in the same round trip, newer-than-server payloads entering read-only mode with an explicit banner, and multi-tab compare-and-set on `meta.seq` all owned by [`DOS-M09-003`](DOS-M09-003.md) and specified in full in ADR-0004.
- **FR-8 (new):** The **mutation round trip** is normative: user act → `handle_event` → server assigns a `mutation_id` and next `seq`, records it in `assigns.pending_writes`, renders optimistically with a "saving" affordance → `push_event` `local_store:put` → hook opens one `readwrite` transaction across affected stores plus `meta`, performs the compare-and-set on `meta.seq`, applies the changes, commits → hook `pushEvent`s `local_store:ack` → server clears the pending write and renders the saved state. **A mutation MUST NOT be rendered as committed until the hook acknowledges it** (Constitution INV-24.2; ADR-0004 §"Mutation round trip"). A missing or errored ack surfaces a persistent "Not saved to this browser" state and offers export.
- **FR-9 (new):** The **impersonal catalog-query surface** rule is ratified: every server-side query into `CatalogRepo` takes catalog identifiers only (year, make, model, engine, `configuration_id`, `oil_family_id`, `filter_part_number`) and never takes a VIN, odometer value, service date, note text, vehicle identifier from the user's garage, or any stable client identifier (Constitution INV-26; ADR-0004 §"Rate limiting and abuse"). The query layer that enforces this is owned by [`DOS-M09-005`](DOS-M09-005.md).
- **FR-10 (replaces pre-pivot FR-9):** The typed error taxonomy is **split along the new boundary**. Server-side catalog errors: `not_ready`, `not_found`, `invalid_input`, `unsupported`, `read_only`, `catalog_unavailable`, each with recoverability metadata. Client-side storage errors surfaced back to the server: `storage_unavailable` (INV-24.6, private-browsing or blocked storage), `quota_exceeded` (INV-24.5), `evicted` (INV-24.4), `newer_than_server` (INV-24 schema-migration rule), `conflict` (INV-24.7 multi-tab compare-and-set failure), `data_missing` (INV-24.8 cleared-storage state). Every error carries recoverability metadata; the on-device `insufficient_space`, `permission_denied`, and `transaction_failed` codes from the pre-pivot taxonomy are retired.
- **FR-11 (replaces pre-pivot FR-10):** All catalog result lists specify a total order/cursor contract so that hydration is idempotent and multi-tab re-hydration is deterministic (Constitution INV-24; ADR-0004 §Enforcement item "A test that hydration is idempotent"). The pre-pivot claim "no runtime function requires the network to read or write core data" is **retired** and replaced by the honest ADR-0004 statement in §Consequences ("Lost — honestly"): the MVP requires connectivity to reach the app and to query the catalog; the user's own records in `UserStore` remain in the browser but are not readable without a LiveView connection to render them.
- **FR-12 (rewrites pre-pivot FR-11):** A static architecture check rejects direct SQL access outside approved persistence modules **and** enforces the domain-namespace decoupling required by ADR-0004 §Decision 6: no module under the domain namespaces (`DigitalOilSticker.Catalog`, `.Garage`, `.Forecast`, and the resolver) references `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules. This is the mechanical guarantee that a future native client can reuse the same domain contexts (owned by [`DOS-M09-003`](DOS-M09-003.md) and [`DOS-M09-008`](DOS-M09-008.md)).
- **FR-13 (replaces pre-pivot FR-6; addresses finding #1):** The **no-server-account rule** is stated in ADR-0004 §Decision 3 and Constitution INV-3: no email/password, remote session, remote sync, analytics identity, push token, or durable server-side identifier of any kind exists in the deployed application. LiveView connects only to the hosted Phoenix endpoint at `digitaloilsticker.com` over WSS with CSRF verification (INV-22).
- **FR-14 (new):** The **portability contract** is ratified: versioned export/import is the sole recovery mechanism and the only way personal data ever leaves the browser (Constitution INV-4, INV-5, INV-25; ADR-0004 §"Export and import"). Export is produced entirely in the hook, wraps the same envelope shape as hydration, appends a SHA-256 content hash, and is delivered as a `Blob` download; import is read in the hook, parsed, hash-checked, then pushed as a normal `local_store:hydrate` so it inherits validation and migration. Import is explicitly **replace** or **merge**, chosen by the user, previewed with counts. Prohibited words in this UI: "backup", "synced", "safe", "we'll remember", "your account". The implementation is owned by [`DOS-M04-009`](DOS-M04-009.md) (re-scoped for browser File APIs).
- **FR-15 (new):** The **release-gating tests** required by ADR-0004 §Enforcement are ratified as MVP release blockers and are owned as follows:
  - Runtime assertion that the deployed application's Ecto repo list is exactly `[DigitalOilSticker.CatalogRepo]` and that its connection is opened read-only — owned by [`DOS-M09-007`](DOS-M09-007.md) FR-13 / AC-9.
  - Schema/migration scan asserting no personal-data table, personal-data migration, or personal-data backup job exists anywhere in the application — owned by [`DOS-M09-007`](DOS-M09-007.md) FR-13.
  - Static check that no domain-namespace module references `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules — owned by [`DOS-M09-003`](DOS-M09-003.md).
  - Scripted-session log-scan test asserting no VIN, odometer value, service date, note text, or custom vehicle name appears in any captured log line during a full hydrate → mutate → export → clear → import session — owned by [`DOS-M09-007`](DOS-M09-007.md) FR-11 and [`DOS-M09-008`](DOS-M09-008.md) FR-17.
  - Hydration-idempotence test: hydrating the same payload twice produces identical assigns and emits no write-back — owned by [`DOS-M09-003`](DOS-M09-003.md) and [`DOS-M09-008`](DOS-M09-008.md) FR-9.
- **FR-16 (replaces pre-pivot FR-7; retires OS-backup decision):** ADR-0004 §Consequences records that browser storage is erasable by parties other than the user (site-data clearing, ITP-style eviction, private-browsing, quota pressure, different browser/profile/device); the pre-pivot OS-backup durability-class decisions are **retired** because there is no OS backup surface. Honest storage-loss messaging is specified by Constitution INV-25 and rendered by the state copy owned by [`DOS-M09-004`](DOS-M09-004.md).
- **FR-17 (new; addresses finding #2):** The **browser-MVP evidence set** replaces the pre-pivot physical-iOS/Android proof. Evidence for AC-2 below is the packaged Fly release digest, the CI output of the FR-15 release-gating tests against that digest, and a captured LiveView session against a running deploy that exercises hydrate → mutate → export → clear → import. The physical-device matrix is preserved in the historical section for a future ADR-0005 revival.

## Technical implementation contract

### Components and ownership boundaries

- **`DigitalOilSticker.CatalogRepo`** is the only `Ecto.Repo` module in the deployed application (FR-2, FR-6). It is owned by the server-side persistence layer.
- **Browser `UserStore`** (the `dos_local` IndexedDB database) is owned by [`DOS-M09-002`](DOS-M09-002.md); its schema is owned by [`DOS-M09-001`](DOS-M09-001.md); its hydration/mutation protocol is owned by [`DOS-M09-003`](DOS-M09-003.md).
- **Domain contexts** (`DigitalOilSticker.Catalog`, `.Garage`, `.Forecast`, and the resolver) are the only consumers of `CatalogRepo` on the server and of hydrated `socket.assigns` on the LiveView side; they have no dependency on `Phoenix.LiveView`, on the browser-storage protocol, or on any transport (ADR-0004 §Decision 6; FR-12).
- **The hydration protocol modules** (`DigitalOilSticker.LocalStore` server side + the `LocalStore` JS hook client side) are the sole seam between server catalog reads and browser personal storage; owned by [`DOS-M09-003`](DOS-M09-003.md).
- **ADR-0004** is the single ratified source for this architecture; it lives at `docs/architecture/ADR-0004-browser-first-client-and-hosting.md` and is pointed at by every M04 child and by the M09 implementation cards.

### Data and persistence

- One SQLite catalog file baked into the Fly release image; no volume, no runtime writable copy, no staging swap, no pointer file. Read-only open mode where `ecto_sqlite3` supports it; `PRAGMA query_only = ON` always. Catalog replacement is a deploy; rollback is a redeploy of the previous image.
- The browser `UserStore` layout (object stores, keys, indexes) is defined by [`DOS-M09-001`](DOS-M09-001.md) and reflected in ADR-0004 §"Storage layout".
- No cross-database, cross-boundary, or cross-transport foreign keys. The `UserStore` records stable catalog reference keys plus readable snapshots from the catalog vocabulary ratified by [`DOS-M03-002`](DOS-M03-002.md).

### Interfaces and events

- `CatalogRepo` behaviors take catalog identifiers only (FR-9); the exhaustive behavior list is finalized in [`DOS-M04-004`](DOS-M04-004.md) and is impersonal by construction — no argument type accepts a VIN, odometer value, or user-vehicle identifier.
- Hydration and mutation events between the LiveView and the hook are the ADR-0004 envelope: `local_store:hydrate`, `local_store:put`, `local_store:ack`, `local_store:conflict`, plus the export/import controls owned by [`DOS-M04-009`](DOS-M04-009.md).
- Errors map to the FR-10 taxonomy with recoverability metadata; downstream cards may extend it (`validation`, `unsupported`) but MUST NOT introduce a code that implies server-side personal storage.
- Boot readiness is exposed as an observable server-side `:ready` state (server catalog boot only) and an observable per-mount `assigns.local_state` (`:hydrating` → `:loaded`/`:empty`/`:data_missing`/`:storage_unavailable`).

### Failure and recovery behavior

- **Server-side:** a catalog-open failure or a failed health-check row-count assertion fails the Fly release health check and traffic is not moved to the new machine (owned by [`DOS-M09-006`](DOS-M09-006.md)); the previous release keeps serving.
- **Client-side:** a missing hydrate event within the deadline yields `assigns.local_state = :storage_unavailable`, which is a **different** state from `:empty` and renders differently (INV-24.6). A hydration whose validation fails partially quarantines the invalid records and hydrates the valid subset with the raw payload offered as export.
- **Reconnect** re-runs hydration under a stable DOM using `phx-disconnected` styling; pending writes queued in `assigns.pending_writes` at reconnect are re-driven from client storage, which is the source of truth.
- **Secret rotation** drops sockets; clients reconnect and re-hydrate; no personal data is lost because none was held.

### Security and privacy

- No online account, no remote session, no analytics identity, no push token, no third-party origin anywhere (Constitution INV-3, INV-4, INV-22).
- Transport is HTTPS with HSTS (enabled only after certificates are verified) and WSS; `check_origin` is an explicit host list; `Plug.SSL` with `rewrite_on` for the Fly proxy (INV-22). Loopback binding is retired (INV-2 → replaced by INV-22).
- CSP is first-party only with no `'unsafe-inline'`; the exact policy is owned by [`DOS-M09-007`](DOS-M09-007.md).
- Session cookies contain framework CSRF and socket identification only, `Secure`, `HttpOnly` where applicable, `SameSite: Lax`, short `max_age`; **no personal data, no stable user identifier** (INV-22, INV-3).
- Server logs MUST NOT contain VIN, odometer or mileage values, service dates, note text, custom vehicle names, the specific vehicle a session selected, any hydration/mutation/import/export payload or fragment, the `tab_id`, or the full client IP (INV-4; enforced by DOS-M09-007 FR-11 and the FR-15 log-scan gate).
- The privacy claim is scoped exactly as ADR-0004 §"LiveDashboard and operator access — stated honestly" scopes it: **the server stores no personal data** — not "no operator could ever observe a live session." The operator rule (no routine production console use, never attaching to inspect a live socket) is written down.

### Accessibility and performance

- No direct UI in this card. The states this ratification names (`:hydrating`, `:empty`, `:data_missing`, `:storage_unavailable`, `:loaded`) are consumed by the M02/M05 UI cards; their accessibility contract is [`DOS-M02-002`](DOS-M02-002.md) as re-scoped (WCAG 2.2 AA verified against a named browser and assistive-technology matrix).
- Concurrency and performance budgets: `pool_size: 1` for `CatalogRepo` (a single-machine, in-process SQLite is not a contention target); server memory per LiveView socket, LiveView round-trip p95 by geography, IndexedDB footprint per 1 000 records, and first-paint payload budgets replace the retired Constitution §9 on-device budgets and are measured and enforced by [`DOS-M07-003`](DOS-M07-003.md) as re-scoped and by [`DOS-M09-008`](DOS-M09-008.md).

## UX and content states

The consumers of these states are M02 and M05:

- **`:hydrating`** — the neutral first-paint state that never claims "no vehicles yet" for even one frame (INV-24.3; ADR-0004 §"First-paint and empty-state rules"). Copy owned by [`DOS-M09-004`](DOS-M09-004.md).
- **`:loaded`** — the server has validated the hydration envelope and `socket.assigns` reflects the user's browser `UserStore`.
- **`:empty`** — hydration completed and the store legitimately holds no records. Distinct from `:hydrating` and `:data_missing`; renders the true first-run empty state and only then.
- **`:data_missing`** — `dos_boot_state == "has_data"` but hydration returned zero records; the browser storage appears to have been cleared. Distinct from `:empty`; explicitly warns the user and offers import (INV-25).
- **`:storage_unavailable`** — the hydrate event failed the deadline, or the fallback ladder concluded storage is blocked. Renders the private-browsing/blocked-storage state; nothing is written; export is offered (INV-24.6; ADR-0004 §"Private browsing and blocked storage").
- **"Not saved to this browser"** — a mutation ack failed or missed the 2 000 ms deadline (INV-24.2, FR-8). Persistent and non-dismissible on the affected record; the user is told the truth that the server holds this only until they close the tab.

## Risks, decisions, and open questions

- **Risk (from ADR-0004 R1):** browser eviction of infrequently-used site storage. A user who checks their oil once a quarter is exactly the profile most at risk, and the browser MVP is the product this risk hits first. Mitigations are `navigator.storage.persist()`, the honest `:data_missing` state (INV-25; FR-10), export nudges after meaningful writes, and per-browser measurement in DOS-M09-008. - **Risk (from ADR-0004 R2):** hydration round-trip latency on every mount, including reconnect. Ratified as measured and budgeted in DOS-M09-008 and DOS-M07-003 (re-scoped); this card does not invent a number.

- **Risk (from ADR-0004 R6):** web-serving rights for licensed catalog sources are unreviewed and are a hard gate owned by the re-scoped [`DOS-M03-001`](DOS-M03-001.md). This ratification does not authorize serving licensed sources over the web; it only ratifies the persistence architecture.
- **Decision ratified:** the deployment has exactly one Ecto repo, `CatalogRepo`, opened read-only, with no `UserRepo` and no personal-data table (FR-2, FR-6, AC-5; ADR-0004 §Decision 4; Constitution INV-23). - **Decision ratified:** the domain contexts are client-agnostic on purpose (FR-12; ADR-0004 §Decision 6); a future native client is one storage adapter and one presentation shell away from reusing them.
- **Open question:** whether `navigator.storage.persist()` grant rates observed in DOS-M09-008 are high enough to change the "browser storage is best-effort" framing shown to users; the answer is a UI copy change owned by DOS-M09-004, not a re-ratification of this ADR.

### (Pre-pivot) Technical implementation contract

- `DigitalOilSticker.CatalogRepo` and `DigitalOilSticker.UserRepo`: the only `Ecto.Repo` modules; owned by the persistence layer.
- `DigitalOilSticker.Boot` (per §7): ordered catalog verification, user migration, Repo startup, recovery state, and endpoint readiness; owns the boot sequence defined here.
- Contexts (`Catalog`, `Garage`, `Maintenance`, `Forecasting`, `Reminders`, `DataPacks`) are the only consumers of the repos; UI/domain code cannot call arbitrary `Ecto.Adapters.SQL`, `Repo.query`, or filesystem operations outside the persistence boundary.
- Two distinct SQLite files under the platform-resolved app-data root: `user/user.sqlite3` (durable, exportable) and `catalog/catalog-<version>.sqlite3` (replaceable, versioned) plus `catalog/catalog-pointer.json` and `staging/`.
- Both Repo runtime configs explicitly set database path and `pool_size: 1`. Catalog connection is opened read-only where `ecto_sqlite3` supports a verified option and always executes `PRAGMA query_only = ON`; `UserRepo` owns writes/migrations.
- No cross-database foreign keys; user rows store a stable catalog key plus a readable snapshot (per §4.2/§8).
- A forced boot failure (missing/corrupt catalog, failed migration) produces a recoverable screen state instead of a crash loop; the boot sequence must be re-runnable.
- Repo start order guarantees `CatalogRepo` never starts without a valid active catalog path and `UserRepo` data services are not ready before migrations complete.
- Phoenix/Cowboy binds strictly to `127.0.0.1` per §7 production shell security; LiveView connects to the in-app endpoint only.
- Logs record redacted storage classes, never raw native paths; no VIN, mileage, notes, or vehicle identifiers in logs or fixtures.
- `pool_size: 1` is the ratified concurrency model; performance budgets for boot and queries are measured and enforced later in `DOS-M04-010`, not invented here.

### (Pre-pivot) Acceptance criteria

- AC-1: ADR and `mix.lock` pin the architecture/toolchain and contain no browser-storage or remote-LiveView alternative.
- AC-2: A packaged debug build on one physical iOS and one physical Android device starts both distinct repos with `pool_size: 1`, inserts/reopens user rows, queries the bundled catalog, and remains functional in airplane mode.
- AC-3: Resolved files live in approved durable app-specific directories, not the app bundle/cache/temp directory; bundle catalog remains immutable.
- AC-4: Replacing or corrupting only the installed catalog cannot overwrite or reset UserRepo data.
- AC-5: Boot readiness prevents LiveViews from querying before catalog installation and `Ecto.Migrator` completion; a forced boot failure produces a recoverable screen instead of a crash loop.
- AC-6: Architecture test rejects direct SQL/filesystem access outside approved persistence/build modules.
- AC-7: The ADR records the typed error taxonomy, durability classes, OS backup decision, path layout, boot sequence, and the required catalog behavior list exactly as specified in Included/Functional requirements.

### (Pre-pivot) Notes on why the historical spec is not the MVP spec

Under ADR-0004 the AC-2 physical-device gate cannot resolve as written (no Mac and no Xcode; five recorded Windows-host defects; no upstream Windows CI). FR-2's `UserRepo` would fail the ADR-0004 §Enforcement / DOS-M09-007 FR-13 release gate that asserts the deployed Ecto repo list is exactly `[CatalogRepo]`. FR-6's "LiveView connects to the Phoenix endpoint inside the same Mob app" no longer describes the production shell (LiveView is hosted on Fly.io at `digitaloilsticker.com`). These are the concrete reasons this ratification card was rescoped rather than closed as complete.
