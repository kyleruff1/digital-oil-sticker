## Outcome

An ADR fixes one concrete on-device architecture: Mob 0.7.20 runs the BEAM and Phoenix LiveView inside the iOS/Android app; `DigitalOilSticker.CatalogRepo` and `DigitalOilSticker.UserRepo` are separate Ecto SQLite repos with `pool_size: 1`; Netlify is static-only. The ADR is approved, the dependency set is pinned in `mix.lock`, and a packaged debug build proves the architecture on one physical iOS and one physical Android device.

## Why this matters and what it unblocks

Repository paths, supervision, migrations, installation, lifecycle recovery, and tests all depend on this decision. Freezing it removes alternate storage/runtime branches and lets every feature team build against the same offline process model. This issue blocks all other M04 numbered issues: schemas (`DOS-M04-002/003`), repository implementations (`DOS-M04-004/005`), native bootstrap (`DOS-M04-006`), migration and install lifecycles (`DOS-M04-007/008`), export/import (`DOS-M04-009`), and certification (`DOS-M04-010`) all consume the paths, supervision order, error taxonomy, and no-server-account rule ratified here.

## Context and source of truth

- Master prompt §4.1 "Mob and LiveView are on-device": Mob 0.7.20 is a pre-1.0 BEAM-on-device framework; LiveView mode embeds the BEAM and Phoenix in each Android/iOS app on `http://127.0.0.1:4000` in a native WebView. Research anchors: [Mob 0.7.20 on hex.pm](https://hex.pm/packages/mob), [Mob LiveView mode](https://mob.hexdocs.pm/liveview.html), [Mob getting-started guide](https://mob.hexdocs.pm/getting_started.html), [Mob 0.7.20 Getting Started](https://hexdocs.pm/mob/0.7.20/getting_started.html).
- Master prompt §4.2 "SQLite is the runtime database": on-device [Ecto plus `ecto_sqlite3`](https://mob.hexdocs.pm/data.html), two local SQLite databases (`CatalogRepo` replaceable read-mostly; `UserRepo` durable and never replaced by a catalog update), `pool_size: 1` for each SQLite Repo, no cross-database foreign keys, stable catalog key plus readable snapshot in user rows.
- Master prompt §4.3 "Netlify is a static boundary" and §7 "Production shell security" (loopback binding, prod release hardening, backup/log redaction posture).
- Master prompt §7 "Runtime boundaries and modules" (`DigitalOilSticker.Boot`, context list) and §8 "Database and data-contract baseline".
- §11.2 catalog entry "DOS-M04-001 — Approve the Mob/Ecto dual-repository persistence ADR" and the M04 epic core rule.
- §11.2 "Research-backed source policy": Mob 0.7.20 embeds the BEAM inside iOS and Android application bundles and does not require a server; Netlify is a static distribution/marketing host only and is never the runtime database or LiveView server.
- §11.2 "Required dependency order": the runtime spike portion of `DOS-M04-001` may start in parallel with `DOS-M03-001/002`; the ADR is finalized after vocabulary approval.

## Included

- Pin compatible versions of Mob `0.7.20`, Ecto, `ecto_sql`, `ecto_sqlite3`, Exqlite, Phoenix, and LiveView in `mix.lock`; record supported iOS/Android/Mob toolchain versions in the ADR.
- Define `DigitalOilSticker.CatalogRepo` and `DigitalOilSticker.UserRepo` with `use Ecto.Repo, otp_app: :digital_oil_sticker, adapter: Ecto.Adapters.SQLite3` and `pool_size: 1`. They use different runtime-resolved database files and never share a transaction.
- Resolve paths at boot through the Mob/native platform path API: durable app-specific Application Support on iOS and app-specific device/files storage on Android. Never hard-code simulator paths, current working directory, home directory, bundle path as writable, or temporary/cache directories for the user DB.
- Define path layout such as `<app-data>/user/user.sqlite3`, `<app-data>/catalog/catalog-<version>.sqlite3`, `<app-data>/catalog/catalog-pointer.json`, and `<app-data>/staging/`. The exact native root is returned by the platform bridge and logged only as a redacted storage class, not a user path.
- Define supervision/boot sequence: resolve/create secure directories → inspect bundled manifest → install/verify catalog if needed → start `CatalogRepo` against active read-only file → start `UserRepo` → run `UserRepo` migrations through `Ecto.Migrator` before LiveView routes that need data become ready → run health probes → expose `:ready`.
- Establish no-server-account rule: the local profile is device-local; no email/password, remote session, remote sync, analytics identity, or push token is required. LiveView connects to the Phoenix endpoint inside the same Mob app, not a Netlify or remote application server.
- Define durability classes: bundled catalog source is immutable; installed catalog is replaceable/rollback-capable; user DB is durable/exportable; staging/cache is disposable. Decide OS backup inclusion explicitly: user DB should be eligible where product policy permits, while replaceable catalog/staging should be marked no-backup when supported.
- UI/domain code uses contexts/query modules; it cannot call arbitrary `Ecto.Adapters.SQL`, `Repo.query`, or filesystem operations outside the persistence boundary — enforce this with an architecture test.
- Produce and approve the ADR document itself (decision, alternatives considered, consequences, toolchain matrix) and a packaged-debug-build proof run on one physical iOS device and one physical Android device, including airplane mode.

## Excluded

- Any PWA/browser/OPFS/IndexedDB/WASM database; a Netlify-hosted Phoenix runtime; cloud accounts/sync; multiple SQLite pool connections; end-user catalog network updates (M08); writing to the signed app bundle.
- Implementing the full schemas, repository query/mutation surfaces, installer, migrations, or export — those are `DOS-M04-002` through `DOS-M04-009`; this issue defines and proves the architectural skeleton only.

## Functional requirements

- FR-1: `mix.lock` pins mutually compatible versions of Mob `0.7.20`, Ecto, `ecto_sql`, `ecto_sqlite3`, Exqlite, Phoenix, and LiveView; the ADR records the supported iOS/Android/Mob toolchain versions.
- FR-2: Both repos are defined with `use Ecto.Repo, otp_app: :digital_oil_sticker, adapter: Ecto.Adapters.SQLite3`, `pool_size: 1`, distinct runtime-resolved database files, and no shared transaction.
- FR-3: Database paths are resolved at boot through the Mob/native platform path API into durable app-specific storage (iOS Application Support, Android app-specific device/files storage); simulator paths, current working directory, home directory, writable-bundle assumptions, and temporary/cache directories are rejected for the user DB.
- FR-4: The path layout (`<app-data>/user/user.sqlite3`, `<app-data>/catalog/catalog-<version>.sqlite3`, `<app-data>/catalog/catalog-pointer.json`, `<app-data>/staging/`) is documented; logs carry only a redacted storage class, never a raw user path.
- FR-5: The supervision/boot sequence is specified and implemented as ordered stages ending in `:ready`; LiveView routes that need data are not ready before catalog installation and `Ecto.Migrator` completion.
- FR-6: The no-server-account rule is stated in the ADR and reflected in configuration: no email/password, remote session, remote sync, analytics identity, or push token anywhere in the boot path; LiveView connects only to the in-app Phoenix endpoint.
- FR-7: Durability classes (immutable bundled catalog, replaceable installed catalog, durable/exportable user DB, disposable staging/cache) and the explicit OS backup inclusion decision are recorded.
- FR-8: The required catalog behaviors are specified as the repository contract: `metadata/0`, `list_years/1`, `list_makes/2`, `list_models/3`, `list_configurations/4`, `get_configuration/1`, `get_schedules/2`, `get_lubricant_requirements/1`, `search_oils/2`, `list_compatible_filters/2`, `get_provenance/2`; user CRUD/transaction/export primitives are defined later.
- FR-9: The typed error taxonomy is defined: `not_ready`, `not_found`, `invalid_input`, `corrupt`, `incompatible_schema`, `insufficient_space`, `permission_denied`, `read_only`, `transaction_failed`, `storage_unavailable`, each with recoverability metadata.
- FR-10: All result lists specify a total order/cursor contract; no runtime function requires the network to read or write core data.
- FR-11: An architecture test rejects direct SQL/filesystem access outside approved persistence/build modules.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.CatalogRepo` and `DigitalOilSticker.UserRepo`: the only `Ecto.Repo` modules; owned by the persistence layer.
- `DigitalOilSticker.Boot` (per §7): ordered catalog verification, user migration, Repo startup, recovery state, and endpoint readiness; owns the boot sequence defined here.
- Contexts (`Catalog`, `Garage`, `Maintenance`, `Forecasting`, `Reminders`, `DataPacks`) are the only consumers of the repos; UI/domain code cannot call arbitrary `Ecto.Adapters.SQL`, `Repo.query`, or filesystem operations outside the persistence boundary.
- The ADR document lives with other ADRs in the repository's committed docs tree and is the single source for this decision.

### Data and persistence

- Two distinct SQLite files under the platform-resolved app-data root: `user/user.sqlite3` (durable, exportable) and `catalog/catalog-<version>.sqlite3` (replaceable, versioned) plus `catalog/catalog-pointer.json` and `staging/`.
- Both Repo runtime configs explicitly set database path and `pool_size: 1`. Catalog connection is opened read-only where `ecto_sqlite3` supports a verified option and always executes `PRAGMA query_only = ON`; `UserRepo` owns writes/migrations.
- No cross-database foreign keys; user rows store a stable catalog key plus a readable snapshot (per §4.2/§8).

### Interfaces and events

- Required catalog behaviors per FR-8, with typed inputs/results (full implementation in `DOS-M04-004`).
- Errors map to the FR-9 taxonomy with recoverability metadata; this taxonomy is the base set that `DOS-M04-005` extends (`validation`, `conflict`, `referenced`).
- All result lists specify a total order/cursor contract.
- Boot readiness is exposed as an observable `:ready` state that gates LiveView data routes.

### Failure and recovery behavior

- A forced boot failure (missing/corrupt catalog, failed migration) produces a recoverable screen state instead of a crash loop; the boot sequence must be re-runnable.
- Repo start order guarantees `CatalogRepo` never starts without a valid active catalog path and `UserRepo` data services are not ready before migrations complete (detailed hardening in `DOS-M04-006/007`).
- Every error in the taxonomy carries recoverability metadata so callers can distinguish retryable, user-actionable, and terminal conditions.

### Security and privacy

- No online account, remote session, analytics identity, or push token exists anywhere in the ratified architecture.
- Phoenix/Cowboy binds strictly to `127.0.0.1` per §7 production shell security; LiveView connects to the in-app endpoint only.
- Logs record redacted storage classes, never raw native paths; no VIN, mileage, notes, or vehicle identifiers in logs or fixtures.
- The signed app bundle is never written to; packaged session keys are local integrity material, not remotely secret credentials.

### Accessibility and performance

- No direct UI; the recoverable boot-failure state must be reachable by the future recovery UI (M05 owns its accessibility).
- `pool_size: 1` is the ratified concurrency model; performance budgets for boot and queries are measured and enforced later in `DOS-M04-010`, not invented here.

## UX and content states

No end-user screens are built by this issue. It defines the states the UI will later consume: boot progress (not ready), `:ready`, and a recoverable boot-failure state that offers recovery instead of a crash loop. Copy and visual design for those states belong to M02/M05.

## Test plan

### Automated

- Repo runtime configuration assertion test: adapter is `Ecto.Adapters.SQLite3`, two distinct database paths, `pool_size: 1` for both repos.
- Architecture-boundary test (e.g., compile-time module dependency check) rejecting `Ecto.Adapters.SQL`, `Repo.query`, and filesystem calls outside approved persistence/build modules.

- Error-taxonomy tests: representative failures map to the typed errors with recoverability metadata.
- Dependency lock check in CI: pinned versions present and unchanged without review.

### Manual/device matrix

- One physical iOS device (minimum supported class): install packaged debug build; verify both repos start, user row insert/reopen, bundled catalog query, airplane-mode operation; capture resolved (redacted) path evidence.
- One physical Android device (minimum supported class): same sequence.
- Airplane-mode packet capture on both devices proving no network traffic during boot, insert, and query.
- Corrupt/replace only the installed catalog file on a device and verify `UserRepo` data is untouched and boot enters the recovery path.

## Risks, decisions, and open questions

- Risk: Mob 0.7.20 is pre-1.0; an `ecto_sqlite3` read-only open option may not be verifiable on-device. Mitigation: the contract requires `PRAGMA query_only = ON` always, with the read-only open flag used only where verified.
- Risk: platform path APIs differ subtly (iOS Application Support vs Android files dir); wrong choices silently land data in cache/temp. Mitigation: FR-3 rejection rules plus AC-3 physical-device evidence.
- Decision to ratify: OS backup inclusion per durability class (user DB eligible where product policy permits; catalog/staging no-backup when supported).
- Decision to ratify: exact supported iOS/Android/Mob toolchain versions.
- Open question: whether `ecto_sqlite3` exposes a verified read-only open option in the pinned version; the answer is recorded in the ADR and consumed by `DOS-M04-004/006`.
- Open question: whether any umbrella split is needed — default is one Mob/Phoenix application per §7 unless the M00 spike proved a concrete need.
