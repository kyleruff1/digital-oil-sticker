## Outcome

The proposed catalog schema is encoded as deterministic, migration-tested SQL that the M03 compiler can populate and on-device `DigitalOilSticker.CatalogRepo` can open read-only through `ecto_sqlite3`. The schema ships with build-time migrations, integrity/foreign-key/semantic checks, index/`ANALYZE` discipline, metadata versioning, and a documented compatible schema window.

## Why this matters and what it unblocks

It converts the vocabulary into a compact executable contract and fixes indexes/checks before datasets and UI rely on them. Downstream, `DOS-M03-010` compiles the production catalog into this schema, `DOS-M04-004` implements the read-only query interface against it, and `DOS-M04-008` installs and atomically upgrades artifacts built with it. Freezing constraints and query-plan-relevant indexes now prevents rework in the M03 pipeline and prevents on-device queries from degrading to full scans after real data arrives.

## Included

- Implement all tables/indexes/checks in the proposed catalog schema; refine only through an ADR that updates the dictionary and repository contract. Name refinements are permitted through that ADR; semantic changes are not.
- Add `schema_version`, `catalog_version`, `minimum_app_version`, year range, feature flags, and logical build hash in metadata (`catalog_metadata`).
- Decide and document SQLite features (`STRICT`, FTS5, generated columns, JSON1) against the exact SQLite/Exqlite versions packaged by Mob on the minimum supported iOS/Android releases. Use portable shadow columns if a feature is unavailable.
- Use deterministic stable text IDs in exported tables; private integer surrogate keys may be added only if benchmarks justify them and public repo results never expose rowids.
- Build indexes after bulk loading when faster, run `ANALYZE`, enforce `foreign_key_check`, `integrity_check`, and semantic checks, then switch the artifact to immutable/read-only handling.
- Define the compatible schema window and app behavior for newer/older schema versions (typed `incompatible_schema`, never a crash or partial result).
- Add CHECK enums for status/condition/kind columns; store booleans as constrained 0/1; validate `qualifier_json` as canonical JSON at build time; store the search normalization version in metadata.
- Produce the build-time migration mechanism itself: ordered, deterministic SQL migrations executed by the catalog build pipeline (not on user devices), with committed schema dump and migration checksums.

## Excluded

- Applying catalog migrations in place on an end-user's active artifact; user tables; raw ingest staging tables in the shipped database.
- Populating the schema with licensed production data (`DOS-M03-010`), the on-device query interface (`DOS-M04-004`), and the on-device installer (`DOS-M04-008`).
- FTS5 tables where the packaged SQLite runtime does not prove support — cascading indexed selectors must work without FTS (per §8).

## Functional requirements

- FR-1: Every table, column, nullability rule, CHECK, uniqueness constraint, and index in the proposed catalog schema exists in the emitted SQL exactly as specified, or with a name refinement recorded in an approved ADR that updates the dictionary and repository contract.
- FR-2: `catalog_metadata` carries at least `schema_version`, `catalog_version`, `minimum_app_version`, year range, feature flags, logical build hash, and the search normalization version.
- FR-3: The SQLite feature decision matrix (`STRICT`, FTS5, generated columns, JSON1) is documented against the exact packaged SQLite/Exqlite versions on minimum supported iOS/Android; any unavailable feature has a portable shadow-column fallback in the schema.
- FR-4: Exported tables use deterministic stable text IDs; if benchmarks justify private integer surrogate keys, public repo results never expose rowids.
- FR-5: The build sequence supports index creation after bulk load, runs `ANALYZE`, and enforces `foreign_key_check`, `integrity_check`, and semantic checks before the artifact is switched to immutable/read-only handling.
- FR-6: The compatible schema window is defined; opening a newer or older schema than supported produces the typed `incompatible_schema` error, never a crash or partial result.
- FR-7: Status/condition/kind columns are constrained by CHECK enums; booleans are constrained 0/1; `qualifier_json` is canonical JSON validated at build.
- FR-8: Schema migrations are deterministic: identical inputs produce byte-identical schema DDL, and the schema dump plus migration checksums are committed and reviewed.
- FR-9: All catalog tables use `WITHOUT ROWID` where measurements show benefit; measurements are recorded, not assumed.
- FR-10: The schema is loadable by the M03 compiler and openable read-only by `ecto_sqlite3` with `PRAGMA query_only = ON` in the packaged app.

## Technical implementation contract

### Components and ownership boundaries

- Catalog schema DDL/migrations live in the catalog build pipeline (M03 compiler tooling), not in the app's `priv/user_repo/migrations` path; the device never migrates catalog files.
- The data dictionary (from `DOS-M03-002`) is the naming authority; this issue owns the executable SQL and its checksums.
- `DOS-M04-004` owns the Elixir query layer over this schema; this issue owns only SQL-level contracts (tables, indexes, checks, metadata keys).

### Data and persistence

- Single deliverable artifact class: a deterministic SQLite database file matching the proposed catalog schema, immutable within one `catalog_version`.
- Full table set per the proposed catalog schema table (see Context); required indexes/constraints include, verbatim from the catalog: PK `key` on `catalog_metadata`; UNIQUE `source_key, source_version, raw_sha256` on `sources`; UNIQUE `manufacturer_id, normalized_name, id` on `makes`; INDEX `model_year, make_id, model_id, id` on `vehicle_configurations`; UNIQUE source/type/key/effective start on `vehicle_external_ids`; positive-interval CHECK and UNIQUE source/source key on `maintenance_schedules`; at least spec-or-viscosity CHECK and positive capacity CHECK on `vehicle_lubricant_requirements`; UNIQUE product/type/code/source/effective start on `oil_product_claims`; UNIQUE brand/normalized part/source on `filter_products`; quantity CHECK and UNIQUE source/source key on `filter_fitments`; provenance and alias indexes on `row_provenance` and `search_aliases`.
- Foreign keys are validated at build time (`foreign_key_check` must return no rows); the shipped artifact is opened read-only on-device.

### Interfaces and events

- SQL-level interface only: table/column/index names and `catalog_metadata` keys are the contract consumed by the M03 compiler and `DOS-M04-004`.
- Version negotiation interface: `schema_version` + `minimum_app_version` in metadata drive the `incompatible_schema` behavior in the app.
- No runtime events; build pipeline emits logs and check reports as artifacts.

### Failure and recovery behavior

- A build in which `foreign_key_check` returns rows, `integrity_check` is not `ok`, or a semantic check fails aborts before the artifact is marked immutable; no partially checked artifact may be published.
- On-device, unsupported schema versions produce typed `incompatible_schema`, never a crash or partial result; recovery (fall back to a compatible catalog) is implemented in `DOS-M04-008`.
- Deterministic rebuild is the recovery path for a bad artifact: rebuild from inputs, never hand-patch a produced SQLite file.

### Security and privacy

- The shipped schema contains no user data, credentials, raw licensed payloads, or ingest staging tables.
- License/source governance data is first-class: `sources`, `row_provenance`, and per-row `source_id`/`source_record_key` columns preserve field-level provenance required by the source policy.
- Checksums (`raw_sha256`, logical build hash) support integrity verification at install time; they are integrity material, not secrets.

### Accessibility and performance

- No UI. Performance contract: query plans for selection, schedules, oil claims, filter fitment, and provenance must use the defined indexes and avoid full scans at measured fixture scale (verified with `EXPLAIN QUERY PLAN`); `ANALYZE` runs at build; index-after-bulk-load is used when measured faster. Final on-device latency budgets are certified in `DOS-M04-010`.

### Data change specifics

- Source/version/license: the schema itself derives from the approved `DOS-M03-002` vocabulary; it stores source/license governance for future data via `sources` (publisher, `source_version`, `license_version`, `retrieved_at`, `raw_sha256`, attribution) and `row_provenance`. No external dataset is ingested by this issue.
- Mapping: data dictionary term → table/column mapping is committed alongside the DDL; any rename goes through the ADR that updates dictionary and repository contract together.
- Stable keys: deterministic stable text IDs on all exported tables; provider integers only as `*_source_id`; rowids never exposed in public results.
- Constraints/indexes: exactly the proposed schema's PK/FK/UNIQUE/CHECK/INDEX set (see Data and persistence); CHECK enums for status/condition/kind; booleans constrained 0/1.
- Idempotency: schema builds are deterministic — same migration set yields byte-identical DDL and identical schema dump checksums.
- Rejected-row policy: not applicable to schema DDL itself; the schema must support the M03 builder's rejected-row reporting (build-time validation hooks, canonical JSON validation for `qualifier_json`), and build validation failures abort artifact publication.
- Checksums: committed schema dump checksum, per-migration checksums, and the logical build hash stored in `catalog_metadata`.
- Coverage report: schema-feature coverage matrix (which SQLite features are used vs shadowed) per packaged runtime; table/index inventory diffable across schema versions.
- Fixture strategy: empty schema, populated fixture schema (synthetic golden catalog), and previous-supported-schema fixtures are maintained for CI; fixtures are synthetic and license-clean.
- Update cadence: schema versions change only via ADR; each shipped catalog artifact pins one `schema_version`; the compatible schema window defines how many versions the app accepts.
- Rollback/recovery: a schema version rollback is a rebuild against the prior migration set; on-device rollback across catalog versions is handled by `DOS-M04-008` retention of the prior artifact.

## Test plan

### Automated

- CI migration matrix: build empty schema; build populated fixture schema; upgrade previous supported schema — all deterministic (checksum-compared).
- Integrity gates: `foreign_key_check` (zero rows), `integrity_check` (`ok`), semantic checks on the golden catalog fixture.
- `EXPLAIN QUERY PLAN` regression tests for selection, schedules, oil claims, filter fitment, and provenance queries at measured fixture scale.
- Constraint tests: CHECK enums reject invalid status/condition/kind; boolean columns reject non-0/1; `qualifier_json` canonical-JSON validation rejects malformed input at build.
- Compatibility tests: artifact with newer-than-supported and older-than-window `schema_version` yields typed `incompatible_schema`.
- Checksum verification: schema dump and migration checksums match committed values.

### Manual/device matrix

- Open the golden fixture artifact read-only through `ecto_sqlite3` with `PRAGMA query_only = ON` in a packaged debug build on the minimum supported iOS and Android device classes (one smoke pass; full device certification is `DOS-M04-010`).
- Verify the documented SQLite feature matrix (`STRICT`, FTS5, generated columns, JSON1) against the actual packaged SQLite/Exqlite versions on those devices; record versions in the decision document.

## Rollout and rollback

Rollout: merge DDL/migrations and checks into the catalog build pipeline; the schema takes effect only in newly built catalog artifacts. Rollback: revert to the prior migration set and rebuild; because catalog migrations are never applied in place on an end-user's active artifact, rollback never touches devices directly — devices roll back at the artifact level via `DOS-M04-008` (retained prior catalog) and the compatible schema window.

## Dependency rationale

Blocked by `DOS-M04-001` (adapter, read-only handling, error taxonomy, and `pool_size: 1` must be fixed before SQL contracts are frozen) and `DOS-M03-002` (the vocabulary/stable-ID contract the tables encode). Synchronize with `DOS-M03-006` so crosswalk match-method/status vocabulary in `vehicle_external_ids` stays aligned — coordination, not a blocking edge. This issue blocks `DOS-M03-010` (the compiler needs the executable schema to emit the release candidate), `DOS-M04-004` (the query layer is written against these tables/indexes), and `DOS-M04-008` (the installer verifies schema/metadata compatibility defined here).

## Risks, decisions, and open questions

- Risk: packaged SQLite/Exqlite versions on minimum devices lack a desired feature (FTS5, `STRICT`, generated columns, JSON1). Mitigation: FR-3 decision matrix plus portable shadow columns; FTS is optional by §8 and selectors must work without it.
- Risk: index design tuned on fixtures may not match production data distribution. Mitigation: `ANALYZE` at build, query-plan regression tests, and re-measurement in `DOS-M04-010` with the representative M03 catalog.
- Decision (via ADR only): any table/column name refinement; addition of private integer surrogate keys, justified by benchmarks.
- Decision: exact compatible schema window (how many schema versions the app accepts) — recorded with FR-6.
- Open question: `WITHOUT ROWID` benefit per table — resolved by measurement, recorded in the evidence.
- Open question: whether prebuilt FTS5 tables ship in v1 artifacts at all; default is no until the Mob/exqlite build proves support (per §8).
