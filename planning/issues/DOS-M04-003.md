> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The logical model and its invariants survive but must be expressed as IndexedDB object stores and indexes enforced in the client adapter and re-validated server-side on hydration, since SQL constraints are no longer available._

## Outcome

A single, client-agnostic **logical model and invariant catalogue** for the anonymous user record — vehicles, service events, odometer readings, usage profiles, reminder intent, and preferences — is published as the semantic contract that every storage realization of the product must preserve. The catalogue enumerates each invariant (nonnegative odometer, one current usage profile per vehicle, one active reminder rule per `(vehicle_id, service_code)`, deterministic ordering by `(performed_at DESC, id ASC)` / `(observed_at DESC, id ASC)`, snapshot-plus-stable-id history, no full VIN by default, no server-derivable key, vehicle-scoped isolation) and, for each, records the **two-point enforcement pairing** the browser-first architecture demands: how the invariant is enforced in the client IndexedDB adapter, and how it is re-validated server-side on hydration through the changeset stack. SQL `CHECK`, `UNIQUE`, and foreign-key constraints — the final invariant boundary the pre-pivot card relied on — no longer exist in the deployment; this card is the written substitute, backed by fixtures the adapter and the hydration validator both target.

The card is a specification and fixtures deliverable. The IndexedDB storage design that realizes the model in the browser is `DOS-M09-001`; the `LocalStore` JavaScript hook, the LiveView hydration/mutation round trip, and the server-side changeset stack that enforce this card's invariants at both ends of the wire are `DOS-M09-002`. This card is the shared source of truth those two read from, and the reason an alternate future storage backend for a different client (were a new ADR to authorize one) could inherit the same invariants without re-arguing the semantics.

## Why this matters and what it unblocks

The pre-pivot card treated SQL as the final invariant boundary: constraints fired even when a changeset was bypassed, so an application bug could not permanently corrupt a user's history. That boundary is gone. In the deployed application there is exactly one Ecto repo, `DigitalOilSticker.CatalogRepo`, opened read-only ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §Decision items 3 and 4; [CONSTITUTION.md](../../docs/product/CONSTITUTION.md) INV-3, INV-23) — there is **no `UserRepo`** and cannot be one. IndexedDB provides none of the missing guarantees: no `CHECK`, no cross-store foreign keys, no `UNIQUE` outside an index, no server-fired trigger that runs regardless of caller. If the invariants are not re-established in writing, and if two independent enforcement points (the client adapter and the server-side hydration changeset) are not held to the same catalogue, then either the browser adapter or a socket-side path can silently write a malformed record with no server copy to restore from.

The logical model itself survives the pivot: a garage is still a set of vehicles, each with events, readings, a current usage profile, and reminder intent; history still needs a stable catalog reference plus an immutable snapshot to remain intelligible after a catalog release changes (INV-15). What has changed is that these truths are now **duplicated by design** across the client adapter and the server-side validator, and one card must own the definitions both sides implement.

Closing this issue unblocks:
- `DOS-M09-001` — its schema document is written against exactly this invariant catalogue; its integrity-rule list is the FR-11 equivalent expressed as read-time checks; its FR-12 quarantine machinery is the disposition catalogue's `quarantine` arm.
- `DOS-M09-002` — its client `readwrite` transaction enforces this card's invariants on the browser side, and its server-side hydration changeset stack re-validates the same rules before any payload reaches `socket.assigns`, so the server never carries a malformed record even transiently ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Validation"). These are the two enforcement points this card pairs.
- `DOS-M04-005` (rescoped: transactional browser-storage adapter workflows), `DOS-M04-006` (rescoped: server catalog boot plus client hydration boot), `DOS-M04-007` (rescoped: IndexedDB `onupgradeneeded` forward-only migrations), `DOS-M04-009` (rescoped: browser-mediated export/import) — each consumes the model as-defined here.

## Included

- Publish the client-agnostic logical entity model: entity names, their relationships, and the fields the product commits to for each. The model is expressed in storage-neutral prose so that a future storage backend belonging to a different client (were a new ADR to authorize one) and the current IndexedDB backend both implement the same shape.
- Publish the invariant catalogue: every rule the SQL migration set previously enforced (nonnegative odometer, one active reminder rule per `(vehicle_id, service_code)`, one current usage profile per vehicle with `effective_to IS NULL`, deterministic ordering, snapshot-plus-stable-id history, vehicle-scoped isolation, no full VIN by default, immutable forecast lineage) restated as a numbered list with acceptance semantics.
- For **each** invariant, record the **two-point enforcement pairing**: how the client IndexedDB adapter enforces it inside the `readwrite` transaction, and how the server-side hydration changeset re-validates it on every mount ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Validation"). The pairing exists precisely because SQL is no longer the third and final gate.
- Publish the mapping from each `DATA_DICTIONARY.md` `UserRepo` table to its browser home, deferring the physical store layout to `DOS-M09-001` and noting which tables deliberately have no browser home (e.g. `scheduled_notifications` per INV-17) and why.
- Publish the ordering contracts — `(performed_at DESC, id ASC)` for service events, `(observed_at DESC, id ASC)` for odometer readings, `(effective_from DESC, id ASC)` for usage profiles — as a contract independent of index shape, so a future backend can honour them differently as long as the observable ordering is identical.
- Publish the unit and time rules unchanged from the pre-pivot spec: integer base units for mileage with conversion at the boundary; UTC instants for exact events plus an IANA time zone in preferences; the canonical local-noon/ISO-date rule for date-only capture, with tests including DST boundaries.
- Publish the failure catalogue the two enforcement points share: which invariant violation surfaces as which typed error, and which of them are recoverable (quarantine to a hold list, `DOS-M09-001` FR-12) versus which are rejections (hard-cap breach, referential linkage failure inside a mutation) versus which put the session into read-only mode (payload newer than the deployment, [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Schema versioning and migration").
- Deliver a shared, versioned fixture suite: for every invariant, at least one valid fixture and at least one violation fixture. The client-side `LocalStore` hook and the server-side hydration validator (both in `DOS-M09-002`) run against the same fixtures, and the equivalence of their rejections is asserted rather than left to reviewer confidence.

## Functional requirements

- FR-1: Publish the client-agnostic logical entity set: `vehicles`, `service_events`, `odometer_readings`, `usage_profiles`, `reminders`, `prefs`, `meta`. Every vehicle-scoped entity references a `vehicle_id`; no singleton "current vehicle" field substitutes for that relationship (INV-18). The garage is realized by `vehicles` + `prefs`; multi-vehicle exposure is a presentation change and never a data migration.
- FR-2: Publish the invariant catalogue as a numbered list with acceptance semantics. At minimum: **INV-A** nonnegative odometer in base units; **INV-B** one current usage profile per vehicle (`effective_to IS NULL`); **INV-C** one active reminder rule per `(vehicle_id, service_code)`; **INV-D** deterministic ordering per FR-5; **INV-E** snapshot-plus-stable-id on every historical record (INV-15); **INV-F** vehicle-scoped referential integrity (every child names an existing `vehicle_id` in the same payload); **INV-G** no full VIN by default (at most a nullable last-six field); **INV-H** no server-derivable key or field (INV-3); **INV-I** monotonic `meta.seq` across writes (INV-24.7); **INV-J** UUIDv4 primary keys and singleton fixed keys for `meta` and `prefs`; **INV-K** unknown-field preservation across read → write-back → export (forward compatibility).
- FR-3: For every invariant in FR-2, record the **client-adapter enforcement point** — the check performed by `DigitalOilSticker.LocalStore.Validation` (and its browser-side counterpart in the `LocalStore` hook) inside the IndexedDB `readwrite` transaction — and the **server-side re-validation point** — the changeset rule applied by the hydration validator on the socket boundary ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Validation"). Both points live in `DOS-M09-002`; both MUST accept and reject the same fixtures; equivalence is a tested property, not a promise. This is the written substitute for the retired SQL constraint boundary.
- FR-4: Publish the mapping from each `DATA_DICTIONARY.md` `UserRepo` table to its browser home. Tables with no browser home (`scheduled_notifications` per INV-17; `local_profiles` folded into `prefs` + `meta` per INV-3) are listed with the reason, so a reviewer can trace any source table to its home or to why it has none. The physical store layout is deferred to `DOS-M09-001`.
- FR-5: Publish the ordering contracts: service events by vehicle and `performed_at DESC, id ASC`; odometer readings by vehicle and `observed_at DESC, id ASC`; usage profiles by vehicle and `effective_from DESC, id ASC`. The contract is observational and MUST hold whether the backend is an IndexedDB index or a future SQL index; the client-adapter and the hydration-hydrated assigns MUST agree on the order.
- FR-6: Publish the unit and time rules: mileage persisted in a single documented integer base unit with conversion at the boundary; UTC instants for exact events with the IANA time zone in `prefs`; a canonical local-noon/ISO-date rule for date-only capture with no accidental date shifts, tested including DST boundaries.
- FR-7: Publish the snapshot-plus-stable-id rule: every historical record (`service_events`, `usage_profiles`, and any future `forecast_snapshots`) stores the stable catalog identifier **and** an immutable human-readable snapshot sufficient to render the record without the current catalog available (INV-15; ADR-0003 provenance).
- FR-8: Publish the correction workflow rule: an odometer correction is an explicit, reason-carrying operation modelled as a superseding record with an audit link to the corrected one; no path silently rewrites a prior reading (INV-15).
- FR-9: Publish the archive-vs-delete rule: archiving a vehicle is the normal action and preserves all history under `is_archived`; a delete-vehicle operation exists only as an explicit transaction that previews counts, and its transactional guarantees are provided by the client adapter's `readwrite` transaction rather than SQL, and are exercised by the shared fixtures.
- FR-10: Publish the hard-cap catalogue that matches the server-side validation caps in [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Validation": decoded payload ≤ 1 MiB, ≤ 200 vehicles, ≤ 5 000 events, ≤ 20 000 readings. A breach is a hydration-level rejection with export offered; silent truncation is prohibited (INV-24.5).
- FR-11: Publish the read-time integrity-rule list the two enforcement points share: required-field presence; type correctness; numeric range (odometer nonnegative in base unit); enumeration membership for units, support status, and provenance mode; primary-key uniqueness within a store; singleton-ness of `meta` and `prefs`; referential linkage (every vehicle-scoped record names a `vehicle_id` present in the payload); parseable instants and dates; and `meta.seq` a non-negative integer no lower than the highest sequence any record claims (INV-24.7).
- FR-12: Publish the failure taxonomy the two enforcement points share, mapping each invariant violation to one of three dispositions: **quarantine** (valid subset hydrates, offender held aside, count surfaced, raw payload exportable — `DOS-M09-001` FR-12); **reject** (the mutation or hydration is rejected at the boundary, prior state preserved, plain-language error surfaced); **read-only mode** (payload newer than deployment, mutations disabled, banner, export offered — [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Schema versioning and migration"). Silent repair, silent truncation, and silent deletion are prohibited.
- FR-13: Publish the vehicle-scoped isolation rule: no query, ordering, or aggregation may cross vehicles; a `scheduled_notifications`-successor rule ("no rule/forecast lineage may cross vehicles") is retained conceptually and applies to any future in-app due-state derivation crossing vehicle boundaries.
- FR-14: Publish the no-server-personal-record rule as a testable property of this model: no field name and no field value type in this specification identifies a person, and the deployed application's Ecto repo list is exactly `[CatalogRepo]` opened read-only ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Enforcement"; INV-3). This card provides the field inventory the audit reads.
- FR-15: Publish, as a numbered addendum obligation to ADR-0004 (CHANGE_CONTROL Rule 2a), any extension this model requires to ADR-0004's storage-layout table or envelope. The extension mechanism is `DOS-M09-001` FR-20; this card records the semantic reason each addendum exists so the ratified architecture and the implemented schema cannot drift apart.
- **Retired FRs (pre-pivot).** The old FR-1 through FR-11 assumed SQL migrations, Ecto changesets, `CHECK`/`UNIQUE` constraints, and a `UserRepo`. All are retired by [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) Decision items 3 and 4 and by the PIVOT disposition. Their semantic content is preserved as the invariants named above; the SQL mechanics are not carried over. The pre-pivot FRs are recorded verbatim in the historical section at the bottom of this file for readability of the change.

## Technical implementation contract

### Components and ownership boundaries

- This card owns the written logical model, the invariant catalogue, the two-point enforcement mapping, the ordering and unit rules, the failure taxonomy, and the shared fixture suite. It owns no runtime code.
- `DOS-M09-001` owns the IndexedDB store shapes, key strategy, index list, version lines, and upgrade steps that realize this model in the browser. Where the two cards touch (mapping tables, invariant list) they reference each other by section rather than restating.
- `DOS-M09-002` owns **both** enforcement points: the client-side `LocalStore` hook and its JS-side integrity checks that run inside the `readwrite` transaction, **and** the server-side hydration changeset stack whose modules are written against this card's field types, ranges, referential rules, caps, and versioning. The two enforcement points are held to the same fixtures by the fixture-equivalence test (AC-3), and neither is the sole enforcer — both are.
- Domain contexts (`DigitalOilSticker.Garage`, `.Maintenance`, `.Forecast`) consume domain structs derived from validated assigns; they never touch IndexedDB and never see raw hydration payloads. This preserves the ADR-0004 §Decision-item-6 property that a future non-browser client would differ from the browser client by one storage adapter and one presentation shell — nothing else.

### Data and persistence

There is no server-side persistence of personal data anywhere in the deployment ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) Decision item 4). The persistence surface is:

- **Client durable storage.** Origin-scoped IndexedDB database `dos_local`, holding the entities and invariants specified here in the object-store layout defined by `DOS-M09-001`. `localStorage` carries only the non-personal boot hint `dos_boot_state` per ADR-0004 §"Storage layout".
- **Server transient state.** `socket.assigns` for the lifetime of one LiveView connection, populated by the hydration protocol and discarded at socket termination. It is never written to disk, database, cache, ETS table, external store, or log ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) Decision item 4).
- **Catalog references.** `catalog_vehicle_configuration_id`, `oil_product_id`, `filter_product_id`, `schedule_id` are stable text identifiers, resolved server-side against `CatalogRepo` at render time and always accompanied by an immutable snapshot in the record (FR-7). A catalog release moving forward may return `unsupported` for a stale identifier (INV-11); the record remains renderable from the snapshot.
- **Base-unit mileage** and **UTC + IANA time** are the persistence contract at both enforcement points; unit conversion happens at the UI boundary only (FR-6).

The `DATA_DICTIONARY.md` `UserRepo` → browser-home mapping is published in this card's schema document and referenced (not restated) by `DOS-M09-001`.

### Interfaces and events

- The model exposes no functions. Its interface is the entity list, the field inventory per entity, the invariant catalogue, the ordering contracts, the failure taxonomy, and the fixture suite.
- The hydration envelope shape is owned by `DOS-M09-001` FR-17 and consumed unchanged by `DOS-M09-002`. This card's contribution is the payload contents' semantic contract: what a valid vehicle looks like, what a valid event looks like, what a valid `meta.seq` means.
- Every record shape is published as a committed schema document (co-owned with `DOS-M09-001`) that both the client-side `LocalStore` hook and the server-side changesets in `DigitalOilSticker.LocalStore.Validation` are written against. The two implementations MUST NOT diverge silently; a fixture-equivalence test is the mechanism (FR-3, AC-3).
- Snapshot sub-documents are versioned; a consumer MUST tolerate reading any released snapshot version.

### Failure and recovery behavior

The failure taxonomy is enforced identically on both sides:

- **Quarantine.** A per-record integrity failure surfaces as a quarantine entry with the store, key, and violated rule named; the valid subset hydrates and the raw payload remains exportable (INV-25; `DOS-M09-001` FR-12).
- **Reject.** A mutation that would violate a mutation-time invariant (FR-11 rules applied inside the `readwrite` transaction) is rejected; the prior state is preserved; the failure surfaces in plain language and export is offered. On the server side, a hydration payload that breaches a hard cap (FR-10) is rejected at the boundary before it reaches assigns.
- **Read-only mode.** A payload whose logical schema version exceeds the deployed server's puts the session into read-only mode: mutations disabled, banner, export offered ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Schema versioning and migration"; INV-24.3).
- **Compare-and-set conflict.** A write against a stale `meta.seq` aborts and reports a conflict (INV-24.7). The server discards its optimistic assign, triggers re-hydration, and the losing tab's UI shows a visible "reloaded from this browser's newer data" notice.
- **Quota exceeded.** The write fails, the prior state is preserved, the failure surfaces in plain language, and export is offered. No record is silently dropped (INV-24.5).
- **Cleared site data.** The `meta`-plus-boot-hint contract (`DOS-M09-001` FR-15) makes the loss detectable; this card's obligation is that the field inventory records enough for that detection to be unambiguous.

There is no server-side rollback of personal state because there is no server-side personal state; recovery is user-initiated import against a prior export (INV-5).

### Security and privacy

- No credential, email, password, remote session, analytics identity, push token, or full-VIN column in any entity (INV-3, INV-4). The at-most-nullable last-six VIN field is the maximum default vehicle-identifier granularity; full VIN requires its own privacy issue.
- No server-derivable key: every primary key is a client-generated UUIDv4 or a fixed singleton key (FR-1, INV-3).
- Hydration input is untrusted client input and is validated exactly like any external payload ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Validation"); no field type in this model bypasses that validation on the server side.
- Redaction: VIN fragments, mileage, notes, and nicknames never appear in logs, error pages, or fixtures (ADR-0004 §"Logging"); test fixtures use synthetic data. `debug_errors: false` in production so that assigns never reach an error page.
- The model contains no automotive fact of its own; every interval, viscosity, capacity, product claim, or fitment in a record is a snapshot of a provenance-carrying catalog value or an explicitly user-entered value labelled as such (INV-15, ADR-0003).
- Transport is HTTPS/WSS with `check_origin` restricted and CSRF verified on socket connect (INV-22; ADR-0004 §"Security and privacy boundary for a hosted application"). This is the hosted substitute for the retired loopback-only INV-2.

### Accessibility and performance

No UI of its own. Two performance obligations bind: the full hydration must complete inside the constitution §9 hydration-completion target with every ordering contract in FR-5 index-backed and no full-store scan-and-sort on the critical path; the read-time integrity pass in FR-11 must be field-local and cheap enough not to threaten that target — if the budget is threatened, the answer is a documented cheaper rule set, never silent skipping. Accessibility obligations attach to the states this model makes distinguishable and are owned by `DOS-M09-003`.

## UX and content states

This card writes no copy but names the states its invariants produce, for `DOS-M09-003` to render:

- **Populated** — valid records for at least one vehicle hydrate; deterministic ordering (FR-5) applies.
- **Quarantine present** — hydration succeeded, one or more records failed integrity; count and stores are known and nameable (FR-12).
- **Rejected mutation** — a write violated a mutation-time invariant; prior state preserved; plain-language error surfaced (FR-12).
- **Read-only mode** — payload newer than deployment; mutations disabled; export offered (FR-12).
- **Compare-and-set conflict** — stale `meta.seq`; re-hydration required (INV-24.7).
- **Cap exceeded** — a hard cap in FR-10 breached at hydration; export offered.
- **Data missing** — the boot hint says this origin held data but the store opens empty or `meta` is absent; distinguishable from a first visit (INV-24.4, INV-24.8, INV-25).

Copy for each belongs to `DOS-M09-003` and MUST satisfy the INV-21 terminology (see `DigitalOilStickerWeb.Copy`): records are "stored in this browser", never "saved to your account", "synced", "backed up", or "restored" (INV-5, INV-21, INV-25).

## Test plan

### Automated

- Schema-document lint: every entity has a field inventory; every field has a type, nullability, and, where applicable, an enumeration or range; the invariant catalogue is numbered and each entry names both enforcement points.
- Shared-fixture equivalence tests: for each invariant fixture (valid and violation), run it through the client hook's `readwrite` transaction and through the server-side hydration changeset (both are `DOS-M09-002`) and assert equal outcomes (accept, quarantine, reject) with equal typed errors.
- Referential test: an event, reading, usage row, and reminder each naming an absent `vehicle_id` quarantine rather than delete on both sides, and are offered to the `DOS-M09-001` repair path.
- Ordering tests: same-instant records for each ordering contract (FR-5) verify `(instant DESC, id ASC)` on both sides; ordering equivalence between client adapter and hydrated assigns is asserted.
- Cap tests: payload size, vehicle count, event count, and reading count each rejected explicitly at the FR-10 boundary; no silent truncation.
- Newer-than-deployment test: a payload one logical version ahead produces read-only mode on the server, no write, export offered; unknown fields survive round-trip.
- Compare-and-set test: a write against a stale `meta.seq` aborts and reports a conflict.
- Historical-readability test: render a fixture whose catalog reference has moved to `unsupported` (INV-11) from its snapshot alone; assert full render.
- Odometer-correction test: the superseding-record path preserves lineage; no path silently rewrites a prior reading.
- Delete-vehicle transaction test: a three-vehicle fixture, delete one, verify counts and byte-identical remaining vehicles.
- Date-only DST test: date-only captures at a spring-forward and a fall-back boundary do not shift by a day on either side.
- Privacy test: a field-name and field-value scan of every fixture asserts no credential, identifier, push subscription, or full-VIN field, and that no fixture value would satisfy a stable-user-identifier heuristic (no email pattern, no long stable random string that persists across fixtures).
- Repo-list test (co-owned with `DOS-M09-007`, which owns the release-gating enforcement of this check): the deployed application's Ecto repo list is exactly `[CatalogRepo]` opened read-only ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Enforcement").

### Manual/browser matrix

- Walk each invariant against a real database in one desktop and one mobile browser drawn from the constitution §9 support matrix (Chrome or Edge desktop, plus iOS Safari 16+), confirming that the enforcement paired with each invariant behaves as specified rather than as assumed. Full matrix coverage is `DOS-M09-008` (browser support matrix and storage-behavior conformance suite); this card confirms the design is implementable on both ends of the matrix before adapter and validator are frozen.
- Inspect a `dos_local` database through browser developer tools after a scripted session and confirm by eye that the entities and fields match this card's inventory and that no unexpected field is present.
- Exercise the data-missing detection manually (populate, clear site data, reload) and confirm the boot hint plus absent `meta` yields the data-missing state rather than a first-visit state.

## Rollout and rollback

Specification and fixtures deliverable; no user-facing rollout of its own. It merges alongside `DOS-M09-001` before `DOS-M09-002` implementation begins, because the hydration protocol at both ends of the wire consumes its invariants and its fixtures. There is no runtime rollback needed for the specification, but the model has a rollback obligation the pre-pivot spec did not: because IndexedDB has no downgrade, a released invariant relaxation that a browser has already written against cannot be tightened later without either a forward-only migration (`DOS-M09-001` FR-7) or a read-time quarantine (FR-12). Every invariant change is therefore additive on the read side (quarantine surface for the tightened case) until a migration has upgraded every deployed browser past it, and this card's fixture suite is edited by adding fixtures, never by removing them. Server-side, a hosted Fly.io release that ships a stricter validator than the deployed clients have code for is rolled back by redeploying the previous image (per `DOS-M09-005`); catalog-artifact rollback is likewise a redeploy of a prior image, because the read-only catalog is baked into the image (ADR-0004 §"Catalog database on Fly").

## Risks, decisions, and open questions

- Risk: the two enforcement points drift silently. The client-side hook code (JavaScript, in the browser transaction) and the server-side changeset (`DigitalOilSticker.LocalStore.Validation`) are written in different languages by different implementers at different times. Mitigation: the shared fixture suite plus the equivalence test (AC-3) is a release gate, not a convention, and every new invariant fixture is added to both harnesses at once.
- Risk: an invariant tightened after release cannot be enforced against browsers that have already written laxer records. Mitigation: tightening is additive on the read side (quarantine) until a `DOS-M09-001` migration has moved every deployed browser past it. Trade-off recorded rather than hidden.
- Risk: the field inventory in this card must stay consistent with `DOS-M09-001`'s store shapes and `app/lib/digital_oil_sticker/local_store/schema/v1.ex`'s implementation. Mitigation: cross-references are section-anchored rather than paraphrased, and a doc-lint test asserts the entity and field names in this card match the store-and-field names in `DOS-M09-001`.
- Risk: hydration integrity checks add work to the critical path of the constitution §9 hydration-completion target. Mitigation: rules are field-local and index-backed on the client side; if the budget is threatened the answer is a documented cheaper rule set with the dropped checks recorded, never silent skipping.
- Decision: retire the pre-pivot FR-1 through FR-11 en bloc rather than translate them one-by-one. The SQL mechanics they described are not reachable in the deployment (`UserRepo` does not exist and cannot, per ADR-0004 Decision items 3 and 4; INV-23); the semantic content is preserved as the invariant catalogue in the new FR-2 and FR-3. The pre-pivot text is retained in the historical section for change readability.
- Decision: **rescope this card rather than close it as superseded by `DOS-M09-001`.** The 2026-08-01 pivot doc's issue-by-issue row (line 108) classifies this card RESCOPE, and the sweep finding that suggested closure ("Close DOS-M04-003 as superseded by the M09 client-storage series") was considered and rejected on one narrow ground: `DOS-M09-001` is the *IndexedDB-specific* schema and upgrade contract, whereas this card is the *client-agnostic* logical model and invariant catalogue that both the current IndexedDB backend and any future non-browser backend must preserve. Keeping the two cards separate is the only way the "two enforcement points against one contract" property has a single owner, and it prevents the roadmap from re-arguing the semantic contract every time a new backend or a new invariant is added. This choice is consistent with the ADR-0004 §Decision-item-6 client-agnostic domain property and does not reintroduce a `UserRepo` in any form.
- Decision: `scheduled_notifications` has no browser home, because nothing is scheduled in this platform (INV-17 rewritten). The concept survives as in-app due-state derivation (rescoped M06 work) that consumes `reminders` + `usage_profiles` and produces no persisted derived record at MVP.
- Open question (owned by this card, to be closed before it merges): whether the invariant catalogue admits a `forecast_snapshots` entity at MVP for explainability and audit. Default is not to persist forecasts, since they are reproducible from stored inputs and the `DOS-M09-001` open question already tracks this decision; the two cards close this question together.
- Open question: whether the usage profile needs full effective-dated history in the browser or one current row plus its inputs is sufficient. Mirrors `DOS-M09-001`'s open question; either answer is a valid realization of this card's model and the two are closed together.
- Open question: whether a future storage backend belonging to a different client (were a new ADR to authorize one — noting that ADR-0005 is already taken by the own-oil-model decision, so a future authorization would be a new number) inherits this card's invariants unchanged. Expected: yes, because the model is deliberately client-agnostic; but the question is left open so a future authorization cannot assume it silently.

## Superseded pre-pivot spec (historical record)

> This section preserves the card as chartered before the 2026-08-01 pivot to browser-first, and is retained for historical readability of the ADR record. The Outcome above is authoritative; the sections below are frozen and no longer describe the work.

### Outcome (pre-pivot)

A fresh UserRepo database supports one local profile, any number of vehicles, odometer history, oil-change history, usage profiles, immutable forecast snapshots, reminder rules, scheduled local notifications, and catalog-install metadata without online identity. The schema is implemented as Ecto migrations with SQL-enforced invariants and deterministic ordering contracts.

### Why this matters and what it unblocks (pre-pivot)

Modeling vehicle ownership explicitly now avoids destructive rework when tabbed multi-vehicle UX arrives after MVP. Every user-facing workflow — recording oil changes, odometer check-ins, forecasts, reminders, notification reconciliation, export/import, and boot migration — persists through these tables. This issue unblocks `DOS-M04-005` (transactional UserRepo workflows), `DOS-M04-007` (boot migrations run over this schema), and `DOS-M04-009` (export/import serializes exactly these entities). Getting invariants into SQL now means later features cannot corrupt history even through bugs in application code.

### Context and source of truth (pre-pivot)

- Master prompt §3 rule 9: "One-vehicle MVP, multi-vehicle-safe internals" — IDs, tables, events, and notification identifiers must safely support many vehicles.
- Master prompt §8 "Database and data-contract baseline", `UserRepo` tables (baseline semantics for `local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications`, `schema_events`), plus the base-unit mileage and UTC/IANA time-zone storage rules.
- §11.2 catalog, "Proposed user schema (multi-vehicle-safe even while the first UI onboards one vehicle)": the full table of required columns, indexes, and constraints for `local_profiles`, `user_vehicles`, `odometer_readings`, `oil_change_events`, `usage_profiles`, `reminder_rules`, `forecast_snapshots`, `scheduled_notifications`, `app_settings`, `catalog_installations`, and `import_history`; and the rule that catalog foreign IDs in user tables are deliberately not SQLite foreign keys across databases — repositories resolve them and always retain display/product/schedule snapshots so history remains intelligible after catalog replacement, product withdrawal, or configuration supersession.
- §11.2 catalog entry "DOS-M04-003 — Implement multi-vehicle-safe user SQL schema and invariants".
- `DOS-M04-001` ADR: adapter, `pool_size: 1`, durability classes, error taxonomy, path layout.

### Included (pre-pivot)

- Implement all proposed user tables through Ecto migrations, including vehicle-scoped `usage_profiles`, `forecast_snapshots`, `reminder_rules`, and `scheduled_notifications`, plus Ecto's migration metadata.
- Generate UUIDs client-side. All child records reference `vehicle_id`; no singleton `current_vehicle` column substitutes for relationships.
- Store catalog stable IDs plus human-readable immutable snapshots on historical events/policies. Catalog deletion or supersession must not erase history.
- Odometer invariants: nonnegative integers, later readings normally cannot be lower; the repository exposes an explicit `odometer_correction` workflow with reason rather than silently rewriting history.
- Date invariants: keep UTC instants for exact events and IANA timezone on profile; if UX captures date-only maintenance, define canonical local-noon/ISO-date behavior rather than accidental UTC date shifts.
- Keep usage inputs separate from forecast outputs: edits close/supersede the current usage profile and the forecast engine appends a new immutable snapshot containing algorithm/input versions. Scheduled notifications reference the exact rule and forecast that produced them so stale native notifications can be cancelled deterministically.
- Default full VIN storage is prohibited (`vin_last6` only, nullable). If later enabled, create a separate privacy/security issue covering consent, encryption, export, deletion, and logging.
- Cascade deletion is allowed only inside an explicit delete-vehicle transaction that previews counts and is separately tested; archive is the normal action.
- Define uniqueness for one active reminder rule per `(vehicle_id, service_code)` and one current usage profile per vehicle (`effective_to IS NULL`).
- Define deterministic ordering `(performed_at DESC, id ASC)`, `(recorded_at DESC, id ASC)`, and `(generated_at DESC, id ASC)`; mirror SQL constraints in Ecto schemas/changesets while SQL remains the final invariant boundary.

### Excluded (pre-pivot)

- Forecast formulas; OS notification scheduling; remote device IDs; catalog product/configuration copies beyond necessary snapshots.
- The transactional workflow layer itself (`DOS-M04-005`), boot-time migration machinery and recovery (`DOS-M04-007`), and export/import (`DOS-M04-009`).
- Any credential, email, password, or online-identity column anywhere in the schema.

### Preconditions (pre-pivot)

- `DOS-M04-001` approved: `Ecto.Adapters.SQLite3`, `pool_size: 1`, user DB durability class, path layout, and error taxonomy fixed.
- The `DOS-M03-002` vocabulary is available (via `DOS-M04-001`'s gate) for snapshot field naming consistency with catalog entities.

### Functional requirements (pre-pivot)

- FR-1: Ecto migrations create all proposed user tables with the required columns, nullability, CHECKs, uniqueness constraints, and indexes: `local_profiles` (PK; CHECK units; initially exactly one active profile by repository policy), `user_vehicles` (PK/FK; nonnegative odometer/year CHECK; INDEX profile/archive/nickname; INDEX catalog config; no full VIN by default), `odometer_readings` (PK/FK; nonnegative CHECK; INDEX vehicle/recorded/id; INDEX vehicle/odometer), `oil_change_events` (PK/FK; value CHECKs; INDEX vehicle/performed/id; INDEX vehicle/odometer), `usage_profiles` (PK/FK; positive/range CHECKs; at most one current row per vehicle; INDEX vehicle/effective dates), `reminder_rules` (PK/FK; UNIQUE active rule per vehicle/service; positive checks; INDEX vehicle/enabled/service), `forecast_snapshots` (PK/FKs; nonnegative/positive CHECKs; immutable by repository policy; INDEX vehicle/generated/id; INDEX reminder rule/generated), `scheduled_notifications` (PK/FKs; UNIQUE platform/native ID when non-null; INDEX vehicle/status/scheduled; INDEX rule/forecast; local OS notification only, no remote push token), `app_settings` (PK key), `catalog_installations` (PK catalog version; INDEX state/installed), `import_history` (PK; INDEX started/status).
- FR-2: All primary keys are client-generated UUIDs (text); every vehicle-scoped child row references `vehicle_id`; no singleton `current_vehicle` column exists anywhere.
- FR-3: Historical events/policies store the stable catalog ID plus a versioned, human-readable JSON snapshot (`configuration_snapshot_json`, `oil_product_snapshot_json`, `filter_product_snapshot_json`, `schedule_snapshot_json`, `input_snapshot_json`), sufficient to render history with the catalog absent or changed.
- FR-4: Odometer values are nonnegative integers; the schema plus repository policy support an explicit `odometer_correction` workflow with a reason, and no path silently rewrites history.
- FR-5: Exact events store UTC instants; the profile stores an IANA timezone; date-only maintenance capture has a defined canonical local-noon/ISO-date rule with no accidental UTC date shifts.
- FR-6: Usage-profile edits close/supersede the current row (`effective_to`); forecast snapshots are append-only and immutable by repository policy, carrying `algorithm_version` and `input_snapshot_json`; `scheduled_notifications` reference the exact `reminder_rule_id` and `forecast_snapshot_id` that produced them.
- FR-7: Full VIN storage is prohibited by schema default (`vin_last6 TEXT NULL` only); enabling full VIN requires a separate privacy/security issue covering consent, encryption, export, deletion, and logging.
- FR-8: Cascade deletion exists only inside an explicit delete-vehicle transaction that previews counts; archiving (`is_archived`) is the normal action and preserves all history.
- FR-9: Every mutable table has `created_at`/`updated_at` timestamps; all JSON snapshots have a versioned canonical shape.
- FR-10: Deterministic ordering contracts are defined and index-backed: `(performed_at DESC, id ASC)` for oil-change events, `(recorded_at DESC, id ASC)` for odometer readings, `(generated_at DESC, id ASC)` for forecast snapshots.
- FR-11: Ecto schemas and changesets mirror the SQL constraints, but SQL remains the final invariant boundary (constraints fire even if a changeset is bypassed).
