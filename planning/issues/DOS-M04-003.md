## Outcome

A fresh UserRepo database supports one local profile, any number of vehicles, odometer history, oil-change history, usage profiles, immutable forecast snapshots, reminder rules, scheduled local notifications, and catalog-install metadata without online identity. The schema is implemented as Ecto migrations with SQL-enforced invariants and deterministic ordering contracts.

## Why this matters and what it unblocks

Modeling vehicle ownership explicitly now avoids destructive rework when tabbed multi-vehicle UX arrives after MVP. Every user-facing workflow — recording oil changes, odometer check-ins, forecasts, reminders, notification reconciliation, export/import, and boot migration — persists through these tables. This issue unblocks `DOS-M04-005` (transactional UserRepo workflows), `DOS-M04-007` (boot migrations run over this schema), and `DOS-M04-009` (export/import serializes exactly these entities). Getting invariants into SQL now means later features cannot corrupt history even through bugs in application code.

## Included

- Implement all proposed user tables through Ecto migrations, including vehicle-scoped `usage_profiles`, `forecast_snapshots`, `reminder_rules`, and `scheduled_notifications`, plus Ecto's migration metadata.
- Generate UUIDs client-side. All child records reference `vehicle_id`; no singleton `current_vehicle` column substitutes for relationships.
- Store catalog stable IDs plus human-readable immutable snapshots on historical events/policies. Catalog deletion or supersession must not erase history.
- Odometer invariants: nonnegative integers, later readings normally cannot be lower; the repository exposes an explicit `odometer_correction` workflow with reason rather than silently rewriting history.
- Date invariants: keep UTC instants for exact events and IANA timezone on profile; if UX captures date-only maintenance, define canonical local-noon/ISO-date behavior rather than accidental UTC date shifts.
- Keep usage inputs separate from forecast outputs: edits close/supersede the current usage profile and the forecast engine appends a new immutable snapshot containing algorithm/input versions. Scheduled notifications reference the exact rule and forecast that produced them so stale native notifications can be cancelled deterministically.
- Default full VIN storage is prohibited (`vin_last6` only, nullable). If later enabled, create a separate privacy/security issue covering consent, encryption, export, deletion, and logging.
- Cascade deletion is allowed only inside an explicit delete-vehicle transaction that previews counts and is separately tested; archive is the normal action.
- Define uniqueness for one active reminder rule per `(vehicle_id, service_code)` and one current usage profile per vehicle (`effective_to IS NULL`).
- Define deterministic ordering `(performed_at DESC, id ASC)`, `(recorded_at DESC, id ASC)`, and `(generated_at DESC, id ASC)`; mirror SQL constraints in Ecto schemas/changesets while SQL remains the final invariant boundary.

## Excluded

- Forecast formulas; OS notification scheduling; remote device IDs; catalog product/configuration copies beyond necessary snapshots.
- The transactional workflow layer itself (`DOS-M04-005`), boot-time migration machinery and recovery (`DOS-M04-007`), and export/import (`DOS-M04-009`).
- Any credential, email, password, or online-identity column anywhere in the schema.

## Preconditions

- The `DOS-M03-002` vocabulary is available (via `DOS-M04-001`'s gate) for snapshot field naming consistency with catalog entities.

## Functional requirements

- FR-1: Ecto migrations create all proposed user tables with the required columns, nullability, CHECKs, uniqueness constraints, and indexes: `local_profiles` (PK; CHECK units; initially exactly one active profile by repository policy), `user_vehicles` (PK/FK; nonnegative odometer/year CHECK; INDEX profile/archive/nickname; INDEX catalog config; no full VIN by default), `odometer_readings` (PK/FK; nonnegative CHECK; INDEX vehicle/recorded/id; INDEX vehicle/odometer), `oil_change_events` (PK/FK; value CHECKs; INDEX vehicle/performed/id; INDEX vehicle/odometer), `usage_profiles` (PK/FK; positive/range CHECKs; at most one current row per vehicle; INDEX vehicle/effective dates), `reminder_rules` (PK/FK; UNIQUE active rule per vehicle/service; positive checks; INDEX vehicle/enabled/service), `forecast_snapshots` (PK/FKs; nonnegative/positive CHECKs; immutable by repository policy; INDEX vehicle/generated/id; INDEX reminder rule/generated), `scheduled_notifications` (PK/FKs; UNIQUE platform/native ID when non-null; INDEX vehicle/status/scheduled; INDEX rule/forecast; local OS notification only, no remote push token), `app_settings` (PK key), `catalog_installations` (PK catalog version; INDEX state/installed), `import_history` (PK; INDEX started/status).
- FR-2: All primary keys are client-generated UUIDs (text); every vehicle-scoped child row references `vehicle_id`; no singleton `current_vehicle` column exists anywhere.
- FR-3: Historical events/policies store the stable catalog ID plus a versioned, human-readable JSON snapshot (`configuration_snapshot_json`, `oil_product_snapshot_json`, `filter_product_snapshot_json`, `schedule_snapshot_json`, `input_snapshot_json`), sufficient to render history with the catalog absent or changed.
- FR-4: Odometer values are nonnegative integers; the schema plus repository policy support an explicit `odometer_correction` workflow with a reason, and no path silently rewrites history.
- FR-5: Exact events store UTC instants; the profile stores an IANA timezone; date-only maintenance capture has a defined canonical local-noon/ISO-date rule with no accidental UTC date shifts.
- FR-6: Usage-profile edits close/supersede the current row (`effective_to`); forecast snapshots are append-only and immutable by repository policy, carrying `algorithm_version` and `input_snapshot_json`; `scheduled_notifications` reference the exact `reminder_rule_id` and `forecast_snapshot_id` that produced them.
- FR-7: Full VIN storage is prohibited by schema default (`vin_last6 TEXT NULL` only); enabling full VIN requires a separate privacy/security issue covering consent, encryption, export, deletion, and logging.
- FR-8: Cascade deletion exists only inside an explicit delete-vehicle transaction that previews counts; archiving (`is_archived`) is the normal action and preserves all history.
- FR-9: Every mutable table has `created_at`/`updated_at` timestamps; all JSON snapshots have a versioned canonical shape.
- FR-10: Deterministic ordering contracts are defined and index-backed: `(performed_at DESC, id ASC)` for oil-change events, `(recorded_at DESC, id ASC)` for odometer readings, `(generated_at DESC, id ASC)` for forecast snapshots.
- FR-11: Ecto schemas and changesets mirror the SQL constraints, but SQL remains the final invariant boundary (constraints fire even if a changeset is bypassed).

## Technical implementation contract

### Components and ownership boundaries

- Migration modules live in the UserRepo-specific bundled migrations path (for example `priv/user_repo/migrations`, finalized in `DOS-M04-007`); this issue authors the initial schema migration set.
- Ecto schema modules and changesets live with their owning contexts (`Garage`, `Maintenance`, `Forecasting`, `Reminders` per §7); this issue defines them as data contracts, while workflow logic is `DOS-M04-005`.
- `catalog_installations` is written by the installer (`DOS-M04-008`) and `import_history` by export/import (`DOS-M04-009`); this issue owns their shape only.

### Data and persistence

- All tables in `user.sqlite3` under the durable user root from `DOS-M04-001`; `pool_size: 1`; foreign keys enforced within the user database only.
- Catalog references (`catalog_vehicle_configuration_id`, `oil_product_id`, `filter_product_id`, `schedule_id`) are plain text stable IDs — deliberately not cross-database SQLite foreign keys — always paired with snapshots.
- Integer mileage columns use a documented fixed unit with boundary conversion so switching miles/kilometers never loses precision (per §8); `odometer_miles`/`interval_miles` columns follow the proposed schema naming with the unit rule documented.
- Uniqueness invariants: at most one current usage profile per vehicle (`effective_to IS NULL`); one active reminder rule per `(vehicle_id, service_code)`; UNIQUE `platform`/`native_notification_id` when non-null.

### Interfaces and events

- The schema exposes no functions; its interface is the migration set, the Ecto schema structs/changesets, and the documented ordering/uniqueness contracts consumed by `DOS-M04-005/007/009`.
- Snapshot JSON shapes are versioned documents; consumers must tolerate reading any released snapshot version.
- Error surfacing uses the `DOS-M04-001` taxonomy (`validation` extensions arrive in `DOS-M04-005`).

### Failure and recovery behavior

- The initial migration creates all tables/constraints/indexes in one transaction; a failure leaves no partial schema.
- Constraint violations surface as typed changeset/constraint errors, never raw SQLite errors, and never corrupt existing rows.
- History readability does not depend on catalog availability: with the catalog file absent or a different version active, all historical rows remain renderable from snapshots.

### Security and privacy

- No credentials, online identity, analytics identity, or push tokens in any table; `scheduled_notifications` holds local OS notification state only.
- Full VIN storage prohibited by default; `vin_last6` is the maximum default vehicle identifier granularity.
- Redaction rule: VIN fragments, mileage, notes, and nicknames never appear in logs or fixtures (§7); test fixtures use synthetic data.
- The user database participates in OS backup per the `DOS-M04-001` durability-class decision.

### Accessibility and performance

- No UI. Index design must support the deterministic ordering contracts and vehicle-scoped lookups without full scans; write amplification stays acceptable at the `DOS-M04-010` stress scale (10+ vehicles, 10 years of monthly readings, 100 oil-change records per vehicle).

## Acceptance criteria

- [ ] AC-1: Fresh migration creates all tables/constraints/indexes in one transaction.
- [ ] AC-2: Two vehicles can independently hold same-dated readings, oil changes, usage profiles, forecasts, reminder rules, and scheduled notifications without cross-contamination.
- [ ] AC-3: Archiving one vehicle preserves it and all history; explicit deletion removes only that vehicle graph.
- [ ] AC-4: Historical rows remain readable with catalog absent or changed because snapshots are sufficient.
- [ ] AC-5: Constraint tests reject orphan vehicle children, negative mileage, invalid units/status, duplicate active reminder rules/current usage profiles, and scheduled notifications that reference another vehicle's rule/forecast.
- [ ] AC-6: Ecto schemas/changesets mirror every SQL constraint, and bypassing the changeset still triggers the SQL constraint (SQL is the final invariant boundary).
- [ ] AC-7: No table contains a credential, email, password, remote session, analytics identity, push token, or full-VIN column.

## Test plan

### Automated

- Migration test: fresh database → single-transaction schema creation; schema dump matches the committed snapshot.
- Entity-relationship fixtures with 3+ vehicles: same-dated rows across vehicles, isolation queries, deterministic ordering assertions for the three ordering contracts.
- Property tests for invariants: nonnegative odometer, one current usage profile per vehicle, one active reminder rule per `(vehicle_id, service_code)`, notification rule/forecast lineage staying within one vehicle, UUID uniqueness.
- Constraint rejection tests per AC-5, exercised both through changesets and through raw inserts that bypass changesets.
- Snapshot sufficiency test: render historical fixtures with no catalog attached and with a different catalog version attached.
- Cascade preview/delete proof: delete-vehicle transaction previews counts, removes exactly one vehicle graph, leaves other vehicles byte-identical.

### Manual/device matrix

- Smoke pass on one physical iOS and one physical Android packaged debug build: run the fresh migration, insert a 3-vehicle fixture, reopen after force-kill, verify counts (full lifecycle/kill matrices are owned by `DOS-M04-006/007/010`).

## Rollout and rollback

Rollout: merge the migration set and schema modules; they take effect on fresh installs and, later, through the `DOS-M04-007` boot migrator. Rollback before any release: revise the unreleased migration set. After a migration set is released, its files are immutable (checksum-enforced in `DOS-M04-007`); changes ship as new forward migrations — never edits, never destructive resets of user history.

## Dependency rationale

Blocked by `DOS-M04-001`: the adapter, `pool_size: 1`, durable user path, durability classes, and error taxonomy must be ratified before the user schema is frozen, and the no-server-account rule constrains what columns may exist. This issue blocks `DOS-M04-005` (workflows mutate these tables), `DOS-M04-007` (boot migrations run this migration set and its fixtures), and `DOS-M04-009` (the export envelope serializes exactly these entities and their snapshot versions).

## Risks, decisions, and open questions

- Risk: snapshot JSON shapes under-specified now cause unreadable history later. Mitigation: versioned canonical shapes (FR-9) plus the AC-4 catalog-absent readability test.
- Risk: date-only capture causing off-by-one dates across time zones. Mitigation: FR-5 canonical local-noon/ISO-date rule with explicit tests, including DST boundaries.
- Decision: exact fixed mileage base unit and conversion boundary (documented per §8; no precision loss on unit switch).
- Decision: canonical date-only representation (local-noon vs ISO-date) — recorded in this issue's docs and consumed by M05/M06.
- Open question: whether `maintenance_plans`/`schema_events` semantics from §8 are folded into `reminder_rules`+`app_settings`+`catalog_installations`/`import_history` naming of the proposed schema — any refinement preserves §8 boundaries and semantics and is recorded with the schema docs.
- Open question: full-VIN support is out of scope indefinitely until a dedicated privacy/security issue exists (consent, encryption, export, deletion, logging).
