## Outcome

Domain/UI code can perform all catalog selection, recommendation-source, product, filter, and provenance queries through a typed, deterministic interface with no knowledge of SQL/storage. `DigitalOilSticker.CatalogRepo` opens the active catalog read-only, returns totally ordered and cursor-paginated results with provenance and freshness, and behaves identically over the golden host fixture and the packaged on-device database.

## Why this matters and what it unblocks

A stable query contract isolates Ecto/SQLite details and allows LiveViews to be built against fixtures before commercial datasets arrive while production uses the same on-device CatalogRepo. Every catalog-consuming feature — the vehicle picker cascade, schedule and requirement display, oil/filter product search, and provenance detail views — depends on this interface, as does the `DOS-M04-010` certification that runs the same contract suite on hosts and physical devices. Freezing ordering, pagination, and typed empty states now prevents UI screens from encoding their own storage assumptions.

## Context and source of truth

- §11.2 catalog entry "DOS-M04-004 — Implement deterministic, read-only `CatalogRepo`".
- `DOS-M04-001` ADR: the required catalog behaviors `metadata/0`, `list_years/1`, `list_makes/2`, `list_models/3`, `list_configurations/4`, `get_configuration/1`, `get_schedules/2`, `get_lubricant_requirements/1`, `search_oils/2`, `list_compatible_filters/2`, `get_provenance/2`; the typed error taxonomy; the total order/cursor contract; read-only/`PRAGMA query_only = ON` handling; `pool_size: 1`.
- `DOS-M04-002`: the catalog SQL schema, indexes, CHECK enums, metadata keys (including search normalization version), and compatible schema window this layer queries.
- Master prompt §4.2 (SQLite runtime, `pool_size: 1`), §7 (`DigitalOilSticker.Catalog` context: read-only vehicle, requirement, product, fitment, provenance, and support-status queries through `CatalogRepo`), §9 "Recommendation resolver" (typed result vocabulary and the rule never to collapse unknown to compatible).
- §11.2 source policy: `list_compatible_filters` semantics — product compatibility means an authorized fitment source asserts the application; supplier assertion must be identified; no fact may be presented as "manufacturer recommended" without qualifying provenance.

## Included

- Implement the methods specified in M04-001 with typed inputs/results and paginated/cursor-based product searches: `metadata/0`, `list_years/1`, `list_makes/2`, `list_models/3`, `list_configurations/4`, `get_configuration/1`, `get_schedules/2`, `get_lubricant_requirements/1`, `search_oils/2`, `list_compatible_filters/2`, `get_provenance/2`.
- Mandatory ordering: years descending; makes/models/configurations by normalized display name then stable ID; schedules by condition/service/effective date/stable ID; oils by brand/product/claim/stable ID; filters by brand/normalized part/stable ID. Never rely on insertion order or collation defaults.
- Normalize search identically at catalog build/query time and record the algorithm version. Prefix search is initial behavior; fuzzy search is excluded until measured and specified.
- Return provenance/freshness/qualifiers alongside recommendation-capable results. `list_compatible_filters` returns only source-asserted, fully applicable fitments for the selected configuration and clearly identifies supplier assertion.
- Prepared/bound parameters only; cap page size; cancel stale UI queries; do not interpolate SQL.
- Start CatalogRepo only after the bundled installer resolves the active database path; open in verified read-only/query-only mode with `pool_size: 1` and reject mutation pragmas/statements.
- Implement typed empty states that distinguish no licensed data, no match, feature disabled, and stale catalog.

## Excluded

- Writing user selections; live provider calls; hiding conflicts or qualifiers; product recommendation ranking without a separately approved rule.
- Fuzzy search (excluded until measured and specified); FTS-dependent behavior where the packaged runtime does not prove FTS5 support.
- The recommendation resolver's verified/partial/conflict decisions themselves (M05/M06 consume this data; `get_schedules` never chooses for the user).

## Preconditions

- `DOS-M04-001` approved: behavior list, error taxonomy, cursor contract, read-only handling.
- `DOS-M04-002` complete: catalog schema, indexes, metadata keys, and golden fixture artifact exist.
- A synthetic/golden catalog fixture (license-clean) is available for host and device contract runs; production data is not required.

## Functional requirements

- FR-1: All eleven behaviors from the M04-001 contract are implemented with typed inputs/results; product searches (`search_oils/2`, `list_compatible_filters/2`, and any configuration search) are paginated/cursor-based.
- FR-2: Mandatory ordering is enforced in SQL with deterministic tiebreakers: years descending; makes/models/configurations by normalized display name then stable ID; schedules by condition/service/effective date/stable ID; oils by brand/product/claim/stable ID; filters by brand/normalized part/stable ID. No result depends on insertion order or collation defaults.
- FR-3: Every page result has `items`, opaque `next_cursor`, `catalog_version`, and `freshness`; cursors encode the last total-order key plus version and are invalid across catalog versions.
- FR-4: Search normalization is byte-identical between catalog build time and query time; the normalization algorithm version is read from catalog metadata and asserted at startup; prefix search is the initial behavior.
- FR-5: Recommendation-capable results (schedules, lubricant requirements, oil claims, filter fitments) carry provenance, freshness, and qualifiers; `list_compatible_filters` returns only source-asserted, fully applicable fitments for the selected configuration and identifies the supplier assertion.
- FR-6: `get_schedules` may return multiple conditions/conflicts and never chooses normal/severe for the user; requirements and oil products are separate types, and any future compatibility service intersects claims explicitly rather than inside this layer.
- FR-7: All SQL uses prepared/bound parameters; page size is capped; stale UI queries are cancellable; string interpolation into SQL is impossible by construction.
- FR-8: CatalogRepo starts only after the installer resolves the active database path, opens in verified read-only/query-only mode (`PRAGMA query_only = ON` plus the verified read-only open option where supported) with `pool_size: 1`, and rejects mutation pragmas/statements with the typed `read_only` error.
- FR-9: Queries return typed empty states distinguishing no licensed data, no match, feature disabled, and stale catalog; corrupted/incompatible databases yield the typed `corrupt`/`incompatible_schema` errors and trigger the manager recovery path.
- FR-10: The same contract suite produces identical domain results from the golden host fixture and the packaged Ecto/SQLite CatalogRepo.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.CatalogRepo` (Ecto repo) plus the `DigitalOilSticker.Catalog` context own all catalog reads; no other module issues catalog SQL (enforced by the `DOS-M04-001` architecture test).
- Query modules translate typed inputs to Ecto queries; result mapping produces typed structs (configurations, schedules, requirements, products, claims, fitments, provenance) — never raw rows or rowids.
- The installer (`DOS-M04-008`) owns path resolution and start/stop around activation; this issue consumes its resolved active path.

### Data and persistence

- Reads exclusively from the active catalog SQLite file produced by `DOS-M04-002`'s schema; zero writes, zero temp tables in the catalog database.
- Cursor encoding: opaque token embedding the last total-order key and `catalog_version`; decoding a cursor from another catalog version returns a typed `invalid_input` (cursor-invalid) result, prompting a fresh first page.
- `metadata/0` exposes `schema_version`, `catalog_version`, `minimum_app_version`, year range, feature flags, and freshness-relevant fields to callers.

### Interfaces and events

- Public behaviors per FR-1 with `@spec`s; every list result is `%{items: [...], next_cursor: opaque | nil, catalog_version: version, freshness: ...}`.
- Errors use the `DOS-M04-001` taxonomy (`not_ready`, `not_found`, `invalid_input`, `corrupt`, `incompatible_schema`, `read_only`, `storage_unavailable`) with recoverability metadata.
- Typed empty states per FR-9 are distinct values, not empty lists with lost meaning.
- On `corrupt`/`incompatible_schema`, the layer notifies the catalog manager (boot/installer recovery path from `DOS-M04-006/008`); it does not attempt self-repair.

### Failure and recovery behavior

- Mutation attempts (statements or pragmas) return typed `read_only` without side effects.
- Corrupted or incompatible databases produce typed errors and trigger the manager recovery path; queries never return partial/garbage rows after an integrity failure is detected.
- Stale-query cancellation: a superseded UI query is cancelled without poisoning the single connection (`pool_size: 1`); timeouts map to typed errors with recoverability metadata.
- `not_ready` is returned (never a crash) if a call arrives before the boot state machine exposes readiness.

### Security and privacy

- Prepared/bound parameters only; SQL injection strings behave as literal search input (proven by tests).
- No user data enters this layer; logs and diagnostics carry query shapes and typed errors, never raw search strings tied to a user identity, and never native paths.
- Provenance/attribution fields pass through unmodified so the UI can meet the source-attribution and "supplier assertion" labeling requirements; this layer never upgrades or hides a qualifier.

### Accessibility and performance

- No direct UI. Performance: queries must use the `DOS-M04-002` indexes (query-plan checked), page size is capped, and exact queries meet the budgets established in `DOS-M04-010` on minimum devices (candidate: warm vehicle-filter query p95 ≤100 ms; oil/filter first page p95 ≤200 ms — final values per the budgets ADR).

## UX and content states

No screens are built here, but the layer defines the data-side vocabulary for UI states: distinct typed empty states (no licensed data, no match, feature disabled, stale catalog), conflict-bearing schedule results (multiple conditions preserved, never auto-resolved), provenance/freshness fields for `SourceBadge`-style components, and supplier-assertion labeling for filter results. M02/M05 own the visual and copy treatment.

## Test plan

### Automated

- Repository contract suite: every behavior, every typed error, every typed empty state, run against the golden host fixture; golden result snapshots committed.
- Determinism tests: rebuild fixture with randomized insertion order and alternate locale/collation environments; assert identical ordering and pagination membership.
- Cursor tests: page walking is gapless/duplicate-free under the total order; cross-version cursor rejection; capped page size.
- Injection tests: adversarial search strings (SQL metacharacters, quotes, `;`, `--`) behave as literals.
- Read-only tests: mutation statements and pragmas return `read_only`; corrupt-file and wrong-schema fixtures return `corrupt`/`incompatible_schema` and invoke the recovery callback.
- Query-plan assertions reusing the `DOS-M04-002` EXPLAIN QUERY PLAN harness for this layer's exact generated SQL.

### Manual/device matrix

- Packaged debug builds on minimum-class physical iOS and Android devices: run the identical contract suite against the installed golden catalog; diff device results against host golden snapshots (must be byte-identical at the domain-result level).
- Airplane-mode execution of the device contract run (no network required for any catalog read).
- Timing capture for the budget-relevant queries on both devices, feeding `DOS-M04-010` certification.

## Rollout and rollback

Rollout: merge behind the boot readiness gate; the layer is exercised first by fixtures/tests, then by M05 screens. Rollback: revert the query-layer commits — the schema (`DOS-M04-002`) and installer (`DOS-M04-008`) are independent, and no persistent state is owned by this layer, so rollback has no data migration cost. Contract changes after M05 consumes the API require a versioned deprecation note in the repository contract doc.

## Documentation and evidence

- Repository contract suite and committed golden result snapshots (host + device).
- Query-plan/performance report for the generated SQL.

## Dependency rationale

Blocked by `DOS-M04-001` (behavior list, error taxonomy, cursor/order contract, read-only rule are ratified there) and `DOS-M04-002` (tables, indexes, CHECK enums, and metadata keys must exist and be frozen before deterministic SQL is written against them). This issue blocks catalog-consuming UI/features (M05 vehicle picker, schedule/requirement display, product pickers) and `DOS-M04-010` (the certification runs this contract suite on hosts and packaged devices). It deliberately precedes licensed data: the golden fixture strategy lets everything ship against synthetic data per the M04 dependency-order rule.

## Risks, decisions, and open questions

- Risk: collation/locale differences between host SQLite and packaged device SQLite silently reorder results. Mitigation: explicit normalized-key ordering with stable-ID tiebreakers (FR-2) plus AC-2 randomized/locale tests on both targets.
- Risk: cursor invalidation across catalog activation surprises the UI mid-scroll. Mitigation: FR-3 typed cursor-invalid result and a documented "restart from first page" recovery the UI must implement.
- Risk: `pool_size: 1` head-of-line blocking from slow queries. Mitigation: capped page sizes, stale-query cancellation, budget enforcement in `DOS-M04-010`.
- Decision (deferred by exclusion): any product recommendation ranking requires a separately approved rule before implementation.
- Open question: whether the verified read-only open option is available in the pinned `ecto_sqlite3` (answer inherited from the `DOS-M04-001` ADR); `PRAGMA query_only = ON` is mandatory either way.
- Open question: fuzzy search remains excluded until measured and specified — a future issue must define matching, ranking, and budgets.

- Golden result snapshots, query-plan report, and read-only/corruption traces committed.
