## Outcome

All local profile, vehicle, odometer, oil-change, usage-profile, forecast-snapshot, reminder-rule, scheduled-notification, settings, and archive/delete workflows are atomic, typed, and safe for multiple vehicles. `DigitalOilSticker.UserRepo` mutations run through one transactional boundary with optimistic concurrency, idempotent retries, explicit `vehicle_id` scoping, and typed field-level validation.

## Why this matters and what it unblocks

Feature teams need one durable mutation boundary so calculations and UI cannot create partial history or accidentally operate on the wrong vehicle tab. The `record_oil_change` transaction defined here is the core write path of the whole product (§6 journey step 8: recording a new oil change closes the previous cycle, starts a new one, recomputes the forecast, and replaces obsolete notification requests atomically). This issue unblocks all user-facing history/reminder features (M05/M06), export/import (`DOS-M04-009` serializes through this boundary's entities), and certification (`DOS-M04-010` runs this contract suite under fault injection on devices).

## Included

- CRUD/list APIs for local profile and vehicles; append/correct odometer; create/update/delete oil-change events; supersede usage profile; append immutable forecast snapshot; upsert reminder rule; schedule/cancel/update local notification state; settings; archive and explicit delete.
- Multi-step `record_oil_change` uses `UserRepo.transaction/1` (or `Ecto.Multi`) to insert the event, optionally add an odometer reading, advance current odometer only when valid, snapshot chosen catalog items, invalidate/recalculate the affected forecast, and return notification-rescheduling work. Any failure rolls back all database steps; native OS notification calls occur after commit and reconcile through `scheduled_notifications`.
- Optimistic concurrency via `updated_at` plus version counter or equivalent; stale edits return typed conflict.
- Every vehicle-scoped mutation requires explicit `vehicle_id`; there is no hidden global active-vehicle dependency inside repository code.
- Typed validations mirror database constraints and return field-level errors without SQL/internal details.
- Local event IDs generated before commit allow idempotent UI retries; duplicate ID with identical payload is success, differing payload is conflict.
- Repository structs and canonical snapshot schemas including snapshot version, catalog version, stable catalog ID, display fields, source/provenance label needed later, and selected qualifiers.
- Deterministic list functions with bounded limit and cursor tied to user DB revision where necessary.

## Excluded

- Forecasting algorithm itself; OS notification call; remote sync/merge; silently deleting history when a catalog item disappears.
- The forecast math (M06) — this issue appends/invalidates snapshots produced elsewhere and returns notification-rescheduling work; it never computes due dates.
- The native notification bridge invocation (owned by the `DeviceCommandBroker`/Reminders adapter path; this issue only persists and reconciles `scheduled_notifications` state).

## Functional requirements

- FR-1: Typed public APIs exist for: local profile CRUD/list; vehicle CRUD/list/archive/explicit delete; odometer append and explicit `odometer_correction` with reason; oil-change event create/update/delete; usage-profile supersession; immutable forecast-snapshot append; reminder-rule upsert; scheduled-notification state schedule/cancel/update; settings read/write.
- FR-2: `record_oil_change` executes as a single `UserRepo.transaction/1` (or `Ecto.Multi`) performing: event insert → optional odometer reading insert → current-odometer advance only when valid → catalog-item snapshot capture → affected-forecast invalidation/recalculation trigger → return of notification-rescheduling work. Any step failure rolls back every database step.
- FR-3: Native OS notification calls happen only after commit and reconcile through `scheduled_notifications`; a crash between commit and native call is recoverable by reconciliation, never by data loss.
- FR-4: Optimistic concurrency uses `updated_at` plus a version counter or equivalent; a stale edit returns the typed `conflict` error and never overwrites the newer row.
- FR-5: Every vehicle-scoped mutation takes an explicit `vehicle_id` parameter; repository code contains no global active-vehicle state.
- FR-6: Validations are typed, mirror the SQL constraints, and return field-level errors without SQL/internal details; the error set extends M04-001 with `validation`, `conflict`, and `referenced`, each with safe recovery guidance.
- FR-7: Local event IDs are generated before commit; retrying with a duplicate ID and identical payload is success (idempotent), a duplicate ID with differing payload is `conflict`.
- FR-8: List functions have deterministic order (per the `DOS-M04-003` ordering contracts), bounded limit, and a cursor tied to user DB revision where necessary.
- FR-9: Canonical snapshot schemas include snapshot version, catalog version, stable catalog ID, display fields, source/provenance label needed later, and selected qualifiers.
- FR-10: Archive is the default lifecycle action; explicit delete runs only in the previewed delete-vehicle transaction from `DOS-M04-003` and removes exactly one vehicle graph.
- FR-11: Mutations emit the local events (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`) carrying local stable IDs and reason codes, not display strings.
- FR-12: All workflows function fully offline; no code path in this boundary performs a network request.

## Technical implementation contract

### Components and ownership boundaries

- Context modules `DigitalOilSticker.Garage` (profile/vehicles), `DigitalOilSticker.Maintenance` (oil-change events, plans/snapshots), `DigitalOilSticker.Reminders` (reminder rules, scheduled-notification state) own their workflows; all write through `DigitalOilSticker.UserRepo` only.
- Forecast computation is invoked as a pure-function dependency (`DigitalOilSticker.Forecasting`, M06); this issue owns persistence of its outputs and invalidation triggers only.
- Native notification execution is behind the `NotificationAdapter` behaviour/DeviceCommandBroker; this issue owns only the post-commit reconciliation contract with `scheduled_notifications` rows.

### Data and persistence

- All writes target the `DOS-M04-003` tables under `pool_size: 1`; transactions are short and never span user interaction.
- Snapshot JSON follows the canonical versioned shapes; snapshots are written inside the same transaction as the rows referencing them.
- Cursor/list reads may use a user-DB revision marker so pagination remains stable across interleaved writes where required.
- Idempotency keys are the client-generated UUID primary keys; no separate dedupe table is required.

### Interfaces and events

- Public typed functions with `@spec`s; results are `{:ok, struct-or-page}` or `{:error, typed_error}` using the extended taxonomy (`validation`, `conflict`, `referenced` plus the M04-001 base set) with recoverability metadata and safe recovery guidance.
- `record_oil_change` returns the committed entities plus a notification-rescheduling work order (rows to cancel/schedule) for the Reminders adapter to execute post-commit.
- Local events per FR-11 are emitted after successful commit (direct context return plus Phoenix PubSub where more than one active process needs it, per §7).

### Failure and recovery behavior

- Any failure inside a multi-step transaction rolls back all database steps; forced failure at each `record_oil_change` statement leaves no partial event/reading/odometer update.
- Post-commit native-call failure leaves `scheduled_notifications` rows in a reconcilable state (status/last_error_code) for deterministic retry; the database commit is never undone by a native failure.
- Stale-edit conflicts, duplicate-ID conflicts, and referenced-deletion attempts return typed errors with recovery guidance; nothing is silently overwritten or deleted.
- When a referenced catalog item disappears in a later catalog version, history is never deleted; snapshots keep rows renderable (per `DOS-M04-003`).

### Security and privacy

- No network access anywhere in this boundary (verified by offline trace); no remote sync/merge.
- Field-level errors never leak SQL, schema internals, or native paths.
- Logs/diagnostics redact VIN fragments, mileage, notes, and nicknames; fixtures are synthetic.
- No credential or online-identity surface exists in any workflow.

### Accessibility and performance

- No direct UI. Write-path budget target from the `DOS-M04-010` candidates: UserRepo write transaction p95 ≤150 ms (final values per the budgets ADR); list reads are bounded and index-backed; transactions never block on user input or network.

## Test plan

### Automated

- Repository contract/property suite covering every FR-1 workflow, typed errors, and field-level validation messages.
- Fault-injection transaction tests: force failure at each statement of `record_oil_change` (and other multi-step flows) and assert full rollback.
- Concurrency tests: parallel stale edits (one commit, one `conflict`); duplicate idempotency ID with identical payload (success) and differing payload (`conflict`).
- Multi-vehicle isolation property tests with 3+ vehicles across all entities and list functions.
- Lineage tests: usage profile → forecast snapshot → reminder rule → scheduled notification chains stay within one vehicle; post-commit reconciliation identifies obsolete notification rows.
- Event-emission tests: correct local events with stable IDs and reason codes after each mutation class.

### Manual/device matrix

- Packaged debug builds on minimum-class physical iOS and Android devices in airplane mode: execute every workflow end-to-end (profile, vehicle, odometer, correction, oil change, usage supersession, forecast append, reminder upsert, notification state, settings, archive, previewed delete) and capture an offline network trace showing zero requests.
- Force-kill the app between commit and simulated native notification call; relaunch; verify reconciliation completes from `scheduled_notifications` state.

## Rollout and rollback

Rollout: merge behind the boot readiness gate; M05 screens adopt the APIs incrementally. Rollback: revert the workflow commits — the schema is owned by `DOS-M04-003` and is unaffected; no data migration is introduced by this issue. Because the API is the single mutation boundary, breaking changes after M05 adoption require a migration note in the repository contract doc and coordinated UI updates.

## Risks, decisions, and open questions

- Risk: post-commit native notification failures could strand stale OS notifications. Mitigation: FR-3 reconciliation-through-`scheduled_notifications` contract plus the kill-between-commit-and-call device test.
- Risk: hidden active-vehicle convenience creeping into APIs under MVP pressure. Mitigation: FR-5/AC-7 explicit-`vehicle_id` rule and API review.
- Risk: long transactions blocking the single connection. Mitigation: short transactions, no user-interaction or network inside a transaction, budget checks in `DOS-M04-010`.
- Decision: exact optimistic-concurrency mechanism (`updated_at` + version counter vs equivalent) — chosen here and documented in the API reference.
- Decision: which list functions need a user-DB-revision-tied cursor vs simple bounded lists — documented per function.
- Open question: the precise notification-rescheduling work-order shape consumed by M06's reminder reconciliation — defined here, versioned, and refined only through the M06 issues without breaking this contract.
