> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Becomes a browser storage adapter providing transactional IndexedDB semantics, with the server holding the same data only in socket assigns for the session lifetime._

## Outcome

A typed, multi-vehicle-safe **domain workflow layer** — `DigitalOilSticker.Garage`, `.Maintenance`, and `.Reminders` — sits over the browser storage adapter defined by [DOS-M09-002](DOS-M09-002.md) and provides **transactional IndexedDB semantics** for every personal-data workflow: local profile CRUD, vehicle CRUD/archive/previewed delete, odometer append and explicit correction, oil-change events, usage-profile supersession, immutable forecast-snapshot append, reminder-rule upsert, in-app reminder state (in place of the retired OS-scheduled notifications), preferences, and versioned export/import staging. The multi-step `record_oil_change` workflow executes as **one IndexedDB `readwrite` transaction** across `events` + `readings` + `vehicles` + `reminders` + `meta` (per [ADR-0004 §"Mutation round trip"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#mutation-round-trip)): event upsert → optional odometer append → current-odometer advance only when valid → catalog-item snapshot capture → affected-forecast invalidation → reminder work-order production → compare-and-set on `meta.seq` — all or nothing. **The server never persists any of this to disk**: personal data exists on the server only as transient values in `socket.assigns` for the lifetime of one LiveView connection ([INV-3](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), [INV-23](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), [INV-24.1](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), [ADR-0004 Decision §4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision)), and every mutation is only considered committed when the hook returns `local_store:ack` per [INV-24.2](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage). Optimistic concurrency is compare-and-set on `meta.seq`, idempotency is by client-generated UUID, and every vehicle-scoped write requires an explicit `vehicle_id`. The snapshot-backed history rule survives so that a catalog reference going `unsupported` in a later `data_version` never deletes a row from the user's garage ([INV-11](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-15](../../docs/product/CONSTITUTION.md#5-core-user-promise)).

## Why this matters and what it unblocks

The `record_oil_change` transaction is the core write path of the whole product — recording a new oil change closes the previous cycle, starts a new one, recomputes the forecast, and replaces obsolete reminder state atomically. Under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) the atomicity boundary is no longer an Ecto `UserRepo.transaction/1` on device — the server has no `UserRepo` at all ([DOS-M01-003](DOS-M01-003.md) as re-scoped, [ADR-0004 Decision §4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision)) — it is a single IndexedDB `readwrite` transaction opened by the `LocalStore` JS hook across every affected object store plus `meta`. Freezing the typed workflow API, the atomicity boundary, the optimistic-concurrency rule, the idempotency-by-UUID rule, the explicit-`vehicle_id` rule, and the canonical snapshot shape at M04 is what lets M05 forms and dashboards, M06 forecasting and reminder reconciliation, [DOS-M04-009](DOS-M04-009.md) export/import, and [DOS-M04-010](DOS-M04-010.md) conformance target a decided contract instead of re-litigating it under the browser adapter.

It also freezes the layering that keeps the domain client-agnostic per [ADR-0004 Decision §6](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision): the `Garage`/`Maintenance`/`Reminders` contexts here MUST NOT reference `Phoenix.LiveView`, the `LocalStore` hook, or any transport. They call the browser-storage port defined by [DOS-M09-002](DOS-M09-002.md); a future OS-shell client would swap that port for a different local storage adapter and reuse this workflow layer unchanged. This card is the seam that makes the OS-shell deferral (INV-1) mechanically true.

## Included

- Typed public workflow API for: local profile CRUD/list; vehicle CRUD/list/archive/previewed delete; odometer append and explicit `odometer_correction` with reason; oil-change event create/update/delete; usage-profile supersession; immutable forecast-snapshot append; reminder-rule upsert; **in-app reminder state** schedule/cancel/update; preferences read/write.
- Multi-step `record_oil_change` executing as **one IndexedDB `readwrite` transaction** across `events` + `readings` + `vehicles` + `reminders` + `meta`. Any step failure (validation, `QuotaExceededError`, stale `meta.seq`, DOMException) aborts the whole transaction; nothing is left partially applied.
- Optimistic concurrency via compare-and-set on `meta.seq` inside the same transaction; a stale write aborts and surfaces `local_store:conflict`, the server triggers re-hydration, and the losing tab is told plainly ([INV-24.7](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)).
- Explicit `vehicle_id` on every vehicle-scoped mutation; no global active-vehicle state. Multi-vehicle isolation verified by property tests across 3+ vehicles.
- Typed validations mirroring [DOS-M04-003](DOS-M04-003.md)-as-rescoped invariants (nonnegative odometer, monotonic-with-correction, at-most-one-current-usage-profile, one-active-reminder-per-`(vehicle_id, service_code)`, snapshot presence on historical rows), returning field-level errors. Error taxonomy extends [DOS-M04-001](DOS-M04-001.md)-as-rescoped with `validation`, `conflict`, `referenced`, `quota_exceeded`, and `storage_unavailable`.
- Client-generated UUID as the idempotency key on every write; same UUID + identical payload is no-op success, same UUID + differing payload is `conflict`.
- Canonical versioned snapshot schemas (snapshot version, catalog `data_version`, stable catalog ID, display fields, provenance label, selected qualifiers) written inside the same `readwrite` transaction as their referencing rows. History is never deleted when a catalog reference disappears ([INV-11](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-15](../../docs/product/CONSTITUTION.md#5-core-user-promise)).
- Deterministic list functions with bounded limit served from hydrated assigns; ordering `(performed_at DESC, id ASC)` / `(recorded_at DESC, id ASC)` / `(generated_at DESC, id ASC)`.
- Archive as default lifecycle; explicit delete only in the previewed delete-vehicle transaction.
- In-process events (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`) emitted **after** `local_store:ack`, carrying stable client-side IDs and reason codes, not display strings. No OS-scheduled local notification ([INV-17](../../docs/product/CONSTITUTION.md#6-reminders-and-notifications)).
- **Append-only audit** for `oil_change_events` and `odometer_readings` enforced in the workflow layer: no code path mutates a prior event in place or silently overwrites an odometer with a lower value.

The `scheduled_notifications` name and shape survive only as **in-app reminder state** rendered on the dashboard and vehicle card; the MVP UI states plainly that the app does not notify the user when it is closed. Web Push is deferred to [DOS-M09-010](DOS-M09-010.md) and MUST NOT be shipped incrementally through this card.
- FR-4 *(rewritten from pre-pivot FR-4)*: Optimistic concurrency is **compare-and-set on `meta.seq` inside the same `readwrite` transaction** ([ADR-0004 §"Multi-tab consistency"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#multi-tab-consistency)); a stale write aborts, surfaces `local_store:conflict`, and the server triggers re-hydration and renders the visible "reloaded from this browser's newer data" notice — never a silent overwrite ([INV-24.7](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)). Last-write-wins-at-record-granularity is a deliberate simplification with the loss made visible; it is not silent.
- FR-5 *(kept)*: Every vehicle-scoped mutation takes an explicit `vehicle_id`; the workflow layer contains no global active-vehicle state, no implicit "current vehicle" resolver, and no per-socket cached vehicle scope. Vehicle-scoped list functions filter on `vehicle_id` in the payload shape.
- FR-6 *(kept; error set extended)*: Validations are typed, mirror the [DOS-M04-003](DOS-M04-003.md)-as-rescoped invariants, and return field-level errors without SQL, schema-internal, or transport details. The error taxonomy extends [DOS-M04-001](DOS-M04-001.md) as re-scoped with `validation`, `conflict`, `referenced`, `quota_exceeded` ([INV-24.5](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), never silent), and `storage_unavailable` ([INV-24.6](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage) private-browsing/blocked-storage), each with safe recovery guidance.
- FR-7 *(kept and reinforced; addresses sweep finding on idempotency-by-UUID)*: Client-generated UUIDs are the idempotency key on every write. Retry with same UUID + identical payload is success (transaction is a no-op because the key already exists); retry with same UUID + differing payload returns `conflict`. Duplicate-payload conflict detection compares the canonical serialization of the incoming record with the stored record; a differing snapshot version alone does not trigger `conflict` (see FR-9). Enforced at the workflow layer against the adapter's key-based reads inside the same transaction; the server never carries a durable dedupe table ([INV-23](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)).
- FR-8 *(kept)*: List functions are deterministic (per the [DOS-M04-003](DOS-M04-003.md) ordering contracts), bounded by an explicit limit, and served from hydrated assigns. Because there is no server database of personal rows, a "user DB revision" cursor is not required; `meta.seq` at list time defines the stable ordering, and interleaved writes advance `meta.seq` (surfacing as re-hydration per FR-4).
- FR-9 *(kept and reinforced; addresses sweep finding on snapshot-backed history)*: Canonical versioned snapshot schemas include snapshot version, catalog `data_version`, stable catalog ID, display fields, source/provenance label, and selected qualifiers. Snapshots are written inside the same `readwrite` transaction as the rows referencing them. When a catalog reference goes `unsupported` in a later `data_version`, history is **never deleted**; the snapshot keeps the row renderable, and the UI labels the reference as unsupported for future use only ([INV-11](../../docs/product/CONSTITUTION.md#4-coverage-contract-ratifies-the-5-planning-default), [INV-15](../../docs/product/CONSTITUTION.md#5-core-user-promise)).
- FR-10 *(kept)*: Archive is the default lifecycle; explicit delete runs only in the previewed delete-vehicle transaction from [DOS-M04-003](DOS-M04-003.md) as re-scoped and removes exactly one vehicle graph.
- FR-11 *(rewritten from pre-pivot FR-11)*: Mutations emit in-process events (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`) **after** `local_store:ack`, carrying stable client-side IDs and reason codes, not display strings. The LiveView updates assigns; cross-tab propagation rides `BroadcastChannel("dos_local_store")` per [ADR-0004 §"Multi-tab consistency"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#multi-tab-consistency) and [DOS-M09-003](DOS-M09-003.md). Because the server never persists these events, socket termination discards them, and reconnect re-runs hydration per [INV-24.1](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage).
- FR-12 *(retires pre-pivot FR-12; the "no network" claim is dead)*: The workflow layer does not itself perform outbound network I/O, but the deployed application **requires connectivity** for the mutation round trip — the write is not committed until the hook returns `local_store:ack` over the LiveView socket ([INV-24.2](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), [INV-6](../../docs/product/CONSTITUTION.md#3-data-availability-and-connectivity-replaces-offline-first) as amended). The old airplane-mode assertion is deleted; the honest-degradation contract is FR-14.
- FR-13 *(new; addresses sweep finding on multi-vehicle isolation)*: Property tests running against the in-memory browser storage double MUST assert that with 3+ vehicles present, no vehicle-scoped read or write ever returns or mutates another vehicle's data, that `record_oil_change` for vehicle A never touches an object-store entry keyed by vehicle B, and that the reminder work-order produced by a mutation on vehicle A never references vehicle B's reminder rules. The property test set is a release gate.
- FR-14 *(new; addresses sweep finding on the hydration protocol and connectivity honesty)*: Every write **is not considered committed** until the hook returns `local_store:ack` for the exact `mutation_id` and `seq` produced by this card ([INV-24.2](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)). If no ack arrives within the [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) 2000 ms window or the ack reports an error (including `QuotaExceededError`), the workflow layer surfaces the affected record as **persistent, non-dismissible "Not saved to this browser"**, keeps the optimistic value visible but visibly marked as unsaved, and offers export; it does not retry silently and it does not roll back invisibly. Pending writes are re-driven from client storage on reconnect ([INV-7](../../docs/product/CONSTITUTION.md#3-data-availability-and-connectivity-replaces-offline-first) — no queued or pending mutation may be silently dropped on reconnect).
- FR-15 *(new; addresses sweep finding on the retired native contract and enforces client-agnostic domain)*: No module in the `DigitalOilSticker.Garage`, `.Maintenance`, `.Reminders`, or `.Forecasting` namespace references `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules ([ADR-0004 Decision §6](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision) and §"Enforcement", second bullet). The workflow layer calls the browser-storage port through a behaviour whose only production is the JS-hook-backed adapter from [DOS-M09-002](DOS-M09-002.md), with a server-side test double for unit tests. This is what makes "native mobile is deferred, not deleted" mechanically true.
- FR-16 *(new; addresses sweep finding on append-only audit and INV-4 log hygiene)*: The workflow layer enforces **append-only** semantics for `oil_change_events` and `odometer_readings`: no function updates a historical event in place, and the odometer path exposes append + explicit `odometer_correction`-with-reason only — never a silent overwrite. Logs emitted from this layer MUST NOT include VINs, odometer values, service dates, note text, custom vehicle names, `mutation_id`, or `tab_id` ([INV-4](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), [ADR-0004 §"Logging"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#logging)); event names and error tags are allowed, params are not.
- FR-17 *(new; enforces INV-26 in write payloads)*: Write payloads produced by this card are consumed by the browser storage adapter only; they MUST NOT be routed to the catalog query layer ([DOS-M09-005](DOS-M09-005.md)) or otherwise leak a VIN, an odometer reading, a note, or any stable client identifier into a request the server could reconstruct a garage from ([INV-26](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)).

## Technical implementation contract

### Components and ownership boundaries

Domain contexts `DigitalOilSticker.Garage`, `.Maintenance`, and `.Reminders` own their workflows; every write goes through the **browser-storage port** defined by [DOS-M09-002](DOS-M09-002.md), never a server database. Forecast computation is invoked as a pure-function dependency (`DigitalOilSticker.Forecasting`, M06); this card owns persistence of its outputs and invalidation triggers only. **No OS-delivery bridge, command broker, or notification adapter behaviour exists in the workflow layer** — the reminder path stops at producing in-app reminder state per [INV-17](../../docs/product/CONSTITUTION.md#6-reminders-and-notifications). The workflow layer does not import `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules (FR-15); the LiveView adapter that carries the round trip is [DOS-M09-003](DOS-M09-003.md).

### Data and persistence

- Personal data is written **only** to IndexedDB, only through the [DOS-M09-002](DOS-M09-002.md) adapter, only inside one `readwrite` transaction spanning the affected object stores plus `meta`, and only after the compare-and-set on `meta.seq` succeeds. Transactions are short and never span user interaction.
- On the server, personal data exists **only as transient values in `socket.assigns`** for the lifetime of one LiveView connection; nothing is written to disk, database, cache, ETS table, external store, or log ([ADR-0004 Decision §4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision), [INV-3](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), [INV-23](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)).
- Snapshot JSON follows the canonical versioned shapes and is written inside the same transaction as the rows referencing them; catalog references are plain UUID/text stable IDs — deliberately not cross-store foreign keys, since IndexedDB has none — always paired with the snapshot.
- Idempotency keys are client-generated UUIDv4 primary keys per [ADR-0004 §"Storage layout"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#storage-layout); no separate dedupe store on the client, and no dedupe cache on the server.

### Interfaces and events

- Public typed functions with `@spec`s return `{:ok, struct-or-page}` or `{:error, typed_error}` using the extended taxonomy (`validation`, `conflict`, `referenced`, `quota_exceeded`, `storage_unavailable`) with recoverability metadata and safe recovery guidance.
- `record_oil_change` returns the committed entities plus a **reminder work-order** (in-app reminder rows to cancel/schedule) that the Reminders context consumes to update `assigns.reminders` — never an OS notification queue.
- In-process events per FR-11 are emitted after successful `local_store:ack` and consumed by the LiveView for assigns updates and by the multi-tab `BroadcastChannel` per [DOS-M09-003](DOS-M09-003.md). `Phoenix.PubSub` is used only for the same-node LiveView notification and never carries the payload to another process outside the socket owner.

### Failure and recovery behavior

- Any failure inside the `readwrite` transaction — a validation error thrown before commit, a `QuotaExceededError` at any request, a DOMException, or a stale `meta.seq` — aborts the whole transaction; no partial state is observable, and the hook returns an error ack that FR-14 renders as **"Not saved to this browser"** with the optimistic value visibly marked unsaved and export offered.
- Stale-edit conflicts, duplicate-ID conflicts (FR-7), and referenced-deletion attempts return typed errors with recovery guidance; nothing is silently overwritten or deleted, and last-write-wins is a **visible** loss per [INV-24.7](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage).
- When a referenced catalog item disappears in a later catalog `data_version`, history is never deleted; snapshots keep rows renderable per FR-9.
- Because there is no post-commit OS-delivery step (FR-3), there is no post-commit crash-between-commit-and-OS-delivery recovery path. The old "force-kill between commit and OS-delivery call, verify reconciliation" test is retired.
- Reconnect re-hydrates rather than assuming assigns survived ([INV-7](../../docs/product/CONSTITUTION.md#3-data-availability-and-connectivity-replaces-offline-first), [INV-24.1](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)); pending writes are re-driven from client storage, so a deploy or a network blip mid-mutation surfaces as re-hydration and re-drive, not silent data loss.

### Security and privacy

- No third-party network access from the workflow layer; no remote sync; no cloud, user-account, auth, anonymous-ID, push-subscription, or session-durable personal table anywhere in the deployed application ([ADR-0004 Decision §4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision), [DOS-M01-003](DOS-M01-003.md) as re-scoped).
- Field-level errors never leak schema internals, transport details, `mutation_id`, or `tab_id`.
- Logs and diagnostics MUST NOT include VINs, odometer values, service dates, note text, custom vehicle names, `mutation_id`, or `tab_id` (FR-16); fixtures are synthetic and contain no real VINs.
- Write payloads MUST NOT reach the catalog query surface ([DOS-M09-005](DOS-M09-005.md)) carrying personal fields (FR-17, [INV-26](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)).
- No credential or online-identity surface exists, and no anonymous stable client identifier is stored on the server or transmitted in a way the server could correlate across visits.

### Accessibility and performance

No direct UI. Write-path budget targets from [CONSTITUTION.md §9](../../docs/product/CONSTITUTION.md#9-measurable-targets) as re-ratified 2026-08-01: hydration completion p95 ≤ 300 ms after socket join; LiveView event round trip p95 ≤ 150 ms measured from the client; write + forecast recompute p95 ≤ 150 ms server-side; client storage footprint held under a 5 MiB working ceiling with `QuotaExceededError` surfaced visibly ([INV-24.5](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)). Transactions never block on user input or on catalog queries.

### Technical implementation contract (pre-pivot)

**Components and ownership boundaries.** Context modules `DigitalOilSticker.Garage` (profile/vehicles), `DigitalOilSticker.Maintenance` (oil-change events, plans/snapshots), `DigitalOilSticker.Reminders` (reminder rules, scheduled-notification state) own their workflows; all write through `DigitalOilSticker.UserRepo` only. Forecast computation is invoked as a pure-function dependency (`DigitalOilSticker.Forecasting`, M06); this issue owns persistence of its outputs and invalidation triggers only. Native notification execution is behind the `NotificationAdapter` behaviour/DeviceCommandBroker; this issue owns only the post-commit reconciliation contract with `scheduled_notifications` rows.

**Data and persistence.** All writes target the `DOS-M04-003` tables under `pool_size: 1`; transactions are short and never span user interaction. Snapshot JSON follows the canonical versioned shapes; snapshots are written inside the same transaction as the rows referencing them. Cursor/list reads may use a user-DB revision marker so pagination remains stable across interleaved writes where required. Idempotency keys are the client-generated UUID primary keys; no separate dedupe table is required.

**Interfaces and events.** Public typed functions with `@spec`s; results are `{:ok, struct-or-page}` or `{:error, typed_error}` using the extended taxonomy (`validation`, `conflict`, `referenced` plus the M04-001 base set) with recoverability metadata and safe recovery guidance. `record_oil_change` returns the committed entities plus a notification-rescheduling work order (rows to cancel/schedule) for the Reminders adapter to execute post-commit. Local events per FR-11 are emitted after successful commit (direct context return plus Phoenix PubSub where more than one active process needs it, per §7).

**Failure and recovery behavior.** Any failure inside a multi-step transaction rolls back all database steps; forced failure at each `record_oil_change` statement leaves no partial event/reading/odometer update. Post-commit native-call failure leaves `scheduled_notifications` rows in a reconcilable state (status/last_error_code) for deterministic retry; the database commit is never undone by a native failure. Stale-edit conflicts, duplicate-ID conflicts, and referenced-deletion attempts return typed errors with recovery guidance; nothing is silently overwritten or deleted. When a referenced catalog item disappears in a later catalog version, history is never deleted; snapshots keep rows renderable (per `DOS-M04-003`).

**Security and privacy.** No network access anywhere in this boundary (verified by offline trace); no remote sync/merge. Field-level errors never leak SQL, schema internals, or native paths. Logs/diagnostics redact VIN fragments, mileage, notes, and nicknames; fixtures are synthetic. No credential or online-identity surface exists in any workflow.

**Accessibility and performance.** No direct UI. Write-path budget target from the `DOS-M04-010` candidates: UserRepo write transaction p95 ≤150 ms (final values per the budgets ADR); list reads are bounded and index-backed; transactions never block on user input or network.

### Risks, decisions, and open questions (pre-pivot)

- Risk: post-commit native notification failures could strand stale OS notifications. Mitigation: FR-3 reconciliation-through-`scheduled_notifications` contract plus the kill-between-commit-and-call device test.
- Risk: hidden active-vehicle convenience creeping into APIs under MVP pressure. Mitigation: FR-5/AC-7 explicit-`vehicle_id` rule and API review.
- Risk: long transactions blocking the single connection. Mitigation: short transactions, no user-interaction or network inside a transaction, budget checks in `DOS-M04-010`.
- Decision: exact optimistic-concurrency mechanism (`updated_at` + version counter vs equivalent) — chosen here and documented in the API reference.
- Decision: which list functions need a user-DB-revision-tied cursor vs simple bounded lists — documented per function.
- Open question: the precise notification-rescheduling work-order shape consumed by M06's reminder reconciliation — defined here, versioned, and refined only through the M06 issues without breaking this contract.
