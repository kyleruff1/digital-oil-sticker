## Outcome

Mob starts two supervised `ecto_sqlite3` repos against secure app-specific files, each with one connection, and preserves committed data across backgrounding, app kill, device reboot, and low-space failures. Native storage paths, the boot coordinator/state machine, lifecycle handling, disk-space detection, containment-safe cleanup, file-protection/backup policy, and redacted health reporting are all implemented and proven on physical devices.

## Why this matters and what it unblocks

On-device SQLite durability depends on native paths, repo start order, journal/checkpoint behavior, and OS lifecycle. This ticket makes those runtime assumptions executable before migrations and bundled catalog upgrades rely on them. `DOS-M04-007` (boot migrations with backup/recovery) and `DOS-M04-008` (atomic catalog install) both build directly on the paths, state machine, space checks, and containment rules delivered here, and `DOS-M04-010` certifies the resulting durability envelope. Without this issue, every later persistence guarantee is untestable folklore.

## Included

- Implement a native storage-path module that obtains the iOS Application Support root and Android app-specific files root from Mob/platform APIs, creates `user`, `catalog`, `staging`, and `recovery` directories with least-permissive available protection, and refuses bundle/cache/temp paths.
- Configure `DigitalOilSticker.UserRepo` and `DigitalOilSticker.CatalogRepo` at runtime with explicit absolute database paths, `pool_size: 1`, finite busy timeout, foreign keys enabled, and measured SQLite pragmas. UserRepo may use WAL if physical-device testing proves checkpoint/recovery behavior; CatalogRepo is immutable/query-only and does not need WAL writes.
- Implement a boot coordinator and supervision strategy that never starts CatalogRepo before a valid active catalog path exists and never marks data services ready before UserRepo migrations finish. Repo restarts must reuse the resolved paths rather than create a database in the working directory.
- Handle Mob/iOS/Android lifecycle callbacks: checkpoint/flush on graceful background/termination when possible, but rely on transactions/journaling for ungraceful kill; reopen and run lightweight integrity/health checks after process restart.
- Detect available disk space via the supported native bridge where available and always handle SQLite/OS `disk full`, I/O, permission, busy, and read-only errors. Reserve measured headroom for the existing installed catalog, bundled candidate, decompressed candidate, user backup, and WAL growth during an app upgrade.
- Make catalog, user, staging, and recovery paths explicit typed values. Destructive cleanup accepts only a validated child path under the app-specific catalog/staging/recovery roots and can never target the user root by prefix/glob accident.
- Define file-protection/backup policy per platform: protect user DB while device is locked to the strongest level compatible with notification/background requirements; mark replaceable catalog/staging no-backup when supported; document whether UserRepo participates in OS device backup.
- Emit redacted health data: repo state, catalog/user schema versions, journal mode, last checkpoint, available-space class, last integrity result, and typed failure — never raw paths, user content, or SQL parameters.

## Excluded

- PWA, browser, OPFS, IndexedDB, SQLite WASM, service workers, tab locks, cloud storage, remote databases, network catalog downloads, and `pool_size > 1`.
- The migration engine and backup/restore protocol (`DOS-M04-007`), the catalog install/activation state machine content (`DOS-M04-008` — this issue provides the hooks/paths it uses), and export/import (`DOS-M04-009`).

## Functional requirements

- FR-1: `StoragePaths` (native storage-path module) resolves the iOS Application Support root and Android app-specific files root via Mob/platform APIs, creates `user`, `catalog`, `staging`, and `recovery` directories with least-permissive available protection, and rejects bundle/cache/temp locations with typed errors.
- FR-2: Runtime config asserts `adapter: Ecto.Adapters.SQLite3`, distinct absolute paths, and `pool_size: 1` for both repos, plus finite busy timeout, foreign keys enabled, and measured SQLite pragmas; the assertion runs in packaged apps, not only in tests.
- FR-3: `StoragePaths` returns `%{user_db:, catalog_root:, active_catalog:, staging_root:, recovery_root:}` only after containment/permissions checks.
- FR-4: The startup state machine is `resolve_paths → ensure_directories → inspect_bundle_and_installed_catalog → install_or_select_catalog → start_catalog_repo → start_user_repo → migrate_user_repo → health_check → ready`; CatalogRepo never starts before a valid active catalog path exists; data services are never ready before UserRepo migrations finish; repo restarts reuse resolved paths and can never create a database in the working directory.
- FR-5: A persisted recovery marker makes an interrupted catalog install/migration diagnosable at next boot.
- FR-6: Lifecycle callbacks checkpoint/flush on graceful background/termination when possible; ungraceful kill safety relies on transactions/journaling; process restart triggers reopen plus lightweight integrity/health checks.
- FR-7: WAL for UserRepo is enabled only if physical-device testing proves checkpoint/recovery behavior; CatalogRepo runs immutable/query-only without WAL writes; the journal-mode decision and measurements are recorded.
- FR-8: Disk-space detection uses the supported native bridge where available; SQLite/OS `disk full`, I/O, permission, busy, and read-only errors are always handled and mapped to the M04 typed errors, preserving low-level codes only in redacted diagnostics; `SQLITE_FULL`/ENOSPC is never retried in a loop; measured headroom is reserved for installed catalog + bundled candidate + decompressed candidate + user backup + WAL growth during an app upgrade.
- FR-9: Destructive cleanup APIs accept only a validated child path under the catalog/staging/recovery roots; the user root can never be targeted by prefix/glob accident; containment rejects `..`, symlinks/aliases escaping the root where applicable, empty paths, root paths, and the UserRepo path.
- FR-10: Per-platform file-protection/backup policy is implemented and documented: strongest user-DB protection compatible with notification/background requirements while locked; catalog/staging marked no-backup when supported; UserRepo OS-backup participation documented per the `DOS-M04-001` decision.
- FR-11: Health reporting exposes repo state, catalog/user schema versions, journal mode, last checkpoint, available-space class, last integrity result, and typed failure — never raw paths, user content, or SQL parameters.

## Technical implementation contract

### Components and ownership boundaries

- `StoragePaths`: sole authority for filesystem locations; all other modules receive typed path values and never construct database paths.
- `DigitalOilSticker.Boot` (boot coordinator): owns the startup state machine, readiness gating, recovery markers, and health probes; supervision strategy restarts repos with resolved paths.
- Platform bridge (Mob native APIs) supplies roots, disk-space queries, and file-protection attributes; accessed only through the typed storage module.
- `DOS-M04-007` (migration engine) and `DOS-M04-008` (installer) plug into named states of this state machine; they do not reimplement path or space logic.

### Data and persistence

- Two SQLite files at `StoragePaths.user_db` and `StoragePaths.active_catalog`, plus `catalog-pointer.json`, staging children, and recovery artifacts under their typed roots.
- Runtime pragmas: finite busy timeout, foreign keys ON for UserRepo, measured journal/synchronous settings per the FR-7 decision; CatalogRepo query-only.
- The recovery marker and health snapshot are small local files/rows under the recovery root and `UserRepo` respectively, containing no user content.

### Interfaces and events

- `StoragePaths` map contract per FR-3; boot state machine states per FR-4 observable for diagnostics; `:ready` gates LiveView data routes (from `DOS-M04-001`).
- Cleanup API: `delete_child(validated_root, child)` style contract that type-rejects anything outside catalog/staging/recovery roots.
- Health data per FR-11 exposed as a redacted struct for the future diagnostics/export surface.
- Error mapping per FR-8 into the M04 typed taxonomy with recoverability metadata.

### Failure and recovery behavior

- Kill during a UserRepo transaction: reopen yields `PRAGMA integrity_check = ok` with the transaction wholly present or absent; WAL/sidecar recovery is tested where enabled.
- Interrupted install/migration: next boot reads the recovery marker and routes to the owning recovery flow (`DOS-M04-007`/`DOS-M04-008`).
- Low space during user write, backup, catalog copy, or catalog decompression: prior database/catalog remains valid, typed `insufficient_space` is returned, no retry loops, no user-data deletion.
- Directory/permission failures at boot produce the recoverable boot-failure state from `DOS-M04-001`, never a crash loop.

### Security and privacy

- Least-permissive directory protection; user DB protected while the device is locked to the strongest class compatible with notification/background needs.
- No raw paths, user content, or SQL parameters in logs or health data; low-level error codes survive only in redacted diagnostics.
- Files live only in app-sandbox storage; nothing is written to the signed bundle or shared/world-readable locations; no network anywhere in this layer.
- Backup flags follow the durability-class policy so replaceable catalog/staging never inflate device backups.

### Accessibility and performance

- No UI. Boot-path budget target from the `DOS-M04-010` candidates: cold two-repo boot plus no-op migration p95 ≤1 s after an already-installed catalog (final value per the budgets ADR); health checks are lightweight; space checks and pragmas are measured, not guessed.

## UX and content states

N/A — native runtime issue with no screens. It supplies the readiness, recovery-marker, and `insufficient_space` states that the M05 boot/recovery UI will present, and the health struct a future diagnostics screen can render.

## Acceptance criteria

- [ ] AC-1: Runtime assertion proves two different files, two Ecto Repo processes, and `pool_size: 1` in packaged iOS and Android apps.
- [ ] AC-2: Files resolve beneath the approved iOS Application Support / Android app-specific files root and never beneath bundle, cache, temp, or current working directories.
- [ ] AC-3: Committed UserRepo rows and the active catalog survive graceful background/foreground, force-kill, five rapid kill/relaunch cycles, and physical-device reboot in airplane mode.
- [ ] AC-4: Kill during a UserRepo transaction reopens with `PRAGMA integrity_check = ok` and the transaction wholly present or absent; WAL/sidecar recovery is tested where enabled.
- [ ] AC-5: Forced low-space during user write, backup, catalog copy, and catalog decompression leaves the prior database/catalog valid, produces `insufficient_space`, and never loops or deletes user data.
- [ ] AC-6: App-data cleanup containment tests reject `..`, symlinks/aliases escaping the root where applicable, empty paths, root paths, and the UserRepo path.
- [ ] AC-7: The boot state machine enforces its stage order (no CatalogRepo before valid active path; no readiness before migrations); an interrupted stage leaves a recovery marker that next boot reads.

## Test plan

### Automated

- Repo config assertion tests (adapter, distinct absolute paths, `pool_size: 1`, busy timeout, foreign keys, pragmas).
- Native host-unit tests for path containment (`..`, symlink/alias escape, empty/root/UserRepo paths) and error mapping (SQLITE_FULL/ENOSPC, I/O, permission, busy, read-only → typed errors; no retry loop on full).
- Boot state-machine unit tests: stage ordering, restart-reuses-paths, recovery-marker write/read, readiness gating.
- Fault-injection tests simulating disk-full and I/O errors at each write site.
- Health-report redaction tests: output contains storage classes/versions/states and never raw paths, user content, or SQL parameters.

### Manual/device matrix

- Minimum-class physical iOS and Android devices, in airplane mode:
  - Resolved-path evidence (screenshots/logs with sensitive portions redacted) proving Application Support / app-specific files roots.
  - Graceful background/foreground, force-kill, five rapid kill/relaunch cycles, and full device reboot — committed rows and active catalog intact each time.
  - Kill injected mid-transaction; reopen; `PRAGMA integrity_check = ok`; transaction atomicity verified; WAL recovery where enabled.
  - Forced low-space runs for user write, backup, catalog copy, and decompression using device storage-filling; typed `insufficient_space`; post-recovery integrity hashes.
  - Journal-mode/WAL checkpoint measurement runs supporting the FR-7 decision.

## Rollout and rollback

Rollout: merge as the foundational runtime layer; `DOS-M04-007/008` build on its states immediately. Rollback: revert the runtime commits — no persistent schema is introduced beyond the recovery marker and health snapshot, both of which are safe to orphan (unknown markers are ignored-and-logged by design). Journal-mode changes after release require a tested transition plan (checkpoint-before-switch) recorded with the FR-7 measurements.

## Dependency rationale

Blocked by `DOS-M04-001` (path layout, durability classes, boot order, and error taxonomy are ratified there) and by the schemas `DOS-M04-002`/`DOS-M04-003` (real catalog/user database files are needed to prove open/migrate/integrity behavior rather than empty stubs). This issue blocks `DOS-M04-007` (boot migrations need the state machine, space checks, recovery root, and backup headroom), `DOS-M04-008` (the installer needs staging/catalog roots, containment-safe cleanup, disk-space reservation, and repo stop/start hooks), and `DOS-M04-010` (certification exercises exactly this durability envelope on devices).

## Risks, decisions, and open questions

- Risk: WAL checkpoint behavior on iOS/Android under kill/reboot may differ from desktop assumptions. Mitigation: FR-7 requires physical-device proof before enabling WAL; fallback is rollback journal mode with measured cost.
- Risk: native disk-space APIs may be unavailable or inaccurate on some devices. Mitigation: FR-8 requires handling the error responses regardless; space detection is an optimization, error handling is the guarantee.
- Risk: file-protection classes that are too strong could break future background notification needs. Mitigation: FR-10 explicitly selects the strongest level compatible with notification/background requirements and documents it.
- Decision: journal mode and pragma set per repo (measured, recorded).
- Decision: exact reserved headroom formula for upgrades (measured across installed catalog, bundled candidate, decompressed candidate, user backup, WAL growth).
- Open question: symlink/alias semantics differ per platform filesystem; containment tests cover "where applicable" per platform and record the per-platform behavior.
