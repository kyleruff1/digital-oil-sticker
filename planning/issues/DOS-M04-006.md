> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Split into server catalog boot at application start and client store open-and-hydrate on LiveView mount; the native durable-file placement requirement drops._

## Outcome

The two halves of what was formerly a co-located dual-repository boot are wired across the new browser-first boundary, and the seam between them is a contract, not a coincidence. On the **server**, `DigitalOilSticker.Application` starts a single supervision tree whose `CatalogRepo` opens the read-only catalog artifact baked into the Fly release image, verifies that the artifact matches the release's declared `data_version`, warms the read-through cache, and only then permits `DigitalOilStickerWeb.Endpoint` to accept traffic; there is no `UserRepo`, no personal-data code path anywhere in application start, no boot state machine outside the supervision tree, and no filesystem-path resolution module. On the **client**, every LiveView mount runs the `LocalStore` `phx-hook`, which opens the `dos_local` IndexedDB database through the schema-and-adapter contract owned by `DOS-M09-001`, runs any forward-only schema upgrade, and hydrates a versioned envelope into `socket.assigns` for the lifetime of that socket only, per the hydration protocol ratified in ADR-0004 and implemented by `DOS-M09-002`. A release-gating test proves the server holds no `UserRepo`, opens `CatalogRepo` read-only, and refuses traffic until the boot payload's SHA-256 has been recorded; a release-gating test proves that a LiveView mount without a working IndexedDB never presents itself as a durable garage. The pre-pivot durable-file placement contract, path-resolution module, boot state machine, and per-platform file-protection policy are retired for the MVP and preserved verbatim in the historical section below for the deferred re-entry track.

## Why this matters and what it unblocks

Under ADR-0004 and Constitution 2.0.0 the "boot" event that mattered to the pre-pivot spec — resolving filesystem paths, ordering two co-located repos, gating readiness on migrations, and handling ungraceful process kill — no longer exists as a single event on a single machine. It is now two events on two machines: a **server** boot that must not accidentally acquire personal state, and a **client** mount that must not accidentally present as durable. Both halves must be pinned down explicitly, because failing either one silently would break invariants the pivot exists to preserve. A server boot that lazily starts something that reads or writes `socket.assigns` values at process boundaries would create the very server-side personal record ADR-0004 and INV-3/INV-23 forbid. A LiveView mount that renders an onboarding-from-zero flow before the client store has answered would look, to a returning user, like data loss — which INV-24.3/INV-24.8 make a release-blocker in the plainest possible words.

This card is now the contract that names the pieces so the surrounding cards can point at it: `DOS-M09-006` (Fly deploy pipeline) operationalizes the server boot this card contractualizes; `DOS-M09-001` (browser storage schema and adapter contract) supplies the open/upgrade/read/write API this card's client half invokes; `DOS-M09-002` (LiveView hydration protocol) defines the wire shape this card gates readiness against; `DOS-M09-003` (pre-hydration, storage-denied, quota, and eviction UX) owns the copy for the resolved states this card enumerates; the re-scoped `DOS-M05-005` (single-vehicle dashboard) depends on this card's determinate pre-hydration state; the re-scoped `DOS-M04-010` (browser conformance certification) and `DOS-M09-009` (browser support matrix and storage-behavior conformance) exercise exactly these two boot halves across the supported browser matrix.

## Included

- Ratify the server-side boot contract as it currently exists: `DigitalOilSticker.Application` starts one supervisor with exactly `[Telemetry, CatalogRepo, Catalog.Metadata, Catalog.OilModel, Catalog.Cache, DNSCluster, PubSub, Endpoint]` (and nothing that opens a writeable personal store), and records the boot payload SHA-256 after `CatalogRepo` is up and before `Endpoint` takes traffic.
- Assert `CatalogRepo` is opened **read-only** at connection time (SQLite read-only open mode against the artifact baked into the Fly image), and that its `data_version` matches the release manifest's declared catalog version — refusing readiness on divergence.
- Provide the release-gating enforcement checks from ADR-0004 §"Enforcement" that fit this card's scope: (a) the deployed application's Ecto repo list is exactly `[CatalogRepo]`; (b) `CatalogRepo`'s connection is opened read-only; (c) no module under `DigitalOilSticker.{Catalog,Garage,Forecast}` references `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules (protecting ADR-0004 decision §6 mechanically).
- Ratify the client-side mount-and-hydrate contract as owned by `DOS-M09-001`/`DOS-M09-002`: on every LiveView mount, the `LocalStore` hook opens `dos_local` through the `DOS-M09-001` adapter contract, runs the forward-only `onupgradeneeded` upgrade, reads a versioned envelope, and `pushEvent`s `local_store:hydrate`; the server places the validated envelope in `assigns.local_state = :loaded | :empty | :data_missing | :storage_unavailable | :session_only` and never persists a personal row.
- Define the readiness gate at the seam: LiveView views that render personal data MUST NOT accept input before `local_state` has resolved out of `:hydrating`; interactive controls remain disabled or absent for the pre-hydration frame(s), per INV-24.3 and §9's "interactive controls MUST NOT accept input before hydration state is known".
- Define the failure-and-recovery behavior at the seam in browser-first terms: a socket disconnect (deploy, network blip, sleep/wake, tab restore) re-runs the hook on remount; pending unacknowledged writes visible in the pre-disconnect UI are re-driven from client storage on remount, since the client is the source of truth (ADR-0004 §"WebSocket and LiveView considerations", INV-7).
- Define the honest logging discipline for boot and mount: server boot logs may include release id, machine id, catalog `data_version`, and payload SHA-256; they MUST NOT include any hydration payload, `tab_id`, or personal record, and `debug_errors: false` in production so no assigns reach an error page (ADR-0004 §"Logging", INV-4).

## Functional requirements

- **FR-1 (retires pre-pivot FR-1/FR-2/FR-3/FR-7/FR-8/FR-9/FR-10 — filesystem-path module, per-platform pragmas, WAL, disk-space, containment cleanup, per-platform file-protection).** The server has no filesystem-path module, no writeable personal store, no WAL/journal-mode decision, no disk-space probe, no containment-safe cleanup API, and no per-platform file-protection policy in the MVP. These are retired under ADR-0004 §4 and PIVOT-2026-08-01 row DOS-M04-006 ("the native durable-file placement requirement drops"), and are preserved in the historical section below. A release-gating check asserts no module under `DigitalOilSticker.*` opens a writeable Ecto repo or references any retired path-resolution module.
- **FR-2 (replaces pre-pivot FR-2 — dual-repo runtime config).** `DigitalOilSticker.Application`'s supervisor children set contains exactly one Ecto repo, `DigitalOilSticker.CatalogRepo`, opened read-only against the catalog artifact baked into the Fly release image. A release-gating test asserts (a) `Ecto.Repo.all_running/0` (or equivalent enumeration) returns exactly `[DigitalOilSticker.CatalogRepo]` in the deployed release, and (b) that repo's connection was opened in read-only mode. There is no `UserRepo`, no `Ecto.Migrator` invocation, and no `pool_size > 1` requirement for a personal store because no personal store exists.
- **FR-3 (replaces pre-pivot FR-4 — startup state machine).** The startup ordering is expressed as a linear supervision tree, not a bespoke state machine: `Telemetry → CatalogRepo → Catalog.Metadata → Catalog.OilModel → Catalog.Cache → DNSCluster → PubSub → Endpoint`. `Endpoint` is the last supervised child so it never takes traffic before `CatalogRepo` and the read-through cache warmers have started. After the supervisor returns `{:ok, pid}`, `HealthController.record_boot_payload_sha256/0` records the artifact hash that the readiness endpoint reports.
- **FR-4 (replaces pre-pivot FR-5 — recovery marker).** There is no persisted recovery marker on the server because there is no interrupted-migration state to recover; the catalog is a build artifact atomically replaced by a deploy (ADR-0004 §"Catalog database on Fly"). An interrupted deploy is recovered by Fly's rolling-deploy semantics and covered by `DOS-M09-006`, not by application code in this card. Client-side, the equivalent property is guaranteed by `DOS-M09-002`'s compare-and-set on `meta.seq` and by the `dos_boot_state` hint owned by `DOS-M09-003`.
- **FR-5 (new — release/artifact binding).** Server boot verifies that the catalog artifact opened by `CatalogRepo` matches the release manifest's declared `data_version` and refuses to mark itself ready if they diverge. This closes the loop that the pre-pivot spec left to a filesystem-level file-protection scheme: a corrupted or wrong catalog file at boot must be detectable at boot rather than at first query, or the machine reports ready and starts serving inconsistent catalog answers.
- **FR-6 (replaces pre-pivot FR-6 — OS lifecycle callbacks).** There are no OS lifecycle callbacks at either end; the browser-first equivalents are: (a) an unexpected process exit on the server is recovered by Fly's restart policy plus supervision, with no personal state to lose; (b) an unexpected socket disconnect on the client is handled by LiveView's automatic reconnect, on which the `LocalStore` hook re-runs `mounted()` and re-hydrates from IndexedDB (INV-7, INV-24.3). Pending unacknowledged writes remain visible in the pre-disconnect UI and are re-driven from client storage on remount, because the client is the source of truth (ADR-0004 §"WebSocket and LiveView considerations").
- **FR-7 (new — client open-and-hydrate on mount, per DOS-M09-001/002).** Every LiveView mount runs the `LocalStore` `phx-hook`; the hook opens `dos_local` through the `DOS-M09-001` adapter contract, runs any `onupgradeneeded` forward-only upgrade, and reads a single `readonly` transaction into an envelope that is pushed to the server as `local_store:hydrate`. The server places the validated envelope in `assigns.local_state` and never writes it to disk, database, cache, ETS table, external store, or log (INV-3, INV-4, INV-23, INV-24.1).
- **FR-8 (new — pre-hydration readiness gate).** Views that render personal data set `assigns.local_state = :hydrating` on static render and MUST NOT render an empty-garage state, an onboarding-from-zero flow, or accept interactive input while `:hydrating` (INV-24.3). Hydration must resolve to `:loaded`, `:empty`, `:data_missing`, `:storage_unavailable`, or `:session_only` within the ADR-0004 default `hydration_deadline` (5,000 ms); expiry surfaces `:storage_unavailable` explicitly (INV-24.3, INV-24.6). The distinction between `:empty` and `:data_missing` is what turns an evicted store from silent data loss into an honest state (INV-25). The state semantics and copy are owned by `DOS-M09-003`; this card only guarantees the readiness gate is present and every resolution state is reachable.
- **FR-9 (new — no personal boot writes).** No code path invoked during server application start, `CatalogRepo` init, or the LiveView `mount/3` for any view writes a personal record to any server-side sink — including but not limited to disk, database, cache, ETS, external store, log line, error report, and crash trace (INV-3, INV-4). A release-gating test drives a scripted mount-plus-hydrate-plus-mutation-plus-export session with log capture and asserts no VIN, odometer value, service date, note text, or custom vehicle name appears in any captured log line.
- **FR-10 (new — hosted transport at the seam).** The socket carrying `local_store:hydrate`, `local_store:put`, `local_store:ack`, and `local_store:conflict` traffic is WSS-only in production, with `check_origin` restricted to the exact production hostnames, `Plug.SSL` enforcing HTTPS, and the session cookie signed/`secure`/`http_only`/`same_site: "Lax"` and carrying no personal data and no stable user identifier (INV-22, INV-26, ADR-0004 §"Security and privacy boundary"). This card owns the assertion that the seam is over hosted transport with these properties; the exact header set, CSP, and rate limits are owned by `DOS-M09-008`.
- **FR-11 (replaces pre-pivot FR-11 — health reporting).** Health reporting exposes: release id, machine id, catalog `data_version`, catalog artifact SHA-256, `CatalogRepo` up/down, cache warm/cold, and last integrity result — and MUST NOT include any hydration payload, `tab_id`, personal record, or raw stack trace of a `handle_event` invocation carrying such a payload. The readiness endpoint uses the SHA-256 recorded by `HealthController.record_boot_payload_sha256/0` after supervision start. Log filter and `debug_errors: false` are release-gating.

## Technical implementation contract

### Module and file layout

- `DigitalOilSticker.Application` (`app/lib/digital_oil_sticker/application.ex`): sole authority for server start-time ordering; owns the supervision tree, the read-only `CatalogRepo` connection, and the post-supervisor `HealthController.record_boot_payload_sha256/0` call.
- `DigitalOilSticker.CatalogRepo`: opens the catalog artifact baked into the Fly image in SQLite read-only mode; refuses writes at the connection level, not only in code review.
- `DigitalOilSticker.Catalog.Metadata`, `DigitalOilSticker.Catalog.OilModel`, `DigitalOilSticker.Catalog.Cache`: server-side supervised children that warm the read-through cache and validate the catalog is coherent enough to serve, before `Endpoint` accepts traffic.
- `DigitalOilStickerWeb.HealthController`: records the boot payload SHA-256 baseline and serves the readiness endpoint that `DOS-M09-006`'s Fly health check queries.
- `DigitalOilStickerWeb.LocalStoreHook` and its client-side `LocalStore` `phx-hook`: the browser-side owner of the mount-and-hydrate operation; specified and implemented in `DOS-M09-002`.
- `DigitalOilSticker.LocalStore.{Envelope, Caps, Validation, Migrations, Schema.V1, Quarantine}`: server-side envelope, cap enforcement, validation, forward-only migration, versioned schema, and quarantine-list modules, specified by `DOS-M09-002` and consumed at mount.
- `DigitalOilStickerWeb.LocalStore.Session`: the LiveView-side owner of `assigns.local_state`, hydration-deadline arming, and mutation round trip, specified by `DOS-M09-002`.
- `DigitalOilStickerWeb.CatalogEvents`: the read-only catalog query interface invoked with hydrated references; carries only impersonal selectors (INV-26).
- Domain contexts (`DigitalOilSticker.Catalog`, `.Garage`, `.Forecast`, resolver): remain client-agnostic (ADR-0004 §6); the static enforcement check that they do not reference `Phoenix.LiveView`, `Plug`, or `LocalStore` modules is part of this card's release gate.

### State machine — server supervision order and client mount handshake

- **Server (supervision tree):** `Telemetry → CatalogRepo (read-only open + data_version check) → Catalog.Metadata → Catalog.OilModel → Catalog.Cache (warm) → DNSCluster → PubSub → Endpoint (last)`. After the supervisor's `start_link` returns `{:ok, pid}`, `HealthController.record_boot_payload_sha256/0` runs; only then does the readiness endpoint report ready and Fly begin routing traffic.
- **Client (mount handshake):** static render at `assigns.local_state = :hydrating` → socket connect → `hydration_deadline` armed (default 5,000 ms per ADR-0004) → hook `mounted()` opens `dos_local` and pushes `local_store:hydrate` → server validates the envelope, coerces it into domain structs, and sets `local_state` to a resolved value → deadline expiry sets `:storage_unavailable` (per `DOS-M09-002` FR-3/FR-4/FR-5).

### Envelope contract at the seam

- Exactly one server-side database file: the read-only catalog SQLite artifact baked into the Fly image. No volume, no Postgres, no personal rows.
- Exactly one client-side database per browser origin: `dos_local` in IndexedDB, defined by `DOS-M09-001`.
- The seam between them is the hydration envelope defined in ADR-0004 §"Payload envelope" and specified in `DOS-M09-002` FR-2 (`envelope`, `schema_version`, `seq`, `tab_id`, `generated_at`, `data`). This card does not redefine the envelope; it guarantees the mount handshake consumes it and that no field of it is ever persisted server-side.

### Interfaces and events

- Server supervision-tree order per FR-3, observable to operators via `Supervisor.which_children/1` diagnostics.
- Readiness endpoint served by `DigitalOilStickerWeb.HealthController`, keyed on the boot payload SHA-256, consumed by the Fly health check in `DOS-M09-006`.
- Mount handshake events per FR-7/FR-8: `local_store:hydrate` (client→server), `local_store:put` and `local_store:conflict` (server↔client) — the full event set and semantics live in `DOS-M09-002`.
- Error mapping at the seam: `IndexedDB open failed`, `probe write failed`, `schema newer than server`, and `hydration deadline expired` are the four states this card requires be distinguishable at the boundary; their copy and screens are owned by `DOS-M09-003`.

### Error handling — failure and recovery behavior

- Server process exit: Fly's restart policy plus BEAM supervision brings the machine back; no personal state is lost because none exists on the server (a genuinely pleasant property of the pivot).
- Deploy: every WebSocket drops; clients auto-reconnect and re-run the mount handshake, which re-runs hydration; pending unacknowledged mutations are re-driven from client storage on remount (ADR-0004 §"WebSocket and LiveView considerations", INV-7).
- Corrupted or wrong catalog artifact at boot: `CatalogRepo` open or the `data_version` check fails, `HealthController` reports not-ready, Fly does not route traffic, and the old release remains reachable during a rolling deploy (owned end-to-end by `DOS-M09-006` — this card guarantees the boot-time signal exists and is release-gated).
- Client IndexedDB blocked, evicted, or in a private-browsing window: detected on mount by the `DOS-M09-001` probe, surfaced as `:storage_unavailable` or `:session_only`, and rendered by `DOS-M09-003`'s honest-degradation states (INV-24.6, INV-25).

### Security and privacy

- `CatalogRepo` opened read-only at the connection layer, not only in code review, so no code path can accidentally write to the catalog artifact (ADR-0004 §"Catalog database on Fly").
- No third-party error reporting on the server, because `socket.assigns` contains the user's garage during a live session and any crash reporter that serialized assigns would exfiltrate exactly the data ADR-0004 and INV-3/INV-23 exist to keep off servers (ADR-0004 §"No third-party anything"). Adding one requires an ADR plus a proven assigns-scrubbing layer.
- Hosted transport per FR-10; session cookie carries no personal data and no stable user identifier per INV-22 and ADR-0004 §"CSRF and session".
- The read-only catalog query interface (`DigitalOilStickerWeb.CatalogEvents`) carries only impersonal selectors (INV-26); it must not accept a VIN, an odometer reading, a note, a free-text field, a record identifier, or any stable client identifier as an input parameter — this card's static check on domain-module contents is the mechanical enforcement.
- Logs at boot and mount follow the ADR-0004 §"Logging" allowlist/prohibition; `handle_event` params are dropped by default with an explicit allowlist for non-personal events. `debug_errors: false` in production.

### Accessibility and performance

- Page load and interaction budgets (per CONSTITUTION §9 provisional): LCP p75 ≤ 2.5 s; TTI p75 ≤ 3.5 s with interactive controls NOT accepting input before hydration state is known (FR-8); LiveView WebSocket connect static-to-live p95 ≤ 1.0 s; automatic reconnect p95 ≤ 2.0 s, re-running hydration.
- Hydration completion target (per CONSTITUTION §9 provisional): hydration p95 ≤ 300 ms from IndexedDB read → `pushEvent` → assigns populated, measured after socket join; the readiness gate in FR-8 ensures no interactive control accepts input before this resolves.
- First-visit payload budget (CONSTITUTION §9 provisional): initial HTML + CSS + JS ≤ 250 KiB compressed; total first-visit transfer ≤ 500 KiB; zero third-party origins. The pre-hydration skeleton must fit within this and is owned by `DOS-M09-003`.

## UX and content states

This card owns no screens directly, but it owns the readiness gate that every screen inherits: no view rendering personal data may accept input before `local_state` resolves, and no view may render an onboarding-from-zero flow while `:hydrating` (INV-24.3). The five resolved states are enumerated here and their copy/screens/affordances are owned by `DOS-M09-003`:

- `:loaded` — hydration returned records; the view renders them.
- `:empty` — hydration succeeded and returned zero records **and** the `dos_boot_state` hint says "never"; this is a genuine first visit and onboarding is honest.
- `:data_missing` — hydration succeeded and returned zero records **but** the `dos_boot_state` hint says "has_data"; this browser previously held records that are now gone (evicted, cleared, or lost). The copy MUST distinguish this from `:empty` and MUST NOT present an empty-garage welcome (INV-24.4, INV-24.8, INV-25). "Stored in this browser" copy per INV-21 applies.
- `:storage_unavailable` — IndexedDB open failed or the hydration deadline expired without a `local_store:hydrate` event; no writes will persist. Copy MUST tell the user before they enter data (INV-24.6).
- `:session_only` — a private-browsing or otherwise ephemeral store was detected on mount; the app is functional for catalog browsing but nothing entered will survive closing the tab (INV-24.6).

`:hydrating` must always resolve within the deadline (FR-8); it is never a terminal state.

## Rollout and rollback

Rollout: the server half of this card is already implemented in `app/lib/digital_oil_sticker/application.ex` and shipped by every current deploy; the release-gating tests that make its properties enforceable land alongside `DOS-M09-006`'s pipeline. The client half lands with `DOS-M09-001`/`DOS-M09-002` and `DOS-M09-003`; this card ratifies the seam contract they satisfy. Browser storage is forward-only versioned (owned by `DOS-M09-001`), so a rollback of the server release never demands a downgrade of a browser database that has already been upgraded — the newer-than-server case is handled by `DOS-M09-002` FR-11's read-only mode.

Rollback: a Fly release rollback restores the prior image (with its prior catalog `data_version`) exactly, and clients auto-reconnect and re-hydrate from their unchanged IndexedDB — a genuinely nice property of the no-server-state design (ADR-0004 §"Secrets" note on rotation is the same property in a different guise). There is no persistent server state introduced by this card that a rollback would need to reason about. If a rollback returns to a `schema_version` older than what a browser's `dos_local` now carries, that browser enters read-only mode (`DOS-M09-002` FR-11) until the next forward release restores compatibility; no user data is lost.

## Risks, decisions, and open questions

- **Risk (from ADR-0004 R8 restated at this seam).** With one always-on machine, every deploy drops every WebSocket. The re-mount / re-hydration path in FR-6/AC-3 is not an edge case — it is the routine deploy experience. If the mount handshake or the client hydration is not truly idempotent, deploys become visible data-loss events. Mitigation: FR-7/FR-8 and AC-3/AC-7 make the round trip release-gating.
- **Risk (from ADR-0004 R1 restated at this seam).** A browser that has evicted `dos_local` returns zero records on hydration. Distinguishing this from a genuine first visit is what turns eviction from silent data loss into an honest `:data_missing` state (INV-24.4, INV-24.8, INV-25). This card requires the state be reachable and gated by AC-9; the distinguishing copy and its evidence live in `DOS-M09-003`.
- **Risk (release-manifest / artifact drift).** If a deploy image is built where the baked catalog artifact does not match the release manifest's `data_version`, FR-5's check must catch it at boot rather than at a first query. Otherwise the machine reports ready and starts serving inconsistent catalog answers. Mitigation: AC-4 makes the boot-time signal release-gating; the deploy-time signal is owned by `DOS-M09-006`.
- **Decision.** The server has no `UserRepo`, no `Ecto.Migrator`, and no personal-data code path anywhere in application start. This is not a temporary MVP simplification; it is the boot-time expression of the ADR-0004 §4 and Constitution INV-3/INV-23 decisions, and it is release-gated by AC-1/AC-2/AC-8.
- **Decision.** The client-side "recovery marker" concept from the pre-pivot spec is not needed at the server seam because the catalog is a build artifact and personal state is not on the server. The client-side equivalent (distinguishing an evicted store from a first visit) is `DOS-M09-003`'s `dos_boot_state` hint, not a marker owned here.
- **Open question.** The exact `hydration_deadline` value. ADR-0004 defaults it to 5,000 ms; CONSTITUTION §9 sets a provisional hydration-completion p95 of 300 ms. The shipped deadline value is recorded with its per-browser measurements by `DOS-M09-002` / `DOS-M09-009`; this card requires the deadline exists and expires to `:storage_unavailable`, not that it be a specific number.
- **Open question (out-of-scope for this rewrite).** All pre-pivot open questions about filesystem symlink/alias semantics, WAL checkpoint behavior under kill/reboot, and per-platform file-protection classes are intentionally out-of-scope for the MVP and park with the historical section below. They revive only if the deferred re-entry track revives per ADR-0004 §"Trigger conditions that revive the native track".

### Outcome (superseded)

### Technical implementation contract (superseded)

#### Components and ownership boundaries

- `StoragePaths`: sole authority for filesystem locations; all other modules receive typed path values and never construct database paths.
- `DigitalOilSticker.Boot` (boot coordinator): owns the startup state machine, readiness gating, recovery markers, and health probes; supervision strategy restarts repos with resolved paths.
- Platform bridge (Mob native APIs) supplies roots, disk-space queries, and file-protection attributes; accessed only through the typed storage module.
- `DOS-M04-007` (migration engine) and `DOS-M04-008` (installer) plug into named states of this state machine; they do not reimplement path or space logic.

#### Data and persistence

- Two SQLite files at `StoragePaths.user_db` and `StoragePaths.active_catalog`, plus `catalog-pointer.json`, staging children, and recovery artifacts under their typed roots.
- Runtime pragmas: finite busy timeout, foreign keys ON for UserRepo, measured journal/synchronous settings per the FR-7 decision; CatalogRepo query-only.
- The recovery marker and health snapshot are small local files/rows under the recovery root and `UserRepo` respectively, containing no user content.

#### Interfaces and events

- `StoragePaths` map contract per FR-3; boot state machine states per FR-4 observable for diagnostics; `:ready` gates LiveView data routes (from `DOS-M04-001`).
- Cleanup API: `delete_child(validated_root, child)` style contract that type-rejects anything outside catalog/staging/recovery roots.
- Health data per FR-11 exposed as a redacted struct for the future diagnostics/export surface.
- Error mapping per FR-8 into the M04 typed taxonomy with recoverability metadata.

#### Failure and recovery behavior

- Kill during a UserRepo transaction: reopen yields `PRAGMA integrity_check = ok` with the transaction wholly present or absent; WAL/sidecar recovery is tested where enabled.
- Interrupted install/migration: next boot reads the recovery marker and routes to the owning recovery flow (`DOS-M04-007`/`DOS-M04-008`).
- Low space during user write, backup, catalog copy, or catalog decompression: prior database/catalog remains valid, typed `insufficient_space` is returned, no retry loops, no user-data deletion.
- Directory/permission failures at boot produce the recoverable boot-failure state from `DOS-M04-001`, never a crash loop.

#### Security and privacy

- Least-permissive directory protection; user DB protected while the device is locked to the strongest class compatible with notification/background needs.
- No raw paths, user content, or SQL parameters in logs or health data; low-level error codes survive only in redacted diagnostics.
- Files live only in app-sandbox storage; nothing is written to the signed bundle or shared/world-readable locations; no network anywhere in this layer.
- Backup flags follow the durability-class policy so replaceable catalog/staging never inflate device backups.

#### Accessibility and performance

- No UI. Boot-path budget target from the `DOS-M04-010` candidates: cold two-repo boot plus no-op migration p95 ≤1 s after an already-installed catalog (final value per the budgets ADR); health checks are lightweight; space checks and pragmas are measured, not guessed.
