## Outcome

Every supported packaged app upgrades the durable UserRepo through bundled Ecto migrations before LiveView data access; a failed or killed migration preserves a verified recoverable copy and never resets local vehicles/history. The boot migration pipeline includes immutable released migrations with checksum enforcement, schema-range inspection, SQLite-safe backup, a recovery marker, postflight verification, and a recovery/export path.

## Why this matters and what it unblocks

User data may exist only on this device. App-store upgrades and abrupt mobile lifecycle events make boot migration safety a release blocker. Every future schema change to `UserRepo` (multi-vehicle UI, forecasting refinements, notification changes) ships through this pipeline, so its guarantees bound the risk of every subsequent release. It blocks the `DOS-M04-010` release QA gate, which certifies the migration matrix and kill-point behavior on physical devices.

## Included

- Store ordered Ecto migration modules in a UserRepo-specific bundled migrations path (for example `priv/user_repo/migrations`). Each has immutable timestamp/version, descriptive module name, explicit `up/down` or carefully reversible `change`, minimum app version, and a checked-in source checksum manifest used by CI to detect edits to released migrations.
- At boot, after UserRepo starts and before readiness, invoke `Ecto.Migrator` against `DigitalOilSticker.UserRepo` with `all: true` and an application-level single-run guard. CatalogRepo never runs these migrations and installed catalog files are never schema-migrated in place.
- Inspect Ecto's migration table and the application-supported schema range before running. A database newer than the app returns `incompatible_schema` — important after an app downgrade — and preserves bytes unchanged.
- Before migrations that could rewrite/copy material data, checkpoint UserRepo, estimate required free space, and create a verified backup under the recovery root using a tested SQLite-safe method (`VACUUM INTO`, SQLite backup API, or coordinated close/checkpoint/copy selected by spike). Copying only the main file while uncheckpointed WAL data exists is prohibited.
- Write a recovery marker containing old schema, target schema, backup checksum, app version, and phase. Run migrations, Ecto/schema validation, `foreign_key_check`, `integrity_check`, semantic counts/hashes, and a UserRepo smoke query; remove/retire backup only after the next successful reopen according to retention policy.
- On error or app kill, next boot detects the marker, validates both candidates, restores the last known-good backup when safe, or preserves both and opens a recovery/export UI. It never automatically deletes the only valid user copy and never retry-loops a deterministic failing migration.
- Create sanitized fixture databases for every released user schema with multi-vehicle histories, usage profiles, forecasts, reminder rules, scheduled notifications, unicode, archived graphs, null legacy fields, and boundary mileage/date values.

## Excluded

- Browser/tab migration logic; raw ad-hoc SQL at startup outside Ecto migrations/recovery checks; in-place catalog migrations; destructive reset fallback; silent schema downgrade; remote migration service.
- Authoring the schema content itself (`DOS-M04-003` and future schema issues); the export/import implementation the recovery UI links to (`DOS-M04-009`).

## Functional requirements

- FR-1: Ordered Ecto migration modules live in a UserRepo-specific bundled path (for example `priv/user_repo/migrations`), each with immutable timestamp/version, descriptive module name, explicit `up/down` or carefully reversible `change`, and minimum app version; a checked-in source checksum manifest lets CI fail on any edit to a released migration.
- FR-2: Boot invokes `Ecto.Migrator` against `DigitalOilSticker.UserRepo` with `all: true` after UserRepo starts and before readiness, under an application-level single-run guard; CatalogRepo never runs these migrations; installed catalog files are never schema-migrated in place.
- FR-3: Preflight inspects Ecto's migration table and the supported schema range; a database newer than the app yields `incompatible_schema` with bytes preserved unchanged (the app-downgrade case).
- FR-4: Before material-data migrations: checkpoint UserRepo, estimate required free space (via `DOS-M04-006` space checks), and create a verified backup under the recovery root using the spike-selected SQLite-safe method; copying only the main file while uncheckpointed WAL data exists is prohibited.
- FR-5: A recovery marker persists old schema, target schema, backup checksum, app version, and phase; the boot states are `inspect → acquire_guard → space_check → checkpoint → backup → migrate_with_ecto → verify → mark_success → reopen → ready`.
- FR-6: Postflight runs Ecto/schema validation, `foreign_key_check`, `integrity_check`, semantic counts/hashes, and a UserRepo smoke query; the backup is removed/retired only after the next successful reopen per retention policy.
- FR-7: On error or kill, the next boot detects the marker, validates both candidates (active DB and backup), restores the last known-good backup when safe, or preserves both and opens a recovery/export UI; it never automatically deletes the only valid user copy and never retry-loops a deterministic failing migration.
- FR-8: Sanitized fixture databases exist for every released user schema, containing multi-vehicle histories, usage profiles, forecasts, reminder rules, scheduled notifications, unicode, archived graphs, null legacy fields, and boundary mileage/date values.
- FR-9: Ecto's migration table is authoritative for applied versions; the source checksum manifest is a build/release immutability check, not a replacement migration engine.
- FR-10: Per-vehicle counts and canonical hashes for vehicles, events, readings, usage profiles, forecasts, reminder rules, scheduled notifications, snapshots, and settings reconcile before/after every migration run in the test matrix.

## Technical implementation contract

### Components and ownership boundaries

- Migration modules and the checksum manifest live in the app repository under the UserRepo-specific bundled path; CI owns manifest enforcement.
- The boot migrator component plugs into the `migrate_user_repo` stage of the `DOS-M04-006` state machine and owns the FR-5 sub-state machine, backup, marker, and postflight.
- The recovery/export UI entry point is owned by M05 screens and `DOS-M04-009`; this issue defines when it opens and what state it receives.

### Data and persistence

- Backups are written under the validated recovery root from `DOS-M04-006` with checksums recorded in the marker; retention policy keeps the backup until the next successful reopen.
- The marker is a small durable record (file under recovery root) containing phase/versions/checksums only — no user content.
- Applied-migration state lives in Ecto's migration table inside `user.sqlite3`; no shadow version store.
- Fixture databases are sanitized (synthetic data only) and stored with the test suite, one per released schema version.

### Interfaces and events

- Boot-state transitions per FR-5 are observable for diagnostics and surfaced through the `DOS-M04-006` health struct (schema versions, phase, last integrity result).
- Failure outcomes map to typed errors: `incompatible_schema`, `insufficient_space`, `corrupt`, `transaction_failed`, each with recoverability metadata; the recovery UI receives a typed reason, not a raw exception.
- The single-run guard is an application-level lock preventing a second migrator start (including a racing restart) until the first completes or is recovered.

### Failure and recovery behavior

- Kill at any boot phase leaves either the old valid UserRepo or the fully migrated one; relaunch recovers via the marker without data reset.
- Deterministic migration failures are not retry-looped: after validation, the app opens the recovery/export UI with both candidates preserved when safe restoration is not provable.
- Low-space preflight aborts before backup/migration mutate anything; injected `SQLITE_FULL` during migration preserves the known-good backup/active DB and yields export/recovery guidance.
- Postflight failure (integrity/foreign-key/semantic mismatch) is treated as migration failure: restore-or-preserve, never mark-success.

### Security and privacy

- Backups inherit the user-DB file-protection and backup-exclusion policy from `DOS-M04-006` (recovery artifacts are not eligible for OS backup unless the documented policy says otherwise).
- Marker, logs, and diagnostics contain schema versions, phases, and checksums — never vehicle data, VIN fragments, notes, or raw paths.
- Fixtures are sanitized/synthetic; no production user data ever enters the repository or CI.
- No network involvement at any phase (no remote migration service).

### Accessibility and performance

- No UI beyond triggering the recovery screen. Boot-time budget: the no-op migration path (nothing to apply) fits within the `DOS-M04-010` cold-boot candidate budget (p95 ≤1 s with installed catalog); material migrations get measured time/space envelopes recorded in the evidence rather than invented limits.

## UX and content states

The pipeline defines three user-visible situations for M05 to render: normal boot (no visible migration state or a brief progress state), blocked boot with `incompatible_schema` after an app downgrade (explain, preserve, direct to app update), and the recovery/export state (both candidates preserved; user can export via `DOS-M04-009` before any restore choice). No silent reset state exists by design.

## Acceptance criteria

- [ ] AC-1: Fresh install and every supported N→latest fixture path run through `Ecto.Migrator` and produce equivalent canonical schema/data.
- [ ] AC-2: LiveView data routes remain unavailable until migration and postflight complete; forced migration error opens recovery state without starting a second migrator.
- [ ] AC-3: App kill injected at every boot phase on physical iOS/Android leaves either the old valid UserRepo or the fully migrated one and recovers on relaunch without data reset.
- [ ] AC-4: Modified source for a released migration fails CI; a newer-than-supported on-device DB is preserved and reports `incompatible_schema`.
- [ ] AC-5: Low-space preflight and injected `SQLITE_FULL` preserve the known-good backup/active DB and provide export/recovery guidance.
- [ ] AC-6: Per-vehicle counts and canonical hashes for vehicles, events, readings, usage profiles, forecasts, reminder rules, scheduled notifications, snapshots, and settings reconcile before/after.
- [ ] AC-7: The backup method demonstrably captures WAL contents (no main-file-only copy while uncheckpointed WAL data exists), proven by a WAL-dirty backup/restore test where WAL is enabled.

## Test plan

### Automated

- Host migration matrix: fresh install plus every released-schema fixture → latest; canonical schema comparison and FR-10 count/hash reconciliation.
- Checksum-manifest CI test: mutate a released migration file → build fails.
- Downgrade test: fixture DB with newer schema than the app → `incompatible_schema`, bytes unchanged (hash-compared).
- Fault injection at each FR-5 phase (error and simulated kill): marker-driven recovery, single-migrator guard, no data reset.
- Low-space and `SQLITE_FULL` injection during backup and migration: known-good preservation and typed guidance.
- Backup-method tests: `VACUUM INTO`/backup-API/close-checkpoint-copy per the spike selection, including the WAL-dirty case; checksum verification of backups.

### Manual/device matrix

- Minimum-class physical iOS and Android devices: install previous released build with a populated fixture, upgrade to the new build, verify migration, counts/hashes, and readiness gating.
- Kill-point campaign on both devices: inject kill at every boot phase (inspect, acquire_guard, space_check, checkpoint, backup, migrate_with_ecto, verify, mark_success, reopen); relaunch and verify recovery each time.
- Device low-space run: fill storage, attempt upgrade, verify preservation and recovery/export guidance.
- One full recovery/export walkthrough: forced deterministic failure → recovery UI → export via `DOS-M04-009` → restore.

## Rollout and rollback

Rollout: this pipeline ships inside packaged app releases; every future schema release rides it. Rollback: an app-store downgrade is explicitly handled — the newer-schema DB is preserved with `incompatible_schema`, never migrated down automatically or reset; recovery is forward (reinstall newer app) or via export/restore. Released migrations are immutable; a bad migration is corrected by a new forward migration, and the backup/marker mechanism protects devices that already ran it.

## Dependency rationale

Blocked by `DOS-M04-003` (the migration set and schema fixtures it protects must exist first) and `DOS-M04-006` (boot state machine, recovery root, space checks, journal/WAL decision, and lifecycle handling are prerequisites for checkpointing, backup, and marker recovery). It blocks release QA `DOS-M04-010`, which certifies the migration matrix, kill-point behavior, and reconciliation hashes on physical devices as release evidence. `DOS-M04-009` pairs with it operationally: export is the user-facing escape hatch this pipeline's recovery UI opens.

## Risks, decisions, and open questions

- Risk: backup methods interact differently with WAL across platforms/versions. Mitigation: the spike-selected method plus the mandatory WAL-dirty backup test (AC-7); prohibition on main-file-only copies is absolute.
- Risk: kill-point coverage is combinatorially expensive on devices. Mitigation: exhaustive phase coverage is automated on host; every phase is still exercised at least once per platform on devices (AC-3).
- Risk: a "helpful" destructive reset creeping in as a support shortcut. Mitigation: excluded by design; recovery preserves both candidates and never deletes the only valid copy.
- Decision (by spike, recorded): the SQLite-safe backup method (`VACUUM INTO` vs backup API vs coordinated close/checkpoint/copy).
- Decision: backup retention policy details (retire after next successful reopen; exact retention count documented).
- Open question: whether large future migrations need a progress UI; the state machine exposes phases so M05 can add one without pipeline changes.
