> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Becomes an IndexedDB onupgradeneeded forward-only schema upgrade executed on connection open, with no rollback path and explicit quota/eviction/abort handling._

## Outcome

Every LiveView mount that opens the anonymous `dos_local` IndexedDB database runs any pending forward-only schema upgrade to completion **before** the hook reads a hydration snapshot, or fails closed with a typed, user-visible state that never destroys the user's data. The upgrade executes inside the browser's `onupgradeneeded` transaction, applies the ordered pure step functions defined by [DOS-M09-001](DOS-M09-001.md) in one all-or-nothing structural version bump, and has no rollback path: a step that raises aborts the upgrade transaction and the database remains at its prior structural version, byte-preserved, with the failure surfaced through the `LocalStore` hook of [DOS-M09-002](DOS-M09-002.md) and the pre-hydration state machine of [DOS-M09-003](DOS-M09-003.md). Quota exhaustion, storage eviction detected at open time, aborted transactions, and the newer-than-server (deploy-rollback) case are each handled by an explicit, testable code path that quarantines rather than deletes, offers export via [DOS-M04-009](DOS-M04-009.md) before any user-initiated repair, and never silently truncates or silently retries. There is no `Ecto.Migrator`, no `UserRepo`, and no server-side migration state — Application.start opens exactly one Ecto repo (`CatalogRepo`, read-only) per ADR-0004 §4 and its enforcement clause, so the upgrade lifecycle owned here runs entirely in the browser tab.

## Why this matters and what it unblocks

Under ADR-0004, the browser is the only home for personal data (INV-23) and IndexedDB is the only place that data lives durably. IndexedDB gives the app one upgrade opportunity per structural version bump, and that opportunity has no undo: once `onupgradeneeded` completes, the database cannot be reopened at the earlier structural version, and a bad upgrade is shipped to every visitor of the deployed page with no deploy rollback able to recall it. The design of the steps lives in M09-001; the design of the hook and hydration protocol lives in M09-002; the copy for the states this lifecycle can produce lives in M09-003; the write-back path that repair produces lives in [DOS-M04-005](DOS-M04-005.md); the export the recovery path emits lives in [DOS-M04-009](DOS-M04-009.md); and the quarantine record the failure surfaces through is already implemented at `app/lib/digital_oil_sticker/local_store/quarantine.ex`. This card owns the **runtime execution and lifecycle** that ties those pieces together at connection-open time: it is the point at which quota, eviction, and abort become concrete errors rather than design footnotes, and the point at which the difference between "safe forward step" and "silent data loss" is decided.

Closing this issue unblocks the M05 write paths and feeds [DOS-M04-010](DOS-M04-010.md), which certifies the browser/engine matrix as release evidence. It also completes the M04 persistence lifecycle triangle alongside the re-scoped [DOS-M04-006](DOS-M04-006.md) (open/hydrate on mount) and [DOS-M04-005](DOS-M04-005.md) (transactional adapter), so that every store the M05 UI reads or writes has been opened, upgraded, integrity-checked, and made writable through one accountable pipeline.

## Included

- Execute the ordered forward-only upgrade steps defined by [DOS-M09-001](DOS-M09-001.md) inside a single IndexedDB `onupgradeneeded` transaction, in strict logical-version sequence, with no step skipped and no step's completion depending on a later step.
- Detect at open time whether the on-disk logical schema version is behind, equal to, or ahead of the deployed server's version, and route to (a) run-the-upgrade, (b) proceed-to-hydrate, or (c) newer-than-server read-only mode respectively.
- Guarantee all-or-nothing structural bumps: if any step raises, the upgrade transaction aborts, the structural version does not advance, and the database remains byte-preserved at the prior version. No partial upgrade is ever committed and no "clean up" pass runs against a half-upgraded store.
- Handle `QuotaExceededError` raised during an upgrade transaction as an abort, not a truncation: the prior state is preserved, the user is presented with the honest quota-exhaustion state defined by [DOS-M09-003](DOS-M09-003.md), and export is offered via [DOS-M04-009](DOS-M04-009.md) before any user-initiated recovery.
- Handle storage eviction detected at open time — an origin database that was populated on a prior visit and is now empty or reset — as the storage-loss state defined by INV-25 and rendered by [DOS-M09-003](DOS-M09-003.md), not as a fresh install and not as a silent successful upgrade.
- Handle blocked or ephemeral storage (private browsing, hardened privacy settings, embedded webviews) at open time by refusing to advertise the store as durable, plugging into the session-only fallback ladder defined by ADR-0004 §"Private browsing and blocked storage", and never running an upgrade against a store that will not survive the session.
- Handle the newer-than-server case by opening the database at its existing structural version, entering read-only mode, disabling mutations, rendering the ADR-0004 §"Schema versioning and migration" banner, and offering export — never downgrading, never dropping unknown fields, and never writing.
- Run the read-time integrity pass from [DOS-M09-001](DOS-M09-001.md) FR-11 immediately after a successful upgrade completes, so that any record whose shape the upgrade could not fully normalise is quarantined (via the already-implemented `LocalStore.Quarantine` struct) rather than silently repaired.
- Offer the user-initiated repair path from [DOS-M09-001](DOS-M09-001.md) FR-13 only after an export of the raw pre-repair payload has been produced, and never as an automatic post-upgrade step.
- Emit only bounded, non-personal telemetry through the LiveView event surface: the from-version, to-version, structural version, outcome (`ok`/`abort`/`quota`/`newer_than_server`/`blocked`), and elapsed time; never a record, a store contents, a `tab_id`, or a fragment of a payload.
- Provide a deterministic single-run guard per tab so that a racing reconnect or a duplicate hook mount cannot start a second upgrade against the same database at the same time.
- Provide recorded fixtures — one per released logical version's upgrade path — and a fault-injection harness that raises inside each step, raises `QuotaExceededError` at each step boundary, and terminates the tab mid-upgrade, so that every abort path is exercised by CI.

## Functional requirements

**Note on retired FRs.** Pre-pivot FR-1 through FR-10 presupposed a server-side `UserRepo` and `Ecto.Migrator`; under ADR-0004 §"Decision" 4 and its enforcement clause, none of these can exist on the server. All ten are retired (preserved verbatim in the historical section). The new FRs below re-anchor the lifecycle in the browser and address sweep finding #1.

- **FR-1 (addresses sweep finding #1):** The upgrade lifecycle runs entirely in the browser tab, executed inside the IndexedDB `onupgradeneeded` transaction against the origin-scoped `dos_local` database. There is no server-side `Ecto.Migrator` invocation, no `DigitalOilSticker.UserRepo`, and no `priv/user_repo/migrations` path in the deployment; this is enforced mechanically by the ADR-0004 §"Enforcement" repo-list test, which this card cites as the structural proof that a server-side migrator cannot exist.
- **FR-2:** The upgrade lifecycle executes the ordered pure step functions specified by [DOS-M09-001](DOS-M09-001.md) FR-7 in strict logical-version sequence, from the on-disk logical version to the deployed server's logical version, with no step skipped and no step re-run inside the same upgrade transaction. Which steps exist and what they compute is not decided here.
- **FR-3:** Every structural version bump is all-or-nothing: if any step raises inside `onupgradeneeded`, the upgrade transaction aborts, the structural database version does not advance, no object store is deleted, no record is deleted, and the database remains byte-preserved at its prior structural version. There is no rollback path because none is needed — the browser's transaction abort *is* the "no change" outcome (per [DOS-M09-001](DOS-M09-001.md) FR-8).
- **FR-4:** On open, the on-disk logical schema version is compared against the deployed server's version. The three routes — **behind** (run the upgrade), **equal** (proceed directly to hydration), and **ahead** (newer-than-server read-only mode) — are the only possible outcomes; a fourth "run partial upgrade" or "downgrade" route does not exist and cannot be introduced.
- **FR-5:** The newer-than-server route opens the database at its existing structural version, disables mutations for the session, renders the ADR-0004 §"Schema versioning and migration" banner via [DOS-M09-003](DOS-M09-003.md), and offers export via [DOS-M04-009](DOS-M04-009.md). It never downgrades the payload, never drops unknown fields, and never writes at the older logical version.
- **FR-6:** A `QuotaExceededError` raised at any point inside the upgrade transaction is handled as an abort per FR-3: the prior state is preserved byte-for-byte, no records are dropped to "make room", the failure is surfaced as the quota-exhaustion state, and export is offered. This is the open-time equivalent of INV-24.5's mutation-time rule.
- **FR-7:** Eviction detected at open time — an origin database whose `meta` singleton indicates a prior populated state but whose stores now return empty on a `readonly` probe — is routed to the storage-loss state defined by INV-24.4 and INV-25, rendered by [DOS-M09-003](DOS-M09-003.md), and paired with an import offer via [DOS-M04-009](DOS-M04-009.md). It is never routed as "empty first install" and never as "successful upgrade".
- **FR-8:** Blocked or ephemeral storage detected at open time — `indexedDB.open()` throws, the probe write+read+delete round trip fails, or the environment self-reports as ephemeral — plugs into the ADR-0004 §"Private browsing and blocked storage" fallback ladder: no upgrade is attempted, no state is advertised as durable, and the session-only banner from [DOS-M09-003](DOS-M09-003.md) is rendered before the user is invited to enter data.
- **FR-9:** A single-run guard prevents a second `onupgradeneeded` from starting against the same database in the same tab while a first is in flight (a racing reconnect, a duplicate hook mount, or a rapid unmount/remount sequence). The guard is per-tab; multi-tab safety is the concern of [DOS-M09-002](DOS-M09-002.md)'s `BroadcastChannel` and compare-and-set on `meta.seq`, not this card.
- **FR-10:** After a successful upgrade transaction commits, the read-time integrity pass from [DOS-M09-001](DOS-M09-001.md) FR-11 runs before the hook emits `local_store:hydrate`. Any record that fails an integrity rule is added to the quarantine list represented by the already-implemented `DigitalOilSticker.LocalStore.Quarantine` struct — carrying only store, id, and rule, never record content (per that module's `@derive Inspect only:` and its module docstring, protecting INV-4).
- **FR-11:** The user-initiated repair path from [DOS-M09-001](DOS-M09-001.md) FR-13 is only reachable *after* an export of the raw pre-repair payload has been produced via [DOS-M04-009](DOS-M04-009.md); it is never invoked automatically at the end of an upgrade, and it never runs against a database in newer-than-server read-only mode.
- **FR-12:** The upgrade lifecycle emits bounded, non-personal telemetry to the LiveView through the [DOS-M09-002](DOS-M09-002.md) event surface: `from_logical_version`, `to_logical_version`, `structural_version`, `outcome` (one of `ok`, `abort`, `quota`, `newer_than_server`, `blocked`, `evicted`), and `elapsed_ms`. It emits no record contents, no store contents, no `tab_id`, no VIN, no odometer value, no note text, and no fragment of any payload; this is enforced by the ADR-0004 §"Enforcement" scripted-session log-scanning test, which this card extends with upgrade-lifecycle fixtures.
- **FR-13:** Retry policy is explicit: a deterministic upgrade failure (the same step raises on every attempt) is **not** retry-looped; the user is offered export, and repair is the only forward path. A transient failure (quota surfaced by a store now cleared, or an open attempt that briefly loses focus mid-flight) may be retried at most once per tab load, with the attempt recorded in telemetry per FR-12.
- **FR-14:** Recorded fixtures cover every released logical version's upgrade path from every earlier released version, plus the newer-than-server case with a version one higher than the deployed server's, plus a corrupt-record fixture matching each integrity rule from [DOS-M09-001](DOS-M09-001.md) FR-11. Each fixture is exercised by the fault-injection harness in FR-15.
- **FR-15:** A fault-injection harness in CI raises inside each upgrade step, raises `QuotaExceededError` at each step boundary, and terminates the tab mid-upgrade (via a fake IndexedDB or a real one in a controlled environment), and asserts for each fault that the database ends at the prior structural version, no record was deleted, no personal value was logged, and the surfaced state matches one of the outcomes enumerated in FR-12.

## Technical implementation contract

### Components and ownership boundaries

- The upgrade lifecycle is a JavaScript module colocated with the `LocalStore` hook, called by that hook before it emits its first `local_store:hydrate`. It owns the open-time decision tree (behind/equal/ahead), the single-run guard, the fault surface, and the integrity-pass invocation.
- Upgrade **steps** are consumed from the module [DOS-M09-001](DOS-M09-001.md) defines; this card does not add or edit steps.
- The **hook and hydration protocol** are owned by [DOS-M09-002](DOS-M09-002.md); this card runs before that protocol begins and hands off through the same event surface on completion or failure.
- The **rendered screens** for every state this card can enter are owned by [DOS-M09-003](DOS-M09-003.md).
- The **quarantine record shape** is `DigitalOilSticker.LocalStore.Quarantine` at `app/lib/digital_oil_sticker/local_store/quarantine.ex`; this card produces quarantine entries but does not modify the module.
- The **export file** produced in every failure path is owned by [DOS-M04-009](DOS-M04-009.md).
- CI ownership: the fault-injection harness and its fixtures ship with this card; the browser/engine matrix that runs it is owned by [DOS-M04-010](DOS-M04-010.md).

### Data and persistence

- Applied-version state lives in two places, both on the client: (a) IndexedDB's own structural version, exposed by the browser and not writable by application code except through `onupgradeneeded`; (b) the logical `schema_version` recorded in the `meta` singleton of [DOS-M09-001](DOS-M09-001.md). There is no shadow version store, no server-side migration table, no on-disk marker file, and no recovery-root artifact.
- The upgrade transaction is the browser's `onupgradeneeded` transaction; no separate application-level transaction wraps it, and no application-authored "backup copy" of any store is created before it runs (per FR-3, the transaction abort *is* the "no change" outcome, and IndexedDB gives no primitive for copying an object store's contents inside the same upgrade transaction anyway).
- The server keeps no upgrade state whatsoever. The ADR-0004 §"Enforcement" repo-list test proves this mechanically.

### Interfaces and events

- Inputs: the on-disk structural version (from `indexedDB.open()`), the on-disk logical version (from `meta.schema_version` after a `readonly` probe), the deployed server's current logical version (from a server-rendered assign on the shell), and the ordered step registry from [DOS-M09-001](DOS-M09-001.md).
- Outputs: one of the six outcomes enumerated in FR-12, delivered to the LiveView through the [DOS-M09-002](DOS-M09-002.md) event surface (`local_store:upgrade_ok`, `local_store:upgrade_abort`, `local_store:upgrade_quota`, `local_store:upgrade_newer_than_server`, `local_store:upgrade_blocked`, `local_store:upgrade_evicted`), each carrying only the FR-12 fields.
- The typed outcomes are the only handoff to the LiveView — no raw exception, no stack trace, and no envelope fragment crosses that boundary.

### Failure and recovery behavior

- **Deterministic step failure:** the upgrade transaction aborts by the browser's guarantee (FR-3), the outcome is `abort`, the user is offered export and, only then, repair (FR-11).
- **Quota exhaustion mid-transaction:** the outcome is `quota`, prior state preserved, export offered (FR-6). Data is never silently dropped to fit.
- **Tab kill mid-transaction:** the browser aborts the transaction and the next open reruns the upgrade attempt fresh; FR-9's single-run guard protects against a racing remount within one tab.
- **Newer-than-server:** read-only mode (FR-5); no write, no downgrade, no field drop, ever.
- **Eviction detected at open:** storage-loss state (FR-7), import offered.
- **Blocked/ephemeral storage:** session-only banner (FR-8), no upgrade attempt.
- **Integrity failure after upgrade:** quarantine (FR-10), export before any repair (FR-11).
- The lifecycle never silently succeeds, never silently retries a deterministic failure, and never automatically deletes a record or a store to reach a successful state.

### Security and privacy

- All personal data stays in the browser (INV-23); this card never sends a record, a store contents, a `tab_id`, or a payload fragment to the server. FR-12 enumerates the entire allowed telemetry surface; ADR-0004 §"Enforcement" scripted-session log-scanning is the mechanical check.
- The server holds no upgrade state, no per-user migration cursor, and no personal row (INV-3, ADR-0004 §"Decision" 4 + Enforcement).
- Exports produced by failure paths flow through [DOS-M04-009](DOS-M04-009.md), which itself operates entirely in the browser and does not round-trip through the server (ADR-0004 §"Export and import").
- Error reporting: `debug_errors: false` in production is inherited from ADR-0004 §"Logging"; upgrade-abort exceptions never reach a user-visible error page carrying assigns, because the upgrade runs on the client and the server never receives the exception at all — only the typed outcome from FR-12.

### Accessibility and performance

- No UI is owned by this card. The rendered screens are [DOS-M09-003](DOS-M09-003.md)'s responsibility and inherit the WCAG 2.2 AA browser-AT bar from [DOS-M07-002](DOS-M07-002.md) as re-scoped.
- Open-time upgrade of a fixture at the Constitution §9 storage budget (≤ 1 MiB per 1,000 text-only records, ≤ 5 MiB working ceiling) completes within a measured provisional envelope recorded in evidence; ADR-0004's note (in §"Consequences" → "Lost — honestly") that Constitution §9 latency budgets are void until re-ratified applies, and this card measures rather than asserts.
- The upgrade lifecycle must not block first paint: the shell renders at `assigns.local_state == :hydrating` (per [DOS-M09-002](DOS-M09-002.md)) before this lifecycle begins, so a slow upgrade shows a skeleton, not a frozen page.

## UX and content states

The upgrade lifecycle defines these state names for [DOS-M09-003](DOS-M09-003.md) to render:

- **`upgrading`** — an `onupgradeneeded` transaction is in flight; shown as a brief progress affordance layered under the shell skeleton, never as a full-screen block.
- **`upgrade_aborted`** — a deterministic step failed; export offered, repair reachable only after export.
- **`upgrade_quota`** — `QuotaExceededError` raised inside the transaction; honest quota-exhaustion copy per INV-24.5; export offered.
- **`newer_than_server`** — a stale deployment case; read-only banner per ADR-0004 §"Schema versioning and migration"; export offered; no mutation controls.
- **`storage_evicted`** — a prior populated store is now empty; the honest INV-25 loss message; import offered.
- **`storage_blocked`** — private browsing or blocked storage; the session-only banner is displayed *before* the user enters data.

No silent-success state exists.

## Rollout and rollback

- **Rollout.** The upgrade lifecycle ships inside the Fly.io release image; every deploy that bumps the logical schema version relies on this lifecycle to reach the new version on the next mount. Because IndexedDB upgrades are per-origin-per-tab, rollout is *not* a coordinated event — every visitor upgrades independently on their next mount.
- **Rollback of a deployed schema.** A deploy rollback that reduces the server's logical version cannot recall an upgrade already run in a user's browser. Users whose browser is now ahead of the server are handled by FR-5's newer-than-server read-only mode, not by an attempted downgrade. This is a deliberate consequence of ADR-0004 §"Schema versioning and migration"; correcting a broken schema is done by a forward step, not by rollback, and this card's fault-injection harness is the primary CI evidence that broken forward steps abort cleanly rather than corrupt.
- **Rollback of this card's own code.** Reverting the upgrade-lifecycle module reverts to the prior lifecycle; it does not touch data. IndexedDB structural versions do not decrement.

## Risks, decisions, and open questions

- **Risk R1:** IndexedDB `onupgradeneeded` abort behavior varies subtly across engines (whether an aborted transaction leaves partial index rebuilds visible on the next open; whether `QuotaExceededError` is raised synchronously or as a transaction event). *Mitigation:* the browser-matrix fault suite from AC-3 is manual-at-least-once per engine; the fake used in unit tests is validated against real engines during the [DOS-M04-010](DOS-M04-010.md) matrix run.
- **Risk R2:** A `QuotaExceededError` on the very first open in a fresh browser is indistinguishable from a hostile constrained environment; treating it as `storage_blocked` versus `upgrade_quota` matters for copy. *Decision:* if the database has never been populated (no `meta` singleton on any store), route to `storage_blocked`; otherwise route to `upgrade_quota`. Recorded here so it does not become a hidden branch.
- **Risk R3:** A schema author ships an upgrade step that always succeeds locally on the fixture but always aborts on real data (a real-world data shape not represented in the fixture). *Mitigation:* the stress fixture in the Included section of [DOS-M09-001](DOS-M09-001.md) (whose measured §9-budget demonstration is bound by that card's FR-18) is required to include a real-shaped corpus; this card's fault suite runs against it.
- **Risk R4:** A user in `newer_than_server` mode is trapped until either they visit the newer deployment again or they export and import into an older browser. *Accepted:* this is the honest outcome of ADR-0004 §"Schema versioning and migration"; the alternative (downgrade the payload) breaks INV-5 by silently discarding fields.
- **Open question:** whether a very slow upgrade (large fixture, slow device) warrants its own progress affordance separate from the shell skeleton. *Deferred to [DOS-M09-003](DOS-M09-003.md);* the FR-12 event surface already exposes `elapsed_ms` and `outcome` so a UI addition would need no lifecycle change.
- **Open question:** whether the fault-injection harness should also exercise a **partial fill** case — the tab is closed cleanly between two hydrations and the store is somehow observed at an intermediate structural version. *Investigated in the M09-001 fixture set;* if such a state proves possible under any engine's aborted-transaction semantics, this card's fault suite grows a case for it and the guarantee in FR-3 is re-verified rather than restated.
- **Decision (recorded):** there is no "backup copy of the store before upgrade" step. IndexedDB does not expose a primitive for this inside the upgrade transaction, and inventing one outside it would silently double the storage footprint against the §9 budget and race with quota-exhaustion behavior. The browser's transaction abort is the "no change" outcome, and FR-3 is written to that fact.

### Outcome (pre-pivot)

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

- Migration modules and the checksum manifest live in the app repository under the UserRepo-specific bundled path; CI owns manifest enforcement.
- The boot migrator component plugs into the `migrate_user_repo` stage of the `DOS-M04-006` state machine and owns the FR-5 sub-state machine, backup, marker, and postflight.
- The recovery/export UI entry point is owned by M05 screens and `DOS-M04-009`; this issue defines when it opens and what state it receives.

#### Data and persistence

- Backups are written under the validated recovery root from `DOS-M04-006` with checksums recorded in the marker; retention policy keeps the backup until the next successful reopen.
- The marker is a small durable record (file under recovery root) containing phase/versions/checksums only — no user content.
- Applied-migration state lives in Ecto's migration table inside `user.sqlite3`; no shadow version store.
- Fixture databases are sanitized (synthetic data only) and stored with the test suite, one per released schema version.

#### Interfaces and events

- Boot-state transitions per FR-5 are observable for diagnostics and surfaced through the `DOS-M04-006` health struct (schema versions, phase, last integrity result).
- Failure outcomes map to typed errors: `incompatible_schema`, `insufficient_space`, `corrupt`, `transaction_failed`, each with recoverability metadata; the recovery UI receives a typed reason, not a raw exception.
- The single-run guard is an application-level lock preventing a second migrator start (including a racing restart) until the first completes or is recovered.

#### Failure and recovery behavior

- Kill at any boot phase leaves either the old valid UserRepo or the fully migrated one; relaunch recovers via the marker without data reset.
- Deterministic migration failures are not retry-looped: after validation, the app opens the recovery/export UI with both candidates preserved when safe restoration is not provable.
- Low-space preflight aborts before backup/migration mutate anything; injected `SQLITE_FULL` during migration preserves the known-good backup/active DB and yields export/recovery guidance.
- Postflight failure (integrity/foreign-key/semantic mismatch) is treated as migration failure: restore-or-preserve, never mark-success.

#### Security and privacy

- Backups inherit the user-DB file-protection and backup-exclusion policy from `DOS-M04-006` (recovery artifacts are not eligible for OS backup unless the documented policy says otherwise).
- Marker, logs, and diagnostics contain schema versions, phases, and checksums — never vehicle data, VIN fragments, notes, or raw paths.
- Fixtures are sanitized/synthetic; no production user data ever enters the repository or CI.
- No network involvement at any phase (no remote migration service).

#### Accessibility and performance

- No UI beyond triggering the recovery screen. Boot-time budget: the no-op migration path (nothing to apply) fits within the `DOS-M04-010` cold-boot candidate budget (p95 ≤1 s with installed catalog); material migrations get measured time/space envelopes recorded in the evidence rather than invented limits.
