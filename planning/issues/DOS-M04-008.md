> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Becomes atomic activation of a new catalog version within a Fly release (no half-swapped reads, version pinning, rollback); the bundle-copy mechanics park with the native re-entry set._

## Outcome

The M04 persistence boundary owns a single guarantee for catalog activation in the hosted browser MVP: a Fly release either serves the new image's read-only catalog end-to-end or it does not enter rotation at all, and no LiveView query, no `Catalog` context call, and no `DOS-M09-004` query-layer result ever observes a half-swapped, mismatched, or partially opened catalog. This card defines the boot contract `CatalogRepo` and the `DigitalOilSticker.Catalog` context obey inside a starting machine — hash-verified pinning to the manifest, read-only open with `PRAGMA query_only = ON`, `data_version` and `schema_version` window enforcement, a strict "not-ready" typed error before readiness passes, and a rollback semantics in which redeploying the previous image digest restores the previous catalog byte-for-byte — and it defines the assertions the `DOS-M09-005` deploy pipeline must pass (in particular its FR-13 "a deploy never serves a half-swapped catalog") for this boundary to hold. First-launch bundle copy, on-device staging, catalog-pointer.json, and the bundle-copy state machine are **not** part of the browser MVP: the image is the only place the artifact lives (ADR-0004 "Catalog database on Fly"), and the historical mechanics park with the native re-entry set.

## Why this matters and what it unblocks

Under ADR-0004 the catalog is a build artifact baked into the deploy image with no runtime writer, no volume, and no managed database. "Catalog replacement is a deploy. Atomic by construction; new image up, old image down. Rollback: redeploy the previous image. The old catalog comes back exactly." That single design collapses the pre-pivot install/upgrade/rollback state machine to a set of readiness and repo-open invariants — but only if something owns those invariants at the M04 boundary. Without this card there is no place where `CatalogRepo`'s read-only open, its `data_version` pin, its response to a manifest-hash mismatch, or its `not_ready` typed error before readiness is defined and tested; those properties would live only in whatever code the deploy pipeline happens to write.

It unblocks the re-scoped `DOS-M04-004` (deterministic read-only `CatalogRepo`) by pinning the open contract it exposes; it feeds `DOS-M09-004` (server-side catalog query layer) the typed `not_ready` and `unsupported_data_version` errors its resolvers surface as INV-11 states; it hands `DOS-M09-005` FR-13 a concrete set of properties to gate readiness on; it clears the pivot's `DOS-M04-000` epic re-scope by resolving the "atomic catalog activation" line item; and it lets the re-scoped `DOS-M04-010` conformance work assert half-swap freedom as a testable release property instead of an aspiration.

## Included

- The read-only open contract for `CatalogRepo` in the deployed image: fixed in-image path, `mode=ro` connection, `PRAGMA query_only = ON`, `journal_mode` and `synchronous` set to the read-only-safe values, `pool_size` sized to the machine's shared-CPU concurrency, and a hard refusal to open if the file is missing or its byte length does not match the manifest's declared size.
- Manifest pinning at boot: read the in-image `catalog-manifest.json`, hash the catalog payload, compare against the manifest hash, refuse to expose the repo on any mismatch, and record the pin (hash, `data_version`, `schema_version`, `min_app_version`) in application env so `DOS-M09-005` readiness and the release identifier can read it.
- `schema_version` window enforcement using `DOS-M04-002` rules: refuse to expose the repo (typed `incompatible_schema`) if the catalog's `schema_version` is outside the compatible window for the deployed application version, or if `min_app_version` is not satisfied.
- A `not_ready` typed error surfaced by the `DigitalOilSticker.Catalog` context whenever the repo is unopened, mid-open, or has failed its pin/window check — never a partial result, never a raw Ecto exception, never a default value pretending the catalog was consulted.
- The half-swap-freedom guarantee at the M04 boundary: within one machine the repo is either fully opened against exactly one hash-verified path with exactly one `data_version` or it is closed and returning `not_ready`; the transition between two such states is the machine's own start/stop, not a runtime rename.
- Cross-machine swap semantics: replacement of the active `data_version` is a Fly release (new image up, old image down); this card asserts and tests that no code path in `DigitalOilSticker.Catalog` mutates the active file, opens a second `CatalogRepo` at runtime, or attempts an in-place upgrade — all of which are meaningless in an in-image, read-only design and are explicitly prohibited.
- Rollback semantics from the repo boundary: a redeploy of the previous image digest restores the previous catalog byte-for-byte and the pin re-verifies against that image's manifest; the repo has no state that survives a machine replacement, so rollback is symmetric with roll-forward.
- Response to a rollback across a client-storage `schema_version` boundary: `DigitalOilSticker.Catalog` still opens correctly, still resolves references, and returns `unsupported` for any catalog reference the older `data_version` does not know — the "newer client data" read-only mode itself lives with the client-storage protocol (`DOS-M09-003`, ADR-0004 §"Schema versioning and migration"), and this card must not gate on it.
- Provenance survival across a swap: for any successful resolve, INV-15 provenance fields belong to whatever `data_version` was pinned at the moment of the resolve; there is no window in which a resolver returns fields from one `data_version` combined with provenance from another.
- Release-gating assertions this card owns and `DOS-M09-005` FR-13 consumes: exactly one Ecto repo in the deployed application (`CatalogRepo`); connection is read-only; a write attempt is rejected by the connection; the repo refuses to open on hash mismatch, size mismatch, missing file, incompatible schema, or unsatisfied `min_app_version`; and every non-`not_ready` `Catalog` result carries the pinned `data_version`.

## Excluded

- The deploy pipeline itself — `Dockerfile`, `fly.toml`, region, machine count, secrets, release identifier composition, readiness endpoint plumbing, one-command rollback, and the survival-of-a-live-deploy rehearsal — all belong to `DOS-M09-005`. This card supplies the repo-level properties readiness reads; it does not implement readiness.
- First-launch copy from an application bundle, `catalog-pointer.json`, staging directories, decompression of a compressed on-device payload, boot-time integrity/foreign-key/smoke passes on a freshly copied file, retained-rollback of a prior on-device catalog, containment-safe GC of inactive catalog files, and the persisted installer state machine (`copying`, `verifying`, `ready`, `activating`, `active`, `failed`, `superseded`). These mechanics presuppose a signed native package, a device filesystem, and a mutable on-device catalog root — none of which exist in the browser MVP — and they carve out to the native re-entry holding set alongside the DEFER'd `DOS-M00-003`/`DOS-M00-005` work and the native halves of `DOS-M05-006` and `DOS-M06-005`. The pre-pivot spec is preserved at the bottom of this file for that revival.
- Any `UserRepo` handling on the server. There is no `UserRepo` in the deployed application (ADR-0004 §4, INV-23). Client-storage schema migration (`DOS-M04-007` re-scoped, `DOS-M09-001`, `DOS-M09-003`) is the browser-side counterpart and is out of this card.
- Catalog compilation, quality gates, manifest generation, and `data_version` selection — `DOS-M03-010`. This card consumes and verifies the artifact and never edits one; CHANGE_CONTROL Rule 6 forbids in-place edits and the in-image design makes them structurally impossible.
- Signed online updates, delta patches, resumable downloads, remote signature/key workflows, provider calls, and any HTTP fetch of catalog bytes at runtime. `DOS-M08` is DEFER'd for the same reasons; a browser MVP that queries the catalog server-side has no client-side update to perform.
- LiteFS, volumes, Postgres, multi-region replicas — all rejected by ADR-0004 for a read-only, deploy-versioned dataset.
- Custom-domain, TLS, HSTS, CSP, `check_origin`, and rate-limiting configuration (`DOS-M09-006`, `DOS-M09-008`); this card must not weaken those and does not configure them.
- Third-party APM, error reporters, and log shippers — ADR-0004 "No third-party anything" and INV-4 prohibit them, especially for a component whose failure paths could otherwise serialize `socket.assigns` off-box.

## Functional requirements

- FR-1: The deployed application starts exactly one Ecto repo, `DigitalOilSticker.CatalogRepo`, opened read-only (`mode=ro`) with `PRAGMA query_only = ON` and `pool_size` sized to the machine's measured shared-CPU concurrency; a write attempt is rejected by the connection itself, not only by convention. (INV-23, ADR-0004 §4; enforcement layer feeding `DOS-M09-005` FR-4/AC-4.)
- FR-2: On boot, the application reads the in-image `catalog-manifest.json`, hashes the in-image catalog payload, compares payload SHA-256 and declared byte length against the manifest, and refuses to expose `CatalogRepo` on any mismatch. The pinned tuple `(payload_hash, data_version, schema_version, min_app_version)` is written to application env for readiness and the release identifier to read.
- FR-3: On boot, the application enforces the `DOS-M04-002` `schema_version` compatibility window and the manifest's `min_app_version`; a catalog outside the window fails to expose with typed `incompatible_schema`, and an unsatisfied `min_app_version` fails to expose with typed `incompatible_app_version`.
- FR-4: `DigitalOilSticker.Catalog` returns a typed `not_ready` result whenever the repo is unopened, mid-open, or has failed FR-2/FR-3; it never returns a partial result, a raw Ecto exception, or a default value that could be mistaken for a resolved answer. `not_ready` is a legitimate INV-11-adjacent state and `DOS-M09-004` renders it as such.
- FR-5: Within one machine, `CatalogRepo` is either fully opened against exactly one hash-verified path with exactly one `data_version` or it is closed and the context returns `not_ready`. No code path in `DigitalOilSticker.Catalog` mutates the active file, opens a second repo at runtime, renames the artifact, or attempts an in-place upgrade; any such attempt is a static-analysis / test-time failure. (Retires the pre-pivot FR-5/FR-6/FR-9 activation-rename mechanics, whose on-device rename semantics are meaningless in an in-image read-only design.)
- FR-6: Cross-machine replacement of the active `data_version` occurs exclusively via a Fly release: a new image comes up, passes readiness, takes traffic; the old image drops out. The M04 boundary owns and tests the property that gates the readiness transition (no half-swapped answer within a machine, FR-2/FR-3/FR-5), and `DOS-M09-005` FR-13 owns the pipeline that gates the machine transition itself. (Retires the pre-pivot FR-1 bundle-packaging requirement — carved out to the native re-entry set — and the pre-pivot FR-4/FR-6 installer state machine, replaced by the deploy pipeline as the sole activation mechanism.)
- FR-7: Rollback is a redeploy of the previous image digest; because the repo holds no state that survives a machine replacement, rollback is symmetric with roll-forward and re-verifies the previous manifest against the previous payload. The `DigitalOilSticker.Catalog` context has no on-device rollback logic to invoke and none is added. (Retires the pre-pivot FR-7 retention/GC requirement — there is no on-device "prior compatible catalog" to retain because there is no on-device catalog at all.)
- FR-8: For any successful resolve, INV-15 provenance and INV-11 support-status fields belong to the `data_version` pinned at the moment of the resolve; there is no window in which a resolver returns fields from one `data_version` combined with provenance from another. The pinned `data_version` is included in the result payload the `DOS-M09-004` query layer stamps for cache-keying and evidence.
- FR-9: A rollback that lands an application version older than a client's stored `schema_version` MUST NOT cause `DigitalOilSticker.Catalog` to error, guess, or fabricate: unknown references resolve to `unsupported` (INV-11) and the client-storage "newer data" read-only mode (`DOS-M09-003`, ADR-0004 §"Schema versioning and migration") owns the mutation-gate. This card asserts only that the resolve path is safe across the boundary. (Retires the pre-pivot FR-8 downgrade-installer behavior — a downgrade is now a deploy, not an installer path.)
- FR-10: The application has no `UserRepo`, no personal-data table, no personal-data migration, and no backup job. A release-gating test enumerates started repos and asserts the list is exactly `[DigitalOilSticker.CatalogRepo]` opened read-only. (Retires the pre-pivot FR-10 on-device-only pool/reopen requirement whose scope was the device shell; the enforcement moves to the deployed-image assertion.)
- FR-11: No runtime network I/O for catalog bytes: no HTTP, no channel-manifest fetch, no signed-online-update path, no third-party call. Catalog acquisition runs at build time only (`DOS-M03-010`), and this card's tests scan the runtime code path for outbound requests keyed on catalog operations. (Restates the pre-pivot exclusion as an active, tested requirement in the hosted context.)
- FR-12: A deploy is a machine replacement; INV-24.1 requires user data to survive machine replacement because the server was never the system of record. This card asserts that `DigitalOilSticker.Catalog` holds no per-connection state that would prevent a re-hydrated LiveView from resuming a resolve after reconnect, and that a resolve issued mid-hydration returns `not_ready` rather than a stale result from the outgoing machine.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.CatalogRepo` — Ecto SQLite repo, read-only, opened in the application's supervision tree with the FR-1 open parameters. Owned by this card.
- `DigitalOilSticker.Catalog` — the read-only context that exposes vehicle-selection and requirement-resolve functions; consumes `CatalogRepo`, enforces FR-4/FR-5/FR-8/FR-9, and is the only surface `DOS-M09-004` calls. Owned by this card at the boundary level; `DOS-M09-004` owns the query-layer facade over it.
- Catalog boot verifier — a small module that runs before `CatalogRepo` is exposed, executes FR-2/FR-3, publishes the pinned tuple to application env, and produces the boolean readiness input `DOS-M09-005` reads. Owned by this card.
- Deploy pipeline (`DOS-M09-005`) — owns the image build, the readiness endpoint, the release identifier, and the rollback command; consumes this card's assertions.

### Data and persistence

- One file: the catalog artifact at a fixed in-image path, read-only, opened by `CatalogRepo` with `mode=ro` and `PRAGMA query_only = ON`.
- No volume, no LiteFS, no managed database, no runtime writer, no mutable state on the machine that outlives a restart.
- No `catalog-pointer.json`, no staging directory, no `catalog_installations` row — those are on-device installer artifacts and do not exist in the deployed application.
- The manifest (`catalog-manifest.json`) is a read-only in-image sibling of the payload; the pinned tuple derived from it lives in application env for the lifetime of the machine.

### Interfaces and events

- Typed errors: `not_ready`, `incompatible_schema` (from FR-3), `incompatible_app_version` (from FR-3), `unsupported_data_version` (surfaced upward when a client-held catalog reference is unknown under the pinned `data_version`). Every `DigitalOilSticker.Catalog` function returns a result tagged with the pinned `data_version` so `DOS-M09-004` can cache and stamp it.
- Boot event: a single structured log line at the moment the repo is exposed, carrying `data_version`, `schema_version`, `payload_hash`, `min_app_version`, and the boolean readiness input. No personal data, no request payload, no `tab_id`.
- No inter-process activation event, no `catalog_activated` topic, no pointer-swap notification — the deploy is the event, and `DOS-M09-005` owns its observability.

### Failure and recovery behavior

- Hash mismatch, size mismatch, missing file, unreadable file, incompatible schema, unsatisfied `min_app_version`, or a failed read-only-mode assertion each cause the boot verifier to leave `CatalogRepo` closed and readiness (per `DOS-M09-005`) to fail closed; the machine does not take traffic. There is no runtime remediation path — a bad image is rolled back at the deploy layer.
- A runtime SQLite-level error on a query surfaces to `DigitalOilSticker.Catalog` as a typed context error; the process does not attempt to reopen the repo, does not swap files, and does not degrade to a default answer.
- Because there is no writer and no mutable state, there is no crash-consistency window to reason about: the file is either the file the manifest describes or the repo is closed.
- A deploy in flight drops sockets; INV-7 and INV-24 require the client to reconnect and re-hydrate. This card asserts `DigitalOilSticker.Catalog` holds no per-connection state that would break that reconnection.

### Security and privacy

- Read-only open enforced by the connection (`mode=ro`) and `PRAGMA query_only = ON`; a write attempt is rejected by the connection, not only by code review (ADR-0004 §4).
- Zero network I/O for catalog bytes at runtime (FR-11); catalog acquisition is a build-time-only concern of `DOS-M03-010`.
- No personal data ever passes through this card: `DigitalOilSticker.Catalog` accepts only catalog-shape parameters, never a VIN, odometer, note, or record id. This complements INV-26 as owned by `DOS-M09-004`.
- Diagnostics record versions, hashes, and typed errors — never user data, never request payloads. `debug_errors: false` in production so a boot-verifier failure never renders assigns.
- No `UserRepo` presence to defend: the release-gating enumeration test (FR-10) is the structural guarantee.

### Accessibility and performance

- No direct UI. Boot time is measured against `DOS-M09-005`'s startup budget and is dominated by the payload hash computation; the pin, once written, is O(1) per request.
- Query latency is `DOS-M09-004`'s budget, not this card's, but the read-only open contract (single-file SQLite, in-process, no network hop) is a precondition for that budget being achievable at all.
- `not_ready` is a first-class UX state through `DOS-M09-004` and the UX contract cards; it is never rendered as an error toast, and it never occupies the empty-garage state (INV-24.3).

## UX and content states

There is no direct UI in this card. The user-visible surfaces of its behavior are: (1) the honest-degradation "catalog is not ready" state during a deploy or a boot-verifier failure, rendered by the query-layer and UX contract cards, which must not be mistaken for an empty garage or a lost record; (2) an `unsupported` INV-11 status on a resolve of a client-held reference the currently pinned `data_version` does not know, which is rendered as such rather than as an error; (3) the "this browser holds data from a newer version" read-only banner across a client-storage schema rollback, which is `DOS-M09-003`'s to render and this card must not accidentally block. Copy for all three lives with `DOS-M09-004` and `DOS-M02-003`/`DOS-M09-004` respectively; this card owns the underlying typed contracts they render.

- [ ] AC-10: A single boot event log line per machine records `data_version`, `schema_version`, `payload_hash`, `min_app_version`, and readiness; the log-scanning gate confirms no personal field appears in this line or in any error emitted by the boot verifier (INV-3, INV-4).

- Rollback-across-schema resolve-safety tests: a client reference known only to the newer `data_version` resolves to `unsupported` under the older, and no call raises (FR-9 → AC-6, AC-7).
- Network-audit / call-graph tests: no outbound HTTP or channel client is reachable from `DigitalOilSticker.Catalog`'s call graph (FR-11 → AC-8).

- Traffic capture during a deploy rehearsal confirming no outbound catalog HTTP originates from the runtime (AC-8).

## Rollout and rollback

Rollout is the Fly release itself, owned by `DOS-M09-005`: a new image containing a new `data_version` is deployed; its boot verifier enforces this card's FRs; only if readiness passes does the machine take traffic. Rollback is a redeploy of the previous image digest; because the repo holds no state that survives a machine replacement, the previous `data_version` is restored byte-for-byte. A rollback that crosses a client-storage `schema_version` boundary enters ADR-0004's read-only "newer data" mode on the client side (`DOS-M09-003`) and this card guarantees that path is safe on the resolve side. There is no on-device install/upgrade/rollback ceremony to run; the pre-pivot state machine for that ceremony is preserved at the bottom of this file for the native re-entry.

## Dependency rationale

Blocked by `DOS-M03-010` (produces the manifest and payload this card pins against), `DOS-M04-002` re-scoped (defines the `schema_version` compatibility window and typed `incompatible_schema` semantics this card enforces), `DOS-M04-001` re-scoped (ratifies the one-repo-server / IndexedDB-client dual-repository model this card operates inside), and the ADR-0004 ratification. Runs alongside `DOS-M09-005` (which builds the image and owns readiness / rollback) — this card supplies the properties readiness reads and the rehearsal script asserts. Blocks the re-scoped `DOS-M04-004` (deterministic read-only `CatalogRepo` exposes the open contract this card fixes), `DOS-M09-004` (surfaces the typed `not_ready` and `unsupported_data_version` results as INV-11 states), `DOS-M09-005` FR-13 (its release-gating half depends on this card's repo-boundary properties), and the re-scoped `DOS-M04-010` (conformance can only assert half-swap freedom once this card defines it).

## Risks, decisions, and open questions

- Risk: the M04-boundary/M09-pipeline split could leave the atomic-activation requirement half-owned. Mitigation: `DOS-M09-005` FR-13 explicitly cites the re-scoped `DOS-M04-008` requirement, this card explicitly cites `DOS-M09-005` FR-13, and the AC-5 rehearsal is jointly owned; the deploy runbook's rehearsal step is the single script that exercises both halves.
- Risk: a future contributor mistakes the preserved pre-pivot spec at the bottom of this file for current scope and re-introduces on-device installer code paths. Mitigation: the banner, the explicit "Excluded" carve-out, the FR-5 static-analysis check, and the release-gating repo-enumeration test all fail closed if any of that code appears in the deployed application.
- Risk: the browser MVP has no offline path and the amended INV-6 states so; if the native track ever revives, the on-device installer will need to interoperate with a browser-first client whose users have IndexedDB records from a different `data_version`. Mitigation: the pre-pivot spec is preserved verbatim and the native re-entry ADR (ADR-0005, prospective) is where the reconciliation will be designed — this card does not attempt to pre-solve it.
- Decision: the "atomic activation" surface is the deploy, not a per-machine rename. This is the direct consequence of ADR-0004's "Catalog database on Fly" table (single-writer problem eliminated; catalog replacement is a deploy; rollback redeploys the previous image), and the card is scoped accordingly.
- Decision: `DigitalOilSticker.Catalog` returns `not_ready` rather than a default answer during any window where the repo is not exposed, mirroring the pre-pivot typed-taxonomy discipline in the hosted context.
- Open question: whether readiness should fail on a slow hash-verification path during boot or accept a bounded warm-up window. Recorded here; resolved with measured evidence in the `DOS-M09-005` startup-budget work.
- Open question: whether the pinned `data_version` should also be surfaced to clients via a stable version endpoint for cache-busting of client-held resolves after a deploy. Recorded here; likely owned by `DOS-M09-005` (release identifier surface) rather than this card.

## Superseded pre-pivot spec (historical record)

> This section preserves the card as chartered before the 2026-08-01 pivot to browser-first, and is retained for historical readability of the ADR record. The Outcome above is authoritative; the sections below are frozen and no longer describe the work.

### Outcome (pre-pivot)

First launch and app-store upgrades copy the exact catalog packaged with the app into durable catalog storage, verify it completely, and atomically activate it without network access or risk to the prior catalog/UserRepo. The installer is a persisted state machine with staging, full verification, atomic rename/pointer activation, retained-rollback, containment-safe garbage collection, and deterministic crash recovery.

### Why this matters and what it unblocks (pre-pivot)

The signed iOS/Android application bundle is immutable and may contain a newer catalog than the installed Application Support/device-files copy. App kill, reboot, or low space during copy/decompression must not disable offline vehicle/history workflows. This issue makes the offline-from-first-launch promise real: without it, no bundled catalog reaches `CatalogRepo`. It blocks `DOS-M04-010` and production catalog releases, and its verify/stage/atomic-activate/rollback protocol is the template M08's signed online updates must follow.

### Context and source of truth (pre-pivot)

- §11.2 catalog entry "DOS-M04-008 — Install and atomically upgrade the catalog from the native app bundle".
- Master prompt §8 "Migration and catalog rules": on first launch, verify and copy the bundled artifact into application support; when a newer compatible bundled catalog exists after an app upgrade, stage, integrity-check, atomically rename, and retain the previous catalog for rollback; an optional network update follows the same protocol in M08 and never overwrites `UserRepo`.
- `DOS-M03-010`: produces `catalog-manifest.json` and the content-addressed compressed SQLite payload this issue packages and installs; `DOS-M04-002`: schema/metadata compatibility rules and `incompatible_schema` behavior.
- `DOS-M04-006`: staging/catalog roots, disk-space reservation, containment-safe cleanup, boot state machine stages (`inspect_bundle_and_installed_catalog → install_or_select_catalog → start_catalog_repo`), and CatalogRepo stop/start hooks.
- `DOS-M04-001` ADR: `catalog_pointer.json` layout, durability classes (bundled source immutable; installed catalog replaceable/rollback-capable), `pool_size: 1`, read-only reopen.
- `DOS-M04-003`: the `catalog_installations` user-table shape that persists installer state.

### Included (pre-pivot)

- Package M03's `catalog-manifest.json` and content-addressed compressed SQLite payload as read-only application-bundle resources for both platforms. Build validation proves the packaged bytes/checksum equal the M03 release candidate.
- At boot, read only the bundle-local manifest and compare `catalog_version`, `schema_version`, payload SHA, minimum app version, feature/source flags, and bundle resource identity against installed metadata. If the installed version/hash is identical and healthy, perform no copy.
- Before installation, validate source resource existence/declared size, compute required free space for compressed resource + candidate + retained rollback copy, and abort safely when insufficient.
- Copy/decompress the bundle resource to a uniquely named staging child under the catalog root with bounded output size. Compute the exact payload SHA-256 and logical hash; run SQLite `integrity_check`, `foreign_key_check`, schema/metadata compatibility, license/source-feature checks, and representative CatalogRepo smoke queries.
- Close/stop CatalogRepo before pointer activation as required by `ecto_sqlite3`. Activate by atomic same-filesystem rename plus atomic pointer/installation-metadata update; restart CatalogRepo with the new absolute path and health-check it before declaring ready. Never overwrite the previous active file in place.
- Persist states `copying`, `verifying`, `ready`, `activating`, `active`, `failed`, `superseded`. On next boot recover/delete only validated staging children, verify the pointer, and fall back to the prior compatible known-good catalog or bundle catalog. UserRepo remains available for manual/history flows if no catalog validates.
- Retain current + one prior compatible catalog when space and license permit. Garbage collection deletes only explicit, resolved, inactive catalog version paths after CatalogRepo has released them; it can never traverse into UserRepo/recovery roots.
- Test both first install and app upgrade/downgrade cases. An older app confronted with a newer installed catalog either uses a compatible schema or installs its own bundled compatible catalog without migrating the newer file in place.

### Excluded (pre-pivot)

- Any HTTP/Netlify/channel-manifest fetch, resumable/range download, background catalog network update, delta patch, remote signature/key workflow, or runtime provider call. Signed online catalog fetch/update belongs exclusively to `DOS-M08`.
- In-place schema migration of any installed catalog file (per `DOS-M04-002` exclusions); user-table migrations (`DOS-M04-007`).

### Preconditions (pre-pivot)

- `DOS-M03-010` release candidate exists: `catalog-manifest.json` plus content-addressed compressed SQLite payload (development may proceed against the synthetic/golden candidate until then).
- `DOS-M04-002` complete: schema/metadata compatibility rules and typed `incompatible_schema`.
- `DOS-M04-006` complete: staging/catalog roots, space reservation, containment cleanup, repo stop/start hooks, recovery markers.

### Functional requirements (pre-pivot)

- FR-1: Build packaging embeds `catalog-manifest.json` and the content-addressed compressed SQLite payload as read-only bundle resources on both platforms; build validation proves packaged bytes/checksum equal the M03 release candidate.
- FR-2: Boot comparison reads only the bundle-local manifest and installed metadata (`catalog_version`, `schema_version`, payload SHA, minimum app version, feature/source flags, bundle resource identity); identical-and-healthy installed state performs no copy.
- FR-3: Preflight validates source resource existence/declared size and computes required free space for compressed resource + candidate + retained rollback copy, aborting safely (typed `insufficient_space`) when insufficient.
- FR-4: Staging copies/decompresses to a uniquely named staging child under the catalog root with bounded output size (decompression-bomb protection); verification computes exact payload SHA-256 and logical hash and runs `integrity_check`, `foreign_key_check`, schema/metadata compatibility, license/source-feature checks, and representative CatalogRepo smoke queries.
- FR-5: Activation stops CatalogRepo first (as `ecto_sqlite3` requires), performs an atomic same-filesystem rename plus atomic pointer/installation-metadata update, restarts CatalogRepo with the new absolute path, and health-checks before ready; the previous active file is never overwritten in place.
- FR-6: Installer states `copying`, `verifying`, `ready`, `activating`, `active`, `failed`, `superseded` are persisted in `catalog_installations`; next boot recovers/deletes only validated staging children, verifies the pointer, and falls back to the prior compatible known-good catalog or bundle catalog; UserRepo remains available for manual/history flows if no catalog validates.
- FR-7: Retention keeps current + one prior compatible catalog when space and license permit; garbage collection deletes only explicit, resolved, inactive catalog version paths after CatalogRepo releases them and can never traverse into UserRepo/recovery roots.
- FR-8: Downgrade handling: an older app with a newer installed catalog either uses a compatible schema (within the `DOS-M04-002` window) or installs its own bundled compatible catalog; it never migrates the newer file in place.
- FR-9: The installed pointer stores app build, catalog version/schema, payload SHA, absolute-version filename (not an unvalidated arbitrary path), activation time, prior version, and state; all source/candidate/active files pass root-containment checks.
- FR-10: `CatalogRepo` uses `pool_size: 1`, is stopped/reconfigured around activation, and reopens query-only; no LiveView ever observes a half-installed database.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

- The installer component owns the state machine and runs inside the `install_or_select_catalog` stage of the `DOS-M04-006` boot coordinator; it is the only writer of `catalog_installations` and `catalog-pointer.json`.
- Build tooling (CI) owns FR-1 packaging/attestation; the M03 pipeline owns manifest/payload production.
- CatalogRepo stop/start is invoked through the `DOS-M04-006` supervision hooks; the installer never manipulates the repo process directly.
- Garbage collection is part of the installer and uses only the `DOS-M04-006` containment-safe cleanup API.

#### Data and persistence

- Bundle resources (read-only): manifest + compressed payload. Durable artifacts: `catalog/catalog-<version>.sqlite3` (content-addressed, absolute-version filename), `catalog-pointer.json`, staging children under `staging/`, and `catalog_installations` rows in `UserRepo`.
- Hashes: exact payload SHA-256 plus the logical build hash from `catalog_metadata`; both recorded in `catalog_installations` and compared on health checks.
- Retention: active version + one prior compatible version when space and license permit; `superseded` rows record history.

#### Interfaces and events

- Installer API surfaces: `ensure_installed/0`-style boot entry, state inspection for diagnostics/health, and an activation event (`catalog_activated` per §7's event contract) carrying version identifiers, not display strings.
- Errors map to the typed taxonomy: `insufficient_space`, `corrupt`, `incompatible_schema`, `storage_unavailable`, `permission_denied`, with recoverability metadata; verification rejections carry the failing check identity in redacted diagnostics.
- Pointer format is versioned JSON with the FR-9 fields; unknown future fields are rejected or ignored per its documented version rules.

#### Failure and recovery behavior

- Kill/reboot/failure at every copy/decompress/verify/stop/rename/pointer/restart phase leaves either the prior catalog queryable or recovers deterministically on next launch; `UserRepo` bytes/hash remain unchanged in every case.
- Rejection matrix: wrong checksum, missing bundle resource, oversized/decompression-bomb payload, incompatible schema/app version, corrupt SQLite, unauthorized source flag, insufficient space, and failed smoke query each reject activation with a typed error and leave the prior state intact.
- If no catalog validates (bundle and installed both bad), the app still boots: UserRepo-backed manual/history flows remain available and the UI receives the catalog-unavailable state.
- GC failures are non-fatal: an undeletable inactive version is retried on a later boot, never force-deleted through containment bypass.

#### Security and privacy

- Only bundle-local resources are read; zero network I/O (no HTTP/Netlify/channel fetch of any kind).
- Bounded decompression output prevents decompression-bomb storage exhaustion; all paths pass root-containment checks; the pointer stores an absolute-version filename, never an unvalidated arbitrary path.
- License/source-feature checks run during verification so an artifact with unauthorized source flags cannot activate.
- Diagnostics record versions, states, hashes, and typed failures — never user data or raw paths; `UserRepo` content is never read by the installer beyond `catalog_installations`.

#### Accessibility and performance

- No direct UI. First-install/upgrade copy+verify gets its own time/space budget measured and approved in `DOS-M04-010` (bundled first-install/upgrade has a dedicated budget per the candidate list); activation downtime for CatalogRepo restart is bounded and measured; boot fast-path (identical version, no copy) must not measurably delay the cold-boot budget.

### UX and content states (pre-pivot)

Installer states surface to users only as: first-launch progress (install/verify), normal boot (no visible state), and the catalog-unavailable fallback where manual/history flows continue with a clear explanation and no fake data. Never show a half-installed catalog; activation is atomic from the UI's perspective. M05 owns the visual/copy treatment of these states.

### Acceptance criteria (pre-pivot)

- [ ] AC-1: A clean physical iOS/Android install in airplane mode copies, verifies, activates, queries, kills/relaunches, and reuses the bundled catalog with zero network request.
- [ ] AC-2: An app upgrade with a newer bundled catalog retains UserRepo data and the prior catalog until the new CatalogRepo passes health checks; identical bundled catalog performs no duplicate copy.
- [ ] AC-3: Kill/reboot/failure at every copy/decompress/verify/stop/rename/pointer/restart phase leaves either prior catalog queryable or recovers deterministically on next launch; UserRepo bytes/hash remain unchanged.
- [ ] AC-4: Wrong checksum, missing bundle resource, oversized/decompression-bomb payload, incompatible schema/app version, corrupt SQLite, unauthorized source flag, insufficient space, and failed smoke query reject activation.
- [ ] AC-5: Successful activation is atomic from the application's point of view; no LiveView sees a half-installed database, and CatalogRepo always runs against exactly one validated path with `pool_size: 1`.
- [ ] AC-6: Safe rollback and explicit-path garbage collection pass on physical devices with exactly two releases and simulated low space; containment tests prove UserRepo cannot be deleted.

### Test plan (pre-pivot)

#### Automated (pre-pivot)

- Build-time attestation test: packaged bundle resources byte/checksum-equal the M03 release candidate.
- State-machine unit/property tests: every state/transition, idempotent re-entry, marker recovery, no-copy fast path, downgrade selection logic.
- Verification rejection tests: each AC-4 fixture (wrong checksum, missing resource, oversized/bomb payload, incompatible schema/app version, corrupt SQLite, unauthorized source flag, insufficient space, failing smoke query).
- Fault injection at each phase (error + simulated kill) with post-condition assertions: prior catalog queryable or deterministic recovery; UserRepo hash unchanged.
- GC/containment tests: explicit-path-only deletion, refusal to traverse UserRepo/recovery roots, retention of current + one prior.
- Pointer tests: atomic update semantics, absolute-version filename validation, version rules for unknown fields.

#### Manual/device matrix (pre-pivot)

- Minimum-class physical iOS and Android devices, airplane mode throughout:
  - First install: copy/verify/activate/query, kill/relaunch, reuse without recopy; packet capture proving zero network requests.
  - App upgrade with newer bundled catalog: prior catalog retained until health checks pass; UserRepo hash compared before/after.
  - Kill and reboot injections across installer phases; low-space simulation during copy and decompression.
  - Two-release rollback drill plus GC verification; containment demonstration that UserRepo deletion is impossible.
  - App downgrade against a newer installed catalog: compatible-schema use or bundled compatible install, never in-place migration.

### Rollout and rollback (pre-pivot)

Rollout: ships inside packaged app releases; each release carries its catalog and installs per this protocol. Rollback: built into the design — the prior compatible catalog is retained and reactivated when the new one fails health checks; a bad shipped catalog is corrected by shipping a new app build whose bundled catalog supersedes it. The same staged/verified/atomic protocol is the mandated template for M08 online updates, which remain out of scope here.

### Risks, decisions, and open questions (pre-pivot)

- Risk: atomic rename semantics vary across filesystems. Mitigation: same-filesystem staging under the catalog root (FR-4/FR-5) and phase-level kill testing on real devices.
- Risk: stopping/restarting CatalogRepo around activation could race UI queries. Mitigation: activation runs inside boot stages or an equivalent quiesced window; `not_ready` typed errors gate callers; AC-5 asserts no half-installed visibility.
- Risk: retention of two catalogs strains low-storage devices. Mitigation: FR-3 space computation includes the rollback copy; retention is conditional on space and license; low-space drills in AC-6.
- Decision: compression format and bounded-decompression limits (recorded with the packaging implementation, aligned with `DOS-M03-010`).
- Decision: exact representative smoke-query set for verification (aligned with the `DOS-M04-004` contract suite).
- Open question: whether license terms permit retaining a prior catalog version on-device in all cases — retention is "when space and license permit"; the license flag in the manifest governs.
