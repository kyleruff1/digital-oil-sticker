## Outcome

First launch and app-store upgrades copy the exact catalog packaged with the app into durable catalog storage, verify it completely, and atomically activate it without network access or risk to the prior catalog/UserRepo. The installer is a persisted state machine with staging, full verification, atomic rename/pointer activation, retained-rollback, containment-safe garbage collection, and deterministic crash recovery.

## Why this matters and what it unblocks

The signed iOS/Android application bundle is immutable and may contain a newer catalog than the installed Application Support/device-files copy. App kill, reboot, or low space during copy/decompression must not disable offline vehicle/history workflows. This issue makes the offline-from-first-launch promise real: without it, no bundled catalog reaches `CatalogRepo`. It blocks `DOS-M04-010` and production catalog releases, and its verify/stage/atomic-activate/rollback protocol is the template M08's signed online updates must follow.

## Context and source of truth

- §11.2 catalog entry "DOS-M04-008 — Install and atomically upgrade the catalog from the native app bundle".
- Master prompt §8 "Migration and catalog rules": on first launch, verify and copy the bundled artifact into application support; when a newer compatible bundled catalog exists after an app upgrade, stage, integrity-check, atomically rename, and retain the previous catalog for rollback; an optional network update follows the same protocol in M08 and never overwrites `UserRepo`.
- `DOS-M03-010`: produces `catalog-manifest.json` and the content-addressed compressed SQLite payload this issue packages and installs; `DOS-M04-002`: schema/metadata compatibility rules and `incompatible_schema` behavior.
- `DOS-M04-006`: staging/catalog roots, disk-space reservation, containment-safe cleanup, boot state machine stages (`inspect_bundle_and_installed_catalog → install_or_select_catalog → start_catalog_repo`), and CatalogRepo stop/start hooks.
- `DOS-M04-001` ADR: `catalog_pointer.json` layout, durability classes (bundled source immutable; installed catalog replaceable/rollback-capable), `pool_size: 1`, read-only reopen.
- `DOS-M04-003`: the `catalog_installations` user-table shape that persists installer state.

## Included

- Package M03's `catalog-manifest.json` and content-addressed compressed SQLite payload as read-only application-bundle resources for both platforms. Build validation proves the packaged bytes/checksum equal the M03 release candidate.
- At boot, read only the bundle-local manifest and compare `catalog_version`, `schema_version`, payload SHA, minimum app version, feature/source flags, and bundle resource identity against installed metadata. If the installed version/hash is identical and healthy, perform no copy.
- Before installation, validate source resource existence/declared size, compute required free space for compressed resource + candidate + retained rollback copy, and abort safely when insufficient.
- Copy/decompress the bundle resource to a uniquely named staging child under the catalog root with bounded output size. Compute the exact payload SHA-256 and logical hash; run SQLite `integrity_check`, `foreign_key_check`, schema/metadata compatibility, license/source-feature checks, and representative CatalogRepo smoke queries.
- Close/stop CatalogRepo before pointer activation as required by `ecto_sqlite3`. Activate by atomic same-filesystem rename plus atomic pointer/installation-metadata update; restart CatalogRepo with the new absolute path and health-check it before declaring ready. Never overwrite the previous active file in place.
- Persist states `copying`, `verifying`, `ready`, `activating`, `active`, `failed`, `superseded`. On next boot recover/delete only validated staging children, verify the pointer, and fall back to the prior compatible known-good catalog or bundle catalog. UserRepo remains available for manual/history flows if no catalog validates.
- Retain current + one prior compatible catalog when space and license permit. Garbage collection deletes only explicit, resolved, inactive catalog version paths after CatalogRepo has released them; it can never traverse into UserRepo/recovery roots.
- Test both first install and app upgrade/downgrade cases. An older app confronted with a newer installed catalog either uses a compatible schema or installs its own bundled compatible catalog without migrating the newer file in place.

## Excluded

- Any HTTP/Netlify/channel-manifest fetch, resumable/range download, background catalog network update, delta patch, remote signature/key workflow, or runtime provider call. Signed online catalog fetch/update belongs exclusively to `DOS-M08`.
- In-place schema migration of any installed catalog file (per `DOS-M04-002` exclusions); user-table migrations (`DOS-M04-007`).

## Preconditions

- `DOS-M03-010` release candidate exists: `catalog-manifest.json` plus content-addressed compressed SQLite payload (development may proceed against the synthetic/golden candidate until then).
- `DOS-M04-002` complete: schema/metadata compatibility rules and typed `incompatible_schema`.
- `DOS-M04-006` complete: staging/catalog roots, space reservation, containment cleanup, repo stop/start hooks, recovery markers.

## Functional requirements

- FR-1: Build packaging embeds `catalog-manifest.json` and the content-addressed compressed SQLite payload as read-only bundle resources on both platforms; build validation proves packaged bytes/checksum equal the M03 release candidate.
- FR-2: Boot comparison reads only the bundle-local manifest and installed metadata (`catalog_version`, `schema_version`, payload SHA, minimum app version, feature/source flags, bundle resource identity); identical-and-healthy installed state performs no copy.
- FR-3: Preflight validates source resource existence/declared size and computes required free space for compressed resource + candidate + retained rollback copy, aborting safely (typed `insufficient_space`) when insufficient.
- FR-4: Staging copies/decompresses to a uniquely named staging child under the catalog root with bounded output size (decompression-bomb protection); verification computes exact payload SHA-256 and logical hash and runs `integrity_check`, `foreign_key_check`, schema/metadata compatibility, license/source-feature checks, and representative CatalogRepo smoke queries.
- FR-5: Activation stops CatalogRepo first (as `ecto_sqlite3` requires), performs an atomic same-filesystem rename plus atomic pointer/installation-metadata update, restarts CatalogRepo with the new absolute path, and health-checks before ready; the previous active file is never overwritten in place.
- FR-6: Installer states `copying`, `verifying`, `ready`, `activating`, `active`, `failed`, `superseded` are persisted in `catalog_installations`; next boot recovers/deletes only validated staging children, verifies the pointer, and falls back to the prior compatible known-good catalog or bundle catalog; UserRepo remains available for manual/history flows if no catalog validates.
- FR-7: Retention keeps current + one prior compatible catalog when space and license permit; garbage collection deletes only explicit, resolved, inactive catalog version paths after CatalogRepo releases them and can never traverse into UserRepo/recovery roots.
- FR-8: Downgrade handling: an older app with a newer installed catalog either uses a compatible schema (within the `DOS-M04-002` window) or installs its own bundled compatible catalog; it never migrates the newer file in place.
- FR-9: The installed pointer stores app build, catalog version/schema, payload SHA, absolute-version filename (not an unvalidated arbitrary path), activation time, prior version, and state; all source/candidate/active files pass root-containment checks.
- FR-10: `CatalogRepo` uses `pool_size: 1`, is stopped/reconfigured around activation, and reopens query-only; no LiveView ever observes a half-installed database.

## Technical implementation contract

### Components and ownership boundaries

- The installer component owns the state machine and runs inside the `install_or_select_catalog` stage of the `DOS-M04-006` boot coordinator; it is the only writer of `catalog_installations` and `catalog-pointer.json`.
- Build tooling (CI) owns FR-1 packaging/attestation; the M03 pipeline owns manifest/payload production.
- CatalogRepo stop/start is invoked through the `DOS-M04-006` supervision hooks; the installer never manipulates the repo process directly.
- Garbage collection is part of the installer and uses only the `DOS-M04-006` containment-safe cleanup API.

### Data and persistence

- Bundle resources (read-only): manifest + compressed payload. Durable artifacts: `catalog/catalog-<version>.sqlite3` (content-addressed, absolute-version filename), `catalog-pointer.json`, staging children under `staging/`, and `catalog_installations` rows in `UserRepo`.
- Hashes: exact payload SHA-256 plus the logical build hash from `catalog_metadata`; both recorded in `catalog_installations` and compared on health checks.
- Retention: active version + one prior compatible version when space and license permit; `superseded` rows record history.

### Interfaces and events

- Installer API surfaces: `ensure_installed/0`-style boot entry, state inspection for diagnostics/health, and an activation event (`catalog_activated` per §7's event contract) carrying version identifiers, not display strings.
- Errors map to the typed taxonomy: `insufficient_space`, `corrupt`, `incompatible_schema`, `storage_unavailable`, `permission_denied`, with recoverability metadata; verification rejections carry the failing check identity in redacted diagnostics.
- Pointer format is versioned JSON with the FR-9 fields; unknown future fields are rejected or ignored per its documented version rules.

### Failure and recovery behavior

- Kill/reboot/failure at every copy/decompress/verify/stop/rename/pointer/restart phase leaves either the prior catalog queryable or recovers deterministically on next launch; `UserRepo` bytes/hash remain unchanged in every case.
- Rejection matrix: wrong checksum, missing bundle resource, oversized/decompression-bomb payload, incompatible schema/app version, corrupt SQLite, unauthorized source flag, insufficient space, and failed smoke query each reject activation with a typed error and leave the prior state intact.
- If no catalog validates (bundle and installed both bad), the app still boots: UserRepo-backed manual/history flows remain available and the UI receives the catalog-unavailable state.
- GC failures are non-fatal: an undeletable inactive version is retried on a later boot, never force-deleted through containment bypass.

### Security and privacy

- Only bundle-local resources are read; zero network I/O (no HTTP/Netlify/channel fetch of any kind).
- Bounded decompression output prevents decompression-bomb storage exhaustion; all paths pass root-containment checks; the pointer stores an absolute-version filename, never an unvalidated arbitrary path.
- License/source-feature checks run during verification so an artifact with unauthorized source flags cannot activate.
- Diagnostics record versions, states, hashes, and typed failures — never user data or raw paths; `UserRepo` content is never read by the installer beyond `catalog_installations`.

### Accessibility and performance

- No direct UI. First-install/upgrade copy+verify gets its own time/space budget measured and approved in `DOS-M04-010` (bundled first-install/upgrade has a dedicated budget per the candidate list); activation downtime for CatalogRepo restart is bounded and measured; boot fast-path (identical version, no copy) must not measurably delay the cold-boot budget.

## UX and content states

Installer states surface to users only as: first-launch progress (install/verify), normal boot (no visible state), and the catalog-unavailable fallback where manual/history flows continue with a clear explanation and no fake data. Never show a half-installed catalog; activation is atomic from the UI's perspective. M05 owns the visual/copy treatment of these states.

## Acceptance criteria

- [ ] AC-1: A clean physical iOS/Android install in airplane mode copies, verifies, activates, queries, kills/relaunches, and reuses the bundled catalog with zero network request.
- [ ] AC-2: An app upgrade with a newer bundled catalog retains UserRepo data and the prior catalog until the new CatalogRepo passes health checks; identical bundled catalog performs no duplicate copy.
- [ ] AC-3: Kill/reboot/failure at every copy/decompress/verify/stop/rename/pointer/restart phase leaves either prior catalog queryable or recovers deterministically on next launch; UserRepo bytes/hash remain unchanged.
- [ ] AC-4: Wrong checksum, missing bundle resource, oversized/decompression-bomb payload, incompatible schema/app version, corrupt SQLite, unauthorized source flag, insufficient space, and failed smoke query reject activation.
- [ ] AC-5: Successful activation is atomic from the application's point of view; no LiveView sees a half-installed database, and CatalogRepo always runs against exactly one validated path with `pool_size: 1`.
- [ ] AC-6: Safe rollback and explicit-path garbage collection pass on physical devices with exactly two releases and simulated low space; containment tests prove UserRepo cannot be deleted.

## Test plan

### Automated

- Build-time attestation test: packaged bundle resources byte/checksum-equal the M03 release candidate.
- State-machine unit/property tests: every state/transition, idempotent re-entry, marker recovery, no-copy fast path, downgrade selection logic.
- Verification rejection tests: each AC-4 fixture (wrong checksum, missing resource, oversized/bomb payload, incompatible schema/app version, corrupt SQLite, unauthorized source flag, insufficient space, failing smoke query).
- Fault injection at each phase (error + simulated kill) with post-condition assertions: prior catalog queryable or deterministic recovery; UserRepo hash unchanged.
- GC/containment tests: explicit-path-only deletion, refusal to traverse UserRepo/recovery roots, retention of current + one prior.
- Pointer tests: atomic update semantics, absolute-version filename validation, version rules for unknown fields.

### Manual/device matrix

- Minimum-class physical iOS and Android devices, airplane mode throughout:
  - First install: copy/verify/activate/query, kill/relaunch, reuse without recopy; packet capture proving zero network requests.
  - App upgrade with newer bundled catalog: prior catalog retained until health checks pass; UserRepo hash compared before/after.
  - Kill and reboot injections across installer phases; low-space simulation during copy and decompression.
  - Two-release rollback drill plus GC verification; containment demonstration that UserRepo deletion is impossible.
  - App downgrade against a newer installed catalog: compatible-schema use or bundled compatible install, never in-place migration.

## Rollout and rollback

Rollout: ships inside packaged app releases; each release carries its catalog and installs per this protocol. Rollback: built into the design — the prior compatible catalog is retained and reactivated when the new one fails health checks; a bad shipped catalog is corrected by shipping a new app build whose bundled catalog supersedes it. The same staged/verified/atomic protocol is the mandated template for M08 online updates, which remain out of scope here.

## Dependency rationale

Blocked by `DOS-M03-010` (the manifest + content-addressed payload it installs are that issue's release candidate; per the M04 dependency order, the installer is implemented/validated after the full approved catalog — or the explicitly reduced free-approved baseline — is compiled), `DOS-M04-002` (schema/metadata compatibility checks and `incompatible_schema` semantics), and `DOS-M04-006` (staging/catalog roots, space reservation, containment cleanup, repo stop/start hooks, boot stages). It blocks `DOS-M04-010` (certification exercises install/upgrade/rollback on devices) and production catalog releases. Its protocol is deliberately reused by M08's signed online updates, keeping network complexity out of v1.

## Risks, decisions, and open questions

- Risk: atomic rename semantics vary across filesystems. Mitigation: same-filesystem staging under the catalog root (FR-4/FR-5) and phase-level kill testing on real devices.
- Risk: stopping/restarting CatalogRepo around activation could race UI queries. Mitigation: activation runs inside boot stages or an equivalent quiesced window; `not_ready` typed errors gate callers; AC-5 asserts no half-installed visibility.
- Risk: retention of two catalogs strains low-storage devices. Mitigation: FR-3 space computation includes the rollback copy; retention is conditional on space and license; low-space drills in AC-6.
- Decision: compression format and bounded-decompression limits (recorded with the packaging implementation, aligned with `DOS-M03-010`).
- Decision: exact representative smoke-query set for verification (aligned with the `DOS-M04-004` contract suite).
- Open question: whether license terms permit retaining a prior catalog version on-device in all cases — retention is "when space and license permit"; the license flag in the manifest governs.
