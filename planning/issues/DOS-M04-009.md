## Outcome

A user can create a portable backup of all local profile, vehicle, history, usage-profile, forecast, reminder-rule, and notification data; restore it safely on a clean install; and erase local data without an account or support intervention. The export is a documented, versioned, checksummed envelope; import is staged, previewed, transactional, and idempotent; delete-all is verified erasure.

## Why this matters and what it unblocks

Offline-only storage is device-bound and can be lost through uninstall, device failure, or unrecoverable migration/storage damage. Export is the practical user-controlled recovery path and makes migrations/app upgrades safer. It is the escape hatch the `DOS-M04-007` recovery UI offers before any restore decision, the launch-hardening requirement "import/export or another approved local recovery mechanism" from §5, and a `DOS-M04-010` certification subject. It blocks production release and M04 completion.

## Included

- Define a documented versioned export envelope containing user data only — including usage profiles, forecast snapshots, reminder rules, and scheduled-notification state — plus stable catalog references/snapshots, record counts, exported-at, app/schema versions, units/timezone, and payload checksum. Do not recreate already-fired OS notifications during import; mark imported scheduling rows for explicit reconciliation.
- Default JSON (optionally ZIP-compressed after measurements). Catalog payload is excluded; manifest/version reference is included. No credentials, native file paths, internal SQLite pages, or native notification handles are exported.
- Validate import envelope/schema/checksum/size before opening a transaction. Stage and preview counts/conflicts. Initial policy supports `replace after backup` and/or deterministic merge by UUID; choose explicitly in ADR.
- Import is idempotent and transactional. Unknown future fields are preserved or rejected according to format-version rules; never silently discard.
- User-facing delete-all closes connections, deletes explicitly resolved user DB/export staging/notification registrations, verifies absence, and leaves replaceable catalog according to clear copy. Vehicle delete remains separate and previewed.
- Warn that exported maintenance history may be sensitive; use platform share/download securely and never upload automatically.
- Implement the envelope contract: `format: digital-oil-sticker-user-export`, `format_version`, `export_id`, `exported_at`, `app_version`, `user_schema_version`, `catalog_versions_referenced[]`, `record_counts`, `payload`, `payload_sha256`; canonical JSON hashing excludes the hash field itself; every snapshot retains its own version.
- Record every import attempt in `import_history` (format version, source fingerprint, timing, status, summary).

## Excluded

- Automatic cloud backup/sync; password-based account recovery; exporting licensed catalog tables; promising encryption unless an audited format/key UX exists.
- The recovery UI screens themselves (M05 renders them; this issue provides the operations and typed results) and OS share-sheet visual design.

## Functional requirements

- FR-1: Export produces the versioned envelope with exactly the documented top-level fields: `format: digital-oil-sticker-user-export`, `format_version`, `export_id`, `exported_at`, `app_version`, `user_schema_version`, `catalog_versions_referenced[]`, `record_counts`, `payload`, `payload_sha256`; canonical JSON hashing excludes the hash field itself.
- FR-2: The payload contains user data only — local profile, vehicles, odometer readings, oil-change events, usage profiles, forecast snapshots, reminder rules, scheduled-notification state, settings — with stable catalog references/snapshots and per-snapshot versions; the catalog payload is excluded while its manifest/version reference is included.
- FR-3: Exports never contain credentials, native file paths, internal SQLite pages, or native notification handles.
- FR-4: Import validates envelope/schema/checksum/size before opening a transaction, stages the data, and previews counts/conflicts to the caller before commit.
- FR-5: The import policy implements the ADR-selected options (`replace after backup` and/or deterministic merge by UUID); replace always creates a verified backup first (reusing the `DOS-M04-007` SQLite-safe method).
- FR-6: Import is idempotent and transactional: re-importing the same envelope follows the documented idempotency/merge policy without duplicates; any failure rolls back completely.
- FR-7: Unknown future fields are preserved or rejected according to format-version rules; nothing is silently discarded.
- FR-8: Imported scheduling rows never recreate already-fired OS notifications; they are marked for explicit reconciliation by the Reminders layer.
- FR-9: Import with catalog unavailable preserves all history/snapshots and marks unresolved current selections without data loss.
- FR-10: Delete-all closes connections, deletes explicitly resolved user DB/export staging/notification registrations through containment-checked paths, verifies absence afterward, and leaves the replaceable catalog per clear copy; vehicle delete remains a separate previewed flow.
- FR-11: Export/share uses platform share/download mechanisms securely, warns that exported maintenance history may be sensitive, and never uploads automatically.
- FR-12: Every import attempt writes an `import_history` row with format version, source fingerprint, started/completed timestamps, status, and summary.

## Technical implementation contract

### Components and ownership boundaries

- An export/import module in the persistence layer owns serialization, validation, staging, and the transactional apply; it calls `DOS-M04-005` workflows/transaction primitives rather than raw SQL where possible, and `UserRepo.transaction` for the atomic apply.
- Delete-all lives beside it, using `DOS-M04-006` containment-checked deletion and the Reminders adapter for notification-registration cleanup.
- The JSON Schema for the envelope is a committed, versioned artifact; format-version rules are documented alongside it.
- M05 owns the screens; `DOS-M04-007`'s recovery UI links to these operations.

### Data and persistence

- Envelope: canonical JSON (stable key order, defined number/date encodings) so `payload_sha256` is reproducible; optional ZIP compression only after size/time measurements justify it.
- Staging: import candidates are staged under a validated staging child (from `DOS-M04-006`) with size caps before any transaction opens.
- `import_history` per FR-12; export writes no persistent state beyond optional staging cleanup.
- Golden export fixtures exist for every supported `format_version`.

### Interfaces and events

- Typed operations: `export/1` (scope: full), `validate_import/1`, `preview_import/1` (counts/conflicts), `apply_import/2` (policy), `delete_all/1` (confirmation token), each returning typed results/errors from the extended M04 taxonomy (`validation`, `conflict`, `invalid_input`, `insufficient_space`, `corrupt`).
- Import completion emits a local event so UI/reminders can trigger explicit notification reconciliation (never automatic recreation).
- Preview output is a structured report (per-entity counts, conflicts, unresolved catalog references), not prose.

### Failure and recovery behavior

- Corrupt checksum, oversized input, path-bearing archive entries, invalid version, duplicate conflicting UUID, orphan child, and malformed snapshot each abort before or roll back within the transaction, leaving active data unchanged.
- Replace-mode failure restores from the pre-import backup; merge-mode failure rolls back to the pre-import state; both outcomes are recorded in `import_history`.
- Interrupted delete-all (kill mid-erasure) completes or reports verifiably on next boot: absence verification runs before "erased" is ever reported to the user.
- Low space during staging/backup aborts with `insufficient_space` before any destructive step.

### Security and privacy

- Exported history is treated as sensitive: explicit user warning, platform-secure share/download, no automatic upload, no network involvement at all.
- No credentials, native paths, SQLite internals, or notification handles in the envelope (FR-3); licensed catalog tables are never exported.
- No encryption promise unless an audited format/key UX exists (excluded for now); the documentation states plainly that the export is unencrypted.
- Delete-all is genuine erasure with verification — the no-account privacy promise depends on it; logs about export/import contain counts and statuses, never row content.

### Accessibility and performance

- No direct UI. Export/import of the stress fixture (3+ vehicles, full history) must complete within the envelope measured for `DOS-M04-010` device certification; staging validation is streaming/size-capped so oversized inputs fail fast without exhausting memory or storage.

## UX and content states

Operations expose the states M05 renders: export ready/share sheet with sensitivity warning; import validation failure (typed reason); import preview (counts/conflicts) with explicit policy choice; import success including "notifications will be re-planned" messaging (no auto-recreated notifications); catalog-unavailable import success with "unresolved selections" marked; delete-all confirmation, progress, and verified-erasure result with clear copy about the remaining replaceable catalog.

## Test plan

### Automated

- Round-trip tests: 3+ vehicle full-history fixture → export → clean DB import → canonical record/count equality and relationship checks.
- Idempotency tests: repeat import under each approved policy; assert no duplicates and policy-conformant outcomes.
- Corruption/abuse matrix per AC-3, each case asserting active data unchanged (hash-compared).
- Catalog-unavailable import test per AC-4.
- JSON Schema validation of golden exports for every supported `format_version`; hash reproducibility test; content scan per AC-7.
- Delete-all tests: erasure, absence verification, `import_history`/staging cleanup, catalog retention per copy; kill-mid-erasure recovery.
- `import_history` row assertions for success/failure/abort paths.

### Manual/device matrix

- Minimum-class physical iOS and Android devices: full export via platform share flow (sensitivity warning shown), file transfer, clean-device restore, verification of restored history — captured as the clean-device restore video/log.
- Delete-all on device: perform erasure, verify via reinstall/inspection that user data is gone and the documented catalog state remains.
- Recovery-path rehearsal: from the `DOS-M04-007` recovery UI, export, then restore on a clean install.
- Airplane-mode execution of export, import, and delete-all proving zero network involvement.

## Rollout and rollback

Rollout: ships with the app; `format_version` starts at its initial value and every later change is additive with documented version rules and new golden fixtures. Rollback: the operations are self-contained — reverting the feature does not affect stored data; already-created export files remain readable by any app version whose supported `format_version` range includes them. Import mistakes are recoverable via the pre-import backup (replace mode) or transaction rollback (merge mode).

## Dependency rationale

Blocked by `DOS-M04-003` (entities, snapshot versions, `import_history` shape), `DOS-M04-005` (transactional boundary, typed errors, and UUID idempotency semantics the import policy builds on), and `DOS-M04-006` (validated staging roots, containment-safe deletion, and space checks for staging, backup, and delete-all). It blocks production release and M04 completion: §5 lists local recovery as launch hardening inside v1, `DOS-M04-007`'s recovery UI depends on export being real, and `DOS-M04-010` certifies export/import as part of the release evidence.

## Risks, decisions, and open questions

- Risk: merge-by-UUID conflicts (same UUID, differing payload) can surprise users. Mitigation: staged preview with explicit conflict counts and the typed `conflict` outcome; policy chosen by ADR, not ad hoc.
- Risk: users treating unencrypted exports as safe to share. Mitigation: FR-11 sensitivity warning and documentation honesty; encryption remains excluded until an audited format/key UX exists.
- Risk: imported notification state resurrecting stale OS notifications. Mitigation: FR-8 explicit-reconciliation marking; reconciliation is owned by the Reminders layer.
- Decision (ADR, this issue): initial import policy — `replace after backup` and/or deterministic merge by UUID.
- Decision: ZIP compression on/off, made only after size/time measurements.
- Open question: exact `record_counts` granularity (per entity vs per entity per vehicle) — fixed in the JSON Schema before freeze.
