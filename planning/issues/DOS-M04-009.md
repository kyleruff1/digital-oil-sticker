> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Export becomes a generated file download and import a file-picker upload via browser File APIs instead of native share sheets, and erasure clears IndexedDB and localStorage — this is now the ONLY portability mechanism and rises in priority._

## Outcome

A user of the hosted browser application can, without an account and without any server-side personal record, produce a portable file backup of their entire browser-held garage — vehicles, service events, odometer readings, usage samples, reminder intent, and preferences — restore it on a browser whose `dos_local` IndexedDB is empty or already populated, and irrevocably erase every personal byte the origin holds when they choose to. Export is a client-side [`Blob`](https://developer.mozilla.org/en-US/docs/Web/API/Blob) download of the versioned envelope owned by [`DOS-M09-001`](DOS-M09-001.md) FR-17; import is a `<input type="file">` upload processed inside the [`DOS-M09-002`](DOS-M09-002.md) storage adapter and pushed through the [`DOS-M09-003`](DOS-M09-003.md) hydration path so it inherits every validation, cap, quarantine, and forward-migration rule the ratified hydration protocol already enforces. Erasure clears the origin-scoped IndexedDB database `dos_local` and the non-personal `localStorage` boot hint `dos_boot_state` — nothing more, nothing less — and verifies absence before the UI is allowed to say "erased." **No byte of a personal record ever traverses the network in either direction**: the export file is generated in the browser, the import file is read in the browser, and the erase operation runs against browser APIs. This mechanism is the *sole* portability and recovery path the browser MVP offers, and the copy that surrounds it says so plainly ([INV-5](../../docs/product/CONSTITUTION.md), [INV-25](../../docs/product/CONSTITUTION.md)).

## Why this matters and what it unblocks

Under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md), browser storage is more easily and more silently destroyed than an app-container database ever was: a "clear site data" click, a private-window tab close, ITP eviction after roughly seven days without a visit, a browser profile reset, or a switch to a different device — any of these ends the garage. There is no server copy, and by [INV-23](../../docs/product/CONSTITUTION.md) there never will be. Export/import is therefore not one recovery mechanism among several; it is *the* recovery mechanism, and [INV-5](../../docs/product/CONSTITUTION.md) plus [INV-25](../../docs/product/CONSTITUTION.md) forbid the UI from ever implying otherwise. That inversion is why the pivot line elevates this card in priority.

Closing this card produces the file format users trust across time — a portable, checksummed, forward-compatible envelope that older and newer deployments can both read honestly — and the erasure primitive that makes the [INV-3](../../docs/product/CONSTITUTION.md)/[INV-23](../../docs/product/CONSTITUTION.md) "no accounts, no server-side personal record" claim end-to-end true. Downstream, [`DOS-M05-007`](DOS-M05-007.md) renders the UI for these operations, [`DOS-M09-004`](DOS-M09-004.md) owns the storage-loss copy that offers export as the escape hatch, and [`DOS-M09-009`](DOS-M09-009.md) certifies export/import round-trip and erasure across the browser matrix.

## Included

- **Export path.** A `LocalStore` phx-hook callback reads every `dos_local` object store in one `readonly` IndexedDB transaction, wraps the payload in the envelope owned by `DOS-M09-001` FR-17 with the export-only fields appended (export identifier, exported-at instant, application version, record counts, SHA-256 hash over canonical serialization with the hash field excluded), serializes it, and hands the browser a `Blob` download named `digital-oil-sticker-export-YYYYMMDD.json` per [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Export and import". The per-tab identifier `tab_id` is deliberately omitted from exported files.
- **Import path.** A `<input type="file" accept="application/json">` returns a `File`; the hook reads it, hash-checks it, and pushes it through the existing `local_store:hydrate` event as though the browser had just been opened — so the file inherits every validation, migration, cap, referential check, and quarantine rule the ratified hydration protocol enforces. Import is explicitly **replace** or **merge**, chosen by the user in a preview screen that shows counts and conflicts *before* commit; it never merges silently.
- **Erasure path.** A dedicated erase operation closes any open `dos_local` connection, calls `indexedDB.deleteDatabase("dos_local")`, calls `localStorage.removeItem("dos_boot_state")`, opens `dos_local` once more to confirm it is fresh, and only then reports "erased" to the LiveView. Erasure targets `dos_local` and `dos_boot_state` and nothing else.
- **The single portability mechanism.** Copy and UX frame export/import/erase as the *only* way to move a garage between browsers, profiles, or devices, and the *only* recovery for a cleared or evicted store — no cloud sync, no server-side backup service, no third-party file-hosting integration is offered or implied ([INV-5](../../docs/product/CONSTITUTION.md), [INV-19](../../docs/product/CONSTITUTION.md), [INV-23](../../docs/product/CONSTITUTION.md)).
- **In-app due-state reconciliation.** When an import completes, the in-app due/overdue state is recomputed against the imported records per [INV-17](../../docs/product/CONSTITUTION.md); there is nothing OS-scheduled to reconcile because the browser MVP schedules nothing.
- **Sensitivity copy and provenance retention.** The export screen warns the file may be sensitive; stored catalog snapshots and their provenance markers survive round-trip verbatim ([INV-11](../../docs/product/CONSTITUTION.md), [INV-15](../../docs/product/CONSTITUTION.md)).
- **Release-gating enforcement.** The [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Enforcement" scripted session exercises this card's operations; a log-scan asserts that no VIN, odometer value, service date, note, or custom vehicle name appears in any captured log line.

## Excluded

- **Any server-side personal-data pipeline.** No upload endpoint, no server-side export renderer, no server-side import validator, no `import_history` table, no server-side staging, no server-held file. The server never sees the file, ever. Sweep finding 1(b)/(c) is addressed by this exclusion (see FR-1 and FR-12).
- **`UserRepo`, `UserRepo.transaction`, and any Ecto machinery for personal data.** The pre-pivot spec built import on top of `UserRepo.transaction` and required an `import_history` row per attempt. Under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) decision §4 the deployed application's Ecto repo list is exactly `[CatalogRepo]`, opened read-only, and asserted by test; there is no `UserRepo` and cannot be one, so those requirements are retired.
- **Re-defining the envelope shape.** The wire and file envelope is owned by `DOS-M09-001` FR-17 (shipped in [`app/lib/digital_oil_sticker/local_store/envelope.ex`](../../app/lib/digital_oil_sticker/local_store/envelope.ex): `envelope`, `schema_version`, `seq`, `tab_id`, `generated_at`, `data`, with an optional `storage` sibling that is deliberately absent from exports). This card consumes that contract and adds only the export-only overlay `DOS-M09-001` FR-17 already specifies. Any envelope-shape change is a `DOS-M09-001` amendment, not an edit here.
- **OS share sheets, iOS/Android file providers, `mob_notify`, OS-scheduled notification handles.** No platform surface outside the browser exists; pre-pivot FR-8 (OS notification reconciliation) is retired.
- **Automatic cloud backup, password-based recovery, third-party file-hosting integration.** Prohibited by [INV-3](../../docs/product/CONSTITUTION.md), [INV-4](../../docs/product/CONSTITUTION.md), [INV-19](../../docs/product/CONSTITUTION.md), [INV-23](../../docs/product/CONSTITUTION.md).
- **Exporting the licensed catalog.** User exports contain stable catalog references and immutable snapshots only. Bulk redistribution of licensed catalog rows via a user export would breach [ADR-0003](../../docs/architecture/ADR-0003-data-boundaries.md).
- **Encryption of the export file.** No encryption is promised at MVP; the export is unencrypted and the UI says so plainly.
- **Service worker caches, OPFS, WASM-SQLite, or any storage this product does not use.** Erasure targets `dos_local` and `dos_boot_state` only.
- **UI screens themselves.** Live in [`DOS-M05-007`](DOS-M05-007.md); storage-loss copy in [`DOS-M09-004`](DOS-M09-004.md). This card exposes the typed operations and states they render.

## Functional requirements

- **FR-1** (retires pre-pivot FR-1; addresses sweep finding 1(a)): The export file uses the envelope shape owned by `DOS-M09-001` FR-17 and implemented in [`app/lib/digital_oil_sticker/local_store/envelope.ex`](../../app/lib/digital_oil_sticker/local_store/envelope.ex): required top-level keys `envelope: "dos_local"`, `schema_version`, `seq`, `tab_id`, `generated_at`, `data`; optional `storage` sibling deliberately omitted from exports; unknown top-level keys rejected. This card **does not** redefine the envelope and **does not** ship the pre-pivot shape (`format: digital-oil-sticker-user-export`, top-level `format_version`, `export_id`, `payload_sha256`, `catalog_versions_referenced[]`, or `payload` as a peer field). The pre-pivot envelope contract is retired in full.
- **FR-2** (replaces pre-pivot FR-2): The `data` map contains only the collections defined in `DOS-M09-001` FR-1 (`meta`, `vehicles`, `events`, `readings`, `usage`, `reminders`, `prefs`) and no others. Stable catalog references and their immutable snapshots ride inside vehicle and event records per `DOS-M09-001` FR-4; the licensed catalog itself is not exported. Every field the schema does not recognize is preserved verbatim (`DOS-M09-001` FR-10).
- **FR-3** (retained, restated for the browser boundary): Exports never contain credentials (there are none — [INV-3](../../docs/product/CONSTITUTION.md)), session cookies, CSRF tokens, `live_socket_id`, `tab_id`, IndexedDB internal structures, OS filesystem paths, OS notification handles, or any server-derivable identifier.
- **FR-4** (replaces pre-pivot FR-4; addresses sweep finding 1(b) — no server transaction): Import validates the file before anything is written to `dos_local`: file size cap client-side; JSON parse; envelope decode via [`Envelope.decode/1`](../../app/lib/digital_oil_sticker/local_store/envelope.ex); SHA-256 hash reproduction per `DOS-M09-001` FR-17; the same server-side validation the `local_store:hydrate` path runs (`DOS-M09-003`), including per-record shape, hard caps ([INV-24.5](../../docs/product/CONSTITUTION.md)), and referential linkage (`DOS-M09-001` FR-11). Preview counts and per-store conflict summaries are computed and rendered *before* the user chooses to commit. **No server-side transaction is opened**, because no server-side personal store exists.
- **FR-5** (replaces pre-pivot FR-5): The import policy is an explicit user choice of **replace** or **merge**, previewed before commit. **Replace** unconditionally erases `dos_local` and rebuilds from the imported payload; the pre-import state is offered as a downloadable safety export at the moment of the choice (the user, not the server, holds the backup — [INV-5](../../docs/product/CONSTITUTION.md), [INV-23](../../docs/product/CONSTITUTION.md)). **Merge** upserts records by UUID per store, using the compare-and-set on `meta.seq` from `DOS-M09-001` FR-16 to prevent silent overwrite of a newer concurrent tab, and surfaces every merge conflict in the preview and post-commit summary.
- **FR-6** (retained restated): Import is idempotent by UUID and by content. Any failure inside the client `readwrite` transaction aborts it wholesale, and `dos_local` is left in its pre-import state (IndexedDB transactional guarantees).
- **FR-7** (retained): Unknown fields inside a record are preserved verbatim on read, in assigns, on write-back, and on the *next* export — same forward-compatibility rule as hydration (`DOS-M09-001` FR-10).
- **FR-8** (retires pre-pivot FR-8; addresses "OS notifications retired"): There are no OS-scheduled notifications to reconcile. Post-import, the in-app due/overdue state is recomputed against the imported records per [INV-17](../../docs/product/CONSTITUTION.md) and the M06 rescope (`DOS-M06-005`); no OS notification handle appears in the payload and none is scheduled during or after import.
- **FR-9** (retained, restated): Import with a catalog reference that resolves to `unsupported` at the current `data_version` preserves the referring record and every immutable snapshot on it, and marks the reference as unresolved — the [INV-11](../../docs/product/CONSTITUTION.md) support-status states this is a legitimate render, not an error. No data is dropped and no fact is fabricated ([INV-15](../../docs/product/CONSTITUTION.md)).
- **FR-10** (replaces pre-pivot FR-10; addresses pivot line "erasure clears IndexedDB and localStorage"): The erase operation is `indexedDB.deleteDatabase("dos_local")` followed by `localStorage.removeItem("dos_boot_state")`, executed in that order after any open connection is closed, and followed by an absence check (re-opening `dos_local` observes `onupgradeneeded` on the fresh database, and `localStorage.getItem("dos_boot_state")` returns `null`). Only after the absence check may the LiveView render "erased." Vehicle-level delete remains a distinct, previewed flow inside the garage; delete-all is scoped to `dos_local` and `dos_boot_state` and nothing else.
- **FR-11** (replaces pre-pivot FR-11; addresses pivot line "generated file download and file-picker upload via browser File APIs"): Export uses browser `Blob` + `URL.createObjectURL` + a synthetic `<a download>` click (or [`showSaveFilePicker`](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker) where available) to produce `digital-oil-sticker-export-YYYYMMDD.json`; import uses `<input type="file" accept="application/json">` (or [`showOpenFilePicker`](https://developer.mozilla.org/en-US/docs/Web/API/Window/showOpenFilePicker) where available). No OS share sheet, no `navigator.share` fallback to a remote target, no upload to any server. The export screen warns that the file may be sensitive and never describes the file as a "backup" (the word is forbidden by [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Export and import").
- **FR-12** (retires pre-pivot FR-12; addresses sweep finding 1(b)/(c) — no `UserRepo`, no `import_history`): No `import_history` table, row, or file exists. Because the browser MVP has no server-side personal store and no `UserRepo` ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) decision §4), there is nowhere on the server to record import attempts, and recording them on the client would either create a durable per-visit identifier (violating [INV-3](../../docs/product/CONSTITUTION.md)) or belong inside `meta` and duplicate the repair-audit already scoped to `DOS-M09-001` FR-13. For operator diagnostics, `meta.last_write_at`, `meta.seq`, and the counters `DOS-M09-001` FR-15 already stores are sufficient; per-attempt attribution to a user is deliberately not available.
- **FR-13** (NEW, addresses pivot line "this is now the ONLY portability mechanism and rises in priority"): The Export/Import/Erase surface is the *only* portability, migration, and recovery mechanism the browser MVP offers. Copy, screen prompts, empty-state offers, and storage-loss states in [`DOS-M09-004`](DOS-M09-004.md) route to these operations and nowhere else; no cloud sync, no server-side backup service, no third-party file-hosting integration, and no `navigator.credentials`-backed identity is offered or implied. The absence of alternatives is stated to the user plainly on the export screen and on every storage-loss screen ([INV-5](../../docs/product/CONSTITUTION.md), [INV-25](../../docs/product/CONSTITUTION.md)).
- **FR-14** (NEW, addresses [INV-25](../../docs/product/CONSTITUTION.md) and [INV-24.4](../../docs/product/CONSTITUTION.md)/[INV-24.8](../../docs/product/CONSTITUTION.md)): The typed results returned to the LiveView distinguish `:hydrating`, `:empty`, `:storage_unavailable`, and `:data_missing` per [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"First-paint and empty-state rules" — an evicted or cleared store never renders as a fresh empty garage, and the `:data_missing` state offers import as its primary action. Erasure success renders through an explicit typed result so "erased" is never rendered from an assumed default.
- **FR-15** (NEW, addresses [INV-4](../../docs/product/CONSTITUTION.md), [INV-22](../../docs/product/CONSTITUTION.md), [INV-26](../../docs/product/CONSTITUTION.md)): No byte of the export file or the imported file ever crosses the LiveView socket, an HTTP request body, an HTTP query string, or any log line. Export is produced inside the hook and never `pushEvent`ed as a whole payload; import is read inside the hook and pushed through `local_store:hydrate` as the same envelope the client would produce on mount. The [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Enforcement" scripted-session log-scan asserts this against the whole flow.

## Technical implementation contract

### Components and ownership boundaries

The `LocalStore` phx-hook (production adapter owned by `DOS-M09-002`) owns every IndexedDB and `localStorage` call — open, read, `readwrite` transaction, `deleteDatabase`, `removeItem`, availability probes — and every File API call — `Blob` construction, `URL.createObjectURL`, `<input type="file">` read, optional `showSaveFilePicker`/`showOpenFilePicker`. The LiveView owns the typed operations `export/1`, `validate_import/1`, `preview_import/1`, `apply_import/2`, and `delete_all/1` in the `DigitalOilSticker.LocalStore.Portability` context (a plain Elixir module against the `LocalStore` behaviour); it never touches browser APIs directly, and it emits results from the error taxonomy in `DOS-M01-002` FR-6. The [`Envelope`](../../app/lib/digital_oil_sticker/local_store/envelope.ex) module owns decode and canonicalization; import reuses `Envelope.decode/1` unchanged so it inherits the same rejection of unknown top-level keys. **No server-side module reads or writes personal data**; the server sees each import as one `local_store:hydrate` event, just as it does on mount.

### Data and persistence

The client uses one `readonly` IndexedDB transaction across every store to snapshot for export, one `readwrite` transaction across every store plus `meta` for the merge-mode upsert-with-compare-and-set, and `indexedDB.deleteDatabase("dos_local")` for erasure. The `localStorage` boot hint `dos_boot_state` is a two-value string (`"never"` | `"has_data"`) whose lifecycle is: set to `"has_data"` after the first meaningful write; explicitly removed on erasure; recomputed on the next successful hydration. Server-side, there is no persistence: no `import_history` table, no export staging, no on-disk file, no ETS cache, no queue — the `DOS-M01-002` FR-8 release gate that asserts the Ecto repo list is exactly `[CatalogRepo]` also protects this card from silent regressions.

### Interfaces and events

- **Typed context API** (`DigitalOilSticker.LocalStore.Portability`):
  - `export/1` → `{:ok, envelope, filename}` — the hook serializes and downloads.
  - `validate_import/1` → `:ok | {:error, taxonomy_reason}`.
  - `preview_import/1` → `{:ok, %ImportPreview{}}` — per-store counts, per-store conflicts, quarantined-record counts, unresolved catalog references, storage-loss impact if the current garage is not empty.
  - `apply_import/2` → `{:ok, summary} | {:error, taxonomy_reason}` — the second argument is `%ImportPolicy{mode: :replace | :merge, safety_export: iodata() | nil}`.
  - `delete_all/1` → `{:ok, :erased} | {:error, taxonomy_reason}` — the argument is a confirmation token issued by a preceding `confirm_delete_all/0` call so a stray event cannot erase. Success is returned only after the absence check succeeds.
- **`LocalStore` message set** (server ⇄ hook) reused verbatim from `DOS-M01-002` FR-3 and `DOS-M09-003`: `local_store:hydrate` (import reuses this on commit), `local_store:put`, `local_store:ack`, `local_store:conflict`. Two additional server → hook messages, neither of which carries a personal payload back over the socket: `local_store:export` (asks the hook to snapshot and offer a download; the whole envelope never crosses back over the socket) and `local_store:erase` (asks the hook to run delete-then-verify and reply `local_store:erased` with a typed outcome only).
- **Local event contract**: `export_produced`, `import_previewed`, `import_committed`, `garage_erased` — each carries only counts, taxonomy codes, and typed outcomes; never a VIN, an odometer value, a note, or a custom vehicle name.

### Failure and recovery behavior

- **Corrupt file, mismatched hash, oversized input, unknown top-level key, wrong `envelope` marker, bad `schema_version`, missing required top-level field, or `data` collection outside the seven allowed names** each yield an explicit typed error from `Envelope.decode/1` and the validation layer; no `dos_local` write occurs.
- **Newer `schema_version` in the imported file than the deployed server** enters the read-only-import-refused state per `DOS-M09-001` FR-9 and `DOS-M09-003`: the LiveView renders an explicit banner, offers export of the *current* garage, and does not write. Downgrading is prohibited.
- **Older `schema_version` in the imported file** is migrated through the ordered `DOS-M09-001` FR-7/FR-8 upgrade steps *before* preview counts are shown.
- **Merge-mode compare-and-set failure on `meta.seq`** (concurrent tab wrote between preview and commit) aborts the transaction atomically, discards optimistic assigns, triggers re-hydration, and the user sees "reloaded from this browser's newer data — re-preview import to see conflicts."
- **Replace-mode failure after the safety export was declined** aborts before `deleteDatabase` runs, so the garage remains intact.
- **Erasure interrupted mid-flight** (tab closed between `deleteDatabase` and `removeItem`, or between removal and the absence check): on the next visit, hydration reads `dos_boot_state` and `dos_local` and renders the honest current state — either both cleared (render `:empty` and record that erasure completed on the prior visit) or one cleared and one not (render `:data_missing` and offer import). "Erased" is never rendered from an assumption.
- **Quota exhaustion during merge-mode import** ([INV-24.5](../../docs/product/CONSTITUTION.md)) fails the `readwrite` transaction as a whole; the taxonomy `:quota_exceeded` error is surfaced with counts.
- **Private-browsing or storage-blocked mode**: erasure returns a `:storage_unavailable` result honestly rather than lying about erasure completing on a store that never opened.

### Security and privacy

- The export file never traverses the network under this card's control. It is generated in the browser, offered as a download, and the user chooses where it goes.
- **Log-scan release gate.** The [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Enforcement" scripted session (hydrate → mutations → export → clear → import) runs against this card's flow; any forbidden value in a captured log line fails the build. `Logger` params are filtered by default; `handle_event` params from portability events are on the explicit non-personal allowlist (counts, taxonomy codes, typed outcomes only).
- **CSRF and origin.** The `local_store:hydrate` event used for import is protected by the same CSRF token and `check_origin` allowlist as every other LiveView event ([INV-22](../../docs/product/CONSTITUTION.md)).
- **CSP.** Export and import use only first-party JavaScript inside the `LocalStore` hook and require no CSP relaxations.
- **`debug_errors: false`** in production ensures no assigns fragment (which could hold an import preview containing VINs) reaches an error page.
- **No third-party error reporting** ([INV-4](../../docs/product/CONSTITUTION.md)).
- **Erasure is genuine.** The absence check exists precisely because [INV-3](../../docs/product/CONSTITUTION.md)'s privacy promise depends on it.

### Accessibility and performance

No direct UI in this card. What this card owes downstream: distinct typed states so live-region announcements ("export ready", "import previewed with N conflicts", "garage erased") map cleanly to WCAG 2.2 AA against the browser assistive-technology matrix owned by [`DOS-M09-009`](DOS-M09-009.md); a stress fixture (3+ vehicles, full history, near the [Constitution §9](../../docs/product/CONSTITUTION.md) 5 MiB working ceiling) whose export/import round trip completes inside the sub-second hydration budget on the browser matrix; streaming, size-capped validation on import so oversized input fails fast.

## UX and content states

Typed operations expose the following states for [`DOS-M05-007`](DOS-M05-007.md) and [`DOS-M09-004`](DOS-M09-004.md) to render:

- **Export ready** — a `Blob` download offered with the sensitivity warning and the copy affirmation that the file is the *only* portability path (forbidden words: "backup", "synced", "safe", "we'll remember", "your account").
- **Import validation failure** — typed reason (bad envelope, hash mismatch, cap exceeded, unknown top-level key, referential-linkage failure); the current garage is not affected.
- **Import preview** — per-store counts, per-store conflict list, quarantined-record count, unresolved catalog reference count, storage-loss impact if `mode: :replace` and the current garage is non-empty; explicit policy choice required; safety-export offer presented at the choice.
- **Import success** — summary counts, "in-app due state re-computed" notice (per [INV-17](../../docs/product/CONSTITUTION.md); no OS notifications rescheduled because none exist), catalog-unresolved marker for any imported reference whose current `data_version` cannot resolve it (an [INV-11](../../docs/product/CONSTITUTION.md) render).
- **Read-only-import-refused** — the imported file's `schema_version` is newer than the deployed server; the LiveView refuses to write and offers a current-garage export.
- **Delete-all confirmation** — copy that names exactly what will be cleared (`dos_local` IndexedDB, `dos_boot_state` `localStorage`) and what will remain (nothing personal; the read-only catalog on the server is unaffected because it was never yours to erase).
- **Delete-all progress** — determinate, never a spinner that hides an interrupted state.
- **Verified erasure** — rendered only after the absence check succeeds; announced through a live region.
- **`:storage_unavailable` erasure** — honest reporting when the browser refused storage; erasure is a no-op and says so.

## Risks, decisions, and open questions

- **Risk:** users treat the export file as automatically safe because a hosted URL implies server-side storage. **Mitigation:** sensitivity warning; the [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) forbidden-copy list; storage-loss copy in [`DOS-M09-004`](DOS-M09-004.md), tested by AC-11.
- **Risk:** [`showSaveFilePicker`](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker) is Chromium-only and its absence on Firefox/WebKit could tempt a `navigator.share` fallback. **Mitigation:** FR-11 pins the fallback path to `Blob` + `<a download>`, and `navigator.share` to a remote target is prohibited; browser-matrix tests exercise both paths.
- **Risk:** the safety export offered at replace-mode preview is skipped by a user and then replace-mode is chosen. **Mitigation:** the safety-export offer is an unmissable step in the preview screen; skipping requires an explicit dismissal and the copy names the loss consequence in plain language.
- **Risk:** a large export file exceeds a constrained mobile browser's memory. **Mitigation:** the [Constitution §9](../../docs/product/CONSTITUTION.md) storage budget (1 MiB per 1,000 records, 5 MiB working ceiling) makes this a non-issue; the stress fixture measures against it on the worst supported combination.
- **Risk:** an import file's `schema_version` is newer than the deployed server on the day a rollback lands. **Mitigation:** the banner is explicit and offers a current-garage export; the rollback runbook in [`DOS-M09-006`](DOS-M09-006.md) records the possibility.
- **Decision (recorded):** the file naming template is `digital-oil-sticker-export-YYYYMMDD.json` per [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md). No time-of-day component is added; the browser's default disambiguation is acceptable.
- **Decision (recorded):** the `import_history` requirement is retired. Any diagnostic need is met by `meta.last_write_at`, `meta.seq`, and `DOS-M09-001` FR-15's counters; per-attempt attribution is deliberately not available under [INV-3](../../docs/product/CONSTITUTION.md).
- **Open question:** whether merge-mode conflict for identical UUID + differing content should be "imported file wins" or "existing wins with imported field surfaced as proposed change". Punted to preview-render evidence in [`DOS-M05-007`](DOS-M05-007.md); the current default is "imported file wins" and the preview shows both sides.
- **Open question:** whether erasure should invalidate the current LiveView socket (forcing a fresh mount) or continue with a `:empty` assigns state. Punted to [`DOS-M09-003`](DOS-M09-003.md) integration testing.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

- An export/import module in the persistence layer owns serialization, validation, staging, and the transactional apply; it calls `DOS-M04-005` workflows/transaction primitives rather than raw SQL where possible, and `UserRepo.transaction` for the atomic apply.
- Delete-all lives beside it, using `DOS-M04-006` containment-checked deletion and the Reminders adapter for notification-registration cleanup.
- The JSON Schema for the envelope is a committed, versioned artifact; format-version rules are documented alongside it.
- M05 owns the screens; `DOS-M04-007`'s recovery UI links to these operations.

#### Data and persistence

- Envelope: canonical JSON (stable key order, defined number/date encodings) so `payload_sha256` is reproducible; optional ZIP compression only after size/time measurements justify it.
- Staging: import candidates are staged under a validated staging child (from `DOS-M04-006`) with size caps before any transaction opens.
- `import_history` per FR-12; export writes no persistent state beyond optional staging cleanup.
- Golden export fixtures exist for every supported `format_version`.

#### Interfaces and events

- Typed operations: `export/1` (scope: full), `validate_import/1`, `preview_import/1` (counts/conflicts), `apply_import/2` (policy), `delete_all/1` (confirmation token), each returning typed results/errors from the extended M04 taxonomy (`validation`, `conflict`, `invalid_input`, `insufficient_space`, `corrupt`).
- Import completion emits a local event so UI/reminders can trigger explicit notification reconciliation (never automatic recreation).
- Preview output is a structured report (per-entity counts, conflicts, unresolved catalog references), not prose.

#### Failure and recovery behavior

- Corrupt checksum, oversized input, path-bearing archive entries, invalid version, duplicate conflicting UUID, orphan child, and malformed snapshot each abort before or roll back within the transaction, leaving active data unchanged.
- Replace-mode failure restores from the pre-import backup; merge-mode failure rolls back to the pre-import state; both outcomes are recorded in `import_history`.
- Interrupted delete-all (kill mid-erasure) completes or reports verifiably on next boot: absence verification runs before "erased" is ever reported to the user.
- Low space during staging/backup aborts with `insufficient_space` before any destructive step.

#### Security and privacy

- Exported history is treated as sensitive: explicit user warning, platform-secure share/download, no automatic upload, no network involvement at all.
- No credentials, native paths, SQLite internals, or notification handles in the envelope (FR-3); licensed catalog tables are never exported.
- No encryption promise unless an audited format/key UX exists (excluded for now); the documentation states plainly that the export is unencrypted.
- Delete-all is genuine erasure with verification — the no-account privacy promise depends on it; logs about export/import contain counts and statuses, never row content.

#### Accessibility and performance

- No direct UI. Export/import of the stress fixture (3+ vehicles, full history) must complete within the envelope measured for `DOS-M04-010` device certification; staging validation is streaming/size-capped so oversized inputs fail fast without exhausting memory or storage.

### UX and content states (pre-pivot)

### Rollout and rollback (pre-pivot)

Rollout: ships with the app; `format_version` starts at its initial value and every later change is additive with documented version rules and new golden fixtures. Rollback: the operations are self-contained — reverting the feature does not affect stored data; already-created export files remain readable by any app version whose supported `format_version` range includes them. Import mistakes are recoverable via the pre-import backup (replace mode) or transaction rollback (merge mode).

### Dependency rationale (pre-pivot)

Blocked by `DOS-M04-003` (entities, snapshot versions, `import_history` shape), `DOS-M04-005` (transactional boundary, typed errors, and UUID idempotency semantics the import policy builds on), and `DOS-M04-006` (validated staging roots, containment-safe deletion, and space checks for staging, backup, and delete-all). It blocks production release and M04 completion: §5 lists local recovery as launch hardening inside v1, `DOS-M04-007`'s recovery UI depends on export being real, and `DOS-M04-010` certifies export/import as part of the release evidence.

### Risks, decisions, and open questions (pre-pivot)

- Risk: merge-by-UUID conflicts (same UUID, differing payload) can surprise users. Mitigation: staged preview with explicit conflict counts and the typed `conflict` outcome; policy chosen by ADR, not ad hoc.
- Risk: users treating unencrypted exports as safe to share. Mitigation: FR-11 sensitivity warning and documentation honesty; encryption remains excluded until an audited format/key UX exists.
- Risk: imported notification state resurrecting stale OS notifications. Mitigation: FR-8 explicit-reconciliation marking; reconciliation is owned by the Reminders layer.
- Decision (ADR, this issue): initial import policy — `replace after backup` and/or deterministic merge by UUID.
- Decision: ZIP compression on/off, made only after size/time measurements.
- Open question: exact `record_counts` granularity (per entity vs per entity per vehicle) — fixed in the JSON Schema before freeze.
