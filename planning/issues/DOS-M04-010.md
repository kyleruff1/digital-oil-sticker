## Outcome

A release gate proves the two on-device Ecto repos remain deterministic and isolated, survive mobile lifecycle/storage faults, require no network, and meet explicit size/latency/memory budgets on packaged physical iOS and Android apps. The gate produces signed release evidence: contract-suite results on hosts and devices, budget measurements against an approved budgets ADR, fault/soak/corruption drill outcomes, and a privacy/network audit.

## Why this matters and what it unblocks

Host tests and simulators cannot reproduce every app-bundle path, SQLite library, filesystem, kill, reboot, or low-space behavior. This issue converts the Mob/Ecto architecture into release evidence on the actual minimum devices. It is the exit gate of the M04 epic: the epic cannot close, and M05-dependent release trains cannot claim persistence readiness, until this certification passes. Its budget ADR also becomes the regression baseline all later milestones (M05–M07) measure against.

## Included

- Define black-box contract suites at the Ecto/context boundary for `DigitalOilSticker.CatalogRepo` and `DigitalOilSticker.UserRepo`. Run fast suites on macOS/Linux hosts where `ecto_sqlite3` supports the pinned dependency set, then run the same golden operations and canonical result assertions through packaged Mob apps on physical iOS and Android.
- Assert runtime architecture on every target run: on-device BEAM/LiveView endpoint, two distinct SQLite paths, `Ecto.Adapters.SQLite3`, `pool_size: 1`, CatalogRepo query-only, UserRepo writable/migrated, and no Netlify/remote app-server dependency.
- Seed a representative M03 catalog and a UserRepo with at least 10 vehicles, 10 years of monthly odometer readings, multiple effective usage profiles, 100 oil-change records per vehicle, forecast history, reminder rules, and scheduled notifications for stress — not product limits.
- Establish budgets in ADR before sign-off. Candidate starting budgets to measure/approve: warm vehicle-filter query p95 ≤100 ms; oil/filter first page p95 ≤200 ms; UserRepo write transaction p95 ≤150 ms; cold two-repo boot plus no-op migration p95 ≤1 s after an already-installed catalog; bundled first-install/upgrade gets its own time/space budget; peak memory and installed bytes fit the lowest supported physical device. Replace candidates only with measured product-approved values.
- Validate deterministic ordering/pagination, Ecto-generated SQL/query plans, no N+1 scans, catalog immutability, transaction rollback, boot migration matrix, bundle install/rollback, export/import, catalog-snapshot continuity, forecast lineage, notification reconciliation, and multi-vehicle isolation.
- Exercise graceful background/foreground, force-kill during reads/writes/migration/catalog activation, rapid relaunch, device reboot, OS update where practical, timezone change, low storage, permission/I/O errors, and airplane-mode first launch/relaunch.
- Run privacy/network audit with platform packet capture/instrumentation: no user-data request or remote runtime dependency; no VIN/event/nickname/notes/native path in logs; no provider credentials/raw licensed payloads in the app bundle. Netlify is tested only as a static site and is not contacted by M04 core flows.
- Corruption drills distinguish catalog recovery (reinstall from current app bundle or roll back to retained catalog/manual entry) from user recovery (verified local backup/export/recovery UI); never discard UserRepo to repair CatalogRepo.
- Run a 24-hour physical-device offline soak and collect signed sign-off from QA, engineering, product, and data owners.

## Excluded

- PWA/browser/OPFS/IndexedDB/WASM or adapter matrices; treating simulator/emulator/host results as sufficient target evidence; online catalog update/signature tests (M08); relaxing correctness for latency without reviewed change; telemetry upload in offline-only scope.
- Building new product features or fixing certified components beyond gate-blocking defects (defects route back to their owning issue; this gate re-runs).

## Functional requirements

- FR-1: Black-box contract suites at the Ecto/context boundary exist for both repos and run identically on supported macOS/Linux hosts (where `ecto_sqlite3` supports the pinned set) and through packaged Mob apps on physical iOS and Android, with canonical result assertions.
- FR-2: Every target run asserts the runtime architecture: on-device BEAM/LiveView endpoint, two distinct SQLite paths, `Ecto.Adapters.SQLite3`, `pool_size: 1`, CatalogRepo query-only, UserRepo writable/migrated, no Netlify/remote app-server dependency.
- FR-3: The stress seed comprises a representative M03 catalog plus a UserRepo with at least 10 vehicles, 10 years of monthly odometer readings, multiple effective usage profiles, 100 oil-change records per vehicle, forecast history, reminder rules, and scheduled notifications — documented as stress fixtures, not product limits.
- FR-4: Budgets are established in an ADR before sign-off, starting from the candidate values (warm vehicle-filter query p95 ≤100 ms; oil/filter first page p95 ≤200 ms; UserRepo write transaction p95 ≤150 ms; cold two-repo boot plus no-op migration p95 ≤1 s after an already-installed catalog; dedicated bundled first-install/upgrade time/space budget; peak memory and installed bytes fitting the lowest supported physical device) and replaced only with measured product-approved values.
- FR-5: The validation matrix covers deterministic ordering/pagination, Ecto-generated SQL/query plans, no N+1 scans, catalog immutability, transaction rollback, boot migration matrix, bundle install/rollback, export/import, catalog-snapshot continuity, forecast lineage, notification reconciliation, and multi-vehicle isolation.
- FR-6: The lifecycle/fault matrix covers graceful background/foreground, force-kill during reads/writes/migration/catalog activation, rapid relaunch, device reboot, OS update where practical, timezone change, low storage, permission/I/O errors, and airplane-mode first launch/relaunch.
- FR-7: The privacy/network audit uses platform packet capture/instrumentation and proves: no user-data request or remote runtime dependency; no VIN/event/nickname/notes/native path in logs; no provider credentials/raw licensed payloads in the app bundle; Netlify uninvolved in app readiness.
- FR-8: Corruption drills prove catalog recovery (reinstall from current app bundle or roll back to retained catalog/manual entry) is distinct from user recovery (verified local backup/export/recovery UI) and that UserRepo is never discarded to repair CatalogRepo.
- FR-9: CI/device-lab output is keyed by app build, Mob/Ecto/ecto_sqlite3/SQLite versions, user schema, catalog/schema, Repo, OS version, physical device model/class, and test seed; reports include runtime Repo assertions, canonical hashes, query plans, latency/memory/storage samples, lifecycle/fault phase, and redacted errors; runs fail on absolute budget violations or statistically material regression per the approved ADR.
- FR-10: A 24-hour physical-device offline soak across background, force-kill/relaunch, and reboot preserves the exact UserRepo canonical hash and valid catalog checksum/integrity.
- FR-11: QA, engineering, product, and data owners sign the release evidence; unresolved waivers carry an owner and expiry.

## Technical implementation contract

### Components and ownership boundaries

- A certification harness (test runner + device-lab orchestration) owns suite execution, measurement capture, and report generation; it consumes — never reimplements — the contract suites from `DOS-M04-004/005`, migration matrix from `DOS-M04-007`, installer matrix from `DOS-M04-008`, and export/import suite from `DOS-M04-009`.
- The budgets ADR is owned jointly by engineering and product; QA owns matrix execution and evidence assembly; data owners review catalog-related results.
- Defects found here are filed against the owning M04 issue; this gate re-runs after fixes.

### Data and persistence

- Stress fixtures per FR-3, generated deterministically from a recorded test seed; synthetic and license-clean where the representative M03 catalog is not yet fully licensed.
- Canonical hashes: a documented canonicalization (stable ordering/encoding) over UserRepo entities producing the before/after hashes used in soak, fault, and corruption comparisons.
- Evidence artifacts are stored with the FR-9 key set so any measurement is reproducible against exact versions.

### Interfaces and events

- The harness drives the app strictly through the public Ecto/context boundary (black-box) plus documented test hooks for fault injection; no private SQL shortcuts.
- Report format: machine-readable results (per-suite pass/fail, samples with percentiles, assertion outputs) plus a human sign-off sheet; regression comparison is automated against the previous accepted baseline.
- Budget violations and material regressions fail the run automatically per the ADR's statistical rules.

### Failure and recovery behavior

- The gate itself must be re-runnable: any failed/aborted campaign can restart from a clean seeded state without hand-cleanup.
- Fault-injection phases verify the recovery behaviors certified in `DOS-M04-006/007/008` end-to-end in one packaged app rather than in isolation.
- A failed certification blocks release; there is no waiver path without owner and expiry recorded (FR-11).

### Security and privacy

- Packet capture/instrumentation proves zero user-data egress and no remote runtime dependency in M04 core flows.
- Log audit proves no VIN/event/nickname/notes/native path appears; bundle audit proves no provider credentials or raw licensed payloads are packaged.
- Evidence artifacts themselves are redacted (no user-like content beyond synthetic fixtures; no raw paths).
- Netlify is exercised only as a static site, and app readiness is demonstrated with it unreachable.

### Accessibility and performance

- This issue is the performance authority for M04: it measures and enforces the approved absolute size/latency/memory/first-install budgets on the lowest supported physical devices and records raw samples, exact catalog/user fixture sizes, and pinned runtime versions. Accessibility is out of scope here (owned by M02/M05/M07 UI issues).

## UX and content states

N/A — certification gate with no end-user UI of its own. It exercises the recovery/readiness states other issues define (recovery UI, catalog-unavailable fallback, export flows) as test subjects.

## Test plan

### Automated

- Host execution of both black-box contract suites (pinned dependency set) with canonical result assertions and golden snapshots.
- Automated device-lab campaigns: same suites through packaged apps; runtime architecture assertions per run; latency/memory/storage sampling with percentile computation; query-plan and N+1 checks on Ecto-generated SQL.
- Automated fault campaigns: kill-point schedules across reads/writes/migration/catalog activation; low-storage simulation; permission/I/O error injection; timezone-change scripts.
- Automated regression comparison against the accepted baseline per the budgets ADR statistical rules.
- Bundle content scan (no credentials/raw licensed payloads) and log-redaction scan.

### Manual/device matrix

- Minimum supported physical iOS device class and minimum supported physical Android device class (every class listed by the release matrix):
  - Airplane-mode first launch and relaunch; graceful background/foreground; rapid relaunch; device reboot; OS update where practical.
  - 24-hour offline soak with scheduled background/kill/reboot events; before/after canonical hash and catalog checksum comparison.
  - Corruption drills for both databases per FR-8.
  - Packet capture/instrumentation session covering all M04 core flows.
  - Sign-off review meeting: QA, engineering, product, and data owners walk the evidence and sign or record waivers with owner and expiry.

## Rollout and rollback

This gate does not roll out code; it gates the release train. Pass → the M04 epic can close and dependent release work may proceed, with the accepted measurements becoming the regression baseline. Fail → the release is blocked, defects route to their owning issues, and the gate re-runs after fixes. There is no partial pass; waivers require owner and expiry and are visible in the signed evidence.

## Dependency rationale

Blocked by all other `DOS-M04-*` issues (`DOS-M04-001` through `DOS-M04-009`) because it certifies their combined behavior as one packaged system rather than in isolation, and by `DOS-M03-010` because it consumes the exact application-bundled release candidate — certifying against anything else would certify a different product. Per the required dependency order, cross-platform certification completes last: "only then close both epics." It unblocks the M04 epic exit, and its budgets ADR becomes the measurement baseline for M05–M07 performance work.

## Risks, decisions, and open questions

- Risk: device-lab flakiness masquerading as regressions. Mitigation: FR-9 keying, deterministic seeds, statistical regression rules in the ADR, and re-runnable campaigns.
- Risk: candidate budgets prove unrealistic on the lowest devices. Mitigation: budgets are replace-only-with-measured-product-approved values; correctness is never relaxed for latency without reviewed change.
- Risk: 24-hour soak scheduling on shared devices. Mitigation: soak automation with event scheduling; the soak is mandatory (AC-3) and planned early in the campaign.
- Decision (ADR, this issue): final absolute budgets and the statistical materiality rule for regressions.
- Decision: the exact minimum supported device classes list (inherited from the release matrix; recorded in the evidence key).
- Open question: OS-update-during-soak practicality per platform — "where practical" is resolved per device class and documented in the matrix report.
