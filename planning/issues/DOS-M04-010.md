> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and functional requirements below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Replace physical-device budgets with browser/engine conformance and server budgets, and add quota-exhaustion, eviction, private-browsing, and multi-tab conformance cases that did not exist on device._

## Outcome

A release-evidence certification gate proves that the hosted browser MVP — Phoenix LiveView on Fly.io, backed by exactly one read-only `CatalogRepo` baked into the deploy image, with all personal data held only in the user's anonymous IndexedDB — is deterministic, honestly-degrading, and internet-facing-safe. The gate does not re-run the underlying suites; it composes and signs off on release evidence assembled by three peer M09 issues (browser/engine conformance from `DOS-M09-009`; internet-facing hardening and the provable absence of any server-side personal record from `DOS-M09-008`; deploy provenance — image digest, baked catalog `data_version`, immutable Fly release ID, rehearsed one-command rollback — from `DOS-M09-006`), together with a **browser/server budgets ADR** promoting Constitution 2.0.0 §9 *provisional* targets to accepted values against measured data. Its output is a signed release checklist that either promotes a Fly release to production or blocks it.

## Why this matters and what it unblocks

Under ADR-0004 the M04 exit gate is no longer "does the packaged native app survive kill/reboot/low-space." It is: **does the deployed browser application (a) hold zero personal rows on the server, (b) hydrate honestly across the browser/engine matrix in the presence of quota exhaustion, ITP-style eviction, private-browsing refusal, and multi-tab writes, (c) meet the re-ratified §9 budgets, and (d) roll back cleanly on the Fly release channel?** Those four questions are what the browser MVP actually risks; nothing else is the exit gate.

Making this the composition-and-sign-off card rather than a suite re-runner has three consequences. First, it keeps the sign-off aligned with where the work actually lives (M09-006/008/009) instead of duplicating those suites here. Second, it preserves the pre-pivot obligation that final budgets are ratified in an ADR **before** sign-off — the "budgets ADR before sign-off" rule survives, now as a browser/server budgets ADR under Constitution 2.0.0 §9. Third, it gives the closing act of the M04 epic a clear, single-page output: a signed release checklist tied to an immutable Fly release ID, with any waiver carrying owner and expiry.

It gates public launch (`DOS-M07-007` re-scoped: staged Fly deploys, custom-domain cutover, canary, monitoring, rehearsed rollback), and the accepted §9 measurements become the regression baseline for `DOS-M06-*`, `DOS-M07-003` (re-scoped page-load / hydration / round-trip / server-memory-per-socket / IndexedDB-footprint budgets), and `DOS-M07-004` (re-scoped browser/engine/OS QA matrix). It does not run any single-vehicle or forecast flow itself; those belong to their owning cards.

## Technical implementation contract

### Components and ownership boundaries

- **Certification harness** (test runner + browser orchestration + evidence assembler): owns evidence composition and report generation. It **consumes — never reimplements** the suites from `DOS-M09-006` (deploy provenance), `DOS-M09-008` (hardening + no-server-side-personal-record proof), `DOS-M09-009` (browser matrix + storage-behavior conformance), the re-scoped `DOS-M04-004` (deterministic server-side `CatalogRepo`), `DOS-M04-008` (atomic catalog activation across a Fly release), and `DOS-M04-009` (export/import/erasure). It runs the FR-10 hosted soak because that is the only cross-suite exercise that must span a real deploy.
- **Browser/server budgets ADR** — jointly owned by engineering and product; QA owns matrix execution and evidence assembly; data owners review catalog-related results.
- **Defects** found here are filed against the owning M09 or M04 issue; this gate re-runs after fixes on a new Fly release.

### Data and persistence

- The server-side artifact under certification is the read-only `CatalogRepo` file baked into the Fly release image (from re-scoped `DOS-M03-010` / `DOS-M04-008`); it is not written to at runtime. The evidence records image digest, catalog `data_version`, and payload SHA-256.
- The client-side stress fixture (FR-3) is generated by the certification harness via a scripted browser session using the IndexedDB schema and adapter from `DOS-M09-001` / `DOS-M09-002`, seeded from a recorded test seed for determinism and license-clean where the representative catalog is not fully licensed. **The server persists none of it** by definition (INV-3, ADR-0004 Decision 4).
- Canonical hashes: the FR-10 soak uses the client-side export SHA-256 (from `DOS-M04-009` re-scoped) taken over the seeded fixture before and after the soak; equality is required. There is no server-side canonical hash because there is no server-side personal record.
- Evidence artifacts are stored with the FR-1 key set so any measurement is reproducible against exact versions.

### Interfaces and events

- The harness drives the deployed application through the public LiveView routes and hooks (black-box), plus documented harness-only fault-injection hooks (`QuotaExceededError` throw in the storage adapter, forced `BroadcastChannel` message, forced `ITP eviction` fake). No private endpoints, no test-only server routes, no personal-data server tables added for testing.
- Report format: machine-readable per-suite pass/fail with sample percentiles, assertion outputs, matrix cells, and referenced evidence blobs, plus a human sign-off sheet; automated regression comparison against the previous accepted baseline per the browser/server budgets ADR statistical rule.
- Budget violations and material regressions fail the run automatically.

### Failure and recovery behavior

- The gate itself is re-runnable: a failed/aborted campaign restarts against a clean synthetic browser and fresh IndexedDB without hand-cleanup, and the certification harness is idempotent per Fly release ID.
- A failed certification blocks release; there is no waiver path without owner and expiry recorded on the signed sheet (FR-11).
- The rehearsed one-command Fly rollback (from `DOS-M09-006`) is exercised as part of the evidence; the harness confirms the previous release ID and the previous baked catalog `data_version`/payload SHA-256 are what the deployed application reports after rollback.

### Security and privacy

- The gate's own evidence collection MUST NOT persist any user-shaped payload beyond the synthetic fixture; captured logs are already redacted at source per ADR-0004 §"Logging"; evidence storage is scoped to non-personal, release-keyed artifacts.
- The internet-facing hardening evidence is composed from `DOS-M09-008`; this card does not re-implement any transport, session, CSP, CSRF, origin, or rate-limit rule but requires all of them present in the evidence for sign-off.
- INV-27 boundary is verified by the FR-7 evidence: Fly serves the application and its socket; Netlify (team `cDiscourse`) serves only static marketing/support/privacy/attribution and is not contacted from the running application.

### Accessibility and performance

- This card is the **performance authority for the browser MVP**: it measures and enforces the §9 rows the budgets ADR promotes to accepted values and records raw samples, exact fixture sizes, and pinned runtime/browser/engine versions. Accessibility for the running application is the concern of re-scoped `DOS-M02-002` and `DOS-M07-002` (WCAG 2.2 AA verified against a named browser AT matrix); this card ratifies WCAG-2.2-AA-row conformance by reading their evidence rather than reproducing the audit.

## Test plan

### Automated

- Evidence-composition job: for a given immutable Fly release ID, fetch and validate all artifacts from `DOS-M09-006`, `DOS-M09-008`, and `DOS-M09-009`; fail if any is missing, stale (keyed to a different release), or does not match the FR-1 key set.
- Runtime architecture assertion job (FR-2): a smoke test executed against the deployed application asserting the repo list, the read-only open mode, the absence of a `UserRepo` module, the static domain-purity check, and that no domain module references `Phoenix.LiveView`, `Plug`, or `LocalStore`.
- Hosted uptime and reconnect soak (FR-10 / AC-3): a synthetic connected browser holds one LiveView session with a seeded IndexedDB for 24 hours, scripted to survive at least one Fly deploy; the harness records reconnect count, remount count, hydration duration percentiles, `meta.seq` progression across the deploy boundary, and asserts the before/after export SHA-256 equality.
- Regression comparison against the previous accepted baseline per the browser/server budgets ADR statistical rule.
- Redaction and no-third-party-origin scans applied to the first-visit payload and to captured logs.

### Manual / browser matrix

## Rollout and rollback

This gate does not roll out code; it gates the Fly release channel for public launch and post-launch releases. Pass → the Fly release is authorized for promotion by `DOS-M07-007` (re-scoped), and the accepted §9 measurements become the regression baseline for `DOS-M06-*`, `DOS-M07-003`, and `DOS-M07-004`. Fail → the release is blocked, defects route to the owning M09 or M04 issue, and the gate re-runs on a new release. There is no partial pass; waivers require owner and expiry and are visible on the signed sheet. The gate's own rollback path is: re-open the signed checklist, mark the waiver expired, and re-run the composition.

## Risks, decisions, and open questions

- Risk: harness flakiness in a synthetic connected browser (network jitter, remote DevTools disconnect) masquerading as budget regressions. Mitigation: FR-1 keying, deterministic seeds, statistical materiality rule in the budgets ADR, and re-runnable campaigns.
- Risk: candidate §9 rows prove unrealistic over the public internet from `ord` to a coast (ADR-0004 R9, "LiveView is latency-multiplying"). Mitigation: rows are replace-only-with-measured-product-approved values; correctness is never relaxed for latency without a reviewed change; a second Fly region is a bounded cost decision that could be exercised if a matrix cell demonstrates the need (ADR-0004 §"Region").
- Risk: 24-hour soak scheduling around Fly deploys is coupled to release cadence. Mitigation: soak automation with event scheduling; the soak is mandatory (AC-3) and planned early in the campaign; a deploy is deliberately scheduled inside the soak window to exercise ADR-0004's "deploys drop every WebSocket" case.
- Risk: browser-vendor eviction behavior (ADR-0004 R1) is documentation-driven, not measured, and the 7-day ITP window cannot be honestly simulated in a single 24-hour soak. Mitigation: `DOS-M09-009` owns the elapsed-time simulation of ITP-style eviction and its conformance row is composed here; a real-world eviction observation is an open post-MVP obligation.
- Risk: a future change accidentally introduces a `UserRepo`, a personal-data table, or a domain-namespace dependency on `Phoenix.LiveView`. Mitigation: FR-2 assertions are re-run on every release and fail the gate; the same static/database-schema checks live in `DOS-M09-008` as CI gates so a broken release never reaches this gate in the first place.
- Decision (browser/server budgets ADR, this card's own deliverable): final accepted §9 values and the statistical materiality rule for regression comparison.
- Decision (recorded in the evidence key): the exact browser/engine matrix inherited from `DOS-M09-009` and the `fly.toml` snapshot inherited from `DOS-M09-006`.
- Open question: whether a scheduled cadence of hosted uptime soaks (weekly? per release?) is warranted post-launch; deferred to release-operations follow-up on `DOS-M07-007` evidence.
