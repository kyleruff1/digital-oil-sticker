## Outcome

A first-time user can install the native Digital Oil Sticker app, select one exact vehicle from the bundled catalog without a network connection, save one local vehicle profile, record an oil change and odometer readings, and understand the vehicle's current time/mileage service position. No sign-in, cloud database, remote profile, or network dependency is allowed in the core journey.

This epic tracks milestone M05 — Single-vehicle offline MVP and closes only when the epic exit gate is fully satisfied: all seven M05 child issues are closed; a clean iOS or Android device can complete the scripted first-run-to-dashboard flow in airplane mode immediately after installation; an existing user can cold-start and read/edit data offline; no request containing user or vehicle data leaves the device; and destructive actions are recoverable until explicitly confirmed.

## Why this matters and what it unblocks

M05 converts the certified M04 persistence layer and the M02 UX/content contract into the first end-to-end user-visible product slice: the digital oil sticker itself. Until this milestone closes, nothing proves that the local-first architecture (Mob LiveView on-device, dual SQLite repositories, loopback-only Phoenix Endpoint) actually delivers the product mission of an accurate, explainable oil-service record that works with no account and no network.

Closing this epic unblocks M06 (forecasting and reminders), which extends the M05 dashboard presentation contract with the estimated mileage due date and locally scheduled notifications, and it feeds the M07 hardening/release gates. DOS-M05-006 specifically blocks DOS-M07-003, DOS-M07-004, DOS-M07-007, and production release; DOS-M05-007 blocks beta/release readiness in DOS-M07-001 and DOS-M07-004 and the M08 migration.

## Included

The seven child issues of this epic (add each to this epic's task list):

- DOS-M05-001 — Integrate the M04 dual-repository domain contract into the single-vehicle runtime: context wiring, one-active-vehicle enforcement, snapshots, idempotency, and error mapping.
- DOS-M05-002 — Build offline exact-vehicle search and selection: progressive Year → Make → Model → Variant filtering and text search over the installed catalog, entirely offline.
- DOS-M05-003 — Create and edit the local vehicle and maintenance-basis profile: nickname, odometer, units, usage classification, and an explicit sourced-or-custom interval basis with provenance.
- DOS-M05-004 — Record oil changes and odometer readings as an auditable local history: add/correct/delete with timeline constraints, undo, and forecast-staleness invalidation.
- DOS-M05-005 — Deliver the single-vehicle digital oil sticker dashboard: latest service, deterministic interval targets, current recorded odometer, and honest missing-data states.
- DOS-M05-006 — Package and boot the Mob LiveView application reliably offline: reproducible Mob 0.7.20 builds, loopback Endpoint, boot coordination, and upgrade preservation.
- DOS-M05-007 — Provide local export, import, reset, and recovery controls: versioned JSON export with checksums, two-phase validated import, and verified reset.

Also included at the epic level: the scripted first-run-to-dashboard airplane-mode flow definition used by the exit gate, and aggregation of child evidence into the milestone closure record.

## Excluded

Epic non-goals, preserved verbatim from the catalog: multiple saved vehicles, background/push synchronization, cloud backup, VIN decoding at run time, automatic odometer/telematics integration, oil-life-monitor integration, automatic notification delivery, and catalog updates after installation. Those capabilities must not be implied by MVP copy.

Additionally excluded per the frozen scope boundaries (§5): predictive usage date and reminder scheduling (M06), data-quality sign-off and release hardening (M07), multi-vehicle UI, signed catalog updates, VIN scan, browser/PWA product, and all cloud/social/commerce features (M08 or out of scope entirely).

## Functional requirements

Entry and exit gate conditions for the milestone:

- FR-1 (entry): No M05 child issue starts before its catalog-stated blockers are closed; DOS-M05-001 is the internal root that gates DOS-M05-002 through DOS-M05-007.
- FR-2 (exit): A clean iOS or Android device completes the scripted first-run-to-dashboard flow — install, first launch, vehicle selection, profile save, oil-change record, odometer reading, dashboard read — in airplane mode immediately after installation.
- FR-3 (exit): An existing user with populated data can cold-start the app and read and edit that data offline.
- FR-4 (exit): No request containing user or vehicle data leaves the device during the scripted flows; the only network traffic in scope is device-loopback WebView-to-Endpoint traffic.
- FR-5 (exit): Every destructive action in the MVP (vehicle replacement, history delete, reset, import-replace) is recoverable until explicitly confirmed.
- FR-6 (exit): Every child issue is closed with all acceptance criteria checked and the listed evidence attached to the issue or linked from CI; a child is not done because code exists.
- FR-7 (exit): MVP copy nowhere implies an epic non-goal capability (accounts, sync, cloud backup, VIN decode, telematics, OLM integration, push delivery, or post-install catalog updates).

## Risks, decisions, and open questions

- Risk: Mob is pre-1.0 (pinned 0.7.20); packaging/boot behavior may shift under OS updates. Mitigated by the pinned toolchain and the ADR required in DOS-M05-006.
- Risk: catalog size or quality issues discovered during full-size search/performance fixtures could bounce work back to M03; treat as new issues, not scope creep.
- Decision recorded: forecasting and notification scheduling are deliberately absent from M05 surfaces; the dashboard shows deterministic thresholds only (DOS-M05-005) until M06 lands.
- Open question tracked in DOS-M05-007: the reminder-cancellation portion of reset depends on DOS-M06-005 and must not stall the rest of that issue.
