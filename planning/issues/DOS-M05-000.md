## Outcome

A first-time user visits `https://digitaloilsticker.com`, sees the pre-hydration skeleton, and — once the browser reports that IndexedDB is available — is guided through selecting one exact vehicle from the server-queried catalog, saves a single vehicle profile into their browser's own IndexedDB store, records an oil change and an odometer reading, and reads the vehicle's current time/mileage service position on a single-vehicle dashboard. All personal data (garage, service events, odometer readings, reminder intent, preferences) stays in the origin-scoped `dos_local` IndexedDB database on that browser; the Fly.io-hosted Phoenix LiveView server holds it only in `socket.assigns` for the lifetime of one WebSocket and never writes a personal row to disk, database, cache, or log. There are no accounts, no sign-in, no cloud sync, no server-side per-user record of any kind, and no third-party analytics or trackers. Versioned JSON export/import is the sole portability and recovery path.

This epic tracks milestone M05 — Single-vehicle browser MVP and closes only when the epic exit gate is fully satisfied: all seven M05 child issues are closed; a clean browser session on the supported matrix (INV-24.6, `CONSTITUTION.md` §9 browser matrix) can complete the scripted first-visit-to-dashboard flow against the deployed application; a returning user with populated `dos_local` records can reconnect and re-hydrate without seeing a false empty-garage flash; every mutation completes the `local_store:put` → `local_store:ack` round trip before being rendered as saved; the storage-unavailable, `:data_missing`, quota-exhausted, and stale-schema states from ADR-0004 §"First-paint and empty-state rules" and §"Quota and eviction" render as their own honest states (not as errors or empty states); and no request or log line contains VIN, odometer, service date, note text, custom vehicle name, or any hydration/mutation payload fragment.

## Why this matters and what it unblocks

M05 is the milestone where the vendored catalog and the domain contexts written for it become a user-visible product. Until this epic closes, nothing proves that the seam ADR-0004 introduces — LiveView server-side rendering over anonymous client-side storage, joined by the INV-24 hydration protocol — actually delivers a usable, honest oil-service record without ever writing a personal row on the server.

The dependency graph after the pivot: M05 is now built directly on the M09 platform work (`DOS-M09-001` browser storage schema, `DOS-M09-002` storage adapter, `DOS-M09-003` hydration protocol, `DOS-M09-005` catalog query layer, `DOS-M09-006` Fly deploy pipeline), the M02 web-first UX contract, and the M04 rescoped persistence layer (server `CatalogRepo` read-only + client `UserStore` in IndexedDB). It supplies the product surface that M06 (forecasting + in-app due state; OS notifications deferred with M06's own rescope) extends, and it feeds the M07 hardening/release gates whose threat model was rewritten against a public host. `DOS-M05-006` (rescoped to the Fly deploy-and-boot contract) blocks the release gates in `DOS-M07-005` and `DOS-M07-007`; `DOS-M05-007` (export/import/reset) blocks `DOS-M07-004` and the M08 multi-vehicle activation.

## Technical implementation contract

### Components and ownership boundaries

N/A — epic-level tracking issue. Component ownership is defined per child; the binding map after the pivot is:

- **Server (Elixir, hosted on Fly.io `ord` region, single machine, `min_machines_running = 1`)** — `DigitalOilSticker.Catalog` context, `.Garage`, `.Forecast`, and the resolver, each client-agnostic per ADR-0004 §Decision item 6; `DigitalOilSticker.CatalogRepo` opened read-only against the SQLite baked into the deploy image; the LiveView(s) that hold user state in `socket.assigns` only.
- **Client (browser, JS)** — the `LocalStore` `phx-hook` from ADR-0004 §"The client-storage + LiveView hydration protocol", which owns `dos_local` IndexedDB opens/upgrades, hydration reads, mutation writes with compare-and-set on `meta.seq`, `BroadcastChannel("dos_local_store")` multi-tab coordination, and export/import file handling.
- **What the pre-pivot spec named (`DeviceCommandBroker`, `MobScreen`, `Mob.Socket`, on-device dual SQLite, loopback `Endpoint`) does not exist in the browser MVP** and is retired for this epic; those design artifacts are preserved in ADR-0001 (deferred) for the future native track.

### Data and persistence

N/A — epic-level tracking issue. The rescoped data contract is fixed by `DOS-M04-001` (dual-persistence ADR: server `CatalogRepo` + browser `UserStore`) and enforced by `DOS-M05-001`. Client storage layout is ADR-0004's `dos_local` object stores (`meta`, `vehicles`, `events`, `readings`, `reminders`, `prefs`). Server-side, exactly one Ecto repo (`CatalogRepo`) is opened read-only; no `UserRepo` is deployed.

### Interfaces and events

The `LocalStore` protocol events are normative:

- `local_store:hydrate` (client → server): the ADR-0004 envelope `{envelope: "dos_local", schema_version, seq, tab_id, generated_at, data: {vehicles, events, readings, reminders, prefs}}`. Server validates per ADR-0004 §"Validation" and moves `assigns.local_state` to `:loaded` / `:empty` / `:data_missing` / `:storage_unavailable`.
- `local_store:put` (server → client): `{mutation_id, seq, upserts: [...], deletes: [...]}` applied by the hook in one `readwrite` transaction with compare-and-set on `meta.seq`.
- `local_store:ack` (client → server): `{mutation_id, seq, status: "ok" | error tag}` — server does not render "saved" until ack.
- `local_store:conflict` (client → server): compare-and-set failure; server discards its optimistic assign and re-hydrates.
- Domain events (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`) fire in `socket.assigns` and drive UI updates; they never persist server-side.
- Catalog queries (`vehicle_search`, `vehicle_resolve`, `requirement_lookup`) go through `DOS-M09-005` and MUST obey INV-26 (impersonal — no VIN, no odometer, no note, no stable client identifier).

### Failure and recovery behavior

N/A — epic-level tracking issue, except that the exit gate requires child-level failure states to be demonstrated before closure: hydration deadline expiry → `:storage_unavailable`; `had-data-now-empty` → `:data_missing`; `QuotaExceededError` → visible failure with prior state preserved and export offered; stale server version vs. client `schema_version` → read-only mode with banner; ack timeout → "Not saved to this browser" state on the affected record with the optimistic value visibly marked unsaved; `BroadcastChannel` unavailable → degraded to per-mount hydration only with compare-and-set still preventing lost updates.

## Risks, decisions, and open questions

- **Risk (R1 from ADR-0004):** browser eviction of infrequently-used site storage. A user who checks their oil once a quarter is exactly the profile most at risk. Mitigations bind at this milestone: `navigator.storage.persist()` requested on first meaningful write; honest storage-status UI; export nudges after meaningful writes; the `:data_missing` state so loss is never disguised as an empty garage. Per-browser eviction behavior MUST be measured, not assumed from documentation (the `DOS-M09-009` conformance suite covers this).
- **Risk (R2 from ADR-0004):** hydration round trip adds latency to first meaningful paint on every mount including every reconnect. Mitigation is the `DOS-M07-003` provisional time-to-hydrated budget and the ADR-0004 requirement that hydration is sub-second on a cold connection.
- **Risk (R4 from ADR-0004):** multi-tab conflict resolution is last-write-wins at record granularity with loss made visible. Accepted for MVP under the single-user assumption; re-examine on evidence.
- **Risk (R8 from ADR-0004):** single region, single always-on machine — Fly outage or zone failure = total product outage; deploys drop all sockets. Accepted at MVP; a second machine is a bounded cost decision deferred. Reconnect + re-hydration MUST be proven robust enough that a deploy is a non-event for users (FR-3).
- **Decision recorded:** forecasting and notification scheduling are deliberately absent from M05 surfaces; the dashboard shows deterministic thresholds only (`DOS-M05-005`) until M06 lands. OS-scheduled local notifications are amended out of MVP scope (INV-17); Web Push is deferred to `DOS-M09-010`.
- **Decision recorded:** the pre-pivot "airplane-mode after native install" exit gate is retired; ADR-0004 records that the browser MVP does not work offline at all and INV-6/INV-7 are amended accordingly. The gate is replaced by the four-hydration-state gate (FR-2, AC-2).
- **Open question tracked in `DOS-M05-007`:** whether import-merge semantics (as opposed to import-replace) need a second-tier conflict-preview UI at MVP or can defer to post-MVP with a clear "replace only" MVP framing.

### Outcome (superseded)

A first-time user can install the native Digital Oil Sticker app, select one exact vehicle from the bundled catalog without a network connection, save one local vehicle profile, record an oil change and odometer readings, and understand the vehicle's current time/mileage service position. No sign-in, cloud database, remote profile, or network dependency is allowed in the core journey.

This epic tracks milestone M05 — Single-vehicle offline MVP and closes only when the epic exit gate is fully satisfied: all seven M05 child issues are closed; a clean iOS or Android device can complete the scripted first-run-to-dashboard flow in airplane mode immediately after installation; an existing user can cold-start and read/edit data offline; no request containing user or vehicle data leaves the device; and destructive actions are recoverable until explicitly confirmed.

### Why this matters and what it unblocks (superseded)

M05 converts the certified M04 persistence layer and the M02 UX/content contract into the first end-to-end user-visible product slice: the digital oil sticker itself. Until this milestone closes, nothing proves that the local-first architecture (Mob LiveView on-device, dual SQLite repositories, loopback-only Phoenix Endpoint) actually delivers the product mission of an accurate, explainable oil-service record that works with no account and no network.

Closing this epic unblocks M06 (forecasting and reminders), which extends the M05 dashboard presentation contract with the estimated mileage due date and locally scheduled notifications, and it feeds the M07 hardening/release gates. DOS-M05-006 specifically blocks DOS-M07-003, DOS-M07-004, DOS-M07-007, and production release; DOS-M05-007 blocks beta/release readiness in DOS-M07-001 and DOS-M07-004 and the M08 migration.
