> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Integration now means wiring server catalog reads to hydrated client state held in assigns, rather than wiring two co-located on-device repos._

## Outcome

The single-vehicle browser MVP consumes exactly one server-side Ecto repo — `DigitalOilSticker.CatalogRepo`, opened read-only per [ADR-0004 §Decision item 4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision) — and treats the user's garage, service events, odometer readings, reminders, and preferences as anonymous browser-owned records held in origin-scoped IndexedDB per [ADR-0004 §Storage layout](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#storage-layout). All personal state on the server lives only as transient values in `socket.assigns`, hydrated per mount from the `LocalStore` JS hook and written back through the mutation round trip specified in ADR-0004. LiveViews call typed context APIs on `Catalog`, `Garage`, `Maintenance`, `Forecasting`, and `Reminders`; they never alias a repo, never open a Phoenix or Plug import inside domain code, and never treat any server-side store as authoritative for personal data. The hydration state machine (`:hydrating`, `:loaded`, `:empty`, `:data_missing`, `:storage_unavailable`) is the frame every downstream M05 screen renders inside.

## Why this matters and what it unblocks

Constitution 2.0.0 [INV-3](../../docs/product/CONSTITUTION.md), [INV-23](../../docs/product/CONSTITUTION.md), and [INV-24](../../docs/product/CONSTITUTION.md) collapse into one release-gating claim: the server holds nothing durable about the user, and the seam between LiveView-server-state and IndexedDB-client-truth is a specified protocol rather than implementation taste. This card is the first place that claim becomes executable code the rest of M05 depends on. Downstream, DOS-M05-002 (server-backed exact-vehicle search over CatalogRepo), DOS-M05-003 (create/edit vehicle through the mutation round trip), DOS-M05-004 (append-only oil-change and odometer history committed client-side), DOS-M05-005 (dashboard rendering the hydration state machine faithfully), and DOS-M05-007 (browser export/import as the sole recovery path) all read from the context APIs and the hydration contract this card wires. DOS-M06-002 and DOS-M06-003 (usage sampling and pure forecast recomputation) attach to the same event bus. DOS-M08-001 (multi-vehicle garage) later relies on the vehicle-scoped shape being present in the IndexedDB payload envelope from day one.

## Included

- Application-facing context APIs on `DigitalOilSticker.Catalog`, `Garage`, `Maintenance`, `Forecasting`, and `Reminders` that accept the hydrated `socket.assigns` view of the user's garage and return typed success/error results consumable by LiveViews without direct repo, SQL, LocalStore-hook, or IndexedDB knowledge.
- Server-side hydration ingress: a documented `handle_event("local_store:hydrate", envelope, socket)` shape that validates the envelope via an embedded-schema changeset per `schema_version`, migrates through the forward-only migration functions when needed, quarantines invalid records instead of failing the session, and sets `assigns.local_state` to one of `:loaded`, `:empty`, `:data_missing`, or `:storage_unavailable`.
- The server side of the mutation round trip: `mutation_id`, `seq`, `pending_writes`, `push_event("local_store:put", ...)`, and the `local_store:ack` / `local_store:conflict` handlers, wired end-to-end for at least one representative mutation per context (vehicle upsert, service-event append, odometer append, reminder-intent upsert, preferences upsert).
- Catalog-key + readable-snapshot resolution: when a user record references a catalog configuration, `Catalog` resolves it against `CatalogRepo` at render time and returns the resolved fields plus a `support_status` (per [INV-11](../../docs/product/CONSTITUTION.md)) that may legitimately come back `unsupported` after a catalog `data_version` bump; snapshots persisted in the client envelope keep history displayable when catalog rows disappear.
- The one-active-vehicle invariant enforced in `Garage` domain code, returning a typed `active_vehicle_exists` decision on a second create so the UI can render the replace/archive choice per INV-18; every vehicle-owned record still carries `vehicle_id` in the envelope so DOS-M08-001 can enable many vehicles by lifting a UI cap alone.
- Idempotency: mutating context APIs accept the `mutation_id` from the round trip; replaying the same `mutation_id` returns the previously computed result rather than producing a second write instruction.
- The reason-coded local event bus (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, `catalog_activated`) published after the client `ack` arrives — never on optimistic assign — carrying local stable IDs and reason codes, never display strings.
- Fixtures exercising `supported`, `partial`, and `manual` catalog states, plus fixtures for each hydration state (`:loaded`, `:empty`, `:data_missing`, `:storage_unavailable`) so every downstream M05 issue renders the same vocabulary.
- The release-gating [ADR-0004 §Enforcement](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#enforcement) checks landed as CI: the repo-list test, the domain-namespace static check, the scripted-session log-redaction test, and the hydration-idempotency test.

## Excluded

- Any `UserRepo`, any second Ecto repo of any kind, any server-side personal table, any server-side cache/ETS/DB entry keyed by user or session content, and any server-side write path for personal data — enforced by AC-7 below.
- Alias imports of `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules inside `Catalog`, `Garage`, `Maintenance`, `Forecasting`, or `Reminders` — enforced by AC-8 below to preserve ADR-0004 Decision §6 (native-client reuse).
- A silent fallback ladder from IndexedDB to `localStorage` or to server storage for records; `localStorage` is used only for the tiny non-personal boot hint per ADR-0004 §"Storage layout".
- Optimistic render as authoritative: mutations MUST NOT be shown as saved before the `local_store:ack` per [INV-24.2](../../docs/product/CONSTITUTION.md).
- Native OS local notifications, native platform storage adapters, and any bundled-catalog copy or activation flow — those are covered by the native re-entry set and by DOS-M04-008's re-scoped server-side activation contract, not here.
- PWA/service-worker offline behavior and Web Push — deferred, per [DOS-M09-010](DOS-M09-010.md); no code path in this card may imply either exists.
- Multi-tab conflict UX beyond the compare-and-set contract in ADR-0004 §"Multi-tab consistency"; deeper reconciliation is out of scope and recorded as an open question.

## Functional requirements

Every functional requirement below is browser-first. FRs FR-1 through FR-10 replace the pre-pivot FRs of the same numbers; the retired forms are preserved in "Superseded pre-pivot spec (historical record)" at the bottom of this file. The finding-addressing map is: findings (a), (b), (c) from the staleness sweep are addressed by FR-1/FR-3 (integration means server CatalogRepo + hydrated assigns + mutation round trip), FR-2 and the Data section (IndexedDB object stores per ADR-0004 §Storage layout), and AC-7 respectively.

- **FR-1** — Integration wires exactly one server-side repo (`CatalogRepo`, `ecto_sqlite3`, opened read-only per ADR-0004 Decision §4) into the `Catalog` context, plus the LiveView-side ingress and egress of the hydration protocol into `Garage`, `Maintenance`, `Forecasting`, and `Reminders`. There is no `UserRepo`, no second repo of any kind, and no server-side personal store. Domain context modules do not alias `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules, so a future native client can mount them behind a different storage adapter without a rewrite (ADR-0004 §Decision item 6). This FR replaces pre-pivot FR-1 (the "wire dual `CatalogRepo` and `UserRepo` in the same runtime" clause) and pre-pivot FR-9 (the "reuse M04's application-support paths, boot ordering, foreign-key pragmas" clause, which described an on-device UserRepo that no longer exists).
- **FR-2** — Personal data lives in the origin-scoped IndexedDB database `dos_local` (opened by the `LocalStore` hook) whose object stores are exactly `meta`, `vehicles`, `events`, `readings`, `reminders`, and `prefs` per [ADR-0004 §"Storage layout"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#storage-layout). Server-side domain code models the same records as embedded-schema structs held in `socket.assigns` for the socket lifetime only; no server persistence path may write them to disk, database, cache, ETS table, external store, or log ([INV-3](../../docs/product/CONSTITUTION.md), [INV-24.1](../../docs/product/CONSTITUTION.md), ADR-0004 Decision §4). This FR replaces pre-pivot FR-1's ten-`UserRepo`-tables list (`local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications`, `schema_events`) — the browser MVP holds the same information under the ADR-0004 §"Storage layout" object-store names and no others.
- **FR-3** — Mount is unhydrated. The server renders the shell with `assigns.local_state == :hydrating` and a skeleton (never an onboarding-from-zero flow) while the socket is disconnected; on connect it arms a `hydration_deadline` (default 5,000 ms). The `LocalStore` hook `mounted()` opens `dos_local`, runs any client-side IDB upgrade, reads all stores in one `readonly` transaction, and `pushEvent`s `local_store:hydrate` with the ADR-0004 payload envelope. `handle_event("local_store:hydrate", envelope, socket)` validates via an embedded-schema changeset per `schema_version`, migrates forward-only when needed and immediately `push_event`s `local_store:put` with the migrated payload, quarantines invalid records rather than failing, and sets `assigns.local_state` to `:loaded` or `:empty`. Deadline expiry sets `:storage_unavailable`; `dos_boot_state == "has_data"` with zero returned records sets `:data_missing`. These four post-hydration states are distinct and render differently — an empty-garage flash on a returning user is prohibited ([INV-24.3](../../docs/product/CONSTITUTION.md), [INV-25](../../docs/product/CONSTITUTION.md)).
- **FR-4** — Every mutation is a `pushEvent` → assigns update with `mutation_id` and `seq = current_seq + 1` recorded in `assigns.pending_writes` → `push_event("local_store:put", …)` → hook `readwrite` transaction with compare-and-set on `meta.seq` → `local_store:ack` → server clears the pending write and publishes the reason-coded event on the local bus. No ack within 2,000 ms (or an error ack) renders a persistent, non-dismissible "Not saved to this browser" state on the affected record, keeps the optimistic value visible but marked unsaved, and surfaces export; the server does not retry silently and does not roll back invisibly ([INV-24.2](../../docs/product/CONSTITUTION.md), ADR-0004 §"Mutation round trip"). Replaying the same `mutation_id` after a reconnect or duplicate click returns the previously committed result rather than producing a second write instruction. This FR replaces pre-pivot FR-4 (Ecto.Multi across two Repos) and pre-pivot FR-6 (server-side idempotency tokens on LiveView submit paths).
- **FR-5** — After the client `ack` arrives, the local event bus publishes reason-coded events (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, `catalog_activated`) via direct context return plus Phoenix PubSub where multiple in-socket processes must react. Payloads carry the client-generated stable IDs (UUIDv4) written into IndexedDB and reason-code atoms only — never display strings, never any value derived from VIN, odometer, dates, note text, or custom vehicle names ([INV-4](../../docs/product/CONSTITUTION.md), Logging rules in ADR-0004 §"Logging"). Events fire on `ack`, not on optimistic assign.
- **FR-6** — Reconnect is a first-class case. `LiveView` reconnect discards assigns; the `LocalStore` hook re-hydrates on every `reconnected` event through the same protocol as first mount, and the server treats the reconnected socket as if it had never held state ([INV-24, general clause](../../docs/product/CONSTITUTION.md)). Any `pending_writes` still visible in the client (unwritten optimistic state that had never received an ack) are re-driven from the client's own storage — the browser is the source of truth. A deploy, a Fly.io machine replacement, or a secret rotation is therefore a data-loss-free event on the server side. This FR replaces pre-pivot FR-7 (which said "temporary socket/form state is disposable and app termination re-renders from `UserRepo`") — the browser-first equivalent is disposable socket state plus re-hydration from IndexedDB.
- **FR-7** — Multi-tab consistency uses `BroadcastChannel("dos_local_store")` plus compare-and-set on `meta.seq`. After any successful commit the writing tab broadcasts `{seq, mutation_id, tab_id}`; receiving tabs whose stored `seq` is behind trigger a fresh `local_store:hydrate` on their own socket, and the losing side of a compare-and-set aborts with `local_store:conflict`, which the server responds to by discarding its optimistic assign, forcing re-hydration, and surfacing a visible "reloaded from this browser's newer data" notice. Absence of `BroadcastChannel` (some private-browsing contexts) MUST degrade to per-mount hydration only while the compare-and-set still prevents lost-update corruption ([INV-24.7](../../docs/product/CONSTITUTION.md)).
- **FR-8** — Domain errors map to the frozen typed vocabulary consumed by every M05/M06 UI state: `:validation`, `:not_found`, `:stale_revision`, `:active_vehicle_exists`, `:catalog_unavailable`, `:catalog_replaced`, `:snapshot_stale`, `:storage_unavailable`, `:storage_evicted`, `:quota_exceeded`, `:hydration_failed`, `:client_write_failed`, `:conflict_seq_mismatch`, and `:schema_version_ahead` (the last covering a client payload from a newer app deployment, which per ADR-0004 §"Schema versioning and migration" MUST render a read-only banner rather than downgrade). Raw Ecto or IndexedDB error text never surfaces to the user and never enters a log at info-or-above severity. This FR replaces pre-pivot FR-8's disk-full/corruption/migration-recovery vocabulary with the browser-storage vocabulary that actually applies.
- **FR-9** — Catalog resolution is impersonal. `Catalog` context functions accept catalog reference keys (year/make/model/configuration/`configuration_key`, catalog `data_version`) and free-text search input, and MUST NOT accept VIN, odometer values, dates, note text, custom vehicle names, `tab_id`, or any value that could correlate one visit to another ([INV-26](../../docs/product/CONSTITUTION.md), [DOS-M09-005](DOS-M09-005.md)). Snapshots of resolved catalog fields (`support_status`, display strings, `data_version`) are returned to the caller so the LiveView can write them into the IndexedDB envelope for provenance-preserving history; a subsequent catalog `data_version` bump that removes the row still lets history render, and MAY legitimately return `unsupported` per [INV-11](../../docs/product/CONSTITUTION.md).
- **FR-10** — Units and time carry the same physical contract as before, adjusted for the new host: mileage persists as the canonical integer base unit inside the envelope (unit conversion happens at LiveView boundary), and instants persist as UTC ISO-8601 plus an IANA time-zone identifier stored in `prefs`, so a user changing units or time zones never loses precision. Server-side rendering derives every displayed number from these canonical values on each mount; there is no per-user server-side derived table (that would violate FR-2).

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Catalog` — the sole module that opens `CatalogRepo`. Every other domain and LiveView caller uses `Catalog.*` functions with catalog reference keys and free-text search only (FR-9). No side effects, no writes.
- `DigitalOilSticker.Garage` — owns local-profile and vehicle lifecycle over the hydrated assigns view: create, edit, archive, one-active-vehicle enforcement (FR-3 UX outcome), and the `vehicle_saved` event emission after ack.
- `DigitalOilSticker.Maintenance` — owns plans, service cycles/events, and selected oil/filter snapshots as pure functions over hydrated assigns; forecasting and reminders receive their vocabulary here but gain product logic in M06.
- `DigitalOilSticker.Forecasting` and `DigitalOilSticker.Reminders` — receive their event vocabulary in this card and are wired to the local bus (`forecast_changed`, `reminders_reconciled`) but their computation lands in M06.
- `DigitalOilSticker.LocalStore` (server side) — the boundary module that owns `handle_event("local_store:hydrate" | "local_store:ack" | "local_store:conflict", …)`, the pending-writes registry, envelope validation, and forward-only migration invocation. LiveViews receive already-hydrated assigns and typed error tuples from this module; they never touch envelopes directly.
- `LocalStore` JS hook — the client half of the protocol, owned by [DOS-M09-002](DOS-M09-002.md); this card consumes its API but does not modify it.
- LiveView modules (`OnboardingLive`, `VehiclePickerLive`, `StickerLive`, `OilChangeLive`, `MileageLive`, `SettingsLive`) — consume context APIs exclusively. No LiveView aliases `CatalogRepo`, `Repo`, `Ecto.*`, or the `LocalStore.*` protocol internals (AC-7, AC-8).
- Boot ordering (per ADR-0004 and the re-scoped [DOS-M04-006](DOS-M04-006.md)) — server-side: `CatalogRepo` open (read-only, verify integrity) → endpoint start. Client-side (per mount, not per boot): shell paint → socket connect → hydrate → assigns filled.

### Data and persistence

Personal data is held **only** in the origin-scoped IndexedDB database `dos_local`, whose object stores are exactly:

| Store | Key | Contents (per [ADR-0004 §Storage layout](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#storage-layout)) |
| --- | --- | --- |
| `meta` | `"meta"` (singleton) | `schema_version`, `seq` (monotonic write counter), `created_at`, `last_write_at`, `persist_granted` (boolean or `null`) |
| `vehicles` | `vehicle_id` (client-generated UUIDv4) | vehicle selection, catalog reference keys, user overrides, resolved catalog snapshots |
| `events` | `event_id` (UUIDv4) | oil-change and service events, `vehicle_id`-scoped |
| `readings` | `reading_id` (UUIDv4) | odometer check-ins, `vehicle_id`-scoped, integer base units |
| `reminders` | `reminder_id` (UUIDv4) | reminder intent/thresholds |
| `prefs` | `"prefs"` (singleton) | units, IANA time-zone identifier, display preferences |

`localStorage` holds only the `dos_boot_state` boot hint (`"never"` | `"has_data"`) per ADR-0004 §"Storage layout"; nothing else. There is no `UserRepo` and no server-side personal table. `CatalogRepo` is opened read-only using SQLite's `mode=ro` open flag (or an equivalent read-only role if a future ADR moves the catalog to Postgres), so the read-only claim is enforced by the connection itself rather than by convention (ADR-0004 §"Catalog database on Fly"). Any catalog schema change ships through the M04 tested build-time forward-migration procedure and a Fly release; there is no runtime catalog write path.

### Interfaces and events

- Context functions return typed results: `{:ok, struct_or_view_model}` | `{:error, %DomainError{code: atom, ...}}` where `code` is one of the FR-8 atoms. `active_vehicle_exists` carries a `%{existing: existing_vehicle, incoming: incoming_vehicle}` payload so the UI can render replace/archive without a second round trip.
- Mutating context APIs accept a `mutation_id` and produce a normalized `{upserts: [...], deletes: [...]}` write-plan the `LocalStore` server module wraps into `push_event("local_store:put", …)`; replaying the same `mutation_id` returns the cached result (FR-4).
- Events fire on `ack` via direct context return plus Phoenix PubSub only where multi-process reaction is needed inside the socket. Payloads are `{event_atom, %{stable_id: uuid, reason: atom, vehicle_id: uuid | nil}}` — no display strings, no personal values (FR-5, ADR-0004 §"Logging").
- The impersonal catalog-query surface (FR-9) is implemented in this card as the seven or so `Catalog.search/1`, `Catalog.resolve_configuration/1`, `Catalog.requirements_for/1`, and `Catalog.product_fitments_for/1`-style functions consumed by [DOS-M05-002](DOS-M05-002.md); their exact signatures land in [DOS-M09-005](DOS-M09-005.md) and are consumed unchanged here.

### Failure and recovery behavior

- Catalog read followed by catalog `data_version` bump: `Catalog` returns a validated immutable snapshot for the caller to write into the envelope; a snapshot referenced later after removal returns `:catalog_replaced` and the UI renders the history from the envelope snapshot alone (FR-9, [INV-11](../../docs/product/CONSTITUTION.md)).
- Deploy or machine replacement mid-mutation: the socket drops; the client retains its optimistic pending write; on reconnect the hook re-hydrates and re-drives the mutation with the same `mutation_id`, and the server produces the same domain result and same event (FR-4, FR-6).
- Storage evicted between visits: hydration returns zero records while `dos_boot_state == "has_data"`, triggering `:data_missing`; the UI never silently shows an empty garage ([INV-24.4](../../docs/product/CONSTITUTION.md), [INV-25](../../docs/product/CONSTITUTION.md)).
- Quota exceeded on a write: hook returns `local_store:ack` with `status: "quota_exceeded"`; server surfaces `:quota_exceeded`, keeps the optimistic value visible-unsaved, and offers export ([INV-24.5](../../docs/product/CONSTITUTION.md)).
- Private browsing / storage blocked: hook signals unavailable; server sets `:storage_unavailable`, session-only mode banner engages, and mutations are refused with `:storage_unavailable` rather than pretending to save ([INV-24.6](../../docs/product/CONSTITUTION.md), ADR-0004 §"Private browsing and blocked storage").
- Client payload `schema_version` ahead of the deployed server: hydration sets `:schema_version_ahead`, the UI enters explicit read-only mode with the banner from ADR-0004 §"Schema versioning and migration", and no `local_store:put` is ever emitted.

### Security, privacy, and observability

- All personal-data traffic is HTTPS + WSS over the exact production hostnames; `check_origin` restricted to the production hostnames (ADR-0004 §Transport, [INV-22](../../docs/product/CONSTITUTION.md)).
- Session cookie holds only the CSRF token and `live_socket_id`; it MUST NOT contain vehicle, event, reading, VIN, note, or `tab_id` values (ADR-0004 §"CSRF and session", [INV-3](../../docs/product/CONSTITUTION.md)).
- `Logger` filter drops `handle_event` params by default and allows only an explicit non-personal event-name allowlist; hydration and mutation envelopes and any values derived from them never reach a log line (ADR-0004 §"Logging", tested by AC-9).
- `debug_errors: false` in production; no assigns reach an error page.
- No third-party crash reporter, analytics, or CDN dependency ([INV-4](../../docs/product/CONSTITUTION.md), ADR-0004 §"No third-party anything").

### Accessibility and performance

- Every FR-8 error is rendered in the vocabulary defined by [DOS-M02-002](DOS-M02-002.md) and [DOS-M02-003](DOS-M02-003.md) (browser AT / WCAG 2.2 AA per pivot's rescope), with a stable code plus human-readable next step; the hydration state transitions are announced to assistive technology.
- Hydration must be sub-second on a cold connection so the skeleton state does not dominate the impression; a formal latency budget is owned by [DOS-M07-003](DOS-M07-003.md) (page-load, time-to-hydrated, LiveView round-trip). This card's contribution to that budget is a hard cap of one `readonly` transaction on the client side and no N+1 catalog queries in the hydration handler.

## UX and content states

This card owns no new end-user screens but freezes the state vocabulary every M05/M06 LiveView renders inside, in one place:

- Server-side pre-connection: shell with `local_state == :hydrating`, skeleton, no data claims.
- Post-hydration, four distinct rendered branches: `:loaded`, `:empty`, `:data_missing`, `:storage_unavailable`. The last three are copy-reviewed under INV-25's honesty rules; an `:empty` state is only shown when `dos_boot_state == "never"`.
- Mutation states: `saving`, `saved`, `unsaved (retry) — Not saved to this browser` (the persistent non-dismissible variant when ack does not arrive), `conflict — reloaded from this browser's newer data`, `read-only — this browser holds data from a newer version of the app`.
- Prohibited copy anywhere the hydration or mutation states surface: "backup", "synced", "safe", "we'll remember", "your account" (ADR-0004 §"Export and import", [INV-5](../../docs/product/CONSTITUTION.md), [INV-25](../../docs/product/CONSTITUTION.md)).
- Fixtures demonstrate `supported`, `partial`, `manual`, and `unsupported` catalog states so downstream screens render provenance honestly per [INV-11](../../docs/product/CONSTITUTION.md).

## Acceptance criteria

- [ ] AC-1 — Fresh visit and returning visit both progress through `:hydrating` → `:loaded`/`:empty` (returning-with-data → `:loaded`; fresh → `:empty`; returning-with-cleared-storage → `:data_missing`; blocked storage → `:storage_unavailable`) and expose one coherent context API per module. Create/read/edit/archive for a vehicle and append for a service event and odometer reading each complete a full mutation round trip without a LiveView calling any repo, Ecto module, or `LocalStore` protocol internal directly.
- [ ] AC-2 — Persisted vehicle records in the IndexedDB envelope carry catalog reference keys plus resolved snapshots sufficient to render history after the referenced catalog row is removed in a test-driven catalog `data_version` bump; the domain returns `:catalog_replaced` on lookup, and the history view renders from the envelope snapshot alone.
- [ ] AC-3 — A second create through `Garage` returns `{:error, %DomainError{code: :active_vehicle_exists, existing: _, incoming: _}}` without any side effect; envelope inspection shows every event, reading, and reminder record carries a `vehicle_id`, so DOS-M08-001 can lift the UI cap alone.
- [ ] AC-4 — Double-submit, LiveView reconnect, deploy-simulating socket drop, and process-kill each yield at most one committed mutation (verified through unique `mutation_id` replay) and the committed state re-renders from IndexedDB after the socket reconnects and re-hydrates; unsaved optimistic values render as `unsaved (retry)`, never as saved.
- [ ] AC-5 — Catalog read followed by catalog `data_version` bump either persists the validated snapshot into the envelope or returns `:snapshot_stale`; no dangling personal reference to a missing catalog row is created, and the UI degrades to `:catalog_replaced` messaging without dropping user history.
- [ ] AC-6 — Storage-evicted fixture triggers `:data_missing` with the INV-25 messaging; quota-exceeded fixture triggers `:quota_exceeded` with the value visible-unsaved and export offered; storage-blocked fixture triggers `:storage_unavailable` with the session-only banner engaged. No branch silently shows an empty garage.
- [ ] AC-7 — The release-gating repo-list test asserts the deployed application's Ecto repo list is exactly `[DigitalOilSticker.CatalogRepo]` and that its connection is opened read-only (SQLite `mode=ro` or equivalent). The pre-pivot form of AC-7 (a static check forbidding LiveView aliases of `CatalogRepo` or `UserRepo` and any WebView-storage writes of authoritative user facts) is retired; the LiveView-alias half is replaced by AC-8, and the WebView-storage half is meaningless in the browser MVP because IndexedDB *is* the authoritative store.
- [ ] AC-8 — A static check (compile-time boundary or Credo-style AST scan) fails CI when a LiveView module aliases `DigitalOilSticker.CatalogRepo`, `Ecto.Repo`, `Ecto.Query`, or the `DigitalOilSticker.LocalStore.*` internals, and when a domain-context module (`Catalog`, `Garage`, `Maintenance`, `Forecasting`, `Reminders`) references `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules (ADR-0004 §Enforcement bullet 2).
- [ ] AC-9 — A scripted-session test drives hydrate → several mutations → export → clear → import with log capture, asserting that no VIN, odometer value, service date, note text, or custom vehicle name appears in any captured log line (ADR-0004 §Enforcement bullet 3).
- [ ] AC-10 — A hydration idempotency test asserts that hydrating the same payload twice produces identical assigns and emits no `local_store:put` (ADR-0004 §Enforcement bullet 4).

## Risks, decisions, and open questions

- **Risk — the M09 storage schema drifts from the domain vocabulary M05 wants.** Mitigation: the FR-8 error-code list and the object-store field lists are both frozen in this card and reviewed against [DOS-M09-001](DOS-M09-001.md) before merge.
- **Risk — the hydration round trip becomes a p95 latency floor for the whole product.** Mitigation: budget owned by [DOS-M07-003](DOS-M07-003.md); this card commits only to sub-second hydration on a cold connection and no N+1 catalog queries in the hydration handler.
- **Risk — a well-meaning refactor moves a `LocalStore` protocol reference into a domain module, silently breaking ADR-0004 Decision §6.** Mitigation: AC-8 is a compile-gating check, not a code-review convention.
- **Decision to record** — the frozen FR-8 error-code list, the fixed hydration state names (`:hydrating`, `:loaded`, `:empty`, `:data_missing`, `:storage_unavailable`, `:schema_version_ahead`), and the fixed event names (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, `catalog_activated`) are set here and consumed verbatim by every downstream M05/M06 card. Renaming any of them requires an ADR amendment.
- **Open question** — whether last-write-wins at record granularity with the loss made visible (ADR-0004 §"Multi-tab consistency", R4) is acceptable in practice, or whether a workflow (two tabs, one logging a service while the other edits it) makes it materially wrong. Re-examine on evidence.
- **Open question** — whether the AC-8 static check is implemented as a compile-time boundary contract (a `@behaviour`-driven check or a `Boundary`-style dependency graph) or a Credo AST scan. Either satisfies AC-8; the choice is recorded with the evidence.

## Superseded pre-pivot spec (historical record)

> This section preserves the card as chartered before the 2026-08-01 pivot to browser-first, and is retained for historical readability of the ADR record. The Outcome above is authoritative.

### Outcome (pre-pivot)

The first feature slice consumes the already-approved M04 persistence layer without inventing a third store, duplicate schemas, or LiveView-owned queries. `CatalogRepo` remains replaceable/read-mostly; `UserRepo` remains durable and contains the exact `local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications`, and `schema_events` contracts established by M04.

### Why this matters and what it unblocks (pre-pivot)

M04 proves storage and migrations; M05 must prove that product flows use those boundaries correctly. This ticket prevents feature work from renaming tables, bypassing contexts, coupling user history to a catalog file, or re-solving persistence inconsistently inside LiveViews. It unblocks every other M05 screen (DOS-M05-002 through DOS-M05-007) and the M06 forecasting/reminder integrations (DOS-M06-002, DOS-M06-003), as well as the M08 multi-vehicle enablement (DOS-M08-001), which relies on every vehicle-owned row already being vehicle-scoped.

### Included (pre-pivot)

- Application-facing context functions on `Catalog`, `Garage`, `Maintenance`, `Forecasting`, and `Reminders` that return typed success/error results consumable by LiveViews without knowledge of Repos, SQL, or filesystem paths.
- Stable local UUID creation for every user-owned entity, generated in the domain layer, never in the UI.
- One-active-vehicle enforcement at the domain layer inside `Garage`, returning a typed `active_vehicle_exists` decision on a second create.
- Catalog-key plus readable-snapshot persistence for vehicles: stable `configuration_key`, catalog version, support status, and year/make/model/configuration display snapshots written into `UserRepo`.
- Same-database atomic operations: `Ecto.Multi` for mutations wholly inside `UserRepo` (for example service event plus linked odometer reading plus derived-state invalidation).
- Optimistic duplicate-submit protection: an idempotency token or equivalent revision guard on every mutating LiveView submit path.
- Invalidation events: the reason-coded local events from the §7 architecture contract, published after commit.
- Fixtures that exercise supported/partial/manual vehicle states for use by every downstream M05 issue.
- A migration only if the M04 schema demonstrably lacks a frozen M05 requirement, in which case the M04 data dictionary/ADR is amended first and its tested migration procedure is used.
- Static analysis or an architectural test wired into CI that fails when a LiveView aliases either Repo or when authoritative user facts are written to WebView storage.

### Excluded (pre-pivot)

- A new database.
- Alternate table vocabulary.
- Raw Repo calls in LiveViews.
- Browser storage (cookies, WebView `localStorage`, Cache Storage, IndexedDB) as an authoritative store.
- Server persistence.
- Sync queues.
- Cross-device merge logic.
- A cross-database transaction illusion.

### Functional requirements (pre-pivot)

- FR-1 (retired, replaced by rescoped FR-1 and FR-2 above): Wire the M04 `CatalogRepo` and `UserRepo`, both `ecto_sqlite3` with `pool_size: 1`, into the `Catalog`, `Garage`, `Maintenance`, `Forecasting`, and `Reminders` contexts. LiveViews call context APIs and render typed outcomes; they do not call `Repo`, compose SQL, or know filesystem paths.
- FR-2 (retired, subsumed by rescoped FR-2 and FR-9): Create a vehicle by reading the selected catalog configuration, then writing its stable `configuration_key`, catalog version, support status, and year/make/model/configuration display snapshots into `UserRepo`. There is no cross-database foreign key and no assumption that a later catalog contains the same row.
- FR-3 (retained in spirit by rescoped FR-3 UX outcome and AC-3): Enforce at most one non-archived/active vehicle for the MVP in `Garage`; preserve `vehicle_id` on every vehicle-owned row so M08 enables many vehicles without reshaping ownership. A second create returns a typed `active_vehicle_exists` decision requiring replace/archive UX — it never overwrites silently.
- FR-4 (retired, replaced by rescoped FR-4 mutation round trip): Use `Ecto.Multi` only for mutations wholly inside `UserRepo`. A read from `CatalogRepo` followed by a `UserRepo` write uses a validated immutable snapshot and explicit stale/missing-catalog error handling.
- FR-5 (retained by rescoped FR-5, moved to fire on ack rather than on commit): Publish the local reason-coded events defined in the architecture contract after commit — at least `vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, and `catalog_activated`.
- FR-6 (retired, replaced by rescoped FR-4's `mutation_id` replay contract): Duplicate LiveView submits carry an idempotency token or equivalent revision guard so reconnect/retry cannot create two vehicles or two service events.
- FR-7 (retired, replaced by rescoped FR-6): Treat temporary socket/form state as disposable. Authoritative facts never live in cookies, WebView `localStorage`, Cache Storage, or IndexedDB. App termination before commit creates no row; app termination after commit re-renders the committed state from `UserRepo`.
- FR-8 (retired, replaced by rescoped FR-8 with browser-storage vocabulary): Map validation, not-found, stale-revision, active-vehicle-conflict, catalog-unavailable, storage-unavailable, disk-full, corruption, and migration/recovery errors to stable domain codes.
- FR-9 (retired, no longer applies — the on-device application-support paths, foreign-key pragmas, forward migrations, backups, and corruption-recovery flows described a `UserRepo` that no longer exists): Reuse M04's application-support/files paths, boot ordering, foreign-key/journal pragmas, forward migrations, backups, and corruption recovery.
- FR-10 (retained by rescoped FR-10): Persist mileage in the M04 canonical integer base unit and convert at the boundary; store UTC instants plus the IANA time zone per §8.

### Technical implementation contract (pre-pivot, superseded)

The pre-pivot contract centered on a co-located dual-repository runtime: `DigitalOilSticker.Garage`, `Catalog`, `Maintenance`, `Forecasting`, and `Reminders` all opened both `CatalogRepo` (read-mostly) and `UserRepo` (durable) via `ecto_sqlite3` with `pool_size: 1`; ten `UserRepo` tables (`local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications`, `schema_events`) held all personal data; `Ecto.Multi` performed same-`UserRepo` atomic mutations; `DigitalOilSticker.Boot` ordered catalog verification → user migration → Repo startup → recovery state → endpoint readiness; failure recovery cited disk-full/corruption/catalog-unavailable/migration-recovery paths inherited from M04; security cited local `UserRepo` writes plus loopback traffic; and accessibility/performance cited the M02 content contract with a `pool_size: 1` responsiveness rule. ADR-0004 replaced this entire contract with the browser-first spec above; the ten `UserRepo` tables were replaced by the six IndexedDB object stores (`meta`, `vehicles`, `events`, `readings`, `reminders`, `prefs`) in ADR-0004 §"Storage layout", and the on-device server-side loopback boundary was replaced by the hosted-transport rules in ADR-0004 §"Security and privacy boundary for a hosted application".

### Acceptance criteria (pre-pivot, superseded)

- AC-1 (pre-pivot): Fresh-install and supported-upgrade fixtures boot through M04, expose one coherent context API, and complete create/read/edit/archive operations without direct Repo calls from LiveViews.
- AC-2 (pre-pivot): Persisted vehicle rows contain a stable catalog key and sufficient readable/provenance snapshots to display history after the referenced catalog row is removed in a test upgrade.
- AC-3 (pre-pivot): The MVP singleton rule rejects a second active vehicle without a destructive side effect, while schema inspection proves every dependent row is already vehicle-scoped for M08.
- AC-4 (pre-pivot): Double-submit, LiveView reconnect, Endpoint restart, and process-kill tests produce at most one committed mutation and show the committed state after recovery.
- AC-5 (pre-pivot): A catalog read followed by catalog replacement either saves the validated snapshot or returns a controlled stale-selection error; it never creates a dangling cross-database reference.
- AC-6 (pre-pivot): Disk-full, corruption, catalog-unavailable, and migration-recovery fixtures display the specified recovery path and preserve the last valid `UserRepo` state.
- AC-7 (pre-pivot, retired and replaced by rescoped AC-7 + AC-8): Static analysis or an architectural test fails CI when a LiveView aliases either Repo or when authoritative user facts are written to WebView storage.
