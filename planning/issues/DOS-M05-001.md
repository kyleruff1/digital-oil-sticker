## Outcome

The first feature slice consumes the already-approved M04 persistence layer without inventing a third store, duplicate schemas, or LiveView-owned queries. `CatalogRepo` remains replaceable/read-mostly; `UserRepo` remains durable and contains the exact `local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications`, and `schema_events` contracts established by M04.

## Why this matters and what it unblocks

M04 proves storage and migrations; M05 must prove that product flows use those boundaries correctly. This ticket prevents feature work from renaming tables, bypassing contexts, coupling user history to a catalog file, or re-solving persistence inconsistently inside LiveViews. It unblocks every other M05 screen (DOS-M05-002 through DOS-M05-007) and the M06 forecasting/reminder integrations (DOS-M06-002, DOS-M06-003), as well as the M08 multi-vehicle enablement (DOS-M08-001), which relies on every vehicle-owned row already being vehicle-scoped.

## Context and source of truth

- Master roadmap prompt (`digital-oil-sticker-claude-code-roadmap-prompt.md`), §11.3 catalog entry "DOS-M05-001 — Integrate the M04 dual-repository domain contract into the single-vehicle runtime".
- §4.2 SQLite is the runtime database: `CatalogRepo` (replaceable, read-mostly) and `UserRepo` (durable), `pool_size: 1` per Repo, no cross-database foreign keys, catalog key plus readable snapshot on user rows.
- §7 Target implementation architecture: contexts `DigitalOilSticker.Catalog`, `Garage`, `Maintenance`, `Forecasting`, `Reminders`, `Boot`, `Clock`; local event contract; no Oban or perpetual background GenServer.
- §8 Database and data-contract baseline: the ten `UserRepo` tables named in the Outcome, integer base units for mileage, UTC instants plus IANA time zone, migration and catalog rules.
- §3 rule 9 (one-vehicle MVP, multi-vehicle-safe internals) and rule 10 (change control).
- Committed M04 artifacts: the M04 data dictionary/ADR, migration procedures, boot ordering, backup and corruption-recovery documentation — this issue may not weaken them.

## Included

- Application-facing context functions on `Catalog`, `Garage`, `Maintenance`, `Forecasting`, and `Reminders` that return typed success/error results consumable by LiveViews without knowledge of Repos, SQL, or filesystem paths.
- Stable local UUID creation for every user-owned entity, generated in the domain layer, never in the UI.
- One-active-vehicle enforcement at the domain layer inside `Garage`, returning a typed `active_vehicle_exists` decision on a second create.
- Catalog-key plus readable-snapshot persistence for vehicles: stable `configuration_key`, catalog version, support status, and year/make/model/configuration display snapshots written into `UserRepo`.
- Same-database atomic operations: `Ecto.Multi` for mutations wholly inside `UserRepo` (for example service event plus linked odometer reading plus derived-state invalidation).
- Optimistic duplicate-submit protection: an idempotency token or equivalent revision guard on every mutating LiveView submit path.
- Invalidation events: the reason-coded local events from the §7 architecture contract, published after commit.
- Fixtures that exercise supported/partial/manual vehicle states for use by every downstream M05 issue.
- A migration only if the M04 schema demonstrably lacks a frozen M05 requirement, in which case the M04 data dictionary/ADR is amended first and its tested migration procedure is used.
- Static analysis or an architectural test wired into CI that fails when a LiveView aliases either Repo or when authoritative user facts are written to WebView storage.

## Excluded

- A new database.
- Alternate table vocabulary.
- Raw Repo calls in LiveViews.
- Browser storage (cookies, WebView `localStorage`, Cache Storage, IndexedDB) as an authoritative store.
- Server persistence.
- Sync queues.
- Cross-device merge logic.
- A cross-database transaction illusion.

## Functional requirements

- FR-1: Wire the M04 `CatalogRepo` and `UserRepo`, both `ecto_sqlite3` with `pool_size: 1`, into the `Catalog`, `Garage`, `Maintenance`, `Forecasting`, and `Reminders` contexts. LiveViews call context APIs and render typed outcomes; they do not call `Repo`, compose SQL, or know filesystem paths.
- FR-2: Create a vehicle by reading the selected catalog configuration, then writing its stable `configuration_key`, catalog version, support status, and year/make/model/configuration display snapshots into `UserRepo`. There is no cross-database foreign key and no assumption that a later catalog contains the same row.
- FR-3: Enforce at most one non-archived/active vehicle for the MVP in `Garage`; preserve `vehicle_id` on every vehicle-owned row so M08 enables many vehicles without reshaping ownership. A second create returns a typed `active_vehicle_exists` decision requiring replace/archive UX — it never overwrites silently.
- FR-4: Use `Ecto.Multi` only for mutations wholly inside `UserRepo`, such as service event plus linked odometer reading plus derived-state invalidation. A read from `CatalogRepo` followed by a `UserRepo` write uses a validated immutable snapshot and explicit stale/missing-catalog error handling, not a false two-phase transaction.
- FR-5: Publish the local reason-coded events defined in the architecture contract after commit — at least `vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`, and `catalog_activated`. Events carry local stable IDs and reason codes, not display strings.
- FR-6: Duplicate LiveView submits carry an idempotency token or equivalent revision guard so reconnect/retry cannot create two vehicles or two service events.
- FR-7: Treat temporary socket/form state as disposable. Authoritative facts never live in cookies, WebView `localStorage`, Cache Storage, or IndexedDB. App termination before commit creates no row; app termination after commit re-renders the committed state from `UserRepo`.
- FR-8: Map validation, not-found, stale-revision, active-vehicle-conflict, catalog-unavailable, storage-unavailable, disk-full, corruption, and migration/recovery errors to stable domain codes and actionable accessible UI states. Never expose raw SQLite/Ecto exceptions or discard valid existing data.
- FR-9: Reuse M04's application-support/files paths, boot ordering, foreign-key/journal pragmas, forward migrations, backups, and corruption recovery. This issue may add feature fixtures and contract tests but may not weaken those certified rules.
- FR-10: Persist mileage in the M04 canonical integer base unit and convert at the boundary; store UTC instants plus the IANA time zone per §8 so unit or time-zone switches never lose precision.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Garage` owns local profile and vehicle lifecycle, including the one-active-vehicle rule and archival state.
- `DigitalOilSticker.Catalog` owns all reads of `CatalogRepo` (configurations, schedules, requirements, provenance, support status); it is the only module that queries catalog tables.
- `DigitalOilSticker.Maintenance` owns plans, service cycles/events, and selected oil/filter snapshots; `Forecasting` and `Reminders` receive their M04 table contracts here but gain product logic only in M06.
- LiveViews (`OnboardingLive`, `VehiclePickerLive`, `StickerLive`, `OilChangeLive`, `MileageLive`, `SettingsLive`, and shared components from §7) consume context APIs exclusively. No LiveView module may alias `CatalogRepo` or `UserRepo`; CI enforces this (AC-7).
- `DigitalOilSticker.Boot` retains M04 ordering: catalog verification, user migration, Repo startup, recovery state, endpoint readiness — before the UI becomes writable.

### Data and persistence

- `UserRepo` tables used exactly as established by M04: `local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications`, `schema_events`. No renames, no parallel tables.
- Vehicle rows persist stable catalog key + catalog version + support status + readable display snapshots so history remains understandable after a catalog replacement (§4.2, §8).
- Both Repos run `ecto_sqlite3` with `pool_size: 1`; no cross-database foreign keys; foreign-key and journal pragmas inherited from M04 unchanged.
- Any schema change requires amending the M04 data dictionary/ADR first and shipping through M04's tested forward-migration procedure with backup-before-risky-migration behavior intact.

### Interfaces and events

- Context functions return typed results (`{:ok, struct_or_view_model}` / `{:error, %DomainError{code: atom, ...}}`); the error-code vocabulary covers at least `:validation`, `:not_found`, `:stale_revision`, `:active_vehicle_exists`, `:catalog_unavailable`, `:storage_unavailable`, `:disk_full`, `:corruption_detected`, and `:migration_recovery_required`.
- Events publish after commit via direct context return plus Phoenix PubSub where more than one active process needs them (§7); payloads carry local stable IDs and reason codes, never display strings.
- Mutating APIs accept an idempotency token or revision argument; replaying the same token returns the originally committed result instead of a second mutation.

### Failure and recovery behavior

- Catalog read followed by catalog replacement: either the validated immutable snapshot is saved or a controlled stale-selection error is returned; no dangling cross-database reference is ever created.
- Disk-full, corruption, catalog-unavailable, and migration-recovery conditions map to their stable domain codes and render the recovery paths specified by M04, preserving the last valid `UserRepo` state.
- Endpoint restart, LiveView reconnect, and process kill around a mutation yield at most one committed mutation, and the committed state re-renders from `UserRepo` after recovery.
- Raw SQLite/Ecto exceptions never surface to the user and never trigger data loss.

### Security and privacy

- All user writes target the local `UserRepo`; all traffic stays on device loopback; the query/log audit evidence must prove both.
- Logs and fixtures redact VIN, mileage, notes, and vehicle identifiers per §7 production shell security; no telemetry or third-party analytics.
- Packaged session keys are local integrity material, not remote secrets; authoritative facts never enter WebView storage.

### Accessibility and performance

- Error states produced by FR-8 are actionable and accessible: announced to assistive technology, with a stable code plus human-readable next step, per the M02 content contract.
- Context APIs stay responsive on-device with `pool_size: 1`: no N+1 catalog queries in hot paths and no long-running transaction that would block the single connection; formal budgets are owned by DOS-M07-003.

## UX and content states

This issue owns no new end-user screens but defines the state vocabulary every M05 LiveView renders: typed success, validation error with field detail, not-found, stale-revision/stale-selection, active-vehicle-conflict (replace/archive decision), catalog-unavailable, storage-unavailable, disk-full, corruption-recovery, and migration-recovery. Each state has reviewed copy from the M02 content contract, never a raw exception. Fixtures demonstrate supported, partial, and manual vehicle states so downstream screens can render provenance honestly.

## Acceptance criteria

- [ ] AC-1: Fresh-install and supported-upgrade fixtures boot through M04, expose one coherent context API, and complete create/read/edit/archive operations without direct Repo calls from LiveViews.
- [ ] AC-2: Persisted vehicle rows contain a stable catalog key and sufficient readable/provenance snapshots to display history after the referenced catalog row is removed in a test upgrade.
- [ ] AC-3: The MVP singleton rule rejects a second active vehicle without a destructive side effect, while schema inspection proves every dependent row is already vehicle-scoped for M08.
- [ ] AC-4: Double-submit, LiveView reconnect, Endpoint restart, and process-kill tests produce at most one committed mutation and show the committed state after recovery.
- [ ] AC-5: A catalog read followed by catalog replacement either saves the validated snapshot or returns a controlled stale-selection error; it never creates a dangling cross-database reference.
- [ ] AC-6: Disk-full, corruption, catalog-unavailable, and migration-recovery fixtures display the specified recovery path and preserve the last valid `UserRepo` state.
- [ ] AC-7: Static analysis or an architectural test fails CI when a LiveView aliases either Repo or when authoritative user facts are written to WebView storage.

- Query/log audit on-device proving all traffic is local and all user writes target `UserRepo`.

## Rollout and rollback

This is pre-release integration work; it ships inside the normal build, guarded by CI gates rather than a runtime flag. Rollback is `git revert` of the integration changes. If the conditional M04 schema amendment path is exercised, rollback follows the amended M04 migration procedure's documented backup/recovery steps; `UserRepo` history is never reset.

## Risks, decisions, and open questions

- Risk: discovering a genuine M04 schema gap mid-milestone. Mitigation: the included conditional path — amend the M04 data dictionary/ADR first, use its tested migration procedure; anything else is change-control scope creep (§3 rule 10).
- Risk: idempotency design (token vs. revision guard) chosen here becomes the pattern for M06/M08; record the choice and its rationale in the schema/context dependency documentation.
- Decision to record: the exact stable domain-error code list (FR-8) is frozen in this issue and reused verbatim by all downstream M05/M06 UI states.
- Open question: whether the architectural CI check is implemented as static analysis or a compile-time boundary test; either satisfies AC-7, and the selection is documented with the evidence.

## Definition of done

All acceptance criteria are checked with automated suites green in CI; physical-device fresh/upgrade runs, the query/log audit, and the dependency diagram are attached to this issue or linked from CI; no LiveView touches a Repo; M04's certified rules are demonstrably unweakened; and downstream M05 issues can consume the context APIs and fixtures without modification.
