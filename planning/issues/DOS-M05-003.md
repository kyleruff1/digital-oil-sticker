## Outcome

The selected catalog vehicle becomes a transparent, editable local profile with a nickname, current odometer, unit preference, driving/use classification, and an explicit maintenance interval basis.

## Why this matters and what it unblocks

Forecasting requires clear user inputs and traceable recommendation provenance. This ticket prevents the UI from presenting an oil brand or a generic interval as a manufacturer mandate — the core honesty rule of the product (§3 rules 4, 5, and 6). It blocks DOS-M05-004 (service history attaches to the profile), DOS-M05-005 (the dashboard renders the confirmed interval basis), and DOS-M06-001 (the forecast engine consumes the usage classification and interval basis established here).

- §9 Recommendation resolver: typed results `verified`, `partial`, `conflict`, `unsupported`, `not_applicable`; `match_basis` recording; never collapse unknown to compatible; manual history never relabeled as verified compatibility.
- The recommendation/provenance schema from earlier milestones (M03/M04 contracts) and the DOS-M05-001 context APIs.

## Included

- Profile create, edit, and replace flows for the single active vehicle.
- Nickname.
- Miles/kilometers display preference.
- Current odometer entry.
- Normal/severe/unknown usage answer (driving/use classification), preserving the answers that selected the condition per §8.
- Recommendation candidates presented in a typed resolution order with full provenance.
- Interval override: a user-entered custom interval, clearly labeled, with the sourced candidate preserved for comparison.
- Provenance display: source, effective model/configuration, time and mileage thresholds, service condition, revision, and catalog verification date.
- Destructive replace flow with history impact preview, export-first offer, and explicit confirmation.

## Excluded

- Oil purchase links.
- Automatic severe-duty diagnosis.
- OLM integration.
- VIN storage.
- Multiple profiles.

## Preconditions

- DOS-M05-001 is closed: `Garage`/`Maintenance` context APIs, one-active-vehicle rule, typed errors, and snapshot persistence exist.
- DOS-M05-002 is closed: an exact catalog-backed selection with stable `configuration_key` and support status is committed.
- The recommendation/provenance schema from earlier milestones is available in the bundled catalog (`maintenance_schedules`, `oil_requirements`, `data_sources` per §8).
- M02 copy for interval types, provenance, custom-interval labeling, and destructive confirmation is ratified.

## Functional requirements

- FR-1: Present interval candidates in a typed resolution order: exact licensed OEM-derived schedule; explicitly qualified broader-configuration schedule labeled with reduced precision; or no sourced schedule. Never invent an editorial interval.
- FR-2: A user may create a separate custom interval after acknowledging that it is user-entered. Never merge conflicting values invisibly.
- FR-3: For every displayed candidate, show source, effective model/configuration, time and mileage thresholds, service condition, revision, and catalog verification date.
- FR-4: Oil product and filter selections are optional service metadata unless the catalog contains the exact evidence required by the M03/M04 contracts.
- FR-5: A product claim may add a stricter documented constraint but may never extend or replace an earlier OEM/vehicle threshold. Filter fitment never establishes an oil-change interval.
- FR-6: Compatibility is reported only as "meets the recorded requirements" or "listed for this configuration" with its match basis and provenance — not merely "present in curated data" and never as a universal safety or warranty guarantee.
- FR-7: Require the user to confirm one interval basis or enter a custom interval. Custom intervals are clearly labeled "Your interval," require at least one of months or distance, and preserve the original sourced candidate for comparison.
- FR-8: Odometer input accepts the display unit, converts deterministically to canonical miles, round-trips within one displayed unit, and rejects negative, nonfinite, or implausibly large values with a correctable message. Do not reject an older vehicle solely on age.
- FR-9: Replacing the only vehicle is a destructive operation: show what local history will be detached/deleted, offer export first, and require explicit confirmation.
- FR-10: Editing disambiguating vehicle identity is implemented as replace, not an in-place foreign-key mutation.
- FR-11: A profile may be saved incomplete with an explicit setup-required state, but at least one interval dimension is required before the profile is "forecast ready."
- FR-12: All profile values persist through `UserRepo` context APIs and survive restart; unit preference changes never alter canonical stored meaning.

## Technical implementation contract

### Components and ownership boundaries

- Profile screens (per §7: `SettingsLive`/vehicle profile surfaces, `RecommendationLive`, `VehicleSummary`, `SourceBadge`, `ProductPicker`) render typed context results only.
- `Garage` owns nickname, unit preference, archival/replace lifecycle; `Maintenance` owns plans and interval basis; `Catalog` supplies recommendation candidates and provenance; the resolver's typed result vocabulary follows §9.
- Interval resolution and precedence logic live in domain code with golden tests — never re-implemented in a LiveView.

### Data and persistence

- `vehicles`: nickname, year/make/model/configuration snapshots, support status, catalog version (from DOS-M05-001 semantics).
- `maintenance_plans`: operating condition, sourced miles/months/OLM rule snapshots, requirement/source/version snapshots, and the optional explicit user override with reason — the custom interval is an override row/field, never a mutation of the sourced snapshot.
- `usage_profiles`: baseline distance/week with unit, severe-use answers, and the selected condition, preserving the answers that selected the condition.
- Odometer entry writes through the DOS-M05-004/M04 `odometer_readings` contract in canonical integer base units; conversion happens at the boundary only.
- Replace archives the outgoing vehicle and its history per the confirmed preview; no orphaned vehicle-scoped rows remain.

### Interfaces and events

- Context APIs: fetch recommendation candidates for a `configuration_key` and operating condition (typed §9 result), confirm interval basis, set custom interval, update usage profile, update nickname/units, replace vehicle.
- Mutations publish the DOS-M05-001 events (`vehicle_saved`, plan-affecting changes marking forecasts stale) with reason codes.
- The data-error reporting route required by §6 is presented as guidance (local instructions), transmitting nothing automatically.

### Failure and recovery behavior

- Missing or partial catalog evidence renders the honest states ("Source unavailable", "Exact configuration not verified", reduced-precision label) rather than a guess; `conflict` results show no automatic product recommendation and retain both facts for review (§9).
- Validation failures (odometer bounds, custom interval missing both dimensions) return correctable field-level messages preserving user input.
- Replace is atomic within `UserRepo`; interruption mid-replace leaves either the old profile intact or the new profile fully committed, never a hybrid.
- Stale catalog selection during candidate fetch surfaces the DOS-M05-001 stale-selection error with re-selection guidance.

### Security and privacy

- No VIN storage in this issue (excluded); nickname, odometer, and usage answers are local-only `UserRepo` facts, redacted from logs per §7.
- Export-first offer during replace hands off to the DOS-M05-007 export path; nothing is transmitted.
- No purchase links, no external product calls; all recommendation data comes from the bundled catalog.

### Accessibility and performance

- All forms are keyboard/screen-reader operable with visible labels and correctable, announced validation messages, consistent with the M02 contract and the DOS-M05-002 control standards.
- Provenance disclosure is reachable without leaving the profile (progressive disclosure), and destructive confirmations are fully accessible.
- Candidate resolution is a bounded local query set; no interaction blocks the single SQLite connection for perceptible time (budgets per DOS-M07-003).

## UX and content states

- Interval basis states: exact sourced schedule (with condition normal/severe); qualified broader-configuration schedule with reduced-precision label; no sourced schedule ("Source unavailable"); custom "Your interval" with the sourced candidate shown for comparison; conflict state retaining both facts without an automatic recommendation.
- Profile completeness states: complete/forecast-ready; saved-incomplete with explicit setup-required state naming the missing interval dimension.
- Product/filter metadata states: recorded-as-metadata (free text or catalog product without claims evidence); evidence-backed "meets the recorded requirements" / "listed for this configuration" with match basis and provenance detail.
- Destructive replace: impact preview (what is detached/deleted, with counts), export-first offer, explicit confirmation; cancel returns without changes.
- Every recommendation detail view shows provider/document, source version/revision, retrieved/verified date, market and condition, and the data-error reporting route (§6).

## Acceptance criteria

- [ ] AC-1: User can create, review, and edit all non-identity fields offline; all values survive restart.
- [ ] AC-2: Every displayed interval has a visible type and provenance; missing evidence is displayed as unavailable.
- [ ] AC-3: Golden precedence tests prove that an oil-brand/product claim, viscosity match, filter fitment, or generic make/model row cannot create or extend a manufacturer interval.
- [ ] AC-4: At least one interval dimension is required before the profile is "forecast ready," but a user may save an incomplete profile with an explicit setup-required state.
- [ ] AC-5: Unit changes do not alter canonical meaning or create cumulative rounding drift.
- [ ] AC-6: Vehicle replacement cannot occur through a single accidental tap and leaves no orphaned rows.

## Test plan

### Automated

- Domain validation tests: odometer bounds and unit conversion, custom-interval dimension requirement, usage-answer persistence.
- Recommendation precedence golden tests covering oil-brand claim, viscosity match, filter fitment, and generic make/model row against a sourced OEM interval (AC-3).
- Imperial/metric round-trip tests proving round-trip within one displayed unit and no cumulative drift (AC-5).
- Provenance UI snapshots for every interval-basis state.
- Destructive-flow E2E test: replace requires preview plus explicit confirmation and leaves no orphaned rows (AC-6).
- Persistence/restart test: create, kill app, relaunch, verify all values (AC-1).

### Manual/device matrix

- Offline create/review/edit pass on packaged iOS and Android builds, including restart survival.
- Screen-reader walkthrough of interval-basis confirmation, custom-interval labeling, and the destructive replace flow.
- Visual check that provenance details and reduced-precision labels match ratified M02 copy.

## Rollout and rollback

Ships in the normal MVP build behind CI gates. Rollback is reverting the profile slice; sourced snapshots and override rows in `UserRepo` follow the M04 migration/rollback rules and are never silently reset. If precedence copy or rules change after release, that is a new issue per change control.

## Dependency rationale

- DOS-M05-001 provides the context APIs, plan/usage persistence, typed errors, and events this profile writes through.
- DOS-M05-002 provides the exact committed catalog selection whose `configuration_key` drives candidate resolution.
- The recommendation/provenance schema from earlier milestones supplies `maintenance_schedules`, `oil_requirements`, and `data_sources` evidence; without it every candidate would be "no sourced schedule."
- This issue blocks DOS-M05-004 (history records against the profile), DOS-M05-005 (dashboard renders the confirmed basis), and DOS-M06-001 (forecast inputs: usage classification and interval basis).

## Risks, decisions, and open questions

- Risk: precedence subtleties (stricter product constraint vs. OEM threshold) are easy to get wrong in UI copy even when domain logic is correct; mitigated by golden tests plus copy review against §6 terminology.
- Risk: users with unsupported vehicles may expect an invented interval; the custom "Your interval" path with acknowledgment is the only outlet, and it never masquerades as sourced.
- Decision to record: the implausibly-large odometer threshold used by FR-8 validation, documented with the domain tests (a documented value, not a magic number).
- Open question: exact placement of the export-first offer inside the replace flow (before or within the confirmation step) — resolve with M02 design review; both satisfy FR-9.

## Definition of done

All acceptance criteria pass with automated suites green; provenance snapshots, precedence golden results, destructive-flow evidence, and restart-survival evidence are attached; copy matches the M02 contract and §6 terminology; and DOS-M05-004/DOS-M05-005 can build on the confirmed interval basis without modification.
