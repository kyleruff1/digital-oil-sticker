## Outcome

The catalog-selected vehicle from `DOS-M05-002` becomes a transparent, editable local profile — nickname, current odometer, unit preference, driving/use classification, and an explicit maintenance interval basis with full source provenance — held **only** in the browser's origin-scoped `dos_local` IndexedDB database on the user's device. Every create and every edit commits through the ADR-0004 §"Mutation round trip" protocol: `pushEvent` from the LiveView → server computes the new state in `socket.assigns` and issues `push_event("local_store:put", …)` with a `mutation_id` and next `seq` → the `LocalStore` hook opens one `readwrite` transaction across the affected stores plus `meta`, performs a compare-and-set on `meta.seq`, applies the changes, commits, and `pushEvent`s `local_store:ack` → the server clears the pending write and only then renders the record as saved (INV-24.2). If no ack arrives within the 2 000 ms budget, or the ack reports an error, the server renders the persistent, non-dismissible **"Not saved to this browser"** state on the affected record, keeps the optimistic value visible but visibly marked unsaved, offers export, and does not retry silently or roll back invisibly — the user is told the truth that the server holds this only until they close the tab.

Profile values persist in the browser's IndexedDB (`vehicles` store keyed by client-generated UUIDv4; `prefs` for unit preference; usage-profile answers written into the profile record; odometer readings written by `DOS-M05-004` to the `readings` store) and **re-hydrate on every LiveView mount and every reconnect** through the INV-24 hydration path. The Fly.io-hosted Phoenix LiveView server holds these values only in `socket.assigns` for the lifetime of one WebSocket and MUST NOT persist them to disk, database, cache, ETS table, external store, or log; the deployed application's Ecto repo list is exactly `[CatalogRepo]` opened read-only per ADR-0004 §"Enforcement", and no `UserRepo` is deployed. There are no accounts, no server-side per-user record, no third-party analytics, and no request payload that could reconstruct the profile from the outside. Interval candidates come from the server catalog query layer (`DOS-M09-005`) using only the impersonal `configuration_key` and operating condition per INV-26 — never the nickname, odometer, or any stable client identifier.

## Why this matters and what it unblocks

Forecasting requires clear user inputs and traceable recommendation provenance; the honesty rules of the product (INV-13 earlier threshold wins, INV-14 vehicle controls prevail, INV-15 no fabricated automotive facts, INV-16 requirements not brand folklore) begin at this profile because everything downstream reads the interval basis and usage classification it commits. Under the pre-pivot design that basis was a row in an on-device `UserRepo` SQLite database with ACID semantics; under ADR-0004 that basis lives in a browser IndexedDB store whose durability depends on the browser's storage-eviction policy, on `navigator.storage.persist()` being granted, on the user not clearing site data, and on every mutation completing an asynchronous round trip whose failure states did not exist in the old design. Getting the write path wrong here means either a false "saved" affordance (breaking INV-5 and INV-25) or a UI that loses the user's confirmed interval on a socket blip. That is the failure this card exists to prevent.

The dependency graph after the pivot: this card is built directly on `DOS-M09-001` (browser storage schema, `vehicles`/`prefs`/`meta` stores), `DOS-M09-002` (storage adapter with quota, persistence, and availability probes), `DOS-M09-003` (LiveView hydration protocol, mutation round trip, multi-tab consistency), `DOS-M09-005` (server-side catalog query layer for interval candidates, impersonal per INV-26), and — for the destructive replace flow's export-first offer — `DOS-M04-009` / `DOS-M05-007`. It consumes the wired-up context APIs from the rescoped `DOS-M05-001` and the committed exact-catalog selection from `DOS-M05-002`. It blocks `DOS-M05-004` (service history and odometer readings attach to this profile), `DOS-M05-005` (the dashboard renders the confirmed interval basis and the pre-hydration state around it), and `DOS-M06-001` (the forecast engine consumes the usage classification and interval basis established here — a card that SURVIVES the pivot per the reclassification, because the forecasting math is pure).

## Functional requirements

Each finding from the 2026-08-01 staleness sweep is addressed below and marked at its FR.

- **FR-1:** Interval candidates are presented in a typed resolution order (§9 recommendation resolver vocabulary: `verified`, `partial`, `conflict`, `unsupported`, `not_applicable`): an exact licensed OEM-derived schedule; explicitly qualified broader-configuration schedule labeled with reduced precision; or no sourced schedule. The candidate set is fetched from the `DOS-M09-005` catalog query layer using **only** the impersonal `configuration_key` and the operating condition selector — never the nickname, odometer value, note text, `mutation_id`, `tab_id`, or any stable client identifier (INV-26). No editorial interval is ever invented (INV-15).
- **FR-2:** A user MAY create a separate custom interval only after acknowledging that it is user-entered. Conflicting values MUST NOT be merged invisibly; a `conflict` result retains both facts for review and does not auto-select.
- **FR-3:** For every displayed candidate, the UI shows source, effective model/configuration, time and mileage thresholds, service condition, revision, and catalog verification date — reachable without leaving the profile (progressive disclosure), and always accompanied by the data-error reporting guidance from `CONSTITUTION.md` §8 / INV-21.
- **FR-4:** Oil product and filter selections are optional service metadata unless the catalog contains the exact evidence required by the M03/M04 contracts. A recorded product without evidence is displayed as metadata, never as a compatibility claim.
- **FR-5:** A product claim MAY add a stricter documented constraint but MUST NEVER extend or replace an earlier OEM/vehicle threshold (INV-13). Filter fitment MUST NEVER establish an oil-change interval.
- **FR-6:** Compatibility is reported only as "meets the recorded requirements" or "listed for this configuration" with its match basis and provenance — never as "present in curated data" and never as a universal safety or warranty guarantee (INV-15, INV-16, INV-21).
- **FR-7:** The user is required to confirm one interval basis or enter a custom interval. Custom intervals are clearly labeled "Your interval", require at least one of months or distance, and preserve the original sourced candidate for comparison.
- **FR-8:** Odometer input accepts the display unit, converts deterministically to canonical integer base miles, round-trips within one displayed unit, and rejects negative, nonfinite, or implausibly large values with a correctable field-level message that preserves user input. An older vehicle MUST NOT be rejected on age alone. The implausibly-large threshold is a documented value in the domain tests, not a magic number.
- **FR-9:** Replacing the only vehicle is a destructive operation: the UI shows what local history will be detached/deleted with counts, offers export-first (handing off to `DOS-M05-007`), and requires explicit confirmation. Replace runs through the `local_store:put` round trip and is atomic within the client IDB `readwrite` transaction — interruption mid-replace leaves either the old profile intact or the new profile fully committed, never a hybrid, and no orphaned vehicle-scoped rows in `events`/`readings`/`reminders` remain.
- **FR-10:** Editing disambiguating vehicle identity is implemented as **replace**, not an in-place mutation of the `vehicle_id`. Foreign-key semantics do not exist in IndexedDB; the client adapter therefore enforces the equivalent by scoping every `events`/`readings`/`reminders` record to a `vehicle_id` and refusing to rewrite that key in place.
- **FR-11:** A profile MAY be saved incomplete with an explicit setup-required state naming the missing interval dimension, but at least one interval dimension is required before the profile is "forecast ready." The incomplete state is a first-class rendered state, not a validation error.
- **FR-12 [REPLACES pre-pivot FR-12 — addresses sweep finding 1]:** Profile values persist in the browser's origin-scoped `dos_local` IndexedDB database (`vehicles` store keyed by client-generated UUIDv4; `prefs` store singleton for unit preference; `meta.seq` monotonic) and MUST re-hydrate on every LiveView mount and every reconnect through the INV-24 hydration path — not just on cold restart. Every create and every edit commits through the ADR-0004 §"Mutation round trip" six-step protocol: `pushEvent` from the LiveView; server assigns a `mutation_id` and next `seq`, records it in `assigns.pending_writes`, and renders optimistically with a **"saving"** affordance; server `push_event`s `local_store:put` with `{mutation_id, seq, upserts, deletes}`; hook opens one `readwrite` transaction across the affected stores plus `meta`, performs the compare-and-set on `meta.seq`, applies the changes, commits; hook `pushEvent`s `local_store:ack` `{mutation_id, seq, status: "ok"}`; server clears the pending write and only then renders the saved state (INV-24.2). The unit preference change is a `prefs` write on this same path and MUST NOT alter the canonical stored meaning of any numeric field. The pre-pivot claim that values persist through `UserRepo` context APIs is retired: the deployed application's Ecto repo list is exactly `[CatalogRepo]` opened read-only per ADR-0004 §"Enforcement", and no `UserRepo` exists in the deployment.
- **FR-13 [NEW — addresses sweep finding 1]:** If no `local_store:ack` arrives within the 2 000 ms budget, or the ack reports an error (including `QuotaExceededError` per INV-24.5), the server renders the persistent, non-dismissible **"Not saved to this browser"** state on the affected record; the optimistic value remains visible but is visibly marked unsaved; export is offered; and the copy states plainly that the server holds this only until the tab closes. There is no silent retry, and no invisible rollback. Silent write failure is a release blocker (INV-24.5).
- **FR-14 [NEW]:** Multi-tab profile edits obey the INV-24.7 discipline: every write is a compare-and-set on `meta.seq` inside the same transaction as the store change; a stale-`seq` write aborts and the hook pushes `local_store:conflict`, at which point the server discards its optimistic assign, triggers re-hydration, and shows a visible "reloaded from this browser's newer data" notice. `BroadcastChannel("dos_local_store")` broadcasts `{seq, mutation_id, tab_id}` after any successful commit so other tabs re-hydrate on the next broadcast rather than waiting for the next mount. Where `BroadcastChannel` is unavailable, the compare-and-set still prevents lost-update corruption; the loss simply surfaces at the next mount.
- **FR-15 [NEW — addresses sweep finding 1]:** No profile value (nickname, odometer, usage answer, unit preference, custom-interval value, custom-interval reason, product metadata) appears in server logs, error reports, crash traces, session recordings, or fixtures, and no such value is embedded in a URL, query string, or session cookie. Nickname and custom-interval text are treated as personal data and follow the ADR-0004 §"Logging" redaction rules. The `tab_id` from the hydration envelope is never logged. The `Logger` filter's `handle_event` param dropping applies to every profile mutation event (`vehicle_saved`, `plan_changed`, `usage_updated`, `nickname_updated`, `units_updated`, `vehicle_replaced`).
- **FR-16 [NEW — addresses sweep finding 1]:** Copy on every profile surface honors INV-25 and the prohibited-word list. The words "backup", "synced", "safe", "we'll remember", "your account", and "restore" MUST NOT appear on any profile surface. The framing "Stored in this browser" is required per INV-21. The "Not saved to this browser" state copy is authoritative and MUST NOT be softened. First-visit onboarding and the always-reachable storage-status affordance state that the profile lives in this browser on this device, that clearing site data destroys it, and that export is the only way to keep or move it.
- **FR-17 [NEW]:** Interval-candidate lookups obey INV-26 in payload as well as spirit: the socket frame carrying the resolve request contains only impersonal selectors (`configuration_key`, operating condition, and pagination cursors); no nickname, odometer, custom-interval value, or `vehicle_id` appears in the request path, query string, body, or socket payload. This is a testable payload audit at CI, not a code-review convention.

## Technical implementation contract

### Components and ownership boundaries

- **Profile screens** (rescoped per ADR-0004 §Decision item 6): the `SettingsLive` / vehicle-profile surfaces, `RecommendationLive`, `VehicleSummary`, `SourceBadge`, and `ProductPicker` render typed context results only. These modules are LiveViews and MAY reach for `Phoenix.LiveView` and `Plug`; they consume the `LocalStore` events but MUST NOT implement the wire protocol themselves — that is `DOS-M09-002`/`DOS-M09-003`.
- **Domain contexts** — `DigitalOilSticker.Garage` owns nickname, unit preference, and the archival/replace lifecycle; `DigitalOilSticker.Maintenance` owns plans and the interval basis; `DigitalOilSticker.Catalog` (server-side, read-only) supplies recommendation candidates and provenance through `DOS-M09-005`; the resolver's typed result vocabulary follows the §9 recommendation resolver. Per the ADR-0004 §"Enforcement" static check, `Garage`, `Maintenance`, `Catalog`, and the resolver MUST NOT reference `Phoenix.LiveView`, `Plug`, or `LocalStore` — they are client-agnostic Elixir domain modules that a future native client will reuse unchanged.
- **Interval resolution and precedence logic** live in domain code with golden tests. It is never re-implemented in a LiveView; a LiveView only renders resolver results.
- **Client-side** the `LocalStore` `phx-hook` from ADR-0004 owns the actual IndexedDB reads and writes for the profile's `vehicles` and `prefs` stores, including the compare-and-set on `meta.seq`. This card writes zero JavaScript of its own.

### Data and persistence

- **`vehicles` store** (ADR-0004 §"Storage layout"): key = client-generated UUIDv4; value carries nickname, catalog reference keys (year, make, model, configuration snapshots, `configuration_key`, support status, catalog `data_version`), operating condition, sourced miles/months/OLM rule snapshots with their requirement/source/version snapshots, and the optional explicit user override with reason. The custom interval is an **override field on the vehicle record**, never a mutation of the sourced snapshot, so the two are always comparable.
- **`prefs` store** (singleton): unit preference (imperial/metric), time-zone choice, dismissed-notice flags. Unit changes are a `prefs` write; they never alter canonical numeric meaning.
- **`meta` store** (singleton): `schema_version`, monotonic `seq`, `created_at`, `last_write_at`, `persist_granted`. Every profile write bumps `seq` in the same `readwrite` transaction as its store change under the compare-and-set discipline.
- **Odometer readings** write through the `DOS-M05-004` `readings` store contract in canonical integer base units; conversion happens at the boundary only.
- **Replace** archives the outgoing vehicle and its history per the confirmed preview: within one `readwrite` transaction across `vehicles`, `events`, `readings`, `reminders`, and `meta`, the old records are deleted and the new records upserted; interruption at any point leaves the transaction uncommitted and no orphaned rows remain. IndexedDB has no foreign keys; the adapter enforces `vehicle_id` scoping and the transaction contains both sides of the swap.
- **No `UserRepo` in the deployment.** ADR-0004 §"Enforcement" is a release-gating test: the deployed application's Ecto repo list MUST be exactly `[CatalogRepo]` and its connection MUST be opened read-only. This is not aspirational.

### Interfaces and events

- **LiveView `handle_event` callbacks** for the profile mutations (`save_vehicle`, `set_custom_interval`, `update_usage_profile`, `update_nickname`, `update_units`, `replace_vehicle`) compute the new state in `socket.assigns`, assign a `mutation_id` (UUID) and `seq = current_seq + 1`, record it in `assigns.pending_writes`, render optimistically with the "saving" affordance, then `push_event("local_store:put", {mutation_id, seq, upserts, deletes})` and wait for `local_store:ack` before rendering as saved (INV-24.2, FR-12).
- **Domain events** — `vehicle_saved`, `plan_changed` (marks forecasts stale), `usage_updated`, `nickname_updated`, `units_updated`, `vehicle_replaced` — fire in `socket.assigns` and drive UI updates; they never persist server-side. Their event names MAY appear in server logs; their params MUST NOT.
- **Catalog queries** (fetching interval candidates for a `configuration_key` and operating condition, returning a typed §9 result) route through `DOS-M09-005`. The request payload MUST carry only the impersonal selectors permitted by INV-26 (FR-17).
- **`local_store:conflict`** (client → server) is handled by discarding the optimistic assign, triggering re-hydration, and rendering the "reloaded from this browser's newer data" notice (FR-14).
- **The data-error reporting route required by INV-21** is presented as guidance (local instructions) and transmits nothing automatically.

### Failure and recovery behavior

- **Missing or partial catalog evidence** renders the honest states — "Source unavailable", "Exact configuration not verified", the reduced-precision label — rather than a guess (INV-11, INV-15). A `conflict` result shows no automatic product recommendation and retains both facts for review.
- **Validation failures** (odometer bounds; custom interval missing both dimensions) return correctable field-level messages that preserve user input.
- **Ack timeout or error** (2 000 ms budget) → the "Not saved to this browser" persistent state (FR-13). `QuotaExceededError` follows the same path with a quota-specific message per INV-24.5. The failed record's optimistic value is visibly marked unsaved and export is offered.
- **Replace atomicity** is a property of the client IDB `readwrite` transaction across `vehicles`/`events`/`readings`/`reminders`/`meta`. Either the old profile is intact or the new profile is fully committed; a socket blip mid-replace surfaces at the next mount as a re-hydration with the pre-replace state, not as a hybrid.
- **Stale catalog selection** during candidate fetch surfaces the `DOS-M05-001` stale-selection error with re-selection guidance; the profile is not committed on stale references.
- **Server payload out of sync** (server `schema_version` older than client's `dos_local` `schema_version`) puts the server into read-only mode with a "this browser holds data from a newer version of the app" banner and disables profile mutations until the deploy catches up. Downgrading or dropping unknown fields is prohibited.
- **`local_store:conflict`** (compare-and-set failure from a concurrent tab) → discard optimistic assign, re-hydrate, render "reloaded from this browser's newer data" (FR-14).
- **`BroadcastChannel` unavailable** (some private-browsing contexts) → degrade to per-mount hydration only; compare-and-set on `meta.seq` still prevents lost-update corruption at write time.

### Security and privacy

- **Personal data placement** (INV-23): nickname, odometer, usage answers, custom-interval values and reasons live **only** in the browser's `dos_local` IndexedDB and, transiently, in `socket.assigns` for the socket's lifetime. They MUST NOT be written to any server-side row, cache, ETS table, external store, or log (FR-15).
- **Transport** (INV-22): HTTPS with HSTS after certificate verification; the LiveView socket over WSS; `check_origin` restricted to the exact production hostnames; `protect_from_forgery` on the LiveView session; the session cookie carrying only the CSRF token and `live_socket_id`, with no personal data and no stable user identifier.
- **Impersonal catalog queries** (INV-26, FR-17): interval-candidate lookups carry only `configuration_key` + operating condition + pagination; a per-CI request-payload audit is a release gate.
- **Export-first offer** during replace hands off to the `DOS-M05-007` export path; nothing is transmitted, and the export file itself never routes through the server.
- **No third-party origins** touched by any profile surface — no fonts, no CDN scripts, no analytics, no error reporters (INV-4, INV-22 enforced structurally by the CSP owned by `DOS-M09-008`).
- **`debug_errors: false`** in production so no `assigns` (which may transiently carry the profile) reach an error page.

### Accessibility and performance

- All profile forms are keyboard/screen-reader operable with visible labels and correctable, announced validation messages, per the `DOS-M02-002` WCAG 2.2 AA contract. The "saving" affordance and the "Not saved to this browser" state each announce via live region so an AT user learns commit state without a visual cue. Focus does not move away from the field being edited on optimistic render; on ack failure focus moves to the "Not saved to this browser" affordance.
- Interactive controls MUST NOT accept input before the hydration state is known per INV-24.3 — profile screens render disabled skeletons under `assigns.local_state == :hydrating` and enable only on `:loaded` (existing profile) or `:empty` (genuine first visit).
- Provenance disclosure is reachable without leaving the profile (progressive disclosure), and destructive confirmations are fully accessible including a keyboard-only path.
- Interval-candidate resolution is a bounded server-side query set delivered over the LiveView socket. Concrete performance budgets are the CONSTITUTION §9 targets and the rescoped `DOS-M07-003`: LiveView round trip p95 ≤ 150 ms; catalog query p95 ≤ 250 ms for the first candidate page and ≤ 150 ms for subsequent filters; hydration completion p95 ≤ 300 ms after socket join; client storage footprint ≤ 1 MiB per 1 000 text-only records with a 5 MiB working ceiling. The pre-pivot single-SQLite-connection latency clause is retired — there is no single-SQLite-connection on the client, and the server's `CatalogRepo` uses the standard read pool.

## UX and content states

- **Interval basis states**: exact sourced schedule (with condition normal/severe); qualified broader-configuration schedule with reduced-precision label; no sourced schedule ("Source unavailable"); custom "Your interval" with the sourced candidate shown for comparison; `conflict` state retaining both facts without an automatic recommendation.
- **Profile save states**: `:hydrating` (skeleton, controls disabled, no empty-garage or onboarding-from-zero content); `:loaded` (existing profile rendered from hydrated assigns); `:empty` (genuine first visit — create flow); `:data_missing` (`localStorage.dos_boot_state == "has_data"` but hydration returned zero records — storage-loss warning with import offered, per ADR-0004 §"First-paint and empty-state rules"); `:storage_unavailable` (hydration deadline expired or hook reported IDB unavailable — read-only catalog browsing offered, no pretense of saving). See INV-24.3, INV-24.4, INV-24.6, INV-24.8.
- **Mutation states**: **"Saving"** (optimistic render, `mutation_id` in `pending_writes`); **saved** (only after `local_store:ack`); **"Not saved to this browser"** (persistent, non-dismissible; optimistic value visibly marked unsaved; export offered; copy names the specific record). Silent success without ack is prohibited.
- **Profile completeness states**: complete/forecast-ready; saved-incomplete with explicit setup-required state naming the missing interval dimension.
- **Product/filter metadata states**: recorded-as-metadata (free text or catalog product without claims evidence); evidence-backed "meets the recorded requirements" / "listed for this configuration" with match basis and provenance detail.
- **Destructive replace**: impact preview (what is detached/deleted, with counts), export-first offer, explicit confirmation; cancel returns without changes; interruption mid-transaction returns to the pre-replace state on re-hydration.
- **Every recommendation detail view** shows provider/document, source version/revision, retrieved/verified date, market and condition, and the data-error reporting route (`CONSTITUTION.md` §8 / INV-21).
- **Required framing** on every profile surface that could imply durability: "Stored in this browser". Prohibited words: "backup", "synced", "safe", "we'll remember", "your account", "restore" (INV-5, INV-21, INV-25).

## Rollout and rollback

Ships in the normal MVP build behind CI gates and deploys through the `DOS-M05-006` (rescoped) Fly.io pipeline established by `DOS-M09-006`. A deploy drops all WebSockets; clients auto-reconnect and re-run INV-24 hydration, at which point in-flight optimistic profile mutations are re-driven from IndexedDB (which is the source of truth per ADR-0004 §"WebSocket and LiveView considerations"). Rollback is a redeploy of the previous container image, restoring both the app and the catalog `data_version`; because there is no server-side personal data, rollback is data-loss-free for the profile by construction. If precedence copy or rules change after release, that is a new issue per `CHANGE_CONTROL.md` Rule 6 — never a silent edit to the surviving profile records. A stale-server / newer-client `schema_version` mismatch after a rollback puts the server in read-only mode with the ADR-0004 §"Schema versioning and migration" banner and disables profile mutations until the deploy catches up.

## Risks, decisions, and open questions

- **Risk (R1 from ADR-0004 — the single biggest product risk of the pivot):** browser eviction of infrequently-used site storage. A user who checks their oil once a quarter is exactly the profile most at risk. Mitigations bind at this card via the always-reachable INV-25 framing on every profile surface, the "Not saved to this browser" state that names loss honestly rather than showing an empty garage, the export-first offer on destructive replace, and the persistent-storage request wired in `DOS-M09-002`. Per-browser eviction behavior MUST be measured on the CONSTITUTION §9 matrix by `DOS-M09-009`, not asserted from documentation.
- **Risk (R4 from ADR-0004):** multi-tab conflict resolution is last-write-wins at record granularity, with the loss made visible. Accepted for MVP under the single-user assumption; the losing tab is told plainly. Re-examine on evidence — the specific worry is two tabs editing the same profile's usage classification concurrently.
- **Risk (R8 from ADR-0004):** single region, single always-on machine — Fly outage = total product outage; deploys drop all sockets. Accepted at MVP; the mitigation is that the client IndexedDB is the source of truth, so a deploy is a re-hydration event rather than a data-loss event (FR-12).
- **Risk:** users may still read a hosted URL as "my data is on their server" and expect a "restore" affordance that does not exist. Mitigated by the INV-25 framing on every profile surface, the required "Stored in this browser" language, and the prohibited-word list — but this is a copy-review-forever obligation, not a solved problem.
- **Decision to record:** the implausibly-large odometer threshold used by FR-8 validation, documented alongside the domain tests (a value, not a magic number).
- **Decision to record:** the exact `pending_writes` shape the LiveView carries in `assigns` — `%{mutation_id => %{seq: integer, kind: atom, optimistic_state: term(), started_at: monotonic_ms}}` — and the exact wording of the "Not saved to this browser" state, both fixed by `DOS-M02-003` copy review before this card can close.
- **Open question:** exact placement of the export-first offer inside the replace flow (before or within the confirmation step) — resolve with the `DOS-M02-003` design review; both satisfy FR-9.
- **Open question:** whether `local_store:conflict` on a profile write should re-render the just-attempted edit in the losing tab (so the user can retry against the newer state) or discard it silently under the last-write-wins-with-notification rule. Current default per FR-14 is to discard silently with the visible notice; upgrade to a retry affordance if user testing shows the silent path is surprising.

- Missing or partial catalog evidence renders the honest states ("Source unavailable", "Exact configuration not verified", reduced-precision label) rather than a guess; `conflict` results show no automatic product recommendation and retain both facts for review (§9).
- Validation failures (odometer bounds, custom interval missing both dimensions) return correctable field-level messages preserving user input.
- Replace is atomic within `UserRepo`; interruption mid-replace leaves either the old profile intact or the new profile fully committed, never a hybrid.
- Stale catalog selection during candidate fetch surfaces the DOS-M05-001 stale-selection error with re-selection guidance.

#### Security and privacy

- No VIN storage in this issue (excluded); nickname, odometer, and usage answers are local-only `UserRepo` facts, redacted from logs per §7.
- Export-first offer during replace hands off to the DOS-M05-007 export path; nothing is transmitted.
- No purchase links, no external product calls; all recommendation data comes from the bundled catalog.

#### Accessibility and performance

- All forms are keyboard/screen-reader operable with visible labels and correctable, announced validation messages, consistent with the M02 contract and the DOS-M05-002 control standards.
- Provenance disclosure is reachable without leaving the profile (progressive disclosure), and destructive confirmations are fully accessible.
- Candidate resolution is a bounded local query set; no interaction blocks the single SQLite connection for perceptible time (budgets per DOS-M07-003).
