## Outcome

Users can add, correct, and delete oil-change events and mileage observations without corrupting the timeline or silently rewriting forecasts.

## Why this matters and what it unblocks

The last completed service and mileage trajectory are the core facts for the digital sticker and the M06 forecast engine. If the history can be corrupted by an edit, a double-submit, or an odometer discontinuity, every downstream target date and reminder is untrustworthy. This issue blocks DOS-M05-005 (the dashboard reads the latest service and latest valid reading), DOS-M06-002 and DOS-M06-003 (the forecast engine consumes valid reading segments), and DOS-M06-006.

- §9 Forecast reference behavior: reject or quarantine negative distance, duplicate-time contradictions, implausible values, and superseded readings — never silently delete them; the odometer-reset path starts a new segment.
- DOS-M05-001 context APIs, `Ecto.Multi` transaction rules, idempotency guards, and event contract; DOS-M05-003 profile and unit semantics.

## Included

- Add, edit, and delete of oil-change events and independent odometer readings.
- Validation of dates, odometer values, ordering, and units.
- Oil/filter notes: optional oil product ID/free-text note and filter product ID/free-text note per event, plus an optional general note.
- Service date and service odometer capture.
- Independent odometer readings separate from service events.
- Chronological history view (newest-first default) exposing source and edits.
- Undo where safe: soft deletion with an in-session undo window before permanent purge.
- Documented odometer-reset/replacement path recording a discontinuity and starting a new forecast segment.
- Forecast/notification staleness invalidation in the same transaction as any history mutation.

## Excluded

- Receipt images.
- Shop integrations.
- GPS.
- Automatic odometer capture.
- Shared history.

## Preconditions

- DOS-M05-001 is closed: `Maintenance` context, `Ecto.Multi` same-database transactions, idempotency guards, typed errors, and events exist.
- DOS-M05-003 is closed: an active vehicle profile with unit preference and (possibly incomplete) interval basis exists to attach history to.
- M02 copy for validation messages, undo, delete confirmation, and empty states is ratified.

## Functional requirements

- FR-1: A service event contains stable ID, vehicle ID, local service date, odometer, entered unit/original value, optional oil product ID/free-text note, optional filter product ID/free-text note, optional general note, created/updated instants, and soft-deletion metadata during the undo window.
- FR-2: Odometer readings contain observation date, mileage, source (`service_event`, `manual`, later `import`), and source reference.
- FR-3: Editing a service event updates its linked observation atomically. Deleting it removes or tombstones only its linked reading, never an independently entered reading at the same date.
- FR-4: Permit same-day readings only when their ordering and latest value are explicit; reject a reading below the preceding reading or above a later reading unless the user invokes a documented odometer-reset/replacement path.
- FR-5: The MVP reset path records a discontinuity and starts a new forecast segment rather than altering history.
- FR-6: Future service dates and future observation dates are rejected. Dates before the vehicle model year produce a warning and require correction.
- FR-7: Notes are local plain text, length-limited, and rendered without HTML.
- FR-8: The history defaults newest-first, exposes source and edits, and never calls a record "manufacturer verified."
- FR-9: Delete requires confirmation and offers an in-session undo before permanent purge.
- FR-10: Any history mutation marks derived forecast and notification plans stale in the same transaction (per the DOS-M05-001 invalidation contract).
- FR-11: Timeline-constraint violations identify the exact conflicting readings and preserve the user's unsaved form values.
- FR-12: All flows work fully offline; recording a new oil change closes the previous cycle per §6 step 8 (cycle bookkeeping via `Maintenance`; forecast recomputation itself is M06).

## Technical implementation contract

### Components and ownership boundaries

- `OilChangeLive` (event add/edit), `MileageLive` (readings and check-ins), and the history surface render typed `Maintenance` context results; validation and timeline rules live in domain code, never in LiveViews.
- `Maintenance` owns service events, cycles, and linked-reading atomicity; `Garage` supplies the active vehicle; `Clock` (§7) supplies injected time so future-date validation is testable.
- Undo/soft-delete state is domain-owned (`UserRepo` metadata), not socket state, so it survives reconnect within its window.

### Data and persistence

- Writes target `service_events` and `odometer_readings` exactly as specified in §8 and FR-1/FR-2; odometer values persist in the canonical integer base unit with the entered unit/original value retained.
- Linked mutations (event plus its reading plus staleness marks) run in one `Ecto.Multi` wholly inside `UserRepo` (DOS-M05-001 FR-4).
- Soft deletion uses tombstone/validity fields during the undo window; permanent purge is a separate explicit step; independently entered readings at the same date are never collaterally removed.
- The odometer-reset path writes an explicit discontinuity marker consistent with §9 segment semantics so M06 can start a new segment without reinterpreting history.

### Interfaces and events

- Context APIs: create/edit/delete service event, create/edit/delete manual reading, list history (newest-first, paged), invoke reset/discontinuity path, undo within window.
- Every committed mutation publishes `service_event_recorded` or `odometer_recorded` with reason codes and marks forecast/notification plans stale in-transaction (FR-10); M06 subscribes to these events.
- Mutating APIs accept the DOS-M05-001 idempotency token/revision guard; double-submit returns the original result.

### Failure and recovery behavior

- Concurrent double-submit, app termination, and retries leave service events and readings referentially consistent with at most one committed mutation.
- Validation failures return field-level, correctable errors naming the exact conflicting readings, and unsaved form values are preserved.
- Storage-level failures (disk-full, corruption) surface the DOS-M05-001 typed recovery states without losing committed history.
- Undo after reconnect: the in-session undo window is honored if still open; expiry purges per FR-9 semantics without surprising resurrection.

### Security and privacy

- Notes are local plain text, length-limited, rendered without HTML (FR-7) — no rich text, no script injection surface in the WebView.
- History never leaves the device; logs and fixtures redact mileage and note content per §7.
- Source and edit exposure (FR-8) is an audit surface for the user, not telemetry.

### Accessibility and performance

- Validation summaries and field errors are announced to assistive technology; the accessibility snapshot of the validation summary is required evidence.
- Delete confirmation and undo controls are keyboard/screen-reader operable with visible labels and adequate touch targets (consistent with DOS-M05-002 standards).
- History list is paged; rendering stays responsive with multi-year histories under the DOS-M07-003 budgets.

## UX and content states

- Empty history: tells the user the next useful action (record the first oil change).
- Incomplete event: names the missing fields and the next useful action.
- Populated history: newest-first, each entry showing source (`service_event`/`manual`), edit lineage, and provenance mode (`catalog` or `manual`) — never "manufacturer verified."
- Validation states: future-date rejection; before-model-year warning requiring correction; ordering conflicts naming the exact conflicting readings with unsaved input preserved.
- Reset/discontinuity flow: documented explanation that a new forecast segment starts and history is not rewritten.
- Delete flow: confirmation, then in-session undo affordance until the window closes.

## Test plan

### Automated

- State-machine/domain tests for event and reading lifecycles, linked-reading atomicity, and the reset/discontinuity path.
- Transaction and idempotency tests: double-submit, retry, and interruption produce at most one committed mutation with in-transaction staleness marks (AC-3, AC-4).
- Boundary tests for same day, leap day, unit conversion, odometer discontinuity, and future dates.
- Tests proving deletion tombstones only the linked reading and never an independent same-date reading.
- Note sanitization tests: length limits and HTML-free rendering.

### Manual/device matrix

- E2E CRUD flow in airplane mode on packaged iOS and Android builds: create, later readings, edit, delete, undo (AC-1).
- Accessibility snapshot of the validation summary plus a screen-reader pass over confirmation/undo.
- App-termination-during-save spot check on device confirming committed-or-absent semantics.

## Rollout and rollback

Ships in the normal MVP build behind CI gates. Rollback is reverting the history slice; committed `service_events`/`odometer_readings` rows follow M04 migration/rollback rules and are never reset. The undo window is an in-session UX affordance, not a schema behavior, so reverting code cannot corrupt stored history.

## Risks, decisions, and open questions

- Risk: same-day ordering semantics are a classic source of silent corruption; FR-4's explicit-ordering requirement plus boundary tests are the mitigation.
- Risk: users may expect edit of an old event to retroactively rewrite analysis; correction lineage (§8) plus staleness events keep derived data honest instead.
- Decision to record: the undo-window duration and the permanent-purge trigger, documented with the domain tests.
- Decision to record: the length limit for notes (FR-7), documented with sanitization tests.
- Open question: whether the `import` reading source (future DOS-M05-007/M08 use) is created now as an enum value or added by migration later — resolve with the M04 data dictionary; §8 already names it as a later source.

## Definition of done

All acceptance criteria pass; automated suites are green in CI; the airplane-mode E2E recording, accessibility snapshot, and boundary-test results are attached; staleness invalidation is proven in-transaction; and M06 can consume the event stream and valid reading segments without reinterpretation.
