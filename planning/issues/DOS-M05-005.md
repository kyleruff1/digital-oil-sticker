> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The dashboard must render a determinate pre-hydration state, must not flash a false empty garage, and must never imply the record is backed up on the server it is loaded from._

## Outcome

The single-vehicle digital oil sticker dashboard renders in a hosted Phoenix LiveView served from Fly.io at `digitaloilsticker.com`, using only facts hydrated from the user's own browser IndexedDB into the socket's assigns for the lifetime of one connection. First paint is determinate — a neutral skeleton that admits it does not yet know whether data exists — and it never, not even for a single frame, tells a user with a full garage that their garage is empty (INV-24.3). Once hydration resolves, the dashboard shows which vehicle is active, when and where the last oil change occurred, the selected interval, the deterministic date and mileage thresholds, and what information is missing, with the DOS-M09-003 storage state (loaded, cleared/evicted, storage-unavailable, session-only) surfaced honestly. Nothing anywhere on the surface implies the record is backed up on the server the page is loaded from; "Stored in this browser" is the required framing (INV-21, INV-25). No estimated arrival date appears — that vocabulary belongs to M06.

## Why this matters and what it unblocks

The dashboard is the MVP's primary value surface and now also the surface where the browser architecture's central promise either holds or quietly breaks. Under ADR-0004 the server holds no personal row and the URL naturally reads to users as "my data is on their server"; the pivot document is explicit that INV-5 gets *harder* under a hosted URL, not easier, and that the dashboard's copy must actively contradict the implicit backup assumption. A false empty-garage flash on any reconnect (network blip, deploy, sleep/wake, tab restore) would be read as data loss; a `:storage_unavailable` case rendered as an empty state would be a silent lie about durability. Both are release-blocking under INV-24.3–24.8 and INV-25.

This card composes what the M09 subsystem produces — the storage schema (DOS-M09-001), the storage adapter (DOS-M09-002), the hydration and storage-state UX contract (DOS-M09-003), and the impersonal catalog query surface (DOS-M09-005) — into the first LiveView the user sees. It blocks DOS-M06-003 and DOS-M06-004 (the M06 forecast engine and its presentation extend this dashboard's honesty contract) and DOS-M08-002 (the multi-vehicle web garage evolves this shell). Its state vocabulary and copy discipline are what the M06 estimator will inherit and extend.

## Functional requirements

Findings from the 2026-08-01 staleness sweep are addressed inline in each FR that changes; retirements are marked explicitly.

- **FR-1 (addresses finding 1 — replaces pre-pivot FR-10 and AC-2):** `StickerLive.mount/3` runs with an empty server-side view of the user's world and MUST render a determinate pre-hydration first paint — a neutral skeleton, driven by the non-personal `dos_boot_state` hint, that admits it does not yet know whether data exists. The dashboard MUST NOT render "You have no vehicles yet", any onboarding-from-zero flow, or any empty-garage claim while `assigns.local_state == :hydrating`, not even for a single frame (INV-24.3). The pre-pivot FR-10 ("The dashboard renders entirely from local data, reaching usable content without any online spinner") is **retired**: in the hosted MVP the LiveView server is the renderer and a network-blocked client cannot reach usable content at all (INV-6 amended).
- **FR-2 (addresses finding 1 — hydration round-trip budget):** After socket connect the JS hook (`phx-hook="LocalStore"`) MUST open `dos_local`, read the user's records in one readonly IndexedDB transaction, and `pushEvent("local_store:hydrate", envelope)` to `StickerLive`, which validates the envelope through the DOS-M09-001 changeset per `schema_version`, places the result in `assigns`, and transitions `local_state` from `:hydrating` to `:loaded` or `:empty`. The full mount → hook read → snapshot → validated assigns round trip MUST meet the Constitution §9 provisional hydration budget (p95 ≤ 300 ms after socket join). A 5 000 ms `hydration_deadline` timer bounds the wait; on expiry `StickerLive` MUST transition to `:storage_unavailable`, never hang (INV-24.3).
- **FR-3 (addresses finding 1 — honest storage-state UX per DOS-M09-003):** `StickerLive` MUST render the five distinct storage states defined by DOS-M09-003 with the copy ratified there — genuine first visit (`:empty`), loaded (`:loaded`), cleared-or-evicted (`:data_missing` when `dos_boot_state == "has_data"` but hydration returns zero records), storage-unavailable (`:storage_unavailable`), and session-only (session-only mode) — each with its own affordances and no shared "something went wrong" fallback. Silently rendering a fresh empty garage to a user who had data is a release-blocking violation of INV-24.4 and INV-25.
- **FR-4 (reconnect behavior):** LiveView reconnect (network blip, deploy, sleep/wake) MUST re-run the FR-2 hydration path; `StickerLive` MUST NOT assume `socket.assigns` survived. During reconnection `phx-disconnected` styling MUST communicate the state honestly without tearing the populated view back to a skeleton (ADR-0004 §"WebSocket and LiveView considerations"; INV-7 amended).
- **FR-5 (retained from pre-pivot FR-1):** Deterministic baseline targets are `target_odometer = service_odometer + interval_distance` and `target_date = service_date + interval_months` using calendar-month arithmetic with end-of-month clamping. These are thresholds; they are **not** the M06 estimated arrival date. Implemented as pure domain functions in `Maintenance` and called from `StickerLive` — no arithmetic in the LiveView (§9 principle; INV-15).
- **FR-6 (retained from pre-pivot FR-2):** When both time and distance dimensions exist, render "Service at whichever comes first." (INV-13). If one is absent, render only the available dimension.
- **FR-7 (retained from pre-pivot FR-3):** A threshold already passed is "Past due by recorded data." Absence of a recent odometer reading is "Mileage status unknown," never "on track" (INV-11, INV-15).
- **FR-8 (retained from pre-pivot FR-4):** The current odometer is the latest valid reading in the current segment per DOS-M05-004's discontinuity semantics. Show its as-of date. M05 never substitutes an estimated current odometer.
- **FR-9 (retained from pre-pivot FR-5):** Progress visuals carry equivalent text, do not rely on color, clamp visual fill to 0–100% while textual overdue amounts remain accurate, and treat zero or invalid intervals as data errors with corrective navigation.
- **FR-10 (retained from pre-pivot FR-6):** The reviewed OLM/owner-manual reminder disclaimer is prominently shown in every populated state: "Digital Oil Sticker is a reminder, not a replacement for the owner's manual or the vehicle's oil-life monitor. Follow an earlier warning." (INV-14, INV-20).
- **FR-11 (retained from pre-pivot FR-7):** All dates are locale-formatted from stored calendar dates; calculations remain timezone-independent in this milestone.
- **FR-12 (retained from pre-pivot FR-8):** No forecast, estimate, or "arrival" date appears anywhere in this dashboard before the M06 inputs and algorithm ship. The build MUST assert this structurally.
- **FR-13 (retained from pre-pivot FR-9):** Critical provenance and the OLM/owner-manual warning are reachable via in-place disclosure without opening a separate legal page (INV-15).
- **FR-14 (new — addresses finding 1's INV-5-adjacent framing risk):** The dashboard MUST use the "Stored in this browser" framing (INV-21) and MUST make a plain-language statement that records live only in this browser on this device — no account, no server copy — reachable at any time from the dashboard, not only at first visit (INV-25). Prohibited on this surface: "backup", "synced", "safe", "saved to your account", "we'll remember", "restore". A hosted URL naturally reads as "my data is on their server" and the copy MUST actively contradict that assumption (pivot §"Architectural consequences" item 1).
- **FR-15 (new — INV-17 amended, in-app due state only):** Due/overdue state is computed on hydration and after each mutation and is displayed **only** in this dashboard. The surface MUST state plainly that the app does not notify the user when it is closed. The dashboard MUST NOT expose a disabled reminder-permission control, a scheduled-notification affordance, or any wording that implies background alerting (INV-19).
- **FR-16 (new — INV-26 impersonal catalog access):** Any catalog reference the dashboard resolves (interval basis provenance label, product/filter identity for the summary) MUST go through the DOS-M09-005 query surface, whose selectors carry no VIN, odometer, note, or client identifier. `StickerLive` MUST NOT build its own catalog query. A catalog reference resolved to `unsupported` (because a `data_version` moved) MUST render as such per INV-11, not as an error.
- **FR-17 (new — WCAG for browser assistive technology):** The dashboard MUST be usable at 320 CSS px reflow width, 200% text zoom, full keyboard operability with a visible focus indicator, and representative screen-reader navigation on the DOS-M09-009 browser/engine matrix. Due-state changes and hydration state transitions MUST be announced via ARIA live regions (Constitution §9 accessibility row).
- **FR-18 (new — honest transport and structural privacy):** All application traffic MUST be served over HTTPS with HSTS and WSS for the LiveView socket (INV-22). This LiveView MUST NOT embed any third-party origin (CDN, font provider, analytic, tag manager, error reporter) — the CSP forbids it structurally. `handle_event` param logging MUST be filtered so no odometer, VIN, date, note, custom vehicle name, or hydration/mutation payload reaches a log line (INV-4, ADR-0004 §"Logging").

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilStickerWeb.StickerLive` mounts the shell, drives the hydration protocol, and composes `VehicleSummary`, `DueStatus`, `SourceBadge`, and progress components inside `AppShell`. All facts arrive as typed context view models from `DigitalOilSticker.Maintenance` and `DigitalOilSticker.Garage`; the LiveView performs no arithmetic and no catalog SQL.
- The `LocalStore` `phx-hook` is the sole client-side owner of IndexedDB access for the dashboard; it is the DOS-M09-002 storage adapter surfaced to LiveView.
- State selection (which honest state applies) is domain logic returning a state code; the LiveView maps codes to reviewed copy from DOS-M02-003 and DOS-M09-003.
- Per ADR-0004 §"Enforcement" the domain namespaces (`DigitalOilSticker.Maintenance`, `.Garage`, `.Catalog`, `.Forecast`) MUST NOT reference `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules; a static test enforces this so a future native client can reuse them unchanged.

### Data and persistence

- **Server side:** the deployed application has exactly one Ecto repo, `DigitalOilSticker.CatalogRepo`, opened read-only. `StickerLive` performs no personal writes to any server store, cache, ETS table, external store, or log. Personal data exists on the server only as transient values in `socket.assigns` for the lifetime of one LiveView connection and dies with the socket (INV-23, INV-24.1).
- **Client side:** all personal facts — active vehicle snapshot, confirmed interval basis, latest service event, latest valid odometer reading in the current segment, preferences — are read from the origin-scoped IndexedDB database `dos_local` (schema owned by DOS-M09-001) into a versioned envelope, validated on the server, and placed in assigns.
- Distances convert at the boundary from canonical integer base units into the profile's display unit; the stored client payload keeps canonical units.
- Derived values (targets, progress percentages) are computed on render from the hydrated facts. Forecast snapshots and any persisted derived state belong to M06.

### Interfaces and events

- **Hydration:** `handle_event("local_store:hydrate", envelope, socket)` validates the envelope against the current `schema_version` changeset, migrates the payload if older per DOS-M09-001, and — if migration changed the payload — immediately `push_event`s `local_store:put` so the client's storage is upgraded in the same round trip.
- **Dashboard queries:** a single `Maintenance.dashboard_view_model/2` returns identity, interval basis with type/provenance, last service, current recorded odometer with as-of date, computed targets, applicable state codes, and any DOS-M09-005 catalog resolutions.
- **Mutation subscription:** the dashboard subscribes to the DOS-M05-001 events (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`) to re-render after mutations; every mutation is a `pushEvent` → server → `local_store:put` → hook commit → `local_store:ack` round trip and is NOT presented as committed until the hook acknowledges (INV-24.2).
- **Navigation:** profile edit (DOS-M05-003), history (DOS-M05-004), provenance detail (in-place disclosure per FR-13). Every route is a real, shareable URL with browser history and refresh semantics (DOS-M02-001 re-scoped).

### Failure and recovery behavior

- `:hydrating` timeout → `:storage_unavailable` with the DOS-M09-003 copy and export/read-only-catalog affordance offered (INV-24.6).
- Envelope validation failure → the valid subset hydrates, invalid records are held aside in a quarantine list, and the UI shows exactly what could not be read plus an export of the raw payload for recovery (ADR-0004 §"Validation").
- A `local_store:put` write not acknowledged within the DOS-M09-002 timeout renders the persistent "Not saved to this browser" state on the affected record, keeps the optimistic value visible but visibly marked as unsaved, and offers export (INV-24.5).
- `dos_boot_state == "has_data"` with zero records returned → `:data_missing` warning with the honest storage-loss copy from DOS-M09-003, not an empty state (INV-24.4, INV-24.8).
- A LiveView reconnect re-runs the FR-2 hydration path; pending writes are re-driven from client storage (the source of truth), so a deploy or network blip during an unsaved mutation is not silent data loss.
- Catalog query failure via DOS-M09-005 renders as an honest connection or `unsupported` state per INV-7 and INV-11 — never as absent user data and never as a fabricated fallback.

### Security and privacy

- HTTPS with HSTS, WSS for the socket, CSRF-protected connect (INV-22).
- The CSP served by every response forbids third-party origins including for scripts, styles, fonts, images, and connect targets; no CDN, no Google Fonts, no external error reporter (INV-4, INV-22, ADR-0004 §"Content Security Policy").
- The session cookie carries no personal data and no stable user identifier — only the CSRF token and `live_socket_id` (ADR-0004 §"CSRF and session").
- `handle_event` params are filtered from logs by an allowlist; `debug_errors: false` in production so no assigns reach an error page (INV-4).
- Catalog access is impersonal (INV-26) — no VIN, odometer, note, or client identifier reaches any wire request originating from this LiveView.

### Accessibility and performance

- Provisional targets from Constitution §9: page load LCP p75 ≤ 2.5 s on a 4G-class connection; TTI / first interaction ready p75 ≤ 3.5 s; hydration completion p95 ≤ 300 ms after socket join; LiveView event round trip p95 ≤ 150 ms measured from the client; zero third-party origins on this page.
- WCAG 2.2 AA per Constitution §9 accessibility row: text contrast ≥ 4.5:1; usable at 200% zoom and 320 CSS px reflow; full keyboard operability with a visible focus indicator and no keyboard traps; target size ≥ 24×24 CSS px; live-region announcement of due-state and hydration changes.
- Progress semantics carry equivalent text and never rely on color alone.

## UX and content states

Every populated state includes the FR-10 disclaimer, the FR-13 provenance access, and the FR-14 "Stored in this browser" framing.

- **Pre-hydration first paint (`:hydrating`):** neutral skeleton, driven by `dos_boot_state`; never an empty-garage or onboarding claim (INV-24.3).
- **Loaded — both dimensions (`:loaded`):** "Service at whichever comes first." with computed target date and target odometer.
- **Loaded — one-dimension (`:loaded`):** time-only or distance-only, rendering only the available dimension.
- **Loaded — overdue:** "Past due by recorded data" with accurate textual overdue amount and clamped visual fill.
- **Loaded — missing reading:** "Mileage status unknown," never "on track."
- **Loaded — month-end and leap-year targets:** end-of-month clamping in evidence text.
- **Loaded — odometer-reset segment:** current reading from the current segment per DOS-M05-004 discontinuity.
- **Genuine first visit (`:empty`):** setup-required copy naming the next useful action; distinguishable from `:data_missing` in wording (INV-25).
- **Cleared-or-evicted (`:data_missing`):** "Your browser appears to have cleared this data. There is no server copy. Import from an export to restore it." with import affordance and a link to the export/import surface (DOS-M05-007 re-scoped).
- **Storage-unavailable (`:storage_unavailable`):** plain-language explanation that this browser is not letting the app save records, with read-only catalog browsing offered and export/import guidance (DOS-M09-003 copy).
- **Session-only mode:** persistent banner stating that nothing is being saved and closing the tab loses everything, with export offered prominently and repeatedly; the dashboard content still renders from session assigns for the connection lifetime (ADR-0004 §"Private browsing and blocked storage").
- **Reconnect / `phx-disconnected`:** populated view retained with the disconnect styling; no tear-down to skeleton (INV-7 amended).
- **Data-error state:** zero or invalid interval treated as a data error with corrective navigation to DOS-M05-003, not a 0%-progress lie.

## Test plan

### Automated

- Pure domain unit tests: calendar-month addition with end-of-month clamping (including leap years), distance targets in canonical units, unit-boundary conversion.
- State-selection tests mapping every input combination to its exact state code and copy string, including the five storage states from DOS-M09-003.

## Rollout and rollback

Ships in the normal MVP release behind CI gates and the DOS-M09-006 Fly.io deploy pipeline. A release is a Docker image with the catalog artifact baked in (ADR-0004 §"Catalog database on Fly"); rollback is redeploying the previous immutable release identifier. Deploys drop every WebSocket by design; reconnect re-runs hydration idempotently, and unsaved mutations are re-driven from client storage — this is precisely why FR-2 must be sub-second and visually non-destructive. Secret rotation invalidates signed session cookies and LiveView socket tokens; clients reconnect and re-hydrate; no user data is lost.

## Risks, decisions, and open questions

- **Risk (ADR-0004 R1, the single biggest product risk of the pivot):** browser eviction of infrequently-used site storage means a quarterly-oil-change user is exactly the profile most at risk. Mitigations here: the FR-3 `:data_missing` state, the FR-14 honest framing, and the export nudges from DOS-M09-003. Actual per-browser eviction behavior is measured, not assumed, on the DOS-M09-009 matrix.
- **Risk:** the dashboard reads as "my data is on their server" simply because it is loaded from one. Mitigation: FR-14 copy discipline plus the AC-8 linter. This risk was not present in the pre-pivot on-device design and is why finding 1's third bullet becomes a first-class FR.
- **Risk:** hydration round trip adds latency to first meaningful paint on every mount, including every reconnect. Mitigation: the FR-2 budget and the AC-3 measurement; if measurement misses budget, the skeleton state becomes the dominant impression and this card's gate holds until the DOS-M09-002 adapter closes the gap.
- **Risk:** subtle date arithmetic (month-end clamping, leap years) diverging between display and future M06 computation; mitigated by shared pure functions in `Maintenance` and golden tests (§9 principle: no screen implements its own arithmetic).
- **Risk:** honest states reading as "broken app" to users; mitigated by DOS-M02-003 next-action copy in every empty/unknown state.
- **Decision to record:** the exact visual design of dual-threshold progress (two indicators vs. combined), resolved with M02 design assets; either must satisfy FR-9.
- **Open question:** whether a service-worker / PWA offline mode would let the dashboard render user data during a network outage. That is an ADR-level decision (ADR-0004 §"Consequences") and DOS-M09-010, not something this card may partially ship (INV-19).

### Functional requirements (pre-pivot)

- FR-1: Deterministic baseline targets are `target_odometer = service_odometer + interval_distance` and `target_date = service_date + interval_months` using calendar-month arithmetic with end-of-month clamping. These are thresholds, not the M06 estimated arrival date.
- FR-2: When both dimensions exist, state "Service at whichever comes first." If one is absent, render only the available dimension.
- FR-3: A threshold already passed is "Past due by recorded data," while absence of a recent odometer is "Mileage status unknown," not "on track."
- FR-4: The current odometer is the latest valid reading in the current odometer segment. Show its as-of date. Never substitute an estimated current odometer in M05.
- FR-5: Progress visuals have equivalent text, do not rely on color, clamp visual fill to 0–100% while textual overdue amounts remain accurate, and handle zero/invalid intervals as data errors.
- FR-6: Prominently show: "Digital Oil Sticker is a reminder, not a replacement for the owner's manual or the vehicle's oil-life monitor. Follow an earlier warning." Use reviewed wording, not diagnosis or warranty advice.
- FR-7: All dates are locale-formatted from stored calendar dates; all calculations remain timezone-independent in this milestone.
- FR-8: No forecast/estimated date appears anywhere before M06 inputs and algorithm are present.
- FR-9: Critical data provenance and the OLM/owner-manual warning are reachable without opening a legal page.
- FR-10: The dashboard renders entirely from local data, reaching usable content without any online spinner, and links to profile edit and history.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

- `StickerLive` composes `VehicleSummary`, `DueStatus`, `SourceBadge`, and progress components inside `AppShell`; all facts arrive as typed context view models from `Garage`/`Maintenance` (DOS-M05-001).
- Target-date/odometer arithmetic is implemented once as pure domain functions (calendar-month addition with end-of-month clamping, distance addition in canonical units) with unit tests; no screen implements its own arithmetic (§9 principle).
- State selection (which honest state applies) is domain logic returning a state code; the LiveView maps codes to reviewed copy.

#### Data and persistence

- Read-only over `UserRepo` facts: active vehicle snapshot, confirmed `maintenance_plans` basis, latest `service_events` row, latest valid `odometer_readings` in the current segment (respecting DOS-M05-004 discontinuities).
- No new tables and no dashboard-owned persistence; derived values are computed on render from committed facts (forecast snapshots belong to M06).
- Distances convert at the boundary from canonical integer base units into the profile's display unit.

#### Interfaces and events

- A single context query returns the dashboard view model: identity, interval basis with type/provenance, last service, current recorded odometer with as-of date, computed targets, and the applicable state codes.
- The dashboard subscribes to the DOS-M05-001 events (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`) to re-render after mutations; it publishes none.
- Navigation targets: profile edit (DOS-M05-003), history (DOS-M05-004), provenance detail (in-place disclosure per FR-9).

#### Failure and recovery behavior

- Zero or invalid intervals render as data errors with corrective navigation, never as a 0%-progress lie (FR-5).
- Missing inputs degrade to the specific honest state (setup-required, "Mileage status unknown", single-dimension) rather than a generic error.
- Storage/catalog failure states inherit the DOS-M05-001 typed recovery vocabulary; the dashboard never renders stale committed state as fresh after recovery.

#### Security and privacy

- Fully local rendering; network blocked changes nothing (AC-2 evidence). No analytics, no remote assets.
- Displayed odometer/notes summaries follow §7 redaction rules in logs and fixtures.

#### Accessibility and performance

- Screen is usable at 320 CSS px, 200% text zoom, keyboard only, and representative screen-reader navigation; progress semantics carry equivalent text and never rely on color alone.
- Cold-start to usable dashboard content meets the offline no-spinner requirement; formal timing budgets live in DOS-M07-003.
