## Outcome

The home screen answers, at a glance and without overclaiming: which vehicle is active, when/where the last oil change occurred, the selected interval, the mileage/date thresholds, and what information is missing.

## Why this matters and what it unblocks

This is the MVP's primary value surface and establishes the presentation contract that the M06 estimator and reminders will extend. The dashboard is the "digital sticker" of the product mission (§2, §6 step 7): if it overstates certainty, invents an estimated date before M06, or hides missing data, the product's core honesty promise fails. It blocks DOS-M06-003 and DOS-M06-004 (estimator and reminder surfaces extend this contract) and DOS-M08-002.

## Included

- Latest-service card (date, odometer, recorded oil/filter metadata summary).
- Target date and target odometer calculated directly from the selected interval.
- Current recorded odometer with its as-of date.
- Progress indicators toward both thresholds with equivalent text.
- Source label for the interval basis (sourced vs. "Your interval", with provenance access).
- Setup, empty, and error states.
- Navigation to edit (profile) and history.
- The prominent reminder disclaimer with reviewed wording.

## Excluded

- Predictive usage date.
- Notification scheduling.
- OLM percentage.
- Multi-vehicle tabs.
- Celebratory claims that maintenance is "safe."

## Preconditions

- DOS-M05-002, DOS-M05-003, and DOS-M05-004 are closed: a committed identity, a confirmed (or explicitly incomplete) interval basis, and an auditable history exist to render.
- M02 dashboard copy — including the disclaimer and every honest-state wording — is ratified.

## Functional requirements

- FR-1: Deterministic baseline targets are `target_odometer = service_odometer + interval_distance` and `target_date = service_date + interval_months` using calendar-month arithmetic with end-of-month clamping. These are thresholds, not the M06 estimated arrival date.
- FR-2: When both dimensions exist, state "Service at whichever comes first." If one is absent, render only the available dimension.
- FR-3: A threshold already passed is "Past due by recorded data," while absence of a recent odometer is "Mileage status unknown," not "on track."
- FR-4: The current odometer is the latest valid reading in the current odometer segment. Show its as-of date. Never substitute an estimated current odometer in M05.
- FR-5: Progress visuals have equivalent text, do not rely on color, clamp visual fill to 0–100% while textual overdue amounts remain accurate, and handle zero/invalid intervals as data errors.
- FR-6: Prominently show: "Digital Oil Sticker is a reminder, not a replacement for the owner's manual or the vehicle's oil-life monitor. Follow an earlier warning." Use reviewed wording, not diagnosis or warranty advice.
- FR-7: All dates are locale-formatted from stored calendar dates; all calculations remain timezone-independent in this milestone.
- FR-8: No forecast/estimated date appears anywhere before M06 inputs and algorithm are present.
- FR-9: Critical data provenance and the OLM/owner-manual warning are reachable without opening a legal page.
- FR-10: The dashboard renders entirely from local data, reaching usable content without any online spinner, and links to profile edit and history.

## Technical implementation contract

### Components and ownership boundaries

- `StickerLive` composes `VehicleSummary`, `DueStatus`, `SourceBadge`, and progress components inside `AppShell`; all facts arrive as typed context view models from `Garage`/`Maintenance` (DOS-M05-001).
- Target-date/odometer arithmetic is implemented once as pure domain functions (calendar-month addition with end-of-month clamping, distance addition in canonical units) with unit tests; no screen implements its own arithmetic (§9 principle).
- State selection (which honest state applies) is domain logic returning a state code; the LiveView maps codes to reviewed copy.

### Data and persistence

- Read-only over `UserRepo` facts: active vehicle snapshot, confirmed `maintenance_plans` basis, latest `service_events` row, latest valid `odometer_readings` in the current segment (respecting DOS-M05-004 discontinuities).
- No new tables and no dashboard-owned persistence; derived values are computed on render from committed facts (forecast snapshots belong to M06).
- Distances convert at the boundary from canonical integer base units into the profile's display unit.

### Interfaces and events

- A single context query returns the dashboard view model: identity, interval basis with type/provenance, last service, current recorded odometer with as-of date, computed targets, and the applicable state codes.
- The dashboard subscribes to the DOS-M05-001 events (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`) to re-render after mutations; it publishes none.
- Navigation targets: profile edit (DOS-M05-003), history (DOS-M05-004), provenance detail (in-place disclosure per FR-9).

### Failure and recovery behavior

- Zero or invalid intervals render as data errors with corrective navigation, never as a 0%-progress lie (FR-5).
- Missing inputs degrade to the specific honest state (setup-required, "Mileage status unknown", single-dimension) rather than a generic error.
- Storage/catalog failure states inherit the DOS-M05-001 typed recovery vocabulary; the dashboard never renders stale committed state as fresh after recovery.

### Security and privacy

- Fully local rendering; network blocked changes nothing (AC-2 evidence). No analytics, no remote assets.
- Displayed odometer/notes summaries follow §7 redaction rules in logs and fixtures.

### Accessibility and performance

- Screen is usable at 320 CSS px, 200% text zoom, keyboard only, and representative screen-reader navigation; progress semantics carry equivalent text and never rely on color alone.
- Cold-start to usable dashboard content meets the offline no-spinner requirement; formal timing budgets live in DOS-M07-003.

## UX and content states

Golden states, each with exact expected text and targets:

- Both-dimension state with "Service at whichever comes first."
- One-dimension state (time-only or distance-only) rendering only the available dimension.
- Overdue state: "Past due by recorded data" with accurate textual overdue amount and clamped visual fill.
- Missing-reading state: "Mileage status unknown," never "on track."
- Month-end and leap-year target dates (end-of-month clamping).
- Odometer-reset state honoring the DOS-M05-004 discontinuity (current reading from the current segment).
- Setup-required/empty states: no vehicle, no confirmed basis, or no service recorded — each naming the next useful action.
- Data-error state for zero/invalid intervals.
- Persistent disclaimer (FR-6) and provenance access (FR-9) present in every populated state.

## Test plan

### Automated

- Pure date/distance unit tests: calendar-month addition with end-of-month clamping (including leap years), distance targets in canonical units, unit-boundary conversion.
- State-selection tests mapping every input combination to its exact state code.
- Visual regression fixtures for every state listed in "UX and content states."
- Assertion tests that no estimated/forecast date string can render in M05 builds (AC-3).

### Manual/device matrix

- Offline cold-start on packaged iOS and Android builds recorded on video (AC-2).
- Accessibility audit: 320 CSS px width, 200% text zoom, keyboard-only, and screen-reader navigation transcript (AC-5).
- Copy review approval against ratified M02 wording, including the disclaimer.

## Rollout and rollback

Ships in the normal MVP build behind CI gates. Rollback is reverting the dashboard slice; it owns no persisted data, so rollback has no data implications. The presentation contract (state vocabulary and copy) is versioned with M02 documents; M06 extends it rather than editing it silently.

## Risks, decisions, and open questions

- Risk: subtle date arithmetic (month-end clamping, leap years) diverging between display and future M06 computation; mitigated by shared pure functions and golden tests, per the §9 rule that no screen implements its own arithmetic.
- Risk: honest states reading as "broken app" to users; mitigated by M02-reviewed next-action copy in every empty/unknown state.
- Decision to record: the exact visual design of dual-threshold progress (two indicators vs. combined), resolved with M02 design assets; either must satisfy FR-5.
- Open question: none blocking; overdue phrasing beyond the mandated strings follows the copy review.
