> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Becomes the Fly.io deploy-and-boot contract — reproducible image, pinned toolchain, health check before traffic, release manifest binding app/catalog/storage-schema versions — with icons, splash screens, and signed native packages carved out to the native re-entry set._

## Outcome

A single, byte-reproducible Fly.io deploy image ships the hosted Phoenix LiveView application at `digitaloilsticker.com` such that a release is atomic, health-gated, and rollback-safe: the container is built from a pinned Elixir/OTP/Phoenix/asset toolchain with the read-only catalog SQLite artifact baked in, `/healthz` succeeds inside the machine before Fly's proxy is allowed to send it traffic, and a signed release manifest binds the app version, the catalog `data_version`, the IndexedDB client-storage `schema_version`, the compiled asset digest, and the immutable Fly release identifier so an incompatible combination is refused before any LiveView mounts. A deploy is a non-event for users: reconnects re-run the INV-24 hydration path against unchanged browser storage, no user data lives on the server to lose, and rolling back is one command that restores the previous image and the catalog it was built with.

## Why this matters and what it unblocks

Under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) the entire product lives or dies with one Fly.io deploy: there is no store review, no signed IPA/AAB to fall back on, and no on-device BEAM continuing to serve while the network fails. Every render, every catalog query, and every mutation round trip flows through this image. If the deploy is not reproducible, a bad release cannot be reasoned about; if traffic is promoted before the app is ready, users see a broken shell on every rollout; if the manifest does not bind app/catalog/storage-schema versions, a stale-client / newer-server (or newer-client / stale-server) mismatch corrupts the [Constitution 2.0.0](../../docs/product/CONSTITUTION.md) INV-24 hydration contract silently.

This card is the release substrate for the browser MVP. Without it, DOS-M05-001 (integrate dual-repository domain contract, rescoped for hosted catalog + hydrated client state) has nowhere to run; DOS-M07-003 (page-load / hydration / server-memory budgets, rescoped) has no production-like target to measure; DOS-M07-005 (signed/attested container images with reproducible provenance, rescoped) inherits this image and manifest; and DOS-M07-007 (staged deploys, canary, monitoring, rehearsed rollback, rescoped) consumes this contract directly. The M09 platform gap issues proposed by the pivot ledger (Fly deploy pipeline, custom domain and TLS boundary, internet-facing hardening) would sit alongside this contract rather than replace it; where they land they refine, they do not re-open the contract this card ratifies.

## Included

- A reproducible container image for the hosted Phoenix LiveView application, built from a pinned base image and a pinned Elixir/OTP/Phoenix/LiveView/esbuild/Tailwind/`ecto_sqlite3` toolchain, produced deterministically in GitHub Actions so two builds of the same commit produce byte-identical image digests.
- The read-only catalog SQLite artifact (from DOS-M03-010's deterministic release) baked into the image at a known path; opened at boot in SQLite read-only mode by the sole configured Ecto repo, `DigitalOilSticker.CatalogRepo`.
- A `fly.toml` pinning region `ord`, `min_machines_running = 1` (scale-to-zero prohibited), an HTTP service that terminates TLS and forwards WebSockets, and a health-check pointing at `/healthz`.
- A `/healthz` endpoint that returns 200 only when the BEAM is up, `CatalogRepo` is opened and a trivial catalog probe query succeeds, the Endpoint is accepting requests, and the release manifest self-consistency check passes; and a deploy strategy that requires the health check to pass on the new machine before the Fly proxy promotes it into rotation.
- A signed release manifest committed into the image at build time binding: application version (git commit SHA + tag), catalog `data_version` and its content SHA, IndexedDB client `schema_version` accepted by this deploy (min and max), compiled asset digest, `SECRET_KEY_BASE` fingerprint (fingerprint only, never the value), Fly release id / image digest, and build timestamp. The manifest is machine-readable and rendered at `/manifest`.
- Secrets set via `fly secrets set` (`SECRET_KEY_BASE`, `PHX_HOST`) and read from `runtime.exs`; no secret is committed and no `.env` is shipped.
- HTTPS-only serving with `force_ssl`, HSTS enabled only after both hostnames verify, `check_origin` restricted to the exact production hostnames, WSS for `/live/websocket`, `Plug.SSL` with `rewrite_on: [:x_forwarded_proto, :x_forwarded_host, :x_forwarded_port]`, and the [ADR-0004 §"Content Security Policy"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#content-security-policy) header set on every response (per INV-22).
- Rollback contract: redeploying a prior image restores the prior application, the prior catalog `data_version`, and the prior manifest exactly, in one operation, without touching user data (there is none on the server to touch — INV-24.1).
- The release-ADR / boot-sequence diagram that documents container startup, `/healthz` gating, manifest checks, and rollback flow; linked from the repository architecture index.
- CI provenance: the image digest, its reproducibility proof (two-build compare), the release manifest, and the Fly release id are attached to the release artifact record so DOS-M07-005's rescoped attestation and DOS-M07-007's rescoped rollout consume them unchanged.

## Functional requirements

- **FR-1: Reproducible image build.** A GitHub Actions workflow builds a single OCI image from a pinned base and pinned toolchain such that two clean builds from the same commit produce byte-identical image digests. Build inputs are recorded (base-image digest, toolchain versions, catalog artifact SHA, source commit SHA); the build fails loudly if any pin drifts. This retires the pre-pivot FR-3 native-generator language while carrying its intent — pinned toolchain, upgrades gated behind a separate dependency PR — into a hosted-image world.

- **FR-2: Browser-first hosting posture; PWA still deferred; static content on Netlify subdomains.** The application is the hosted Phoenix LiveView surface approved by [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md), served from `digitaloilsticker.com` and `www.digitaloilsticker.com` on Fly.io. Per [Constitution 2.0.0 INV-27](../../docs/product/CONSTITUTION.md), static marketing / support / privacy / source-attribution content lives on `help.` and `legal.` subdomains (and later `catalog.`) served by Netlify (team `cDiscourse`); `digitaloilsticker.net` permanently redirects to `.com`. A PWA / service-worker offline mode is an explicitly deferred separate decision (ADR-0004 §"Consequences → Lost") and is not implied, promised, or partially built by this contract. _This FR replaces the pre-pivot FR-2 Netlify clause, whose "a browser/PWA product requires a separate future ADR" sentence directly contradicted ADR-0004 (finding #2)._

- **FR-3: Pinned toolchain and pinned Fly runtime.** Elixir, OTP, Phoenix, LiveView, esbuild, Tailwind, and `ecto_sqlite3` are pinned to exact compatible versions; the Docker base image and `flyctl` version are pinned in `.tool-versions` (or equivalent) and referenced by the CI job. Upgrades require a separate dependency PR with the reproducibility check green on both the pre- and post-upgrade commit and a browser-matrix smoke pass (per FR-11).

- **FR-4: Catalog baked read-only into the image; no runtime writers.** The read-only catalog SQLite artifact from DOS-M03-010 is copied into the image at build time. The application's `runtime.exs` opens `DigitalOilSticker.CatalogRepo` in SQLite read-only mode (`mode: :ro`), and no other Ecto repo is configured, started, or referenced by the deployed release. This enforces ADR-0004 §"Enforcement" and INV-23 structurally: the deploy has no personal-data table to write to because it has no writable repo at all.

- **FR-5: `fly.toml` pins region, scale, and WebSocket-safe service.** `fly.toml` sets `primary_region = "ord"`, `min_machines_running = 1`, `auto_stop_machines = false`, and an `[[services]]` block that terminates TLS at Fly's proxy and forwards WebSockets to `/live/websocket`. A concurrency limit is set to bound per-machine load. Deviations from these values require an ADR amendment, not a config tweak — they encode ADR-0004 §"Region" and §"WebSocket and LiveView considerations".

- **FR-6: `/healthz` gates traffic promotion.** A `/healthz` route returns 200 only when: (a) the BEAM has fully booted, (b) `CatalogRepo` is open, (c) a trivial catalog probe query (a `SELECT` against a stable table with a known-non-empty result) succeeds within a small budget, (d) the Endpoint accepts connections, and (e) the release manifest self-consistency check (FR-7) passes. Fly's deploy strategy is configured so the new machine's `/healthz` must succeed before the proxy sends any user traffic to it. A failed check on a rolling deploy blocks the promotion and surfaces the failure in `flyctl` logs; no partial promotion is possible. This retires the pre-pivot FR-4's WebView-navigation-waits-for-local-ready-signal in a hosted form: the ready signal is now the Fly health check, gated by the same "explicit signal, not a timed sleep" principle.

- **FR-7: Signed release manifest binds app, catalog, and client-storage versions.** A build-time step writes `priv/release_manifest.json` (and serves it at `/manifest`) containing: application version (commit SHA + release tag), catalog `data_version` and content SHA, the range of IndexedDB client `schema_version` values this deploy accepts, compiled asset digest, `SECRET_KEY_BASE` fingerprint (not the value), Fly release id (populated at deploy time via the Fly-provided env var), and build timestamp. The manifest is signed (see FR-13). On boot, the app performs a self-consistency check: the catalog SHA on disk must match the manifest, the app version must match the compiled `Application.spec/2` value, and the accepted client `schema_version` range must not be empty. Failure fails `/healthz`. This preserves the pre-pivot FR-7 spine ("release manifest as compatibility gate") and updates its bound entities to the browser-first world; the on-device `UserRepo` and native bridge/plugin versions from the pre-pivot manifest are retired and replaced by the client IndexedDB `schema_version` range and asset digest.

- **FR-8: Client / server schema-version compatibility is checked at hydration and refused honestly.** A client whose `schema_version` falls outside this deploy's accepted range MUST NOT have its payload mutated by the server. Older-client payloads are migrated forward through pure functions and written back per ADR-0004 §"Schema versioning and migration"; newer-client payloads (a rolled-back deploy) put the session into read-only mode with an explicit banner and export offered. The refusal states are rendered per INV-25 and are covered by the [test plan](#test-plan). This is a direct consequence of the manifest FR-7 in the hydration protocol and it retires the pre-pivot FR-7's "refuse an incompatible combination before mounting product LiveViews" in a hosted, per-connection form.

- **FR-9: Hosted transport security per INV-22 replaces retired INV-2 loopback.** `force_ssl` is on with an HTTP-to-HTTPS redirect; HSTS is enabled once both hostnames verify (`preload` not requested at MVP). `check_origin` is an explicit host allowlist (never `true`, never `false`). The session cookie is `secure`, `http_only`, `same_site: "Lax"`, contains no personal data or stable identifier, and its `max_age` is short. LiveView `_csrf_token` is passed through `connect_params` and verified on connect. The CSP from ADR-0004 §"Content Security Policy" is served on every response. `debug_errors: false` in production. Client IP for rate limiting is taken from Fly's forwarded headers via a trusted-proxy-aware plug and is used in memory only, never persisted or logged. This retires pre-pivot FR-9's iOS ATS / Android cleartext exception language: with no on-device WebView, no loopback binding, and no cleartext transport, those controls are meaningless and their replacement is the hosted-transport rule set above.

- **FR-10: First-party runtime; no third-party origins.** All JS, CSS, and fonts are first-party, bundled by esbuild, and served from the same origin; no CDN font, no external script, no analytics SDK, no tag manager, no third-party error reporter is loaded on any page. The CSP enforces this structurally (`default-src 'self'`, no `unsafe-inline`, no external `script-src`). If a LiveView behavior requires inline styles, the answer is a per-request nonce plug, not a blanket relaxation. This preserves the pre-pivot FR-10's "no third-party requests to boot or use" spine in a hosted form and satisfies INV-4 at the transport layer via INV-22.

- **FR-11: Deploy is a non-event for user data; reconnect re-runs INV-24 hydration.** Per INV-24.1, a deploy or a Fly.io machine replacement MUST NOT lose user data, because the server was never the system of record. When Fly promotes a new machine and drops live WebSockets, clients auto-reconnect with backoff and the JS hook re-runs the INV-24 hydration path against unchanged IndexedDB. A pending optimistic mutation held only in the previous socket's `assigns` is re-driven from client storage after remount. The deploy pipeline includes a scripted "deploy while a user is mid-session with an unsaved mutation" smoke case whose pass condition is that the mutation survives and completes after reconnect. This retires the pre-pivot FR-6 root-screen-restart / stale-command-rejection language in a form that fits the hosted architecture.

- **FR-12: Rollback is one command and restores the prior catalog too.** Redeploying a prior image (`flyctl releases rollback <id>` or equivalent) restores the previous application version, the previous catalog `data_version`, the previous asset digest, and the previous manifest exactly. Because the catalog is baked in, no separate catalog rollback step exists and none is possible — this is the ADR-0004 §"Catalog database on Fly" property "Rollback: Redeploy the previous image. The old catalog comes back exactly." A rehearsed rollback drill (documented steps, timed, run on a non-production release id) is part of this card's evidence; DOS-M07-007's rescoped staged rollout consumes it. This retires the pre-pivot FR-11's app-store upgrade / preserve-database language: browser-storage user data is user-owned across origin-scoped IndexedDB and is unaffected by a server rollback by construction.

- **FR-13: Secrets, provenance, and least-privilege deploy token.** `SECRET_KEY_BASE`, `PHX_HOST`, and any future runtime secret are set with `fly secrets set` and read only from `runtime.exs`; nothing sensitive is committed and no `.env` ships. The GitHub Actions deploy job holds a deploy-scoped Fly token in repository secrets. The release manifest (FR-7) is signed with a build-time key whose public half is committed; the signature is verified on boot as part of the manifest self-consistency check. Secret rotation is data-loss-free (ADR-0004 §"Secrets"): rotating `SECRET_KEY_BASE` invalidates signed session cookies and LiveView socket tokens, clients reconnect, and INV-24 hydration re-runs against unchanged browser storage.

## Technical implementation contract

### Components and ownership boundaries

- **Container image**: a single OCI image containing the compiled OTP release, the bundled JS/CSS/font assets, the read-only catalog SQLite file, the release manifest, and the manifest signature. Nothing else. Built by CI, not by developer machines.
- **Fly machine**: runs the OTP release. `min_machines_running = 1`, no auto-stop, no volume attached. One always-on machine in `ord` at MVP; a second always-on machine for HA and zero-downtime deploys is a bounded cost decision deferred to a follow-up (ADR-0004 §"Cost shape").
- **BEAM release**: supervision tree owning `Endpoint`, the sole `CatalogRepo` (opened read-only), the rate-limit table, and the manifest service. `LiveDashboard` is disabled in production. `remsh` / distribution is disabled.
- **CI**: owns reproducibility. Two clean CI builds of the same commit must produce identical image digests; the compare is a release gate.
- **Fly proxy**: terminates TLS, enforces `check_origin`'s effect indirectly (via SNI + our own check), forwards WebSockets, and gates traffic on `/healthz`.
- **Netlify (team `cDiscourse`)**: serves static content on `help.` / `legal.` subdomains only, per INV-27; never touches Phoenix.

### Data and persistence

- **Catalog**: SQLite, read-only, baked into the image. Path is stable; connection is opened `mode: :ro`. No writers exist in the deployed process, structurally enforcing CHANGE_CONTROL.md Rule 6 (catalog immutability within a `data_version`).
- **User data**: none on the server. IndexedDB lives in the browser, per INV-23. `socket.assigns` holds hydrated user records for the LiveView connection lifetime only, and is discarded at socket termination (INV-24.1). No cache, no ETS table, no external store, no log line holds a personal value (see FR-9 and the log-scan test in the [test plan](#test-plan)).
- **Release manifest**: `priv/release_manifest.json` inside the image, plus signature. Served at `/manifest` as read-only content-typed JSON; content is stable for the life of the image.
- **Secrets**: `SECRET_KEY_BASE` and `PHX_HOST` in Fly secrets; nothing else at runtime. The build-time signing key is a CI secret; only its public half ships in the image.

### Interfaces and events

- **Boot sequence**: container start → BEAM start → `runtime.exs` reads Fly secrets → supervision tree starts (`CatalogRepo` open read-only, `Endpoint` start, rate-limit table, manifest service) → manifest self-consistency check runs → `/healthz` begins returning 200 → Fly proxy promotes the machine and starts routing traffic → LiveView requests begin arriving and each mount enters the INV-24 hydration path (server assigns `local_state = :hydrating`, no writable per-user state exists).
- **Health check protocol**: `/healthz` is a plain HTTP GET, unauthenticated, returns 200 with a short JSON body containing the release id and the manifest digest (no personal data, no secrets). It returns 503 with a machine-readable reason code on any failure of its checks (`beam_not_ready`, `catalog_not_open`, `catalog_probe_failed`, `endpoint_not_ready`, `manifest_invalid`). The Fly deploy strategy is configured to require the pre-promotion check.
- **Manifest endpoint**: `/manifest` returns the parsed manifest JSON with the signature verified server-side at boot; clients do not verify the signature (that is a boot-time server responsibility), and the endpoint is safe to expose because it contains no secret values (the `SECRET_KEY_BASE` field is a fingerprint only).
- **Deploy pipeline**: on merge to `main` (or a tagged release), CI builds the image, runs the reproducibility compare, uploads the image, records provenance (image digest, manifest, source SHA, catalog SHA) into the release artifact record, and calls `flyctl deploy` with the immutable image digest. The Fly release id captured in the response is written back into the release artifact record for DOS-M07-005's attestation and DOS-M07-007's rollout.

### Failure and recovery behavior

- **BEAM boot failure**: the container exits; Fly does not promote the machine; the previous release keeps serving.
- **`CatalogRepo` open failure or probe query failure**: `/healthz` fails with `catalog_not_open` / `catalog_probe_failed`; the machine is not promoted; deploy is aborted, previous release keeps serving.
- **Manifest self-consistency failure** (SHA mismatch, signature invalid, empty accepted `schema_version` range): `/healthz` fails with `manifest_invalid`. This is a build defect that reached CI's reproducibility check and must be treated as a release blocker, not a config tweak.
- **Endpoint failure post-boot**: supervised restart. If the machine's `/healthz` starts failing, Fly's health check trips and it is drained; the second machine (if provisioned) carries traffic; with a single machine, users see reconnect UI (INV-24 hydration on reconnect) and the machine restarts.
- **Client / server schema-version mismatch** (per FR-8): the session enters read-only mode with an explicit banner and export offered — never a silent downgrade, never a silent write. This is not a deploy failure; it is a per-session state.
- **Rollback**: `flyctl releases rollback <prior-id>` restores the previous image, which restores the previous catalog `data_version` and the previous manifest atomically. Live sockets drop; clients reconnect against the older release; INV-24 hydration re-runs. If the rolled-back release had a narrower accepted `schema_version` range, clients newer than it enter FR-8's read-only banner state — again, this is honest, not silent.

### Security and privacy

- HTTPS everywhere; HSTS post-verification; CSP per ADR-0004 §"Content Security Policy" on every response; `Referrer-Policy: no-referrer`; `X-Content-Type-Options: nosniff`; `Permissions-Policy` denying geolocation/camera/microphone/payment; `check_origin` allowlist. CSRF on all non-idempotent HTTP endpoints and on the LiveView socket connect.
- Session cookie carries only the CSRF token and `live_socket_id`; no anonymous stable identifier and no personal value (INV-3, INV-23).
- No third-party origins on any page (INV-4, INV-22); CSP enforces structurally.
- `LiveDashboard` disabled in production (ADR-0004 §"LiveDashboard and operator access — stated honestly"); no routine production console use.
- Server logs redact per ADR-0004 §"Logging": no VIN, no odometer, no dates, no note text, no vehicle-selection, no hydration/mutation/import/export payload, no `tab_id`, no full client IP. The log-scan test from ADR-0004 §"Enforcement" runs as a release gate.
- Rate limits per-IP on socket connect and HTTP requests, per-socket on hydrate / catalog / import events. Payload caps rejected explicitly, never truncated (per ADR-0004 §"Validation"). The catalog-query surface accepts no personal identifier (INV-26).

### Accessibility and performance

- Any HTML surface that a user could see during a deploy incident (rare, since promotion is health-gated) is accessible: readable text, screen-reader labels, keyboard reachable. Per Constitution 2.0.0 §9, page-load p75 ≤ 3.5 s and first-visit payload ≤ 250 KiB compressed HTML+CSS+JS with zero third-party origins — these are the budgets this image must fit; DOS-M07-003 measures them against this deploy.
- `/healthz` and `/manifest` are cheap, cacheable-off, and unauthenticated; they must not become a slow path.

## UX and content states

- **First-visit shell** (before hydration): the determinate loading skeleton required by INV-24.3. This deploy contract's job is to make sure the shell renders promptly and honestly, not to fabricate content.
- **Reconnect during a deploy**: `phx-disconnected` styling per ADR-0004 §"WebSocket and LiveView considerations" communicates reconnection honestly; on reconnect the INV-24 hydration path re-runs and unsaved mutations are re-driven from client storage.
- **Client-newer-than-server (rolled-back release)**: read-only banner per FR-8 with export offered; no silent write.
- **Client-older-than-server**: server migrates the payload forward per ADR-0004 §"Schema versioning and migration" and writes it back in the same round trip; the user sees a normal render.
- **`/healthz` failure during a deploy**: no user-visible state — Fly holds traffic on the previous release; the deploy fails in `flyctl` and CI.
- **Rollback**: user-visible only as a brief reconnect. Nothing implies the record moved anywhere.
- **The M09 gap disposition** (per the pivot ledger): if the M09 milestone lands, its issues on custom domain / TLS / hardening / conformance matrix refine this contract's edges but do not change these user-visible states.

## Rollout and rollback

Deploys are triggered by CI on merge to `main` (or a tagged release); staging is an unlisted hostname on the same Fly app definition (per the rescoped DOS-M07-006). Promotion to production requires `/healthz` green on the new machine before the Fly proxy sends traffic. A canary step and the browser-matrix smoke pass live in the rescoped DOS-M07-007 and consume the image, manifest, and release id this card produces.

**Rollback is one command** (`flyctl releases rollback <id>` or equivalent) and restores the previous application, catalog `data_version`, asset digest, and manifest atomically (FR-12). Because the catalog is baked in, there is no separate catalog rollback and none is possible — CHANGE_CONTROL.md Rule 6 is structurally enforced. User data is untouched by rollback because none of it lives on the server (INV-23, INV-24.1); live sockets drop, clients reconnect, INV-24 hydration re-runs against unchanged browser storage. Toolchain upgrades roll back by reverting the pinned-versions PR (FR-3).

If a rolled-back release advertises a narrower accepted client `schema_version` range than the newest release, clients newer than it enter the FR-8 read-only banner state and are offered export; this is the honest behavior, not a bug, and it is user-visible only as a banner and disabled write controls.

## Risks, decisions, and open questions

- **Risk: single region and single always-on machine.** Per ADR-0004 §"Region", a Fly outage or zone failure in `ord` is a total product outage, and every deploy drops all sockets. Mitigation: the deploy contract makes reconnect + re-hydration robust enough that a routine deploy is a non-event (FR-11 + AC-7); a second always-on machine for HA is a bounded cost decision revisited on real usage.
- **Risk: baked-in catalog grows the image.** Acceptable while the catalog fits comfortably; ADR-0004 §"Catalog database on Fly" documents the fallback (a Fly persistent volume) if it stops fitting. The image-size trend is recorded in the build manifest so growth is not a surprise.
- **Risk: schema-version mismatch on rollback surprises users.** Mitigated by the FR-8 honest read-only banner and by the rehearsed rollback drill (AC-6) that exercises the banner state before it appears in production.
- **Risk: CSP too strict for a LiveView behavior we have not yet built.** Mitigation per ADR-0004 §"Content Security Policy": if a nonce is required, a per-request nonce plug — not `unsafe-inline` — and the deployment spike verifies the CSP against actual runtime behavior before this card closes.
- **Risk: browser eviction of client storage between deploys (R1 in ADR-0004).** Not this card's mitigation to own — INV-24 / INV-25 and the M09 conformance suite carry it — but this card's reconnect + hydration contract must not add to it. FR-11 pins the property.
- **Decision recorded here:** the release ADR and boot-sequence diagram (FR-1 evidence + AC-1) — this card carries the needs-decision gate and cannot close without approval.
- **Open question:** the exact `SECRET_KEY_BASE` fingerprint algorithm in the manifest (a truncated SHA-256 is the default; whether to use HKDF with a separate salt is worth the paragraph). Resolved inside the release ADR before merge; both satisfy FR-13's "fingerprint only, never the value" rule.
- **Open question:** whether to add a second always-on machine for HA at MVP. Deferred to a follow-up cost/benefit decision per ADR-0004 §"Cost shape"; this card is single-machine by default and does not preclude the second.

### Technical implementation contract

#### Components and ownership boundaries

- Native shell (per platform): app lifecycle, WebView hosting, icons/splash, native failure/retry surface, allowlisted open-URL action.
- BEAM release: supervision tree owning `Boot`, both Repos, the Endpoint, and the DeviceCommandBroker; `DigitalOilSticker.MobScreen` is the sole owner of the `Mob.Socket` (§4.1, §7).
- The ADR (FR-1) is the ownership document of record: WebView↔LiveView↔Mob bridge responsibilities, failure states, and upgrade policy; the repository architecture index links it.
- CI owns reproducibility: the pinned toolchain image and build manifest are CI artifacts, not developer-machine folklore.

#### Data and persistence

- Starter catalog is verified and copied into application support on first launch per §8; catalog staging/activation retains the previous catalog for rollback.
- `UserRepo` migrations run forward exactly once per upgrade before the UI becomes writable; a populated database from the previous signed build is preserved (FR-11).
- The release manifest (FR-7) is the compatibility gate between app version, schema versions, catalog version, asset digest, and bridge/plugin versions.

#### Interfaces and events

- Boot sequence contract: BEAM start → `Boot` ordering (catalog verify, user migration, Repo start, recovery state) → Endpoint ready → explicit local health/ready signal → WebView navigation → root `Mob.Screen` registration → hidden `MobHook` mount before page hooks → DeviceCommandBroker start.
- Health/ready is an explicit local signal (route or bridge callback), never a timed sleep.
- DeviceCommandBroker command/acknowledgement flow with correlation IDs and generation counters is the only native-capability path; no Phoenix socket ever reaches a Mob plugin API.

#### Failure and recovery behavior

- Endpoint-not-ready: native splash/progress until the ready signal; a timeout escalates to the native retry/error surface with accurate guidance.
- Endpoint crash/restart: supervised restart; WebView recovers via the ready signal; in-flight broker commands are rejected as stale by generation, never duplicated.
- Database-open failure and migration failure: do not enter the main LiveView, do not delete data; show the recovery path from the DOS-M05-001/M04 vocabulary.
- Corrupt starter catalog: detected by integrity verification before activation; accurate recovery guidance rather than a blank WebView.
- Incompatible manifest combination: refused with a recovery path before product LiveViews mount (FR-7).

#### Security and privacy

- Endpoint bound strictly to `127.0.0.1`; never `0.0.0.0`; LAN/Wi-Fi unreachability verified by packet capture/port scan evidence.
- `MIX_ENV=prod` releases: code reload, LiveDashboard, dev routes, remote inspector, and Erlang distribution disabled; CSRF protections retained (§7).
- iOS ATS and Android network security config permit loopback only; Android cleartext exception limited to device loopback; WebView navigation restricted to loopback application routes; external links only via the allowlisted native open-URL action.
- No third-party requests at boot or during core use: no CDN fonts, remote scripts, analytics SDKs, or Netlify calls (FR-10).
- Packaged session keys are local integrity material, not remote secrets.

#### Accessibility and performance

- Splash/failure/retry surfaces are accessible (readable text, screen-reader labels) since they may be the only UI a user sees on a bad boot.
- Deterministic boot without arbitrary sleeps; cold-start timing is measured here informally and budgeted formally in DOS-M07-003.
- Package size is tracked in the build manifest so catalog growth decisions in M07/M08 are informed, not surprising.

### UX and content states

- Native splash → ready transition into the LiveView UI with no blank-WebView gap.
- Endpoint-not-ready progress state; Endpoint failure retry/error surface with accurate recovery guidance.
- Migration-failure and corrupt-catalog recovery states that never drop the user into a broken product UI.
- Incompatible-version refusal state with recovery path.
- Honest uninstall/upgrade descriptions in help content: upgrades preserve data; uninstall behavior follows the OS.
