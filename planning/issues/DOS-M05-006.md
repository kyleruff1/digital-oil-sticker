## Outcome

The iOS and Android bundles contain the OTP release, Phoenix/LiveView assets, native Mob shell, SQLite migrations, and starter catalog needed for an immediate, deterministic offline first boot.

## Why this matters and what it unblocks

"Offline-first" is a release property, not a database choice. The embedded Endpoint/WebView boot lifecycle must protect user data and avoid blank screens, loopback races, or mismatched catalog/code versions. Without this issue, every M05 feature exists only in development harnesses; with it, the scripted airplane-mode gate of the M05 epic becomes testable on real devices. It blocks DOS-M07-003, DOS-M07-004, DOS-M07-007, and production release.

## Functional requirements

- FR-1: Commit an architecture ADR and boot/data-flow diagram that pin Mob `0.7.20` LiveView mode: the on-device BEAM supervises Ecto/SQLite and a Phoenix Endpoint, the native shell hosts the WebView, and their traffic stays on loopback. The ADR defines WebView↔LiveView↔Mob bridge ownership, failure states, and upgrade policy.
- FR-2: Netlify hosts only static marketing/help/privacy content and, beginning in DOS-M08, signed public catalog artifacts. It is not a Phoenix runtime, profile API, login service, or user database. A browser/PWA product requires a separate future ADR and is out of scope.
- FR-3: Generate the project in Mob LiveView mode and pin exact compatible Mob, `mob_new`, Elixir, OTP, Phoenix, LiveView, esbuild, Tailwind, SQLite adapter, Xcode, and Android/Gradle versions in the build documentation/CI image. Upgrades require a separate dependency PR and both-device smoke test.
- FR-4: Bundle compiled JS/CSS/fonts locally. The native app starts the BEAM and the Phoenix Endpoint bound only to `127.0.0.1`; WebView navigation waits for an explicit local health/ready signal rather than an arbitrary sleep.
- FR-5: Start and register the root `Mob.Screen` that owns the WebView and `Mob.Socket`; mount the generated hidden `MobHook` element before page-specific hooks; start the DeviceCommandBroker only when the root-screen dispatch target is available.
- FR-6: Root-screen restart increments a generation/rejects stale commands and recovers the loopback WebView without duplicating a previously acknowledged native action.
- FR-7: Use a release manifest that binds app version, Ecto schema version, catalog schema/version, asset digest, and native bridge/plugin versions. Refuse an incompatible combination with a recovery path before mounting product LiveViews.
- FR-8: Supervise Repo and Endpoint with explicit restart strategy. A transient Endpoint failure shows a native-hosted retry/error surface; a migration failure does not enter the main LiveView or delete data.
- FR-9: Configure iOS App Transport Security and Android network security narrowly enough to allow the loopback HTTP endpoint without broadly permitting cleartext network traffic. Prevent WebView navigation to remote origins; external help links must cross an allowlisted native open-URL action.
- FR-10: Core UI assets and catalog ship in the signed IPA/AAB/APK. No CDN font, remote script, analytics SDK, or Netlify request is needed to boot or use M05.
- FR-11: App-store/package upgrade opens the existing application-support database, runs forward migrations once, and preserves records. Uninstall behavior follows the OS and is described honestly.

## Technical implementation contract

### Components and ownership boundaries

- Native shell (per platform): app lifecycle, WebView hosting, icons/splash, native failure/retry surface, allowlisted open-URL action.
- BEAM release: supervision tree owning `Boot`, both Repos, the Endpoint, and the DeviceCommandBroker; `DigitalOilSticker.MobScreen` is the sole owner of the `Mob.Socket` (§4.1, §7).
- The ADR (FR-1) is the ownership document of record: WebView↔LiveView↔Mob bridge responsibilities, failure states, and upgrade policy; the repository architecture index links it.
- CI owns reproducibility: the pinned toolchain image and build manifest are CI artifacts, not developer-machine folklore.

### Data and persistence

- Starter catalog is verified and copied into application support on first launch per §8; catalog staging/activation retains the previous catalog for rollback.
- `UserRepo` migrations run forward exactly once per upgrade before the UI becomes writable; a populated database from the previous signed build is preserved (FR-11).
- The release manifest (FR-7) is the compatibility gate between app version, schema versions, catalog version, asset digest, and bridge/plugin versions.

### Interfaces and events

- Boot sequence contract: BEAM start → `Boot` ordering (catalog verify, user migration, Repo start, recovery state) → Endpoint ready → explicit local health/ready signal → WebView navigation → root `Mob.Screen` registration → hidden `MobHook` mount before page hooks → DeviceCommandBroker start.
- Health/ready is an explicit local signal (route or bridge callback), never a timed sleep.
- DeviceCommandBroker command/acknowledgement flow with correlation IDs and generation counters is the only native-capability path; no Phoenix socket ever reaches a Mob plugin API.

### Failure and recovery behavior

- Endpoint-not-ready: native splash/progress until the ready signal; a timeout escalates to the native retry/error surface with accurate guidance.
- Endpoint crash/restart: supervised restart; WebView recovers via the ready signal; in-flight broker commands are rejected as stale by generation, never duplicated.
- Database-open failure and migration failure: do not enter the main LiveView, do not delete data; show the recovery path from the DOS-M05-001/M04 vocabulary.
- Corrupt starter catalog: detected by integrity verification before activation; accurate recovery guidance rather than a blank WebView.
- Incompatible manifest combination: refused with a recovery path before product LiveViews mount (FR-7).

### Security and privacy

- Endpoint bound strictly to `127.0.0.1`; never `0.0.0.0`; LAN/Wi-Fi unreachability verified by packet capture/port scan evidence.
- `MIX_ENV=prod` releases: code reload, LiveDashboard, dev routes, remote inspector, and Erlang distribution disabled; CSRF protections retained (§7).
- iOS ATS and Android network security config permit loopback only; Android cleartext exception limited to device loopback; WebView navigation restricted to loopback application routes; external links only via the allowlisted native open-URL action.
- No third-party requests at boot or during core use: no CDN fonts, remote scripts, analytics SDKs, or Netlify calls (FR-10).
- Packaged session keys are local integrity material, not remote secrets.

### Accessibility and performance

- Splash/failure/retry surfaces are accessible (readable text, screen-reader labels) since they may be the only UI a user sees on a bad boot.
- Deterministic boot without arbitrary sleeps; cold-start timing is measured here informally and budgeted formally in DOS-M07-003.
- Package size is tracked in the build manifest so catalog growth decisions in M07/M08 are informed, not surprising.

## UX and content states

- Native splash → ready transition into the LiveView UI with no blank-WebView gap.
- Endpoint-not-ready progress state; Endpoint failure retry/error surface with accurate recovery guidance.
- Migration-failure and corrupt-catalog recovery states that never drop the user into a broken product UI.
- Incompatible-version refusal state with recovery path.
- Honest uninstall/upgrade descriptions in help content: upgrades preserve data; uninstall behavior follows the OS.

## Rollout and rollback

Builds flow to internal testing tracks (TestFlight / Play internal testing) per §4.3 distribution; store-facing rollout itself is M07 scope. Rollback: a bad package is superseded by re-releasing the previous good build; the catalog staging protocol retains the previous catalog for rollback; `UserRepo` is never rolled back by packaging — forward migrations plus M04 backup/recovery govern data. Toolchain upgrades roll back by reverting the pinned-versions PR.

## Risks, decisions, and open questions

- Risk: Mob is pre-1.0; 0.7.20 behavior (bridge lifecycle, build tooling) may have platform-specific edge cases. Mitigation: the pinned toolchain, `mix mob.doctor` in CI, the two-bridge smoke test, and the M00 gate precedent. Any Mob upgrade is a separate dependency PR with both-device smoke (FR-3).
- Risk: WebView/OS updates changing loopback or cleartext policy on Android/iOS; the narrow ATS/network-security configs are documented in the ADR with verification steps.
- Decision recorded here: the runtime ADR itself (FR-1) — this issue carries the needs-decision gate and cannot close without its approval (AC-1).
- Open question: exact health/ready signal mechanism (dedicated route vs. bridge callback) — resolved inside the ADR; both satisfy FR-4's no-arbitrary-sleep rule.
