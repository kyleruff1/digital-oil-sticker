> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Same envelope, checksum, preview-before-import, and replace semantics, delivered through browser download/upload with added guidance that browser data-clearing is the realistic loss scenario._

## Outcome

A user of the hosted browser application can create a portable local backup as a downloaded file, validate and restore that file into a compatible browser session, and intentionally erase all locally held records — with no account, no server-side personal store to reconcile against, and no support intervention. Export/import is the *only* recovery path (INV-5, INV-25), and every user-facing surface says so plainly against the implicit "it must be on their server" reading that a hosted URL invites.

## Why this matters and what it unblocks

Under ADR-0004 all personal data lives in origin-scoped IndexedDB in the user's browser (INV-23). That storage can be lost in ways an on-device SQLite file could not: the user clears site data, the browser's storage-eviction policy reclaims quota for an infrequently-visited site (the quarterly-oil-check profile is exactly the risk profile from ADR-0004 R1), private-browsing sessions discard on close, a different browser or profile is a different garage, and a device swap has no automatic bridge. Under those conditions a user-controlled, offline-usable, download-based export/import is not an extra — it is the sole portability and recovery mechanism the product offers, and the browser MVP cannot honestly reach beta without it.

This card unblocks the browser-hardening and release-readiness work in the rescoped [DOS-M07-001](DOS-M07-001.md) (hosted threat model) and [DOS-M07-004](DOS-M07-004.md) (browser/engine/OS QA matrix with eviction, quota, private-browsing, multi-tab, and reconnect rows), which explicitly rely on export/import as the approved local recovery mechanism. It also completes the "honest storage-loss messaging" contract in INV-25 by providing the recovery affordance every loss-state banner points at, and it satisfies the amended INV-5 wording that requires an *always-reachable* export offer when the app implies no remote durability.

## Included

- The single versioned JSON envelope shape defined by ADR-0004 §"Payload envelope" is the export format. No second format, no compression variant, no per-store split files.
- Export is a client-side download: the `LocalStore` hook reads every store in one `readonly` IndexedDB transaction, wraps the result in the envelope, appends a SHA-256 content digest computed over the canonical serialization, and hands the browser a `Blob` download named `digital-oil-sticker-export-YYYYMMDD.json` via a synthetic anchor click. No `pushEvent` fires, no server route serves the file, no bytes leave the browser.
- Import is a client-side file selection: a file input in the hook reads the chosen `File`, parses JSON, verifies the digest, and dispatches it to the server as a `local_store:hydrate` event so it inherits the full validation, migration, and quarantine pipeline already specified for hydration.
- Preview-before-import: the server responds with a computed preview (record counts per store, vehicle identity summary, date range of events/readings, catalog compatibility notes, and any quarantined records) and the user must issue an explicit "Replace local data" confirmation before commit.
- Replace semantics for M05: a confirmed import replaces the browser's stores wholesale from the migrated envelope. Merging is out of scope for M05 and is recorded as an open question below.
- Reset is a client-driven erase: an explicit destructive confirmation, deletion of every `dos_local` object store record, clearing of the `dos_boot_state` `localStorage` hint, deletion of the (transient) `assigns` copy, and a post-deletion verification pass before the first-run state is shown.
- Copy against the "hosted URL implies backup" reading (INV-5, INV-25): every export/import/reset surface states, without user prompting, that the record lives in this browser only and that clearing browser data deletes it permanently; the prohibited-words list from ADR-0004 §"Export and import" is enforced by copy review.
- The scripted-session log-scanning test that closes ADR-0004 §"Enforcement" is authored here.

## Excluded

- No server-side export endpoint, no upload endpoint, and no server route that ever holds a copy of an exported envelope. Export is purely client-produced and client-consumed; the server sees only the parsed hydrate payload during import and only for the socket lifetime, per INV-3 and INV-24.1.
- No cloud backup, background sync, encrypted key escrow, sharing to a third-party service, or any transport that would require a server-held copy or a subscription record.
- No merge-import for M05 (see Open questions). No importing arbitrary third-party service records.
- No OS-scheduled reminder cancellation on reset. `mob_notify` is retired for the browser MVP (INV-17 amended); there are no OS-scheduled notifications in the browser to cancel. The rescoped [DOS-M06-005](DOS-M06-005.md) computes due/overdue state from records at hydrate time, so reset removing the records removes the state.
- No PWA/service-worker offline export; no Web Push subscription cleanup — both explicitly deferred (ADR-0004, INV-19 amended).
- No native platform share sheet, file-picker command broker, or `Mob.*` module of any kind. All such references are deleted (sweep finding 1).

## Functional requirements

- **FR-1: Export envelope shape and content.** Export produces exactly the ADR-0004 §"Payload envelope" JSON envelope (`envelope`, `schema_version`, `seq`, `tab_id`, `generated_at`, `data`), UTF-8, with `data` covering every user-owned store — `vehicles`, `events`, `readings`, `reminders`, `prefs` — and no other data. The envelope MUST NOT include `meta.persist_granted`, catalog rows, log lines, error stacks, `SECRET_KEY_BASE`-derived material, any session cookie value, machine ID, IP address, `X-Forwarded-*` header value, or any server-side identifier. INV-3, INV-4, INV-23. _Retires pre-pivot FR-1's list of `UserRepo` tables in favor of the ADR-0004 store list; the "no cache/no device IDs/no tokens/no logs/no secrets" prohibition carries over verbatim._
- **FR-2: Content digest.** Export appends a SHA-256 hex digest computed over the canonical serialization of the envelope (a deterministic JSON encoding with sorted object keys, `\n` line endings, no BOM). Import recomputes the digest over the parsed-and-re-serialized envelope and rejects a mismatch as a distinct `digest_mismatch` error. The UI states plainly that a default export is not encrypted and may contain vehicle/maintenance information. INV-5, INV-25. _Carries pre-pivot FR-2 forward unchanged in intent; the "may contain vehicle/maintenance information" honesty statement now runs before the download instead of before a share sheet._
- **FR-3: Client-side download path (browser MVP).** Export is built entirely inside the `LocalStore` `phx-hook` JavaScript module. The hook opens one `readonly` transaction across every user-owned store, serializes the envelope, computes the digest, constructs a `Blob` with `type: "application/json"`, and triggers download via a synthetic `<a download="digital-oil-sticker-export-YYYYMMDD.json">` element revoked on click. No `pushEvent` is dispatched during export. No server route receives, buffers, caches, or logs the envelope bytes. INV-3, INV-23, ADR-0004 §"Export and import". _Directly addresses sweep finding 1: rewrites away from `Mob.Files`/native share surfaces to the browser Blob download._
- **FR-4: Client-side file-input import path (browser MVP).** Import is a `<input type="file" accept="application/json">` inside the hook. On selection the hook reads the file via `FileReader.readAsText` (or `Blob.text()`), parses JSON in a `try`/`catch`, verifies the digest, and dispatches a `local_store:hydrate` `pushEvent` carrying the parsed envelope and an `import: true` marker so the server can branch into the preview state instead of the ordinary mount-hydrate path. No native picker command, no DeviceCommandBroker, no correlation-ID protocol — the file input's own cancel event is the cancellation signal, and it is a first-class non-error outcome. INV-3, INV-22, INV-23, ADR-0004 §"Export and import". _Directly addresses sweep finding 1: rewrites away from `Mob.Storage`/`Mob.Socket`/`Mob.Screen`/DeviceCommandBroker to the browser file input._
- **FR-5: Two-phase import with preview.** The server, on receiving `local_store:hydrate` with `import: true`, runs the full validation and migration pipeline (§"Validation" and §"Schema versioning and migration" in ADR-0004) against a scratch copy of the payload, computes counts per store, the vehicle identity summary (nickname or "unnamed vehicle"), the event/reading date range, catalog compatibility notes against the current `CatalogRepo`, and the quarantine list of records that failed per-record validation, then renders a preview state. Nothing is committed to the client stores until the user issues the explicit "Replace local data" confirmation. Preview MUST show the migrated shape, not the raw shape, so a user is not asked to confirm data that will not survive migration.
- **FR-6: Replace-only commit, atomic at the client store.** On confirmation the server `push_event`s a `local_store:put` carrying the full migrated envelope with a `replace: true` flag. The hook opens one `readwrite` transaction across every user-owned store plus `meta`, clears each store, writes the migrated records, updates `meta.schema_version`, and bumps `meta.seq` in the same transaction. If the transaction aborts (quota, browser interruption, tab close, unexpected error), no store is left partially written — either every store reflects the import or none does. The hook `pushEvent`s `local_store:ack` on success, and a failed ack leaves the *pre-import* browser state intact and surfaces a persistent, non-dismissible error state on the affected surface.
- **FR-7: Version handling.** An envelope whose `schema_version` is *older* than the deployed server version is migrated forward through the ordered `LocalStore.Migrations.migrate/3` chain and imported at the current version. An envelope whose `schema_version` is *newer* than the deployed server version is rejected with an explicit `newer_unsupported` error and no client-store change; the UI states that this browser holds data from a newer version and offers to re-download the export unchanged. ADR-0004 §"Schema versioning and migration" and its "MUST NOT write" clause.
- **FR-8: Reset with category-and-count preview and post-deletion verification.** Reset lists categories and counts by reading the current hydrated assigns, requires an explicit destructive confirmation, then `push_event`s a `local_store:reset`. The hook opens one `readwrite` transaction across every user-owned store plus `meta`, deletes each store's contents, resets `meta` to a freshly-initialized singleton (bumping `seq`), commits, then broadcasts on `BroadcastChannel("dos_local_store")` so peer tabs re-hydrate to empty. `localStorage.dos_boot_state` is set to `"never"`. The hook then re-reads every store in a `readonly` transaction and `pushEvent`s a verification result before the server transitions to the first-run state; if verification reports any surviving record, the UI stays in an error state and the first-run flow is not shown. INV-3, INV-24.1.
- **FR-9: Prohibited-word copy contract for export/import/reset.** No surface introduced by this card uses "backup", "backed up", "synced", "safe", "we'll remember", "your account", "restore" (except as an accessible verb for the local file-input action, and never in a way that implies remote durability). Every export surface is accompanied by an always-visible statement that the record lives in this browser only and that clearing browser data deletes it permanently. INV-5, INV-25, ADR-0004 §"Export and import".
- **FR-10: Browser support and offline behavior.** Export, import, and reset all work in every browser in the [DOS-M09-009](DOS-M09-009.md) support matrix. Export and reset function **without a network connection** because they are entirely client-side; if the user is offline when they invoke them the `LocalStore` hook completes the operation and surfaces success. Import requires a live LiveView socket because validation/migration are server-side; if the socket is disconnected the import UI states this plainly and offers to retry when reconnected. This is the honest degradation shape ADR-0004 §"Consequences — Lost" describes; it is not "offline import" and MUST NOT be described as such. _Retires pre-pivot FR-10's physical iOS+Android airplane-mode matrix, replacing it with the browser/engine matrix owned by DOS-M09-009._
- **FR-11: Diagnostic export (opt-in, redacted).** A separate "diagnostic summary" action produces a human-readable text summary — record counts, browser/engine identification, `navigator.storage.estimate()` output, IndexedDB version, `meta.persist_granted`, hydration state timings — and offers it as a `.txt` download. It MUST NOT include VINs, odometer values, service dates, note text, or custom vehicle nicknames (INV-4, ADR-0004 §"Logging" prohibitions apply verbatim to this file). Nothing is uploaded automatically; the user pastes it if they choose.
- **FR-12: Log-scanning enforcement gate.** The scripted-session test required by ADR-0004 §"Enforcement" — drive a full `hydrate → several mutations → export → clear → import` scenario with `capture_log`, assert no VIN, odometer value, service date, note text, or custom vehicle name appears in any log line — is authored under this card and blocks the release pipeline. INV-3, INV-4.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilStickerWeb.LocalStore` JavaScript hook (extended, not new) owns every IndexedDB transaction and every DOM-side download/upload primitive for this card. It exposes `export()`, `importFile(file)`, `reset()`, and `diagnosticSummary()` methods invoked from the settings LiveView.
- `DigitalOilStickerWeb.SettingsLive` (or the equivalent post-M02 route) owns the settings UI, the preview state, the confirmation modals, and the copy contract. It renders assigns produced by the domain module below.
- `DigitalOilStickerWeb.LocalStore.Server` (Elixir) — the `handle_event` handlers for `local_store:hydrate` (extended with an `import: true` branch), `local_store:put` (extended with `replace: true`), `local_store:reset`, and `local_store:reset_verify`. It calls into the domain module for validation, migration, preview computation, and typed error shaping.
- `DigitalOilStickerWeb.LocalStore.Migrations` — pure `migrate/3` functions authored in [DOS-M09-001](DOS-M09-001.md); this card adds fixture coverage for every version step and asserts round-trip stability.
- No module under `DigitalOilSticker.Catalog`, `DigitalOilSticker.Garage`, or `DigitalOilSticker.Forecast` gains a Phoenix or LiveView dependency; the ADR-0004 §"Enforcement" static check remains green.
- **Deleted for the browser MVP:** every reference to `Mob.Files`, `Mob.Storage`, `Mob.Socket`, root `Mob.Screen`, and the DeviceCommandBroker. These are retained in the historical section for the native re-entry only.

### Data and persistence

- Envelope shape is authoritative and matches ADR-0004 §"Payload envelope" byte-for-byte. `schema_version` is the server-owned monotonically increasing integer. `seq` is the browser's current `meta.seq` at export time. `tab_id` is included for symmetry with the hydrate envelope but is ignored on import.
- Canonical serialization for the digest: `Jason.encode!/2` with `pretty: false`, then a post-processing step that sorts object keys deterministically at every level and normalizes numeric encodings. The exact serializer is committed as `DigitalOilSticker.LocalStore.CanonicalJson` with property tests; the digest algorithm is SHA-256, encoded as lowercase hex.
- The envelope is subject to the ADR-0004 §"Validation" hard caps on import (≤ 1 MiB decoded, ≤ 200 vehicles, ≤ 5 000 events, ≤ 20 000 readings). Exceeding a cap yields an explicit `cap_exceeded` error naming the cap; the import UI offers "re-download this file for the record" but does not partial-import.
- The client stores enumerated in ADR-0004 §"Storage layout" are the only stores read during export and the only stores cleared during reset. No other browser storage (cookies, other IndexedDB databases from unrelated origins, extension storage) is touched.
- Server holds the imported payload in `socket.assigns` for the socket lifetime only (INV-24.1). The scratch copy used for preview computation is a plain Elixir value; nothing is written to any Ecto repo. The deployment has one repo, `CatalogRepo`, opened read-only (ADR-0004 §"Catalog database on Fly").

### Interfaces and events

- Client → server: `local_store:hydrate` with `{envelope, import: true}` opens the preview flow; `local_store:reset_verify` with `{stores: %{...counts...}}` reports the post-deletion state.
- Server → client: `local_store:put` with `{mutation_id, seq, replace: true, upserts: [...], deletes: []}` commits an approved import; `local_store:reset` with `{mutation_id}` triggers the reset transaction; standard `local_store:ack` acknowledges both.
- Broker/correlation-ID protocol from the pre-pivot spec is deleted. The `mutation_id` field on `local_store:put`/`local_store:reset` — already required by ADR-0004 §"Mutation round trip" — is the sole correlation mechanism.
- Successful import and successful reset both publish the DOS-M05-001 invalidation events so any derived assigns (forecast, due state) recompute. Export publishes nothing.

### Failure and recovery behavior

- Distinct actionable errors for import: `parse_error`, `envelope_shape_error`, `unknown_top_level_keys`, `digest_mismatch`, `cap_exceeded`, `newer_unsupported`, `duplicate_id`, `broken_reference`, `catalog_incompatible`, `quota_exceeded_on_commit`. Each renders its own message and its own recovery affordance. None mutates the pre-import browser stores.
- Injected `readwrite` transaction failure mid-import must leave every user-owned store in its pre-import state (proven by IndexedDB's own transaction atomicity plus a test that opens the store after abort and asserts full pre-import content).
- File-input cancel is a first-class non-error outcome. Closing the tab or the browser mid-preview simply discards the socket assigns; no partial state is written anywhere.
- Reset interrupted before the transaction commits leaves the store unchanged (again, IndexedDB atomicity). If the verification step fails (some record survived), the UI shows an error state and does not transition to first-run.
- Quota-exceeded on import commit is surfaced with a quota-specific message pointing at the browser's storage settings, offers to re-download the same export the user just tried to import, and preserves the pre-import state.

### Security and privacy

- Every honesty statement runs *before* the download link is materialized (FR-2, FR-9). The user reads what an unencrypted export can contain before their browser writes bytes to disk.
- Envelope exclusions in FR-1 are enforced by the test suite: an export is generated, parsed, and its keys asserted against an allowlist; any additional top-level key or any known-sensitive substring in a value fails the build.
- Import validation runs the ADR-0004 §"Validation" gate: size caps, changeset per `schema_version`, referential checks, and quarantine of per-record failures rather than session-wide rejection.
- The `import: true` marker on `local_store:hydrate` cannot be used to escape the ordinary rate limits ADR-0004 §"Rate limiting and abuse" puts on hydrate events; a repeated flood of oversized imports fails the same way any other oversized hydrate does.
- No exported bytes ever reach a server route, a log line, or an error page. The FR-12 log-scanning gate is the enforcement.
- Neither the export nor the diagnostic summary contains the `tab_id`, the session cookie, `SECRET_KEY_BASE`-derived material, or the client IP (ADR-0004 §"Logging").

### Accessibility and performance

- The destructive confirmations (Replace local data, Reset) meet WCAG 2.2 AA against the browser assistive-technology matrix in rescoped [DOS-M07-002](DOS-M07-002.md): they are keyboard-operable, focus is trapped in the modal, the destructive verb is stated in the accessible name, and the confirmation cannot be issued by a single accidental tap or single Enter press on the initial focus.
- Preview counts, catalog compatibility notes, quarantine lists, and each distinct error state are screen-reader navigable with reviewed copy that satisfies FR-9.
- Export of a realistic multi-year single-vehicle history (target: ≤ 1 000 events, ≤ 5 000 readings, well under the 1 MiB envelope cap) completes in under one second on the browser matrix; the download is initiated within 200 ms of the click. Formal budgets remain [DOS-M07-003](DOS-M07-003.md) scope.

## UX and content states

- **Export flow.** Explanation card (including the unencrypted-content honesty statement) → "Download export" primary action → browser download initiated (no server round trip) → success confirmation showing the digest and file name → failure state (rare: hook exception, out-of-quota during envelope construction). No share-sheet state; no cancellation state (the browser's own download UI owns cancellation).
- **Import flow.** File input entry point → parsing progress (usually instant) → digest verification result → preview state (per-store counts, vehicle identity, date range, catalog compatibility notes, quarantine list, prohibited-word-clean explanatory copy) → explicit "Replace local data" confirmation → atomic-replace progress → success confirmation → each distinct validation-failure state with actionable guidance (FR-7, "Failure and recovery"). File-cancel returns silently to the settings screen.
- **Reset flow.** Category-and-count listing → explicit destructive confirmation with the honest storage-loss copy → deletion progress → verification result → first-run state; a separate, honestly worded paragraph explains that the server-side catalog (which is not personal data and never was) is unaffected.
- **Diagnostic summary flow.** Opt-in entry point → generated `.txt` download → explicit "nothing is uploaded" statement → link to the FR-11 redaction rules for a user who wants to audit before sharing.

Under all four flows, the ADR-0004 §"First-paint and empty-state rules" states (`:hydrating`, `:empty`, `:storage_unavailable`, `:data_missing`) render exactly as [DOS-M09-004](DOS-M09-004.md) specifies; this card does not introduce alternate empty-state copy.

## Test plan

### Automated

- **Round-trip and property tests.** Generate valid M05 states via StreamData, export, digest-verify, parse, migrate through zero-or-more version steps, and assert `assigns` equality after import (AC-1, AC-5).
- **Canonical JSON tests.** Assert that shuffling object-key insertion order produces the same digest; assert that any non-canonical whitespace change would produce a different digest (regression guard for the canonicalization rule).
- **Corrupt-fixture suite.** Each of the eight AC-2 error types has at least one committed fixture and one test asserting the typed error, the copy key rendered, and unchanged post-attempt stores.
- **Atomicity tests.** Inject a `readwrite` transaction abort during the `local_store:put` `replace: true` step (via a faulted store method in the hook's test harness) and assert every user-owned store retains its pre-import content.
- **Reset tests.** Category/count accuracy against realistic hydrated assigns; deletion verification (verification probe finds zero records); the post-reset render assertion for first-run state; the `BroadcastChannel` peer-tab re-hydrate assertion.
- **Version tests.** Newer-unsupported rejection without side effects; older-supported migration forward with the write-back to the client's storage (ADR-0004 §"Schema versioning and migration" step 5).
- **Log-scanning enforcement.** The FR-12 / AC-6 scripted-session test, wired as a release-gating check under the ADR-0004 §"Enforcement" bucket.
- **Copy linter.** The AC-7 prohibited-word check runs against all templates and locale files under the settings scope.

### Manual / browser matrix

## Rollout and rollback

Ships as part of the normal MVP Fly.io deploy pipeline behind the CI gates in rescoped [DOS-M01-006](DOS-M01-006.md) and the release-provenance work in [DOS-M09-006](DOS-M09-006.md). The envelope `schema_version` is stamped from day one (FR-1, AC-5); any later schema change adds a new `LocalStore.Migrations` step and a fixture at the new version. Older exports created against a prior deploy remain importable per the "migrate forward" clause of FR-7; newer exports created against a later deploy are the "MUST NOT write" rejection path for a rollback.

Code rollback does not orphan users: previously downloaded exports remain importable against any deploy at or after their `schema_version`, and reset requires no server rollback coordination because the browser is the sole system of record. There is no staged rollout — export, import, and reset are user-invoked and appear in the settings UI once deployed.

## Risks, decisions, and open questions

- **Risk (accepted).** Users treat unencrypted downloads as private files. Mitigated by the mandatory before-download honesty statement (FR-2) and privacy-reviewed copy (FR-9). Consistent with ADR-0004 §"Consequences — Lost" wording.
- **Risk (accepted).** Users read "hosted app" as "my data is on their server". This is the exact reading INV-25 exists to counter; the FR-9 always-visible statement and the M09-004 copy contract are the mitigations. Not eliminated by any technical mechanism — it is a copy discipline.
- **Risk (open).** File-input UX on mobile browsers is inconsistent; some iOS/Android browsers surface a document picker that lists sources this app cannot describe. Documented by the M09-009 matrix as observed behavior; no attempt to normalize.
- **Risk (open).** A user in private-browsing mode who imports an export will lose the import when the session ends. The import flow detects `storage_unavailable` (per ADR-0004 §"Private browsing and blocked storage") and refuses to proceed with an explanation, but the risk of surprise remains and is recorded.
- **Decision to record.** SHA-256 as the digest algorithm and the canonical-JSON algorithm defined in the technical contract; both frozen in the AC-5 schema document.
- **Decision to record.** M05 import is **replace-only**. The user-choice replace/merge option ADR-0004 §"Export and import" mentions is a post-M05 decision recorded in the open-questions list below.
- **Decision to record.** Reset does not touch the (server-side, read-only, non-personal) catalog. The reset UI's separate paragraph makes this explicit.
- **Open question.** Whether the M08 multi-vehicle work reopens the replace/merge decision (importing an export from a different browser that has a different vehicle set into an existing garage is exactly the case merge would serve). Tracked against rescoped [DOS-M08-000](DOS-M08-000.md).
- **Open question.** Whether the FR-11 diagnostic summary is worth its complexity given no third-party error-reporting service is permitted (ADR-0004 §"No third-party anything"); if defect intake in rescoped [DOS-M07-006](DOS-M07-006.md) does not require it, this FR could reduce to a "storage status" panel only.

## Superseded pre-pivot spec (historical record)

> This section preserves the card as chartered before the 2026-08-01 pivot to browser-first, and is retained for historical readability of the ADR record. The Outcome above is authoritative.

### Outcome (pre-pivot)

A user can create a portable local backup, validate and restore it on a compatible app, and intentionally erase all user data without an account or support intervention.

### Why this matters and what it unblocks (pre-pivot)

App uninstall, device loss/replacement, and storage corruption are real risks. A local-only product needs user-controlled portability and a safe QA/recovery path before beta. This is the §5 "import/export or another approved local recovery mechanism" launch-hardening requirement realized in M05. It blocks beta/release readiness in DOS-M07-001 and DOS-M07-004, and the M08 migration.

### Context and source of truth (pre-pivot)

- Master roadmap prompt (`digital-oil-sticker-claude-code-roadmap-prompt.md`), §11.3 catalog entry "DOS-M05-007 — Provide local export, import, reset, and recovery controls".
- §3 rule 1 (no online accounts: recovery must be local and user-controlled) and rule 2 (offline from first launch).
- §4.1 bridge rules: capabilities requiring `Mob.Socket` go through the root `Mob.Screen` via the DeviceCommandBroker; a Phoenix LiveView socket is never passed to a Mob plugin API.
- §5 Launch hardening: import/export or another approved local recovery mechanism.
- §7 production shell security: opt-in diagnostic export is local, reviewable, and redacted; no telemetry.
- §8 `UserRepo` baseline: the user-owned record set that the export envelope must cover, and the forward-migration rules a restore must run.
- DOS-M05-001 (contexts, transactions, typed errors), DOS-M05-003 and DOS-M05-004 (the profile and history being exported), and DOS-M06-005 for the notification-cancellation portion of reset.

### Included (pre-pivot)

- Full export through `Mob.Files`/native share surfaces.
- Schema metadata in the export envelope.
- Checksums (SHA-256 content digest) for accidental-corruption detection.
- Preview-before-import with counts, identity, date range, and compatibility warnings.
- Replace semantics for import (M05 does not merge).
- Corruption/version error handling with distinct actionable errors.
- Reset with category/count listing, explicit destructive confirmation, and post-deletion verification.
- Local diagnostic summary (opt-in, human-readable, redacted by default).

### Excluded (pre-pivot)

- Automatic cloud backup.
- Background sync.
- Encrypted key escrow.
- Importing arbitrary third-party service records.

### Preconditions (pre-pivot)

- DOS-M05-001, DOS-M05-003, and DOS-M05-004 are closed: the complete user-owned record set (profile, vehicle, plans, history, readings, usage, preferences) exists to export.
- The DeviceCommandBroker/root `Mob.Screen` path from packaging/bootstrap work is available for file-picker/share commands.
- The notification-cancellation portion of reset additionally depends on DOS-M06-005; the rest of this issue must not stall on it (reset cancels locally tracked pending reminders when that capability exists).

### Functional requirements (pre-pivot)

- FR-1: Export a documented, versioned UTF-8 JSON envelope containing product/export schema version, creation instant, app version, catalog identity, unit metadata, and every user-owned record. Do not include cache entries, device IDs, notification permission tokens, raw logs, or secrets.
- FR-2: Produce a SHA-256 content digest for accidental-corruption detection. State plainly that a default export is not encrypted and may contain vehicle/maintenance information.
- FR-3: Use the Mob file picker/share APIs and application document directory; do not route exports through a WebView download URL or remote server.
- FR-4: Resolve/write app-local files through the approved `Mob.Storage`/filesystem boundary. Any picker or share capability that requires `Mob.Socket` is invoked by the root `Mob.Screen` through the DeviceCommandBroker, with an allowlisted private path, correlation ID, cancellation result, and root-containment check; a Phoenix LiveView socket is never passed to a Mob file/share API.
- FR-5: Import is two phase: parse/size-limit/schema/checksum/referential validation into memory or a temporary store; then show counts, vehicle identity, date range, catalog compatibility warnings, and "replace local data" confirmation. M05 does not merge.
- FR-6: Restore is atomic and runs normal forward migrations. A failed import leaves the existing database unchanged.
- FR-7: A newer unsupported export is rejected without destructive side effects; an older supported export is migrated.
- FR-8: Reset lists categories and counts, requires an explicit destructive confirmation, cancels locally tracked pending reminders when that capability exists, deletes user records and preferences, and then verifies deletion. The installed public catalog/cache may remain and must be described separately.
- FR-9: Diagnostic export is opt-in, human-readable, and redacts notes, exact vehicle nickname, and mileage values by default; nothing is uploaded automatically.
- FR-10: Export, import, and reset all work offline on iOS and Android, with documented native picker/share behavior and cancellation handling.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

- A dedicated data-portability domain module owns envelope serialization, validation, digest computation, and reset orchestration; settings/recovery LiveViews render its typed results.
- The root `Mob.Screen` plus DeviceCommandBroker own every native file-picker/share interaction (FR-4); LiveViews and domain code never touch `Mob.Socket`.
- `Garage`/`Maintenance` context deletion APIs execute reset; the portability module verifies deletion afterward rather than trusting a single call.

#### Data and persistence

- Export reads every user-owned `UserRepo` record per §8: `local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications` (as user-owned reminder configuration/state), and relevant `schema_events` versioning facts — as defined by the committed export schema document.
- The envelope records product/export schema version, creation instant, app version, catalog identity, and unit metadata (FR-1); values use canonical units and stable IDs so restore is deterministic.
- Import staging happens in memory or a temporary store, never in the live database; atomic restore swaps in committed data only after full validation and confirmation.
- Reset deletes user records and preferences and verifies deletion; the installed public catalog/cache may remain and is described separately (FR-8).

#### Interfaces and events

- Domain APIs: `export/0-1` (build envelope + digest, then broker share/save command), `validate_import/1` (phase one), `apply_import/1` (phase two, post-confirmation), `reset/1` (post-confirmation), `diagnostic_summary/1` (opt-in, redacted).
- Broker commands carry correlation IDs and return success, cancellation, or typed failure; cancellation is a first-class non-error outcome (FR-4, FR-10).
- Successful import/reset publish the DOS-M05-001 invalidation events so any derived state and (post-M06) reminder reconciliation react; export publishes nothing.

#### Failure and recovery behavior

- Truncated, tampered, oversized, wrong-product, newer-version, duplicate-ID, and broken-reference files fail with distinct actionable errors and no local-data change.
- Injected failure mid-restore leaves the pre-import database intact (atomicity evidence required).
- Picker/share cancellation returns the user to a stable state with no partial file and no dangling temp store.
- Reset interrupted mid-way must not leave a half-erased state that claims to be first-run; verification (FR-8) is the gate before the first-run state is shown.

#### Security and privacy

- The export honesty statement (FR-2): default export is not encrypted and may contain vehicle/maintenance information — shown before the file leaves the app via share.
- No cache entries, device IDs, notification permission tokens, raw logs, or secrets in the envelope (FR-1); diagnostic export redacts notes, exact vehicle nickname, and mileage values by default (FR-9).
- Nothing is uploaded automatically, ever; all destinations are user-chosen native share/save targets on-device (FR-3).
- Import validation enforces size limits and schema checks before parsing deeply — defense against malformed or hostile files (the malicious/corrupt fixture suite is required evidence).

#### Accessibility and performance

- Destructive confirmations (import-replace, reset) are fully accessible, cannot be completed by a single accidental tap, and clearly announce what will be lost.
- Preview and error states are screen-reader navigable with reviewed copy.
- Export/import of realistic multi-year histories completes within reason on device (measured informally here; formal budgets are DOS-M07-003 scope) with progress indication for long operations.
