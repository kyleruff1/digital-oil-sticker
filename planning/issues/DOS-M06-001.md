## Outcome

A reviewed forecast specification, pure function contract, and golden-vector corpus remove all ambiguity from data eligibility, robust averaging, fallback behavior, confidence, and the “whichever comes first” rule. The specification is normative: it defines exact formulas, thresholds, reason codes, and a frozen `forecast_policy_version` so that any two independent implementations produce identical results for every golden vector.

## Why this matters and what it unblocks

Forecast code, dashboard language, tests, reminder planning, and future algorithm migrations must agree on the same result. Writing the policy first prevents product behavior from being hidden inside LiveView handlers. Master prompt §9 requires that "The algorithm issue must choose and freeze weights/half-life; no screen may implement its own arithmetic" and that "M06 freezes exact thresholds with tests" — this issue is where both happen. It blocks `DOS-M06-002` through `DOS-M06-005` (capture, engine, presentation, and reminder planning all consume this policy) and `DOS-M08-003` (future policy evolution starts from this versioned baseline).

## Included

- Canonical units: mileage in canonical miles at full precision internally (integer/decimal, no binary floating-point equality), time intervals in whole months, dates as local `Date` values; metric entry converts at the boundary per §8 ("integer base units for persisted mileage … convert at the boundary").
- Eligible sample window: normalization to one effective point per local date, the `7 <= elapsed_days <= 90` adjacency rule, and the trailing 180-day eligibility window.
- Weekly-rate calculation: `delta_miles * 7 / elapsed_days` per interval, weighted-mean aggregation with the exact weight and evidence formulas below.
- Outlier rule: median/MAD robust statistics with the exact rejection threshold and the minimum-retention safeguard.
- Baseline blending: the declared weekly mileage as a prior, `observation_share` blending, and full replacement after 42 evidence-days.
- Calendar arithmetic: clamped month addition, mileage arrival-date projection, leap-day and month-end behavior.
- Overdue behavior: crossing dates on/before `today`, overdue status semantics, retained crossing date for explanation.
- Confidence tiers: deterministic `high`/`medium`/`low` criteria with machine-readable downgrade reasons.
- Stale inputs: stale-aggregation exclusion, stale-observation confidence caps, and unknown states when data cannot support a projection.
- Algorithm versioning: `forecast_policy_version` semantics, recompute-on-upgrade rules, and persistence requirements.
- Error/reason codes: the full closed set of result, cause, exclusion, and downgrade codes, including `:insufficient_interval` and `:missing_service`.
- The golden-vector corpus and worked human-readable examples that make the specification independently verifiable.

## Functional requirements

- FR-1 (pure entry point): The pure entry point accepts `today` as an explicit local `Date` plus: current odometer segment; last completed oil-change date/odometer; selected time interval in whole months or `nil`; selected distance interval in canonical miles or `nil`; nonfuture odometer observations; optional user-declared non-negative weekly miles; and policy version. It never reads the system clock, database, locale, or UI state internally.
- FR-2 (baseline targets): `time_target = add_calendar_months_clamped(service_date, interval_months)` and `mileage_target = service_odometer + interval_miles`. Month addition preserves the day when valid and clamps to that target month's final day (for example, January 31 + 1 month = February 28 or 29).
- FR-3 (observation normalization and interval construction): Normalize observations to one effective point per local date in the current odometer segment using the explicitly accepted latest correction. Sort ascending. Build adjacent intervals only when `7 <= elapsed_days <= 90`, both points are on/before `today`, and mileage delta is non-negative. The weekly rate is `delta_miles * 7 / elapsed_days`. Preserve zero-rate intervals. Exclude shorter intervals as too noisy and longer intervals as stale aggregation, retaining a reason code for explanation.
- FR-4 (outlier detection and retention safeguard): Consider eligible intervals ending within the trailing 180 days. If at least four rates exist, calculate median `m` and median absolute deviation `MAD`; robust sigma is `1.4826 * MAD`. Mark a rate an outlier when `abs(rate - m) > max(3 * robust_sigma, 50 miles/week, 0.5 * max(m, 1))`. Never silently discard points: retain their IDs/reason. If filtering would leave fewer than three intervals or remove at least half, retain all rates, set `unstable_samples = true`, and downgrade confidence.
- FR-5 (observed rate aggregation): Compute the observed weekly rate as a weighted mean of retained interval rates. Each weight is `min(elapsed_days, 28) * 0.5^(age_days_of_interval_end / 42)`. Do not round during calculation. `evidence_days = min(42, sum(min(elapsed_days, 28)))` and `observation_share = evidence_days / 42`.
- FR-6 (baseline blending): Treat the user's declared weekly mileage as a prior, not truth. When observed and declared rates both exist, `effective_rate = observation_share * observed_rate + (1 - observation_share) * declared_rate`; after 42 evidence-days the observed value fully replaces the prior. With only observed data use the observed rate. With only declared data use the declaration. With neither, mileage arrival date is unknown. Zero effective rate also means unknown unless the recorded odometer has already reached the threshold.
- FR-7 (mileage arrival projection): The mileage arrival date, when not already reached and rate is positive, is `latest_reading_date + ceil((mileage_target - latest_reading_miles) / effective_rate * 7)` calendar days. Do not call the projected mileage an observed current odometer. If the formula lands on/before `today`, mileage status is overdue as of `today` while retaining the calculated crossing date for explanation.
- FR-8 (earlier-wins resolution): Candidate due dates are the time target and projected mileage arrival date. `estimated_due_date` is the earlier known candidate; label its cause `:time`, `:mileage`, or `:both` on a tie. If mileage projection is unavailable, the numeric mileage threshold remains visible but time is the only schedulable candidate. If neither interval dimension exists, return `:insufficient_interval`; if service baseline is missing, return `:missing_service`.
- FR-9 (deterministic confidence): Confidence is deterministic. `high` requires at least four retained intervals, observation span ≥42 days, latest observation age ≤14 days, observation share = 1, not unstable, and robust relative dispersion `(1.4826 * MAD / max(m, 1)) <= 0.35`. `medium` requires at least two retained intervals, span ≥21 days, latest age ≤30 days, observation share ≥0.5, and not unstable. Everything else with a forecast is `low`. Declared-only forecasts are always low. Return machine-readable downgrade reasons.
- FR-10 (persistence and versioning contract): Persist `forecast_policy_version`, input record IDs/revisions, computed-at date/instant, raw targets, effective rate at full precision, cause, confidence, excluded interval IDs, and reason codes. Display rounding never changes stored results. A policy upgrade recomputes; it does not mutate source history.
- FR-11 (golden-vector corpus): The corpus covers, at minimum, every scenario enumerated in AC-2 below, each vector stating full inputs (including `today` and policy version) and full expected outputs (targets, rate, cause, confidence, reason codes, excluded interval IDs).
- FR-12 (normative completeness): The specification contains no “TBD” branches, defines every reason code it emits, and includes worked human-readable examples suitable for support and QA.

## Technical implementation contract

### Components and ownership boundaries

- Deliverable is a normative specification document (forecast RFC/ADR) plus a machine-readable golden-vector corpus, owned by the Domain Rules workstream and reviewed by engineering, design, data, and QA.
- The specification defines the contract that `DigitalOilSticker.Forecasting` (master prompt §7) must implement in `DOS-M06-003`; no LiveView, Ecto, or bridge concern appears in the policy. The pure function boundary is the FR-1 input record and a typed result; the spec names the module-level contract but ships no application code.
- Policy versions are immutable: version 1 is frozen at approval; any change is a new version with its own vectors and an ADR.

### Data and persistence

- The spec fixes the persisted forecast record shape consumed by `DOS-M06-003` and stored per §8 `forecast_snapshots`: `forecast_policy_version`, input record IDs/revisions, computed-at date/instant, raw targets, effective rate at full precision, cause, confidence, excluded interval IDs, and reason codes.
- The spec fixes canonical units (miles, whole months, local dates) and the rule that display rounding never changes stored results; metric entry is converted at the boundary and covered by a dedicated golden vector.
- Input tables are the §8 `service_events`, `odometer_readings`, and `usage_profiles` contracts as frozen by `DOS-M05-003`/`DOS-M05-004`; the spec references their fields but changes nothing about them.

### Interfaces and events

- The pure contract is a single entry point taking the FR-1 inputs and the policy version and returning a typed result carrying targets, effective rate, cause (`:time` | `:mileage` | `:both`), confidence (`high` | `medium` | `low`), reason codes, and excluded interval IDs, or the typed non-results `:insufficient_interval` / `:missing_service`. The concrete Elixir typespec is finalized in `DOS-M06-003` but must be expressible without loss from this spec.
- No events are emitted by a specification; the downstream `forecast_changed(vehicle_id, revision)` event contract belongs to `DOS-M06-003`.

### Failure and recovery behavior

- The spec must define total behavior: every input combination maps to a defined result or a typed non-result; the algorithm never returns NaN/infinity or a date outside supported bounds.
- Degenerate inputs are specified, not left to implementations: MAD = 0, zero driving, excessive outliers (minimum-retention safeguard with `unstable_samples = true`), same-day corrections, reset segments, and empty observation sets.
- Recovery from a policy defect is by issuing a new policy version and recomputing; stored snapshots from the old version remain explainable by their recorded version (FR-10).

### Security and privacy

- The specification and golden vectors contain no real user data, VINs, locations, or personal identifiers; vectors use synthetic odometer and date values only (consistent with §7's redaction rule for fixtures).
- The policy consumes only locally entered odometer, date, interval, and declared-usage values; it must not require or reference any sensor, network, or telematics input.

### Accessibility and performance

- Reason codes and confidence tiers must be designed for accessible presentation downstream: every downgrade or exclusion has a machine-readable code that `DOS-M06-004` can render as plain-language, non-color-dependent text.
- The spec states a complexity expectation: computation is linear in the number of observations in the trailing window so `DOS-M06-003`'s worst-supported-history benchmark has a defined target.

## UX and content states

N/A — specification issue with no shipped UI. However, the spec must supply the semantic vocabulary the UI will render: cause labels (`:time`, `:mileage`, `:both`), non-result states (`:insufficient_interval`, `:missing_service`), confidence tiers with their exact qualifying conditions, `unstable_samples`, and per-interval exclusion reasons (too-noisy short interval, stale-aggregation long interval, outlier). Worked human-readable examples (FR-12) double as the reference for support and QA copy in `DOS-M06-004`.

## Test plan

### Automated

- Checked-in JSON or Elixir golden vectors, each pairing full inputs with full expected outputs, structured so `DOS-M06-003` consumes them directly as its acceptance suite.
- Property-test definitions (normative statements plus generator constraints) for: monotonicity (higher weekly rate cannot make mileage arrival later), clamped month arithmetic (validity, day preservation, month-end clamping, leap-day behavior), and deterministic replay (identical inputs and policy version produce structurally identical results).
- A vector-lint check (schema validation of the corpus) runs in CI so malformed or incomplete vectors fail fast.

### Manual/device matrix

- Independent spreadsheet/manual calculation for at least five vectors, performed by someone other than the spec author, attached as evidence (AC-6).
- Review walkthrough with engineering, design, data, and QA covering every branch table in the spec; sign-off recorded per discipline.
- No device matrix applies — the policy is device-independent by construction (FR-1 forbids reading clock, locale, or UI state).

## Rollout and rollback

- Rollout: the approved RFC/ADR is merged into the repository docs with `forecast_policy_version = 1`; downstream issues reference it by version. Approval is the freeze point; later edits require a new version and re-approval.
- Rollback: reverting to a prior approved revision of the spec is a normal docs change before implementation begins; after `DOS-M06-003` ships, a policy defect is corrected by issuing a new policy version that recomputes (FR-10) — never by silently editing the frozen version or mutating source history.

## Risks, decisions, and open questions

- Decision (frozen here): robust statistics (median/MAD with `1.4826 * MAD` sigma and the `max(3 * robust_sigma, 50 miles/week, 0.5 * max(m, 1))` gate) rather than mean/standard deviation, so single anomalous samples cannot swing the estimate.
- Decision (frozen here): evidence half-life of 42 days and per-interval weight cap of 28 days, satisfying §9's requirement that weights/half-life be chosen and frozen by the algorithm issue.
- Risk: the defined decimal tolerance for AC-3 could mask real divergence if set too loose; the RFC must state the tolerance explicitly and justify it against the full-precision persistence rule.
- Risk: reviewers may propose "small" behavioral tweaks late; per non-negotiable rule 10, post-approval changes require a new policy version, not an edit.
- Open question (must close before approval, may not remain TBD): the exact supported date bounds for AC-4 (the RFC must state the minimum/maximum representable projection horizon).
