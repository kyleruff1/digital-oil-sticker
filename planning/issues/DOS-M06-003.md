## Outcome

A side-effect-free Elixir engine computes forecasts from immutable input structs, while an application service safely persists/recomputes snapshots after every relevant change. The engine implements the `DOS-M06-001` policy exactly; the service guarantees that persisted forecasts are always consistent with one input revision and one policy version.

## Why this matters and what it unblocks

Separating arithmetic from Ecto/LiveView makes the estimate auditable, replayable, and testable, and gives reminder reconciliation one stable revision to consume. Master prompt §9 mandates that "no screen may implement its own arithmetic" and §7 defines `DigitalOilSticker.Forecasting` as "deterministic pure functions for mileage rate, confidence, due thresholds, and reason codes" — this issue builds that boundary. It blocks `DOS-M06-004` (presentation renders engine results), `DOS-M06-005` (the reminder planner consumes forecast revisions), and `DOS-M08-003` (future policy versions plug into the dispatcher created here).

## Included

- Typed structs: immutable input and result structs mirroring the `DOS-M06-001` FR-1 input record and typed result.
- Decimal/rational strategy: integer/Decimal arithmetic for mileage/rates with an explicit documented rounding boundary.
- Calendar helper: clamped month addition and arrival-date arithmetic implementing the spec's calendar rules.
- Result/reason types: the full closed code set from the spec (`:time`/`:mileage`/`:both`, `:insufficient_interval`, `:missing_service`, confidence tiers, exclusion and downgrade reasons).
- Policy-version dispatcher: immutable per-version modules/data definitions with version-tagged dispatch.
- Ecto loading/persistence: consistent snapshot loading and forecast persistence in the application service.
- Invalidation: honoring capture-side invalidation markers and recompute triggers.
- Concurrency control: `Ecto.Multi` or compare-and-swap revision guards against stale writes.
- The `forecast_changed(vehicle_id, revision)` event published after commit.

## Functional requirements

- FR-1 (exact implementation, typed contract): Implement the RFC exactly in a domain module with `forecast(input, policy_version) :: {:ok, result} | {:insufficient, reasons} | {:error, reason}`. Use integer/Decimal arithmetic for mileage/rates and an explicit documented rounding boundary; never use binary floating-point values as persisted equality keys.
- FR-2 (immutable policy versions): Put each policy version in an immutable module or data definition. Existing snapshots remain explainable by their version; the current version can recompute from source records. Removing old policy code requires a data migration and retained golden fixtures.
- FR-3 (transactional recompute service): The application service loads a consistent Ecto snapshot, computes outside LiveView render functions, and writes only if input revisions still match. Use an `Ecto.Multi` or compare-and-swap revision so two rapid edits cannot persist an older forecast over a newer one.
- FR-4 (recompute triggers): Recompute after profile interval, service event, odometer reading, declared usage, unit-independent value, odometer segment, date/time-zone context, or policy version changes. Presentation-only unit/locale changes do not alter the canonical result.
- FR-5 (disposable snapshots): Snapshot records are disposable derived data. If corrupt/missing, recompute from sources; never treat a cached snapshot as more authoritative than history.
- FR-6 (event publication): Publish an internal `forecast_changed(vehicle_id, revision)` event after commit so the reminder-plan service can react. Coalesce duplicate events and make consumers idempotent.
- FR-7 (deterministic replay): Replaying the same canonical input and policy version returns structurally equal results regardless of locale, timezone environment, or process restart; `today` and all time context arrive through explicit inputs/`DigitalOilSticker.Clock`, never ambient reads inside the engine.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Forecasting` (§7): the pure engine. No Repo, PubSub, Clock, or process dependencies inside `forecast/2`; inputs are immutable structs, outputs are typed results. One module (or data definition) per policy version, dispatched by the version argument (FR-2).
- A forecasting application service (same context, separate module) owns: loading a consistent input snapshot from `UserRepo`, invoking the engine, persisting the snapshot, revision management, and event publication. It runs synchronously or on a supervised foreground task after a relevant mutation and at app foreground — never via Oban or a perpetual background GenServer (§7).
- LiveView modules may call the service and read results; they never call arithmetic or reimplement any policy branch (§9).
- Calendar helpers implementing clamped month addition live in the Forecasting namespace and are the only calendar arithmetic used for forecast dates.

### Data and persistence

- `forecast_snapshots` (§8): persist vehicle/cycle ID, algorithm (policy) version, input hash, computation time, effective rate at full precision, due odometer, projected/calendar/effective dates, confidence code, and reason codes — plus the `DOS-M06-001` FR-10 fields (input record IDs/revisions, excluded interval IDs, raw targets).
- Mileage/rate values persist as integers/Decimals per the documented rounding boundary; binary floats never serve as persisted equality keys (FR-1). Display rounding happens strictly in presentation.
- A monotonic forecast revision per vehicle orders snapshots and is the value carried by `forecast_changed` and consumed by the reminder planner.
- The input hash covers the canonical input record so replay and audit can verify a snapshot against its sources (§9: "Persist the algorithm version and input hash").

### Interfaces and events

- Engine: `forecast(input, policy_version) :: {:ok, result} | {:insufficient, reasons} | {:error, reason}` with typespecs for the input and result structs mirroring the RFC vocabulary exactly.
- Service API: an idempotent `recompute(vehicle_id, trigger)` style entry point invoked by capture mutations (`DOS-M06-002`), settings/plan changes, foreground hooks, and policy upgrades.
- Event: `forecast_changed(vehicle_id, revision)` published after commit via the §7 local event contract (direct context return plus Phoenix PubSub where more than one active process needs it); events carry local stable IDs and reason codes, not display strings. Duplicate events are coalesced; consumers must be idempotent (FR-6).

### Failure and recovery behavior

- Stale-write prevention: `Ecto.Multi`/compare-and-swap ensures a slow computation cannot overwrite a newer revision (FR-3); the losing writer discards its result and may re-trigger.
- Atomicity: every relevant source mutation either commits its invalidation/recompute intent atomically or leaves the previous consistent result; the dashboard never combines targets from different revisions.
- Self-healing: a missing or corrupt snapshot is detected on read and recomputed from source records without altering source data (FR-5).
- Engine totality: per the RFC, every input maps to a typed result; `{:error, reason}` is reserved for contract violations (malformed input), not for legitimate sparse-data states, which return `{:insufficient, reasons}`.

### Security and privacy

- The engine and snapshots contain only local mechanical data: dates, odometer values, rates, codes. No VIN, notes, location, or free text enters the input struct or snapshot.
- Logs and error reports redact odometer values and vehicle identifiers per §7 production-shell rules; input hashes are non-reversible digests, safe to log.
- No network access anywhere in this issue's scope; computation is fully offline (rule 2).

### Accessibility and performance

- Accessibility: N/A — no UI in this issue; the engine's reason codes preserve the machine-readable vocabulary `DOS-M06-004` renders accessibly.
- Performance: recomputation completes within an interactive budget for the worst supported history size (benchmark required as evidence); computation is linear in trailing-window observations per the RFC's complexity expectation. `pool_size: 1` SQLite access means the service must hold transactions briefly and never block the UI thread on long computation.

## Test plan

### Automated

- ExUnit unit/property/golden suite: the full `DOS-M06-001` golden-vector corpus consumed directly, plus property tests for monotonicity (higher weekly rate cannot make mileage arrival later), month arithmetic, and deterministic replay.
- Ecto integration tests: snapshot persistence round-trips, input-hash verification, and self-healing from deleted/corrupted snapshots.
- Race tests: concurrent rapid edits with an artificially slowed computation proving compare-and-swap rejection of the stale write (AC-3).
- Mutation-to-recompute coverage matrix: one test per FR-4 trigger class (profile interval, service event, odometer reading, declared usage, unit-independent value, odometer segment, date/time-zone context, policy version) proving recompute occurs, plus a presentation-only unit/locale change proving the canonical result is unchanged.
- Locale/timezone-environment matrix runs of the golden suite (for example, differing `LANG`/`TZ` process environments) proving structural equality (AC-2).
- Dialyzer/type-contract evidence if used.

### Manual/device matrix

- Benchmark for the worst supported history size, run on representative hardware (at minimum one mid-range physical Android device and one supported physical iPhone), with timings recorded as evidence.
- Process-restart replay spot check on device: kill and relaunch the app, verify the recomputed forecast is structurally equal to the pre-kill snapshot for unchanged inputs.

## Rollout and rollback

- Ships inside the normal app build. The policy-version dispatcher makes rollout inherently staged: a new policy version is added alongside the old, recomputation migrates snapshots forward, and old snapshots remain explainable by their recorded version.
- Rollback: reverting the engine reverts to the prior policy version's code path; snapshots are disposable derived data (FR-5), so any inconsistency after rollback is repaired by recomputation from source records. Removing old policy code requires a data migration and retained golden fixtures (FR-2) — never a silent deletion.

## Risks, decisions, and open questions

- Decision (fixed by catalog): pure engine with explicit inputs, immutable policy versions, and transactional snapshot persistence; no background scheduler of any kind (§7).
- Decision (fixed by catalog): integer/Decimal arithmetic with a documented rounding boundary; floats never persisted as equality keys.
- Risk: subtle divergence between engine and spec under degenerate inputs; mitigated by consuming the golden corpus directly as the acceptance suite plus property tests (AC-1).
- Risk: SQLite `pool_size: 1` contention between recompute writes and UI reads; mitigated by short transactions, compare-and-swap over long locks, and the benchmark gate.
- Open question: whether `Ecto.Multi` alone or an explicit revision-compare column implements the CAS guard — an implementation detail to be resolved in code review; both satisfy FR-3 and the race test decides adequacy.
