> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Keep the desired-reminder plan as a pure domain output rendered as in-app due/overdue state; the `mob_notify` delivery half splits out into a new deferred native issue._

## Outcome

Forecast results and user reminder preferences produce a deterministic, inspectable **desired-reminder plan** as a pure domain output of `DigitalOilSticker.Reminders`, and the browser MVP renders that plan as **in-app due/overdue state** in the hosted Phoenix LiveView application. Reminder preferences and the resulting due/overdue view are computed on every hydration and after every mutation, persisted only in the user's anonymous IndexedDB store, and never written to any server-side row or cache. A `NotificationAdapter` behaviour exists as a seam whose only MVP implementation is the in-app due-state renderer; every other implementation (Web Push, OS-scheduled local notifications, `mob_notify`) is deferred behind an explicit ADR gate. The UI states plainly that the app does not notify the user when it is closed and never implies otherwise.

## Why this matters and what it unblocks

Under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) the MVP is a hosted Phoenix LiveView application on Fly.io with all personal data in IndexedDB; there is no on-device BEAM, no `Mob.Screen`, no `Mob.Socket`, no `DeviceCommandBroker`, no `mob_notify`, and no OS-scheduled local notification path in the browser (Constitution 2.0.0 [INV-1](../../docs/product/CONSTITUTION.md#1-platform-promise) restated, [INV-17 amended](../../docs/product/CONSTITUTION.md#6-reminders-and-notifications)). The forecasting math and the desired-reminder plan are pure Elixir domain code and survive the pivot intact; the OS-delivery half does not. Splitting the card at that seam is the only way to keep the surviving planner honestly shippable without gating it on infrastructure the MVP does not have.

The pure planner produces the deterministic "what the app currently recommends" set that the browser UI turns into due/overdue badges, banners, and settings previews. This work is what makes the M06 forecasting epic legible to the user in the browser: without it, a numerically correct estimate never crosses into user-visible reminder state.

- It consumes the frozen `estimated_due_date` semantics from `DOS-M06-001` and the forecast revisions from `DOS-M06-003`.
- It reuses the reviewed OLM/manual warning and confidence presentation from `DOS-M06-004` in the settings surface (`DOS-M06-004` remains SURVIVES per the pivot ledger).
- It feeds `DOS-M06-007` (rescoped to an in-app reminder control center and a due-state correctness gate; the OS delivery-reliability portion of that card was carved out to the native re-entry).
- It writes and reads reminder preferences and plan snapshots through the [INV-24](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage) hydration/mutation round trip owned by the M09 storage adapter (`DOS-M09-002`) and hydration protocol (`DOS-M09-003`).
- It settles the Constitution 2.0.0 [INV-17](../../docs/product/CONSTITUTION.md#6-reminders-and-notifications) obligation for the MVP: in-app due/overdue state only, with a plain-language "the app does not notify you when it is closed" statement wherever reminder preferences are shown.

The following pieces of the pre-pivot spec explicitly do **not** ship here and are carved out to a parked native re-entry holding card, alongside `DOS-M00-003`, `DOS-M00-005`, `DOS-M06-006`, and `DOS-M08-004`: activation of `mob_notify` in `mob.exs`, the pinned plugin version, `Mob.Screen`/`Mob.Socket` command dispatch, `MobNotify.schedule/cancel/Mob.Permissions.request`, the Android maintenance channel, iOS/Android permission flow, and the physical-device schedule/cancel/delivery evidence. Web Push is a separate, later, still-deferred decision tracked as the `DOS-M09-010` spike and cannot be adopted incrementally through this card.

## Included

- The pure `DigitalOilSticker.Reminders` planner: a client-agnostic Elixir function that takes forecast revision, semantic `estimated_due_date`, `today`, enabled leads, local delivery time, IANA timezone, privacy mode, and vehicle ID, and returns a deterministic desired-reminder set with stable logical keys.
- A `NotificationAdapter` behaviour whose only MVP implementation is `DigitalOilSticker.Reminders.InAppDueState` — it renders the desired plan as in-app due/overdue state (badges, banners, settings previews) in the LiveView UI. No other implementation ships in the MVP.
- Reminder preference persistence through the INV-24 hydration/mutation round trip: preferences are read from IndexedDB (`prefs` singleton and per-vehicle `reminders` store as defined in ADR-0004 §"Storage layout"), placed in `socket.assigns` for the socket lifetime only, mutated via `pushEvent` → `local_store:put` → hook write → `local_store:ack`, and never persisted server-side.
- Enable/disable per-vehicle reminders (off by default), lead-time toggles (default set after opt-in: 14 days, 7 days, due day), local delivery time (default 09:00) as a *label on the plan* rather than a scheduling instruction, and privacy content preference (default generic; explicit opt-in for vehicle nickname/estimated date).
- Deterministic stable notification IDs `{vehicle_id, forecast_revision, lead_days, purpose}` and plan revision management, so that a future adapter (if ADR-approved) can be handed the same identifiers.
- An in-app due/overdue banner independent of any OS delivery path — this is authoritative for "what the app currently recommends" and is the only user-visible reminder surface in the MVP.
- Settings UX reusing `DOS-M06-004`'s reviewed warning and confidence presentation so the explain-then-enable copy is not re-designed here.
- The "honest no-alert" copy: everywhere reminders are configured or previewed, the UI states in plain language that the app does not notify the user when it is closed (INV-5, INV-17, INV-25). This includes an accessible statement announced to assistive technology, not only visual text.
- A wire-level idle-capture test (§9 "Privacy on the wire", INV-4/INV-22/INV-26) proving the deployed browser build makes zero outbound requests to APNs, FCM, Mozilla autopush, or any push-notification service during a full session that enables reminders, plans, previews, and disables them.
- A negative structural test that no module under the deployed application references `Mob.Screen`, `Mob.Socket`, `MobNotify`, `Mob.Permissions`, `mob_notify`, `mob_push`, `apns`, or `fcm` — protecting the ADR-0004 §"Enforcement" static check against silent drift.
- An explicit ADR-gate note in the code and documentation: any implementation of `NotificationAdapter` other than the in-app renderer requires a new ADR (per ADR-0004 §"Trigger conditions that revive the native track") and a Constitution revision amending INV-17 before it may be enabled in production.

## Excluded

- Everything in the pre-pivot Excluded list, unchanged and re-affirmed: remote push, `MobNotify.register_push`, `mob_push`, APNs/FCM server registration, email/SMS, exact-to-the-minute delivery guarantees, exact alarms, and cross-vehicle notification-slot allocation (M08).
- OS-scheduled local notifications of any kind. `mob_notify`, `Mob.Screen`, `Mob.Socket`, the `DeviceCommandBroker`, `mob.exs` pinning, an Android notification channel, iOS/Android permission prompts, native permission-primer flows, and any settings deep-link to OS notification preferences — all deferred to the native re-entry holding card (see Dependency rationale).
- Web Push, service-worker delivery, VAPID keys, push subscription endpoints, and any server-held per-browser subscription record — deferred as the `DOS-M09-010` spike and independently gated by INV-3/INV-4/INV-23 and INV-17's Web Push tension paragraph. This card MUST NOT add scaffolding for a future Web Push adoption that would require a server-side subscription table.
- Reconciliation of a desired plan against OS state (pre-pivot `DOS-M06-006`, now DEFER) — there is no OS state in the browser MVP to reconcile.
- Any settings surface that hints at background alerting, delivery guarantees, or a "we'll remind you" promise. This card owns the copy that prevents that surface from existing (INV-5, INV-25).
- Any write path from the reminder planner or its adapter to a server-side database, cache, ETS table, or log sink. Reminder preferences and plan snapshots exist server-side only in `socket.assigns` for the current LiveView connection (INV-23, INV-24.1).

## Functional requirements

- **FR-1 (defaults and settings — carried and rescoped):** Reminders are off by default per vehicle. The settings screen explains that the app computes due/overdue state in the browser and stores preferences in this browser only (INV-23, INV-25), that the estimate's confidence and any OLM/manual precedence still apply, and that **the app does not notify the user when the tab or browser is closed** (INV-17). Default leads after opt-in are 14 days, 7 days, and due day; users can independently toggle allowed leads and choose a local delivery time (default 09:00) as a label carried by the plan. The delivery-time value is **not** interpreted as a scheduling instruction to any OS API in the MVP; it is a preference the planner records so that a future ADR-approved adapter would receive it.
- **FR-2 (pure planner — carried):** A pure planner accepts forecast revision, semantic `estimated_due_date`, `today`, enabled leads, local delivery time, device/browser IANA timezone, privacy mode, and vehicle ID, and returns a desired-reminder set with stable logical keys `{vehicle_id, forecast_revision, lead_days, purpose}`, title/body template version, and local semantic fire date/time. The planner has no side effects, no dependency on `Phoenix.LiveView`, no dependency on the browser-storage protocol, and no dependency on any transport — this is the [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Decision 6" client-agnostic domain rule stated for this card and enforced by the ADR-0004 §"Enforcement" static check.
- **FR-3 (no past reminders, due-now collapse — carried):** Do not plan past reminders. If a new/edited forecast is already due, plan at most one `due_now` entry for the next permissible local time and show an immediate in-app banner; never emit a burst for missed lead times. Do not plan when the interval/last service is missing or mileage is the only dimension and its arrival date is unknown.
- **FR-4 (earlier-due semantics — carried):** Reminders use the earlier estimated due date (INV-13). When later readings move that date, replanning replaces obsolete entries in the desired plan; because there is no OS-scheduled state in the MVP, the in-app rendering simply reflects the new plan on the next hydration or after the mutation round trip completes. The plan records the target cause/confidence; delivered copy says "estimated" and does not claim the vehicle's live odometer (INV-12, INV-20).
- **FR-5 (privacy mode — carried and re-anchored):** Privacy mode defaults to generic banner text ("Oil change reminder — open Digital Oil Sticker for details"). An explicit setting may include the vehicle nickname and estimated date in in-app surfaces only. Under no MVP path is exact mileage, notes, VIN, oil/filter purchase history, or catalog IDs included in any user-visible reminder surface. Because there is no OS notification in the MVP, the "lock screen text" phrasing of the pre-pivot FR-5 is replaced with "in-app banner text" phrasing; the exclusion list is unchanged.
- **FR-6 (persistence and ID rules — rescoped to IndexedDB):** Preferences (per-vehicle enable/leads/delivery time/privacy mode) live in the IndexedDB `reminders` object store keyed by `reminder_id`, and any shared reminder-scoped preference lives in the `prefs` singleton (ADR-0004 §"Storage layout"). The desired plan is a *derived* value computed from preferences + forecast on hydration and after every mutation; it MAY be cached in `socket.assigns` for the socket lifetime, MUST NOT be written to any server-side row or cache, and MAY be persisted in IndexedDB only as a client-derived convenience with a plain marker that it is derived. Stable notification IDs are deterministic functions of the logical key, bounded, collision-checked, and never derived from private display text — this rule carries forward unchanged so a future ADR-approved adapter (native or Web Push) can be handed the same identifiers without a schema migration.
- **FR-7 (in-app truth — carried and now the only truth):** The in-app banner and reminder history are local and authoritative for "what the app currently recommends"; because the MVP has no OS delivery, this is the *sole* truth surface. The UI MUST NOT assert that any notification was delivered outside the app, MUST NOT imply background alerting, and MUST show the honest no-alert statement of FR-1 wherever reminder preferences are configured or previewed. Reminder state is recomputed on every LiveView mount and reconnect (INV-7, INV-24.1, INV-24.3).
- **FR-8 (adapter boundary — rewritten per finding 2):** Define a `DigitalOilSticker.Reminders.NotificationAdapter` behaviour with `render_plan/2`, `announce/2`, and `dismiss/2` callbacks that describe *what* the plan communicates to the user, not *how* any OS delivers it. Its only MVP implementation is `DigitalOilSticker.Reminders.InAppDueState`, which returns LiveView assigns describing badges, banners, and live-region announcements. **No other adapter ships in the MVP.** The pre-pivot FR-8 language pinning `mob_notify` in `mob.exs`, dispatching through the DeviceCommandBroker to the root `Mob.Screen`, and calling `MobNotify.schedule(mob_socket, ...)` is explicitly retired here and carved out to the native re-entry holding card. Any future implementation of `NotificationAdapter` (Web Push, `mob_notify`, or any other) requires a new ADR under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §"Trigger conditions that revive the native track" and a Constitution revision amending [INV-17](../../docs/product/CONSTITUTION.md#6-reminders-and-notifications) before it may be enabled in production; this gate is documented alongside the behaviour and enforced by the ADR-0004 §"Enforcement" static check that no module under the domain namespaces references `Phoenix.LiveView`, `Plug`, or transport specifics (the same check is extended here to forbid `MobNotify`, `Mob.Screen`, `Mob.Socket`, `Mob.Permissions`, `mob_push`, `apns`, `fcm`, and any Web Push subscription API surface).
- **FR-9 (retired — permission flow does not exist in the MVP):** The pre-pivot FR-9 required a call to `Mob.Permissions.request(mob_socket, :notifications)` gated on a user tap. There is no OS permission in the browser MVP because there is no OS notification. The Notifications API is not requested. Web Push permission is deferred and prohibited by exclusion. This FR is retired here and carved out to the native re-entry holding card; the retirement is stated so future readers see it is deliberate, not lost in an edit.
- **FR-10 (retired — no OS denial state to preserve):** The pre-pivot FR-10 described denial behavior for an OS permission request. Because FR-9 is retired, there is no OS denial state in the MVP; the surviving substance ("preserve preferences as desired-but-not-applied and keep the in-app due state") is subsumed by FR-7 (in-app truth is the only truth). This FR is retired here and carved out to the native re-entry holding card.
- **FR-11 (retired — no UTC scheduling and no Android channel):** The pre-pivot FR-11 committed to `mob_notify` scheduling absolute UTC instants, to command replay/cancellation idempotency across the root-screen adapter, and to a low-noise Android maintenance channel. None of that exists in the browser MVP. The FR is retired here and carved out to the native re-entry holding card. The surviving *semantic* — that the planner works in local semantic date/time and that a future ADR-approved adapter is responsible for its own timezone conversion — is preserved in FR-2 and the adapter boundary in FR-8.
- **FR-12 (Test action — rescoped to in-app preview):** A rate-limited "Preview reminder" action renders a clearly labeled test entry in the in-app due state for a few seconds without changing the real plan. It never invokes any OS notification API, never leaves the browser tab, never sends a request over the wire, and is presented as a preview of what the user would see when opening the app on the reminder day — never as a delivery test. Rate limiting is enforced client-side; the copy is reviewed against INV-5/INV-25 to avoid implying background delivery.
- **FR-13 (tap payload — rescoped to in-app link):** The in-app banner links open the vehicle's current view via a standard LiveView `navigate`; the link carries only local route/purpose/logical ID. Routing always resolves against current truth from the hydrated assigns and IndexedDB, not archived content. Malformed/stale link data opens the garage home safely. No exact mileage, note, or VIN is embedded in any link.
- **FR-14 (wire-level no-push evidence — new):** The deployed browser build MUST make zero outbound requests to APNs, FCM, Mozilla autopush, or any push-notification service during any operation of this card's flows (enable, disable, preview, plan replan, mutation round trip, reconnect). Evidence is a CI-run network capture over a full session that exercises those flows (§9 "Privacy on the wire", INV-4, INV-22, INV-26). This is the MVP half of the pre-pivot AC-7 finding-3 split.
- **FR-15 (INV-17 copy — new):** Every surface that exposes reminder preferences (settings, previews, empty state, storage-loss state) states in plain language that the app computes due/overdue in the browser, does not schedule OS notifications, and does not notify the user when the tab or browser is closed (INV-17). The statement is copy-reviewed against INV-5 and INV-25 (no "backup", "synced", "we'll remind you", "your account") and is announced to assistive technology, not only rendered visually. First-visit onboarding also mentions this so users decide whether the browser MVP fits their usage before entering data (§"UX and content states" in ADR-0004 §"First-paint and empty-state rules").

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Reminders` (client-agnostic Elixir domain module) owns the pure planner (FR-2), stable ID generation (FR-6), plan-revision management, and the `NotificationAdapter` behaviour (FR-8). It has no dependency on `Phoenix.LiveView`, on the browser storage adapter, or on any transport (ADR-0004 §"Decision 6"). It is one of the modules the ADR-0004 §"Enforcement" static check protects.
- `DigitalOilSticker.Reminders.InAppDueState` (the MVP `NotificationAdapter` implementation) converts a desired plan into LiveView assigns describing badges, banners, and live-region announcements. It is called only by the LiveView layer, is pure with respect to its inputs, and never calls out to any OS or network API.
- `DigitalOilOilStickerWeb.RemindersLive` (LiveView; module name follows the project's `_web` convention — see the existing `DigitalOilStickerWeb` namespace) owns the settings screen and the in-app banner surface. It reads reminder preferences and current due state from `socket.assigns` (populated by the M09 hydration protocol), dispatches mutations through `pushEvent` → `local_store:put`, and re-renders on `local_store:ack` (INV-24.2). Settings copy reuses the `DOS-M06-004` warning and confidence components.
- The M09 browser storage adapter (`DOS-M09-002`) owns the actual IndexedDB read/write for the `reminders` object store and the `prefs` singleton. This card consumes that API and does not re-implement it.
- The M09 hydration protocol (`DOS-M09-003`) owns the mount/reconnect hydration path and the mutation round trip. This card consumes that protocol and does not re-implement it.

### Data and persistence

- IndexedDB `reminders` object store (per-vehicle) records: `reminder_id` (UUIDv4, client-generated), `vehicle_id`, `enabled` (bool), `leads` (set of lead-day values), `local_delivery_time` (HH:MM), `privacy_mode` (`generic` | `nickname_and_date`), `template_version`, and `updated_at` (client wall clock). No server-side row exists for any of these.
- IndexedDB `prefs` singleton MAY hold a small non-personal "reminders onboarding acknowledged" boolean so first-visit copy does not re-appear on every hydration; this is a UX preference, not a personal record.
- The desired plan is *derived* from the current `reminders` record for a vehicle plus the current forecast revision and `estimated_due_date`; it is computed by the pure planner on hydration and after every mutation, held in `socket.assigns` for the socket lifetime (INV-24.1), and MAY be persisted in IndexedDB only as a client-derived convenience — never as the source of truth.
- Stable notification IDs are deterministic functions of `{vehicle_id, forecast_revision, lead_days, purpose}`, bounded to the tightest identifier length any future ADR-approved adapter is expected to require, collision-checked at generation, and never derived from private display text (FR-6).
- The IndexedDB schema additions defined here are subject to the ADR-0004 §"Schema versioning and migration" rules and to `DOS-M09-001` / `DOS-M09-002`'s schema/version-line contract. Any schema change is a forward-only migration through `LocalStore.Migrations.migrate/3`.

### Interfaces and events

- Planner: pure function from `(forecast_revision, estimated_due_date, today, enabled_leads, delivery_time, iana_timezone, privacy_mode, vehicle_id)` to `%DesiredPlan{entries: [...], stable_ids: [...], template_version: v}`.
- The planner consumes `forecast_changed(vehicle_id, revision)` from `DOS-M06-003` (SURVIVES) to invalidate/replan; replanning identical inputs makes no IndexedDB writes (AC-2). The event is delivered in-process on the server for the current socket; no cross-socket, cross-user event is published.
- Mutation round trip (per INV-24.2, ADR-0004 §"Mutation round trip"): user acts → LiveView `handle_event` → planner recomputes → server pushes `local_store:put` with `{mutation_id, seq, upserts, deletes}` → hook writes → hook `pushEvent("local_store:ack", {mutation_id, seq, status})` → server clears pending write. A failed or timed-out ack follows the ADR-0004 "Not saved to this browser" path.
- No event, message, or payload from this card is transmitted through the `DOS-M09-005` catalog query surface (INV-26).

### Failure and recovery behavior

- LiveView reconnect or Fly machine replacement re-runs hydration (INV-7, INV-24.1); the planner is re-invoked with the freshly hydrated preferences and the current forecast revision; the in-app due state re-renders with no user-visible loss (ADR-0004 §"First-paint and empty-state rules").
- IndexedDB unavailable or evicted → the M09 storage-denied / eviction UX (`DOS-M09-004`) is shown; the reminder settings surface reflects that reminders cannot be stored in this browser session and offers export/import (`DOS-M04-009`). This card does not silently degrade to in-memory state.
- Quota-exceeded on a mutation → the ADR-0004 "Not saved to this browser" state on the affected reminder record; export offered; no silent write loss.
- Malformed or stale in-app link data → routes to garage home safely (FR-13); routing always resolves against current truth in assigns/IndexedDB.
- Server restart, secret rotation, or deploy → the M09 hydration protocol re-establishes state; reminder preferences and desired plan are recomputed with no user data loss because the server was never the source of truth (ADR-0004 §"Secrets", §"WebSocket and LiveView considerations").

### Security and privacy

- Reminder preferences and derived plans exist server-side only in `socket.assigns` for the current LiveView connection (INV-23, INV-24.1). No personal-row schema is added; the ADR-0004 §"Enforcement" test asserting `[CatalogRepo]` and read-only opening is protected by this card, not weakened.

## Rollout and rollback

- Ships inside a normal Fly.io deploy of the hosted Phoenix LiveView application (ADR-0004 §"Hosting specifics"). Reminders are off by default per vehicle (FR-1), so rollout risk is opt-in by construction: users who never enable see no behavior change.
- **Rollout is a deploy.** A canary Fly deploy of the release image validates the wire-level idle-capture assertion (AC-7) and the static-check assertion (AC-8) before traffic cutover (`DOS-M09-006`).
- **Rollback is redeploying the previous image.** Because reminder preferences live only in the user's IndexedDB, a rollback loses no user data. A rolled-back build that lacks a preference field written by the newer build follows the ADR-0004 §"Schema versioning and migration" rule for a newer-than-server payload: the server enters read-only mode for that record, renders the explicit "this browser holds data from a newer version" banner, and offers export — it does not silently drop fields.
- Disabling reminders in a later build is a copy change (settings screen and honest no-alert statement); there is no OS-scheduled state to cancel because none was created (INV-17, FR-8 gate).

## Risks, decisions, and open questions

- **Risk (accepted, honest):** the MVP does not notify users when the browser is closed. This is the core product bet of the ADR-0004 pivot (ADR-0004 §"Risks and open questions" R11). Mitigation is the honest no-alert copy (FR-15, AC-12) and export/import (`DOS-M04-009`) so a user who wants reminders that fire when they aren't looking can either wait for a future Web Push or native decision, or use their own calendar. This card does not pretend to solve it.
- **Risk (accepted):** browser storage eviction can lose reminder preferences (ADR-0004 R1). Mitigation: `navigator.storage.persist()` requested by `DOS-M09-002`, honest storage-status UI in `DOS-M09-004`, and the explicit `:data_missing` state so loss is never disguised as an empty configuration.
- **Risk (accepted):** the desired plan is derived, not authoritative-in-storage. If a future adapter is added, it must not rely on the derived plan being present in IndexedDB. The FR-6 stable-ID rule and the pure planner (FR-2) mean any future adapter can recompute from the same preferences.
- **Decision (fixed by ADR-0004 and INV-17):** OS-scheduled local notifications, Web Push, and any push-service integration are prohibited in this card and require a new ADR plus a Constitution revision to enable (FR-8, AC-13). The `NotificationAdapter` behaviour exists specifically so this gate is one code-level check away.
- **Decision (fixed by INV-26):** reminder preferences and plan snapshots MUST NOT travel through the `DOS-M09-005` catalog query surface. A future feature that would require them to must add a new endpoint under a new ADR, not extend the catalog path.
- **Decision (recorded):** delivery-time is preserved as a preference the planner records, even though the MVP does not schedule anything at that time. This keeps the future-adapter contract clean and avoids a schema migration if an ADR revives OS notifications.
- **Open question:** how loudly the settings screen should surface the honest no-alert statement — banner, inline note, or expandable disclosure. Recorded for `DOS-M02-003` / `DOS-M09-004` copy work; this card ships a defensible default and defers the aesthetic decision.
- **Open question:** whether `DOS-M09-010` (PWA/Web Push spike) will change the answer for this card. Recorded so it is not forgotten; a positive Web Push decision would revive this card's scope, not silently extend it — a new ADR is required.
