## Outcome

Forecast results and user preferences produce a deterministic, inspectable desired plan. The packaged app sends typed commands through the M00/M01 DeviceCommandBroker; the registered root `Mob.Screen` requests permission and schedules/cancels local notifications through `mob_notify` using its `Mob.Socket`. Notification intent exists as data in SQLite before any native call, and no push infrastructure of any kind is introduced.

## Why this matters and what it unblocks

Treating notification intent as data before crossing the native boundary makes permission, cancellation, rescheduling, DST, killed-app delivery, and future multi-vehicle capacity testable while still proving the real device bridge early. This issue realizes non-negotiable rule 8 ("Local notifications only in v1") on real devices and is the prerequisite for `DOS-M06-006` (reconciliation of the desired plan against OS state), `DOS-M06-007` (the control center and reliability gate), and `DOS-M08-004` (post-MVP cross-vehicle allocation).

## Functional requirements

- FR-1 (defaults and settings): Reminders are off by default. The settings screen explains on-device scheduling, the estimate's confidence, and OLM/manual precedence before the user chooses Enable. Default leads after opt-in are 14 days, 7 days, and due day; users can independently toggle allowed leads and choose a local delivery time, default 09:00.
- FR-2 (pure planner): A pure planner accepts forecast revision, semantic `estimated_due_date`, `today`, enabled leads, local delivery time, device IANA timezone, privacy mode, and vehicle ID. It returns desired reminders with stable logical keys `{vehicle_id, forecast_revision, lead_days, purpose}` plus title/body template version and local semantic fire date/time.
- FR-3 (no past reminders, due-now collapse): Do not plan past reminders. If a new/edited forecast is already due, plan at most one `due_now` notification for the next permissible local time and show an immediate in-app banner; never emit a burst for missed lead times. Do not schedule when the interval/last service is missing or mileage is the only dimension and its arrival date is unknown.
- FR-4 (earlier-due semantics): Reminders use the earlier estimated due date. When later readings move that date, the next reconciliation replaces obsolete OS requests. The plan records the target cause/confidence; delivered copy says “estimated” and does not claim the vehicle's live odometer.
- FR-5 (privacy mode): Privacy mode defaults to generic lock-screen text (“Oil change reminder — open Digital Oil Sticker for details”). An explicit setting may include the vehicle nickname and estimated date; never include exact mileage, notes, VIN, oil/filter purchase history, or catalog IDs.
- FR-6 (persistence and ID rules): Keep desired plan, applied-plan revision, native request-ID mapping, permission state as last observed, and last reconciliation result in SQLite. IDs passed to `mob_notify` must be deterministic, bounded for platform constraints, collision-checked, and never derived from private display text.
- FR-7 (in-app truth): The in-app banner/history is local and authoritative for “what the app currently recommends”; it must work even when notifications are denied or OS delivery cannot be proven. Do not assert that an OS notification was delivered unless a platform callback actually establishes that fact.
- FR-8 (plugin pinning and adapter boundary): Pin a `mob_notify` release verified compatible with Mob `0.7.20`, activate it in `mob.exs`, and record native host requirements generated/merged for both targets. `LocalNotifications` emits validated schedule/cancel/permission command envelopes; the root `Mob.Screen` adapter handles them, calls `MobNotify.schedule(mob_socket, ...)` or `MobNotify.cancel(mob_socket, id)`, and sends a correlation-ID result. Domain and Phoenix LiveView modules never call the plugin directly.
- FR-9 (permission flow): Have the root-screen adapter call `Mob.Permissions.request(mob_socket, :notifications)` only after a user taps Enable/Test and sees the benefit/context in LiveView. Model `unknown/not_requested`, `granted`, `denied`, `provisional/limited` if surfaced, and `unavailable`; never request on launch or repeatedly nag after denial. Route the asynchronous permission result back through the broker and ignore a reply for a superseded request revision.
- FR-10 (denial behavior): On denial, preserve preferences as desired-but-not-applied and keep the in-app due state. Offer an explicit “Open notification settings” button only if the pinned Mob/plugin API or a reviewed thin native adapter proves that capability on the target OS; otherwise show accurate platform instructions. Do not invent an undocumented Mob function. Recheck permission on return/resume.
- FR-11 (UTC scheduling and channel): `mob_notify` schedules absolute UTC instants. Convert semantic local date/time under the reconciliation issue (`DOS-M06-006`), then command the root-screen adapter to call `MobNotify.schedule` with stable ID/reviewed content/minimal route data; make command replay and cancellation idempotent. Configure one low-noise Android maintenance channel and do not request exact-alarm access.
- FR-12 (Test action): A rate-limited Test action schedules a clearly labeled test about 10 seconds ahead without changing the real plan. Report the API result without calling it guaranteed delivery.
- FR-13 (tap payload): A tap payload contains only local route/purpose/logical ID. Route to current truth; malformed/stale data opens home safely. Never embed a full record, exact mileage, note, or VIN.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Reminders` (§7) owns: the pure planner (FR-2), desired-plan persistence, plan revisions, stable ID generation, and the `NotificationAdapter` behaviour. Pure planning has no side effects; persistence and command dispatch live in the service layer.
- `LocalNotifications` (the adapter-facing module) emits validated schedule/cancel/permission command envelopes to the `DeviceCommandBroker`; the broker delivers them to the registered root `Mob.Screen` adapter, which alone holds a `Mob.Socket` and calls `MobNotify.schedule/…`, `MobNotify.cancel/…`, and `Mob.Permissions.request(mob_socket, :notifications)`, returning correlation-ID results (FR-8/FR-9).
- Domain and Phoenix LiveView modules never call the plugin directly and never hold a `Mob.Socket`; tests must demonstrate that a Phoenix socket cannot take the plugin path (AC-8).
- Settings LiveView owns the explain-then-enable flow, reusing the `DOS-M06-004` warning component and confidence presentation.

### Data and persistence

- `reminder_rules` (§8): per-vehicle reminder kind, lead value/unit, preferred local time, enabled flag — multi-vehicle-safe from the first migration (rule 9).
- `scheduled_notifications` (§8): stable notification ID primary key, vehicle/cycle/rule IDs, desired and scheduled instants, due-date snapshot, payload version, platform state, last error/reconciliation time.
- Desired plan rows carry the stable logical key `{vehicle_id, forecast_revision, lead_days, purpose}`, title/body template version, and local semantic fire date/time (FR-2); the applied-plan revision, native request-ID mapping, last observed permission state, and last reconciliation result are persisted alongside (FR-6).
- Notification IDs are deterministic functions of the logical key, bounded for platform constraints, collision-checked at generation, and never derived from private display text (FR-6).

### Interfaces and events

- Planner: pure function from (forecast revision, `estimated_due_date`, `today`, enabled leads, delivery time, IANA timezone, privacy mode, vehicle ID) to a desired-reminder set — deterministic and directly testable.
- Consumes `forecast_changed(vehicle_id, revision)` from `DOS-M06-003` to invalidate/replan; replanning identical inputs makes no database changes (AC-2).
- Command envelopes: typed schedule/cancel/permission commands with correlation IDs and redacted acknowledgements per §7; asynchronous permission results route back through the broker and are ignored when their request revision is superseded (FR-9).
- Emits the plan-revision data `DOS-M06-006` reconciliation consumes; actual OS convergence triggers live there.

### Failure and recovery behavior

- Adapter/broker failure or root-screen restart leaves the desired plan intact and the applied revision unadvanced; commands are idempotent and safely retryable (FR-11; detailed convergence in `DOS-M06-006`).
- Permission denial preserves preferences as desired-but-not-applied; the in-app due state continues to work (FR-7/FR-10).
- Malformed or stale tap payloads open home safely (FR-13); routing always resolves against current truth, not archived payload content.
- The Test action is rate-limited and reports the API result honestly, including failure (FR-12).

### Security and privacy

- Default notification content is generic (“Oil change reminder — open Digital Oil Sticker for details”); vehicle nickname and estimated date appear only after an explicit setting; exact mileage, notes, VIN, oil/filter purchase history, and catalog IDs never appear in any notification (FR-5) — AC-4 enforces this.
- No push token, APNs/FCM registration, or notification server exists anywhere in the build; a packet capture proving no push registration is required evidence (AC-7).
- Notification IDs and payloads contain no private display text (FR-6, FR-13); acknowledgements crossing the broker are redacted per §7.
- Permission is requested only from explicit user action with visible context — never on launch, never as a nag loop (FR-9), consistent with §6 step 6.

### Accessibility and performance

- The settings screen meets the app accessibility baseline: labeled toggles for each lead, accessible time picker, focus order, and status announcements for permission changes; the explain-then-enable copy is readable at large text sizes.
- The permission primer and denial states are fully operable with screen readers (`PermissionPrimer` per §7).
- Planning is O(leads) per vehicle and runs synchronously within the mutation path without perceptible UI delay; scheduling commands are dispatched off the render path.

## UX and content states

- Settings states: reminders off (default), explain-then-enable context (on-device scheduling, estimate confidence, OLM/manual precedence — reusing the `DOS-M06-004` reviewed warning), enabled with per-lead toggles (14 days, 7 days, due day) and delivery time (default 09:00), privacy mode (generic default vs. explicit nickname/date opt-in with preview).
- Permission states: `unknown/not_requested`, `granted`, `denied` (with accurate recovery guidance per FR-10), `provisional/limited` if surfaced, `unavailable`.
- Plan visibility: the UI shows the exact next planned local reminder(s), confidence, and how to disable them before asking permission (AC-5).
- Due-now state: immediate in-app banner plus at most one `due_now` notification at the next permissible local time (FR-3).
- Test state: clearly labeled test notification about 10 seconds ahead; result reported without delivery guarantees (FR-12).
- Notification copy: says "estimated", never claims the vehicle's live odometer (FR-4).

## Rollout and rollback

- Ships inside the normal app build. Reminders are off by default (FR-1), so rollout risk is opt-in by construction: users who never enable see no behavior change.
- Rollback: disabling the feature in a subsequent build must first cancel applied OS requests via the idempotent cancellation path; desired-plan rows in SQLite are inert data if the feature is reverted. The pinned `mob_notify` version is recorded so a plugin rollback is a reviewed `mob.exs` change with regenerated host requirements, not an ad-hoc downgrade.

## Risks, decisions, and open questions

- Risk: `mob_notify`/Mob 0.7.20 API drift or platform quirks (pre-1.0 framework); mitigated by pinning a verified release, the fake-adapter contract seam, and physical-device evidence before close.
- Risk: the "Open notification settings" capability may not be provable from the pinned API; FR-10's fallback (accurate platform instructions) is the default until a reviewed thin native adapter proves it — inventing an undocumented Mob function is prohibited.
- Decision (fixed by catalog): notification intent is data first (SQLite desired plan) and crosses the native boundary only through the typed DeviceCommandBroker; no exact alarms; one low-noise Android channel.
- Decision (fixed by catalog): privacy-first content default; opt-in nickname/date only; hard exclusion list for payload fields.
- Open question: which `mob_notify` release is pinned — resolved by the compatibility verification precondition and recorded in the configuration diff.
