> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The threat model changes fundamentally — a public internet-facing server replaces a loopback listener — and must now cover socket/origin abuse, transient personal data in assigns, log and error-report redaction, and a provable absence of personal-data tables._

## Outcome

A reviewed threat model, transient-personal-data lifecycle audit, hosted-transport hardening evidence, log/error-report redaction test, and a **provable absence** of any personal-data table in the deployed release together prove that the public Phoenix LiveView application on Fly.io at `digitaloilsticker.com` holds personal data only in `socket.assigns` for the lifetime of one LiveView connection and never persists, replicates, logs, or exports it — while the client-side IndexedDB store, the hosted transport, and the hosted-application attack surface are all threat-modelled and hardened for a public internet audience. Honest privacy content on the Netlify static privacy page and the in-app privacy screen reflects exactly what the code proves, including the operator-access honesty required by ADR-0004 §"LiveDashboard and operator access — stated honestly".

## Why this matters and what it unblocks

The pre-pivot boundary was a loopback endpoint inside a Mob WebView (retired INV-2). Under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) that boundary is gone and replaced by a **public** boundary: Phoenix LiveView on Fly.io behind `digitaloilsticker.com`, personal data held in anonymous browser storage (IndexedDB), and a strict rule that the server-side deployment contains exactly one Ecto repo — `DigitalOilSticker.CatalogRepo`, opened read-only — and no personal-data tables of any kind. That is a weaker boundary in kind than loopback and therefore must be stronger in detail: the hosted app can be reached by anyone on the internet, the socket can be hijacked from a cross-origin page, `socket.assigns` briefly holds the user's garage, and every log line and every error report is a potential exfiltration path.

This issue is the pre-release gate that turns those risks into evidence: a hosted threat model, an assigns-lifecycle audit, a log/error-report redaction test, and a repo-list assertion that proves the absence of personal tables. It consumes the M09 platform hardening and blocks the closed-beta distribution work (`DOS-M07-006`) and the public web launch (`DOS-M07-007`).

Constitution 2.0.0 anchor invariants: INV-3 (no server-side personal record), INV-4 (no telemetry, no third-party exfiltration — scope adjusted to browser), INV-5 (no implied backup — strengthened by INV-25 for erasable browser storage), INV-22 (hosted transport security — replaces retired INV-2), INV-23 (anonymous client-side storage is the only home for personal data), INV-24 (LiveView hydration protocol and the server-state boundary), INV-25 (honest storage-loss messaging), INV-26 (impersonal catalog-query surface), and INV-27 (Fly/Netlify content boundary).

## Functional requirements

- **FR-1 (retires pre-pivot FR-1).** Produce a hosted-application threat model — data-flow diagram plus STRIDE-style register — covering the scenarios named in AC-1. Each threat records the mitigation, the evidence link, and the residual risk with reviewer disposition. Client-side equivalents in IndexedDB are inventoried with storage-location, validation-boundary, log policy, deletion-path, and eviction-behavior columns.
- **FR-2 (replaces pre-pivot FR-2 — loopback binding is retired).** Enforce hosted transport per ADR-0004: HTTPS with `force_ssl` and plain-HTTP redirect; WSS-only sockets; `Plug.SSL` with `rewrite_on: [:x_forwarded_proto, :x_forwarded_host, :x_forwarded_port]` behind Fly's proxy; HSTS enabled only **after** both `digitaloilsticker.com` and `www.digitaloilsticker.com` serve verified certificates (never earlier); `check_origin` set to an explicit host list (never `true`, never `false`).
- **FR-3.** Enforce CSRF and session-cookie constraints per ADR-0004 §"CSRF and session": Phoenix `protect_from_forgery` on all HTTP routes; LiveView `_csrf_token` passed through socket connect params and verified on connect; session cookie signed, `secure`, `http_only`, `same_site: "Lax"`, short `max_age`; cookie contents restricted to the CSRF token and `live_socket_id` and **never** any vehicle, VIN, odometer, date, note, preference, anonymous user ID, or any value that could correlate visits. Add a static test asserting the session-cookie contents allowlist. Any future stable-identifier proposal requires a new ADR and privacy re-review.
- **FR-4.** Serve the ADR-0004 Content Security Policy on every response, verbatim: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' wss://digitaloilsticker.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`. Plus `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and a `Permissions-Policy` denying geolocation, camera, microphone, and payment. All assets first-party and esbuild-bundled; no CDN, no external fonts, no external script. `'unsafe-inline'` is not used; a per-request nonce plug is the only acceptable path if inline styles become necessary. Header content is assertion-tested per response type.
- **FR-5.** Rate-limit for abuse per ADR-0004 §"Rate limiting and abuse": per-IP token-bucket on socket connects and HTTP requests; per-socket caps on catalog search/filter events (they hit the database) and on hydrate/import events (they are the largest payloads); server-side payload caps as specified in ADR-0004 §"Validation" (payload ≤ 1 MiB decoded, ≤ 200 vehicles, ≤ 5 000 events, ≤ 20 000 readings), **rejected explicitly with an error state offering export — never silently truncated**. Client IP taken from Fly forwarded headers via a trusted-proxy-aware plug, used for rate limiting **in memory only**, and never persisted or logged (see FR-7).
- **FR-6 (new, addresses the "transient personal data in assigns" finding).** Constrain the socket-lifetime rule for `socket.assigns`: personal data may exist there only for the lifetime of one LiveView connection, and **never** be written to disk, database, cache, ETS table, external store, session cookie, or log. A dedicated lifecycle audit walks each personal field from arrival (`local_store:hydrate` and `local_store:ack` handlers) through use to release (`terminate/2`) and confirms no reachable code path violates the rule. `debug_errors: false` in production so assigns never reach an error page.
- **FR-7 (replaces and tightens pre-pivot FR-5, addresses the "log redaction" finding).** Redact logs. Server logs **MAY** contain: timestamp, HTTP method/path/status/duration for non-LiveView routes, LiveView event **name** (not params), error type and stacktrace, release version, machine ID, and coarse aggregate counters. Server logs **MUST NOT** contain: VIN; odometer or mileage values; service dates; note text; custom vehicle names; the specific vehicle a session selected; any hydration, mutation, import, or export payload or fragment thereof; the `tab_id`; or the full client IP address (truncate, salt-hash with a rotating salt, or omit — omit is the default). Enforcement: request-param logging disabled, `filter_parameters` configured, a Logger filter that drops `handle_event` params by default with an explicit allowlist for non-personal events, `debug_errors: false` in production.
- **FR-8 (new, addresses the "error-report redaction" finding).** Third-party error reporting is **prohibited**. `socket.assigns` contains the user's garage; any crash reporter that serializes assigns would exfiltrate exactly the data this architecture exists to keep off servers. The CSP structurally blocks it (`connect-src 'self' wss://digitaloilsticker.com` only); an additional static check enumerates dependencies and asserts none is a crash/error-reporting SDK. Any future error-reporting adoption requires a new ADR plus a proven assigns-scrubbing layer plus a privacy re-review.
- **FR-9 (new, addresses operator-access honesty).** LiveDashboard is **disabled in production** (there is no "behind basic auth" compromise at MVP; process state here means live users' vehicles and mileage). Written operational rule: no routine production console use; `fly ssh console` / remote IEx is for application incident diagnosis, never for inspecting a live user socket. The privacy copy (FR-12) matches this scope precisely: **"we store no personal data on the server"** — not "no operator could ever observe a live session."
- **FR-10 (new, addresses the "provable absence of personal-data tables" finding).** Prove the absence of any personal-data table in the deployed release. Automated test asserts (a) the deployed application's Ecto repo list is exactly `[DigitalOilSticker.CatalogRepo]`; (b) the `CatalogRepo` connection is opened **read-only** (SQLite `mode=ro`; if Postgres is ever adopted, a `SELECT`-only role); (c) no `UserRepo` module is compiled into the release; (d) no personal-data schema (`local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications`, `schema_events` — the pre-pivot table set — or anything semantically equivalent) is present; (e) no migration in the release would create one. This is a release-gating check per ADR-0004 §"Enforcement".
- **FR-11 (new, addresses domain-namespace isolation and hydration idempotence).** Ratify the remaining two ADR-0004 §"Enforcement" checks as release gates: (a) a static check that no module under the domain namespaces (`DigitalOilSticker.Catalog`, `.Garage`, `.Forecast`, resolver, etc.) references `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules — protecting native reuse (ADR-0004 decision §6) mechanically; (b) a test that hydration is **idempotent** — hydrating the same payload twice produces identical assigns and emits no write-back.
- **FR-12 (replaces pre-pivot FR-9).** Publish honest privacy content on the Netlify static privacy page (`legal.digitaloilsticker.com`) and the in-app privacy screen, containing all of: no accounts; personal data lives in the user's browser (IndexedDB) on this device only; clearing site data, private-browsing sessions, storage eviction under pressure, and quota exhaustion **destroy the record** — export is the only recovery (INV-5 + INV-25); catalog query requests reveal ordinary IP/user-agent metadata to the host and are used in memory for rate limiting only (FR-5, FR-7); operator-access honesty per FR-9; the Fly/Netlify content boundary (INV-27); a contact/data-error report route; and a policy revision date. Prohibited language: "backup", "synced", "safe", "we'll remember", "your account", and any phrasing that implies the server holds personal data or that the browser storage is backed up. Copy is reviewed against INV-5 and INV-25.
- **FR-13 (retires pre-pivot FR-7 and FR-8).** OS backup exclusion attributes (iCloud, Android backup/device-transfer) and native permissions inventory (notifications, file-picker/share, location, contacts, Bluetooth, camera, microphone, advertising ID, push token) are **retired for the browser MVP** — there is no OS-managed application container and no native permission surface. The browser-side equivalents this card covers instead are: FR-4's `Permissions-Policy` denying geolocation/camera/microphone/payment; the file-picker surface used only by import (`DOS-M05-007`), which reads a user-chosen file entirely client-side; and the export surface (`DOS-M04-009`), which produces a `Blob` download entirely client-side and does not round-trip through the server. Native re-entry inherits the retired items.

## Technical implementation contract

### Components and ownership boundaries

- **Endpoint and transport hardening** (`DOS-M09-008` implements; this card gates): Phoenix `Endpoint` configuration, `Plug.SSL`, `check_origin`, security-headers plug, CSP plug, session cookie configuration, and the router pipelines. Reviewed against ADR-0004 §"Security and privacy boundary for a hosted application".
- **Socket hardening**: `Phoenix.Socket` `connect/3` verifies the CSRF token on every connect; assigns are populated only after the `local_store:hydrate` event validates the payload against the ADR-0004 §"Validation" schema and caps.
- **Rate limiter**: a token-bucket plug for HTTP and a socket-scoped counter for `handle_event` categories, coordinated with `DOS-M09-005`'s catalog query layer so the per-socket cap and the query-layer cap do not double-account.
- **Log redaction and error handling**: Logger backends configured with `filter_parameters`, `handle_event` param filter, and a formatter that never serializes assigns; `debug_errors: false` in production; error pages generated from a static template with no per-request data.
- **Repo-list and namespace-isolation guards**: compiled into the release-check tooling (`mix release_audit` or equivalent under `DOS-M07-005`'s supply-chain gates), not into the runtime.
- **Client-side attack surface** (`DOS-M09-002` / `DOS-M09-003` implement; this card gates): IndexedDB adapter open/upgrade/read/write/transaction/erase, the `LocalStore` hook, quota/persistence probes, `BroadcastChannel` compare-and-set for multi-tab.
- **Privacy content** owned by this card: the Netlify static privacy page (published under the `legal.` static-content boundary, INV-27) and the in-app privacy screen copy.

### Data and persistence

- **Server-side (Fly.io release image):** exactly one Ecto repo — `DigitalOilSticker.CatalogRepo` — opened read-only. The catalog is a build-time artifact baked into the deploy image per ADR-0004 §"Catalog database on Fly". There is no `UserRepo`, no personal-data schema, no personal-data table, no ETS store keyed by session, no on-disk cache keyed by session, and no external durable store of any kind. Personal data exists only as transient values in `socket.assigns` for the lifetime of one LiveView connection.
- **Client-side (browser):** IndexedDB database `dos_local` per ADR-0004 §"Storage layout" (object stores `meta`, `vehicles`, `events`, `readings`, `reminders`, `prefs`); `localStorage` used only for the non-personal `dos_boot_state` hint. This card inventories what the client stores, how it is validated on hydration, how quota/eviction are surfaced, and how reset erases it — but the client store is owned by `DOS-M04-005` / `DOS-M09-002` / `DOS-M05-007`.
- **Reset (client-side, `DOS-M05-007`):** clears all `dos_local` object stores and the `dos_boot_state` `localStorage` key. There is nothing to reset server-side because there is nothing durable server-side (FR-10). Secret-key rotation invalidates signed session cookies and LiveView socket tokens; clients reconnect and re-hydrate from browser storage; **no user data is lost** by a secret rotation, and this property is verified by test.

### Interfaces and events

- **Hydration and mutation events** (`local_store:hydrate`, `local_store:put`, `local_store:ack`, `local_store:conflict`) are treated as **untrusted client input** and validated exactly per ADR-0004 §"Validation": explicit embedded-schema changeset per `schema_version`, hard caps enforced and rejected (never silently truncated), type/range/referential checks, catalog references resolved at render time and returning legitimate `unsupported` states when a `data_version` moves.
- **Catalog query events** (`DOS-M09-005`) are constrained by INV-26: no query parameter carries personal identifiers. This card verifies the constraint by a static check against the query-layer handler list plus a runtime assertion in the scripted-session test that the outbound query payloads contain no personal fields.
- **Export/import** (`DOS-M04-009` / `DOS-M05-007`): export is produced entirely in the hook (read all stores → wrap envelope → SHA-256 hash → `Blob` download) and does not round-trip through the server; import is read in the hook, hash-checked, then pushed as `local_store:hydrate` (inheriting validation and migration). This card treats both files as untrusted input and regression-tests the import parser for malformed/oversized/hostile content.
- **Deep-link and route parameters** are validated before routing; the router has no route that accepts a personal identifier as a URL segment or query parameter (per INV-26 and ADR-0004 §"CSRF and session" — no stable identifier in cookies or URLs).

### Failure and recovery behavior

- **Rejected origin / failed CSRF / bad session** returns a safe error without leaking configuration; the shell recovers to a known route.
- **Malformed hydrate/import payload** fails validation with an explicit error state and quarantines the invalid records per ADR-0004 §"Validation"; the valid subset still hydrates; raw payload is offered for export so nothing is silently discarded.
- **Payload cap exceeded** yields an explicit error state with export offered; data is never silently truncated (FR-5).
- **Rate limit exceeded** returns a safe backoff response; the UI (owned by `DOS-M09-004`) reflects it honestly.
- **Log-redaction failure** in a smoke run fails the release gate (FR-7). Third-party error reporting is prohibited (FR-8), so there is no "external report failed" path — there are no external reports.
- **Deploys drop every WebSocket** (ADR-0004 §"WebSocket and LiveView considerations"). Clients auto-reconnect, remount, and re-run hydration from browser storage; pending unsaved writes are re-driven after remount. The log-scan test covers the reconnect path.

### Security and privacy

This entire card is the security/privacy contract. Summary of hard constraints, cross-referenced to their FR:

- **Transport:** HTTPS + WSS only; HSTS after cert verification; `check_origin` exact-hostname allowlist (FR-2).
- **Auth surface:** no accounts, no login, no identity provider (ADR-0004 decision §3); session cookie holds no personal data and no stable identifier (FR-3).
- **CSRF:** enforced on HTTP and on socket connect (FR-3).
- **CSP + security headers:** as specified in ADR-0004; no `'unsafe-inline'`; no CDN; no external fonts; first-party only (FR-4).
- **Third parties:** zero — no analytics, no tag manager, no session recording, no A/B service, no third-party error reporting, no embedded widgets. The CSP enforces structurally; a static dependency check verifies (FR-8).
- **Rate limiting and payload caps:** per ADR-0004; rejected explicitly (FR-5).
- **Assigns lifecycle:** socket-lifetime only; never persisted, cached, ETS-copied, error-reported, or logged (FR-6).
- **Logs:** allowlist of fields; prohibited list enforced; scripted-session release gate (FR-7).
- **Operator access:** LiveDashboard disabled in production; no routine console use against live sockets; privacy copy scoped precisely (FR-9).
- **Server persistence:** exactly `[CatalogRepo]`, opened read-only; no personal-data table; automated release gate (FR-10).
- **Domain-namespace isolation and hydration idempotence:** release-gating static/property checks (FR-11).
- **Privacy content:** honest, dated, and scoped precisely (FR-12).
- **Storage-loss honesty:** INV-5 + INV-25 — no interface implies backup; export is the only recovery (FR-12; UX owned by `DOS-M09-004`).
- **Domain and content boundary:** INV-27 — Fly for the app, Netlify for static content only.

### Accessibility and performance

- The in-app privacy screen and any new copy must meet the rescoped `DOS-M07-002` WCAG 2.2 AA bar verified against a named browser + assistive-technology matrix (mobile screen readers plus keyboard-only desktop use).
- Hardening must not measurably regress the rescoped `DOS-M07-003` browser budgets — page load, time-to-hydrated, LiveView round-trip latency, server memory-per-socket, and IndexedDB footprint. CSP, origin checks, CSRF verification, and the rate-limiter plug are constant-cost per request; verify no measurable regression in the deploy spike.

## UX and content states

- **In-app privacy screen:** states the FR-12 content; reachable from a persistent footer link; shows policy revision date and contact/data-error report route.
- **First-run and pre-hydration states** (owned by `DOS-M09-004`; verified here): the shell never renders "You have no vehicles yet" while `local_state == :hydrating`; `:data_missing` is used instead of an empty-state flash for returning users whose browser cleared storage.
- **Storage-loss messaging:** private-browsing, storage-blocked, quota-exhausted, and "your browser cleared this data" states are copy-reviewed against INV-25 and against FR-12's prohibited-language list.
- **Reset flow (`DOS-M05-007`):** destructive confirmation describing what is deleted (all `dos_local` object stores + the `dos_boot_state` hint); success state confirms completion; nothing implies server-side reset.
- **Export/import flow copy (`DOS-M04-009` / `DOS-M05-007`):** states that exported files leave app control at the user's direction and that import is the only recovery path.
- **Rate-limit and payload-cap errors:** surfaced plainly with export offered; never silently truncated.
- **No dark-pattern states:** rate-limit messaging does not gate the product behind persuasion; the app degrades honestly to a read-only catalog view when the socket is unreachable.

## Risks, decisions, and open questions

- **Decision required.** Whether error reporting will ever be added post-MVP. If so, the ADR path in FR-8 (proven assigns-scrubber + privacy re-review) is mandatory.
- **Decision required.** Whether an emergency operator-observation path is ever needed. Default under FR-9 is **no**; a yes requires the operational rule to change with written justification and privacy copy re-review.
- **Risk.** Storage-eviction behavior (R1 in ADR-0004) is the biggest product risk of the pivot; measured per the `DOS-M09-009` browser matrix. The threat register records eviction as an accepted operational reality, mitigated by `navigator.storage.persist()`, honest UI (`DOS-M09-004`), and export nudges.
- **Risk.** The strict CSP (FR-4) is unverified against every LiveView JS runtime behavior; if a nonce plug is required, add it — `'unsafe-inline'` is not acceptable.
- **Risk.** Catalog endpoints are publicly scrapable in a way an app bundle was not (R7 in ADR-0004). Rate limiting (FR-5) is a mitigation, not a solution; any further scrape-mitigation change is out of scope and must not collect personal data.
- **Risk.** Deploy-drop-and-remount can transiently include personal data in the reconnect churn; AC-4 covers the reconnect path.
- **Open question.** Whether `_csrf_token` plus `check_origin` is sufficient defense against a malicious browser extension. Extensions have DOM-level access and can bypass CSP for their own contexts; accepted residual risk in the threat register.
- **Open question.** Whether the `filter_parameters` + Logger-filter allowlist is expressive enough for future `handle_event` categories; revisit if a new category appears.
