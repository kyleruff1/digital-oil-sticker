## Outcome

A reviewed threat model, privacy data inventory, loopback hardening, retention/deletion policy, and store disclosure matrix prove what stays on the device and what can leave only through explicit user action.

## Why this matters and what it unblocks

"No account" does not automatically mean private: WebView content, loopback Phoenix, OS backups, exports, logs, dependencies, catalog downloads, and notification payloads can leak data. Release claims must match code and platform behavior. This issue turns the product's local-first promise from an assertion into verified, evidenced fact, and it produces the data inventory that Apple App Privacy and Google Play Data safety answers (DOS-M07-007) must be derived from. It blocks beta distribution (DOS-M07-006) and the production release (DOS-M07-007): no build may reach external testers before the privacy boundary is locked down.

## Functional requirements

- FR-1: Classify vehicle identity, nickname, service dates, odometers, notes, usage profile, forecasts, notification plans, local diagnostics, and exports. For each, document storage location, encryption-at-rest inherited from the OS, retention, log policy, backup behavior, notification exposure, deletion path, and whether it is "collected" under current store definitions.
- FR-2: Bind Phoenix to loopback only; enforce Host/Origin checks for the expected loopback origin and configured port; retain CSRF protection for forms/LiveView; use secure random session material generated and stored on-device; disable remote debug/distribution in production; block arbitrary WebView navigation, mixed content, file-origin access, and JavaScript interfaces not required by the Mob bridge.
- FR-3: Apply a restrictive Content Security Policy compatible with Phoenix LiveView and local assets, with no remote scripts/styles/fonts/frames.
- FR-4: Escape user notes/nicknames through HEEx, validate deep-link/notification route data, and add explicit regression tests for XSS, path traversal, oversized import, and malformed native messages.
- FR-5: Ensure release builds log no note text, exact odometer, nickname, export contents, notification body, database path, tokens, or native payload. Local structured diagnostics use allowlisted fields, bounded rotation, and redaction.
- FR-6: Keep production secrets/signing material out of source, client assets, and diagnostics.
- FR-7: Decide and implement OS backup behavior explicitly. Default recommendation for a strict "this device only" promise: mark the SQLite database and exports as excluded from iCloud backup and disable Android cloud backup/device-transfer unless product/legal approve different copy. Manual user export remains the portability path. Test actual manifests/attributes, not just configuration.
- FR-8: Request only notifications and file-picker/share capabilities at point of use. No location, contacts, Bluetooth, camera, microphone, advertising ID, or push-token permission/capability is allowed.
- FR-9: Publish privacy content (Netlify privacy page and in-app privacy screen) stating: no account; user records remain on the device; public catalog download requests may reveal ordinary IP/user-agent metadata to the host; exports leave app control at user direction; uninstall/Reset behavior; OS notification exposure; contact route; and policy revision date. Do not say "we collect nothing" without validating store definitions and server logs.
- FR-10: Produce the threat model covering the required scenarios (see AC-1) with documented mitigations and residual risk, and obtain reviewer approval or explicitly accepted, owned residual-risk records.

## Technical implementation contract

### Components and ownership boundaries

- Endpoint/transport hardening: Phoenix Endpoint configuration, router pipelines, and plug-level Host/Origin/CSRF enforcement — owned here, reviewed against the "Production shell security" baseline.
- WebView shell hardening: Mob root WebView navigation policy, mixed-content and file-origin settings, JavaScript interface surface — changes limited to lockdown; the `DeviceCommandBroker`/`MobScreen` boundary from M00/M01 is not redesigned here.
- Data classification and policy artifacts: threat model, inventory, retention/deletion policy, disclosure matrix — documentation deliverables owned by this issue and consumed by DOS-M07-006 and DOS-M07-007.
- Logging/diagnostics: redaction and allowlist rules across domain contexts and the diagnostic export from M06.

### Data and persistence

- No schema changes. The classification inventory enumerates existing `UserRepo` tables and any on-disk artifacts (SQLite files, WAL/journal files, exports, diagnostic files, WebView caches/localStorage) with their backup and deletion behavior.
- Reset must remove every classified user record and pending reminder; verify physical file handling (including SQLite sidecar files) matches the retention policy.
- Backup exclusion attributes (iOS file attributes/manifest, Android backup/device-transfer rules) are applied to the user database and export/diagnostic directories per the FR-7 decision.

### Interfaces and events

- No new domain events. Deep-link/notification route parameters are treated as untrusted input and validated before routing (FR-4).
- The diagnostic export interface gains an allowlist contract: only approved, redacted fields may appear.
- The disclosure matrix is a reviewed artifact interface consumed verbatim by DOS-M07-007's store forms.

### Failure and recovery behavior

- Rejected Host/Origin or CSRF failures return a safe error without leaking configuration; the app shell recovers to a known route.
- Malformed native messages, hostile imported files, and oversized imports are rejected with bounded resource use and without partial writes (regression-tested per FR-4).
- If backup exclusion attributes cannot be applied, startup surfaces a diagnosable (non-user-facing) fault in `schema_events`-style local records rather than silently shipping unprotected files.

### Security and privacy

This entire issue is the security/privacy contract. Summary of hard constraints: loopback-only endpoint with Host/Origin/CSRF enforcement; restrictive CSP with no remote scripts/styles/fonts/frames; HEEx escaping of user text; release-build log redaction (no note text, exact odometer, nickname, export contents, notification body, database path, tokens, native payload); secrets never in source/assets/diagnostics; explicit OS-backup posture, tested via actual manifests/attributes; permission minimalism (notifications and file-picker/share only, at point of use); no third-party SDK that transmits data; truthful privacy copy with revision date and contact.

### Accessibility and performance

- The in-app privacy screen and any new copy must meet the DOS-M07-002 accessibility bar (semantic structure, contrast, large-text reflow).
- Hardening must not measurably regress the DOS-M07-003 budgets (CSP and origin checks are constant-cost; verify no startup regression).

## UX and content states

- In-app privacy screen: states the FR-9 content; reachable offline; shows policy revision date and contact/data-error report route.
- Reset flow: destructive confirmation clearly describing what is deleted (all classified user records and pending reminders); success state confirms completion.
- Export flow copy: states that exported files leave app control at the user's direction.
- Permission prompts: notifications and file-picker/share requested only at point of use with explanatory priming (existing M05/M06 surfaces; verified here, not redesigned).
- No dark-pattern states: denial of notification permission never blocks the product.

## Test plan

### Automated

- CSP/CSRF/XSS regression tests: HEEx escaping of notes/nicknames, CSP header assertions, CSRF rejection, Host/Origin rejection of non-loopback origins.
- Path-traversal, oversized-import, and malformed-native-message regression tests (FR-4).
- Production-configuration assertions: loopback bind, disabled code reload/LiveDashboard/dev routes/remote inspector/Erlang distribution.
- Log-redaction tests: exercise critical flows in a release-configured build and assert prohibited fields never appear in output.
- Dependency inventory generation and diff against an approved allowlist (coordinates with DOS-M07-005 SBOM tooling).

### Manual/device matrix

- `nmap`/port scan and a second LAN device attempting to reach the endpoint on both physical platforms: connection must fail.
- Packet capture during full critical journeys: no unexpected outbound request.
- Remote-navigation attempt from WebView content: privileged bridge operations unreachable; external links open in the system browser only.
- OS backup extraction test on physical iOS (iCloud/local backup manifest) and Android (backup/device-transfer): excluded files absent per the FR-7 decision.
- Lost/unlocked-phone walkthrough: what is visible from notifications, previews, and app screens without further authentication, documented in the threat model.
- Reset then filesystem inspection: no classified user record or pending reminder remains.

## Rollout and rollback

Planning-bootstrap context: this issue ships hardening changes and policy artifacts inside the normal build pipeline, not a user-visible rollout. Hardening lands behind the existing CI gates; if a lockdown change breaks a legitimate flow (e.g., CSP blocking a required local asset), revert the offending config commit — each hardening control is a separately revertible change. Policy artifacts (threat model, disclosure matrix, privacy copy) are versioned documents; corrections are new revisions with dates, never silent edits.

## Dependency rationale

- `DOS-M05-001`, `DOS-M05-006`, `DOS-M05-007`: the app shell, privacy/permission surfaces, and complete MVP flows must exist before their data flows can be classified, hardened, and inspected.
- `DOS-M06-005`, `DOS-M06-006`: notification payloads and export/import are two of the highest-risk egress paths; they must be implemented before their exposure can be tested.
- This issue blocks beta distribution and `DOS-M07-007`: external testers and store submissions may not receive a build whose privacy boundary is unproven, and store disclosure forms are filled from this issue's inventory.

## Risks, decisions, and open questions

- Decision required (FR-7): OS backup posture. Default recommendation is exclusion for a strict "this device only" promise; product/legal may approve different copy. Must be recorded with rationale.
- Risk: store "collected" definitions change; the disclosure matrix records the definition version/date used and DOS-M07-007 rechecks on release day.
- Risk: Mob WebView may not expose every desired lockdown control; any gap becomes a documented residual risk with reviewer sign-off, or an upstream issue.
- Risk: over-aggressive CSP or origin checks could break LiveView reconnection; mitigated by regression tests on critical journeys.
- Open question: whether the loopback port is fixed or dynamic in the Mob shell affects Host/Origin check configuration; resolve against the M00/M01 evidence and record in the threat model.
