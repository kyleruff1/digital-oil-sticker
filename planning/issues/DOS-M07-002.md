> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Native platform accessibility APIs are replaced by WCAG 2.2 AA conformance verified across a named browser and assistive-technology matrix, including keyboard-only desktop use that the mobile bar never covered._

## Outcome

Every critical browser workflow — first-visit onboarding, vehicle selection, oil-change and odometer logging, forecast/due presentation, reminder state, export/import, and honest degradation states (pre-hydration, storage-unavailable, data-missing, offline) — is usable at WCAG 2.2 AA conformance across a named browser and assistive-technology (AT) matrix, is fully operable by keyboard alone on desktop with a visible focus indicator, and remains intelligible in a linear screen-reader transcript from the moment the LiveView hydrates through every subsequent LiveView patch, reconnect, and multi-tab consistency event.

## Why this matters and what it unblocks

The product's core information is time-sensitive maintenance guidance and must remain understandable regardless of vision, motor, or cognitive access needs. Accessibility defects become expensive when repeated across every ticket. Two things the browser-first pivot makes newly load-bearing:

- **New AT surfaces.** ADR-0004 puts the app in a browser, so desktop keyboard-only users and desktop screen readers (NVDA on Windows, JAWS on Windows, VoiceOver on macOS) become production users that a mobile-only shell never had to serve. The mobile bar as written never covered them; this card does.
- **New states that only exist in a browser.** INV-24 (hydration), INV-24.3 (pre-hydration first paint), INV-24.4–24.8 (eviction, quota, private-browsing, multi-tab, cleared storage), INV-25 (honest storage-loss messaging), and INV-7 (honest degradation without connectivity) each produce a UI state that must be perceivable and operable — including its announcement to screen readers when it changes underneath a user.

This card certifies the accessibility release bar for the browser MVP, produces the accessibility acceptance checklist that every future UI issue must attach, and unblocks the QA matrix (`DOS-M07-004`, whose axes now include browser and AT), the closed beta (`DOS-M07-006`, on an unlisted staging hostname), and the public web release (`DOS-M07-007`, custom-domain cutover).

- The named **browser × assistive-technology matrix** below is the certification surface, not a suggestion. It is the minimum required to close this card; adding rows is allowed, removing rows requires a recorded exception.

- **Keyboard-only desktop operability** with a visible focus indicator, sequential focus order matching reading order, no keyboard traps, and skip-links where a landmark chain is long. This is new work for the browser MVP; the mobile bar had no keyboard axis.
- Semantic HTML/HEEx landmarks, headings, labels, fieldsets, lists, buttons, and dialogs; ARIA used only where a native element is unavailable (INV-22 rules out third-party UI libraries that would bring their own).
- Focus management across LiveView patches, dialog open/close, hook-driven state changes, and — new — LiveView **reconnect and re-hydration**: focus must not silently reset when the socket re-establishes.
- **Live-region and announcement policy** covering:
  - hydration completion (transition from `:hydrating` to `:loaded`/`:empty`) — the user must know their data is now on screen or that the store was empty;
  - INV-24.3 first-paint state — the pre-hydration skeleton MUST NOT be announced as "no vehicles yet";
  - INV-25 honest storage-loss messaging — a detected `:data_missing` (had-data-but-store-is-empty) state is announced with the honest message, not as a fresh-install welcome;
  - INV-7 connection state — socket-disconnect and reconnect changes are announced;
  - INV-24.7 multi-tab conflict — a "reloaded from this browser's newer data" notice is announced without stealing focus.
- Contrast ≥ 4.5:1 (normal text), ≥ 3:1 (large text, UI components, graphical objects) enforced against design tokens; verified in light and dark themes and in Windows High Contrast / forced-colors mode.
- **Text scaling in the browser**: the app must remain fully usable at browser zoom up to 200% and at the browser's largest user-configured default text size, and must reflow at 320 CSS px without loss of content or function. Because the browser exposes text scaling and zoom directly via the user agent, the app must not defeat them (`user-scalable=no` is prohibited; fixed viewport pixel widths are prohibited).
- Target sizes: ≥ 24×24 CSS px universally, ≥ 44×44 CSS px where touch is the primary input on mobile viewports, with adequate spacing per WCAG 2.5.8.
- Reduced-motion (`prefers-reduced-motion`), dark mode (`prefers-color-scheme`), and forced-colors (`forced-colors: active`) preferences respected; animations are nonessential and pausable/omittable.
- Text equivalents for progress, confidence, due status, source badges, and unusual samples (INV-11 statuses, INV-21 terminology) — every visual signal has a screen-reader-intelligible label.
- Error and validation presentation: field name, cause, correction; persistent until addressed; not spoken continuously while typing.
- Long-text tolerance: pseudo-locale expansion review on every screen.
- **A reusable accessibility acceptance checklist template** attached to every future UI issue (required artifact under `DOS-M07-005`).
- Representative users with assistive technology in beta where feasible and consented (executed via `DOS-M07-006`; the cohort requirement is defined here).

## Functional requirements

Every FR below is scoped to browser-first work. Findings from the staleness sweep are addressed inline: the old FR-1 native-host clause is retired; the old FR-3 "extent the Mob WebView exposes" caveat is retired and replaced by FR-3 below; the old FR-4 Android-native 48 dp guidance is retired; the old test-plan reliance on Xcode Accessibility Inspector, XCTest, Android Accessibility Scanner, and Espresso is retired and replaced by FR-11's tooling.

- **FR-1:** Use semantic HTML and HEEx landmarks, headings, labels, fieldsets, lists, buttons, dialogs, and live regions in the LiveView. ARIA is used only where a native element does not exist, and never to paper over an incorrect element. Stable `id`/`data-testid` attributes are added to every interactive element and every announcement region so the same hooks support automated axe-core + Playwright inspection and the DOS-M07-004 scripted matrix runs.
- **FR-2:** Meet at least 4.5:1 contrast for normal text and 3:1 for large text, UI components, and meaningful graphical objects. Information never relies on color, position, icon, or animation alone. Provide screen-reader-intelligible equivalents for progress, confidence, due status, source badges (INV-11), and unusual samples. Design tokens are checked by an automated contrast assertion in CI.
- **FR-3:** **Browser text scaling and zoom (retires the pre-pivot Mob-WebView caveat).** The app must remain fully usable at browser zoom up to 200% and at the browser's largest user-configured default text size. Layouts reflow at 320 CSS px without loss of content or function. The viewport meta tag MUST NOT set `user-scalable=no` or a `maximum-scale` below 5. No CSS uses fixed pixel widths on primary containers where an em/rem/percentage/`min()`/`clamp()` would preserve reflow. There is no dependency on a WebView-specific text-scaling API; the browser is the text-scaling API.
- **FR-4:** Interactive targets are ≥ 24×24 CSS px universally and ≥ 44×44 CSS px where touch is the primary input on mobile viewports, with spacing sufficient to satisfy WCAG 2.5.8 (Target Size — Minimum). Native-mobile 48 dp guidance is not restated because there is no native host on the MVP path.
- **FR-5:** Focus order matches visual/reading order; the focus indicator is visible (not defeated by `outline: none` without an equivalent replacement) and satisfies WCAG 2.4.11 Focus Not Obscured (Minimum) and 2.4.13 Focus Appearance where reachable. **LiveView-specific rules:** a LiveView patch MUST NOT unexpectedly reset focus; a modal dialog traps and restores focus; on socket reconnect and re-hydration (INV-24), focus is preserved to the pre-disconnect element where possible and otherwise moved to a documented, announced landmark. Regression tests cover patch-induced and reconnect-induced focus behavior.
- **FR-6:** **Announcement policy for browser-first states.** Announce with `role="status"` (polite) or `role="alert"` (assertive) as appropriate: validation summaries; result counts after search or filter; save success (only after the hook's `local_store:ack`, per ADR-0004 §"Mutation round trip"); forecast changes; destructive-confirmation prompts. Do not announce continuously while typing. Errors name the field, cause, and correction and persist until addressed.
- **FR-7:** **Hydration- and storage-state announcements (new for browser-first).** The transition from `:hydrating` to `:loaded` / `:empty` is announced without stealing focus; the pre-hydration skeleton is NEVER announced as an empty garage (INV-24.3); a detected `:data_missing` state (had-data-but-storage-was-cleared) is announced with the INV-25 honest storage-loss message and is distinguishable in copy and in the accessible name from a genuine first-visit `:empty`; a detected `:storage_unavailable` (private browsing, blocked storage) is announced before the user enters data (INV-24.6); a multi-tab `:conflict` re-hydration announces the outcome (INV-24.7) without hijacking focus.
- **FR-8:** **Connection-state announcements (new for browser-first).** LiveView disconnect and reconnect changes are announced politely; the `phx-disconnected` styling has a text equivalent that a screen reader reads; a socket-down or catalog-query failure surfaces as the connection-problem state (INV-7), never as "no data for this vehicle".
- **FR-9:** Respect `prefers-reduced-motion`, `prefers-color-scheme`, and `forced-colors: active`. Animations are nonessential and pausable/omittable; content and function do not depend on animation. In forced-colors mode, custom colors used for status meaning have text equivalents so information is not lost when the system palette is imposed.
- **FR-10:** **Full keyboard operability (new for browser-first, not covered by the mobile bar).** Every critical journey — onboarding, vehicle selection cascade, service and odometer entry, forecast review, reminder settings, export and import, and every honest-degradation state — is completable using keyboard alone on desktop, with a visible focus indicator throughout and no keyboard trap. Skip-links are provided where a landmark chain exceeds a documented threshold. This is a certified axis of the matrix (two dedicated rows above).
- **FR-11:** **Automated + manual audit tooling for browsers, not devices.** Automated: axe-core run under Playwright (or an equivalent WCAG-aware browser automation) in CI against every rendered LiveView state including `:hydrating`, `:storage_unavailable`, `:data_missing`, and post-reconnect. Contrast-token assertions run in CI. Focus regression tests for LiveView patches and dialogs run in CI. Manual: full critical-journey passes with each AT in the matrix, screen-reader speech logs captured as evidence; NVDA speech-log capture; VoiceOver rotor navigation; JAWS Insert+F7 landmark checks; TalkBack reading-controls swipe traversal.
- **FR-12:** Create the reusable **accessibility acceptance checklist template** and attach it as a required artifact to every future UI issue (process handoff to `DOS-M07-005` review requirements).
- **FR-13:** Include representative users with assistive technology in beta where feasible and consented (executed via `DOS-M07-006` on an unlisted staging hostname; the cohort requirement is defined here). Recruitment MUST cover at least one desktop-screen-reader user and one keyboard-only user, since these axes are new to the browser-first MVP.
- **FR-14:** Track every found issue with severity and owner; close all critical/serious findings before release. The severity taxonomy aligns with `DOS-M07-004`'s S1–S4 scale, so "critical/serious" maps to release-blocking S1–S2.

## Technical implementation contract

### Components and ownership boundaries

- **LiveView HEEx templates, function components, CSS, and JS hooks** (including the `LocalStore` hook that owns the INV-24 hydration and mutation round trip): primary remediation surface; owned by the LiveView UI workstream.
- **AppShell / first-paint layer**: owns the `:hydrating` skeleton, `phx-disconnected` styling, and the announcement targets for FR-7 and FR-8. Announcement live regions live here so they persist across LiveView patches.
- **Design-token layer** (contrast, focus-indicator, forced-colors mappings): owned jointly by design (`DOS-M02-002`) and this card; changes flow through the design system, not per-screen overrides.
- **Test hooks and audit tooling**: axe-core + Playwright harness owned here; the checklist template and the findings register are owned here; the browser × AT matrix is owned here (with test-execution reused by `DOS-M07-004`).
- **No new screens or product behavior**: remediation only. Content wording changes must preserve INV-21 required terminology ("Stored in this browser", "Estimated due date", "Source unavailable", "Exact configuration not verified"; never "saved to your account" / "synced" / "backed up" / "restore").
- **No native host surfaces.** ADR-0004 explicitly removes the Mob WebView shell from the MVP; any accessibility work on native error dialogs, native permission surfaces, or OS-integrated notification interactions is out of scope and parked with the native re-entry set.

### Data and persistence

N/A — no schema or persisted-data changes; this card modifies presentation semantics only. Stable element IDs added for automated inspection are template attributes, not data. No personal data is ever added to `aria-label`, `aria-describedby`, or any accessibility metadata beyond what already appears on screen (INV-3, INV-4).

### Interfaces and events

- **Live regions and announcement targets** (single set, owned by AppShell): a polite `role="status"` region for hydration transitions, save success, result counts, connection state, and multi-tab conflict; an assertive `role="alert"` region reserved for storage-loss (INV-25), quota exhaustion (INV-24.5), private-browsing detection (INV-24.6), and validation summaries requiring user response.
- **Stable, documented `id`/`data-testid` hooks** consumed by the axe-core + Playwright harness (FR-1, FR-11) and reused by `DOS-M07-004`'s browser × engine matrix runs.
- No new domain events; announcements are derived from existing ADR-0004 mount, hydration, mutation-round-trip, reconnect, and multi-tab conflict events, never new arithmetic.

### Failure and recovery behavior

- Every INV-24.3–24.8 and INV-7 state has a specified accessible screen (per Constitution §9 "Honest-degradation coverage" row) and an automated or scripted test.
- A LiveView reconnect or patch MUST NOT strand focus or silently discard an in-progress announcement; regression cases cover patch-induced and reconnect-induced focus behavior (FR-5).
- A `:storage_unavailable` result on hydration MUST be announced before the user is given any input to enter data (INV-24.6); the announcement text matches the INV-25 required framing.
- A `:data_missing` result (previous visit had data; store now empty) MUST be visually and audibly distinguishable from a genuine `:empty` first-visit onboarding (INV-24.4, INV-24.8, INV-25).

### Security and privacy

- Accessibility labels and speech transcripts MUST NOT leak data beyond what is already on screen; no additional personal data is introduced into accessibility metadata (INV-3, INV-4).
- Screen-reader recordings, speech logs, and screenshots captured as audit evidence use fixture data only, consistent with the `DOS-M07-001` (rescoped) redaction rules — never a real person's vehicle data, VIN, odometer, or notes.
- Audit tooling runs against the staging origin over HTTPS + WSS (INV-22); no third-party accessibility overlay, CDN-hosted AT script, or remote accessibility reporter is used at runtime (INV-4, INV-22 CSP).
- The `debug_errors: false` production rule from ADR-0004 §"Secrets" is preserved; assigns MUST NOT reach an error page rendered to an AT user any more than to a sighted one.

### Accessibility and performance

- This card IS the accessibility bar; see Functional requirements.
- Remediations (live regions, larger targets, reflow layouts, focus management) MUST NOT regress the Constitution §9 hydration-completion (p95 ≤ 300 ms), LiveView event round-trip (p95 ≤ 150 ms), or first-visit payload (≤ 250 KiB compressed) budgets — spot-check on remediated screens; this is the seam with `DOS-M07-003` (rescoped browser-budget card).

## UX and content states

- All critical-journey screens and their `:hydrating`, `:loaded`, `:empty`, `:storage_unavailable`, `:data_missing`, `:conflict`, and connection-down/reconnecting states are in scope, including: onboarding; vehicle selection cascade; recommendation/provenance display; sticker/dashboard due states (in-app due/overdue only per INV-17); service and odometer entry; forecast explanation with confidence; reminder settings (in-app only); export/import/reset.
- Forecast cause/confidence, due status, warnings, and validation MUST be intelligible in a linear screen-reader transcript (verbatim release criterion). INV-21 terminology is enforced verbatim: "Estimated due date"; confidence labels; "Source unavailable"; "Exact configuration not verified"; "Stored in this browser".
- **Distinct states, distinct copy, distinct announcements.** `:hydrating` vs `:empty` vs `:data_missing` vs `:storage_unavailable` are four different states with four different accessible names and four different announcements. No two collapse into "you have no vehicles" (INV-24.3, INV-25).
- Light/dark, forced-colors, largest text size, reduced motion, portrait/landscape (mobile), and 320 CSS px reflow width are all supported presentation states, not exceptional ones.
- No critical content truncates at 320 CSS px or largest browser text; horizontal scrolling is limited to genuinely tabular optional detail, never the primary flow.

## Rollout and rollback

Remediations land as ordinary reviewed PRs behind `DOS-M07-005` gates; **the rollout mechanic is a Fly.io deploy per** `DOS-M09-006`, not a store submission. Because a Fly deploy drops every WebSocket (ADR-0004 §"WebSocket and LiveView considerations"), each deploy re-exercises the reconnect + re-hydration path — this is precisely the behavior FR-5 and FR-6 certify, so a deploy IS a regression test of the accessibility contract, not a separate ceremony. Changes are sliced per screen/component to keep reverts small; if a remediation regresses layout, behavior, or a Constitution §9 budget, revert that PR and redeploy the previous immutable release identifier. The signed checklist, axe-core CI history, and AT recordings are versioned; a re-audit is required if a critical screen changes materially after certification.

## Dependency rationale

- The **rescoped M05/M06 LiveView UI cards** must be closed first: the bar certifies real shipped screens; auditing unfinished UI produces throwaway findings.
- `DOS-M05-006` (rescoped as the Fly deploy-and-boot contract) and `DOS-M02-002` (rescoped as the responsive web design system) provide the substrate this card certifies; INV-21 terminology and the ADR-0004 state model are what the transcript checks verify.
- `DOS-M09-006` (Fly deploy) and `DOS-M09-007` (custom domain + TLS) are required so AT auditing happens against the real HTTPS + WSS transport (INV-22); assistive technologies behave differently under insecure or mixed-content conditions.
- This card **blocks** `DOS-M07-004` (the rescoped browser/engine/OS QA matrix reuses the stable IDs, the audit tooling, and the checklist), `DOS-M07-006` (the closed beta on an unlisted staging hostname includes representative AT users), and `DOS-M07-007` (the public web release depends on the audit evidence and the signed checklist).
- This card explicitly does **not** chain to any DEFER-bucket card: it must not become a hidden native-mobile gate. If PWA offline or Web Push is ever adopted through `DOS-M09-010`, a new accessibility card for that surface is filed rather than reopening this one.

## Risks, decisions, and open questions

- **Risk (new for browser-first): the hydration-completion announcement is unproven at scale.** Between a fast connection (hydration in ~150 ms) and a slow one (hydration deferred until near the 5 000 ms deadline), the announcement's timing and phrasing must not confuse users of NVDA / VoiceOver / TalkBack. Measure with each AT; adjust phrasing and `role` (polite vs assertive) per evidence rather than a priori.
- **Risk: LiveView DOM patching fights AT focus.** Unchanged from the pre-pivot analysis and still binding; mitigated with explicit focus management (FR-5) and regression tests. Residual quirks documented with severity.
- **Risk (new for browser-first): cross-browser WSS reconnect timing differs.** Firefox, Safari, Chromium, and iOS Safari behave differently on tab-restore and sleep/wake; the reconnect-and-re-hydration announcement (FR-6, FR-8) must work in all. Document measured behavior per row rather than assuming parity.
- **Risk: automated tools cover only part of WCAG.** The manual matrix is mandatory, not optional. Automated axe-core catches a well-known minority of criteria; keyboard operability, focus management, announcement quality, and screen-reader intelligibility require the manual pass.
- **Risk: multi-tab conflict announcement (INV-24.7) may steal focus.** The "reloaded from this browser's newer data" notice must be announced without hijacking the caret or the focus point; verified per AT.
- **Risk: JAWS is a paid product; automated JAWS-in-CI is not free.** Decision: JAWS is a manual-only row. NVDA covers the Windows-screen-reader automation surface in CI.
- **Risk (retired from pre-pivot): the Mob WebView may not propagate platform text-size settings.** RETIRED — no Mob WebView in the MVP path. Browser text scaling is a first-class user-agent capability and is covered by FR-3 directly. This item is retained here only so a reader who remembers the pre-pivot version knows the risk has been retired, not silently dropped.
- **Decision: severity taxonomy** aligns with `DOS-M07-004` S1–S4 so "critical/serious" maps to release-blocking S1–S2.
- **Open question: forced-colors coverage.** Windows High Contrast (`forced-colors: active`) exposes a small palette and imposes it on every element; some status colors used for confidence and due state will need text equivalents when the palette is imposed. Measure per screen; document trade-offs where a color-only signal cannot survive the mapping.
- **Open question: iOS 16 vs iOS 17+.** iOS Safari behavior on VoiceOver differs materially between versions; the matrix says "iOS Safari 16+" but the audit may reveal that iOS 16 warrants a separate row.

- Findings register shows zero open S1 or S2 accessibility findings.
- Signed accessibility checklist committed for this release; reusable accessibility acceptance checklist template committed and referenced by the `DOS-M07-005` UI review requirement.

- No scope beyond remediation and certification was implemented; new feature ideas discovered during audit are filed separately.
- No dependency on any DEFER-bucket card was introduced during the work.

### Outcome

### Functional requirements

- FR-1: Use semantic HTML/HEEx landmarks, headings, labels, fieldsets, lists, buttons, and live regions in the LiveView WebView. Native host error/permission surfaces expose equivalent accessibility labels, roles, state, and focus. Stable IDs support automated XCUITest/Espresso/Appium inspection.
- FR-2: Meet at least 4.5:1 contrast for normal text and 3:1 for large text and meaningful UI components; information never relies on color, position, icon, vibration, or animation alone. Provide text equivalents for progress, confidence, status, and unusual samples.
- FR-3: Support WebView 200% text zoom and iOS/Android preferred text-size settings to the extent the Mob WebView exposes them; critical content must reflow without clipping/overlap at the platform's largest supported accessibility size. Do not disable pinch zoom. Use responsive vertical layouts instead of shrinking text.
- FR-4: Interactive targets are at least 44×44 CSS points in the WebView and meet platform native guidance (48 dp on Android where native controls are used), with adequate spacing.
- FR-5: Focus order matches visual/reading order, focus is visible, dialogs trap/restore focus, and LiveView patches do not unexpectedly reset it.
- FR-6: Announce validation summaries, result counts, save success, forecast changes, notification status, and destructive confirmations succinctly; do not announce continuously while typing. Errors name the field, cause, and correction and persist until addressed.
- FR-7: Respect reduced-motion and system light/dark/contrast preferences. Animations are nonessential and pausable/omitted. Dates, units, and controls work without relying on swipe-only gestures or haptics.
- FR-8: Create an accessibility acceptance checklist attached to every future UI issue.
- FR-9: Include representative users with assistive technology in beta where feasible and consented (executed via DOS-M07-006; the cohort requirement is defined here).
- FR-10: Track every found issue with severity and owner; close all critical/serious findings before release.
