## Outcome

Every critical workflow is usable with VoiceOver, TalkBack, keyboard/switch-style navigation where supported, large text, high contrast, reduced motion, color-vision differences, and one-handed compact screens.

## Why this matters and what it unblocks

The app's core reminder information is time-sensitive and must remain understandable regardless of vision, motor, or cognitive access needs. Accessibility defects become expensive when repeated across every ticket. This issue certifies the accessibility release bar for v1, produces the accessibility acceptance checklist that every future UI issue must attach, and unblocks the QA matrix (`DOS-M07-004`), beta distribution, and the production release (`DOS-M07-007`), whose store submissions include accessibility declarations.

## Included

- WCAG 2.2 AA mapping for WebView content.
- Platform accessibility conventions for native host surfaces (iOS and Android).
- Screen reader semantics (VoiceOver, TalkBack) across all critical workflows.
- Focus management: order, visibility, dialog trap/restore, LiveView patch behavior.
- Dynamic Type/text scaling and WebView zoom support.
- Contrast verification for text and meaningful UI components.
- Touch-target sizing and spacing.
- Reduced-motion support.
- Error presentation and validation announcement patterns.
- Text alternatives for charts/progress/confidence/status indicators.
- Localization expansion tolerance (long-text behavior).
- Native notification and settings flows exposed with equivalent accessibility.
- An accessibility acceptance checklist attached to every future UI issue.
- Representative users with assistive technology in beta where feasible and consented (handoff to DOS-M07-006).

## Excluded

- Unsupported desktop-only interactions.

## Functional requirements

- FR-1: Use semantic HTML/HEEx landmarks, headings, labels, fieldsets, lists, buttons, and live regions in the LiveView WebView. Native host error/permission surfaces expose equivalent accessibility labels, roles, state, and focus. Stable IDs support automated XCUITest/Espresso/Appium inspection.
- FR-2: Meet at least 4.5:1 contrast for normal text and 3:1 for large text and meaningful UI components; information never relies on color, position, icon, vibration, or animation alone. Provide text equivalents for progress, confidence, status, and unusual samples.
- FR-3: Support WebView 200% text zoom and iOS/Android preferred text-size settings to the extent the Mob WebView exposes them; critical content must reflow without clipping/overlap at the platform's largest supported accessibility size. Do not disable pinch zoom. Use responsive vertical layouts instead of shrinking text.
- FR-4: Interactive targets are at least 44×44 CSS points in the WebView and meet platform native guidance (48 dp on Android where native controls are used), with adequate spacing.
- FR-5: Focus order matches visual/reading order, focus is visible, dialogs trap/restore focus, and LiveView patches do not unexpectedly reset it.
- FR-6: Announce validation summaries, result counts, save success, forecast changes, notification status, and destructive confirmations succinctly; do not announce continuously while typing. Errors name the field, cause, and correction and persist until addressed.
- FR-7: Respect reduced-motion and system light/dark/contrast preferences. Animations are nonessential and pausable/omitted. Dates, units, and controls work without relying on swipe-only gestures or haptics.
- FR-8: Create an accessibility acceptance checklist attached to every future UI issue.
- FR-9: Include representative users with assistive technology in beta where feasible and consented (executed via DOS-M07-006; the cohort requirement is defined here).
- FR-10: Track every found issue with severity and owner; close all critical/serious findings before release.

## Technical implementation contract

### Components and ownership boundaries

- LiveView WebView content (HEEx templates, components, CSS, JS hooks): primary remediation surface; owned by the LiveView UI workstream.
- Native host surfaces (Mob shell error/permission dialogs, notification interactions, any native settings hand-off): must expose equivalent labels/roles/state/focus; changes coordinated with the Mob shell owner.
- Audit tooling and checklist: owned here; the checklist becomes a required artifact on all future UI issues (process handoff to DOS-M07-005 review requirements where applicable).
- No new screens or product behavior: remediation only. Content wording changes must preserve the required terminology contract.

### Data and persistence

N/A — no schema or persisted-data changes; this issue modifies presentation semantics only. Stable element IDs added for automated inspection are template attributes, not data.

### Interfaces and events

- LiveView live regions and announcement patterns for the FR-6 event set (validation summaries, result counts, save success, forecast changes, notification status, destructive confirmations).
- Stable, documented element IDs/test hooks consumed by XCUITest/Espresso/Appium automation (FR-1) and reused by DOS-M07-004's scripted matrix runs.
- No domain event changes; announcements are derived from existing context results/events, never new arithmetic.

### Failure and recovery behavior

- Error and recovery states (offline, empty, permission-denied, corruption-recovery surfaces from M05/M06) are in the audit scope and must be fully perceivable and operable with assistive technology.
- A LiveView reconnect or patch must not strand focus or silently discard an in-progress announcement; regression cases cover patch-induced focus resets (FR-5).

### Security and privacy

- Accessibility labels and transcripts must not leak data beyond what the screen already shows; no additional personal data is introduced into accessibility metadata.
- Screen-reader recordings and screenshots captured as evidence use fixture data only, consistent with the DOS-M07-001 redaction rules (no real person's vehicle data).

### Accessibility and performance

- This issue is the accessibility bar itself; see Functional requirements.
- Remediations (live regions, larger targets, reflow layouts) must not regress DOS-M07-003 interaction budgets; spot-check the p95 interaction latency on remediated screens.

## UX and content states

- All critical-journey screens and their empty/error/loading/recovery states are in scope, including onboarding, vehicle selection cascade, recommendation/provenance display, sticker/dashboard due states, service and odometer entry, forecast explanation with confidence, reminder settings, permission primer/denied fallback, export/import/reset.
- Forecast cause/confidence, due status, warnings, and validation must be intelligible in a linear screen-reader transcript (verbatim release criterion).
- Light/dark/high-contrast appearance, largest text sizes, reduced motion, portrait/landscape, and 320 CSS px width are all supported presentation states, not exceptional ones.
- No critical content truncates at 320 CSS px/large text; horizontal scrolling is limited to genuinely tabular optional detail, never the primary flow.

## Test plan

### Automated

- axe-style automated accessibility checks against the WebView content where compatible, run in CI on every screen/state reachable by the test harness.
- Xcode Accessibility Inspector/XCTest audit runs on iOS.
- Android Accessibility Scanner/Espresso checks on Android.
- Contrast assertions for the design tokens/palette (4.5:1 normal text, 3:1 large text and meaningful components).
- Regression tests for focus behavior across LiveView patches and dialog open/close using the stable IDs from FR-1.

### Manual/device matrix

- Full critical-journey passes with VoiceOver on physical iOS and TalkBack on physical Android, recorded.
- Manual reviews per screen: contrast spot-checks on real devices, reflow at largest accessibility text size, 200% zoom, reduced motion enabled, both orientations, target-size measurement, noncolor information audit.
- 320 CSS px narrow-viewport pass for truncation/horizontal scrolling.
- Long-text pseudo-locale expansion review (coordinates with the DOS-M07-004 locale axis).
- Signed manual checklist completed by the accessibility owner.

## Rollout and rollback

Remediations land as ordinary reviewed PRs behind DOS-M07-005 gates; no user-facing rollout mechanics. If a remediation regresses layout or behavior, revert that PR — changes are sliced per screen/component to keep reverts small. The signed checklist and audit evidence are versioned; a re-audit is required if critical screens change after certification.

## Dependency rationale

- Completed M05/M06 UI: the bar certifies real shipped screens; auditing unfinished UI would produce throwaway findings.
- `DOS-M05-006`: the UI conventions/content-state layer is the substrate being certified; its terminology and state patterns are what the transcript checks verify.

## Risks, decisions, and open questions

- Risk: the Mob WebView may not fully propagate platform text-size settings; FR-3 scopes support "to the extent the Mob WebView exposes them" — measure actual behavior, document gaps, and decide compensating controls (in-app text scaling) via a recorded decision if needed.
- Risk: LiveView DOM patching can fight assistive-technology focus; mitigated with explicit focus management and regression tests; residual quirks documented with severity.
- Risk: automated tools cover only part of WCAG; the manual matrix is mandatory, not optional.
- Decision: exact severity taxonomy for findings aligns with the DOS-M07-004 S1–S4 scale so "critical/serious" maps to release-blocking S2 or higher.
- Open question: keyboard/switch-style navigation depth "where supported" on each platform/WebView combination; record measured support level in the mapping document rather than overclaiming.
