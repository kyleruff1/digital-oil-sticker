## Outcome

The BEAM + Repo + loopback Phoenix + LiveView/WebView architecture remains acceptably lightweight with the full starter catalog and maximum supported local history.

## Why this matters and what it unblocks

Mob's embedded runtime and the 30-year catalog create real package/startup/storage costs. Budgets force measurement and prevent "lightweight" from becoming an untested adjective. Without enforced budgets, the pre-1.0 embedded-BEAM architecture could silently drift into unshippable startup times, store-size problems, or battery complaints that surface only in reviews. This issue blocks `DOS-M07-004` (the matrix runs against budget-verified builds) and `DOS-M07-007` (release evidence includes the performance baseline).

## Context and source of truth

- Master prompt "Research-backed architecture decisions" 4.1: Mob 0.7.20 embeds the BEAM and Phoenix in each app with the endpoint on `http://127.0.0.1:4000` in a native WebView — the runtime whose cost is being budgeted.
- Master prompt "Target implementation architecture": no Oban or perpetual background GenServer for deadlines; mobile operating systems suspend normal processes; recompute synchronously/on a supervised foreground task after a relevant mutation and at app foreground, then let the OS hold local notification requests. This is the architectural basis for the background/idle budget.
- Master prompt "Non-negotiable product rules" 2 (offline-first) and 8 (local notifications only — no push infrastructure that could mask background traffic).
- Master prompt "Frozen scope boundaries": performance validation is part of "Launch hardening, still in v1"; the coverage contract (30 model years, 1997–2026 for the 2026 baseline) sets the full starter catalog scale.
- Master prompt "Database and data-contract baseline": `CatalogRepo`/`UserRepo` structure, indexes, and the FTS caveat (cascading indexed selectors must work without FTS) that the query-plan work must respect.
- Roadmap catalog entry "DOS-M07-003 — Enforce startup, interaction, storage, memory, and battery budgets."
- Upstream: `DOS-M05-001`, `DOS-M05-002`, `DOS-M05-006` (app shell, vehicle selection, UI layer), `DOS-M06-003` (forecast recompute path), and the full-size catalog fixture from M03.

## Included

- Cold and warm start measurement with endpoint-ready and interactive markers.
- Search/transaction latency and scroll responsiveness budgets.

## Functional requirements

- FR-1: Define a low/mid-tier supported Android reference device and the oldest supported iPhone class plus current-device controls. Measure signed release builds with production logging, full starter catalog, 10 years of synthetic monthly readings/service events, and both cold and warm OS states.
- FR-2: Adopt these initial release budgets, changeable only by an approved ADR with measured Mob baseline: cold tap-to-interactive p95 ≤4.0 s and no run >6.0 s; warm p95 ≤1.5 s; local LiveView interaction p95 ≤100 ms; first paged catalog result p95 ≤250 ms and subsequent filter p95 ≤150 ms; database write + forecast recompute p95 ≤150 ms; sustained list interactions avoid user-visible long tasks >100 ms.
- FR-3: Enforce size targets: per-architecture store-delivered compressed app ≤50 MiB before store transformations; total installed app + starter catalog + empty DB ≤150 MiB; starter catalog artifact ≤30 MiB compressed; normal user-data growth ≤1 MiB per 1,000 text-only records. Report actuals even if a target is missed; do not hide the OTP runtime.
- FR-4: Enforce memory targets: steady-state resident memory ≤200 MiB on reference devices and no monotonic growth >10% after 50 repeated navigation/add/edit cycles. A crash/OS kill due to memory is a blocker regardless of average.
- FR-5: Verify background behavior: app backgrounding must suspend rather than run an Elixir polling loop, Android foreground service, or repeated network job. Local OS notifications are the only due-date background mechanism. A 24-hour idle test must show no app-attributed network traffic and no material scheduled wake loop.
- FR-6: Add database indexes justified by query plans; page search/history; debounce inputs; avoid loading full catalog rows into LiveView assigns or sending oversized diffs. Run catalog parsing/import off the rendering path with visible progress/cancel semantics.
- FR-7: Instrument only in local test builds or locally aggregated diagnostics. No production telemetry SDK is introduced. Performance evidence is generated in CI/lab and attached to releases.
- FR-8: Give every budget an automated or repeatable measurement command, a baseline number, an owner, and fail/warn thresholds wired into CI comparison.

## Technical implementation contract

### Components and ownership boundaries

- Measurement harness and evidence pipeline: owned by this issue (QA workstream); produces the repeatable commands and CI comparison jobs consumed by DOS-M07-005 gates.
- Optimization changes: applied in the owning modules (Catalog queries in `DigitalOilSticker.Catalog`, forecast recompute path in `DigitalOilSticker.Forecasting`/`Maintenance`, LiveView assigns/diffs in the UI layer) as reviewed PRs; this issue defines the budget, the owning workstream fixes its own regressions.
- Reference-device policy: recorded alongside the DOS-M07-004 support matrix so both use the same device set.
- Budget-change control: only an approved ADR with a measured Mob baseline may change a budget (FR-2).

### Data and persistence

- Synthetic history fixture: 10 years of monthly readings/service events generated through supported interfaces, deterministic and reusable across runs.
- Query-plan evidence for every index added or relied on (`EXPLAIN QUERY PLAN` on SQLite); no speculative indexes.
- Database growth measured per 1,000 text-only records against the ≤1 MiB target.
- No schema semantics change; any index migration follows the standard `UserRepo`/`CatalogRepo` migration rules and is validated in DOS-M07-005 migration CI.

### Interfaces and events

- Interactive markers: instrument endpoint-ready and tap-to-interactive markers exposed in local test builds only.
- Measurement commands are the interface: documented, repeatable invocations (CI job or scripted device run) per budget, producing comparable numbers.
- No new domain events; catalog import progress/cancel semantics (FR-6) use existing UI state patterns.

### Failure and recovery behavior

- A failed budget in CI produces a fail/warn per its threshold; unexplained regressions block release.
- Memory-pressure OS kill during soak is a blocker regardless of averages (FR-4) and must be reproduced/traced, not averaged away.
- Catalog parsing/import off the rendering path must remain cancelable and leave a consistent state if interrupted (verified with the existing boot/recovery behavior from `DigitalOilSticker.Boot`).

### Security and privacy

- No production telemetry SDK; instrumentation exists only in local test builds or locally aggregated diagnostics (FR-7), consistent with DOS-M07-001.
- Performance traces and evidence contain fixture data only; device identifiers beyond model/OS version are not collected.
- The 24-hour idle network trace doubles as privacy evidence (no app-attributed traffic) and feeds the DOS-M07-001/DOS-M07-007 disclosure crosswalk.

### Accessibility and performance

- This issue is the performance bar. Budgets are measured with production logging on signed release builds — never debug builds.
- Interaction budgets apply equally with accessibility features active; DOS-M07-004 covers combined axes (large text + screen reader) so remediation and budgets are verified together.

## UX and content states

- Catalog parsing/import shows visible progress and supports cancel; the UI never blocks on an unbounded spinner without state (FR-6).
- Search and history views are paged; no state may require loading the entire catalog into a screen.
- No other user-visible UX changes; if an optimization changes perceived behavior (debounce timing, paging), it must preserve the M05 UX contract and be noted in evidence.

## Acceptance criteria

- [ ] AC-1: All budgets have automated or repeatable measurement commands, baseline numbers, owners, and fail/warn thresholds.
- [ ] AC-2: Critical journey meets budgets on both reference devices in airplane mode and after upgrade migration.
- [ ] AC-3: Full-size search uses expected indexes and does not load the entire catalog into a socket/process or WebView DOM.
- [ ] AC-4: Background/idle test finds no polling, foreground service, analytics request, or preventable wake lock.
- [ ] AC-5: Any accepted budget exception has an ADR, user impact, mitigation, owner, and target release; unexplained regressions block release.
- [ ] AC-6: Size and memory actuals (per FR-3/FR-4) are reported against every target, including misses, with the OTP runtime cost visible.

## Test plan

### Automated

- CI performance comparison job: runs the repeatable measurement commands, compares against baselines, and applies fail/warn thresholds per budget.
- SQLite query-plan assertions for catalog search, history paging, and forecast-input queries.
- Package/DB size report generated per build (per-architecture compressed size, installed footprint, catalog artifact size, growth-per-1,000-records).
- Memory soak automation: 50 repeated navigation/add/edit cycles with resident-memory sampling and monotonic-growth check.
- BEAM telemetry captured locally in lab builds for startup phases and recompute latency.

### Manual/device matrix

- Android Macrobenchmark/Perfetto traces and iOS Instruments/signposts runs where applicable, on the defined reference devices, signed release builds, full starter catalog, 10-year synthetic history, cold and warm OS states.
- Airplane-mode critical-journey runs on both reference devices; repeat after an upgrade migration.
- 24-hour idle test on both platforms with battery/idle/network trace: no app-attributed network traffic, no material scheduled wake loop, no foreground service.
- Scroll-responsiveness and long-task observation during sustained list interaction on the low/mid-tier Android reference device.

## Rollout and rollback

Budgets and harness land as CI configuration and lab procedures; no user-facing rollout. Optimization PRs are individually revertible; a revert that re-breaks a budget is caught by the same CI comparison. Budget values themselves are change-controlled: any change requires an approved ADR with a measured Mob baseline — there is no silent re-baselining.

## Dependency rationale

- `DOS-M05-001`, `DOS-M05-002`, `DOS-M05-006`: the shell, catalog selection flow, and UI must exist before startup/search/interaction can be measured meaningfully.
- `DOS-M06-003`: the database write + forecast recompute budget requires the frozen forecast algorithm path.
- Full-size catalog fixture: budgets against a sample catalog would be fiction; the 30-year starter catalog is the load-bearing input.
- This issue blocks `DOS-M07-004` (matrix runs on budget-verified builds and shares the reference-device set) and `DOS-M07-007` (release evidence includes the performance baseline and any exception ADRs).

## Risks, decisions, and open questions

- Risk: the embedded BEAM may make the 4.0 s cold-start or 50 MiB package targets unreachable; the contract requires reporting actuals and an ADR-approved exception with user impact, mitigation, owner, and target release — not hiding the miss.
- Risk: emulator/simulator numbers diverge from device numbers; only reference-device measurements are authoritative for release evidence.
- Decision required: the specific low/mid-tier Android reference device and oldest supported iPhone class — must align with the DOS-M07-004 support matrix and be recorded with rationale.
- Decision path: any budget change goes through an approved ADR with measured Mob baseline.
- Open question: which startup markers the Mob shell can expose for endpoint-ready vs. tap-to-interactive; resolve during harness construction and document the exact marker definitions so numbers stay comparable across releases.

- Evidence pack is attached and consumable by DOS-M07-004 and DOS-M07-007.
- No optimization was made without a trace justifying it; discoveries out of scope are filed as new issues.
