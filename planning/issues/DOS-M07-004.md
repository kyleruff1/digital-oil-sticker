## Outcome

A risk-based matrix proves critical journeys across supported OS versions, form factors, app states, storage states, locales, timezones, and upgrades on simulators/emulators and physical devices.

## Why this matters and what it unblocks

Host ExUnit and one simulator cannot reveal native permission, WebView, killed-app alarm, file picker, lifecycle, or OEM behavior. This is the release evidence gate. Every launch-hardening promise in the v1 scope — offline-first, migration safety, killed-app/reboot reminder delivery, time-zone and DST correctness, corruption recovery — is only credible once demonstrated on real devices under a published support policy. This issue produces the signed release-candidate evidence that `DOS-M07-006` needs to exit beta and that `DOS-M07-007` needs to ship.

## Functional requirements

- FR-1: Declare minimum and current supported iOS/Android versions based on Mob `0.7.20`, OTP/native toolchain, store requirements, and actual device evidence. Recheck these facts immediately before release; do not freeze a stale platform-policy assumption in code.
- FR-2: Define matrix axes to include: fresh/upgrade/restore/reset; Wi-Fi/cellular/airplane/no-DNS; permission not asked/granted/denied/revoked; foreground/background/suspended/killed/rebooted; light/dark/large text/screen reader; EN plus long-text pseudo-locale and at least one non-US date/unit locale; UTC, DST-observing, half-hour-offset, and date-line timezones; low storage/disk full/corrupt fixture; portrait/landscape and compact/large phone.
- FR-3: Define device tiers: Tier 1 must run each release on physical current iPhone, minimum-supported iPhone, current Google-reference Android, and one supported lower/mid-tier Android/OEM. Tier 2 simulator/emulator coverage runs per PR/nightly; additional OEM exploratory coverage runs per release candidate.
- FR-4: Script the critical journeys: first offline boot; vehicle select; interval provenance; service/readings; forecast evolution; permission/reminder/test; killed-app delivery/tap; oil-change cancellation; export-reset-import; upgrade from every supported schema/catalog baseline; storage/migration recovery; privacy reset.
- FR-5: Record per run: build/version, device/OS, catalog/policy/schema version, preconditions, actual result, timestamps, native/BEAM logs, screenshots/video, and defect link. Seed fixtures through supported test hooks, not manual database surgery for user-facing tests.
- FR-6: Apply the severity taxonomy: S1 data loss/security/privacy/unbootable; S2 incorrect due result, duplicate/stale notification, blocked core/accessibility journey; S3 degraded/noncritical; S4 cosmetic. S1/S2 block RC; only product+engineering+QA together may time-box a documented S3 waiver.
- FR-7: Record actual notification behavior for killed app, reboot, timezone travel, and permission revocation on both OSes.
- FR-8: Run a final exploratory session including design, engineering, QA, and a user unfamiliar with implementation.

## Technical implementation contract

### Components and ownership boundaries

- Matrix definition, scripts, dashboard, and defect/waiver register: owned by the QA workstream (this issue).
- Supported test hooks for fixture seeding: implemented in the app codebase by the owning workstreams to QA's specification; user-facing tests never use manual database surgery.
- Support-policy document: co-owned with release management; consumed by DOS-M07-007 and store metadata.
- Automated Tier-2 runs: wired into the DOS-M07-005 CI (per PR/nightly); Tier-1 physical runs are release-gated manual/assisted procedures.

### Data and persistence

- Upgrade fixtures: an installable artifact/data image for every supported schema/catalog baseline, maintained as immutable fixtures (aligned with DOS-M07-005 migration CI).
- Corrupt-database and disk-full fixtures for storage/migration recovery scripts.
- Test-run records, evidence files, and the defect/waiver register are stored with the release candidate, containing fixture data only (no real personal/vehicle data).

### Interfaces and events

- Matrix scripts drive the app through UI automation (XCUITest/Espresso/Appium) using the stable IDs from DOS-M07-002, plus documented supported test hooks for state seeding and clock/timezone control where the platform permits.
- Notification verification observes the OS-level scheduled/delivered state, not just app-internal `scheduled_notifications` rows — both must agree.
- Results feed the dashboard as structured records (FR-5 fields), traceable from matrix cell to evidence.

### Failure and recovery behavior

- The matrix itself tests failure/recovery: storage pressure, corrupt fixture, interrupted migration recovery, killed-app and reboot delivery, permission revocation.
- A failed cell produces a defect with severity per FR-6; flaky/unreproducible results are recorded and investigated, never re-run to green silently.
- If a Tier-1 device cannot complete the run (hardware/OS issue), the gap is documented and the RC does not pass until the cell is executed or explicitly waived per the S3-only waiver rule (S1/S2 scope may never be waived).

### Security and privacy

- Privacy reset, export-reset-import, and permission-revocation scripts double as privacy-boundary verification, consistent with DOS-M07-001.
- Evidence (screenshots/video/logs) uses fixtures; native/BEAM logs attached to runs must already comply with the DOS-M07-001 redaction rules.
- Device-farm usage must not upload user data (fixtures only) and complies with the no-telemetry rule.

### Accessibility and performance

- Accessibility axes (large text, screen reader, light/dark) are integrated matrix dimensions, reusing the DOS-M07-002 checklist; a blocked accessibility journey is S2.
- Matrix runs occur on budget-verified builds; observed performance anomalies during runs are logged as defects against the DOS-M07-003 budgets.

## UX and content states

- The matrix exercises every shipped UX state: first offline boot, no-result/manual fallback in vehicle selection, unknown/unsupported provenance states, permission-denied fallback, due/overdue states, notification deep link, export/import/reset confirmations, storage-pressure and corruption-recovery surfaces, and localization expansion (long-text pseudo-locale, non-US date/unit locale).
- No new UX is created; gaps found in states are defects, not scope to patch ad hoc.

## Test plan

### Automated

- Tier-2 simulator/emulator suite per PR/nightly in CI: scripted critical journeys across the automatable axes (offline modes, permission states where scriptable, locales, timezones, light/dark/large text).
- Migration/upgrade automation from each supported schema/catalog baseline fixture with logical-data and pending-reminder assertions.
- UI automation (XCUITest/Espresso/Appium) using DOS-M07-002 stable IDs.
- Dashboard generation from structured run records with CI links.

### Manual/device matrix

- Tier-1 per release: physical current iPhone, minimum-supported iPhone, current Google-reference Android, one supported lower/mid-tier Android/OEM — full critical-script pass on each.
- Killed-app delivery/tap, reboot delivery, timezone travel (UTC, DST-observing, half-hour-offset, date-line), and permission revocation on both OSes with recorded actual behavior.
- Storage pressure: low storage, disk full, corrupt fixture recovery on physical devices.
- Screen-reader and large-text matrix cells on physical devices.
- Additional OEM exploratory coverage per release candidate; final cross-functional exploratory session (design, engineering, QA, implementation-unfamiliar user).
- Device-farm runs where used, with artifacts attached.

## Rollout and rollback

The matrix is a release gate, not a rollout: it runs against each release candidate. If the RC fails the gate, the candidate is rejected and a new build enters the same matrix; there is no partial pass. The published support policy is versioned; narrowing it after publication is a release-note-visible decision, not a silent edit. Matrix definitions/scripts are version-controlled with the release they validated.

## Risks, decisions, and open questions

- Risk: platform-policy or store-requirement drift between matrix definition and release; FR-1 mandates a recheck immediately before release.
- Risk: OEM-specific alarm/notification throttling on the lower/mid-tier Android device may produce behavior automation cannot reach; mitigated by physical-device recordings and documented actual behavior (FR-7).
- Risk: clock/timezone manipulation is restricted on physical iOS; scripts document the achievable method per platform (settings travel, profile, or simulator supplement) and record what was actually done.
- Decision required: the concrete Tier-1 device models and the supported-version floor — recorded in the published support policy with rationale and evidence.
- Decision recorded: severity taxonomy and waiver rule (FR-6) govern RC gating; only product+engineering+QA jointly may time-box an S3 waiver.
- Open question: device-farm vendor/usage for supplemental coverage; choose under the constraint that fixtures only, no user data, and evidence artifacts must be exportable.
