## Outcome

Pull requests and release tags cannot produce distributable artifacts unless Elixir, LiveView, assets, SQLite migrations, native shells/plugins, dependencies, and secrets pass repeatable quality/security checks.

## Why this matters and what it unblocks

The app spans BEAM, JavaScript/CSS, SQLite, Swift/iOS, Kotlin/Android, and Mob plugins. A code-only green test suite can miss a broken or compromised native bundle. Release trust is a supply-chain property: signed artifacts must be traceable to reviewed source, locked dependencies, immutable released migrations, and protected signing credentials. This issue is the gate through which every beta candidate (`DOS-M07-006`) and the production release (`DOS-M07-007`) must pass.

## Context and source of truth

- Master prompt "Research-backed architecture decisions" 4.1 and 4.3: Mob 0.7.20 is pre-1.0 (hence exact dependency locking and per-update native compatibility review); build and test native applications and catalogs in GitHub Actions; distribute iOS through TestFlight/App Store and Android through internal testing/Play Store.
- Master prompt "Target implementation architecture," "Production shell security": `MIX_ENV=prod` releases; disable code reload, LiveDashboard, development routes, remote inspector, and Erlang distribution in release builds — enforced here as automated build assertions.
- Master prompt "Database and data-contract baseline," "Migration and catalog rules": forward Ecto migrations, fresh-install and every-upgrade-path testing, backup-before-risky-migration — operationalized as migration CI.
- Master prompt "Non-negotiable product rules" 10 (change control) — enforced through branch protection and required reviews.
- Roadmap catalog entry "DOS-M07-005 — Establish CI, supply-chain, migration, and signed-build quality gates."
- Upstream: repository/bootstrap milestones (CI skeleton from M01), `DOS-M05-006`, and the stable migration and test suites from M04–M06.

## Included

- Branch protection and rulesets.
- Formatting/lint/type/security/test PR jobs.
- Dependency lock review and update-PR protocol.
- SBOM generation and archival.
- Secret scanning.
- Migration fixtures and migration CI (including interrupted-recovery attempts and released-migration immutability).
- Native compile and signing separation (unsigned PR artifacts; signed protected-tag artifacts).
- Artifact provenance and checksums.
- Release-tag gates and generated release notes/evidence attached to a GitHub release draft.

## Excluded

- Committing signing keys.
- Automated production rollout without approval.
- Unreviewed hot-push to production devices.

## Preconditions

- Repository/bootstrap milestones complete: repository, base CI, and branch conventions exist.
- `DOS-M05-006` closed: the UI/asset layer whose lint/build jobs are being gated is stable.
- Stable migration and test suites exist (M04–M06): migration CI needs the real migration history and passing suites to gate on.
- Access to protected CI secret storage and macOS build capacity for iOS jobs.

## Functional requirements

- FR-1: Required PR jobs: `mix format --check-formatted`, compile with warnings as errors, ExUnit including property/golden/migration tests, Credo strict or approved equivalent, Dialyzer if adopted, Phoenix/Sobelow-style static review configured for the local Endpoint, asset lint/test/build, dependency vulnerability/license audit, secret scan, export/catalog fixture validation, and Android native build/test. iOS build/test runs on protected macOS capacity at least for merge/release.
- FR-2: Lock exact direct dependency versions appropriate for Mob's early-development status. Dependency update PRs include changelog/security review, Mob/plugin native compatibility, fresh and upgrade builds, both-device smoke tests, and rollback note. No floating git branch dependency is allowed in release.
- FR-3: Generate CycloneDX/SPDX or equivalent SBOM for BEAM, npm assets, Mob plugins, and native Gradle/iOS dependencies. Archive it with package checksums, toolchain versions, Ecto/catalog/forecast versions, licenses, and build provenance.
- FR-4: Migration CI creates each historical fixture, installs the new build/migrations, asserts logical output, and attempts interrupted recovery. A migration already present in a released tag is immutable.
- FR-5: Production signing credentials live in platform/CI protected secret storage with least privilege, rotation/recovery owners, and no PR access. Build unsigned test artifacts on ordinary PRs; sign only reviewed tags in protected environments.
- FR-6: Disable release hot-code push/Erlang distribution and development WebView inspection. A production-build assertion fails if debug endpoints, debug entitlements, cleartext nonloopback allowance, test menu, or remote code loading is enabled.
- FR-7: Protect the default branch; require review from domain/data and native owners for schema, forecast, notification, security, signing, or catalog trust-root changes. Attach generated release notes and evidence to a GitHub release draft.
- FR-8: Verify every gate with deliberate canaries (failing test, vulnerable fixture, secret canary, modified released migration, debug capability, tampered artifact) so gate effectiveness is demonstrated, not assumed.

## Technical implementation contract

### Components and ownership boundaries

- GitHub Actions workflows (PR, merge, nightly, release-tag), branch protection/rulesets, and CODEOWNERS: owned by DevOps/Release (this issue).
- Job content ownership: Elixir jobs gate the domain workstreams' code; asset jobs gate the LiveView UI; native build/test jobs gate the Mob/iOS/Android shell; migration CI gates the M04 persistence layer; fixture validation gates catalog/export artifacts.
- Signing/secret administration: restricted owner set with rotation/recovery documented; PR-level workflows have no signing access by construction.
- Release drafting: automated notes/evidence assembly owned here; approval to ship remains human (DOS-M07-007).

### Data and persistence

- Historical migration fixtures: one per released schema baseline, immutable once their tag ships; new baselines are added, never edited.
- Export/catalog fixture validation data: versioned fixtures validated on every PR.
- SBOMs, checksums, and provenance records archived per build with retention aligned to release history; no user data exists in CI.

### Interfaces and events

- Required status checks are the interface between CI and merge/release: a PR cannot merge and a tag cannot produce a distributable artifact unless all required jobs pass.
- Release-tag pipeline consumes a signed/protected tag and emits: signed IPA archive/AAB, checksums, SBOM, generated release notes, and the evidence bundle attached to a GitHub release draft.
- Dependency-update PRs follow a documented template (changelog/security review, native compatibility, fresh+upgrade builds, both-device smoke, rollback note).

### Failure and recovery behavior

- Any failed required job blocks merge/release with actionable output; flaky jobs are quarantined via an owned process, never by removing the check.
- Interrupted-migration recovery is exercised in CI (FR-4): a migration killed mid-run must leave a recoverable state per the M04 backup/recovery rules.
- Tampered or checksum-mismatched artifacts fail the release job; the pipeline never "fixes" an artifact post-signing.
- Loss of a signing credential follows the documented rotation/recovery runbook with named owners.

### Security and privacy

- Secret scanning on every PR; production secrets/signing material never in source, client assets, or diagnostics (consistent with DOS-M07-001 FR-6).
- Least-privilege, PR-inaccessible signing (FR-5); protected environments for release jobs.
- Sobelow-style static security review configured for the local loopback Endpoint architecture.
- Dependency vulnerability/license audit with release-blocking thresholds; SBOM provides the third-party inventory that DOS-M07-001/DOS-M07-007 disclosures cross-check.
- Production-build assertion (FR-6) enforces the shell-security baseline mechanically.

### Accessibility and performance

- CI hosts the DOS-M07-002 automated accessibility checks and the DOS-M07-003 performance comparison as required or scheduled jobs once those issues land them; this issue provides the gate infrastructure and required-check wiring.
- CI throughput: keep the required PR path fast enough that engineers do not route around it; long-running device jobs run on merge/nightly/release tiers rather than every PR.

## Acceptance criteria

- [ ] AC-1: A deliberately failing test, vulnerable fixture, secret canary, modified released migration, debug capability, and tampered artifact each fail the intended gate.
- [ ] AC-2: Clean CI builds produce traceable unsigned artifacts; protected release job produces signed IPA archive/AAB with matching source tag and checksums.
- [ ] AC-3: SBOM covers all packaged components and has no unresolved release-blocking vulnerability or incompatible license.
- [ ] AC-4: Branch/ruleset and CODEOWNERS enforce required reviews/status checks without administrator bypass as routine practice.
- [ ] AC-5: Build/release runbook can be followed by a second authorized maintainer.
- [ ] AC-6: All FR-1 required PR jobs are enforced as required status checks, and iOS build/test runs on protected macOS capacity at least for merge/release.
- [ ] AC-7: No floating git branch dependency exists in the release lockfiles, and every dependency-update PR carries the FR-2 review items.

## Test plan

### Automated

- The pipeline is itself the automated test surface: PR jobs (format, warnings-as-errors compile, ExUnit with property/golden/migration tests, Credo strict, Dialyzer if adopted, Sobelow-style review, asset lint/test/build, dependency vulnerability/license audit, secret scan, export/catalog fixture validation, Android build/test), merge/release iOS jobs, migration CI with interrupted recovery, SBOM generation, checksum/provenance emission, and production-build assertions.
- Gate-canary suite (FR-8) runs on demand and at release rehearsal to prove each gate still fails what it must fail.

### Manual/device matrix

- Second-maintainer rehearsal: an authorized maintainer other than the author follows the build/release runbook end to end (unsigned PR artifact, protected-tag signed artifact, checksum verification).
- Both-device smoke test for dependency-update PRs per FR-2 (physical iOS and Android).
- Manual verification that PR-level workflows cannot access signing secrets (attempt from a non-protected context fails).
- Review of branch protection/ruleset/CODEOWNERS configuration against the FR-7 required-reviewer matrix.

## Rollout and rollback

Gates are introduced incrementally on the default branch (announce, land as non-required, then flip to required) so in-flight PRs are not stranded; once flipped, removal of a required check requires the same review as a security change. Workflow definitions are version-controlled; a broken gate is fixed or rolled back by reverting its workflow commit — never by disabling branch protection. Administrator bypass is reserved for documented emergencies and is not routine practice (AC-4).

## Dependency rationale

- Repository/bootstrap milestones: the workflows extend the M01 engineering foundation; there is nothing to gate before it exists.
- `DOS-M05-006`: asset/UI jobs need the stabilized asset pipeline to gate meaningfully.
- Stable migration and test suites: migration CI and required ExUnit gates presuppose the M04–M06 suites; gating on churning suites would institutionalize flakiness.
- This issue blocks the beta candidate (`DOS-M07-006` distributes only gate-passing signed builds) and `DOS-M07-007` (release artifacts, SBOM, checksums, and the protected-tag path are produced here).

## Risks, decisions, and open questions

- Risk: Mob's pre-1.0 cadence may force frequent dependency updates; the FR-2 update protocol (native compatibility, both-device smoke, rollback note) contains this without freezing security fixes out.
- Risk: macOS CI capacity cost/availability; mitigated by tiering iOS build/test to merge/release rather than every PR (FR-1 floor).
- Risk: gate fatigue leading to bypass culture; mitigated by fast PR tiers, quarantine process for flaky jobs, and AC-4's no-routine-bypass requirement.
- Decision required: Dialyzer adoption ("if adopted") and the exact Credo-strict-equivalent — record the choice and rationale in the workflow docs.
- Decision required: SBOM format (CycloneDX vs. SPDX or equivalent) and vulnerability/license blocking thresholds.
- Open question: which Sobelow-style checks need tailoring for the loopback-only Endpoint (some hosted-app checks may be inapplicable); configuration is documented with justification per suppressed rule.

- Required checks, branch protection, CODEOWNERS, and protected release environments are live.
- SBOM/checksum/provenance archival works for both platforms; signed artifacts verified against their tag.
- Runbook rehearsed by a second authorized maintainer.
