> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Signed native store builds become signed/attested container images with reproducible provenance and an immutable Fly release identifier._

## Outcome

Pull requests and release tags cannot produce a deployable Fly.io release unless Elixir, LiveView, browser assets, the read-only `CatalogRepo` migration history, dependencies, secrets, and the ADR-0004 §Enforcement release gates all pass repeatable quality/security checks — and the release artifact itself is a **signed and attested container image** whose provenance is reproducible and whose deployment is recorded as an **immutable Fly release identifier**.

Closing this card means all four of the following are true and reviewed together:

1. Every PR is gated by required checks that reflect a hosted Phoenix LiveView application on Fly.io — no Android build/test, no iOS build/test, no macOS runner tier ([ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) §Decision 1, §"Hosting specifics"; PIVOT §"Architectural consequences" point 1).
2. The release artifact is an OCI container image signed and attested by CI (cosign-style keyless attestation, or an equivalent OCI-spec signing scheme), carrying a build-provenance attestation and an SBOM attestation, pushed to a container registry, and deployed to Fly.io by a protected workflow that records the resulting **immutable Fly release identifier** (release digest and machine image digest) in the release ledger (ADR-0004 §"Hosting specifics", §"Secrets"; PIVOT verbatim disposition).
3. The four release-gating checks named in [ADR-0004 §Enforcement](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#enforcement) are wired as required status checks against the packaged release image — the `[CatalogRepo]` repo-list-and-read-only assertion, the domain-namespace static check, the scripted-session log-scan test, and the hydration-idempotence test. Ownership of the checks stays with their implementation cards (`DOS-M09-003`, `DOS-M09-007`, `DOS-M09-008`); wiring them as merge/release gates is the deliverable of *this* card.
4. `CatalogRepo` migration CI, dependency locking, SBOM generation, secret scanning, log-redaction, and gate-canary rehearsal continue to bind — they were architecture-independent quality gates before the pivot and remain so, retargeted to the browser-first substrate.

The pre-pivot deliverables — signed IPA archives, signed AAB bundles, TestFlight/Play upload paths, Android native build/test on every PR, macOS runner capacity for iOS jobs, and the "macOS CI capacity cost/availability" risk — are retired. They are preserved verbatim under `## Superseded pre-pivot spec (historical record)` for the native re-entry set defined in [PIVOT §"Related bookkeeping"](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#related-bookkeeping-this-classification-implies-not-new-milestone-work).

## Why this matters and what it unblocks

The M07 hardening milestone exists to make every release *evidenced*. When the release surface was a store submission, "release trust" meant a signed IPA/AAB tied to reviewed source; under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) the release surface is a container image running on Fly.io in region `ord`, with `min_machines_running = 1`, whose reproducibility, tamper-evidence, and rollback all live at the image and Fly-release layer. If that layer is not gated, three concrete failures follow:

- **Downstream release cards inherit a dead deliverable.** `DOS-M07-006` (rescoped to closed beta on an unlisted Fly hostname or invite link, not TestFlight/Play tracks) and `DOS-M07-007` (rescoped to staged Fly deploys, custom-domain cutover, canary smoke, and rehearsed rollback) both consume "the release artifact this gate produces." As chartered pre-pivot they consume a signed IPA/AAB. If this card is not rewritten, both remain blocked on an artifact that this architecture does not produce.
- **ADR-0004 §Enforcement has no enforcement point.** The four release-gating checks in ADR-0004 §Enforcement (Ecto repo list = `[CatalogRepo]` with a read-only connection; domain-namespace static check; scripted-session log-scan; hydration idempotence) are the mechanical guarantee that INV-3, INV-4, INV-22, INV-23, INV-24, and INV-25 do not silently regress at deploy time. Their *implementation* is owned by the M09 issues, but their *wiring as required status checks against the packaged release image* is a CI/release-gate concern — i.e. this card.
- **The "release trust" property degrades to a promise.** Without image signing, attested SBOM, and an immutable Fly release identifier recorded per deploy, a rollback to "the previous known-good release" becomes ambiguous, a tampered image cannot be distinguished from a legitimate one at deploy time, and the reproducible-catalog claim in ADR-0004 §"Catalog database on Fly" (rollback = redeploy the previous image) has nothing to point at.

This card converts each of those failure modes into an enforced release gate. It is the trust boundary through which `DOS-M07-006` and `DOS-M07-007` must pass.

## Functional requirements

Each FR below either replaces a pre-pivot FR that the rescoping invalidated, retains a pre-pivot FR that survives the pivot with the same intent, or introduces a new obligation created by ADR-0004. Mapping to the sweep finding is called out inline.

- **FR-1 (replaces pre-pivot FR-1; addresses the sweep finding).** Required PR status checks reflect a hosted Phoenix LiveView application on Fly.io. The floor is: `mix format --check-formatted`; compile with warnings-as-errors under `MIX_ENV=prod`; ExUnit including property, golden, and `CatalogRepo` migration tests; Credo strict-or-approved-equivalent; Dialyzer if adopted (recorded as a decision — see Risks); Sobelow configured for the hosted Endpoint (not loopback), with each suppression carrying documented justification; asset lint/test/build; a first-visit payload budget check against Constitution §9 (`≤ 250 KiB` initial HTML+CSS+JS compressed; `≤ 500 KiB` total first-visit transfer; **zero** third-party origins per INV-22); dependency vulnerability/license audit; secret scan; and catalog fixture validation. **There is no Android build/test job, no iOS build/test job, no macOS runner tier, and no protected-macOS release path.** The pre-pivot native tier is retired; its lockfile-native-compatibility clauses are preserved in the historical section for the native re-entry set.
- **FR-2 (retained from pre-pivot FR-2; retargeted).** Direct dependencies are locked exactly across `mix.lock`, the JS asset lockfile, and the container base-image digest (image `sha256:…` pinned, not a floating tag). No floating git branch dependency is allowed in release. Dependency update PRs include changelog/security review, browser/engine impact (which now replaces "native compatibility"), a fresh boot and a hydration round-trip smoke on a supported browser from [`DOS-M07-004`](DOS-M07-004.md), and a rollback note. Dependabot-style automation is acceptable when the reviewer performs those checks by hand and records the outcome in the PR.
- **FR-3 (retained from pre-pivot FR-3; retargeted).** CycloneDX/SPDX-or-equivalent SBOM covers the BEAM release, the JS/asset dependency tree, and the OS/base-image layer of the container. The SBOM is emitted as a **file archived with the build** and as an **OCI attestation attached to the signed image** (see FR-5). Archival includes package checksums, toolchain versions, catalog `data_version`, license inventory, and build provenance metadata (source commit, workflow run URL, builder identity, ISO-8601 build timestamp).
- **FR-4 (retained from pre-pivot FR-4; retargeted to `CatalogRepo` only).** Migration CI creates each historical `CatalogRepo` baseline fixture, installs the new build with the new migrations, asserts the logical output (row counts, known-good sample rows, `data_version` bumps consistent with CHANGE_CONTROL Rule 6), and attempts an interrupted-recovery run — a migration killed mid-run must leave a recoverable state and never a partially applied schema. A `CatalogRepo` migration already present in a released image tag is **immutable**; a PR that edits an already-released migration file fails the gate. No `UserRepo` migration CI exists because no `UserRepo` is deployed (ADR-0004 §Decision 4; INV-23).
- **FR-5 (replaces pre-pivot FR-5; addresses the sweep finding).** The release artifact is a **signed and attested OCI container image**, produced only by a protected release workflow triggered by a reviewed protected tag. Signing uses cosign or an equivalent OCI signing scheme, with keyless OIDC-based signing preferred (the workflow's OIDC identity signs; the transparency log entry is the public audit trail) and a key-based fallback if the CI or registry does not support keyless. The image carries two OCI attestations: (a) a **build-provenance attestation** covering source commit, workflow run URL, builder identity, and build timestamp, and (b) an **SBOM attestation** carrying the FR-3 inventory. Before Fly deploy, the deploy step **verifies both the signature and the two attestations** against the release workflow's OIDC identity; verification failure aborts the deploy and rings an alert. Fly deploy tokens live in GitHub Actions protected environment secret storage, are **deploy-scoped** (never org-admin), are not readable by PR workflows, and follow the rotation runbook in the Documentation section. PR builds produce **unsigned** images tagged `pr-<sha>` for local pull and preview use only; they are never deployed and are not attested. The pre-pivot IPA/AAB signing lane is retired; the "no PR access to signing" invariant survives, retargeted to the release workflow's OIDC identity and to the cosign key or Fulcio-issued certificate.
- **FR-6 (retained from pre-pivot FR-6; retargeted to the hosted shell).** A production-build assertion fails if any of the following is enabled in the packaged release image: `code_reloader`, LiveDashboard, `debug_errors`, development routes, Phoenix live-reload, Erlang distribution (`RELEASE_DISTRIBUTION=none` enforced), a remote inspector, an unrestricted `check_origin`, `force_ssl` off, HSTS-off after certificate verification, or a `Permissions-Policy` that grants geolocation/camera/microphone/payment. The CSP is asserted against the ADR-0004 §CSP text exactly; `'unsafe-inline'` is a build-time failure unless a nonce plug is verified in place. LiveDashboard, remote IEx, and remote observer are asserted off; `fly ssh console` availability is a runtime operator concern, not a build-time one.
- **FR-7 (retained from pre-pivot FR-7; retargeted).** Branch protection and rulesets protect `main`; required reviews by CODEOWNERS cover schema (`CatalogRepo` and IndexedDB `dos_local` layout), security (transport, CSP, session, headers, threat model), signing (release workflow, cosign key handling, Fly deploy secret), catalog trust-root and licensing, hosting configuration (`fly.toml`, region, machine size, `min_machines_running`, secrets), and hydration protocol (server-side envelope validation, mutation round trip). Generated release notes and the evidence bundle (SBOM, provenance, signature verification transcript, immutable Fly release identifier) are attached to a GitHub release draft.
- **FR-8 (new; addresses the sweep-finding sub-action "release-gating checks that mirror ADR-0004 §Enforcement").** The four release-gating checks named in [ADR-0004 §Enforcement](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#enforcement) are wired as **required status checks against the packaged release image**, not just against the source tree:
  - (a) A test asserting the deployed application's Ecto repo list is exactly `[DigitalOilSticker.CatalogRepo]` and that its connection is opened read-only (implementation owned by [`DOS-M09-007`](DOS-M09-007.md) FR-13/AC-9; this card wires it).
  - (b) A static check that no module under the domain namespaces references `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules (implementation owned by [`DOS-M09-003`](DOS-M09-003.md); this card wires it).
  - (c) A scripted-session log-scan test that drives a full hydrate → several mutations → export → clear → import session with log capture and asserts no VIN, odometer value, service date, note text, or custom vehicle name appears in any captured log line (implementation owned by `DOS-M09-007` FR-11 and cross-checked by [`DOS-M09-008`](DOS-M09-008.md) FR-17; this card wires it).
  - (d) A hydration-idempotence test asserting that hydrating the same payload twice produces identical assigns and emits no write-back (implementation owned by `DOS-M09-003`; this card wires it).
  If any of the four does not pass on the release image, the deploy job aborts and the immutable Fly release identifier is not recorded.
- **FR-9 (new; addresses the "immutable Fly release identifier" sub-action).** Every deploy — canary and production — records an entry in the release ledger consisting of: the source commit SHA, the container image digest, the signature and attestation verification transcript (with cosign command output and transparency-log entry reference where keyless), the **immutable Fly release identifier** returned by the deploy (release digest and machine image digest), the target application name and region, the deployer identity (workflow OIDC subject), and the ISO-8601 timestamp. Rollback is a redeploy of a **previously recorded** Fly release identifier, not "the previous image somewhere in the registry" — ambiguity here is a P1 defect against this card. The release ledger's canonical location is defined in the runbook and is version-controlled.
- **FR-10 (new; hosts the M07-002/M07-003/M07-004 CI infrastructure).** CI hosts the required infrastructure for the other rescoped M07 cards: the WCAG 2.2 AA automated axe-core checks from [`DOS-M07-002`](DOS-M07-002.md); the page-load, time-to-hydrated, LiveView-round-trip, server-memory-per-socket, and IndexedDB-footprint budget checks from [`DOS-M07-003`](DOS-M07-003.md); and the browser/engine/OS conformance suite (hydration, schema migration, quota exhaustion, ITP-style eviction, private-mode refusal, multi-tab, reconnect, export/import round trip) from [`DOS-M07-004`](DOS-M07-004.md) and [`DOS-M09-008`](DOS-M09-008.md). Each is required or scheduled per those cards' cadence; this card owns the wiring, the required-check flip, and the flake-quarantine process.
- **FR-11 (retained from pre-pivot FR-8; expanded).** A gate-canary suite proves every gate still fails what it must fail, run on demand and at release rehearsal: (1) a deliberately failing ExUnit test, (2) a fixture with a known vulnerable dependency, (3) a plausible-looking secret canary in a PR, (4) a modified released `CatalogRepo` migration, (5) a build with `code_reloader: true` in prod (FR-6), (6) an image whose signature does not verify (tampered manifest or wrong signer OIDC subject), (7) an image with a missing or wrong SBOM attestation (FR-5), (8) a canary log line containing a fake VIN (FR-8c), (9) a domain-namespace module that imports `Phoenix.LiveView` (FR-8b), and (10) a `Repo` list containing a stub `UserRepo` (FR-8a). Each canary must trip the intended gate and nothing else; a canary that fails to trip its gate is a P1 defect against this card.

## Technical implementation contract

### Components and ownership boundaries

- GitHub Actions workflows (PR, merge, nightly, release-tag, deploy), branch protection/rulesets, and CODEOWNERS: owned by DevOps/Release (this card).
- Container image Dockerfile, base-image digest pinning, and the release-tag build/sign/push workflow: owned by this card; the runtime `fly.toml`, region, machine size, `min_machines_running`, and the deploy step itself are owned by [`DOS-M09-006`](DOS-M09-006.md) and consumed here.
- The four ADR-0004 §Enforcement checks: **implementation** owned by `DOS-M09-003` (b, d) and `DOS-M09-007` (a, c); **wiring as required status checks against the packaged release image** owned by this card.
- The M07-002/M07-003/M07-004 CI infrastructure: rules owned by those cards; wiring owned by this card.
- Signing keys / OIDC signer identity / cosign public key or Fulcio identity: least-privilege owner set with documented rotation and recovery, no PR-workflow access by construction.
- Release ledger: file lives in the repository, format defined in the runbook, canonical write path is the release workflow.

### Data and persistence

- Historical `CatalogRepo` migration fixtures: one per released schema baseline, immutable once their image tag ships; new baselines are added, never edited.
- Catalog fixture validation data: versioned catalog fixtures validated on every PR against the resolver contract.
- SBOMs, checksums, provenance attestations, signature verification transcripts, and release-ledger entries are archived per build with retention aligned to release history.
- **There is no user data in CI, ever.** No IndexedDB export, no browser-storage snapshot, no session capture is ever attached to a workflow artifact. This is not a "we try not to" — it is a release gate (see the FR-8c log-scan test and the FR-11 canary).

### Interfaces and events

- Required status checks are the interface between CI and merge/release: a PR cannot merge and a protected tag cannot deploy unless all required jobs pass and, at the release-tag layer, unless the FR-8 four-check quartet passes against the packaged image.
- Release-tag pipeline emits, atomically per tag: a signed OCI image with build-provenance and SBOM attestations, the image digest, the release-ledger entry, generated release notes, and the evidence bundle — all attached to a GitHub release draft.
- Deploy pipeline consumes a signed image digest plus a deploy-scoped Fly token from the protected environment, verifies signature and both attestations, calls the Fly deploy, receives the Fly release identifier, and appends it to the release ledger. A verification or deploy failure aborts before recording the identifier.
- Dependency-update PRs follow a documented template (FR-2 review items: changelog/security, browser/engine impact, fresh boot + hydration smoke, rollback note).

### Failure and recovery behavior

- Any failed required job blocks merge/release with actionable output naming the failing gate precisely. Flaky jobs are quarantined via an owned process (opened issue, owner, deadline), never by removing the check.
- Interrupted `CatalogRepo` migration recovery is exercised in CI (FR-4); a migration killed mid-run must leave a recoverable state.
- Signature or attestation verification failure at deploy time aborts the deploy; the release ledger is not appended, an alert fires, and the runbook's tampered-artifact incident procedure runs.
- Loss of a signing identity or Fly deploy token follows the rotation/recovery runbook with named owners; rotation invalidates old release-signing credentials but does not invalidate already-signed images already recorded in the release ledger.
- Rollback is a redeploy of a previously recorded Fly release identifier (FR-9). There is no "roll back to whatever was there yesterday"; ambiguity is a defect.

### Security and privacy

- Secret scanning on every PR; production secrets never in source, in client assets, or in error diagnostics (`debug_errors: false` in prod, `filter_parameters` configured, LiveView `handle_event` params logging disabled with an explicit non-personal allowlist per ADR-0004 §Logging).
- Least-privilege, PR-inaccessible signing (FR-5); protected environments for release and deploy jobs; the Fly token is deploy-scoped, not org-admin.
- Sobelow configured for the hosted Endpoint; every suppressed rule is justified in the workflow docs.
- Dependency vulnerability/license audit with release-blocking thresholds; SBOM provides the third-party inventory that [`DOS-M07-001`](DOS-M07-001.md) (threat model), [`DOS-M07-007`](DOS-M07-007.md) (release), and privacy disclosures cross-check.
- Production-build assertion (FR-6) enforces the hosted-shell security baseline mechanically.
- The FR-8c scripted-session log-scan test is treated as a **security** gate, not a "nice to have" — a log line containing a VIN or odometer value is an INV-4 breach at the source.

### Accessibility and performance

- CI hosts the [`DOS-M07-002`](DOS-M07-002.md) WCAG 2.2 AA automated checks and the [`DOS-M07-003`](DOS-M07-003.md) browser-first budget checks (page load, time-to-hydrated, LiveView round-trip, server memory-per-socket, IndexedDB footprint) as required or scheduled jobs. This card is the gate infrastructure; the rules and thresholds belong to those cards and the Constitution §9 table.
- CI throughput: the required PR path is kept fast enough that engineers do not route around it; long-running browser-conformance and multi-engine runs from [`DOS-M07-004`](DOS-M07-004.md) run on merge/nightly/release tiers rather than every PR.

## UX and content states

N/A — infrastructure issue with no user-facing UI. Developer-facing outputs (job logs, release drafts, gate failure messages, signature verification transcripts, release-ledger entries) must be actionable and name the failing gate precisely.

## Acceptance criteria

## Rollout and rollback

Gates are introduced incrementally on the default branch: announced, landed as non-required for a rehearsal window, then flipped to required. In-flight PRs are not stranded. Once flipped, removal of a required check is treated as a security change and follows the FR-7 review path. Workflow definitions are version-controlled; a broken gate is fixed or rolled back by reverting its workflow commit — never by disabling branch protection.

Production rollback follows the ADR-0004 §"Catalog database on Fly" rule: redeploy a previously recorded Fly release identifier. Because the catalog is baked into the image, "roll the catalog back" and "roll the app back" are the same operation. Administrator bypass on the CI side is reserved for documented emergencies (AC-4).

## Risks, decisions, and open questions

- **Risk:** Container base image and Elixir/Phoenix cadence may force frequent dependency updates; the FR-2 update protocol (browser/engine impact, fresh boot + hydration smoke, rollback note) contains this without freezing security fixes out. Base-image digest pinning is deliberate — floating tags would silently invalidate reproducibility.
- **Risk:** A cosign/OIDC signing outage (registry unavailable, Fulcio/transparency log outage in keyless mode, expired keypair in keyed mode) blocks legitimate releases. Mitigation: the runbook documents a keyed fallback for the keyless path (and vice versa), and the rotation runbook is rehearsed as part of AC-5. This is a *live-issue* risk to catch, not a "we'll figure it out later."
- **Risk:** Registry availability affects deploy; Fly must be able to pull the signed image. Mitigation: the deploy step retries with backoff, and the runbook covers the incident path where the registry is unreachable.
- **Risk:** Gate fatigue leading to bypass culture; mitigated by fast PR tiers, an owned flake-quarantine process, and AC-4's no-routine-bypass requirement.
- **Retired risk (was pre-pivot R2):** "macOS CI capacity cost/availability." Removed — the browser-first MVP has no iOS build/test lane, no macOS runner tier, and no store-submission path. This is not a mitigation; the risk itself is gone with the workload.
- **Decision required:** Dialyzer adoption ("if adopted") and the exact Credo-strict-equivalent — record in the workflow docs.
- **Decision required:** SBOM format (CycloneDX vs. SPDX or equivalent) and vulnerability/license blocking thresholds, and whether the SBOM attestation uses the in-toto SPDX predicate or the CycloneDX predicate. The choice is recorded in the runbook; whichever is chosen is applied consistently to both the file archive and the OCI attestation.
- **Decision required:** Signer identity model — keyless OIDC signing (preferred; the workflow's OIDC subject signs, transparency log is the public audit trail) versus a keyed cosign keypair stored in the protected environment. The runbook picks one and documents the fallback for the other.
- **Open question:** Whether to publish the signed image publicly (e.g. as a public GHCR package). The default is **private** until the [ADR-0004 §"ADR-0003 → Unchanged"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#adr-0003--unchanged) web-serving licensing review clears the catalog contents for that broader distribution mode; public visibility is a distribution decision, not a CI decision.
- **Open question:** Whether Sobelow's hosted-app rule set needs further tailoring beyond the retired loopback-only suppressions from the pre-pivot spec; each suppression carries documented justification.

### Outcome (pre-pivot)

Pull requests and release tags cannot produce distributable artifacts unless Elixir, LiveView, assets, SQLite migrations, native shells/plugins, dependencies, and secrets pass repeatable quality/security checks.

### Why this matters and what it unblocks (pre-pivot)

The app spans BEAM, JavaScript/CSS, SQLite, Swift/iOS, Kotlin/Android, and Mob plugins. A code-only green test suite can miss a broken or compromised native bundle. Release trust is a supply-chain property: signed artifacts must be traceable to reviewed source, locked dependencies, immutable released migrations, and protected signing credentials. This issue is the gate through which every beta candidate (`DOS-M07-006`) and the production release (`DOS-M07-007`) must pass.

### Context and source of truth (pre-pivot)

- Master prompt "Research-backed architecture decisions" 4.1 and 4.3: Mob 0.7.20 is pre-1.0 (hence exact dependency locking and per-update native compatibility review); build and test native applications and catalogs in GitHub Actions; distribute iOS through TestFlight/App Store and Android through internal testing/Play Store.
- Master prompt "Target implementation architecture," "Production shell security": `MIX_ENV=prod` releases; disable code reload, LiveDashboard, development routes, remote inspector, and Erlang distribution in release builds — enforced here as automated build assertions.
- Master prompt "Database and data-contract baseline," "Migration and catalog rules": forward Ecto migrations, fresh-install and every-upgrade-path testing, backup-before-risky-migration — operationalized as migration CI.
- Master prompt "Non-negotiable product rules" 10 (change control) — enforced through branch protection and required reviews.
- Roadmap catalog entry "DOS-M07-005 — Establish CI, supply-chain, migration, and signed-build quality gates."
- Upstream: repository/bootstrap milestones (CI skeleton from M01), `DOS-M05-006`, and the stable migration and test suites from M04–M06.

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

- GitHub Actions workflows (PR, merge, nightly, release-tag), branch protection/rulesets, and CODEOWNERS: owned by DevOps/Release (this issue).
- Job content ownership: Elixir jobs gate the domain workstreams' code; asset jobs gate the LiveView UI; native build/test jobs gate the Mob/iOS/Android shell; migration CI gates the M04 persistence layer; fixture validation gates catalog/export artifacts.
- Signing/secret administration: restricted owner set with rotation/recovery documented; PR-level workflows have no signing access by construction.
- Release drafting: automated notes/evidence assembly owned here; approval to ship remains human (DOS-M07-007).

#### Data and persistence

- Historical migration fixtures: one per released schema baseline, immutable once their tag ships; new baselines are added, never edited.
- Export/catalog fixture validation data: versioned fixtures validated on every PR.
- SBOMs, checksums, and provenance records archived per build with retention aligned to release history; no user data exists in CI.

#### Interfaces and events

- Required status checks are the interface between CI and merge/release: a PR cannot merge and a tag cannot produce a distributable artifact unless all required jobs pass.
- Release-tag pipeline consumes a signed/protected tag and emits: signed IPA archive/AAB, checksums, SBOM, generated release notes, and the evidence bundle attached to a GitHub release draft.
- Dependency-update PRs follow a documented template (changelog/security review, native compatibility, fresh+upgrade builds, both-device smoke, rollback note).

#### Failure and recovery behavior

- Any failed required job blocks merge/release with actionable output; flaky jobs are quarantined via an owned process, never by removing the check.
- Interrupted-migration recovery is exercised in CI (FR-4): a migration killed mid-run must leave a recoverable state per the M04 backup/recovery rules.
- Tampered or checksum-mismatched artifacts fail the release job; the pipeline never "fixes" an artifact post-signing.
- Loss of a signing credential follows the documented rotation/recovery runbook with named owners.

#### Security and privacy

- Secret scanning on every PR; production secrets/signing material never in source, client assets, or diagnostics (consistent with DOS-M07-001 FR-6).
- Least-privilege, PR-inaccessible signing (FR-5); protected environments for release jobs.
- Sobelow-style static security review configured for the local loopback Endpoint architecture.
- Dependency vulnerability/license audit with release-blocking thresholds; SBOM provides the third-party inventory that DOS-M07-001/DOS-M07-007 disclosures cross-check.
- Production-build assertion (FR-6) enforces the shell-security baseline mechanically.

#### Accessibility and performance

- CI hosts the DOS-M07-002 automated accessibility checks and the DOS-M07-003 performance comparison as required or scheduled jobs once those issues land them; this issue provides the gate infrastructure and required-check wiring.
- CI throughput: keep the required PR path fast enough that engineers do not route around it; long-running device jobs run on merge/nightly/release tiers rather than every PR.
