## Outcome

Approved signed builds, static Netlify support/privacy content, store metadata/disclosures, release notes, staged-rollout controls, and a rehearsed forward-fix/rollback plan deliver version 1 safely.

## Why this matters and what it unblocks

Store release is an operational change with irreversible migration and policy implications, not merely an uploaded binary. Once users install v1, its schema migrations, notification identifiers, and privacy declarations become a permanent compatibility baseline: every M08 migration starts from what ships here. This issue converts all prior M07 evidence into an approved, staged, recoverable production release and closes the v1 launch gate.

## Technical implementation contract

### Components and ownership boundaries

- Release management (this issue, DevOps/Release workstream): store records, submissions, rollout controls, release manifest, runbooks, approval assembly.
- Netlify static site: built and deployed from versioned source with immutable deploys; contains no app runtime, no user records, no tracking — content co-owned with product/documentation; privacy/accessibility pages sourced from DOS-M07-001/DOS-M07-002 artifacts.
- Signed artifacts, checksums, SBOM: produced by the DOS-M07-005 protected pipeline; this issue consumes and verifies, never rebuilds outside the pipeline.
- Approval authority: product, engineering, QA, privacy/security, and operations owners named in the release approval; no single-owner ship decision.

### Data and persistence

- No app schema changes. The release manifest freezes the shipped database/catalog/forecast versions and migration list as the M08 compatibility baseline (FR-6).
- Migration policy at release: additive/forward-compatible migrations only in emergency patches; never downgrade a migrated SQLite database with an older binary unless compatibility is proven (FR-7).
- Release evidence archive excludes private beta data (FR-6) and contains no user records.

### Interfaces and events

- Store interfaces: App Store Connect and Google Play Console records, submissions, phased-release/staged-rollout controls, and platform-provided crash/vitals summaries.
- Netlify interface: versioned deploys with instant rollback to a prior immutable deploy; status/release-notes page as the public communication channel.
- Internal interface: the release manifest/tag is the single traceability record linking source SHA, artifacts, checksums, SBOM, toolchain, versions, migrations, known issues, support owner, and exact store build.

### Failure and recovery behavior

- Store rejection: resolve and document every rejection; resubmission follows the same gates (AC-1).
- Bad release detected in rollout: halt expansion (or remove availability), assess with monitoring thresholds, then forward-fix through the tested emergency patch branch; user recovery/export guidance is issued for critical data risk (FR-7).
- Netlify content fault: restore via prior immutable deploy — independent of app rollback.
- Smoke-test failure at any stage blocks expansion; approvals are per-stage and manual (FR-5).
- All recovery paths are rehearsed before release day (AC-4), with owners and exact commands recorded.

### Security and privacy

- Disclosures (Apple App Privacy, Google Play Data safety, permissions, content ratings) must match package inspection and observed traffic exactly — sourced from the DOS-M07-001 crosswalk and re-verified on the final build.
- Netlify site: HTTPS, security headers, no tracking cookies/scripts; DNS/domain ownership verified and access-controlled.
- Signing and store credentials remain in the DOS-M07-005 protected storage; release-day operations use least-privilege roles.
- Postrelease monitoring introduces no telemetry: only platform-provided summaries, user-initiated reports, and opt-in diagnostics (FR-8).
- Release evidence archive is scrubbed of private beta data.

### Accessibility and performance

- Netlify pages meet accessible-content requirements (FR-2) and are checked as part of the deploy report.
- Store accessibility declarations are backed by DOS-M07-002 evidence.
- Final Tier-1 smoke tests include the performance-sensitive journeys; the shipped build is the one measured in DOS-M07-003 or a gate-passing successor.

## UX and content states

- Store listings: truthful copy per FR-3 with production-matching screenshots (fixture data only), on both stores.
- Netlify site states: marketing, support/manual, privacy, accessibility, status/release notes, contact path — all static, versioned, and link-checked.

## Test plan

### Automated

- Store pre-submission validation (platform validation tooling for IPA/AAB) in the release pipeline.
- Checksum/tag verification of signed artifacts against the protected release job outputs.
- Netlify deploy checks: link integrity, security headers, HTTPS, no third-party script/cookie scan, accessibility checks on published pages.
- Package inspection scripts confirming declared permissions/SDKs match disclosures (with DOS-M07-001 tooling).

### Manual/device matrix

- Final Tier-1 smoke suite on physical devices per rollout stage: offline boot and core journeys, upgrade migration from the prior released baseline, reset, export/import, killed-app notification delivery.
- Observed-traffic capture on the final build to re-verify disclosures (AC-3).
- Rollout rehearsal: staged-release start/halt/expansion on the store consoles' test paths where available; Netlify prior-deploy restore; emergency patch branch build-and-verify; data-recovery guidance walkthrough — each executed by the authorized owner (AC-4).
- Store listing review on-device (both platforms): copy, screenshots, privacy URL, support links.

## Rollout and rollback

- Rollout: internal/closed candidates first; then phased/staged production rollout where stores permit, beginning at the smallest operational cohort; manual approval at each expansion only after store processing completes and Tier-1 smoke tests pass.
- Rollback lanes (kept distinct): (1) halt rollout/remove store availability; (2) restore static Netlify content via prior immutable deploy; (3) mobile forward-fix via the tested emergency patch branch with additive/forward-compatible migrations. Never downgrade a migrated SQLite database with an older binary unless compatibility is proven. For critical data risk, publish user recovery/export guidance through the support/status channel.
- Postrelease: monitoring thresholds (FR-8) trigger halt, hotfix, support notice, or catalog disablement with a named owner/on-call path.

## Risks, decisions, and open questions

- Risk: store review friction — the loopback Phoenix architecture could be mistaken for an external backend or hidden-code mechanism; mitigated by explicit review notes (FR-3) and, if rejected, documented resolution (AC-1).
- Risk: store policy changes between submission and release day; FR-4/AC-7 mandate a recorded release-day recheck with sources.
- Risk: irreversible migration baseline — a defect shipped in v1 migrations constrains all future upgrades; mitigated by the DOS-M07-005 immutability rule, additive/forward-compatible emergency policy, and rehearsed recovery.
- Decision required: trademark/name availability verification for "Digital Oil Sticker" through the appropriate owner — a repository search is explicitly insufficient; outcome recorded before store records are final.
- Decision required: staged-rollout cohort sizes/stages per store and the monitoring thresholds for halt/hotfix/support notice/catalog disablement.
- Open question: exact phased-release mechanics differ between App Store and Play; the runbook documents each store's actual controls as verified on release day, not assumptions.
