> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Store records, screenshots, ratings, and review notes drop; the deliverable becomes staged Fly deploys, custom-domain cutover, canary smoke checks, monitoring, and a rehearsed rollback._

## Outcome

The v1 browser MVP is live at `digitaloilsticker.com` (apex and `www`) served by a signed Phoenix LiveView container image on Fly.io in `ord`, cut over from the Netlify placeholder through a staged pipeline — build-and-attest, unlisted staging, production canary with DNS still on Netlify, then DNS cutover — with canary smoke checks against the real HTTPS/WSS surface, monitoring on Fly platform metrics and a browser-side error stream that carries no personal data, and a rehearsed three-lane rollback (Fly release rollback, DNS revert to the Netlify placeholder, Netlify static prior-deploy restore) that returns the public surface cleanly if anything fails.

## Why this matters and what it unblocks

Public web launch is an operational change with the same cost-of-failure shape as any user-facing release — user-visible outage on a public URL — but a materially different recovery topology from the pre-pivot spec: DNS cutover reversal, Fly release rollback, and static-content restoration replace app-store patches and phased-rollout percentages. This card converts every M07 hardening and QA and beta evidence artifact — hosted threat model (DOS-M07-001), WCAG browser-AT release bar (DOS-M07-002), page-load and hydration budgets (DOS-M07-003), browser/engine/OS matrix QA (DOS-M07-004), signed container images with SBOM and provenance (DOS-M07-005), unlisted-staging closed beta (DOS-M07-006) — into a launched production release on Fly and closes the browser-MVP launch gate. It freezes the catalog `data_version` and the IndexedDB `schema_version` shipped at cutover as the compatibility baseline the M08 multi-vehicle work (DOS-M08-001) activates on top of, and the M08 catalog operations work (DOS-M08-005/006) evolves.

## Functional requirements

- FR-1: The v1 release is a hosted browser application on Fly.io at `digitaloilsticker.com`. **There is no app-store submission in this card** — no bundle/package identifier, no store record, no App Privacy or Data safety form, no IPA/AAB validation, no review notes, no staged store rollout. Store distribution is deferred with the native re-entry set (`DOS-M00-003` DEFER, PIVOT-2026-08-01). The pre-pivot store-native FRs are retired and preserved verbatim in the "Superseded pre-pivot spec" section for historical readability of the ADR record (addresses staleness finding 1).
- FR-2: Publish a production Fly configuration that fixes region `ord`, `min_machines_running = 1`, `auto_stop_machines = false` (scale-to-zero is prohibited — a cold start that drops live WebSockets makes hydration timeouts routine, per ADR-0004 §"Region"), a WebSocket-capable proxy route on `/live/websocket`, a health check path and interval that gate traffic to a new release, machine size/RAM sized to the DOS-M07-003 server budgets, `PHX_HOST` set to `digitaloilsticker.com`, `Endpoint` `:url` configured for `https` on port 443 so generated URLs and the socket endpoint are correct behind the proxy, `Plug.SSL` with `rewrite_on: [:x_forwarded_proto, :x_forwarded_host, :x_forwarded_port]`, `force_ssl` on, and `check_origin` set to an explicit host list (never `true`, never `false`).
- FR-3: The release proceeds through four stages, each requiring manual approval and Tier-1 smoke: (1) **Build and attest** — GitHub Actions produces a signed container image with the catalog artifact baked in, an SBOM, and a provenance attestation per DOS-M07-005; catalog `data_version` and IndexedDB `schema_version` are recorded on the image. (2) **Staging** — deploy the image to an unlisted staging Fly app on a hostname not resolvable from the marketing surface, opened to the DOS-M07-006 invite audience for their walkthroughs. (3) **Production canary** — deploy the image to the production Fly app while `digitaloilsticker.com` DNS still points at the Netlify placeholder; canary smoke exercises the app via the Fly hostname. (4) **DNS cutover** — repoint the apex A/AAAA and `www` CNAME to Fly after Fly-managed TLS certificates verify on both hostnames; enable HSTS only after successful verification.
- FR-4: The custom-domain cutover targets exactly `digitaloilsticker.com` (apex) and `www.digitaloilsticker.com`; `digitaloilsticker.net` is a permanent redirect to `.com`; `help.digitaloilsticker.com` and `legal.digitaloilsticker.com` continue to resolve to Netlify per ADR-0002 as amended by ADR-0004. The Netlify placeholder deploy that served the apex prior to cutover is retained as the DNS-revert target; its deploy identifier is captured in the release ledger. HSTS `preload` is not requested at MVP. The chosen DNS TTL at cutover is bounded so the DNS-revert lane recovers within a documented window and is recorded in the release ledger.
- FR-5: Canary smoke checks execute per stage against the real HTTPS/WSS surface using the DOS-M07-004 browser/engine/OS matrix and pass all of: hydration cold-connect within the DOS-M07-003 budget with a determinate first paint that never shows a false empty garage; mutation round-trip acknowledged before the UI reads as saved (ADR-0004 §"Mutation round trip"); reconnect after a simulated Fly deploy re-hydrates the same DOM without teardown (ADR-0004 §"WebSocket and LiveView considerations"); `:storage_unavailable` banner renders in a browser with IndexedDB disabled, and `:data_missing` renders when `dos_boot_state == "has_data"` but hydration returns zero records; a catalog search returns a known-good result; export produces a hash-verified envelope and import round-trips it. Any stage failure halts the next stage; there is no automatic promotion.
- FR-6: Enable Fly platform monitoring (machine health, deploy state, request/socket rate, error rate, p95 latency, TLS certificate status) with alert thresholds bound to the DOS-M07-003 budgets; enable Netlify uptime checks on `help.` and `legal.` and on the retained placeholder deploy so the DNS-revert target is continuously proven live; run a scheduled QA smoke against the live URL that exercises the hydration and catalog-query paths; enable a browser-side error stream reporting script errors with **no assigns payload, no VIN, no odometer, no service date, no note text, no vehicle name** — the DOS-M09-008 redaction is enforced at the reporting boundary and verified as a release gate. The named on-call rotation binds thresholds to actions: halt cutover, forward-fix, DNS revert, or support-page notice on the Netlify static surface. (This retires the pre-pivot store-crash/vitals-summary framing.)
- FR-7: Implement three distinct, rehearsed rollback lanes: (a) **Halt cutover / DNS revert** — pause the pipeline before the DNS switch, or if already switched, revert DNS to the Netlify placeholder within the FR-4 TTL window. (b) **Fly release rollback** — `fly releases rollback` to the prior signed image identifier; the catalog `data_version` and the client `schema_version` compatibility line return exactly, because the artifact is baked into the image (ADR-0004 §"Catalog database on Fly"). (c) **Netlify content restore** — restore the prior immutable deploy for `help.` / `legal.` / placeholder independently of the app. **The pre-pivot never-downgrade-a-migrated-SQLite-database rule does not apply on the hosted server** (the runtime holds no persistent personal state), but the equivalent hazard exists client-side and is preserved: a rolled-back deployment older than the client's IndexedDB `schema_version` **MUST NOT** write — it enters read-only mode with a banner per ADR-0004 §"Schema versioning and migration". This is verified in rehearsal.
- FR-8: Produce a release ledger entry mapping source SHA, signed container image digest, provenance attestation, SBOM, catalog `data_version`, IndexedDB `schema_version`, Fly release identifier, DNS record + TLS certificate fingerprint snapshot, Netlify placeholder deploy identifier, canary/staging/cutover timestamps, named owners, and residual risks. Archive the entry with no personal data. This ledger line is the M08 compatibility baseline: `DOS-M08-001` activates a multi-vehicle IndexedDB `schema_version` migration on top of the `schema_version` frozen here, and `DOS-M08-005` / `DOS-M08-006` evolve the catalog release path this cutover establishes. (Replaces the pre-pivot store-manifest FR framing and directly addresses staleness finding 3 by naming the post-pivot equivalents.)
- FR-9: Before cutover, re-verify per ADR-0004 §"ADR-0003 → Unchanged" that `SOURCE_REGISTER.md` and `LICENSING_CHECKLIST.md` have completed the **web-serving** rights review for every catalog source in the shipped `data_version`. Public-domain U.S. Government sources (vPIC, FuelEconomy.gov — 17 U.S.C. §105) require only a recorded entry. Documented-facts and permission-needed sources cannot be served from the hosted app until reviewed; a missing review is a hard release hold. This is a new obligation the pre-pivot spec did not carry and it is now non-negotiable.

## Technical implementation contract

### Components and ownership boundaries

- Release management (this issue, DevOps/Release workstream): Fly configuration, deploy pipeline, cutover choreography, release ledger, runbooks, approval assembly.
- Fly application (hosts Phoenix LiveView): serves `digitaloilsticker.com` and `www` over HTTPS/WSS; opens exactly one Ecto repo (`CatalogRepo`) read-only; holds personal data only as transient values in `socket.assigns` for the lifetime of one LiveView connection.
- Netlify static content (team `cDiscourse`): `help.digitaloilsticker.com`, `legal.digitaloilsticker.com`, and the pre-cutover apex placeholder — the DNS-revert target. Never hosts Phoenix; distributes no application binaries.
- Signed container image, SBOM, provenance attestation: produced by the DOS-M07-005 pipeline; this issue consumes and verifies, never rebuilds outside the pipeline.
- Approval authority: product, engineering, QA, privacy/security, and operations owners named on the release approval; no single-owner ship decision.

### Data and persistence

- **The Fly runtime persists no personal rows.** Enforced by the ADR-0004 §"Enforcement" test asserting the deployed application's Ecto repo list equals `[CatalogRepo]` and that its connection is opened read-only — run against the deployed release as a gate.
- The catalog artifact is baked into the container image; catalog rollback is image rollback (ADR-0004 §"Catalog database on Fly"). No volume, no LiteFS, no managed database — the read-only single-writer problem is eliminated, not managed.
- The catalog `data_version` and IndexedDB `schema_version` shipped at cutover are frozen at the release ledger (FR-8) as the M08 compatibility baseline. Any emergency patch that changes either bumps both under change control.
- Browser-side IndexedDB schema is forward-only; a rolled-back server that reads a newer client payload enters read-only mode per ADR-0004 §"Schema versioning and migration" (FR-7). Downgrading or dropping unknown fields on the client is prohibited.
- The release evidence archive contains no personal data.

### Interfaces and events

- Public application interface: HTTPS at `digitaloilsticker.com` and `www.digitaloilsticker.com`; WSS at `/live/websocket` on the same hostnames. Fly proxy terminates TLS; `check_origin` restricts to this exact host list.
- Static content interface: HTTPS at `help.digitaloilsticker.com` and `legal.digitaloilsticker.com`, plus the retained apex placeholder — Netlify immutable deploys with instant rollback to a prior immutable deploy.
- Internal interface: the Fly release identifier plus signed image digest is the atomic release unit; the DNS record set plus TLS certificate fingerprint is the cutover unit; the release ledger (FR-8) is the single traceability record linking source SHA, image digest, attestation, SBOM, catalog and client `schema_version`s, Fly release identifier, DNS/TLS snapshot, and named owners.
- No third-party runtime interface exists. Catalog acquisition runs at build time in GitHub Actions, not in the request path (ADR-0004 §"Secrets"). CSP forbids third-party origins structurally.

### Failure and recovery behavior

- Staging failure: fix on the staging app; do not promote to the production canary Fly release.
- Canary failure (Fly app live but DNS still on Netlify): abort the cutover; no user impact — the placeholder is still serving.
- Post-cutover regression (Fly release live at apex): (a) `fly releases rollback` to the prior image; if the regression persists, (b) DNS revert to the Netlify placeholder within the FR-4 TTL window; if `help.` / `legal.` faults independently, (c) Netlify prior-deploy restore.
- Deploys drop every WebSocket by construction with one machine — clients auto-reconnect and remount, which re-runs hydration; pending mutations re-drive from client storage. This is why hydration must be idempotent, sub-second, and visually non-destructive (ADR-0004 §"First-paint and empty-state rules") — verified by FR-5 canary smoke.
- Client-side data loss risk is a product-level concern this release does not solve: users have export (from `DOS-M04-009` rescoped) as the only recovery mechanism, and the UI/legal pages state this unprompted (INV-5).
- All recovery paths are rehearsed by named owners before release day with commands recorded (AC-4).

### Security and privacy

- Transport per INV-22: HTTPS/WSS only; `Plug.SSL` with proxy-aware `rewrite_on`; `force_ssl` with redirect; HSTS enabled only after certificate verification on both hostnames; `check_origin` set to the exact production host list.
- CSP served on every response per ADR-0004 §"Content Security Policy": `default-src 'self'`, `script-src 'self'`, `style-src 'self'`, `img-src 'self' data:`, `font-src 'self'`, `connect-src 'self' wss://digitaloilsticker.com`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, `object-src 'none'` — plus `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and a `Permissions-Policy` denying geolocation, camera, microphone, payment. No `'unsafe-inline'`. All assets first-party and bundled by esbuild. Fonts self-hosted. **No CDN, no Google Fonts, no external script.**
- Session cookie: signed, `secure`, `http_only`, `same_site: "Lax"`, short `max_age`, carrying **only** the CSRF token and `live_socket_id`. No personal payload, no stable anonymous identifier. INV-3 and INV-4 preserved without qualification.
- No server-side personal record: verified on the deployed release by the ADR-0004 §"Enforcement" repo-list assertion and by the scripted-session log-scan test (hydrate → several mutations → export → clear → import) asserting no VIN, odometer value, service date, note text, or custom vehicle name appears in any captured log line.
- LiveDashboard **disabled in production**. No routine `fly ssh console` use. The privacy page states the scoped claim ("we store no personal data on the server" — not "no operator could ever observe a live session") verbatim per ADR-0004 §"LiveDashboard and operator access — stated honestly".
- Rate limiting per DOS-M07-001: per-IP HTTP + socket connect via a token-bucket plug; per-socket limits on catalog search/filter and on hydrate/import. Client IP taken from Fly's forwarded headers via a trusted-proxy-aware plug; used **in memory only** and never persisted (see logging).
- Secrets: `SECRET_KEY_BASE` and `PHX_HOST` via `fly secrets set`, read only in `runtime.exs`, never committed. Deploy-scoped Fly token in GitHub Actions repository secrets. `debug_errors: false` in production. `filter_parameters` and a Logger filter drop `handle_event` params by default with an explicit allowlist for non-personal events.
- No third-party error reporting. If ever added it requires an ADR plus a proven assigns-scrubbing layer (ADR-0004 §"No third-party anything").

### Accessibility and performance

- WCAG 2.2 AA per DOS-M07-002 verified across the DOS-M07-004 browser + assistive-technology matrix, including keyboard-only desktop paths through hydration, the storage-status UI, the cutover-day banner if any, and export/import.
- Page-load, time-to-hydrated, and LiveView round-trip latency budgets per DOS-M07-003 are measured on the live production URL as part of the canary smoke (FR-5); a failed budget blocks cutover. The pre-pivot Constitution §9 latency budgets were written for a loopback socket and are void until re-ratified (ADR-0004 R9); this card uses the provisional browser-first budgets from DOS-M07-003.
- Static pages on `help.` / `legal.` are accessibility-checked as part of the Netlify deploy report.

## UX and content states

- Live app: no change from RC — the RC that passed DOS-M07-004 and DOS-M07-006 is the release build. In-app: pre-hydration first paint follows ADR-0004 §"First-paint and empty-state rules" — `:hydrating` skeleton → `:loaded` / `:empty` / `:storage_unavailable` / `:data_missing`, never a fake empty garage.
- Cutover-day communication: the Netlify placeholder page prior to cutover states the launch is imminent and does not imply an app is running there; on cutover the app is live at apex; if halted the placeholder returns via DNS revert with a short "launch delayed" note.
- Public communication states: launch note published on the release-notes area of `help.` / `legal.` at cutover; support notice appears on the Netlify static surface within the FR-6 threshold window on any halt or forward-fix. No in-app broadcast facility exists (no server-side per-user record to broadcast to).
- Legal/help copy honors INV-5 without softening: data lives in this browser only, clearing browser data deletes it permanently, export is the only recovery, "backup"/"synced"/"safe"/"we'll remember"/"your account" are prohibited words for user data.

## Rollout and rollback

- Rollout: build-and-attest (GitHub Actions signed container image + SBOM + provenance) → staging Fly app for the DOS-M07-006 invite audience → production canary on the Fly app with DNS still on Netlify → per-stage manual approval and Tier-1 smoke → DNS cutover of apex + `www` to Fly after TLS verifies → HSTS enable → post-cutover Tier-1 smoke and monitoring watch → cutover complete. No automatic promotion at any stage.
- Rollback lanes (distinct, rehearsed):
  - (a) **Halt cutover / DNS revert to Netlify placeholder** — the fastest reversal; bounded by the FR-4 DNS TTL window; recovers the pre-cutover public surface with no application-server involvement.
  - (b) **Fly release rollback** — `fly releases rollback` to the prior signed image identifier; catalog `data_version` and IndexedDB `schema_version` compatibility line return exactly (artifact baked into the image, ADR-0004 §"Catalog database on Fly").
  - (c) **Netlify static prior-deploy restore** — for `help.` / `legal.` / placeholder, independently of the app.
- **No SQLite-downgrade rule on the hosted server** — no persistent personal state exists there — but the client-side downgrade prohibition stands: a rolled-back deployment older than the client's IndexedDB `schema_version` enters read-only mode per ADR-0004 §"Schema versioning and migration"; verified in rehearsal.
- Postrelease: FR-6 thresholds trigger halt, forward-fix, DNS revert, or support-page notice under the named owner/on-call path. There is no store-review, staged-rollout-percentage, or `mob_notify` control surface on this release — those are historical (see "Superseded pre-pivot spec").

## Risks, decisions, and open questions

- Risk: **DNS TTL bounds the DNS-revert speed.** Too long and rollback (a) is slow; too short and the resolver load is impractical. Decision required: TTL value at cutover, recorded in the release ledger.
- Risk: **Single-region, single-always-on machine** (ADR-0004 R8). Accepted for MVP; monitoring FR-6 flags outage fast; the Netlify placeholder is the visible revert. Second-machine cost decision deferred.
- Risk: **HSTS applied before both hostnames verify** would strand the DNS-revert lane behind a browser-cached policy. FR-4 mitigates by enabling HSTS only after verification; `preload` is not requested at MVP.
- Risk: **Web-serving rights not complete** for every source in the shipped `data_version` (FR-9). Hard release gate; the pre-pivot spec did not have this obligation because it shipped inside a signed native package.
- Risk: **Client-side data loss under browser eviction** (ADR-0004 R1) is a product-level risk this release does not solve — quarterly-oil-check users are the highest-risk cohort. Mitigated by INV-5 copy, export prominence, and honest storage-status UI; measured (not assumed) per-browser eviction behavior is on the DOS-M09-009 conformance suite, not this card.
- Risk: **§9 latency budgets are void until re-ratified** (ADR-0004 R9). FR-6 uses the provisional browser-first budgets from DOS-M07-003; Constitution 2.0.0 ratification of new budgets is a governance responsibility, not a release blocker on its own.
- Risk: **Constitution 2.0.0 not yet ratified.** ADR-0004 records that INV-1/2/6/7/17/19 are contradicted by the pivot. No ticket may cite the superseded forms as binding; this card cites the ADR-0004 discrepancy table as the authoritative record.
- Decision required: **canary audience for the staging Fly app** — drawn from the DOS-M07-006 closed beta cohort or fresh; recorded on the release approval.
- Decision required: **who pulls DNS at cutover** — on-call operator or engineering lead — with a documented fallback if that person is unreachable.
- Open question: **cost drift under real traffic.** ADR-0004 §"Cost shape" requires recording measured monthly cost after provisioning; the release ledger entry is the tracking mechanism, and an alert threshold on Fly billing should be set rather than discovered on a bill.
- Open question: **whether the Netlify placeholder deploy remains the right long-term DNS-revert target**, or whether a Fly maintenance app should replace it post-MVP; deferred to a post-launch retrospective.
