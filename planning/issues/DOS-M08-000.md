> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Remains post-MVP, but multi-vehicle now means multi-vehicle in browser storage and catalog operations now means server-side catalog releases._

## Outcome

A user can maintain many fully isolated vehicles inside the anonymous browser store the MVP established, switch among them through an accessible web navigation pattern with real per-vehicle URLs, and see correctly derived per-vehicle in-app due and overdue state on load and after every mutation. The catalog team can build, sign, and publish new catalog versions as immutable Fly.io release deploys that atomically replace the read-only catalog artifact inside the deployed image with a canary-verified rehearsed rollback, without ever touching the user's browser storage, without introducing a client-side pack updater, and without any operator ever holding a durable copy of any user's garage.

## Why this matters and what it unblocks

M08 is the explicit post-MVP expansion milestone. The v1 browser MVP deliberately ships a one-active-vehicle experience over multi-vehicle-safe internals (INV-9, restated for the browser store in `DOS-M09-001`) and a catalog that is only replaced when the operator ships a Fly release (ADR-0004 §"Catalog database on Fly"). This epic converts those reserved capabilities into shipped product under the browser-first architecture:

- Multiple vehicles enabled in the UI over an already-vehicle-scoped IndexedDB layout, with per-vehicle records, forecasts, and derived due state — the first item of the "Explicit post-MVP" scope boundary, expressed against the browser storage adapter (`DOS-M09-002`) rather than an on-device SQLite `UserRepo`.
- Signed, versioned, rehearsed catalog **releases** on Fly.io with atomic activation and one-command rollback — the second item of that boundary, translated from the pre-pivot client-side `.dospack` updater into the immutable server-side release model that ADR-0004 chose and that the Fly deploy pipeline in `DOS-M09-005` already builds on. Every future catalog refresh reuses this discipline.

Nothing after M08 exists in the current bootstrap roadmap; completing this epic establishes the multi-vehicle browser product and the server-side catalog-release discipline (build, sign, deploy, canary, rollback) that all subsequent catalog refreshes reuse. Notably, several capabilities the pre-pivot epic promised are structurally impossible in a hosted browser client and are addressed by explicit deferral rather than translation — see `Excluded` below.

## Included

Child issues tracked by this epic under the rescope:

- `DOS-M08-001` — Enable multi-vehicle in the anonymous browser garage: a `schema_version` upgrade of the IndexedDB `vehicles` object store (and dependent stores) via the forward-only migration contract owned by `DOS-M09-001`, with an ownership audit and singleton-guard removal in the domain contexts and LiveViews that assumed one vehicle. No Ecto migration is involved because there is no server `UserRepo` (INV-23).
- `DOS-M08-002` — Build the accessible tabbed garage and vehicle-management UX as a web navigation pattern: garage landing, WCAG 2.2 AA-compliant tab semantics verified against browser assistive technology (per the matrix owned by `DOS-M09-008`), add/reorder/archive/restore/delete flows, active-vehicle banner, and **real per-vehicle URLs** (`/garage/:vehicle_id`) that survive refresh, back/forward, deep-linking, and reconnect re-hydration (INV-24.2, INV-24.7).
- `DOS-M08-003` — Isolate service history, intervals, usage samples, forecasts, and derived due state per vehicle: vehicle-scoped aggregates enforced in the client store and re-validated server-side on hydration (since IndexedDB has no cross-store foreign-key enforcement), revision-safe recompute after every mutation round trip, garage overview summaries, and per-vehicle slices of the shared export/import envelope from `DOS-M04-009` (rescoped).
- `DOS-M08-005` — Define the signed catalog-artifact and trust-root contract for **build-and-deploy-time** signing and verification: the canonical catalog artifact format, the signing key roster, key rotation and revocation, anti-rollback protection at release-manifest granularity, and test vectors. The verifier runs in CI and in the Fly deploy readiness check, **not in the browser**, because the browser never downloads a catalog pack.
- `DOS-M08-006` — Build, sign, publish, observe, and roll back catalog releases through the Fly deploy pipeline (`DOS-M09-005`): reproducible artifact build in GitHub Actions, separation of duties for signing, an immutable release identifier that binds image digest, git commit, catalog `data_version`, and client-storage `schema_version`, a canary readiness gate that fails closed on manifest mismatch, and an operator runbook for the one-command rollback that restores the previous image and its exact catalog.

Deferred children of this epic (retained under the native re-entry holding set, not started here):

- `DOS-M08-004` — Fair per-vehicle notifications within OS pending-notification limits. Deferred to native re-entry because there is no OS notification scheduler in a browser and INV-17 (amended) ships in-app due/overdue only. See `Excluded` for the boundary this leaves and the FR that replaces it.
- `DOS-M08-007` — Client-side download / verify / atomically activate / recover catalog updates. Deferred to native re-entry (and revisited only if PWA/service-worker offline is later approved via `DOS-M09-009`) because the browser MVP queries the catalog from the server-side query surface (`DOS-M09-004`) and has no client-side catalog artifact to install.

## Excluded

- Any OS-scheduled or platform-scheduled notification, alert, alarm, badge, or lock-screen presentation for reminders. The MVP ships in-app due/overdue state only, computed on hydration and after each mutation, and every surface must say so plainly (INV-17 amended, INV-25). This includes silent adoption of Web Push: Web Push requires a service worker, a VAPID key pair, a browser-vendor push service, and a per-browser subscription endpoint that would have to live *somewhere* — adopting it would introduce remote infrastructure and a durable per-person identifier and therefore requires an ADR and a new ratified constitution revision, not a ticket in this epic (INV-17 amended, INV-19, and the `DOS-M09-009` spike).
- Any client-side `.dospack` updater, background catalog download, incremental/delta catalog fetch, or in-app catalog activation flow. Catalog replacement is a Fly deploy (ADR-0004 §"Catalog database on Fly"). This retires the pre-pivot `DOS-M08-007` client updater as a browser MVP concept.
- Any server-side write of any personal row — including any table, cache, ETS entry, external store, log line, error report, or crash trace — from any part of this epic. Any code path that would create one is a defect (INV-3, INV-4, INV-23; enforced by the release-gating tests specified in `DOS-M09-007`).
- Cloud sync, shared or household garages, remote push, telematics, shop booking, commerce, ads, social features, fleet analytics, cross-vehicle predictive modeling, exact alarms, remote signing in the client, executable code or plugins inside catalog artifacts, user records inside catalog artifacts, and any other item in the "Prohibited scope" set (INV-19).
- Every exclusion restated by the surviving rescoped children (parallel `garage_entries` object stores, silent last-write-wins across tabs without visible loss, silent record dropping on quota, silent destructive remapping across catalog versions, arbitrary schema migrations pushed from the server to the client store).
- Backporting any M08 capability into an MVP or M09 ticket (epic entry rule). Any MVP-era or M09-era deviation is filed as a new issue.

This FR replaces the pre-pivot FR-6 that promised an OS-scheduled reminder allocator; the pre-pivot FR-6 is **retired** by INV-17 amended and by the deferral of `DOS-M08-004`.
- FR-9: A new catalog release ships as an immutable Fly deploy (`DOS-M09-005`, `DOS-M08-006`) whose readiness check verifies the catalog artifact signature and manifest hash before the machine accepts traffic; the previous release can be restored by a rehearsed one-command rollback; and the browser client is **never** asked to download, verify, or activate a catalog artifact. This FR replaces the pre-pivot FR-7 that promised a Netlify-published `.dospack` with a client-side updater.
- FR-10: **There is no server-side personal record**, before, during, or after any M08 child ships. The deployed application's Ecto repo list remains exactly `[CatalogRepo]` opened read-only, the "no personal-data table" and "no personal value in logs" release-gating tests from `DOS-M09-007` continue to pass, and no catalog operation delivered in this milestone writes, migrates, corrupts, reads, or observes any user's browser storage from the server (INV-3, INV-4, INV-23). This FR is the browser-first equivalent of the pre-pivot FR-8 "`UserRepo` is never overwritten by a catalog operation".
- FR-11: Tampered, unsigned, revoked-key, or incompatible catalog artifacts are rejected **at build/CI and at Fly readiness**, not at the client. A release that fails signature verification or `data_version`/`schema_version` compatibility fails the readiness check, does not accept traffic, and does not replace the running catalog. Rollback restores the previous artifact byte-identically (ADR-0004 §"Catalog database on Fly").

## Technical implementation contract

### Components and ownership boundaries

Epic-level tracking issue. Ownership is delegated per child:

- Multi-vehicle domain and client-store scoping: `DOS-M08-001` (schema-version upgrade + singleton-guard removal) and `DOS-M08-003` (per-vehicle isolation, cross-store invariants, defensive server validation), both consuming the storage adapter contract from `DOS-M09-001`/`DOS-M09-002`.
- Garage LiveView and web navigation: `DOS-M08-002`, consuming the hydration protocol and pre-hydration UX contracts from `DOS-M09-002`/`DOS-M09-003`.
- In-app due/overdue derivation and presentation: reuses the forecast engine from `DOS-M06-003` (SURVIVES) and the derived-state persistence from `DOS-M04-005` (rescoped); presentation lives in `DOS-M08-002`/`DOS-M08-003`.
- Catalog artifact/trust contract: `DOS-M08-005`, consuming the catalog build determinism from `DOS-M03-010` (rescoped) and delivered by the Fly release pipeline in `DOS-M09-005`.
- Catalog release operations: `DOS-M08-006`, consuming the Fly deploy pipeline, release identifier, and rollback machinery in `DOS-M09-005`, and the domain/TLS boundary in `DOS-M09-006`.

### Data and persistence

Epic-level invariants:

- Server side: exactly one Ecto repo, `DigitalOilSticker.CatalogRepo`, opened read-only, containing zero personal-data tables (INV-23; enforced by the release-gating test from `DOS-M09-007`). The catalog SQLite artifact is baked into the deploy image (ADR-0004 §"Catalog database on Fly") and is replaced only by a full Fly release.
- Client side: exactly one IndexedDB database (`dos_local`) with the object stores and version line defined by `DOS-M09-001`, extended by the `schema_version` upgrade delivered in `DOS-M08-001` to activate ordering/active-selection metadata for multi-vehicle. `localStorage` continues to hold only the non-personal `dos_boot_state` hint.
- Boundary: hydration and mutation round-trip envelopes remain the sole transport for personal data across the network, and remain untrusted client input server-side (INV-24, `DOS-M09-002`). No catalog operation delivered in this milestone reads, writes, migrates, or observes any user's IndexedDB from the server.

### Interfaces and events

Epic-level tracking issue. Child issues define: multi-vehicle-shaped hydration payload extensions and their changesets (`DOS-M08-001`), the vehicle-scoped LiveView events and routes (`DOS-M08-002`), the derived-state recompute contract (`DOS-M08-003`), the catalog artifact manifest schema and signature envelope (`DOS-M08-005`), and the Fly release-identifier binding and rollback command surface (`DOS-M08-006`).

### Failure and recovery behavior

Epic-level tracking issue. The epic gate requires that: (a) a `schema_version` migration that is interrupted at the tab, network, or browser level leaves the client store in a consistent state on next hydration per `DOS-M09-001`'s forward-only-and-idempotent rules; (b) a mutation whose acknowledgement is lost is either re-driven from the client store on reconnect or surfaced honestly as "not saved to this browser" per INV-24.6, never silently dropped; (c) a Fly release that fails the readiness signature/manifest check does not accept traffic and the previous release remains authoritative (`DOS-M09-005`); (d) a one-command rollback restores the previous release image and its exact catalog artifact byte-identically.

### Security and privacy

Epic-level constraints inherited by children: catalog signing keys never reside in the repository, in CI logs, in the deployed image, in the running application, in Netlify, or on any operator's daily-driver workstation (the ceremony is specified in `DOS-M08-005`); the catalog artifact contains public catalog data only (no user rows and no operational metadata that identifies a person); operational metrics carry no personal parameter (INV-4, INV-26); the internet-facing hardening posture from `DOS-M09-007` (HTTPS/WSS, CSP, CSRF, origin checks, rate limits, log redaction) applies unchanged; and no operator ever inspects a live socket's assigns for user-facing diagnosis (ADR-0004 §"LiveDashboard and operator access").

### Accessibility and performance

Epic-level tracking issue. The epic gate requires the garage UI to pass the M07 (rescoped) accessibility and first-visit-payload/latency budgets at the maximum supported vehicle count, verified against the browser/AT matrix owned by `DOS-M09-008` and reported per engine.

## Dependency rationale

Under the browser-first architecture, M08 is downstream of both the MVP (M00→M07 rescoped) and the M09 platform milestone that the pivot introduced. It must not begin before either because it extends work only both have proven:

- The multi-vehicle chain extends the browser storage schema (`DOS-M09-001`), the hydration/mutation protocol (`DOS-M09-002`), and the storage-condition UX (`DOS-M09-003`), all of which are M09 gates.
- The catalog-release chain extends the Fly deploy pipeline and release-identifier binding (`DOS-M09-005`), the domain/TLS boundary (`DOS-M09-006`), and the internet-facing hardening (`DOS-M09-007`).
- The `DOS-M07-007` (rescoped) release rehearsal is the trigger that permits any post-MVP capability, and its priority-uplift rule (M08 defaults to `P3 Low`, `Target = Post-MVP` until the v1 launch gate changes priority) is preserved. Two children (`DOS-M08-004`, `DOS-M08-007`) are deferred to the native re-entry holding set as marked in the pivot table and are not on this dependency chain.

## Risks, decisions, and open questions

- Risk: singleton-vehicle assumptions from the browser MVP leaking into reused LiveView modules, contexts, or client-store helpers could corrupt cross-vehicle state; mitigated by the ownership audit in `DOS-M08-001` and the isolation property tests in `DOS-M08-003`, plus defensive server-side validation on every hydration (`DOS-M09-002`).
- Risk: IndexedDB offers no cross-store foreign-key enforcement, so per-vehicle isolation can regress silently through a code path that skips the adapter; mitigated by making the adapter the sole write path (`DOS-M09-002`), by property-testing isolation across concurrent tabs, and by revalidating references at hydration time.
- Risk: users may read a hosted URL and infer "my garage is on their server" even harder in a multi-vehicle product than in a single-vehicle one; the INV-25 honest-loss and INV-5 no-implied-backup obligations bind especially hard on the garage overview, empty-state, and delete-flow copy (`DOS-M08-002`), and are audited at exit.
- Risk: a bad catalog release could take the product offline for every user because there is one always-on machine and one release identifier serving traffic; mitigated by the canary readiness gate that fails closed (`DOS-M08-006`, `DOS-M09-005`) and by the rehearsed one-command rollback whose recovery time is captured as evidence.
- Risk: format or signature mistakes in the catalog artifact contract are expensive to correct once deploys have shipped against them; `DOS-M08-005` requires an approved RFC and test vectors before `DOS-M08-006` begins the pipeline work.
- Decision (deferred to `DOS-M08-002`): approved maximum active garage count (50 proposed for product review) and the visible-tab threshold vs. overflow-list threshold at responsive breakpoints (5 proposed at mobile viewports).
- Decision (deferred to `DOS-M08-003`): unit preference is app-global or vehicle-scoped, by product decision and a corresponding `schema_version` extension in `DOS-M09-001`.
- Open question: whether user demand for background reminders becomes strong enough to trigger the `DOS-M09-009` Web Push spike or, alternatively, to help revive the native track (ADR-0004 "Trigger conditions that revive the native track" §4). Recorded, not resolved here.
- Open question: post-M08 priority uplift timing — M08 stays `P3 Low` until the v1 browser launch gate changes priority.

## Superseded pre-pivot spec (historical record)

> This section preserves the card as chartered before the 2026-08-01 pivot to browser-first, and is retained for historical readability of the ADR record. The Outcome above is authoritative.

### Outcome (superseded)

A user can maintain many fully isolated vehicles, switch among them through an accessible tabbed garage, and receive correctly budgeted reminders for each. The data team can build, sign, publish, audit, roll back, and retire public catalog packs on Netlify; clients can verify and atomically activate them without risking private vehicle/history data or losing offline operation.

### Why this matters and what it unblocks (superseded)

M08 is the explicit post-MVP expansion milestone of the roadmap. The v1 product deliberately shipped a one-active-vehicle experience over multi-vehicle-safe internals (non-negotiable product rule 9) and a bundled, replace-on-app-update catalog only. This epic converts those reserved capabilities into shipped product:

- Multiple vehicles enabled in the UI, vehicle tabs/list switching, and per-vehicle reminders — the first item of the "Explicit post-MVP" scope boundary.
- Signed catalog updates from Netlify with atomic activation and rollback — the second item of that boundary, and the operational baseline every later incremental/delta catalog capability builds on.

Nothing after M08 exists in the bootstrap roadmap; completing this epic establishes the multi-vehicle product and the catalog-operations discipline (format contract, publishing pipeline, client updater) that all future catalog refreshes reuse.
