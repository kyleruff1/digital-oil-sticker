## Outcome

The product removes the M05 one-active-vehicle domain restriction and exposes the already vehicle-scoped M04/M05 records as a garage. A small additive migration supplies deterministic ordering and active selection without changing the identity or logical content of the existing vehicle or its dependent history.

## Why this matters and what it unblocks

Tabs, per-vehicle forecasts, notifications, import, and deletion all require strict ownership and a safe migration before UI begins. Non-negotiable product rule 9 required MVP internals to be multi-vehicle-safe precisely so this issue could be a small additive change rather than a rewrite; this issue proves that promise held and unblocks `DOS-M08-002` (garage UX), `DOS-M08-003` (per-vehicle isolation), and `DOS-M08-004` (per-vehicle notifications).

## Context and source of truth

- Master prompt §3, rule 9: "One-vehicle MVP, multi-vehicle-safe internals" — IDs, tables, events, and notification identifiers already support many vehicles; multi-vehicle tabs are an explicit post-MVP milestone.
- Master prompt §8 "Database and data-contract baseline": `UserRepo` tables `local_profiles`, `vehicles`, `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, `scheduled_notifications`, `schema_events`, and the migration rules (forward Ecto migrations run explicitly before the UI becomes writable; test fresh install and every supported upgrade path; local atomic backup before a risky migration; never silently reset user history).
- Master prompt §7: context boundaries `DigitalOilSticker.Garage`, `DigitalOilSticker.Maintenance`, `DigitalOilSticker.Reminders`; local event contract carrying local stable IDs.
- Catalog entry "DOS-M08-001 — Enable the existing vehicle-scoped schema as a multi-vehicle garage" in the master prompt.
- Epic entry rule of `DOS-M08-000`: preserve the M05 vehicle as the first garage item; the additive forward migration introduces only the ordering/active-selection metadata that was intentionally deferred.

## Included

- Additive garage metadata on the established `vehicles`/`local_profiles` contracts: deterministic `position`, optional favorite/color/icon presentation tokens, any missing ordering constraint, and nullable `active_vehicle_id` on `local_profiles`.
- Active vehicle selection and ordering as explicit persisted state with validation.
- Reuse of the existing archive/delete state on `vehicles` (`archived_at`, timestamps, archival state).
- A vehicle-ownership audit of every vehicle-owned table (audit, not redesign).
- The forward Ecto migration itself, including deterministic handling of empty databases and preexisting multiple-row fixtures.
- Removal of the M05 `active_vehicle_exists` creation guard after the migration succeeds.
- Explicit vehicle-scoped context APIs and rejection of cross-vehicle child IDs.
- Transactional enforcement of the approved maximum active garage count.
- Archive and permanent-delete semantics, including deterministic active-vehicle succession.
- Export/import schema compatibility for multiple entries with backward import of supported M05 exports.
- Fixture factories for multi-vehicle test data.

## Excluded

- A parallel `garage_entries` table.
- Renaming established schemas.
- Tabs/screens (garage UI is `DOS-M08-002`).
- Sharing vehicles between devices.
- Household accounts.
- Sync/merge.

## Functional requirements

- FR-1: Extend the established `vehicles` table only where needed with deterministic `position`, optional favorite/color/icon presentation tokens, and any missing ordering constraint; reuse its stable UUID, nickname, `archived_at`, and timestamps. Do not create any new vehicle-identity table.
- FR-2: Add nullable `active_vehicle_id` to `local_profiles` (or an equivalently explicit single source of truth) with validation that the target belongs to that profile and is not archived. Do not use a global process variable for active-vehicle state.
- FR-3: Audit — not redesign — every vehicle-owned table: `maintenance_plans`, `service_events`, `odometer_readings`, `usage_profiles`, `forecast_snapshots`, `reminder_rules`, and `scheduled_notifications` must retain their existing non-null vehicle foreign key and vehicle-scoped indexes. Record the audit result as evidence.
- FR-4: Catalog metadata/installations remain app-global. Profile preferences remain app-global unless the field is explicitly modeled on a vehicle/reminder rule.
- FR-5: The migration assigns the existing non-archived vehicle position 0 and makes it active using its existing UUID, preserving all dependent IDs, timestamps, and revisions.
- FR-6: An empty M05 database becomes an empty garage, not a phantom vehicle.
- FR-7: Fixtures containing more than one row — possible through imports/development even while the old UI was single-vehicle — are ordered deterministically and never collapsed.
- FR-8: Remove the M05 `active_vehicle_exists` creation guard only after the migration succeeds.
- FR-9: Enforce the approved maximum active count transactionally; creating another vehicle uses the same CatalogRepo snapshot rules and UserRepo context boundary as `DOS-M05-001`.
- FR-10: All read/write context APIs require an explicit `vehicle_id` or an explicit current-garage command that resolves then delegates. Reject cross-vehicle child IDs even if the caller supplies a valid ID from another vehicle.
- FR-11: LiveViews subscribe to vehicle-scoped topics/events.
- FR-12: Nicknames need not be globally unique, but the UI contract must disambiguate duplicates with year/make/model (rendering is `DOS-M08-002`; this issue supplies the disambiguation data).
- FR-13: Enforce a documented maximum active garage count based on tested storage/notification/UI limits; propose 50 for product review, with archives excluded from active notification scheduling.
- FR-14: Archive preserves history but removes the vehicle from default tabs and cancels its desired reminders.
- FR-15: Delete is permanent after export offer and typed/second-step confirmation; it transactionally deletes vehicle-owned rows and notification intent, then reconciles native cancellations.
- FR-16: Deleting the active vehicle chooses the next ordered active item or empty-garage state deterministically.
- FR-17: The export/import schema supports multiple entries while retaining backward import of supported M05 exports; a newer multi-vehicle export is never silently flattened by an older app.
- FR-18: Provide fixture factories that generate valid multi-vehicle `UserRepo` states for downstream M08 tests.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Garage` owns the garage aggregate: vehicle list, ordering, active selection, archive/restore, delete, and the maximum-count policy.
- `DigitalOilSticker.Maintenance`, `DigitalOilSticker.Forecasting` (inputs), and `DigitalOilSticker.Reminders` remain owners of their vehicle-owned tables; this issue audits their scoping but does not move ownership.
- The Ecto migration lives with the other `UserRepo` forward migrations and runs explicitly before the UI becomes writable (master prompt §8 migration rules).
- No LiveView/UI work beyond what context contracts require; screens are `DOS-M08-002`.

### Data and persistence

- `vehicles`: add deterministic `position` (with an ordering constraint ensuring contiguous deterministic order per profile), optional favorite/color/icon presentation tokens. Existing columns (stable UUID, profile ID, nullable `configuration_key`, catalog version, nickname, snapshots, support status, optional local-only VIN, timestamps/archival state) are reused unchanged.
- `local_profiles`: add nullable `active_vehicle_id` validated to reference a non-archived vehicle of the same profile.
- No cross-database foreign keys; `pool_size: 1` per SQLite Repo remains in force (master prompt §4.2).
- Migration is forward-only and additive; it never rewrites vehicle UUIDs, child-row IDs, timestamps, or revisions. Before this risky migration, create a local atomic backup and document recovery per master prompt §8.
- Vehicle-scoped indexes verified by the audit remain in place (for example `odometer_readings (vehicle_id, observed_at)`).

### Interfaces and events

- Context APIs: every read/write takes an explicit `vehicle_id`, or an explicit current-garage command that resolves the active vehicle and then delegates to the vehicle-scoped API.
- Authorization: APIs reject a child ID (plan, event, reading, rule, notification row) that belongs to a different vehicle than the `vehicle_id` argument, even when the child ID itself is valid.
- Events: reuse the local event contract (`vehicle_saved`, `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled`) with vehicle-scoped topics; add garage lifecycle events for create/reorder/archive/restore/delete/active-change carrying local stable IDs and reason codes, not display strings.
- Export/import: schema version bump that supports multiple entries; importers detect and refuse to silently flatten newer multi-vehicle exports on older apps.

### Failure and recovery behavior

- Migration interruption and disk-full recovery leave either the old valid schema or the fully migrated schema, never partially unscoped data.
- Delete is a single transaction over vehicle-owned rows plus notification intent; native cancellation reconciliation afterward is idempotent, and a crash between transaction and reconciliation converges on the next reconciliation pass.
- Active-vehicle succession on delete/archive is deterministic (next ordered item, else empty-garage state) and survives restart.
- Failed maximum-count enforcement aborts the creating transaction with a typed error; it never leaves an orphan vehicle row.

### Security and privacy

- No new sensitive fields. Optional local-only VIN handling, log redaction of VIN/mileage/notes/vehicle identifiers, and no-telemetry defaults from master prompt §7 are unchanged.
- Export files continue to be local, user-initiated artifacts; the export offer before permanent delete must not upload anywhere.
- Presentation tokens (favorite/color/icon) are cosmetic metadata and carry no personal data.

### Accessibility and performance

- Ordering and active-selection queries must be indexed so garage listing at the documented maximum active count (proposed 50) meets the M07 query budgets; supply query plans as evidence.
- This issue provides the disambiguation data (year/make/model) needed for accessible duplicate-nickname labels in `DOS-M08-002`.

## UX and content states

The issue nevertheless fixes the state vocabulary the UI will render: active vehicle, ordered garage, archived list, empty garage, at-limit, and delete-confirmation (export offer plus typed/second-step confirmation) states are all representable from persisted data with no global process variable.

## Test plan

### Automated

- Ecto migration golden fixtures: historical single-vehicle, empty, and preexisting-multiple-row databases, each with expected post-migration snapshots.
- Row-count/digest reconciliation across migration for every vehicle-owned table.
- Cross-vehicle isolation/property tests: randomized attempts to read/mutate vehicle A data through vehicle B scopes and forged child IDs must all fail.
- Interruption/disk-full tests: kill/fault injection during migration and delete transactions; assert old-or-fully-migrated invariant.
- Backward import/export tests: supported M05 export imports into the multi-vehicle schema; a multi-vehicle export presented to an older-schema importer is rejected, not flattened.
- Ordering property tests: arbitrary create/reorder/archive/restore/delete sequences preserve contiguous positions and a valid active selection.

### Manual/device matrix

- One physical iOS and one physical Android device: upgrade an installed v1 build with real user data, verify the garage migration is lossless, then restart to confirm ordering/active selection persists.
- Manual disk-pressure migration attempt on at least one device class to confirm the recovery behavior matches the automated result.

## Rollout and rollback

- Ships as a forward `UserRepo` migration inside the next post-MVP app release; it runs explicitly before the UI becomes writable.
- Pre-migration local atomic backup plus documented recovery is mandatory (master prompt §8); rollback of the app to a v1 binary is not supported after migration, so the release notes and runbook must state the one-way nature and rely on the backup for recovery.
- The `active_vehicle_exists` guard removal lands only after migration success, so a failed migration leaves the M05 behavior intact.

## Risks, decisions, and open questions

- Decision for product review: the documented maximum active garage count (50 proposed), grounded in tested storage/notification/UI limits.
- Risk: hidden singleton assumptions in v1 contexts surface during the audit; per product rule 10, each becomes a scoped fix in this issue only if it is an ownership defect, otherwise a new issue.
- Risk: preexisting multiple-row databases in the wild (via imports/development builds) differ from fixtures; deterministic ordering rules must be defined for any observed shape, never collapsing rows.
- Open question: exact modeling of the ordering constraint (per-profile unique position versus ordered index) — resolved inside this issue with the schema diff as evidence.
- Open question: whether favorite/color/icon tokens ship in the same migration or a follow-up additive migration; both are additive and must not block AC-1.
