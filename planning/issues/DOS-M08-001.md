> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The vehicle-scoped schema it activates is the IndexedDB object-store layout, and enabling it requires a client storage schema-version migration rather than an Ecto migration._

## Outcome

The product removes the MVP one-active-vehicle UI restriction and exposes the **already vehicle-scoped `vehicles` IndexedDB object store** ([DOS-M09-001](DOS-M09-001.md) §"Storage layout", [ADR-0004 §"Storage layout"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#storage-layout)) as a garage. The multi-vehicle-safe internals promised by [INV-18](../../docs/product/CONSTITUTION.md#7-vehicles-and-scope-shape) — every vehicle-scoped record already keyed by a client-generated `vehicle_id`, no singleton "current vehicle" field standing in for the relationship — landed with the M09 client-storage work and do not need to be re-shipped here. What this card ships is: a **`schema_version` bump** under `DigitalOilSticker.LocalStore.Migrations` per [ADR-0004 §"Schema versioning and migration"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#schema-versioning-and-migration) that adds the additive per-record fields multi-vehicle presentation needs (deterministic `position`, optional favorite/color/icon tokens, disambiguation-ready display fields), the removal of whatever code path still prevents a second vehicle from being saved, an audit that per-vehicle isolation holds in the object-store layout at 3+ vehicles, the documented MVP-active-count decision (proposed 50 for user-facing UI, well under the [DOS-M09-001](DOS-M09-001.md) payload cap of 200), and the export/import schema compatibility bump so a newer multi-vehicle export is never silently flattened by an older deployment.

The bump follows the ADR-0004 protocol without invention: pure forward-only functions in `LocalStore.Migrations.migrate/3` handle upgrade from `schema_version: 1` to the next integer, the migrated payload is written back to the client's storage in the same round trip via `local_store:put` ([ADR-0004 §"Mount and hydration sequence"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#mount-and-hydration-sequence) step 5), records that fail validation are **quarantined** — held aside, surfaced to the user, and exportable as raw payload — never silently dropped or repaired ([ADR-0004 §"Validation"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#validation-server-side)). No Ecto migration runs — there is no server-side `UserRepo` in the deployment ([ADR-0004 Decision §4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision), [DOS-M01-003](DOS-M01-003.md) as re-scoped) — and no personal row is written on the server at any point.

## Why this matters and what it unblocks

Under the pre-pivot spec this card unblocked native-tab UX, per-vehicle isolation, and per-vehicle OS notifications. Under [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) that dependency graph has shifted:

- **Unblocks** [DOS-M08-002](DOS-M08-002.md) (accessible tabbed garage as a **web** navigation pattern with real per-vehicle URLs) and [DOS-M08-003](DOS-M08-003.md) (per-vehicle isolation, now enforced in the client store and re-validated on hydration since there is no server-side row scoping to rely on). Both are re-scoped by the pivot table and depend on the additive object-store fields (position, disambiguation) and the removal of the second-vehicle guard that this card delivers.
- **Does not unblock** `DOS-M08-004` (fair per-vehicle notifications within OS pending-notification limits) — the pivot table classifies that card as `DEFER` because its entire subject is fairness within a limit that exists only on a native platform, and [INV-17](../../docs/product/CONSTITUTION.md#6-reminders-and-notifications) retires OS local notifications for the MVP. Multi-vehicle reminder work in the browser MVP is entirely in-app due/overdue state per vehicle, which is `DOS-M08-003`'s concern, not this card's.
- **Preserves the "multi-vehicle-safe from day one" promise mechanically**, not aspirationally: the `vehicle_id`-keyed object store, the `active_vehicle_id` pref, and the per-record `vehicle_id` foreign keys that made this a small additive change (rather than a rewrite) are exactly what M09 shipped, so this card measures how well that promise held and closes the small gaps.

## Included

- A `schema_version` bump under `DigitalOilSticker.LocalStore.Migrations` per [ADR-0004 §"Schema versioning and migration"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#schema-versioning-and-migration), adding the additive per-record fields multi-vehicle presentation needs on the `vehicles` object store: deterministic `position` (integer, per-payload contiguous), optional `favorite` boolean, optional `color_token` and `icon_token` presentation strings, and any missing disambiguation display fields (year/make/model source-of-truth on the `display_snapshot`) that [DOS-M08-002](DOS-M08-002.md) needs for duplicate-nickname resolution.
- Pure, ordered, forward-only migration functions in `LocalStore.Migrations.migrate/3` covering upgrade from `schema_version: 1` to the next integer, with recorded fixtures at every prior version and byte-equal write-back semantics for unknown keys.
- Removal of whatever code path or UI guard still prevents a second vehicle from being saved (see FR-2). No `active_vehicle_exists` guard exists in this codebase; the enforcement to remove is the browser-MVP equivalent — the UI/session code that treats the garage as single-slot.
- Object-store isolation audit (audit, not redesign) at 3+ vehicles: every write path key-scopes correctly by `vehicle_id`; every read path filters by `vehicle_id` in the payload shape; the record shapes in `Schema.V1` for `events`, `readings`, `usage`, and `reminders` each carry `vehicle_id` and every list function filters on it. Record the audit result as evidence.
- Deterministic UI order for the garage: contiguous per-payload `position` (0, 1, 2, …), stable across restart and reconnect, and the migration function assigns positions deterministically for pre-bump payloads (existing single vehicle → position 0; pre-existing multi-vehicle test fixtures → ordered by `created_at ASC, vehicle_id ASC`).
- The `active_vehicle_id` pref semantics stay as-shipped: `Session.active_vehicle/1` honors it only when it names a non-archived vehicle; deleting or archiving the active vehicle triggers deterministic succession via FR-9. This card does not re-implement `active_vehicle_id`; it only formalizes the succession rules against the multi-vehicle case.
- Archive and previewed permanent-delete semantics against 3+ vehicles, including deterministic active-vehicle succession, and the previewed export offer before permanent delete required by [INV-5](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage).
- Export/import schema bump: a newer multi-vehicle export is **rejected, not flattened**, by an older deployment per [ADR-0004 §"Schema versioning and migration"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#schema-versioning-and-migration) ("Client payload newer than the server's version … MUST NOT write. It enters read-only mode …"). Supported MVP single-vehicle exports import into the multi-vehicle schema without loss.
- Fixture factories that produce valid multi-vehicle hydration envelopes for downstream M08 tests, including duplicate-nickname payloads and archived-with-history payloads.
- Documented **MVP-visible active-vehicle count** decision, proposed 50, well under the [DOS-M09-001](DOS-M09-001.md) hydration payload cap of 200 (`Caps.max_vehicles`). The decision cites tested storage/latency limits; archives count against neither the visible list nor active reminder rendering.

## Functional requirements

- FR-1 *(rewritten from pre-pivot FR-1; addresses sweep finding 1 — contradicts-ADR)*: The additive per-record fields multi-vehicle presentation needs are added to the `vehicles` object store via the [DOS-M09-001](DOS-M09-001.md) record-shape contract: `position` (integer, per-payload contiguous starting at 0), `favorite` (boolean, optional), `color_token` (string, optional), `icon_token` (string, optional), and any missing year/make/model disambiguation fields on the `display_snapshot`. Unknown-key preservation (`Schema.V1` `@unknown_key`) means older deployments carry these fields through `__unknown__` byte-for-byte; the migration merely promotes them out on the first read at the new `schema_version`. **No Ecto migration**, no server-side `UserRepo` DDL, and no server-persisted personal row.
- FR-2 *(rewritten from pre-pivot FR-2; addresses sweep finding 2 — shipped-not-marked)*: `active_vehicle_id` **shipped with M09** in `app/lib/digital_oil_sticker/local_store/schema/v1.ex` `@prefs_keys` and is enforced at read time by `DigitalOilStickerWeb.LocalStore.Session.active_vehicle/1` (which honors `prefs.active_vehicle_id` only when it names a non-archived vehicle and otherwise falls back). This card does **not** re-add or re-model the field. The remaining work is removing the UI/session guard that still prevents a second vehicle from being saved in the MVP shape; the guard's removal ships behind the same release as the FR-1 additive fields so that a second `vehicles` record and the presentation metadata to distinguish it become saveable together. Live usage sites (`sticker_live.ex`, `vehicle_picker_live.ex`, `oil_change_live.ex`, `garage_switcher_test.exs`, `local_store/session.ex`) are re-verified against the multi-vehicle case; any lingering single-vehicle assumption is scoped to this card only if it is an ownership defect, otherwise a new issue per product rule 10.
- FR-3 *(rewritten from pre-pivot FR-3; addresses sweep finding 1)*: The object-store isolation audit for `vehicles`, `events`, `readings`, `usage`, `reminders`, and `prefs` runs at 3+ vehicles. Every read path filters by `vehicle_id` in the payload shape; every write path key-scopes by `vehicle_id`; no code path exposes vehicle A's records under a vehicle B scope. The audit is recorded as evidence and the record shapes it verifies are the ones in `DigitalOilSticker.LocalStore.Schema.V1` (`@vehicle_keys`, `@event_keys`, `@reading_keys`, `@usage_keys`, `@reminder_keys`). **No server-side database indexes or SQL constraints are involved** — the invariants live in the client adapter and are re-validated server-side on hydration ([DOS-M04-003](DOS-M04-003.md) as re-scoped).
- FR-4 *(kept, restated)*: Catalog references (`configuration_key`, `catalog_data_version`) remain resolved server-side against `CatalogRepo` at render time via the impersonal catalog-query surface ([DOS-M09-005](DOS-M09-005.md)) and MUST NOT carry personal identifiers ([INV-26](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage)). Prefs remain app-global on the singleton `prefs` record.
- FR-5 *(rewritten from pre-pivot FR-5; addresses sweep finding 1)*: The `schema_version` bump migration function assigns the existing single vehicle `position: 0`, preserves its client-generated `vehicle_id` UUIDv4, its `display_snapshot`, its `maintenance_plan` sub-document, its child records' `vehicle_id` foreign keys, and every timestamp. The migration is a **pure, ordered, forward-only function** of one prior payload version; it is unit-tested against recorded fixtures per [ADR-0004 §"Schema versioning and migration"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#schema-versioning-and-migration). The migrated payload is written back to the client in the same round trip via `local_store:put` per [ADR-0004 §"Mount and hydration sequence"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#mount-and-hydration-sequence) step 5.
- FR-6 *(rewritten from pre-pivot FR-6; addresses sweep finding 1)*: An empty hydration envelope migrates to an empty garage — never a phantom vehicle. The migration function distinguishes "no vehicles in payload" from "vehicles in payload but none has `position`" (the latter is a pre-bump multi-vehicle payload; positions are assigned by `created_at ASC, vehicle_id ASC`).
- FR-7 *(kept and reinforced)*: Pre-bump payloads with more than one vehicle (possible through imports or development builds even while the MVP UI was single-slot) are **ordered deterministically and never collapsed**. If any position collision is detected in the migrated payload, the offending records are held aside in the quarantine list per [ADR-0004 §"Validation"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#validation-server-side) — held aside, surfaced to the user, exportable as raw payload — never silently dropped or repaired.
- FR-8 *(rewritten from pre-pivot FR-8; addresses sweep finding 1)*: The MVP-visible active-vehicle count decision is documented (proposed 50) and is a **presentation cap on the user-facing garage list**, not a schema constraint or a hydration-payload cap. The hydration-payload cap is [DOS-M09-001](DOS-M09-001.md)/`Caps.max_vehicles = 200`; a payload exceeding it is rejected explicitly, never silently truncated. Archives count against neither the visible list nor in-app reminder rendering.
- FR-9 *(kept, restated for the browser MVP)*: Enforce **archive as default lifecycle** with `archived: true` on the `vehicles` record. Explicit permanent delete runs only via the previewed delete-vehicle transaction from [DOS-M04-005](DOS-M04-005.md) as re-scoped, offers export beforehand per [INV-5](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), and executes as **one IndexedDB `readwrite` transaction** across `vehicles` + `events` + `readings` + `usage` + `reminders` + `meta` per [ADR-0004 §"Mutation round trip"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#mutation-round-trip). Deleting or archiving the active vehicle chooses the next `position`-ordered non-archived vehicle as active, or `nil` for an empty-garage state; the choice is deterministic and survives reconnect and multi-tab.
- FR-10 *(kept)*: Nicknames need not be unique per garage. When two vehicles share a nickname, the [DOS-M08-002](DOS-M08-002.md) UI disambiguates them with year/make/model taken from `display_snapshot`. This card supplies the disambiguation data; rendering is `DOS-M08-002`'s.
- FR-11 *(rewritten from pre-pivot FR-17; addresses sweep finding 1)*: The export/import envelope bump is a **hydration-envelope `schema_version` change**, not a schema-file change. A supported MVP single-vehicle export ingests through `local_store:hydrate` and is migrated forward by the same `LocalStore.Migrations.migrate/3` chain used at mount. A **newer multi-vehicle export presented to an older deployment** is refused per [ADR-0004 §"Schema versioning and migration"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#schema-versioning-and-migration): the deployment enters read-only mode, renders the "this browser holds data from a newer version of the app" banner, disables mutations, and offers export. **Downgrading or dropping unknown fields is prohibited** — no silent flattening.
- FR-12 *(kept; multi-tab semantics)*: Multi-tab consistency continues to ride `BroadcastChannel("dos_local_store")` per [ADR-0004 §"Multi-tab consistency"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#multi-tab-consistency): every write is a compare-and-set on `meta.seq` inside the same `readwrite` transaction; a stale write aborts, surfaces `local_store:conflict`, the server triggers re-hydration, and the visible "reloaded from this browser's newer data" notice is shown. Multi-tab tests are extended to cover two tabs each editing a different vehicle in the same garage without cross-vehicle overwrite.
- FR-13 *(kept and reinforced; addresses sweep finding 1)*: Fixture factories generate valid multi-vehicle hydration envelopes for downstream M08 tests, including: 3+ vehicles with contiguous `position` values, duplicate-nickname pairs, one archived vehicle with retained history, and one payload with more vehicles than the FR-8 MVP-visible cap but under the [DOS-M09-001](DOS-M09-001.md) payload cap (to exercise the presentation-cap-versus-payload-cap distinction).
- FR-14 *(new; addresses sweep finding 1 — quarantine-based failure handling)*: The migration MUST NOT crash the session on partially invalid pre-bump payloads. Records that fail per-record validation post-migration follow the [ADR-0004 §"Validation"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#validation-server-side) quarantine path: the valid subset hydrates, the invalid records are held aside in the quarantine list, and the UI shows exactly what could not be read plus an export of the raw payload for recovery. Migration failure is never fatal to the session; it is fatal to the affected records only, and always visibly.
- FR-15 *(new; enforces client-agnostic domain per ADR-0004 Decision §6)*: The migration functions and the workflow layer that gains multi-vehicle behaviour MUST NOT reference `Phoenix.LiveView`, `Plug`, or the `LocalStore` protocol modules. `LocalStore.Migrations.migrate/3` is a pure function of a payload plus a target `schema_version`; the LiveView adapter carries the round trip. This is what makes "native mobile is deferred, not deleted" mechanically true for the multi-vehicle path.

## Technical implementation contract

### Components and ownership boundaries

The migration ships under `DigitalOilSticker.LocalStore.Migrations` (pure, forward-only, unit-testable against recorded fixtures) and consumes the record shapes from `DigitalOilSticker.LocalStore.Schema.V1` and its bump successor. The `Garage` workflow layer ([DOS-M04-005](DOS-M04-005.md) as re-scoped) gains multi-vehicle behaviour but does not gain a new transactional primitive — it continues to open one IndexedDB `readwrite` transaction per mutation through the browser-storage port defined by [DOS-M09-002](DOS-M09-002.md). No native notification bridge, `DeviceCommandBroker`, `NotificationAdapter`, or `UserRepo` is added or reused; the reminder path stops at producing in-app reminder state per [INV-17](../../docs/product/CONSTITUTION.md#6-reminders-and-notifications). The tabbed UI, and any per-vehicle URL routing, are `DOS-M08-002`'s concern.

### Data and persistence

- **`vehicles` object store** (per [DOS-M09-001](DOS-M09-001.md) §"Storage layout" and [ADR-0004 §"Storage layout"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#storage-layout)): keyed by `vehicle_id` (client-generated UUIDv4). Existing record shape from `Schema.V1` `@vehicle_keys` is reused unchanged; additive per-record fields introduced by this bump are `position`, `favorite`, `color_token`, `icon_token`, plus any missing year/make/model fields on `display_snapshot`. `archived_at`/`archived`, `created_at`, `updated_at`, `configuration_key`, `catalog_data_version`, `display_snapshot`, `support_status`, `engine_class_code`, `oil_model_version`, `vin_last6`, and `maintenance_plan` (embedded sub-document per [DOS-M09-001](DOS-M09-001.md)) are untouched.
- **`prefs` singleton**: unchanged. `active_vehicle_id` is already present per `Schema.V1` `@prefs_keys` and is enforced at read time by `DigitalOilStickerWeb.LocalStore.Session.active_vehicle/1`. This card does not model a new field on `prefs`.
- **Vehicle-scoped child stores** (`events`, `readings`, `usage`, `reminders`): unchanged. Each record already carries `vehicle_id` per `Schema.V1`; the audit re-verifies isolation at 3+ vehicles without adding fields.
- **No cross-store foreign keys** — IndexedDB does not enforce them ([DOS-M09-001](DOS-M09-001.md) FR notes). Cross-store integrity is enforced by the `Garage` workflow layer at write time and re-validated on hydration.
- **No structural IndexedDB database-version bump** ([ADR-0004 §"Schema versioning and migration"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#schema-versioning-and-migration): "IndexedDB's own version is bumped only for object-store/index changes"). Only the logical `schema_version` in `meta` (and in the envelope) advances.
- **No `pool_size`, no SQLite Repo, no Ecto migration, no `UserRepo`** — the deployed application has one Ecto repo, `CatalogRepo`, opened read-only ([ADR-0004 Decision §4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision)). The pre-pivot "no cross-database foreign keys; `pool_size: 1` per SQLite Repo" line does not apply here.

### Interfaces and events

- **Hydration + write-back**: exactly the [ADR-0004 §"Mount and hydration sequence"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#mount-and-hydration-sequence) protocol. When the server-owned `schema_version` is ahead of the client payload, the migration runs, the result is placed in assigns, and the server immediately `push_event`s `local_store:put` carrying the migrated payload so the client's storage is upgraded in the same round trip.
- **Mutation**: every create/archive/restore/delete of a vehicle rides the same `local_store:put` → hook `readwrite` transaction → `local_store:ack` round trip, with compare-and-set on `meta.seq`. Failed ack renders persistent "Not saved to this browser" per [INV-24.2](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage) and offers export.
- **In-process events** reused from [DOS-M04-005](DOS-M04-005.md) as re-scoped: `vehicle_saved`, `vehicle_archived`, `vehicle_restored`, `vehicle_deleted`, `active_vehicle_changed`. Emitted **after** `local_store:ack`, carrying stable client-side `vehicle_id`s and reason codes, not display strings.
- **Export/import**: the same envelope shape from [ADR-0004 §"Payload envelope"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#payload-envelope) with the bumped `schema_version`; hash-checked; replace/merge chosen by the user; previewed with counts before commit.

### Failure and recovery behavior

- **Migration interruption is inapplicable** — the migration function is pure, executes server-side inside one `handle_event("local_store:hydrate", …)`, and either produces a migrated payload or returns a validation error. The client's storage is only touched by the follow-up `local_store:put` in step 5, which is one atomic `readwrite` transaction; a crash between the migration and the write-back means the client still holds the old payload and the next mount runs the migration again — idempotently.
- **Partially invalid pre-bump payloads** follow the FR-14 quarantine path.
- **Newer-than-server payloads** enter read-only mode per FR-11; the app renders the explicit banner, disables mutations, and offers export. **Never** flattens.
- **Delete** is a single `readwrite` transaction over the deleted vehicle's rows plus `meta`; a crash between the transaction and any downstream in-process event emission converges on the next `local_store:hydrate` — there is no notification-cancellation reconciliation because there are no OS notifications.
- **Active-vehicle succession** on delete/archive is deterministic (next `position`-ordered non-archived vehicle, else `nil`) and survives reconnect.

### Security and privacy

- No new sensitive fields. `color_token`, `icon_token`, `favorite`, and `position` are cosmetic metadata and carry no personal data.
- The migration is a pure function of the untrusted client payload; it is validated exactly like any other hydration input ([ADR-0004 §"Validation"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#validation-server-side)).
- Logs emitted by the migration and the multi-vehicle workflow MUST NOT include VINs, odometer values, service dates, note text, custom vehicle names, `mutation_id`, `tab_id`, or any hydration/mutation/import/export payload fragment ([INV-4](../../docs/product/CONSTITUTION.md#2-no-online-accounts-anonymous-client-side-storage), [ADR-0004 §"Logging"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#logging)). Event names and error tags are allowed.
- The export offer before permanent delete is a client-produced `Blob` download only; it does not round-trip through the server ([ADR-0004 §"Export and import"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#export-and-import)).

### Accessibility and performance

- Ordering and active-selection reads are served from hydrated assigns; there are no database indexes to design. First-paint on a garage at the FR-8 MVP-visible cap of 50 vehicles must remain inside the provisional page-load budget in [CONSTITUTION §9](../../docs/product/CONSTITUTION.md#9-measurable-targets) — measured with a fixture-generated 50-vehicle payload and reported in the release notes.
- This card supplies the `display_snapshot` disambiguation data (year/make/model) that [DOS-M08-002](DOS-M08-002.md) needs to render accessible duplicate-nickname labels for browser assistive technology under the WCAG 2.2 AA contract in [DOS-M07-002](DOS-M07-002.md) as re-scoped.

## Rollout and rollback

- **Ships as a `LocalStore.Migrations` bump inside the next post-MVP Fly release** ([DOS-M09-006](DOS-M09-006.md) deploy pipeline). The migration runs server-side inside `handle_event("local_store:hydrate", …)` on every mount; the write-back rides the same round trip. **No Ecto migration is scheduled and no `UserRepo` DDL runs**, because there is no `UserRepo` in the deployment ([ADR-0004 Decision §4](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision)).
- **Pre-migration atomic backup is inapplicable at the server layer** — there is nothing on the server to back up. The client-side equivalent is the export offer, which the user is prompted to take before the first mutation at the new `schema_version` per FR-11's read-only-banner path (for the reverse direction) and is generally available at any time from Settings.
- **Rollback**: a redeploy of the previous Fly release brings back the previous server-owned `schema_version`. Clients that already migrated their local payload to the new `schema_version` will see the older deployment refuse writes and enter the read-only "this browser holds data from a newer version of the app" mode per [ADR-0004 §"Schema versioning and migration"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#schema-versioning-and-migration). **Downgrading or dropping unknown fields is prohibited**; there is no lossy rollback path. The release runbook must state this plainly and rely on export for recovery.
- **The single-slot guard removal lands only after the FR-1 bump is proven** in the deploy's canary step, so a failed rollout leaves the MVP single-vehicle behaviour intact.

- AC-8: The maximum active garage count is enforced transactionally and documented, with archives excluded from active notification scheduling.
