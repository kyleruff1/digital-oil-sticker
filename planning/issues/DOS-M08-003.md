## Outcome

Every vehicle independently owns its maintenance basis, readings, service history, forecast version/confidence, due status, and next action; one vehicle's edit cannot change another's derived state.

## Why this matters and what it unblocks

Reusing singleton assumptions is the highest multi-vehicle correctness risk and could cause a user to service the wrong car on the wrong schedule. This issue is the correctness core of the multi-vehicle release: `DOS-M08-004` (per-vehicle notifications) and the multi-vehicle release itself cannot ship until derived state is provably vehicle-scoped and revision-safe.

## Included

- Per-vehicle contexts: interval selection/source, service baseline, readings, usage, forecast, and due status as a vehicle-scoped aggregate.
- Vehicle-keyed forecast workers/events with revision-safe recompute and invalidation.
- Reuse of the M05/M06 history and dashboard surfaces under per-vehicle scoping.
- Garage overview summaries (one denormalized/derived summary per active vehicle).
- Per-vehicle units if approved by the product decision recorded in this issue.
- Stale-state handling ("Updating"/revision-safe loading states during recompute and tab switches).
- Concurrent edit isolation across vehicles.
- Single-vehicle and all-garage export/import with duplicate-ID handling.

## Excluded

- Cross-vehicle predictive modeling.
- Fleet analytics.
- Shared mileage patterns.
- Automatic maintenance bundling.

## Preconditions

- `DOS-M06-001`, `DOS-M06-003`, and `DOS-M06-004` are closed: the deterministic forecast functions, recompute pipeline, and due-state behavior exist in final v1 form; this issue scopes them per vehicle without changing their math.
- `DOS-M08-001` is closed: strict ownership, vehicle-scoped context APIs, and fixture factories exist.
- `DOS-M08-002` is closed (for user-facing completion): the navigation/identity contract that renders per-vehicle state exists.

## Functional requirements

- FR-1: Treat interval selection/source, service baseline, odometer segment/readings, declared usage, forecast snapshot, and due status as a vehicle-scoped aggregate. Pure forecast functions remain unchanged and receive one aggregate only.
- FR-2: Recompute/invalidation events carry vehicle ID and input revision.
- FR-3: A supervised keyed worker or serialized transaction prevents same-vehicle stale writes while allowing independent vehicles to compute concurrently.
- FR-4: PubSub/topic names and LiveView subscriptions must not broadcast private aggregate data globally; subscriptions are vehicle-scoped.
- FR-5: The garage overview may query one denormalized/derived summary per active vehicle: nickname/identity, observed odometer as-of, estimated due date/cause, confidence, status, and reminder state.
- FR-6: Update summaries transactionally or rebuildably; never calculate every full history in one render.
- FR-7: Unit preference is explicitly app-global or vehicle-scoped by product decision and migration. Whichever is chosen, canonical stored miles do not change.
- FR-8: Date/timezone for scheduling remains device-global while due targets are vehicle-specific.
- FR-9: Adding an oil change while vehicle A is active invalidates/schedules A only.
- FR-10: Switching tabs during recomputation shows A's prior result as "Updating" or a revision-safe loading state and never displays B's result under A.
- FR-11: Export can include all or one selected vehicle. Single-vehicle export includes referenced catalog/provenance metadata sufficient to import as a new entry.
- FR-12: Import duplicate-ID handling never overwrites another vehicle silently; the user receives explicit duplicate/replace choices.
- FR-13: Recompute triggers remain those of master prompt §9 (vehicle/plan/service/reading/unit/time-zone/catalog changes and app foreground), applied per affected vehicle only.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Maintenance` owns the vehicle-scoped aggregate assembly; `DigitalOilSticker.Forecasting` stays a set of deterministic pure functions with unchanged signatures receiving one aggregate.
- A supervised keyed recompute worker (or serialized per-vehicle transaction) owned by the domain layer — not a perpetual background GenServer for deadlines (master prompt §7) — serializes same-vehicle recomputes and permits cross-vehicle concurrency.
- The garage overview summary is a domain-owned read model; LiveViews (`StickerLive`, history, garage overview from `DOS-M08-002`) render it without recomputing.
- Export/import ownership stays with the context that owned it in v1, extended for vehicle selection.

### Data and persistence

- No changes to forecast math tables: `forecast_snapshots` keeps algorithm version, input hash, computation time, confidence code, and reason code per vehicle/cycle.
- Overview summary rows (or derived queries) are per active vehicle, updated transactionally with their inputs or rebuildable from source data; they are never the source of truth.
- Input revision is persisted or derivable so stale recompute results are detectable and discarded.
- If the unit-preference decision selects vehicle-scoped units, the change ships as an additive migration; canonical stored mileage (integer base units) is untouched either way.
- Single-vehicle export bundles referenced catalog/provenance metadata (configuration key, catalog version, source snapshots) sufficient for standalone import.

### Interfaces and events

- Events `service_event_recorded`, `odometer_recorded`, `forecast_changed`, `reminders_reconciled` carry vehicle ID plus input revision; topics are vehicle-scoped.
- Aggregate read API: one call returns the complete vehicle aggregate at a revision; UI requests carry the expected revision so late replies are identifiable.
- Summary read API: garage overview reads the per-vehicle summary; a reconciliation query can compare summary versus full dashboard at the same revision.
- Import API returns explicit duplicate/replace decisions to the UI rather than resolving silently.

### Failure and recovery behavior

- A crashed recompute worker for vehicle A does not affect other vehicles; supervision restarts it and the next event or foreground recompute converges.
- Stale async replies (from a superseded revision) are dropped, never rendered.
- A summary that cannot be updated transactionally is marked stale and rebuilt; it must never persist a value from a different revision than its inputs.
- Import failures roll back completely; a partially imported vehicle never appears in the garage.

### Security and privacy

- Vehicle-scoped topics prevent one LiveView from receiving another vehicle's private aggregate data; no global broadcast of history, odometer, or notes.
- Export files remain local and user-initiated; they carry vehicle history and provenance, so the UI presents them as user data to handle carefully. Log redaction rules (VIN, mileage, notes, vehicle identifiers) apply to all new worker/event logging.

### Accessibility and performance

- Garage summaries must meet query/performance budgets from M07 at 50 active vehicles; one summary query per vehicle, never full-history computation in a render path.
- "Updating"/loading states are announced accessibly (consistent with the `DOS-M08-002` accessibility bar) and never trap focus.

## UX and content states

- Per-vehicle dashboard: identical to v1 dashboard semantics, always labeled with the owning vehicle identity from the `DOS-M08-002` contract.
- Garage overview: per-vehicle summary rows (nickname/identity, odometer as-of, estimated due date/cause, confidence, status, reminder state).
- "Updating"/revision-safe loading state during recomputation and tab switches; the prior result remains visible and labeled rather than swapped for another vehicle's data.
- Export flow: all-garage or single-vehicle selection; import flow: explicit duplicate/replace choices.
- Established terminology is unchanged: "Estimated due date" with confidence label, source attribution, unknown/unsupported states (master prompt §6).

## Acceptance criteria

- [ ] AC-1: Parallel randomized mutations across at least 50 fixture vehicles yield results identical to calculating each vehicle in isolation.
- [ ] AC-2: Editing/deleting/replacing/archiving vehicle A changes no source, forecast, overview, or desired reminder record for B.
- [ ] AC-3: Garage summaries match full dashboards at the same revision and meet query/performance budgets.
- [ ] AC-4: Single-vehicle and all-garage export/import preserve referential integrity and present explicit duplicate/replace choices.
- [ ] AC-5: UI never renders a vehicle label from one aggregate with service/forecast data from another, including rapid tab switching and stale async replies.
- [ ] AC-6: The unit-preference decision (app-global or vehicle-scoped) is recorded with its migration consequence, and canonical stored miles are unchanged under either outcome.

## Test plan

### Automated

- Isolation property/concurrency tests: parallel randomized mutations across at least 50 fixture vehicles compared against per-vehicle isolated computation (AC-1).
- Topic/subscription tests proving no global broadcast of private aggregate data and correct vehicle-scoped delivery.
- 50-vehicle benchmark for garage summary queries against the M07 budget.
- Revision-race tests: interleave recompute completion with tab switches and assert stale replies are dropped.
- Export/import fixtures: single-vehicle, all-garage, duplicate-ID, and referential-integrity cases.
- Summary-versus-detail reconciliation test comparing overview rows with full dashboards at identical revisions.

### Manual/device matrix

- Tab-switch race capture on a physical device: rapid switching during recomputation, recorded as video evidence showing no cross-vehicle rendering.
- Foreground-recompute check on both platforms: background the app, mutate time/timezone, foreground, and verify only affected vehicles recompute.
- Manual export/import round trip on device, including a duplicate-ID import.

## Rollout and rollback

- Ships with the multi-vehicle release train after `DOS-M08-001`/`DOS-M08-002`; no independent server component.
- If the unit-preference decision requires a migration, it follows the M08-001 forward-migration and backup rules.
- Rollback is a corrective app release; because forecast snapshots are explainability records and summaries are rebuildable, no derived state blocks recovery.

## Dependency rationale

- `DOS-M06-001`, `DOS-M06-003`, `DOS-M06-004` (blockers): the deterministic forecast functions, recompute triggers, and due-state semantics being scoped per vehicle are frozen there; this issue must not fork their math.
- `DOS-M08-001` (blocker): strict ownership and vehicle-scoped APIs are prerequisites for any aggregate isolation guarantee.
- `DOS-M08-002` (blocker): user-facing completion requires the navigation/identity contract so isolated state is rendered under unambiguous identity.
- Blocks `DOS-M08-004` and the multi-vehicle release: fair notification allocation consumes per-vehicle due dates and revisions produced here.

## Risks, decisions, and open questions

- Decision: unit preference app-global versus vehicle-scoped (with migration); recorded in this issue, canonical storage unchanged either way.
- Risk: hidden shared state (process dictionaries, module attributes, singleton caches) from v1 surfaces under concurrency; the property/concurrency suite is designed to expose it.
- Risk: the overview read model drifts from full dashboards; mitigated by transactional/rebuildable updates and the reconciliation report.
- Open question: keyed-worker versus serialized-transaction recompute implementation; either must satisfy FR-3, chosen with evidence inside this issue.
