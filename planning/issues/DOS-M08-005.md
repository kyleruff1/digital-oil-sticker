## Outcome

A public catalog artifact has a deterministic format, provenance, compatibility policy, cryptographic signature, anti-rollback rule, and embedded verification trust root before any network updater exists.

## Why this matters and what it unblocks

HTTPS and Netlify deployment alone do not let the app prove that a downloaded vehicle/oil catalog is authorized, complete, compatible, or newer. Format/signature mistakes are difficult to repair once clients ship: the trust root is embedded in signed native binaries, so a broken contract can strand installed apps. This contract must be approved before `DOS-M08-006` (publishing pipeline) and `DOS-M08-007` (client updater) implement against it.

## Included

- Canonical serialization rules for the manifest (byte-exact canonical JSON).
- Signature and hash algorithms (Ed25519, SHA-256) and domain separation.

- Validation-order specification and a stable validation error-code catalog.

- Executable code/plugins in packs.
- User records in packs.
- Remote signing in the client.
- Delta updates until justified separately.

## Functional requirements

- FR-1: Define `.dospack` as a nonexecuting archive containing a read-only `catalog.sqlite3` plus canonical UTF-8 `manifest.json` and detached signature(s).
- FR-2: The manifest includes product/format/schema/catalog versions, monotonic sequence, release channel, created-at, optional not-after advisory, minimum/maximum app version, source snapshot IDs/dates/URLs/licenses, transformation-pipeline/source commit, SQLite version/page settings, artifact SHA-256/bytes, table row counts, per-table logical digests, and signing key ID.
- FR-3: Use Ed25519 signatures over a documented domain-separation prefix plus the exact canonical manifest bytes; the manifest hashes the exact catalog bytes.
- FR-4: Embed only public verification keys in the signed native app. Private keys reside in protected/offline release custody, never Netlify, the repository, CI logs, the catalog pack, or the application.
- FR-5: Pin the canonical JSON scheme/library with cross-language fixtures: UTF-8, key ordering, number representation, whitespace, and newline rules must be byte-exact. Prefer integer/string manifest fields where JSON numeric ambiguity could occur.
- FR-6: The catalog SQLite file contains public normalized catalog data only — no triggers with side effects, extensions, user tables, writable migration, executable code, HTML/JS, or external attachments.
- FR-7: Specify SQLite integrity/foreign-key/schema allowlist checks, and require that every displayed text is queried as untrusted escaped content.
- FR-8: Verification order is bounded size/header → archive path/count/compression-ratio defense → manifest parse/schema/product/channel/app compatibility → known nonrevoked key/signature → artifact hash → SQLite integrity/schema/count/logical digests → semantic data invariants.
- FR-9: Extraction happens only into a private temporary app directory and defends against absolute paths, `..`, symlinks, duplicate entries, bombs, and trailing data.
- FR-10: Anti-rollback defaults to rejecting a sequence below the highest successfully activated stable sequence. A separately signed emergency rollback authorization may name an exact prior digest/sequence and expiry; ordinary `latest.json` pointer changes cannot defeat client anti-rollback. Beta/stable sequences are independently namespaced.
- FR-11: Key rotation requires a release that trusts both old and new public keys before packs signed only by the new key. Revocation ships through an app release and/or a manifest signed by a still-trusted key; document lost-key/offline-device recovery.
- FR-12: Signatures authenticate publisher integrity, not source factual correctness; documentation and UI-facing language must preserve this distinction.
- FR-13: Define size/count limits (archive entries, manifest size, pack size bounds) and a stable machine-readable validation error-code catalog covering every rejection class.
- FR-14: Publish nonsecret test vectors (valid and invalid) and a reference verifier so `DOS-M08-006` and `DOS-M08-007` implement against fixed fixtures.

## Technical implementation contract

### Components and ownership boundaries

- Deliverables: the format RFC, JSON schema for the manifest, SQLite schema allowlist, signature procedure, key ceremony/rotation/revocation documents, compatibility matrix, error-code catalog, test-vector corpus, an Elixir/client verifier module contract, and an independent reference verifier (separate implementation for cross-checking).
- The verifier contract is consumed unchanged by `DOS-M08-007` (client) and `DOS-M08-006` (pipeline canary verification); neither may relax or reorder checks.
- Key custody ownership is a release-management responsibility defined here and operated in `DOS-M08-006` under separation of duties.

### Data and persistence

- Pack contents: read-only `catalog.sqlite3` (public normalized catalog data conforming to the frozen `CatalogRepo` schema of master prompt §8), `manifest.json` (canonical UTF-8), detached signature(s). No user data of any kind.
- Manifest fields are the authoritative compatibility record: product/format/schema/catalog versions, monotonic sequence, channel, created-at, optional not-after advisory, min/max app version, provenance (source snapshot IDs/dates/URLs/licenses, transformation-pipeline/source commit), SQLite version/page settings, artifact SHA-256/bytes, row counts, per-table logical digests, signing key ID.
- Client-side persisted trust state (highest successfully activated stable sequence per channel, trusted key set) is specified here and stored by `DOS-M08-007` in app-owned storage, never inside any pack.

### Interfaces and events

- Verifier interface: input pack bytes/paths plus client context (product, channel, app version, schema versions, highest activated sequence, trusted/nonrevoked keys); output typed accept, or typed rejection carrying a stable error code from the catalog.
- Error codes are stable identifiers for diagnostics and UI mapping (consumed by `DOS-M08-007` failure UX and `DOS-M08-006` monitoring); codes are never repurposed.
- The emergency rollback authorization is a separately signed document type with its own schema: exact prior digest/sequence, expiry, channel, and signing key ID.

### Failure and recovery behavior

- Any verification failure is terminal for that pack: no partial trust, no fallback to weaker checks, and the client retains its current catalog (continuity guarantee stated in AC-5).
- Expired signatures/not-after: the offline app with its existing catalog remains functional; expiry blocks new activation according to policy, never existing offline reads.
- Lost-key and offline-device recovery paths are documented: how clients that missed a rotation release regain update capability (through an app release trusting the successor keys).
- One-bit tampering anywhere in manifest, catalog, or signature must be detected (hash/signature layering leaves no unauthenticated bytes).

### Security and privacy

- Ed25519 with documented domain separation; SHA-256 content addressing; no weaker algorithm negotiable by data.
- Private keys: protected/offline custody only, never Netlify, repository, CI logs, pack, or application (FR-4).
- Archive hardening: zip-slip/absolute path/`..`/symlink/duplicate-entry/bomb/compression-ratio/trailing-data defenses specified with limits (FR-9, FR-13).
- SQLite hardening: schema allowlist, no side-effect triggers/extensions/executable content; all displayed text treated as untrusted and escaped (FR-6, FR-7).
- Packs are public artifacts: no user records, no confidential material; signatures prove publisher integrity, not factual correctness (FR-12).

### Accessibility and performance

- Verification-order design keeps cheap structural checks first (bounded size/header, archive defense) so hostile inputs are rejected before expensive hashing/SQLite work, bounding client CPU/memory on mobile devices.
- N/A for UI accessibility — this issue defines a format and verifier contract; user-facing states belong to `DOS-M08-007`.

## Test plan

### Automated

- Test-vector suite: valid packs plus the full malicious corpus (unsigned, unknown/revoked key, wrong product/channel, incompatible app/schema, rollback, corrupt SQLite, wrong count/digest, zip-slip/symlink/bomb/oversize, duplicate path, semantic-invalid).
- One-bit tampering fuzz: flip bits across manifest, catalog, and signature; both verifiers must reject every mutation.
- Fuzz/property suite over archive structure, manifest parsing, and canonical JSON round-tripping.
- Cross-implementation check: Elixir verifier versus independent reference verifier produce identical accept/reject decisions and error codes on the whole corpus.
- Reproducibility check: identical inputs produce an identical pack digest from two clean builds.

### Manual/device matrix

- Key-ceremony rehearsal: generate, store, and use signing keys per the documented ceremony with the custody roles, capturing the record as evidence.
- Manual inspection of a pack with documented standard tools (archive lister, SQLite CLI, JSON pretty-printer) proving AC-4.
- Tabletop walk-through of rotation, revocation, and lost-key recovery scenarios against the documents.

## Rollout and rollback

- This issue ships documents, fixtures, and verifier contracts — no runtime rollout. The RFC approval gate (AC-1) is the promotion event.
- Contract changes after approval require an RFC revision with its own compatibility analysis; the format version field exists so future revisions are detectable by clients.
- Rollback of the contract itself before client shipment is an RFC supersession; after clients ship, only forward-compatible evolution per the compatibility matrix is possible.

## Risks, decisions, and open questions

- Risk: canonical JSON divergence across languages/libraries silently breaks signatures; mitigated by pinned implementations and byte-exact cross-language fixtures (AC-6).
- Risk: an over-strict not-after policy could brick offline updating; policy explicitly separates advisory expiry (blocks new activation) from offline reads (never blocked).
- Risk: key compromise; mitigated by offline custody, rotation/revocation design, and the `DOS-M08-006` compromise runbook.
- Decision: exact archive container format and compression settings for `.dospack` — chosen in the RFC with determinism and hardening as criteria.
- Decision: single versus multiple detached signatures per pack (rotation overlap support) — resolved in the RFC.
- Open question: whether beta channels need their own trust root or only namespaced sequences — resolved in the RFC before approval.
