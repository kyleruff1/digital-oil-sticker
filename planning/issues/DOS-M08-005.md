> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _The client-verified pack and trust root become build-and-deploy-time signing and verification of the catalog artifact, since the browser client never downloads a pack._

## Outcome

Every catalog artifact baked into a Fly.io deploy image is accompanied by a canonical, cryptographically signed manifest that lets any auditor — and, mechanically, the Fly release readiness check — prove that the `catalog.sqlite3` file the running application will open matches, byte for byte, what CI built from pinned inputs under a documented key ceremony. The manifest pins format/schema/`data_version`, `generated_at`, `min_app_version`, artifact SHA-256/byte length, per-table row counts and logical digests, source versions and license versions from the M03 pipeline, and the signing key ID; the signature is Ed25519 over the exact canonical bytes of the manifest under a documented domain-separation prefix; private keys live in offline custody and never touch Fly, the repository, CI logs, the image, or the running application. A build-time verifier and an **independent reference verifier** produce identical accept/reject decisions and identical stable error codes on a published test-vector corpus, and the readiness check refuses to accept traffic if the artifact, manifest, or signature disagree.

## Why this matters and what it unblocks

ADR-0004 §"Catalog database on Fly" ships the catalog **read-only inside the deploy image** with the deliberate consequence that "catalog replacement is a deploy. Atomic by construction; new image up, old image down." That decision retires the pre-pivot problem this card was originally chartered to solve — a browser client never downloads a pack, so a client-side verifier, an embedded trust root in a signed native binary, and client-persisted anti-rollback state have no consumer in the current architecture. What survives, and what the browser-first MVP still needs, is a shorter but load-bearing chain: **the SQLite file inside the image is the entire product's authority for automobile identity, oil-service schedules, lubricant requirements, and filter fitments** (INV-15), and the CI job that produces it (`DOS-M03-010`, shipped 2026-08-02) currently proves integrity but does not prove authorship — a substituted artifact between CI and Fly registry would still pass integrity because the substituted artifact would carry its own valid hash.

This card closes that gap by binding the artifact to a signature made offline by the release owner. It unblocks the M09 release contract in three concrete ways: `DOS-M09-005` (Fly deploy pipeline, release provenance, rollback) gains a readiness gate that fails closed if the image's catalog does not match a manifest signed by a trusted key, so a corrupted or unauthorized image cannot receive traffic; `DOS-M09-004` (server-side catalog query layer) inherits the guarantee that every `CatalogRepo` process opens exactly the artifact CI vouched for, so INV-11 support statuses and INV-15 provenance render honestly; and the rescoped `DOS-M08-006` (build/publish/observe/rollback on Netlify → build/publish/observe/rollback of the Fly catalog release channel) inherits the signing procedure, key custody, and error-code catalog specified here rather than reinventing them.

The card is deliberately scoped away from anything the browser-first architecture no longer contains. There is no `.dospack` archive, no client verifier, no embedded public key in an app binary, no client-persisted anti-rollback ledger, and no runtime channel-manifest fetch — every one of those has been retired and is called out explicitly in §"Findings addressed" so the retirement is auditable rather than accidental.

## Included

- A canonical JSON schema for `catalog-manifest.json` **extended** with the signing fields (`signing_key_id`, `signature_algorithm`, `signature_domain_prefix`, `manifest_canonical_form_version`) alongside every field `DOS-M03-010` already emits (`manifest_version`, `catalog_version`, `schema_version`, `data_version`/`built_at`/`generated_at`, `min_app_version`, `payload_sha256`, `payload_bytes`, per-source `source_versions`/`license_versions`, record counts, per-table logical digests, `supersedes`).
- A pinned canonical serialization rule set (UTF-8, key ordering, number representation, whitespace, newline rules) with cross-language byte-exact fixtures.
- An **Ed25519** signing procedure over the domain-separation prefix concatenated with the exact canonical manifest bytes; the manifest hashes the exact catalog bytes; the detached signature is a sibling file to the manifest inside the deploy image.
- Key custody, ceremony, rotation, and revocation documentation: private keys generated and used only on an offline signing host, never exported, never present in Fly secrets, repository history, CI logs, the deploy image, or the running application. Rotation is a two-release procedure that first ships a trust store containing both old and new public keys before any release signed only by the new key; revocation is a trust-store update shipped as a normal release.
- A **build-time verifier** (Elixir module) invoked in CI after `DOS-M03-010` succeeds, before the image is tagged, that reads the artifact, manifest, and signature and either exits zero or exits with a stable numeric error code from the published catalog.
- A **deploy-time readiness gate** (part of the `DOS-M09-005` release contract) that re-runs the same verifier in-process at Fly machine start using the trust store baked into the image; failure fails the readiness check and no traffic is served.
- An **independent reference verifier** in a second language (published outside the Elixir application source tree) that consumes the same test vectors and produces identical accept/reject decisions with identical error codes.
- A published, versioned test-vector corpus (valid vectors plus the full malicious corpus applicable to a build/deploy-verified artifact: wrong hash, wrong per-table digest, wrong row count, wrong signing key, unknown key, revoked key, expired trust store, mismatched `data_version`, wrong `min_app_version`, one-bit tampering in manifest/signature/catalog, forward-incompatible `manifest_canonical_form_version`).
- A stable, machine-readable **error-code catalog** shared between the build-time verifier, the deploy-time gate, and the reference verifier; codes are never repurposed and are surfaced in CI logs and Fly readiness-check output.

## Excluded

- **`.dospack` archive format, in any revision.** Retired with the pack itself.
- **Any client-side verifier or embedded trust root in a client binary.** There is no client binary. The browser MVP verifies nothing about the catalog because the catalog never leaves the server.
- **Client-persisted anti-rollback state.** Rollback in the browser-first architecture is redeploy of the previous Fly release identifier (ADR-0004 §"Catalog database on Fly"); there is no client to persist a sequence counter.
- **Runtime channel-manifest fetch, or any download of catalog bytes to the client.** The catalog is read server-side only through `DOS-M09-004`'s query surface, which returns typed resolved results (INV-26), not catalog rows.
- **Confidentiality/DRM of the catalog.** The catalog is public content served via `DOS-M09-004`. The signature proves publisher integrity, not confidentiality.
- **Executable code, plugins, or migration scripts inside the catalog.** Same rule as the pre-pivot spec.
- **User records inside the catalog, in any form.** INV-3 and INV-23: personal data does not exist on the server.
- **Remote signing at deploy time.** The private key never runs on Fly, in a Fly secret, in a CI runner with third-party actions attached, or on any always-on host.
- **Delta catalog releases.** The MVP replaces the whole catalog per deploy.
- **PWA/Web Push adoption changing this contract.** If `DOS-M09-009` ever accepts service-worker catalog caching or Web Push, a *new* card re-opens the client-verifier question; this card does not pre-decide that.

## Functional requirements

- **FR-1 — Manifest extension.** `catalog-manifest.json` produced by `DOS-M03-010` is extended (not replaced) with `signing_key_id` (opaque stable identifier), `signature_algorithm` (fixed value `"ed25519"` for MVP), `signature_domain_prefix` (fixed documented ASCII string), and `manifest_canonical_form_version` (integer, starts at `1`). Every pre-existing field enumerated in `DOS-M03-010` FR-2 remains authoritative and byte-identical to what the builder emitted.
- **FR-2 — Canonical serialization.** The manifest is serialized in a pinned canonical JSON form (UTF-8 without BOM, sorted keys, no insignificant whitespace, integer preservation, `\n` line endings, integer/string fields where JSON numeric ambiguity could occur). A cross-language fixture corpus proves byte-exact equivalence across the pinned implementations.
- **FR-3 — Signature.** A detached Ed25519 signature is produced over `signature_domain_prefix ‖ canonical_manifest_bytes` and stored beside the manifest in the deploy image at a documented path. The manifest's `payload_sha256` already covers the catalog bytes end-to-end, so one-bit tampering anywhere in catalog, manifest, or signature is detectable.
- **FR-4 — Offline key custody.** Ed25519 private keys are generated and used only on an offline signing host. They MUST NOT be present in Fly secrets, environment variables of any always-on host, the repository or its history, CI runner state, third-party GitHub Actions, the deploy image, or the running application's memory at any time. Only the **public** trust store is baked into the deploy image.
- **FR-5 — Signing under separation of duties.** The signing ceremony requires two named roles: the release owner (initiates), and the custodian of the offline host (executes). Each release records ceremony date, key ID used, manifest hash signed, and the two role holders. Solo signing is prohibited by the ceremony documentation and refused by the recorded procedure.
- **FR-6 — Build-time verification (CI).** After `DOS-M03-010` succeeds and before the deploy image is tagged, the build-time verifier reads the artifact, manifest, and signature against a trust store checked into the repository, and fails the CI job on any rejection with a stable error code. The CI job artifact records the verifier version, trust-store hash, key ID, and error code (if any).
- **FR-7 — Deploy-time readiness gate.** At Fly machine boot, the readiness check runs the same verifier in-process against the same trust store baked into the image, and the machine refuses to accept traffic on failure. This is a hard gate in `DOS-M09-005`'s readiness contract; failure returns a non-200 readiness response and the Fly proxy withholds the machine from rotation. No fallback to a weaker check; no "degraded" mode.
- **FR-8 — Independent reference verifier.** A second-language reference verifier (target: a small Python or Node module published in this repo's `tools/` tree or as a separate crate) implements the same rules from the same spec. The two verifiers are proven to produce identical accept/reject and identical error codes across the full test-vector corpus.
- **FR-9 — Stable error-code catalog.** Every rejection class carries a stable numeric code and a stable machine-readable name. Codes are never repurposed; adding a code requires an RFC revision recorded here. The catalog is the single source shared by CI logs, Fly readiness-check output, and both verifiers.
- **FR-10 — Test-vector corpus.** A published corpus covers: valid pack; wrong `payload_sha256`; wrong per-table logical digest; wrong row count; wrong signing key; unknown key; revoked key (trust-store update removes it); expired trust store; mismatched `data_version`; wrong `min_app_version`; one-bit tampering in manifest; one-bit tampering in catalog; one-bit tampering in signature; forward-incompatible `manifest_canonical_form_version`.
- **FR-11 — Key rotation.** Rotation ships as **two** releases: (a) a release trusting both old and new public keys and still signed by the old key; (b) subsequent releases signed only by the new key. Rotation MUST NOT skip step (a); the ceremony documentation refuses to.
- **FR-12 — Key revocation.** Revocation is a normal release whose baked trust store removes the compromised key ID. There is no "revocation server" and no runtime revocation channel; a revoked release is undeployed by deploying its successor. The `supersedes` chain from `DOS-M03-010` FR-2 records what was withdrawn and why.
- **FR-13 — Signatures authenticate publisher integrity, not source factual correctness.** Documentation and any UI copy that surfaces catalog freshness or provenance MUST preserve this distinction; a signed manifest does not imply the underlying automotive facts are correct — that is INV-11 and INV-15's job.
- **FR-14 — No personal data touched.** Neither the manifest, the signature, the trust store, the verifier, the CI logs, nor the Fly readiness-check output may contain, hash, or reference any personal identifier or personal record. INV-3, INV-4, INV-23 apply to release engineering.
- **FR-15 (retirement notice).** The pre-pivot `.dospack` archive format, the client-side verifier interface, the embedded trust root in a native binary, the client-persisted anti-rollback state, and the runtime channel-manifest fetch are formally **retired** by this card. Any future re-opening (see §"Excluded") requires a new card, not a re-interpretation of this one. This FR exists so the retirement is auditable.

## Technical implementation contract

### Components and ownership boundaries

- **Catalog signer** (CI step, owned by release engineering): reads the catalog and the M03-010 manifest, extends the manifest with the FR-1 signing fields, canonically serializes it (FR-2), invokes the offline signing host to produce the Ed25519 detached signature (FR-3, FR-4, FR-5), and emits both files. The private key never touches the CI runner.
- **Build-time verifier** (Elixir module in the application's release engineering namespace, owned jointly with `DOS-M09-005`): consumes catalog + manifest + signature + trust store, produces `{:ok, key_id}` or `{:error, code}` with `code` from FR-9.
- **Deploy-time readiness gate** (Elixir plug or release task, owned by `DOS-M09-005`): re-invokes the build-time verifier at machine boot with the trust store baked into the image; readiness returns 200 only on `:ok`.
- **Reference verifier** (second-language implementation, owned by release engineering; independent code path so a bug in the Elixir verifier does not silently pass the reference): consumes the same corpus, produces the same result set.
- **Trust store** (checked-into-repo file listing key IDs with their Ed25519 public keys and optional not-after advisory dates): baked into every deploy image; rotation and revocation are edits to this file that ship as normal releases.
- **Offline signing host** (release engineering operational asset): documented per the ceremony; the signer script it runs is version-controlled but the key material is not.

### Data and persistence

- Deploy image contents relevant to this card: `catalog.sqlite3` (from `DOS-M03-010`), `catalog-manifest.json` (extended per FR-1, canonically serialized per FR-2), `catalog-manifest.json.sig` (detached Ed25519 signature per FR-3), and `trust-store.json` (public keys per FR-4). No user data of any kind.
- Manifest fields are the authoritative compatibility and provenance record. The MVP's authoritative field set is exactly what `DOS-M03-010` produces plus the FR-1 signing fields; no personal identifier, no user-derived value, no telemetry counter is added.
- The trust store lives inside the deploy image because the verification runs inside the image; a rotation or revocation therefore ships through the normal deploy channel and inherits its rollback contract (`DOS-M09-005`).
- No client-side trust state exists in the browser-first MVP; the "highest activated stable sequence per channel" concept from the pre-pivot spec is retired (FR-15).

### Interfaces and events

- **Verifier interface (Elixir):** `DigitalOilSticker.CatalogVerify.verify(catalog_path, manifest_path, signature_path, trust_store) :: {:ok, key_id} | {:error, error_code, detail}`. `error_code` is drawn from the FR-9 catalog. `detail` is a bounded, personal-data-free string suitable for CI logs and Fly readiness output.
- **CI event:** signer produces artifacts; verifier consumes them; the CI job records verifier version, trust-store hash, signing key ID, and outcome to the release ledger.
- **Deploy event:** Fly readiness check invokes the verifier; on success, the machine is added to rotation; on failure, the readiness endpoint returns a non-200 response and Fly proxy withholds the machine per `DOS-M09-005`'s rollback contract.
- **Rotation/revocation event:** a normal PR edits `trust-store.json` and ships through the normal release pipeline; no runtime side-channel.

### Failure and recovery behavior

- Any verification failure is **terminal for that release**: the release does not enter service. Recovery is the standing `DOS-M09-005` rollback: the previous release identifier is redeployed, which brings back the previous, already-verified catalog artifact byte-for-byte.
- CI failures at signing time hold the release at the CI stage and do not produce an image tag.
- CI failures at build-time verification hold the release at the same stage and record the FR-9 error code in the ledger.
- Deploy-time verification failures at machine boot never serve traffic; the previous release keeps serving, and the failure is a monitoring event on `DOS-M09-005`'s dashboards.
- One-bit tampering anywhere in the catalog, manifest, or signature is caught either at build time (if it was introduced before signing) or at deploy time (if it was introduced after signing, including a substituted image between CI and Fly registry).
- Trust-store expiry (not-after advisory reached with no rotation shipped) is a **CI warning** that blocks the next release; running deploys are unaffected because the trust check happens at boot, not periodically.

### Security and privacy

- **Algorithms:** Ed25519 for signatures, SHA-256 for content addressing. No algorithm is negotiable by data in the manifest or signature.
- **Key custody:** offline signing host only (FR-4). The CI runner performing the release is a "propose signing" role — it hands the canonical manifest bytes to the offline host and receives the signature back through an out-of-band channel the ceremony documents.
- **Supply chain:** no third-party GitHub Action holds, sees, or has permissions to request the signing key. The signing step runs on a runner the release engineering owner controls, and the signer script's dependencies are pinned by hash.
- **Trust store integrity:** the trust store is checked in and reviewed like code; a PR that edits it requires the release engineering owner's approval. A malicious trust-store edit would still need to ship through the release pipeline it is trying to defeat.
- **INV-3/INV-23:** No personal identifier or personal record appears in any artifact produced by this card. INV-4: no third-party telemetry in the signing or verification path; logs contain error codes and key IDs, never personal data (FR-14). INV-22: every hop between CI, signing host, Fly registry, and the running machine is over TLS, and the signature is checked at the point of use regardless.
- **Signatures authenticate the publisher, not the facts** (FR-13). A signed manifest attests that CI, under the documented ceremony, produced this artifact from these pinned inputs; it does not attest that a 5W-30 recommendation is right for a 2018 Camry, which is `DOS-M03-*`'s job.

### Accessibility and performance

- No UI. The card produces a build artifact, a signature, and a readiness-check verdict.
- Verification runtime is bounded and negligible relative to the M03-010 build itself; the deploy-time gate is a single SHA-256 hash over the catalog, a canonical serialization of the manifest, and one Ed25519 verification — small constant time on the Fly machine, comfortably inside the readiness budget from `DOS-M09-005`.
- Verification-order design keeps cheap structural checks (manifest schema, presence of required fields, key ID known to trust store, trust store not expired) first, so a corrupted image fails quickly without hashing the whole catalog when the failure is knowable earlier.

### Data change specifics

- **Manifest evolution:** adding a signing-relevant field bumps `manifest_canonical_form_version`. The verifier accepts all forms it knows and rejects strictly newer forms with a specific error code (FR-9, FR-10), so a rolled-back deploy that meets a newer form never silently ignores fields it does not understand.
- **Trust-store evolution:** additions (rotation) and removals (revocation) each ship as a normal release with a PR record. A trust-store that removes the currently-in-use key without also adding a successor is refused by CI (`no signing path`).
- **Reproducibility:** unchanged from `DOS-M03-010` FR-12 — this card does not weaken it. Two builds from identical pinned inputs produce identical catalog SHA-256, identical canonical manifest bytes (after this card's extension), and — with the same private key — identical signature bytes.

## UX and content states

N/A — build/release engineering artifact with no direct UI. Indirect contract: the deploy-time readiness gate is what a returning user actually depends on when they land on `digitaloilsticker.com`, because it is the check that prevents a rotten catalog from ever answering their query. Its failure surfaces to operators as a `DOS-M09-005` monitoring event, never to users as a "catalog error" screen — users see the previous release keep serving because rollback is redeploy of the previous release identifier. `DOS-M09-004`'s honest degradation states (INV-11 support statuses) are unaffected by this card.

## Acceptance criteria

- [ ] AC-1 — Signed manifest ships in every release image. Every Fly deploy image contains `catalog-manifest.json` extended per FR-1, canonically serialized per FR-2, and `catalog-manifest.json.sig` signed per FR-3. A grep-and-verify script in CI proves both files exist and the signature verifies against the trust store baked in the same image.
- [ ] AC-2 — CI blocks the release on any verifier rejection. A red-team fixture flipping one bit in the catalog after M03-010 succeeds and before signing causes CI to fail with the FR-9 code for `catalog_hash_mismatch`; another fixture flipping one bit in the signature after signing causes CI to fail with `signature_invalid`. Neither ever tags a release image.
- [ ] AC-3 — Deploy readiness gate refuses to serve a tampered image. An out-of-band test that swaps `catalog.sqlite3` inside a candidate image before Fly machine boot causes the readiness check to return non-200 with the FR-9 code recorded in the machine log; the Fly proxy withholds the machine from rotation; the previous release keeps serving traffic; `DOS-M09-005`'s rollback contract is exercised end-to-end.
- [ ] AC-4 — Independent reference verifier agrees on the full corpus. The Elixir verifier and the second-language reference verifier produce byte-identical `{accept | reject, error_code}` output over the FR-10 test-vector corpus. A diff of the two output files is empty.
- [ ] AC-5 — Canonical JSON is byte-exact across pinned implementations. Cross-language fixtures prove UTF-8 encoding, key ordering, number representation, whitespace, and newline rules produce byte-identical manifests from two different serializers.
- [ ] AC-6 — Key rotation is a two-release procedure and skipping the first release is refused. A dry-run rehearsal ships (a) a release trusting both old and new keys signed by the old key, then (b) a release signed only by the new key; a control rehearsal that attempts (b) without (a) is refused by CI with a specific error code.
- [ ] AC-7 — Revocation is a normal release and undeploys the revoked key by rollout, not by side channel. A dry-run rehearsal ships a release whose trust store no longer contains the revoked key ID; the release deploys, the previous release keeps serving until it does, and there is no runtime revocation server.
- [ ] AC-8 — No personal data anywhere in the release evidence. The release ledger entries produced by this card contain only artifact/manifest/signature hashes, key IDs, error codes (if any), and ceremony role names — no VIN, no personal record, no personal identifier of any kind (FR-14).
- [ ] AC-9 — Retired scope stays retired. Repository search proves the shipped implementation contains no `.dospack` archive, no client-side verifier interface, no client-embedded trust root, and no runtime channel-manifest fetch. Their absence is a positive test, not a "nothing found" absence — the test enumerates the retired names from FR-15 and asserts each returns zero matches under the application source tree.

## Test plan

### Automated

- **Signing round trip:** signer emits manifest+signature; build-time verifier accepts; recorded in CI logs.
- **Verifier corpus:** the FR-10 test-vector corpus runs against the Elixir verifier and the reference verifier; a diff of the two `{accept | reject, error_code}` outputs is empty (AC-4).
- **Tamper suite:** flipping one bit in each of (a) catalog, (b) manifest, (c) signature produces the correct FR-9 code (AC-2).
- **Canonical JSON fuzz:** property-based tests prove the canonical serializer is deterministic across shuffled input orders and equivalent Elixir/reference re-serializations (AC-5).
- **Readiness-gate simulation:** a test harness runs the release entry point against a tampered image and asserts a non-200 readiness response and the FR-9 code (AC-3).
- **Trust-store evolution:** rotation test ships a trust store with both old and new keys signed by the old key; a follow-up test ships one signed only by the new key; a control test attempts to ship only the second and is refused (AC-6).
- **Revocation test:** trust-store update removes a key ID; verification against a signature by that key ID now rejects with `signing_key_revoked` (AC-7).
- **No-personal-data scan:** the scripted-session log-scan test defined in ADR-0004 §"Enforcement" is extended to cover the CI signing pipeline logs and the readiness-check output; no VIN, odometer, service date, note text, custom vehicle name, or personal identifier appears (FR-14, AC-8).
- **Retired-scope absence scan:** a repo-wide grep for the FR-15 retired names asserts zero matches under the application source tree (AC-9).
- **Reproducibility:** two clean builds from identical pinned inputs and the same signing key produce identical `payload_sha256`, identical canonical manifest bytes, and identical signature bytes.

### Manual/device matrix

- **Key-ceremony rehearsal:** two named roles (release owner, custodian of the offline signing host) execute the documented ceremony end to end for a rehearsal release, recording ceremony date, key ID, manifest hash signed, and the two role holders as release evidence.
- **Tabletop walk-through:** rotation, revocation, lost-key recovery, and offline-host-unavailable scenarios walked through against the documentation with the release engineering owner and a second role holder present.
- **Registry-substitution drill:** an out-of-band operator swaps the `catalog.sqlite3` inside a candidate image before Fly machine boot; readiness gate refuses; the previous release keeps serving; the incident is filed and closed with the FR-9 error code (AC-3).
- **Trust-store review:** the release engineering owner reviews the trust-store PR before every rotation or revocation ships.

## Rollout and rollback

Promotion path: `DOS-M03-010` produces the catalog and its (pre-extension) manifest → signer extends the manifest, canonically serializes it, and produces the detached Ed25519 signature under the FR-5 ceremony → build-time verifier passes → deploy image is tagged with the release identifier from `DOS-M09-005` → Fly registry receives the image → Fly machine boots and the deploy-time readiness gate re-runs verification → machine enters service. Every step records a ledger entry.

Rollback: the standing `DOS-M09-005` procedure — redeploy the previous release identifier. Because the catalog is inside the image and the signature travels with it, "the previous catalog comes back exactly" (ADR-0004 §"Catalog database on Fly"). No side-channel rollback for the catalog exists or is needed.

Contract changes after ratification (adding a manifest field, changing the canonical serialization, changing the signature algorithm) require an RFC revision recorded here and a `manifest_canonical_form_version` bump.

## Risks, decisions, and open questions

- **Risk:** the offline signing host becomes a single point of unavailability that stalls releases. **Mitigation:** the ceremony documents a "lost-host" playbook: the release engineering owner can regenerate a new key pair on a fresh offline host and ship a rotation release trusting both the old (unavailable) and new keys, then subsequent releases signed only by the new key.
- **Risk:** a third-party GitHub Action added to CI in the future gains access to the signing invocation and exfiltrates the signature-request channel to the offline host. **Mitigation:** the signer script is invoked only from a pinned, first-party CI job that a third-party action cannot reach; adding a third-party action to that job requires the release engineering owner's approval and is a documented review item.
- **Risk:** the trust store baked in an image outlives its usefulness because `not-after` advisories are ignored on running machines. **Mitigation:** trust-store `not-after` is a CI-time warning that blocks the *next* release, not a runtime kill switch, so a running deploy is never killed by clock drift, but the next release forces attention.
- **Risk:** the two-verifier equivalence rots because the reference verifier is unmaintained. **Mitigation:** the test-vector corpus and both verifiers are exercised in the same CI job, so equivalence is a release gate not a periodic check.
- **Risk:** operators mistake a signed manifest for a factual guarantee about automotive claims (FR-13). **Mitigation:** the copy in every place the signing state is surfaced (release notes, ledger entries, monitoring dashboards) uses "publisher integrity" language, never "verified data" language.
- **Decision:** MVP uses Ed25519 exclusively; multi-algorithm negotiation is deferred until a concrete threat model (post-quantum, algorithm agility) requires it. Deferral is recorded here rather than in a hidden preference.
- **Decision:** the trust store is a checked-in file, not a network-fetched artifact. Ratified because the reason a network trust root would exist — updating trust without a redeploy — is exactly the anti-pattern ADR-0004 §"Catalog database on Fly" retires ("ad-hoc production edits: impossible. This is a feature.").
- **Decision:** the reference verifier lives in this repo rather than a separate one, because separate-repo maintenance overhead outweighs the incremental blast-radius benefit for the MVP. Revisit if release engineering ever gains a second maintainer.
- **Open question:** does `DOS-M09-009`'s eventual PWA/Web Push verdict re-open the client-verifier question, and if so, does the client-side verifier reuse this card's Elixir verifier compiled to WebAssembly or the reference verifier ported to a browser runtime? Left open until `DOS-M09-009` produces its verdict.
- **Open question:** does a future beta channel need its own trust root or only a distinct signing key ID? Left open until a beta channel is actually proposed; the FR-9 error-code catalog reserves `unknown_channel` for that expansion.

### Outcome

A public catalog artifact has a deterministic format, provenance, compatibility policy, cryptographic signature, anti-rollback rule, and embedded verification trust root before any network updater exists.

### Why this matters and what it unblocks

HTTPS and Netlify deployment alone do not let the app prove that a downloaded vehicle/oil catalog is authorized, complete, compatible, or newer. Format/signature mistakes are difficult to repair once clients ship: the trust root is embedded in signed native binaries, so a broken contract can strand installed apps. This contract must be approved before `DOS-M08-006` (publishing pipeline) and `DOS-M08-007` (client updater) implement against it.

### Context and source of truth

- Master prompt §4.2: `CatalogRepo` is replaceable, read-mostly reference data; `UserRepo` is never replaced by a catalog update.
- Master prompt §4.3: Netlify serves "immutable versioned catalog packages and their signed manifest" as a static boundary.
- Master prompt §8 "Migration and catalog rules": the optional network update "follows the same protocol in M08: signed manifest, hash, size, schema/min-app compatibility, staged integrity check, atomic activation, rollback"; the catalog builder emits rejected-row reports, coverage counts, collisions, source diffs, a manifest, and a deterministic SQLite artifact; catalog records are immutable within one `data_version`; `catalog_metadata` includes `schema_version`, `data_version`, `generated_at`, `min_app_version`, and content hash; `data_sources` carries provenance, license reference, SHA-256, and attribution.
- Master prompt §7 "Production shell security": treat packaged material appropriately; no remote secrets in the client.
- Catalog entry "DOS-M08-005 — Define the signed, versioned catalog-pack and trust-root contract" in the master prompt.
- M07 dependencies `DOS-M07-001`, `DOS-M07-005`, `DOS-M07-007` for the hardening/release baselines this contract builds on.

### Included

- Pack/manifest layout for the `.dospack` archive.
- Canonical serialization rules for the manifest (byte-exact canonical JSON).
- Signature and hash algorithms (Ed25519, SHA-256) and domain separation.
- Keys, rotation, and revocation policy, including key ceremony documentation.
- Schema/app compatibility policy (minimum/maximum app version, schema versions).
- Provenance and license metadata carried by the manifest.
- Anti-rollback rule and the exceptional signed emergency rollback authorization.
- Size/count limits and archive-hardening rules.
- Validation-order specification and a stable validation error-code catalog.
- Published nonsecret test vectors and a reference verifier.

### Excluded

- Confidentiality/DRM.
- Executable code/plugins in packs.
- User records in packs.
- Remote signing in the client.
- Delta updates until justified separately.

### Preconditions

- `DOS-M07-001`, `DOS-M07-005`, and `DOS-M07-007` are closed: v1 hardening, security posture, and release controls the trust design extends are proven.

### Functional requirements

- FR-1: Define `.dospack` as a nonexecuting archive containing a read-only `catalog.sqlite3` plus canonical UTF-8 `manifest.json` and detached signature(s).
- FR-2: The manifest includes product/format/schema/catalog versions, monotonic sequence, release channel, created-at, optional not-after advisory, minimum/maximum app version, source snapshot IDs/dates/URLs/licenses, transformation-pipeline/source commit, SQLite version/page settings, artifact SHA-256/bytes, table row counts, per-table logical digests, and signing key ID.
- FR-3: Use Ed25519 signatures over a documented domain-separation prefix plus the exact canonical manifest bytes; the manifest hashes the exact catalog bytes.
- FR-4: Embed only public verification keys in the signed native app. Private keys reside in protected/offline release custody, never Netlify, the repository, CI logs, the catalog pack, or the application.
- FR-5: Pin the canonical JSON scheme/library with cross-language fixtures: UTF-8, key ordering, number representation, whitespace, and newline rules must be byte-exact. Prefer integer/string manifest fields where JSON numeric ambiguity could occur.
- FR-6: The catalog SQLite file contains public normalized catalog data only — no triggers with side effects, extensions, user tables, writable migration, executable code, HTML/JS, or external attachments.
- FR-7: Specify SQLite integrity/foreign-key/schema allowlist checks, and require that every displayed text is queried as untrusted escaped content.
- FR-8: Verification order is bounded size/header → archive path/count/compression-ratio defense → manifest parse/schema/product/channel/app compatibility → known nonrevoked key/signature → artifact hash → SQLite integrity/schema/count/logical digests → semantic data invariants.
- FR-9: Extraction happens only into a private temporary app directory and defends against absolute paths, `..`, symlinks, duplicate entries, bombs, and trailing data.
- FR-10: Anti-rollback defaults to rejecting a sequence below the highest successfully activated stable sequence. A separately signed emergency rollback authorization may name an exact prior digest/sequence and expiry; ordinary `latest.json` pointer changes cannot defeat client anti-rollback. Beta/stable sequences are independently namespaced.
- FR-11: Key rotation requires a release that trusts both old and new public keys before packs signed only by the new key. Revocation ships through an app release and/or a manifest signed by a still-trusted key; document lost-key/offline-device recovery.
- FR-12: Signatures authenticate publisher integrity, not source factual correctness; documentation and UI-facing language must preserve this distinction.
- FR-13: Define size/count limits (archive entries, manifest size, pack size bounds) and a stable machine-readable validation error-code catalog covering every rejection class.
- FR-14: Publish nonsecret test vectors (valid and invalid) and a reference verifier so `DOS-M08-006` and `DOS-M08-007` implement against fixed fixtures.

### Technical implementation contract

#### Components and ownership boundaries

- Deliverables: the format RFC, JSON schema for the manifest, SQLite schema allowlist, signature procedure, key ceremony/rotation/revocation documents, compatibility matrix, error-code catalog, test-vector corpus, an Elixir/client verifier module contract, and an independent reference verifier (separate implementation for cross-checking).
- The verifier contract is consumed unchanged by `DOS-M08-007` (client) and `DOS-M08-006` (pipeline canary verification); neither may relax or reorder checks.
- Key custody ownership is a release-management responsibility defined here and operated in `DOS-M08-006` under separation of duties.

#### Data and persistence

- Pack contents: read-only `catalog.sqlite3` (public normalized catalog data conforming to the frozen `CatalogRepo` schema of master prompt §8), `manifest.json` (canonical UTF-8), detached signature(s). No user data of any kind.
- Manifest fields are the authoritative compatibility record: product/format/schema/catalog versions, monotonic sequence, channel, created-at, optional not-after advisory, min/max app version, provenance (source snapshot IDs/dates/URLs/licenses, transformation-pipeline/source commit), SQLite version/page settings, artifact SHA-256/bytes, row counts, per-table logical digests, signing key ID.
- Client-side persisted trust state (highest successfully activated stable sequence per channel, trusted key set) is specified here and stored by `DOS-M08-007` in app-owned storage, never inside any pack.

#### Interfaces and events

- Verifier interface: input pack bytes/paths plus client context (product, channel, app version, schema versions, highest activated sequence, trusted/nonrevoked keys); output typed accept, or typed rejection carrying a stable error code from the catalog.
- Error codes are stable identifiers for diagnostics and UI mapping (consumed by `DOS-M08-007` failure UX and `DOS-M08-006` monitoring); codes are never repurposed.
- The emergency rollback authorization is a separately signed document type with its own schema: exact prior digest/sequence, expiry, channel, and signing key ID.

#### Failure and recovery behavior

- Any verification failure is terminal for that pack: no partial trust, no fallback to weaker checks, and the client retains its current catalog (continuity guarantee stated in AC-5).
- Expired signatures/not-after: the offline app with its existing catalog remains functional; expiry blocks new activation according to policy, never existing offline reads.
- Lost-key and offline-device recovery paths are documented: how clients that missed a rotation release regain update capability (through an app release trusting the successor keys).
- One-bit tampering anywhere in manifest, catalog, or signature must be detected (hash/signature layering leaves no unauthenticated bytes).

#### Security and privacy

- Ed25519 with documented domain separation; SHA-256 content addressing; no weaker algorithm negotiable by data.
- Private keys: protected/offline custody only, never Netlify, repository, CI logs, pack, or application (FR-4).
- Archive hardening: zip-slip/absolute path/`..`/symlink/duplicate-entry/bomb/compression-ratio/trailing-data defenses specified with limits (FR-9, FR-13).
- SQLite hardening: schema allowlist, no side-effect triggers/extensions/executable content; all displayed text treated as untrusted and escaped (FR-6, FR-7).
- Packs are public artifacts: no user records, no confidential material; signatures prove publisher integrity, not factual correctness (FR-12).

#### Accessibility and performance

- Verification-order design keeps cheap structural checks first (bounded size/header, archive defense) so hostile inputs are rejected before expensive hashing/SQLite work, bounding client CPU/memory on mobile devices.
- N/A for UI accessibility — this issue defines a format and verifier contract; user-facing states belong to `DOS-M08-007`.
