## Outcome

A controlled pipeline turns pinned source snapshots into reproducible validated packs, signs them under separation of duties, deploys immutable artifacts to Netlify, promotes a signed channel pointer, and retains an auditable rollback path.

## Why this matters and what it unblocks

Catalog operations must be repeatable and recoverable; manually uploading a mutable database risks partial releases, unverifiable provenance, and client breakage. This issue turns the `DOS-M08-005` contract into an operated publishing capability and unblocks `DOS-M08-007` (client updater) and the catalog-update launch.

## Context and source of truth

- Master prompt §4.3 "Netlify is a static boundary": Netlify hosts the static site, deploy previews, and "immutable versioned catalog packages and their signed manifest"; build and test catalogs in GitHub Actions; Netlify is not an always-on Elixir/Phoenix host. Research anchors from §4.3: https://docs.netlify.com/build/functions/get-started/ and https://docs.netlify.com/build/edge-functions/api/ (context on what Netlify is and is not; catalog paths in this issue are static artifacts, not functions).
- Master prompt §8: the catalog builder emits rejected-row reports, coverage counts, collisions, source diffs, a manifest, and a deterministic SQLite artifact; catalog records are immutable within one `data_version`; `data_sources` records provenance/license/SHA-256/attribution.
- Master prompt §4.4: source rights discipline (three-lane approval model, source register) that pack provenance and license metadata must reflect.
- Catalog entry "DOS-M08-006 — Build, sign, publish, observe, and roll back catalog packs on Netlify" in the master prompt.
- `DOS-M08-005`: the `.dospack` format, canonical manifest, signing procedure, key custody, anti-rollback, and test vectors this pipeline must produce and satisfy.
- `DOS-M07-007`: the Netlify site and release controls this pipeline extends.

## Included

- Source pinning (immutable raw-source snapshots/digests and locked transform code).
- Deterministic Elixir build of the normalized SQLite catalog in a clean environment.
- Validation and diff review (source/license/provenance and semantic validators; row/add/change/remove coverage comparison to the prior release).
- Preview and approval steps; signing under separation of duties.
- Immutable Netlify publish at content-addressed paths.
- Signed channel manifest (`latest.json`) promotion as the last step.
- Correct headers/CORS for pack and pointer paths.
- Production canary verification.
- Retention policy for referenced packs.
- Rollback pointer procedure and incident runbook.
- Operational metrics from host logs only.

## Excluded

- User/profile endpoints.
- Server-side search.
- Unsigned hotfix files.
- Client code updates.
- Secret keys in Netlify.

## Functional requirements

- FR-1: The pipeline consumes immutable raw-source snapshots/digests and locked transform code, creates the normalized SQLite catalog in a clean environment, runs source/license/provenance and semantic validators, compares row/add/change/remove coverage to the prior release, and fails on unexplained threshold anomalies.
- FR-2: Produce identical pack bytes from identical inputs, or document unavoidable signed metadata and isolate it from the reproducible content digest.
- FR-3: Attach source manifest, validation report, data diff, sample query results, licenses, SBOM/tool versions, and pack digest to the GitHub catalog release.
- FR-4: Separate build, approval, and signing roles. Signing consumes only an approved digest/manifest in a protected/offline step, requires two-person confirmation for stable, and emits signature/public metadata without exposing the private key.
- FR-5: Verify the final pack independently after signing (reference verifier from `DOS-M08-005`).
- FR-6: Deploy packs to immutable content-addressed paths such as `/catalogs/<channel>/<sequence>/<sha256>.dospack`.
- FR-7: Set correct content type, `Content-Length`, `ETag`, `Accept-Ranges` if supported, strict CORS limited to what the native downloader needs, immutable caching for hashed packs, and short revalidation for pointers.
- FR-8: Do not use an SPA fallback on catalog paths; missing paths return a real 404 and never HTML.
- FR-9: Publish order is pack first → fetch/hash/signature/canary verify from the production URL → publish a small canonical, signed `latest.json` channel pointer last. A client can always keep using the prior pack if any step fails.
- FR-10: Netlify is a static artifact origin only; no functions/endpoints serve catalog logic.
- FR-11: Rollback normally repoints `latest.json` to a still-safe higher-sequence corrective pack. A cryptographic rollback to a lower sequence uses the exceptional authorization defined in `DOS-M08-005`.
- FR-12: Preserve every referenced pack for the published support window and prevent garbage collection while installed clients may need it.
- FR-13: Operational checks monitor static availability, TLS/certificate, pointer/pack status/content type/size/hash, and CDN errors without ingesting application profile data.
- FR-14: Define alert owners, retry/backoff guidance, host outage behavior, compromised pack/key response, and a catalog disable notice on the static support site.

## Technical implementation contract

### Components and ownership boundaries

- GitHub Actions owns build/validate/diff/preview stages (master prompt §4.3: build and test catalogs in GitHub Actions); Netlify owns only static artifact hosting and pointer serving.
- The protected/offline signing step is outside CI secrets scope and consumes only the approved digest/manifest; two-person confirmation for stable channel.
- Release engineering owns promotion, retention, rollback, and the incident runbook; data engineering owns validators and diff review; roles are distinct per FR-4.
- The reference verifier from `DOS-M08-005` is the canary/verification tool; this issue does not fork or weaken it.

### Data and persistence

- Pipeline inputs: immutable raw-source snapshots with digests, locked transform code at a pinned commit, prior-release manifest for diffing.
- Pipeline outputs: the `.dospack`, its manifest, signatures, validation report, data diff, sample query results, licenses, SBOM/tool versions — attached to the GitHub catalog release (FR-3).
- Netlify state: content-addressed pack paths (immutable) plus per-channel `latest.json` pointers (mutable, signed, canonical).
- A published-artifact inventory tracks every referenced pack, its channel/sequence/digest, and its retention obligation.

### Interfaces and events

- Publishing interface to clients is exactly the `DOS-M08-005` contract: pack bytes at `/catalogs/<channel>/<sequence>/<sha256>.dospack` and the signed canonical `latest.json` pointer per channel.
- HTTP behavior contract: correct content type, `Content-Length`, `ETag`, optional `Accept-Ranges`, strict CORS for the native downloader, immutable cache headers on hashed packs, short revalidation on pointers, real 404s.
- Pipeline stage gates emit auditable records (who approved, what digest, when promoted) forming the signing audit trail.
- Operational alerts route to defined owners with documented retry/backoff and outage guidance.

### Failure and recovery behavior

- Any stage failure before pointer promotion leaves clients untouched (they never see the new pack); the pointer is always the last artifact to change (FR-9).
- Canary failure from the production URL halts promotion automatically.
- Bad-catalog incident: halt promotion, repoint `latest.json` to a still-safe higher-sequence corrective pack (or execute the exceptional signed lower-sequence authorization), publish the support-site notice, preserve evidence, identify affected catalog sequences without user tracking.
- Compromised pack/key response is runbook-scripted: freeze publishing, revoke per `DOS-M08-005`, corrective release path.
- Host outage: installed apps remain fully usable with their active local pack; the pipeline queues promotion until the origin is healthy.

### Security and privacy

- No secret keys in Netlify, the repository, or CI logs; signing is protected/offline with two-person stable confirmation (FR-4).
- An unapproved digest cannot be signed; an immutable digest path cannot be overwritten; controls enforce both (AC-3).
- Strict CORS limited to the native downloader's needs; no wildcard exposure beyond necessity.
- Operational metrics come from host logs only, without ingesting application profile data; incident identification of affected sequences works without user tracking (FR-13, AC-4).

### Accessibility and performance

- Pack and pointer delivery are CDN-cached static files; immutable caching on hashed packs and short revalidation on pointers keep client checks cheap and rollback-fast.
- The support-site catalog disable notice must meet the static site's existing accessibility standards.
- N/A otherwise — no interactive product UI in this issue.

### Data change specifics

- Source/version/license: every pack embeds source snapshot IDs/dates/URLs/licenses and the transformation-pipeline/source commit in its manifest (`DOS-M08-005` FR-2); the license/provenance validator blocks packs whose sources lack a permitted-redistribution disposition in the source register (master prompt §4.4).
- Mapping: locked transform code maps pinned raw snapshots to the frozen `CatalogRepo` schema; no ad hoc edits to the built SQLite are permitted.
- Stable keys: catalog stable IDs/`configuration_key` values persist across releases so client vehicle references survive updates; the diff review flags key churn as an anomaly.
- Constraints/indexes: the built catalog must pass the SQLite schema allowlist, integrity, and foreign-key checks from `DOS-M08-005` before signing.
- Idempotency: re-running the pipeline on identical inputs yields identical pack bytes (FR-2) and is safe at every stage; publishing an already-published digest is a no-op, never an overwrite.
- Rejected-row policy: validator-rejected rows are reported per master prompt §8 (rejected-row reports, collisions), reviewed in the approval stage, and never silently dropped into a shipped pack.
- Checksums: SHA-256 for the artifact and per-table logical digests in the manifest; the production canary re-verifies hash and signature from the served URL.
- Coverage report: row/add/change/remove coverage compared to the prior release with thresholds; unexplained anomalies fail the build (FR-1).
- Fixture strategy: pipeline tests run against `DOS-M08-005` test vectors plus miniature source snapshots producing known-good packs; preview channels rehearse promotion end to end.
- Update cadence: releases are event-driven by reviewed source snapshot updates, not scheduled; each release is a new monotonic sequence per channel.
- Rollback/recovery: pointer repoint to a safe higher sequence as the normal path; exceptional signed lower-sequence authorization; retention inventory guarantees every referenced pack stays fetchable for the published support window.

## Test plan

### Automated

- Reproducibility test: two clean builds from identical pinned inputs produce identical pack bytes (or an isolated, documented signed-metadata delta with identical content digest).
- Validator tests: source/license/provenance and semantic validators against seeded good/bad fixtures; coverage-threshold anomaly detection.
- Netlify deploy checks: headers, CORS, content type, `ETag`, immutable caching, pointer revalidation, and 404 behavior probed automatically post-deploy.
- Control tests: pointer-before-pack, digest-path overwrite, unapproved-digest signing, and key-exposure attempts all fail (AC-3).
- Canary verification: scripted fetch/hash/signature/reference-verify from the production URL gating pointer promotion.

### Manual/device matrix

- Full release rehearsal on a preview/beta channel: build → validate → diff review → approve → sign (two-person for stable rehearsed) → publish → canary → promote.
- Bad-catalog incident tabletop plus a live rehearsal of halt/repoint/notice/evidence steps (AC-4).
- Key-compromise tabletop against the `DOS-M08-005` revocation design.
- Native-device fetch check: a physical iOS and Android device fetches pack and pointer through the production CDN path with expected headers (coordinates with `DOS-M08-007` device evidence).

## Rollout and rollback

- The pipeline itself rolls out through preview/beta channels first; stable channel activates only after a full rehearsal and control-test pass.
- Release rollback: repoint `latest.json` to a still-safe higher-sequence corrective pack; cryptographic lower-sequence rollback only via the `DOS-M08-005` exceptional authorization.
- Every referenced pack is retained for the support window; garbage collection is blocked while installed clients may need a pack.
- Pipeline-defect rollback: promotion halts are always safe because clients keep their prior pack (FR-9 continuity).

## Dependency rationale

- `DOS-M08-005` (blocker): the pipeline produces, signs, and verifies packs strictly per that approved contract and uses its reference verifier for canary checks.
- Source ingestion/normalization pipeline (prerequisite capability): supplies the pinned snapshots and deterministic catalog build this issue packages; without it there is nothing valid to publish.
- `DOS-M07-007` (blocker): the Netlify site and release controls being extended are established there.
- Blocks `DOS-M08-007` and the catalog-update launch: the client updater needs real published artifacts, headers, and pointers to verify against, and launch requires the operational runbooks proven here.

## Risks, decisions, and open questions

- Risk: nondeterministic build inputs (timestamps, locale, SQLite version drift) break reproducibility; mitigated by clean-environment builds, pinned toolchains, SBOM/tool versions, and the two-build check.
- Risk: CDN/header misconfiguration (SPA fallback, HTML 404s) breaks client verification; mitigated by automated post-deploy probes (AC-2).
- Risk: retention failure strands slow-updating clients; mitigated by the inventory and GC guard (AC-7).
- Decision: published support window length for referenced packs — set with product/release review in this issue.
- Decision: coverage-anomaly thresholds for the diff gate — set from prior-release baselines and documented.
- Open question: exact hosting of the protected/offline signing step (hardware/system) — resolved within the key-custody constraints of `DOS-M08-005`, never Netlify or CI.
