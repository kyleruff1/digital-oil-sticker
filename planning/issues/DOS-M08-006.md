> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Content-addressed immutable publish, canary verification, and pointer rollback survive as concepts but target the Fly catalog release channel; Netlify retains only static content._

## Outcome

A controlled release channel turns pinned raw-source snapshots and locked transform code into a reproducible, validated, read-only `catalog.sqlite3` build artifact; bakes that artifact — bit-for-bit and content-addressed by its SHA-256 — into a **signed and attested OCI container image**; deploys that image to a **preview Fly.io application** for automated canary verification against the reference verifier from `DOS-M08-005`; promotes the exact same image digest to the **production Fly.io application** on approval; and rolls back by redeploying a **previously recorded immutable Fly release identifier** rather than by any pointer flip or file move. The Netlify hostnames (`help.` and `legal.` per [ADR-0004 §"ADR-0002 → Amended"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#adr-0002--amended) and [INV-27](../../docs/product/CONSTITUTION.md)) retain only static marketing, support, privacy, and source-attribution content and never publish or reference catalog packs, `latest.json` pointers, or any client-fetched artifact.

Three properties survive from the pre-pivot spec and are load-bearing here:

1. **Content-addressed immutability.** The catalog artifact is identified by the SHA-256 of its bytes; two builds from identical pinned inputs produce identical bytes; the rescoped mechanism is the artifact's presence inside a specific signed OCI image at a recorded layer digest, whose deploy is stamped with an immutable Fly release identifier.
2. **Canary verification is prerequisite to promotion.** Nothing reaches the production Fly application until the reference verifier from `DOS-M08-005` runs against a preview Fly application serving that exact image and passes on the served catalog bytes.
3. **Rollback is by redeploying a known-good release identifier**, not by mutating a pointer.

Three properties are **retired** because the transport they described no longer exists:

- The Netlify-published `.dospack` at content-addressed URLs (pre-pivot FR-6).
- The signed `latest.json` channel pointer and its "publish pack first, promote pointer last" ordering (pre-pivot FR-9 and FR-11).
- The HTTP header/CORS/`Content-Length`/`ETag`/`Accept-Ranges`/immutable-cache/short-revalidation contract on `/catalogs/` paths (pre-pivot FR-7 and FR-8).

## Why this matters and what it unblocks

Under [ADR-0004 §"Catalog database on Fly"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#catalog-database-on-fly), the catalog is a read-only SQLite database file **baked into the Fly deploy image**, opened read-only at boot, queried in-process by the hosted Phoenix LiveView application, and **replaced only by a deploy**. That single architectural fact rewrites every catalog-operations question this card answers:

- The "publish" verb means "produce an OCI image whose bundled catalog is bit-identical to a validated build, sign it, attest to its provenance, push it to a container registry the Fly deploy target can pull from, and record the deploy's immutable Fly release identifier in the release ledger."
- The "signed pointer promotion" concept collapses. A browser-first client has no pointer to poll. The system of record for "which catalog is live" is the currently-deployed Fly release identifier for the production application.
- "Canary verification" becomes "canary Fly deployment": the same immutable image is deployed to a preview Fly application first, the reference verifier runs against it, and only on green is the same image digest promoted to production.
- "Rollback" becomes "redeploy a previously recorded release identifier." No pointer flip, no `.dospack` retention window, no ambiguity about which pack "is" the latest.

**Downstream and sibling cards unblocked or coordinated:**

- [`DOS-M07-005`](DOS-M07-005.md) (rescoped: signed and attested container images) is the CI/release-gate this card publishes through; the signing scheme, attestation shape, release-ledger structure, and rollback definition are shared.
- [`DOS-M07-007`](DOS-M07-007.md) (rescoped: staged Fly deploys, custom-domain cutover, canary smoke checks, monitoring, rehearsed rollback) is the release-cutover surface for the *application*; this card is the release-cutover surface for the *catalog artifact*. The two must share the release ledger and the rollback procedure.
- [`DOS-M09-005`](DOS-M09-005.md) (read-only server-side catalog query layer) is the sole runtime reader; the canary verification includes a query-layer smoke against the preview Fly app.
- [`DOS-M09-006`](DOS-M09-006.md) (Fly.io deploy pipeline, release provenance, rollback) owns the general Fly deploy pipeline this card extends.
- [`DOS-M09-008`](DOS-M09-008.md) sets the log-redaction and secret-handling rules the release ledger and canary logs must respect.
- [`DOS-M03-001`](DOS-M03-001.md) (source-rights matrix for hosted serving) is a hard upstream gate — a source flipped to `pending` or lacking `web_serving: true` MUST fail the Fly deploy image build.
- [`DOS-M08-005`](DOS-M08-005.md) survives as the source of the canonical serialization rules, SQLite schema allowlist checks, per-table logical digests, and the independent reference verifier this card runs at canary time.
- [`DOS-M08-007`](DOS-M08-007.md) (offline native client updater) is **deferred**; this card does **not** unblock it and MUST NOT produce artifacts intended for a client-side updater.

## Included

- A GitHub Actions release-channel workflow — separate from the ordinary application-release workflow — that consumes immutable raw-source snapshots and locked transform code and produces a reproducible, validated, read-only `catalog.sqlite3` in a clean environment, running source/license/provenance and semantic validators and coverage diffing.
- A two-build reproducibility check: two clean builds from identical pinned inputs produce byte-identical `catalog.sqlite3` files. Required job, not advisory.
- Attachment of the source manifest, validation report, data diff, sample query results, license inventory, SBOM/tool versions, and the artifact SHA-256 (with the `DOS-M08-005` manifest bytes) to a **GitHub catalog release** whose tag names the catalog `data_version` and channel.
- Reuse of the `DOS-M07-005` FR-5 container signing and attestation scheme: bake the validated `catalog.sqlite3` into an OCI image built by a protected release workflow, sign the image using cosign or equivalent OIDC-based scheme, and produce build-provenance and SBOM attestations. The image includes the catalog SHA-256 as an image label.
- A **preview Fly application** (distinct app in region `ord`) reserved for canary deploys. The image is deployed to the preview app first, and the reference verifier runs against the catalog bytes as extracted from the deployed image **and** against a `DOS-M09-005` scripted read. Verification failure aborts promotion.
- Promotion to production Fly (`digitaloilsticker.com`) by redeploying the **exact same image digest** — never a rebuild — recording the resulting immutable Fly release identifier in the release ledger.
- A **rollback procedure** that is exclusively "redeploy a previously recorded Fly release identifier from the release ledger"; the immediately prior known-good identifier is the default target.
- A **retention policy**: every image whose Fly release identifier has ever been recorded as production or preview is retained for the published support window plus a two-release rolling headroom. Garbage collection is blocked while a still-recorded release identifier references the image.
- A **release/incident runbook** covering canary halt, rollback, bad-catalog notice (published on the Netlify `help.` static site, copy owned by the M02 content contract), key/signer compromise response, and honest recovery boundaries.
- **Operational checks** driven by Fly and the release ledger, not by ingesting user activity.
- Alert-owner mapping and retry/backoff guidance for canary failure, registry unavailability, and Fly deploy failure.
- **A ratified boundary rule** that Netlify hostnames do not serve catalog packs, catalog manifests, `latest.json`, or any URL under a `/catalogs/` prefix. Serving catalog content from Netlify is an INV-27 breach this card asserts against in CI.

## Excluded

- Any Netlify-published catalog artifact: no `.dospack`, no `latest.json`, no `/catalogs/` path, no HTTP header/CORS contract on such paths. **Retired with the pre-pivot spec.** Netlify is INV-27 static-only.
- Any client-side updater. The client is a browser and reads the catalog through server-rendered LiveView responses (INV-26). `DOS-M08-007` is deferred and this card does not stand in for it.
- Native-device fetch evidence. Retired: there is no CDN pack fetch to evidence.
- A signed `latest.json` channel pointer of any form. Retired: the browser-first client has nothing to poll.
- A CDN, second registry, or Netlify redirect layer in front of the catalog artifact.
- Public visibility of the container registry, unless the licensing review has cleared the bundled catalog contents for that distribution mode.
- User/profile endpoints (INV-3).
- Server-side search or bulk-download catalog endpoints. The read path is the `DOS-M09-005` query layer, which is per-request and never bulk.
- Unsigned hotfix files of any kind. A production catalog change is a signed, attested image deploy or it does not happen.
- Secret keys in Netlify, in the repository, in CI logs, in image layers, or in the release ledger.
- Client code updates (owned by [`DOS-M07-005`](DOS-M07-005.md), [`DOS-M07-007`](DOS-M07-007.md), [`DOS-M09-006`](DOS-M09-006.md)).
- PWA/service-worker offline gating or Web Push (deferred; [`DOS-M09-010`](DOS-M09-010.md)).

## Functional requirements

- **FR-1.** The release-channel workflow consumes immutable raw-source snapshots/digests and locked transform code, creates the normalized read-only `catalog.sqlite3` in a clean environment, runs source/license/provenance and semantic validators, compares row/add/change/remove coverage to the prior catalog release, and fails on unexplained threshold anomalies. Coverage thresholds are documented alongside the workflow.
- **FR-2.** Two clean builds from identical pinned inputs produce byte-identical `catalog.sqlite3` files. An unavoidable signed metadata delta (e.g., a `PRAGMA user_version` timestamp) must be isolated so the reproducible content digest is unchanged. The reproducibility job is a required release-channel status check.
- **FR-3.** A GitHub catalog release for the run attaches the source manifest, validation report, data diff, sample query results, licenses, SBOM/tool versions, `catalog.sqlite3` SHA-256, and the `DOS-M08-005` canonical manifest bytes and detached signature. The release tag names the catalog `data_version` and channel (e.g., `catalog/2026-08-01/stable`).
- **FR-4.** Separation of duties across build, approval, and signing is preserved. The build role produces the validated `catalog.sqlite3` and the GitHub catalog release evidence. The approval role marks the release approved-for-promotion. The signing role — the release workflow's OIDC identity acting under the [`DOS-M07-005`](DOS-M07-005.md) FR-5 scheme — signs the OCI image and produces the build-provenance and SBOM attestations. Two-person confirmation is required for a stable-channel image promotion, recorded as an approving reviewer plus a distinct promoter identity in the release ledger.
- **FR-5.** The reference verifier from `DOS-M08-005` runs against the built `catalog.sqlite3` in CI **and** against the catalog bytes as extracted from the signed image deployed to the preview Fly app **and** against a scripted read via the `DOS-M09-005` query layer on the preview app. Only images whose canary passes all three checks are eligible for promotion.
- **FR-6.** The catalog artifact is content-addressed by the SHA-256 of its bytes, and that SHA-256 is a required image label on the signed OCI image (`org.digitaloilsticker.catalog.sha256`) and a required field in the release-ledger entry. **The pre-pivot mechanism of publishing `.dospack` at `/catalogs/<channel>/<sequence>/<sha256>.dospack` on Netlify is retired**: no route serves the catalog artifact as a client-fetched pack. Immutability is enforced by "the artifact is inside a specific signed image whose deploy is stamped by an immutable Fly release identifier" — not by a URL naming convention.
- **FR-7.** **The pre-pivot HTTP behavior contract for `/catalogs/` paths is retired**: no such path exists in the rescoped architecture. The HTTP contract that matters instead is the hosted-transport contract owned by [`DOS-M09-008`](DOS-M09-008.md) applied to the LiveView pages that render catalog results. This card asserts, as a CI check, that no route is provisioned under a `/catalogs/` prefix at all.
- **FR-8.** **The pre-pivot promotion order "pack first → canary → publish signed `latest.json` last" is retired**: a browser client has no pointer to poll. The rescoped promotion order is: (a) build and validate `catalog.sqlite3`; (b) build, sign, and attest the OCI image; (c) deploy to the preview Fly app; (d) run the reference verifier and query-layer smoke against the preview; (e) on green and on two-person approval, redeploy the **exact same image digest** to production; (f) record the resulting immutable Fly release identifier. The single source of truth for "which catalog is live" is the production Fly release identifier.
- **FR-9.** **The pre-pivot rollback of "repoint `latest.json`" is retired**. The rescoped rollback is: **redeploy a previously recorded Fly release identifier for the production app**, drawn from the release ledger. The default target is the immediately prior production release identifier. Anti-rollback discipline continues to bind via the `DOS-M08-005` catalog `sequence`/anti-rollback rule; a redeploy whose bundled catalog sequence is lower than the highest-ever-successfully-promoted stable sequence requires the exceptional signed lower-sequence authorization from `DOS-M08-005` FR-10, recorded in the ledger entry.
- **FR-10.** Pre-pivot FR-10 stated that Netlify is a static artifact origin only. **The static-only rule survives** but its scope moves to the marketing/support/privacy/attribution hostnames only; re-asserted at a broader scope in FR-16.
- **FR-11.** Every OCI image whose Fly release identifier has ever been recorded as production or preview is preserved in the container registry for the published support window, with a two-release rolling headroom for rehearsed rollback. Registry garbage collection is blocked while a release identifier that references the image is still recorded as production, previous production, or a scheduled canary rehearsal. A published retention inventory maps each retained image digest to its channel, catalog `data_version`, catalog SHA-256, and referring Fly release identifiers.
- **FR-12.** Operational checks monitor: (a) the current production Fly release identifier equals the intended one; (b) the image serving traffic exposes the intended `org.digitaloilsticker.catalog.sha256` label; (c) TLS/certificate healthy for `digitaloilsticker.com` and `www`; (d) the release-ledger append log is intact; (e) the preview Fly app is either idle or running an approved canary image. These checks read Fly and CI signal only and do not ingest user activity.
- **FR-13.** Alert owners, retry/backoff guidance, host outage behavior, compromised image/signer response, and the catalog-disable notice on the static support site (`help.digitaloilsticker.com`) are documented in the release/incident runbook. The static notice copy is owned by the M02 content contract; this card owns the escalation and posting procedure.
- **FR-14.** The catalog-release workflow signs and attests images under the same OIDC-based scheme, key custody, and CODEOWNERS rules as [`DOS-M07-005`](DOS-M07-005.md) FR-5, and records deploys in the same release ledger as that card's FR-9. There is exactly one release ledger, one signer identity family, and one immutable-release-identifier concept across application and catalog cadences.
- **FR-15.** A preview Fly application dedicated to catalog-release canaries exists in region `ord`, sized identically to production, configured with the same `runtime.exs`, `PHX_HOST` (a stable preview hostname such as `catalog-preview.internal`), Endpoint URL configuration, and security posture, and covered by the same log-redaction rules. The preview app is **not** a certificate subject for `digitaloilsticker.com`, is **not** in the production `check_origin` allowlist, and is `noindex`. Access is restricted to the release workflow and on-call operators.
- **FR-16.** A CI check asserts: (a) no route in the application router matches a `/catalogs/` prefix, an `/api/catalogs/` prefix, or any client-facing catalog-pack path; (b) the Netlify site configuration for `help.` and `legal.` publishes no file under a `/catalogs/` prefix and no `latest.json` at any path; (c) the release-channel workflow does not push artifacts to any Netlify hostname. This is the machine-checkable form of the INV-27 boundary as it applies to the catalog artifact.
- **FR-17.** Secret keys — cosign private key, Fly deploy token, registry push token, source-acquisition credentials — are never present in Netlify configuration, in the repository, in CI logs, in image layers, in the release ledger, in the SBOM, or in any canary log. Secret scanning covers the release-channel workflow definition, the release ledger, the SBOM archive, and the produced image layers. Runtime image contents hold **no** third-party API keys.
- **FR-18.** The release ledger entry for a catalog-release deploy records: source commit SHA of the release-channel workflow run; the built `catalog.sqlite3` SHA-256; the canonical manifest SHA-256 and detached signature transcript; the OCI image digest; the signature and attestation verification transcript; the immutable Fly release identifier (release digest and machine image digest) for the preview canary deploy and for the production promotion; the approving reviewer identity and the distinct promoter identity for stable-channel promotions; target application name and region (`ord`); ISO-8601 timestamp. The ledger is append-only and version-controlled.

## Technical implementation contract

### Components and ownership boundaries

- **GitHub Actions release-channel workflow** (this card): Release/DevOps + Data; consumes M03 outputs; produces the validated `catalog.sqlite3` and triggers the signed-image build.
- **OCI image build/sign/attest scheme** (`DOS-M07-005` FR-5): reused under the same signer identity and CODEOWNERS rules; MUST NOT fork a parallel signing scheme.
- **Preview Fly application** (this card): Release/DevOps; provisioned via the same `DOS-M09-006` pipeline with a distinct `fly.toml` app name and non-production hostname; log-redaction inherits from `DOS-M09-008`.
- **Production Fly application** (`DOS-M09-006`): this card only *promotes to* it by redeploying an approved image digest.
- **Reference verifier** (`DOS-M08-005`): consumed unchanged at canary time.
- **Release ledger** (`DOS-M07-005` FR-9): this card extends its entry schema per FR-18 and appends catalog-release entries; append-only invariant and canonical location are shared.
- **Retention inventory** (this card): versioned mapping of retained image digest to channel, catalog `data_version`, catalog SHA-256, and referring Fly release identifiers.
- **Release/incident runbook** (this card): Release Engineering; static-notice copy authored by M02 content; escalation and posting procedure authored here.
- **Netlify site controls** (`help.` / `legal.`): consumed at INV-27 assertion time only; this card does not publish to them.

### Data and persistence

- **Build inputs:** immutable raw-source snapshots with digests, locked transform code at a pinned commit, prior-release manifest for diffing.
- **Build outputs:** validated `catalog.sqlite3`, its canonical manifest and detached signature, validation report, data diff, sample query results, license inventory, SBOM/tool versions — all attached to the GitHub catalog release.
- **Runtime state on Fly:** the bundled read-only `catalog.sqlite3` inside the deploy image, opened read-only by `CatalogRepo` on boot. No persistent volume, no writable path, no per-machine state to reconcile.
- **Release ledger state:** append-only entries per FR-18, shared with `DOS-M07-005`. Entries are the system of record for "which catalog is live."
- **Retention inventory state:** the mapping described under FR-11.
- **No personal data at any layer.** The release-channel workflow, the preview app, the canary, and the release ledger MUST NOT ingest, log, or persist any value that could correlate to a user.

### Interfaces and events

- **Publish interface to the runtime read path** is the read-only `catalog.sqlite3` bundled in the current production Fly image, queried in-process by `CatalogRepo`, exposed to LiveView through the `DOS-M09-005` query layer with no bulk endpoint.
- **Publish interface to operators** is the GitHub catalog release (evidence bundle) plus the release ledger.
- **Deploy interface to Fly** is the `DOS-M09-006` deploy step, invoked once against the preview app with the newly built image and once against production with the same image digest after canary and approval.
- **Verification interface** is the `DOS-M08-005` reference verifier plus a `DOS-M09-005` scripted read on the preview app; both are gates on promotion.
- **CI events:** workflow start, build complete, validation complete, reproducibility check complete, image signed/attested, canary deployed/verified, approved for promotion (with reviewer and promoter identities), promoted (with the immutable Fly release identifier).
- **Operational alerts** route to the FR-13 alert-owner map with documented retry/backoff and outage guidance.

### Failure and recovery behavior

- **Any stage failure before promotion leaves the production Fly app untouched** — no production release identifier is recorded, no image serves user traffic. FR-9 continuity property: aborted releases are no-ops for users.
- **Canary failure** on the preview Fly app halts promotion automatically. The failure classification, halting reviewer/promoter, failing check, and failing image digest are recorded in the ledger as a `canary_failed` entry.
- **Bad-catalog incident**: halt further promotion; redeploy the immediately prior production Fly release identifier; post the incident notice on `help.digitaloilsticker.com`; preserve evidence; identify affected catalog `data_version`s from the ledger without user tracking. A corrective target lower than the highest-promoted stable sequence requires the `DOS-M08-005` FR-10 exceptional signed lower-sequence authorization.
- **Compromised image or signer response** is runbook-scripted: freeze the workflow (revoke the deploy-scoped Fly token and registry push token; rotate the OIDC trusted signer identity); redeploy a known-good image whose signer pre-dates the compromise; issue a corrective release once the signer path is restored.
- **Host outage** (Fly region `ord` unreachable): production is down for the duration; browser MVP has no local pack fallback. This is an application-availability concern handled by [`DOS-M07-007`](DOS-M07-007.md), not by this card.
- **Registry unavailability** during promotion: promotion halts; current production release identifier remains authoritative; workflow retries with exponential backoff; production is unaffected.
- **Loss of approval evidence** for a proposed release is treated as `pending` and fails closed.

### Security and privacy

- No secret keys in Netlify, the repository, CI logs, image layers, SBOM, or the release ledger. Secret scanning covers workflow, SBOM archive, release ledger, and image layers.
- Signing is protected/offline under separation of duties. The signer identity is the release workflow's OIDC subject (or cosign key custody per `DOS-M07-005` FR-5), never a developer's key.
- An unapproved digest cannot be signed and promoted; an immutable Fly release identifier cannot be overwritten; a promoted image with a mismatched attestation aborts the deploy step. Enforced by pipeline and ledger invariants, not by human discipline.
- Release ledger, canary logs, retention inventory, and operational metrics MUST NOT ingest personal data or query parameters. Log-redaction from `DOS-M09-008` applies to the preview app as much as to production.
- Container registry visibility remains constrained — a public registry is a redistribution decision.

### Accessibility and performance

- The card ships no in-app UI; the only user-visible surface is the static incident notice on `help.digitaloilsticker.com`, whose accessibility is asserted by the M02 content contract.
- Performance targets are inherited: the runtime read path is `DOS-M09-005`'s p95 latency budget on the in-process SQLite reads; the release-channel workflow is bounded by the M03 build cadence.

### Data change specifics

- **Source/version/license:** every produced catalog embeds source snapshot IDs/dates/URLs/licenses and transformation-pipeline commit in its manifest; the `DOS-M03-001` license/provenance validator blocks a release whose sources lack `web_approved` / `web_approved_with_conditions`. Fly deploy image build fails closed.
- **Mapping:** locked transform code maps pinned raw snapshots to the frozen `CatalogRepo` schema; no ad hoc edits, no runtime write path (connection opened read-only).
- **Stable keys:** catalog stable IDs / `configuration_key` values persist across releases so browser-stored references in IndexedDB survive updates; the diff review flags key churn. Unresolvable references surface as INV-11 `unsupported`, never as errors.
- **Constraints/indexes:** the built catalog must pass the `DOS-M08-005` SQLite schema allowlist, integrity, and foreign-key checks before signing.
- **Idempotency:** re-running the workflow on identical inputs yields identical bytes; publishing an already-published catalog SHA-256 as a new image requires re-executing the approval flow.
- **Rejected-row policy:** validator-rejected rows are reported, reviewed in the approval stage, and never silently dropped.
- **Checksums:** SHA-256 for `catalog.sqlite3` and per-table logical digests in the manifest; the canary re-verifies both against bytes extracted from the deployed image and against a scripted `DOS-M09-005` read.
- **Coverage report:** row/add/change/remove coverage vs. prior release; unexplained anomalies fail the build.
- **Fixture strategy:** tests run against `DOS-M08-005` test vectors plus miniature source snapshots; the preview Fly app rehearses promotion end to end at each catalog release.
- **Update cadence:** releases are event-driven by reviewed source snapshot updates; each release produces a new monotonic catalog sequence per channel and a new OCI image digest.
- **Rollback/recovery:** production redeploy of a prior recorded Fly release identifier; exceptional signed lower-sequence authorization gates any redeploy whose sequence is below the highest-promoted stable sequence.

## Rollout and rollback

The release-channel workflow rolls out through preview-channel rehearsal first; stable-channel activation waits until a full rehearsal and the control-test/canary-suite pass. Ordinary release rollback is the production redeploy of the immediately prior recorded Fly release identifier; a cryptographic lower-sequence rollback uses the `DOS-M08-005` exceptional authorization. Every image referenced by a still-recorded release identifier is retained; registry GC is blocked while any release identifier that references it is still on the ledger. Pipeline-defect rollback is always safe because production keeps running on the last successfully promoted release identifier.

## Risks, decisions, and open questions

- **Risk: nondeterministic build inputs** (timestamps, locale, SQLite version drift) break reproducibility; mitigated by clean-environment builds, pinned toolchains, SBOM/tool versions, and the two-build check.
- **Risk: silent divergence between application-release and catalog-release cadences.** Mitigated by sharing FR-14 so every catalog promotion is legible to the same operators. A parallel ledger or signer would be worse than the mixing risk.
- **Risk: registry as single point of failure for rollback.** Mitigated by the retention GC guard and by keeping the retention inventory version-controlled outside the registry.
- **Risk: image size growth.** Recorded per ADR-0004 as an acceptable trigger to revisit the SQLite-in-image decision, not a gate here.
- **Risk: publicly scrapable catalog responses** through `DOS-M09-005`. Mitigated by `DOS-M03-001` FR-12 (no bulk endpoints; per-IP and per-socket rate limits). An unacceptably-scrapable source is `rejected` at the source-rights layer, not served under aspirational rate limits.
- **Risk: rollback SLO ambiguity.** The AC-10 SLO must be a real measurement of Fly deploy time on region `ord`, not a hope.
- **Decision: two release ledgers, or one?** One. A separate catalog ledger would recreate the ambiguity FR-9 exists to close.
- **Decision: preview Fly app configuration.** Sized identically to production; distinct app name and hostname; not a cert subject for `digitaloilsticker.com`; `noindex`; not in the production `check_origin` allowlist.
- **Decision: coverage-anomaly thresholds** for the diff gate — set from prior-release baselines and documented alongside the workflow.
- **Decision: published support window length** for referenced images — set with product/release review.
- **Open question: image size growth trigger for a SQLite-on-volume fallback.** ADR-0004 records the fallback if the catalog outgrows a comfortable image. This card does not commit to a specific size ceiling.
- **Open question: whether a future PWA / service-worker decision** ([`DOS-M09-010`](DOS-M09-010.md)) would require reviving a client-fetched catalog artifact. Not resolved by this card.
