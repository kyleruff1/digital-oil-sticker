> **RESCOPED FOR BROWSER MVP — 2026-08-01.** [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) established the browser-first MVP. This card is retained with the same identity; its Outcome and FRs below are the rescoped spec. The pre-pivot spec is preserved at the bottom under "Superseded pre-pivot spec (historical record)". Disposition per [PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md#issue-by-issue-classification): _Content-addressed immutable publish, canary verification, and pointer rollback survive as concepts but target the Fly catalog release channel; Netlify retains only static content._

## Outcome

A controlled release channel turns pinned raw-source snapshots and locked transform code into a reproducible, validated, read-only `catalog.sqlite3` build artifact; bakes that artifact — bit-for-bit and content-addressed by its SHA-256 — into a **signed and attested OCI container image**; deploys that image to a **preview Fly.io application** for automated canary verification against the reference verifier from `DOS-M08-005`; promotes the exact same image digest to the **production Fly.io application** on approval; and rolls back by redeploying a **previously recorded immutable Fly release identifier** rather than by any pointer flip or file move. The Netlify hostnames (`help.` and `legal.` per [ADR-0004 §"ADR-0002 → Amended"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#adr-0002--amended) and [INV-27](../../docs/product/CONSTITUTION.md)) retain only static marketing, support, privacy, and source-attribution content and never publish or reference catalog packs, `latest.json` pointers, or any client-fetched artifact.

Three properties survive from the pre-pivot spec and are load-bearing here:

1. **Content-addressed immutability.** The catalog artifact is identified by the SHA-256 of its bytes; two builds from identical pinned inputs produce identical bytes; a given SHA-256 is served only by an image whose build attestation binds it. The pre-pivot mechanism was a `/catalogs/<channel>/<sequence>/<sha256>.dospack` URL on Netlify; the rescoped mechanism is the artifact's presence inside a specific signed OCI image at a recorded layer digest, whose deploy is stamped with an immutable Fly release identifier.
2. **Canary verification is prerequisite to promotion.** Nothing reaches the production Fly application until the reference verifier from `DOS-M08-005` runs against a preview Fly application serving that exact image and passes on the served catalog bytes.
3. **Rollback is by redeploying a known-good release identifier**, not by mutating a pointer. This is stronger than a signed `latest.json` flip because there is no separate mutable pointer surface to protect.

Three properties are **retired** because the transport they described no longer exists:

- The Netlify-published `.dospack` at content-addressed URLs (pre-pivot FR-6).
- The signed `latest.json` channel pointer and its "publish pack first, promote pointer last" ordering (pre-pivot FR-9 and FR-11).
- The HTTP header/CORS/`Content-Length`/`ETag`/`Accept-Ranges`/immutable-cache/short-revalidation contract on `/catalogs/` paths (pre-pivot FR-7 and FR-8).

The rescope replaces these with the Fly release-channel equivalents documented under Functional requirements below. Retired items are explicitly acknowledged in FR-6 through FR-9 rather than silently dropped, so a future reader sees the trade — not a hole.

## Why this matters and what it unblocks

Under [ADR-0004 §"Catalog database on Fly"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#catalog-database-on-fly), the catalog is not a downloadable pack that a client-side updater installs — it is a read-only SQLite database file **baked into the Fly deploy image**, opened read-only at boot, queried in-process by the hosted Phoenix LiveView application on every user interaction, and **replaced only by a deploy**. That single architectural fact rewrites every catalog-operations question this card answers:

- The "publish" verb no longer means "make a `.dospack` reachable at a CDN URL." It means "produce an OCI image whose bundled catalog is bit-identical to a validated build, sign it, attest to its provenance, push it to a container registry the Fly deploy target can pull from, and record the deploy's immutable Fly release identifier in the release ledger."
- The "signed pointer promotion" concept collapses. A browser-first client that queries the hosted application has no pointer to poll — there is no client-side updater to redirect. The system of record for "which catalog is live" is the currently-deployed Fly release identifier for the production application, which is authoritative by construction because the application in that release reads the SQLite file that was baked into that release's image.
- "Canary verification" becomes "canary Fly deployment": the same immutable image is deployed to a preview Fly application first, the reference verifier from `DOS-M08-005` runs against the catalog bytes as extracted from that image (and against a live query response from the preview app), and only on green is the same image digest promoted to production.
- "Rollback" becomes "redeploy a previously recorded release identifier" per [ADR-0004 §"Catalog database on Fly"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#catalog-database-on-fly): "Rollback: Redeploy the previous image. The old catalog comes back exactly." No pointer flip, no `.dospack` retention window on Netlify, no ambiguity about which pack "is" the latest — the release ledger owns that fact.

This card converts the surviving concepts (immutability, canary-before-promote, rollback-by-known-good) into the Fly release-channel form and retires the transport-specific requirements that produced signed catalog packs and their pointer.

## Context and source of truth

- [ADR-0004 §"Catalog database on Fly"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#catalog-database-on-fly) — the constitutive statement: the catalog is a read-only SQLite build artifact baked into the Fly deploy image; catalog replacement is a deploy; rollback is redeploying the previous image; backups are the build inputs plus the deterministic pipeline (stronger than a DB dump because reproducible, not merely restorable); zero runtime writers eliminates the single-writer problem; each Fly machine carries its own identical read-only copy. The "Rejected alternatives" section explicitly rejects a Fly volume-hosted SQLite ("swap-and-flip ritual for catalog replacement — all to solve a problem the MVP does not have") and managed Postgres for the catalog, and states that the catalog connection is opened read-only "so decision §4 is enforced by the connection itself, not only by code review".

- [ADR-0004 §"Secrets"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#secrets) — "There are no third-party API keys at runtime. Catalog acquisition (vPIC, FuelEconomy.gov, licensed sources) runs at build time in GitHub Actions, not in the request path"; the CI deploy-scoped Fly token is a repository secret (least privilege, not org-admin); `SECRET_KEY_BASE` rotation does not lose user data (INV-23).

## Included

- A GitHub Actions release-channel workflow — separate from the ordinary application-release workflow — that consumes immutable raw-source snapshots and locked transform code and produces a reproducible, validated, read-only `catalog.sqlite3` in a clean environment. The workflow runs source/license/provenance and semantic validators, compares row/add/change/remove coverage to the prior catalog release, and fails on unexplained threshold anomalies.
- A two-build reproducibility check: two clean builds from identical pinned inputs produce byte-identical `catalog.sqlite3` files (or an isolated, documented `PRAGMA`/metadata delta whose content digest is identical). The check is a required job, not an advisory one.
- Attachment of the source manifest, validation report, data diff, sample query results, license inventory, SBOM/tool versions, and the artifact SHA-256 (and the manifest bytes as produced by `DOS-M08-005`) to a **GitHub catalog release** whose tag names the catalog `data_version` and channel.
- Reuse of the `DOS-M07-005` FR-5 container signing and attestation scheme: the release-channel workflow bakes the validated `catalog.sqlite3` into an OCI image built by a protected release workflow triggered by a reviewed protected tag, signs the image using cosign or an equivalent OIDC-based scheme, and produces two OCI attestations — a build-provenance attestation (source commit, workflow run URL, builder OIDC identity, ISO-8601 timestamp) and an SBOM attestation. The image includes the catalog SHA-256 as an image label so the image digest and the catalog digest are cross-referenced.
- A **preview Fly application** (a distinct Fly app in region `ord`) reserved for canary deploys of catalog-release images. The image is deployed to the preview app first, and the reference verifier from `DOS-M08-005` runs against the catalog bytes as extracted from the deployed image **and** against a scripted read via the `DOS-M09-005` query layer on the preview app. Verification failure aborts promotion.
- Promotion to production Fly (`digitaloilsticker.com`) by redeploying the **exact same image digest** — never a rebuild — and recording the resulting immutable Fly release identifier (release digest and machine image digest) in the release ledger `DOS-M07-005` FR-9 defines.
- A **rollback procedure** that is exclusively "redeploy a previously recorded Fly release identifier from the release ledger" for the production Fly application; the immediately prior known-good identifier is the default target. No pointer flip, no `latest.json` publish, no CDN cache purge.
- A **retention policy** for signed catalog-release images: every image whose Fly release identifier has ever been recorded as production or preview is retained in the registry for the published support window, plus a two-release rolling headroom for rehearsed rollback. Image garbage collection is blocked while a release identifier that references the image is still recorded as production, previous production, or a scheduled canary rehearsal.
- A **release/incident runbook** covering canary halt, rollback, bad-catalog notice (published on the Netlify `help.` static site — copy is owned by the M02 content contract, not this card), key/signer compromise response, and the honest recovery boundaries.
- **Operational checks** driven by Fly and by the release ledger, not by ingesting user activity: the current production Fly release identifier matches the intended one; the image serving traffic exposes the intended catalog SHA-256 label; the preview app is either idle or running an approved canary image; certificates and TLS are healthy; the release-ledger append log is intact.
- Alert-owner mapping and retry/backoff guidance for canary failure, registry unavailability, and Fly deploy failure.
- **A ratified boundary rule** that Netlify hostnames do not serve catalog packs, catalog manifests, `latest.json`, or any URL under a `/catalogs/` prefix. Serving catalog *content* from Netlify is an INV-27 breach that this card asserts against in CI.

## Excluded

- Any Netlify-published catalog artifact: no `.dospack` at a content-addressed URL, no `latest.json` channel pointer, no `/catalogs/<channel>/<sequence>/<sha256>.dospack` path, no HTTP header/CORS/`ETag`/immutable-cache/short-revalidation contract on such paths. **Retired with the pre-pivot spec** — preserved for the historical record only. Netlify is INV-27 static-only per ADR-0004 §"ADR-0002 → Amended".
- Any client-side updater. Under [ADR-0004 §Decision 1](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#decision) the client is a browser and reads the catalog through server-rendered LiveView responses (INV-26). `DOS-M08-007` is deferred and this card does not stand in for it.
- Native-device fetch evidence (iOS/Android through the CDN with expected headers). Retired: there is no CDN pack fetch to evidence, and per [ADR-0004 §"Context → The native gate cannot complete as written"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#context) the physical-device work is retained for the deferred native track only.
- A signed `latest.json` channel pointer of any form. Retired: the browser-first client has nothing to poll (see Outcome and FR-8).
- A CDN, second registry, or Netlify redirect layer in front of the catalog artifact.
- Public visibility of the container registry, unless the licensing review in [ADR-0004 §"ADR-0003 → Unchanged"](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md#adr-0003--unchanged) has cleared the bundled catalog contents for that distribution mode. Registry visibility is a redistribution decision, not a CI convenience decision — mirrors [`DOS-M07-005`](DOS-M07-005.md) Excluded.
- User/profile endpoints (the browser MVP has none — INV-3).
- Server-side search or bulk-download catalog endpoints. The read path is the `DOS-M09-005` query layer, which is per-request and never bulk (INV-26; `DOS-M03-001` FR-12).
- Unsigned hotfix files of any kind. A production catalog change is a signed, attested image deploy or it does not happen.
- Secret keys in Netlify, in the repository, in CI logs, in image layers, or in the release ledger.
- Client code updates (they are ordinary Fly application deploys owned by [`DOS-M07-005`](DOS-M07-005.md), [`DOS-M07-007`](DOS-M07-007.md), [`DOS-M09-006`](DOS-M09-006.md)).
- PWA/service-worker offline gating or Web Push (deferred; [`DOS-M09-010`](DOS-M09-010.md)).

## Functional requirements

Each FR below either replaces a pre-pivot FR that the rescoping invalidated, retains a pre-pivot FR that survives the pivot with the same intent retargeted to Fly, or introduces a new obligation created by ADR-0004. Mapping to the sweep finding is called out inline.

- **FR-1 (retained from pre-pivot FR-1; retargeted to the release-channel workflow on Fly).** The release-channel workflow consumes immutable raw-source snapshots/digests and locked transform code, creates the normalized read-only `catalog.sqlite3` in a clean environment, runs source/license/provenance and semantic validators, compares row/add/change/remove coverage to the prior catalog release, and fails on unexplained threshold anomalies. Coverage thresholds are documented alongside the workflow and are reviewed against the prior release, per pre-pivot decision 2.
- **FR-2 (retained from pre-pivot FR-2; retargeted).** Two clean builds from identical pinned inputs produce byte-identical `catalog.sqlite3` files. An unavoidable signed metadata delta (e.g., a `PRAGMA user_version` timestamp) must be isolated so the reproducible content digest is unchanged; the delta is documented in the workflow's reproducibility report. The reproducibility job is a required release-channel status check, not an advisory one.
- **FR-3 (retained from pre-pivot FR-3; retargeted).** A GitHub catalog release for the run attaches the source manifest, validation report, data diff, sample query results, licenses, SBOM/tool versions, `catalog.sqlite3` SHA-256, and the `DOS-M08-005` canonical manifest bytes and detached signature. The release tag names the catalog `data_version` and channel (e.g., `catalog/2026-08-01/stable`).
- **FR-4 (retained from pre-pivot FR-4; retargeted).** Separation of duties across build, approval, and signing is preserved. The build role produces the validated `catalog.sqlite3` and the GitHub catalog release evidence. The approval role reviews the release evidence and marks the release approved-for-promotion. The signing role — the release workflow's OIDC identity acting under the [`DOS-M07-005`](DOS-M07-005.md) FR-5 scheme — signs the OCI image that bakes the approved `catalog.sqlite3` and produces the build-provenance and SBOM attestations. Two-person confirmation is required for a stable-channel image promotion, recorded as an approving reviewer plus a distinct promoter identity in the release ledger. The `DOS-M08-005` `.dospack` signature is produced from the exact `catalog.sqlite3` bytes and included in the GitHub catalog release evidence so the reference verifier remains an independent oracle.
- **FR-5 (retained from pre-pivot FR-5; retargeted to canary verification against a preview Fly app).** The reference verifier from `DOS-M08-005` runs against the built `catalog.sqlite3` in CI **and** against the catalog bytes as extracted from the signed image deployed to the preview Fly app **and** against a scripted read via the `DOS-M09-005` query layer on the preview app. Only images whose canary passes all three checks are eligible for promotion.
- **FR-6 (replaces pre-pivot FR-6; addresses the sweep finding — retires content-addressed pack paths).** The catalog artifact is content-addressed by the SHA-256 of its bytes, and that SHA-256 is a required image label on the signed OCI image (`org.digitaloilsticker.catalog.sha256`) and a required field in the release-ledger entry. **The pre-pivot mechanism of publishing `.dospack` at `/catalogs/<channel>/<sequence>/<sha256>.dospack` on Netlify is retired**: no Fly application route, no Netlify hostname, and no CDN path serves the catalog artifact as a client-fetched pack. The runtime read path is the in-process `CatalogRepo` query behind the `DOS-M09-005` layer, and immutability is enforced by "the artifact is inside a specific signed image whose deploy is stamped by an immutable Fly release identifier" — not by a URL naming convention.
- **FR-7 (replaces pre-pivot FR-7; addresses the sweep finding — retires the HTTP header/CORS contract on pack paths).** **The pre-pivot HTTP behavior contract for `/catalogs/` paths (content type, `Content-Length`, `ETag`, `Accept-Ranges`, strict CORS for the native downloader, immutable caching on hashed packs, short revalidation on pointers) is retired**: no such path exists in the rescoped architecture. The HTTP contract that matters instead is the hosted-transport contract owned by [`DOS-M09-008`](DOS-M09-008.md) (HTTPS/WSS, CSP, `check_origin`, CSRF, security headers, rate limiting) applied to the LiveView pages that render catalog results. This card only asserts, as a CI check, that no route in the application router and no Netlify path is provisioned under a `/catalogs/` prefix at all.
- **FR-8 (replaces pre-pivot FR-9 and FR-11; addresses the sweep finding — retires `latest.json` pointer promotion).** **The pre-pivot promotion order "pack first → canary → publish signed `latest.json` last" is retired**: there is no signed `latest.json` pointer under browser-first because a browser client that queries the hosted application server-side has no pointer to poll. The rescoped promotion order is: (a) build and validate `catalog.sqlite3`; (b) build, sign, and attest the OCI image that bakes it; (c) deploy the image to the preview Fly app; (d) run the reference verifier and query-layer smoke against the preview app; (e) on green and on two-person approval, redeploy the **exact same image digest** to the production Fly app; (f) record the resulting immutable Fly release identifier in the release ledger. The single source of truth for "which catalog is live" is the production Fly release identifier — there is no pointer file to sign, promote, or fail to promote.
- **FR-9 (replaces pre-pivot FR-11 rollback clause; retargeted).** **The pre-pivot rollback of "repoint `latest.json` to a still-safe higher-sequence corrective pack" is retired**: there is no pointer to repoint. The rescoped rollback is: **redeploy a previously recorded Fly release identifier for the production app**, drawn from the release ledger, whose bundled catalog is the still-safe target. The default target is the immediately prior production release identifier. An anti-rollback discipline continues to bind at the artifact layer via the `DOS-M08-005` catalog `sequence`/anti-rollback rule; a redeploy of an image whose bundled catalog sequence is lower than the highest-ever-successfully-promoted stable sequence requires the exceptional signed lower-sequence authorization defined in `DOS-M08-005` FR-10, recorded in the ledger entry.
- **FR-10 (retired — with acknowledgment).** Pre-pivot FR-10 stated that "Netlify is a static artifact origin only; no functions/endpoints serve catalog logic." **The static-only rule for Netlify survives** (ADR-0004 §"ADR-0002 → Amended"; INV-27), but its scope moves to the marketing/support/privacy/attribution hostnames only, and the "catalog logic" phrase becomes vacuous because Netlify no longer serves catalog anything. Recorded as retired here so the earlier FR number's semantics are not silently re-used, and re-asserted at a broader scope in FR-16.
- **FR-11 (retained from pre-pivot FR-12; retargeted).** Every OCI image whose Fly release identifier has ever been recorded as production or preview is preserved in the container registry for the published support window, with a two-release rolling headroom for rehearsed rollback. Registry garbage collection is blocked while a release identifier that references the image is still recorded as production, previous production, or a scheduled canary rehearsal. A published retention inventory maps each retained image digest to its channel, catalog `data_version`, catalog SHA-256, and the Fly release identifiers that reference it.
- **FR-12 (retained from pre-pivot FR-13; retargeted).** Operational checks monitor: (a) the current production Fly release identifier equals the intended one; (b) the image serving traffic exposes the intended `org.digitaloilsticker.catalog.sha256` label; (c) TLS/certificate healthy for `digitaloilsticker.com` and `www`; (d) the release-ledger append log is intact and its append-only invariant holds; (e) the preview Fly app is either idle or running an approved canary image. These checks read Fly and CI signal only and do not ingest user activity or query parameters (INV-4, INV-26).
- **FR-13 (retained from pre-pivot FR-14; retargeted).** Alert owners, retry/backoff guidance, host outage behavior, compromised image/signer response, and the catalog-disable notice on the static support site (`help.digitaloilsticker.com`) are documented in the release/incident runbook. The static notice copy is owned by the M02 content contract; this card owns the escalation and posting procedure, not the words.
- **FR-14 (new; addresses the sweep-finding sub-action "align with `DOS-M07-005`'s rescope").** The catalog-release workflow signs and attests images under the same OIDC-based scheme, key custody, and CODEOWNERS rules as [`DOS-M07-005`](DOS-M07-005.md) FR-5, and records deploys in the same release ledger as [`DOS-M07-005`](DOS-M07-005.md) FR-9. There is exactly one release ledger, exactly one signer identity family, and exactly one immutable-release-identifier concept across application and catalog cadences. A separate ledger or a separate signer would recreate the ambiguity FR-9 exists to close.
- **FR-15 (new; addresses the sweep-finding sub-action "canary against a preview Fly app").** A preview Fly application dedicated to catalog-release canaries exists in region `ord`, sized identically to production, configured with the same `runtime.exs`, `PHX_HOST` (a stable preview hostname such as `catalog-preview.internal`), Endpoint URL configuration, and security posture as production, and covered by the same log-redaction rules ([`DOS-M09-008`](DOS-M09-008.md)). The preview app is **not** a certificate subject for `digitaloilsticker.com`, is **not** in the `check_origin` allowlist for production ([`DOS-M09-007`](DOS-M09-007.md)), and is `noindex`. Canary access is restricted to the release workflow and to on-call operators; it is never a user-reachable staging surface for the MVP.
- **FR-16 (new).** A CI check asserts: (a) no route in the application router matches a `/catalogs/` prefix, an `/api/catalogs/` prefix, or any client-facing catalog-pack path; (b) the Netlify site configuration for `help.` and `legal.` publishes no file under a `/catalogs/` prefix and no `latest.json` at any path; (c) the release-channel workflow does not push artifacts to any Netlify hostname. This is the machine-checkable form of the INV-27 boundary as it applies to the catalog artifact.
- **FR-17 (new).** Secret keys — cosign private key (if a key-based fallback is used rather than OIDC-keyless), Fly deploy token, registry push token, source-acquisition credentials — are never present in Netlify configuration, in the repository, in CI logs, in image layers, in the release ledger, in the SBOM, or in any canary log. Secret scanning covers the release-channel workflow definition, the release ledger, the SBOM archive, and the produced image layers. Runtime image contents (`ENTRYPOINT`, environment, config) hold **no** third-party API keys because the catalog-acquisition credentials live in the release workflow only (ADR-0004 §"Secrets").
- **FR-18 (new).** The release ledger entry for a catalog-release deploy records: source commit SHA of the release-channel workflow run; the built `catalog.sqlite3` SHA-256; the `DOS-M08-005` canonical manifest SHA-256 and detached signature transcript; the OCI image digest; the signature and attestation verification transcript (cosign command output, transparency-log entry reference where keyless); the immutable Fly release identifier (release digest and machine image digest) for the preview canary deploy; the same for the production promotion deploy; the approving reviewer identity and the distinct promoter identity for stable-channel promotions (FR-4 two-person confirmation); target application name and region (`ord`); ISO-8601 timestamp. The ledger is append-only and version-controlled.

## Technical implementation contract

### Components and ownership boundaries

- **GitHub Actions release-channel workflow** (this card): owned by Release/DevOps jointly with Data; consumes M03 outputs; produces the validated `catalog.sqlite3`, the GitHub catalog release evidence, and triggers the signed-image build.
- **OCI image build/sign/attest scheme** ([`DOS-M07-005`](DOS-M07-005.md) FR-5): owned there; this card *reuses* it under the same signer identity and CODEOWNERS rules, and MUST NOT fork a parallel signing scheme.
- **Preview Fly application** (this card): owned by Release/DevOps; created via the same [`DOS-M09-006`](DOS-M09-006.md) deploy pipeline that provisions production, with a distinct `fly.toml` app name and stable non-production hostname; covered by the same log-redaction rules ([`DOS-M09-008`](DOS-M09-008.md)).
- **Production Fly application** ([`DOS-M09-006`](DOS-M09-006.md)): owned there; this card only *promotes to* it by redeploying an approved image digest.
- **Reference verifier** ([`DOS-M08-005`](DOS-M08-005.md)): owned there; consumed unchanged at canary time. No fork; no relaxation of check ordering.
- **Release ledger** ([`DOS-M07-005`](DOS-M07-005.md) FR-9): owned there; this card extends its entry schema for catalog-release fields per FR-18 and appends catalog-release entries; the append-only invariant and canonical location are shared.
- **Retention inventory** (this card): a versioned document tracking every retained image digest, its channel, catalog `data_version`, catalog SHA-256, and referring Fly release identifiers; consumed by the retention garbage-collection guard.
- **Release/incident runbook** (this card): owned by Release Engineering; the static-notice copy is authored by M02 content; the escalation and posting procedure is authored here.
- **Netlify site controls** (`help.` / `legal.`, [`DOS-M09-006`](DOS-M09-006.md) / [`DOS-M09-007`](DOS-M09-007.md) inheritance): consumed at INV-27 assertion time only; this card does not publish to them.

### Data and persistence

- **Build inputs:** immutable raw-source snapshots with digests, locked transform code at a pinned commit, prior-release manifest for diffing.
- **Build outputs:** the validated `catalog.sqlite3`, its `DOS-M08-005` canonical manifest and detached signature, the validation report, the data diff, sample query results, license inventory, SBOM/tool versions — all attached to the GitHub catalog release (FR-3).
- **Runtime state on Fly:** the bundled read-only `catalog.sqlite3` inside the deploy image, opened read-only by `CatalogRepo` on boot per ADR-0004 §"Catalog database on Fly". There is no persistent volume, no writable path to the catalog, no runtime SQL that could re-introduce a disallowed source, and no per-machine state to reconcile.
- **Release ledger state:** append-only entries per FR-18, shared with [`DOS-M07-005`](DOS-M07-005.md). Entries are the system of record for "which catalog is live."
- **Retention inventory state:** the mapping described under FR-11.
- **No personal data at any layer.** The release-channel workflow, the preview app, the canary, and the release ledger MUST NOT ingest, log, or persist any value that could correlate to a user (INV-3, INV-4, INV-26).

### Interfaces and events

- **Publish interface to the runtime read path** is exactly the ADR-0004 §"Catalog database on Fly" contract: the read-only `catalog.sqlite3` bundled in the current production Fly image, queried in-process by `CatalogRepo`, exposed to LiveView through the [`DOS-M09-005`](DOS-M09-005.md) query layer with no bulk endpoint (INV-26; `DOS-M03-001` FR-12).
- **Publish interface to operators** is the GitHub catalog release (evidence bundle) plus the release ledger (system of record for identifiers and approvals).
- **Deploy interface to Fly** is the general [`DOS-M09-006`](DOS-M09-006.md) deploy step, invoked twice per release: once against the preview app with the newly built image, once against the production app with the same image digest after canary and approval.
- **Verification interface** is the [`DOS-M08-005`](DOS-M08-005.md) reference verifier plus a `DOS-M09-005` scripted read on the preview app; both are gates on promotion (FR-5, FR-8).
- **CI events:** release-channel workflow start, build complete, validation complete, reproducibility check complete, image signed, image attested, canary deployed, canary verified, approved for promotion (recorded with reviewer and promoter identities), promoted (recorded with the immutable Fly release identifier).
- **Operational alerts** route to the FR-13 alert-owner map with documented retry/backoff and outage guidance.

### Failure and recovery behavior

- **Any stage failure before promotion leaves the production Fly app untouched** — no production release identifier is recorded, no image serves user traffic. This is the FR-9 continuity property: because "which catalog is live" is the production release identifier and promotion is the last step, an aborted release is a no-op for users.
- **Canary failure** on the preview Fly app halts promotion automatically. The canary failure classification, the halting reviewer/promoter, the failing check, and the failing image digest are recorded in the ledger as a `canary_failed` entry so a later post-mortem can reconstruct the trace.
- **Bad-catalog incident** (a defect discovered after promotion): halt further promotion; redeploy the immediately prior production Fly release identifier (FR-9); post the incident notice on the `help.digitaloilsticker.com` static site (FR-13); preserve evidence; identify affected catalog `data_version`s from the ledger without user tracking (INV-4, INV-26). If the corrective target is a lower sequence than the highest-ever-successfully-promoted stable sequence, the exceptional signed lower-sequence authorization from `DOS-M08-005` FR-10 is required and recorded.
- **Compromised image or signer response** is runbook-scripted: freeze the release-channel workflow (revoke the deploy-scoped Fly token; revoke the registry push token; if OIDC-keyless, rotate the trusted signer identity); redeploy a known-good image whose signer identity pre-dates the compromise; issue a corrective release once the signer path is restored; the [`DOS-M08-005`](DOS-M08-005.md) revocation design binds for the catalog-signature layer.
- **Host outage** (Fly region `ord` unreachable): production application is down for the duration; there is no client-side pack that installed apps fall back to under browser-first (INV-6 was retired for hosted MVP per ADR-0004 §Consequences). The rescope makes this an application-availability concern rather than a catalog-availability concern; it is handled by [`DOS-M07-007`](DOS-M07-007.md) and by the future two-machine/multi-region decision, not by this card.
- **Registry unavailability** during a scheduled promotion: promotion halts; the current production release identifier remains authoritative; the release-channel workflow retries with exponential backoff per FR-13; production is unaffected.
- **Loss of approval evidence** for a proposed catalog release is treated as `pending` and fails closed; a rollback to an earlier image whose approval evidence is intact is unaffected.

### Security and privacy

- No secret keys in Netlify, in the repository, in CI logs, in the image layers, in the SBOM, or in the release ledger (FR-17). Secret scanning is run against the release-channel workflow, the SBOM archive, the release ledger, and the produced image layers.
- Signing is protected/offline under separation of duties (FR-4). The signer identity is the release workflow's OIDC subject (or the cosign key custody described in [`DOS-M07-005`](DOS-M07-005.md) FR-5), never a developer's key on a developer's machine.
- An unapproved digest cannot be signed and promoted; an immutable Fly release identifier cannot be overwritten (append-only ledger); a promoted image with a mismatched attestation aborts the deploy step in `DOS-M07-005` FR-5 before it reaches production. These are enforced by the pipeline and by the release-ledger invariants, not by human discipline (AC-3).
- The release ledger, canary logs, retention inventory, and operational metrics MUST NOT ingest personal data or query parameters (INV-3, INV-4, INV-26). Log-redaction from [`DOS-M09-008`](DOS-M09-008.md) applies to the preview Fly app as much as to production.
- Container registry visibility remains constrained per Excluded — a public registry is a redistribution decision, not a CI decision.

### Accessibility and performance

- The card ships no in-app UI; the only user-visible surface is the static incident notice on `help.digitaloilsticker.com`, whose accessibility is asserted by the M02 content contract and [`DOS-M09-006`](DOS-M09-006.md) FR-8's third-party-origin prohibition.
- Performance targets are inherited: the runtime read path is `DOS-M09-005`'s p95 latency budget on the in-process SQLite reads, and the release-channel workflow is bounded by the M03 build cadence rather than a user-facing latency.
- The image size is a Fly deploy concern (bounded by the ADR-0004 note that catalog release is a deploy and the image grows with the catalog); a size trigger for revisiting the SQLite-in-image decision is recorded as an open question here, not gated.

### Data change specifics

- **Source/version/license:** every produced catalog embeds source snapshot IDs/dates/URLs/licenses and the transformation-pipeline/source commit in its `DOS-M08-005` manifest; the [`DOS-M03-001`](DOS-M03-001.md) license/provenance validator blocks a release whose sources lack a `web_approved` / `web_approved_with_conditions` disposition in the source register. A Fly deploy image build fails closed on this check (`DOS-M03-001` FR-8, FR-15).
- **Mapping:** locked transform code maps pinned raw snapshots to the frozen `CatalogRepo` schema; no ad hoc edits to the built `catalog.sqlite3` are permitted; no runtime write path exists (the connection is opened read-only per ADR-0004).
- **Stable keys:** catalog stable IDs / `configuration_key` values persist across releases so browser-stored user references in IndexedDB (INV-23) survive updates; the diff review flags key churn as an anomaly (FR-1). References that cannot be resolved after a catalog release are surfaced as INV-11 `unsupported` by [`DOS-M09-005`](DOS-M09-005.md), never as errors.
- **Constraints/indexes:** the built catalog must pass the SQLite schema allowlist, integrity, and foreign-key checks from `DOS-M08-005` before signing.
- **Idempotency:** re-running the release-channel workflow on identical inputs yields identical `catalog.sqlite3` bytes (FR-2); publishing an already-published catalog SHA-256 as a new image is permitted only if the ledger's approval and promotion flow is re-executed — the image is treated as a new artifact for approval purposes even if its bundled catalog matches a prior release.
- **Rejected-row policy:** validator-rejected rows are reported per master prompt §8, reviewed in the approval stage, and never silently dropped.
- **Checksums:** SHA-256 for the `catalog.sqlite3` artifact and per-table logical digests in the `DOS-M08-005` manifest; the canary re-verifies both against the bytes extracted from the deployed image on the preview Fly app, and against a scripted `DOS-M09-005` read.
- **Coverage report:** row/add/change/remove coverage compared to the prior release with thresholds; unexplained anomalies fail the build (FR-1).
- **Fixture strategy:** release-channel tests run against `DOS-M08-005` test vectors plus miniature source snapshots producing known-good `catalog.sqlite3` outputs; the preview Fly app rehearses promotion end to end at each catalog release.
- **Update cadence:** releases are event-driven by reviewed source snapshot updates, not scheduled; each release produces a new monotonic catalog sequence per channel and a new OCI image digest.
- **Rollback/recovery:** production redeploy of a prior recorded Fly release identifier (FR-9); exceptional signed lower-sequence authorization gates any redeploy whose bundled catalog sequence is below the highest-ever-successfully-promoted stable sequence (`DOS-M08-005` FR-10); the retention inventory guarantees every image referenced by a still-recorded release identifier remains pullable for the published support window.

## Rollout and rollback

The release-channel workflow itself rolls out through preview-channel rehearsal against the preview Fly app first; stable-channel activation waits until a full rehearsal and the control-test/canary-suite pass (AC-9). Ordinary catalog release rollback is the production redeploy of the immediately prior recorded Fly release identifier (FR-9, AC-10); a cryptographic lower-sequence rollback uses the [`DOS-M08-005`](DOS-M08-005.md) exceptional authorization and is recorded in the ledger. Every image referenced by a still-recorded Fly release identifier is retained per FR-11; registry garbage collection is blocked while any release identifier that references it is still on the ledger as production, previous production, or a scheduled rehearsal. Pipeline-defect rollback is always safe because production traffic keeps running on the last successfully promoted Fly release identifier — the FR-9 continuity property carries over from the pre-pivot FR-9 continuity guarantee.

## Risks, decisions, and open questions

- **Risk: nondeterministic build inputs** (timestamps, locale, SQLite version drift) break reproducibility; mitigated by clean-environment builds, pinned toolchains, SBOM/tool versions, the two-build check (FR-2), and the pinned base-image digest from [`DOS-M07-005`](DOS-M07-005.md) FR-2.
- **Risk: silent divergence between the application-release cadence and the catalog-release cadence.** Because the catalog is baked into the same image scheme, a catalog release and a code release both produce OCI images going through the same signing/attestation and the same release ledger; sharing FR-14 forces every catalog promotion to be legible to the same operators using the same procedures. The risk is *not* sharing them — a parallel ledger or signer would be worse than the mixing risk.
- **Risk: the container registry becomes a single point of failure for rollback.** Mitigated by the retention garbage-collection guard (FR-11) and by keeping the retention inventory version-controlled outside the registry; a registry migration is a bounded, rehearsed procedure rather than a lost-history event.
- **Risk: image size growth** as the catalog grows. Recorded per ADR-0004 as an acceptable trigger to revisit the SQLite-in-image decision (open question below), not a gate here.
- **Risk: publicly scrapable catalog responses** through `DOS-M09-005` are the new redistribution risk — the pre-pivot risk was a scrapable `.dospack` at a CDN URL. Mitigated by [`DOS-M03-001`](DOS-M03-001.md) FR-12 (no bulk endpoints; per-IP and per-socket rate limits at or below the tightest source cap). Not a legal solution — an unacceptably-scrapable source is `rejected` at the source-rights layer, not served under aspirational rate limits.
- **Risk: rollback SLO ambiguity.** A redeploy of a previous Fly release identifier is bounded by Fly deploy time on region `ord`; the documented SLO for AC-10 must be a real measurement, not a hope.
- **Decision: two release ledgers, or one?** One (FR-14). A separate catalog ledger would recreate the ambiguity FR-9 exists to close and would fragment the operators' mental model. Recorded so a future maintainer does not split them.
- **Decision: preview Fly app configuration.** Sized identically to production; same `runtime.exs`; distinct app name and hostname; not a certificate subject for `digitaloilsticker.com`; `noindex`; not in the production `check_origin` allowlist (FR-15). Recorded so the preview app cannot accidentally become an alternate public origin.
- **Decision: coverage-anomaly thresholds** for the diff gate — set from prior-release baselines and documented alongside the workflow.
- **Decision: published support window length** for referenced images — set with product/release review and reflected in FR-11 retention.
- **Open question: image size growth trigger for a SQLite-on-volume fallback.** ADR-0004 §"Catalog database on Fly → Rejected alternatives" records the fallback (SQLite on a Fly persistent volume) if the catalog outgrows a comfortable image or needs updating without a deploy. This card does not commit to a specific size ceiling; the trigger is a decision recorded in the roadmap ledger when a real measurement warrants it.
- **Open question: whether a future PWA / service-worker decision** ([`DOS-M09-010`](DOS-M09-010.md)) would require reviving a client-fetched catalog artifact and a signed pointer of some form. Recorded so it is not forgotten; not resolved by this card.

### Outcome (pre-pivot)

### Technical implementation contract (pre-pivot)

#### Components and ownership boundaries

- GitHub Actions owns build/validate/diff/preview stages (master prompt §4.3: build and test catalogs in GitHub Actions); Netlify owns only static artifact hosting and pointer serving.
- The protected/offline signing step is outside CI secrets scope and consumes only the approved digest/manifest; two-person confirmation for stable channel.
- Release engineering owns promotion, retention, rollback, and the incident runbook; data engineering owns validators and diff review; roles are distinct per FR-4.
- The reference verifier from `DOS-M08-005` is the canary/verification tool; this issue does not fork or weaken it.

#### Data and persistence (pre-pivot)

- Pipeline inputs: immutable raw-source snapshots with digests, locked transform code at a pinned commit, prior-release manifest for diffing.
- Pipeline outputs: the `.dospack`, its manifest, signatures, validation report, data diff, sample query results, licenses, SBOM/tool versions — attached to the GitHub catalog release (FR-3).
- Netlify state: content-addressed pack paths (immutable) plus per-channel `latest.json` pointers (mutable, signed, canonical).
- A published-artifact inventory tracks every referenced pack, its channel/sequence/digest, and its retention obligation.

#### Interfaces and events (pre-pivot)

- Publishing interface to clients is exactly the `DOS-M08-005` contract: pack bytes at `/catalogs/<channel>/<sequence>/<sha256>.dospack` and the signed canonical `latest.json` pointer per channel.
- HTTP behavior contract: correct content type, `Content-Length`, `ETag`, optional `Accept-Ranges`, strict CORS for the native downloader, immutable cache headers on hashed packs, short revalidation on pointers, real 404s.
- Pipeline stage gates emit auditable records (who approved, what digest, when promoted) forming the signing audit trail.
- Operational alerts route to defined owners with documented retry/backoff and outage guidance.

#### Failure and recovery behavior (pre-pivot)

- Any stage failure before pointer promotion leaves clients untouched (they never see the new pack); the pointer is always the last artifact to change (FR-9).
- Canary failure from the production URL halts promotion automatically.
- Bad-catalog incident: halt promotion, repoint `latest.json` to a still-safe higher-sequence corrective pack (or execute the exceptional signed lower-sequence authorization), publish the support-site notice, preserve evidence, identify affected catalog sequences without user tracking.
- Compromised pack/key response is runbook-scripted: freeze publishing, revoke per `DOS-M08-005`, corrective release path.
- Host outage: installed apps remain fully usable with their active local pack; the pipeline queues promotion until the origin is healthy. *(Retired by the current AC-5 — the browser MVP has no local pack; a Fly outage is an application-availability event.)*

#### Security and privacy (pre-pivot)

- No secret keys in Netlify, the repository, or CI logs; signing is protected/offline with two-person stable confirmation (FR-4).
- An unapproved digest cannot be signed; an immutable digest path cannot be overwritten; controls enforce both (AC-3).
- Strict CORS limited to the native downloader's needs; no wildcard exposure beyond necessity. *(Retired; there is no native downloader.)*
- Operational metrics come from host logs only, without ingesting application profile data; incident identification of affected sequences works without user tracking (FR-13, AC-4).

#### Accessibility and performance (pre-pivot)

- Pack and pointer delivery are CDN-cached static files; immutable caching on hashed packs and short revalidation on pointers keep client checks cheap and rollback-fast. *(Retired; there is no client-fetched pack.)*
- The support-site catalog disable notice must meet the static site's existing accessibility standards.
- N/A otherwise — no interactive product UI in this issue.

#### Data change specifics (pre-pivot)

- Source/version/license: every pack embeds source snapshot IDs/dates/URLs/licenses and the transformation-pipeline/source commit in its manifest (`DOS-M08-005` FR-2); the license/provenance validator blocks packs whose sources lack a permitted-redistribution disposition in the source register (master prompt §4.4).
- Mapping: locked transform code maps pinned raw snapshots to the frozen `CatalogRepo` schema; no ad hoc edits to the built SQLite are permitted.
- Stable keys: catalog stable IDs/`configuration_key` values persist across releases so client vehicle references survive updates; the diff review flags key churn as an anomaly.
- Constraints/indexes: the built catalog must pass the SQLite schema allowlist, integrity, and foreign-key checks from `DOS-M08-005` before signing.
- Idempotency: re-running the pipeline on identical inputs yields identical pack bytes (FR-2) and is safe at every stage; publishing an already-published digest is a no-op, never an overwrite.
- Rejected-row policy: validator-rejected rows are reported per master prompt §8 (rejected-row reports, collisions), reviewed in the approval stage, and never silently dropped into a shipped pack.
- Checksums: SHA-256 for the artifact and per-table logical digests in the manifest; the production canary re-verifies hash and signature from the served URL. *(The "served URL" mechanic is retired; hash/signature verification now runs against the preview Fly app deploy.)*
- Coverage report: row/add/change/remove coverage compared to the prior release with thresholds; unexplained anomalies fail the build (FR-1).
- Fixture strategy: pipeline tests run against `DOS-M08-005` test vectors plus miniature source snapshots producing known-good packs; preview channels rehearse promotion end to end.
- Update cadence: releases are event-driven by reviewed source snapshot updates, not scheduled; each release is a new monotonic sequence per channel.
- Rollback/recovery: pointer repoint to a safe higher sequence as the normal path; exceptional signed lower-sequence authorization; retention inventory guarantees every referenced pack stays fetchable for the published support window. *(Retired by the current FR-9.)*
