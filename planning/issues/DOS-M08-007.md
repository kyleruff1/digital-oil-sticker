## Outcome

The app can discover a signed stable catalog, download it safely to temporary storage, verify every trust/compatibility invariant, atomically switch the catalog read path, migrate user references when allowed, and retain a last-known-good rollback without interrupting offline use.

## Why this matters and what it unblocks

The client activation path is where hostile/corrupt data, disk pressure, app termination, and changed vehicle mappings can damage the experience. It must never mutate the only working catalog in place. This issue completes M08 and establishes the catalog-operations baseline for later incremental/delta updates; it is the final consumer of the `DOS-M08-005` contract and the `DOS-M08-006` published artifacts, and it must respect every multi-vehicle invariant from `DOS-M08-001`/`DOS-M08-003`/`DOS-M08-004`.

## Included

- Manual/optional check policy and network settings (Wi-Fi-only/any-network).
- Pointer verification (`latest.json` signature/product/channel/sequence).
- Bounded download with progress/cancel and an explicit resume decision.
- Full pack verification per `DOS-M08-005` before opening data.
- Saved-vehicle reference preflight and classification.
- Atomic activation with generation semantics.
- Rollback to last-known-good and "Reset catalog" to bundled factory data.
- Storage cleanup with retention guarantees.
- App compatibility handling (min/max app version, schema).
- Update UX (version/size/provenance summary, progress, errors).
- Failure diagnostics with stable redacted reason codes.

## Excluded

- Mandatory startup fetch.
- Profile upload.
- Server search.
- Arbitrary SQL migrations from pack.
- Silent destructive remapping.

## Preconditions

- `DOS-M08-005` is closed: the verifier contract, error codes, anti-rollback policy, and test vectors exist.
- `DOS-M08-006` is closed: production packs, signed pointers, headers, and preview channels exist to test against.
- `DOS-M08-001`, `DOS-M08-003`, and `DOS-M08-004` are closed: vehicle-scoped references, revision-safe forecasts, and reconciliation generations exist so activation can replan safely.

## Functional requirements

- FR-1: The existing catalog always loads first. Update checks are user-initiated initially or an explicitly enabled, infrequent foreground-only preference; never block app boot/dashboard, and never claim a backgrounded BEAM will poll.
- FR-2: Provide a Wi-Fi-only/any-network choice using available native reachability; absence of connectivity is normal, silent for core use, and retriable.
- FR-3: Fetch the small signed channel pointer with bounded timeout/backoff and response-size/content-type limits. Verify its signature/product/channel/sequence before trusting its pack URL, size, or digest.
- FR-4: Restrict downloads to an HTTPS allowlist of the configured Netlify catalog origin and reject redirects to other origins or downgrade to HTTP.
- FR-5: Stream to a private temporary file with a hard byte limit while hashing; never buffer the whole pack in LiveView assigns or BEAM memory.
- FR-6: Show version/size/provenance summary, progress, cancel, and storage-needed errors before and during download.
- FR-7: If resumable range downloads are implemented, bind partial metadata to the exact digest/ETag and restart safely on mismatch; otherwise delete the partial deterministically.
- FR-8: Run the complete `DOS-M08-005` verifier before opening data. Then open the catalog read-only, run integrity/query smoke tests, and preflight every saved vehicle's stable catalog reference.
- FR-9: Classify each saved vehicle reference as exact retained, superseded-with-explicit stable mapping, ambiguous, or removed. Apply only signed deterministic mappings; ambiguous/removed vehicles retain a frozen display/provenance snapshot and require user review rather than silently changing identity/recommendations.
- FR-10: Keep the private user DB and public catalog file separate. Activation writes a catalog-installation row pointing to the verified new file/digest/sequence in one durable transaction/atomic rename boundary, invalidates affected recommendation/forecast plans with revisions, and only then exposes it to new queries.
- FR-11: Existing processes finish or reopen against a consistent catalog generation; no query ever spans two generations.
- FR-12: Retain the last-known-good pack and activation metadata until the new catalog passes cold-start, representative queries, saved-vehicle resolution, and reminder replan.
- FR-13: On boot after interrupted download/verification/activation, clean temp state and choose the last fully committed generation. Never delete the bundled factory catalog.
- FR-14: Allow user rollback to last-known-good only when anti-rollback policy authorizes it; otherwise ship a corrective higher sequence.
- FR-15: "Reset catalog" returns to bundled factory data without deleting vehicle/history, flags mappings needing review, and preserves exportability.
- FR-16: Storage cleanup removes only unreferenced verified/temp pack files after explicit reference checks and keeps at least active + last-known-good + bundled. Disk-full never removes the active pack or user database.
- FR-17: All errors have stable redacted reason codes and Retry/Keep current catalog guidance.
- FR-18: Forecast/reminder recomputation after activation is vehicle-scoped and revision-safe, reusing the `DOS-M08-003` recompute and `DOS-M08-004` reconciliation contracts so a catalog update cannot create a burst of missed notifications.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.DataPacks` owns discovery, download, verification orchestration, activation, generations, rollback, reset, and cleanup; `DigitalOilSticker.Boot` owns startup generation selection and interrupted-state recovery.
- The verifier is the `DOS-M08-005` contract implementation, used unmodified; download networking uses the platform-appropriate HTTP client under the origin allowlist; native reachability flows through the established `DeviceCommandBroker` boundary if a bridge call is required.
- Update UX (settings, summary, progress, errors, review flows) lives in LiveView within the `DOS-M08-002` navigation contract; `DigitalOilSticker.Catalog` continues to serve all reads against the active generation.
- Recompute/replan after activation delegates to `DOS-M08-003` (forecast revisions) and `DOS-M08-004` (reminder reconciliation generation).

### Data and persistence

- Catalog files live in app-owned storage: bundled factory pack (never deleted), active pack, last-known-good pack, and private temporary download/staging files.
- A catalog-installation row records file path/digest/sequence/generation and activation state; it is the single durable switch written in one transaction/atomic rename boundary (FR-10).
- Client trust state per `DOS-M08-005`: highest successfully activated stable sequence (anti-rollback input) persisted in app storage, never inside packs.
- Saved-vehicle preflight results (classification, applied signed mappings, frozen display/provenance snapshots, review flags) are persisted in `UserRepo` so review survives restart; `UserRepo` content is otherwise untouched by updates.
- Partial-download metadata (digest/ETag binding) exists only when resume is implemented; otherwise partials are deleted deterministically (FR-7).

### Interfaces and events

- Settings: manual "Check for updates", optional infrequent foreground-only auto-check preference, Wi-Fi-only/any-network choice.
- Pipeline states exposed to UI: idle → pointer-verified → downloading (progress/cancel) → verifying → preflight review (if needed) → ready → activating → active / failed(reason code).
- `catalog_activated` event (master prompt §7) carries generation/sequence and triggers vehicle-scoped invalidation with revisions; reminder replan flows through the `DOS-M08-004` reconciliation generation.
- All failures map to the stable redacted reason codes of `DOS-M08-005` plus client-side codes (network, storage, compatibility), each with Retry/Keep current catalog guidance (FR-17).

### Failure and recovery behavior

- Offline/no-DNS/timeout/404/HTML response/wrong content type/redirect/partial/tampered/oversized/incompatible/rollback-sequence/disk-full: every scenario leaves the current catalog and all private data usable (AC-1); errors are terminal for that attempt and retriable.
- Process kill at any checkpoint (mid-download, mid-verification, mid-activation): boot cleans temp state and selects the last fully committed generation (FR-13).
- Activation gate: last-known-good is retained until the new catalog passes cold-start, representative queries, saved-vehicle resolution, and reminder replan (FR-12); failure at the gate reverts to the previous generation.
- Disk-full during any phase never removes the active pack or user database; cleanup requires explicit reference checks and honors the minimum retained set (FR-16).
- Concurrent queries during cleanup/activation are safe: a referenced file cannot be deleted while queries may use it, and readers see exactly one generation.

### Security and privacy

- HTTPS-only, origin-allowlisted downloads with redirect and downgrade rejection (FR-4); bounded response sizes and content-type checks on the pointer (FR-3).
- The complete `DOS-M08-005` verification order runs before any data is opened; catalog text remains untrusted escaped content.
- No profile upload, no server search, no telemetry; update checks send no user data, and diagnostics use redacted stable reason codes only.
- Private user DB and public catalog remain separate files; no pack-supplied SQL/migration ever runs against `UserRepo` (excluded: arbitrary SQL migrations from pack).

### Accessibility and performance

- Streaming download with a hard byte limit bounds memory; hashing is incremental; verification is staged so hostile inputs fail early (per `DOS-M08-005` ordering).
- Update UI states (progress, errors, review) meet the app's established accessibility bar: text status (not color alone), screen-reader announcements for progress and completion, and focus-safe dialogs.
- Update checks and activation never block boot or dashboard interactivity (FR-1); recompute after activation stays within the foreground budgets from M07.

## UX and content states

- Settings: update check control, optional auto-check preference (foreground-only, infrequent), Wi-Fi-only/any-network choice.
- Pre-download summary: version, size, provenance summary from the verified pointer/manifest.
- Downloading: progress with cancel; storage-needed error state.
- Verifying: indeterminate progress; failures show reason code with Retry/Keep current catalog guidance.
- Preflight review: list of ambiguous/removed vehicles with frozen display/provenance snapshots and explicit review actions; superseded mappings shown with provenance.
- Up to date / update available / offline (normal, silent for core use) states.
- Rollback (when policy authorizes) and "Reset catalog" flows with clear consequences (vehicle/history preserved, mappings flagged for review).
- Post-activation: recommendations/forecasts show new catalog provenance; no recommendation changes without visible provenance/review.

## Test plan

### Automated

- Verifier/malicious-response integration suite: every `DOS-M08-005` rejection class plus client-layer hostility (HTML bodies, wrong content types, cross-origin redirects, HTTP downgrade, oversize streams, slow/stalled responses).
- Fake HTTP server tests and Netlify preview tests exercising pointer verification, allowlist, bounded download, and resume-or-delete behavior.
- Process-kill fault injection at every activation checkpoint (download, verification, preflight, installation-row write, generation switch, cleanup); assert old-or-new-complete-generation invariant.
- Catalog-reference mapping fixtures: exact retained, superseded-with-mapping, ambiguous, removed — each with the specified outcome and review flags.
- Disk-full and concurrent-query tests for cleanup/retention (AC-5).
- Recompute/replan tests proving vehicle-scoped, revision-safe invalidation and a churn-free reminder reconciliation generation after activation.

### Manual/device matrix

- Physical iOS and physical Android: full signed Netlify-pack update end to end, then airplane mode to prove continued offline operation (video evidence).
- Interrupted update (kill during download and during activation) and rollback recovery on both platforms (video evidence).
- Storage-pressure walk-through: fill storage, attempt update, verify guidance and retention invariants.
- Preflight review walk-through with a fixture pack containing superseded/ambiguous/removed references.
- Data and reminder reconciliation spot-check: compare pre/post-activation forecasts and pending notifications on device.

## Rollout and rollback

- Feature ships in a post-MVP release after the catalog channel is live; the first supported flow is user-initiated checks, with the optional auto-check preference default off.
- Client rollback of a catalog: last-known-good restore when anti-rollback policy authorizes it; otherwise the corrective higher-sequence path from `DOS-M08-006`.
- "Reset catalog" is the deepest client-side recovery, returning to bundled factory data with review flags and no user-data loss.
- App-binary rollback is governed by the standard release process; catalog generations and `UserRepo` remain forward-safe because activation never mutates user history.

## Dependency rationale

- `DOS-M08-005` (blocker): the client implements exactly that verification contract, error codes, and anti-rollback policy.
- `DOS-M08-006` (blocker): real signed packs, pointers, headers, and preview channels are required for meaningful client testing and launch.
- `DOS-M08-001` (blocker): saved-vehicle references and garage semantics the preflight classifies are defined there.
- `DOS-M08-003` (blocker): vehicle-scoped, revision-safe recompute is the only safe post-activation invalidation path.
- `DOS-M08-004` (blocker): reminder replan must flow through the global reconciliation generation to avoid missed-notification bursts.
- Completes M08 and establishes the catalog-operations baseline for later incremental/delta updates.

## Risks, decisions, and open questions

- Risk: activation bugs are the highest-consequence client failure (only working catalog); mitigated by never-in-place mutation, staged gates, retained last-known-good, and fault injection at every checkpoint.
- Risk: reference remapping silently changes recommendations; mitigated by signed deterministic mappings only, frozen snapshots, and mandatory review for ambiguous/removed (FR-9, AC-3).
- Risk: platform WebView/BEAM memory limits during download; mitigated by streaming with a hard byte limit and no full-pack buffering (FR-5).
- Decision: implement resumable range downloads or deterministic-delete-and-restart — decided in this issue with the FR-7 binding rules if resume is chosen.
- Decision: exact auto-check frequency bounds for the optional foreground preference.
- Open question: user-visible policy wording for anti-rollback-blocked restores (when only a corrective higher sequence is acceptable) — coordinated with the support-site content from `DOS-M08-006`.
