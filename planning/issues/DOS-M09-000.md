## Outcome

Digital Oil Sticker runs as a hosted browser application whose personal data never touches a server, and the seam between those two facts is an implemented, tested protocol rather than an assumption.

At epic close: the Phoenix LiveView application is served over HTTPS with HSTS and WSS from Fly.io on an owner-controlled domain, with CSRF protection, a Content-Security-Policy that forbids third-party script and connect origins, and zero third-party origins on any page (INV-22, INV-27). The deployed application runs exactly one Ecto repo — `DigitalOilSticker.CatalogRepo`, opened read-only — and contains no personal-data table, no personal-data migration, and no personal-data backup job (INV-3, INV-23). The garage, service history, odometer readings, usage profile, reminder intent, and preferences live in the browser's IndexedDB under a versioned, forward-only schema (INV-23). Hydration, mutation round trips, reconnect re-hydration, first-paint honesty, eviction, quota, private-browsing, multi-tab consistency, and cleared-storage detection are each implemented and each covered by a passing automated or scripted test (INV-24.1 through INV-24.8). Storage-loss messaging is honest and reachable at any time, and an empty-or-evicted store is distinguishable in copy from a genuine first visit (INV-5, INV-25). Catalog queries are served from a read-only server-side query layer that accepts no personal parameter and no stable client identifier (INV-26). Export/import is the sole portability path, produced and consumed entirely client-side (INV-5). The supported browser matrix is named and its storage behaviors are certified. The PWA/service-worker and Web Push questions are closed by a dated written decision rather than by drift (INV-6, INV-17, INV-19).

## Why this matters and what it unblocks

The 2026-08-01 pivot moved the MVP from a signed native package with a bundled database and no server to a hosted application with a public server and a browser-resident user record. The re-classification of the existing 77 issues found nine areas of work with **no owner anywhere in the roadmap** — client-side storage as a designed subsystem, the hydration protocol, pre-hydration and storage-denied UX, a server-side catalog query layer, Fly.io deployment, custom domain and TLS, internet-facing hardening, a browser support matrix and storage-behavior conformance suite, and the PWA/Web Push decision. None of these is a re-scope of an existing issue, because nothing analogous existed. This epic is where that work lives.

The hydration protocol is the single highest-risk new component in the product. Phoenix LiveView keeps UI state on the server; the owner's decision keeps the authoritative personal record on the client. Getting this wrong produces one of exactly two failures, both fatal to the product's promise: a silent server-side personal record, or a UI that loses the user's garage on every reconnect. Closing this epic is what makes the browser MVP releasable at all — the single-vehicle MVP screens, the export/import controls, the forecast presentation, and the hardening and release gate all write against the storage adapter, the hydration events, and the catalog query layer delivered here.

## Included

## Rollout and rollback

Planning-stage epic with no rollout of its own, but unlike earlier milestones its children stand up real production infrastructure, so rollback is per child and must be rehearsed rather than assumed. Sequencing follows FR-3: schema first, then the adapter and the hydration protocol, then the storage-state copy, with the query layer, deploy pipeline, domain, and hardening proceeding in parallel once the foundation exists, then conformance, and the deferred-decision spike last so it can weigh measured eviction behavior rather than documentation. Rollback of unmerged application work is reverting the child commits. Rollback of a deployed release is a redeploy of the previous immutable image, which restores the previous catalog exactly because the catalog is a build artifact rather than mutable state. Client-storage schema changes are the one component with no rollback: a browser upgraded to a newer schema cannot be downgraded, so a rolled-back deployment must enter read-only mode with export offered rather than write a downgrade — that behavior is itself a tested requirement (FR-7, `DOS-M09-001`, `DOS-M09-003`). HSTS is enabled only after certificates are verified and both hostnames serve correctly, because enabling it early is self-inflicted downtime that no rollback undoes quickly.

## Dependency rationale

M09 consumes and is bound by three earlier bodies of work. From **M02** it takes the UX and content contract: the interaction model, the required terminology, the safety-adjacent copy rules, and the accessibility contract that `DOS-M09-004`'s storage-state copy must satisfy rather than restate, and that every rendered state in this epic inherits (INV-20, INV-21). From **M03** it takes the catalog itself: `DOS-M09-005` serves a rights-cleared, normalized, provenance-carrying artifact and adds no automotive fact of its own, so the hosted-serving rights re-review under CHANGE_CONTROL Rule 2b gates which sources this epic may serve at all (INV-15). From **M04** it takes the domain and persistence contracts: the catalog schema and the read-only catalog repository that `DOS-M09-005` queries, and the logical user-record model in `DATA_DICTIONARY.md` that `DOS-M09-001` mirrors in browser terms, since the browser stores must preserve those semantics — vehicle-scoped children, snapshot-plus-stable-key history, integer base units for mileage, UTC instants plus IANA time zone — even though SQL constraints are not available to enforce them.

M09 blocks the browser MVP release. The single-vehicle MVP screens cannot commit a write without the mutation round trip, cannot render a first paint without the hydration states, and cannot resolve a vehicle without the query layer; the hardening and release milestone consumes this epic's transport, logging, and no-personal-record evidence as its gate; and there is no public URL to release at all until the deploy pipeline and domain boundary exist.

One sequencing discrepancy is recorded rather than resolved here. The pivot document proposes that M09 execute **after M01 and before M02, M04, and M05**, on the reasoning that the UX contract cannot be frozen without knowing the hydration and empty-state model — the reverse of the content dependency stated above, which makes the two orderings mutually circular at the milestone level. The circularity is real and is not resolved by an issue body: the interface it turns on is small and nameable (the storage-state vocabulary M09 defines versus the terminology and accessibility contract M02 defines), so it is tractable by splitting the interface rather than the milestone. Resolving it is a change-control action on the roadmap, recorded as an open question below, and the pivot document remains a proposed classification until that action is taken. No child of this epic may be marked Ready on the strength of one ordering while the other is recorded as authoritative.

## Risks, decisions, and open questions

- Risk (ADR-0004 R1, the largest product risk of the pivot): browsers evict script-writable storage for sites a user has not visited recently, and a user who checks their oil once a quarter is exactly that profile. Mitigation: request persistent storage, honest storage-status UI, export nudges after meaningful writes, and a data-missing state so loss is never disguised as an empty garage. Per-browser eviction behavior must be **measured** in `DOS-M09-009`, not assumed from documentation.
- Risk (R2): the hydration round trip adds latency to first meaningful paint on every mount, including every reconnect. Mitigation: an explicit budget in constitution §9 and measurement in `DOS-M09-003`; if hydration is not sub-second on a cold connection the skeleton becomes the dominant impression of the product.
- Risk (R3): the strict CSP is unverified against LiveView's runtime behavior. Mitigation: verify during the deployment work; if a nonce is required, add a nonce plug — a blanket inline relaxation is not an acceptable resolution.
- Risk (R6): hosted-serving rights for licensed catalog sources are unreviewed, because the earlier legal analysis assumed in-bundle redistribution. Mitigation: hard gate — documented-facts and permission-needed sources are not served until the register and checklist are re-reviewed. Public-domain U.S. Government sources are unaffected.
- Risk (R8): single region and a single always-on machine mean a Fly outage is a total product outage, and every deploy drops all sockets. Mitigation: reconnect plus re-hydration must be proven robust enough that a deploy is a non-event; a second machine is a bounded cost decision revisited on real usage.
- Risk (R11): whether users accept a product that does nothing offline and never notifies them is honestly unknown. This is the core bet of the pivot and the primary thing the browser MVP exists to find out.
- Decision (recorded in ADR-0004, ratified here as the epic's baseline): one always-on machine in a single central-US region with scale-to-zero prohibited; the catalog shipped read-only inside the deploy image with no volume and no managed database; export/import as the only recovery path; multi-tab conflict resolution as last-write-wins at record granularity with the loss made visible.
- Open question (owned by `DOS-M09-001`): whether a usage-profile store and any derived-forecast records belong in the client schema at MVP, and how the browser store set maps onto the remaining `DATA_DICTIONARY.md` `UserRepo` tables.
- Open question (owned by `DOS-M09-010`): whether a PWA install path is adopted as the strongest known mitigation for eviction risk, weighed against the offline promise it must not create.
- Open question (owned by change control, per the Dependency rationale): the execution order of M09 relative to M02 and M04, and which slice of the UX contract must be frozen first to break the circularity.
- Open question (ADR-0004 R4): whether any real workflow — two tabs, one logging a service while the other edits it — makes record-granularity last-write-wins materially wrong. Re-examine on evidence rather than pre-emptively.
