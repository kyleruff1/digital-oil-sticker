## Outcome

The anonymous client storage subsystem has a written, versioned, testable design before a single line of it is implemented: an origin-scoped IndexedDB database with named object stores for the garage's vehicles, service events, odometer readings, usage profile, reminder intent, preferences, and store metadata; a documented key and index strategy; two distinct version lines with an explicit relationship between them; a forward-only upgrade contract that is idempotent, never destroys a store holding data, and has no downgrade path; and the compensating machinery that IndexedDB does not provide — read-time integrity checks, defensive validation, record quarantine, and a user-visible repair path. The versioned export/import envelope is specified here as the sole portability and recovery mechanism, with export-only fields separated from the hydration envelope so that no ephemeral value can leak into a file the user keeps.

This is a specification and fixture deliverable. The running adapter, the hydration protocol, and the copy that renders these states are separate issues; this issue is the contract they implement against.

## Why this matters and what it unblocks

This is the schema for every personal record the product will ever hold, and the product holds them in the one place that offers no safety net. IndexedDB has no rollback to a prior schema, no `CHECK` constraints, no `UNIQUE` constraints outside an index, no foreign keys of any kind, and no cross-store referential integrity. The `UserRepo` design it replaces leaned on all five: constraints fired even when a changeset was bypassed, and SQL remained the final invariant boundary. That boundary is gone. If the same guarantees are not re-established deliberately — in the schema shape, in read-time validation, and in a repair path — then the first application bug that writes a malformed record corrupts a user's history permanently, with no server copy to restore from and no migration to undo.

A version line that is wrong is equally unrecoverable. Once a browser's database has been upgraded, it cannot be opened at a lower version, so a bad upgrade step is shipped to every user who loads the page and cannot be recalled by a deploy rollback. That asymmetry is the reason this design is a separate, ratified issue rather than a paragraph inside the adapter ticket.

Closing this issue unblocks `DOS-M09-002` (the adapter implements exactly this open/upgrade/read/write/erase contract), `DOS-M09-003` (the hydration payload is this schema serialized into the envelope, and server-side validation is written against these field types, caps, and referential rules), `DOS-M09-004` (the states it writes copy for are distinguishable only because this schema records enough metadata to tell a first visit from a cleared store), and `DOS-M09-009` (the forward-migration fixtures are the conformance suite's migration cases).

## Included

- Specify the origin-scoped IndexedDB database `dos_local` and its object stores: `meta`, `vehicles`, `events`, `readings`, `usage`, `reminders`, and `prefs`, with each store's key path, key type, indexes, and the record shape it holds.
- Record the mapping from every `DATA_DICTIONARY.md` `UserRepo` table to its browser home, including the tables that deliberately have no store, with the reason stated for each.
- Define the key strategy: client-generated UUIDv4 primary keys for all record stores, singleton fixed keys for `meta` and `prefs`, and a rule that no key is derived from a value the server could see or correlate (INV-3).
- Define the index set that replaces the `UserRepo` deterministic ordering contracts, so history renders in a stable order without a full-store scan.
- Define the two version lines and their relationship: the logical `schema_version` carried in `meta` and in the envelope, owned by the server, and the structural IndexedDB database version, bumped only for object-store or index changes.
- Specify the forward-only upgrade contract: ordered, pure, idempotent upgrade steps; the version-change transaction is all-or-nothing; no upgrade step deletes an object store holding data; a database at a newer logical version than the deployed server puts the session into read-only mode with export offered, never a downgrade write.
- Specify the compensations for IndexedDB's absent constraints: a read-time integrity pass covering type, range, enumeration, uniqueness, singleton-ness, referential linkage, monotonic `seq`, and unknown-field preservation; a quarantine list for records that fail; and a repair path that exports the raw payload before it changes anything and never deletes a record silently.
- Specify the versioned export/import envelope as the sole portability path: the shared hydration envelope plus export-only fields, canonical serialization, a SHA-256 content hash computed over the payload excluding the hash field itself, record counts, and an explicit rule that ephemeral values are omitted from exported files.
- Specify how the schema makes a genuine first visit distinguishable from a cleared, evicted, or blocked store, so that `DOS-M09-004` has something concrete to render (INV-24.4, INV-24.8, INV-25).
- Deliver recorded fixtures: one canonical payload per released logical schema version, a corrupt-record fixture set covering each integrity rule, and a stress fixture sized against the §9 storage budget.
- Record the ADR-0004 addendum obligation for every place this design extends the ADR's storage-layout table or envelope.

## Excluded

- The running adapter module — open, upgrade, read, write, transaction, erase, persistence request, quota estimate, and availability probes — which is `DOS-M09-002`. This issue defines what that module must implement.
- The hydration protocol, event names, server-side changeset modules, socket assigns handling, acknowledgment gating, and multi-tab broadcast implementation, which are `DOS-M09-003`. This issue defines the payload it carries and the compare-and-set field it depends on.
- User-facing copy and screen states for storage loss, quota, private browsing, and eviction, which are `DOS-M09-004`.
- Catalog schema, catalog queries, and any automotive fact. This schema stores stable catalog references plus immutable snapshots and never restates a fact of its own (INV-15).
- Forecast arithmetic and confidence policy. Whether any derived forecast record is persisted at all is an open question below, not a decision this issue makes silently.
- Any credential, email address, password, account identifier, device identifier, or server-derivable storage key anywhere in the schema (INV-3).
- Full VIN storage by default. The schema permits at most a last-six-digit field, nullable and off by default; enabling full VIN requires its own privacy issue covering consent, export, deletion, and logging.
- Scheduled-notification records. OS-scheduled local notifications do not exist in this platform (INV-17), so there is nothing to schedule and nothing to reconcile.
- Service-worker caches, `localStorage` record storage, OPFS, WASM SQLite, and any server-side personal row (INV-19, INV-23).

## Functional requirements

- FR-1: The design names one origin-scoped IndexedDB database, `dos_local`, and exactly these object stores: `meta`, `vehicles`, `events`, `readings`, `usage`, `reminders`, `prefs`. Each store has a documented key path, key type, index list, and record shape. No personal record is held anywhere else — `localStorage` carries only the non-personal boot hint and nothing else (INV-23).
- FR-2: The garage is the logical container realized by the `vehicles` store together with `prefs`, and is multi-vehicle-safe from the first write: every vehicle-scoped record carries a `vehicle_id`, and no singleton "current vehicle" field substitutes for that relationship, so exposing multiple vehicles later is a presentation change and never a data migration (INV-18).
- FR-3: All record primary keys are client-generated UUIDv4 values; `meta` and `prefs` are singletons at fixed literal keys. No key, and no field used as a key, is derived from a value the server transmits, assigns, or could correlate across visits (INV-3).
- FR-4: The design records a complete mapping from each `DATA_DICTIONARY.md` `UserRepo` table to its browser home, including tables that deliberately have no store, each with a stated reason. The mapping preserves the source semantics: vehicle-scoped children, stable catalog reference plus immutable human-readable snapshot on every historical record, integer base units for mileage with conversion at the boundary, UTC instants for exact events plus an IANA time zone in preferences, and a defined canonical rule for date-only capture with no accidental date shifts.
- FR-5: The index set supports the deterministic ordering contracts without a full-store scan: service events by vehicle and performed instant descending with the record identifier as the tiebreaker, odometer readings by vehicle and observed instant descending with the same tiebreaker, usage-profile rows by vehicle and effective-from, and reminder intent by vehicle. Ordering is specified as a contract, not left to insertion order.
- FR-6: Two version lines are defined and their relationship is stated. The **logical schema version** is a single monotonically increasing integer stored in `meta` and carried in the envelope; it is owned by the server and governs record shape. The **structural database version** is IndexedDB's own version; it is bumped only when an object store or index is added or changed. A logical version bump that does not change structure MUST NOT bump the structural version, and every structural bump MUST state which logical versions it is compatible with.
- FR-7: Upgrade steps are ordered, pure, idempotent functions from one logical version to the next, applied in sequence with no step skipped. Re-running a step on an already-upgraded payload produces an identical payload and no write. Every step has a recorded fixture of the version it upgrades from.
- FR-8: The upgrade path is forward-only and has no rollback. The version-change transaction is all-or-nothing: if any step raises, the transaction aborts and the database remains at its prior structural version, unmodified. No upgrade step deletes an object store that holds data, and no step deletes a record it cannot interpret — unrecognized records are preserved verbatim.
- FR-9: A database whose logical schema version is **newer** than the deployed server's puts the session into read-only mode: mutations are disabled, an explicit banner states that this browser holds data from a newer version of the application, and export is offered. Downgrading the payload, dropping unknown fields, or writing at the older version is prohibited.
- FR-10: Records carry unknown fields through unchanged. A field the deployed version does not recognize is preserved verbatim on read, in assigns, on write-back, and in export, so an older deployment never destroys data a newer one wrote.
- FR-11: A read-time integrity pass is specified and runs on every hydration, covering at minimum: required-field presence; type correctness; numeric range, including that odometer values are non-negative integers in the documented base unit; enumeration membership for units, support status, and provenance mode; primary-key uniqueness within a store; singleton-ness of `meta` and `prefs`; referential linkage, so that every vehicle-scoped record names a `vehicle_id` present in the payload; parseable instants and dates; and a `meta.seq` that is a non-negative integer no lower than the highest sequence any record claims.
- FR-12: Integrity failures are never fatal and never silent. Valid records hydrate; failing records move to a quarantine list that names the record, the store, and the rule it violated; the count and nature of quarantined records is surfaced; and the raw payload remains exportable for recovery. Silent truncation, silent repair, and silent deletion are all prohibited.
- FR-13: A repair path is specified as an explicit, user-initiated operation that first produces an export of the raw payload, then applies only the documented repairs — re-linking or quarantining orphans, deduplicating identical records that share a key, and normalizing values that are recoverable without guessing — and records what it did in a bounded, non-personal entry in `meta`. Repair never deletes a record the user has not seen described, and never fabricates a value to satisfy a rule (INV-15).
- FR-14: Hard caps are specified and are rejected explicitly rather than silently truncated, matching the server-side validation caps: a decoded payload size ceiling, a maximum vehicle count, a maximum service-event count, and a maximum odometer-reading count. Exceeding a cap yields an explicit error state with export offered (INV-24.5).
- FR-15: `meta` records enough to distinguish a genuine first visit from a store that was populated and is now empty: a creation instant, a last-write instant, a monotonic write counter, the logical schema version, and the recorded outcome of the persistent-storage request. Combined with the non-personal `localStorage` boot hint, this makes the empty state and the data-missing state separable in code and therefore separable in copy (INV-24.3, INV-24.4, INV-24.8, INV-25).
- FR-16: `meta.seq` is the compare-and-set field for multi-tab safety: every write transaction reads it, compares it against the expected value, and aborts if it differs, so a stale tab cannot overwrite newer records without the conflict being surfaced (INV-24.7).
- FR-17: The export/import envelope is specified as the sole portability and recovery path (INV-5). It reuses the hydration envelope's identity and payload fields and adds export-only fields — an export identifier, an exported-at instant, the application version, record counts per store, and a SHA-256 hash computed over a canonical serialization of the payload with the hash field itself excluded. Ephemeral values, specifically the per-tab identifier, MUST be omitted from any exported file. Import validates the envelope, version, caps, and hash before anything is written, previews counts, and requires an explicit replace-or-merge choice; it never merges silently.
- FR-18: The persisted footprint stays within the constitution §9 budget: no more than 1 MiB per 1,000 text-only records, with the total origin footprint held under a 5 MiB working ceiling. The stress fixture demonstrates the measured figure rather than asserting it.
- FR-19: The schema contains no credential, email address, password, account identifier, device identifier, push subscription, or server-assigned identifier of any kind, and no full VIN by default (INV-3, INV-4, INV-17).
- FR-20: Every extension this design makes to ADR-0004's storage-layout table or envelope is recorded as a numbered ADR-0004 addendum obligation with its rationale, so the ADR and the implementation cannot drift apart (CHANGE_CONTROL Rule 2a).

## Technical implementation contract

### Components and ownership boundaries

- This issue owns the written schema specification, the version-line record, the ordered upgrade-step definitions, the integrity-rule list, the envelope definition, and the committed fixtures. It owns no runtime module.
- `DOS-M09-002` owns the adapter that implements the open, upgrade, read, write, transaction, and erase contract defined here, and is the only module permitted to touch IndexedDB.
- `DOS-M09-003` owns the hydration protocol and the server-side validation modules, which are written against the field types, caps, referential rules, and version semantics defined here.
- `DOS-M09-004` owns the copy for the states this schema makes distinguishable.
- The domain contexts consume domain structs, never store records or IndexedDB concepts, preserving the rule that a future native client differs by one storage adapter.

### Data and persistence

Object stores in `dos_local`:

| Store | Key | Contents | Indexes |
| --- | --- | --- | --- |
| `meta` | fixed singleton key | logical schema version, monotonic write counter, created-at, last-write-at, persistent-storage grant result, bounded non-personal migration and repair log | none |
| `vehicles` | `vehicle_id` (UUIDv4) | vehicle selection, stable catalog configuration reference, immutable identity and configuration snapshot, support status, nickname, optional last-six VIN field (null by default), archived flag, timestamps, and the active maintenance plan as a versioned sub-document | archived flag |
| `events` | `event_id` (UUIDv4) | service events: performed instant or date, normalized odometer plus input unit, oil and filter product snapshots, notes, provenance mode, correction lineage, timestamps | `vehicle_id`; `(vehicle_id, performed_at)` |
| `readings` | `reading_id` (UUIDv4) | odometer check-ins: observed instant, normalized odometer, input unit, source, validity and supersession fields | `vehicle_id`; `(vehicle_id, observed_at)` |
| `usage` | `usage_id` (UUIDv4) | usage profile rows: baseline distance per week, unit, the severe-use answers that selected the condition, selected condition, effective-from and effective-to | `vehicle_id`; `(vehicle_id, effective_from)` |
| `reminders` | `reminder_id` (UUIDv4) | reminder intent: kind, lead value and unit, preferred local time, enabled flag | `vehicle_id` |
| `prefs` | fixed singleton key | unit system, IANA time zone, onboarding version, display preferences, dismissed-notice flags | none |

Mapping from the `DATA_DICTIONARY.md` `UserRepo` tables:

| `UserRepo` table | Browser home | Reason |
| --- | --- | --- |
| `local_profiles` | `prefs` singleton plus `meta` | There is no profile identity to model. Unit system, time zone, and onboarding version are preferences; the rest was identity scaffolding an anonymous store does not need (INV-3). |
| `vehicles` | `vehicles` store | Direct equivalent, keyed by client-generated UUID. |
| `maintenance_plans` | versioned sub-document inside each `vehicles` record | IndexedDB has no cross-store foreign keys, and the plan is never read without its vehicle. Embedding removes an unenforceable join at the cost of a slightly larger vehicle record. One active plan per vehicle at MVP. |
| `service_events` | `events` store | Direct equivalent; the store name follows ADR-0004. |
| `odometer_readings` | `readings` store | Direct equivalent. |
| `usage_profiles` | `usage` store | Direct equivalent. This store is **not** in ADR-0004's layout table and is an addendum obligation under FR-20. |
| `forecast_snapshots` | no store at MVP | Forecast output is derived from stored inputs and recomputed on load; persisting an audit trail of it is an open question below, and adding a store later is a forward-only version bump. |
| `reminder_rules` | `reminders` store | Direct equivalent, narrowed to intent only. |
| `scheduled_notifications` | no store | Nothing is scheduled in this platform, so there is nothing to record or reconcile (INV-17). |
| `schema_events` | bounded non-personal log inside `meta` | Migration and repair outcomes are diagnostic, must survive, and must contain no automotive or user content. A bounded ring keeps the footprint fixed. |

Additional persistence rules: mileage is persisted in a single documented integer base unit with conversion at the boundary, so switching between miles and kilometers never loses precision; exact events store UTC instants while the IANA time zone lives in `prefs`; date-only capture follows one documented canonical rule with no accidental shifts; historical records always carry the stable catalog reference **and** an immutable human-readable snapshot, so history stays intelligible after a catalog release changes, a product is withdrawn, or a configuration is superseded; and the non-personal boot hint in `localStorage` records only whether this origin has ever held data, never what it held.

### Interfaces and events

- The schema exposes no functions. Its interface is the store definitions, the record shapes, the ordered upgrade steps, the integrity-rule list, the caps, and the envelope definition.
- The hydration envelope identity fields — envelope name, logical schema version, write counter, generated-at, ephemeral per-tab identifier — and the payload keyed by store name are defined here and consumed unchanged by `DOS-M09-003`.
- The export envelope is the hydration envelope minus the ephemeral per-tab identifier, plus export identifier, exported-at, application version, per-store record counts, and the payload hash.
- Snapshot sub-documents are versioned; a consumer must tolerate reading any released snapshot version.
- Every store record shape is published as a committed schema document that both the client adapter and the server-side validation are written against, so the two cannot diverge silently.

### Failure and recovery behavior

- Upgrade step raises: the version-change transaction aborts, the database remains at its prior structural version with its records untouched, and the adapter surfaces a typed upgrade-failed error. There is no partial upgrade.
- Database at a newer logical version than the deployment: read-only mode, explicit banner, mutations disabled, export offered. No write of any kind occurs (FR-9).
- Integrity failure on read: valid subset hydrates, failing records quarantine with their rule named, counts surfaced, raw payload exportable (FR-12).
- Orphaned vehicle-scoped record whose `vehicle_id` is absent: quarantined, never deleted, and offered to the repair path, which may re-link it only if the user chooses a target and never by inference.
- Duplicate primary key across a merge import: rejected as a conflict, previewed with counts, and resolved by the user's explicit replace-or-merge choice.
- Compare-and-set mismatch on `meta.seq`: the write transaction aborts and the conflict is reported so the losing side re-reads rather than overwriting (FR-16, INV-24.7).
- Quota exceeded during a write: the transaction fails, the prior state is preserved, the failure is surfaced in plain language, and export is offered. No record is dropped to make room (INV-24.5).
- Store unavailable, blocked, or discarded at session end: this schema is simply not present; the session-only path and its disclosure belong to `DOS-M09-002` and `DOS-M09-004`, and this issue's obligation is that nothing in the schema design makes that state indistinguishable from an empty store (INV-24.6).
- Cleared site data: the data is gone, there is no server copy, and the schema's job is to make that detectable rather than recoverable (INV-24.8, INV-25).

### Security and privacy

- Every field in every store is either the user's own record or a non-personal preference. No credential, account identifier, device identifier, push subscription, or server-assigned value exists in the schema (INV-3).
- No key is server-derivable or stable across origins, and the ephemeral per-tab identifier is never persisted to a store, never written to a cookie, and never included in an export file (INV-3, INV-4).
- Full VIN is prohibited by default; at most a nullable last-six field exists, and enabling more requires its own privacy issue.
- The `meta` migration and repair log carries versions, outcomes, and counts only — never automotive content, record contents, or field values — so it is safe to display in a diagnostics surface and safe to include in an export (INV-4).
- Export files carry the user's records by definition; the schema's obligations are that the file contains nothing the user did not enter or choose, that it is produced client-side without a server round trip, and that its contents are never transmitted anywhere by the product (INV-4, INV-23).
- The specification carries no automotive fact of its own; every interval, viscosity, capacity, product claim, and fitment in a record is a snapshot of a provenance-carrying catalog value or an explicitly user-entered value labeled as such (INV-15, INV-20).

### Accessibility and performance

No UI of its own. Two performance obligations bind the design: the persisted footprint must hold to the constitution §9 budget of 1 MiB per 1,000 text-only records under a 5 MiB working ceiling, demonstrated by the stress fixture; and the store and index layout must let a full hydration read complete inside the §9 hydration-completion target, which means every ordering contract in FR-5 is index-backed and no hydration path performs a full-store scan and sort. Accessibility obligations attach to the states this schema makes distinguishable and are owned by `DOS-M09-004`, including the requirement that hydration and storage-state changes are announced rather than only rendered.

## UX and content states

This issue writes no copy, but it is the reason certain states can be told apart at all, and it owes `DOS-M09-004` a precise list:

- **First visit** — no database, no boot hint. Genuinely nothing has ever been stored.
- **Populated** — a database with a `meta` record and at least one vehicle.
- **Data missing** — the boot hint says this origin has held data, but the store opens empty or has no `meta` record. This is the eviction-or-cleared case and must never render as a first visit (INV-24.4, INV-24.8, INV-25).
- **Quarantine present** — hydration succeeded but some records failed integrity; the count and the affected stores are known and nameable.
- **Newer than the deployment** — the stored logical version exceeds the server's; mutations are disabled and export is offered.
- **Upgrade failed** — the version-change transaction aborted; the database is intact at its prior version and the failure is explicit rather than silent.
- **Cap exceeded** — the payload is larger than a documented cap; the specific cap is named and export is offered.

Copy for each of these belongs to `DOS-M09-004` and must satisfy the required terminology: records are "stored in this browser", never "saved to your account", "synced", "backed up", or "restored" (INV-5, INV-21, INV-25).

## Test plan

### Automated

- Schema-document lint: every store has a key path, key type, index list, and record shape; every record field has a type, nullability, and, where applicable, an enumeration or range.
- Migration chain tests: for each recorded prior-version fixture, run the full ordered upgrade chain and assert the result equals the current-version fixture; assert idempotence by re-running each step; assert step ordering is total and has no gap.
- Upgrade-abort test: inject a raising step and assert the database remains at its prior structural version with records unchanged and a typed error surfaced.
- Newer-payload test: present a payload one logical version ahead and assert read-only mode, no write, and export offered.
- Unknown-field preservation test: round-trip a payload containing unrecognized record fields through read, write-back, and export and assert byte equality of those fields.
- Integrity-rule tests: one case per rule in FR-11 using the corrupt-record fixture set; assert the valid subset hydrates and the offending record quarantines with the correct rule named.
- Referential test: an event, reading, usage row, and reminder each naming an absent `vehicle_id` quarantine rather than delete, and are offered to repair.
- Cap tests: payload size, vehicle count, event count, and reading count each rejected explicitly at the boundary, with no silent truncation.
- Compare-and-set test: a write against a stale `meta.seq` aborts and reports a conflict rather than committing.
- Envelope tests: canonical serialization is stable; the hash reproduces and excludes itself; the ephemeral per-tab identifier is absent from export output; import rejects a mismatched hash, an unknown version, and an oversized file before writing anything.
- Footprint test: the stress fixture is measured and asserted against the §9 budget.
- Privacy test: a field-name and field-value scan of every fixture asserts no credential, identifier, push subscription, or full VIN field, and that the `meta` log contains no record content.

- Walk each store definition and each integrity rule against a real database in one desktop and one mobile browser drawn from the constitution §9 support matrix, confirming that key paths, indexes, and ordering behave as specified rather than as assumed. Full matrix coverage is `DOS-M09-009`'s job; this issue only confirms the design is implementable on both ends of the matrix before the adapter is built.

- Perform one manual export and one manual import in each of those two browsers and confirm the file contents match the specification, including the absence of the ephemeral per-tab identifier.
- Exercise the data-missing detection manually: populate a store, clear site data through the browser's own controls, reload, and confirm the boot hint plus absent `meta` record yields the data-missing determination rather than a first-visit determination.

## Rollout and rollback

Specification and fixture deliverable; no user-facing rollout of its own. It merges before `DOS-M09-002` and `DOS-M09-003` begin implementation. Rollback of the specification is reverting the document and fixture commits, which is safe only because no browser has yet been upgraded against it — and that is precisely the property that disappears the moment the adapter ships. From the first deployment that opens `dos_local` at a structural version, there is no rollback: a browser cannot be reopened at a lower structural version, and a deployment rollback meets databases that are already ahead of it. The design therefore treats a deployment rollback as a first-class case with a defined behavior (FR-9: read-only mode with export offered) rather than as an incident. Every future logical version bump adds a step and a fixture and never edits a released step, so the recorded chain stays a faithful history of what shipped.

## Dependency rationale

Blocked by the ratification of Constitution 2.0.0 and ADR-0004 and by the closure of the re-scoped `DOS-M00-002`, because CHANGE_CONTROL Rule 2a forbids implementing against an unratified architecture and this schema refines a table that ADR-0004 owns. Blocked by the logical user model from the re-scoped `DOS-M04-003`, because the point of this issue is to preserve those semantics in browser terms rather than to re-derive them, and by the catalog vocabulary and stable-ID contract, because every historical record stores a stable catalog reference alongside its snapshot.

This issue blocks `DOS-M09-002`, which implements exactly this open, upgrade, read, write, and erase contract and may not choose its own store layout; `DOS-M09-003`, whose server-side validation, caps, referential checks, and version handling are written against these definitions and whose compare-and-set discipline depends on the `meta` sequence field specified here; `DOS-M09-004`, which can only write honest copy for states the schema makes distinguishable, and specifically cannot write the data-missing message without the first-visit-versus-cleared determination in FR-15; and `DOS-M09-009`, whose migration and export/import conformance cases are the fixtures delivered here. Downstream of the milestone, the MVP write paths and the export, import, and reset controls all serialize exactly these stores.

## Risks, decisions, and open questions

- Risk: a released upgrade step that corrupts data cannot be recalled, because a deployment rollback does not downgrade a browser. Mitigation: every step is pure, idempotent, and fixture-tested against every prior version before release; the version-change transaction is all-or-nothing; and the newer-than-deployment case is a tested read-only behavior rather than an unhandled path.
- Risk: embedding the maintenance plan inside the vehicle record trades an unenforceable cross-store join for a larger record, and a future need for plan history would require a store and a version bump. Accepted for MVP, with the trigger recorded: if plan history becomes a requirement, it arrives as a new store through the ordinary forward-only path.
- Risk: read-time integrity checking adds work to every hydration, which is on the critical path of the §9 hydration-completion target. Mitigation: rules are field-local and index-backed, the stress fixture measures the cost, and if the budget is threatened the answer is a cheaper rule set with the dropped checks recorded, never silent skipping.
- Risk: browser behavior around key ordering, index collation, and structured-clone of unusual values differs across engines. Mitigation: the design avoids exotic key types, and the manual two-browser walk plus `DOS-M09-009`'s matrix verify behavior rather than assuming it.
- Decision: seven object stores, with the maintenance plan embedded in the vehicle record and no scheduled-notification store, because nothing is scheduled in this platform.
- Decision: two version lines — logical schema version owned by the server, structural database version bumped only for store or index changes — rather than one shared integer, so that a pure record-shape change does not force a structural upgrade on every browser.
- Decision: quarantine rather than repair-on-read. Automatic repair during hydration would change a user's records without their knowledge, which the honest-messaging rule forbids.
- Decision: the export file omits the ephemeral per-tab identifier, so that a file a user keeps or shares carries nothing that was not their own record or preference.
- Open question (owned by this issue, to be closed before it merges): whether any derived forecast record is persisted at MVP for explainability and audit, or whether forecasts are recomputed on load from stored inputs only. The default is not to persist, because a derived store adds footprint, an invalidation rule, and a migration surface for data that is reproducible; the argument against the default is that an audit trail of what the user was told is itself a product value.
- Open question: whether the usage profile needs a full effective-dated history in the browser, or whether one current row plus the answers that selected it is sufficient for MVP. The store shape supports history; whether the adapter writes it is the open part.
- Open question (owned by the ADR addendum): whether the `usage` store and its envelope key are folded into ADR-0004's storage-layout table by addendum or by a superseding revision, given that the ADR is Accepted and the change-control rule is that amendments are recorded rather than edited in place.
