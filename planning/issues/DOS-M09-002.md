## Outcome

The `LocalStore` JavaScript hook and the LiveView server exchange the user's records over one specified, versioned, testable protocol instead of an implicit convention. On every mount the hook opens IndexedDB, reads a versioned snapshot, and `pushEvent`s it to the server; the server treats that payload as untrusted client input, validates it through an explicit changeset, coerces it into domain structs, and holds it in `socket.assigns` **for the lifetime of that socket only** — never persisting, caching, replicating, forwarding, or logging a personal row (INV-3, INV-4, INV-23, INV-24.1). Every mutation is a round trip: `pushEvent` → server computes the new state → server pushes a write instruction → hook commits the IndexedDB transaction → hook acknowledges — and the UI does not present a mutation as committed until that acknowledgment arrives (INV-24.2). Hydration re-runs on every reconnect (deploy, network blip, sleep/wake, tab restore), and it is idempotent, cheap, and visually non-destructive. Two tabs sharing one IndexedDB cannot silently overwrite each other (INV-24.7).

## Why this matters and what it unblocks

Phoenix LiveView keeps UI state on the server; this product keeps user data on the client. CONSTITUTION §0.2 and ADR-0004 both record that these two facts do not compose for free, and the pivot's gap analysis names this seam **gap #2 — "the single highest-risk new component," with zero coverage anywhere in the existing 77 issues**. Getting it wrong produces one of exactly two failures, both fatal to the product's premise: a silent server-side personal record (breaking INV-3, INV-4, and INV-23 while appearing to satisfy them), or a UI that loses the user's garage on every reconnect — which, with one always-on machine and deploys that drop every WebSocket (ADR-0004 R8), is not an edge case but a routine event.

Everything that writes or reads a personal record depends on this contract. `DOS-M09-003` renders the states this protocol defines and names. The re-scoped `DOS-M04-005` (browser storage adapter with transactional semantics), `DOS-M04-009` (export/import), and every M05 write path — `DOS-M05-003` create/edit vehicle, `DOS-M05-004` record oil changes and odometer history, `DOS-M05-005` dashboard — commit through this round trip and cannot be specified until it exists. `DOS-M09-009` (browser support matrix and storage-behavior conformance suite) exercises exactly this protocol across engines. `DOS-M02-001` cannot freeze flow entry states without knowing the hydration model.

## Included

- Implement the `LocalStore` `phx-hook` mounted on the application shell element, owning the client half of the protocol: read-on-mount, write-on-instruction, acknowledge, broadcast, and re-hydrate.
- Implement the payload envelope (`envelope`, `schema_version`, `seq`, `tab_id`, `generated_at`, `data`) as the single shape used by hydrate, write-back, and export, with `tab_id` regenerated per tab load, never persisted, never written to a cookie, and never logged.
- Implement the server-side mount and hydration sequence: static render at `:hydrating`, socket connect, armed hydration deadline, `local_store:hydrate` handling, assigns population, migration write-back, and deadline expiry to `:storage_unavailable`.
- Implement server-side validation of the hydrate payload as untrusted input: per-`schema_version` embedded-schema changesets, rejection of unknown top-level keys, verbatim preservation of unknown keys *within* a record, hard caps rejected explicitly rather than truncated, type/range/referential checks, and a quarantine list for records that cannot be read.
- Implement forward-only schema migration (`LocalStore.Migrations.migrate/3`) with immediate write-back of the migrated payload, plus the newer-than-server read-only mode that disables mutations and never downgrades or drops unknown fields.
- Implement the six-step mutation round trip with `mutation_id`, monotonic `seq`, `assigns.pending_writes`, the `local_store:put` instruction, the client `readwrite` transaction across affected stores plus `meta`, the compare-and-set on `meta.seq`, and `local_store:ack`.
- Implement the acknowledgment-timeout and error paths: persistent non-dismissible unsaved state on the affected record, no silent retry, no invisible rollback, export offered.
- Implement re-hydration on every mount and reconnect, proven idempotent, with the previous DOM retained and `phx-disconnected` styling rather than a teardown to skeleton.
- Implement multi-tab consistency: `BroadcastChannel("dos_local_store")`, seq comparison and re-read, `local_store:conflict`, wholesale assigns replacement in the losing tab, and record-granularity last-write-wins with the loss made visible.
- Implement the logging discipline for this surface: `handle_event` parameters dropped by default with an explicit allowlist for non-personal events, and no envelope, fragment, `tab_id`, or record value in any log sink.
- Deliver the four ADR-0004 enforcement checks that belong to this protocol, as release-gating tests.

## Functional requirements

- FR-1: A `phx-hook` named `LocalStore` is mounted on the application shell element and is the sole client-side owner of the protocol; no other script reads or writes `dos_local` (INV-23, INV-24.1).
- FR-2: All hydrate, write-back, and export payloads use one envelope shape carrying `envelope`, `schema_version`, `seq`, `tab_id`, `generated_at`, and `data` with the six record collections. `tab_id` is regenerated per tab load, is never persisted to IndexedDB, never written to a cookie, and never logged (INV-3, INV-4).
- FR-3: On static render (`connected?(socket) == false`) the server sets `assigns.local_state = :hydrating` and renders a skeleton. It never renders an empty state, an onboarding-from-zero flow, or any "no vehicles yet" claim while `:hydrating` (INV-24.3).
- FR-4: On socket connect the server arms a `hydration_deadline` timer (ADR-0004 default 5,000 ms; the shipped value is recorded with its measurement). Expiry without a hydrate event sets `assigns.local_state = :storage_unavailable`, which is a distinct state from `:empty` and renders differently. Hydration always resolves or surfaces an explicit failure state; it never hangs silently (INV-24.3).
- FR-5: The hook's `mounted()` opens `dos_local` through the `DOS-M09-001` adapter, reads all stores in one `readonly` transaction, and calls `pushEvent("local_store:hydrate", envelope)` (INV-24.1).
- FR-6: `handle_event("local_store:hydrate", …)` validates the envelope as untrusted client input through an explicit embedded-schema changeset selected by `schema_version`. Unknown top-level keys are rejected. Unknown keys *within* a record are preserved verbatim in assigns and written back unchanged, so an older deployment never destroys fields a newer one wrote.
- FR-7: Hard caps are enforced server-side and rejected explicitly, never silently truncated: payload ≤ 1 MiB decoded, ≤ 200 vehicles, ≤ 5,000 events, ≤ 20,000 readings. Exceeding a cap yields an explicit error state with export offered (INV-24.5-adjacent; ADR-0004 §"Validation").
- FR-8: Type, range, and referential checks run on every record: an event's `vehicle_id` exists among the payload's vehicles, odometer values are non-negative and within sane bounds, dates are parseable. Validation failure is never fatal to the session: the valid subset hydrates, invalid records are held aside in a quarantine list, and the UI reports exactly what could not be read and offers an export of the raw payload (INV-24.3).
- FR-9: Catalog references in a hydrated payload are resolved against the read-only catalog at render time. A reference that resolves to `unsupported` or `identity_only` because a `data_version` moved is rendered as that legitimate support status, not as an error (INV-11, INV-15).
- FR-10: When the client payload's `schema_version` is older than the server's, the server migrates it through pure, ordered, forward-only functions and immediately `push_event`s `local_store:put` carrying the migrated payload, so the client's storage is upgraded in the same round trip.
- FR-11: When the client payload's `schema_version` is **newer** than the server's, the server MUST NOT write. It enters read-only mode, renders an explicit banner, disables mutations, and offers export. Downgrading the payload or dropping unknown fields is prohibited.
- FR-12: Every mutation follows the six-step round trip: `handle_event` → server computes new state in assigns, assigns `mutation_id` and `seq = current_seq + 1`, records it in `assigns.pending_writes` → server `push_event`s `local_store:put` with `{mutation_id, seq, upserts, deletes}` → hook opens one `readwrite` transaction across the affected stores plus `meta`, performs the compare-and-set on `meta.seq`, applies and commits → hook `pushEvent`s `local_store:ack` `{mutation_id, seq, status}` → server clears the pending write and renders the saved state (INV-24.2).
- FR-13: A mutation is not rendered as committed until its acknowledgment arrives. Optimistic rendering is permitted only where a failed commit visibly reverts the change and reports it; an optimistic value is visually marked as in-flight until acknowledged (INV-24.2).
- FR-14: If no acknowledgment arrives within 2,000 ms, or the acknowledgment reports an error, the server renders a persistent, non-dismissible "Not saved to this browser" state on the affected record, keeps the optimistic value visible but visibly marked unsaved, and offers export. It does not retry silently and does not roll back invisibly (INV-24.5, INV-25).
- FR-15: Hydration re-runs on every mount, including every reconnect after a deploy, network blip, sleep/wake, or tab restore. The server never assumes surviving assigns. On reconnect the previous DOM is retained and `phx-disconnected` styling communicates reconnection; the view is not torn down to a skeleton (INV-7, INV-24.3).
- FR-16: Hydration is idempotent: hydrating the same payload twice produces identical assigns and emits no write-back.
- FR-17: Each tab opens a `BroadcastChannel("dos_local_store")` and broadcasts `{seq, mutation_id, tab_id}` after any successful commit. A receiving tab whose last-known `seq` is behind re-reads storage and pushes a fresh `local_store:hydrate` on its own socket; its assigns are replaced wholesale, and still-pending optimistic edits are re-applied on top or surfaced as a conflict if the same record changed (INV-24.7).
- FR-18: Every client write performs a compare-and-set on `meta.seq` inside the same transaction. A mismatch aborts the transaction and the hook pushes `local_store:conflict`; the server discards its optimistic assign, triggers re-hydration, and shows a visible notice that it reloaded from this browser's newer data. Conflict resolution is last-write-wins at record granularity **with the loss made visible**; a stale tab never overwrites newer records without the user being told (INV-24.7).
- FR-19: Where `BroadcastChannel` is unavailable, behavior degrades to per-mount hydration only; the compare-and-set still prevents lost-update corruption and the conflict surfaces later rather than never.
- FR-20: No hydrate, write-back, acknowledgment, conflict, import, or export payload — or any fragment, record value, or `tab_id` — is written to any log sink, error report, crash trace, or fixture. `handle_event` parameter logging is disabled by default with an explicit allowlist for non-personal events (INV-4).
- FR-21: No protocol event carries a personal field into a catalog query. Catalog requests triggered by hydrated state carry only impersonal selectors; the server cannot reconstruct a garage from its request stream (INV-26).

## Technical implementation contract

### Components and ownership boundaries

- **`LocalStore` hook (client)** — sole client-side owner of the protocol: mount read, `local_store:put` application, acknowledgment, `BroadcastChannel` publish/subscribe, conflict signaling, re-hydration. It calls the `DOS-M09-001` adapter for all IndexedDB work and contains no storage-layout knowledge of its own.
- **`DOS-M09-001` storage adapter (client)** — owns open/upgrade/read/write/transaction/erase and the typed error vocabulary. It is called by the hook and by nothing else.
- **`LocalStore.Envelope` / `LocalStore.Validation` (server)** — envelope parsing, per-version embedded schemas, caps, referential checks, quarantine construction. Pure functions over untrusted maps.
- **`LocalStore.Migrations` (server)** — ordered, pure, forward-only migration functions keyed by version pair; owns nothing else and touches no transport.
- **`LocalStore.Session` (server)** — the assigns lifecycle: `local_state`, `seq`, `pending_writes`, quarantine, read-only flag. It is the only module that mutates protocol assigns.
- **Domain contexts (`Garage`, `Forecast`, `Catalog`)** — receive coerced structs and remain free of `Phoenix.LiveView`, `Plug`, and every `LocalStore` module, enforced by the ADR-0004 decision §6 static check.

### Data and persistence

- Client: origin-scoped IndexedDB database `dos_local` with the `meta`, `vehicles`, `events`, `readings`, `reminders`, and `prefs` stores defined by `DOS-M09-001`. `meta` carries `schema_version`, the monotonic `seq`, `created_at`, `last_write_at`, and `persist_granted`.
- Server: **no personal persistence of any kind.** The deployed application has exactly one Ecto repo, `CatalogRepo`, opened read-only. Personal values exist only as transient `socket.assigns` for one connection and are never written to disk, database, cache, ETS, external store, or log (INV-3, INV-23, ADR-0004 decision §4).
- `localStorage` is used for nothing in this issue beyond the non-personal boot hint owned by `DOS-M09-003`.
- A server restart, machine replacement, deploy, or `SECRET_KEY_BASE` rotation loses no user data, because the server was never the system of record (INV-24.1).

### Interfaces and events

- Client → server: `local_store:hydrate` (envelope), `local_store:ack` (`{mutation_id, seq, status}`), `local_store:conflict` (`{expected_seq, found_seq, mutation_id}`).
- Server → client: `local_store:put` (`{mutation_id, seq, upserts, deletes}`) used for both mutation write-back and post-migration upgrade.
- Server assigns contract: `local_state ∈ {:hydrating, :loaded, :empty, :data_missing, :storage_unavailable}`, plus `seq`, `pending_writes`, `quarantine`, and a read-only flag for the newer-schema case. `:data_missing` is raised by `DOS-M09-003`'s boot-hint rule and consumed here as a first-class state.
- Cross-tab: `BroadcastChannel("dos_local_store")` carrying `{seq, mutation_id, tab_id}` only — no record content.

### Failure and recovery behavior

- **Hydration deadline expires** → `:storage_unavailable`, distinct from `:empty`, mutations disabled, no silent retry loop.
- **Validation partially fails** → valid subset hydrates, invalid records quarantined and named, raw-payload export offered, session continues.
- **Cap exceeded** → explicit rejection with export offered; never a silent truncation.
- **Newer client schema** → read-only mode, banner, mutations disabled, export offered; no write of any kind.
- **Acknowledgment timeout or error** → persistent non-dismissible unsaved state on the affected record, optimistic value retained and marked, export offered, no silent retry, no invisible rollback.
- **Compare-and-set mismatch** → transaction aborts, `local_store:conflict`, optimistic assign discarded, re-hydration, visible notice.
- **Reconnect mid-mutation** (including a deploy during an unsaved write) → the pending write is re-driven after remount from client storage, which is the source of truth; no pending mutation is silently dropped (INV-7).
- **Quota-exceeded on commit** → follows the acknowledgment-error path with the quota-specific message defined by `DOS-M09-003`; data is never silently dropped to make room (INV-24.5).

### Security and privacy

- The hydrate payload is untrusted client input and is validated exactly like any external payload, even though the client is the user.
- No durable server-side identifier is created, derived, or transmitted. `tab_id` is ephemeral and explicitly not a user identifier (INV-3).
- Session cookie contents are unchanged by this issue and remain limited to the CSRF token and `live_socket_id`; no protocol value enters the cookie.
- Logging follows the ADR-0004 allowlist: event **name** only, never parameters. `debug_errors: false` in production so no assigns reach an error page. Third-party error reporting remains prohibited because assigns contain the user's garage.
- Rate limits apply per socket to hydrate and import events, which are the largest payloads.
- Nothing in this protocol adds a personal field to a catalog query (INV-26).

### Accessibility and performance

- Interactive controls MUST NOT accept input before the hydration state is known (CONSTITUTION §9 TTI row, INV-24.3).
- Hydration state transitions and save/unsaved status changes are announced through a polite live region; the skeleton-to-content swap must not steal or destroy focus.
- Targets (all §9 *provisional*, to be measured on the deployed environment and re-ratified, not silently missed): hydration completion p95 ≤ 300 ms after socket join; LiveView event round trip p95 ≤ 150 ms from the client; automatic reconnect p95 ≤ 2.0 s including re-hydration.
- The hook's mount read is a single `readonly` transaction; write-back is a single `readwrite` transaction across affected stores plus `meta`. Re-hydration on reconnect must not cause a visible layout teardown.

## UX and content states

This issue defines and emits the states; `DOS-M09-003` and the UX milestone own their copy, layout, and Settings placement.

- `:hydrating` — determinate skeleton. No empty-garage claim of any kind, not even for one frame.
- `:loaded` — records present in assigns and rendered.
- `:empty` — hydration resolved and the store genuinely holds nothing.
- `:data_missing` — the boot hint says data existed but hydration returned zero records: an explicit warning with import offered, never a cheerful empty garage (INV-24.4, INV-24.8, INV-25).
- `:storage_unavailable` — hydration never arrived or storage cannot be used; distinct from `:empty` and says so in words (INV-24.6).
- Per-record **saving** and **not saved to this browser** affordances, the latter persistent and non-dismissible (INV-24.2, INV-24.5).
- **Read-only, newer data** banner for the newer-client-schema case, with mutations disabled and export offered.
- **Reloaded from this browser's newer data** notice after a cross-tab conflict (INV-24.7).
- **Could not read some records** notice naming the quarantined counts, with raw-payload export.
- All copy on these surfaces uses "stored in this browser" framing; "saved to your account", "synced", "backed up", and "restore" are prohibited (INV-5, INV-21, INV-25).

## Test plan

### Automated

- Envelope and validation unit tests: unknown top-level key rejection, in-record unknown key preservation, each hard cap, referential integrity, non-negative and bounded odometer values, unparseable dates, and quarantine construction.
- Migration unit tests against recorded fixtures of every prior `schema_version`, asserting purity, ordering, forward-only behavior, and byte-stable write-back.
- Newer-than-server schema tests asserting read-only mode, zero writes, and no field loss.
- LiveView tests for the mount sequence: static render, connect, deadline expiry, hydrate handling, and each `local_state` transition, including the assertion that no empty-garage text renders while `:hydrating`.
- Mutation round-trip tests with a scripted hook double: acknowledgment success, acknowledgment error, acknowledgment timeout, and quota-exceeded fault injection.
- Idempotence test (AC-4) and reconnect test driving a full remount with a pending write outstanding.
- Multi-tab tests driving two sockets against one simulated store: broadcast-driven re-hydration, compare-and-set abort, conflict event, and the `BroadcastChannel`-absent degradation path.
- The four ADR-0004 enforcement checks as release gates: repo list, domain static check, log-scanning scripted session, hydration idempotence.
- Log-redaction tests asserting `handle_event` parameters are dropped by default and that the allowlist contains only non-personal events.
- Payload-audit test for INV-26 across every catalog query the hydrated state can trigger.

### Manual/browser matrix

Run on the CONSTITUTION §9 *provisional* matrix — current and prior stable Chrome, Edge, Firefox, and Safari on desktop, plus iOS Safari 16+ and Android Chrome:

- Cold first visit: observe the skeleton, confirm no empty-garage flash at any point, and record measured time from socket join to populated assigns against the 300 ms p95 target.
- Returning visit with a populated garage: confirm no empty-garage flash on load, on refresh, and on back/forward navigation.
- Reconnect matrix: forced deploy-style restart, network interruption, laptop sleep/wake, mobile background/foreground, and tab restore — each re-hydrating without a visible teardown, with a pending mutation outstanding in at least one run.
- Two-tab matrix on each engine: concurrent mutation, stale-tab commit rejection, and the visible reload notice; repeat in a context where `BroadcastChannel` is unavailable.
- Quota fault injection using per-engine storage limits, confirming the unsaved state and message rather than silent loss.
- Network-panel capture of a full session confirming zero third-party origins and no personal field in any request or socket frame.
- Screen-reader passes (one per platform family) over hydration transition, save, unsaved, and conflict announcements; keyboard-only pass confirming no input is accepted before hydration state is known.

## Rollout and rollback

Rollout: this protocol is foundational and merges before any personal-data write path is exposed to users. Behind it, `DOS-M09-003` supplies the states' copy and `DOS-M04-005`/M05 write paths adopt the round trip. The shipped `hydration_deadline` and acknowledgment-timeout values are recorded with the measurements that justify them rather than carried forward as ADR defaults unexamined.

Rollback: revert the protocol commits. There is no server-side personal schema to unwind — that is the point of the design — so a revert orphans nothing on the server. On the client, a revert must not lower the `dos_local` schema version or delete stores; a deployment older than the client's `schema_version` is exactly the newer-than-server case in FR-11 and lands the user in read-only mode with export offered rather than in data loss. Any change to the envelope shape after release requires a new `schema_version` with its migration and fixture, never an in-place reinterpretation.

## Dependency rationale

Blocked by `DOS-M09-001`, because a protocol that reads and writes a store cannot be specified against a store whose layout, version line, upgrade path, and typed errors do not exist; the compare-and-set on `meta.seq` in particular requires `meta` to be defined first. Blocked by `DOS-M00-002` as the ratification gate for the browser architecture, and by `DOS-M01-002` so the domain-boundary static check has something to enforce.

Blocks `DOS-M09-003`, which renders the states this issue names and cannot specify copy for transitions that are not yet defined. Blocks the re-scoped `DOS-M04-005` (browser storage adapter with transactional semantics as seen from the domain), `DOS-M04-009` (export/import, which re-enters through `local_store:hydrate` to inherit validation and migration), and every M05 write path — `DOS-M05-003`, `DOS-M05-004`, `DOS-M05-005` — because none of them may render a write as committed without this acknowledgment contract. Blocks `DOS-M09-009`, whose conformance suite exercises this protocol across the browser matrix. Informs `DOS-M02-001`, which cannot freeze flow entry states without the hydration model.

## Risks, decisions, and open questions

- Risk (ADR-0004 R2): the hydration round trip adds latency to first meaningful paint on **every** mount, including every reconnect. Mitigation: single-transaction reads, an explicit measured budget, and the AC-14 reconnect evidence; if hydration is not sub-second on a cold connection, the skeleton becomes the dominant impression of the product and the design must be revisited rather than shipped past.
- Risk (ADR-0004 R8): with one always-on machine, every deploy drops every socket, so reconnect-plus-re-hydration is a routine path, not a rare one. Mitigation: FR-15, FR-16, and AC-14 make a deploy a non-event by construction; the re-drive of pending writes is explicitly tested.
- Risk: optimistic rendering makes a failure mode where a user believes a write landed. Mitigation: FR-13 permits it only with visible revert and report, and FR-14 makes the unsaved state persistent and non-dismissible.
- Risk: server-side assigns hold the user's garage, so any future crash reporter or verbose error page would exfiltrate exactly what this architecture exists to keep off servers. Mitigation: FR-20, `debug_errors: false`, and the standing prohibition on third-party error reporting; adding one would require an ADR and a proven assigns-scrubbing layer.
- Decision: last-write-wins at record granularity, with the loss made visible, is accepted for the MVP under the single-user assumption (ADR-0004 §"Multi-tab", R4). It is recorded as a deliberate simplification, not presented as a general solution.
- Decision: unknown keys within a record are preserved verbatim so that a rolled-back deployment cannot destroy fields a newer one wrote.
- Open question (ADR-0004 R4): whether a real workflow — two tabs, one logging a service while the other edits it — makes record-granularity last-write-wins materially wrong. Re-examine on evidence from the conformance suite and beta, not on speculation.
- Open question: whether the MVP uses optimistic rendering at all, or renders only the pending affordance until acknowledgment. Both satisfy INV-24.2; the choice is made on measured round-trip latency and recorded.
- Open question: the shipped `hydration_deadline` and acknowledgment timeout. The ADR defaults (5,000 ms and 2,000 ms) stand until the deployed environment supplies measurements; the values are then recorded, not silently adjusted.

## Definition of done

- All functional requirements implemented; all acceptance criteria checked with evidence attached or linked from CI.
- The four ADR-0004 enforcement checks run as release gates and pass: single read-only `CatalogRepo`, domain static check, scripted-session log scan, and hydration idempotence.
- Every `local_state` transition is exercised by an automated test, and every INV-24 sub-clause that this issue owns has at least one named test.
- Measured hydration, round-trip, and reconnect timings are recorded per browser against the §9 provisional targets, so re-ratification proceeds on numbers rather than assumptions.
- `DOS-M09-003`, `DOS-M04-005`, `DOS-M04-009`, and the M05 write paths are unblocked with an executable, engine-proven contract rather than a described intention.
