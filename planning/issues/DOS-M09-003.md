## Outcome

Every storage condition a real browser can put the user in has a specified, distinguishable, honest state — and none of them ever tells a person with a full garage that their garage is empty. First paint is determinate: a skeleton that admits it does not yet know whether data exists, never a flash of "no vehicles yet" (INV-24.3). Persistent storage is requested once after the first meaningful write and its answer — granted, denied, or unavailable — is reported honestly and never described as a backup. The quota estimate is surfaced in Settings, and quota pressure and exhaustion are visible, plain-language states rather than silent write failures (INV-24.5). Eviction, private-browsing, and blocked-storage conditions are detected and stated **before** the user enters data, with read-only catalog browsing offered instead of a pretense of saving (INV-24.6). Empty-because-cleared is distinguishable in copy from a genuine first visit, and it says the truth: the data is gone, there is no server copy, and there never was (INV-24.4, INV-24.8, INV-25).

## Why this matters and what it unblocks

This is where the product either keeps its central promise or quietly breaks it. The pivot's gap analysis names it **gap #3**: the existing first-run issue "covers first-run for a device that always has storage; it has no concept of a browser that refuses to store, evicts after seven days, or is in a private window." ADR-0004 records browser eviction of infrequently-used site storage as **R1, the single biggest product risk of the pivot** — and notes the specific bite: a person who checks their oil once a quarter is exactly the profile most at risk, and quarterly is this product's natural usage cadence.

The failure this issue prevents is not a crash. It is a returning user seeing an empty garage and concluding the product lost their data, or a private-window user entering six months of service history that evaporates when they close the tab, or a quota-exceeded write that fails silently — which CONSTITUTION INV-24.5 makes a release blocker outright. There is a second, subtler failure: a hosted URL naturally reads to users as "my data is on their server." The pivot document is explicit that INV-5 gets *harder* under a browser architecture, not easier, and that first-run copy, Settings, and export must **actively contradict** that assumption rather than merely avoid confirming it.

This unblocks the re-scoped `DOS-M02-003` (first-run, local-profile, privacy, readiness UX), `DOS-M05-005` (the dashboard that must render a determinate pre-hydration state), `DOS-M05-007` (export/reset/recovery controls, whose guidance depends on these states), and `DOS-M09-009` (the conformance suite that tests eviction, private mode, and quota). It is also the surface CONSTITUTION §9's honest-degradation-coverage row measures: every INV-7, INV-24.3–24.8, and INV-25 state must have a specified screen and a test.

## Included

- Specify and implement the determinate pre-hydration first-paint state: skeletons for both the static render and the pre-hydration live render, chosen by the non-personal `dos_boot_state` boot hint, with no empty-garage or onboarding-from-zero content reachable while hydrating.
- Specify and implement the five distinct storage states — genuine first visit, loaded, cleared/evicted (`:data_missing`), storage-unavailable, and session-only — each with its own copy, its own affordances, and no shared "something went wrong" fallback.
- Own the boot-hint write discipline: `dos_boot_state` in `localStorage` holds only `"never"` or `"has_data"`, contains no personal value, and is the sole basis for distinguishing empty-because-cleared from a genuine first visit at first paint.
- Implement the persistent-storage request: `navigator.storage.persist()` called once after the first meaningful write, its boolean or unavailable result recorded in `meta.persist_granted`, and that answer reflected honestly in the storage-status surface. Denial is not an error. A grant is never described as a backup.
- Implement the quota surface: `navigator.storage.estimate()` read on hydration, usage and quota rendered in Settings in plain units, an explicit pressure state when usage exceeds 80% of quota with export and pruning suggested, and an explicit exhaustion state on `QuotaExceededError`.
- Implement the availability probe ladder and its states: IndexedDB opens and a probe write/read/delete round-trips → durable-capable; open or probe fails → session-only mode with a persistent banner, prominent and repeated export offers, and read-only catalog browsing presented as a legitimate use rather than a broken app.
- Write and place the honest storage-loss messaging required by INV-25: at onboarding, on the export surface, and at an always-reachable Settings location, in the required terminology.
- Implement the always-reachable storage-status surface in Settings: where records live, persistence answer, quota estimate, last write time, what will destroy the data, and export as the only way to keep or move it.
- Add the copy-lint gate that fails the build on prohibited words in any user-facing string on these surfaces.
- Specify the accessibility behavior of each state: live-region announcements, focus handling across the skeleton-to-content swap, and the rule that interactive controls do not accept input before the hydration state is known.
- Run and record the per-engine storage-behavior measurements that these states depend on, so no copy asserts vendor behavior that has not been observed.

## Functional requirements

- FR-1: The static render and the pre-hydration live render show a determinate skeleton. No empty-garage claim, no "welcome, let's add your first vehicle", and no onboarding-from-zero flow is present in the DOM while `local_state == :hydrating` — not in hidden markup, not behind a CSS transition, not for one frame (INV-24.3).
- FR-2: `dos_boot_state` in `localStorage` holds exactly one of `"never"` or `"has_data"`, carries no personal value, is written on the first successful meaningful write, and selects the pre-hydration skeleton so a returning user sees a garage-shaped skeleton rather than a first-visit-shaped one (INV-23, INV-24.3).
- FR-3: When `dos_boot_state == "has_data"` and hydration returns zero records, the UI renders the `:data_missing` state — an explicit warning that this browser's storage appears to have been cleared, with import offered — never an empty garage and never a first-visit welcome (INV-24.4, INV-24.8, INV-25).
- FR-4: `:empty` (genuine first visit) and `:data_missing` (empty-because-cleared) use different copy, different headings, and different calls to action, and the difference is legible without reading fine print (INV-25).
- FR-5: `:storage_unavailable` renders copy distinct from `:empty` and from `:data_missing`, states in words that storage could not be used, and does not present a garage-entry flow as if writes would persist (INV-24.3, INV-24.6).
- FR-6: Hydration always resolves to a rendered state or an explicit failure state within the configured deadline. No spinner persists indefinitely and no state is reachable in which the user is left uncertain (INV-24.3).
- FR-7: On mount, the availability probe ladder runs: open IndexedDB, then a probe write, read, and delete round trip. Success yields durable-capable. Failure at either rung yields **session-only mode** — there is no silent rung, no fallback to `localStorage` for records, and no fallback to server storage (INV-24.6, INV-23).
- FR-8: Session-only mode shows a persistent, non-dismissible banner stating that nothing is being saved and that closing the tab loses everything. This appears **before** the user enters data, not after (INV-24.6).
- FR-9: Session-only mode offers read-only catalog browsing as a legitimate, fully functional use — vehicle lookup, requirements, and attribution — and does not present it as a degraded or broken state. It simply is not a garage (ADR-0004 §"Private browsing and blocked storage").
- FR-10: In session-only mode, export is offered prominently and repeatedly, at minimum after each meaningful entry, and the offer states plainly that export is the only way anything entered will survive the tab closing (INV-5, INV-25).
- FR-11: After the user's first meaningful write, the hook calls `navigator.storage.persist()` exactly once and records the result in `meta.persist_granted` as granted, denied, or unavailable. All three are reflected honestly in the storage-status surface. Denial is not treated as an error, and a grant is never described to the user as a backup, as safety, or as durability (INV-24.4, INV-5, INV-25).
- FR-12: `navigator.storage.estimate()` is read on hydration and its usage and quota are rendered in Settings in plain units, with an honest note when the browser reports no estimate rather than a fabricated number (INV-15-adjacent honesty rule; INV-24.5).
- FR-13: When reported usage exceeds 80% of reported quota, the UI surfaces a pressure state that suggests export and pruning. It does not block writes and does not delete anything on the user's behalf (INV-24.5).
- FR-14: A write that fails with `QuotaExceededError` surfaces an explicit quota-specific message in plain language, preserves the prior state, offers export, and leaves the affected record in the persistent unsaved state defined by `DOS-M09-002`. No data is silently dropped to make room, and no write fails silently — silent write failure is a release blocker (INV-24.5).
- FR-15: The storage-status surface is reachable at any time from Settings, not only at first visit, and states: that records live only in this browser on this device; that clearing site data, browser storage eviction, private-browsing sessions, uninstalling or resetting the browser, or switching devices will lose them; that there is no account and no server copy; and that export is the only way to keep or move them (INV-25, INV-5, INV-3).
- FR-16: Onboarding and the export surface both carry the INV-25 statement in full, in plain language, before the user has entered data in the onboarding case (INV-25).
- FR-17: Required terminology is enforced on every string in this issue's surfaces: "stored in this browser" framing is used; "saved to your account", "synced", "backed up", "restore", "backup", "safe", and "we'll remember" are prohibited. A copy-lint check fails the build on any occurrence in a user-facing string (INV-21, INV-5, ADR-0004 §"Export and import").
- FR-18: A connectivity failure or a failed catalog query renders as a connection problem and is visually and textually distinct from every storage state in this issue. "No data for this vehicle" is never shown for a connection problem, and a connection problem is never shown as storage loss (INV-7).
- FR-19: No copy on these surfaces states, implies, or numerically asserts a browser vendor's eviction window, quota size, or retention policy unless that behavior has been measured on the supported matrix and recorded as evidence for this issue (INV-15 honesty discipline; ADR-0004 §"Research anchors").
- FR-20: No surface in this issue implies a deferred capability. No "enable notifications", "install app", "work offline", or "sync" control appears, including as a disabled-but-visible control, and copy states plainly that the app does not notify the user while it is closed (INV-17, INV-19).
- FR-21: Interactive controls do not accept input before the hydration state is known; state resolution and every subsequent storage-state change are announced through a polite live region; the skeleton-to-content swap preserves focus and does not move it (CONSTITUTION §9 accessibility and TTI rows).

## Technical implementation contract

### Components and ownership boundaries

- **State-rendering components (server, LiveView)** — one component per `local_state` value plus the session-only, quota-pressure, quota-exhausted, and persistence-answer surfaces. They are pure functions of assigns and hold no protocol logic.
- **`DOS-M09-002` protocol layer** — emits `local_state` and the acknowledgment-failure and quarantine signals. This issue subscribes; it does not compute them.
- **`DOS-M09-001` adapter** — performs `open`, the probe round trip, `persist()`, `estimate()`, and typed error mapping. This issue calls it through the hook at the moments specified in FR-7, FR-11, and FR-12 and never re-implements a storage call.
- **Boot-hint module (client)** — the only writer of `dos_boot_state`; a two-value non-personal flag with no other consumer.
- **Copy catalog** — all user-facing strings for these states live in one reviewed content module so the copy-lint gate has a single surface to scan and the UX milestone has a single place to review.

### Data and persistence

- `localStorage` holds `dos_boot_state` only, with values `"never"` or `"has_data"`. No personal value, no identifier, no timestamp that could correlate visits (INV-3, INV-23).
- `meta.persist_granted` in IndexedDB holds the tri-state persistence answer, written once after the first meaningful write.
- The quota estimate is read live on hydration and is not persisted; a stale stored estimate would be a lie the moment the browser changed it.
- Nothing in this issue writes any server-side record. The server holds these states only in `socket.assigns` for the socket lifetime (INV-3, INV-23, INV-24.1).

### Interfaces and events

- Consumed from `DOS-M09-002`: `local_state ∈ {:hydrating, :loaded, :empty, :data_missing, :storage_unavailable}`, the read-only newer-schema flag, the quarantine list, and per-record saving/unsaved status.
- Consumed from `DOS-M09-001` via the hook: `{:ok, :durable_capable}`, `{:ok, :session_only, reason}`, `{:ok, persist_result}`, `{:ok, %{usage, quota}}` or `:estimate_unavailable`, and `{:error, :quota_exceeded}`.
- Emitted to the user: the state surfaces listed under "UX and content states", the Settings storage-status panel, and the export offers at the moments FR-10 and FR-13 require.
- No new network interface is introduced. No storage state is reported to the server as anything other than a transient assign (INV-4, INV-26).

### Failure and recovery behavior

- **Hydration deadline expires** → `:storage_unavailable` with its own copy; writes are not offered as if they would persist.
- **Probe fails** → session-only mode with the persistent banner, read-only catalog browsing, and repeated export offers. Recovery is the user changing browser settings or leaving private browsing; the copy says so without instructing on a specific vendor's menus unless that path has been verified on the matrix.
- **Boot hint says data existed, hydration returns zero** → `:data_missing` with import offered. There is no recovery path beyond import, and the copy does not invent one (INV-24.8).
- **Quota pressure** → surfaced, non-blocking, export and pruning suggested.
- **Quota exhaustion on write** → explicit message, prior state preserved, record left visibly unsaved, export offered; nothing deleted on the user's behalf.
- **Persistence denied or unavailable** → reported as-is; the product continues normally and does not retry the request in a loop or nag.
- **A storage state coinciding with a connection failure** → both are shown, and neither is described as the other (INV-7).

### Security and privacy

- No storage state, probe result, quota figure, or persistence answer is transmitted anywhere or logged in a form tied to a session (INV-4).
- The boot hint is deliberately two-valued precisely so it cannot become a fingerprinting or correlation surface (INV-3).
- Storage-status copy states the accurate privacy claim — that no personal data is stored on the server — and does not overclaim that no operator could observe a live session, matching the scoped claim ADR-0004 requires of the privacy page.
- No third-party origin, font, script, or beacon is introduced by any surface in this issue (INV-4, INV-22).

### Accessibility and performance

- WCAG 2.2 AA per CONSTITUTION §9: text contrast ≥ 4.5:1 and UI components ≥ 3:1; usable at 200% zoom and at 320 CSS px reflow width with no loss of content or function; full keyboard operability with a visible focus indicator and no keyboard traps; target size ≥ 24×24 CSS px, ≥ 44×44 where touch is primary.
- Hydration resolution and every storage-state change are announced in a polite live region; the persistent unsaved and session-only banners are reachable in reading order and are not announced repeatedly on every re-render.
- Skeletons occupy the same layout box as their resolved content so the swap causes no layout shift and no focus loss.
- These surfaces add no blocking script and no additional network request; they must not push the first-visit payload past the §9 *provisional* budgets (initial HTML + CSS + JS ≤ 250 KiB compressed, total first-visit transfer ≤ 500 KiB, zero third-party origins).

## UX and content states

Each state below is a specified screen or region with its own copy, satisfying the CONSTITUTION §9 honest-degradation-coverage row.

- **Pre-hydration skeleton (first-visit shape)** — `dos_boot_state == "never"`. Neutral, determinate, makes no claim about whether data exists.
- **Pre-hydration skeleton (returning shape)** — `dos_boot_state == "has_data"`. Garage-shaped placeholder so a returning user never perceives an empty product, even momentarily.
- **Genuine first visit (`:empty`)** — welcome and onboarding, carrying the full INV-25 statement before any data entry: records live in this browser on this device, there is no account and no server copy, and export is the only way to keep or move them.
- **Cleared or evicted (`:data_missing`)** — distinct heading and body: this browser's storage appears to have been cleared, the records are gone, there is no server copy and there never was, import from an export file is the only recovery. No cheerful welcome, no "let's get started", no implied recovery link.
- **Storage unavailable (`:storage_unavailable`)** — storage could not be used; what the user can still do; how to check browser settings in general terms; export offered for anything entered in this session.
- **Session-only mode banner** — persistent and non-dismissible: nothing is being saved, closing the tab loses everything. Shown before data entry. Paired with a prominent export affordance repeated after each meaningful entry.
- **Read-only catalog browsing** — presented as a legitimate, complete use of the product for lookups, with no broken-app framing.
- **Persistence answer (Settings)** — granted, denied, or unavailable, in plain words, with no durability or backup language attached to any of the three.
- **Quota estimate (Settings)** — usage and quota in plain units, or an honest "this browser does not report an estimate".
- **Quota pressure** — usage above 80% of quota: what it means, export and pruning suggested, nothing blocked, nothing deleted.
- **Quota exhausted** — the write did not happen, in plain language; the prior state is intact; the record is visibly unsaved; export offered.
- **Storage-status panel (always reachable)** — the full INV-25 statement, the persistence answer, the quota estimate, the last write time, and export.
- **Connection problem** — visually and textually distinct from every state above (INV-7).

Required framing throughout: "stored in this browser". Prohibited in every string: "saved to your account", "synced", "backed up", "restore", "backup", "safe", "we'll remember".

## Test plan

### Automated

- Render tests for each `local_state` and each storage state, asserting distinct headings and bodies and asserting the absence of empty-garage text during `:hydrating` (AC-1, AC-3).
- Boot-hint tests: value constraint, write timing on first meaningful write, skeleton selection, and the `"has_data"` + zero-records → `:data_missing` rule (AC-2, AC-4).
- Probe-ladder tests with injected failures at the open rung and at the probe-write rung, asserting session-only mode, banner presence before data entry, and the absence of any `localStorage`-for-records or server-storage fallback path (AC-5, AC-8).
- Persistence-request tests asserting exactly one call across a multi-write session and honest rendering of granted, denied, and unavailable (AC-9).
- Quota tests: estimate rendering, unavailable-estimate rendering, the 80% pressure threshold, and `QuotaExceededError` injection at every write site with an assertion that no write path lacks a rendered failure state (AC-10 through AC-12).
- Copy-lint gate over the content module, with negative fixtures for each prohibited word (AC-14).
- Connectivity-versus-storage distinction test driving a catalog-query failure and a storage-loss condition and comparing rendered output (AC-15).
- Deferred-capability audit over the DOM of every state (AC-16).
- Automated accessibility checks per state: contrast, reflow at 320 CSS px, zoom at 200%, keyboard traversal, focus retention across the skeleton swap, and live-region assertions (AC-18, AC-19).

### Manual/browser matrix

Run on the CONSTITUTION §9 *provisional* matrix — current and prior stable Chrome, Edge, Firefox, and Safari on desktop, plus iOS Safari 16+ and Android Chrome. Every row records what was **observed**, and an unobserved behavior is recorded as unknown rather than inferred from documentation (ADR-0004 §"Research anchors", R1):

- **Normal window, first visit:** skeleton shape, no empty-garage flash, onboarding copy, persistence request after first write, recorded answer.
- **Normal window, returning visit:** returning-shaped skeleton, no empty-garage flash on load, refresh, or back/forward.
- **Private/incognito window on each engine:** whether `indexedDB.open()` throws, provides an ephemeral database, or provides a tiny quota; the resulting rung of the ladder; banner appearing before data entry; export offer behavior; read-only catalog browsing verified working.
- **Storage blocked by browser settings** (cookies/site-data blocked, hardened privacy settings) and, where reachable, an embedded webview: same observations.
- **Cleared site data:** clear storage between visits, confirm `:data_missing` rather than a welcome, confirm import is the only offered recovery and that no recovery link is implied.
- **Quota:** constrain the origin quota by the means each engine supports, drive writes to exhaustion, and confirm the message, the preserved prior state, the visibly unsaved record, and the export offer.
- **Persistence:** record granted/denied/unavailable per engine and confirm the copy for each is free of durability language.
- **Eviction measurement:** the dormancy experiment on iOS Safari and any other engine with a documented eviction policy — visit, write, leave the origin untouched, re-visit at recorded intervals, and record whether data survived. This is a measurement task with a recorded result, not a documentation citation, and its outcome is what FR-19 permits copy to reference.
- **Accessibility passes:** one screen-reader pass per platform family across pre-hydration, first visit, cleared, session-only, and quota states; keyboard-only pass on each; 200% zoom and 320 CSS px reflow on each.

## Rollout and rollback

Rollout: these states gate the first user-facing release of any write path — CONSTITUTION §9's honest-degradation-coverage row and INV-24.5's release-blocker clause make them non-optional rather than a polish pass. They merge after `DOS-M09-002` and before `DOS-M02-003` finalizes first-run content, which consumes them. The eviction measurement runs in parallel and its results gate only the copy in FR-19, not the states themselves.

Rollback: revert the presentation commits. No schema, no server record, and no personal data is introduced, so a revert orphans nothing. Two constraints on any revert or partial rollout: the `dos_boot_state` hint must not be removed while `:data_missing` is still reachable, or a cleared-storage user would silently fall back to a first-visit welcome — the exact failure INV-24.4 and INV-24.8 prohibit; and the copy-lint gate must not be disabled to unblock a release, because a prohibited word shipping is an INV-5 breach, not a lint annoyance.

## Dependency rationale

Blocked by `DOS-M09-002`, because these are the rendered faces of the states that protocol emits; specifying copy for `:data_missing` or `:storage_unavailable` before those transitions exist would produce screens with no trigger. Blocked by `DOS-M09-001`, because the probe ladder, the persistence request, the quota estimate, and the `QuotaExceededError` path are adapter calls whose typed results this issue renders — without them the states could only be simulated, and simulated storage states are exactly what INV-24.6 warns against shipping.

Blocks the re-scoped `DOS-M02-003` (first-run, local-profile, privacy, readiness UX), which must build its onboarding on the pre-hydration and first-visit states rather than assume a device that always has storage. Blocks `DOS-M05-005` (single-vehicle dashboard), which must render a determinate pre-hydration state and must never flash a false empty garage. Blocks `DOS-M05-007` (export, import, reset, recovery controls), whose guidance about browser data-clearing as the realistic loss scenario is the copy defined here. Blocks `DOS-M09-009`, whose conformance suite automates the eviction, private-mode, and quota cases this issue specifies. Informs `DOS-M07-004`, whose QA matrix inherits the storage-eviction, quota, private-browsing, and multi-tab rows.

## Risks, decisions, and open questions

- Risk (ADR-0004 R1, named the single biggest product risk of the pivot): browsers evict script-writable storage for origins a user has not visited recently, and a person who checks their oil once a quarter is precisely that user. Mitigation: the persistence request, the honest storage-status surface, export nudges after meaningful writes, and the `:data_missing` state so loss is never disguised as an empty garage. The residual risk is real and is not closed by this issue; it is measured by it.
- Risk: a hosted URL reads to users as "my data is on their server," so silence is misread as durability. Mitigation: FR-15 and FR-16 require the statement at onboarding, on export, and at an always-reachable location, and FR-17 makes the prohibited vocabulary a build gate rather than a review habit.
- Risk: copy that cites a vendor's eviction window becomes false when the vendor changes it, and the product would then be asserting an unverified fact — the failure mode INV-15 exists to prevent in the automotive domain, applied here to platform behavior. Mitigation: FR-19 and AC-17 permit only measured, recorded behavior in copy.
- Risk: the persistence request is a permission-adjacent moment and could appear before the user sees value. Mitigation: it fires only after the first meaningful write, per ADR-0004 and CONSTITUTION §11 scenario 1, which requires no permission prompt before value is clear.
- Risk: a quota-pressure or session-only banner that is persistent by requirement becomes noise and is tuned out. Mitigation: the banners are distinct per state and the export offer is tied to meaningful entries rather than to a timer; this is re-examined on beta evidence, not adjusted by preference.
- Decision: session-only mode is offered as read-only catalog browsing rather than as a degraded garage. It is a legitimate use of the product; it simply is not a garage, and the copy says exactly that.
- Decision: `dos_boot_state` is a two-value flag and nothing more, so it cannot become a correlation surface.
- Open question: whether the `:data_missing` state should also be triggerable when the boot hint itself was cleared alongside site data — in which case a returning user is indistinguishable from a first visitor at first paint. This is a genuine limitation of the hint, it is recorded rather than papered over, and the mitigation under consideration is that the first-visit onboarding copy carries the INV-25 statement anyway, so the honest message is present in both branches.
- Open question: how prominent the export nudge should be for a durable-capable user who has never exported. Too quiet fails R1; too loud reads as anxiety. Resolve on beta evidence.
- Open question: whether any engine's private-window behavior differs enough from the three-rung ladder to need a fourth state. Answered by the matrix measurement, not by assumption.
