## Outcome

The hosted application resolves vehicles and their oil-service requirements through one read-only, impersonal, server-side query surface. `DigitalOilSticker.Catalog` sits over a `CatalogRepo` opened read-only, answers year → make → model → configuration selection plus schedule, lubricant-requirement, oil-product, and filter-fitment resolution as typed deterministic results that carry the INV-11 support statuses and INV-15 provenance, is cached by catalog `data_version`, is rate limited per socket and per client address, is measured against a stated latency budget, and accepts **no personal parameter of any kind** — so the server's request stream cannot become a de facto activity log of anyone's garage (INV-26).

## Why this matters and what it unblocks

Every search and resolve issue written before the 2026-08-01 pivot assumed an in-process read of a database sitting on the same device as the user: `DOS-M02-004` (search, filtering, selection), `DOS-M04-004` (deterministic read-only `CatalogRepo`), and `DOS-M05-002` (exact-vehicle search) all treat catalog access as a local function call with no network, no shared tenancy, and no request stream. ADR-0004 moved the catalog to the server (decision §2) and the constitution amended INV-6 to match: the catalog is queried from the server, and connectivity is required to select a vehicle or read a schedule. Nothing in the roadmap owns the resulting query layer — the pivot's gap analysis lists it as gap 4, with no existing issue to re-scope into it.

This issue closes that gap, and it closes a privacy hole at the same time. The browser architecture creates a network path the on-device architecture never had, and INV-26 exists specifically to shut it. If catalog access is built ad hoc inside LiveViews, personal values will reach the wire by accident — a VIN pasted into a lookup, an odometer value used to pick an interval, a client record id used as a cache key — and the product's central claim (INV-3, INV-4: no server-side personal record, nothing personal leaves the browser) would be false in practice while remaining true in the schema. A single audited surface with a closed parameter vocabulary makes the claim structurally enforceable and testable.

It unblocks the re-scoped vehicle-selection and requirement-display work in M02 and M05, the recommendation resolver's inputs in M05/M06 (which consume catalog results but must not re-implement queries), and the hydration path in `DOS-M09-003`, which must resolve client-held catalog references against a possibly newer `data_version` and render `unsupported` honestly instead of erroring.

## Included

- A single public query facade, `DigitalOilSticker.Catalog`, that is the only module any LiveView, controller, or test may call to read catalog data. It wraps the `DOS-M04-004` `CatalogRepo` behaviors and adds the hosted concerns: parameter validation, caching, rate limiting, budget instrumentation, and typed failure states.
- A closed selector vocabulary. Every accepted parameter is one of: a model year integer inside the INV-8 rolling window, a catalog-scoped make id, model id, configuration id, oil-product id, or filter id, a closed-vocabulary facet value, an opaque page cursor previously issued by this layer, or a page size within a capped range. Anything else is rejected before it reaches a query.
- A validator that rejects, rather than strips, unknown or extra keys, and that rejects any value failing its type/range/membership check — with a typed `:invalid_selector` error and no fallback to a "best guess" result.
- Cascading enumeration endpoints so the client never needs to type: list years, list makes for a year, list models for a year and make, list configurations for a year, make, and model, get one configuration.
- Resolution endpoints: schedules for a configuration, lubricant requirements for a configuration, compatible filters for a configuration, oil products meeting a requirement, and provenance for any returned fact.
- Typed results that always carry, alongside the payload: the INV-11 support status, the provenance/qualifier records required by INV-15, the catalog `schema_version` and `data_version`, and effective model-year context (INV-20).
- A result vocabulary that keeps four things distinct and never collapses them: a genuine value; `not_applicable` (for example, a battery-electric configuration with no engine-oil plan); `identity_only`/`unsupported` (the vehicle resolves but the maintenance fact is not licensed or not present); and a transport/query failure (INV-7). "No result" is never rendered from a failure and a failure is never rendered as "no data for this vehicle".
- A read-through cache keyed by `{data_version, normalized_query}` holding only catalog-derived values, with a bounded size and an eviction policy. Because `data_version` is part of every key, a catalog change is invalidated by construction when the new image deploys.
- Rate limiting: a per-socket token bucket on catalog events, and a per-address bucket for any HTTP-exposed catalog route, both in memory only, both returning a typed `:rate_limited` result the UI can render honestly rather than a silent empty page.
- Budget instrumentation: first-party, in-process, aggregate-only counters and timing histograms for query latency, cache hit ratio, and rejection counts, with no query parameters and no personal fields recorded, no export to any third party, and no per-connection retention (INV-4, INV-22).
- Read-only enforcement at the connection, not only in code review: SQLite read-only open mode plus `PRAGMA query_only = ON`, and a test asserting the deployed repo list is exactly `[CatalogRepo]` (ADR-0004 decision §4 and "Enforcement").
- A Logger filter contract for this layer: catalog event **names** may be logged; catalog event **parameters** may not (ADR-0004 "Logging").
- A static check that no module under `DigitalOilSticker.Catalog` references `Phoenix.LiveView`, `Plug`, or the client-storage modules, preserving ADR-0004 decision §6 so a future native client reuses this contract unchanged.

## Excluded

- **Free-text vehicle or product search on the network surface.** INV-26 names "a free-text field" among the payload contents that MUST NOT be carried, so the MVP selection path is a cascading picker over server-enumerated closed vocabularies. `DOS-M04-004`'s normalized prefix search remains valid as an in-process capability, but exposing it over the wire is a separate decision requiring an ADR and an argument that a typed term is not personal. Recorded in "Risks, decisions, and open questions"; not silently shipped in either direction.
- Any write path, any personal parameter, any per-user or per-session cache, any query log that retains parameters, and any durable identifier that could correlate one socket to another (INV-3, INV-19, INV-26).
- The recommendation resolver's verified/partial/conflict decisions and the forecast arithmetic (M05/M06 consume these results; this layer never chooses for the user).
- Catalog compilation, manifest generation, and quality gates (`DOS-M03-010`); shipping and swapping the catalog artifact on deploy (`DOS-M09-005`).
- Client-side or service-worker caching of catalog results, and any offline promise (INV-6, INV-19 — deferred).
- Screen layout, copy, and empty-state wording (UX milestone); this issue defines the states and the data the copy must describe, not the words.
- CSP, security headers, CSRF, socket origin checks, and global log redaction (the M09 internet-facing hardening issue); this issue supplies only its own parameter allowlist and Logger filter.
- Any third-party service of any kind, including hosted caches, search services, and APM agents (INV-4, INV-22).

## Functional requirements

- FR-1: `DigitalOilSticker.Catalog` is the sole public read surface for catalog data. No LiveView, controller, channel, or template calls `CatalogRepo`, Ecto, or SQL directly; a static check enforces this (INV-26 — one surface is the only surface that can be audited).
- FR-2: Every query parameter belongs to the closed vocabulary in "Included". The validator rejects unknown keys, extra keys, wrong types, out-of-range values, and non-member facet values with a typed `:invalid_selector` error, and never coerces or silently drops them (INV-26).
- FR-3: No query accepts a VIN, odometer or mileage value, service date, note, custom vehicle name, client record id, `tab_id`, session id, cookie value, or any other stable client identifier, in any position — path, query string, body, header, or socket payload (INV-26, INV-4).
- FR-4: Cascading enumeration is available for year, make, model, and configuration, each returning the closed set from which the next selector's value must be drawn, so the client never needs to originate an uncontrolled value (INV-26).
- FR-5: Resolution queries return schedules, lubricant requirements, filter fitments, and qualifying oil products for a configuration, with the intersection semantics of INV-16 preserved — a brand name or viscosity alone never proves compatibility, and filter compatibility stays part-number/configuration-specific.
- FR-6: Every result carries an INV-11 support status from exactly the set `identity_only | schedule_supported | full_product_supported | not_applicable | unsupported`, and missing data is returned as unknown or unsupported, never inferred, defaulted, or averaged (INV-11, INV-15).
- FR-7: Every recommendation-capable result carries provenance, freshness, qualifiers, and effective model-year context sufficient for the UI to satisfy INV-15 and INV-20 without a second query.
- FR-8: Results carry the catalog `schema_version`, `data_version`, and content hash from `catalog_metadata`, so the UI, the cache, and the release ledger all agree on which catalog answered.
- FR-9: A configuration, product, or filter id held in a client's hydration payload that no longer exists in the deployed `data_version` resolves to the INV-11 `unsupported` state with an explanatory qualifier — not to an error, not to a crash, and not to a substituted nearest match (ADR-0004 "Validation", INV-24.1, INV-15).
- FR-10: Query failure, rate limiting, and absent data are three distinct typed outcomes (`:catalog_unavailable`, `:rate_limited`, and an INV-11 status respectively), and the layer never returns a partial or stale result labeled as authoritative (INV-7).
- FR-11: Results are totally ordered and cursor-paginated per the `DOS-M04-004` contract, with page size capped server-side; cursors are opaque, derived only from catalog values, and contain nothing client-specific (INV-26).
- FR-12: A read-through cache keyed by `{data_version, normalized_query}` serves repeat queries, holds only catalog-derived values, is bounded in memory with a stated eviction policy, and is invalidated by construction when `data_version` changes.
- FR-13: Catalog events are rate limited per socket and catalog HTTP routes per client address, using in-memory buckets; the client address is never persisted and never logged in full (ADR-0004 "Rate limiting and abuse", "Logging").
- FR-14: The layer meets the §9 *provisional* budget — first paged result p95 ≤ 250 ms and subsequent filter p95 ≤ 150 ms, measured server-side and reported separately from network time — or the measured value is recorded and re-ratified rather than quietly missed (§9, ADR-0004 R9).
- FR-15: Instrumentation is first-party, in-process, and aggregate-only. No query parameters, no personal fields, no per-connection retention, and no export to any third-party sink (INV-4, INV-22).
- FR-16: `CatalogRepo` is opened read-only at the connection level (SQLite read-only open mode plus `PRAGMA query_only = ON`), mutation statements are rejected by the connection rather than by convention, and a test asserts the deployed repo list is exactly `[CatalogRepo]` (ADR-0004 decision §4).
- FR-17: The Logger filter for this layer allows catalog event names and denies catalog event parameters by default; adding a parameter to the allowlist requires an explicit non-personal justification recorded in the code (INV-4).
- FR-18: No module under `DigitalOilSticker.Catalog` references `Phoenix.LiveView`, `Plug`, or the client-storage modules, enforced by a static check (ADR-0004 decision §6).

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Catalog` — the public facade and the only caller of `CatalogRepo`. Client-agnostic plain Elixir; a future native client mounts the same functions.
- `Catalog.Selector` — the typed query struct plus its validator; owns the closed vocabulary and the `:invalid_selector` taxonomy. It is the single place a new parameter can be added, which is what makes an INV-26 audit finite.
- `Catalog.Cache` — bounded in-memory read-through cache keyed by `{data_version, normalized_query}`. Holds catalog values only; never holds an assign, a payload fragment, or anything derived from a client record.
- `Catalog.RateLimit` — token buckets per socket and per address, in memory, no persistence.
- `Catalog.Telemetry` — aggregate counters and histograms; parameter-free by construction because it receives the query *shape*, not the query.
- `CatalogRepo` — unchanged from `DOS-M04-004` in behavior, now running server-side and opened read-only.
- Boundary rule: LiveViews own presentation and hold hydrated personal state in assigns (INV-24.1); they pass only selectors down. Personal values never cross into this layer, and this layer has no way to accept them.

### Data and persistence

- One database: the read-only catalog artifact baked into the deploy image (ADR-0004 "Catalog database on Fly"). No volume, no LiteFS, no Postgres, no runtime writer.
- No table, cache entry, ETS row, or file written by this layer contains a personal value. There is no personal table to omit — there is no personal repo in the deployment at all.
- `catalog_metadata` (`schema_version`, `data_version`, `generated_at`, `min_app_version`, content hash) is read once at boot and exposed through `Catalog.metadata/0`; it keys the cache and stamps every result.
- Connection pool size is a **measured** configuration value recorded with its measurement, not an asserted constant; the binding property is that the connection is read-only, not its pool size. The on-device `pool_size: 1` rule from the pre-pivot plan described a single-user device and does not carry over unexamined.

### Interfaces and events

- Query functions mirror the `DOS-M04-004` behaviors — `metadata/0`, `list_years/1`, `list_makes/2`, `list_models/3`, `list_configurations/4`, `get_configuration/1`, `get_schedules/2`, `get_lubricant_requirements/1`, `search_oils/2`, `list_compatible_filters/2`, `get_provenance/2` — each taking a validated `Catalog.Selector` and returning `{:ok, result}` or a typed error.
- LiveView event names are fixed and enumerable: `catalog:select_year`, `catalog:select_make`, `catalog:select_model`, `catalog:select_configuration`, `catalog:resolve_requirements`, `catalog:resolve_products`, `catalog:resolve_filters`, `catalog:page`. The allowlist of payload keys per event is a data structure in the code, not a convention, and is asserted by test.
- Result shape: `%{status: <INV-11 status>, data: …, provenance: […], qualifiers: […], data_version: …, schema_version: …, cursor: …, total_known?: boolean}`.
- Error shape: `{:error, :invalid_selector | :rate_limited | :catalog_unavailable | :stale_cursor}` with a machine-readable reason and no free-text echo of the offending input (echoing input back would defeat FR-3's audit).
- The layer emits no outbound network request of any kind. There is no upstream API in the request path; acquisition runs at build time in CI (ADR-0004 "Secrets").

### Failure and recovery behavior

- Catalog missing, unreadable, hash-mismatched, or of an incompatible `schema_version` at boot: the application fails its readiness check and the machine does not take traffic (the readiness contract itself belongs to `DOS-M09-005`). A half-usable catalog is never served.
- Query error at runtime: `:catalog_unavailable`, surfaced to the UI as a connection/service problem that is visually distinct from "no data for this vehicle" (INV-7). No cached result is promoted to authoritative to paper over it.
- Rate limit reached: `:rate_limited` with a retry affordance; the layer never returns an empty page to a throttled caller, because an empty page reads as "nothing exists" and that would be a fabricated fact by omission (INV-15).
- Stale client catalog reference after a `data_version` change: `unsupported` per FR-9, with the user's own record intact — the vehicle they saved is theirs, in their browser, and only the catalog's opinion of it changed (INV-23, INV-24.1).
- Stale cursor after a `data_version` change: `:stale_cursor`; the caller restarts the page sequence rather than receiving rows from two catalogs interleaved.
- Cache pressure: bounded eviction, never an unbounded cache; a cache miss is a slower correct answer, never a wrong one.

### Security and privacy

- INV-26 is enforced by construction: a closed selector vocabulary, an allowlist per event, rejection of unknown keys, and no free-text field on the surface.
- The honest scope of the privacy claim, stated precisely rather than overclaimed (following ADR-0004's LiveDashboard precedent): during one socket's lifetime the server necessarily knows which configuration that socket asked about, because it must answer. What this layer guarantees is that the selection is **not persisted, not logged, not cached against anything client-specific, and not correlatable to any other visit** — there is no identifier that would let a request stream be reassembled into a person's garage across sockets or across days (INV-3, INV-4, INV-26).
- Parameters never reach logs; event names may (ADR-0004 "Logging"). Client addresses are used for rate limiting in memory only and are truncated or omitted in any log line.
- No SQL interpolation; prepared and bound parameters only; page size capped; results ordered deterministically so a caller cannot use ordering instability as an oracle.
- No third-party origin is introduced, so the CSP in ADR-0004 needs no relaxation for this layer (INV-22).
- Public scrapability (ADR-0004 R7) is acknowledged, not solved: rate limiting raises cost and does not prevent bulk collection. Any access constraint that the `DOS-M03-001` web-serving rights review imposes is implemented here as a source-level gate, and a source that is not cleared for web serving is not queryable at all (INV-15, ADR-0004 R6).

### Accessibility and performance

- No UI is shipped here, but the layer must make an accessible UI possible: it returns result counts and `total_known?` so a live region can announce "12 models" honestly (or say the count is unknown rather than guess), and returns statuses as machine-readable values rather than pre-rendered prose, so screen-reader copy is the UX milestone's to control.
- Budgets: §9 *provisional* catalog query p95 ≤ 250 ms first paged result server-side, ≤ 150 ms subsequent filter, with the LiveView event round trip p95 ≤ 150 ms measured from the client. Server time and network time are reported separately so a single-region deployment's coast-to-coast RTT (ADR-0004 "Region") is never mistaken for slow queries.
- Latency is a UX property in a LiveView app because every filter is a round trip; pagination caps, index coverage, and cache hit ratio are therefore treated as user-facing measurements, recorded with the values that produced them.

## UX and content states

This layer ships no screens; it defines the states the UX milestone must have copy for, and guarantees they are distinguishable in data rather than by inference:

- **Resolving** — a query is in flight; the UI shows a determinate pending state, never a speculative result.
- **Value present** — the fact plus its provenance and effective model-year context (INV-15, INV-20).
- **`identity_only`** — the vehicle is real and selectable, and the maintenance fact is not available; copy uses "Source unavailable" and, where trim or engine could not be resolved, "Exact configuration not verified" (INV-11, INV-21).
- **`not_applicable`** — an honest identification with no engine-oil plan, for example a battery-electric configuration; never an invented plan (INV-9, INV-11).
- **`unsupported`** — including the case where a stored client reference no longer exists in the deployed `data_version`; the user's own record remains visible and intact (FR-9).
- **No match** — the selectors are valid but resolve to nothing; distinct from all failure states.
- **Query failed** — a connection or service problem, presented as such and never as absent data (INV-7).
- **Rate limited** — a plain-language "too many requests, try again" state; never an empty result set.
- Terminology binding on any copy written against these states: "Meets the recorded requirements" (never "manufacturer approved" without a documented OEM approval), "Estimated due date" with a confidence label, "Source unavailable" / "Exact configuration not verified" rather than a generic value (INV-21).

- [ ] AC-13: A log-capture test over a scripted session asserts that catalog event parameters appear in no log line while event names may, and that no personal value appears anywhere in captured logs (FR-17, INV-4).

## Test plan

### Automated

- Selector validator property tests: generated valid and invalid parameter maps, asserting acceptance only for the closed vocabulary and typed rejection otherwise.
- Payload-allowlist test: the declared per-event key allowlist is compared against the keys the LiveViews actually push, failing on any drift — this is the mechanical form of the INV-26 audit and must run in CI, not by hand.
- Scripted-session request-stream capture asserting no personal field on the wire, complementing the log-capture test.
- Contract tests reused from `DOS-M04-004` run against the fixture catalog through the new facade, proving the hosted layer did not change query semantics.
- Support-status coverage tests over fixtures containing each of the five INV-11 statuses, including a `not_applicable` configuration and an `identity_only` configuration with no licensed schedule.
- Stale-reference and stale-cursor tests across two fixture `data_version`s.
- Fault injection: repo unavailable, repo slow past budget, cache disabled, rate limiter saturated — asserting distinct typed outcomes and no result promotion.
- Cache tests: hit/miss accounting, bound enforcement, eviction under flood, zero stale hits after a version change, key content audit.
- Rate-limit tests: threshold, window recovery, no persistence, no full address in logs.
- Read-only enforcement: repo-list assertion, attempted `INSERT`/`UPDATE`/`DELETE`/`PRAGMA` mutation rejected at the connection.
- Static checks: no `Phoenix.LiveView`/`Plug`/client-storage references under the catalog namespace; no direct `CatalogRepo` callers outside the facade; no SQL string interpolation.
- Benchmark suite producing p50/p95 server-side timings per query type against the fixture catalog, run in CI for regression and re-run on the deployed environment for the ratified figure.

### Manual/browser matrix

- On the §9 support matrix — current and prior stable Chrome, Edge, Firefox, and Safari on desktop, plus iOS Safari 16+ and Android Chrome — walk the full cascading selection and requirement resolution and confirm: results render with provenance; statuses render distinctly; and no request to any origin other than the application origin appears in the network panel (INV-22).
- Throttled-network runs (a 4G-class profile) recording observed first-result and subsequent-filter latency from the client, kept separate from the server-side p95 figure.
- Deliberate failure walkthroughs with the network interrupted mid-query and with the rate limiter forced, confirming that a connection problem and an absent fact are visually distinguishable on every affected screen (INV-7).
- A `data_version` change exercised across a live session (paired with `DOS-M09-005`'s deploy rehearsal), confirming a stored vehicle reference degrades to `unsupported` without losing the user's own record.
- Network-panel capture of a complete session, exported as evidence, showing every catalog request payload for INV-26 review by eye as well as by test.

## Rollout and rollback

Rollout: this layer is additive and introduces no schema, no migration, and no persistent state — the cache and rate-limit buckets are in memory and are rebuilt on boot. It merges behind the existing UI work and becomes load-bearing when the re-scoped M02/M05 selection screens call it. Because a catalog change is a deploy (ADR-0004), there is no separate data rollout step here.

Rollback: revert the commits. Nothing to drain, nothing to migrate, no orphaned rows possible, and no user data is touched in any direction because no user data ever enters this layer. A budget regression is a revert-or-tune decision, not a data incident. If the `DOS-M03-001` rights review later withdraws a source, the source gate turns it off without a schema change and the affected facts render as an INV-11 status.

## Dependency rationale

Blocked by `DOS-M00-002` in its re-scoped form, because the browser-MVP architecture ADR is the ratification gate that makes a server-side catalog legitimate at all; by `DOS-M04-002` and `DOS-M04-004`, because this layer serves an existing query contract rather than inventing one and needs the schema and behaviors to exist; by `DOS-M01-004` or `DOS-M03-010` for a deterministic fixture or release to query; and by the re-scoped `DOS-M03-001`, because ADR-0004 R6 makes web-serving rights a hard gate — a source not cleared for network serving must not be queryable, and that gate is implemented here.

Blocks the re-scoped `DOS-M02-004` and `DOS-M05-002`, which specify selection and search screens that now have no local database to read; `DOS-M05-001`, which wires domain contracts to hydrated state; and the resolver and forecast work in M05/M06, which consume statuses and provenance from these results. Interacts with `DOS-M09-003`, which must resolve client-held catalog references through this layer during hydration, and with `DOS-M09-005`, which ships the artifact this layer opens and owns the readiness check that keeps a bad catalog out of rotation.

## Risks, decisions, and open questions

- **Decision:** the network selection path is cascading-selector-only. INV-26 forbids a free-text field on the query surface, so MVP selection uses server-enumerated closed vocabularies. This is a real UX cost — typing "civic" is faster than three dropdowns — and it is accepted rather than hidden.
- **Open question:** whether a constrained typeahead can ever satisfy INV-26. It would require an ADR arguing that a partial model-name token is not personal, plus a demonstration that the term cannot be joined to anything else on the wire. Not attempted here.
- **Risk (ADR-0004 R7):** the catalog is publicly scrapable in a way an app bundle was not. Rate limiting raises cost; it does not prevent bulk collection. Mitigation is bounded and stated honestly; any access constraint the rights review imposes is implemented as a source gate.
- **Risk (ADR-0004 R6):** serving licensed data over a public endpoint is a materially different distribution mode than in-bundle redistribution. Mitigation: sources are gated off by default until cleared, and the gate is a code path with a test, not a note in a document.
- **Risk (ADR-0004 R9, §9):** the latency budgets are provisional and were re-derived after the pivot voided the loopback figures. Mitigation: measure on the deployed environment, report server and network time separately, and re-ratify rather than ship against a number known to be inapplicable.
- **Risk:** an in-memory cache is per-machine, so a second machine (ADR-0004 "Cost shape") halves the hit ratio rather than sharing it. Accepted; a shared cache would add infrastructure for a read-only dataset that a deploy already invalidates.
- **Risk:** a well-meaning future contributor adds a parameter "just for this one screen". Mitigation: the vocabulary lives in one module and the allowlist test fails the build, so the addition is visible in review rather than discovered in a packet capture.
- **Decision:** connection pool size and cache bounds are measured values recorded with their measurements, not inherited constants from the on-device plan.
