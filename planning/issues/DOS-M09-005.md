## Outcome

The application ships to production by deploy, not by store review. A reproducible multi-stage container image carries the OTP release, first-party assets, and the versioned read-only catalog artifact; `fly.toml` pins the single `ord` region with one always-on machine and scale-to-zero prohibited; a readiness check fails closed unless the catalog opens read-only and matches its manifest hash; secrets are set through `fly secrets set` and read in `runtime.exs`; every release carries an immutable identifier binding image digest, git commit, application version, catalog `data_version`, and client-storage `schema_version`; and a rehearsed one-command rollback restores the previous image and its exact catalog. Because a deploy drops every LiveView socket, the deploy contract explicitly includes proving that reconnect re-runs the INV-24 hydration path with no user data lost and no false empty garage shown.

## Why this matters and what it unblocks

The pre-pivot roadmap had no concept of a deployment. `DOS-M05-006` ("package and boot the Mob app reliably offline") and `DOS-M07-007` ("prepare, stage, monitor, recover the production release") were written about signed native packages, bundle identifiers, TestFlight, and store listings; the pivot's gap analysis lists Fly.io deployment as gap 5, with those two issues re-scoping *toward* it but not covering it. Nothing in the roadmap owns a Dockerfile, a region choice, a health check, a secret, a release identifier, or a rollback path.

Two things make this more than routine infrastructure work. First, ADR-0004 chose to ship the catalog **inside the image** rather than on a volume or in a managed database, which means catalog replacement, rollback, backup, and horizontal scaling are all properties of the deploy pipeline rather than of a database operations practice — the artifact swap is a deploy or it is nothing. Second, the product depends entirely on Fly.io availability (ADR-0004 "Consequences"), and with one machine every deploy drops every WebSocket. In an architecture where the server holds user state only in socket assigns (INV-24.1) and the browser is the system of record (INV-23), a dropped socket must be survivable by construction — so "a deploy is a non-event for users" is a testable claim this issue must actually prove, not an aspiration (ADR-0004 R8).

It unblocks the re-scoped `DOS-M07-007` (public web launch instead of store release), gives `DOS-M09-004` a runtime to measure its latency budget against, gives the M09 hydration work a real reconnect to test against, and is the precondition for the custom-domain and hardening issues that configure what this pipeline deploys.

## Included

- A multi-stage `Dockerfile`: a builder stage on a base image pinned **by digest** with the `DOS-M01-001` Elixir/OTP versions, dependency fetch and compile with `MIX_ENV=prod`, first-party asset build via esbuild and Tailwind with no CDN and no remote font (INV-22), `mix release`; and a runtime stage on a pinned slim base by digest containing the release, the catalog artifact, and nothing else — no build toolchain, no source, no `.env`, running as a non-root user.
- Catalog artifact handling inside the build: fetch the `DOS-M03-010` release payload, verify its SHA-256 against `catalog-manifest.json`, fail the build on mismatch, copy it to a fixed in-image path, and record its `data_version` and hash in the release identifier. The artifact is opened read-only at boot; the image is the only place it lives.
- `fly.toml`: application name, `primary_region = "ord"`, single region, `min_machines_running = 1`, auto-stop/auto-start disabled, `http_service` with `force_https`, concurrency limits sized to measured per-socket memory, VM size recorded as a measured value, and a `[checks]` block wired to the readiness endpoint.
- A liveness endpoint and a **separate** readiness endpoint. Liveness answers "the BEAM is up". Readiness answers "this machine can serve correct answers": catalog present, opened read-only, `PRAGMA query_only` verified, payload hash matching the manifest, catalog `schema_version` inside the supported window, `min_app_version` satisfied, client-storage `schema_version` known, and the release identifier populated. Readiness fails closed and the machine does not take traffic.
- Release identity: image digest, Fly release version, git commit SHA, application version, catalog `data_version` plus payload hash, and client-storage `schema_version`, assembled at build time, embedded in the release, exposed on a non-indexed version endpoint, and recorded in the release ledger. It is a build identifier and never a user identifier (INV-3).
- Secrets: `SECRET_KEY_BASE` and `PHX_HOST` via `fly secrets set`, read in `runtime.exs`; `debug_errors: false`; no `.env` in production; secrets never logged, never echoed in an error page, never baked into an image layer. A deploy-scoped Fly token held in CI repository secrets, least privilege rather than an organization-admin token. A documented rotation procedure, with the recorded property that rotation invalidates signed cookies and socket tokens but loses **no user data** because the browser is the system of record.
- Deploy execution from CI: build once, push one digest, deploy that exact digest. Deploying a locally built image is not the supported path.
- Deploy strategy and its socket consequences, written down rather than discovered: with one machine a deploy is a brief total disconnect; clients reconnect with backoff, remount, and re-run hydration (INV-7, INV-24). The rolling-versus-immediate strategy decision, and the second-machine option that would make rolling meaningful, are recorded as a bounded cost decision with the measured inputs.
- Proof that a deploy is survivable: a scripted rehearsal that deploys while sessions are live — idle, mid-selection, and with an unacknowledged mutation in flight — asserting no user data loss, no false empty-garage frame (INV-24.3), and correct pending-write re-drive from client storage.
- Rollback: a rehearsed one-command redeploy of the previous image digest, restoring the previous catalog exactly, with the forward-only client-storage consequence handled explicitly — a rollback to an application version older than the client's `schema_version` MUST enter ADR-0004's read-only "this browser holds data from a newer version" mode rather than downgrade or drop fields.
- A deploy runbook covering preflight checks, the deploy command, readiness verification, the post-deploy smoke walk, the rollback command, and the rollback verification — short enough to actually follow under pressure.
- Recording measured monthly cost in the ledger after provisioning, read from current pricing at that time (ADR-0004 "Cost shape", R10).

## Excluded

- Custom domain, DNS records, certificate issuance, HSTS enablement, canonical redirects, and the Fly/Netlify content boundary (INV-27) — the separate M09 domain-and-TLS issue. This issue deploys to the Fly-assigned hostname and hands over a working application.
- CSP and security headers, `check_origin` host list contents, CSRF configuration, rate limiting, and global log redaction — the M09 internet-facing hardening issue. This issue must not weaken any of them and provides the configuration seams they use.
- Application-store packaging, signing identities, icons, splash screens, store metadata, screenshots, and review notes. These carve out to the deferred native re-entry set (INV-1, INV-19); there is no store release in the MVP.
- Catalog compilation, quality gates, and manifest generation (`DOS-M03-010`). This pipeline consumes and verifies the artifact; it never builds or edits one, and it can never modify a catalog in place (CHANGE_CONTROL Rule 6).
- Multi-region deployment, read replicas, Postgres, Fly volumes, and LiteFS — all rejected or deferred by ADR-0004 for a read-only, deploy-versioned dataset.
- Container image signing, attestation, and SBOM generation (re-scoped `DOS-M07-005`); this issue records the digest those gates will sign.
- Public-launch monitoring, alerting thresholds, canary cohorts, and incident response (re-scoped `DOS-M07-007`); this issue supplies the readiness signal, release identifier, and rollback command they depend on.
- Any third-party runtime service: APM agents, error reporters, log shippers, hosted caches, CDNs. Third-party error reporting is specifically prohibited because `socket.assigns` holds the user's garage (ADR-0004 "No third-party anything", INV-4).
- Autoscaling policy tuning beyond the fixed always-on baseline; scale-to-zero is prohibited outright, not tuned.

## Functional requirements

- FR-1: The production image is built by a multi-stage `Dockerfile` from base images pinned by digest, produces an OTP release with `MIX_ENV=prod`, and contains no build toolchain, no source tree, no test fixtures, and no `.env` in the runtime stage.
- FR-2: All assets are first-party and built in the image (esbuild, Tailwind, self-hosted fonts). The build fails if any asset references a remote origin (INV-22, INV-4).
- FR-3: The build fetches the catalog payload, verifies its SHA-256 against `catalog-manifest.json`, and **fails the build** on mismatch, absence, or an unsupported catalog `schema_version`; the verified payload is copied to a fixed in-image path (INV-15, CHANGE_CONTROL Rule 6).
- FR-4: The image contains no personal data, no personal-data table, no personal-data migration, and no backup job; the deployed application starts exactly one Ecto repo, `CatalogRepo`, opened read-only (INV-23, ADR-0004 decision §4).
- FR-5: `fly.toml` sets `primary_region = "ord"`, one region, `min_machines_running = 1`, auto-stop disabled, `force_https`, concurrency limits from measured per-socket memory, and a VM size recorded with its measurement (ADR-0004 "Region", "Cost shape").
- FR-6: A liveness endpoint and a distinct readiness endpoint exist. Readiness returns healthy only when the catalog is present, read-only, hash-verified, version-compatible, and the release identifier is populated; it fails closed and keeps the machine out of rotation otherwise.
- FR-7: Health endpoints expose no personal data, no secret, no absolute filesystem path, and no stack trace, are excluded from indexing, and are safe to call unauthenticated (INV-4).
- FR-8: Every release carries an immutable identifier binding image digest, Fly release version, git commit, application version, catalog `data_version` and payload hash, and client-storage `schema_version`. It is exposed on a non-indexed version endpoint, written to the release ledger, and is never used as or derivable into a user identifier (INV-3).
- FR-9: `SECRET_KEY_BASE` and `PHX_HOST` are supplied by `fly secrets set` and read in `runtime.exs`; no secret is present in any image layer, build log, deploy log, or error page; `debug_errors: false` in production (ADR-0004 "Secrets").
- FR-10: CI deploys with a deploy-scoped Fly token from repository secrets, builds once, and deploys the exact digest it built; the same digest is reproducible from the same inputs.
- FR-11: A secret-rotation procedure is documented and rehearsed, recording that rotation invalidates signed session cookies and socket tokens, that clients reconnect and re-hydrate, and that **no user data is lost** because the browser is the system of record (INV-23, INV-24.1).
- FR-12: The catalog is swapped only by deploying a new image. There is no runtime path — no endpoint, no console procedure, no volume mount — by which a catalog can be replaced, patched, or partially written in a running machine (CHANGE_CONTROL Rule 6, ADR-0004).
- FR-13: A deploy never serves a half-swapped catalog: a machine either serves the old image's catalog or the new image's catalog, and readiness gates the transition (re-scoped `DOS-M04-008` requirement).
- FR-14: The deploy strategy and its socket impact are documented and measured: reconnect behavior, backoff, remount, and re-hydration are exercised, and the observed disconnect window is recorded rather than assumed (ADR-0004 R8, §9 socket-connect target).
- FR-15: A deploy performed while a session holds an unacknowledged mutation does not lose that mutation: after remount, the pending write is re-driven from client storage, and until it is acknowledged the UI shows it as unsaved rather than as saved (INV-24.2, INV-7).
- FR-16: A deploy never produces a false empty state: no client shows "no vehicles yet" or any empty-garage claim during reconnect or re-hydration (INV-24.3).
- FR-17: Rollback is one rehearsed command that redeploys the previous image digest, restoring the previous catalog exactly; rollback is verified by readiness plus a smoke walk, and the rehearsal is evidenced.
- FR-18: A rollback to an application version older than a client's stored `schema_version` puts that client into ADR-0004's read-only "newer data" mode with mutations disabled and export offered; it MUST NOT downgrade, drop unknown fields, or overwrite client data.
- FR-19: The runtime contains no third-party service integration of any kind, and no outbound request to any non-application origin occurs in the request path; catalog acquisition remains a build-time CI concern (INV-4, INV-22, ADR-0004 "Secrets").
- FR-20: A deploy runbook exists covering preflight, deploy, readiness verification, smoke walk, rollback, and rollback verification, and it is the document actually used in the rehearsals.
- FR-21: Measured monthly cost is recorded in the ledger after provisioning, read from current pricing at that time; no dollar figure is asserted from memory or from this document (ADR-0004 "Cost shape", R10).

## Technical implementation contract

### Components and ownership boundaries

- `Dockerfile` — sole authority for what enters the image. Builder and runtime stages are separated so the runtime surface is auditable by inspection.
- `fly.toml` — sole authority for region, machine count, concurrency, and check configuration. Region and scale-to-zero values are ratified by ADR-0004 and are not tunable without an ADR amendment.
- Release-identity module — assembles the identifier at build time and exposes it read-only at runtime; owned here, consumed by the ledger, by `DOS-M09-004`'s result stamping, and by the re-scoped `DOS-M07-007`.
- Readiness module — owns the catalog verification sequence and the ready/not-ready decision; it calls the `DOS-M09-004` catalog layer's metadata function rather than opening the database itself, so there remains exactly one reader.
- CI deploy workflow — owns build, digest capture, and deploy invocation; holds the deploy-scoped token and nothing broader.
- Not owned here: domain/TLS configuration, security headers, origin and CSRF configuration, rate limiting, log redaction policy. This issue provides configuration seams and must not set weaker values that the hardening issue then has to undo.

### Data and persistence

- One database in the image: the read-only catalog artifact at a fixed path, opened read-only with `PRAGMA query_only = ON`. No volume, no LiteFS, no Postgres, no runtime writer, no mutable state on the machine that matters after a restart.
- The image is the unit of catalog versioning. Backups are the git-tracked build inputs plus the deterministic pipeline, which is a stronger property than a database dump: the artifact is reproducible, not merely restorable.
- Machine-local state is limited to in-memory caches and rate-limit buckets (`DOS-M09-004`), which are rebuilt on boot and hold no personal value.
- No personal data exists on the server at any point except transiently in `socket.assigns` for the lifetime of a connection (INV-24.1). A machine replacement therefore has no data-loss dimension — this is the property the deploy rehearsal exists to demonstrate rather than assert.

### Interfaces and events

- Liveness endpoint: process-alive only, no dependencies consulted.
- Readiness endpoint: catalog present, read-only verified, hash matches manifest, `schema_version` in the supported window, `min_app_version` satisfied, client-storage `schema_version` known, release identifier populated. Returns a compact machine-readable status with a stable field set and no diagnostic detail beyond it.
- Version endpoint: the release identifier fields from FR-8, non-indexed, cacheable, containing nothing client-specific.
- CI → Fly: build, capture digest, deploy digest, poll readiness, run smoke walk, report the release identifier into the ledger.
- Client-visible protocol during a deploy: socket close → LiveView backoff reconnect → remount with `local_state == :hydrating` → hook re-hydration → pending-write re-drive. This issue does not implement that protocol (`DOS-M09-003` does); it must not break it and must prove it under a real deploy.

### Failure and recovery behavior

- Catalog missing, hash-mismatched, unreadable, or version-incompatible at boot: readiness fails, the machine stays out of rotation, and the deploy does not complete. Failing closed is preferred to serving a machine that would answer catalog queries incorrectly (INV-15).
- Deploy failure mid-rollout: the previous release keeps serving; the runbook's rollback step redeploys the previous digest explicitly rather than relying on an ambiguous partial state.
- Machine crash or replacement: a new machine boots the same image, passes readiness, and serves; connected clients reconnect and re-hydrate; no user data is involved (INV-24.1).
- Fly platform or region outage: total product outage, accepted at MVP and stated plainly (ADR-0004 R8). No copy anywhere may imply the product keeps working while the host is down (INV-7).
- Secret rotation: clients disconnect, reconnect, and re-hydrate; no data loss; documented as routine rather than exceptional.
- Rollback across a client-storage schema boundary: the read-only "newer data" mode per FR-18, with mutations disabled and export offered — never a silent field drop.
- A deploy that lands during an unacknowledged mutation: the pending write is re-driven after remount; if it still cannot be acknowledged, the record shows the non-dismissible "not saved to this browser" state rather than a false saved state (INV-24.2).

### Security and privacy

- Runtime image runs as a non-root user, contains no build toolchain, no source, no fixtures, no secrets, and no shell conveniences beyond what the release requires.
- Secrets exist only as Fly secrets read in `runtime.exs`; they never appear in an image layer, build log, deploy log, error page, or stack trace. `debug_errors: false` so no assign ever reaches an error page (INV-4).
- The CI token is deploy-scoped. Broader tokens are not used, and no credential is created by automation on the owner's behalf.
- LiveDashboard stays disabled in production; process state here means live users' vehicles and mileage, and there is no "behind basic auth" compromise at MVP (ADR-0004).
- Operator console access is for diagnosing the *application*, not *users*: no routine production console use and never attaching to inspect a live socket. The privacy claim this supports is stated precisely — "we store no personal data on the server" — and is not inflated into "no operator could ever observe a live session" (ADR-0004, INV-15's honesty standard applied to our own claims).
- Deploy and release logs record the release identifier, image digest, and machine id; they record no request parameter, no assign, and no client address in full (INV-4, ADR-0004 "Logging").
- No third-party runtime dependency is introduced, so the CSP owned by the hardening issue needs no exception for deployment tooling (INV-22).

### Accessibility and performance

- Deploy-time user experience is an accessibility surface: `phx-disconnected` styling must communicate reconnection honestly, the reconnect state must be announced to assistive technology rather than silently changing the page, and no interactive control may accept input while hydration state is unknown (§9 accessibility row, INV-24.3).
- Budgets this pipeline must not violate, all §9 *provisional*: LCP p75 ≤ 2.5 s and TTI p75 ≤ 3.5 s on a 4G-class connection and mid-tier mobile device; static-to-live socket transition p95 ≤ 1.0 s after HTML paint and automatic reconnect p95 ≤ 2.0 s; hydration completion p95 ≤ 300 ms after socket join; HTTP TTFB p95 ≤ 400 ms; first-visit payload ≤ 250 KiB compressed with **zero** third-party origins and total first-visit transfer ≤ 500 KiB; repeat-visit ≤ 60 KiB on a warm cache.
- Asset compression, cache headers, and long-lived digest-stamped asset paths are configured here because they are properties of the built image; measured values are recorded, and a missed budget is reported for re-ratification rather than absorbed (ADR-0004 R9).
- Image size is tracked per release because the catalog grows inside it; a size trend that threatens deploy time is the documented trigger to revisit the in-image decision (ADR-0004).

## UX and content states

Deployment is mostly invisible, but it produces four user-visible states that this issue must not leave to chance. Copy is owned by the UX milestone; the states and their honesty constraints are owned here.

- **Reconnecting (deploy in progress).** `phx-disconnected` styling indicates reconnection rather than freezing a stale-looking UI. The previous DOM is retained; the shell does not tear down to a skeleton (ADR-0004 "First-paint rules").
- **Re-hydrating after remount.** The neutral hydrating state, never an empty-garage claim, not even for one frame (INV-24.3).
- **Unsaved mutation across a deploy.** A write that was pending when the socket dropped is re-driven; while unacknowledged it is visibly marked unsaved, and if it fails it shows the persistent "not saved to this browser" state with export offered — never a silent rollback and never a false "saved" (INV-24.2, INV-5).
- **Rolled-back application versus newer client data.** The read-only banner stating that this browser holds data from a newer version of the app, with mutations disabled and export offered (FR-18, ADR-0004 "Schema versioning and migration").
- Prohibited framing across all four: nothing may suggest the server holds or restores the user's records. "Stored in this browser" is the required framing; "saved to your account", "synced", "backed up", and "restore" are prohibited (INV-5, INV-21, INV-25).

## Test plan

### Automated

- Image build determinism: two builds from identical inputs produce the same digest, or the sources of nondeterminism are identified and eliminated.
- Runtime-image content assertions: absence of build tools, source, fixtures, `.env`; non-root user; presence of the catalog at its fixed path with the expected hash.
- Secret-absence scan across image layers and across build and deploy logs.
- Asset audit for remote origins in built HTML, CSS, and JS.
- Catalog verification tests: matching hash passes; mismatched, absent, truncated, and version-incompatible payloads each fail the build with a distinct message.
- Repo-list and read-only connection assertions executed against the built image, not only against the dev environment.
- Readiness fault-injection matrix (one case per fault in AC-6), asserting fail-closed behavior and rotation exclusion.
- Release-identifier consistency test comparing build metadata, running application values, and the ledger entry.
- Endpoint content tests for health and version responses (no secret, no path, no stack trace, no personal field).
- A configuration test asserting `fly.toml` values against the ADR-0004 ratified set, so an accidental scale-to-zero or region change fails CI rather than production.
- Payload-budget check in CI measuring first-visit and repeat-visit transfer sizes against the §9 budgets.
- An outbound-request test asserting no non-application origin is contacted during a scripted server-side session.

### Manual/browser matrix

- Deploy rehearsal across the §9 support matrix — current and prior stable Chrome, Edge, Firefox, and Safari on desktop, plus iOS Safari 16+ and Android Chrome — with each browser holding a live session during the deploy: record the disconnect window, the reconnect, the remount, and hydration completion, and confirm no empty-garage frame and no data loss.
- Deploy with an unacknowledged mutation in flight in at least two engines, confirming the write is re-driven and correctly marked unsaved until acknowledged.
- Deploy with a backgrounded tab and with a sleeping laptop resumed after the deploy, confirming reconnect and re-hydration rather than a stale or blank view.
- Two-tab deploy: both tabs reconnect and re-hydrate, and the multi-tab consistency discipline still holds afterward (INV-24.7).
- Rollback rehearsal executed from the runbook by following it literally, including verification of the restored catalog `data_version`.
- Rollback-across-schema rehearsal: a client written by the newer application version meets the rolled-back application and enters read-only mode with its stored fields intact.
- Private-browsing and storage-blocked sessions held across a deploy, confirming the session-only banner survives reconnect and never converts into an implied-durability state (INV-24.6, INV-25).
- Throttled 4G-class runs on a mid-tier mobile device capturing LCP, TTI, socket connect, and hydration completion for the §9 record.
- Network-panel capture during first visit and repeat visit confirming zero third-party origins and recording transfer sizes.

## Rollout and rollback

Rollout: provision the Fly application and deploy-scoped CI token, land the `Dockerfile`, `fly.toml`, readiness and version endpoints, and release-identity module, then deploy to the Fly-assigned hostname and run the deploy and rollback rehearsals there before any custom domain exists. The domain cutover is deliberately a separate issue so that a hosting mistake is never simultaneously a public-DNS mistake. Once the rehearsals pass, this pipeline becomes the only supported path to production, and locally built images are no longer deployed.

Rollback: for the pipeline itself, revert the commits — no persistent server state is created, and no user data is touched in any direction. For a bad release, redeploy the previous image digest per FR-17; the previous catalog returns exactly because it is part of that image. The one asymmetry to respect is client-storage schema: application rollback is always available, but a client that has already written a newer `schema_version` enters read-only mode rather than being downgraded (FR-18), so a schema-advancing release should be treated as a higher-consequence deploy and rehearsed as such.

## Dependency rationale

Blocked by `DOS-M00-002` in its re-scoped form, because region, single-machine posture, in-image catalog, and the no-personal-row rule are ADR-0004 decisions rather than deployment preferences; by the re-scoped `DOS-M01-001`, because an image built from unpinned bases is not the reproducible artifact this contract promises; by `DOS-M01-006`, because the deploy runs from CI with a scoped token rather than from a workstation; by `DOS-M03-010` (or the `DOS-M01-004` fixture) for a manifest and payload hash to verify against — verification is not optional, so an artifact without a manifest cannot be shipped; and by owner provisioning of the Fly organization, application, and deploy token, which is a credential action that belongs to the owner and not to automation.

Blocks the M09 custom-domain and TLS issue, which needs a deployed, healthy application before DNS and certificates can point anywhere; the M09 internet-facing hardening issue, which configures headers, origin checks, and rate limits on a running deployment; and the re-scoped `DOS-M07-007`, whose staged release, canary, monitoring, and rehearsed recovery are built directly on the readiness signal, release identifier, and rollback command delivered here. It gives `DOS-M09-004` the environment its latency budget must be measured on, and gives `DOS-M09-003` the real reconnect that its hydration protocol must survive. It also absorbs the surviving spine of the re-scoped `DOS-M05-006` (reproducible build, pinned toolchain, health signal before traffic, release manifest binding versions) and the atomic-activation requirement of the re-scoped `DOS-M04-008`, with their native mechanics parked in the deferred re-entry set.

## Risks, decisions, and open questions

- **Risk (ADR-0004 R8):** single region and a single always-on machine mean a Fly or zone outage is a total product outage, and every deploy drops every socket. Mitigation is honesty plus proof: the deploy rehearsal must show reconnect and re-hydration are robust enough that a deploy is a non-event for users, and the outage exposure is stated rather than papered over.
- **Decision (deferred, bounded):** a second always-on machine would enable rolling deploys and survive a machine failure. It is a cost decision revisited on real usage, recorded with the measured inputs; it is not silently assumed by this issue's strategy setting.
- **Risk (ADR-0004 R2):** hydration latency is paid on every mount, including every reconnect, so a deploy multiplies it across all connected clients at once. Mitigation: measure hydration completion during the deploy rehearsal, not only on a quiet first visit.
- **Risk:** image size grows with the catalog, lengthening builds and deploys. Mitigation: track image size per release; a size trend that threatens deploy time is the documented trigger to revisit the in-image decision, whose fallback (a Fly volume) ADR-0004 already records.
- **Risk:** the Fly proxy's idle timeout versus the LiveView heartbeat is version-specific and must be verified during deployment rather than assumed from documentation (ADR-0004 "WebSocket and LiveView considerations").
- **Risk (ADR-0004 R10):** cost under traffic or abuse is unmeasured. Mitigation: record measured monthly cost in the ledger and set a threshold alert rather than discovering it on a bill. No dollar figure is asserted here.
- **Risk:** a rollback across a client-storage schema boundary is the one deploy operation with a user-visible cost. Mitigation: FR-18's read-only mode is mandatory, and schema-advancing releases are treated as higher-consequence and rehearsed as such.
- **Open question:** whether the readiness check should also assert a minimum successful catalog query rather than only metadata and hash verification. A query-level check catches a wider class of corruption; it also lengthens boot. To be decided with measurement during the deployment work and recorded either way.
- **Open question:** whether CI should deploy automatically on merge or require an explicit trigger. The recorded consideration is that automatic deploys drop live sockets on every merge; the decision is made and written down, not left to habit.
- **Decision:** scale-to-zero is prohibited and region is `ord`; both are ADR-0004 ratifications, and changing either requires an ADR amendment rather than a `fly.toml` edit.

## Definition of done

- All functional requirements implemented and all acceptance criteria checked, with evidence attached or linked from CI.
- The production image builds reproducibly from pinned digests, carries a hash-verified catalog, contains no secret and no build toolchain, and starts exactly one read-only `CatalogRepo`.
- `fly.toml` matches the ADR-0004 ratified hosting decisions and is guarded by a configuration test.
- Readiness fails closed on every injected catalog fault, and no machine with an unverified catalog serves traffic.
- Deploy and rollback have both been rehearsed from the runbook, across the browser matrix, with evidence that no user data is lost, no pending mutation disappears, and no false empty garage is shown.
- Secret handling and a rehearsed rotation are documented, with the no-data-loss property demonstrated rather than claimed.
- Release identifiers are recorded in the ledger for every release, and measured §9 figures and measured monthly cost are recorded with their conditions.
- The M09 domain/TLS and hardening issues and the re-scoped `DOS-M07-007` are unblocked with a deployed, healthy, rollback-capable application to build on.
