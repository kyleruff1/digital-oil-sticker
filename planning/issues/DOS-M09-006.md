## Outcome

`https://digitaloilsticker.com` is the single canonical origin of the Phoenix LiveView application on Fly.io, reachable over HTTPS with a Fly-managed certificate that renews automatically. `www.digitaloilsticker.com`, `digitaloilsticker.net`, and `www.digitaloilsticker.net` resolve and issue permanent redirects to the canonical origin with path and query preserved. Static marketing, support, privacy, and source-attribution content is served from the existing paid Netlify account (team `cDiscourse`) on its own hostnames. HSTS is enabled only after every application hostname has been verified serving correctly. A written, machine-checkable host-ownership manifest states which host owns which URL prefix, is enforced in CI, and defines exactly what happens when a stale static page links an application route that has moved: a mapped permanent redirect or an honest retired-route page, never a dead link, and never a page that implies anything about the user's stored records.

## Why this matters and what it unblocks

INV-27 makes the two-origin split a constitutional boundary, not an ops preference. The split is also forced by the platform: ADR-0002, as amended by ADR-0004, still holds that **Netlify cannot host Phoenix** — Functions run TypeScript/JavaScript/Go, Edge Functions run Deno, and there is no always-on BEAM anywhere in Netlify's product. So the interactive application must live on Fly.io and the static content may live on Netlify, and the only open questions are which hostname points where, how certificates are obtained and renewed, and what the seam does when the two halves drift apart.

That seam is the real risk. Fly deploys and Netlify deploys are independent, so a static page can outlive the application route it links. Under INV-25 a user who lands on a broken URL of ours must not be given any reason to believe their garage is affected, and under INV-15/INV-27 no static page may restate an automotive fact or a coverage claim without provenance. A domain configuration that produces bare 404s, redirect loops, or a cheerful "start over" page is therefore a product-honesty defect, not a cosmetic one.

This issue unblocks `DOS-M09-007` (the CSP `connect-src`, the LiveView `check_origin` allowlist, and the HSTS ordering all depend on a final, frozen hostname set), the re-scoped release and cutover work in `DOS-M07-007` (#69), the attribution publication obligation created by INV-15 and INV-27, and the always-reachable privacy and storage-loss content that INV-25 requires the application footer to link.

## Functional requirements

- FR-1 (INV-27): `https://digitaloilsticker.com` is the single canonical application origin. Exactly one hostname is canonical; all other owned hostnames that serve the application are redirect sources, not alternate origins.
- FR-2 (INV-27, INV-22): The complete DNS record set for both zones is recorded in the repository as the source of truth — record type, name, value, TTL, and owning host for each row — and the deployed zones are asserted to match it. `CAA` records restrict issuance to the certificate authorities Fly and Netlify actually use.
- FR-3 (INV-22): Certificates exist and validate for `digitaloilsticker.com` and `www.digitaloilsticker.com` via `fly certs add`, with the full chain served correctly. Renewal is either demonstrated or covered by an expiry alarm with a documented lead time; "Fly handles it" is not accepted as evidence.
- FR-4 (INV-27, INV-22): The redirect matrix is implemented and complete: `http` to `https` on every hostname; `www.digitaloilsticker.com` to the canonical; `digitaloilsticker.net` and `www.digitaloilsticker.net` to the canonical. Every redirect is permanent, preserves path and query, terminates in at most two hops, and contains no loop.
- FR-5 (INV-22): `PHX_HOST` is set explicitly; the `Endpoint` `:url` is configured for `https` on port 443; `force_ssl` is on; `Plug.SSL` uses `rewrite_on: [:x_forwarded_proto, :x_forwarded_host, :x_forwarded_port]`. Generated URLs and the LiveView socket URL resolve to `wss://` on the canonical host, with no mixed-content request on any page.
- FR-6 (INV-22): HSTS is enabled only after FR-3 and FR-4 are verified on every application hostname. The rollout uses a short initial `max-age` during a recorded verification window, raised to the production value only after that window passes cleanly; the exact values, the `includeSubDomains` decision, and its consequence for the static subdomains are recorded in the runbook. `preload` is not requested at MVP.
- FR-7 (INV-27): A host-ownership manifest in the repository maps every public URL prefix to its owning host, its purpose, and whether it accepts user input. The Phoenix runtime never appears under a Netlify-owned prefix (ADR-0002, unchanged). A CI check fails if a route exists in the application router that is not covered by the manifest, or if a static page is published under a prefix the manifest assigns to Fly.
- FR-8 (INV-4, INV-22, INV-3, INV-5, INV-25, INV-19): Static content on the Netlify hostnames carries no third-party script, style, font, frame, pixel, tag manager, session recorder, or analytics of any kind; collects no personal data and ships no form that could; never uses "account", "sign in", "sign up", "synced", "backed up", "saved to your account", or "restore"; and never describes the MVP as offline-capable, as notifying the user, or as installable as an app.
- FR-9 (INV-15, INV-11, INV-27): The source-attribution page is served at a stable URL, is linked from the application footer, publishes exactly the attribution the licenses in `SOURCE_REGISTER.md` require, and is covered by a check that fails when the published page and the register diverge. No static page states an interval, viscosity, capacity, filter fitment, or product claim, and no static page asserts coverage in any terms other than the five INV-11 statuses — "we support every vehicle" and equivalents are prohibited.
- FR-10 (INV-27, INV-25, INV-5, INV-7): Stale static links to moved application routes are handled by an explicit contract rather than by whatever the framework does by default. Every application route referenced by static content is either (a) currently valid, (b) present in the repository-owned redirect map with a permanent redirect to its current canonical path, or (c) explicitly retired, in which case the canonical origin answers with a real retired-route page that names the current entry point and links it. That page MUST return a correct status code (no soft-404 returning 200 with "not found" text), MUST NOT redirect the user to an unrelated page, and MUST NOT say or imply anything about the user's stored records — a routing miss is not a storage state, and the copy must not be confusable with the INV-24.4/INV-24.8 storage-loss message. A bare, unstyled 404 reached from a link the project itself publishes is a defect.
- FR-11 (INV-4, INV-26): No hostname, path, redirect target, static link, or canonical URL carries personal data. Redirects never append tracking or identifying parameters, and no static page links an application route with a query string carrying a vehicle, VIN, odometer value, note, or record identifier.
- FR-12 (INV-22, INV-27): Non-production hostnames — Fly-assigned hostnames, Netlify deploy previews, and any staging hostname — are excluded from the canonical set, are not certificate subjects for the production application, and are marked `noindex`. The frozen production host list handed to `DOS-M09-007` contains production hostnames only.
- FR-13 (INV-27): Duplicate indexing across the two owned domains is prevented: `.net` never serves content, only redirects; the canonical origin declares itself canonical; `robots.txt` on each host reflects that host's role.
- FR-14 (INV-22, INV-27): A cutover runbook exists and is followed: TTL reduction before the change, an ordered verification list (DNS resolution, certificate chain, redirect matrix, socket connectivity, static hostnames, link check, attribution sync), evidence capture at each step, and HSTS enabled last. The runbook records the honest rollback limit — DNS can be re-pointed, but an HSTS `max-age` already served cannot be recalled from browsers that received it, which is precisely why FR-6 gates it behind verification.

## Technical implementation contract

### Components and ownership boundaries

- **DNS zones** (`digitaloilsticker.com`, `digitaloilsticker.net`): the recorded record set is authoritative; changes are made by editing the recorded plan and applying it, never by an unrecorded console edit.
- **Fly application**: owns the canonical origin, the `www` application hostname, all application routes, the LiveView socket, and the retired-route response. Certificates for its hostnames are Fly-managed.
- **Netlify site (team `cDiscourse`)**: owns the static marketing, support, privacy, and source-attribution hostnames and nothing else. It never proxies, rewrites, or fronts an application route, and it never runs Elixir — Netlify has no always-on BEAM (ADR-0002).
- **Host-ownership manifest and redirect map**: repository-owned artifacts, consumed by CI checks and by the runbook. They are the arbiter when the two hosts disagree.
- **Endpoint configuration** (`runtime.exs`): owns `PHX_HOST`, `:url`, `force_ssl`, and `Plug.SSL` rewriting. It does not own CSP or security headers (`DOS-M09-007`).

### Data and persistence

- No personal data is created, stored, or transited by anything in this issue. DNS records, certificates, the manifest, and the redirect map contain hostnames and paths only (INV-3, INV-23).
- Certificates and their private keys are Fly-managed; no key material is committed, echoed into build logs, or copied into the repository.
- The redirect map and host manifest are plain files under version control, reviewed like code; there is no runtime database behind either.
- Nothing in this issue introduces an Ecto repo, a table, a cache entry, or a cookie. The deployed application's repo list remains exactly `[CatalogRepo]`, opened read-only (INV-23; asserted by `DOS-M09-007`).

### Interfaces and events

- Public interface is the hostname set itself: canonical application origin, `www` redirect source, two `.net` redirect sources, and the static hostnames.
- The frozen production host list is the artifact handed to `DOS-M09-007` for `check_origin` and for the CSP `connect-src` `wss://` entry; it is a single file so the two issues cannot drift.
- The host-ownership manifest is machine-readable and consumed by two CI checks: router coverage and static-prefix collision.
- The redirect map is consumed by the link checker and by whichever host implements a given redirect; each entry records source, target, status code, and owning host.
- The application footer links the privacy, storage-loss, and attribution URLs; those URLs are declared in the manifest, so a rename that breaks the footer fails CI rather than shipping.

### Failure and recovery behavior

- **Certificate issuance fails or a hostname does not validate**: HSTS stays off (FR-6), the cutover halts at that step, and the previous DNS target remains in place. Enabling HSTS on a partially working hostname set is the one irreversible mistake available here and the runbook says so.
- **Fly is down, Netlify is up**: static support and privacy pages remain reachable and must be able to state that the application is unavailable without claiming anything about the user's records. The application depends entirely on Fly.io (ADR-0004 §Consequences); the static half must not paper over that.
- **Netlify is down, Fly is up**: the application keeps working, but footer links to privacy, storage-loss, and attribution content fail. The application must degrade to an in-application statement of the INV-25 storage-loss facts rather than leaving the user with a dead link to its own privacy content.
- **A static page links a route that moved**: FR-10 applies — mapped permanent redirect, or an honest retired-route page. The scheduled link check catches the drift before a user does.
- **Redirect loop or missing hop after a DNS or configuration change**: the redirect-matrix test fails in CI and on the post-deploy check, and the cutover runbook's ordered verification stops the change.
- **Zone or registrar change**: recovery is re-applying the recorded record set. Because the record set is the source of truth, recovery is a file, not a memory.

### Security and privacy

- HTTPS everywhere with a valid chain; WSS for the socket; no mixed content on any page of either host (INV-22).
- HSTS after verification, never before; `preload` not requested at MVP, because preload is effectively permanent and this product has no operational history to justify it yet.
- `CAA` records limit which authorities may issue for these names.
- The static half inherits INV-4 without exception: zero third-party origins, verified by an automated scan, not by intent.
- No hostname, redirect, or published URL carries personal data (INV-26); no static page collects any.
- Non-production hostnames are excluded from the certificate subjects and from the frozen host list, so a preview hostname can never satisfy the production `check_origin` allowlist configured in `DOS-M09-007`.
- The privacy claim published on this boundary is scoped exactly as ADR-0004 scopes it: the server stores no personal data. It must not be inflated into a claim about what an operator could observe in a live session.

### Accessibility and performance

- Redirect chains are at most two hops, so a user arriving from a printed or shared `.net` link does not pay a visible latency penalty against the constitution §9 page-load budget (LCP *provisional* p75 ≤ 2.5 s, TTI *provisional* p75 ≤ 3.5 s).
- The retired-route page is a real page in the application's design system: keyboard operable, visible focus indicator, contrast at or above 4.5:1 for text, usable at 200% zoom and at 320 CSS px reflow width, and screen-reader operable, per constitution §9 accessibility.
- Static pages carry no third-party font or script, so they inherit the first-visit payload discipline (*provisional* ≤ 250 KiB compressed initial HTML/CSS/JS, zero third-party origins) rather than undercutting it.
- Certificate and redirect configuration adds no per-interaction latency to the LiveView round trip; the only measured effect is on first navigation.

## UX and content states

- **Canonical arrival**: user reaches `https://digitaloilsticker.com` directly. No visible state; the socket connects and the M09 hydration states take over.
- **Redirected arrival**: user reaches a `www` or `.net` hostname, or an `http` URL. One permanent redirect, path and query preserved, no interstitial, no flash of a redirect page.
- **Retired application route**: an honest page that says the address no longer exists, names and links the current entry point, and says nothing about vehicles, records, or storage. Required distinction: this page MUST NOT be mistakable for the INV-24.8 "your browser cleared this data" state, and MUST NOT offer import, reset, or any storage action.
- **Static page reached while the application is down**: support and privacy content renders normally and may state that the application is currently unreachable. Prohibited: any claim that data was lost, any claim that data is safe on a server, any invitation to "sign in when it's back" (INV-3, INV-5, INV-25).
- **Application reachable while static content is down**: footer links fail. The application still presents the INV-25 storage-loss facts in-application, so the required messaging is never dependent on the other host being up.
- **Certificate error**: the browser's own interstitial, which the product cannot style. This is a hard failure state and the reason FR-6 gates HSTS; the runbook treats it as cutover-blocking rather than something to explain in copy.
- **Attribution page**: renders the license-required attribution and links back to the application. Contains no interval, viscosity, capacity, fitment, or product claim (INV-15), and states coverage only in INV-11 terms.

- Manifest checks: router coverage (every route has an owner) and static-prefix collision (no static page under a Fly-owned prefix).
- Third-party-origin scan over every static page, asserting zero cross-origin requests.
- Static-copy lint for the prohibited-vocabulary list in FR-8 and for coverage claims outside the INV-11 statuses.

- Link checker over static content plus the redirect map, run in CI and on a schedule against the live canonical origin.
- Retired-route contract test: status code correctness, absence of storage-related copy, presence of a working link to the current entry point.
- Personal-data-in-URL scan across the manifest, the redirect map, and all published static links.

### Manual/browser matrix

Across the constitution §9 support matrix — current and prior stable Chrome, Edge, Firefox, and Safari on desktop, plus iOS Safari 16+ and Android Chrome:

- Enter `digitaloilsticker.net`, `www.digitaloilsticker.net`, `www.digitaloilsticker.com`, and an `http://` URL by hand; confirm a single visible navigation to the canonical origin with the deep path preserved.
- Confirm the padlock and certificate details on the canonical origin, and confirm the LiveView socket connects over `wss://` with no console mixed-content warning.
- After HSTS enablement, confirm the browser performs an internal redirect for a typed `http://` URL on a fresh profile.
- Navigate from each static page's footer or body into the application and back; confirm no dead links and no interstitial.
- Visit a deliberately retired route; read the page as a first-time user and confirm it cannot be misread as data loss.
- Simulate the application being unreachable and read the static support page; confirm it makes no claim about the user's records.
- Screen-reader and keyboard-only pass over the retired-route page and the attribution page.

## Rollout and rollback

Rollout is staged and ordered, and the order is the point. Lower TTLs on both zones first. Deploy the endpoint configuration (`PHX_HOST`, `:url`, `force_ssl`, `Plug.SSL` rewriting) and verify it against the Fly-assigned hostname before any DNS points at it. Add certificates for the apex and `www`, complete ACME validation, and verify the chain. Point DNS and verify the redirect matrix and socket connectivity. Publish the static hostnames and run the link checker and attribution sync. Only then enable HSTS with a short `max-age`, hold for the recorded verification window, and only then raise it to the production value. Restore TTLs last.

Rollback for anything before the HSTS step is re-pointing DNS to the previous target and reverting the configuration commit; the recorded record set makes that a file operation rather than a reconstruction. Rollback after the HSTS step is materially weaker and the runbook must not pretend otherwise: browsers that already received the header will refuse plaintext for the remaining `max-age`, so recovery means keeping valid TLS serving on those hostnames, not turning HSTS off. That asymmetry is the entire justification for FR-6's gate and for starting with a short `max-age`.

It also unblocks the INV-15/INV-27 attribution obligation and gives INV-25's storage-loss and privacy content the stable, always-reachable URLs the application footer must link.

## Risks, decisions, and open questions

- Risk: enabling HSTS before every hostname serves correctly causes self-inflicted, non-recallable downtime. Mitigation: FR-6's verification gate, the short initial `max-age`, and no `preload` at MVP (ADR-0004 §"Custom domain and TLS").
- Risk: Fly and Netlify deploy independently, so static content silently drifts out of sync with application routes. Mitigation: FR-10's redirect map plus a link checker that runs on a schedule against the live origin, not only at build time.
- Risk: a two-origin product invites a "sign in on the marketing site" affordance to creep in. Mitigation: FR-8's prohibited-vocabulary lint and AC-8, enforced in CI rather than in review habit (INV-3, INV-5).
- Risk: the static half is the easiest place for a well-meaning third-party font, embed, or share widget to appear, which would breach INV-4 and INV-22 on a page most people would not think of as "the app". Mitigation: the automated third-party-origin scan runs over static pages, and the same rule is written into the manifest.
- Risk: the application depends entirely on Fly.io availability (ADR-0004 §Consequences, R8), so a Fly outage takes the product down while the static half stays up and looks healthy. Mitigation: the static outage copy is specified here and is forbidden from making any claim about user records.
- Decision: exactly one canonical application origin (the apex), with `www` as a redirect source rather than an alternate origin — a single origin keeps `check_origin`, CSP `connect-src`, and cookie scope unambiguous for `DOS-M09-007`.
- Decision: `digitaloilsticker.net` is a redirect only, never a second product surface (ADR-0004; INV-27).
- Decision: static content lives on its own hostnames rather than under application paths, so that no Netlify-served path can ever sit inside the application origin's cookie or CSP scope.
- Open question: whether `includeSubDomains` is set on HSTS. It is the stronger posture, but it binds the static subdomains to HTTPS-only for the same non-recallable duration, so the decision is recorded with the ramp rather than assumed.
- Open question: whether `www` should be canonical instead of the apex if a future CDN or DNS constraint makes apex records awkward. Recorded rather than pre-decided; changing it later is a redirect-matrix change plus a re-freeze of the host list for `DOS-M09-007`.
- Open question: the exact retired-route status code per case (permanently removed versus temporarily withdrawn) is recorded per entry in the redirect map rather than fixed globally, so that correctness is auditable per route.
