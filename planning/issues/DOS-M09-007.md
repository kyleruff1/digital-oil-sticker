## Outcome

The internet-facing application enforces a hosted security boundary that replaces the retired loopback promise: HTTPS and WSS only, a strict first-party Content-Security-Policy with no `'unsafe-inline'` and no third-party origin, the full security-header set, an explicit `check_origin` host list plus CSRF verification on the LiveView socket connect and on every non-idempotent HTTP route, per-IP and per-socket rate limits with server-side payload caps that reject rather than truncate, and a session cookie carrying nothing but framework CSRF and socket-identification material. On top of that posture, two release-gating automated tests make the product's central privacy claim falsifiable: the deployed application's Ecto repo list is exactly `[CatalogRepo]` opened read-only with no personal-data table anywhere in the schema, and a scripted full session — hydrate, mutate, export, clear, import — produces no log line anywhere containing a VIN, odometer or mileage value, service date, note text, custom vehicle name, selected-vehicle identifier, hydration or mutation payload fragment, `tab_id`, or full client IP.

## Why this matters and what it unblocks

Revision 1.0.0 protected personal data with a physical fact: the endpoint bound `127.0.0.1`, so nothing off-device could reach it. INV-2 is retired precisely because restating that promise for a publicly hosted application would be a false security claim, and its protective intent now has to be carried by INV-22, INV-23, and INV-26 — which are configuration and code, not physics. ADR-0004 states the consequence plainly: the replacement boundary "is weaker in kind and therefore must be stronger in detail."

The detail that matters most is not the header set; it is the *proof*. This architecture's differentiator is that the server holds nothing. That claim is worth exactly as much as the test that fails when it stops being true. Because `socket.assigns` transiently holds a user's entire garage, the realistic leak paths are mundane: a default parameter log, an error page rendering assigns, a crash reporter serializing process state, a debug statement that survives review. Each of those turns a privacy architecture into a privacy story. The scripted-session log scan and the repo-list assertion exist so that a regression in any of them breaks the build rather than the promise.

This issue is the hosted rewrite of `DOS-M07-001` (#63), which currently reasons about a device-local endpoint and cannot be salvaged by editing; the pivot's gap analysis says the same. It unblocks the re-scoped `DOS-M07-001` threat model, which consumes this issue's evidence instead of re-deriving it, and it is a hard precondition for the closed beta (`DOS-M07-006`, #68) and the public launch (`DOS-M07-007`, #69): no external tester may reach a deployment whose privacy boundary is unproven.

## Included

- The CSP exactly as ADR-0004 specifies it, served on every response, with `'unsafe-inline'` prohibited and a per-request nonce plug as the only permitted resolution if LiveView behavior demands inline content.
- A report-only CSP phase preceding enforcement, with a same-origin report sink whose stored reports are asserted to contain no personal data.
- The remaining security headers: `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and a `Permissions-Policy` denying geolocation, camera, microphone, and payment. `frame-ancestors 'none'` carries the framing defense.
- LiveView socket hardening: `check_origin` set to the explicit production host list from `DOS-M09-006` — never `true`, never `false` — and `_csrf_token` passed through socket connect params and verified on connect.
- `protect_from_forgery` on all HTTP routes, with CSRF verification on every non-idempotent endpoint.
- Session-cookie scope: signed, `secure`, `http_only`, `same_site: "Lax"`, short `max_age`, with an allowlist test proving the cookie carries only the CSRF token and `live_socket_id`.
- Rate limiting: per-IP token buckets on HTTP requests and socket connects; per-socket limits on catalog search/filter events and on hydrate/import events; client IP read from Fly's forwarded headers through a trusted-proxy-aware plug, used in memory only and never persisted.
- Server-side payload caps enforced on hydration and import, rejected explicitly with an honest user-facing state and an export offer.
- Log scrubbing: request-parameter logging disabled, `filter_parameters` configured, a Logger filter that drops `handle_event` params by default with an explicit allowlist for non-personal events, `debug_errors: false` in production, and no assigns reachable from any rendered error page.
- Production posture: LiveDashboard disabled, development routes and code reloading absent, remote inspection and Erlang distribution disabled, and a written operator-access rule for `fly ssh console`.
- The prove-no-server-record gates: the repo-list and read-only assertion, a schema/migration scan proving no personal-data table exists, and the scripted-session log-scan test.
- The impersonal-request audit: an automated capture asserting that no request, socket payload, header, or query string carries a personal field, plus the §9 idle-capture check for outbound requests beyond the application origin.
- A dependency audit asserting that no third-party analytics, error-reporting, or beaconing package is present in the server or asset dependency trees.

## Excluded

- DNS, certificates, canonical redirects, the HSTS enablement decision, and the Fly/Netlify content split — owned by `DOS-M09-006`. This issue consumes the frozen host list and asserts the transport properties that depend on it.
- The Fly deploy pipeline, image build, release identifiers, and rollback mechanics — owned by the M09 Fly deploy-pipeline issue.
- The client-side storage adapter, the hydration protocol implementation, and the multi-tab discipline — owned by the M09 storage-adapter and hydration-protocol issues. This issue hardens the server side of the same events and must not re-specify them.
- The catalog query layer's own latency budget and caching design; this issue adds only its rate limits and its no-personal-parameter assertion.
- Authentication, authorization, accounts, anonymous user identifiers, and session persistence of any kind (INV-3, INV-19) — prohibited, not deferred.
- Web Push, service workers, and background sync (INV-17, INV-19, deferred by constitution and ADR).
- A commercial WAF, DDoS scrubbing beyond the token-bucket limits, a bug-bounty program, and an external penetration test engagement. The last is recorded as an open question rather than assumed.
- Third-party error reporting and crash analytics in any form — prohibited by ADR-0004 and INV-4, and asserted against in the dependency audit.

## Preconditions

- `DOS-M09-006` has frozen the production host list and the canonical `wss://` origin; `check_origin` and the CSP `connect-src` cannot be written correctly before that.
- The M09 Fly deploy-pipeline issue has produced a deployment whose headers, cookies, and logs can be inspected on a real environment rather than only in a test harness.
- The hydration protocol and storage adapter are implemented far enough that a scripted session — hydrate, several mutations, export, clear, import — can run end to end, because that session is the input to the log-scan gate.
- The catalog query layer exposes the search and resolve events that per-socket rate limits apply to.
- A log sink and its retention are known, so "no personal data reaches any log sink" is a testable statement about a real destination rather than about stdout alone.

## Functional requirements

- FR-1 (INV-22): All application traffic is served over HTTPS and the LiveView socket over WSS; plain HTTP redirects; no response and no page produces a mixed-content request. HSTS presence follows the sequencing established in `DOS-M09-006`.
- FR-2 (INV-22, INV-4): The CSP in ADR-0004 is served on every response, unmodified in substance: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' wss://<canonical host>; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`. `'unsafe-inline'` and `'unsafe-eval'` are prohibited in every directive. If LiveView requires inline content, the resolution is a per-request nonce plug, verified on the deployment; a blanket relaxation is a release blocker.
- FR-3 (INV-22, INV-4): The policy is first shipped in report-only mode with a same-origin report sink, reviewed, and only then enforced. Stored reports are asserted to contain no personal data; if a report field could carry one, that field is dropped before storage.
- FR-4 (INV-22): `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and a `Permissions-Policy` denying geolocation, camera, microphone, and payment are served on every response. Any future need for a denied capability is a separate decision that amends this header, never a quiet relaxation.
- FR-5 (INV-22, INV-3): `check_origin` is configured with the explicit production host list from `DOS-M09-006`. `true` and `false` are both prohibited values. A socket connect from an origin outside the list is refused, and the refusal is not distinguishable to the caller in a way that aids probing.
- FR-6 (INV-22): The LiveView `_csrf_token` is supplied through socket connect params and verified on connect; `protect_from_forgery` is applied to all HTTP routes; every non-idempotent HTTP endpoint verifies CSRF. A request or connect with a missing, stale, or foreign token is rejected.
- FR-7 (INV-3, INV-4, INV-22): The session cookie is signed, `secure`, `http_only`, `same_site: "Lax"`, with a short `max_age`, and carries only the CSRF token and `live_socket_id`. Prohibited contents, asserted by test: any vehicle, VIN, odometer value, date, note, preference, garage fragment, anonymous user identifier, `tab_id`, or any value that could correlate one visit to another. Introducing a stable identifier requires a new ADR and a privacy re-review.
- FR-8 (INV-22, INV-26): Rate limits are enforced per IP on HTTP requests and socket connects, and per socket on catalog search/filter events and on hydrate/import events. Limits are recorded as measured decisions with their rationale; the client IP is read via a trusted-proxy-aware plug from Fly's forwarded headers, held in memory only, and never persisted or logged in full.
- FR-9 (INV-24.5, INV-7, INV-25): Hydration and import payloads are validated against the ADR-0004 caps — ≤ 1 MiB decoded, ≤ 200 vehicles, ≤ 5 000 events, ≤ 20 000 readings — and an exceeded cap is rejected explicitly with a plain-language state that preserves prior state and offers export. Silent truncation is prohibited.
- FR-10 (INV-7, INV-11, INV-24.3, INV-24.6): A rate-limited or rejected request degrades honestly and distinguishably. A throttled catalog query renders as a temporary limit or connection state, never as "no data for this vehicle" and never as an `unsupported` status. A throttled or refused hydrate renders as an explicit failure of hydration, never as `:empty` and never as the storage-unavailable state, so a security control can never masquerade as data loss.
- FR-11 (INV-4): Server-side logging is structured so that no personal data reaches any sink. Request-parameter logging is disabled, `filter_parameters` is configured, and a Logger filter drops `handle_event` params by default with an explicit allowlist for non-personal events. Logs MAY contain timestamp, method/path/status/duration for non-LiveView routes, LiveView event name, error type and stacktrace, release version, machine ID, and coarse aggregate counters. Logs MUST NOT contain VIN, odometer or mileage values, service dates, note text, custom vehicle names, the specific vehicle a session selected, any hydration/mutation/import/export payload or fragment, the `tab_id`, or the full client IP.
- FR-12 (INV-4, INV-23): `debug_errors: false` in production; no error page, error response, or stacktrace rendering path can serialize `socket.assigns`. Error output is asserted to be free of personal data under induced failures at each event handler.
- FR-13 (INV-3, INV-23): A release-gating test asserts that the deployed application's Ecto repo list is exactly `[CatalogRepo]` and that its connection is opened read-only, and a schema/migration scan asserts that no personal-data table, personal-data migration, or personal-data backup job exists anywhere in the application.
- FR-14 (INV-4, INV-23, INV-24): A release-gating test drives a full scripted session — hydrate, several mutations, export, clear, import — with log capture across every configured sink, and fails if any captured line contains a VIN, odometer value, service date, note text, custom vehicle name, selected-vehicle identifier, payload fragment, `tab_id`, or full client IP. The fixture data is distinctive enough that a match is unambiguous.
- FR-15 (INV-26, INV-4): An automated audit of a full scripted session asserts that no HTTP request, socket payload, header, or query string carries a VIN, odometer reading, note, free-text field, record identifier, or stable client identifier; and that the server cannot reconstruct a garage from its request stream. Paired with the §9 idle capture asserting zero outbound requests beyond the application origin.
- FR-16 (INV-4, INV-22): A dependency audit over the server and asset dependency trees asserts the absence of analytics, tag-manager, session-recording, advertising, beaconing, and third-party error-reporting packages, and the absence of any CDN-hosted font, script, or style reference in built assets. Adding third-party error reporting requires an ADR plus a proven assigns-scrubbing layer.
- FR-17 (INV-3, INV-4): Production posture is asserted: LiveDashboard disabled, development routes and code reloading absent, remote inspection and Erlang distribution disabled, secrets read from the runtime environment and never echoed into logs, error pages, or stacktraces.
- FR-18 (INV-4, INV-5, INV-15): The published privacy claim is scoped exactly as ADR-0004 scopes it — the server stores no personal data — and is explicitly not inflated into a claim that no operator could ever observe a live session. The operator rule is written down: no routine production console use, and never attaching to inspect a live socket; console access is for diagnosing the application, not users.
- FR-19 (INV-2 retired, INV-22, INV-23, INV-26): The superseded loopback controls are recorded as replaced rather than deleted. The hosted control set here is mapped one-to-one against the protective intent of the retired binding rule, and `DOS-M07-001` (#63) is re-pointed at INV-22, INV-23, and INV-26 with this issue's evidence as its input.

## Technical implementation contract

### Components and ownership boundaries

- **Security-header plug**: sole owner of the CSP, `Referrer-Policy`, `X-Content-Type-Options`, and `Permissions-Policy` on every response, including error responses. It reads the canonical host from the frozen host list rather than hardcoding it.
- **Nonce plug** (conditional): introduced only if the deployment proves LiveView requires inline content; owns nonce generation and injection, and is the only permitted alternative to `'unsafe-inline'`.
- **Endpoint and socket configuration**: owns `check_origin`, the CSRF token flow through connect params, the session-cookie options, and `force_ssl`. It consumes `DOS-M09-006`'s host list; it does not define hostnames.
- **Rate-limit plug and per-socket limiter**: token buckets held in memory on the machine; the trusted-proxy-aware IP resolution lives here and nowhere else, so no other module ever sees a full client IP.
- **Logger filters and formatter**: own parameter filtering, the `handle_event` allowlist, and redaction. No module logs personal data directly; the filter is a backstop, not the primary control.
- **Enforcement test suite**: owns the repo-list assertion, the schema scan, the scripted-session log scan, the request-payload audit, and the dependency audit. These are release gates, not conventions (ADR-0004 §Enforcement).
- Not owned here: the storage adapter, the hydration protocol, the catalog query implementation, and the client-side UI states these controls trigger.

### Data and persistence

- The server persists no personal data of any kind. Exactly one Ecto repo, `CatalogRepo`, opened read-only; no `UserRepo` in the deployment; no personal-data table, migration, or backup job (INV-23; asserted by FR-13).
- Personal data exists server-side only as transient values in `socket.assigns` for the lifetime of one LiveView connection, and is never written to disk, database, cache, ETS, external store, or log (INV-24.1).
- Rate-limit state is in-memory, keyed by a client IP that is never persisted; buckets die with the machine and are not replicated.
- CSP reports are stored only if they are proven free of personal data; the sink is same-origin and is not a third-party service.
- The session cookie carries the CSRF token and `live_socket_id` only. `SECRET_KEY_BASE` rotation invalidates cookies and socket tokens; clients reconnect and re-hydrate from browser storage, and no user data is lost — a property worth asserting because it makes rotation cheap enough to actually perform.

### Interfaces and events

- Response headers are the primary external interface and are asserted on real responses from the deployment, not only in unit tests.
- The socket connect interface carries `_csrf_token` in connect params and is gated by `check_origin`; the frozen host list from `DOS-M09-006` is read from a single shared artifact so the two issues cannot drift.
- Rate-limited events return typed refusals that the LiveView renders as the FR-10 states; the refusal type is distinguishable from `unsupported`, from `:empty`, and from storage-unavailable.
- Cap violations on hydrate and import return an explicit rejection carrying which cap was exceeded, never a truncated payload.
- The enforcement suite exposes its results as CI artifacts consumed by `DOS-M07-001` (#63), `DOS-M07-006` (#68), and `DOS-M07-007` (#69).

### Failure and recovery behavior

- **CSP violation in production**: the report-only phase surfaces it before enforcement; after enforcement, a violation breaks a feature visibly rather than silently degrading, and the fix is a first-party asset change or a nonce, never a relaxed directive.
- **Origin check refuses a legitimate hostname**: symptom is a socket that never connects. The frozen host list is the single fix point, and the deployment check asserts every production hostname connects before launch.
- **Rate limit trips for a real user**: the UI shows a temporary-limit state that names the wait, preserves the user's in-progress input, and never implies data loss or missing catalog data (FR-10).
- **Cap exceeded on hydration**: the session enters an explicit error state with export offered; prior client state is untouched, because the client is the system of record and the server never wrote anything (INV-24.5).
- **Crash inside a request or event handler**: `debug_errors: false` means no assigns reach the response; the stacktrace is logged with the parameter filter applied; the log-scan test covers induced crashes so this path is proven rather than assumed.
- **A log sink is added or changed**: the log-scan gate runs against every configured sink, so adding a sink without re-running the gate fails the release.
- **Secret rotation**: sockets drop, clients reconnect and re-hydrate; no personal data is lost because none was held.

### Security and privacy

- The replacement boundary is public, so it is specified in detail rather than assumed: transport, origin, CSRF, cookie scope, CSP, rate limits, payload caps, logging, and production posture each have an assertion behind them.
- The honest scope of the privacy claim is fixed by FR-18: the server stores no personal data. `fly ssh console` grants an operator the technical ability to inspect a running process, so the claim is bounded by an operational rule rather than overstated as a technical impossibility.
- LiveDashboard is disabled in production with no "behind basic auth" compromise, because process state here means live users' vehicles and mileage.
- Third-party error reporting is prohibited outright; a reporter that serialized assigns would exfiltrate precisely the data this architecture exists to keep off servers.
- The catalog-query surface stays impersonal (INV-26): rate limiting keys on IP in memory, never on a user-derived value, because a per-user key would be the durable identifier INV-3 forbids.
- Rate limiting is a mitigation for scraping, not a solution (ADR-0004 R7); this issue does not claim otherwise.

### Accessibility and performance

- Every state these controls introduce — temporary limit, cap exceeded, connect refused, hydration failed — is a real UI state with an accessible name, keyboard operability, a visible focus indicator, and live-region announcement where it changes asynchronously, per constitution §9 accessibility.
- Header and CSP work adds no measurable per-interaction cost; the LiveView event round trip stays inside its *provisional* p95 ≤ 150 ms budget and HTTP TTFB inside *provisional* p95 ≤ 400 ms.
- The rate limiter is in-memory and O(1) per request; it must not add a database or network hop, which would put the §9 catalog-query budget at risk.
- The strict CSP forbids third-party fonts and scripts, which keeps the first-visit payload budget (*provisional* ≤ 250 KiB compressed, zero third-party origins) structurally enforced rather than aspirational.

## UX and content states

- **Temporary limit reached**: plain-language state naming that the app is limiting requests briefly, preserving input, offering retry. Prohibited: presenting it as missing catalog data, as an `unsupported` vehicle, or as anything about stored records (INV-7, INV-11).
- **Hydration refused or capped**: an explicit hydration-failure state that is visually and textually distinct from `:empty` and from storage-unavailable, states what happened, and offers export. It must never read as "your garage is empty" (INV-24.3) and never as "your browser cleared this data" (INV-24.8) unless that is genuinely what happened.
- **Import rejected for exceeding a cap**: names the cap exceeded, confirms nothing was changed, and offers the file back to the user unmodified.
- **Socket refused by origin check**: the app cannot go live; the shell shows the honest connection-problem state rather than a partially interactive page, and does not present stale catalog data as authoritative (INV-7).
- **Error page**: carries no assigns, no stacktrace, and no vehicle or record content; states what failed at the level of the application, not the user's data.
- **Privacy content**: states the claim in FR-18's exact scope — records live in this browser, the server stores no personal data — and does not overclaim about operator access (INV-5, INV-15, INV-25).

## Test plan

### Automated

- Header assertions against live responses from the deployment for every route class — application page, static asset, redirect, and error response — covering the CSP and each security header.
- CSP regression test that fails on any appearance of `'unsafe-inline'`, `'unsafe-eval'`, or a non-first-party origin in any directive other than the canonical `wss://` `connect-src` entry.
- Origin-check tests: accepted for each production hostname, refused for a foreign origin, and a configuration test asserting `check_origin` is neither `true` nor `false`.
- CSRF tests: socket connect without and with a valid token; non-idempotent HTTP endpoints without and with a valid token.
- Cookie-contents allowlist test decoding the session cookie and failing on any key outside the permitted set.
- Rate-limit tests: per-IP HTTP and connect thresholds, per-socket catalog-query and hydrate/import thresholds, plus a test that the resolved client IP never appears in persisted state or logs.
- Cap tests at and above each ADR-0004 boundary, asserting explicit rejection, preserved prior state, and no truncation.
- State-distinguishability tests asserting that throttled and refused paths render limit/failure states rather than `:empty`, storage-unavailable, or `unsupported`.
- Repo-list and read-only assertion, plus the schema/migration scan for personal-data tables.
- Scripted-session log-scan gate over hydrate, mutations, export, clear, and import with distinctive fixture values, run against every configured sink and including induced crashes.
- Request-payload audit over the same scripted session, plus the §9 idle-capture check for outbound origins.
- Dependency and built-asset audit for third-party packages and external references.
- Production-posture assertions for LiveDashboard, dev routes, code reloading, remote inspection, and distribution.

### Manual/browser matrix

Across the constitution §9 support matrix — current and prior stable Chrome, Edge, Firefox, and Safari on desktop, plus iOS Safari 16+ and Android Chrome:

- Load the application with the browser console open and confirm zero CSP violations and zero mixed-content warnings during a full session.
- Confirm in the network panel that every request goes to the application origin and that no request carries a personal field.
- Inspect the session cookie in each browser's storage inspector and confirm its flags and that its decoded contents match the allowlist.
- Drive the rate limit deliberately and read the resulting state as a first-time user; confirm it cannot be misread as missing data or data loss.
- Attempt an oversized import and confirm the rejection names the cap and leaves the browser's records untouched.
- Force a server error and confirm the error page shows no vehicle, record, or stacktrace content.
- Attempt a socket connect from a foreign origin using a scratch page and confirm refusal.
- Screen-reader and keyboard-only pass over the temporary-limit, cap-exceeded, and hydration-failure states, confirming accessible names and live-region announcement.

## Rollout and rollback

Roll out in the order that makes each control observable before it is enforced. Ship the security headers with the CSP in report-only mode first, collect and review reports, and resolve any inline-content requirement with a nonce plug rather than a relaxed directive. Enable CSP enforcement. Then land origin and CSRF hardening and the cookie-scope change, verifying socket connectivity on every production hostname. Then land rate limits and payload caps with generous initial thresholds, observe, and tighten to the recorded values. Land log scrubbing and the production-posture changes with the enforcement suite wired as a release gate from the moment it exists, so a regression cannot ship while the suite is still "informational".

Rollback is per-control and cheap for everything except reputation: each control is configuration in the release, so reverting the commit and redeploying restores the prior behavior, and no data migration is involved because there is no data. Two honest limits. First, the enforcement gates are not rollback candidates: if the repo-list, schema-scan, log-scan, or payload-audit gate fails, the correct response is to fix the leak, because disabling the gate would restore the release while removing the only proof of the claim the product makes. Second, HSTS sequencing belongs to `DOS-M09-006` and inherits its non-recallable `max-age` limitation; nothing in this issue can undo it.

## Dependency rationale

Blocked by `DOS-M09-006`, because `check_origin` and the CSP `connect-src` are meaningless without a frozen production host list and a canonical `wss://` origin, and because HSTS sequencing is owned there. Blocked by the M09 Fly deploy-pipeline issue, because headers, cookies, logs, and production posture must be asserted against a real deployment rather than a config file. Blocked by the M09 hydration-protocol and storage-adapter issues, because the log-scan gate's input is a full scripted session — hydrate, mutate, export, clear, import — that cannot be driven until those exist; a gate that runs against a stub proves nothing.

This issue blocks the re-scoped `DOS-M07-001` (#63): the threat model for a public internet-facing server consumes this issue's control set and evidence rather than re-deriving them, and its loopback-era FR-2 is superseded here. It blocks `DOS-M07-006` (#68), because no external tester may reach a deployment whose privacy boundary is unproven, and `DOS-M07-007` (#69), whose launch gate includes the INV-4 and INV-26 checks this issue automates. It also supplies the INV-22, INV-23, and INV-26 verification rows that constitution §10 routes to Browser Delivery & Hosted Transport.

## Risks, decisions, and open questions

- Risk: the strict CSP is unverified against LiveView's runtime behavior — transitions, JS commands, uploads (ADR-0004 R3). Mitigation: the report-only phase, and a per-request nonce plug as the only permitted resolution; `'unsafe-inline'` is a release blocker, not a fallback.
- Risk: a future dependency or a well-meaning debug statement reintroduces personal data into logs. Mitigation: the log-scan gate runs on every release across every configured sink, with distinctive fixture values, so the regression fails the build.
- Risk: log scrubbing cannot cover a third-party library that serializes process state on crash. Mitigation: third-party error reporting is prohibited outright and asserted against in the dependency audit — the control is exclusion, not filtering.
- Risk: rate limiting is a mitigation for catalog scraping, not a solution (ADR-0004 R7), and licensing review may impose access constraints that change the product surface. Recorded, not solved here.
- Risk: a rate limit or refusal is misread by a user as data loss or as an unsupported vehicle. Mitigation: FR-10 and AC-8 make state distinguishability a tested requirement rather than a copy preference.
- Risk: an "anonymous" identifier is introduced later for a defensible-sounding operational reason and quietly becomes an account. Mitigation: FR-7's cookie allowlist test fails on any new key, and ADR-0004 requires a new ADR plus privacy re-review for any stable identifier.
- Decision: `check_origin` is an explicit host list, never `true` and never `false`.
- Decision: rate limits key on in-memory client IP only; no user-derived key exists to key on, and creating one would breach INV-3.
- Decision: LiveDashboard stays disabled in production with no basic-auth compromise at MVP.
- Decision: the privacy claim is scoped to server storage, with operator access bounded by a written operational rule rather than an overstated technical claim.
- Open question: the exact rate-limit thresholds and burst allowances, which must be measured against real interaction patterns rather than guessed; recorded with their measurements when set.
- Open question: whether a same-origin CSP report sink is worth keeping after enforcement, given that every stored report is one more thing to prove free of personal data.
- Open question: whether an external penetration test is warranted before public launch. Recorded here rather than assumed; it is a scope and cost decision for the Hardening and Release milestone, not a silent omission.

## Definition of done

- All functional requirements are implemented and all acceptance criteria are checked, with the evidence above attached or linked from CI.
- The CSP is enforced with no `'unsafe-inline'`, the security headers are served on every response, and the deployment shows zero CSP violations and zero mixed-content warnings during a full session on the supported browser matrix.
- Origin, CSRF, cookie-scope, rate-limit, and payload-cap controls are live and tested, and every refusal path renders a state distinguishable from missing data and from storage loss.
- The four proof gates — repo list and read-only, schema scan for personal-data tables, scripted-session log scan across every sink, and request-payload plus idle-capture audit — are wired as release-blocking checks and pass.
- The dependency audit shows no third-party analytics, beaconing, or error reporting anywhere in the server or asset trees.
- The written operator-access rule, the scoped privacy claim, and the loopback-to-hosted control mapping are merged, and `DOS-M07-001` (#63) is re-pointed at INV-22, INV-23, and INV-26.
- `DOS-M07-001` (#63), `DOS-M07-006` (#68), and `DOS-M07-007` (#69) are unblocked with a tested, evidenced hosted privacy boundary rather than an asserted one.
