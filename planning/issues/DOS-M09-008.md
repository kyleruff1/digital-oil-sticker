## Outcome

The product has a named, tiered, testable **browser support matrix** — which browser engines, browser versions, and host operating systems are supported, at what support tier, and what a user on an untested browser is honestly told — and an executable **storage-behavior conformance suite** that exercises the client-storage behaviors that actually break users rather than the ones that are convenient to test. The suite covers availability probing, hydration, forward schema migration, eviction and the storage-loss state, private-browsing and blocked storage, quota exhaustion, multi-tab concurrent writes, socket-drop and reconnect re-hydration, and export/import round-trip fidelity, and it runs the same assertions on every Tier 1 engine. Its output is a machine-readable conformance report per engine that becomes release evidence. The `Browser support matrix` and `Multi-tab consistency` rows of [CONSTITUTION.md](../../docs/product/CONSTITUTION.md) §9 move from *provisional* to measured, with a re-ratification proposal carrying the measured values.

## Why this matters and what it unblocks

The 1.0.0 plan verified durability on two physical phones under our control. The browser MVP has no such surface: storage durability is now decided by a browser vendor's eviction policy, by whether the user is in a private window, by how much disk the device has left, and by how many tabs are open — none of which the product controls and none of which the existing device matrix models. [ADR-0004](../../docs/architecture/ADR-0004-browser-first-client-and-hosting.md) records storage eviction as **the single biggest product risk of the pivot** (R1) precisely because the natural usage cadence for an oil reminder — a visit every few months — is the profile most exposed to it, and it requires that per-browser eviction behavior be **measured, not assumed from documentation**. Nothing in the roadmap measures it today ([PIVOT-2026-08-01](../../docs/governance/PIVOT-2026-08-01-ROADMAP-RECLASSIFICATION.md) gap 8).

This issue is where INV-24's eight sub-clauses stop being prose and become failing tests. It converts the constitution's `Honest-degradation coverage` §9 row — "every INV-7, INV-24.3–24.8, and INV-25 state has a specified screen and an automated or scripted test" — from an aspiration into a gate. It unblocks the re-scoped `DOS-M07-004` (cross-browser QA matrix), supplies `DOS-M04-010` with the conformance envelope it certifies, gives `DOS-M07-003` the per-engine measurements its budgets need, and gives `DOS-M07-007` the pre-cutover evidence that a release is safe on more than the author's own browser.

## Included

- A ratified `SUPPORT_MATRIX.md` naming supported engines, browser versions, host operating systems, and support tiers, with an explicit tier definition (what a tier promises, what gates release on it, and what happens when a tier fails).
- A version policy expressed as a rule rather than a frozen list, so the matrix does not silently rot as browsers ship: which release channels count, how a newly released stable version enters the matrix, and how an aged-out version leaves it.
- Runtime capability probing (feature detection) as the production mechanism for deciding what a given browser can do — never user-agent sniffing.
- The honest advisory shown when a required capability probe fails on an untested browser, reusing the INV-25 storage-loss and storage-unavailable copy owned by `DOS-M09-004` rather than inventing a second vocabulary.
- An executable conformance suite with one assertion set per storage behavior, run against every Tier 1 engine: availability probe, hydration from empty, hydration from populated, forward schema migration, newer-payload read-only mode, evicted/cleared store, private-browsing and blocked storage, quota exhaustion, multi-tab concurrent writes, socket drop and reconnect re-hydration, and export/import round trip.
- Deterministic simulation harnesses for behaviors that cannot be waited out in CI: evicted store, quota exhaustion, blocked IndexedDB, and absent `BroadcastChannel`.
- A separately scheduled, real-device **eviction observation** whose result is recorded as measured evidence, plus an explicit statement of what remains unmeasured until it completes.
- A machine-readable conformance report per engine and per run, retained as release evidence, plus the CI wiring that makes Tier 1 failures block a release.
- Cross-engine assertions for the impersonal-query and no-third-party-origin rules (INV-4, INV-22, INV-26) and for cookie contents (INV-3), because these are engine-observable and cheap to regress.
- Conformance coverage of the Netlify static origin at the same tiers for reachability, absence of third-party origins, and absence of account-implying copy (INV-27).
- The measured values and the re-ratification proposal for the §9 `Browser support matrix` and `Multi-tab consistency` rows.

## Excluded

- Implementing the storage adapter, the hydration protocol, or the copy under test — owned by `DOS-M09-002`, `DOS-M09-003`, and `DOS-M09-004`. This issue tests them and may only file defects against them.
- Server-side security hardening and the "no personal-data table" proof — owned by the milestone's hardening issue. This suite asserts client-observable behavior only.
- Any service worker, web app manifest, installability path, or Web Push subscription — deferred and decided by `DOS-M09-009` (INV-6, INV-17, INV-19). The suite MUST assert their absence, not their behavior.
- Native iOS/Android device matrices and the retained Motorola Razr Ultra 2025 evidence — parked with the native re-entry set (INV-1).
- Load, soak, and concurrency testing of the server; catalog data-quality gates (`DOS-M03-010`); and the forecast property tests (M06).
- Any telemetry, real-user monitoring, or field beacon to collect browser data from actual users (INV-4). Matrix evidence comes from our own runs, not from users' sessions.

## Functional requirements

- FR-1: `SUPPORT_MATRIX.md` names each supported combination as **engine × browser × host OS × support tier**, and states for each tier what is promised, what is gated, and what is merely observed. Tier 1 baseline is the §9 row: current and prior stable release of Chrome, Edge, Firefox, and Safari on desktop, plus iOS Safari 16+ and Android Chrome (INV-1, §9).
- FR-2: The matrix records the engine behind each browser and does not double-count shells that share an engine. Where a platform constrains which engines a browser may use, that constraint MUST be verified at matrix-authoring time and recorded with its verification date — never assumed from memory (INV-15's honesty standard applied to platform facts).
- FR-3: The version policy is a rule, not a list: it states which channels are in scope, how a new stable release enters the matrix, how an old version ages out, and the maximum time a Tier 1 browser may go un-run before its row is marked stale.
- FR-4: Production code decides capability by **runtime feature probe**, never by user-agent string. The suite asserts that no user-agent-conditional branch exists in the shipped client bundle (INV-24.6).
- FR-5: A browser outside the matrix is not blocked. If every required capability probe passes, the app runs normally. If a required probe fails, the app enters the already-specified `:storage_unavailable` / session-only state and says so in the INV-25 vocabulary — it MUST NOT display a generic "unsupported browser" wall and MUST NOT imply data is being kept (INV-5, INV-24.6, INV-25).
- FR-6: **Availability conformance.** On each Tier 1 engine the suite asserts the fallback ladder: IndexedDB opens and a probe write/read/delete round-trips → durable-capable; open or probe fails → session-only mode with a persistent banner and prominent export, with no silent fallback to `localStorage` for records and no fallback to server storage (INV-23, INV-24.6).
- FR-7: **Hydration conformance.** For an empty store and for a populated store the suite asserts: the static render and pre-hydration live render show the skeleton; `:hydrating`, `:empty`, `:data_missing`, and `:storage_unavailable` render distinctly; no empty-garage claim appears in any frame before hydration resolves; and hydration either resolves or surfaces an explicit failure state within the specified deadline rather than hanging (INV-24.3).
- FR-8: **Idempotence and re-hydration.** Hydrating the same payload twice produces identical assigns and emits no write-back; a socket drop followed by reconnect re-runs hydration, restores the same state, and does not tear the view down to a skeleton (INV-7, INV-24.1).
- FR-9: **Migration conformance.** Recorded fixtures of every prior `schema_version` hydrate, migrate forward, and write back the migrated payload in the same round trip; a payload newer than the server's version puts the session into read-only mode with the explicit banner, disables mutations, offers export, and writes nothing (INV-23, INV-24.2).
- FR-10: **Eviction and cleared-storage conformance.** With `dos_boot_state == "has_data"` and an empty store, the app renders the `:data_missing` storage-loss state — distinguishable in copy from a genuine first visit — offers import, and never presents a cheerful empty garage (INV-5, INV-24.4, INV-24.8, INV-25).
- FR-11: **Quota conformance.** A write that fails with a quota error surfaces a quota-specific plain-language message, preserves the prior state, offers export, and never silently drops data or silently truncates a payload; a store above the estimate threshold surfaces the usage warning (INV-24.5, §9 client storage footprint).
- FR-12: **Private-browsing conformance.** In each engine's private/incognito mode the suite asserts that the user is told **before entering data** that nothing will persist, that the mode is not silently degraded to in-memory state that looks durable, and that export remains reachable (INV-24.6).
- FR-13: **Multi-tab conformance.** Two tabs on one origin: a commit in tab A is reflected in tab B; a stale-`seq` commit is rejected by the compare-and-set and surfaces the re-hydration notice rather than silently overwriting; where `BroadcastChannel` is unavailable the compare-and-set still prevents lost-update corruption and the divergence surfaces on the next hydration (INV-24.7, §9 multi-tab row).
- FR-14: **Export/import round-trip fidelity.** Export → clear store → import reproduces the garage, service history, odometer readings, reminder intent, and preferences byte-for-byte at the record level; the content hash verifies; replace and merge are distinct, previewed with counts, and never silently merged; unknown record-level keys written by a newer version survive the round trip unchanged (INV-5, INV-23).
- FR-15: **Catalog references are re-resolved, never replayed.** After import, catalog-referenced facts are resolved against the deployed catalog at render time; a reference whose `data_version` moved renders as the appropriate INV-11 status (`identity_only`, `unsupported`, `not_applicable`) and never as a remembered interval, viscosity, capacity, or product claim carried in the export file (INV-11, INV-15).
- FR-16: **Connection failure is not a data status.** With the socket down or a catalog query failing, the suite asserts an explicit connection state, asserts that no stale or partial catalog result is presented as authoritative, asserts that no fallback interval is fabricated, and asserts that a connection problem is visually distinct from "no data for this vehicle" (INV-7, INV-11, INV-15).
- FR-17: **Privacy assertions per engine.** For a full scripted session the suite captures network traffic and asserts: zero requests to any origin other than the application origin; no request path, query string, body, header, or socket payload carrying a VIN, odometer value, note, record identifier, or stable client identifier; and cookies limited to session and CSRF with no personal value and no stable identifier (INV-3, INV-4, INV-22, INV-26).
- FR-18: **Static-origin conformance.** The Netlify-served static pages are checked at the same tiers for reachability, zero third-party origins, absence of account-implying copy, and presence of the attribution required by the source register (INV-22, INV-27, INV-15).
- FR-19: Every run emits a machine-readable conformance report keyed by engine, browser version, host OS, tier, and application release identifier, listing each assertion as pass, fail, or **unproven-because-unrun** — with no third outcome that can be mistaken for a pass.
- FR-20: An engine that cannot be executed in a run is reported as unproven and, at Tier 1, fails the run. Silently skipping an engine is prohibited.
- FR-21: A scheduled real-device eviction observation records, per observed browser, what actually happened to a populated origin store after a dwell period with no visits. Vendor documentation MAY inform the observation design; only the measured result may be recorded as fact (ADR-0004 R1).
- FR-22: The suite asserts the absence of deferred capabilities on the shipped client: no service worker registration, no web app manifest, no push subscription, and no background sync (INV-6, INV-17, INV-19).
- FR-23: Per-engine timings for hydration completion, socket connect, and first-visit payload are recorded against the §9 provisional budgets, and the measured `Browser support matrix` and `Multi-tab consistency` values are submitted as a re-ratification proposal rather than silently edited into §9.

## Technical implementation contract

### Components and ownership boundaries

- `SUPPORT_MATRIX.md` is the single authority for tiers, engines, versions, and the version policy. No test file, CI job, or product surface may name a supported browser that the matrix does not list.
- The conformance suite lives entirely in the test tree and ships no production code. It owns fixtures, harnesses, drivers, and the report writer.
- The suite drives the application through its public UI and through the **documented** protocol event names owned by `DOS-M09-003` (`local_store:hydrate`, `local_store:put`, `local_store:ack`, `local_store:conflict`). It MUST NOT reach into undocumented internals; if an assertion needs a seam that does not exist, the seam is added to `DOS-M09-003` as a documented interface, not improvised in a test.
- A thin driver abstraction hides the multi-engine automation toolchain so that assertions are written once and executed per engine. The toolchain and its version are pinned by `DOS-M01-001`; this issue names engines, not tool versions.
- Simulation harnesses (evicted store, quota exhaustion, blocked IndexedDB, absent `BroadcastChannel`) are separate, individually documented modules, each stating exactly which real-world condition it approximates and which it does not.
- The report writer is the only component that produces release evidence; CI consumes its output and does not re-derive pass/fail from console text.

### Data and persistence

- All fixtures are **synthetic**. No real VIN, no real odometer history, no real personal note may enter the fixture set (INV-4). Fixtures use obviously synthetic markers so a leaked value is identifiable in a log scan.
- One recorded envelope fixture per historical `schema_version`, retained permanently. Deleting an old fixture is prohibited; it is the only proof that a user's aged store still migrates.
- Seeded storage states are constructed through the adapter's public API where possible, and by direct IndexedDB seeding only for states the adapter cannot legally produce (a store written by a newer version; a store emptied under a `has_data` boot hint).
- The suite writes only to disposable origins and disposable browser profiles. It MUST NOT run destructive storage assertions against the production origin.
- Conformance reports and network captures are CI artifacts with a stated retention period; captures are scanned before retention so that no synthetic-but-personal-shaped payload is retained beyond its run without being flagged.

### Interfaces and events

- Report schema: a versioned JSON document — run identifier, application release identifier, catalog `data_version`, engine, browser version, host OS, tier, and an assertion array of `{id, requirement, status, evidence_ref}` where `status` is one of `pass`, `fail`, `unproven`.
- CI contract: Tier 1 `fail` or `unproven` blocks the release job. Lower tiers record and report without gating unless the matrix says otherwise.
- The suite consumes the copy strings owned by `DOS-M09-004` from a single shared source rather than duplicating them, so a copy change breaks the test that asserts it instead of quietly diverging.
- Network assertions consume the same allowlist that the CSP declares (INV-22), so a CSP change and a test change cannot drift apart.

### Failure and recovery behavior

- A Tier 1 assertion failure is a release blocker; there is no "known failure" list that silently accumulates. A failure is either fixed, or the matrix is amended by a dated revision explaining the reduced promise.
- Flake policy: a re-run is permitted only with the flake recorded in the report. Three recorded flakes on one assertion promote it to a defect against the assertion or the behavior — quarantining without a defect is prohibited.
- Engine unavailable (toolchain break, vendor build pulled): reported `unproven`, which fails Tier 1. The run does not pass by omission.
- Timing-sensitive assertions (hydration deadline, 2 000 ms ack timeout) assert **observable behavior at the boundary** — that the timeout state renders — rather than asserting a wall-clock number that will flake in CI; the wall-clock measurements are recorded separately as budget evidence.
- The real-device eviction observation cannot fail a CI run; an incomplete observation is reported as unmeasured, and the matrix says so plainly rather than implying the behavior is known.

### Security and privacy

- The suite is an evidence producer, not a data collector. It gathers nothing from real users and introduces no field instrumentation (INV-4).
- Network captures are asserted against and then treated as sensitive artifacts: scanned for personal-shaped values, retained only for the stated period, and never published to a public location.
- Cookie assertions verify `Secure`, `HttpOnly` where applicable, `SameSite` restriction, absence of personal values, and absence of any stable identifier that could correlate two visits (INV-3, INV-22).
- Impersonal-query assertions inspect the full request surface — path, query string, body, headers, and socket payload — because INV-26 binds all five, not just the URL.
- Test credentials, deploy tokens, and environment secrets are never written into reports or captures.

### Accessibility and performance

- Every Tier 1 engine runs the accessibility assertions from §9: text contrast, 200% zoom, 320 CSS px reflow, full keyboard operability with a visible focus indicator and no keyboard traps, target size, and live-region announcement of due-state and hydration changes. An engine that passes storage conformance but fails accessibility fails the tier.
- Screen-reader operability is verified in the manual matrix, not asserted by automation alone; automated checks are treated as a floor, never as proof of operability.
- Recorded per engine against the §9 provisional budgets: LCP, TTI, LiveView socket connect, hydration completion, event round trip, and first- and repeat-visit payload. Recorded as measurements feeding re-ratification, not asserted as thresholds until those rows are re-ratified.
- The suite's own runtime is budgeted so the Tier 1 sweep stays inside the CI window; simulation harnesses exist partly so that eviction and quota cases cost seconds rather than days.

## UX and content states

This issue ships no new screens, but it owns one user-facing decision and asserts many others.

- **Owned — the untested-browser advisory.** There is no user-agent wall and no "please use a supported browser" gate. Capability is probed at runtime; if the probes pass, the app behaves normally regardless of whether the browser is in the matrix. If a required probe fails, the user sees the existing `:storage_unavailable` / session-only state in the INV-25 vocabulary: records are not being kept in this browser, closing the window loses them, there is no account and no server copy, and export is offered. No new wording is invented here (INV-5, INV-24.6, INV-25).
- **Asserted, not owned.** `:hydrating` skeleton, `:empty` genuine first visit, `:data_missing` storage-loss, `:storage_unavailable`, session-only banner, quota-exceeded message, unsaved-mutation state after a failed or timed-out ack, multi-tab "reloaded from this browser's newer data" notice, connection-down state, and the INV-11 catalog statuses. All are owned by `DOS-M09-004` and the M02 content contract; this suite pins them so they cannot regress silently.
- **Prohibited across every engine.** "backup", "synced", "safe", "we'll remember", "your account", "restore", and any empty-garage claim rendered before hydration resolves. These are asserted as absent, per engine, in the rendered DOM (INV-5, INV-21, INV-24.3, INV-25).

## Test plan

### Automated

- Matrix-integrity tests: every engine named in CI exists in `SUPPORT_MATRIX.md` and vice versa; no orphan tier; version policy fields present.
- Static check of the client bundle for user-agent-conditional branching (FR-4) and for service worker / manifest / push / background-sync registration (FR-22).
- Per-engine storage conformance sweep: availability ladder, hydration from empty and populated, idempotence, reconnect re-hydration, forward migration across all recorded fixtures, newer-payload read-only mode, `:data_missing`, quota exhaustion, private-mode behavior where drivable, two-tab propagation and compare-and-set rejection, degraded no-`BroadcastChannel` path.
- Export/import round-trip tests including hash verification, replace-versus-merge semantics, preview counts, and forward-compatible unknown-key preservation.
- Post-import catalog re-resolution tests asserting INV-11 statuses on a deliberately moved `data_version` fixture.
- Connection-failure tests: socket drop, catalog query error, and slow query, asserting distinct connection states and absence of fabricated values.
- Network-capture assertions per engine for third-party origins, personal fields across all five request surfaces, and cookie contents.
- Copy assertions per engine for required INV-25 strings and prohibited INV-5 / INV-21 words, sourced from the shared copy module.
- Accessibility assertions per engine for contrast, zoom, reflow, keyboard operability and focus visibility, target size, and live-region announcements.
- Report-writer tests: schema validity, `unproven` propagation, and a deliberate red-run rehearsal proving the release job blocks.
- Static-origin checks for reachability, third-party origins, copy, and attribution consistency.

### Manual/browser matrix

- Real desktop browsers per Tier 1 on their host operating systems: first visit, populated visit, private window, storage cleared through the browser's own settings UI (not through script), and two-window concurrent editing.
- Real mobile browsers per Tier 1: iOS Safari and Android Chrome on physical hardware — first visit, add a vehicle, log a service, background the browser, return, reconnect, and re-hydrate; private/incognito equivalents; storage cleared through browser settings; export downloaded and re-imported through the real file picker.
- Screen-reader passes on at least one desktop and one mobile assistive technology per the §9 accessibility row, covering hydration announcements and due-state announcements.
- Reduced-storage device run: fill device storage and exercise the quota path against a real quota rather than a simulated one; record the observed quota and the resulting message.
- Deploy-during-session run against the non-production environment: trigger a deploy while a mutation is in flight, confirm reconnect, re-hydration, and that the pending write is re-driven from client storage rather than lost (ADR-0004 §"WebSocket and LiveView considerations").
- Real-device eviction observation: populate a store on physical hardware per observed browser, leave it un-visited for the recorded dwell period, return, and record what actually happened. Result recorded as measurement; no vendor-documented number is written down as fact.
- Export files opened and inspected by hand once per matrix revision to confirm they contain only the user's own records and no server-side or catalog-licensed bulk content.

## Rollout and rollback

Rollout is in three steps so the gate never lands before the evidence it gates on. Step 1: merge `SUPPORT_MATRIX.md` and the report schema, with the suite running non-gating. Step 2: bring assertion groups up one at a time — availability, hydration, migration, loss states, quota, private mode, multi-tab, export/import, privacy, accessibility — each gating only after it has run green on every Tier 1 engine across consecutive runs with no unexplained flake. Step 3: flip Tier 1 to release-blocking and rehearse a deliberate red run to prove the block works.

Rollback: the gate is a CI flag, so reverting to non-gating is a one-line change that keeps the evidence flowing; this is the correct response to a toolchain or vendor-build break, and it is recorded in the run report rather than done quietly. Reverting the suite itself orphans no production behavior, since it ships none. Narrowing the matrix — dropping a tier or a browser — is a **dated supersession** in `SUPPORT_MATRIX.md` stating what is no longer promised and why, never a silent edit, and it triggers a §9 re-ratification proposal because §9 names the matrix.

## Documentation and evidence

- `SUPPORT_MATRIX.md` with tiers, engines, versions, version policy, and any dated supersessions.
- Conformance report artifacts per run, per engine, retained per the stated retention period and linked from the release record.
- The deliberate red-run rehearsal proving Tier 1 failures block the release job.
- Recorded fixture set covering every historical `schema_version`, with a note that fixtures are permanent.
- Manual matrix run logs: desktop, mobile, screen-reader, reduced-storage, storage-cleared-via-settings, and deploy-during-session runs.
- The real-device eviction observation design, its schedule, and its recorded result — or an explicit "unmeasured" statement while it is outstanding.
- Per-engine measurements for LCP, TTI, socket connect, hydration completion, event round trip, and payload budgets, plus the §9 re-ratification proposal for the `Browser support matrix` and `Multi-tab consistency` rows.
- Network-capture summaries evidencing zero third-party origins and zero personal fields (INV-4, INV-22, INV-26).

## Dependency rationale

Blocked by `DOS-M09-001`, `DOS-M09-002`, and `DOS-M09-003` because a conformance suite must conform to something: the object stores and version line, the adapter's typed errors and probes, and the named protocol events are the contract under test, and writing the suite first would freeze guesses instead of behavior. Blocked by `DOS-M09-004` because copy assertions must reference fixed strings from a shared source rather than restate them, or the test and the product drift. Blocked by `DOS-M01-006` for multi-engine CI capacity and artifact retention, and by `DOS-M09-006` / `DOS-M09-007` for a real HTTPS/WSS environment, since TLS, origin checks, socket behavior under a real proxy, and the deploy-during-session case cannot be observed against a local dev server.

This issue blocks `DOS-M04-010` (repo and storage conformance certification runs on this matrix and this harness rather than inventing a second one), `DOS-M07-004` (the re-scoped cross-browser QA matrix is this matrix plus scripted exploratory passes), `DOS-M07-003` (per-engine measurements are the input to the re-ratified budgets), and `DOS-M07-007` (release preparation cannot present cutover evidence without a green Tier 1 report). It also gives `DOS-M09-009` its measured eviction input: the PWA decision's strongest argument is storage durability, and that argument must rest on measurement rather than on documentation.

## Risks, decisions, and open questions

- Risk: eviction is time-dependent and cannot be waited out in CI, so the temptation is to assert vendor-documented behavior as if it were measured. Mitigation: FR-21 splits the two — simulation proves the app's *response* to an evicted store, and only the scheduled real-device observation may be recorded as what browsers *actually do*. ADR-0004 R1 requires exactly this split.
- Risk: private-browsing behavior differs per engine and changes across browser releases, so a matrix pinned to today's behavior will rot. Mitigation: FR-3's version policy plus a staleness limit per Tier 1 row; a stale row is reported, not assumed still true.
- Risk: automation on mobile Safari is materially more constrained than on desktop engines, which pushes iOS coverage toward the manual matrix. Mitigation: iOS assertions that cannot be automated are named explicitly in the matrix as manual, with the manual run recorded per release — never marked pass by inference from desktop WebKit.
- Risk: timing assertions (hydration deadline, ack timeout) flake in shared CI and get quietly relaxed. Mitigation: assert boundary behavior, record wall-clock separately as budget evidence; relaxation of a budget requires §9 re-ratification, which a test file cannot perform.
- Risk: a growing "known failures" list turns a gate into decoration. Mitigation: no such list exists; a Tier 1 failure is fixed or the matrix is amended by dated supersession.
- Risk: network captures could themselves become a store of sensitive-shaped data. Mitigation: synthetic fixtures only, scanned captures, stated retention, no public publication.
- Decision: capability probing, never user-agent sniffing, as the production mechanism (FR-4) — and therefore the matrix describes what we *test*, not what we *permit*.
- Decision: an unrun Tier 1 engine is a failure, not a skip (FR-20).
- Decision: fixtures for historical schema versions are permanent artifacts.
- Open question: whether Tier 2 should gate release at all, or only report. Recorded as open; the matrix must answer it explicitly rather than leave it to CI configuration.
- Open question: the dwell period for the eviction observation, and whether it must be re-run per browser release. To be set from the observation design, not assumed.
- Open question: whether the multi-tab rule survives contact with a real two-tab workflow (ADR-0004 R4). If the observation shows last-write-wins losing something a user cares about, that is a defect against `DOS-M09-003`, not a matrix exception.

## Definition of done

- `SUPPORT_MATRIX.md` merged and ratified, with tiers, engines, versions, version policy, and staleness rule.
- All functional requirements implemented and all acceptance criteria checked, with conformance reports and manual run logs attached or linked from CI.
- Tier 1 conformance is release-blocking, proven by a deliberate red-run rehearsal, with the flake and unproven policies enforced by the report writer rather than by convention.
- Every INV-24 sub-clause, plus INV-7 and INV-25, has at least one automated or scripted case that fails when the behavior regresses — satisfying the §9 `Honest-degradation coverage` row.
- Measured §9 values submitted for re-ratification; §9 itself left unedited pending that act.
- The real-device eviction observation is either complete and recorded, or explicitly outstanding and labeled unmeasured in both the matrix and the release evidence.
- `DOS-M04-010`, `DOS-M07-003`, `DOS-M07-004`, and `DOS-M07-007` are unblocked with executable, per-engine evidence rather than a single developer's browser.
