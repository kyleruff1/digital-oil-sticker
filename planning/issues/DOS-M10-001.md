## Outcome

A pure, transport-free resolver turns a third party's free-text vehicle and service values into either **exactly one** canonical sticker code or an **explicit, typed refusal** — and never anything in between. Resolution is deterministic, versioned, and refusing by default: no scoring function, no nearest match, no confidence threshold, no unit inference, no date-format inference. A vehicle that cannot be proven to be exactly one catalog configuration does not receive a `configuration_key`: a guessed key puts a stranger's vehicle on a customer's windshield, and there is no way to take paper back. A viscosity string not in the frozen grade table is carried into the manual-grade tail **verbatim**, never snapped to the nearest known grade. This issue ships the resolver and its refusal taxonomy only; no network transport of any kind is wired.

## Why this matters and what it unblocks

A shop's system sends what its own database holds: `2019 TOYOTA CAMRY` in one column, `5w30` in another, `full syn` in a third, an odometer with no declared unit, and a date in whatever format the DMS was configured with in 2011. Each value is a lossy rendering of something the catalog models precisely, and every conversion is a place where software can silently decide that a customer owns a different car than they do.

The shipped catalog already shows the shape: `2019 / Toyota / Camry` resolves to **more than one** configuration — 2.5 L inline-four, 3.5 L V6, and 2.5 L hybrid variants, several with a NULL trim. Year, make, and model are a one-to-many input, and `DigitalOilSticker.StickerCode` requires exactly one UUID. `VehiclePickerLive` makes a human choose. A machine intake has no human in the loop unless the design puts one there, and the default behavior of every fuzzy matcher ever written is to take the first row and move on.

This issue makes that impossible by construction and testable. It defines what "resolved" means, enumerates every way resolution can fail, and requires each failure to produce a distinct, machine-readable refusal rather than a plausible answer — closing, for an input path the policy did not anticipate, the rule `RECOMMENDATION_CLAIMS_POLICY.md` already states: "never infer a manufacturer interval from a generic model family; never use a nearest engine/configuration match." The cards it unblocks are recorded in Dependency rationale.

## Included

- A resolver in **two separable pure layers**, so the transport decision is made later and made once: **vehicle resolution**, which reads the catalog through `DigitalOilSticker.Catalog` and nothing else and accepts only vehicle descriptors; and **value normalization**, which is catalog-free, covers viscosity grade, oil base stock, odometer, and service date, and carries no `Catalog` reference, so it ships into a caller's own process without a database.
- A closed input schema for vehicle resolution: `model_year` (integer), `make_text`, `model_text`, optional `engine_text`, each separately labeled. Unknown keys are **rejected, never stripped**, matching `Catalog.Selector`.
- Matching that is exact-on-normalized only: NFKC → casefold → strip to `[a-z0-9]`, then equality against `normalized_name` or a row in the existing `aliases` table. No edit distance, trigram similarity, token scoring, prefix match, substring containment, or confidence value anywhere in the result.
- A **closed set of refusal reason codes**, each carrying the field it applies to, the resolver version, and the catalog `data_version` — and never the offending value.
- Ambiguity as a first-class result: when narrowing ends with more than one candidate, the resolver returns the candidate list as impersonal descriptors and **no** `configuration_key`, so the caller must put the choice in front of a human; candidates projecting to identical human-readable descriptors refuse instead.
- Grade resolution driven entirely by the frozen `StickerCode.grades/0` list: a generated table of accepted spellings plus a separately committed, human-reviewed synonym file. Anything not an exact member goes to the **manual-grade tail verbatim**. Base-stock resolution on the same terms against `StickerCode.base_stocks/0`, with the difference the wire format forces: that byte has no manual tail, so an unresolved value becomes **absent** with a warning, never a nearest guess.
- Odometer normalization that **requires a declared unit** (`mi` or `km`), refusing when it is absent or unrecognized and otherwise delegating to `DigitalOilSticker.Units.to_metres/2`; and service-date normalization that **requires an ISO 8601 calendar date or an explicitly declared format token**, refuses ambiguous numeric forms outright, and range-checks against the codec epoch.
- Version stamping on every result — `resolution_version`, `search_normalization_version`, catalog `data_version` and `schema_version`, codec `format_version` — so a disputed sticker is reproducible years later from the code plus five version stamps.
- A cross-implementation vector file, `conformance/fixtures/intake-resolution-vectors.json`, generated by a mix task and round-tripped before emission on the same terms as `conformance/fixtures/sticker-code-vectors.json`: any future port is held to the vectors, not to a second reading of this document.
- `Catalog.Aliases.all/0` — a zero-parameter read of the existing `aliases` table, loaded at boot; impersonal by construction, adding nothing to the INV-26 audit surface.
- A build-time ambiguity coverage report over the shipped artifact: what fraction of year/make/model triples resolve to exactly one configuration, published as a measured number.

## Excluded

- **Any network transport.** No HTTP route, controller, channel, LiveView event, MCP tool, CORS configuration, authentication, API key, or tenant identifier. `router.ex` gains zero routes. Exposing the resolver is a separate card gated on revision 3.0.0 and ADR-0006; FR-1 makes the absence build-enforced rather than disciplinary.
- **Any relaxation of `Catalog.Selector` or `Catalog.Vocabulary`.** Free text does not enter the catalog query surface; the resolver consumes free text and emits closed-vocabulary selectors, exactly as `VehiclePickerLive` does today. A golden-set test asserts the vocabulary is unchanged.
- Any persistence: no print queue, job table, retry buffer, idempotency-key table, per-shop configuration store, submission log, or per-caller counter. Each is a writable table and would fail ADR-0004's repo-list gate on the first migration.
- Any logging of any input value at any level, including error paths, exception messages, and fixtures (INV-4, ADR-0004 "Logging").
- The printed artifact — template, layout, required lines, the INV-14 oil-life-monitor deference line, the no-affiliation statement, and the lint-tested copy. This issue defines only what the resolver can and cannot license that card to print.
- Any interval, due date, or product-compatibility claim. A resolved `configuration_key` licenses a *code*, not a maintenance statement; intervals remain `DOS-M09-004`'s `get_schedules`/`get_oil_interval` under INV-13, INV-15, and INV-16.
- Acceptance of any personal field as a resolution input (see FR-3), and free-text oil product or brand search (INV-16; the product path has its own discipline in `DOS-M09-010`).
- Single-line vehicle strings — `2019 TOYOTA CAMRY` as one unsplit field is refused by the closed schema itself, with no dedicated reason code and no detection logic; see the Decision below.
- Any assumption about whether INV-26 permits a free-text vehicle descriptor on a *remote* surface. That belongs to revision 3.0.0 and is left open here.

## Functional requirements

- FR-1: The resolver is transport-free. No intake module references `Phoenix.LiveView`, `Plug`, `Phoenix.Controller`, `Phoenix.Channel`, or the router; no route, socket handler, or tool definition is added anywhere by this issue. A static check fails the build on any such reference (ADR-0004 decision §6).
- FR-2: The vehicle-resolution input schema is exactly `{model_year, make_text, model_text, engine_text?}`. Unknown keys and extra keys cause a whole-request refusal with `:unknown_field`; missing required keys, non-string text values, and a non-integer `model_year` cause one with `:field_type_invalid`. Nothing is stripped, coerced, or defaulted.
- FR-3: A payload containing `vin`, `odometer`, `mileage`, `service_date`, `changed_on`, `note`, `customer_name`, `plate`, `ro_number`, `phone`, `email`, `shop_id`, `tenant_id`, `api_key`, `session_id`, or `tab_id` — under any casing — is refused in whole with `:personal_field_present`, the value is not echoed in the refusal, and no part of the payload reaches any log sink at any level (INV-26, INV-4).
- FR-4: Text matching is exact-on-normalized. Normalization is NFKC → casefold → strip to `[a-z0-9]`, identical in behavior to `keys.mjs` `normalizeKey`, versioned by `search_normalization_version`. No edit-distance, similarity, trigram, phonetic, or score-ranking function exists in the implementation, and a source-level check asserts their absence.
- FR-5: A `model_year` outside the INV-8 window read from `catalog_metadata` (`window_start_year`, `window_end_year`) is refused with `:year_out_of_window`. The year is never clamped to the nearest in-window year and never dropped to widen the search.
- FR-6: `make_text` resolves by exact normalized match against `makes.normalized_name`, falling back to an exact normalized match in `aliases` where `entity_type = 'make'`. A direct `normalized_name` match beats an alias match; the precedence is stated in code and asserted by test. If two makes in one `data_version` share a normalized name, the catalog build fails rather than the resolver choosing (INV-10).
- FR-7: `model_text` resolves the same way within the resolved make and year. Failure at either level is `:make_not_resolved` or `:model_not_resolved` — never a fallback to a broader query, never a cross-make search, never a "did you mean" list generated by similarity.
- FR-8: **Partial resolution never yields a `configuration_key`.** If year, make, and model resolve but configuration narrowing ends with a candidate count other than exactly one, the result is `:ambiguous` with a candidate list and a null `configuration_key`. There is no tie-break, no first-row selection, no NULL-trim preference, and no "most common configuration" heuristic.
- FR-9: `engine_text`, when supplied, narrows candidates only by exact normalized equality against `engine_descriptor`, or by exact numeric equality against `displacement_l` or `engine_cylinders` when the token parses unambiguously as one of those. A token narrowing to zero candidates is `:engine_not_matched` — never silently dropped to restore a wider set.
- FR-10: A configuration carrying `engine_oil_service = 'not_applicable'`, or that `Catalog.Status.bev?/1` identifies as battery-electric, **resolves**: the result carries its `configuration_key` and that status, licensing honest identification and an identification-only code (the codec's absent sentinels cover grade and base stock) — and no grade claim, interval, or oil plan. The presenting surface renders the mandated framing verbatim; what prints is the printed-artifact card's decision (`DOS-M10-000` AC-9). A NULL electrification level is not a BEV; unknown stays unknown and resolution proceeds (INV-9, INV-11).
- FR-11: Every `:resolved` result carries the configuration's INV-11 `support_status` verbatim from `%Result{}`, and records explicitly that a resolved `configuration_key` authorizes a code and **no** interval, due date, viscosity requirement, or compatibility statement (INV-13, INV-15, INV-16).
- FR-12: Grade resolution matches the supplied string, after a declared total transform, against a table of accepted spellings **generated from** `StickerCode.grades/0` plus a committed, human-reviewed synonym file. The generated table is asserted injective, so appending a grade to the frozen list cannot silently create a collision. Each synonym row carries `reviewer` and `reviewed_at`.
- FR-13: A viscosity string that is not an exact member of that table is carried into the **manual-grade tail verbatim**, in the caller's original bytes, only outer whitespace removed. It is never snapped to the nearest known grade, never matched by substring containment, and never truncated: a string exceeding the codec's 20-byte tail limit is refused with `:manual_grade_too_long`.
- FR-14: The manual-grade tail is constrained to a declared printable character set, its first character must be alphanumeric, and control characters, line breaks, and spreadsheet-formula lead-ins are refused with `:manual_grade_unprintable`.
- FR-15: Base-stock resolution follows FR-12's discipline against `StickerCode.base_stocks/0`. Because the wire format has no manual tail for base stock, an unresolved value yields **absent** plus a `:base_stock_not_resolved` warning and the code is still produced. A genuinely ambiguous value — a bare `synthetic`, which is neither `synthetic_blend` nor `full_synthetic` — is `:base_stock_ambiguous` and likewise absent, never resolved by preference.
- FR-16: Odometer normalization requires a separately supplied unit token in `{mi, km}`. An absent, empty, or unrecognized unit is refused with `:odometer_unit_not_declared`, and the magnitude of the value is never used to infer the unit. Conversion delegates to `Units.to_metres/2`, surfacing its `:not_a_number`, `:negative`, and `:implausible` outcomes as distinct refusals. An omitted odometer is legal and encodes as the absent sentinel — distinct from a present value with an undeclared unit.
- FR-17: Service-date normalization accepts an ISO 8601 calendar date (`YYYY-MM-DD`) or a value accompanied by an explicitly declared format token from a closed set. Anything else, including all-numeric forms whose day/month order is not determined by the value itself, is refused with `:date_format_not_declared`. Locale, caller address, and "the first component exceeds twelve" are never used to disambiguate.
- FR-18: A service date outside the codec's representable window (`2000-01-01` plus `0..65_534` days) is refused with `:date_out_of_range`. A present `service_date` makes `caller_local_date` required; its absence is `:caller_local_date_not_declared`. A date more than one calendar day after the caller-declared local date is `:date_in_future`. The rule, reference, and tolerance are this issue's own decisions, recorded in Risks — no invariant states them. An omitted date is legal and encodes as the absent sentinel.
- FR-19: Every result — resolved, ambiguous, or refused — carries `resolution_version`, `search_normalization_version`, catalog `data_version` and `schema_version`, and `StickerCode.format_version/0`. A resolution is valid only for the `data_version` that produced it; a caller may not carry one across a version change.
- FR-20: Resolution is a pure function of its inputs and the catalog artifact. Identical inputs against identical versions produce a byte-identical code and result structure. It writes nothing, caches nothing keyed on input, and emits no telemetry containing an input value; aggregate refusal-code counters are permitted and carry no field values.
- FR-21: The refusal reason set is closed and enumerable, each member carries the field it applies to, and no refusal echoes the offending input. Adding a reason code is a source change with a test, not a string constructed at the call site.
- FR-22: A `:catalog_unavailable`, `:rate_limited`, `:invalid_selector`, or `:stale_cursor` outcome from the facade propagates as a refusal, never as an absent-vehicle result. A degraded catalog produces no sticker (INV-7).
- FR-23: There is no code path producing a `configuration_key` other than the exactly-one-match branch. A structural test asserts the resolver has no default or catch-all clause returning a resolved result.
- FR-24: `conformance/fixtures/intake-resolution-vectors.json` covers every refusal reason and every resolution branch, is round-tripped before emission, and is the contract any future port is held to.

## Technical implementation contract

### Components and ownership boundaries

- `DigitalOilSticker.Intake.Resolver` — vehicle resolution; the only intake module that reads the catalog, exclusively through `DigitalOilSticker.Catalog` with validated closed-vocabulary selectors. Plain Elixir; no Phoenix, Plug, or client-storage reference.
- `Intake.Text` — the versioned normalization transform, held to `keys.mjs` semantics by shared vectors so the Elixir and JavaScript sides cannot drift.
- `Intake.Values` — grade, base stock, odometer, and service-date normalization. **Has no `Catalog` dependency**, asserted by static check — what makes it shippable into a caller's process without a database, so the personal half of a sticker (the odometer and the date) is composed in the caller's process, as `sticker_code.js` already does for the browser.
- `Intake.Refusal` — the closed reason-code set and the result struct. One module, so an INV-26 or INV-4 audit of what a refusal can contain is finite.
- `Catalog.Aliases` — `all/0`, a zero-parameter read of the existing `aliases` table, held as a closed map. `Mix.Tasks.Dos.Intake.Vectors` — generates the vector file, round-tripping each case before emitting it, mirroring `Mix.Tasks.Dos.StickerCode.Vectors`.
- Unchanged and explicitly protected: `Catalog.Selector`, `Catalog.Vocabulary`, `Catalog.Cache`, `Catalog.RateLimit`, `StickerCode`. This issue adds no selector field, no cache key, and no byte to the wire format.
- Composition boundary: `Intake.Resolver` returns the impersonal half of a sticker (`configuration_key`, `grade`, `base_stock`, `support_status`); `Intake.Values` normalizes the personal half (`changed_on`, `odometer_m`); `StickerCode.encode/1` composes them. Nothing requires the three steps to share a process, and the design arranges that the last two need not run in ours.

### Data and persistence

- **No writes anywhere.** The deployed repo list remains exactly `[CatalogRepo]`, read-only with `PRAGMA query_only = ON` (ADR-0004 decision §4). No migration, table, ETS row, or file holding an input value. Reads are `list_years`, `list_makes`, `list_models`, `list_configurations`, and `get_configuration` through the existing facade, plus `Catalog.Aliases.all/0`. Metadata consumed: `window_start_year`, `window_end_year`, `data_version`, `schema_version`, `search_normalization_version`.
- The grade and base-stock synonym tables are **committed source files**, not catalog rows: adding a synonym is a reviewed code change with a version bump, not a data edit shipping silently in a catalog release. Each row carries `reviewer` and `reviewed_at`.
- `resolution_version` is a module attribute, incremented on any change to a matching rule, a synonym table, a refusal code, or the normalization transform, with the vector file regenerated on every increment — with the warning `sticker_code_test.exs` already carries: codes already printed came from the previous vectors, and paper cannot be regenerated.
- Nothing derived from an input enters `Catalog.Cache`; its key remains `{data_version, normalized_query}` over a validated selector, so free text never becomes part of a cache key.

### Interfaces and events

- `Intake.Resolver.resolve_vehicle(map()) :: {:ok, %Resolution{}} | {:ambiguous, %Ambiguity{}} | {:error, %Refusal{}}`. Three outcomes, not two: ambiguity is neither success nor failure, and collapsing it into either is where the wrong vehicle gets chosen.
- `%Resolution{}`: `configuration_key`, `support_status`, `engine_oil_service`, `model_year`, `make_display_name`, `model_display_name`, `trim`, `engine_descriptor`, `resolution_version`, `search_normalization_version`, `data_version`, `schema_version`, `warnings`.
- `%Ambiguity{}`: `candidates` (impersonal descriptors — `configuration_key`, `trim`, `series`, `body_class`, `drive_type`, `engine_descriptor`, `displacement_l`, `engine_cylinders`, `transmission`), `narrowed_by`, `discriminating_fields` (the descriptor fields whose values actually differ across the candidates, computed rather than guessed, so the caller can ask the one question that narrows to one — `DOS-M10-000` AC-7), and a null `configuration_key`. The candidate projection is asserted pairwise distinct; otherwise the resolver refuses with `:candidates_indistinguishable`.
- `%Refusal{}`: `code` (from the closed set), `field`, `resolution_version`, `data_version`. No value, no echo of the input, no free-text message.
- `Intake.Values.normalize(map()) :: {:ok, %Values{}} | {:error, %Refusal{}}` over `{grade_text?, base_stock_text?, odometer?, odometer_unit?, service_date?, service_date_format?, caller_local_date?}` — `caller_local_date` is optional only while `service_date` is absent; a present `service_date` makes it required (FR-18) — returning `grade` (a frozen code or a manual-tail string), `base_stock` (a frozen code or `nil`), `odometer_m`, `changed_on`, `warnings`.
- Zero LiveView events, HTTP routes, or tool definitions; no `router.ex` entry, no event-allowlist key.
- Refusal codes, closed set: `:unknown_field`, `:field_type_invalid`, `:personal_field_present`, `:year_out_of_window`, `:make_not_resolved`, `:model_not_resolved`, `:engine_not_matched`, `:ambiguous`, `:candidates_indistinguishable`, `:manual_grade_too_long`, `:manual_grade_unprintable`, `:odometer_unit_not_declared`, `:odometer_not_a_number`, `:odometer_negative`, `:odometer_implausible`, `:date_format_not_declared`, `:caller_local_date_not_declared`, `:date_out_of_range`, `:date_in_future`, `:catalog_unavailable`, `:invalid_selector`, `:rate_limited`, `:stale_cursor`. Deliberately absent: `:fields_not_separated` (the closed schema refuses an unsplit string — see Decisions), `:make_ambiguous` (unreachable: `makes.normalized_name` and `aliases (entity_type, normalized_alias)` are `UNIQUE`, name beats alias; FR-6 fails the build instead), `:engine_oil_service_not_applicable` (a BEV resolves — FR-10).
- Warning codes, closed set (non-fatal; the code is still produced): `:base_stock_not_resolved`, `:base_stock_ambiguous`, `:manual_grade_used`, `:trim_not_verified`, `:support_status_identity_only`.

### Failure and recovery behavior

- The governing rule: **exactly one branch returns a `configuration_key`, and it requires a candidate count of one.** Every other path returns an ambiguity or a refusal; FR-23 makes this structural rather than aspirational.
- Partial resolution — year and make resolve, model does not — refuses at the level that failed; no fallback upward, no "model-level configuration", no synthesized identity row. Ambiguous resolution returns candidates and stops; the recovery is a human choosing from the list, and a caller that cannot present a choice prints no sticker.
- An engine qualifier narrowing to zero refuses. Restoring the wider set by discarding a qualifier the caller supplied is the most tempting failure mode here, and the one that puts a V6 schedule on a four-cylinder.
- Catalog unavailable, rate limited, or `:invalid_selector` mid-cascade: refuse. The shop gets a fast explicit failure and falls back to its own process — never a sticker assembled from a partially answered cascade (INV-7).
- `get_configuration` returning `{:ok, %Result{status: :unsupported, data: nil}}` — the shape a well-formed but unknown key produces — is treated as **not resolved**, never as success. A caller that only pattern-matches `{:ok, _}` silently treats a missing vehicle as found; the resolver guards on non-nil `data`, as `VehiclePickerLive` does.
- A `data_version` change between a resolution and its use makes the resolution stale; because the result carries the version it used, this is detectable rather than silent. The cascade has a bounded call budget and refuses on exceed — a hung resolver is worse than a refusal; the counter's fallback is the paper sticker book. Recovery has no persistent component: no queue to drain or replay; a refused submission is the caller's to retry with values it still holds.

### Security and privacy

- FR-2's closed schema contains no personal field; FR-3's named-field rejection is a second layer for the realistic case — a DMS export that includes a VIN column because it includes every column.
- No input value reaches a log sink at any level, including exception messages; refusals carry codes and field names only. `DOS-M09-004` AC-13's log-capture test is extended to intake with a scripted run supplying a VIN, an odometer value, and a note. `Catalog.Selector` remains structurally incapable of holding free text, and AC-3's INV-26 payload audit is re-run unchanged — proving this issue widened nothing.
- The manual-grade tail is the one attacker-controlled string surviving into a printed artifact and a QR payload. FR-14's constraints exist because a keyboard-wedge scanner types a decoded payload into whatever field has focus, and a leading `=`, `+`, `-`, or `@` is a formula-injection prefix in spreadsheets and several point-of-sale text fields.
- The sticker code is **not a secret and not an identifier**. `sticker_code.ex` states the bijection plainly: anyone who can read the code can read the values. Identical inputs produce identical codes, so a caller using the code as a job, customer, or deduplication key will collide — the integration documentation must say so in those words. The code carries no unit: a shop printing kilometres and a browser rendering miles show the same value, so the printed artifact must state the unit it displays.
- No durable identifier is created, accepted, or derivable: no API key, tenant id, correlation token, or per-caller counter (INV-3, INV-19, and ADR-0004's rejected alternative 5, which names a stable-identifier store "an account without a password").

### Accessibility and performance

- No UI ships here, but the resolver decides what a human at the counter is asked to do — an accessibility property. The ambiguity result must be actionable in seconds by a service writer who is not an automotive engineer: candidates carry trim, engine descriptor, displacement, cylinders, body class, and drive type, and pairwise distinctness means the resolver refuses rather than presenting two identical choices. The list is capped, and exceeding the cap refuses rather than truncates, because a truncated list invites picking from candidates that may not contain the right one.
- `trim` is NULL on a meaningful share of shipped rows. Where the resolved configuration has a NULL trim the result carries `:trim_not_verified`, so the printed artifact renders "Exact configuration not verified" (INV-21) rather than an empty field that reads as certainty.
- Performance budget, *provisional* pending measurement: vehicle resolution p95 ≤ 400 ms server-side for the full three-step cascade plus local matching, floored by the §9 catalog budget of p95 ≤ 250 ms first paged result and ≤ 150 ms subsequent filter. Value normalization is pure and sub-millisecond. Measured figures are recorded with their conditions and re-ratified rather than quietly missed.

## UX and content states

This issue ships no screens; it defines the states a caller's interface must represent, distinguishable in data rather than by inference:

- **Resolved, `identity_only`** — the vehicle is real and a code can be produced; no interval, due date, or viscosity requirement may be printed. In the current shipped `data_version` every resolvable non-BEV configuration is `identity_only` — no licensed schedule or requirement source has cleared the `DOS-M09-010` gates — so a sticker printed today carries a vehicle, a date, an odometer reading, and a grade, and no maintenance claim. Copy uses "Source unavailable" (INV-21).
- **Resolved, trim not verified** — the configuration matched but carries a NULL trim; "Exact configuration not verified" (INV-21).
- **Ambiguous** — more than one candidate. The caller presents the list; nothing prints until a human picks.
- **Not resolved** and **out of window** — the refusal names the field that failed and does not claim the vehicle does not exist: this `data_version` did not resolve it, or the model year is outside INV-8's window.
- **Engine oil service not applicable** — a battery-electric configuration, resolved for honest identification only; the mandated string is used verbatim, and no oil plan, grade, or interval claim is licensed (INV-9, INV-11).
- **Value refused** (undeclared odometer unit, undeclared date format, oversized or unprintable manual grade), **value dropped with a warning** (base stock unresolved or ambiguous — the code is produced without it and the caller is told), and **catalog unavailable**, which is distinct from every state above and from "no data for this vehicle" (INV-7).

Binding terminology for copy against these states: "Meets the recorded requirements" only where every mandatory requirement has a source-backed match, and never "manufacturer approved" absent a documented OEM approval; "Estimated due date" always with a confidence label; "Source unavailable" and "Exact configuration not verified" rather than a generic value; "Not specified" for an absent field; "Engine oil service not applicable" for a BEV; oil-life monitor, calendar interval, mileage interval, normal service, and severe service kept distinct (INV-20, INV-21). "Our estimate" is the label for our own model's interval, never a manufacturer statement.

One vocabulary gap is recorded rather than improvised: INV-21 mandates "Stored in this browser" as *the* framing for user data, and on a shop's receipt there is no browser and no stored record. This issue does not invent softer wording. A shop-facing vocabulary is a revision 3.0.0 item, and the printed-artifact card is blocked on it.

## Test plan

### Automated

- Property tests over the fixture catalog: for every generated input, either the result is `:resolved` with exactly one matching candidate, or `configuration_key` is null. The most important test in the issue, written as a property because a table only covers the cases someone thought of.
- Refusal-taxonomy table tests: one case per member of the closed set, asserting code, field, and the absence of any echoed input value in the returned structure.
- Ambiguity tests on the live `2019 / Toyota / Camry` shape — unqualified, displacement-qualified, fully qualified — asserting candidate counts from the fixture rather than hardcoded constants, plus pairwise distinctness of the candidate projection. Negative narrowing: an engine qualifier that empties the set must refuse, and a mutant that drops the qualifier to restore the wider set must fail.
- Grade table tests: generated-spelling injectivity across all fourteen frozen grades; substring-containment cases (`5W-30 Dexos`, `0W-20 Euro`); near-miss cases (`5W-31`, `5W-25`); monograde cases (`SAE 30`, `30 weight`); the 20/21-byte boundary, including a multi-byte UTF-8 string under 20 characters but over 20 bytes; the printable-character and leading-character rules.
- Base-stock tests: frozen-code spellings, the reviewed synonym rows, the ambiguous bare `synthetic`, an unknown value, and that all unresolved paths yield an absent base stock and a produced code, not a refusal.
- Odometer tests: undeclared unit at magnitudes plausible in both units; declared `mi` and `km` producing distinct metre values; the `Units` error surface; the omitted-field path; the implausibility ceiling. Date tests: the ambiguous numeric forms in both orders; the ISO and declared-format forms; the epoch boundaries at day 0 and day 65,534; the absent sentinel; the future-date tolerance at one and two days; a present date with no declared caller local date.
- Personal-field tests: each FR-3 field injected in several casings, plus a log-capture assertion at `:debug` over the whole suite that no fixture VIN, odometer value, note, or date string appears in any captured line.
- Boundary preservation: `Vocabulary` golden set unchanged; `DOS-M09-004` AC-2 and AC-3 re-run unmodified; static checks that `Intake.Values` has no `Catalog` reference and that no intake module references Phoenix, Plug, or the router; route-inventory diff; migration-inventory assertion.
- Determinism across processes and restarts; vector round-trip and drift (a refusal code without a vector fails the build; the JavaScript normalization is held to the shared vectors so `Intake.Text` and `normalizeKey` cannot drift); coverage report generated in CI against the shipped artifact and recorded with its `data_version`.

### Manual/device matrix

This issue ships a library and no artifact, so most physical verification belongs elsewhere.

- **Pilot-gated:** a real DMS export (columns as exported, no hand-cleaning) run through the resolver, recording resolved/ambiguous/refused counts by code. It cannot run before a consenting pilot shop exists — a pre-pilot project holds no DMS export, and such a file is real customers' personal data. Redact per `RELEASE_GATES.md`: no VIN, mileage, notes, or customer identifiers in any artifact. Until then the AC-23 report is the stand-in.
- A timed walkthrough with a service writer: present a 2019 Camry ambiguity result and confirm the list resolves correctly and quickly from the descriptors alone — no VIN, no parts catalog. Record the cases where it cannot.
- A deliberate refusal walkthrough at the counter — undeclared odometer unit, ambiguous date, unresolvable model — confirming the shop's fallback is available and no partial sticker is produced.

Print and scan verification — QR printing on thermal stock, wedge-scanner behavior on the manual-grade tail, what an `identity_only` sticker carries in print — belongs to the milestone's printed-artifact and scan-matrix cards (cited by role while identifiers are unreconciled): this issue defines no template, and the application has no `/s` route or scanner path today.

## Rollout and rollback

Rollout: additive and inert. No schema, migration, persistent state, route, or reachable surface. The modules ship as library code exercised only by tests and the vector generator, becoming load-bearing only when the M10 transport and printed-artifact cards land — each gated on revision 3.0.0 and ADR-0006. Merging this changes nothing a user or shop can observe, which is the point: the contract can be argued over, measured, and rejected before anything is exposed.

Rollback: revert the commits. Nothing to drain or migrate, no orphaned rows possible, no personal data touched because none is persisted. Reverting also removes the vector file, which is safe only while nothing has been printed from it.

**A printed sticker cannot be rolled back.** Once on a windshield it stays for a year, in a state we cannot query, count, or correct. The recall mechanism is therefore a record, not a fix — `resolution_version` plus `data_version` on every result — and works only if the caller retains them. That asymmetry is the whole argument for a refusing resolver: refusing costs a service writer a few keystrokes; guessing costs a stranger the wrong oil interval.

## Risks, decisions, and open questions

- **Decision:** the resolver refuses rather than scores. There is no confidence value in any result, because a confidence value is a knob, a knob has a threshold, and a threshold silently decides which vehicle goes on a stranger's windshield. Exactly one match, or no key.
- **Decision:** vehicle fields must arrive separately labeled. `2019 TOYOTA CAMRY` as one string is refused: tokenizing it requires knowing where the make ends and the model begins, and `LAND ROVER RANGE ROVER` and `MERCEDES-BENZ C 300` show no rule solves that. The cost lands on the integrator's field mapping, where it can be reviewed. The refusal is carried by the closed schema itself (`:unknown_field` or `:field_type_invalid`), not a dedicated code — *recognizing* an unsplit descriptor would itself require the forbidden tokenization.
- **Decision:** the odometer unit and the date format must be declared by the caller. Magnitude does not determine unit — 240,000 is plausible in both miles and kilometres. `03/04/2026` does not determine its own order, and a resolver that succeeds on `13/04/2026` by noticing the day exceeds twelve is *more* dangerous than one that always refuses, because it works often enough to be trusted.
- **Decision:** an unrecognized viscosity string goes to the manual tail verbatim rather than being snapped to the nearest frozen grade. `5W-31` is not `5W-30`, and `5W-30 Dexos` is a different claim from `5W-30` even though it contains it. The tail is the escape hatch `sticker_code.ex` designed for this, capped at 20 bytes with refusal rather than truncation — a truncated grade is a fabricated grade.
- **Decision (this issue's own rule; no invariant states it):** a service date more than one calendar day past the caller-declared local date is refused. The reference is caller-declared because the resolver is pure (FR-20) — a wall-clock read would break that — and the one-day tolerance absorbs time-zone skew. The harm (a future date pushes every projected due date later) parallels INV-13's concern, but INV-13 governs interval extension, not date validation, and is not this rule's source. Recorded so it reads as a choice, not a mandate.
- **Decision:** an unresolved base stock becomes absent rather than refusing the whole sticker, because the wire format has an absent sentinel for it and a missing base stock is honest while a wrong one is not. A bare `synthetic` is ambiguous and is dropped, not resolved to either candidate.
- **Decision:** the personal half of a sticker — the odometer and the service date — is normalized and encoded in the caller's process. `Intake.Values` carries no `Catalog` dependency specifically so this is possible, mirroring the argument `sticker_code.js` makes for the browser: the values must never leave the device, so the server cannot generate the QR. Reversing this makes the server where a third party's customer's odometer arrives — what INV-26 exists to prevent.
- **Risk (INV-26):** the invariant's literal text names "a free-text field" among the payload contents that MUST NOT be carried on the catalog-query surface. Whether a make or model token is free text for this purpose — and therefore whether vehicle resolution may ever run remotely at all — is **not decided here**. Building transport-free is precisely how this issue avoids assuming an answer (CHANGE_CONTROL Rule 4); if revision 3.0.0 declines to permit it, the resolver still ships, as a library the caller runs.
- **Risk:** the ambiguity rate may be high enough that the feature is not viable. `2019 / Toyota / Camry` producing several configurations is the ordinary case, not the tail. AC-23's coverage report makes the milestone's go/no-go a measured number, and should run before the transport card is written, not after.
- **Risk:** in the current `data_version` every resolvable non-BEV configuration is `identity_only` (see UX states) — a sticker produced today carries no interval and no due date, and any pitch implying otherwise is a claim the data does not support.
- **Risk (copy lint):** recorded as a hard precondition above — the scan gap would let unlinted claim copy ship onto paper with the gate green; AC-22 proves the widening.
- **Risk:** the manual-grade tail is attacker-controlled text reaching a printed artifact and a keyboard-wedge scanner. FR-14's constraints are narrow by design and will reject some legitimate strings, which is the correct trade for a field nobody validates upstream.
- **Risk:** the `aliases` table holds one row and is read by nothing. Activating it makes a previously inert data path load-bearing, and a bad alias now silently redirects a make. Mitigation: alias rows carry `alias_kind` and a `source_id`, the precedence rule is tested, and a duplicate normalized name fails the catalog build rather than the resolver.
- **Open question (epic reconciliation, excluded classes):** `DOS-M10-000` FR-11/AC-8 require an excluded-class vehicle refused with a **distinct** typed reason. This resolver cannot mint one honestly: excluded classes ship no catalog rows (INV-9), so they surface as `:make_not_resolved`/`:model_not_resolved`, indistinguishable from a coverage gap. The distinct reason needs class data the artifact does not carry, or an amendment to the epic's AC-8; a make-list heuristic would be a guess (Rule 4). Owed to the epic, not silently resolved here.
- **Open question:** whether a caller-supplied trim string may narrow candidates. `trim` is NULL on many shipped rows, so trim-narrowing would systematically prefer trimmed rows over untrimmed ones — a guess wearing a filter's clothing. Not attempted here; recorded so the next person finds the reasoning.
- **Open question:** whether a caller's `model_year` field is a model year or a calendar year. The two differ for vehicles sold ahead of their model year; the value cannot tell us. The contract must name the field `model_year` and the printed artifact must show it, so a customer can see it is wrong. There is no software fix.
- **Open question (governance):** `SOURCE_REGISTER.md` and `LICENSING_CHECKLIST.md` need a third Rule 2b review for machine-to-machine redistribution to a commercial integrator — a mode beyond bundle redistribution and hosted serving (INV-15, ADR-0004 R6). Resolution results are catalog facts leaving our rendering control; this issue neither resolves that gate nor assumes its outcome. Relatedly, the marks policy fixes the initial territory as the U.S.; a machine intake will receive non-U.S. vehicles, and the INV-8 refusal covers model year, not market.
