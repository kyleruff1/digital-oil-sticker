## Outcome

A Model Context Protocol server, mounted at a path on the existing application origin, exposes a bounded tool surface in two lanes separated in the build rather than by convention.

The **impersonal lane** — seven tools — projects a bounded subset of `DigitalOilSticker.Catalog` into MCP tool schemas: catalog metadata, the year/make/model/configuration cascade, and single-configuration lookup — six of the facade's fourteen functions — plus a `codec_contract` tool, reading `StickerCode` rather than `Catalog`, that hands the caller the frozen wire format, index tables, and full emitted vector set so an integrator can encode locally and stop calling us. This lane carries no VIN, odometer, date, note, record identifier, or caller-supplied free text; it is the existing `%Selector{}` contract over a different transport.

The **encoding lane** — four tools: `encode`, `decode`, `qr_svg`, `qr_png` — accepts and returns personal data, is therefore **absent from `tools/list` and unreachable unless a compile-time flag set by a ratified constitution revision and an accepted ADR is on**, and ships here as a specified, tested, flag-off implementation. Every value it touches is classified personal for logging, caching, and retention purposes, including the sticker code itself, because the code is a bijection over those values and not a digest.

The server retains nothing beyond an in-memory rate-limit bucket whose record shape is fixed and asserted. "Nothing" is discharged by a scripted-session retention gate — filesystem diff, ETS sweep, `persistent_term` sweep, named-process state sweep, log scan across every sink — that fails the build when a distinctive fixture odometer, service date, sticker code, or `configuration_key` appears anywhere after the calls complete. Encoding is idempotent at this layer as well as in the codec: the same normalized values return a byte-identical code, SVG, and PNG across processes and restarts, with no idempotency key or deduplication store anywhere in the path; the `x-request-id` header set by `Plug.RequestId` is stripped from MCP responses, so no server-assigned request identifier reaches the caller.

The server returns a QR image and nothing else — no interval, no due date, no viscosity claim, no vehicle name, no prose — because a thermal receipt has no tooltip, no provenance panel, and no revision path.

## Why this matters and what it unblocks

The existing privacy claim is structural. `sticker_code.ex`'s moduledoc states the reason: there is nothing to store, the same values always produce the same code, and the code carries the values. The JS port exists precisely because the values must never leave the device, so the server cannot generate the QR and the browser has to. This issue proposes a server that generates a QR from values a third party sent it — a reversal of a shipped, tested decision rather than an extension of it.

Two things follow. First, the honest architecture is a **distributed codec**, not a remote encoder: the codec is a pure function over five fields with a frozen wire format and an emitted vector set, so an integrator can run it locally and never put an odometer on our wire; `codec_contract` makes that the path of least resistance. Second, if the owner will not accept a distributed codec, the encoding lane requires a ratified amendment naming which clauses of INV-19 and INV-26 are relaxed and which stand — a request body carrying an odometer, a service date, and a free-text grade is exactly what INV-26 prohibits, and a sticker code base32-encodes those same values.

What this unblocks is bounded: a pilot in which a shop resolves a vehicle through impersonal selectors, composes the personal half locally, and prints a QR that a customer scans into their own browser storage. It does not unblock a customer record we hold, a lookup a customer performs against us, or a reminder we send. A centrally generated code invites a lookup service next; that risk is recorded below and the capability excluded in the terms of INV-19 and INV-23.

## Included

- An MCP server implementing `initialize`, `tools/list`, and `tools/call` over streamable HTTP at a single path on the existing Fly.io application origin, behind the router's `:api` pipeline. No new origin, no new host, no server-initiated notifications.
- The impersonal lane, seven tools: six thin adapters over one `Catalog` function each, plus `dos_codec_contract`, which reads `StickerCode` rather than `Catalog`. JSON Schemas are generated from `Catalog.Vocabulary` so schema and validator cannot drift.
- `dos_codec_contract`: the complete local-encoding contract enumerated in FR-7 — everything an integrator needs to encode locally without ever calling the encoding lane.
- The encoding lane, four tools, implemented, tested, and compiled behind a flag that is off in every environment until the amendment and ADR land.
- Two image outputs for one code: `qr_svg` (the existing renderer, reused unmodified in substance) and `qr_png` (a new deterministic 1-bit raster path, because a thermal printer that cannot rasterize SVG cannot print the SVG).
- One structured error shape shared by every tool, with a closed error-code vocabulary mapped from the existing `StickerCode`, `Selector`, `Catalog`, and `Units` error atoms, and a hard rule that no error ever echoes the offending input.
- Cross-request rate limiting: `Plugs.ClientIP` mounted for the first time, an in-memory per-machine bucket store, separate classes for resolution and rendering, a concurrency cap on rendering, and a request-size cap set explicitly on this path.
- Stripping the `x-request-id` response header — set by `Plug.RequestId` in `endpoint.ex` — on the MCP path before send; the plug and the header stay in place for the rest of the origin.
- The retention gate: the filesystem, ETS, `persistent_term`, process-state, and log-sink sweeps over a scripted session using distinctive fixture values.
- The idempotency and determinism gate: byte-identical code, SVG, and PNG for the same normalized input across processes, machines, and restarts.
- Widening `copy_lint_test.exs` `surface_files/0` to cover every shop-facing module wherever it lives, as a precondition of merging any string this server can return.
- An integration contract stating what the caller must do that we cannot enforce, and what we refuse to do at all.

## Excluded

- Any print queue, retry buffer, delivery receipt, job table, submission log, per-caller history, idempotency-key table, per-shop configuration store, or database-backed credential store. Each is a writable table; the first migration that adds one fails the existing repo-list release gate.
- A free-text vehicle resolver. `Selector` structurally cannot hold free text, and `RECOMMENDATION_CLAIMS_POLICY.md` forbids a nearest engine or configuration match. Matching a shop's strings against the closed sets returned by the cascade happens in the caller's process; the refusing resolver is `DOS-M10-001`, a separate issue.
- Any printed prose: interval, due date, viscosity or specification claim, base-stock claim, vehicle name, shop name, or advisory sentence. This server returns a QR image. The receipt template carrying the required framing, basis, status, source, deference, and no-affiliation content is a separate issue and a hard precondition for printing anything beside the QR.
- ESC/POS, ZPL, or any printer command framing; owning a print protocol would make us responsible for hardware we do not test. A general-purpose QR service: the renderer refuses any payload that is not a decodable sticker code.
- Booking, scheduling, payment, invoicing, customer contact, loyalty, fleet administration, and any notification of any kind (INV-17, INV-19).
- Server-side storage of anything a customer could later retrieve by scanning. There is no lookup endpoint and no plan for one.
- The constitution revision and ADR-0006 themselves, the source-rights re-review for machine-to-machine redistribution, and the refusing-resolver design — each is its own issue in this milestone; their gating split is stated in Dependency rationale.

## Functional requirements

- FR-1 (INV-27, INV-22): The server is mounted at a single path on the existing Fly.io application origin behind the `:api` pipeline. No second origin is introduced. Every response carries the existing security-header set. Plain HTTP is redirected by `force_ssl`; the integration contract states that callers must use `https://` directly, because a client that does not follow a 301 on POST breaks silently at the counter.
- FR-2 (INV-3, INV-22): No response sets a cookie and no handler reads or writes the session. The MCP path strips the `x-request-id` header `Plug.RequestId` sets before send, so no server-assigned session, connection, or request identifier is returned to the caller.
- FR-3 (INV-26): The impersonal lane is exactly `dos_catalog_metadata`, `dos_catalog_list_years`, `dos_catalog_list_makes`, `dos_catalog_list_models`, `dos_catalog_list_configurations`, `dos_catalog_get_configuration`, and `dos_codec_contract`. Their input schemas are generated from `Catalog.Vocabulary` at compile time and admit only its closed key set for these tools — `year`, `make_id`, `model_id`, `configuration_key`, `page_size`, `cursor` — with no `q`, `search`, `text`, or name field of any kind. An unknown key is rejected, never stripped.
- FR-4 (INV-8, INV-9, INV-11): `dos_catalog_list_configurations` returns each candidate's `configuration_key` with its distinguishing descriptors and its `support_status`. A year outside the rolling window is refused rather than normalized to the nearest in-window year. A battery-electric configuration returns `not_applicable`, rendered with the copy catalog's exact string `Engine oil service not applicable` (`Copy.not_applicable_ev/0`), per INV-9. Excluded classes — heavy commercial, motorcycles, powersports, off-highway, non-U.S. schedules — are absent from the catalog and resolve to nothing rather than to something close.
- FR-5 (INV-11, INV-7): `dos_catalog_get_configuration` treats `{:ok, %Result{data: nil}}` as a refusal, not a success. The facade returns `status: :unsupported` with qualifier `:configuration_not_in_data_version` for a well-formed but unknown key, and a caller matching only on `{:ok, _}` would print a sticker for a vehicle we do not have.
- FR-6 (INV-15): Every impersonal-lane result carries `data_version` and `schema_version`. A cursor minted under a different `data_version` is refused as stale rather than silently re-paged.
- FR-7: `dos_codec_contract` returns the format version, byte layout, epoch, every field range and sentinel, the frozen grade and base-stock tables **in wire order**, the manual-tail rules — including FR-14's printable-subset restriction, published here as a normative wire rule — and the full vector set. It states that base-stock wire order is insertion order while the catalog's `oil_base_stocks` query returns a display ordering (`ORDER BY published_miles_low, code`), so an integrator must never derive an index from a catalog query.
- FR-8 (INV-19, INV-26, INV-3): The encoding lane — `dos_sticker_encode`, `dos_sticker_decode`, `dos_sticker_qr_svg`, `dos_sticker_qr_png` — is behind a compile-time flag. With the flag off the four tools are absent from `tools/list` and a direct `tools/call` returns the unknown-tool error naming the required amendment. The flag is off in every environment shipped by this issue.
- FR-9 (INV-26): `dos_sticker_encode` accepts exactly `configuration_key`, `changed_on`, `odometer`, `grade`, `base_stock`, and `odometer_source`. It accepts no VIN, plate, name, note, customer reference, shop reference, or invoice number, and no free-text field other than the manual grade string the wire format already reserves. An input object carrying any additional property is rejected with `unknown_field`, and the offending key is not echoed, not logged, and not counted per-key.
- FR-10: `configuration_key` is required in canonical lowercase UUID form; an uppercase or otherwise non-canonical form is refused with `invalid_configuration_key` rather than normalized, because `Selector`'s identifier pattern is lowercase-only and lowercasing in one lane while refusing in another creates an input that encodes but cannot be resolved.
- FR-11 (INV-11, INV-15): `dos_sticker_encode` resolves `configuration_key` against the current `data_version` before encoding and refuses when the configuration is absent. The success result returns the resolved descriptors and `support_status` so the shop can confirm the vehicle on screen. Confirming before printing is a contractual obligation recorded in the ADR and the integration contract, stated as unenforceable rather than as a control.
- FR-12: `odometer` is an object of `{value, unit}` with `unit` in the closed set `mi | km`, converted through `DigitalOilSticker.Units.to_metres/2`. A bare number with no unit is refused with `missing_odometer_unit`. Assuming a unit would print a sticker wrong by a factor of 1.609 that would look entirely plausible on paper.
- FR-13: `changed_on` is an ISO 8601 calendar date, encoded as days since 2000-01-01, valid 0 through 65 534, with 65 535 reserved as absent. A date outside the range, a timestamp, a Unix epoch value, or a malformed string is refused with `date_out_of_range` or `invalid_date`; nothing is clamped, defaulted, or read from the server clock. Omitting the field encodes the absent sentinel and is distinct from sending a wrong date.
- FR-14: `grade` matching a frozen table entry encodes to its index. Any other string encodes through the manual tail, at most 20 **UTF-8 bytes** rather than 20 characters, valid UTF-8 with no C0 or C1 control character, no line terminator, and no escape byte — a DMS free-text column reaching a thermal printer is a command-injection surface we can cheaply refuse to participate in. This printable subset lives in one place — the codec contract (FR-7) — and binds every lane that writes the tail; `DOS-M10-001`'s promise to carry a non-table viscosity string into the tail **verbatim** is reconciled to *verbatim within this subset*, so one DMS string cannot yield a code through the resolver lane and a refusal through the encode lane. An unrecognised `base_stock` is refused with `unknown_base_stock`; there is no manual path, because an unknown value in a closed set is a caller bug rather than user input.
- FR-15 (INV-12): `odometer_source` is required from the closed set `observed | customer_reported`; a telematics or OBD-derived value is refused. This is a contractual control, documented as one: we cannot verify the caller's answer and retain nothing to audit. Its force is that an integrator must write it in their code and defend it at integration review.
- FR-16: `dos_sticker_qr_svg` and `dos_sticker_qr_png` accept a sticker code, not arbitrary text, and decode it before rendering; a payload that is not a decodable code is refused with `not_a_sticker_code`. `qr_svg` returns the existing renderer's output unmodified in substance — `viewBox` in module units, no `width`/`height`, four-module quiet zone painted white, `crispEdges`, merged runs in one path — plus `version` and `modules`. `qr_png` returns a 1-bit, alpha-free PNG at an integer `module_px` of at least 2 with no interpolation, plus pixel dimensions, `modules`, `module_px`, and the printed physical size for a caller-supplied `dpi` so the shop can check it against their printer before a run.
- FR-17: Rendering is deterministic and byte-identical for identical inputs. ECC level, mask selection, quiet zone, and path construction are fixed by input; the PNG carries no `tIME` chunk, no text chunk, and no producer string, and uses a pinned filter strategy and compression level.
- FR-18 (idempotency): The same normalized sticker returns the same code, and the same code returns the same images, at this layer as well as in the codec. `normalize/1` is applied before encoding so round-trip identity holds for a normalized sticker rather than for any map that happens to encode. There is no idempotency key, no deduplication, no cache keyed on any personal value, and no request identifier returned to the caller; repetition is a property of the function, not of a memory.
- FR-19 (INV-23, INV-4): The server retains nothing. Exactly one Ecto repo, `CatalogRepo`, opened read-only; no personal-data table, migration, or backup job; the catalog cache keyed on a validated impersonal selector only and never on a code, date, odometer, or grade; the rate-limit bucket a fixed two-field record of tokens and last-refill time, asserted by a shape test, keyed by a per-boot-salted hash and never by a request payload. No file is written, no ETS table holds a personal value, and no named process holds one after its call returns.
- FR-20 (INV-4): Logs MAY contain timestamp, tool name, outcome class, error code, duration bucket, release version, machine identifier, and the salted 32-hex client bucket. Logs MUST NOT contain a sticker code, any decoded field of one, a `configuration_key`, a manual grade string, an odometer or date value, a rendered image or its bytes, a caller credential or any prefix of one, a full client IP, or a body fragment. `configuration_key` is personal here because ADR-0004 prohibits logging the specific vehicle a session selected. `debug_errors` is false, no stacktrace serializes parameters, and third-party error reporting is prohibited outright.
- FR-21 (INV-22, ADR-0004 R7): Rate limiting is enforced per resolved client through `Plugs.ClientIP`, in memory, per machine, with separate buckets for resolution and rendering and a hard concurrency cap on rendering so one caller cannot saturate a machine. Starting points — 60 resolution calls per minute burst 30, 20 render calls per minute burst 10, at most 4 concurrent renders per machine — are to be measured, not asserted constants. Because Fly may run several machines and buckets are neither shared nor replicated, the effective ceiling is the per-machine limit times the machine count; the integration contract states this.
- FR-22 (INV-22): The request-body cap for this path is explicit and small — a decoded body over 16 KiB is rejected with `payload_too_large` rather than parsed or truncated; the current parser configuration would otherwise accept 8 MB. No CORS header is emitted on any method, including `OPTIONS`.
- FR-23 (INV-3): If the encoding lane is ratified with authentication, the credential identifies a business and never a customer; it is compared in constant time against a hash held in the runtime environment; it is never logged, never returned, never used as a cache key, and never used as any key outliving a request other than the in-memory rate-limit bucket, which holds a counter and a timestamp and nothing derived from the request. There is no per-credential request history and no counter that is per-credential and per-vehicle at the same time.
- FR-24 (INV-7, INV-11): Every refusal is returned to the caller as a refusal. The server never returns a best-effort code, a nearest-match configuration, a fabricated interval, or a partially valid image. A failure at our end must be able to reach the counter while the customer is still there, which the integration contract requires the caller to surface; we guarantee only that we do not hand them something plausible instead.
- FR-25 (INV-15, INV-16, INV-20, INV-21): No tool returns prose. The only strings any tool emits are enumerated status and error codes, `data_version`, `schema_version`, and the descriptor fields the catalog already publishes. The server emits no interval, no due date, no compatibility statement, and no advisory sentence. Shop-facing user-visible vocabulary does not exist yet and is not invented here; adding one is a ratified change, not a copy choice.

## Technical implementation contract

### Components and ownership boundaries

- **`DigitalOilStickerWeb.MCP.Router`** — MCP framing only: `initialize`, `tools/list`, `tools/call`, protocol-version negotiation, and the JSON-RPC error envelope. No domain logic and no field names.
- **`DigitalOilStickerWeb.MCP.Tools.Catalog`** — the impersonal lane. Generates its JSON Schemas from `Catalog.Vocabulary` at compile time and dispatches to `Catalog`. It is the only module permitted to build a `%Selector{}` from an MCP payload, by the same reject-not-strip rules the LiveView edge uses, and it deliberately follows the shape of the existing `CatalogEvents` edge — allowlist, rate-limit, validate, dispatch — so the two edges can be diffed.
- **`DigitalOilStickerWeb.MCP.Tools.Sticker`** — the encoding lane, compiled only when the flag is on. It is the only module that encodes or decodes on behalf of a third-party request. A boundary test enumerates the permitted web-facing callers of `StickerCode.encode/1` and `decode/1` as exactly this module and the existing `StickerLive` fragment-URL path (`qr_for/2`, which encodes the user's own record), and fails on any other caller.
- **`DigitalOilSticker.StickerQR`** — new; the server-side renderer. Ports `sticker_qr.js`'s SVG output and adds the PNG path, held to the same emitted vectors plus a new image-fixture set, so three implementations agree rather than two.
- **`DigitalOilStickerWeb.MCP.Errors`** — the single mapping from internal atoms to the closed wire vocabulary, total over the known atom sets, mapping anything unrecognised to `internal_error` so a new atom cannot leak a name through an error path.
- **`DigitalOilStickerWeb.Plugs.ClientIP`** — existing, mounted here for the first time; the only module that ever sees a full client address. **`DigitalOilStickerWeb.MCP.RateLimit`** — new; the shared in-memory bucket store a stateless transport needs, since `Catalog.RateLimit` is per-socket and an HTTP request has no socket.
- Not owned here: the catalog implementation, the codec, the browser client, the receipt template, the resolver, the constitution revision, and the ADR.

### Data and persistence

- Exactly one Ecto repo, `CatalogRepo`, opened read-only with `PRAGMA query_only`. This issue adds no repo, no migration, and no table. There is no queue, retry buffer, delivery receipt, idempotency table, or credential table.
- Personal values exist only as arguments and return values within one request, and are unreachable once the response is written. Nothing is cached on any value derived from a code, odometer, date, or grade.
- The catalog ETS cache stays keyed on the validated impersonal selector; a test asserts no cache key or value in any generation contains a personal value after a scripted encoding session.
- Rate-limit buckets are per-machine, in memory, keyed by a per-boot-salted hash, holding tokens and a refill timestamp only. They die with the machine and are never replicated — a limitation rather than a design goal, and stated as one.
- Credentials, if the lane is ratified, live in the runtime environment as hashes, which bounds a pilot to the number of entries a release can reasonably carry; growing past that is the credential-store open question recorded below.

### Interfaces and events

- Transport is streamable HTTP at one path; request and response are JSON, with no server-initiated message and no long-lived connection.
- Every tool result is an MCP content block plus a `structuredContent` object of the shape `{ok: true, data: {...}, data_version, schema_version}`.
- Every failure is `isError: true` with `{ok: false, error: {code, class, retryable}}`, where `class` is one of `invalid_input | refused | not_found | rate_limited | unavailable | internal` and `retryable` is a boolean the caller can branch on without parsing a message. The object carries no free-text message, no field path, and no echo of input. Closed codes include `unknown_field`, `invalid_selector`, `year_out_of_window`, `configuration_not_found`, `stale_cursor`, `invalid_configuration_key`, `missing_configuration_key`, `missing_odometer_unit`, `odometer_out_of_range`, `odometer_not_a_number`, `odometer_implausible`, `date_out_of_range`, `invalid_date`, `invalid_grade`, `manual_grade_too_long`, `manual_grade_not_printable`, `unknown_base_stock`, `invalid_base_stock`, `not_a_sticker_code`, `unsupported_format_version`, `payload_too_large`, `module_size_too_small`, `payload_too_long`, `rate_limited`, `catalog_unavailable`, and `internal_error`.
- `qr_svg` returns `{svg, version, modules}`; `qr_png` returns `{png_base64, width_px, height_px, modules, module_px, printed_mm}`, with `printed_mm` present only when the caller supplied `dpi`. The image is also returned as an MCP image content block.
- Telemetry reuses the existing `[:dos, :catalog, :cache]` and `[:dos, :catalog, :unavailable]` events and adds MCP-level counters. A test asserts every handler's metadata carries no selector and no personal value.

### Failure and recovery behavior

- **The catalog is unavailable.** `catalog_unavailable`, `retryable: true`, render nothing. There is no cached fallback and no last-known-good configuration, because presenting a stale catalog result as authoritative is prohibited.
- **The vehicle does not resolve to exactly one configuration.** The cascade returns the candidate set with descriptors and the caller chooses; `encode` refuses a key absent from the current `data_version`. There is no confidence score, no closest trim, and no silent dropping of the engine qualifier.
- **The DMS sends an odometer with no unit, a date in the wrong format, or a 30-byte grade string.** Each is a distinct refusal code. Nothing is coerced. The technician sees an error rather than a sticker that is quietly wrong.
- **A code is printed and the catalog is later rebuilt.** A `configuration_key` can disappear across a `data_version` (it is a UUIDv5 over parts including, for EPA-enriched rows, a source row identifier not derivable from vehicle text). A printed code that no longer resolves must scan into an explicit unknown-vehicle state, never into a different vehicle. The response carries `data_version` so an integrator can record which version a run was printed under; we hold no such record.
- **The QR is printed too small, or on a worn print head.** There is no checksum byte by design; the QR's own error correction is the stated layer for transcription damage. The renderer enforces a minimum module size and reports printed physical size, and the device matrix measures real scans; we do not claim scannability on untested hardware.
- **The rate limit trips mid-shift.** `rate_limited`, `retryable: true`. The caller must not fall back to printing an unverified sticker; the integration contract says so, and we cannot enforce it.
- **The encoding-lane flag is off and a caller calls it.** Unknown-tool error naming the amendment; the tool is absent from `tools/list`, so a conformant client never reaches this path.
- **A request exceeds the body cap.** Rejected before parsing, never truncated.
- **A crash inside a tool.** `internal_error` with no detail; the stacktrace is logged with parameter filtering applied and is covered by the retention gate's induced-crash runs, because a crash trace is the most likely path for an odometer to reach a log.

### Security and privacy

- The two lanes are separated in the build, not by a runtime check, so a misconfiguration cannot expose the encoding lane; the flag-off release does not contain the tool definitions at all.
- A sticker code is personal data. It is a bijection, not a digest — anyone who can read it can read the values — so accepting a code at `qr_svg` or `qr_png` transmits an odometer and a service date to the server in encoded form. This is stated plainly rather than treated as anonymization, and every retention, logging, and caching rule applies to the code string itself.
- Server-side rendering is a convenience, not a necessity: rasterizing a QR module matrix to a monochrome bitmap needs no font and no graphics library, so an integrator who can run the vendored renderer can produce the PNG locally. The server-side path exists only for callers who cannot, and the ADR records that as its sole justification.
- The renderer refuses non-code payloads, which keeps the surface from becoming an open QR service and from printing arbitrary payloads a scanner would attribute to us.
- The manual grade tail is the only caller-supplied free text reaching the wire; it is length-capped in bytes, UTF-8 validated, and stripped of control and escape characters before encoding.
- No credential, if one exists, is ever a cache key, log field, correlation key, or durable record; a per-integrator submission store is the shape ADR-0004 already named and rejected.
- The vendored `qrcodegen.js` provenance record stands; the Elixir renderer adds no runtime dependency and no third-party service, per ADR-0004.
- The residual risk this design cannot close is that a shop's own systems retain everything we refuse to. We are not the only party on the wire, and the integration contract says so instead of implying a privacy property we do not control.

### Accessibility and performance

- This surface has no user interface; what matters is that its artifact is read by a human with a phone camera in a shop. `qr_svg` sets `role="img"` with a `<title>` when the caller supplies one and `role="presentation"` with `aria-hidden` when it does not, so an embedded SVG inherits a correct accessible name; a title containing a personal value is refused.
- The printed artifact must reach a stated minimum module size, retain its four-module quiet zone, and be measured by real scans at 203 dpi and 300 dpi rather than assumed. Contrast on thermal paper degrades with head wear and paper age, so the device matrix includes a worn-media pass.
- Rendering is CPU-bound and is capped by concurrency rather than allowed to compete with LiveView sessions on the same machine; resolution calls ride the existing catalog cache and stay inside its budget.
- Payloads stay small: a fully populated code is 40 characters, an SVG of merged runs is a few kilobytes, and the PNG is bounded by the module-size cap so a caller cannot request a multi-megapixel raster.

## UX and content states

There is no interface here, but there are human-visible surfaces, and the failure modes belong to them.

- **The technician's screen, on refusal.** The integration contract requires that every refusal class reaches the person at the counter before the customer leaves, and that no refusal is retried into a print. We can guarantee only the refusal shape; we state that limit rather than claiming the outcome.
- **The technician's screen, on ambiguity.** Where a year, make, and model resolve to several builds, the caller shows the candidate descriptors and a human picks, as the browser application's build selector does. Auto-selecting the first candidate is prohibited by the contract; a nearest match is prohibited by policy.
- **The printed artifact.** A QR, its quiet zone, and nothing else from us — no interval, no date, no grade claim, no vehicle name, no sentence. The correct response to a surface that cannot carry the qualifications is to print nothing that needs them.
- **What surrounds our block on the paper.** We do not control the receipt. Our output is self-contained, carries no third-party mark, and sits in no lockup with a manufacturer name; the no-affiliation statement and source attribution belong to the receipt-template issue and the attribution page.
- **What a customer will infer.** A QR printed by a shop reads as "they have my record on file". Nothing here may contradict the truth that we hold nothing, and nothing may imply a record, a reminder, or a recovery path. The vocabulary that would say so correctly on a receipt does not exist in INV-21 yet — a reason to ship no prose rather than to invent some.

## Acceptance criteria

- [ ] AC-1: `tools/list` returns exactly the seven impersonal tools in the flag-off build; a `tools/call` for any of the four encoding tools returns an unknown-tool error, and a build-artifact scan confirms the encoding-lane tool definitions are absent from the compiled release.
- [ ] AC-2: Each impersonal tool's JSON Schema is generated from `Catalog.Vocabulary`, and a test fails if any tool admits a key outside the closed set or if a schema and its validator disagree on any key.
- [ ] AC-3: A request carrying any additional property — including `vin`, `plate`, `customer`, `note`, `invoice`, `shop_id`, or a name field — is rejected with `unknown_field`, and the offending key and value appear in no response, no log line, and no metric label.
- [ ] AC-4: A year outside the rolling window is refused rather than adjusted; a well-formed but unknown `configuration_key` returns `configuration_not_found` rather than a success with null data; a cursor from a different `data_version` returns `stale_cursor`.
- [ ] AC-5: An independent implementation, written against `dos_codec_contract` output alone as a build discipline, encodes and decodes all 18 committed vectors byte-for-byte, and its grade and base-stock indices match the frozen wire order rather than the catalog query's display order.
- [ ] AC-6: With the flag on in a test build, `dos_sticker_encode` refuses each of: an uppercase `configuration_key`; a bare numeric odometer with no unit; an odometer that is negative, non-numeric, or above the plausibility ceiling; a date outside 0 through 65 534 days from 2000-01-01; a malformed or timestamp-shaped date; a manual grade over 20 UTF-8 bytes; a manual grade containing a control, escape, or line-terminator character; an unknown `base_stock`; and an `odometer_source` of `telematics` or `obd`. Each returns its own error code, and no input is coerced, clamped, defaulted, or echoed.
- [ ] AC-7: `dos_sticker_encode` for a `configuration_key` absent from the current `data_version` refuses, and its success result carries the resolved descriptors, `support_status`, and `data_version`.
- [ ] AC-8: `dos_sticker_qr_svg` and `dos_sticker_qr_png` refuse any payload that is not a decodable sticker code with `not_a_sticker_code`, and refuse a `module_px` below the minimum with `module_size_too_small`.

- [ ] AC-10: For every committed vector and for 10 000 generated stickers, `encode` after `normalize` returns the identical code on repeat calls in the same process, in a fresh process, and after a machine restart; no response-body field or image byte varies between repeats; and no header varies outside the enumerated per-request set (the mandatory `Date` header and transport framing headers), with `x-request-id` asserted absent from every MCP response.

- [ ] AC-12: The rate-limit record is asserted to be a fixed struct of tokens and last-refill time with no field derived from any request payload, and the bucket key is asserted to be a salted hash whose salt is generated at boot and never persisted.
- [ ] AC-13: The scripted-session log scan across every configured sink finds no sticker code, decoded field, `configuration_key`, manual grade, odometer, date, image byte, credential or credential prefix, full client IP, or body fragment — including under induced crashes at each tool — while confirming the permitted fields are present, so the scan is proven to be reading real output.

- [ ] AC-15: No response carries a `Set-Cookie` header, no handler touches the session, and no response carries any CORS header on any method including `OPTIONS`.

## Test plan

### Automated

- Schema-generation tests: every impersonal tool schema is derived from `Catalog.Vocabulary`; a deliberately added vocabulary key appears without a code change; an unknown key in a payload is rejected. Reject-not-strip tests mirroring the existing selector suite, run through the MCP adapter, so the transport cannot reintroduce coercion.
- Refusal-code tests for every entry in the closed error vocabulary, each asserting the response carries no message string, no field path, and no echo of input; and result-shape tests asserting `{:ok, %Result{data: nil}}` converts to `configuration_not_found` and never to a success.
- Codec-contract conformance: a from-scratch encoder built only from `dos_codec_contract` output reproduces all 18 committed vectors, including manual-tail cases and absent-value sentinels.
- Renderer conformance: Elixir SVG output compared byte-for-byte with the JS renderer over every vector at each ECC level; a new image-fixture set pins the PNG bytes; a chunk-level assertion proves no time, text, or producer chunk is present.
- Determinism and idempotency: property tests over generated stickers asserting `encode(normalize(s))` is stable across repeats, processes, and a simulated restart, and that images are stable for the same code.
- Injection and bounds tests on the manual grade tail: 20-byte and 21-byte multi-byte strings, control characters, escape sequences, line terminators, and invalid UTF-8. Unit-handling tests: mile and kilometre inputs converging on the same metre value at the boundary, comma- and space-formatted numeric strings, and refusal for a missing unit.
- Retention gate: a scripted session, then a filesystem diff, an `:ets.all()` sweep, a `persistent_term` sweep, a `:sys.get_state` sweep over named processes, and a log scan across every sink, repeated with an induced crash at each tool.
- Rate-limit tests: separate resolution and render thresholds, burst behavior, the render concurrency cap, bucket record shape, and an assertion that the client address is absent from state and logs.
- Transport tests: cookie absence, session untouched, CORS absence on every method, body-cap rejection before parsing, and HTTPS redirection of a plain-HTTP request.
- Build-shape tests: the flag-off release contains no encoding-lane tool definition; `tools/list` matches the expected seven; a boundary test pins the enumerated web-facing callers of the codec.
- Copy-surface tests: the widened `surface_files/0` covers this tree, and the enumerated returnable-strings fixture contains no claim language. Telemetry metadata tests assert no event carries a selector or personal value.

### Manual/device matrix

Real hardware, because a QR that has only ever existed as bytes is an untested artifact. Each row records module size, printer resolution, media state, scanner, and outcome.

- Thermal receipt printer at 203 dpi, fresh roll: print at the minimum module size and one step above; scan with iOS Camera, Android's built-in scanner, and a handheld 2D imager.
- Thermal receipt printer at 203 dpi, worn print head or aged media: same passes, recording the smallest module size that still scans reliably.
- Thermal label printer at 300 dpi: same passes, confirming the quiet zone survives label edge trimming.
- Office laser at 600 dpi as a control, to separate renderer defects from thermal-media defects.
- SVG path: render the returned SVG in a POS-terminal-class browser and print through the terminal's own print path, confirming the missing `width`/`height` scales rather than collapses in that stack.
- Scan a server-produced code and a JS-client-produced code from the same values, and confirm both decode to the same sticker in the browser application.
- Scan a code whose `configuration_key` was removed in a later `data_version` and confirm the client shows an explicit unknown-vehicle state rather than a different vehicle.
- Walk the counter workflow end to end with a stopwatch: resolve, confirm the vehicle on screen, print, hand over. Record what a technician does when a refusal appears and a customer is waiting — the scenario FR-11 and FR-24's contractual controls are up against.

## Rollout and rollback

Roll out contract-first. Publish `dos_codec_contract` and the impersonal lane, and let a pilot integrator implement encoding and rendering locally against the vectors; that path needs no constitution amendment and transmits no personal field, though it still waits on the accepted ADR-0006 and the Rule 2b re-review, which gate this issue in full. Only if a real integrator demonstrably cannot execute the codec does the encoding lane become worth its cost, and by then the amendment, the ADR, and the re-review are either done or the lane stays off.

Enable the encoding lane, if at all, on one integrator, in one shop, with the retention gate wired as a release blocker from the moment it exists. Watch the ratio of `encode` calls to `codec_contract` fetches: a caller that never fetches the contract never intended to encode locally — a product decision to revisit rather than a metric to celebrate.

Rollback is asymmetric and the asymmetry is the point. Every server-side control is configuration in the release: revert, redeploy, and the surface is gone, with no data migration because there is no data. The stickers are not recallable: a printed code outlives the release that produced it and the `data_version` that resolved it, and cannot be corrected, revoked, or re-issued. A defect in encoding, resolution, or module size is therefore discovered on a customer's window rather than in a dashboard. Two consequences: the device matrix runs before the pilot, and a suspected encoding defect stops printing immediately rather than after triage.

## Dependency rationale

Blocked by `DOS-M10-001`, the refusing intake resolver, per the epic's reconciled roster. Blocked by the epic's governance child carrying the constitution revision and ADR-0006. The split: the accepted ADR blocks the whole issue, because a machine surface is outside ADR-0004's fenced grant; the revision blocks only the encoding-lane flag flip, because the encoding lane accepts an odometer, a service date, and a free-text grade in a request body and INV-26 prohibits exactly those fields in a body — writing the tools before the amendment is permitted only because they ship compiled out, and enabling them before it is not. Blocked in full — impersonal lane included — by the epic's source-rights re-review child, because handing catalog facts to a commercial integrator's system for reprint is a distribution mode neither the bundle analysis nor the hosted-serving analysis covered, and ADR-0004 R6 records that gate as hard. Blocked by `DOS-M09-004`, because the impersonal lane is a projection of that facade and its `%Result{}`, cursor, and status semantics. Blocked by `DOS-M09-007`, because this issue mounts `Plugs.ClientIP` for the first time and extends that issue's repo-list assertion and scripted-session log scan rather than writing a second, weaker copy. Blocked by the copy-lint surface widening, assigned by the epic to its printed-template child, because a gate that does not scan this tree would stay green while unlinted strings reached a customer's paper.

Blocks the M10 receipt-template issue, which cannot specify what is printed beside the QR until the QR's format, module-size floor, and refusal semantics are fixed. Blocks any M10 pilot issue, because no integrator may be onboarded against an unproven retention gate. It does not block, and must not be represented as unblocking, any customer-facing lookup, reminder, or record-retrieval capability; those are prohibited by INV-3, INV-19, and INV-23 rather than sequenced behind this issue.

## Risks, decisions, and open questions

- **Risk (foundational):** this feature inverts a shipped design decision — `sticker_code.ex` says nothing is stored and the code carries the values; `sticker_qr.js` says the values never reach the server. A server-side encoder makes both false for one caller class. Mitigation is containment, not resolution: two lanes separated in the build, a contract tool designed to make the server-side path unnecessary, and an ADR that records the reversal in the open rather than letting it accumulate as precedent.
- **Risk:** a centrally generated code invites a lookup service next — "let the customer scan it and pull their record from you" — which is a server-side garage. Mitigation: the exclusion is written into this issue in the terms of INV-19 and INV-23, and the codec's property tests are the standing argument that a lookup table would be redundant.
- **Risk:** a `configuration_key` can disappear across a `data_version`, and printed paper outlives catalog rebuilds. Mitigation: responses carry `data_version`, and a scan of a stale key must produce an explicit unknown-vehicle state; the device matrix tests that path deliberately.
- **Risk:** the QR is printed too small or on worn media and does not scan, and nobody finds out until the customer tries. Mitigation: a module-size floor, printed physical size reported back, and a real-hardware matrix including a worn-media row; we do not claim scannability on untested hardware.
- **Risk:** a technician facing a refusal with a customer waiting reaches for a workaround. Mitigation is contractual and stated as such: FR-11 and FR-24 place the obligation on the integrator, and we can guarantee only that we never hand back a plausible substitute.
- **Risk:** a shop's DMS free-text grade column carries whatever a service writer typed, and it crosses our wire and may reach a printer. Mitigation: byte-capped, UTF-8 validated, control and escape characters refused.
- **Risk:** an integrator credential becomes an account, and the pair of a credential and a stream of vehicles becomes a customer service history. ADR-0004 already named and rejected this shape. Mitigation: credentials in the runtime environment only, no per-credential history, no counter that is per-credential and per-vehicle at once, and a rate-limit record whose shape is asserted by test.
- **Risk:** rate limiting is a mitigation for catalog scraping, not a solution (ADR-0004 R7), and a machine surface is easier to scrape than a browser one. Recorded, not solved here. Relatedly, a machine surface on the user application's origin adds attack surface and shares CPU with the LiveView app — recorded against the counter-risk that a second origin needs an INV-27 amendment.
- **Risk (process):** the epic assigns the transport question (MCP versus one client of an HTTP/JSON contract) to the contract child while this card assumes MCP; letting that assumption stand would turn an unresolved question into an implementation decision (CHANGE_CONTROL Rule 4). Mitigation: ADR-0006 carries the transport decision explicitly.
- **Decision:** two lanes separated at compile time, not one lane with a runtime permission check; a sticker code is classified personal data everywhere in this design; the QR renderer accepts only decodable sticker codes, never arbitrary text.
- **Decision:** this server returns a QR image and no prose; the receipt template carrying the estimate framing, basis sentence, INV-11 status, source, and oil-life-monitor deference is a separate issue and a precondition for printing anything else.
- **Decision:** no free-text vehicle resolution in this issue — matching a DMS string against the closed sets returned by the cascade happens in the caller — and `configuration_key` is required in canonical lowercase and refused otherwise, rather than normalized in one lane and refused in another.
- **Open question:** whether the owner accepts a distributed codec at all. If yes, the encoding lane may never need to be enabled and this issue's most valuable output is `dos_codec_contract`. If no, the amendment is the real gate and this issue waits on it.
- **Open question:** the credential model past a pilot. Environment-held hashes bound the integrator count; a credential store is a writable database, which points at a separate deployment with its own ADR and repo list rather than a second repo in this one. Unanswered, and it must not become an implementation assumption.
- **Open question:** the exact rate-limit thresholds and render concurrency cap, to be measured against a real shop's call pattern rather than guessed, and re-recorded.
- **Open question:** the minimum module size that scans reliably on worn thermal media — a measurement, not a specification we can assert in advance.
- **Open question:** whether a commercial or partnered integration would flip the always-false affiliate and sponsorship fields, making adjacent disclosure a requirement on the receipt and changing what the receipt-template issue must carry.

## Definition of done

- All functional requirements are implemented and all acceptance criteria are checked, with the evidence above attached or linked from CI.
- The impersonal lane is live, its schemas are generated from the vocabulary, and an independently built codec reproduces every committed vector from `dos_codec_contract` alone.
- The encoding lane is implemented, fully tested, and absent from the shipped build, with a build-artifact scan proving its absence.
- The retention gate, the log scan, the repo-list and read-only assertion, the schema and migration scan, and the determinism gate are wired as release-blocking checks and pass, including under induced crashes.
- The device matrix has been executed on real printers and real scanners, with failing rows recorded as unsupported rather than omitted.
- The copy-lint scan surface covers this tree, and the enumerated set of strings this server can return contains no claim language, no interval, and no due date.
- The integration contract is published, including the controls we require but cannot enforce and the effective rate ceiling under per-machine buckets.
- The constitution revision, ADR-0006, and the source-rights re-review are linked, or the encoding-lane flag remains off and the issue closes with that stated as its outcome rather than deferred silently.
