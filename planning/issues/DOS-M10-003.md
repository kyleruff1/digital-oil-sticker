## Outcome

A shop can capture a vehicle and an oil change in the workflow it already uses, and hand the customer a receipt carrying a symbol that scans. The integration surface that makes this true is three separate things, deliberately kept apart: a **local codec package** that runs inside the shop's own system and composes the sticker code from values that never traverse our network; an **impersonal resolution call** — consumed from `DOS-M10-001` and `DOS-M10-002`, not defined here — that turns a year/make/model/engine selection into a `configuration_key` and an INV-11 support status and carries nothing else; and a **print contract** — a fixed template, an explicit error-correction level, an integer dot scale, a minimum printed width owned by `DOS-M10-004`'s measurement, and a fallback ladder that ends in typed text rather than in a symbol that looks scannable and is not.

The first integration target is named with its reason, the patterns that were rejected are named with theirs, and every refusal path — an ambiguous vehicle, a vehicle outside the rolling window, a vehicle with no engine oil service, an oil the codec cannot encode, a printer that silently ignored the command — resolves to something a service advisor can read while the customer is standing at the counter.

## Why this matters and what it unblocks

The existing architecture is not neutral about this feature. `sticker_code.ex:6-9` records the design decision in the affirmative — "there is nothing to store… a QR is generated from the record itself rather than from a row in a table somewhere. No server-side garage, no identifier to correlate, nothing to leak (INV-23, INV-26)" — and `sticker_qr.js:10-11` states the consequence for rendering: "the values never reach the server, so the server cannot render this." A shop-facing surface designed the obvious way, where a point-of-sale system POSTs `{vin, odometer, service_date, oil}` and we answer with a QR, is not an extension of that architecture. It is its reversal, and INV-26 prohibits every field in that payload by name.

So the value of this issue is not the integration. It is establishing that the integration can exist *without* the reversal, by moving the codec instead of the data. The codec is already a bijection with a frozen wire format and an emitted cross-implementation vector set (`conformance/fixtures/sticker-code-vectors.json`), and it has already been ported once to a second client for exactly this reason. Porting it a second time, to the shop's machine, is a pattern the repository already uses rather than a new one.

This unblocks the milestone's shop-facing surface without touching the server's privacy posture, and it produces the print contract that any later channel — a different printer family, a label stock, a partner's own template — is measured against. It stays blocked until the constitution revision and the ADR land, because INV-19 currently lists "shop booking, commerce" in prohibited MVP scope and the preamble is explicit that amendments require a new ratified revision, never an in-place edit.

## Included

- **The packaged codec**: the sticker codec plus a QR encoder, packaged to run inside the shop's system and held to `conformance/fixtures/sticker-code-vectors.json` exactly as the browser port is. It composes the payload locally and never calls us to encode.
- **The integration-pattern evaluation**, with rejected patterns and their reasons, and one first target chosen with its reason recorded.
- **The resolution adapter**: consuming the contract `DOS-M10-001` defines and `DOS-M10-002` transports — the only network call in the feature, carrying year, make, model, and engine descriptor selectors and returning a `configuration_key`, an INV-11 status, a `data_version`, and qualifier codes — with refusing semantics, so exactly one match or a named refusal, and ambiguity as a first-class result rather than an error to be smoothed over.
- **The print contract**: template layout, ECC level, integer dot scale, quiet-zone rule, the derived minimum printed width in millimetres at 203 dpi, and the fit check for 58 mm and 80 mm stock.
- **The fallback ladder**: native printer QR → rasterized bitmap → text-only → print nothing about the sticker at all, with each rung's entry condition stated as something a program can evaluate.
- **The printed claim block**: the mandated strings, the basis sentence, the INV-11 status line, the OLM deference line where INV-14 applies, the verbatim no-affiliation statement, and the rule that a receipt too narrow to carry them prints symbol and code and nothing else.
- **The copy-lint scan-surface extension**, so no shop-facing or print-template module can ship unlinted claim copy. The paper re-measurement of the 1.6-device-pixels-per-module figure is `DOS-M10-004`'s, consumed here.

## Excluded

- **Any live endpoint accepting a VIN, odometer reading, service date, note, custom vehicle name, record identifier, or free-text grade.** Prohibited by INV-26 and not resolvable by adding a filter. `DOS-M10-002`'s flag-off MCP encoding lane — compiled out, deferred behind the revision and ADR — is that card's scope; this card neither ships, enables, nor falls back to it.
- **A print queue, retry buffer, delivery-receipt store, idempotency-key table, per-shop configuration store, or submission log.** Every one is a writable table, and the first migration that adds one fails the existing repo-list release gate (ADR-0004 §Decision 4). A stateless synchronous call whose failure is returned to the caller is the only shape in scope.
- **Shop accounts, API keys, tenancy, and any per-shop identifier.** If shop authentication is required it is a business-account system and belongs in the constitution revision under its own name, with the correlation argument answered — not smuggled in as a header.
- **Any lookup service.** No endpoint accepts a code and returns a record. The code carries the values, so there is nothing to look up (`sticker_code.ex:6-9`), and building one would be a server-side garage in a single step (INV-3, INV-23).
- **Fleet administration, shop booking, scheduling, invoicing, payment, and anything that reads or writes the shop's customer list** (INV-19).
- **Any claim that the customer will be reminded** — the MVP is in-app due/overdue state only and must not imply background alerting of any kind (INV-17) — and **any machine odometer feed treated as authoritative**: a DMS odometer value is a number a human typed upstream, and the print block labels it as recorded, not read (INV-12).
- **Changing the wire format, the frozen grade or base-stock index tables, or the epoch.** This issue consumes the format; it does not amend it.
- **A second origin, a CORS policy, or a browser-side cross-origin call.** The enforced CSP `connect-src` is first-party plus the canonical `wss://` origin; a browser integration calling anywhere else is blocked by our own policy (INV-22).
- **Non-US territory**, which is a named risk rather than accepted scope, and **label stock, synthetic media, and windshield-durable printing** — excluded precisely because a thermal receipt is not a windshield sticker.

## Functional requirements

- FR-1 (INV-26, INV-23, INV-24.1): No component in this feature transmits a VIN, odometer reading, service date, note, custom vehicle name, record identifier, free-text grade, or stable client identifier to any server operated by this project, in any position — path, query string, body, header, cookie, or socket payload. This is a structural property of the packaged codec, asserted by a wire-capture test over a full shop workflow, not a filter applied to a payload that once contained them.
- FR-2 (INV-26, INV-1): The shop-facing surface is split into a **local half** and a **network half**. The local half — sticker-code encoding, QR generation, print-command assembly — executes entirely inside the shop's system. The network half is a single stateless resolution call carrying only impersonal selectors. No third position exists.
- FR-3: The packaged codec is held to `conformance/fixtures/sticker-code-vectors.json` and fails its build if any of the 18 vectors does not round-trip. The Elixir module remains canonical; the package is a port, not a second definition, on the same terms as the JS port (`sticker_code.ex:51-57`).
- FR-4: The packaged codec derives grade and base-stock byte values from the frozen tables carried in the package itself, never from a catalog query. The catalog's `oil_base_stocks` returns rows alphabetically while the wire order is insertion order; deriving indices from a query silently produces wrong codes that decode to a different oil.
- FR-5 (INV-11, INV-10): The resolution call accepts `year`, `make`, `model`, and an engine descriptor selection, and returns exactly one of: a single `configuration_key` with its INV-11 status and `data_version`; an **ambiguous** result carrying the candidate list for a human to choose from; or a named refusal. It never scores, ranks, or picks a nearest match.
- FR-6 (INV-8, INV-9): A model year outside the rolling window is refused with `out_of_window` and the window bounds. A vehicle class outside MVP coverage — heavy commercial, motorcycle, powersports, off-highway — is refused with `class_out_of_scope`. Neither is normalized into the nearest in-window or nearest-class row.
- FR-7 (INV-11, INV-7): A well-formed but unknown configuration returns `{:ok, %Result{}}` with `status: :unsupported` and qualifier `:configuration_not_in_data_version` — it is **not** an error at the facade. The integration adapter treats that shape as a refusal explicitly, and a test proves that a caller matching only the success shape cannot reach the print path.
- FR-8 (INV-11, INV-13, INV-20): A configuration whose status is `:not_applicable` with basis `:electrification_bev` prints `Engine oil service not applicable` and no interval, no grade, and no due date. A configuration with `:identity_only` prints the identity and the QR and states that no schedule was available, using `Source unavailable` where the source is the missing part.
- FR-9 (INV-7, INV-15): If resolution fails for any reason — refusal, rate limit, catalog unavailable, stale cursor — the shop's system MUST NOT print an interval, a due date, or a grade claim. It prints nothing about the sticker and shows the advisor the refusal. A best-effort sticker is prohibited; a missing sticker is recoverable at the counter and a wrong one is not.
- FR-10 (INV-16, INV-12): The oil the shop actually used is recorded as a recorded value, not as a compatibility finding. `Meets the recorded requirements` may appear only when every mandatory requirement has a source-backed match; if only viscosity matches, the print block says exactly that. The odometer is labelled as a recorded reading, never as one the product read.
- FR-11: An oil base stock the codec does not recognize returns `unknown_base_stock` and **does not encode** — there is no code and therefore no symbol. The advisor is told which value was unrecognized and which four values are accepted. A free-text grade encodes through the manual tail at ≤ 20 UTF-8 bytes and is length-checked in bytes, not characters; an over-length value is refused rather than truncated, because a truncated grade prints a different oil.
- FR-12: A free-text grade string is treated as untrusted input at every boundary it crosses: byte-length validated, control characters and line-ending bytes rejected before it can reach a print command stream, and never interpolated into an escape sequence. A DMS oil column is whatever the last advisor typed into it.
- FR-13 (odometer and date): The odometer is converted at the boundary with the existing unit conversion, and `not_a_number`, `negative`, and `implausible` are surfaced as named refusals. A service date outside the encodable range is refused with `date_out_of_range` rather than clamped, because a clamped date prints a sticker that is wrong by years.
- FR-14 (**integration patterns**): The evaluation is recorded with a verdict per pattern, and the first target is chosen with its reason. The five patterns and the assessment this issue adopts:
  - **Native printer QR command (`GS ( k`)** — the printer generates the symbol from the payload string we hand it. Realistic and cheap where present, widely implemented on mainstream ESC/POS hardware, and the only pattern with no rasterization step. **Not universal**: clone firmware varies, some units ignore the model selector, some cap the module-size parameter. It must be feature-probed per printer model and recorded, never assumed from a datasheet.
  - **Rasterized bitmap (`GS v 0`)** — we render the symbol to a bitmap and send dots. Works anywhere raster printing works, which is nearly everywhere, at the cost of owning the scaling. **Realistic**, and it is the required second rung because it is the only path that works when the native command does not.
  - **Hosted webhook** — the shop's system POSTs a service record and we answer with an image. **Rejected.** It is the pattern a shop will ask for and it is precisely the INV-26 violation; it additionally requires per-shop credentials (INV-3), a queue or retry buffer (INV-23), and a second production client (INV-1). On the INV-26 axis, `DOS-M10-002`'s flag-off MCP encoding lane is the same surface, not architecturally different; its disposition — specified, tested, compiled out, deferred behind the revision and ADR — is recorded there, this rejection here, and neither revives the other by side effect.
  - **Paste-in URL / manual handoff** — the advisor opens the app in a browser on the shop terminal, enters the four values, and prints from the browser. **Realistic today, with zero new invariant exposure, and it is the honest baseline every other pattern must beat.** It ships as the documented fallback for any shop with no integration at all.
  - **Browser extension** — realistic only for browser-based shop-management systems, and it buys a store review process, a second distribution and auto-update channel, a permissions prompt on the shop's own pages, and our codec running where the host page can read it. **Deferred**, with the cost recorded rather than the reach overstated.
  - **First target: the local command-builder package driving the native QR command, with the raster path as its required fallback.** The reason: it is the only pattern that satisfies INV-26 structurally rather than by policy — the payload is composed on the shop's machine from values that never reach our network — and it needs no account, no queue, no second origin, and no second production client. It is also the only pattern testable on a bench without a partner's cooperation.
- FR-15 (**thermal-printer reality and the derived width**): 203 dpi is the common resolution and is the binding case; one dot is 25.4 / 203 = 0.1251 mm. The symbol's printed extent is its module count plus the 4-module quiet zone on each side. The measured floor is roughly **1.6 device pixels per module** (`sticker_qr.ex:18-19`), which a thermal head cannot render because it places whole dots, so the scale is rounded **up** to the next integer. The derivation, for the common-case payload URL — a 40-character code — in byte mode:

  ```
  dot pitch at 203 dpi            25.4 / 203        = 0.1251 mm
  symbol, ECC medium              37 modules  + 8 quiet =  45 modules

  at 2 dots/module (smallest integer at or above the 1.6 floor)
    ECC medium    45 x 2   =  90 dots  ->  11.3 mm
  at 3 dots/module (the working scale)
    ECC medium    45 x 3   = 135 dots  ->  16.9 mm
  ```

  The **derived arithmetic floor is 11.3 mm** including the quiet zone, at 2 dots per module; the working scale is **3 dots per module**, 16.9 mm at ECC medium, because the 1.6 figure was measured decoding a backlit screen and thermal paper is a lower-contrast, damage-prone medium. Both are common-case, provisional figures — the shipped scale is `DOS-M10-004`'s, one integer step above its measured cliff — and a manual-grade tail (FR-11) can lengthen the code to 74 characters, raising the symbol version and every derived figure.
- FR-16: The module count is read from the encoder's returned value and the width computed from it at print time. It is never hardcoded. The payload length depends on the host name and on the per-sticker manual-grade tail, and the ECC level is a print decision, so any of the three can move the symbol to the next version and change every dimension in FR-15. A test asserts the computed printed width for the production host's common-case payload at the chosen ECC level and fails if the symbol version moves.
- FR-17: Scaling is by integer dot multiples only. A fractional or non-uniform scale produces modules of unequal width, which is a decode failure that looks like a print-quality problem and gets diagnosed as one for a week. The quiet zone is unprinted paper and no template element — rule, border, text, logo, or fold mark — may fall within 4 modules of the symbol on any side. The symbol block occupies a full-width line of its own.
- FR-18 (paper fit): The template is verified against 58 mm stock (typically 384 printable dots, ~48 mm) and 80 mm stock (typically 576 dots, ~72 mm). At 3 dots per module the common-case symbol consumes 135 of 384 dots on the narrower stock, and the densest manual-grade symbol 147, so both fit; the printable dot count is read from the printer's own capability where available and asserted in the fixture where not.
- FR-19 (**the fallback ladder**, in order, each rung entered only on the stated condition):
  1. **Native QR command.** Entered when the printer's model has a recorded, bench-verified `GS ( k` result. Verified by a probe response where the firmware answers one, and by a recorded model allowlist where it does not.
  2. **Raster bitmap.** Entered when the native command is absent, unverified, or returned an error, and the printer accepts raster image data. This is the rung that carries most real hardware.
  3. **Text only.** Entered when the printer cannot render an image at all — no raster support, image commands rejected, or a device the shop drives through a text-only spooler. The receipt prints the **full sticker code** — 40 characters in the common case, up to 74 with a manual-grade tail — unseparated and in the exact form the decoder accepts, plus the scan URL in a typeable form. Grouping the characters for readability is prohibited: it would mean the printed text is not what the decoder accepts, which is a trap for exactly the fallback the printing exists to serve (`sticker_qr.ex:29-31`). The code is printed in a font wide enough for the line to hold the common-case 40 characters without wrapping where the paper allows, and where it cannot, it wraps at a fixed documented column with no hyphen and no inserted character.
  4. **Print nothing about the sticker.** Entered when there is no code to print — encoding refused, resolution refused, or the value set incomplete. The receipt carries no sticker block at all and the advisor sees the refusal at the terminal. A partial or degraded symbol is never printed, on the same reasoning the browser hook already applies: a broken symbol next to the text "looks scannable" (`qr_symbol.js:46-48`), and a customer who trusts it discovers the failure months later in a parking lot.
- FR-20 (**the printed claim block**): The print template is fixed, versioned, and lint-tested. Where the receipt has room it carries, in print: the estimate framing with a confidence label; the basis sentence naming whose interval this is and that a maker's schedule would replace it (ADR-0005); the INV-11 status; the source or `Source unavailable`; `Exact configuration not verified` where the build was not pinned exactly; the oil-life-monitor deference line where INV-14 applies; and the verbatim no-affiliation statement. If the receipt cannot carry them, it prints the symbol and the code and **nothing else** — no interval, no due date, no grade claim — because there is no tooltip, details view, or provenance panel on thermal paper.
- FR-21 (INV-5, INV-21, INV-25): The printed block MUST NOT imply that a record is held, recoverable, or synchronized. The prohibited terms are build-failing: `saved to your account`, `synced`, `backed up`, `restore your`, `restore from`, `we'll remember`, `best oil`, `guaranteed`, `warranty safe`, `manufacturer approved`, `API approved`, `recommended by`, `works with every`. INV-21's mandated `stored in this browser` framing does not apply on paper, where there is no browser and no stored record; the replacement wording is an **open question requiring a ratified addition to INV-21**, not something this issue improvises.
- FR-22 (FACTUAL_USE_AND_MARKS_POLICY): Our printed block is self-contained, carries no third-party logo, certification mark, or trade dress, and renders vehicle and product names as plain text. We do not control the rest of the receipt, which is why the no-affiliation statement travels inside our block rather than being assumed from context.
- FR-23 (INV-22, INV-4): The resolution call is served over HTTPS from the existing origin, is rate-limited by a key that is not derived from any shop or customer value, and its parameters are covered by the existing log-scrubbing configuration. A test asserts that a full shop workflow produces no log line containing any personal field.
- FR-24 (copy lint): The copy-lint scan surface is extended to cover every shop-facing and print-template module wherever it lives, and the mandated-string assertions are extended to the print block. A print template placed outside `lib/digital_oil_sticker_web/` currently escapes every prohibited-term and mandated-string assertion; the gate must fail on unlinted print copy before any such module exists.

## Technical implementation contract

### Components and ownership boundaries

- **The packaged codec** owns sticker-code encoding, QR generation, and the frozen grade and base-stock tables. It has no network client, enforced by AC-2's dependency allowlist and network-API scan — a package that can make a request will eventually make one.
- **The command builder** owns ESC/POS assembly: the native QR sequence, the raster path, the text-only path, the rung-selection logic, the printer capability record, and byte-level escaping of any value reaching a command stream.
- **The print template** owns layout, the claim block, and the width computation from the encoder's returned module count. It owns nothing about transport.
- **The resolution adapter** owns the mapping between a shop's selection and a validated selector, and owns treating the `{:ok, %Result{}}` / `status: :unsupported` shape as a refusal. It never widens the selector's closed vocabulary.
- **`DigitalOilSticker.Catalog`** is unchanged and unaware of this feature; its facade is already transport-agnostic and stays that way. Not owned here: the catalog implementation, the hosted transport, the browser app's own sticker rendering, and the revision and ADR that gate the issue.

### Data and persistence

- No new table, no new repo, no migration. The deployment keeps exactly one Ecto repo, `CatalogRepo`, opened read-only (ADR-0004 §Decision 4), and the existing repo-list release gate is the enforcement.
- No print queue, retry buffer, delivery receipt, idempotency record, per-shop configuration row, or submission log exists; a failed print returns to the caller synchronously — a retry buffer holding a customer's service record is the hidden server-side storage INV-19 names.
- The printer capability record is static repository data keyed by printer model — it contains no shop identifier and no vehicle data, and it is committed, not collected.
- Personal values exist only inside the shop's own system and on the paper the customer takes away.

### Interfaces and events

- **Local:** `encode(sticker) -> code | refusal`, `symbol(payload, ecc) -> modules + raster | refusal`, `commands(symbol, capability) -> bytes | refusal`. Every one returns a named refusal rather than raising, because the caller is a point-of-sale terminal mid-transaction.
- **Network:** one resolution call — `DOS-M10-002`'s impersonal MCP lane over `DOS-M10-001`'s contract — request carrying `year`, `make`, `model`, engine descriptor, and nothing else; response carrying `configuration_key`, INV-11 `status`, `data_version`, and qualifier codes. The versioned wire mapping for atom statuses and qualifier codes is those cards' to define; this issue consumes it and adds no field. The ambiguous result carries its candidates as an explicit list with the fields that distinguish them: a normal response, not an error code.
- The printer capability probe, where firmware supports one, is a local interface; its result is recorded per model and never inferred across models.

### Failure and recovery behavior

- **Ambiguous vehicle** (the shipped catalog returns seven configurations for a 2019 Toyota Camry, two with a null trim): the shop's UI must present the choice. No fallback picks one. If the shop's workflow cannot present a choice, the correct outcome is no sticker.
- **Unknown configuration**: arrives as success at the facade with `status: :unsupported`. The adapter converts it to a refusal at the boundary and a test proves the print path is unreachable from that shape.
- **Catalog unavailable or rate-limited**: no interval, no date, no grade claim printed; the advisor sees a retry state. A degraded print is prohibited (INV-7).
- **Encode refused** (`unknown_base_stock`, `manual_grade_too_long`, `date_out_of_range`, `odometer_out_of_range`, `missing_configuration_key`): no code exists, so rung 4 applies — nothing about the sticker is printed and the advisor is told which field was refused and what is accepted.
- **Native QR command silently ignored**: the receipt prints with a blank space where the symbol should be. This is the worst failure in the feature because it produces a plausible-looking receipt and no error. Mitigation: the native rung is entered only for bench-verified models, and the verification includes a scan of the physical output, not a check of the return code.
- **Printer out of paper, cover open, or offline mid-job**: the transaction has already happened and the customer is waiting. The reprint path re-runs the whole composition from the same input values and produces a byte-identical code, because the codec is a pure function — there is nothing to look up and nothing to have lost.
- **Head dot failure**: a dead thermal-head element strikes a QR as a straight white stripe. `DOS-M10-004` characterizes the tolerance; the printed code beneath the symbol is the recovery path.
- **Paper fading**: thermal paper darkens in a hot car and loses contrast; not recoverable, not mitigated here — why label stock is excluded and recorded as a risk.

### Security and privacy

- The privacy property is structural: the values are composed on the shop's machine, so there is no request to filter, no log to scrub, and no assign to leak. A filtered payload is a policy; a payload that never existed is a guarantee, and this repository's other privacy properties are all of the second kind.
- The resolution call is impersonal by the same construction the browser uses — the closed vocabulary in `catalog/selector.ex` structurally cannot hold free text, and this issue does not widen it.
- The sticker code is not a secret: anyone who can read it can read the values (`sticker_code.ex:17-21`). It is printed on a receipt and taped to a window, and the design is correct only because the payload was constrained to what a person would tape to their own window. Nothing here may grow it.
- A free-text grade crossing into a printer command stream is an injection surface. Length, character-class, and escaping rules are enforced in the command builder and covered by fuzz input.
- No shop credential exists in this issue's scope. If the revision introduces one, it is an account and is named as one; a per-shop key plus a stream of submissions reconstructs customer service history, which is what INV-3's closing sentence forbids. No third-party runtime dependency and no third-party API key (ADR-0004 §Secrets); the QR encoder is the already-vendored MIT library, carried in with its provenance record.

### Accessibility and performance

- The print block is not an accessible surface and cannot be made one; the accessibility obligation lands on the shop-terminal states — refusal, ambiguity, retry — which carry accessible names, keyboard operability, visible focus, and live-region announcement where they change asynchronously.
- The printed code beneath the symbol is the low-vision and damaged-symbol fallback and is set at a size readable without magnification on both paper widths. The scan URL opens the browser app, and everything the customer does from there inherits the app's existing accessibility bar.
- Encoding and symbol generation are pure local computation on inputs of fixed small size; the only network cost is the single resolution call, subject to the existing catalog query budget. The print path must not add a second round trip — a service advisor with a customer at the counter is the performance context that matters.

## UX and content states

- **Ambiguous vehicle**: the shop's UI lists the candidate builds with the fields that distinguish them and requires a choice. Copy states that the exact build was not determined from the year, make, and model alone. Prohibited: a default selection, a pre-highlighted "most likely" option, or language implying the choice is cosmetic.
- **Vehicle outside the window or outside covered classes**: states plainly that this vehicle is not covered, names which condition failed, and offers no sticker. It must not read as a temporary outage.
- **No engine oil service** (`:not_applicable`): prints and displays `Engine oil service not applicable`, with no interval and no grade. **Identity only**: the sticker prints with the recorded values and the QR; the interval area carries `Source unavailable` rather than a number, and `Exact configuration not verified` where the build was not pinned.
- **Encode refused**: names the field and the accepted values — for an unrecognized base stock, the four accepted values; for an over-length manual grade, the byte limit. It never offers to truncate. **Resolution unavailable**: an explicit retry state at the terminal, never a printed best-effort sticker (INV-7).
- **Printer produced no symbol**: the advisor is told the receipt has no symbol and given the reprint path. Prohibited: reporting success because the bytes were accepted.
- **The printed block itself**: the FR-20 claim set in full, and no wording implying a record is held for the customer anywhere but on the paper and in their own browser.

## Acceptance criteria

- [ ] AC-1: A wire capture over a full shop workflow — resolve, encode, render, print, reprint — contains no VIN, odometer value, service date, note, custom vehicle name, record identifier, or free-text grade in any request path, query string, body, header, or cookie reaching any project-operated origin.
- [ ] AC-2: The package build pins a dependency allowlist over its transitive closure and statically scans both for network APIs (`fetch`, `XMLHttpRequest`, `WebSocket`, sockets, HTTP modules); a dependency outside the allowlist or a network-API reference fails the build.
- [ ] AC-3: The packaged codec round-trips all 18 vectors in `conformance/fixtures/sticker-code-vectors.json`, and a mutation of any single vector fails the build.
- [ ] AC-4: A test asserts the package's base-stock indices match the frozen module order and **not** the catalog's alphabetical order; a fixture built from a catalog query fails.
- [ ] AC-5: Resolving a 2019 Toyota Camry from year, make, and model alone returns an ambiguous result listing the seven candidate configurations; no code path selects one, and no result is scored or ranked.

- [ ] AC-7: A 1996 model year is refused with `out_of_window` naming the 1997–2026 bounds; a medium-duty truck and a motorcycle are each refused with `class_out_of_scope`. None is normalized into a nearest in-window or nearest-class row.

- [ ] AC-12: The computed printed width for the production host's common-case payload at the specified ECC level equals the FR-15 derivation to within one dot, asserted from the encoder's returned module count — a manual-grade width from the returned count alone, never a fixed figure; a change that moves the symbol version fails the test rather than silently changing the artwork.

- [ ] AC-17: With no code available, the receipt contains no sticker block at all: no empty frame, no placeholder, no partial symbol. A scan of the physical output finds nothing that presents itself as scannable.
- [ ] AC-18: The print template renders the estimate framing with a confidence label, the ADR-0005 basis sentence, the INV-11 status, the source or `Source unavailable`, `Exact configuration not verified` where applicable, the INV-14 deference line where applicable, and the verbatim no-affiliation statement; and where the paper cannot carry them, the block reduces to symbol plus code with no interval, date, or grade claim.

## Test plan

### Automated

- Vector conformance for the packaged codec across all 18 vectors, plus a mutation test proving the suite fails on a changed vector; and frozen-table assertions that grade and base-stock indices match the module order, with a fixture derived from a catalog query failing.
- Refusal-path suite over the complete encode error set — `missing_configuration_key`, `invalid_configuration_key`, `date_out_of_range`, `invalid_date`, `odometer_out_of_range`, `manual_grade_too_long`, `invalid_grade`, `unknown_base_stock`, `invalid_base_stock` — asserting each produces a named terminal state and no printed sticker block.
- Resolution-adapter tests: single match, seven-candidate ambiguity, `:unsupported` inside a success tuple, out-of-window year, out-of-scope class, `:not_applicable` BEV, `:rate_limited`, `:catalog_unavailable`, `:stale_cursor`; plus an unreachability test proving the print path cannot be entered from the `{:ok, %Result{}}` / `status: :unsupported` shape.
- Width derivation test computing the printed width from the encoder's returned module count for the production host's common-case payload at the specified ECC level, asserted against the FR-15 numbers to within one dot, and failing if the symbol version moves. Integer-scale and quiet-zone template lint.
- Command-builder golden-byte tests for the native, raster, and text rungs; rung-selection tests driven by recorded capability records; and an escaping and fuzz suite over the manual-grade tail against the command stream.
- Text-rung round-trip: parse the printed code string back through the decoder and assert sticker equality; assert no separator, hyphen, or grouping is present.
- Wire-capture assertion over a full workflow for the absence of every personal field, paired with a log scan over every configured sink; repo-list, schema, and no-new-table assertions; asset scan for third-party marks; and copy-lint extension tests including planted prohibited terms in a print template.

### Manual/device matrix

On real hardware, because none of this is provable in a harness. Minimum matrix: one mainstream 203 dpi thermal printer with documented native QR support; one 203 dpi unit without it; one clone unit with undocumented firmware; one text-only or spooler-driven device. Each on 58 mm and 80 mm stock where supported.

- Density sweeps, scan-success, fold, scuff, and aging runs are `DOS-M10-004`'s and are not re-run here; this matrix consumes its `SCAN_MATRIX.md` cells (AC-13).
- Exercise the ladder: disable the native command on a printer that supports it and confirm the raster fallback; drive a text-only device and confirm the code prints unseparated and round-trips when typed.
- Pull the paper mid-job, open the cover mid-job, and power-cycle mid-job. Confirm the reprint produces a byte-identical code and that no partial symbol reaches the customer.
- Run the ambiguous-vehicle path with a 2019 Camry end to end at the terminal, as a service advisor with a customer waiting, and time it. If a human cannot resolve the ambiguity in that context, that is a finding about the feature, not about the tester.
- Read the printed block cold, as a customer who has never seen the product, and check that nothing on it suggests the shop or this product is holding their record.

## Rollout and rollback

Nothing ships before the constitution revision and `ADR-0006` are accepted and the source-rights re-review is complete. Until then this issue's only permitted work is the part that changes no product behavior: the copy-lint scan-surface extension and the pattern evaluation document. The paper measurement is `DOS-M10-004`'s, and this issue's print specification waits for its `SCAN_MATRIX.md` record — specifying a width before measuring paper would be the guess that Rule 4 of change control names as a violation even when the guess turns out right.

After the gates clear, roll out in the order that keeps the riskiest rung last. Ship the paste-in browser handoff first, because it needs no integration and establishes the print template against real paper. Then the packaged codec with the raster rung only, so the fallback path is the one that gets the first mileage. Then the native QR rung, per printer model, entered only from the bench-verified capability record. A model is added to that record by scanning physical output, never by reading a datasheet.

Rollback is per-rung and cheap. Removing a model from the capability record demotes it to raster on the next print with no data migration, because there is no data. Two honest limits. First, receipts already printed cannot be recalled: a template defect ships to customers on paper and stays there, which is why the template lint and the claim block are gates rather than reviews. Second, the packaged codec runs inside systems we do not control, so a defect in it is fixed at whatever pace the shops update — which is an argument for the package doing as little as possible and for the vector suite being the thing that gates its release.

Blocked by `DOS-M10-004`, whose `SCAN_MATRIX.md` supplies the measured print floor, per-medium ECC decision, and stroke width every print dimension here is provisional without; in return this card supplies the dimensioned template draft its protocol needs.

Blocked by `DOS-M09-004`, because the resolution call is a caller of the catalog facade and its INV-11 statuses and qualifier codes are the vocabulary the print block renders. Blocked by `DOS-M09-006` and `DOS-M09-007`, because the payload URL's host determines the symbol version and therefore every dimension in FR-15, and because the transport and log-scrubbing guarantees this issue asserts are theirs.

Blocks the milestone's partner-pilot work, referenced by role because no pilot card is issued yet: no shop may receive the package before the print contract is measured and the ladder is verified on real hardware, because a pilot's failures land on a customer's paper where nothing can be revised. It supplies the print contract and capability record that any later output channel is measured against.

## Risks, decisions, and open questions

- Risk (INV-26): the naive design — a webhook accepting a service record and returning an image — is the one every integrator will propose, and it is a direct violation. Mitigation: the local/network split is FR-2 and the absence of a personal field on the wire is AC-1, so the violation fails a test rather than a review.
- Risk: a thermal receipt is not a windshield sticker. Thermal coatings darken with heat and fade with time; `DOS-M10-004`'s aging runs are the evidence for the decision, not a pass. Label or synthetic stock is excluded here and is the honest follow-up.
- Risk: a printer accepts the native QR command and prints nothing, producing a receipt that looks complete. Mitigation: the native rung is entered only from a bench-verified capability record whose evidence is a scan of physical output, never a return code or a datasheet.
- Risk: the 1.6-device-pixels-per-module floor was measured decoding a backlit screen. Paper is lower contrast, and a worn head or a low density setting makes it worse. Mitigation: AC-13 ties the shipped scale to `DOS-M10-004`'s measured cliff, not the screen figure.
- Risk: the symbol version moves when the host name, the print ECC level, or the manual-grade tail length changes, and every dimension in FR-15 moves with it. Mitigation: FR-16 and AC-12.
- Risk: a free-text grade from a DMS oil column crosses into a printer command stream. Mitigation: byte-length, character-class, and escaping rules in the command builder, with a fuzz corpus (AC-11).
- Risk: the ambiguity refusal is correct and unusable. Seven Camry configurations presented to an advisor with a customer at the counter may simply mean no sticker gets printed. Mitigation: the timed end-to-end manual run treats that as a finding about the feature. If ambiguity cannot be resolved at the counter, the honest answer is that this shop workflow is not supported, not that we pick one.
- Risk: a shop co-brands the receipt around our block, and the surrounding page implies an endorsement we do not have. Mitigation: the block is self-contained and carries the no-affiliation statement itself; we do not control the rest of the paper and do not pretend to.
- Risk: an integration channel reaches non-US shops without anyone deciding to. Initial territory is the United States and another review is required before targeted distribution elsewhere; recorded, not solved here.
- Risk: once a shop-facing surface exists, the next request is "let the customer scan it and pull their record from you." Mitigation: the Excluded section names that as prohibited in INV-19's own terms, and the codec's property is the mechanism — the code carries the values, so there is nothing to look up.
- Decision: the codec moves to the shop; the data does not move to us. This is the whole architecture of the issue and every other decision follows from it.
- Decision: the first integration target is the local command-builder driving the native QR command, with the raster path as its required fallback, because it is the only pattern that satisfies INV-26 structurally and needs no account, queue, second origin, or second production client.
- Decision: the hosted webhook is rejected as this card's pattern, with its reason and its FR-14 relation to `DOS-M10-002`'s flag-off lane recorded, so the proposal does not recur unanswered.
- Decision: scaling is integer dots only; the provisional working scale is 3 dots per module — 16.9 mm including the quiet zone at ECC medium, common case, on 203 dpi hardware — against an arithmetic floor of 11.3 mm at 2 dots, with the shipped value owned by `DOS-M10-004`'s sweep.
- Decision: a symbol that cannot be rendered leaves nothing behind, in print as in the browser. Rung 4 prints no sticker block rather than a placeholder.
- Decision: the printed code is unseparated, because grouping would mean the printed text is not what the decoder accepts.
- Open question: the replacement for INV-21's mandated `stored in this browser` framing on a surface with no browser and no stored record. This needs a ratified addition to INV-21; improvising softer wording in this ticket is the failure mode, and the print block ships without that line until it is ratified.
- Open question: whether shop authentication is required at all. If it is, it is a business-account system and must be named as one in the revision, with the argument answered that a shop key plus a submission stream does not reconstruct customer service history. No design in this issue assumes one exists.
- Open question: the print ECC level. Medium keeps the common-case symbol at 37 modules; quartile grows it to 41 but survives more damage. `DOS-M10-004`'s per-medium sweep and damage runs decide it; this issue does not guess.
- Open question: whether the packaged codec is distributed as source, as a compiled artifact, or both, and what its version and deprecation policy is once it is running in systems we cannot update. Recorded rather than assumed, because it determines how expensive a codec defect is.
